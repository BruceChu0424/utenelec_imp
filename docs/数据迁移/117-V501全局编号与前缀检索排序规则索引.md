# V501 全局编号与前缀检索排序规则索引

迁移：`V501__business_identifier_c_collation_lookup_indexes.sql`。只加四个索引，不改历史数据、唯一性、所属人规则或已应用迁移。

## 实际原因

触发器的 `TG_TABLE_NAME` 等参数带有 `C` 字符排序规则。进入全局编号/前缀保护函数后，文本参数会继承该规则。在数据库默认规则为 `en_US.utf8` 等其它值时，`normalized_identifier = 参数 COLLATE "C"` 不能使用现有默认规则的主键索引。

十万订单准备期间，实际 PostgreSQL `auto_explain` 捕获到：每条新编号查找都扫描已有约 83,580 条编号，所属关系的三次检查也扫描约 83,682 条历史关系。这会随着历史增长拖慢新建单据；降低前端请求大小不能根治。

四个匹配索引覆盖：

- 编号保留表：`normalized_identifier COLLATE "C"`。
- 编号所属关系：同规则的编号、所属域及实体 UUID。
- 前缀保留表：`normalized_prefix COLLATE "C"`。
- 前缀所属关系：同规则的前缀、所属类型和所属键。

默认规则的原主键/唯一约束全部保留。默认规则查询继续用原索引，触发器的 C 规则查询用新增索引；不改变大小写规范、历史编号永久保留或跨实体冲突判定。

## 验证

- `BusinessIdentifierCollationLookupPostgresTest` 3 项真实 PG 验证通过：V499 非空编号/前缀历史执行本迁移前后内容摘要一致，四种查询均走匹配索引，同实体旧编号兼容、他人重复编号和前缀继续拒绝。
- 同一隔离压力数据库，新增 50 张测试订单的回滚式诊断由约 1,209.9ms 降至 135.8ms；编号触发器由约 1,167.1ms 降至 94.5ms。此为局部诊断，不冒充全业务写吞吐。
- 原 8 万多行全扫描改为索引定位；诊断查询只访问 3 个缓冲块，执行约 0.062ms。未设置 `enable_seqscan=off` 强制计划。
- 100,000 订单、100,000 发货、100,000 退货和对应应收关系下，8 个并发读者完成 2,000 次逐次校验的资金汇总查询，0 错误；P95 25.90ms、P99 44.93ms，约 408.64 次/秒。该次为 V499 加本迁移同源四索引的诊断环境，不包含 HTTP、实物流转写入或正在实现的 V500 成本链。

本迁移不增加业务表。最终候选需与 V500 及其它改动一起冻结、回放和全量验证后才能发布。公司服务器尚未应用本迁移。
