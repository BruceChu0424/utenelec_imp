# ADR-094 报销链路完整化(发票登记 + 修订重提 + 事件轨迹 + 批量审批 + 打印报销单)

- 状态：已接受(2026-09-19，V608基础决策、V617前向修订；源码候选，待发布与岗位验收)
- 关联：[全局机制 §3.3](../05-架构/全局机制.md) · [实体字典 §2.4](../04-数据模型/实体字典.md) ·
  [报销详情页](../03-页面/报销详情页.md) · 迁移 [198-V608](../数据迁移/198-V608报销链路完整化.md)

## 背景与决策

V133 落地的报销域只有单据头 + 明细 + 单级审批字段，存在六个结构性缺口：
审批人看不到发票附件、驳回即终点(不能修订重提)、无正式单据号、
审批轨迹由前端时间戳合成(操作人匿名)、无后端批量审批、发票无结构化登记与查重。
本 ADR 决定补齐员工申请到财务登记付款的业务闭环(仍保持单级审批，不做多级审批流)。
法规、人工核验和归档条件分别列在[合规依据与凭证清单](../07-业务链路/员工报销合规依据与凭证清单.md)，
不能仅凭源码功能宣称已完成税务合规或电子档案验收。以下为 V608 基础决策，后续修订见本页末。

1. **报销单号**：创建时铸造 `BX + YYYYMMDD + 6 位日流水`(V279 DocNumberService 命名空间，
   终身占号)；仅缺号存量按创建日回填，已有号码原样保留，日流水兼顾终身占号且不回退。
   单号只用于识别/打印/归档，
   关联与幂等始终用 UUID。
2. **发票登记表** `expense_claim_invoices`：结构化票面要素(类型/代码/号码/开票日期/
   购销双方/不含税金额/税额/价税合计/勾稽状态)，号码形状按税务总局 2024 年第 11 号公告
   (数电票 20 位无代码；老票 8 位 + 10/12 位代码)做 CHECK 约束；
   **“代码+号码”在存活报销单间唯一索引，防止本报销域重复登记**。
   设计参照财会〔2020〕6号第三条第(三)项，但该索引不覆盖其他费用单、采购或其他账套，
   不等于完整防重复入账认证。草稿物理删除级联释放号码，
   驳回重提同单保留。DRAFT/REJECTED 且本人可登记/改/删；审批与打款侧只读核对。
3. **发票识别(OCR)**：`POST /invoices/recognize` multipart 图片 →
   `InvoiceOcrClient` 端口。**口径：不向外部付费 AI API 发送票据**，仍有本地运维与计算成本。
   接线实现为 `PaddleOcrClient`(`uten.expense-ocr.provider=paddle` 装配)：调用
   服务器**本地部署的开源 PaddleOCR 侧车**(Apache-2.0，纯 CPU，仅回环 8501；
   部署三件套在 `deploy/ocr/`，运维见 RUNBOOK §八)。侧车只输出 OCR 文本行，
   票面字段抽取由 `InvoiceTextParser`(锚点+正则，`InvoiceTextParserTest` 锁口径)
   在 Java 进程内完成——升级模型不动业务代码。未部署/未启用时识别端点明确报
   「未配置」引导手工登记，全链路仍可用。识别只是**预填建议**：
   保存前人工核对，登记校验(号码形状/金额勾稽)与 DB 约束兜底。
4. **修订重提**：`submit` 接受 DRAFT 与 REJECTED；编辑(`PUT /{id}`)限 DRAFT/REJECTED
   本人、明细整组替换。REJECTED 编辑保存后仍 REJECTED，重提时清驳回痕迹并重新通知审批人。
5. **事件表** `expense_claim_events`：创建/提交/撤回/编辑/通过/驳回/打款逐笔留痕
   (操作人姓名快照 + 备注=驳回原因)，详情审批轨迹改由事件渲染(老单由迁移回填)。
   原「ExpenseApproval 多级审批表」目标收敛为本事件表，仍不做多级。
6. **批量审批**：`approve-batch` / `reject-batch`(≤50)单事务全成全败、稳定 UUID 顺序，
   取代前端逐单循环(对齐财务订货审批 approveBatch 语义)。
7. **打印报销单**：参考《会计基础工作规范》的凭证要素生成 A4 公司内部《费用报销单》
   ——表头(单号/日期/部门/报销人/附件张数大写)、事由、明细表、
   合计(小写 + 人民币大写，银发〔1997〕393 号口径 `rmbCapital`)、付款信息、
   五格签字栏(报销人/部门负责人/财务审核/批准人/出纳，留空供手写，
   岗位分离作为本系统内控设计) + 系统操作记录区。展示单不能替代原始凭证、记账凭证或
   电子签名；附件文件份数也不能自动认定为会计凭证张数。
   pdf 包生成 + printing 系统打印对话框(与货品配件清单打印件同基建)。
8. **队列汇总**：`GET /summary`(待审批/待打款单数金额 + 本月提交/本月已打款)
   供审批页统计条；两队列分段用 actionable 红徽章口径(确实在等本页用户动手)。

## 合规依据(要点)

- 财会〔2020〕6号第三、四条：电子凭证仅电子化处理有前提；纸质打印件与电子原件必须配套。
  文件保存、原件验签、税务查验、长期档案管理是不同能力，按专题逐项验收。
- 《会计基础工作规范》第四十八条是原始凭证要素，第五十一条是记账凭证及附件张数要求，
  第五十二条涉及金额书写。不能把内部报销展示单称为自动生成的法定记账凭证。
- 税务总局2024年第11号公告：数电票20位号码与官方查验渠道；号码规则不适用于所有非发票凭证。
- 税务总局2018年第28号公告：按真实业务区分发票及其他扣除凭证；允许填写无票原因不等于可扣除。
- 岗位分离是应用内控要求：申请人不得自审、自付，审核与付款职责须按实际服务端规则验证。
  不把固定五格签字栏或固定审批级数宣称为所有企业统一法定格式。
- 财会〔2025〕9号、国家档案局令第22号及2026年财政部验证系统要求见[官方来源清单](../07-业务链路/员工报销合规依据与凭证清单.md)。

## V608基础权限与迁移

- 零新权限码：沿用 `expense:apply / approve / pay`；新路由 `/expense/:id/edit`
  由既有 `/expense/` 前缀守卫覆盖。
- V608 迁移：命名空间注册 + `claim_no` 列回填 + 两张新表 + 存量事件回填；
  reset 白名单 +2 CLEAR(`expense_claim_invoices` / `expense_claim_events`)。

## 后果

- 报销业务链：申请(含 OCR 建议) → 提交 → 材料核验与审核 → 驳回补正或批准 →
  财务登记实际付款(YF 联动) → 打印与财务归档交接。系统未接银企直连，不能据 PAID 证明银行到账。
- 打款结果(账户/费别/付款日期/操作人/关联财务单)回显至详情与审批详情。
- 识别服务未配置时全链路仍可用(手工登记)，不给假数据。

## 2026-09-19前向修订：凭证事实、财务设置与并发

V608旧字段曾把金额加总相符写成 `VERIFIED_MANUAL`，容易被误读为真实查验。V617保留旧迁移字节，
把这些旧值转为 `AMOUNTS_MATCH`，新增核验人、时间和依据字段。只有审核人员在非本人单据上显式
登记核验结果才写 `VERIFIED_MANUAL`；批准前每张已登记票据须核验通过，历史人员与税务结果不得补造。

1. **凭证适用性**：增加购买方税号，`OTHER` 支持非增值税发票号码并必填开具单位。
   OTHER自编号按规范化开具单位、代码和号码查重；标准增值税号码形状统一按代码和号码查重，
   不因改选OTHER而绕过。该机制仍只覆盖报销域。
2. **材料门槛**：提交校验明细日期与用途、扫描通过附件、票据日期与本单原件关联。
   公司可要求至少登记一张票据；未要求时，无登记票据也要有附件及备注依据，由财务判断适用性。
3. **公司业务设置**：单行 `expense_claim_settings` 保存抬头、税号、提交说明及票据要求，
   使用新增 `expense:settings` 显式授权，清业务数据时保留。不是高危部署配置入口，OCR地址仍归运维。
4. **版本与岗位**：DTO版本返回所有写入口；批量携带逐单预期版本。申请人不能自审、自付，
   审核人不能支付自己批准的报销单；队列、计数、汇总和明细使用一致范围。
5. **真实流程**：新建只保存后补材料；OCR建议需人工对照原件确认；撤回、修改和重提不能沿用
   旧轮人工核验结论。付款按钮表示登记已发生的付款，不触发银行转账。
6. **统一待办**：`/counts` 返回本人草稿/待修订及本人可处理的待审/待付；红徽章统一注册累加，
   通知阅读状态不改变业务待办。通过、驳回、付款的通知按业务轮次接力。
7. **打印计量**：区分电子文件份数、登记票据份数与实际纸张张数，保留真实全量事件。
   公司抬头目前读实时设置，未冻结为单据快照；财务保留正式归档版本。
8. **付款证据**：独立附件owner `EXPENSE_PAYMENT_PROOF`，仅待付款且满足岗位回避的出纳维护。
   付款前须有扫描通过的银行回单或现金签收凭据；付款后冻结，原申请凭证始终按原状态只读。

详细结构见[V617说明](../数据迁移/207-V617报销凭证核验与财务设置.md)，操作见[报销 SOP](../07-业务链路/员工报销全链路-SOP.md)。
候选测试、服务器只读基线、OCR启用和岗位验收分别记录在[验收专题](../99-项目治理/2026-09-19-员工报销全链路验收.md)。


## 2026-09-20 图片识别资源门禁

OCR 方法与入口都要求 `expense:apply`。图片在进入侧车前与附件共用 `ImageDimensionGuard`，仅解析头部，拒绝超过 4000 万像素、任一边超过 30000 像素、零尺寸或无法确认尺寸的 PNG/JPEG/WebP。检查不分配解码后的像素数组。并发槽位在读取上传字节前取得，拒绝、读取异常、引擎异常都释放槽位；侧车自己的相同边界继续作为下一层校验。回归覆盖伪装 MIME、截断头、窄长超边界图片、无符号溢出尺寸、真实合法图片与缺少申请权限。
