# ADR-088 分析过的订单行离开待排产；关联订单只读货品清单另立一页

- 日期：2026-09-15
- 状态：已决策；后端 / Flutter 为本地源码候选，单元与契约测试通过。
  真实多岗位 UAT、切账号越权走查、部署回读未完成，生产 **NO-GO**。
- 迁移：**无**。不新增权限码，不新增表/列，不改 `chain_status` 派生。
  新只读页复用既有 `production_material_analysis:view`。
- 取代范围：[V545](../数据迁移/README.md) 确立的「待排产缺口 = 剩余未排量」这一条
  **仅在调度台待排产列表这一个读模型上**再扣一层「活动分析已承接量」。
  `SalesOrderChainSql` 的链路口径、`chain_status` 派生、销售进度 PENDING、
  「从订单带明细」`orderLines` 一律不变。
- 相关：[生产调度工作台](../03-页面/生产调度工作台.md)、
  [生产物料分析页](../03-页面/生产物料分析页.md)、

## 一、问题

用户口径(2026-09-15)：

> 生产调度与进度页面，只要分析过的，待排产中就不显示，都在进行中显示。
> 待排产中批量，就是多个一起分析；在进行中也是汇总成一个的。
> 双击进入物料分析页面，在顶部的卡片里面加上关联销售订单，然后点订单编号还能查看订单货品列表。
> 记住这个页面是自己新写的页面，不能是去到销售订单页面，不然很多比如加个啥的都能看到；
> 就是你自己重新设置个页面，点击编号跳转到这个，就是个表格显示，下面汇总。

现状与诉求的差距只有一条：**做过物料分析的订单行仍然留在「待排产」**。
调度员每天要在一张越滚越长的表里重新分辨「这行我昨天已经分析过了」。

「批量一起分析」与「进行中汇总成一条」两条诉求**现状已满足**，本 ADR 只做确认与钉死：

- 批量：待排产表是受控多选(跨页保留)，右下角「联合分析所选 N 项」一次开一张联合分析；
- 汇总：`v_production_execution_workbench_roots` 的 `analysis_roots` CTE 主键就是
  `production_material_analyses.id`，**一张分析恒一行**，与它下面挂几条订单行、几张计划、
  几个执行段无关；由分析下达出来的计划不会另外产生 PLAN 根(`legacy_roots` 只收
  `material_analysis_id IS NULL` 的历史计划)。

## 二、真正的难点：字面照做会丢量

`SalesOrderChainSql.unplannedQtySql` 是全站唯一的链路口径：

```
剩余未排量 = 未交付 − 预留 − max(已排产 − 已完工, 0)
```

它**不减物料分析的 requested_qty**。因为分析在下达成计划之前不写 `planned_qty`，
所以「订 100、分析里只放了 40」时，待排产那一行的缺口列今天显示的是 **100，不是 60**。

于是「只要分析过就整行踢掉」的字面实现会让这 100 全部消失，而「进行中」只表达 40。
同源的第二个触发器更高频：**改单增量**。`SalesOrderService` 与 `ChainNoticeService`
的通知正文都承诺「剩余缺口自动回到调度待排产列表」——订 100 改 150 后，
只要该行还挂着一张活动分析，新增的 50 就永远回不去。

## 三、决策

### 3.1 按量扣减，不按行踢

调度台待排产列表引入第二个口径(**只在这一个读模型上**)：

```
活动分析已承接量 = Σ GREATEST(requested_qty − approved_qty − root_fulfilled_qty, 0)
                   over 该订单行上 status <> 'CANCELLED' 的未删除分析行

待排产缺口 = GREATEST(剩余未排量 − 活动分析已承接量, 0)
```

**为什么减掉 approved 与 root_fulfilled，却保留 submitted。** 分析行有四个量桶
(V478 的 CHECK：`submitted + approved + root_fulfilled ≤ requested`)，其中两桶
已经落到订单行的数量列上，再算一次就是两段双扣：

- `approved_qty` —— 计划审核时 `ProductionPlanService.applyAllocation` 在**同一事务**里
  写 `sales_order_items.planned_qty`，已被链路口径的 `max(planned − produced, 0)` 扣过；
- `root_fulfilled_qty` —— 根产品供给交接时 `MaterialAnalysisRootSupplyService` 同步写
  `sales_order_items.reserved_qty`，已被链路口径的 `− reserved` 扣过。

反过来 `submitted_qty`(已提交草稿计划、尚未审核) **不能**减：草稿计划不写 `planned_qty`
(`create`/`update` 全程不碰该列，唯一加点是 `approve` 路径)，减了就等于这批量两段都不表达。

于是 covered = `submitted + 未下达余量`，正好是「分析已经接走、但订单行数量列上还看不见」的那部分。
审核那一刻 `approved += X` 与 `planned_qty += X` 同事务发生，covered 少 X、链路剩余也少 X，
两边对冲，待排产缺口不跳变。

- 全量承接的行缺口归零 → 自动离开「待排产」，改在「进行中」按分析批次汇总成一行。
  日常勾选默认量就是整个缺口，所以**用户看到的就是「分析过的不再出现」**。
- 部分承接的行按**未被承接的残量**留下，量不会凭空消失；改单增量、让单释放同理。
- 分析状态白名单与「进行中」根视图**同源**(`analysis_roots` 的 `status <> 'CANCELLED'`，V487)。
  两侧收录同一批分析，才谈得上：

  > **待排产缺口 + 进行中已承接量 ≈ 链路剩余未排量**

  写成 `≈` 而不是恒等式，是因为两处已知例外(见 §5)。这条口径由
  `ProductionScheduleNeedTest` 以源码文本断言钉死：少减 `submitted`、多减一项、
  或把状态集合改回 `IN ('ACTIVE','PARTIALLY_PLANNED')` 都会红。
- `CANCELLED` 被排除：分析一取消，承接量归零，该行自动回到「待排产」；
  「进行中」根视图同时踢掉它。往返闭环成立。
- 取数用的 `latest_analysis` LATERAL 准入谓词与 covered **逐项同源**，
  保证「已分析 > 0」的行一定有一张可点开的分析——否则表上写「双击可直达」、
  双击却弹「还没有分析承接」。该 LATERAL 是纯投影，只挂在取数查询上；
  COUNT / facets / 工作台徽标三条只算数的 SQL 共用不含它的 WHERE。

列表 / facets / 工作台徽标三处统一走 `pendingFiltersBase`，
徽标数字与点进去看到的行数不可能漂移。

### 3.2 待排产表删两列、加一列

删「可生产量」「预计可生产」。理由：齐套是**分析批次**的事实；本段的行现在只代表
「还没被任何分析承接的残量」，在这里显示齐套率说的是另一笔量。
改挂「已分析」列指路——有数就去「进行中」看那张分析。
`materialAnalysisId` / `readyNowQty` / `readinessRatio` 等投影字段保留(wire 契约与
`ProductionMaterialAnalysisWorkflowContractTest` 都依赖其存在)，但语义变了：
它们描述的是**同一订单行上已被承接的那一部分**。

顺带修掉一个既有缺陷：`readiness_ratio` 的 CASE 在 `latest_analysis` 未命中时，
`NULL > 0` 求值为 NULL 落进 `ELSE 1`，对没有分析的行伪造出 100% 齐套。补 NULL 守卫。

### 3.3 「进行中」补权限引导

待排产读 `production_plan:view`，进行中读 `production_execution:overview`
并按 `root.owner_employee_id` 做对象级范围。改口径后，「看不见进行中」就等于
「那批量从这个账号的世界里消失」。因此：

- 缺 `production_execution:overview` 时，分段渲染权限引导占位而不是撞 403 错误面板；
- **遗留风险明写**：纯调度岗位需补授 `production_execution:overview`；
  跨制单人查看同事建的分析仍须 `production_plan:view:all`。
  这是权限配置问题，不是代码可以单方面消解的。

### 3.4 关联订单另立只读页，不复用销售订单详情

物料分析顶部卡片新增「关联销售订单」chip 组，点订单编号进
`/production/material-analyses/:id/sales-orders/:orderId`。

**不跳销售订单详情**是明确决策：销售订单详情是业务单据页，带编辑 / 审核 / 财务 / 价格
一整套动作与字段；计划员从物料分析点过去只是要核对「这张单订了些什么货、还差多少要生产」。
所以新页：

- 权限只要 `production_material_analysis:view`，**不要求 `sales_order:view`**；
- 作为交换，服务端过**两道闸**：
  ① 先按物料分析的对象级范围判定调用方能不能读这张分析
  (`MaterialAnalysisService.requireReadableAnalysis`，按 `maker_id` 隔离，
  跨制单人需 `production_plan:view:all`)；
  ② 再反查 `orderId` 是否确实被这张分析引用。
  **只做 ② 是越权**：那只挡住「换订单」，没挡住「换分析」——拿同事的 analysisId
  就能读到自己无权查看的销售订单明细，而本端点刻意不要求 `sales_order:view`。
  门禁不过时一条 SQL 都不发，并统一吐 404 不吐 403；
- **纯数量口径，不返回任何单价 / 金额 / 折扣**。单头备注同样不返回：
  销售备注是自由文本，现实中常写折扣与付款条件；
- 全页零写入动作。读取会记一条 `view_sales_order_detail` / `sales_orders` 审计
  (与销售侧详情查看同一 action/targetType 对)——这是一次跨模块读，必须可追溯。

chip 的去重口径是**本张分析的来源行**(排除 `MAKE_COMPONENT` / `SUBCONTRACT_MAKE`
子层锚点行)。注意与「进行中」表那列「关联订单」不同源：后者(V487 `sales_order_rollup`)
还并进了执行段的销售分摊，跨分摊 / 让单会带进不属于本分析来源的订单，
**两处数字可以不相等，不是 bug**。

## 四、被否掉的方案

1. **整行踢出(`AND latest_analysis.analysis_id IS NULL`)**。改动最小，但见 §二：
   部分覆盖与改单增量会丢量，且兜底入口(空白分析页 + 候选选择器)本身也不减分析承接量，
   很容易对同一行开出第二张活动分析——跨分析没有唯一约束拦得住。
2. **把承接量并进 `chain_status` 派生**。会反转全站唯一的链路口径，
   波及销售进度、断链扫描、报表与物化视图。本 ADR 刻意把新口径限制在一个读模型内。
3. **新页直接复用 `GET /production/schedule/order-lines`**。该端点对未审核 / 未财务确认
   的订单直接抛 BUSINESS，明细还被 `chain_status BETWEEN 1 AND 8` 过滤，
   与「看这张单的完整货品清单」语义不符；权限也是 `production_plan:view`，与入口页不同源。

## 五、已知例外(不变量写成 `≈` 的原因)

1. **同一订单行挂两张活动分析**。`sales-candidates` 的可选量只扣草稿计划、
   不扣已有活动分析的承接量；唯一索引 `uq_production_material_analysis_item_source`
   只禁同一张分析内重复，跨分析不拦。两张分析各承接 X 时，
   `GREATEST(..., 0)` 会把超额承接直接压成 0，该行提前离开待排产。
   要真正消掉，得在 `salesCandidates` 的可选量里也扣承接量，或在 preview 落库前
   按订单行做承接上限校验——本 ADR 不做，只记录。
2. **`COMPLETED` 分析的残量**。状态集合已与根视图对齐，但 `COMPLETED` 的判定
   (V490 `fn_material_analysis_fulfillment_status`) 看的是实际入库量，
   理论上仍可能留下 `requested − approved − root_fulfilled > 0` 的尾数。
   此时两段都会表达它，方向是重复显示而不是丢失。

## 六、验收缺口

- `UTEN_RUN_DB_TESTS` 门控的真实 PostgreSQL 用例**尚未覆盖**新口径与新端点：
  当前证据是源码文本契约测试 + 替身 EntityManager 的行为测试，
  真库上「全量承接消失 / 部分承接留残量 / 取消后回流」三态待补。
- 切账号越权走查(计划员 / 纯调度 / 跨制单人)未做。
