## 三、发布链事故：跨境上传把 Simple Release 打穿两次

v1.0.0 至 v1.2.0 全程都是 10 分钟出头，本次同样的产物传了一个多小时。**构建与签名仍是 8 分钟，慢的全在传 OSS。**

- 第一次(tag 触发，run 35589761594)：`SHA256SUMS` 与签名在开跑 3 分钟后就传完了，此后**两小时零对象落地**，
  最后被 job 的 `timeout-minutes: 120` 砍掉。根因是 `oss2.Bucket` 没设超时，单次 `put_object` 传 113MB 的服务端 JAR
  在卡死的连接上无限空转，既不报错也不重试。
- 第二次(修了超时 + 大文件分片，run 35601964351)：迁移器 JAR(5.9MB)顺利落地，服务端 JAR 分片传了一小时还没完，
  眼看装不进 120 分钟，主动取消。当天实测吞吐只有几十 KB/s，是平时的十分之一量级。
- 第三次(run 35610146636，**成功，1h23m25s**)：服务端 JAR 分片传了 50 分钟落地，其余近两千个 Flutter Web 小文件
  16 线程并发传完，`LATEST.txt` 指向 v1.3.0。

发布脚本相应改了三处(`.github/workflows/simple-release.yml`)：

1. `oss2.Bucket(..., connect_timeout=60)`——oss2 里这个值同时作用于连接与读写，卡住就报错走重试，不再空转。
2. 超过 8MB 的文件走 `oss2.resumable_upload`(4MB 一片、4 线程)，每片独立重试，断链只重传该片。
3. 小文件 16 线程并发上传且**不再逐个整体回读**：上传带 `Content-MD5`，OSS 在收件时就拒掉损坏的体；
   整体内容完整性由 Ed25519 已签名的 `SHA256SUMS` 保证——更新器下载后逐文件核对，那才是权威闸门。
   原先「传一遍再整体下回来比一遍」在近两千个小文件上等于把往返和流量翻倍。
4. job 超时 120 → 330 分钟：宁可慢慢传完，不要传到一半被砍。

因为发布脚本本身要随版本走，`v1.3.0` 这个 tag 在发布成功前被移动过两次(前两次都没有发布产物，移动是安全的)，
最终指向 `99fdcf5f`。前两次失败留下的残片不影响：`LATEST.txt` 全程指向 v1.2.0，服务器不会误取。
