# 官网询盘转换并发与来源回执修复

日期: 2026-09-30。来源: 全平台整改R0新增N-R0-01。状态: 实现和真实PG红绿及相关单测完成，待主线程集成；未提交、未发布、未部署。

## 当前根因

`WebsiteInquiryService.convert`原先普通读取询盘后，按旧状态决定创建客户，再把clientId/status写回。相同询盘的两次转换可以先后读到new，分别创建客户；`updateStatus`也会基于旧快照写回，可能在转换之后覆盖clientId、跟进人或备注。仅串行第二次点击返回同一客户的单测不能覆盖此问题。

JPA持久上下文还可能先前已加载该询盘。单纯加锁查询不足以证明已管理实体的字段会刷新，状态守卫必须以锁后重新读取的值作判断。

`ingest`也有首次投递的先查不存在再插入窗口。同source_id的唯一约束会阻止重复行，但并发重推可能收到唯一键错误，与“已接收过即正常返回false”的合同不同。

只锁询盘还不足以正确接入现有交接协议。DataHandover先锁员工再锁询盘，客户owner/活跃询盘assignee的V398触发器会共享锁员工。如果询盘命令先锁询盘后等待员工，可能形成倒序。因此候选在锁询盘之前共享锁最终会引用的员工；锁后发现未预锁的新跟进人则返回冲突，不持询盘锁再补员工锁。

## 写入口与修改边界

| 写入口 | 当前合同和本次处理 |
| --- | --- |
| ingest | 使用`WEBSITE-INQUIRY-SOURCE:`加原sourceId的事务咨询锁，再查重和插入。只串行同一来源；重放保留第一次原始快照，不覆盖跟进/转换结果 |
| updateStatus | 先把最终跟进人UUID复制到局部变量(认领时是当前员工，否则是预读的原跟进人)，共享锁员工，再`EntityManager.refresh(..., PESSIMISTIC_WRITE)`锁询盘并刷新。converted先拒绝；保留跟进人的请求若锁后跟进人漂移则409；检查通过才改字段 |
| convert | 先共享锁可能新建客户的owner(当前员工)，再锁行刷新。已转换且有clientId直接返回原客户；只有锁后仍未转换时创建客户、关联并写同事务审计 |
| DataHandoverService交接跟进人 | 已有员工→询盘`FOR UPDATE`锁序及`status IN ('new','following')`更新。本次不改交接模块；询盘命令遵守相同上游锁序，转换保留交接后跟进人，保留跟进人的状态请求在漂移时退出 |
| 业务清空/迁移 | 属独立受控维护流程，不是普通询盘命令；本次不改、不执行 |

权限不变: convert仍要求`webinquiry:convert_client`；状态更新按close/claim动作判断，带`assignToMe=true`额外要求claim。客户仍由真实`WebsiteInquiryClientAdapter`创建，归属本次转换员工；已存在询盘跟进人保留；原sourceId保留在询盘和客户来源备注。不按客户名称自动合并，不引入新的客户来源模型。员工预锁不额外要求历史跟进人在职，避免改变关闭历史询盘的资格；活跃责任仍由现有触发器校验。已转换回放也不新增必须有员工档案的限制。

无需schema修改、无需Flyway迁移号。V760由主线程死信索引候选占用，本工作没有修改它。

## 回归设计与实际结果

新增`WebsiteInquiryConcurrencyPostgresTest`使用完整`MigratedSchemaBaseline`私有数据库、真实Spring方法权限/事务代理、真实询盘仓库、真实客户adapter、数据库约束和审计。并发顺序由外部数据库锁及`pg_stat_activity.wait_event_type='Lock'`确认，不用mock安排业务调用先后。仅在回滚场景中向真实审计写入后注入失败。

1. 同询盘两个员工同时转换: 只产生一个真实客户、同一clientId返回；保留原来源、先赢转换人的客户归属、已有跟进人和备注；只一条转换业务审计。
2. 转换先赢，new/following/closed三种状态请求等待: 后来的状态变更必须冲突，不能抹clientId或复活询盘。
3. 认领先赢，转换等待: 锁后保留赢得的跟进人和备注，客户归属仍为执行转换的人。
4. 同事务已预载旧JPA实体，再等另一事务转换提交: 后续转换须刷新，不创建第二客户。
5. 真实客户和审计写入后失败: 客户、询盘变化、审计一起回滚；新重试只产生一个客户。
6. 只有查看、只有关闭、只有认领的身份不能越权转换/混合认领关闭；单独转换权限仍按原合同可办理。
7. 同sourceId两次首次投递: 一次true、一次false，原始快照不被第二份载荷改写。
8. 交接事务先锁员工，转换等待: 交接使用`FOR UPDATE NOWAIT`仍能锁询盘，证明没有询盘→员工倒序；交接后转换保留新跟进人。
9. 交接事务先锁员工，保留原跟进人的状态修改等待: 同样不反向占询盘锁；交接改了跟进人后命令返回409，交接结果及备注保留。
