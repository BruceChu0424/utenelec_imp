## 一、结论（一句话）

**客户分类 = 老库 `SystemItem` 表中 `ItemclassID = 2` 的 40 个节点（10 根、最大深 3，外贸/区域→省份→分销商）；客户主档 = `B_Client`（260 行、34 字段），通过 `B_Client.ParentID → SystemItem.ItemID`（ItemclassID=2）把每条客户挂到分类树的某个节点下。**

> ⚠️ `SystemItem` 是万能分类树表，迁移时必须用 `ItemclassID` 过滤（货品=1、客户=2、供应商=3、部门=5、模具=18…），否则会把无关数据一起迁过来。

## 二、老库表结构

### 2.1 `SystemItem`（ItemclassID=2，客户/业务区域分类，40 行）

字段同货品分类（见 [02](02-货品分类-老库溯源.md) §2.1）。ItemclassID=2 的特点：

- **10 个根节点**（`ParentID=0`），下挂省份/分销商，**有真实嵌套**（最大深 2，即根→区/省→分销商 3 层）。
- `Number`（编码）有重复：`GD`（内销轨道）在「外贸苏 2855」与「内销轨道王 3145」下各一条；`CL` 两条等。
- `Level` 不可信（同货品/模具），迁移按 parent 链重算。

## 三、数据质量风险（迁移已处理）

| 风险 | 数量/说明 | 处理策略（已落地） |
|---|---|---|
| **6 条未分组客户** | `B_Client.ParentID=0`（无分类） | `category_id` 置 NULL；前端「全部客户」视图可见 |
| `Number` 编码重复 | GD（内销轨道）两条、CL 两条 | 新库 `code` 不设 UNIQUE，定位用 `id`/`legacy_id` |
| `Level` 字段不可靠 | 全树 | 迁移按 parent 链递归重算 `level` |
| `SystemItem` 混存多类 | 7 种 ItemclassID | 迁移严格 `WHERE ItemclassID = 2` |
| 文本 GBK 编码 | 老库 `Chinese_PRC_CI_AS` | 导出走 PowerShell + .NET SqlClient 原生解码 → UTF-8 CSV |
| **地址/备注含管道符 `\|`** | 部分行（如王海东） | `export_legacy.ps1` 加 RFC4180 引号转义（字段含分隔符/引号/换行则双引号包裹） |
| `QYName` 与 `ParentID` 冗余 | 区域文本 vs 分组 | 两列都保留（`region` + `category_id`），不互相覆盖 |
