## 一、问题

安全审计把认证相关的缺口归成四类，根子是同一个：**会话、再认证和运行设置的权威状态不在服务端的一个地方**。

1. **会话只在前端。** 「自动退出登录」是浏览器里的计时器；登出不作废 access token；refresh 每次轮换都滑动续期，没有从登录时刻起算的上限。偷到 token 的人不受空闲超时约束。
2. **二次密码确认是一个「对/错」接口。** `/auth/verify-password` 无限次可试、结果不和任何操作绑定；页面各写一个密码框，有的敏感操作(授权、数据范围、远程访问、清空业务数据)根本没问。改密的旧密码和进入切换人的密码不计失败次数。
3. **临时密码弱且可预测。** 入职/补开账号的初始密码是身份证后 6 位且永不过期；重置密码允许管理员自定义；持 `account:support` 的整个行政与人力资源部都能重置任意非超管账号(包括持高危权限的账号)并拿到明文。
4. **系统设置四处各写一份。** 键、类型、默认值、取值范围、说明分散在迁移种子、服务、调用方和前端 `switch`；代码默认值与库值不一致(access TTL 15/480/15)，`impersonation_window_minutes` 代码在读却没有数据行；业务预警天数、密码最短长度、附件上限、角标刷新间隔写死在代码里；一个设置有三条写路径(单项 PUT、批量 PUT、庆典设置 PUT)。

另有几处边角：登录锁定期内仍校验真实密码(可借锁定区分密码对错)；Argon2 哈希无并发上限(登录洪峰能把 CPU 打满)并且在数据库事务里做；限流器按「账号」维度对未知账号也建桶、IP 维度没有突发上限；网站询价入口 token 强度无门槛、失败无限流；生产环境来源网段未配置时静默放行；客户/供应商按手机、银行账号筛选时值进 URL 查询串(反向代理访问日志会整行记下)。

## 二、同行做法(归纳)

- **OWASP ASVS v4 第 3 章(会话管理)**：会话状态以服务端为准；登出、改密、账号停用必须让服务端会话失效；同时有空闲超时和绝对超时；自动刷新类请求不应延长空闲计时。
- **NIST SP 800-63B §7(再认证)**：空闲超时与绝对期限分别设定，达到任一必须重新认证；敏感操作前要求重新提供认证因子。
- **GitHub「sudo mode」/ AWS 控制台敏感操作**：敏感操作前重新输入密码，得到一个短时、绑定当前会话的授权；连续失败有锁定。
- **金蝶/用友/SAP 的系统参数**：参数定义(类型、范围、默认、说明)只在产品元数据里登记一次，数据库只存企业选择的值；界面和校验都读同一份定义。

共识：会话与再认证的判定只在服务端做一次；前端只是「提示」和「弹框」；参数定义单一登记。

## 三、决策

### 3.1 服务端会话 (`auth_sessions`，V658)

- 每次登录(员工或访客)插一行，`sid` 写进 access token；`JwtAuthFilter` 在**原来查账号状态的同一条 SQL** 里连带查会话，不加往返。
- 判定只有五种：有效 / 不存在 / 已吊销 / 空闲超时 / 超过绝对期限；后四种一律 401。空闲超时时由过滤器(事务外)顺手把会话标记吊销(`idle_timeout`)；刷新事务只判定不写(非有效时整个刷新事务回滚，在里面写吊销原因是无效写)。
- 空闲以「最后一次人为请求」计：`last_seen_at` 最多 60 秒更新一次；**用户没在操作时发出的请求不更新**。判定依据是客户端声明头 `X-Uten-Automatic: 1`：前端全局采集键盘/鼠标/触摸输入(`UserActivityTracker` 挂在指针路由与硬件键盘的全局入口上，根导航器上的弹窗里的操作同样算)，距上次输入超过 30 秒才发出的请求一律由 `AutomaticRequestInterceptor` 带上此头(员工与访客两个网络客户端都装)；服务端 `AutomaticRequestPolicy` 只看这个头。
  - 为什么不按端点名单判定：第一版按「路径以 count/counts/badges… 结尾」约定判定，评审实测漏掉了服务器状态(超管工作台每 18 秒)、分来源未读数、审核心跳、物料分析页 45 秒刷新、销售统计等常驻轮询——最高权限账号只要开着工作台就永不超时；它与审计降噪的端点清单也是两套口径。按「人在不在场」判定，新增任何轮询都不需要登记，也就不会漏；反过来，人正在长时间填表(没有发请求)时，这期间的轮询算人为请求，不会把正在干活的人踢出去。
  - 为什么可以信任客户端声明：这个头只能让会话**更早**过期；持有令牌的一方随时可以发一个不带头的请求续期，伪造没有好处。服务端空闲超时防的是「人离开了、页面还开着」与「令牌泄露后被搁置」，这两种情况下诚实的客户端都会带头。请求审计是否降噪是另一个问题，仍由服务端按端点声明(审计工作流)，不看本请求头。
- 绝对期限从登录时刻起算(`jwt_refresh_ttl_days`，1–30 天)，refresh 轮换不延长。
- 登出、改密、管理员重置密码、账号锁定/停用/启用/解锁、离职、复职、改登录手机号(`login_account_changed`)、远程访问授权变更、refresh 重放、再认证锁定都吊销会话；登出后旧 access token 下一请求即 401。
- 「重放」只认**已被轮换出新令牌**(`replaced_by` 非空)的旧令牌再次出现。整族被作废的令牌(改登录手机号、权限变更、远程访问变动…)在会话仍有效时出现，是普通 401 让客户端回登录页，不误报 `refresh_reuse` 安全事件、不连坐吊销其它会话。
- 访客同一套：访客登录/刷新/登出同样建、查、吊销会话。
- 存量 refresh token 全部作废(发版后所有人重新登录一次；平台未上线，不做兼容)。

### 3.2 敏感操作再认证 (`POST /auth/step-up`)

- 输入当前登录密码，换取**绑定当前会话、5 分钟有效、只能用一次**的凭证；会话行只存凭证的 sha256。请求带 `X-Uten-Step-Up` 头使用，服务端在进入业务前原子核销(`UPDATE … RETURNING`)，被拒的请求什么都没做。
- 连续输错按「账号锁定阈值」次(默认 5)暂停「锁定时长」分钟(默认 15)，并吊销当前会话；改密时的旧密码、进入切换人与再认证**共用一个计数**(`auth_step_up_states`)。输错回 422 `REAUTH_FAILED`(不用 401，避免前端当成登录过期去刷新重放、一次输错算两次)，暂停回 429 `REAUTH_LOCKED`。
- 需要再认证的接口一律标 `@RequiresStepUp`，缺凭证回 403 `REAUTH_REQUIRED`：设/撤超管、远程访问授权、个人权限覆盖、数据范围、部门权限、重置他人密码、**给存量员工补开账号**(`POST /api/org/employees/{id}/account`，同样把明文临时密码交给操作人)、进入切换人、保存系统设置、清理测试业务附件、清空业务数据；提交改手机号/姓名/户籍地址(需人事审核的个人资料)在服务里核销。
- 核销顺序：`StepUpInterceptor` 是挂在控制器代理上的方法拦截器(`StepUpAdvisorConfig`，顺序 700)，排在方法级权限判定(`@PreAuthorize`，100–600)之后、履约冲突自动重跑(1000)与事务之前。一次请求依次经过参数绑定与 `@Valid` 校验(不合法直接 422，凭证不动)→ 权限判定(无权直接 403 `FORBIDDEN`，不会先弹密码框)→ 核销凭证 → 业务。第一版用 MVC 拦截器在进控制器前核销，无权的人会先被要求输入密码、请求体校验失败也会白白用掉凭证。
- `ArchitectureBoundaryTest` 锁边两条：`/api/admin/**` 下所有写接口，以及**响应里带明文临时密码的接口(不论路径前缀；凭据 DTO 按记录组件 `temporaryPassword` 自动识别)**，必须标 `@RequiresStepUp` 或 `@StepUpExempt("原因")`，漏标即红。豁免项逐条写明原因：锁定/解锁/停用/启用账号(要求填原因且只收紧)、审计导出等；入职开号(`POST /api/org/employees`)豁免——那是新员工第一次拿到账号，人事当面交付系统随机、限时的初始密码，不存在对已有账号的接管，每办一次入职都输密码会严重拖慢人事日常。
- 删除 `/auth/verify-password`；进入切换人不再在请求体里带密码。
- 前端：页面不再自己问密码。网络层 `StepUpInterceptor` 收到 403 `REAUTH_REQUIRED` 后经 `StepUpCoordinator` 弹统一的「请确认是你本人」框(`ReauthDialog`)，换到凭证后把原请求带上请求头原样重发一次；并发时弹框排队；取消则原 403 照常抛给页面。
- 弹框期间所有整页忙碌遮罩让位(`UtenBusyOverlay.yieldWhile`)：部门权限、个人权限、数据范围、清空业务数据、清理测试附件等写操作先挂遮罩再发请求，遮罩是 root Overlay 里的裸 entry，导航器每推一个路由都会把它抬回最顶层、盖住密码框——请求等密码、遮罩等请求，整页卡死。让位在弹框这一处统一做，各页不必逐个去掉遮罩，以后新增的敏感写操作也不会再踩；让位期间对话框自带的模态屏障照样挡住底下页面，关框后遮罩恢复到重发请求结束。

### 3.3 登录与密码

- 锁定期内**不校验真实密码**：只跑一次 dummy 哈希，回与「账号或密码错误」相同的码和文案，同时计数并顺延锁定——锁定期内不断试密码的人拿不到任何结果。管理员手动锁定/停用只在密码正确后才透出。
- 哈希闸门 `BoundedPasswordEncoder`：同时进行的 Argon2 校验不超过 CPU 核数，排队 1 秒拿不到回 503 `AUTH_BUSY` + `Retry-After`。登录与改密拆成「短读事务 → 事务外哈希 → 短写事务」，哈希不占数据库连接。
- 限流：先扣 IP 桶再扣主体桶，IP 超限直接拒绝、不为随机账号建主体条目；IP 桶平滑回填、瞬间最多 20 次；条目按访问过期(2 分钟)，不再整表清空，满额时只拒绝需要新建条目的请求；IPv6 按 /64 聚合。网站询价入口 token 不足 32 位生产拒绝启动，入口每 IP 每分钟最多 5 次失败。
- 临时密码(开通账号、入职、重置)一律系统随机 20 位高熵，**有效期由「临时密码有效期」决定(默认 72 小时)**，过期不能登录；V660 把存量「必须改密但没有过期时间」的非超管账号置为已过期。不再接受管理员自定义临时密码。
- **临时凭据不得永不过期**：V660 加触发器 `trg_users_temp_password_expiry`：必须改密的非超管账号没有过期时间时一律按已过期落库(失败关闭，这张临时凭据立即不可用)，任何写路径都造不出永久有效的临时凭据。没用 CHECK 约束：`users.must_change_password` 的列默认值是 TRUE，三十来个只为占位建号的原生 INSERT 不写这两列，CHECK 会让它们全部报错；触发器给出同样的保证。离职冻结、交接加固、复职不再把过期时间写回空：离职即把旧密码置为已过期，复职保持作废——否则 V660 之前开号、从未登录的员工离职再复职，身份证后 6 位的旧初始密码会重新永久有效。复职后由账号支持重置密码(走再认证、高危闸与通知)，复职确认框写明这一步。唯一例外是超管的初始密码(引导管理员来自部署密钥；置过期会让系统无人可管)；超管被降为普通账号时若还没改过初始密码，同时置为已过期。
- 密码最短长度改为系统设置 `password_min_length`(8–64，公开下发，前端改密页按它提示和预校验)。

### 3.4 账号支持收紧

- `account:support` 只能个人点名授权(V660 删除部门级授予，部门权限守卫触发器同时拦截；服务层与前端部门权限页、「一键全部授权」同步排除)。
- 账号支持一律不能对超管和本人操作；**发放登录凭据**(重置密码、给存量员工补开账号)另加一道：目标的有效权限(部门授权、个人授权与委派；补开账号按开号后的权限在同一事务里判定，不允许即整体回滚)含任一高危权限时，只有超管能发放——否则账号支持人员可以借「重置/开号 + 拿到明文临时密码」冒充审批人、付款人。判定集中在 `CredentialIssuancePolicy`。
- 高危清单是权限目录上的 `permissions.high_risk` 标记，在迁移里集中维护，代码不手写：V212「高危/个人-only」清单(审计查看/导出、授权管理、用户管理、流程指派、库存余额调整、固定资产审批/过账/处置/导出/期间)，账号支持本身、账户余额调整，**财税模块全部审批与执行类权限**(付款/收款/转账/费用/其它收入的审批与冲销、过账、预收、对冲、结算、销售财务确认、委外索赔…)，报销审批与付款，工资生成/审核/发布与查看全员工资。第一版手写清单漏了付款/收款/转账等真正动钱的审批，且含一个已退役的权限码。契约测试断言财税模块的审批/执行类权限全部被标记，新增此类权限不打标会变红。
- 锁定/解锁/停用/启用/重置都在同一事务里写语义化安全事件，并给**目标本人**发一条账号安全提醒(失败随业务回滚)；同时吊销目标全部会话。账号安全提醒**不能被删除**(冒充登录的人删不掉)；账号支持人员(非超管)重置别人密码时，另给其他超管发一条提醒——目标本人所有设备已退出、也不知道新密码，往往要等拿到临时密码后才看得到自己的提醒，另有人知情，冒充登录才藏不住。

### 3.5 系统设置单一登记 (V659)

- Java 枚举 `SystemSettingKey` 是唯一登记：键、类型、默认、最小、最大、分组、是否公开、名称、单位、排序、说明。数据库 `system_settings` 只存当前值与最后修改人/时间，删掉元数据列；`SystemSettingRegistryContractTest` 在全新库上断言行集合与种子默认值和枚举一致。
- 读设置只能按枚举读(删除按字符串读的 API)；列表接口随项下发 `minValue/maxValue/defaultValue`，前端校验只认它，删掉前端 `switch`。
- 唯一写路径：批量 PUT `/api/admin/system-settings`(要求再认证)；删除单项 PUT 和庆典设置 PUT，庆典「自动发布」开关走同一批量路径。删掉 10 个 yml 里没人读的设置字段与 getter。
- 新登记：切换人窗口(补数据行)、密码最短长度(公开)、临时密码有效期、交货期预警提前天数、预留超期提醒天数、委外回厂预警提前天数(三个业务预警调度器不再写死天数)、待办角标刷新间隔(公开，默认 60 秒)。公共设置接口新增 `passwordMinLength`、`attachmentMaxBytes`(部署配置)、`badgePollSeconds`。
- 基础资料导出统一按「导出行数上限」(`export_max_rows`)截断，与报表、审计导出同一口径(经 `ExportLimitPort`，不跨 feature 直调)。
- 取值范围：登录令牌有效期 5–1440 分钟、登录保持时长 1–30 天。**与审计建议(5–30 分钟)的偏差**：服务端会话检查后，access TTL 不再是安全边界(登出/空闲/账号变动都即时生效)，只影响「多久静默换一次令牌」，放宽上限不削弱安全。

### 3.6 其它

- 生产环境来源网段：未配置 `UTEN_LOCAL_ALLOWED_CIDRS` 启动失败；配置了过宽网段(如整个 RFC1918)只告警不拦(现网部署脚本已配置，不打断现有部署)。
- 「清空业务数据」(security-06)：开关与生产默认值按用户测试期口径保留(正式上线随 ADR-067 整体删除)；本次只加三道：清空与清理测试附件都要求再认证；生产 profile 开着时启动日志醒目提示「测试期开关」；云端站点无论开关如何一律关闭。
- 通知的回执人/祝福列表只对能看到这条通知的人开放，看不到的一律 404(不再凭通知编号就能列出谁读过、谁祝福过)。
- 客户/供应商按手机、电话、备用电话、银行账号筛选，以及**搜索框关键字(会匹配手机号)**，改走 `POST /master/{clients,suppliers}/search`，值只在请求体；GET 列表不再接受关键字；导出把这些值放进导出请求体的 `sensitiveFilter`。「筛为空」只暴露字段名，仍走查询串。

## 四、后果

- 发版后所有人需要重新登录一次(存量 refresh 作废)。
- 每个请求的鉴权仍是 1 条 SQL(账号 + 会话 + 空闲阈值合一)；人为请求每 60 秒最多多 1 条更新；用户没在操作时的请求不写库(实测 `/api/auth/me`：到续期时间的人为请求 15 条语句、不续期 14 条、同一端点带自动声明头 14 条)。
- 每个敏感操作多输一次密码(凭证一次性、5 分钟内有效；连续两个敏感操作各输一次)。
- 清空业务数据的清空表多两张(298→300)：清空后全员重新登录本就是既有行为。
