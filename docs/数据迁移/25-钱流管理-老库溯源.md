### 1.2 "单头 + 流水" 两层结构（钱流的核心范式）

钱流 6 类收付款单据全部遵循同一模式 —— 单头（金额/账户/客户）挂在主表，明细/核销挂在 Item 表或对应流水表：

```
销售收款:   M_Get (单头) ──┬─ M_GetItem  (0 行，未启用：核销明细的本意设计)
                          └─ M_In       (4.2 万行，实际承载应收/核销流水的表)

采购付款:   M_Paid (单头) ──┬─ M_PaidItem (0 行，未启用)
                           └─ M_Out      (4.5 万行，实际承载应付/核销流水)

一般费用:   M_DPaid (单头) ── M_DPaidItem (8.5 千行，按部门/费用类分摊)
其它收入:   M_OGet  (单头) ── M_OGetItem  (1.5 千行，按部门/收入类分摊)
银行存取:   M_Bank  (单头) ── M_BankItem  (0 行，未启用)
财务盘点:   M_O_Check(头) ── M_O_CheckItem(0 行，未启用，且写 MK_StockGoods)
```

> ⚠️ **关键观察**：M_Get/M_Paid 各有**两套**核销明细设计 ——
> - `M_GetItem/M_PaidItem`（0 行）：原本设计为"按应收单立帐逐行核销"的明细，**实际未启用**；
> - `M_In/M_Out`（4 万行大表）：才是真正的应收应付立帐 + 核销流水表，承载全部业务。
>
> 触发器 `TRI_M_get_B_M_in` / `TRI_M_Paid_B_M_Out` 同时检查这两套：若 `M_GetItem EXISTS` 则走游标核销、否则自动 INSERT 一行 `M_In`（BStyle=20 直接收款）。新库统一为一套 `finance_receipts_lines` / `finance_payment_lines`。

### 1.3 应收应付的真正"立帐"表 —— M_In / M_Out

`M_In`（应收）和 `M_Out`（应付）是钱流**最容易被误读**的两张表。它们不是"收款/付款单的明细"，而是**应收应付立帐台账 + 核销流水**：

| 表 | 业务含义 | 数据来源（BStyle 标识来源） |
|---|---|---|
| `M_In` | **应收账款台账**（客户欠我） | 销售出货 S_Out 审核自动立帐（BStyle=3, 单号 XC*）<br>直接收款 M_Get 触发器自动立帐（BStyle=20, 单号 XS*）<br>其它特殊（BStyle=18, 单号 XT*，疑似退货转卖） |
| `M_Out` | **应付账款台账**（我欠供应商） | 采购入库 P_In 审核自动立帐（BStyle=1, 单号 CJ*）<br>委外进仓 E_In 审核自动立帐（BStyle=1, 单号 EJ*）<br>直接付款 M_Paid 触发器自动立帐（BStyle=21, 单号 CF*） |

每行有 `Total`（应收/应付原额）、`M_In/M_Out`（已收/已付累计）、`M_Rare`（未收/未付余额）、`Paid` bit（结清标志）。**结清由触发器自动维护**：当 `M_Rare=0` 时 `TRI_GatheringCheck/TRI_PaymentCheck` 自动置 `Paid=1, PaidDate=getdate()`。

> 🔎 这是为什么采购模块 [14] 提到"应收应付"但不展开 —— 因为**应收应付的数据全部在 M_ 表里**，是钱流模块的资产。

#### 触发器揭示的 M_Acc ↔ M_Style 联动

`TRI_M_Acc`（INSERT）自动在 `M_Style` 树下创建对应的帐户叶节点（`ItemID = M_Acc.ID`），并回写 `M_Acc.StyleID`：

```sql
IF (@AStyle=1) SET @StyleNumber_='102', @StyleName_='银行存款'
ELSE            SET @StyleNumber_='101', @StyleName_='现金'
-- 在 M_Style 树的 101/102 父节点下创建叶节点，ItemID 指向 M_Acc.ID
INSERT INTO M_Style(...,ItemID) VALUES(...,@ID)
UPDATE M_Acc SET StyleID=@ItemID WHERE ID=@ID
```

`TRI_M_Acc_Update`（UPDATE）：帐户改名时同步 `M_Style.StyleName`。

> 新库无需此联动（账户主档和类别字典解耦），但迁移时需保留 `M_Acc.StyleID` → `payment_styles.legacy_id` 的对应关系。

```

  └─触发器 TRI_M_get_B_M_in (无 M_GetItem 分支)
```

### 4.3 M_AllCheck 的作用

它是**账户统一流水帐**（bank register），不分单据类型，每条记录一次账户进/出动作。报表 `S 帐户进出流水帐` 和 `Z 应收应付` 的核心来源。新库对应 `finance_reconciliations`，但**应收应付核销本身**（哪笔收款核销哪笔应收）实际不在 M_AllCheck 里 —— 而是通过 M_In.M_In/M_Rare 的累加体现（`M_Get → M_In.M_In +=` 即核销）。

> 💡 新库设计提示：`finance_reconciliations` 保留两类语义 ——
> 1. **账户流水**（M_AllCheck 1:1 迁移，按 BStyle 区分来源）
> 2. **核销明细**（在 finance_receipts_lines 里记录 `applied_to_ar_id`，对应 M_In 的累加核销）
>
> 老库把这两层混在一起：M_AllCheck 是账户流水 + 弱化的核销痕迹；真正的核销关系靠 M_In/M_Out 的数字累加 + BillID 推断。

## 五、触发器揭示的业务规则（设计金子）

老库 91 个触发器中，钱流相关 11 个。揭示以下规则，**新库必须保留语义、改用 Service 层事务实现**。

### 5.1 状态机驱动一切（与采购同构）

所有钱流单据的副作用都由 `Status` 字段变化触发：

```sql
IF (@Status<>0 AND @Status2<>@Status)  -- 状态确实变了才触发
```

- `Status = 0`：草稿，**不产生任何业务影响**
- `Status = 1`：审核生效 → 更新账户余额 / 写 M_AllCheck / 自动建应收应付立帐
- `Status = -1`（反审/红冲）：**反向冲销**（账户余额减、删 M_AllCheck、删自动建的 M_In/M_Out）
- `Status2` 记录"上一次状态"，用于判断方向

### 5.2 ⭐ 规则一：单据审核 → 账户余额 + 应收应付 + 对账流水 三联动

**最核心的触发器** —— `TRI_M_get_B_M_in`（M_Get）/ `TRI_M_Paid_B_M_Out`（M_Paid）：

```
当 M_Get 审核 (Status: 0→1):
  ├─ 分支 A (有 M_GetItem 核销明细，老库实际未启用):
  │   └─ 游标 UPDATE M_in (按 SellID): M_In += 本次收款, M_Rare -= 本次收款
  │      UPDATE M_Acc.GetTotal += 本次收款
  │
  ├─ 分支 B (无 M_GetItem，直接收款，实际全走这条):
  │   ├─ INSERT M_in (BStyle=20, BillID=本M_Get.ID, Total=0, M_In=本次, M_Rare=-本次)
  │   └─ UPDATE M_Acc.GetTotal += Total
  │
  ├─ INSERT M_AllCheck (BStyle=20, InTotal=Total, AccID=RecAcc, Company=客户名)
  ├─ 若有支票号: INSERT M_Check (CheckNo, Total, AccID, Source='收')
  └─ UPDATE M_Get SET Status2=Status

红冲 (Status=1→-1): 全部反向 (DELETE M_in / M_Acc.GetTotal-=Total / DELETE M_AllCheck / DELETE M_Check)
```

M_Paid 触发器完全对称（Paid/Out/M_Out/BStyle=21）。

> 🔑 **设计金子**：审核动作**一次触发**完成三件事：(1) 账户余额累加 (2) 应收应付核销（M_In.M_In 累加或新建立帐） (3) 对账流水登记。新库用 Service 层事务保证三件事原子完成，但**不分散到触发器**。

### 5.3 ⭐ 规则二：应收应付自动结清（M_Rare=0 → Paid=1）

`TRI_GatheringCheck`（M_in）/ `TRI_PaymentCheck`（M_Out）：

```sql
IF (@M_Rare=0)  UPDATE M_in SET Paid=1, PaidDate=getdate() WHERE ID=@ID
ELSE            UPDATE M_in SET Paid=0, PaidDate=null      WHERE ID=@ID
```

每次 M_in.M_Rare 被 5.2 的核销触发器改写后，本触发器自动判别结清状态。**这是应收应付"自动结清"机制** —— 不需要业务员手动打勾。

> 🔑 **新库**：结清标志 `is_settled` 派生计算（`remaining_amount <= 0`），不冗余存储；或保存但在 Service 层显式维护，避免触发器链。

### 5.4 ⭐ 规则三：账户主档与类别字典联动（TRI_M_Acc）

见 §2.1。插入账户时自动在 M_Style 树下创建对应类别叶节点（101 现金 / 102 银行存款），并回写 StyleID。

> 🔑 **新库**：账户主档 `accounts` 和类别字典 `payment_styles` **解耦**。账户通过 `account_type` 枚举分类，不需要每个账户建一个字典叶节点。但迁移时需保留 `M_Acc.StyleID → payment_styles.legacy_id` 对应关系，以便老报表按字典节点查询能继续工作。

### 5.5 规则四：动态 SQL 汇总成本/税额（TRI_M_in_STotalCheck / TRI_M_Out_STotalCheck）

```sql
SELECT @TableName=TableName FROM SystemSource WHERE SourceID=@BStyle
-- 动态拼接: SELECT @a=sum(STotal),@b=sum(Total) FROM <TableName>Item WHERE BillID=@BillID
exec sp_executesql @str, N'@a float output,@b float output', @STotal output, @TTotal output
UPDATE M_in SET STotal=@STotal, TTotal=@TTotal WHERE ID=@ID
```

M_in/M_Out 的 `STotal`（成本合计）/ `TTotal`（税额）通过动态 SQL 反查上游单据明细表（SystemSource 表维护 BStyle→TableName 映射）。这是**反范式冗余字段**，新库应在视图/查询时计算，不存储。

### 5.6 规则五：M_Bank 银行存取款的汇率换算

`TRI_BankItem` 在游标处理多个存款账户时，对每个账户做汇率换算：

```sql
UPDATE M_Acc SET GetTotal = GetTotal + @Total * @OCRate / @CRate WHERE ID=@InAcc
```

`OCRate` = 取款账户的原始汇率，`CRate` = 存款账户的汇率。新库银行存取款单需保留跨币种换算逻辑（虽有空表，但建结构时要把这套语义放进 Service 层）。

### 5.7 规则六：红冲的反向一致性

所有钱流触发器的 ELSE 分支（Status=1→−1）严格反向：删除自动建的 M_in/M_Out 行、回滚 M_Acc 余额、删除 M_AllCheck、删除/还原 M_Check。**红冲不保留痕迹**（硬删除），新库应改为软删/标记红冲保留审计。

## 八、老库设计的核心问题（新库要解决的）

1. **业务逻辑全埋在触发器**（账户余额、应收应付核销、对账流水、结清标志全由 11 个触发器维护）→ 换库即丢失、不可测、不可审计。**新库上移到 Service 层事务**。
2. **单据"两套核销明细"设计冗余**（M_GetItem + M_in、M_PaidItem + M_Out）→ 实际只用 M_in/M_Out，M_GetItem/M_PaidItem 是 0 行死代码。新库**一套 `finance_receipts_lines`**。
3. **应收应付核销靠数字累加 + 触发器**，无显式核销关系表 → 哪笔收款核销哪笔应收只能从 M_in.M_In 累加 + 时间序推断。新库**显式 `applied_to_*` 关联**。
4. **账户余额字段冗余**（GetTotal/PaidTotal/FactTotal 存在 M_Acc 上，每次审核触发器维护）→ 与库存 StockGoods.QTY 同构的反范式。新库**余额派生计算**或单独余额表，流水先行。
5. **M_Acc.AStyle 退化**（全为 1，账户类型实际靠 AccName 字符串）→ 新库重建 `account_type` 枚举（银行/现金/支票/外来支票/第三方支付/境外）。
6. **M_Style 是个"多用途混合树"**（账户类叶节点 + 费用项目 + 收入项目 + 付款方式混在一棵 124 节点的树里）→ 新库 `payment_styles` 按 `category` 分根节点，或拆成多个独立字典。
7. **命名极度不统一**（对方账户字段在 M_Get 叫 `dfch`、在 M_Paid/M_DPaid/M_OGet 叫 `dfzh`；经手人在 M_Paid 是文本 `jsr`、在 M_Bank 是 `WorkID` 外键；账户类型叫 `AStyle` 又叫 `StyleID`）→ 新库统一命名规范。
8. **人员字段指向两个表**（Sys_Operator + B_Worker）→ 无对齐，迁移留空。
9. **`float` 存金额**（M_in.CRate / M_Out.CRate / M_Bank.CRate / M_BankItem.CRate / M_DPaid.CRate / M_OGet.CRate 都是 float）→ 精度风险。新库全用 `numeric`。
10. **红冲硬删除**（Status=-1 触发器 DELETE 自动建的数据）→ 不保留审计痕迹。新库改为软删/红冲单据标记 + 审计日志。
11. **动态 SQL 汇总成本/税额**（`TRI_M_in_STotalCheck` 用 `exec sp_executesql` 反查 SystemSource.TableName）→ 反范式 + 注入风险 + 不可优化。新库在视图/查询时计算。
12. **跨模块应收应付立帐依赖外部触发器**（M_in 的 BStyle=3 立帐由 S_Out 触发器写入，但本批 dump 未包含 S_Out 触发器；M_Out 的 BStyle=1 由 P_In/E_In 写入）→ 迁移 M_in/M_Out 是**只迁结果**，立帐链路在新库需在销售/采购/委外模块的 Service 层显式重建。
13. **支票无独立主表**，混在账户主档 + 类别字典里 → 见 §九支票管理结论。

## 九、支票管理最终结论

老库**没有独立的"支票"表作为单据**。"支票管理(A) / 外来支票管理(G)" 在老系统里是这样实现的：

### 9.1 支票的三层表示

```
1. 支票账户（M_Acc）: ID 50 "支票"（禁用）/ ID 56 "支票"（使用）
   └─ M_Acc.StyleID → M_Style 的"支票"类别叶节点

2. 支票登记簿（M_Check）: CheckNo(支票号) / Total(金额) / AccID(银行) /
                          Status('已用'/'未用') / Source('收'/'付') / Cancel
   └─ 0 行（未启用登记簿功能，但结构在）
   └─ 由 M_Get / M_Paid / M_DPaid / M_OGet / M_Bank 触发器在审核带 InvoicesNo 时
      自动 INSERT/UPDATE/DELETE

3. 支票流水: M_in / M_out 中 RecAcc/PaidAcc 指向"支票"账户的子集
   └─ M_AllCheck 中 AccID = 支票账户 ID 的子集
```

### 9.2 新库支票管理方案

| 新库对象 | 来源 | 设计 |
|---|---|---|
| `accounts` (account_type='CHECK' / 'FOREIGN_CHECK') | M_Acc ID 50/56 | 支票作为账户的一种类型，迁 2 行 |
| `finance_check_register`（新表，可选） | M_Check（0 行） | 独立支票登记簿，迁空结构；触发器逻辑改成 Service 层在收/付款审核时自动登记 |
| `finance_receipts` / `finance_payments` (account_id→支票账户) | M_Get / M_Paid 中 RecAcc/PaidAcc=50/56 | 支票收/付款流水（account_id 指向支票账户即可查询） |
| `finance_reconciliations` (AccID=支票账户) | M_AllCheck AccID=50/56 | 支票账户的对账流水 |

> 💡 **结论**：新库**不单独建"支票管理"模块**。支票作为 `accounts.account_type='CHECK'` 的特殊账户存在，支票流水 = 该账户的收付款流水子集，支票登记簿作为可选扩展表（迁 M_Check 空结构）。前端"支票管理(A) / 外来支票(G)" 报表 = 按支票账户过滤的流水查询。
