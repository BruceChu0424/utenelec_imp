## 零、数字从哪来(2026-09-23, ADR-108)

- 全站红黄徽章、容器之和、导航总数、通知未读数, 由 **一次** `GET /api/workbench/badges` 带回;
  服务端按当前身份复用各入口原计数端点的资格判定与查询, 在一个只读事务里算完, 某个来源出错
  只让它的入口标记为「本次没算出」(前端沿用上一份的数, 容器与总数按差额修正), 不拖垮整份汇总。
- 工作台「今日概览」的本部门待办卡与红徽章同一口径: 服务端经徽章只读端口只算本部门要的入口
  (permissions-08), 不再另写「部门 + 权限码」计数。
- 前端 `badgeSummaryProvider` 是唯一数据源: 登录后立即拉一次、之后每 60s 一次; 页面隐藏时暂停,
  回到前台立即补一次; 写操作成功 / 返回工作台 / 新通知到达时 `refreshBadges(ref)`(单飞合并);
  登出即停。此前约 40 个计数 provider 各自 60s 轮询, 回一次工作台打出约 40 个请求。
- **口径只在服务端目录登记一处**: 新增入口 = 在 `WorkbenchBadgeCatalog` 加一行(写明红/黄各由哪些
  事实数相加) + 前端 `BadgeEntry` 加同名一项(只声明归属容器)。前端**不做加法**; 页内分段要的细分数
  (各类草稿、品质结果分来源、车间任务分段等)读汇总里的事实数 `BadgeFact`, 不单独请求。
- 下文所有「登记进注册表」一律指服务端目录; 历史章节里提到的 `todo_badge_registry.dart` /
  `in_progress_badge_registry.dart` 已于 2026-09-23 删除, 其规则原样搬进服务端目录。

界面上的数字只有三种，**选错形态就是 bug**。挑形态前按顺序回答两个问题：

> ① 这个数字变大的时候，是「有人在等我干活」吗？是 → **红色**。
> ② 不是 → 这一档的东西「还在流程里没结束」吗？是 → **黄色**；已经结束的、
>    历史的、全部的 → **中性括号**。

一句话记：红色 = 我还欠多少活；黄色 = 我手上还有多少在跑；括号 = 这里堆了多少东西。

### 两枚徽章的实底色（2026-09-22 定稿）

| | 实底 | 数字 | 对比度 | 常量 |
| --- | --- | --- | --- | --- |
| 红 · 轮到我动手 | `#DC2626`（red-600） | 白 w700 | 4.8:1 | `UtenColors.dangerStrong` |
| 黄 · 进行中 | `#F5B301`（亮琥珀） | 深棕 w800 | 5.3:1 | `UtenColors.warningStrong` + `UtenColors.onWarningStrong` |

用户口径「红变得更红，黄变得更黄、偏亮一点，两个色差明显点」。两枚**配色是反的**：
红是深底白字，黄是亮底深字——这不是不一致，是约束逼出来的。黄一旦调亮，白字对比度必掉
（amber-600 配白字已经只有 3.2:1），所以要「黄更亮」就只能把数字换成深色；换完反而比
原来的白字方案更清楚。

两条硬规矩：

- **红徽章不吃 `colorScheme.error`。** 那是全站语义红（输入框错误边框、校验文案、危险图标，
  400 多处引用），为了角标去改深它是过度波及。徽章有自己的实底常量。
- **底色与字色是配套的，改一个必须改另一个。** 亮黄配白字、深红配深字都会糊。
  三轮定色的完整过程记在 `UtenColors.warningStrong` 的注释里，动之前先读。

## 一、三种呈现形态

### 1. 通知数量徽章 `UtenNotificationBadge`（醒目 / 告警色）

只给 **「需要我处理、不处理会出事」** 的入口：

待审 · 待确认 · 待收货 · 待出库 · 待检 · 被驳回 · 超期 · 异常 · 等待物料 · 本人草稿。

- 用户看见它就应该点进去干活。
- **0 → 整个不渲染**（不留灰色的 `0`，不占位）。
- `null`（仍在加载 / 读取失败）同样不渲染——不把「未知」伪装成真实 0。
- 挂在 `UtenHubCard.badge` 槽位（右上角浮层），或分段标签的徽章位
  （`UtenSegmentBadgeLabel` + `UtenSegmentCountForm.actionable`，见 §四·分段标签）。
- **会被上层容器逐级累加**（见 §三）。

### 2. 进行中数量徽章 `UtenInProgressBadge`(黄色 / 2026-09-21 新增)

只给 **「已经在办、还没完、现在不用我动手」** 的入口：

生产中 · 加工中 · 执行中 · 在途 · 等待财务审核 · 财务已通过待执行 · 等待检查结果。

- 用户看见它就知道「这些在跑着，不用管」——它不是催办，是进度。
- **0 → 整个不渲染**；`null`(加载中 / 读取失败)同样不渲染。
- 挂在 `UtenHubCard.progressBadge` 槽位(右上角，**红徽章左边那枚**)，
  或分段标签的 `UtenSegmentCountForm.inProgress`。
- **会被上层容器逐级累加，但走另一条链**
  (服务端目录每个入口的「黄」一栏)，与红色是两条互不相干的链。

> **同一张单据可以同时出现在红数和黄数里**，这不是双计：它既在跑、又等你动手，
> 是两个问题的两个答案。双计只在**同一条链内**才成立。

### 3. 括号数字 `UtenCountSuffix`(中性 / 不抢眼)

给 **「已经结束了、供我掂量」** 的入口：

已完成 · 已审 · 已出库 · 红冲 · 历史 / 记录 · 全部 · 一切浏览型集合。

> **草稿 2026-09-11 起不在此列**，改走红色徽章并参与累加，见 §草稿。

- 直接写进标签：`等待下达车间 (46)`、`采购收货 (2)`。
- 卡片上 **0 → 不渲染**（`标题 (0)` 只是噪声）；
  **分段标签可以显示 `(0)`** 保持队形（传 `hideWhenZero: false`）。
- 挂在 `UtenHubCard.labelSuffix` 槽位（标题文字右侧，随标题一起换行），
  或分段标签的计数位（`UtenSegmentBadgeLabel` 的**默认**形态）。
- **永不进上层累加**。

> 同一语义的入口，全平台必须用同一种形态。草稿在哪个模块都是红色徽章；
> 「待退回供应商」在采购和委外都是红色徽章。

### 反例

| 写法 | 为什么错 |
|---|---|
| 报表卡挂红徽章显示「本月 320 行」 | 报表不需要我处理，红色是在喊狼来了 |
| 基础资料卡显示「货品 5231」 | 主档行数不是待办，也不是需要掂量的工作量 |
| 待审单据写成 `订货审批 (7)` | 该喊的时候不喊，用户会漏掉审批 |
| 徽章显示灰色 `0` | 占视觉预算却不传递信息 |

## 二、什么绝不挂数字

- **报表 / 查询 / 分析类卡片**（销售报表、仓库报表、钱流 10 张报表、物料反查、链路健康）。
- **基础资料主档**（货品 / 模具 / 客户 / 供应商 / 颜色 / 单位 / 币种 / 仓库 / 账户 / 付款方式 / 结算方式）——
  行数不是待办，基础资料 hub 恒 0 徽章是**设计结论**，不是遗漏。
- **历史 / 只读专页**（委外成品退货单历史、委外损耗单历史、历史 BOM 子件发料、品质检测记录）。

订单进度查询虽名为“查询”，同时承载财务驳回修订与可分批发货办理，属于有真实待办的明确例外。其红色数量来自 `REJECTED + SHIPPABLE` 阶段订单数，不是浏览记录数或完工通知未读数。

## 三、外层累加内层(两条链，各自独立)

```
TodoEntry(红色入口)      → BadgeModule → todoTotalCountProvider
InProgressEntry(黄色入口) → BadgeModule → inProgressTotalCountProvider
                              ↑ hub 卡 / 工作台模块卡 = 该容器内同色入口之和
```

容器划分 `BadgeModule`(原 `TodoModule`)两条链共用，住
[`badge_module.dart`](../../lib/shared/badges/badge_module.dart)。

**导航 Tab 的角标只有红色**：那是「提醒你欠了活」的告警位，而黄色的定义就是
「现在不用你动手」，放进告警位自相矛盾。「工作台就是汇总」指的是工作台**页面**
(每张模块卡右上角黄左红右，分区收起时的组徽标也是两枚)。

三条硬规则：

1. **只有徽章参与累加，且红黄各走各的表。** 括号数字(浏览型计数)两条链都不进。
   草稿是**红色徽章**，参与红链累加(2026-09-11 起，见 §草稿)。
2. **同一条链内同一件活只能被计一次。** 父层按「入口」去重；两个入口指向同一批单据时，
   只让其中一个登记进注册表，另一个在语义标签/副标题里说明「已计入 xxx」。
   **跨链不算双计**(见 §一·2 的说明)。
3. **每条链的累加只有一处实现。** 红黄两链全部登记在服务端
   `WorkbenchBadgeCatalog`(每个入口一行, 写明红/黄各由哪些事实数相加),
   容器之和与导航总数也由服务端算好随汇总带回(ADR-108)。
   **不要在 hub 页或工作台里手写加法**——新增入口只改服务端目录 + 前端 `BadgeEntry` 映射。

已登记的切片（故意不重复登记，避免双计）：

| 入口 | 为什么不单独登记 |
|---|---|
| 钱流「销售订单修改」 | 与「销售订单财务确认」是同一批单据的两个队列切片，累加只认总数一次 |
| 仓库三张任务中心卡的内部分段 | 卡面角标已是分段之和，分段本身不再登记 |
| 采购「采购申请」 | 待处理量已由「采购任务中心 · 待分解」计入 |
| 销售「客户零星发货」草稿 | 与「销售出货」同属 `sales_shipments`，且 `/sales/shipments` 列表本就含这批单 |
| 仓库 `stockTransfer` / `stockCheck` 切片 | 模块累加用 `stockDocument` 整表合计；再把两个切片加进去就是同一张单数两遍（`DraftCounts.sumOf` 里有 assert 挡住） |

## 仓库生产退料与测试装配

`TodoEntry.warehouseProductionReturn` 对应车间已正式提交、仓库尚未实收的生产退料。生产领料任务中心卡合计待领与待退实收，模块汇总从注册表分别读取一次；不能再把卡片合计登记为第三份待办，也不能把全部退料历史计入。提交、撤销、仓库确认及页面恢复通过 `invalidateWarehouseTaskCounts` 刷新，身份/代操作切换后清除前一身份的计数。

该计数读取真实 `sessionProvider` 及仓库单据仓储依赖，间接需要应用启动时注入的 `sharedPreferencesProvider`。宿主测试新增徽章后必须同步装配该依赖；不能把新徽章移出注册表、屏蔽会话隔离或吞掉provider异常来通过测试。测试边界与入口见[仓库管理枢纽页](../03-页面/仓库管理枢纽页.md)。

## 草稿（2026-09-11 口径反转）

**结论：草稿走红色徽章，并逐级累加到 hub 卡与工作台模块卡。**

### 为什么改

本文件 2026-09-11 上午立的规则是「草稿 = 浏览型计数，走中性括号，永不累加」，
理由是「草稿是我自己没写完的东西，没人在等它」。**当日用户推翻了这条**，原话：

> 一些新建的地方右上角不是有草稿按钮嘛，里面的数字我想要的是改成我们自己写的通知徽章，
> 就是红色的背景里面白色的数字……然后在外面也要显示……最外面的工作台销售管理卡片
> 也要显示里面的全部累计。

产品理由成立：草稿不是「可看可不看的集合」，是**本人开了头却没交出去的活**。
它不出现在任何待办队列里，如果连个红点都没有，就只能靠人自己记得——这正是它该被
喊出来的原因。所以草稿在本文件的分类里从「浏览型」移到「待办型」。

### 落地

| 位置 | 形态 |
|---|---|
| 新建页顶栏「草稿」按钮 | 文案右侧红底白字徽章（`UtenAppBarActionButton.badge`） |
| hub 单据卡 | `UtenDraftBadge`。该卡**没有**其它待办徽章 → 放 `UtenHubCard.badge`（右上角）；**已有**待办徽章 → 草稿徽章退到 `labelSuffix`（标题右侧行内，仍是红色），一个槽位不塞两个红圆点 |
| hub 页顶栏 | 本模块累计(`todoModuleCount(BadgeModule.x)`，已含草稿); 左边另有一枚黄色「进行中 N」(`inProgressModuleCount`) |
| 工作台模块卡 / 导航 Tab | 自动包含——`module_badge_sum` 早已委托注册表，注册表加了 `TodoEntry.*Drafts` 就生效，**页面里不要手写加法** |

组件：`lib/components/feedback/uten_draft_badge.dart`（原 `UtenDraftCountSuffix` 已删除）。
注册：`TodoEntry.salesDrafts` / `purchaseDrafts` / `subcontractDrafts` / `financeDrafts` /
`warehouseDrafts` / `productionDrafts`，数字来自 `draftCountsProvider` 的模块切片求和
（`DraftCounts.sumOf`）。

### 唯一要小心的地方

仓库模块累加**只能用 `DraftDocKind.stockDocument`（整表合计）**，
不能再把 `stockTransfer` / `stockCheck` 切片加进去——它们是同一张表的 doc_type 切片，
一起加就是双计。`DraftCounts.sumOf` 里有 assert 兜底。

## 四之二、红徽章只数「轮到本部门动手」的档（2026-09-11 收口）

用户当天两条反馈同源：

- 「采购任务工作台『财务已通过』的数量，不合计在采购任务中心的通知数量合计里面」；
- 「仓库·品质部检查结果，如果是『等待检查』这个不计入消息累计，只有检查结束后通知」。

**口径**：同一条链上的阶段，凡是「球在别人手上」的，**不进红徽章、不参与红色上卷**。

> **2026-09-21(ADR-100)修订**：这一类档原本的呈现是「中性括号」——本节下面那句
> 「页内照常以中性计数呈现」已作废。它们现在有自己的颜色：**黄色进行中徽章**，
> 并且**参与黄色那条链的上卷**。本节的判定结论(哪些档不进红)完全不变，
> 变的只是这些档被画成什么颜色、以及它们现在也会被汇总到工作台。

已落地三处(下表的「不计入」列 = 现在挂黄色的那些档)：

| 计数 | 计入 | 不计入 | 实现 |
| --- | --- | --- | --- |
| 采购任务中心 | 申请待分解 `WAITING_ORDER`、财务驳回 `FINANCE_REJECTED` | 等待财务审核 `ORDER_PENDING_APPROVAL`、财务已通过 `FINANCE_APPROVED`、已完成 | `FulfillmentWorkbenchQueryService.countPending` |
| 委外任务中心(ADR-098, 2026-09-20) | 待处理 `WAITING_ORDER`；「进行中」段内异常小类行的 财务已退回 `FINANCE_REJECTED`、回厂短交待判定 `SHORT_DELIVERY`(含分批等待过了预计到齐日) | 「进行中」段合计 `IN_PROGRESS`(等待财务审核 + 财务已通过 + 财务已退回)、状态列各档、已完成 | `FulfillmentWorkbenchQueryService.countPending`(按订货单去重：WAITING_ORDER + FINANCE_REJECTED + 有待判定案件的 FINANCE_APPROVED 单)；委外 hub「回厂短交判定」卡片徽章 = `/subcontract/short-deliveries/count.pending` 同数展示，不登记 registry |
| 仓库 · 品质部检查结果 | 待入库、需退回 | 等待检查结果 `WAITING_INSPECTION`、已完结 | `WarehouseQualityResultService.typeCounts`(2026-09-21 起红黄同出一次聚合: 返回 `TypeCounts(actionable, inProgress)`, 红 = 本列「计入」那两档、黄 = 「不计入」列里的 `WAITING_INSPECTION`, 已完结两支都不数; 原 `pendingTypeCounts` / `countPending` 与 `GET /quality-results/count` 端点一并删除) |
| 仓库 · 销售出库(2026-09-20) | 待出库 `PENDING_PICK` | 历史迁移异常 `LEGACY_PENDING`(V443 起只读, 仓库无动作)、已出库 | `SalesShipmentService.countPendingWarehouseWork` / `countWarehouseWorkByStatus` |

自检方法：**hub 卡上的红数字 = 页内各红色分段之和**；同理**黄数字 = 页内各黄色分段之和**。
对不上就是某个档挑错了形态(前端 `_stageCountForm` 与后端 count 必须同时改)。

> **对账前先确认参与的数不是 0**(2026-09-21 实测踩到)：拿真实环境验这条恒等式时，
> 如果库里那几档恰好都空，`0 == 0` 会全绿，其实什么都没验证 —— 并发会话清过业务数据、
> 刚重置过环境、或者你挑的筛选条件本来就没数据，都会掉进这个坑。验证前先看一眼
> 参与对账的数字是否非零；是零就先造出可判定的数据(克隆一个库造，别污染共享环境)再验。

> 2026-09-21 教训(品质部检查结果, ADR-100 落地后第一个回归): 光靠人工对这个账会漏 ——
> 那一页的红数走 `/type-counts`、黄数走另一支端点, 大类行只接了红的那一支, 黄数字
> 一进页面就没了, 谁也没发现。**结构性的做法是让同色的卡面数与分段数同出一次服务端聚合**:
> 一条 SQL 分桶、一个响应带回红黄两组数, 前端两支计数 provider 从同一份数据派生。
> 这样「卡面 = 页内同色分段之和」不是靠人守的纪律, 而是拆不开的同一个数。

> 已知例外(沿袭既有实现，不是本次引入)：采购/委外任务中心的**卡面红数**
> `countPending` 数的是**单据**(`DISTINCT action_doc_id`)，而**分段数**是**任务行**。
> 这两个数量纲本来就不同，别拿它们去对账。黄色沿用同一套口径。

## 四之三、徽章数在刷新期间不许清零

徽章汇总取数失败保留上一份的数; 服务端标记为「本次没算出」(staleEntries)的入口沿用上一份的数,
所在容器与导航总数**按差额修正**(减去该入口本次的残缺数、加回上一份的数; ADR-108,
`BadgeSummary.keepStaleFrom`)——不整体沿用上一份的容器/总数, 否则某个来源持续出错时总数冻结在
第一次的值上、其它入口怎么变都不动; 没算出的来源(staleSources)的页内分段事实数也沿用上一份。
轮询带回相同的数不触发重建。
否则轮询每转一圈就把徽章打回 0 再弹回来
（用户 2026-09-11：「徽章会突然消失下又出现，然后又消失又出现」）。

配套两条硬性要求：

1. 喂给注册表的计数 provider **一律常驻**（不 `autoDispose`）。autoDispose 的
   provider 一离开页面就销毁，回来没有「上一次」可留，表现为「点进去要等一会
   徽章才出现」，而采购那种常驻 StateNotifier 点进去就有。
2. 常驻后**必须自带轮询**（`Timer(60s, ref.invalidateSelf)` + `onDispose` 取消），
   否则值会停在首次加载那一刻。没人看时定时器不再续期，不会空转发请求。

回归用例：`test/shared/badges/todo_badge_async_retention_test.dart`。

## 四之四、草稿计数：一次往返 + 存盘即刷新 + 进工作台（2026-09-11 晚）

用户三条反馈，三个不同的坑：

**① 「新建销售订货单里明明有草稿，要等十几秒红色徽章才出来」**
不是 21 条 count 慢，是**最多 63 次往返**：`DocumentDraftCountQueryService.counts`
逐类型建 `DraftScopeAccessPolicy`，而 `OwnerVisibility.evaluate` 对非超管每次都要查
「交接继承」+「授权归属人」两条 SQL。现在归属范围**按 scope 串去重**只算一次
（21 个类型只有 6 个 scope），21 条 count 合并成一条 `SELECT (子查询), …`。
闸门用例 `DocumentDraftCountSqlContractTest#allDraftCountsAreFetchedInASingleRoundTrip`
——退回逐条会直接炸。

> 写新的 `/counts` 端点时按这条自检：**范围解析次数 ≤ 不同 scope 数，SQL 条数 = 1**。

**② 「我没审核、退出了，草稿就该立马记录并显示」**
失效点挂在 `bumpListRefresh`——全部单据编辑页保存/审核/删除成功后的唯一公共钩子，
一处覆盖 7 个编辑页。不走该钩子的页面（生产计划单 / 生产日报用 `context.replace`
直达详情）各自补一次 `ref.invalidate(draftCountsProvider)`。
漏一个页面，用户就要等下一轮 60 秒轮询。

**③ 「工作台 销售管理 那里没有显示」**
`module_badge_sum` 里 `WorkbenchBadgeKind.sales` 被写死成**单个入口** `salesAttention`，
不是整模块累计，销售草稿因此永远进不了工作台（hub 顶栏看得到、工作台看不到）。

> 规矩：**模块在工作台只有一张卡 → 用 `todoModuleCount(模块)`；有多张卡 → 用
> `sumTodoEntries([...])` 显式列出该卡负责的入口**，保证「各卡之和 = 模块累计」
> 且互不重叠。「生产管理」卡即属后者（车间任务另有一张卡，不能算进来）。
> 回归用例 `test/features/dashboard/workbench_card_badge_drafts_test.dart`。

## 四之五、服务器状态告警：从「只能拉」改成「会推」（2026-09-11）

用户：「有任何报警 都推给我」「我就怕业务附件 196G 不够用」。

**改之前**：`ServerStatusProbe` 算出的 `alerts`（磁盘 80%/90%、内存、数据库、备份、
定时任务越线）**只塞进状态页的返回值**。工作台那张「服务器状态」卡是纯跳转卡、没有徽章。
结果：附件卷可以从 1% 一路涨到 91%，只要没人主动点开那个页面就无人知晓。

**改之后**：

| 面 | 做法 |
| --- | --- |
| 推送 | `ServerStatusAlertScheduler`（住 `features/notice`，因为架构边界只允许 `notice->admin`）每 5 分钟采样一次，越线即站内通知 |
| 收件人 | 新权限码 `server_status:alert:receive`（V552），**与 `server_status:view` 分开授**——「能看」和「该被半夜吵醒」不是一回事。默认授给已有 view 权的那些部门，之后在权限页自由调整 |
| 不刷屏 | 节流判据是 `notices.source_event = SERVER_STATUS_ALERT:<指标>:<档>` + 收件人 + 6 小时窗口，**存在数据库里**，所以重启不会重新刷一遍；WARNING→CRITICAL 是不同事件，升级不受旧档压制 |
| 恢复 | 从 CRITICAL 回正常补一条「已恢复」；警告档恢复不发。恢复判定靠内存里的上一轮档位，**进程重启会丢**（已在类注释里写明，不为它加一张表） |
| 工作台 | 卡上挂红徽章 = 当前 warning/critical 条数（`TodoEntry.serverStatusAlert` / `TodoModule.system`）。UNKNOWN 不计——拿不到数不等于有事要办 |
| 类型 | `notices.type` 与 `priority` 必须落在 `NoticeService` 白名单内：危急 `urgent/urgent`、警告 `system/important`、恢复 `system/normal`。写 `warning`/`info` 会在运行期被拒（已有用例钉住） |

**顺带**：状态页此前把同一文件系统的多个用途**合并成一行**（`/data` 既放数据库又放备份，
只显示一条「数据库与业务数据 / 本地备份」），看不出各自是什么。现在**一个用途一行**，
并在说明里标出路径与设备；两行落在同一文件系统时互相点名，免得有人把同一份剩余空间当两份花。

**2026-09-20 修正: 一次推了四条「定时任务 Xxx.yyy 接近预警值」**。四个每 2 秒的轮询任务共用一根调度线程,
被别的任务占了 7 秒就全部被判「超过 2 个周期未执行」, 恰好被 15 秒采样抓到, 服务重启后第一轮扫描 (2 分钟)
就推了四条。用户原话: 「不要用代号, 用实际的文字明确表达」「我没有设置过定时任务啊」。

| 面 | 做法 |
| --- | --- |
| 不误报 | 「多久没执行才算异常」= max(2 个周期, 10 分钟); 单根调度线程被某个任务占着时, 其余任务的「没执行」记为排队 (正常, 说明里写在等谁), 只有占线的那个按「疑似卡住」告警 (`ServerStatusProbe.jobReports`) |
| 说人话 | `ScheduledTaskCatalog` 给每个 `@Scheduled` 方法登记中文名称与一句话用途, 状态页任务列与通知一律用它, 程序标识只留在 key; `ScheduledTaskCatalogTest` 扫源码双向对账, 漏登记即红 |
| 通知文案 | 标题 = 一句话现状 (「后台任务「库存金额结算」已 30 分钟没有执行」); 正文 = 「这是平台内置、随服务自动运行的后台任务, 不需要任何人设置」+ 用途 + 现状 + 建议, **不再把标题抄进正文** (卡片只预览正文头两行); 「已恢复」也用名称不用 key |

## 四之六、员工报销计数与通知分离(2026-09-19)

报销使用一次 `/api/expense-claims/counts` 返回本人草稿、待修订、本人可审核及可付款的数量。
`TodoEntry.expenseMine` 归属 people，只累计本人草稿与驳回待修订；`expenseFinance` 归属 finance，
累计待审核和待付款，每张单同一时刻只在一个队列。审批列表、汇总与计数均排除申请人自审、自付，
待付款还排除本单审核人。无对应权限返回0且不查询该队列。
工作台今日概览中的报销待办同样排除本人申请及本人批准后需他人付款的记录，不能与入口队列使用两套回避口径。

钱流卡包含报销审批入口，工作台不再另放一张重复累计同一财务待办的直卡。本人列表的草稿与待修订
分段显示红徽章，处理中及历史集合使用中性口径。常驻 provider 60秒刷新并按身份隔离，业务写成功
主动失效缓存。通知已读、关闭弹窗或“稍后”都不清业务计数；只有业务状态变化才改变待办。

## 四之八、黄色「进行中」登记了哪些入口(2026-09-21，ADR-100)

分段计数**永不登记**(累加只认入口)，所以页面里的黄分段可以放开挑形态；
需要小心去重的只有**卡面/注册表入口**这一层。黄链目前只登记这些：

| 容器 | 入口 | 数什么 |
|---|---|---|
| 人事 | 我的访客 / 访客审批 / 我的报销 | 我已确认、这趟来访还没走完(HR 审批中 + 已通过待来访)；我已批准、访客还没来核验的申请；本人已提交、正在审批或待付款的报销 |
| 生产 | 生产管理 | 进行中的分析 / 根计划**批次**数(计划员视角) |
| 生产 | 我的车间任务 | 本人**生产中的执行段**数(车间工视角) |
| 研发 | 任务中心 | 已认领、正在做的任务(`IN_PROGRESS`) |
| 仓库 | 品质部检查结果 | 等待检查结果(货已收，等品质部出结论) |
| 采购 / 委外 | 任务中心 | 进行中 = 等待财务审核 + 财务已通过 + 财务驳回，与页内同段同数 |
| 销售 | 订单进度查询 | 在途订单数 = 待排产 + 生产中 + 出货待财审 + 等仓库出货 |

**刻意不登记**(登记了就是链内双计，每一条都有具体理由)：

| 不登记的 | 为什么 |
|---|---|
| 销售「出货 / 订货 / 报价 / 退货」四张单据卡 | 订单进度的「出货待财审 / 等仓库出货」本就是从出货单派生的(服务端 `progressStageExpr` 看 `shipment_*_qty`)，再按单据数一遍就是同一批出货翻倍 |
| 采购 / 委外的订货单卡 | 那些在途单据已经全在各自任务中心的 `IN_PROGRESS` 里 |
| 委外「回厂短交判定」卡 | 短交案件只挂在已回厂 / 在途的 `FINANCE_APPROVED` 订货单上，那些单已全在 `IN_PROGRESS` 里 |
| 钱流整个模块 | 财务的活清一色是审批队列：要么等财务动手(红)，要么球已经离开财务、落在采购 / 仓库 / 销售那几张卡上；在钱流再数一遍是跨卡双计 |
| 品质任务中心 | IQC / FQC 只有「待检(红)」与「已出结论(终态)」两档，没有中间的在办态。仓库侧「等待检查结果」由仓库那一条计一次(那是仓库在等品质部) |
| 仓库「出库任务中心 · 委外出库」的等子件到货任务(2026-09-22 ADR-103) | 这些委外订货单财务已批准、子件还没到, 已经全在委外任务中心的 `IN_PROGRESS` 黄数里(「待处理」段的 `WAITING_COMPONENT_STOCK` 锁行也计进同一枚黄)。仓库这边是同一张单换个部门再看一眼, 球没离开委外链, 与钱流那条同理: 仓库卡再数一遍是跨卡双计。所以黄枚只画在出库任务中心的大类行与「待出仓任务」小类行(`warehouseSubcontractOutboundWaitingComponentCountProvider`), hub「出库任务中心」卡与工作台仓库卡不带这枚黄; 契约用例 `in_progress_badge_registry_test` 钉住仓库容器只有「等待检查结果」一条 |
| HR 任务中心 / 信息变更审核 / 服务器状态 | 今日到期事项、纯审批队列、告警，都没有「在办」这个中间态 |
| 基础资料 / 报表 / 主档 / 历史只读页 | §二 的结论对黄色同样成立 |

「生产管理」与「我的车间任务」两条**都登记**是有意为之：它们不是同一批活的两次计数，
一个是计划员视角的批次、一个是车间工视角的工单段，读取范围也不同(全部可见 vs 仅指派给本人)；
这两张卡在红链里本来也是各登记各的。

## 五、后端计数端点的规矩

新增/扩展计数接口时：

- **一个模块一个 `/counts`**，返回一个小 record；不要一张卡一个端点。
  跨模块草稿走唯一的 `GET /api/documents/drafts/count`（21 类一次返回）。
- 必须复用该模块的 `DocumentAccessPolicy.nativeReadScope`，与列表页同口径。
- **无权限时返回 0 且不查库**（权限自卫），前端同样不渲染——两层一致。
- 必须廉价：走索引的 `count(*)`，不做 N+1 行级展开。
- 前端轮询统一 60s，并登记进登录/刷新时的失效清单
  （`invalidateWorkbenchBadgeCaches` / `rehydrateGlobalState`）。

## 四之七、父有红徽章, 子分段必有数; 财务退回件独立分段(2026-09-21)

用户两条反馈同源: 「出库任务中心父分类有红色通知徽章但子的没有」「财务退回的子分类没有徽章显示,
而且会放在草稿里面」。

**口径**:

1. 凡 hub 卡 / 任务中心大类挂了红徽章, 进去的小类行**每一段都要有数**: 等本人动手的段
   (草稿 / 财务已退回 / 待出库 / 待确认 …)红徽章, 还在流程里滚着的段(等待财务审核 /
   财务已通过待执行 / 生产中 / 等待检查结果 …)**黄色徽章**, 已经结束的(已审 / 已出库 /
   红冲 / 已驳回 …)中性括号; 「全部」与时间门控的「历史记录 / 历史单据」不挂
   (已出库本身就是历史, 不数两遍)。
   > 2026-09-21(ADR-100)修订: 本条原文把「等待财务审核」等在办档一并写成中性括号,
   > 现已拆成黄色一档。红/括号两档的判定不变。
   > 2026-09-21 追加(品质部检查结果踩出来的): 本条原文只管到**小类行**, 于是双维度页
   > (大类在上、小类在下)的**大类行**成了漏洞 —— 大类行只挂红那一枚时, 卡面的黄数字
   > 一进页面就在大类行上凭空消失, 点到当下没有在办单的那个大类只剩一张空表, 用户会
   > 以为徽章在骗人。口径补齐: **大类行同样要红黄两枚、黄左红右, 每枚都是本大类下同色
   > 小类之和**(`UtenFilterSegment.count` + `countForm` 挑红, 第二枚走 `inProgressCount`,
   > 不要自己拼 Row)。现有两处范本: 销售订单进度查询、仓库品质部检查结果。
2. **财务退回件不是草稿**: 出货单 / 采购订货 / 委外订货被财务退回后, 列表有自己的「财务已退回」段
   (红徽章), 草稿段与跨模块草稿计数都排除它(`DocumentDraftCountQueryService`: 出货只数销售未确认的
   两审草稿; 订货只数最新一条审批 case 既非 PENDING 也非 REJECTED 的单)。
3. hub 单据卡的红数字 = 页内红色分段之和: 销售出货 / 采购订货 / 委外订货三张卡 = 草稿 + 财务已退回
   (`UtenDraftBadge(withFinanceRejected: true)`, 数据 `GET /documents/finance-rejected/count`)。
   待办累加只认一次: 销售出货退回件新登记 `TodoEntry.salesShipmentFinanceRejected`; 采购 / 委外订货
   退回件已由任务中心 `FINANCE_REJECTED` 计入, 卡面只是同数展示, 不再登记。
4. 分段计数统一走 `GET /documents/status-counts?kind=<DraftDocKind>`(`DocumentStatusCountQueryService`,
   一条 SQL `COUNT(*) FILTER` 分桶, 与列表同一读范围; DRAFT 桶与草稿计数同一谓词), 前端
   `documentStatusCountsProvider(DocumentStatusScope)` autoDispose 随页面轮询, 列表重拉时 invalidate;
   不再各页 `list(size:1)` 凑数。仓库出库任务中心「销售出库」小类同理走 `GET /warehouse/sales-outbound/counts`。

自检: 打开任一有红徽章的 hub 卡, 页内红色分段之和 = 卡面数字; 财务退回一张单, 它从「草稿」消失、
出现在「财务已退回」并带红数, 卡面数字不变。
