# 工资付款事实桥与六流程接口

父任务拟在成本资产域稳态后并行交接。当前只有端口合同/方案，**不是工资付款功能完成**。前端/表单数据和截图最终由根归入Word培训说明。

唯一Java合同：`server/src/main/java/com/uten/imp/application/port/FinancePayrollPaymentPort.java`。六流程负责申请/原顺序角色、认领、源指纹/版本、干净付款凭据与批准支付；工资桥负责下面原工资事实、计提/负债清偿、资金与GL、确认/反审。不要复用采购AP控制科目，也不要从普通报销再计一次工资费用。

## 现有权威来源

- `payroll_batches`：`id/payroll_year/payroll_month/department_id/status/generated_by/headcount/gross_income/total_deduction/net_income/version`。
- `payroll_slips`：`id/batch_id/employee_id/employee_code_snapshot/employee_name_snapshot/department_id_snapshot/active/gross_income/total_deduction/net_income/version`。
- `payroll_items`：`id/slip_id/line_no/item_code/name/item_type/amount/source_type/description`。扣款代码按真实行读取，不硬猜“社保/税/罚款”等实际分类。
- `PayrollService`目前只有生成→提交→审核→发布，没有工资实际支付会计桥。仅APPROVED/PUBLISHED且active的原批次/工资行可作来源，发布不等于已支付。
- `AccountFlowLedgerService`是资金账户唯一写入口，`GlPostingService.lockAutoProjectionPeriod`是原账期锁。V997 `fn_finance_cost_expense_style_allowed(uuid)`允许EXPENSE末级或已明确对应4101的ACCOUNT末级；加工人工归制造费用已由财务确认。

## 金额和状态合同

1. `source(batchId, forUpdate)`先锁原批次（如果请求forUpdate），再读取原应发/扣款/实发及原项；源指纹包括实际工资内容/有效行/来源身份，不因仅发布或已读而无故漂移。必须核对批次与行汇总、应发−原扣款=实发，不能以缺失金额补0。
2. `prepare`保存财务明确的科目/计提模式/原依据元数据。费用按真实部门归属，应付工资用明确负债末级，扣款按真实item_code逐项配置；允许的类别/辅助往来必须有明确会计含义，缺对应返回Issue，不按同名猜。Instruction不带任何可覆盖原工资的金额。
3. `NATIVE_APPROVED_PAYROLL`由原工资事实唯一计提（借明确部门费用/制造成本，贷应付工资和真实扣款对应科目）；`EXISTING_CONFIRMED_LIABILITY`必须追到已确认计提/期初负债来源，不能再计一次费用。不能只凭同月份/相同金额认定已有计提；也不能因新申请就重提历史工资。原批次只允许一份权威计提，支付反审后再次支付不能再提费用。
4. `execute`只在应用流程已批准、原指纹/冻结Instruction仍有效、真实银行回单/现金签收为CLEAN后调用；从源实发取本金。源工资目前为本位币，账户/币种必须经原账户账本核验，不能凭空改外币工资。银行实扣=原实发+明确实际手续费；手续费按独立明确费用科目和真实凭据，不用汇差/工资扣款轧平。计提、实际账户流水与GL在同一事务里幂等保存。
5. 实际工资付款借应付工资贷资金；手续费独立。原扣款沿原工资事实及明确对应入账，不擅改成普通费用、不重新计算税费、不把完整COGS再减一次工费。若扣款涉及员工往来，必须有明确辅助身份/核销来源，不能只动一个猜测科目冒充已清往来。
6. Result状态建议`POSTED_PENDING_CONFIRMATION/CONFIRMED/REVERSED`。`confirm`确认既有原支付凭证，不新增费用或资金流水；`reverse`仅依原事实对称红冲一次并保留历史，不重算工资、不悄悄撤工资计提。后续再付要求新的授权/请求身份，旧请求重放仍返回旧结果。所有会计期间/依赖/权限反审保护沿现有公共能力。

## 权限/锁与接口职责

- 人事提交源批次：沿`payroll:generate`/原批次查看资格；六流程原工资路径为“人事附凭证→财务吴兰梅复核→总经办王经理批准支付”。实际人物在设置内以UUID配置。
- 审批：六流程按当前节点、员工/账号有效性和`expense:approve`等既有/精确权限核验，工资详情只给本申请人/当前明确节点，不能因此放开所有员工薪资。
- 执行：实际支付者和最终批准人分离，除流程授权外仍需执行源的财务/薪资支付权限。准确新增权限若需要，应与六流程端点/前端可见性同源登记。
- `prepare/execute/confirm/reverse`是可信应用调用的端口，不允许浏览器直接传任意工资金额。工资桥还应复核源状态、映射叶子/类别、指纹、唯一计提/支付和回执身份。
- 锁顺序先原工资header→申请/节点→任务认领；真正过账再沿公共账期→账户顺序。读取人员姓名等会触发Hibernate flush的查询，须在修改多字段会计状态前完成，避免半成品状态落库。

## 必验（隔离数据库）

非零应发/多类扣款/净额、多个部门、明确4101成本科目；已有计提不能重复；未知映射/无效来源/工资更正后待核；两次请求只记一次；银行实扣/手续费守恒；计提/付款分离；确认/反审/再付保留原历史；锁定账期/下游依赖阻断；不能把工资桥接成供应商AP或一般报销。实际Web/Flutter页面、极端操作和Word截图仍须后续共同验收。

## 端口补充（回应B三个源边界）

1. `Instruction.deductionSettlements`按原payrollItemId明确auxiliaryId与`OpenItemReference(kind,sourceId,allocationNo,sourceFingerprint)`。不得外部覆盖扣款金额。原账GL分配用明确entry UUID+allocation_no，原业务未结项用其真实源种类/UUID；与原slip.employeeId必须是同一明确辅助身份。没有可核对的原往来/核销桥时返回Issue，不许仅贷一个ACCOUNT科目就宣称员工借款已结。
2. 已有计提必须指定`ExistingLiabilityBasis`：GROSS_BEFORE_DEDUCTIONS或NET_AFTER_DEDUCTIONS，并列出具体原工资负债分录`existingLiabilityLines`（原行指纹和明确分配额）+不可变原凭据`originalEvidenceIds`。gross模式先依原扣款拆分再付net；net模式不能又拆一次。准备记录绑定native batch UUID/fingerprint和财务明确确认的原批次依据，不按同月/同额匹配。原源行额度还需防多批重复认领；原负债是否仍未清偿也需明确核对，不能把贷方发生直接当未付余额。
3. 新`FinanceApplicationPaymentAuthorityPort`由申请域实现。B依赖该只读接口获取requirePayrollPreparation/Execution/Confirmation/Reversal的Permit，不直接猜流程表结构。准备须当前FINANCE_REVIEW_2及本人有效认领；执行须流程APPROVED、原工资/冻结Instruction指纹、CLEAN付款凭据、实际支付人不是申请人/最终批准人。确认/反审依其精确动作和原支付身份，不擅加原要求未规定的“确认人必须不同支付人”限制。账期/资金/原源依赖保护仍由工资桥负责。

当前新增窄权限为finance_application:view/apply/review/execute/confirm/reverse（设置仍expense:settings）。新入口不要求公司报表finance_report:view+finance:view:all；只读不得产生任务/通知。原工资细目只在本批申请业务目的内给明确参与者，不能凭新增查看码开放全部员工薪资。
