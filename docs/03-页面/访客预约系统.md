# 访客预约管理系统

> 外部访客来访的完整闭环：**入口选择 → 访客手机验证码预约 → HR 审批 → 签名二维码凭证 → 保安扫码核验**。
> 前后端打通（Flutter + Spring Boot），双主体 JWT 鉴权，pgcrypto 加密 PII，HMAC 签名二维码防伪造。

---

## 1. 角色与入口

| 角色 | 入口 | 能力 |
|---|---|---|
| 访客（外部） | 入口页「访客登录」 | 手机号验证码注册/登录、提交来访申请、查看申请状态、查看已批准二维码 |
| HR / admin | 工作台「访客审批」 | 审批申请（批准/拒绝/转接待人确认） |
| 被访人（普通员工） | 工作台「我的访客」 | 确认/拒绝转给自己的访客（可选两级环节） |
| 保安（security）/ admin | 工作台「安保」 | 扫码核验（绿放行/红禁止）、签到 |

**入口选择页**（`/entry`，登录前默认页）：两个按钮分流——
- 「内部人员登录」→ 现有员工登录页（账号密码）
- 「访客登录」→ 访客手机验证码登录页

## 2. 访客端流程

1. **注册/登录**：手机号 → 获取验证码（后端生成 6 位；dev log 网关只记手机号尾四位、不记录验证码，只有 dev profile 且显式开启开发响应时才返回 `devCode`；默认/生产禁止暴露）→ 输入验证码 → 后端校验并签发访客 JWT。
   - **员工检测**：登录时后端查 `employee_sensitive.phone_hash`，命中则拦截 → 提示「该手机号为优腾员工账号，请走员工通道」。
   - 注册即创建访客账号，自动生成 `visitor_no`（V + 手机尾4 + 随机2位）。
2. **提交来访申请**：姓名 / 身份证（选填）/ 来访单位 / 来访事由 / 是否开车 + 车牌 / 接待部门 + 接待人（从员工目录选）/ 计划到访时间。
   - **被访人目录**自动排除离职员工（`status != resigned`）。
3. **查看状态**：申请中 / 待接待人确认 / 已批准 / 已拒绝 / 已签到。本人列表使用服务端分页
   `{items,page,size,total,totalPages}`，按 `createdAt DESC,id DESC` 稳定排序，单页最多 100 条。
4. **已批准** → 显示**入厂二维码凭证**（后端 HMAC 签名）+ 下方**6位通行码**（二维码扫不了/电脑无摄像头时，保安可手动输入该数字核验）。

## 3. 审批与核验流程

- **HR 审批**：列表（待审批/已批准/已拒绝）→ 详情 → 批准 / 拒绝（填原因）/ **转接待人确认**（可选两级）。
- **被访人确认**：员工在「我的访客」看到转给自己的申请 → 同意接待 / 拒绝。同意后回 HR 最终批准。
- **审批事件 → 工作通知**：每个流转动作完成后，经 `lib/features/visitor_approval/providers/visitor_notice_bridge.dart` 自动生成工作类 Notice（入通知收件箱 + 刷新角标 + 按重要度弹到达提醒）：
  - HR 批准 → `approval / normal` → 顶部弹条「审批通过」
  - HR 驳回 → `approval / important` → **居中橙色弹窗**「审批驳回」（必须被看见）
  - HR 转接待人 → `workflow / normal` → 顶部弹条「流程流转」
  - 被访人确认接待 → `workflow / normal` → 顶部弹条；被访人拒绝 → `approval / important` → 居中弹窗
  - 接真后端推送后，由服务端推送给相关接收端，前端落点即本桥（见 [UtenNotify §七](../02-组件库/UtenNotify.md)）。
- **保安核验**：`mobile_scanner` 扫二维码，或手动**输入6位通行码**（二维码扫不了时）→ 后端验签/查码 + 查状态 → **绿（放行，可签到）/ 红（禁止 + 原因）** → 签到后状态变 `checkedIn`，再核验变红「已使用」。

## 4. 状态机

```
pending ──forward──> hostReviewing ──hostConfirm──> pending(hostConfirmed=true)
   │                       └──hostReject──> rejected
   ├──approve──> approved ──checkIn──> checkedIn
   └──reject────> rejected
```
（`cancelled` 预留）

## 5. 数据模型（后端，V12__visitor.sql）

| 表 | 说明 |
|---|---|
| `visitor_accounts` | 访客账号：phone_enc/phone_hash(HMAC)/name/visitor_no/status |
| `visitor_sms_codes` | 短信验证码（sha256 入库，短期，限流） |
| `visitor_refresh_tokens` | 访客刷新令牌（独立于员工，轮换+重用检测） |
| `visitor_applications` | 来访申请：访客/事由/车牌/接待人/状态/qr_token/审批信息 |
| `visitor_approval_steps` | 审批轨迹（submit/forward/hostConfirm/approve/reject/checkIn） |

PII（手机/身份证）走 pgcrypto 加密 + HMAC 查重，与员工 `employee_sensitive` 范式一致。

## 6. 安全设计

- **双主体 JWT**：员工 `typ=staff`、访客 `typ=visitor`；`JwtAuthFilter` 按 typ 分支复查账号状态；
  权限点天然隔离（访客 JWT 只含 `visitor:*`）。JWT 只签名、不加密；新 visitor access token 的
  `acc/vno` 均为 `visitorNo`，`avs` 只作头像 seed，不携带原手机号。登录、刷新与 Flutter 冷启动
  恢复均已同步，旧 token 仅作短期兼容。
- **签名二维码 + 通行码**：二维码 `base64({aid,exp}).HMAC`（扫码，防伪造/截图转借）+ 6位 `passcode`（手动输入，降级方案）；均 7 天有效，签到后失效。passcode 生成时尽量全局唯一（冲突重生成）。
- **员工检测**：手机号命中员工 → 拦截（防员工绕过内部登录）。
- **脱敏与对象范围**：访客只能查看自己的申请；staff 端按权限点和用途返回所需字段，不以角色名作为授权；日志不得记录完整手机、身份证或验证码。
- **审计**：visitor 表挂 `fn_audit` 触发器；登录/员工检测走 `AuditService.logExplicit`。
- **限流**：短信码 60s/条 + 每日上限 + 尝试 5 次失效；同手机号发送先以 HMAC 派生键取得
  PostgreSQL transaction advisory lock，再在本地签发事务内复查最近发送与日计数并提交 OTP
  哈希，之后才调用短信供应商，避免供应商已接收而本地回滚；明确拒绝才删除签发记录，网络结果
  不确定时保留记录且不自动重发。原始手机号不作为数据库锁键。鉴权入口使用“手机号低阈值 +
  IP 高阈值”双桶，并把发码和登录 namespace 分开，避免园区 NAT/运营商 CGNAT 互相误伤。

## 7. 路由

| 路径 | 页面 | 守卫 |
|---|---|---|
| `/entry` | 入口选择 | 两端未登录 |
| `/visitor/login` `/home` `/apply` `/apply/:id` | 访客自助 | 访客 session |
| `/visitor-approval` `/:id` | HR 审批 | `visitor:approve` |
| `/my-visitors` | 被访人确认 | `visitor:approve` |
| `/security/scan` | 保安扫码 | `visitor:check-in` |

访客流程独立于 ShellRoute（有自己的 session）；审批/被访人/保安在 ShellRoute 内（员工登录后）。

## 8. 后端接口（`/api`）

- 访客鉴权（permitAll）：`POST /visitor/auth/send-code|login|refresh|logout`
- 访客自助（visitor 主体）：`GET /visitor/applications/mine?status=&page=&size=` `/{id}`、`POST /visitor/applications`
- 被访人目录（authenticated）：`GET /visitor/directory/departments|employees`
- 审批（`visitor:approve`）：`GET /visitor-approval?status=&page=&size=` `/{id}`
  `POST /{id}/action|host-confirm` `GET /as-host?status=&page=&size=`。HR 与被访人队列均只返回
  当前页；`as-host` 始终按当前员工过滤，未传状态时只查 `hostReviewing`
- 保安核验（`visitor:check-in`）：`POST /security/verify` `/check-in/{appId}`
- 黑名单（`visitor:blacklist`）：后端存在 `POST /security/blacklist/{visitorId}`；当前 Flutter
  扫码/审批/详情页没有拉黑按钮或独立管理页。

## 9. 短信验证码

开发期 dev profile 可用 `uten.sms.provider=log`，但日志只记录手机号尾四位，不记录验证码；只有
显式启用开发响应时 send-code 才返回 `devCode`，且不真实发送。默认与生产缺省为 `disabled`。
生产显式选择 `aliyun` 后使用阿里云国内短信 V2 SDK `dysmsapi20170525:4.6.0`，AccessKey、签名、
模板和 endpoint 缺失会 fail-fast；客户端单例复用、模板参数 JSON 序列化、SDK 自动重试关闭，
日志不记录完整手机号、验证码或密钥。同号发送的 HMAC advisory lock 已有源码与 2 项单元测试，
仍须在真实 PostgreSQL 双连接/多实例下证明限流不能被并发穿透，并完成模板审核、发送/失败/
余额、故障与告警验收。

访客 access JWT 的 PII 最小化测试 `JwtVisitorPiiMinimizationTest` 已加入：断言 `acc/vno` 为
`visitorNo`、包含头像 `avs` 且没有 `phone` claim。定向 Flutter analyze 为 0；仍须完整 Maven、
登录/刷新实测，以及确认切换前旧 access token 已过期或清退。

## 10. 长周期分页

- V139 为本人申请、本人+状态、全局状态队列、被访人+状态队列建立 4 个 `is_deleted=false`
  部分复合索引，排序统一为 `created_at DESC,id DESC`。
- 列表页把当前页涉及的员工/部门一次批量 JOIN FETCH，避免逐条查员工造成 N+1。
- Flutter 本人、HR 审批、被访人三个页面复用分页条，只保留当前页。预约时间冲突检查只逐页
  拉取 `pending/hostReviewing/approved/checkedIn` 活跃状态，不再把多年已拒绝/已结束历史全部下载。
- 预约/认证/审批请求已启用 Bean Validation；提交时后端校验在职被访人、从被访人推导部门、
  离开时间晚于到访、驾车必须有车牌，并禁止客户端覆盖短信验证手机号。
- 被访人详情读取执行对象级校验：只有申请的实际 host 可读；审批者可读全部，其他 host 按不存在
  处理，防止 UUID 枚举。
- 仍须在生产同构数据验证 count、深页、状态选择性、索引写放大和 P95/P99。员工目录虽然仍返回
  `List`，但已按姓名/id 稳定排序、数据库 `LIMIT 50` 并批量加载部门；大组织仍应改为带
  total/truncated 的服务端分页搜索。

## 11. 当前交付边界

明确的首发访客闭环是预约、审批、被访人确认、核验和签到。`visitor:blacklist` 当前只有后端能力，
页面需求没有定义从哪种访客状态发起、拉黑原因、解除流程、列表查询和误操作恢复。产品若将黑名单
纳入首发，必须先补齐这些规则、Flutter UI、独立权限显隐、审计和正反向 E2E；否则应明确为
“后端预留运营能力”，不得把接口存在写成用户功能完成。
