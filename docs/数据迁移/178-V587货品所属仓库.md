## 一、这一列解决什么

新 ERP 导出的产品列表里，每个货品都带一个「所属仓库」：这批货平时归哪个仓管。
平台一直没有这个字段。计划员在物料分析里下达采购 / 委外 / 车间时，看不出这行料
归哪个仓，只能靠记；仓库那边也无法按归属把货分开看。

```sql
ALTER TABLE goods
    ADD COLUMN IF NOT EXISTS owning_warehouse_id UUID;

CREATE INDEX IF NOT EXISTS idx_goods_owning_warehouse
    ON goods(owning_warehouse_id)
    WHERE owning_warehouse_id IS NOT NULL;

ALTER TABLE goods
    ADD CONSTRAINT fk_goods_owning_warehouse
        FOREIGN KEY (owning_warehouse_id) REFERENCES warehouses(id)
        ON DELETE RESTRICT
        NOT VALID;

ALTER TABLE goods
    VALIDATE CONSTRAINT fk_goods_owning_warehouse;
```

## 二、为什么叫 owning_warehouse_id 而不是 warehouse_id

平台里 `warehouse_id` 已经是**单据落点仓**的通名(`stock_movements`、
`warehouse_goods_place_preferences` 等 6 张表都用它)，而物料分析页另有一套
**分析范围仓**(前端偏好键 `production.materialAnalysis.warehouses`)。
再叫 `warehouse_id`，三个不同语义会在同一屏里撞名——物料分析表里一个
「仓库」列，用户分不清是「这行料归谁管」「这批要发到哪个仓」还是
「本次分析统计了哪几个仓」。`owning_` 前缀把**归属**与**落点**、**范围**分开。

## 三、为什么不限叶子仓

V476 立过「单据 / 收发存只允许落到具体(叶子)仓，父仓仅作查询聚合与下拉分组」。
那条约束是给**过账**定的。所属仓库是主档分类，不产生任何库存事实；而且
「成品仓库」这类合法值本身可能挂着不良子仓，leaf-only 会把一个正当取值拒掉。
因此数据库只有外键(存在且未软删由服务端校验)，不加叶子 CHECK。

## 四、回填：为什么不在迁移里，下次数据迁移要做什么

名称→仓库的对照数据在 `product lists/` 三个 `.xls` 里，该目录被
`.gitignore` 第 86 行明确排除(真实业务数据，绝不入库)。迁移一旦内嵌对照，
等于把那批数据提交进仓库，还会让不同环境跑出不同结果。所以：

**迁移只建列，回填走 `server/legacy_migration/import_product_lists.py`。**

对照数据实测(2026-09-15，三份 Excel 合并)：

| 口径 | 数值 |
| --- | --- |
| Excel 数据行 | 23104 |
| 带「所属仓库」的行 | 22315 |
| 去重后的产品名称 | 17010 |
| **同名映射到两个不同仓库的冲突** | **0** |
| 取值 | 五金仓库 5316 / 塑胶仓库 8262 / 成品仓库 6771 / 包材仓库 1962 / 五金车间 4 |

匹配键是**产品名称**(用户 2026-09-15 明确指定)，不是产品编号：既有的按编号
匹配在 22488 个编号里只命中 85 个，按名称在开发库 117 个货品上命中 84 个。
名称去空白归一后命中数不变，说明两边名称本来就是干净的。

**下次数据迁移必须一起做的两件事**：

1. 跑 `python server/legacy_migration/import_product_lists.py --apply`
   ——该脚本已带所属仓库段：按名称匹配、只填空(不覆盖用户在界面上改过的值)、
   仓库按名称对 `warehouses`，缺的仓库自动建 `auto_created=true` 存根。
2. 核对 `product lists/import_report/warehouse_unmatched.csv`：
   里面是 Excel 有名称、库里没有同名货品的行，属正常差集，不必强行灌入。

> 开发库缺 `塑胶仓库` / `包材仓库` / `五金车间` 三个仓库主档(只有五金仓库 C01
> 与成品仓库 C04)。脚本会按名称补建存根，正式库若已有同名仓库则直接复用。

## 四之二、平台侧已落地的读写面

| 面 | 落点 |
| --- | --- |
| 货品主档读写 | `Goods.owningWarehouse` / `GoodsSaveRequest.owningWarehouseId`(presence 机制：不传=不动，传 null=清空) / `GoodsDetail`+`GoodsListItem`+`GoodsDictItem` 末尾追加 / 导出列「所属仓库」/ 导入表头登记为 ignored 哨兵 |
| 分析快照 | `MaterialView` 与 `ProductView` 末尾各加 `owningWarehouseId`+`owningWarehouseName`，两段原生 SQL 各 LEFT JOIN 一次 warehouses |
| 写回端点 | `PUT /api/production/material-analyses/goods-owning-warehouses`，体 `[{goodsId, owningWarehouseId}]`，返回 `{updated, skipped}`；单次上限 200；仓库无效整批 VALIDATION_FAILED；货品不存在/已软删/值没变 = skipped |
| 权限 | 复用 `production_material_analysis:view` + `production_material_analysis:route`。所属仓库与供料路线是同一类「计划员在分析页维护的货品级计划属性」，同一批人同一把锁；另铸权限码要再发迁移并登记 V228 权限目录，不值当 |
| 界面 | 物料分析主表、下达采购 / 下达委外 / 下达车间三个分桶、「父件+下层一起下单」整页，五处都在**供料路线之后**挂同一列，可点可改可筛；货品主档列表/详情/编辑、即时库存也各加一列 |
| 刻意不做 | 写成功后**不刷分析快照**、不进快照指纹、不 bump 版本——否则改一个归属就让别人正在编辑的分析 CAS 令牌失效 |

回归：`GoodsOwningWarehouseWritePostgresTest`(真 PostgreSQL 7 条，覆盖清空走
`CAST(? AS uuid)`、无变化不推版本、软删跳过、仓库无效整批拒、超 200 拒、同货品去重)。
