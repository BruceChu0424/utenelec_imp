# ADR-182: 货品操作历史与可控撤回

- 日期: 2026-10-16
- 状态: 源码候选，正式环境未升级
- 迁移: V871

## 背景

货品资料原有入口只撤回最近导入，查询未按操作人隔离，撤回也没有可靠的后续修改快照比较。批量删除、启停、普通编辑和组装信息维护缺少统一的撤回与取消撤回入口。

## 决策

固定服务器路由及目标表白名单，在原写事务内捕获变更，按操作人、请求和事务聚合。历史摘要只返回本人最近 10 次操作及撤回事件，不返回原始快照。完整记录仍遵守统一审计和保留规则。

撤回使用原 UUID 和 before/after 谱系；目标快照、原权限、当前身份、引用关系及业务约束必须全部满足。任何冲突使整个回放事务失败。删除与恢复均沿软删除语义，不回退版本、审计时间和编号序列。只有系统自身已验证的回放可以更新前后历史的期望状态；外部修改后即使值相同，也不能忽略版本变化。

取消撤回恢复上次成功撤回。新写入使旧取消撤回分支失效，成功 UNDO/REDO 追加事件。普通资料维护和专用业务命令保持不同边界，发料转换、实际学习、成本确认及附件原件不能通过通用快照回放绕过业务流程。

界面应用 `frontend-design` 并复用现有 Uten 主题与组件。右上角显示文字“撤回”“取消撤回”，历史展示具体动作、目标、时间、数量及状态。每次执行均另弹确认框，选择历史条目不代表确认；等待服务器回执期间禁止重复提交。

## 验证与放行

以隔离 PostgreSQL 迁移、事务回放及权限/冲突回归核对持久数据，以 Flutter 测试核对选择、二次确认、取消、加载失败和窄屏大字号。通过源码测试后，正式发布仍需前向迁移及岗位验收，不能把隔离测试视为公司库已升级。详细范围见[货品操作历史](../03-页面/货品操作历史.md)。

## 多账号与并发补充

历史属于认证账号 UUID，不随员工姓名、设备或资料交接转让。新设备登录继承原账号历史，同时遵守系统已有的单设备会话吊销规则。只读能力、资料可见范围、原动作权限与当前可写范围分别判定；前端每次权限集合或超管标志变化都重新取得能力。

参考 [Yjs 的事务来源](https://docs.yjs.dev/api/undo-manager)及 [Figma 的多人撤回](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/#implementing-undo)，保留服务器整行冲突检查和按实际变化字段回放；对他人后续修改采取明确拒绝的策略，避免未经领域定义的自动字段合并。

通过通用 `TransactionWritePreparationPort` 在事务审计上下文绑定后、业务 DML 前执行货品模块的个人命令协调，基础设施不依赖业务模块。正向命令和反向命令统一先取得个人锁；反向命令对业务表使用 NOWAIT，竞争时返回可重试冲突并完整回滚。原始 SQL 未预先协调时，捕获触发器只尝试非阻塞加锁，失败则中止事务，不能持有业务行再等待个人锁。此设计防止分类、导入、普通货品编辑之间的锁顺序相反。
