# 采购与委外到货退换货实现与验收

本页合并原 IQC 资金切片计划、两份 V510 续作记录和实际贷项前端交接，维护当前规则、实现/API 与专项证据。原未发布 V510 已顺延为正式 V518；当前状态只看[统一验收记录](2026-09-07-全平台本地审计与整改验收.md)，本页不维护另一份任务进度。

## 正常到货、实退与补回

仓库登记真实到货，品质 PASS 只形成合格待入库量，仓库实际接收后才成为可用库存。实物退回与供应商贷项分别留证；免费补回履行原供应商义务，不能重复立应付。

| 来源 | 本次新增 AP | 承接和结清 |
|---|---|---|
| 原失败份额未取得贷项 | 0，不生成零 AP | 沿原资金和实物来源，合格且实际入库后结清。 |
| 原失败份额已取得贷项 | 只按已贷份额重新计款 | 新收货建立新的商业取得；旧贷项仍保留。 |
| 部分贷项、部分免费补回 | 只计 CREDIT_REPURCHASE 部分 | 一行可冻结多个 STANDARD/NO_CHARGE/CREDIT_REPURCHASE 切片。 |
| 免费补回再次 FAIL | 不新增 AP | 沿原资金根建立新品质代际；必须本代实际退回后才能再补/再贷。 |
| 历史来源不明 | 不改旧账 | 保留原凭证并待核对，不能伪造审批、funding 或默认免费。 |

原订 20×50、实退 8、免费补回 8，最终 AP 应保持 1000，不是 1400。已贷 400 再重新计款 400 的对照也应为 1000。真实反例为 `server/target/procurement-iqc-money-and-sc-return-r1.log`，失败断言不能放宽或将收货名义价格改成 0。

到货行 `replacementIntent` 区分 NORMAL 与 RETURN_REPLACEMENT：前者只占正常未到池，后者先按同订单有效退回案 return_date+UUID 顺序占补回池、余量再占正常池。有两种可能时必须明确，不用“是否超过订货总量”猜来源；不同意图逐行累计。正常超到仍走实际超到审批，不能被已退额度掩盖。当前普通/批量到货页的“自动识别/正常/先补退货”入口及测试状态以统一验收记录为准。

补回预占与贷项占用互斥，未合格实收不能显示已结清。反向追加事实，不删除原片；已被下一代使用的来源不能直接抹除。部分凭证可以反向，但一张实际凭证跨多个案件时必须一起反向。

委外加工费与公司自有材料分开。加工费 1000+材料 600，失败 8/20 对应保管价值 640；免费补回承接旧价值，AP 为 0 不代表库存为 0；贷项只撤对应加工费，材料仍在真实保管/在制链。实现见[库存实际成本接线](库存实际成本接线与验收.md)。

## 实际金额和共同账面计划

实际贷项头原币 A 由真实供应商凭证确定，同一原 AP 下可以明确多个 case/version/qty/A 分项；分项 A 必须精确合计为头 A。用户数量与不合格名义金额都不能自动替代实际贷项金额。A 最多 24 位有效小数，账面 B 最多 30 位，绝对值小于 10^40；完整有限值不裁剪，详见[财务原始金额口径](../07-业务链路/2026-09-07-财务原始金额与精确分摊口径.md)。

[ProcurementCreditBookAllocationPort](../../server/src/main/java/com/uten/imp/application/port/ProcurementCreditBookAllocationPort.java) 由[共同 planner](../../server/src/main/java/com/uten/imp/features/finance/payables/ProcurementCreditBookAllocationService.java)实现。plan 返回来源原始、已分、剩余 A/B、头 A/B、抵销 A/B、贷项剩余及 BookBasis。头保存完整 `book_allocation_plan` JSONB，负 AP 用头 B；抵销只消费 `applyOffset` 的同一冻结计划，不能再算一遍比例制造 FX。

头 B 按 PostgreSQL 的 UUID 字节顺序分配，Java 使用规范UUID文本排序，不能使用有符号的 `UUID.compareTo` 改变先后关系。有限值原样保留，非有限内部账面分配向零到 30 位且末项取得完整余额。`procurement_iqc_credit_case_allocations` 保存每项实际 A/B 与头内分配前后余额。funding 片按真实 FAIL event 时间和 UUID 取精确数量，只保存来源/份额/关联分项；非有限金额投影为 NULL，不能当实际 0 或生成零 AP。

共同计划由 V519 在头 INSERT 前比较当前来源，并延迟验证金额守恒及 offset 一致性。SQL 和服务都要拒绝重复 case、错 AP、超出本代已实退可用份额、过期版本/hash。确认按公共商业前缀及 case 顺序锁行，整笔原子更新。来源余额发生变化后必须重预览；不将正常除不尽的分摊永久卡住。

实际入库事务预留 movement UUID → 插入真实 stock item → settleStockIn → `StockService.recordMovementWithId`，携 `ProcurementStockIn(stockItemId)`。数据库以精确延迟 FK 和身份/数量/重量守卫保持同事务一致，不能关闭守卫或用旧函数整段覆盖。

API 前缀 `/api/procurement/iqc-rejections/{id}`：

- `POST /preview-credit` 接收与确认相同请求，hash 可空；只读返回 bookAllocationHash、头 A/B、offset A/B、creditRemaining A/B、sourceBefore/sourceAfter A/B 以及 caseAllocations 的数量、实际 A/B 和前后余额。
- `POST /confirm-credit` 为 10 字段：expectedVersion、commandId、creditReference、creditDate、reason、baseQty、actualAmountOriginal、sourceApLedgerId、allocations、expectedBookAllocationHash。每项 allocation 为 caseId/expectedVersion/baseQty/amountOriginal。前端总 baseQty 为 null，避免混合单位合成假总量；每案数量明确显示自己的基本单位。
- `POST /reverse`：expectedVersion、commandId、reason、creditDocumentId；明确一凭证全部分项反向。旧历史构造器/哈希兼容只用于已有路径，新 funded 确认不能缺实际金额、分项或预览。

CaseDetail 包含 resolution、creditDocuments、creditSources，来源提供原 AP 原始/已贷/剩余 A 和可用案件；凭证显示冻结 A/B、余额与来源。缺金额查看权时金额为 null、来源为空，不能通过 Exact 字符串绕过脱敏。预览/确认需要 view+confirm_credit+amount:view；反向还要 reverse，并核对服务端 allowedActions/canReverse。

前端全部 A、数量、B 和余额使用十进制原文；A 用 BigInt 精确校验 24 位与合计相等，数量 4 位，B 不裁位。改来源/案件/金额/数量/凭证信息使预览失效，光标移动不失效；迟到的旧异步预览丢弃。提交中不重复发送，网络结果不明保留 command UUID 和原 payload/hash 重试；明确冲突后刷新来源版本并重预览，保留用户填写原文。说明与错误沿 `UtenInputDecoration`/`UtenDropdownField` 放在框内。

## 正式迁移与历史兼容

正式入口为 [V518](../../server/src/main/resources/db/migration/V518__procurement_iqc_replacement_consideration.sql)，依赖 V516 已有 replacement_intent，再加合法值约束；[V519](../../server/src/main/resources/db/migration/V519__financial_actual_amounts_and_book_allocations.sql)补共同 book 守卫，V517 接实际价值位置。迁移 normal order 加载，不使用 outOfOrder/repair，也不能恢复已撤销的 V512 自动尾差损益原型。

V518 包含 10 张明确 CLEAR 的事实表：receipt consideration、quality consideration、funding slices、credit documents、credit case allocations、credit slices、stock consideration、funding settlements、consideration reversals、review approvals。完整表名及 ALWAYS/来源/容量守卫以 SQL 为准；旧版本记录的 7/9 表数量已被替代。

共享 `fn_migrate_financial_amount_columns(JSONB)` 接受显式 table/column/schema 与可选 kind=actual/book；默认 local、amount_balance、amount_settled 为 book。它保留 view/MV 依赖拓扑、owner/ACL/grant-option、comments、reloptions、MV 索引/填充状态及真实 base trigger 定义/启用态，DROP RESTRICT 而非 CASCADE；列 ACL、额外规则/security label、委托 grantor、继承或非正常 trigger 等不支持情形先拒绝。临时重建只做 DDL，不插业务事实。V519 复用同函数，不复制另一套算法。

原 21 列包括 P/SC order/receipt 头和行金额、approval amount snapshot 及四个 price；case 和 physical allocation 的六个金额投影也去 typmod，历史值不改。单价 10 位/14 位整数、数量 4、汇率 6 的输入域保持。A/B 分别使用 `fn_financial_amount_is_exact` 与 `fn_financial_book_amount_is_exact`。

历史未 funded 案件不能按旧派生金额新建实际贷项，但原已确认凭证仍能按原快照反向。`ProcurementConsiderationCorrectionEvidencePort` 是证据合同，不能凭合同存在就宣称已有可操作历史核对流程；历史来源补全及普通 P/SC 退货共同 book 仍须按统一计划完成。
