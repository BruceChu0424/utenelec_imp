# ADR-060：单维护者简化发布链与旧发布链退役

- 状态：已接受（2026-09-01）
- 决策人：Bruce（唯一维护者）
- 取代：ADR-044（单维护者内部测试离线发布例外）及 `deploy/` 重链在 internal-test 范围内的操作效力
- 关联：[ADR-031 本地云端单主库部署架构](ADR-031-本地云端单主库部署架构.md)、[deploy/simple/RUNBOOK.zh-CN.md](../../deploy/simple/RUNBOOK.zh-CN.md)

## 背景

公司开发和运维只有一名维护者。2026-08 以来按多人大企业标准设计的发布链
（离线签名设备、五把分离密钥、H01–H12 带外证据、OSS OIDC/WORM create-only 仪式、
retention/配额/告警作为启用前置）始终没有产出任何一次服务器部署：目标机持续 NO-GO，
员工始终没有 ERP 可用。复杂度本身成为最大的交付风险——单人无法执行的流程等于没有流程。

## 决策

### 1. 代码托管迁移

- 主仓库迁移到个人私有仓库 `BruceChu0424/utenelec_imp`，`main` 即开发主干，保留全部提交历史。
- 旧组织仓库 `UTEN-ELECTRICAL/uten_imp` 归档为只读备份，不再作为操作对象。
- CI 质量门禁（quality.yml / codeql.yml / osv-scanner.yml）原样保留并在新仓库继续生效；
  旧 `release.yml` 的 `v*` tag 自动触发摘除（文件与其余旧 workflow 全文保留为参考，
  防止与 simple-release.yml 在同一 tag 上双跑）。

### 2. 简化发布链（deploy/simple/）

```
git tag vYYYY.MM.DD-N && git push origin v…        【维护者，任意地点】
        │
GitHub Actions simple-release.yml
  构建（双 JAR + Flutter Web，复用 quality 门禁已验证的同一提交）
  生成 SHA256SUMS → Ed25519 签名（ssh-keygen -Y sign）
  上传阿里云 OSS releases/<version>/** + LATEST.txt
        │
服务器 uten-imp-updater.timer（每日 05:00 北京时间，root）
  拉 LATEST → 下载 → 验签 + sha256sum -c → 落盘 /opt/uten-imp/releases/<version>/
  迁移集与当前版本一致（纯代码）→ 自动激活：原子切 current + 重启 + 健康检查
    失败 → 自动切回上一版并重启
  迁移集有变化 → 仅暂存，等待维护者 SSH 执行：
    uten-imp-updater activate <version>
    （自动先 pg_dump 全量备份，再跑 migrator，再切换；失败停机保留证据）
```

### 3. 保留的安全要素（不简化）

- 制品端到端签名：CI 用 Ed25519 私钥签 SHA256SUMS，服务器只信钉死的公钥
  （`allowed_signers`），验签失败一律拒装；
- 原子 symlink 切换 `current`，保留最近 5 个版本，纯代码失败自动回滚；
- 数据库迁移永远走独立 migrator JAR + 事前 `pg_dump -Fc` 备份，迁移失败不自动回滚库、
  停机等待人工处理；
- 后端只监听 `127.0.0.1:8080`，入口仅 Nginx（内网/VPN 网段），数据库只监听回环；
- 发版前置：对应提交的 Quality Gate 全绿。

### 4. 有意接受的简化（与旧链的差异）

| 旧链要求 | 新链做法 | 理由 |
|---|---|---|
| 离线设备签名、五把密钥角色分离 | 签名私钥放 GitHub Environment secret，本地另存一份冷备份 | 组织内无第二人可执行隔离仪式；泄露后果=撤销密钥+重发版本 |
| 无特权 updater + root 激活器分离 | 单一 root systemd 服务（约 250 行可审计 bash） | 单机内网环境；代码足够短到一人可全文审计 |
| staging timer 必须 disabled | timer 常开；纯代码自动激活 | 这是"远程自动更新"的核心诉求；健康检查+回滚兜底 |
| 激活前全停+会话清退 | 直接重启；JWT 无状态可跨重启 | 内部测试用户量极小，最坏情形=用户重新登录 |
| H01–H12、CMDB、双管理员 | 常规运维：SSH 密钥登录 + VPN | 组织内没有第二管理员，双人控制本来不成立 |
| WORM/OIDC/STS 发布 | RAM 子账号长期密钥（发布只写、服务器只读，按前缀限权）+ 桶版本控制 | 风险=密钥泄露→撤销轮换，可接受 |

### 5. 旧链的去处

`deploy/` 下的重链源码与全部测试**保留在仓库内不删除**，标记为"未来引入第二维护者/团队时
的分阶段加固参考"。它们不再具有操作效力；与本文冲突时以本文为准。

## 后果

- 服务器首次部署从"无限期 NO-GO"变为"现场半天 + 之后全自动"；
- 信任边界收敛为两把密钥（GitHub 账号、发布签名私钥）+ OSS 两个 RAM 子账号，
  任何一把泄露的处理方式都是撤销+轮换+重发，不再需要证据链仪式；
- 未来若公司引入第二名维护者，应先恢复：分支保护与非作者评审、签名密钥离线化、
  updater 降权、激活双人确认——按旧链文档分阶段执行。
