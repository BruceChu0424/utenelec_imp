# 2026-10-21 全平台权限目录审查

本轮对当前迁移链 V895 的完整权限目录逐项检查名称、说明、分组、授权策略和代码引用，并结合报价核价、销售发货、单据反审、资产计提、库存盘点及权限模板的实际调用判断拆分与保留边界。修改使用向前迁移 V896、V897，历史迁移不改写。

## 范围与目录基线

- 在全新、隔离的 PostgreSQL 16 Testcontainers 数据库实际执行到 V895，共成功执行 821 个迁移；没有修改运行中的业务库。
- 基线为 **492 项权限、13 个模块、108 个分组**；完全同名的权限为 **0 项**。
- 492 个目录码均在当前服务端主代码中存在字符串引用。这是全量引用检查，不等同于全部接口、角色及业务状态的运行验收；不能仅据此断言每项权限都有可达操作入口。
- V896 将报价财务权限拆成核价确认、退回、重新核价，并将资产计提入账与撤销入账分开，新增 3 个动作码，目标目录为 **495 项**，模块及分组数量不变。
- V897 显式更新 **81 项**权限的名称或说明，其中 **79 项**更名、2 项只修正说明；基线中名称含“红冲”的 **24 项**全部逐项对照业务处理。
- V897 不修改权限码、主键、动作分类、授权策略、基础包、默认授权、数据范围或授权记录。权限页面继续读取后端目录，前端继续使用 Uten 组件与主题；相关界面修改默认遵循 `frontend-design`。

## 合并、拆分与保留判断

本轮没有为减少目录数量而合并权限码。目录无完全同名项，常见的同页多权限实际对应操作、敏感字段或对象范围的不同边界；合成一个开关会给原本只需查看或只需处理实物的人附加写入、金额或跨负责人的能力。需要简化授权时，可用现有权限模板组合，不把模板变成运行中的权限来源。

| 类别 | 决定 | 原因 |
| --- | --- | --- |
| 报价财务确认、退回、重新核价 | 拆为三项 | 确认价格、要求销售修改、推翻已确认结果是不同责任；可分别授权 |
| 资产启用及计提入账、撤销计提入账 | 拆为两项 | 执行正常入账不应顺带取得撤销已入账结果的权限；撤销仍为逐人授予的高风险能力 |
| 新增、编辑、删除、启停主档 | 保留独立 | 修改名称不应顺带拥有删除或停用能力 |
| 单据审核与反审 | 保留独立 | 正向批准与撤回已生效记录的责任及下游风险不同 |
| 查看本人范围、查看全部范围 | 保留独立 | 操作权限不能顺带扩大至其他负责人或全公司数据 |
| 查看单据与查看单价、金额、成本 | 保留独立 | 仓库和生产需要实物数据，不因此取得商业和财务金额 |
| 附件列表、下载、上传、删除、清理未关联附件 | 保留独立 | 读取元信息、领取内容、提交附件与永久清理是不同能力 |
| 盘点录入、普通仓财务审核、车间仓审核、直接余额调整 | 保留独立 | 提交盘点不应直接改变库存，审核职责也不能跨仓种类混用 |
| 供应商月结确认、争议、撤销 | 保留独立 | 正常对账、争议登记、撤回错误快照应分别控制 |
| 来料实物退回、金额查看、确认应退金额、撤销处理 | 保留独立 | 仓库实物与财务金额/结案责任分离 |
| 生产任务开工、仓库发料、车间直送审核、超产/补料申请 | 保留独立 | 生产操作、实物出库、审核和提出申请不能互相替代 |
| 生产调度和进度的页面权限面 | 沿用 V878 已完成的合并 | 当前是同一物理页面；仅合并页面入口，不把不同操作权限混为一项 |
| 资产编辑与删除 | 保留 V819 已拆分边界 | 编辑权限已不包含删除，修正文案而不重新合并 |

### 仍保留的复合职责

以下属于已识别的复合权限，本轮把实际包含的动作写清楚，没有借文案迁移改变它们的授权含义。进一步拆分需要覆盖相关审批流程、全部按钮、模板及有效委派的完整回归。

- `finance_asset:post` 保留启用已审核资产/待摊、计提批次预览和提交、正式入账等正向步骤；撤销入账已拆为 `finance_asset:reverse`。这些是同一计提办理链上的准备及执行步骤，继续共享正向授权，不把预览拆成额外开关。
- `finance_asset:approve` 同时审核资产、待摊、类别及计提批次，仍受服务端状态、审批流程和会计期间限制。
- `finance_asset:dispose` 表示资产处置和待摊终止的办理能力；批准还必须具备 `finance_asset:post`，并由不同于申请人的员工处理，退回同样不能由申请人自行办理。保留现有职责分离，不为了增加开关数量把同一处置流程再拆成多个码。
- `sales_quote:edit` 是报价办理的复合能力，包含编辑、提交/撤回核价、客户接受、取消及按规则重新打开。`sales_quote:reverse` 可以只授予取消报价；两者是取消操作的可选授权来源，不是互斥能力。仅收回 reverse 不能阻止仍持有 edit 的员工取消报价。本轮把这层含义说明白，不改写既有编辑职责和明确收回记录的含义。
- `account:support` 包含开通、启停、锁定、解锁及重置登录账号。它保持逐人授权；目标账号持有高风险权限时仍由超级管理员处理。
- `production_material_analysis:cross_reallocate` 等跨分析调料能力保留独立高风险授权，不与普通物料查看或生成计划合并。

### 不删除仅凭名字看起来旧的权限

`sales_quote:reverse` 实际用于取消报价，不能因旧代码名叫 reverse 就删除。`sales_shipment:approve` 实际用于销售确认发货内容，不能因为旧直审端点已禁用就删除。历史其他出货仍有只读核对及受约束的旧记录处理路径，不能仅凭通用反审不支持就删除相关权限。需要退役时应确认全部服务、历史查询、仓库动作、权限面及存量授权来源后再单独迁移。

## 授权保留与兼容边界

- 纯名称与说明修改不推进授权纪元，因此不会仅因改文案使现有负责人委派失效；授权策略、基础包、敏感度及后续新增的未知字段仍默认触发授权失效。
- 报价与资产拆码保留来源权限的部门授权、个人加授/收回、历史覆盖、有效及已失效委派状态、页面权限面和未删除权限模板的原有含义；已失效委派不能借迁移恢复。
- 内部权限码保持稳定，外部旧权限备份仍按原码校验。旧备份导入是一次新的管理员配置决策，不自动把其中一个旧码扩展成新动作；已有在线模板由迁移扩展并更新版本，旧预览需重新生成。
- 目录变更不替代服务端对象范围、任务归属、仓库/车间责任、状态、版本、再认证和会计期间校验。
