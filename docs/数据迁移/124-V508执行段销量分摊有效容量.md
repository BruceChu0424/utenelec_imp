## 问题与变化

真实业务复现为：原计划 10，下达执行段 10，未开工取消计划包，再用新幂等键按原计划下达 10。V157 将旧已取消段和新段都计入计划销售联动容量，错误累计为 20 并在提交期拒绝合法重建。

V508 只替换三项校验函数，不改写任何历史数量、分摊、单据或审核事实，不增加业务表。仅 `CANCELLED`、`REVERSED` 段退出有效占用；`READY`、`WAITING`、`IN_PROGRESS`、`COMPLETED` 仍计入。单纯软删执行段/计划包也不作为排除已完成实物的依据。

每个执行段的分摊总量、计划行/销售行身份一致性、原分摊行禁止 UPDATE/DELETE 的约束保持不变。容量查询先限定当前段关联的 plan link，利用既有索引求和，避免每次聚合全平台历史。

## 并发与隔离边界

同一 plan link 按 UUID 顺序取 `FOR NO KEY UPDATE` 后才读取身份和容量。该锁兼容明细外键的 KEY SHARE，避免两个新增明细事务在提交期相互升级锁。

新增销量分摊和修改计划联动容量/身份使用应用现行 `READ COMMITTED`：

- 新增分摊的非 RC 写在 BEFORE 触发器拒绝。
- `allocated_qty`、`is_deleted`、`plan_item_id`、`order_item_id` 变化的非 RC 写，由原延迟约束在检查时拒绝，默认提交期整笔回滚。
- RR / SERIALIZABLE 不能据此新增分摊或更改容量；不声称纯行锁能刷新这两类事务的旧快照。
- 不改变容量的责任人/审计元数据更新允许 RR，避免误阻合法交接。

失败使用 `23514` 约束异常；容量错误为 `execution_segment_sales_link_capacity_guard`，不支持的分摊写隔离为 `execution_sales_allocation_isolation_guard`。它们不是可忽略的警告，调用方须回滚。

## 兼容与恢复

旧取消/红冲分摊完整保留，旧已完成量仍受保护；本迁移不猜测历史错账，不自动压缩超额分摊。没有数据回填，也没有新的 CLEAR 表。若需回退应用，应先停止相关写入并核对已创建的新执行包；不能恢复旧函数后继续用它把新旧已取消历史重复计量，更不能为让旧函数通过而删除不可变分摊。
