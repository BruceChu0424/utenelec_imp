# 2026-09-19 车间全链路并行对抗验证

本轮承接[路线与混合供料重构](2026-09-19-车间路线与混合供料重构验收.md)。验证对象为共享开发工作区，未提交、未部署、未写现有业务数据库；数据库验证使用独立 PostgreSQL 容器，保持默认 Hibernate 实体校验、Flyway、业务触发器及事务约束。

**追加口径正在集成验证：** 当前车间直送余料送正常仓库，不回上游车间。V618记录仓库真实目的地确认，V619承接已领/未领来源、专属保管、实际库存腿和原成本。下表中V617及以前的通过记录仍是相应快照证据，不能用于宣称新增收仓链已通过；新收仓结果单独记录。

用户追加开发阶段口径：不再保留旧接口/旧状态运行时兼容支线，统一新模型。已经删除重复持续开工入口/能力字段，原来源仓与实际目的仓使用独立规范字段。老数据只在迁移时核验、转换；消费投影与真实领退流水不一致时阻断迁移，不在运行时放行未知期初差额，也不猜补ISSUE。

## 验证方式

数量、执行权限、供料来源三组并行编写反例，随后交叉审查他组修复。根代理处理页面数量口径、模块依赖、迁移/审计/清库整体合同和全项目回归。拒绝错误操作的测试必须同时检查事务没有留下副作用，并保留正常路径、重复请求、反向后恢复的正向测试；不能把不相关的启动错误、权限错误或夹具错误当成业务反例成功。

## 发现与根因处理

| 被证伪的假设 | 修复后的规则与验证 |
|---|---|
| 齐套时已验证材料，之后普通报工无需再查 | 所有普通路线报工都使用实际净投入容量；待退、实退、额外损耗不能超报，实退后剩余量仍可合法报工 |
| 原日报封顶时只保存计划总封顶量即可 | V614按精确日报记录CAP/RESTORE和材料RELEASE/RESTORE；禁止跨日报恢复、伪造同事务证据或错记操作者；分析计划数量和责任保持可审计 |
| 提前完结能直接释放所有余量 | 有未来供给或未实发领料承诺时拒绝短产完结；普通报工及原任务续领继续有效；内部子件保留父层责任，不能截断后留下无主需求 |
| 同车间、同货品即可直送 | V615要求真实上下层来源责任；同名货品、无关联手工单、其他分析单不能借走专属来源 |
| 多批来源只核对合计即可 | 逐来源记录占用、实际投入和反向，已用来源不能因释放另批余量而重新可用；总量与每个来源同时守恒 |
| 技术位只靠页面排除就不会被普通出库搬走 | 旧通用草稿和数据库流水同样核验来源；旧异常以真实UUID隔离，新正常到货不替历史缺口抵账 |
| 给历史流水加维度索引即可持续快速检查异常 | 升级时一次性记录旧异常，热路径只查小型隔离事实表，新流水按ID实时检查；正常流水历史增长不导致每个来源重复全维度扫描 |
| 一个来源拆成两个执行段就有两份直送责任 | 按原计划行/MAKE peg合计承诺，未兑现直送也占用同一来源额度；接收需求总缺口与本来源可送额度分别检查 |
| 旧手工计划预留同主仓另一叶仓即代表可领取 | 备料、发料及真实收货分配统一使用实际叶仓UUID；同主仓范围用于资格，不能替换实际库存身份 |
| 计划编制人身份足以执行 | 操作者在职状态、动作权限、对象范围独立核验；暂停/关闭计划也不能暴露执行能力；保留有效编制人授权管理路径 |
| 未开工就可以任意换车间 | V616以实发、直送和共享物料依赖为界；无实物交接的未发草稿同事务同步收料归属，有实物时必须先按原来源处理 |
| 当前材料最多可报量就是任务尾批 | 页面按任务剩余目标判断完成，多销售分摊行仅合计实际提交的同任务行；本批材料上限独立校验 |
| 别的草稿占额也能代表产出已完成 | 可报上限仍扣有效草稿占用；尾批提示只扣已审普通产出，8件/2件两待审稿不能提前把另一稿材料当余料退回 |
| 草稿读取失败可按空稿继续编辑 | 既有稿未成功读取时仅提供重试，不出现编辑表格和保存按钮；不能用默认版本0覆盖未读原稿 |
| 用料输入依附第一条成品行即可 | 每个需求UUID只有一份输入状态；镜像行共用，删除/取消首行后由实际参与的行继续提交，不丢失未保存实耗；线性建议合计勾选产出，前批共享材料不猜比例 |
| 候选读取失败可以自动改投仓库或唯一其他任务 | 已明确选择按原UUID保留，失效时要求重新核对；复制行保留去向；迟到响应必须同时匹配来源、请求版本和仍存活的行 |
| 旧提前完结草稿可隐藏标记继续保留 | 编辑旧草稿显示历史标记，并提供明确改为普通报工的动作；不把旧意图偷偷改变，也不把员工卡在不可清除的旧门槛中 |
| 直送日报填写的箱数可以直接比件数 | 前端按冻结换算率转基础量，同次多行投向同一需求合计检查；后端仍做权威事务校验 |
| 整包/固定批次可用平均单耗自动填用量 | 仅已证明LINEAR的需求提供比例建议；其他情况确认真实工艺耗用，允许明确0；正常BOM损耗与额外损坏分开解释 |
| 新模型只需更新主表和API | 新事件表同时登记审计与业务清库；报销标签通过应用端口读取，客户/销售发运策略提为共享契约，保留架构检查 |

具体业务步骤见[场景矩阵](../07-业务链路/车间任务路线与供料场景矩阵.md)、[计量与来源守恒](../07-业务链路/生产计量与来源守恒.md)，权限见[总设计](../05-架构/权限体系总设计.md)。

## 历史与开发边界

旧库存、日报、FQC、成本和来源事实继续保留，新增事实表不通过改写已发生数量掩盖问题。旧来源只有可证明的记录才允许关联，歧义需要对账；没有从当前BOM或同名货品猜来源。额外损耗历史不会自动重分类，误登记按原事实反向后修正。
