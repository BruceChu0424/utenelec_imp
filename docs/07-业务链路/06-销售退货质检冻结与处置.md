# 销售退货质检冻结与处置

> 适用基线：V189。本文描述后端已落地的最小安全闭环，不把“收到退货”误写成“质检合格”。

## 一、核心原则

销售退货审核表示公司已确认收到客户退回的实物、回写 `returned_qty` 并立红字应收，**不表示质量合格**。新退货审核后的实物进入独立质量冻结台账，不写入 `stock_balances`，因此不计入 ATP、不能被预留，也不能被仓库拣货。

当前订单链按“替换需求”重算 `qty - shipped_qty + returned_qty - flag_qty` 对应 outstanding/chain，并清空原来的 `CUSTOMER_CONFIRM`；这只是重开需求，**不会直接增加 `reserved_qty`**。如需补发，必须重新预留或排产，并重新取得客户确认。

只有持有 `sales_return_quality:handle` 的人员作出受控处置后，系统才按结论处理：

- `GOOD_RELEASE`：良品释放，按基本单位数量写销售退货入库流水并增加可售库存；
- `SCRAP`：报废，只减少冻结数量，不增加可售库存；
- `REWORK`：转返工，只减少待质检冻结数量并进入返工数量桶，不增加可售库存。

每次处置都必须填写原因。退货收货、良品释放、报废、返工和未处置收货撤销均写入 `sales_return_quality_events`；事件表禁止更新和删除，只能追加新事实。

## 二、状态与数量守恒

每条退货明细按 `qty × unit_rate` 冻结基本单位数量：

`待处置 = 收货冻结 - 良品释放 - 报废 - 返工`

数据库与服务端同时限制各数量非负，且累计处置不得超过收货冻结数量。处置时对冻结明细执行行锁，因此两个操作员不能并发超额处置。

当前投影状态：

- `PENDING`：尚未处置；
- `PARTIAL`：已处置一部分，仍有冻结数量；
- `DISPOSED`：已全量处置；
- `REVERSED`：完全未处置的退货收货随原退货单红冲撤销。

原退货单只允许在所有冻结明细完全未处置时直接红冲。只要发生过良品释放、报废或返工，就拒绝直接红冲，避免库存、质量事实和财务事实被一键抹除。

**V291 起已落地受控纠错（追加式补偿命令）**：`POST /api/sales/returns/{id}/quality/{returnItemId}/correct`
按桶撤回已登记处置量——撤回 GOOD_RELEASE 反向出库（要求该仓「余额 − 生效预留 ≥ 撤回量」，
已被承诺或消耗的释放量禁止凭纠错抽走）、撤回 SCRAP/REWORK 恢复待处置；事件账追加
`GOOD_RELEASE_REVOKED/SCRAP_REVOKED/REWORK_REVOKED`（原事件保留），金额按累计舍入口径
精确互抵，全量撤回后明细回到 PENDING（「未处置才可整单红冲」语义自然恢复）。幂等键独立
键空间；权限沿用 `sales_return_quality:view+handle`。真实 PostgreSQL 证据见
`SalesReturnQualityIdempotencyPostgresTest`（8/8）。双人复核/岗位分离仍属上线前业务签字项。

## 三、接口与权限

| 接口 | 权限 | 说明 |
|---|---|---|
| `GET /api/sales/returns/{id}/quality` | `sales_return_quality:view` | 查看一张退货单的冻结、已处置和剩余基本单位数量 |
| `POST /api/sales/returns/{id}/quality/{returnItemId}/dispose` | `sales_return_quality:handle` | 提交 `action/baseQty/reason`，执行良品释放、报废或返工 |

默认部门授权为：销售与 PMC 可查看，PMC 可处置；上线前必须按公司真实的品质、仓库职责重新复核岗位授权，不能把默认部门授权当作职责分离签字。

普通 `sales_return_quality:view` 仍受退货 owner/委派范围约束。现有按退货 ID 的 GET 与处置 POST 在对象策略调用层使用同一 PMC 操作旁路，且 handle 不授予退货编辑、红冲或其它销售单据全量权限；但这只覆盖已知退货 ID 后的直接接口。

当前没有独立跨 owner 质检任务列表/最小投影或 PMC 工作台，普通销售退货列表与详情仍受 owner 范围保护，因此不能宣称处置岗位已可端到端发现和领取他人任务。view/handle 方法权限组合、handle-only 负向、已知 UUID 返回投影和真实账号页面深链都仍须专项验证。

## 四、历史兼容

V189 不为历史已审核退货补建质检记录，也不推断其良品、不良品或返工结果。历史退货在旧逻辑中已经进入库存，因此没有质量冻结行时，红冲仍按历史库存流水反向处理。这样既不伪造过去的质检事实，也不重复增加或扣减历史库存。

目标数据库执行迁移前后必须对账：历史 `sales_returns`、`sales_return_items`、`stock_movements`、`stock_balances` 的数量和金额不得因 V189 改变；新质量表初始行数必须为 0。

## 五、当前边界与 NO-GO

- ~~当前没有“退款结案 / 换货 / 补发 / 维修后返还”的客户处置权威字段与审批。~~ **V220 已闭合**：`sales_returns.customer_disposition`（REFUND_CLOSED/EXCHANGE/RESHIP/REPAIR_RETURN）+ 审批（`sales_return:disposition`）+ 追加式 `sales_return_disposition_events`。RESHIP/EXCHANGE 重开替换履约预留（修 BUG-S1 退货不重预留）、REFUND_CLOSED/REPAIR_RETURN 以 `flag_qty` 关闭替换需求（不补产），确认后禁整单红冲。EXCHANGE 当前按同品补发处理（跨品换货需另建订单行）。仍不自动触发排产，须销售显式选择并驱动 outstanding/应收/履约。源码候选，待重启后端+真实岗位 UAT。
- 已登记质量处置没有受控复核红冲/补偿事件；误判只能停下并走线下更正调查。数据库 append-only 是防篡改边界，不能用管理员改表作为长期业务流程。
- `REWORK` 当前仅形成受控、可追溯的返工数量桶，尚未自动创建客返工单、拆解工单或重新检验任务；在返工工单挂接和二次检验闭环落地前，不得把返工数量释放到可售库存。
- 当前未落地批次、序列号、库位、照片/检验报告附件、缺陷代码、检验方案和复核签字；有这些监管或客户要求的产品仍需外部受控流程。
- 当前候选已在隔离 Testcontainers PostgreSQL 16.14 从空库迁移并校验至 V190，但尚无公司目标库历史对账、V189 双会话处置并发、真实账号权限负向及库存/财务/售后岗位 UAT，因此不等于生产可上线。

## 六、验收清单

1. 新退货审核后，`returned_qty`/替换需求与红字应收成功，旧客户确认清空，但 `reserved_qty` 和 `stock_balances` 不增加。
2. 无质检处置权限直接调用处置接口返回 403。
3. 两个会话同时处置同一冻结行，累计数量不得超过冻结数量。
4. `GOOD_RELEASE` 才增加库存；`SCRAP/REWORK` 均不改变可售库存。
5. 任一处置发生后，原退货单直接红冲必须失败。
6. 质量事件 UPDATE/DELETE 必须由数据库拒绝，审计中心能看到投影变更和事件新增。
7. 历史退货不出现伪造的质量行，V189 前后历史库存与流水对账一致。
8. 未选择客户处置前不自动排产；选择补发时重新预留/排产并重新客户确认。
9. 已登记处置没有直接改事件或整单红冲旁路；未来补偿必须以新事件追加并经复核。
