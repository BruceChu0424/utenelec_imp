# AI 真实接口诊断与聊天体验修复

日期: 2026-10-03。关联 [ADR-140](../99-决策记录-ADR/ADR-140-权限内对话助手与页面示例指导.md)。

## 已确认的真实原因

本轮用户发送 hello 仍收到对话格式异常。前一轮已修的页面说明与 JSON 约束没有解决配置的实际接口错配，因此这次先读取现行配置及技术调用记录，再做不含业务数据的最小真实请求。

数据库连接使用只读事务，未读聊天正文、人员业务数据或改变配置。密钥仅在探测进程内解密并发送给原配置的官方 HTTPS 主机，不输出或落盘。

| 项目 | 观测结果 |
|---|---|
| 当前默认服务商 | ZHIPU，glm-5.3，MAINLAND |
| 持久化协议 | OPENAI_CHAT |
| 配置地址路径 | /api/anthropic |
| 原实际请求路径 | /api/anthropic/chat/completions |
| 原响应 | HTTP 200，但仅有 code/msg/success，code=500，没有 choices、usage 或对话正文 |
| 原技术日志 | 连续 INVALID_RESPONSE，HTTP 200，输入/输出 token 均为 0 |
| 同地址、密钥和模型，改用正确协议的最小请求 | /api/anthropic/v1/messages 返回 HTTP 200、end_turn 和有效文本 |
| 正确协议的 hello 路由探测 | 实际返回 KNOWLEDGE / SELF_HELP 和参数对象，约 3 秒 |
| 新代码真实 AiProviderService → AiGateway → 客户端 → 已配置 GLM → AiChatJobHandler | 自由表达的生产日报学习问题返回 KNOWLEDGE 和具体例子，约 6.5 秒；使用合成测试身份及静态说明，无业务记录读取/写入 |

新代码探测观测到 configuredProtocol=OPENAI_CHAT、effectiveProtocol=ANTHROPIC_MESSAGES；配置版本保持 2。后续真实服务商、模型或配置变化不受这次单次探测结果担保。

[智谱官方 Claude API 兼容文档](https://docs.bigmodel.cn/cn/guide/develop/claude/introduction)给出的基础地址是 /api/anthropic，Messages 完整路径为 /api/anthropic/v1/messages。它与 OpenAI chat/completions 不是同一个协议。

## 根因修复

- 对精确的 ZHIPU + open.bigmodel.cn + 官方已知路径提供运行期兼容解析；存量 /api/anthropic(/v1) 使用 ANTHROPIC_MESSAGES，/api/paas/v4 使用 OPENAI_CHAT。
- 兼容解析不修改数据库中的协议、密钥、配置版本、主机或基础路径，也不在请求失败后轮番尝试其他地址。日志只记录 provider ID 与 configured/effective 协议。
- CUSTOM、子域名和未知代理路径不猜协议。新建、修改及未保存配置的测试遇到已知错配直接拒绝，明确提示正确协议。
- 两协议请求显式 stream=false。HTTP 200 中明确的 success=false 或失败响应码不再当作空文本解析，转为安全的配置错误，不向用户反射响应正文，也不无效重试。
- 现有密钥与地址/协议修改约束、出网地域、SSRF 检查及管理员预算继续适用。

## 会话能力与权限

- 问候、感谢及能力介绍能直接沟通，介绍内容取实际可用部门和工具。该路径不作为掩盖服务商故障的验收证据；真实模型链另行验证。
- “举例”“下一步”“简单点”延续当前已授权业务话题，分别提供已有具体例子、原规则分步呈现或简明说明。
- 模型只选择允许的知识、字段、工具和说明形式。任意模型生成正文仍不直接展示，避免合法来源 ID 夹带其他部门信息。
- 话题来源在读取时再授权；模型请求中不带旧成本答案、授权签名或文件内容。页面感知关闭后不恢复历史页面。
- 根据后续安全复核，知识条目增加功能级读取门禁: 财务部门身份本身不开放成本说明，仍需货品查看与成本查看；授权说明需真实超管与授权管理权限。能力介绍、模型候选、回答、历史和跟进使用同一门禁。该问题涉及说明范围，未据此声称发现了真实成本数值泄漏。
- 数据查询仍经原业务服务的数据范围，授权仍是超管、确认、再次认证和原事务审计链。没有增加任意 SQL、接口或脚本工具。

## 界面与发送状态

- 用户消息靠右，以较窄气泡显示；助手靠左。保留字体、主题、手机和键盘适配。
- 上传与纯图标发送放在输入框内部底部两端，图标有可访问标签和适当点击区域。
- 发送后清空输入。失败只标记在原消息旁，不将上一条重新塞入输入框，不覆盖正在编辑的新消息。
- 区分“送达未知”“已受理但 AI 失败”“已受理但读取中断”。明确重试保留原消息载荷；读取中断优先恢复原 job，而不是再提交一次。
- 权限或身份边界变化时清空消息、文件和确认窗，迟到响应不得回写。
- 按用户后续要求移除输入区底部常驻提示，相关说明通过不占底部常驻空间的帮助入口查看。
- 真实 Widget 预览使用合成数据，见 build/ui-audit/ai-chat-desktop.png、ai-chat-mobile.png、ai-chat-failure-mobile.png、ai-chat-authorization-dark.png。

## 语言攻击专项与调研依据

本轮继续核对官方 [OWASP 提示注入防御](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html)、[AI Agent 安全](https://cheatsheetseries.owasp.org/cheatsheets/AI_Agent_Security_Cheat_Sheet.html)、[对象授权](https://api-security.owasp.org/editions/2023/en/0xa1-broken-object-level-authorization/)、[功能授权](https://api-security.owasp.org/editions/2023/en/0xa5-broken-function-level-authorization/)以及 [Microsoft Copilot 分层提示防御](https://learn.microsoft.com/en-us/microsoft-365/copilot/copilot-prompt-defense-in-depth)。实现采用模型之外的授权与结果边界，不将角色提示词、关键词拒绝或另一个模型的评分作为安全证明。

AiChatAdversarialSecurityTest 的 20 个展开场景使用真实 handler、registry 和页面目录，并故意让受控提供商完全配合攻击者:

- 中英文假装超管、空格拆字、编码、伪造 system JSON、伪造不可信内容分隔符。
- 强推未授权成本、授权、SQL、HTTP、工资工具；额外 owner/scope 参数试图替换真实账号。
- 多轮先建立信任再提权；模型等待期间撤权；引用他人对话和隐藏成本字段。
- 合法知识 ID 附带恶意正文或操作卡；非法和其他部门知识 ID。

判断标准是业务工具未执行、业务秘密标记未回传，未授权工具/知识不进入可信模型目录；不以模型最后说了“拒绝”作为唯一断言。每一次真实业务读取、历史及工具执行继续由服务端权限与记录范围校验。

“自己的范围”指服务器当前授予的本人、负责客户、部门或车间等具体数据范围。共享货品资料与生产部汇总沿既有配置及独立权限，不声称所有数据只限本人创建，也不允许用户通过一句话扩大这些范围。本轮测试没有替代真实文件间接注入、生产告警及全部可能攻击的长期验收。

真实探测只复用了已配置服务商做无业务数据的请求；数据库全程只读，没有启动完整应用或其后台任务，没有修改当前服务配置或重启常驻 8080 服务。实际界面要加载新前后端版本后才具备上述修复。
