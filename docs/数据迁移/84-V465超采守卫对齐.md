# 84. V465 ordered_qty 守卫与「放开超采」对齐

> ADR-068（订货允许超申请量）的数据库层遗留修复；与 ADR-069（订货行多来源锚定）
> 同批落地——合并行的末位来源吸收超额同样依赖本修复。

## 问题

V144 在 `purchase_request_items` / `subcontract_application_items` 上挂的
`trg_*_ordered_guard`（V132 `fn_guard_processed_quantity`）在 `ordered_qty` 超过申请
`qty` 时抛 23514。2026-09 Java 侧已放开超采/超委外（容量校验移除、剩余量夹 0、
申请照常结案），但**财务批准回写 ordered_qty 时**仍会撞数据库上限：

- 单行超采订货单：草稿/送审成功 → 财务批准 500（观感是「卡死在审批」）；
- V463 合并行：末位来源吸收超额（如 60 = 30 + 30，末位申请只有 30）同样被拒。

## 修复（V465__ordered_qty_guard_allow_overbooking.sql）

- 新函数 `fn_guard_ordered_qty_non_negative()`：**只禁负数**（红冲对称性兜底保留）；
- 两个触发器沿用原名换挂新函数（`InventoryTransactionalIntegrityPostgresTest`
  按名计数 6 不变）；
- 重复回写由应用层防护：仅草稿可审批、仅已审可红冲、approval case CAS。
- 不新增表、不修改业务数据；reset 白名单/CLEAR 计数不变（V464 的 320 表口径），
  仅 ops 脚本版本门增至 **V465/427**。

## 验证

- 行为证据在 `FullChainEndToEndTest.orderSourceMerge...`（合并单超采 55=20+35，
  财务批准成功、ordered_qty 按来源拆分回写、末位来源 35 > 申请 30 不再 23514）；
- ops/契约同步：`ResetBusinessDataScriptContractTest` 门清单含 (465, 427)。
