## 现有事实与必须修复的限制

来源、AP 付款、供应商抵销分类在 V1003；AR 收款和客户抵销在 V1015。它们都是 append-only 批次，`v_finance_*_classification_current` 取原对象最大 revision。原生金额、实际现金和 GL 由原业务保持权威。

已有防护：

- `classifySource` 和 `fn_finance_classification_serial` 会阻止已经被收付款/抵销/预付应用引用的来源独立换版本。
- 每个批次的 deferred reconcile 校验原来源、当前来源批次及各金额轴守恒；parts 只能在原 batch 创建事务写入。
- AP 有原币/实际现金本币/账面三轴；AR 收款另有冲销原币、冲销本币，共五轴。
- AP 当前剩余与逐日容量共用 `FinanceClassificationCapacitySql.EVENTS`；AR 逐日容量使用 `v_finance_receivable_category_consumption_events` 与 `fn_finance_receivable_classification_exceeds`。
- 原 `finance_supplier_advance_applications.target_category` 和已批减免行 `category` 是不可变原业务/审批事实，不能原地改写。

现有入口在需要更正整图时只会拒绝，没有可用替代，因此不能把“源码有分类”写成整图更正完成。整笔已经全额付款仍须能更正，例如来源 GOODS100 和真实付款 GOODS100 一次共同改为 MOULD100；不得要求先把真实银行付款反审、重付。

现有独立收付款/抵销写入还存在回执顺序问题：部分方法先 `requireBatch(current, input.sourceClassificationId)`，再查原 `requestId`。若原请求其实已成功，后来整图换了 current batch，原成功请求的未知重试会被 409 卡住。必须连同这些入口一起改成“先查本人同请求的真实结果，再校验本次新操作的 current/CAS”。不能只给新整图接口加早重放。

## 图的读取与有界范围

从真实 ledger UUID 读取当前来源及所有实际关联行，保留未归类和已反向记录的状态、真实发生/反向日期。不得只查“尚未付款余额”。

实际读取集合包括：

1. 所选来源 current batch、parts、原 ledger 与受验 legacy proof。
2. 关联实际付款行或收款行；同一付款的行级现金/book 已冻结，不能拿 header 总现金替代某一行。
3. 所有 source/target 两端 offset 及对端 current source batch。对端即使不修改也必须保留真实身份与原分配；需要修改其来源时扩入同次图。
4. AP 预付应用的原 target 分类和已有更正 effective 分类；source 资产归属保留。
5. V1029 的已批/已反向减免原审批标签、实际 credit/offset 和当前分类证据。

图按完整依赖闭包读，使用明确总量上限、分页读取和 epoch/cancel fencing。超出有界范围应明确拒绝并保留输入，不能截掉后面的关联行后宣称完整。先定义“只读对端”和“本次改写节点”，避免把一个大客户所有无关付款拉成无界图；但是所有被改来源的实际引用必须包含。

## V1020 基础 schema 设计

V1020 只能依赖 V1003/V1007/V1015 及之前表，不引用未来 V1023。SQL 先放本域 tmp，完整语法和专测通过后一次原子放入 migration。

建议最小结构（名称可在实作时统一，但语义不能省）：

- `finance_classification_corrections`：`id`、唯一 `request_id`、原 actor、direction/party/currency、原因、源图 fingerprint、plan hash、完整不可变 command/旧图快照、创建时间与 `created_tx`、BUILDING/APPLIED 状态及真实 result。
- `finance_classification_correction_nodes`：correction FK、受限 node kind、真实 source/line/offset/application UUID、旧/新 batch UUID、旧/新 fingerprint、原事实轴快照与本次 parts。批次 UUID 必须按 node kind 校验到真实 owning table，不接受客户端表名或动态任意表。
- 预付 target 分类版本及 parts：application FK、revision、correction FK、原标签快照、目标 source batch、明确 target 分类份额。更正可以把一次应用的目标归属明确拆成两类，不能用单字符串覆盖掩盖混合归属。原币与 target book 分别和实际 application 守恒。

预付建议用一份 `v_finance_supplier_advance_target_parts_effective` 提供目标消费，返回 application UUID、current batch、category、amount_original、target_local：无更正时投影原 application；有更正时只用当前 metadata parts。原 source asset leg 继续只读原 application 一次，不能因 target 拆成两行而把 source_local 重复两次。

原 batch/parts 不更新、不删除。普通独立写原依赖门保留。仅同 TX、同 actor、已注册且精确匹配本次 source/expected old version 的 correction 能插新的 source 批次；不能只设置一个 session boolean 绕过。

最终 deferred 验证至少包括：

- 所有改写 source 的真实当前子引用均已指向本次新 source batch，未漏收付款/offset 任一端。
- 所有新批次和 parts 均属于同一合法 correction 创建事务，旧/新 revision 及 UUID 对应正确。
- 各节点所有金额轴与原真实事实分别完整相等；原币、现金、冲销、book 不互相替换。
- AP 和 AR 最终逐类/逐日预算成立；不以提交顺序造成的中间不一致挡正确整图。
- 原 ledger/payment/receipt/offset/application 的真实金额、GL、资金流水与库存没有被此更正改写。
- 原回执保留，不能把后来 current 变化倒算到原成功操作上。

现有 reconcile 已是 deferred，主要应窄改 source serial 的受控许可，跳过本次图内部 Java 的逐子步骤容量检查，再在整图写完后调用共同最终容量入口。不要删除普通 reconcile 或放宽独立分类。

## 写事务与幂等顺序

1. 完整财务/ARAP read scope；锁本次 request key，先读取同 actor 的原 request receipt。相同完整内容已成功则直接返回旧真实结果，不进入后来 current 校验。
2. 对新操作检查 direction 对应的 supplier settlement / payment approve / receipt approve 权限。
3. 使用分类 family 唯一公共锁。`FinancePayableClassificationPort.lockForWrite()` 已由 Root 增加，MANDATORY，内部复用 `classifications.read()+lock()`，不复制 advisory key。
4. 确认读图 fingerprint、所有 expected current batch/revision，以及真实财务各轴；锁必要实际 ledger/line，避免并发业务改变图。
5. 注册同 TX correction，再追加全部来源和引用批次；保留原记录。
6. 追加预付 target effective metadata，执行最终共同预算/引用验证，完成 APPLIED result。任一环节失败整个事务回滚。
7. 提供本人 requestId 的只读回执查询，页面中断后可核对。未知重试仍保原 path/body/key/业务 headers；不持久 Authorization、Cookie 或旧登录凭据。

本域 V1023 新增 `NativeFinancialPostingAccountPort.lockDebtSources(ids, additionalStyleIds)`，会把债务与全部对方 style 放一个排序集合再锁 AP。涉及金额操作时沿用 period → 分类公共锁 → 全部 style → AP 行顺序。更正纯 metadata 不应额外调用 journal/cash writer。

接手必须补核实际收款/反向调用方的同一锁顺序：V1015 的 `finance_receipts_category_capacity` 和 `customer_offsets_category_capacity` 在提交阶段会执行 `fn_finance_receivable_category_capacity_guard` 并取得分类全局锁。若实际 AR 收款先持有 ledger 行、在 commit 才取分类锁，而整图已持分类锁再等该 ledger，会形成反转。不要只给新整图加早锁。可把唯一锁原语下沉到 application/concurrency（仿 `PaymentStyleHierarchyLock`），由既有分类 service 和已授权的原生 money caller 共用；纯锁不能附加不属于原收款审核人的 `finance_report:view` 等读取权限。当前 `FinancePayableClassificationPort.lockForWrite()` 内有 `classifications.read()`，适合已具备完整财务读取权限的 V1023/整图，不应直接强塞进所有旧收款审批。

若 V1020 给 AP 付款/抵销/预付状态更新增加最终容量触发器，也要同阶段迁移其原生 caller，不能新增一个提交末尾才等待分类锁的入口。该锁顺序核对属于实际并发验收，不以一般单线程金额例通过代替。

### 唯一公共入口与实际 schema
