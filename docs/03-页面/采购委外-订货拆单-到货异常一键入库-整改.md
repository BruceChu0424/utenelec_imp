# 采购/委外：订货拆单 + 到货异常一键入库 + 默认值/徽标 整改

> 本文件记录 2026-08-04 对采购/委外/仓库的一组整改。部分为 ADR-019 的**操作层折中**（底层「一单一商」归集不变）。
>
> **2026-08-16 口径更新（ADR-038）**：订货单不再携带仓库——编辑/列表/详情均无仓库字段，任务中心可跨仓库选行分解；「入到哪个仓库」由仓库在收货/进仓（到货登记）时必填，预计到货任务不再因缺仓库而阻止登记。

## 2026-08-11 现行覆盖

下文 2026-08-04 的空白订货、逐行供应商和到货异常按钮是历史整改记录。现行业务优先从生产物料分析的统一 BOM 树进入：计划员先显式「采用采购/采用委外」，只有路线已确认且可执行的逐路径节点才显示复选框；点「提交采购需求（N）」或「提交委外需求（N）」后，服务端才创建 `preplan_supply_actions`、逐路径 allocation 和真实采购/委外申请。采购/委外端申请只读，业务人员从任务中心按申请剩余量部分分解订货；一张权威订单仍只有一个供应商/委外商（仓库已随 ADR-038 从订货中移除），保存后送财务审核组。

生产来源不得在拆单时丢失：申请行、订货行、收货/回厂行、质检结果和库存流水必须能回查到原 analysis/item/path。财务批准只形成预计到货；只有 IQC PASS 并进入原分析目标仓的合格可用量才能刷新物料齐套。采购/委外入库不能直接增加生产计划「已报工」或成品「已入库」，子件入库也必须先按 MAKE peg 回供父需求。

本文件第 5 节「只入库 {acceptedQty}」只处理特定超量到货异常的批准量，不是通用计划料到货按钮，也不是 IQC/逐路径唤醒已经闭环的证据；若该历史链没有显式质检与 allocation 回写，发布时必须继续 fail-closed 或列为 NO-GO。物料页的「备料汇总预览」同样只是可打印的只读「生产备料计划汇总单」，不会代替这里的 action、申请、订货、收货和质检单据。

- 取消了原先 `_requiresTaskSource`/`_orderSourceReady` 的「必须从任务中心生成」硬阻断（编辑页可直达新建）。

## 4. 订货单明细逐行供应商 + 保存按供应商自动拆单（决策1，ADR-019 折中）

**背景**：ADR-019 §2.3「一张订货单只有一个供应商/委外商」是为应付/到货异常/退货按「单据×供应商」归集服务的，不可推翻。用户要「明细放供应商」的诉求，通过**操作层折中**满足：

- 表头仍是默认供应商；订货单明细新增「供应商」列（`ProcurementSupplierCell`，共享件 `lib/shared/widgets/procurement_supplier_cell.dart`），逐行可覆盖；行未覆盖时显示表头供应商。
- 保存时每行带 `supplierId`（为空后端按表头回落）；后端 `createBatch` 按 `supplierId` 分组，**单事务**生成 N 张订货单（多数 1 张），每张各自 supplier_id + 明细链回申请行。前端对每张调 `submitFinance`。
- 端点：`POST /api/purchase/orders/batch`、`POST /api/subcontract/orders/batch`，返回 `{items:[OrderDetail...]}`。DTO `OrderItemLine` 增可选 `supplierId`。
- **收货/退货不加明细供应商**：沿用上游订货单的单一供应商（链路约束）。

## 5. 到货异常任务中心：一键入库 + 搜索 + 历史（决策3）

**根因**：财务 `REJECT_EXCESS` 后已静默把草稿收货单下调到接受量，但入库要仓库**手动重开草稿单重审**，中间无任何提示/刷新 → 用户觉得「没反应」。

**一键入库（复用，零新库存逻辑）**：
- 新端点 `POST /api/warehouse/inbound/arrival-exceptions/{id}/stock-in`（权限 `purchase_receipt:edit` 或 `subcontract_receipt:edit`）。
- `ProcurementArrivalControlService.requireStockableException(id)`：校验 `status==RECEIPT_ADJUSTED` 且有 receipt_id，返回 `StockTarget(orderType, receiptId)`。
- 控制器按 orderType 调 `PurchaseReceiptService.approve` / `SubcontractReceiptService.approve` —— 该 `approve()` 已含 validate（命中 `exactlyFinanceAdjusted` 放行）→ 入库 stock_movement + received_qty 回写 + 立应付 + `recordApproval`（RECEIPT_ADJUSTED→RECEIPT_POSTED）。
- 财务 REJECT_EXCESS 阶段早已 `upsertReturnTask(PENDING_RETURN)` + 发 `EVENT_RETURN_REQUIRED` 通知采购退回余量——本端点只补「入库」这一步，消除人工重审断点。

**任务中心 UI**（`warehouse_arrival_exceptions_page.dart`）：
- 顶部 `UtenSearchBar`（搜单号/货品/供应商）+ 「进行中/历史」ChoiceChip。
- 后端 `warehouseExceptions(page,size,keyword,includeHistory)`：历史查 `status IN (CLOSED,CANCELED)`。
- 卡片在 `canStockIn`(RECEIPT_ADJUSTED 且 accepted>0) 时显「只入库 {acceptedQty}」按钮 → 调新端点 → 刷新 + invalidate 徽标。
- 模型 `ProcurementArrivalException.canStockIn` getter。

## 6. 供应商退回：批量确认（决策4，物流凭证）

**关键**：当前后端是「先调后入」——超量从未进库存、没立应付，所以一张退货单「冲库存/应付」无东西可冲。决策保留先调后入，**退货确认只作物流凭证**。

- 待退供应商列表加多选（checkbox + 全选本页/清空）+ 底部「批量确认退回 (N)」→ 对所选逐个调 `completeReturn`（行政关闭：任务 COMPLETED、异常 CLOSED、进历史）。不冲库存/应付。
- `completeReturn` 限原下单人（`requireExactOwner`），采购员满足。

## 7. 降噪

- `server/.../config/MetricsConfig.java`：`MeterFilter.replaceTagValues("uri", …)` 把 UUID/数字 id 段折叠为 `{id}`，消除 `OnceLoggingDenyMeterFilter: Reached the maximum number of 'uri' tags` 噪音（无害，纯观测）。

## 8. 入库/退货通知补全（2026-08-06）

**根因**：原实现只在财务 `REJECT_EXCESS` 阶段发 `EVENT_RETURN_REQUIRED`、且仅定向**原下单人**;仓库「一键入库」（`ProcurementArrivalControlService.recordApproval`）**完全不发 outbox 事件** → 采购/委外部门收不到「已入库 X，余 Y 待退」的提醒，用户体感「没通知」。

补全（沿用 outbox + ChainNoticeService 范式，**无 schema 改动**）：
- 新增事件 `PROCUREMENT_ARRIVAL_RECEIPT_POSTED`。`recordApproval` 在异常推进到 `RECEIPT_POSTED`（即仍有待退量）时 `publishOnce`；全部接收、无需退回（→`CLOSED`）则不发，避免普通满额收货误扰。`PostedAllowance` 增加 `version` 字段以传新版本号（dedupe key）。
- `ChainNoticeService.notifyProcurementArrivalEvent` 新增 `RECEIPT_POSTED` 分支，并对 `RETURN_REQUIRED` / `RECEIPT_POSTED` 都向采购部 `SUB_PURCHASE`（**委外单也归采购部**，无独立委外部）广播；新增 `broadcastToPurchaseDept` 去重排除原下单人，停用/已删账号由 `sendToUser` 内部跳过。
- 触发链：仓库任务中心「只入库 {acceptedQty}」→ `POST /api/warehouse/inbound/arrival-exceptions/{id}/stock-in` → 收货 `approve` → `recordApproval` → outbox → 采购部全员 + 原下单人各收一条「到货已入库，余量待退」。

> `recordReversal`（收货红冲路径）暂未对称补发，属未列入本轮范围的边缘场景；如需「红冲撤回入库」也通知采购，可后续对称加 `EVENT_RECEIPT_REVERSED`。

## 9. 仓库登记到货独立页 + 收货单价格脱敏（2026-08-19，V302）

**背景**：登记实际到货此前复用采购/委外收货单编辑页的到货模式——币种/汇率/结帐方式/
单价金额对仓库全量可见，保存后还跳收货单详情（同样露金额）。本轮把「价格只给
采购/财务看」收口到货链路末端。

**仓库到货登记独立页**（`/warehouse/inbound/receipts/new`，详见
[仓库到货登记页](仓库到货登记页.md)）：
- 预计到货任务卡「登记实际到货」改跳本页（`receiptCreateRoute` 两类统一指向）；
  页面只有数量与库位：表头 = 单据日期/供应商（只读）/入库仓库/采购员（采购必选）/
  收货人（必选，默认当前登录人，默认仓储部 `SUB_WH`）/备注，**无币种/汇率/结帐方式/交货人**；
  明细逐行「本次实收 + 库位号/物料系列/物料编码」（主档带出可改）；底栏只有行数与实收合计件数。
- **建议仓锁定**：`InboundExpectationTask` 新增 `suggestedWarehouseId/Name`
  （沿 订货明细→申请明细→`preplan_supply_action_allocations`→有效物料分析目标仓回溯，
  整页批量查询无 N+1，唯一才建议）；登记页据此预填并禁用锁定，防入错仓导致分析进度不刷新。
- **货品资料学习**：保存成功后 `POST /api/warehouse/inbound/goods-profile-hints`
  回写库位号/系列/编码（code 仅补空且防重、series/stock_place 不同才更新、空值跳过、
  仅未删除货品，带 updated_at/updated_by）；下次登记自动带出。
- 保存 body 不带 price；审核时服务端 `recomputeReceiptAmount` 按订货明细权威回填金额。
  保存后回任务中心，不再跳收货单详情；审核通过后采购/委外侧即见同一张收货单。

**收货单价格脱敏（V302，仿 V90 `sales_order:price:view`）**：
- 新权限点 `purchase_receipt:price:view` / `subcontract_receipt:price:view`
  （种子授 DEPT_PMC/SUB_PURCHASE/DEPT_FIN/GM；仓库/生产不授）。
- `ReceiptPriceMasker` + 两个收货单 Service 的 list/detail：无权限时
  `price/amountOriginal/amountLocal/totalOriginal/totalLocal`（委外明细另含
  `returnAmount`）置 null + DTO `priceMasked=true`；前端列表合计/详情合计/明细单价金额
  渲染 `***`。
- 预计到货明细接口自 2026-08-18 起不再下发 `unit_price`（`NULL AS unit_price`，
  去掉两个 order_items join）；仓库侧到货异常任务的金额快照同口径置 null。
- 服务端置 null 是底线；前端 `***` 只是呈现。

## 10. 到货登记一步完成：登记即送检 + 断点恢复（2026-08-27）

**根因**：仓库登记页保存的草稿**不带币种/汇率/结算方式**，而收货审核
`requireHeaderMatches` 要求与财务批准订货单一致 → 仓库「审核」必报
「供应商、币种、汇率或结算方式与财务批准订单不一致」，被迫进采购收货单编辑页补
采购字段；且保存后 pop→整页重载→push 收货单详情页（再人工点审核）造成秒级串行
链路与闪跳；登记后退出任务卡变灰「已登记待审核」无恢复入口。

**改动**：

- 新端点 `POST /api/warehouse/inbound/arrivals`（`WarehouseArrivalRegistrationService`）：
  请求体为稳定客户端 `idempotencyKey` + 数量/库位/收货人/仓库/日期；服务端按明细 `orderItemId` 回查来源订货单
  **权威回填币族**（多单来源 fail-closed），同事务复用各收货单 Service
  `create + approve`（IQC/订货回写/立应付全链路不变，权限仍由两段 Service
  `@PreAuthorize` 收口）。实到超量时 `ProcurementArrivalBlockedException`
  （noRollbackFor）翻译为正常响应 `EXCESS_QUARANTINED`（携带 exceptionId），
  由到货异常任务中心接管（财务定案 → 一键入库），不再以 409 弹错。
- V419 增加 `warehouse_arrival_registration_commands`：当前登录制单人范围内 key 唯一，规范请求 SHA-256 与 key 永久绑定；命令先 `PENDING`，同事务只允许一次终态化。丢响应后 Flutter 复用原 key 可精确回放原 receipt/outcome；同 key 改 body 409，数据库禁止改写命令身份、终态结果或删除记录。
- 登记页按钮改「**登记并送检**」：统一审核责任确认框一次覆盖登记+审核责任；成功后
  pop(结果) 回任务中心就地刷新并按 outcome 提示下一步（合格自动入库 / 超量待财务），
  **不再自动跳采购/委外收货单详情页**；货品学习回写改 `unawaited` 不阻塞。
- 断点恢复：`expectations` 每任务新增 `draftReceiptIds`（草稿收货单，按订货明细
  关联整页批量查）；任务卡「已登记待审核」有草稿时可点「已登记待审核 · 继续处理」
  直达审核页，中途退出回到停止的步骤。

**二轮深化（同日）：任务卡即流水线，仓库全程不进采购/委外单据页**

- 任务卡按步骤驱动（`InboundArrivalStep`），断在哪一步按钮就停在哪一步：
  待登记到货 → 已登记·待送检 → 超量·待财务审批 → 已送检·待品质检验。
- 新端点 `POST /api/warehouse/inbound/arrivals/{receiptId}/complete`：
  草稿一键「继续送检」。服务端先按来源订货单**权威修复表头币族**（老草稿缺
  币种/汇率/结算方式、原审核必报错——顺带修复存量卡死草稿），再走同一审核链路。
- `expectations` 新增 `pendingInspectionReceipts`（待品质放行收货单数）与
  `openArrivalExceptions`（未结异常数）；列表/计数口径扩为
  `OPEN + CLOSED 但仍有待检明细`（`PENDING_INSPECTION_EXISTS`）——收货审核即入
  IQC 隔离，品质放行完任务才从任务中心消失，仓库全程可见每张单停在哪一步。
