# ADR-120 物料汇总办理与共享制造来源

- 日期：2026-09-25。
- 状态：已接受，按 2026-09-26 复核改为原产品树统一办理。历史专项证据见[专项验收](../99-项目治理/2026-09-25-物料汇总办理验收.md)，不代表本轮源码已安装到业务库。
- 背景与现场数据：[三产品只读诊断](../99-项目治理/2026-09-25-物料汇总只读诊断.md)。
- 扩展 ADR-099/102/104/116；保留其按产品的分批、追加、来源与开工门禁。

## 1. 根因和目标

原“按物料汇总”仅把节点套在展示头下面。汇总头没有单节点操作组，因此被选择、数量编辑、累计下单和指派判断排除；展开后的每个旧节点又各自走原写入管道。同料看似合并，办理和数量仍是分离的。

现行默认入口仍是原产品树，每个产品行独立填量，合计选中行后自动合单；一行改量不覆盖另一个产品的输入，只同步可用和缺口。可选汇总视图才按货品 UUID / 颜色 / 基本单位显示主行总量，展开查看来源、真实路径及分配份额。生产批次只在货品、颜色、单位、冻结 BOM 与已确认路线、生产指派、日期、超产比例等相容时合并。不同参数不能静默采用首个来源的值。

设计参考：Odoo 的制造合并要求同产品且同 BOM；Microsoft 将合并后的供给与需求关联分开保存。这里使用本项目既有不可变来源及实际库存账实现，不套用第三方软件的默认库存规则。

- [Odoo 制造拆分与合并](https://www.odoo.com/documentation/master/applications/inventory_and_mrp/manufacturing/workflows/split_merge.html)
- [Microsoft 供需关联](https://learn.microsoft.com/en-us/dynamics365/supply-chain/master-planning/planning-optimization/marking)
- [Microsoft 多层 BOM 生产计划](https://learn.microsoft.com/en-us/dynamics365/supply-chain/master-planning/planning-optimization/production-planning)

## 2. 员工看到的操作

准备主表和车间、采购、委外三个桶共用同一核对下单页、状态和提交器。相容同料自动合单，组件无论一个还是多个来源都走同一管道；根产品保留原销售/手工计划来源。员工仍在原产品树填写和追加，不需要理解或进入“共享批次”。汇总视图是可选核对入口。

1. 原行 UUID 保持不变。父件改变数量后，全树后代按缺口预填并默认选择，折叠和分页不影响；手工数量与手动取消分别保护。
2. 下单数量显示实际发出量，含公共超量；分配给需求的私有份额单独保存。逐行输入通过 `sourceRequestedQtyByMaterialLineId` 纳入指纹和不可变事件意图。例如 A10000/B1000 不能回显成 A5500/B5500。
3. 任意已下达子件可独立追加，供给需求转交不再作为禁用原行的理由。后台根据精确来源桥解析当前办理节点，缺少唯一证明不能按同货品或首行猜测。
4. 统一依赖编排先父后子，同一层合批；只确认一次，失败停止后续并保留输入和回执。缺少车间/负责人在同一表补齐，不回退另一套通知管道。
5. 下单进度读取真实单据，不添加“并入共享批次”技术前缀。三桶数字与主表同源，未到货量只算计划可用，不算可领料。

## 3. 数量口径

| 字段 | 含义 |
|---|---|
| 需要数量 | 原产品来源沿原路径 BOM 得到的原始数量；共享批次不再创造一份来源需求 |
| 当前备料需求 | 当前真实制造批次所需材料，按实际计划和批次规则计算 |
| 累计已下单 | 真实计划/申请的有效下单总量，含超量；逐原行输入有证明时按意图回显，不能拿需求份额替代 |
| 待安排 | 扣除已落实供给后的来源余额；不能用物理 `shortage_qty` 替代 |
| 继承供给 | 原子件计划/已安排供给经精确桥承接的量，不是又新下了一单 |
| 可用数量 | 合法可安排的现货加未办理/在途供给剩余量，扣除占用/认领并按真实来源去重；实际领料仍只认已到仓实物 |

现场例：三产品各 1000，保护门已有三个真实 1000 计划，累计应为 3000、相同目标的追加建议为 0；弹簧一张采购申请下三条来源各 2000，累计为 6000。实际库存仍为 0，不能把这些已安排数字展示为已可领料。

总量分配使用基本量整数刻度(0.0001)：先按既有来源优先级、交期分桶，桶内按剩余需求比例分配，尾差按稳定 UUID 顺序给未满来源。分配量之和加独立公共份等于总量，每个来源不超过其真实容量。运算按来源条数进行，不按数量大小循环。

物理办理组仍最多500组；原来源路径独立限10000条，不能误用“单据500明细”限制一组同料的来源数。前端在同一依赖层内按500组/10000来源分窗口，同料不拆成不同单据。重复兼容规则的两个组在只读核对即拒绝，避免同批被拆算包装、撞幂等键或发生无提示的二次追加。

## 4. 真实共享批次

采购与直接委外在合单时使用一个供给 action、多个既有 `preplan_supply_action_allocations` 和一条真实申请明细。商业订货继续复用已有多来源桥。

制造使用显式系统来源 `AGGREGATE_MAKE`，一份共享 BOM 展开、一张相容生产计划。它没有伪造的单一父件；原父的份额保存在 action allocations。批次 proof 与事件记录新增、追加、取消及完整意图范围。数据库 action 的 `SUPPLY` 含义不变，展示 DTO 从 proof 派生 `AGGREGATE_SUPPLY`。

需要前置自制的共享委外台账使用共享批次和准备项身份，单父物料字段只在精确共享证明成立时允许为空，任务页批量读取并展示全部原来源。自制入库后的委外通知继续沿这些来源分配到一条实际委外申请明细；它是同一订单的后续步骤，DTO 标记 `AGGREGATE_CONTINUATION`，不再增加累计下单数或公共量。该通知的反向按整份委外申请处理，不能拿原生产批次撤回去抹掉已经发生的产出。

已领料、开工或其它正式事实使原批不可增长时，新建独立批次。未领料可增长时复用同一个判据，预览子料只计算 `f(旧批量 + 本次量) - f(旧批量)`。例如每 5 件一个整包，原批 3 件已需 1 包，再追加 2 件不再多要一包。

## 5. 父子责任和已有供给

共享父的转交量是父产出份额。原子料应先按剩余未转交父产出重算，不能从旧子料数直接扣一个新批子料比例。三个父各 1 件、每批 5 件需 1 kg，真正共享一批 3 件只需 1 kg，不能留下三份各 1 kg 再加新 1 kg。

`preplan_aggregate_material_aliases` 以原父、原子料、新 canonical 子料和真实相对 BOM 边链关联已有供给。实物承接只到该共享批需要的上限；旧原料单多出的数量保留原来源与历史，走既有受控处置，不改成公共库存。0 份额 alias 只保存容量/身份快照，不记实物、不增加需求 allocation。

关键次序：锁定并捕获旧来源容量 → 创建共享父与 canonical 树 → 刷新原未转交责任 → 按 alias 承接合法权益 → 再刷新当前供给。原 C 已有计划时，它自己的冻结原料 D 继续留原工单；只有实际需要的新 C 批次才产生新的 D 责任。

部分转交必须保留原需求优先权：原 H 需 1500，旧 C 仅安排 500，本次共享 H1000 后，原 H 剩余 500 仍占该旧 C500，共享 H 不能再重复把它当自己的 500。全转交后原需归零，才可把合法旧供给按配额承接。

## 6. 安全与一致性

- 已有三个历史工单、三条采购来源不自动搬单或重写；新汇总命令才使用共享批次。
- 原来源、在途、现货、正式占用、消耗和反向沿精确 UUID 保存，别名承接不造第二份库存。
- 共享公共份不属于某个产品。保存完整意图上下文，纯公共时也不补造 0.0001 私有需求。
- 预览只读，包含实际分配与批次兼容信息并生成指纹；提交在完整锁范围内重算核对，重试幂等。
- 真实祖先和后代按依赖先后执行，不并行改写同一需求树。父成功、子失败如实保留父回执与子输入，不能宣称整树已齐。
- 单来源的旧撤回入口不能暗中取消别人的共享份额；有正式计划/库存依赖时先按真实反向顺序处理。
- 下单完成表示生产/采购责任已落实，开工仍要求合法到料和实际领用。

共享直送反向沿实际记录办理：先撤真实实发，再取消未投入的接收包、恢复精确权益，最后红冲原入库与日报。已开工、仍实发、缺来源证明、部分/多源成本返回或仍有成本占用继续拒绝。仅对完整共享直送证明的同池、单源、全量已返回WIP成本根补齐谱系识别，不改金额、不绕原成本传播规则。红冲历史仍可追溯，重新报工不重复原份额。

## 6.1 大来源数量的约束调度

批量分摊和别名通过批量SQL写入，仍执行全部逐行来源、不可变历史与延迟总量守卫。V234原总量守卫在每条分摊的延迟事件中重新SUM全批，实测10000条插入并登记外部明细时，仅COMMIT约31.67秒。

V712对有精确共享批次证明（含委外后续通知）的行动，在每个SQL语句后按涉及行动去重排总量校验。`preplan_supply_actions.aggregate_allocation_check_revision` 只负责触发排队，不存数量，也不作为“已验证”缓存；最终仍查询真实allocation之和。原allocation约束和header companion使用同名，使单独指定allocation为IMMEDIATE仍有效；独立技术列避免误触原header_total的具名立即校验。批次/通知证明晚绑定时同样排核。普通行动保留原逐行守卫。

永久PostgreSQL回归覆盖两种分别具名IMMEDIATE、保存点、晚绑定、I/U/D、多行动和错误提交；10000来源同工况COMMIT约539毫秒。该数字仅是隔离约束工况，不代表整页、全部生产链或多用户吞吐。

## 6.2 原行办理投影

`AggregateDelegationProjection` 只沿有效 allocation、含追加事件的 alias 数量及精确 BOM 边链解析任意深度与嵌套目标。多批目标保留为列表；无真实根行的制造锚点不能用首个子件冒充父件。删除按货品匹配、按首行回退和 `putIfAbsent` 丢累计的旧实现。

`aggregatePreparation` 区分实际备料需求、真实已下单、需求分配份额、尚需安排、净缺口和精确目标。实际订单量来自有效计划/申请及原行提交意图；别名的转交量不是已下单，未办理的子件不能因转交就锁成“已下单”。固定批次按实际目标总量计算再分份，不对每个来源分别取整导致放大。

前端原行可填写首单或追加，服务端核对时解析原 ID；请求指纹、完整锁内重算和事件仍保留原意图。旧单来源未执行计划/申请经统一入口复用原位增长，已有业务历史不迁移重写。

## 6.3 公共供给可安排量

有效申请尚未商业订货时，其公共余量也可被其它订单采用。V721 增加 planning 容量口径，原 approved 实际商业在途语义保留。认领先占该来源剩余，后续商业下单、批准和实收入库继续追踪同一来源；取消、减量和并发超认领受容量守卫约束。

公共来源的展示与认领资格分开：采购/委外的本需求自来源仍展示批准在途数量、交期及来源记录，仅把该需求的可认领量置零。判断依据原材料行和聚合别名的精确自来源关系，且先于单据权限脱敏执行；不能因 `sourceIsCurrentAnalysis` 为真就隐藏来源或禁止同分析其它合法需求采用。来源未商业批准时，planning 可安排量也不改写成 approved 在途。

MAKE 使用真实计划明细的公共份，V722 的认领/撤回记录只记供给承诺，实际入库仍通过原 `stock_reservations`、exact peg 和 entitlement events。公共产出有自己的 claim 来源证明，不继承原计划的私有需求。已认领量先分配给接收分析，未认领实物留公共库存；红冲和下游已用量继续受原反向守卫约束。

查询性能分别由 [V729](../数据迁移/249-V729公共供给按分析先筛选再计算.md) 的采购/委外范围读取和 [V732](../数据迁移/251-V732制造公共供给按来源筛选后计算.md) 的制造来源读取收口：先按当前分析的同主仓和精确物料维度筛选完整来源，再计算容量、实收和认领；单来源读取可指定计划明细。保留原权属、数量及反向算法，旧视图继续兼容，不以提高超时代替修复。准备页的整体业务回归、批量下单实测及未完成性能项见[物料准备收尾记录](../99-项目治理/2026-09-26-物料准备统一流程修复.md)；相邻领料与编号链路的证据另见[领料收尾记录](../99-项目治理/2026-09-26-领料申请批量出库与编号收尾.md)，两者不能互相代替验收。

## 7. 验证

以只读现场数据构建隔离场景：三产品共同组件、首次合并、旧累计显示、部分/公共追加、未领追加包装边界、先子后父、部分责任保留、单一供给去重、品质/实收、反向、权限、混合参数、草稿和跨视图输入、分页折叠三态与迟到预览。

前向迁移、源文件/运行资源、真实 PostgreSQL 业务验收、前端回归与安装状态分别记录；不以构建成功替代业务链通过。
