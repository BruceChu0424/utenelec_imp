## 一、问题

用户口径(2026-09-16)：

> 现在入库必须先要品质部质检。一天来的货品多了就会堆在一起，或者质检没空。能不能做一个流程：
> 先入库、后质检——原本的流程保留，但加个选项。如果先入库后质检，入库任务中心那里直接入库，
> 品质部那里照样发过去，但得提示：顶部标红，明细点上「货品已入库，需到对应储放区域检查」。
> 品质部后面检查全部不合格，是要再出库？这个出库属于什么？还是直接把之前的入库记录删除？还是特意弄个啥？

痛点是物理的：到货多、质检忙，货只能堆在待检区。要的是「货先落位、质检去库位查」，整个流程要简单、
少操作、数据准确。

## 二、决策

### 2.1 「先入库」定义为「实物先上架落位」，不是「先记一笔库存」

数据库层面早已把「品质放行」与「仓库入库」钉成两个独立事实(V446)：

- 任何写 `stock_balances` 的采购/委外入库流水，必须挂在一个品质 PASS 事件和一条入库批次行上
  (`fn_validate_procurement_iqc_stock_in_item`)；直接以待检行为来源写库存被
  `fn_guard_legacy_procurement_iqc_auto_stock_in` 拒绝；
- 价值账(V517 custody positions)按「收货取得 → 品质待定 → 合格/拒收 → 入库存储」逐步移动价值位置，
  入库存储必须能找到品质切片。

在品质结论之前就写库存，等于回到 V222 之前「未检品当现货」的 P0 缺口——可用量、物料分析、销售出货都会
把未检品当成现货；不合格时还要发明一种「质检不合格出库」流水，并解释它与红冲、退货、贷项的关系。
用户问的三个选项(再出库 / 删入库记录 / 特意弄个啥)都是这条路上的坑。

**所以本方案**：待检明细行记住实物的实际记账叶仓 + 库位(四列，V596)，实物真的放进那个库位；
品质部到库位检验；品质 PASS 时由系统按记录的位置**自动完成正式入库**——走仓库手工确认完全相同的
批次/流水/价值/守卫路径，只是没有人再点一次「确认入库」；品质 FAIL 时什么库存动作都不需要——
实物从来没进过 `stock_balances`，仓库按位置去库位取货，走 V440 既有退回/贷项链路。

回答用户的问题：**不出库、不删记录、也不用特意造新单据**。「入库记录」= 上架事件(`PRE_STOCKED`)
永久留在事件账里；正式的入库流水只在合格时产生；不合格的从库位取出登记退回。

### 2.2 两个入口，一套内核

1. 到货登记页(单张/批量)点「登记并送检」左边的「先入库后质检」按钮：登记 + 送检 + 上架同一事务，每行的「库位号」从学习字段
   升级为必填的实物落点，实到超量隔离的单不上架(没有待检行)；
2. 品质部检查结果页对「等待检查结果」的收货单点「先入库上架」(列表行菜单 / 详情页悬浮按钮)：逐行选记账
   叶仓 + 填库位，可只上架部分行；位置放错可在出结论前重新上架(追加调整事件)。

两条路径都落到 `ProcurementIqcPreStockInService`，只写四列 + `PRE_STOCKED` 事件 + 一条品质部通知。

### 2.3 品质结论后的自动转正

`ProcurementInspectionService.applyDisposition` 写完 PASS 事件后只记下「该行已上架」；本次结论(单张
`dispose` 或批量 `decide-batch` / `pass-batch`)收尾时(`completeReceiptDisposition`)把所有已上架的合格行
一次交给 `ProcurementIqcStockInService.confirmPreStockedReleases`：与手工确认同一条 `confirmOne`，批次
`origin=PRE_STOCKED_AUTO`、操作人为出结论的品质账号、金额/重量按放行切片全额、库位学习照旧；幂等键由 PASS
事件派生——单行 `prestock:<PASS 事件 UUID>`，多行 `prestock:<全部 PASS 事件 UUID 排序后的 SHA-256>`。
**2026-09-21 起一次结论 = 一个自动批次**(此前每个 PASS 事件各起一个批次：每行都重跑一遍来源预锁发现、
放行切片加锁、订单结案重算、库位学习与仓库待办撤回，5 行收货单一次结论 1200 多条 SQL，是品质「批量审批」
特别慢的主因；委外回厂按原材料批次拆行后超过 100 行时按放行事件对半拆成多个批次)。自动转正批次在结案回调前
推进生产联动(`afterInspectionStockInConfirmed`)；整单在本次结论里结案时，结案回调本就按整单 RESOLVED 维度
刷新同一批物料分析，自动转正那一步只推进供给状态与到货通知、不再先刷一遍。部分合格 = 只转正合格量，
其余量仍在库位等下一次结论；一行多次结论 = 多个自动批次。**不再**给仓库投递「待确认入库」任务。

### 2.4 「简单、少操作」的落地

仓库：登记时点「先入库后质检」而不是「登记并送检」(库位本来就在填)——完。品质：到库位检验、提交报告——完。仓库对不合格：到库位取货、
登记退回(原动作)。品质结果页对先入库单不再出现「全部合格·待入库」这一档，直接完结或转「需退回」，
仓库徽章少一个待办。

### 2.5 独立权限

把未检品放进真实库位是一个独立决定：新码 `warehouse_iqc_stock_in:before_inspection`，服务端在到货登记
与上架接口两处都兜底；默认授仓储部/PMC 运营部/总经办，可按部门或个人回收；采购部不默认持有。

## 三、每一种情况怎么走

| 情况 | 结果 |
| --- | --- |
| 点了先入库，但实到超量被隔离 | 不上架；财务定案后仓库可在检查结果页补做上架 |
| 上架时仓不是记账叶仓 / 是线边仓 / 已停用 / 库位空 | 服务端 400/409 拒绝；数据库触发器同口径兜底 |
| 上架后位置放错 | 出结论前可重新上架，追加「调整上架位置」事件；同内容重放静默 |
| 已出任何结论(PASS/FAIL/部分) | 不能再改上架位置(409 + 触发器 23514)；位置成为历史事实 |
| 部分行上架、部分行未上架 | 逐行独立：已上架行合格自动转正，未上架行走原「待仓库确认」队列 |
| 整行合格 / 部分合格 / 多次分批合格 | 一次结论里所有已上架合格行合成一个自动批次(2026-09-21 起；此前每个 PASS 事件一个批次)，只转正合格量；多次分批合格 = 多次结论各一个批次 |
| 整行不合格 / 部分不合格 | 不动库存；拒收案件、退回任务与通知都带「实物位置：仓 / 库位」 |
| 上架仓在结论前被停用或改成父仓(运维动作) | 自动转正前再校验，不通过就退回原流程(放行进仓库待确认队列)，品质结论不被挡 |
| 同一结论幂等重放 | 不产生第二个批次、库存不翻倍(幂等键由 PASS 事件派生：单行 `prestock:<事件>`、多行 `prestock:<事件集合 SHA-256>`) |
| 收货红冲 | 仍要求整单结案；按批次行反向(含自动转正批次)；四列保留为历史 |
| 即时库存 | 已上架待检量按实际上架仓计入「待检量」，不进可用量 |
| 检测记录页 | `PRE_STOCKED` 不在 PASS/FAIL/撤销的记录口径里，不影响记录 |

## 四、边界与不做的事

- 只覆盖采购/委外到货 IQC。自制产成品 FQC(仓库送检登记 → 品质 FQC → 仓库点收)是另一套事实
  (V410–V548)，本方案不碰；若日后需要同样的「先上架」，应复用「位置先记、合格自动点收」的同一思路而不是先写库存。
- 不做「上架即可用」变体：那会让 FAIL 时库存可能已被消耗，正是用户担心的坑。
- 不做撤销上架的独立动作：出结论前可直接重新上架覆盖；出结论后位置就是历史。

## 六、自制产成品(FQC)同款：V597

用户口径(2026-09-16 补充)：「所有入库的行为都支持『先入库后质检』或者『直接登记并质检』这样才对。」
系统里需要过品质才能入库的链有两条：采购/委外到货(IQC，上面五节)与自制产成品报工入库(FQC)。

FQC 这条链的实物流与 IQC 不同：**送检登记本身就是实物交到成品仓库位的那一刻**
(`production_finished_arrival_registrations.warehouse_id` + 行 `place_snapshot`)，品质部本来就到库位检验。
它比 IQC 多的是尾巴上那一步：品质合格后仓库还要再点一次「确认实收并入库」。

所以这条链上的「先入库后质检」= **登记时就承诺「合格按这个位置全量入库」**：

| 环节 | 做法 |
| --- | --- |
| 入口 | 送检登记页(单张/批量)「登记并送检」左边的「先入库后质检」按钮，权限 `production_finished_in:before_inspection` |
| 记在哪 | 登记头三列(`stock_in_before_inspection` / `pre_stocked_at` / `pre_stocked_by_employee_id`)。登记表追加式，决定不可改 |
| 品质侧 | 检查单队列「储放位置」标红「已入库待检(n 行)」；办理页顶部标红横幅 + 明细「储放位置」列逐行「已入库 · 仓 / 库位」 |
| 合格 | 判定同事务按登记位置自动点收(`StockDocService.confirmPreStockedFinishedInbound`，走 V338 同一条确认链路)，确认行 `origin=PRE_STOCKED_AUTO`，仓库不再收到「待点收」任务 |
| 不合格 | 与原流程完全一样：不动库存，开恢复授权/补产任务 |
| 代价 | 自动点收 = 实收恒等于报工量，放弃「短收改量 + 差异原因 + 余量单」(与 V584 车间直送同口径)。要按实物改量就走原按钮 |
| 落仓口径 | 选了先入库的登记，目标仓必须是启用中的记账叶仓且非线边仓(与 V596 共用 `fn_warehouse_is_active_accounting_leaf`) |
| 授权模型 | 自动点收对单据走「证据即授权」：入库单每一行都必须来自一个未撤回的先入库登记行且落仓一致，否则 403；数据库触发器再兜一层 |
| 并发 | 品质判定的预锁集合按「未来那张 FINISHED_IN」的等价前像一次拿全(落仓唤醒 + 父工序需求 + 销售归属)，回调时不再补拿上游目标 |

两条链共享的口径：位置是事实、库存只在合格时产生、不合格永远不需要出库单、独立权限、原流程保留为默认。

## 七、修订 2026-09-21：品质批量审批提速

用户口径：「质检部批量审批点击提交报告特别慢」。用真实链路探针(`QualityBatchApprovalPerfProbeTest`，
Testcontainers 真库、逐条 SQL 计时)量出：5 行先入库后检的收货单一次结论 2.2-2.8 秒、1233-1457 条 SQL，
93% 时间在等数据库往返；未上架的普通合格单 0.6 秒、318 条。三处改动：

1. **一次结论一个自动转正批次**(上节)。此前逐行各起一个批次，来源预锁发现跑 30 遍、订单结案重算 26 遍、
   生产推进按批次跑 5 遍。
2. **同一事务只刷一遍物料分析**：整单在本次结论里结案时，`afterInspectionStockInConfirmed(batches, false)`
   只推进供给状态与到货通知，物料分析刷新交给结案回调(`onPurchaseReceiptApproved` /
   `onSubcontractReceiptApproved` 按整单 RESOLVED 维度，是本批维度的超集)。未结案(部分行仍待检)时照旧刷新。
3. **前端逐单提交**：批量审批页此前 4 条并行通道；同一主仓/同一订货单的单据在服务端按同一把
   物料分析仓级锁与订单行锁串行，并行只会互相等锁并撞「来源集合在预读后变化」整笔重跑。改为按报告顺序
   逐单发送，进度逐单推进、失败不连坐、重试只补未确认的单。
