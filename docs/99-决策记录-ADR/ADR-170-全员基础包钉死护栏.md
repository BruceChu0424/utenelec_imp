# ADR-170：全员基础包钉死护栏（体系准入码不可在管理页移出）

- 日期：2026-10-09。
- 状态：用户授权实施；源码及本地回归不代表公司服务器已部署。
- 遵循 ADR-109（grant_policy 是「一个码能怎么授」的唯一事实源）与 V677 平移的员工基础包口径；
  修订 ADR-168 §2.5 中「三码仍在全员基础包（要整体关掉就到『全员基础包』页移出）」的口径。

## 1. 背景与事故

2026-10-09 用户反馈「销售下单 → 财务通过后，计划部（李桃秀）没有收到新任务弹窗」。
全链路排查结论（开发库实证）：

1. 全员基础包按「期望的完整集合」整体保存，**移出一律允许、无任何护栏或告警**。
   2026-10-09 01:29 超管在权限管理页一次保存把当时包内 6 个码全部移出
   （audit_log 89403-89408，同一 request_id；含 `notice:read`）。
2. `notice:read` 一旦离开基础包，**全体非超管用户同时失去三样东西**：
   - 前端 `NoticeArrivalListener` / `ReviewPendingLoginGate` 的挂载资格（`AppUser.can('notice:read')`）；
   - `/api/notices/**` 全部接口的访问权；
   - `ChainNoticeService` 每个发卡池的接收资格（发卡池都要求 `notice:read`，如计划接手卡
     要求 `SUB_PLAN 子树 ∩ notice:read ∩ production_material_analysis:view ∩ :create`）。
3. 于是财务确认事件 `SALES_ORDER_FINANCE_CONFIRMED` 投递"成功"却生成 **0 行**计划接手通知
   （outbox status=1、无报错）；V825 补发用的是同一个资格池，同样永远补不回来。财务侧弹窗
   「看似正常」只是因为测试操作者是超管（有效权限恒为全量目录码）。
4. 事后一次手工修复只恢复了 V831 断言卡住的 3 个自助码，漏掉 `notice:read` 与
   `profile:edit:self`（治理记录 2026-10-08 第 51 行），偏差持续到本次定位。

问题的本质：**一个可整体编辑的集合里坐着多个子系统的准入开关，一次误操作就能让全公司
通知静默熄火，且熄火路径上没有任何日志、报错或护栏。**

## 2. 决策

**员工基础包 5 码是「体系准入」权限，钉死在全员基础包（`permissions.baseline_pinned`），
管理页不可移出；只有数据库迁移能解除钉死或调整钉死名单。**

1. 钉死名单（V677 平移的员工基础包里存活至今的全部码）：
   `notice:read`、`profile:edit:self`、`expense:apply`、`suggestion:submit`、`payroll:view:self`。
   （`visitor:host_confirm` 已由 V679 移出、`ai:use` 已由 V821 移出，均维持各自决策，不钉。）
2. 三层护栏：
   - **服务层**：`setBaseline` 差量计算后，`removed ∩ 钉死码 ≠ ∅` 即整单拒绝（BUSINESS 报错，
     报错文案点名码并指引「个别收回用个人收回；调整钉死名单走迁移」）。
   - **数据库层**：CHECK 约束 `permissions_baseline_pinned_chk`（钉死码必须同时在基础包）；
     V832 迁移同时把 5 码恢复/置为 `baseline=TRUE, baseline_pinned=TRUE` 并失败关闭断言。
   - **前端层**：基础包编辑器里钉死码开关锁定（禁用、恒显示已包含、带锁图标与提示），
     「本组/本模块全部移出」批量操作跳过钉死码；保存提交集合恒含钉死码——即使库被手工
     改坏，从该页保存也会把它们带回基础包。
3. **排除个别人的通道不变**：`user_permission_overrides` 的个人收回仍最高优先
   （`PermissionResolver` 合成规则不变），「个别滥用者按人收回」仍可用；钉死只封「整体移出」。
4. 名单数据驱动：钉死标记是 `permissions` 表的一列（目录 DTO 下发 `baselinePinned`），
   遵守 ADR-109「代码里不得按码写死授权名单」的契约；未来增减钉死码一律走迁移。

## 3. 与既有决策的关系

- ADR-109「基础包管理页可编辑」维持：**非钉死码**的加入/移出照旧按差量保存。
- ADR-168 §2.5「要整体关掉就到全员基础包页移出」对 4 个自助码的口径废止：它们现在是钉死码；
  要整体关闭某个自助能力，改为「钉死解除迁移 + 部门/个人按需加授」，且必须先评估
  通知链熄火面（`notice:read` 永不允许走这条路径，它等价于关闭全公司通知体系）。
- V831 的「三码 baseline 必须维持」迁移断言升级为运行时也成立（此前断言只在迁移时检查，
  运行期管理页仍可改掉——本次事故正是钻了这个缝）。

## 4. 影响面

- 迁移 `V832__pin_employee_baseline_package.sql`（加列 + 恢复 5 码 + CHECK + 断言）。
- 服务端：`Permission` 实体与 `PermissionRepository.findBaselinePinnedCodes()`、
  `DepartmentPermissionAdminService.setBaseline` 护栏、`PermissionCatalogDto.Item.baselinePinned`。
- 前端：`AdminPermission.baselinePinned`（模型两处解析）、`AdminBaselinePermView` 锁定交互。
- 契约锁定：`DepartmentPermissionAdminServiceTest.baselineRejectsPinnedCodeRemovalWithoutAnyWrite`、
  `PermissionAdministrationPostgresTest.baselineRejectsPinnedEmployeeCodesAndKeepsThemInPlace`（真库）、
  `admin_grant_policy_ui_test` 新增钉死用例（开关禁用 + 批量移出跳过 + 提交集合恒含钉死码）。
- 数据修复：开发库 2026-10-09 已直接恢复 5 码 baseline（等价 V832 的 UPDATE 部分，
  授权纪元触发器已让全员令牌按新基础包重算）。
