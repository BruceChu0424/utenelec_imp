# V895 生产备注来源与规模核验

日期：2026-10-21。范围：生产分析、生产计划和车间按任务读取销售整单备注及销售行备注的 SQL 投影；V895 原始私有来源函数的调用边界。本记录不是部署、浏览器验收或完整生产流程的通过证明。

## 来源与权限边界

`ProductionSalesRequirements` 从已经授权的分析项、计划项或可见执行分段读取要求。分析详情、计划详情/历史、车间工作台及工单入口继续执行各自已有的文档和责任范围检查；本变更没有新增读取入口或放宽数据权限。

备注按销售行 UUID 来源传递，不按货品名称或货品 UUID 合并。执行分段存在明确销售分摊时只读取正数量的分摊；全部分摊为零时不回退到整个计划。合并任务可以保留来自多个销售行的不同要求，分别列出。

独立子批次保留后，原父批次撤回不会删除子批次 CREATE/APPEND 事件中记录的原始来源。函数仍校验当前 allocation 份额合计、货品/颜色/单位和冻结 BOM 路径。存在精确事件结构时，精确来源替代物理父指针和泛化 allocation 祖先；证据不平衡或结构不符时不退回泛化来源。因此，父批次同时服务 A/B 两单而子批次仅属于 A 时，B 的备注不会混入。

## 性能根因与最终形状

最初按整个分析调用来源函数，即使只读取一个子任务也会展开无关历史批次。真实 PostgreSQL 计划中，1000 批的 `proof` 被重复扫描 1000 次，且触发高成本 JIT；999 批已取消、只剩一个活动批次时仍会展开 1000 批。

把函数放进带 context 的递归虽然解决单任务读取，但 1001 个 context 的递归估价又使 PostgreSQL 生成 243 个 JIT 函数，单次约 1.39 秒用在编译。仅物化函数输出、改 PL/pgSQL 边界或调整 ROWS 估计均未稳定解决，因此均未采用，也没有关闭全局 JIT。

最终 SQL 先在本次分析范围内一次物化便宜的候选结构边，再对不带 context 的 item UUID 求去重闭包。候选边包含物理父项、活动 allocation 指向的 canonical 所属项以及该 canonical 的历史 alias 原始所属项。它们仅用于限定可能需要解析的批次，不直接产生备注。

这个上界完整：合法精确来源要么 `original=canonical`，要么必须具备原始材料到 canonical 的有效 alias，两种路径均在候选边中。候选中活动 anchor 批次按 analysis 组成 UUID 数组，由唯一 `_scoped_batches` JSON 解析函数一次处理。随后物化真正的来源边，再计算各 context 的精确 lineage；两次递归均使用 `UNION` 去重终止循环。没有为备注复制另一套事件解析或数量计算规则。

## PostgreSQL 证据

采用 PostgreSQL 16 默认 JIT 设置。表形状、主键、唯一约束和真实函数来自完整 Flyway 迁移的 catalog；额外加入对应的分析/事件索引。包括真实的 `UNIQUE(anchor_analysis_item_id)`。薄表夹具不复制 CHECK、外键或业务触发器，因此这是投影、来源和容量验证，完整撤回/收货写链由相应业务 PostgreSQL 用例验证。

隔离夹具同一 analysis 下有 1000 个活动 anchor 批次，均有合法原始来源证据。每次预热两次、计时五次，并另存 `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`。最终生产源码生成的 SQL 与胜出候选去掉注释和空白后完全一致；迁移 catalog 中实际 array parser 与当前源码函数体也一致。

| 无合并批次，读取销售根项 | 16.72 ms | 1.87 ms | 0 | 1 |
| 100 批，读取子批次 | 2.84 ms | 2.04 ms | 1 | 1 |

## 回归与复测状态

`ProductionSalesRequirementsPostgresTest` 当前四个真实 PostgreSQL 用例全部通过：

1. 同货品不同订单保持整单/行备注隔离，多层子件继承及共享来源分别保留；旧父指针循环可以终止。
2. 执行分段采用准确分摊、零份额不回退、未明确分摊时采用原有计划回退规则。
3. 合法 NULL 父指针的独立 anchor 在撤父后保留原始备注；活动父 A/B、子仅 A 不混单；额外防御无效旧父指针；份额不平衡和冻结 BOM 改变均不猜来源。
4. 1000 批容量回归：单项只处理一条 proof、全项总处理 1000 条，默认 PostgreSQL 不对递归 JSON 执行 aggressive JIT optimization，且全部 1001 个 context 的销售行 UUID 正确。断言使用计划工作量，不设置机器墙钟阈值。

薄表测试依赖按顺序复制真实 `_scoped_batches` core、scoped wrappers 和公开 wrapper。`MigratedProjectionSchema` 缓存实际迁移后的函数定义，同名重载按参数数目降序复制；未使用空函数 stub。

此前 110 项性能/稳定性快照早于 V895，不能被当作本轮新函数和新 SQL 的覆盖。本记录的四项通过与全平台最终门禁、2970 节点服务复测、打包和部署状态分别报告。

## 数量函数早返回的资源跟进

备注 SQL 冻结后，又只读审查了 `fn_preplan_aggregate_retained_private_sources_scoped`、`fn_preplan_allocation_admitted_qty` 和 material pending。这里的基线取自另一套完整迁移 PostgreSQL catalog 的真实 retained 函数，并复制其实际非唯一索引到隔离薄表；没有用空函数替代。仅在隔离数据库替换早返回条件、增加试验索引作对照，没有据此改数量、FIFO 或领用规则。

普通路径只执行存在性查询便返回，不解析事件 JSON 或计算 BOM 容量。但一条存在性 SQL 并不等于常数工作量：现有 `idx_preplan_supply_action_analysis_open` 和 workbench partial index 均排除了 CANCELLED 行。早返回查询在本次夹具中每次顺序扫描 1000 个活动 action，过滤 1000 行、命中 23 个 shared blocks；调用 1000 次就是约百万行检查。

两组均使用 1000 个活动合并批次、同 analysis 的 1000 个不同 material，目标 analysis 没有任何取消父批次，所有函数调用都返回空集。第二组再加入另一个 analysis 的 1000 个普通 CANCELLED action，以验证全局历史不能侵入目标范围。

| 早返回形状 | 无其他取消历史，1000 次调用中位数 | 另 analysis 有 1000 取消 action，1000 次调用中位数 |
| --- | ---: | ---: |
| 原条件、实际现有索引 | 56.58 ms | 624.80 ms |
| 仅补 `action.analysis_id=p_analysis` | 61.11 ms | 125.59 ms |
| 范围条件 + CANCELLED partial index | 14.89 ms | 30.53 ms |
| 仅 partial index，保留原条件 | 17.21 ms | 599.60 ms |

试验索引为 `preplan_supply_actions(analysis_id,id) WHERE status='CANCELLED'`。范围条件加该索引后，计划采用目标 analysis 的空范围 Index Only Scan，命中 1–2 个 blocks；第二组的单次存在性查询执行约 0.04 ms。仅有索引仍会扫描别的 analysis 的取消 action，再逐个尝试 batch 关联，因此不能只加索引而省略范围条件。这两项是有计划证据的建议；是否已经并入业务迁移及最终业务门禁结果由主任务记录，不以本次试验代替。

证据：`server/target-notes-v895-review/retained-early-return/` 与 `retained-early-unrelated-history/`，含真实函数定义、实际索引定义、四种形状的外层/存在性 EXPLAIN 和计时 JSONL。第二组复用第一组已采集的真实 catalog 定义及索引，未把试验 index 当作基线索引。两组均默认 JIT，未生成 JIT；墙钟数值来自隔离夹具，不作为生产 SLO。

## 尚未证明消除的相关责任重复计算

当前 retained 已先筛选“活动 child allocation 指向取消 parent canonical”的候选批次，再按准确 material aliases 限定责任，避免一次取消引起无关整个分析的 JSON 展开。这不意味着同一个 canonical 的大量相关批次可以任意过滤：它们共享原始容量与 FIFO 竞争，必须一起参与权威计算。

进一步的薄表 probe 原样使用当前 `candidate_batches` 条件，设置真实冻结 BOM alias 且 `original<>canonical`，复用真实迁移的 array parser；核对 parser 函数体与当前源码忽略空白后一致。1000 个活动 child 的逐批解析中位 243.26 ms，一次 array 解析 49.44 ms，均处理 1000 条 proof 且逐行原始材料 UUID 正确。999 个 child 取消后两种形状均只处理剩余一条 proof；array 中位 4.77 ms。全部 1000 个 child 取消后，array scope 使用 `HAVING count(*)>0`，零返回且 `proofWork=0`，中位 4.42 ms。以上均未生成 JIT。

这证明候选状态过滤已经生效，历史已取消 child 不会进入解析；可进一步把候选 UUID 汇成一次 array 调用。聚合空集时必须跳过调用或传空 `uuid[]`，不能直接传 `array_agg` 产生的 NULL，因为 core 的 NULL 参数表示整个分析。证据为 `server/target-notes-v895-review/retained-eligible-scope/`。该 probe 只验证 immutable proof 的工作范围，不是完整 retained 容量、FIFO、admitted 或服务详情资源改善证明。

有两个明确的读侧复用位置仍需真实相关批次样例验证，不能因普通空路径通过便宣称解决：

- `MaterialAnalysisService.ACTIVE_FUTURE_COVERAGE_SQL` 已物化一次 `retained_private`，但 `allocation_pending_raw` 的普通分支仍逐 allocation 调 `fn_preplan_allocation_admitted_qty`。受影响 allocation 会再次进入同 canonical 的 retained 容量/FIFO 计算。若同 canonical 有 N 个相关 allocation，这里存在 N 次重算 N 条责任的调用形状。可验证的候选是在这个 SQL 已有 retained 快照内按 allocation 汇总 admitted，严格保留公开函数的“无 retained 行回退 base；有行时保留真实 received 下限”规则；涉及 future transfer/shared claim 的分支不能擅自替代。
- `preparationAdoptedQuantities` 也逐 allocation 调 admitted，可在其单一 SQL 读取阶段采用同样的准确汇总。`AggregatePrivateIntentReader.ALLOCATION_PENDING_CTES` 的 allocation capacity 和 action admitted 分支同样会进入该公开函数，需纳入相关用例的内部数据库工作量观察。SQL 条数统计不会看到这些函数内的重复语句。

复用时按 allocation 汇总 `SUM(retained.admitted_qty)`，精确对应公开函数：sum 为 NULL 时回退 `fn_preplan_allocation_base_admitted_qty`，否则取该 sum 与真实 allocation received 的较大值。sum 为零仍必须命中责任计算，不能以 `qty>0` 决定回退。`MaterialPreparationBudgetReader` 本体目前没有 retained CTE 或直接 admitted 调用；这里的 `preparationAdoptedQuantities` 属于 `MaterialAnalysisService`，不应误改前者已有的普通计划私有供给规则。

`aggregateMembers`、future coverage、`hasAggregateAliasSupply` 之间属于固定数量的独立 SQL；收货侧 `retainedReceiptSources` 已对整张收货单一次读取并复用。优先保证同一只读 SQL/阶段内复用，不在写入之后、跨请求或跨事务复用旧责任。material pending 的既有 alias 递归有路径/32 层保护，原始 BOM 容量另有访问集合/64 层检查；这些深度边界不自动证明新 admitted/retained 回调在任意旧结构下都不会重复工作。

最小完整服务复测方案为复用 `ProductionMaterialAnalysisScalePostgresTest#readProjectionQueryBudgetAndSalesRequirementsAreBatched` 一个方法：真实 Spring/完整迁移下，198/2970 节点分别预热后读三次，检查零 DML、最多 45 条 SQL、32/128 MiB 线程累计分配预算，并保留相同输入 refresh 的 xmin 和真实改量断言。待 V895 业务冻结后仅运行这一方法，单独记录源码、class/resources 指纹及 SQL trace，与 V894 快照比较。该无供给行动样本不能证明取消父后的密集相关批次资源问题已经解决。
