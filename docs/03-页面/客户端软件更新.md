> 2026-10-26 增加[软件下载页](软件下载页.md)：工作台右上角进入，自动将当前设备平台放在最前；当前仅 Windows Setup.exe 可下载，Android、macOS、iOS 暂时无法下载。安装程序使用 `packageKind=installer` / `installMode=windows_setup`，与原应用内更新包共用发布目录、上传下载和权限，但不会参与 `/check` 更新检查。旧请求及历史元数据默认 `packageKind=update`；旧 `windows_bundle` 完整 ZIP 兼容保留。包生成和正式上传按用户后续明确指令执行。

> 2026-10-29 网页更新提示改为屏幕居中的品牌弹窗并新增空闲自动更新，桌面客户端同步纳入。网页端：新打开页面发现新版时在应用加载前直接刷新到新版；已打开页面每分钟核对 `version.json`，检测到新版后弹居中提示（公司名称 + 平台名，标题「有新的版本（版本号）」，正文「建议立即更新」，附当前版本），下方提供「空闲时自动更新」勾选框，默认勾选、按设备保存在 `localStorage`。页面连续空闲且没有未保存内容、没有未完成的提交或下载时，弹窗中出现大数字倒计时（每秒变化）并在主按钮上同步显示秒数（如「已保存，立即刷新（8 秒）」），10 秒后自动刷新；任何输入立即取消倒计时，可点「继续工作」先保留页面。安全性由 Dart 侧安全登记表提供：编辑器脏状态、在途请求、未知提交结果、浮窗与不可自动刷新的路由都会阻止自动刷新，未知状态一律视为不可刷新。桌面客户端：软件更新专页显示当前版本与最新版本，新增「软件空闲时自动更新」设置，默认开启、保存在本机。开启后 Windows 更新包在检查发现时即下载并校验暂存（登录前后均可，暂存包与服务器端点绑定、登录切换即失效）；应用内连续空闲 5 分钟、或退出到登录界面连续空闲 60 秒且工作已保存时，弹出同款品牌倒计时弹窗：大数字 10 秒倒数到 0 自动安装，「立即更新（N）」立即安装，「稍后」取消本次（点击本身算输入，需再等一个完整空闲窗口才会再次提示）；倒计时到 0 时若有操作未完成会在 0 处等待，操作结束后继续安装；安装前重新校验 SHA-256，自动安装失败一次后该版本转为手动处理不再自动重试。登录界面安装路径不发任何网络请求。关闭设置后仍弹更新提示（无倒计时），由用户手动更新。服务器更新的既有 10 分钟倒计时流程不受本批改动影响。

## 使用方式

员工在设置页“关于”中打开“软件更新”专页，查看当前安装版本、详细更新内容并检查更新；持有“发布客户端版本”权限（`client_release:publish`）的员工另有发布对话框，Web 端也可使用发布入口。服务器发布适合本机平台、架构的新构建后，客户端在员工登录后、回到前台时以及前台每五分钟检查。居中提示只告知发现新版本，不展示长篇说明；点击“查看详情”进入软件更新专页，在页面阅读新增、优化、修复内容，点击“立即更新”后下载、校验并升级。本轮访客端不启动自动检查。

管理员先上传安装包，再发布。上传完成但尚未发布的草稿不会触发客户端更新；撤回停止后续检查和下载，不会远程降级已升级的设备。客户端更新不执行数据库迁移、后端重启或服务器更新作业。

应用关闭、设备离线、账号未登录时，本轮不提供系统推送或常驻后台服务。重新打开并登录后继续检查。界面中的“自动收到”表示应用运行期间自动检查，不能解释为设备关机或应用完全退出时仍会收到通知。

客户端自动检查只访问当前已登录的公司业务服务器，读取该服务器已经发布的客户端版本；不调用阿里云 OSS，也不触发服务器检查发布源。公司内网的这类请求不会产生 OSS 请求或下载费用。通过外网远程入口下载时，仍可能消耗该入口的云端带宽或流量，不能据此承诺所有网络使用均免费。服务器从 OSS 获取新版的规则见[服务器更新](服务器更新页.md#检查与更新)：仅手动检查或明确确认的更新作业访问发布源。

## 平台范围

| 客户端 | 本轮方式 | 必须满足的条件 |
|---|---|---|
| Windows | 下载本项目生成的 ZIP；退出后备份并替换程序文件，再启动 | 先安装含更新能力的完整客户端；运行账号对安装目录有写权限；包与本机架构一致 |
| Android | 应用内下载 APK，校验后打开系统覆盖安装确认 | 首次允许本应用安装更新；APK 的包名与签名须与现有安装一致，版本代码更高；系统仍可能要求确认 |
| iPhone / iPad | 提示后打开官方 App Store 更新入口 | 已建立对应 App Store 应用，管理员填写该应用的 `https://apps.apple.com/…` 链接 |
| macOS | 提示后打开官方 App Store 更新入口 | 已建立对应 Mac App Store 应用；本轮不提供 ZIP 覆盖更新或 Sparkle 接入 |
| Linux | 本轮不提供包发布和应用内覆盖升级 | 后续需接入正式签名、安装及更新链路；不得以打开普通文件下载页冒充自动升级 |
| Web | 不显示原生客户端覆盖安装操作 | 沿用网页已有版本检查与刷新机制 |

Android 也允许管理员选择 `https://play.google.com/store/apps/…` 官方商店链接，此时通过商店更新而不上传 APK。普通 APK 更新不能保证无确认静默安装。Android 安装器是否允许免确认取决于系统版本、更新所有者和安装权限等条件，详见[Android 安装器官方说明](https://developer.android.com/reference/android/content/pm/PackageInstaller.SessionParams#setRequireUserAction(int))。
iOS 原生应用升级遵守应用分发渠道，不能由应用自行下载并替换可执行代码；参见 [Apple 软件要求 2.5.2](https://developer.apple.com/app-store/review/guidelines/#software-requirements)。本轮没有 Apple 企业 MDM 或 TestFlight 推送接入。

## 界面约束

沿用 `frontend-design` 与项目现有 Uten 组件、主题和响应式约定。更新行使用已有设置分组与按钮，发布页使用现有容器、表单和反馈；不另建颜色或权限体系。

- 登录提示与软件更新专页分层：居中提示保持简洁，仅显示发现新版本及“查看详情/稍后”；专页完整呈现版本对比、更新说明、“立即更新”及下载和安装进度。
- 明确区分“当前安装版本”“可更新版本”“正在下载”“正在校验”“即将重启”与失败原因。
- 更新前说明会关闭并重新打开程序；用户应先保存当前工作。持久草稿、语言、主题、服务器选择等既有本机数据不属于程序替换范围。
- 网络错误或无有效更新源时显示检查失败，不显示“已是最新版本”。
- 校验失败时保留当前可用程序，提供重试；点击重复更新不得并发下载或启动多个安装器。
- 发布管理员与普通使用者分别看见其权限允许的操作。更新自己安装的软件不要求服务器更新权限。

## API 与发布状态

员工读取接口使用现有登录身份；沿用网络、远程访问、改密与会话安全边界。

| 请求 | 用途 |
|---|---|
| `GET /api/client-updates/check?platform=windows&architecture=x64&currentBuildNumber=2527` | 按本机平台、架构和构建号查询；返回 `updateAvailable`、`release` 和检查间隔 |
| `GET /api/client-updates/{id}/download` | 下载仍为已发布状态的指定安装包 |
| `GET /api/admin/client-releases` | 查询管理员发布列表 |
| `POST /api/admin/client-releases` | 创建发布草稿 |
| `PUT /api/admin/client-releases/{id}/package` | `application/octet-stream` 上传安装包原始字节 |
| `POST /api/admin/client-releases/{id}/publish` | 发布已完成校验的草稿 |
| `POST /api/admin/client-releases/{id}/withdraw` | 撤回发布 |

发布元数据包含请求 UUID、平台、架构、显示版本、严格递增的数字构建号、更新说明、是否重要更新、文件名、包 SHA-256；iOS 使用商店链接。服务端计算实际 SHA-256 和字节数，客户端重新核对后才安装。显示版本只用于阅读，版本先后由构建号比较，避免把 `2.5.10` 排在 `2.5.9` 前面。

发布管理统一要求 `client_release:publish`，覆盖发布记录查看、草稿创建、安装包上传、正式发布和撤回。该权限使用 `INDIVIDUAL_ONLY` 策略，由超级管理员逐人授权，不能授予部门或由负责人转授；不会因已有 `authorization:manage` 或 `server:update` 而自动获得。超级管理员的权限仍由服务端目录统一下发，前端不另设绕过条件。V946 新增目录与“客户端版本发布”权限面。

无此权限时设置入口隐藏，直接打开对话框也不能加载发布记录或提交；后端各接口与服务层同样拒绝。访客、代操作和必须改密的会话不允许管理。权限撤销、换号或服务器变化后，已经打开的发布对话框退出，旧操作的迟到回执不能继续上传或发布；重新授权后须重新进入。创建与上传只准备不可分发的草稿；发布和撤回继续执行现有敏感操作再认证。普通员工可更新自己客户端，无需发布权限或 `server:update`。

状态为 `DRAFT`、`PUBLISHED`、`WITHDRAWN`。已上传且校验通过的包仍保持 `DRAFT`，通过 `sha256` 和 `sizeBytes` 表达上传事实；发布后才进入 `PUBLISHED`。以接口返回的 `state` 为准，不能凭一次上传进度或按钮反馈认定已经发布。网络响应不明时先读取原请求/发布记录，不通过新建草稿掩盖原请求结果。

## Windows 安装包与本机更新

Windows 应用内更新包必须由 `deploy/client/package_windows.py` 从完整 Flutter Release 输出生成。ZIP 根包含 `uten_imp.exe`、Flutter 引擎及插件文件、`data/` 与 `uten-client-manifest.json`。清单固定为 `schemaVersion: 1`，记录 `platform`、`architecture`、`buildNumber`、`executable` 及每个文件的相对路径、字节数、SHA-256；不能直接上传任意 ZIP 或安装脚本。首次安装则由标准 Setup.exe 完成，构建及上传说明见[客户端部署](../../deploy/client/README.zh-CN.md)。以后点击软件内的“立即更新”自动使用当前目录，不再启动首次安装器或重选路径。

例如下一版构建号为 `2528` 时，由发布人员在可信环境构建并封包：

```powershell
flutter build windows --release --build-name=2.5.28 --build-number=2528 --dart-define=APP_VERSION=2.5.28 --dart-define=API_BASE_URL=https://<公司可信域名>/api --dart-define=CLOUD_API_BASE_URL=https://<云端可信域名>/api
python deploy/client/package_windows.py --bundle build/windows/x64/runner/Release --output output/uten-imp-2.5.28-windows-x64.zip --build-number 2528 --architecture x64
```

占位域名须替换为现有批准的地址，不在命令里填写凭据。包工具输出 SHA-256 与大小，管理员界面选择更新包后也会计算摘要。正式签名与各平台构建前提继续遵守[多端发布与签名](../99-项目治理/多端发布与签名.md)。封包器和更新程序都核对 EXE 的实际 PE 构建号与架构，不能仅修改表单数字充当新程序。

首装版本随 CMake 安装固定更新程序 `client_updater/client_updater.ps1`；后续更新包排除该目录。应用通过 `com.uten.imp/client_update` 桥读取本机平台、架构、原生构建号和私有暂存目录，将已校验安装包交给固定程序。服务端不能指定客户端执行的命令。

更新程序先等待原应用退出，再备份现有程序、替换文件并重新启动。异常时尝试恢复旧文件，并将诊断写入暂存目录的 `last-update.log` 与 `last-update-result.json`。本机仍运行失败目标的旧构建时，详情页显示上次更新未完成。成功后只清除此作业的解压文件和下载 ZIP，恢复备份保留；跨作业旧备份尚未自动裁剪，需要纳入本机空间保留策略。这不等同于断电后的完整事务保证；断电、磁盘损坏、防病毒阻断、权限不足与新程序运行后业务错误仍需单独验证和处理。

程序文件替换保留现有技术标识及 AppData，不清空 shared preferences、安全存储、设备标识或持久草稿。尚未保存的内存编辑不会因替换程序自动保存。首次安装过的旧客户端若没有更新检查器，无法通过本次上传自动获得它，必须先安装一次新的完整客户端；以后才可走应用内更新。

## 管理员发布步骤

1. 从待发布的同一份完整源代码构建客户端。Android 使用固定正式签名；Windows 使用完整 Release 目录和打包脚本。保持应用标识不变并增加构建号；Windows 原生版本字段允许 `1..65535`。
2. 核对平台、架构、显示版本和构建号。计算安装包 SHA-256；填写更新说明，创建草稿。
3. 上传所选 ZIP/APK，等待服务端读完并验证哈希、大小及包结构。上传进度达到 100% 不等于校验或发布完成。
4. 确认草稿显示的版本、架构、哈希和大小，再点击发布。iOS 核对官方商店链接指向自己的应用。
5. 用已安装上一版本的测试设备登录，确认收到提示、下载、校验、升级和重启；核对设置与草稿保留后再推广。
6. 发现问题时撤回阻止继续分发。已升级的客户端需要发布新的更高构建修复版；不通过降低构建号远程覆盖。

## 部署与存储

客户端包与元数据均保存在后端专用持久目录，每个发布 UUID 下包含 `release.json` 与 `package.bin`；目录级 `.catalog.lock` 串行化元数据变更，元数据经临时文件和替换写入。大包上传在锁外写入独立暂存并校验，提交时重新加锁核对草稿与发布参数，避免慢上传阻塞在线客户端检查；同时最多两个上传。上传过程中每 8 MiB 检查剩余磁盘空间，保留默认 1 GiB 空间。文件落盘不等同于所有系统断电场景的完整事务保证。本轮不创建数据库发布表。配置项如下；最终有效默认值以 `ClientUpdateProperties` 和当前应用配置为准。

| 配置 | 环境变量 | 默认/用途 |
|---|---|---|
| `uten.client-updates.directory` | `UTEN_CLIENT_RELEASES_DIR` | 留空时从后端存储目录派生；正式环境建议指定绝对持久目录 |
| `uten.client-updates.max-package-bytes` | `UTEN_CLIENT_UPDATE_MAX_PACKAGE_BYTES` | `536870912`，单包最多 512 MiB |
| `uten.client-updates.min-free-bytes` | `UTEN_CLIENT_UPDATE_MIN_FREE_BYTES` | `1073741824`，上传后至少保留 1 GiB 可用空间 |
| `uten.client-updates.poll-interval-seconds` | `UTEN_CLIENT_UPDATE_POLL_SECONDS` | `300`，客户端检查间隔秒数 |
| `uten.client-updates.max-releases` | `UTEN_CLIENT_UPDATE_MAX_RELEASES` | `200`，持久目录最多保留的版本记录数；达到上限需受控归档 |

此目录必须由后端服务账号读写，不能位于 Web 静态根目录或随发布删除的临时目录。保证磁盘空间覆盖当前包、上传临时包和待分发版本；备份与恢复必须同时保留包目录中的元数据和实际二进制。目录默认位于已有私有存储写入边界内；显式改到外部路径时，须预建目录并同步 systemd `ReadWritePaths` 允许范围。客户端包生命周期独立于业务数据清空，不能被普通附件清理或业务清空误删。

反向代理默认 2 MiB 请求上限不足以上传安装包。本轮已同步 `deploy/nginx/uten-imp-http-lan.conf`、`uten-imp.conf.example`、`uten-imp-internal-test.conf.example`、`deploy/cloud/nginx-cloud.conf.example` 与 `deploy/remote-access/templates/company-nginx.conf.tmpl`：仅安装包上传路径单独允许 512 MiB 原始流与 30 分钟读写超时，下载路径流式传输并禁止代理缓存，保留认证、请求标识和来源头。普通 JSON/附件额度维持原范围；应用仍按实际字节数执行上限。云端远程通道只转发 TLS 字节，不新增 HTTP 放行。上线需重新渲染当前使用的模板，运行 `nginx -t` 后受控重载，并用超过 2 MiB 的真实测试包核对路径。

生产下载与 API 使用可信 HTTPS 端点。客户端不接受任意下载主机或服务端指定执行命令。SHA-256 证明下载内容与已授权发布包一致，不是独立的软件发布者签名；Windows 本轮尚未接入独立签名公钥或 Authenticode 发行证书，发布权限和 HTTPS 是当前信任边界。Android 覆盖安装另外由系统验证应用签名。
