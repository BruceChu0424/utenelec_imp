# ADR-003 - 性能分级三档（lite/standard/rich）

- **状态**：已接受
- **日期**：2026-07-21

---

## 上下文

用户场景：
- 员工设备差异大（从最新 iPhone 到 2GB 内存的老 Android 都有）
- 用户要求：**性能好的设备要"更炫"，性能差的设备要"流畅"，自动适配**
- 同时要允许用户手动调整（不喜欢动效的人能关掉）

## 决策

**采用三档性能分级：lite / standard / rich**，自动检测 + 手动覆盖。

## 档位定义

| 档 | 视觉表现 | 目标设备 |
|---|---|---|
| lite | 无模糊、动画压缩、骨架屏不闪烁 | 低端 Android（<3GB 内存）、老旧设备 |
| standard | 标准动画、轻度模糊 | 中端设备（默认） |
| rich | 玻璃模糊、进场动画、3D 效果 | 高端手机、平板、桌面 |

详细规则见 [../00-项目准则/07-性能自适应.md](../00-项目准则/07-性能自适应.md)。

## 理由

### 为什么三档而不是两档？

- 两档（开关）太粗：要么全开要么全关，中端设备用户没选择
- 三档（lite/standard/rich）覆盖典型设备分布的低/中/高三档
- 多于三档管理成本上升，收益递减

### 为什么自动检测 + 手动覆盖？

- 纯自动：用户失去控制（如高端机用户讨厌动画想关）
- 纯手动：低端用户不知道要切到 lite，体验差
- **自动检测给出建议 + 用户可覆盖**：兼顾两者

### 为什么不在 Flutter 性能优化上做？

- Flutter 性能优化（repaint boundary、const Widget、ListView.builder）**本来就该做**，和性能档无关
- 性能档是**额外的视觉降级机制**，针对 BackdropFilter / 着色器 / 复杂动画这类重负载

## 实现要点

- `PerformanceTier` 枚举（`auto` / `lite` / `standard` / `rich`）
- `PerformanceProvider`（Riverpod）管理当前档位
- 设备能力检测：`device_info_plus` 读内存/CPU/系统版本，打分映射
- 组件读取 `ref.watch(performanceProvider)` 决定行为
- 持久化到 `shared_preferences`
- 设置页提供切换 UI

## 后果

### 正面
- 低端设备用户也能流畅使用
- 高端设备用户享受更炫视觉
- 每个组件可以独立决定如何降级，灵活

### 负面
- 组件实现复杂度增加（每个要写两套或三套行为）
- 测试成本上升（三档都要测）
- 设计师要为三档都出设计稿（视觉简化规则）

## 缓解措施

- 把性能档行为集中在组件库里，业务代码不感知
- 标准档设计稿做主，lite/rich 在其基础上做减法/加法
- 自动化测试覆盖三档
