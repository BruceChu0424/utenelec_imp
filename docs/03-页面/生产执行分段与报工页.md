# 生产执行分段与报工页

## 2026-10-05 报工产出分组与审核摘要由服务端给出([ADR-148](../99-决策记录-ADR/ADR-148-产成品实物交接批同去向合单.md))

报工详情带 `outputBatches[]`：一次录入的实际产出批次一行，批内按实物交接批分去向组(转给哪个上层工单多少、送入仓库多少及其中计划公共 / 实际超产)，
摘要文案由服务端拼好，例：「V51043 共 1100：送入仓库 1100(其中实际超产 100)」。审核确认逐批列出这句摘要；编辑草稿按批次的 `itemIds`
把同批各份合回一行(一次实际申报)。页面不再自己按 `outputBatchId` 拼组和拼文案(`routeSummary`、`productionDailyReportInputGroups` 删除)。
送入仓库的同一批货在仓库、品质、点收侧都是一批实物：一次登记、一次判定、一张入库单。


## 2026-10-04 只直送给已开通内料仓的车间([V802](../数据迁移/V802-车间内料仓开通单一真源.md) / [ADR-147](../99-决策记录-ADR/ADR-147-车间内料仓开通单一真源与发料来源仓.md))

车间直送不再第一次直送时自动建内料仓。收料车间还没在「车间内料仓」里开通内料仓时，上层工单不能收直送：去向分配里这个工单红字显示「{车间}还没开通内料仓，请仓库在「车间内料仓」开通后再直送，这次先送入仓库」(原因码 `WORKSHOP_BIN_NOT_OPEN`)，报工这部分按原因送入仓库；已开通的车间照旧直送，料落进开通记录里的那个内料仓。报工审核时才发现没开通(例如保存后被撤销)会整单拒绝(409)并说明「收料车间还没开通内料仓，请仓库在「车间内料仓」开通后再直送，这次先送入仓库」，什么都不写。下文「线边仓由系统自动配置」的说法只代表 V595-V801。

## 2026-09-27 一张报工分给多个上层工单时，审核不再越分越慢(V736 / ADR-127 §8)

一行报工分给 11 个上层工单，审核就要在一笔事务里办 11 块直送。改前实测：1 块 2.5 秒、3 块 6.5 秒、11 块 37.4 秒，
已经贴着服务端 40 秒的事务上限(超时整单回滚，页面按「结果未知」重读后仍是草稿)。时间几乎全花在两个库函数问题上：

- 「这批料还能投给这个上层工单多少」的查询把父子关系判定下推到同一货品的全部报工明细上逐条先算，分给 N 个工单就判 N 遍，
  整次审核随 N 平方增长；改为先按接收需求取出这批料，再对出现的生产工单各判一次。
- 几个「来源是否合格」的证明函数每次调用都要重新规划一遍(一次 60-130 毫秒，执行不到 1 毫秒)；改为按数据库连接缓存计划，
  查询条件一字不改(ADR-127 §8)。

审核仍然逐块办：每块自己的班组自检、自己的线边仓入库单、投给自己的上层工单(自己的线边仓领料单)，所有校验与记账照旧。
同一次运行把新旧函数交替实测：中等负载下 11 块由 38.5 秒降到 13.0 秒、3 块由 6-9 秒降到 3.7-4.7 秒；
本机重负载时 11 块由 54-68 秒降到 21-24 秒(看比值，绝对值随机器负载变化很大)。
「把同一线边位置的各块合成一张入库单一次点收」试过，实测反而慢一倍(各块同时进线边仓后，后面每个上层工单投料都要把还没投出去的
各块再查一遍)，没有采用。常驻用例：`WorkshopDirectTransferBatchEndToEndTest#threeReceiverApproveStaysInsideItsStatementBudget`。

## 2026-09-27 一行报工分给多个上层工单：先急后缓逐条分，余量自动补一条(V736 / ADR-127 §7)

一个共享子件批次常要交给好几个上层工单(例如 HV5G001 共享批 11000 分给 11 个成品工单各 1000)。
以前一行报工只能投一个工单，要投多个得手工拆行，没拆的部分被悄悄送进仓库。现在：

- **每个成品报工行下面挂「产出去向」子行**，每条 = 去向(某个上层工单 或 送入仓库) + 去向数量。
  成品行的「产出去向」格写摘要(例如「转下一道工序 2 个工单 2000 · 送入仓库 8000」)；2026-10-01 起，一个可送的都没有时正常显示「送入仓库」及对应数量，悬停查看不可转原因。
- **系统先给建议(黄框)**：第一条给最急的上层工单(先急后缓 = 所属产品行的优先级、交期)，数量 = 它还差的；
  还有余量就在下面自动补一条给下一个还缺料的上层工单，都分满了余量送入仓库。
- **工人可以改任一条的去向和数量**：改大会压低下面的条目，改小则多出来的自动排到下面(下一个还缺料的上层工单，
  没有就送入仓库)；改成 0 的条目离开输入框后消失；一行只留一条「送入仓库」(自动合并)；
  工人从某条上改掉的上层工单不会再被自动建议(想给可以在下拉里再选)。合计始终等于完工申报量。
- **完工申报量改了**：去向按新数量重排；工人改过的数只被压低显示，被压到 0 的条目先藏起来(不提交、不报问题)，
  改回原量后按原数回来——逐键改数(例如 10000 改成 12000 途经 1、12…)不会弄丢工人定的条目；
  只有工人自己把某条改成 0 或清空，离开输入框后才删掉。
- **工人定的「送入仓库」顺带接下的余量不算工人要的**：例如把第一条改成送入仓库 1000，下面分完剩的 4000 暂时并进这一条
  (显示 5000)，但记住的仍是 1000；之后改产量或有上层工单能收了，余量照样先急后缓分给上层工单，不会被这条占住。
- **粘贴行、改勾选也重排**：从复制粘贴栏粘贴进来的行立即按当前余量给出建议(不会空着整行送入仓库)；
  新建日报勾选或取消勾选后，勾选行重新先占上层工单「还差多少」，未勾选行只分剩下的。
- **去向下拉**：按先急后缓列出可送的上层工单「工单号 · 父件产品 · 还差 N」(N 已扣掉本张报工其它行分给它的)；
  本张报工其它行已分满的置灰「已分满」，本行别的条目已分给它的置灰「本行已分给它」；结构上是上层但现在不能收的
  置灰**红字**写原因(跨车间、委外件、已备齐等)，最后一项是「送入仓库」。一行最多同时转给 30 个上层工单。
- **保存时**服务端逐条校验(同一份判定)：不能收或超过还差的数当场报「无法转到下一道工序：<原因>」；
  只有「需求份」能转下一道工序，计划内公共备货与超出计划的产量一律送入仓库，分给上层工单的合计超过需求份时报
  「本行最多 N 可以转下一道工序」。服务端每个上层工单拆一条转送明细，送入仓库的明细记下原因。
- **编辑已存草稿**：按同批次还原成一行报工和它的去向(每个上层工单一条 + 送入仓库合成一条)，都算工人定过的，
  候选读到后只校验、不替换；原来的上层工单现在不能收了就标红，请重新选择。
- **不再按上次报工记忆预填去向**：默认去向由服务端给的先急后缓次序决定。
- **没刷新的旧页面**：部署前打开的报工页仍按「一行一个去向」提交，保存(及追加计划预览/申请)时整单拒收并提示
  「页面版本已更新，请刷新页面后重新填写去向」，不会把旧页面想转下一道工序的量悄悄送进仓库。

**详情页**明细表「去向说明」列：转送明细写「转给 父件产品 · 工单号」，送仓明细写原因(例如「能直送的上层工单都已分满，
其余送入仓库」「报工时选择送入仓库」「HV5ZJ012 是委外件…」「计划内的公共备货部分，统一送入仓库」)。
**审核确认框**逐批列出「货品 共 N：转给 … 多少；送入仓库 多少 (原因)」，最多列 6 批。

共享批次送仓部分入库后分给哪个来源，也按同一「先急后缓」次序(不再按随机顺序)，不会抢先占掉本可直送的上层工单份额。

回归用例：`test/features/production/daily_output_allocation_test.dart`、
`test/features/production/widgets/production_daily_direct_transfer_cells_test.dart`、
`test/features/production/pages/production_daily_report_exact_segment_test.dart`(整页去向分配)；服务端
`DailyReportOutputAllocationServiceTest`、`AggregateMaterialDirectTransferEndToEndTest`。

## 能不能转下一道工序：一份判定，无法流转时显示仓库去向并悬停说明原因(V736 / ADR-127，2026-10-01 更新)

「转下一道工序」能不能送、为什么不能送，只由服务端一份判定给出
([ADR-127](../99-决策记录-ADR/ADR-127-直送资格单一事实源、不可转原因与报工自动分流.md))；
候选、保存、审核与数据库守卫用同一句话：「无法转到下一道工序：<原因>」。

- **一个可送的上层工单都没有**：成品行正常显示「送入仓库」及对应数量，尚未填数量时也显示「送入仓库」；去向子行同样只读显示「送入仓库」，不给下拉。
  两种去向格悬停时均显示完整的「无法转到下一道工序：<原因>」，不把不可转原因作为去向正文，也不标红。常见原因：
  - 上层是委外件(本工单做的是委外件的直属物料)：做好后送入仓库，由委外人员在委外任务中心领料、仓库发给委外商，车间之间不能直送，拦住是对的；
  - 「上层工单 ZX… 在二车间，跨车间必须送入仓库」；
  - 「上层工单 ZX… 的 … 按采购供应，只能从仓库领料」；
  - 「上层工单 ZX… 的生产计划已暂停」「… 已按齐套开工，不再接收直送」「… 已经备齐」；
  - 「本工单做的是顶层产品，没有下一道工序，请送入仓库」「上层工单还没下达到车间，暂时没有可接收的工单」。
- **已定过的上层工单现在不能收**(例如编辑旧草稿时接收方已暂停)：那条去向保留并标红，让人自己改，不替人静默改去向。
- **候选读取失败**：成品行红字「转给工单候选读取失败，请刷新后重试」——读取失败不等于没有上层工单，
  已定的去向不锁死、不判错，也不再给新的转送建议；已定的上层工单在下拉里写「原来选的上层工单(候选读取失败，暂时无法核对)」，
  不标红、不说成「现在不能收」。**提交时**先自动重读一次：仍读不到就拦下「第 N 行：转给工单候选读取失败，请刷新后重试」，
  不会把整行当成送入仓库提交；重读成功则去向按先急后缓重新分配并提示「请核对后再提交」，看过再提交。
- **保存时**就按同一份判定校验：跨车间、委外件、采购件、没有父子关系、接收方停产/关闭/已开工、计划包取消、
  需求已关闭、已备齐、超过还差的数，当场报「无法转到下一道工序：<原因>」，不再拖到审核才报一句笼统的话，
  也不再把送不下的部分悄悄拆成送入仓库(同日第二步起由工人逐条分配，见上)。
- **审核时**同一份判定带本次数量再核一次，数据库守卫最后兜底；原因原样显示。

回归用例：`test/features/production/widgets/production_daily_direct_transfer_cells_test.dart`、
`test/features/production/direct_transfer_candidates_result_test.dart`；服务端
`WorkshopDirectTargetReasonPostgresTest`。

## 2026-09-27 报工不良数 ([ADR-129](../99-决策记录-ADR/ADR-129-BOM设计使用数量与真实使用数量.md) §2.13)

报工明细表在「完工申报量」后多一列「不良数」(可选，空 = 0，与完工申报量同单位)。它只记录：不改良品数，
不进库存、FQC、超产允许量与产量分流。BOM 学习的真实使用数量仍按良品算，不良数只用来另算两个说明数：
实产单耗 = 净耗 ÷ (良品 + 不良)，不良率 = 不良 ÷ (良品 + 不良)。表头说明「只记录，不影响良品数和库存；
用来算实产单耗和不良率」(编辑表与详情表同一句)。

- 只有已选报工工单的成品行能填，没选工单的行显示「—」，物料子行不显示；输入框只接受数字、最多 4 位小数。
- 页面校验 (格内红框与保存共用，保存时前面加「第 N 行」)：「不良数请填写不小于 0、最多 4 位小数的数量」
  「不良数只能记在已选择报工工单的行上」「先填写大于 0 的完工申报量，才能记录不良数」。保存时排在完工申报量与来源的
  原有检查之后，后两句因此很少弹出：没选工单的行本来就不能填，填了不良数却没填完工申报量的行格子红框，保存先提示
  「第 N 行完工申报量必须大于 0」。服务端在新建和修改草稿时
  同样把关：「不良数不能为负」「不良数最多 4 位小数」「不良数只能填在已选车间任务且良品数大于 0 的报工行上」。
- 表单草稿保存并恢复不良数；复制行带上不良数 (已批准追加批次的复制行不带来源，也不带不良数)；换选或清除来源时
  清空。已批准追加批次的行来源与总量固定，不良数、备注、重量和实际用料仍可改。
- FQC 补产行也能填，照样记录，但不计入 BOM 学习的不良率。

**接口**：`POST /api/production/daily-reports` 与 `PUT /api/production/daily-reports/{id}` 的 `items[].defectQty`
可选，缺省或 null 按 0，页面只在大于 0 时发送；追加计划申请带的整单快照 `reportContext` 同一字段，从申请回到原表时
一起恢复。详情与编辑载入返回的 `items[].defectQty` 总是数字 (没有为 0)。创建指纹只在不良数不为 0 时计入它：不填与
填 0 指纹相同；同一幂等键改了不良数再提交，得到 409「同一幂等键已用于不同的生产日报创建请求」。

**拆段**：服务端按良品数把一次录入拆成多段 (需求份额与公共产出、转下一道工序与送仓库、原工单与追加工单) 时，
整笔不良只放在第一段，其余段为 0，数据库延迟约束 `daily_report_defect_first_slice` 兜底。编辑草稿时同一产出批
各段的不良数加回一行；详情页一批拆成多条明细时只有第一条显示不良数，其余留空 (没有不良的行也留空)。

详情页明细表列序：名称 → 编号 → 颜色 → 单位 → 完工申报量 → 不良数 → 产出归属 → 实际重量 → 计划号 →
产出去向 → 转给工单。

## 2026-09-27 BOM 用量变化后的排产预览与执行分段 ([ADR-129](../99-决策记录-ADR/ADR-129-BOM设计使用数量与真实使用数量.md) §2.6)

执行分段按每条 BOM 边实际采用的用量生成：由物料分析下达的计划用分析锁定的用量，手工计划用
「有真实使用数量用真实值，否则用设计使用数量」。执行指纹只含影响计量的内容，改 BOM 的审核标记或备注
不再让已保存的草案或排产预览过期；分析计划不受学习影响，手工计划在真实使用数量更新后要重新预览。

预览过期的提示统一成两句 (草案保存、正式确认与分段核对共用)：

- 整份排产预览对不上：「排产预览已过期：目标仓库存、占用、计划行或 BOM 已变化，请重新预览」；
- 执行分段的 BOM 对不上：「执行分段 BOM 已变化，请重新预览」。

手工计划 (没有来源物料分析) 两句都在「，请重新预览」前多一句「，或用量已按真实数据更新」。原来的
「预排草案已过期…请重新计算」「请刷新排产预览」不再出现。

BOM 里某一行生产用料 (硬门槛、生产阶段的行；发货包装与参考行不管) 的用量小于或等于 0 (新写入早已拦住，
只可能是历史数据) 时，不再报笼统的「BOM、颜色或基本单位数据不完整」，而是点名父件和组件 (编号 + 名称)
并给出修法，例如「「父件」→ 组件「组件」：用量小于或等于 0，不能排产。请在父件的 BOM 里把这一行的用量
改成大于 0。」

## 2026-09-28 车间内料仓: 报工截止与整批领料 ([ADR-131](../99-决策记录-ADR/ADR-131-车间整批领料与盘点计耗.md))

线边仓面向用户改叫"{车间名}内料仓" (下文历史段落里的"内料仓"即原来的线边仓), 车间直送规则不变。开启整批领料的车间, 颗粒这类料整批放在内料仓, 报工照常、不填用料:

- **报工页面不变**。理论用量 = 已审报工的良品量 × BOM 单个重量 (报工日期按表头日期归期, 夜班跨零点照现行口径); 盘点结算时按这个比例把实际用量分到各工单。报工不良数上线后 (ADR-129 §2.13) 自动变为 (良品 + 不良) × 单个重量。
- **截止守卫**: 工单接上内料仓后, 报工日期落在内料仓已经结算的那一期, 新建、审核、红冲一律拒绝。新建时提示"这个日期所在的一期车间内料仓已经结算, 报工日期请填 {下一期起始日} 或以后"; 审核或红冲时提示"{起止日} 的车间内料仓已经结算, 不能再改这期的报工。需要改的话请找有撤销结算权限的人 ({姓名}) 撤销后再改"。截止日及以前的报工在结算前照常可以新建、审核、红冲。
- **未审报工会拦结算**: 内料仓已盘点、截止日及以前还有没审核的报工时, 结算会停下, 审核人与制单人都会收到通知; 审核后系统立即再试一次结算。
- **零料原因**: 产品只有整批领料的料时, 工单的零料原因显示"无需生产领料: 车间内料仓供料", 不建按工单的领料需求。
- **FQC 报废补产**: 原工单只用整批领料的料时, 补产任务不再建补产领料轮次, 直接就绪; 补产报工按报废 / 拒收计理论用量, 返工不计。
- 服务端: `ProductionDailyReportService` 的保存、审核、红冲经 `WorkshopMaterialReportGuardPort.lockAndCheck`; 数据库另有报工截止触发器兜底。

## 2026-09-24 同一工单的订单量和公共备货量分别报工

同一执行工单允许包含订单生产与公共备货。例如订单1000、计划2000，前1000已报并完成
订单后，剩余1000仍在原工单继续报工。来源查询分别计算销售分摊与公共备货额度，原订单
结案不抹掉公共备货来源，也不把销售额度转成公共额度。

从车间任务进入时，只剩一个有效来源便自动带出货品、车间与本次可报数量；有订单和
备货等多个来源时由用户选择。选择器将无订单归属的行标为“内部计划 / 公共备货”。
草稿占用仍扣本次可报量，保存、审核、质检入库与红冲保持原计划行和执行段身份；
公共备货不生成销售订单分摊或重新占用已完成订单的库存。

同一计划的多个销售订单可以分别、多次报工，一个订单先完成不封锁其它订单的剩余
来源。车间页单张报工按“当前可以报工”开放；“可以自动批量带出来源”只决定多张任务
能否自动合并，有多个来源的工单仍可单独进入并选择，不能因此锁住整个报工入口。

修复包含V690前向迁移；现场证据、本地验证和服务器安装状态分别记录在
[半量报工专项记录](../99-项目治理/2026-09-24-车间半量报工后公共备货来源缺失.md)。

## 2026-09-22 审核带幂等键、名称随单下发、直送审核去掉一次重复提升

三件事一起收口，都是 2026-09-21 那次「审核 15.094 秒、浏览器掐断、页面停在草稿」的余项。

**审核带幂等键(V644)**。`POST /api/production/daily-reports/{id}/approve` 现在要求 body
`{"idempotencyKey": "..."}`。V409 的「创建命令账本」升级为「日报命令账本」: 同一张表加
`command_kind`, 同一把 (操作者, 幂等键) 仍然全局唯一。语义与创建完全对称:

- 同一操作者 + 同一把键 + 同一张日报 -> **200 原样返回当前详情**，一行都不再写;
- 同一把键用在别的命令、别的日报或别的载荷 -> **409**「同一幂等键已用于不同的生产日报审核请求」;
- 键是新的但单据已不是草稿 -> **409**「生产日报已不是草稿状态，不能重复审核；请刷新后查看当前状态」
  (原来是 400，和「明细为空」「报工量超计划剩余」同码，客户端分不出该刷新还是该改单)。

**状态闸绝不放宽**。幂等判定排在闸门**之前**：命中回放就直接返回，没命中才继续走原来的闸。
闸门本身仍然是硬拒绝——它是唯一挡住重复副作用的东西(fqty 累加与直送单都是纯增量写)。

**键怎么取**。客户端用 `businessIdempotencyKey('daily-report-approve', '单据id:当前rowVersion')`
确定性派生，不在页面里存随机数：页面重建或来回跳转后仍算得出同一把键，而服务端一旦真的提交、
版本号变了，键自然就换掉，不会把下一次操作当成上一次的重放。

**名称随单下发**。明细的货品名称/编号/颜色/单位，以及表头的车间与生产参与人员，全部由服务端
随详情解析下发，页面不再查任何主档字典、也不再调员工档案接口(那个接口要 `employee:view`
且会落人事查看审计)。客户端字典缓存会随连接恢复或权限快照变化整体清空，那时逐格解析出来的名字
会集体变成「—」且不会自愈——这正是事故当天截图里「货品名称啥的都没有了」的成因。

**审核提速：先量，再只动安全的那两处**。语句剖面自此有常驻用例
(`WorkshopDirectTransferBatchEndToEndTest#oneDirectTransferApproveStaysInsideItsStatementBudget`)，
实测一行直送审核 490 条语句、约 2.0s JDBC + 0.4s 提交。本轮落了两处：内料仓 (原名线边仓) 入库连就绪提升一起跳过
(判定移到提升之前)，以及同一张报工里重复的车间成员资格校验按执行工单去重。
**实测这两处一共只省个位数语句**——原先推断的「白跑 N 遍可用量扫描」经测量不成立。
剩下的成本是提交时的延迟约束触发器、被两条契约刻意钉住的锁后复核，以及几条本身就慢的读；
要再快一个量级只能改单据粒度或触发器触发时机，属于重设计，另行决策。
明细见 [ADR-089 §2.5](../99-决策记录-ADR/ADR-089-车间直送v2持续生产与线边仓自动配置.md)。

## 2026-09-21 日报详情页审核：结果未知必须重读，不得继续画「审核」按钮

**事故事实**：一次 4 行直送报工的审核，服务端跑了 15.094 秒、返回 200 并已提交;
浏览器在 15.000 秒把连接掐了(原因见
[网络层与拦截器 §5.2](../05-架构/网络层与拦截器.md))。页面因此停在草稿、「审核」按钮还在,
用户 45 秒后又点一次，服务端回「仅草稿单据可审核」400。重复点击没有造成重复副作用——
`approve` 的状态闸在任何写入之前，第二次请求一个字节都没写。

因此本页口径：

1. **写请求失败就是结果未知**。POST 永不自动重放，超时/断连都可能是「服务端已经做完了」。
   `_settleFailedAction` 在两条失败路径上都先重读一次详情：状态真变了就据实提示
   「本次提交服务端已完成，页面已刷新」并把按钮换成红冲；状态没变才报原始错误。
2. **权威状态先落地，名称后补**。拿到审核响应后先 `setState` 换 `_detail`，再去补货品/员工名称缓存。
   名称只是展示，绝不能挡在状态翻转前面。
3. **名称缓存被清空要自愈**。`MasterNameService` 的缓存是实例字段，连接恢复或权限快照变化会整体
   重建、缓存清零，届时货品名称/编号/颜色/单位/车间会集体变成「—」，而服务端随单下发的
   制单员/计划号/转给工单照常显示。本页监听 provider 换实例后补一次名称。

回归用例：`test/features/production/pages/production_daily_report_detail_approve_test.dart`。

**未闭环**：审核本身仍慢(1.4 秒到 15.1 秒，随直送行数近似 4 倍放大，耗时全在
`directTransfer.executeForApprovedReport` 之后那一段)，以及 `approve` 没有幂等键，
这两项另行处理。(2026-09-27 补记：多块直送审核的平方增长与函数反复规划已按 ADR-127 §8 处理，见本页顶部。)

## 2026-09-16 记忆预填、实际用料自动算、持续生产父件可收料(V595 / ADR-089)

(2026-09-27 起记忆预填退役：默认去向按先急后缓由系统建议，见本页顶部。)

**产出去向与转给工单带记忆**：选好来源工单后，服务端随候选一起返回本车间上次报同一货品
(同颜色)时选的去向与投给的父件产品(草稿也算最近意愿)。上次是「转下一道工序」就直接预填，

- 持续生产父件的可报量(`maxReportQty`)按「同车间直送已到料 ÷ 单耗」封顶，子件没送到前报不了；

## 2026-09-15 产出去向：送仓库 还是 转下一道工序(V584/V585 / ADR-087)

报工明细表每个成品行多了一列「产出去向」：

- **送入仓库**(默认，与以前完全一样)：交仓库送检登记 → 品质部 FQC → 仓库点收入库。
- **转下一道工序**：班组自检合格后不入库，直接投给**本车间**的上层工单。

选了转下一道工序要在旁边的「转给工单」列指名投给谁。候选由服务端按**同车间、真实父子关系、
自制路线、接收方仍在收料、还缺料**给出：只有一个候选时自动选中；一个候选都没有时这一项不可选。
跨车间不出现在候选里——料一旦离开本车间就脱离同一批人的视线，必须走仓库。
(2026-09-27 起「为什么不能选」按服务端原因红字显示，见本页顶部；「缺线边仓」自 V595 起已不是原因，
线边仓由系统自动配置。)

候选下拉显示的是**父件工单的产品**：首行产品名称+编号(车间认「投给谁」认的是这个)，
第二行工单号 · 还差多少；收起后格子里显示「产品名 编号 · 还差多少」。

**只有一个人工动作**：主管点审核，同一笔事务里自动完成班组自检放行 → 料进本车间内料仓
→ 重算上层工单齐套 → 把料投给上层需求。上层工单直接从等待物料变成可开工，
不用再提交领料，仓库全程不出现任何待办。上层还缺别的料时不算失败，料留在内料仓等后续到料。
**不卡齐套(2026-09-15 修复)**：父件工单缺其他物料(各自的子件还没做完/送齐)不拦报工审核，
各子件各自完成直送，全齐了由既有就绪补偿自动把父件提到可开工——此前审核会抛
「按本任务已合格入库来源及可用公共库存核算后仍缺料:…」把整张报工回滚，与「尽力而为」
的承诺相反(根因：直送误用了会抛错的人工重核路径 promoteAfterMaterialRecheck)。

线边仓是车间自己的料架：仓库部门不管、不点收、不进成品仓报表，但它是一个真实的叶子仓
(参与核算、非不良、归属该车间、与收料需求同主仓)，料确实在那里。V595 起由系统按
「车间 × 收料主仓」在第一次直送时自动配置，不用再手工建，也不再有「缺线边仓」灰显。(2026-10-04 起改为在「车间内料仓」里开通，一个车间一个，见本页顶部。)

**一行只有一个去向，要拆量就拆行**：送检登记与检验都按报工行唯一。
一部分送仓库、一部分转车间 = 报两行；超出上层需求的部分不能直送(没有指向对象)。
(2026-09-27 起由「去向分配」子行取代：员工一行报工逐条分配，服务端按接收工单拆成多条明细，
每条仍只对一个接收需求；超过还差的数在保存时明确报错，不再悄悄拆成送入仓库。见本页顶部。)

权限：审核带直送的报工需要 `production_direct_transfer:approve`(默认授予生产部与 6 车间)。
它不等于品质部或仓库的码——只允许在「同车间直送」这条被数据库守卫钉死的窄路径上写那几笔事实。


## 2026-09-15 报工同页登记实际用料(V583 / ADR-086)

实际用料不再是车间任务页的独立滑窗，改为在生产日报明细表里一起填。明细表变两层：
成品报工行 + 它所属工单**已领用的物料子行**(缩进 + 层级连线，浅底区分)。
物料子行只有一个可填列「本次实际用料」，旁边只读显示领料量。

日报**详情页**明细表列序：名称 → 编号 → 颜色 → **单位**(2026-09-15 起独立成列，
不再并在货品名称格副行) → 完工申报量 → 实际重量 → 计划号。(现行完整列序见文首「报工不良数」一节。)

必填、红框、拒负数、不得超过「本次还能登记多少」(该上限已扣掉待仓库收料的部分)；
**允许填 0**——「这批料一点没用」是合法事实，与成品行「完工量必须大于 0」是两种口径。
物料子行由来源工单派生：不能单独勾选、复制或删除，删成品行时连带删掉；同一个执行工单挂在
多个成品行下时只有第一处可填，其余是只读镜像，避免同一份额度被两行各自当满额填。

子行的来源要先问 `material-usage-sources` 再拉台账：分批生产时本批段可能一条物料需求都
没有，料挂在前批原领料段上，直接拿报工段查会查出零条、提交还会被按段归属判 403。
批量报工超过 20 个工单时不逐单加载，明说「本单只报工」，不静默少挂几行。

**记账时点跟着审核走**：草稿只承载数字(不记账)，主管审核时才在同一笔事务里转成
`CONSUMED` 结算，日报红冲时按结算事件上的日报来源反查、整单冲销。无 `production_material:settle`
权限的账号子行只读、不参与必填，不会被卡在一个永远填不完的红框上。

**收尾才问退仓，并按实物清点** (2026-09-27 起，[ADR-129](../99-决策记录-ADR/ADR-129-BOM设计使用数量与真实使用数量.md) §2.7)：本行勾了完结或把可报量报满时，
只要该工单还有账面可用的料，就弹「清点剩余物料」窗，逐物料列出账面可用 (不同单位不给合计)，
每种料填**实际剩余** (实物清点，预填纸面剩余 = 账面可用 − 本次填的用料；用完了填 0；不超过
账面可用，最多 4 位小数，按基本单位)。两个出口——「退回仓库」把意愿和清点数
(`materialLines[].countedLeftoverQty`) 随日报保存，审核时本次用料 = 审核时的账面可用 − 实际剩余
(覆盖本单登记的用料)，先结实耗，再按实际剩余 (加上未领直送料，见下) 开退料单，BOM 真实使用数量据此学习；「留在车间」
不带清点数、不发任何请求，并明确告知本工单会一直处于未完工状态。关掉弹窗回到报工表，不保存。
账面已无可用则不弹窗、不建单、不打扰仓库。实际剩余超过账面可用 (之前的报工多记了用料) 时
拒绝并提示先核对用料；按实际剩余算下来本次零用料、本批却有产出且之前没登记过用料时也拒绝。
账面可用只算领料领来的料 (各原领料过账还没用、也没在退料途中的量)，与材料清账行的 `availableToSettleQty`
是同一个数，页面不再自己算。车间直送过来、还没领用的料 (未领直送料) 不在账面可用里，不要计入实际剩余：弹窗在这种料
下面提示「另有未领直送料 X <单位>，退回仓库时一并退回，不要计入实际剩余」，退回仓库时它整批跟着退，
退仓数量 = 实际剩余 + 未领直送料。已被后续生产批次承接、或任务状态不许退料的料仍算在账面可用里，
按实际剩余记账后，这部分实际剩余留在车间，不退仓。审核时账上已没有这条料的，照本单登记的用料过账。
顺序不可颠倒：退仓申请一提交就冻结领料过账额度，先冻后结会让实耗登记撞「超过准确原领料未耗用数量」。

`APPROVED_LOSS` / `LEGAL_WIP`(损耗 / 在制)仍只在生产计划详情的管理侧滑窗登记——

执行段的车间、班组、负责人和日期是持久化安排。货品主档默认值仅在正式下达或 `assign` 成功且同货品本次车间无歧义时学习未来默认车间；空值、多车间、失败事务和幂等回放不学习，用户始终可以覆盖建议，历史执行段不回写。

候选新数据的处置明确分为 `READY`（整套占用、可进入派工）、`AUTO_WAIT`（系统缺料、到料后允许自动齐套）和 `DEFERRED`（用户主动延期、禁止自动提升）。`release-defer` 只允许将已确认的 `DEFERRED` 单向人工放行：同事务解除延期并立即重做齐套，齐套转 `READY`，仍缺料转 `AUTO_WAIT`，不能用该动作把已放行段重新延期。

安排必须通过服务端组织校验：车间是 `DEPT_PROD` 直属子部门，班组直属所选车间，负责人为在职/试用且位于所选班组或车间路径内，计划开工不晚于计划完工。前端联动过滤和清空失效选择只改善体验，不能替代服务端及 V194 数据库守卫。

V194 将直接层 MAKE 子计划明细作为父需求的明确供给来源。已审核 `FINISHED_IN` 必须带真实上游子计划明细，按货品/颜色/单位/计划包/供给 peg 精确回供；系统缺料 WAITING 可在全套齐料后自动转 READY，用户主动延期 `USER_DEFER` 即使齐套也保持延期。入库红冲在父段未派工/领料时释放回供并回到 WAITING；已进入执行时 fail-closed，必须先走业务反向。

「生产计划单（流水线执行工卡）」从确认计划包和执行段只读生成，不在本页手工创建另一套数量或状态事实。生成结果可立即打印，已审计划详情可补打；服务端先按计划制单人对象范围鉴权，再以计划→确认包顺序悲观读，只有已审、未停止/未取消且包为 `CONFIRMED/V1` 才返回。草稿、红冲、停止、取消或失效包均不得形成有效流水线打印件。V195 只刷新 V194 新增业务表的未来写入审计覆盖，不回填历史业务行或历史审计；目标环境仍为 V190，候选未部署且未完成真实岗位 UAT，因此生产发布仍为 **NO-GO**。

## 一、页面职责

生产计划详情统一展示父计划事实、BOM/MRP 预览、执行分段和真实自制件子计划。页面不得把不同层级揉成一个列表：

- `production_plans` 通常是可独立审核和下钻的计划；但 `EXECUTION_V1` 派生子计划禁止通用删除/红冲，必须从父计划包走受控反向，不能拆断谱系；
- `subplan_links` 表达父计划与自制件子计划的谱系；
- `production_execution_segments` 表达同一计划明细按齐套状态、车间和日期拆出的执行部分；
- 执行分段的报工、领料、成品入库和结案都必须回到同一父计划及其数量权威。

## 二、加载与失败隔离

计划详情、MRP 物料需求、执行分段和子计划列表分别加载。MRP 预览失败不能吞掉子计划列表；子计划列表失败显示独立错误卡和重试；执行分段加载失败显示明确错误和重试。

当路由携带 `executionSegmentId` 时：

1. 先打开对应父计划；
2. 执行分段数据加载完成后定位目标分段；
3. 自动打开一次分段详情；
4. 目标不存在时停止重复尝试，不叠加多个对话框。

## 三、执行分段交互

点击任一执行分段必须打开自适应详情：

- 紧凑屏使用底部弹层；
- 中等和展开屏使用对话框；
- 查看者可看到分段编号、状态、计划/已报工/剩余数量、物料齐套、车间、班组、负责人和计划日期；
- `WAITING` 明确显示待料，不能伪装为可派工；
- `COMPLETED` 明确显示已完成，不能继续展示非法动作。

动作按“权限 + 当前状态”共同决定：

| 状态 | 允许动作示例 | 约束 |
|---|---|---|
| `READY` | 调整、仓库备料/出库；备料完成后报工 | 不再派工或确认开工；首次报工原子进入生产中 |
| `WAITING`（`AUTO_WAIT`） | 调整、跟进备料 | 到料后自动重做齐套，未齐套不得报工 |
| `WAITING`（`DEFERRED`） | 调整、人工放行 | 只有 `release-defer` 可单向解除延期 |
| `DISPATCHED` | 历史兼容查看；备料完成后报工 | 新页面不再生成；首次报工原子进入生产中 |
| `IN_PROGRESS` | 继续报工 | 跳转日报新建并携带精确 `executionSegmentId` |
| `COMPLETED/CANCELLED/REVERSED` | 查看 | 反向须走专用状态机，不在详情里直接改值 |

只读账号点击行也必须得到详情或明确无权提示，不能出现可点击样式却没有反馈。

## 四、真实子计划交互

详情底部“子任务 · 子计划”来自 `subplan_links`，每行显示子计划单号、交货日、入库/计划数量和状态。点击后打开子计划自己的详情页；空 ID、自引用或路由失败显示强提示。这里展示的是子计划自身事实，不证明其入库已按 supply peg 回供父需求；未闭环前不得把子计划入库直接计为父计划或销售履约完成。

执行分段的“详情”与真实子计划的“跳转”是两套行为。任何后续改版都必须用独立组件和测试守住该边界。

## 五、权限与数据安全

- 查看权限不能推导出编辑、派工或报工权限；
- 前端隐藏按钮只改善体验，服务端仍须校验权限、对象范围、锁版本和状态；
- 车间、班组、负责人和日期的组织层级约束由服务端强制执行，禁止仅靠下拉框过滤；
- 销售深链只能定位被授权查看的计划和分段，不得把成本、供应商报价、员工绩效或内部质量责任带回销售端；
- 日期字段兼容后端返回的日期对象或文本格式，但兼容转换不改变业务日期语义。
