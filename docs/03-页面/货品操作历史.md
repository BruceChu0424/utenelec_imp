# 货品操作历史

货品资料右上角使用文字操作“撤回”和“取消撤回”。“撤回”打开最近 10 次操作，让工作人员先核对操作名称、时间、影响数量和状态，再选择要撤回的记录。“取消撤回”恢复上一次成功撤回的操作；两种动作均保留记录。

界面按 `frontend-design` 维护，复用 Uten 组件、现有字体和主题 token。历史内容左对齐，状态和动作使用明确文字；窄屏及大字号下允许重排和滚动。

2026-10-20 起，货品详情也提供同一组文字入口。既有货品保存后留在当前详情查看态，新增仍返回来源页；取消编辑只放弃未提交输入。基本信息草稿、BOM 编辑模式、组件选择/导入/删除确认、拖拽及保存仍在处理时，暂停历史操作。

历史回放成功后重新读取货品、组装和库存信息，并重新创建 BOM 状态，保留主线的退出编辑保存守卫、顶部刷新和价格分析入口。若撤回新增使货品不存在，隐藏旧资料，仍可通过取消撤回恢复。货品列表的行内编辑也进入同一份个人历史；每行保存是独立事务，按实际成功行形成记录，不将多行逐次提交描述为一次原子操作。

## 行为约定

- 历史来自服务器，只显示当前操作人的记录，刷新页面后仍可查询。
- 最近 10 次是可操作窗口，不是删除审计历史的规则。
- 一次服务器事务中的成功变更合成一条操作。批量删除、启停只包含实际成功变更的数据，失败和未改动的条目不能被“恢复”。
- 可以选择较早的操作；若目标记录后来已被修改，整次撤回失败，并提示先处理后续变更。不能用旧快照覆盖他人的工作。
- 校验整行快照后，仅回放本次实际修改的字段；组装信息按恢复后的结构和当前成本重新计算材料成本，较早的名称或价格修改不能覆盖这些派生值。
- 取消撤回只针对上次成功撤回。新操作形成后，原来的取消撤回分支失效，历史记录仍保留。
- 新增的撤回使用软删除；删除的撤回恢复原 UUID 及本次一同删除的 BOM 行，不重新创建货品，也不恢复更早已删除的行。
- 撤回和取消撤回都增加当前版本，不回退版本、审计时间或编号序列。
- 每次点击撤回或取消撤回，都另弹确认框，显示具体操作、时间及影响数量。选择历史条目不代表确认，取消确认框不发送写请求。
- 确认后等待服务器回执，处理期间不允许连点。失败时保留面板，支持刷新；成功后刷新分类树和货品列表。

## 多账号、会话与并发

个人历史以服务器认证的 `users.id` 区分，不按姓名、员工编号、设备标识或客户端传入的操作人区分。账号之间共享业务资料时，个人历史仍相互独立。

| 场景 | 行为 |
|---|---|
| A/B 账号分别操作 | 各自读取和操作自己的最近 10 次；B 不能用 A 的历史 UUID 执行撤回或取消撤回，超级管理员也不代撤别人的个人历史 |
| 同一员工对应不同账号、同名员工或重建账号 | 账号 UUID 不同即是不同个人历史，不因姓名或员工资料相同而合并 |
| 同账号换设备登录 | 历史随账号保留；系统已有单设备登录，新登录会吊销旧会话，旧设备请求返回 401 |
| 同一有效会话多标签页/重复请求 | 服务端串行个人命令并检查版本，同一状态迁移只能成功一次；历史由服务器确定 |
| B 修改另一货品 | 不清空 A 的取消撤回分支 |
| B 后续修改同一货品 | A 的旧操作因快照变化被阻止；别人的修改不能被覆盖。即便修改字段不同，也按整行冲突保守处理，不自动猜测字段依赖 |
| 他人撤回到一个已知历史状态 | 仅精确匹配的系统回放更新历史期望值；普通外部编辑即使改回原值，也不放行 |
| 原操作权限被撤销 | 执行时重新核对原动作与价格/成本等字段权限；仍有其他编辑权限不代表还能撤回该操作 |
| 超管降级、部分撤权或账号切换 | 清除旧能力、确认框和在途响应归属，重新读取；原账号发出的已受理请求仍属于原账号，不改记给后来登录者 |
| 只可见、不可写的资料 | 可见摘要与可执行能力分开判断；可以查看不等于可以撤回修改 |
| 资料正式交接 | 沿用现有资料可见/可写范围，不把原账号的个人撤回历史转让给接手账号 |
| 仅核对或清理既有 BOM 行 | 按原命令的父件及动作权限判定；恢复新增组件关系时再核对组件可见性，受限组件名称不会从摘要泄露 |
| 模拟身份、首次登录强制改密、停用/删除/已吊销会话 | 沿用服务器账号与只读门禁；模拟身份的历史能力明确只读，强制改密期间不能访问历史或执行操作 |
| 并发导入、分类调整或撤回 | 正向写入前先协调个人命令锁；撤回拿不到所需表锁时立即失败并回滚，提示稍后刷新重试，不形成反向锁等待 |
| 网络超时或断开 | 先 GET 查询服务器状态，再由用户决定下一步，不自动重放 POST；版本检查防重复迁移，不宣称已实现幂等键响应重放 |
| 快速重复确认 | 对话框决策一次生效，避免重复提交或连续关闭下层面板；撤回与取消撤回每次仍须二次确认 |

HTTP 入口按服务器账号、会话及授权版本核验新请求。切换账号、登出或后台撤权不等于强制取消所有已经受理的数据库事务；在途请求仍属于其原认证账号，客户端丢弃迟到结果，再通过新请求核对服务器记录。并发测试中切换测试主体的权限快照，仅证明领域检查发生在等待个人锁之后，不作为“数据库撤权可自动取消所有在途 HTTP 请求”的证据。

## 范围和业务边界

货品新增、修改、英文名称、批量删除、启停、Excel 导入、默认采购超收与委外损耗设置，以及货品分类和组装信息的直接维护，使用同一历史入口。一次界面操作若原本分成多次服务器请求，则按实际提交分别记录，不把部分完成的工作冒充原子整批。

发料方式切换、成本确认、库存和财务处理、实际耗用学习、期间领料或学习来源相关 BOM、图片原件修改及附件原件生命周期，仍按各自业务命令办理。不能通过通用历史恢复旧行来绕过下游凭证、来源数量或文件保留规则。旧版本导入批次没有可信变更快照时，不提供盲目删除式撤回。

服务器每次执行都重新检查当前身份、原动作权限、历史版本、数据快照和引用约束。任何一条目标冲突，整组回滚；原有单位使用限制、唯一性、有效关联和 BOM 约束继续生效。历史列表不返回原始行快照或隐藏价格字段。

重新引入的关联还须满足当前启用、可见和可选规则；分类层级与编号调整记录提交时的子树摘要，拦截后来新增或移入的资料，不用事务开始时间推断是否发生后续变更。

## 设计参考

[Microsoft Office 的撤销与重做](https://support.microsoft.com/en-gb/office/foundations-experiences/undo-redo-or-repeat-an-action?nochrome=true)提供连续撤销及恢复已撤销动作的交互参考；[Google AppSheet 的撤销与重做](https://support.google.com/appsheet/answer/12289555?hl=en)提供最近 10 次历史的参考。这里处理的是多人共享、已经提交的数据，因此可执行性以服务器实时校验为准。

追加参考 [Yjs UndoManager](https://docs.yjs.dev/api/undo-manager) 的事务来源筛选与命令分组，以及 [Figma 多人撤回设计](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/#implementing-undo)对撤回、重做和后来修改关系的处理。来源筛选本身不构成认证授权，编辑器历史也不等同于审计留存。

工程选择是服务器个人历史、明确命令边界、当前状态校验和业务约束；普通新操作清除本人重做分支，不清他人的分支。库存和财务等按领域规则反向，符合[微软补偿事务模式](https://learn.microsoft.com/en-us/azure/architecture/patterns/compensating-transaction)强调的业务补偿边界。本系统继续使用单库原子事务，不引入分布式补偿队列。
