# ADR-107 履约预锁一轮发现、行版本复核与服务端截止时间

- 状态：已接受(2026-09-23，零迁移，零新增权限码)
- 涉及审计发现：perf-warehouse-quality-01、perf-material-analysis-05、perf-production-exec-05、perf-material-analysis-11、perf-material-analysis-17、perf-warehouse-quality-12(tx.bind 部分)、dup-backend-split-15(部分：事务开始自动绑定，530 处手写调用未删)、perf-warehouse-quality-14、perf-warehouse-quality-03(只做等锁有上限与读写区分)、db-schema-02(只做新建来源登记改为只看行版本)、overhaul-gap-01(服务端截止时间)
- 取代：[2026-09-07 履约事务锁顺序与来源漂移处理](../07-业务链路/2026-09-07-履约事务锁顺序与来源漂移处理.md) §3「嵌套命令各自重跑发现并复核」与 §4「新建来源登记校验审计日志 INSERT 证据」两处做法；锁的偏序(§2)不变。

## 一、背景

「预读 → 按偏序加锁 → 锁后复核」是全平台履约写命令的并发根。实测它本身成了最慢的一段：

- 嵌套命令不区分最外层：外层已经把锁拿全，嵌套的收货、质检、入库、分析刷新、逐张建计划仍各自整跑一遍发现，再整跑一遍复核。品质判定链一次要跑 11 遍，日报直送审核 8 遍，委外发料草稿改一行也要展开同一张分析约 10 次。
- 复核靠对依赖图里每一行做 `md5(to_jsonb(row))`，成本随分析规模线性增长，与本次真正写几行无关。
- 同一轮发现里，订货单、分析展开、库存变化唤醒、目标 BOM 被不同入口按相同参数重复读取。
- 回调超出预锁集合(编码层面的足迹缺口)被当成瞬时冲突自动重跑 5 遍，最后仍是 409。
- 全公司只有 1 个主仓，主仓协调锁是阻塞式的 `pg_advisory_xact_lock`，排队没有上限；数据库侧 `lock_timeout`、`statement_timeout`、`idle_in_transaction_session_timeout` 全为 0，没有事务总时长上限。客户端 45 秒放弃后服务端照样提交，出现「界面报失败、库里已成功」，排队多了还会占满 20 条连接拖垮全站读请求。
- 审计操作人靠 131 个文件 530 处手写 `tx.bind()`，每处一次 `set_config` 往返，漏写就丢操作人；一次质检判定发 37 次。
- `BaseEntity` 预设 UUID 又没告诉 Spring Data 这是新实体，每个 `save()` 新建都先按主键查一次再插入。

## 二、决策

### 1. 以事务为单位：一轮发现 + 一次版本复核

- 事务里第一次 `FulfillmentMutationLocks.acquire(discovery)` 跑一轮只读发现，按原偏序(商业来源头 → 明细 → 库存维度 → 主仓 → 分析头)拿齐锁，把这一轮的计划和发现函数记在事务状态里。
- 之后的 `acquire`(嵌套命令)不再执行发现，只对调用方**声明的已知 id** 做纯内存覆盖检查：`acquire(declared, discovery)`。例如 `lockHeader(分析)` 声明该分析；采购/委外订货入口声明订货单与库存维度；销售单据入口声明销售订单(按订单加锁时)与请求行维度；逐张建计划声明请求行的库存维度。拿不出已知 id 的入口声明为空。
- 锁后复核整个事务只做一次：取锁命令的守卫在锁住执行对象、第一笔写之前调用 `verifyUnchanged()`，重读一轮与预读逐行比 `(id, xmin)`；之后再调用不读库。已提交的同键幂等重放仍可在锁后、复核前只读返回原结果(原约定不变)。嵌套 acquire 的守卫调用 `verifyUnchanged()` 只确认守卫属于当前事务、前缀没有随保存点回滚失效。
- 有些入口只为给嵌套出库预锁、自己从不调用复核(例如确认齐套路线时按计划预锁，随后改执行段、就地出库)。这时第一个嵌套 `acquire` 替它做一次锁后**覆盖**复核：重读**取锁命令自己的**那轮发现，只要求结果仍落在已持有集合内——它可能已经写过，行版本必然变了，不能比相等；要多拿锁说明预读后依赖图被别的事务改过，可重跑冲突整笔回滚。它补的是外层预读的锁后复核，**不**证明嵌套命令自己的足迹被覆盖。
- 一轮发现之内用 `FulfillmentDiscoveryRound` 去重：订货单、来源明细、收货/单据足迹、唤醒目标、目标 BOM、当前 BOM、分析结构按「方法 + 参数」只读一次；物料分析的展开(来源、供给动作、表头、结构、预留)推迟到本轮末尾，对全部分析的并集只展开一次。各展开查询都是 `IN (:ids)` 的并集语义，并集展开的锁集合与逐个展开的并集完全相同。两轮之间不共享任何缓存，锁后复核一定重新读库。

**覆盖由谁兜底(如实说明)**：以前「嵌套命令重跑发现 + requireCovered」是运行期唯一一道证明「嵌套足迹 ⊆ 预锁」的网。改后生产配置下：

- 仍有运行期检查的：调用方声明的已知 id(`lockHeader` 等声明分析；采购/委外订货入口声明订货单与库存维度；销售订单入口声明订单与请求维度；逐张建计划声明请求行的库存维度)；实际加锁入口的内存检查——库存维度锁入口(`beforeInventoryLocks`)、分析头(`lockHeader`/`headerAfterPrelock`/唤醒刷新 `requireAnalysesCovered`)、批量下达结构范围(`openAnalysisStructureScope`)；拿不出已知 id 的写后回调(收货送检、FQC 回退、补产授权撤回)用 `requireReceiptCovered`(只读收货明细的订货单与维度)或 `requireDiscoveredCovered`(一轮去重发现)。
- **不再**有运行期检查的：嵌套命令没声明的商业来源(例如生产单据出库、质检报告、计划审核这类只拿得到单据 id 的入口)与主仓协调锁。今天已测路径在旧代码下都被证明是覆盖的，所以没有已知会出错的路径；但以后改了某个足迹，嵌套写可能落在没拿锁的订货单/申请单头上或没拿主仓锁，而生产不会报错。
- 为此新增诊断开关 `uten.concurrency.verify-nested-footprint`(环境变量 `UTEN_VERIFY_NESTED_FOOTPRINT`，生产默认关)：打开后嵌套 `acquire` 也在一轮去重发现里重跑自己的足迹并要求落在预锁集合内。测试类路径 `src/test/resources/config/application.yml` 默认打开，全部 Spring Boot 真库用例(全链路、路线闸门、直送、委外、质检……)持续证明覆盖；只有量语句数/发现次数的 7 个用例类在自己的 properties 里关掉，量的是生产配置。

### 2. 行版本复核取代整行哈希

发现结果里每行带 `(id, xmin)`：`xmin` 是 PostgreSQL 为每个行版本记录的写入事务号，任何 UPDATE(即使值没变)都会产生新版本，只加行锁(`FOR UPDATE`)不会改变它；新增或消失的行直接体现在行集合里。锁后复核比较两轮的行集合与行版本，删除全部 `md5(to_jsonb(...))` 快照语句。值没变的 UPDATE 也会被看作变化，这只会让命令多一次可重跑冲突，不会漏判。

业界同类做法：EF Core/Npgsql 把 `xmin` 作为 PostgreSQL 的并发令牌，Hibernate/JPA 用版本列做乐观锁复核；本平台多表依赖图没有统一版本列，直接取各行 `xmin`。

### 3. 声明缺口不重跑；自动重跑有两道时长预算

- `requireCovered` 对调用方**声明的已知 id** 做的内存检查失败(需要的来源、库存维度、主仓或分析不在已持有集合里)是足迹声明的编码缺陷，同一请求重跑多少遍都一样：改为不可重跑冲突，服务端记 ERROR(含缺少的具体 id)，客户端文案不变。
- 靠**重新发现**做的覆盖检查(`requireDiscoveredCovered`、嵌套锁后覆盖复核、诊断开关下的嵌套发现)仍按可重跑处理并记 WARN：发现会读到预锁没锁住的依赖(例如计划的 BOM 递归；改 BOM 不拿主仓锁)，别人在本事务复核之后给产品加了一个硬门槛子件，就会多出一个库存维度——这是瞬时情形，不能当编码缺陷直接 409。
- 真正的瞬时冲突(复核发现来源在预读后被别的事务改了；预锁阶段任一把锁——订货单头与明细行锁、库存维度锁、主仓协调锁、分析头——等待超过 lock_timeout)仍自动重跑，上限仍为 5 次，另加两道时长预算：
  - **重跑预算 10 秒，从第一次冲突开始计**。第一次执行(含排队等锁)是命令本来就要花的时间——等锁之后才发现来源变了，恰恰是 2026-09-21 引入自动重跑要解决的情形，不能算进重跑的账(评审指出：若从第一次执行开始计 3 秒，前一个持锁命令只要跑 3 秒以上——IQC 入库 p50 就是 3.3 秒——冲突就不再重跑，直接 409)。之后的重跑(含它们各自的等锁)累计超过 10 秒就停，慢命令不会被放大成几倍时长。
  - **命令开始后已过 30 秒不再发起新的一次**：客户端 45 秒放弃等待，再跑一遍大概率在它放弃之后才提交，界面会误报失败而库里已成功。
- 超过上限或预算返回原 409(带 `Retry-After`)。客户端不会自动重发业务写请求(`SafeRequestRetryInterceptor` 只重放安全请求)，由用户稍后重新提交。重跑的前提不变：冲突在本命令第一笔写之前抛出，或在写之后但事务整体回滚，什么都没生效。

### 4. 主仓协调锁等待有上限、读写区分

- `MATERIAL-ANALYSIS-WAREHOUSE:<主仓>` 仍用阻塞式 `pg_advisory_xact_lock`(共享版 `pg_advisory_xact_lock_shared`)，等待上限就是连接上的 `lock_timeout`(应用连接默认 10 秒，见第 8 条；后台任务可在自己的事务里调短，例如备料自动核对设 500 毫秒)。到点拿不到，锁入口直接接住 55P03，返回可重跑的 409：「有人正在处理同一仓库的单据，请稍后再试」，并交给第 3 条的自动重跑。
- 不照审计原稿改成 `pg_try_advisory_xact_lock` 轮询 3 秒(本 ADR 初稿曾这样实现，评审后改回)：全公司只有 1 个主仓，这把锁的典型持有时间就是命令全程(IQC 入库 p50 3.3 秒)，3 秒上限会让第二个人在正常排队时直接收到 409；轮询不在锁管理器里排队，持续有人抢时等待方可能一直抢不到；数据库也检测不到轮询构成的死锁。阻塞锁保住排队顺序和死锁检测，lock_timeout 给出同样的「不无限排队占住连接」保证。多个主仓各自最多等一个 lock_timeout(实际部署只有 1 个)。
- 预锁阶段的其它锁(订货单头与明细行锁、库存维度锁、分析头)等待超过 lock_timeout 同样转成可重跑的 409「有人正在处理相关单据，本次操作未生效，请稍后再试」：本命令还没写任何东西，交给最外层在重跑预算内再排一次队。修复轮全量回归里「同一分析两个相同的下达车间命令并发」用例(ProductionMaterialAnalysisScalePostgresTest)在机器负载高时，第一个命令持有销售订单超过 10 秒，第二个在预锁处等锁超时直接成了裸的锁超时 409——这正是 lock_timeout 取 10 秒会误伤的形态。改后第二个先由服务端重排一次队；第一个仍没结束(负载很高时超过 20 秒)才回可重跑 409「请稍后再试」，用户再点一次按幂等键重放、绝不第二次提交——用例按这个口径断言「恰好一次提交、一次重放」。预锁之后(命令已开始写)的等锁超时仍由全局异常处理回 409，不在服务端重跑。
- 主仓锁语句走 JDBC 直接执行并在入口处接住等锁超时，不经 JPA 查询异常转换，Hibernate 不会把事务标成只能回滚(数据库事务已因这条语句作废；调用方若在保存点里，回滚到保存点即可恢复)。
- 只读可用量、最后整笔回滚的预览(物料分析「下达车间预览」`previewIssuePlans`)在取锁前声明 `useSharedWarehouseLocksForReadOnlyPreview()`，取共享锁：预览之间并行，与真实下达、入库仍互斥。预览会真实跑一遍下达(建计划、审核、写预留)再回滚，同主仓两份分析反复同时预览的真库用例证明两边都成功、不互相等死或死锁、库里一行不留。
- 去掉库存写命令上的主仓锁依赖「入库不再同步刷新分析」(perf-warehouse-quality-02)，属于下一波。

### 5. 新建来源登记只看行版本(db-schema-02)

`registerCreatedSource`/`registerCreatedAnalysis` 只校验「事先确认该 UUID 不存在 + 行版本属于本事务(xmin = 当前事务号)」，不再读 `audit_log`。审计有保留期、可能改为只记变化列，不能当业务事实源。新建必须是普通 INSERT：别的事务抢先提交同一 UUID 时由主键唯一约束拒绝、整笔回滚；upsert 不是受支持的新建方式(实体层配合第 7 条，`save()` 新实体一律 INSERT，不再 merge)。

### 6. 审计操作人在事务开始时统一绑定

- `TransactionAuditActorBinder`(Spring 事务执行监听器，由 Spring Boot 挂到自动配置的事务管理器)在每个新开的读写事务开始后立即绑定当前登录人与请求元数据；只读事务不绑，嵌套保存点沿用外层。业务代码漏写 `tx.bind()` 不再丢审计操作人。
- `TxSessionVars` 用事务资源记住本事务已绑定的(操作人、账号、请求号)：同一事务同一身份再调用 `bind()` 只做内存比较；`bindActor` 换成系统操作人、之后又换回登录人都会如实重绑；回滚到保存点时跟着还原(PostgreSQL 也撤销了那次 `set_config`)，挂起/恢复随事务切换。
- 现存的 530 处手写 `tx.bind()` 暂不删除：它们现在是内存比较，且少数路径(登录、切换身份)依赖「中途换了登录人后重绑」，需按模块逐处确认后再清理。因此 dup-backend-split-15 只算部分完成(根因「漏写就丢操作人」已消除，清理留作后续)。
- 全上下文用例证明监听器真的挂在 Spring Boot 自动配置的事务管理器上：一段故意不写 `tx.bind()` 的写事务，审计行照样记到当前登录人和本次请求号，整笔只发 1 次会话变量绑定。

### 7. BaseEntity 实现 Persistable

`BaseEntity` 增加不入库的新建标记：新 new 出来的实体 `isNew()` 为真，`save()` 直接 persist 一条 INSERT；`@PostLoad`/`@PostPersist` 后为假，再 `save()` 走 merge 更新。`StockService` 删除为预留流水 UUID 做的按主键预查——该 UUID 由调用方当场随机生成，撞主键只可能是编码错误，交给主键唯一约束拒绝。

### 8. 服务端截止时间(overhaul-gap-01)

| 项 | 取值 | 配置 |
|---|---|---|
| 等锁上限 lock_timeout | 10 秒 | `uten.database.lock-timeout` / `UTEN_DB_LOCK_TIMEOUT` |
| 单条语句上限 statement_timeout | 60 秒 | `uten.database.statement-timeout` / `UTEN_DB_STATEMENT_TIMEOUT` |
| 事务内空闲上限 idle_in_transaction_session_timeout | 120 秒 | `uten.database.idle-in-transaction-session-timeout` / `UTEN_DB_IDLE_IN_TX_TIMEOUT` |
| 事务总时长默认上限 | 40 秒(小于客户端 45 秒) | `spring.transaction.default-timeout` / `UTEN_TX_DEFAULT_TIMEOUT` |
| 连接泄漏告警 | 借出超过 120 秒 | `spring.datasource.hikari.leak-detection-threshold` / `UTEN_DB_LEAK_DETECTION_MS` |
| 长任务单条语句放宽 | 15 分钟 | `uten.database.long-work-statement-timeout` |

- 前三项写进 Hikari `connection-init-sql`(与原有 `SET jit` 一起，每条新连接执行一次)，对应用连接生效，不改全库或角色配置。
- 事务默认 40 秒由 Spring 按剩余时间给每条 JPA/JDBC 语句设查询超时，到点取消并回滚，保证客户端放弃等待时服务端也已回滚。
- 真正的长任务显式放宽：报表物化视图刷新在各自的短事务里 `set_config('statement_timeout', ..., true)`(事务结束即恢复，不带回连接池)；「清空业务数据」事务上限 30 分钟(与其原有 `SET LOCAL statement_timeout = '30min'` 一致)；遗留数据导入在应用外(脚本 + psql)执行，不经过应用连接池。
- 全部定时任务与启动回填逐项排查(评审要求)，结论：除上面两处外没有需要放宽的长事务。

| 任务 | 事务形态 | 结论 |
|---|---|---|
| 审计留存归档 `AuditRetentionScheduler` | 自动提交，每批 5000 行一条语句，非阻塞 `pg_try_advisory_lock` | 不受 40 秒事务上限约束；单条语句远低于 60 秒 |
| 附件孤儿对账 `AttachmentReconciliationService.scheduledReconcile` | 调度入口在同一对象内调用 `reconcileInventory`，不经代理，**没有**事务，逐对象自动提交 | 评审担心的「整个对象存储清单一笔事务、到点整笔回滚」不成立；只有测试经代理调用时才是一笔事务 |
| 附件出库箱/上传过期/内部存储清理 | 每轮最多 20 条，逐条短事务；网络调用不在事务里 | 无需放宽 |
| 政策情报刷新 | 网络抓取与模型调用在事务外，只有逐条 upsert 在事务里 | 无需放宽 |
| 庆典/交期/预留持有/委外回厂交期/委外短交逾期/服务器告警 | 一条只读查询 + 逐单短事务发通知或事件 | 无需放宽 |
| 业务事件出库箱 `BusinessOutboxScheduler` | 逐条短事务，批量上限 | 无需放宽 |
| 委外备料自动开始、备料自动核对 | 逐项 `TransactionTemplate`；备料核对自带 `lock_timeout 500ms`/`statement_timeout 5s` | 无需放宽；主仓锁改回阻塞式后同样服从其 500 毫秒等锁上限 |
| 库存价值传播 `InventoryValueWorkScheduler` | 每项一笔短事务，批量上限 10/50 | 无需放宽 |
| 库存余额对账 | 两条只读聚合查询 | 单条语句远低于 60 秒 |
| 报表物化视图刷新 | 各视图一笔短事务 | 已放宽到 15 分钟(见上) |
| 员工敏感信息 V282 回填、资料变更快照 V284 回填(启动时) | 逐行短事务；V282 用会话级 `pg_advisory_lock` 串行多实例 | 平台未上线、无存量明文，回填为空跑，全局锁持有毫秒级，10 秒等锁上限不会触发 |
| 管理员引导 `BootstrapRunner` | 单个短事务 | 无需放宽 |
- Flyway 迁移改用独立的非池化连接(同库同账号)，不继承连接池的截止时间；生产环境迁移本来就由发布流程单独执行。
- `GlobalExceptionHandler` 把 SQLState 55P03(等锁超时)、57014(语句被取消)、40P01(死锁牺牲者)以及事务到点(`TransactionTimedOutException`)统一识别——不论被 Spring、JPA 还是 Hibernate 哪层包着——回 409 并带 `Retry-After: 1`，中文提示分别为「有人正在处理相关单据，本次操作未生效，请稍后再试」「本次操作处理时间过长已自动取消，没有生效，请稍后再试」「与他人同时处理相关单据发生冲突，本次操作未生效，请稍后再试」。可重跑的业务冲突(`ApiException#retryable()`)同样带 `Retry-After`。死锁不在服务端自动重跑：死锁可能发生在命令中途，重跑前的非数据库副作用无法保证幂等。

## 四、验证

- `FulfillmentMutationLocksPostgresTest`：嵌套 acquire 不执行发现、声明 id 越界为不可重跑冲突；取锁守卫整个事务只复核一次；取锁命令没复核就写了再进入嵌套命令时，第一个嵌套 acquire 只做一次覆盖复核、不把自己的写入判成变化，而足迹在预读后长大时回可重跑冲突；主仓协调锁等待超过 lock_timeout 回可重跑冲突和大白话提示、只读预览共享锁互不阻塞；**同仓第二个写命令排在持锁约 3 秒的命令后面等到成功，不回 409**；**前一个命令持有订货单约 3.5 秒后改了来源，第二个命令等锁后发现漂移，被最外层事务边界(真实的重跑拦截器 + 事务拦截器)自动重跑一次并成功**；诊断开关打开时嵌套 acquire 拦下没声明却超出预锁的足迹(可重跑)，`requireDiscoveredCovered` 的缺口可重跑；别的事务抢先提交同一 UUID 时普通 INSERT 被主键拒绝；原有等待方向、来源切换拒绝、保存点、挂起恢复用例全部保留。
