## 二、决策

### 2.1 保留确认路线门禁, 但把「改」做顺

| 事项 | 结论 |
| --- | --- |
| 未确认路线的行 | **不能下单**。供应方式格画红框, 两个数量格不给填, 办理按钮置灰并说明原因 |
| 确认后改路线 | 随时可改, 改完立即生效, 三个下达分桶的行与计数当场跟着变 |
| 已下达的行改路线 | 禁止。库侧 `MaterialAnalysisRouteBatchWriter` 已有 409「请先撤回后再改路线」, 界面直接置灰不让点出来 |
| 路线记忆 | 确认时同事务回写 `goods.source_type`, 下次分析按主档带出建议路线 |

这三条**在本次改动之前就已经成立**, 本 ADR 只是把它们确认为口径并补上红框。
库侧三条守卫、V477 约束与批量写入器一行未动。

> 为什么不做「默认路线直接生效」: V467 的自制/委外子件任务守卫比的是
> `parent_material.confirmed_route IS DISTINCT FROM action.route`(NULL 必然命中),
> V574 的在途调拨接收方守卫写死 `target.confirmed_route IS NULL` 即拒,
> V478 的根产出守卫第二句同样对 NULL 必然 DISTINCT。服务端做 `COALESCE` 放行之后,
> 写入仍会在库层被顶回来, 用户看到的是一串 23514 而不是「下单成功」。

### 2.2 勾选换义: 一个选中集, 两个按钮

主表的复选框以前只服务「确认路线」, 判据还绑死在路线权限上。换义后:

- 可勾判据 = **并集**: 有待提交的路线决定 **或** 这一行此刻能下单/追加;
- 勾选框的权限门 = 路线 / 下达采购委外 / 下达车间 / 跨计划调拨 **四把锁的并集**——
  缺哪一把只是少一个可做的动作, 不该整列没有勾选框(旧写法会让只有采购权限的采购员一行都勾不上);
- 悬浮区两个按钮: `确认路线(N)` 与 `下单(N)`, 各自只对自己够格的子集动手, 缺权限就少一个按钮。

### 2.3 「看到的勾选 = 提交的内容」

主表折叠不撤勾、表头筛选也不撤勾, 而选中集是跨分页累积的。提交前按**当前投影**过一遍:
藏起来的行不进提交集合, 但要在确认框里如实数出来告诉人——不能静默丢掉, 也不能偷偷提交。

退役四列, 信息并入而非丢弃:

| 退役列 | 去向 |
| --- | --- |
| 可用数量 | 「还缺数量」悬浮说明的「仓库现在可用 X」 |
| 在途未到 | 「还缺数量」悬浮说明的「已安排但还没合格入库 X」 |
| 公共认领未实收 | 「还缺数量」悬浮说明的「已按公共在途扣减 X」 |
| 在途调拨 | 「物料办理」列调拨按钮的悬浮说明 |

十五列全部**无条件出现**。旧表有两个条件列, 一次轮询让某行的公共认领量归零, 列集合就翻转,
用户刚拖好的列宽列序当场被重置——这个坑随条件列一起消失。

**不给任何列开点击排序**: 本表是树, 按列重排会把层级打散。用户口径里的「表头排序或者添加删除」
指的是列的顺序与显隐, 那两件事表头设置(拖拽换位 / 竖拖隐藏)本来就支持。

### 2.5 还缺数量: 把公共的算进去, 但只在真会认领的行上

```text
还缺数量 = max(0, 建议下单量 − 该行下达时服务端真会自动认领的公共在途)
建议下单量 = max(0, 本批净需求 − 本分析已安排且仍有效的在途)
```

仓库里的公共现货**本来就已经**扣在「建议下单量」里了(它从 `allocatedAvailableQty` 起算,
而那正是本节点从公共现货池分到的份额)。真正新扣的只有一项: 别人计划可认领的公共在途。

四条硬约束:

1. **不动 `shortageQty` 的算法。** 它同时是 `actionable()`、让料候选与入库齐套三处的判据;
   把公共量算进它会让大量行 `shortage` 归零、整行掉出可下达集合——与「一张表能直接下单」正好相反。
   新口径落在**另一个字段** `netShortageQty` 上。
2. **只是展示量, 不建任何占用。** 真正的占用仍然只发生在下达那一刻由服务端自动认领(ADR-099)。
   这与 ADR-029 §二.2「在途不是现货」共存: 它不进物理预留, 也不抬「可立即生产量」。
3. **这个数绝不能拿去预填「下单数量」。** 见 §2.6——这是本 ADR 初稿写错、被 2026-09-22
   对抗复查推翻的一条。
4. **只在两个条件同时成立时才扣。**
   - ① 下达时服务端真会自动认领: 自制、需先自制目标件的委外、我方供料带 BOM 的委外件
     这三类在下达段是跳过认领的;
   - ② 这个物料维度在本分析里只有这一行: 公共在途池是按 (仓+货+色+单位) 共享的,
     `SharedFutureIndex.forMaterial` 对同维度的每一行都返回**整池**, 而「建议下单量」是逐行
     可加的。同料多行时逐行扣会把同一池扣 N 次——三行各需 100、池里只有 100 时会算出三行
     都「不缺」, 人照着填就少下 200。

> **判错方向是刻意选的。** 把「其实会扣」的行判成不扣, 人看到毛数, 照着填不会多买;
> 反过来净数偏小才会**少下单**, 那是真损失。因此两个条件都取保守侧。
> 同料多行按份额精确分摊是更好的做法, 但要在装配期跨行算一遍池的分配, 见 §六待办。

晚到来源算进扣减(与服务端 `allowLateSupply = true` 一致), 但在悬浮说明里**单独列出**
「其中含晚到来源 X」——ADR-070 要求人看得见自己接受了什么。

### 2.6 下单数量与追加下单

| 行状态 | 下单数量 | 追加下单 |
| --- | --- | --- |
| 未确认路线 | 横杠, 不可填 | 横杠, 不可填 |
| 已确认未下达 | **可填**, 预填**毛量**(见下), 可超量 | 横杠, 不可填 |
| 已下达 | **只读**, 显示累计已下单量 | **可填**, 默认 0 |
| 需先自制目标件的委外 | 有「下达车间」权限: **可填**, 预填毛量, 可超量(走 ARRANGE 段, 2026-09-22 修订见 §12.6); 没有权限: **只读**, 显示必须整批接管的量 | 同左: 有权限按已下达行的规则; 没有权限**横杠**, 追加产出在计划里填 |
| 自制 | **可填**, 预填毛量, 可超量(2026-09-22 修订, 见 §八) | **可填**, 已下达后走 `publicSurplusOnly` |

> **「下单数量」预填的是毛量, 不是左边那个「还缺数量」。这两个数不一样是对的。**
>
> 服务端下达时是 `demandQty = requested.min(delta)`, 之后再从中减掉自动认领的公共在途——
> **认领是从用户填的这个数里切走的, 不是在它之上另加**。需求 1000、可认领 300 的行,
> 填净数 700 只会换来「认领 300 + 新单 400 = 700」, 对着 1000 仍差 300, 每一行都少下一个
> 认领量。本 ADR 初稿把预填写成净数, 2026-09-22 对抗复查推翻。
>
> 界面上用「还缺数量」的悬浮兜住这个反直觉: 写明「右边填的是本次要覆盖的总量 X,
> 服务端会从中认领 Y、只为余下部分开新单」。(初稿还在「下单数量」的表头 ⓘ 里写了一遍
> 「要覆盖多少而不是要新开多少单」, 2026-09-22 晚按用户口径撤掉了表头 ⓘ, 见 §12.8。)

> **累计已下单量不含调拨与公共认领。** 跨计划调拨与公共在途认领也会投影进
> `downstreamReferences`, 而且服务端按**目标行的确认路线**归位, 路线过滤拦不住它们。
> 把它们算成「已下单」会让一条刚调过一点料的行被锁进「追加=0」、批量下单静默跳过它——
> 而调拨正是「物料办理」列主推的第一个动作。按 `operationType` 排除
> `FUTURE_TRANSFER` / `SHARED_FUTURE_CLAIM`。

两件必须让用户知道的事:

- **「显示累计、提交增量」是刻意的分裂。** 线上契约 `SupplyQuantityInput.qty` 与
  `IssuePlanLine.qty` 的语义都是「本次要下达的量」, 累计只能是展示值。
- **追加只增不减。** V640 的守卫硬性要求 `new.qty > old.qty`, 且只在「申请明细还没被采购/委外
  做成订货单」这个窗口内能就地改大原申请; 过了窗口只能另立新单。**不提供改小的入口**, 只提供撤回。

「可超量」在一张表里有三套规则, 界面按行分形态表达而不是让人填完吃 403/400:
采购与直接外发委外可超, 超出部分需超量下达权限; 需先自制目标件的委外既不能超也不能少;
自制可超, 走 `publicSurplusOnly`, 按 V577 口径不要超量权限。
自制填得比「还需安排」少时只给一行提示、**不拦提交** —— 没下的那部分仍留在这一行,
下一轮接着下, 分批下达本来就是合法用法。

### 2.7 父行改量带动子层: 委托给服务端, 客户端一行算术都不做

父行的「下单数量 / 追加下单」每敲一下, 页面**当场**按比例把它下面每一层实际备料需求换算好，
还缺数量和下单预填随之变化，来源「需要数量」保持不变；再去抖 300ms 带着**用户亲手填过的数**(不是界面显示值)调
`issue-plans/preview`(`lines` 为空 = 只重算不模拟下达), 拿服务端算好的「下达之后」快照整体覆盖
估算值(起订量抬量、锚点配额、包装取整只有服务端算得准)。

- 当场换算走共用件 `material_cascade_math.dart`(与「父件 + 下层一起下单」同一份, 见 §9.3),
  从头算不增量: 分母永远是服务端快照当时的数, 退格、改回、清空都是幂等的。
- 去抖是**页面级单例**, 不是每行一个定时器: 整张表铺开输入框后, 每行一个 Timer 会把回滚式
  预览的请求量放大到不可接受——那个端点在服务端是真跑一遍下达再整体回滚(实测 1.4 到 7 秒,
  这也是只靠它时主表看起来「改了没反应」的原因)。
- 代际丢弃: 用户还在敲时迟到的那一份直接作废。
- 预览结果与估算值**只用于展示**, 绝不替换权威快照: 它的版本与指纹都是模拟态, 提交一律按权威快照走。
- 清空输入框 = 把这一行交还给系统算, 不是「填了 0」。

> 2026-09-22 上午本 ADR 曾**刻意不复制** ADR-099 那条线的客户端即时估算, 等它稳定并抽成共用件。
> 同日下午共用件就位后接进主表, 见 §9.3; 当初列出的四个坑(分母要取服务端快照当时的值而不是上一拍
> 键入值、送回服务端的只能是 userTypedQty、父件落地后重建时屏上的数只能上不能下、换算比例要用
> 「这一行要下多少」而不是本批需求的比例)全部由共用件与它的单测兜住。

### 2.8 调拨

- 语义不变: **只能从别的计划已锁定的量里调**, 血缘只认 `ORIGIN_IQC` / `ORIGIN_MAKE`,
  调进来的量不能二次转调。这与现有权益所有权语义完全一致。
- **不进多选批量。** V311 规定一个物料节点不能同时参与多笔未补齐的让料, 多选调拨必然部分失败,
  同一行也不能拆成多笔来源。多选只服务下单与追加, 调拨仍逐行点开。
- 新增只读端点 `GET /{id}/transferable-in-summary` 给主表按行决定按钮灰不灰。

### 2.9 表头筛选: 能加的都加

十五列里十四列有筛选。唯一没有的是树形的「物料名称」——它已经有关键词搜索框,
再挂一个几百个值的下拉没有意义。

> 2026-09-22 晚被 §12.8 部分推翻: 「物料办理 / 编号 / 需要数量 / 还缺数量 / 下单数量」五列
> 按用户口径列头只留字, 不再有筛选(也不挂 ⓘ)。现在是十五列里九列有筛选。

实现上收成一张**取值器表**: 加一条取值器, 建桶、匹配与失效清理三处自动跟上。
老写法是三处各写一遍, 加列必漏其中一处。

| `ROUTE_PENDING` 阶段 | `MaterialAnalysisFlowStageService` | 路线未定的行不进任何一条供应链 |
| `transferableInSummary` | `MaterialStockReallocationService` | 按物料维度一次算完, 见下 |
| `GET /{id}/transferable-in-summary` | `MaterialAnalysisController` | 只读, 挂 `:cross_reallocate` |

**没有新增 Flyway 迁移**, 因此迁移头五处一处未动。

批量可调拨量能从逐行降成一次, 靠的是一个结构性事实: **某一行供方能不能借出, 只取决于供方自己**
(它自己的血缘、它自己的未了结关系、它自己的可分配余量), 与接收方是哪一行无关。唯一与接收方
相关的排除项是「接收方自己已卷在一笔未了结的让料/借用里」, 那一整行的可调拨量直接归零。
于是 `可调拨量 = 接收方自身合格 ? 该物料维度的供方合计 : 0`, 一次按维度聚合即可,
语义与逐行口径逐字一致。

结果随登录人的对象级可见范围变, **不可跨账号缓存**, 也不进分析快照的热路径。

## 四、界面契约(实现约束)

- 主表容器继续用 `MasterDataTableView` + `cellBuilder` 内放输入控件, 控制器存宿主 State。
  分桶详情页已经在生产里跑着「多行行内编辑 + 跨分页 + 抗轮询回填」这套做法, 不需要换成
  `UtenEditableGrid`, 列显隐/列序/列宽与表头筛选这些主表既有能力一个都不丢。
- **输入保全是硬要求**: 轮询与 409 恢复都会整树换快照。新快照回来后只回填「仍等于旧系统预填值」
  的格子, 用户改过的一律保留。少了这一步, 用户填了一屏的数会被后台刷新静默吃掉。
- 多选下单**不是一个事务, 是编排**: **逐层自上而下, 同一层先下达车间(自制 + 需先自制的委外)、
  再直接外发委外; 采购件没有下层, 全部父件落地后最后一次提交**(2026-09-23 修订, 见 §十)。
  每段独立幂等键, 任一段失败就停下并如实回报已完成的段, 未完成的行保留勾选。
  父先子后是硬约束: 一行的需求由它上面每一层的计划产出量决定(含父件超出需求的公共备货产出,
  V577/V589), 父件没落地时子件按父件新数量填的量会被服务端当成超出当时需求、记成公共备货产出;
  之后父件的超量把子件需求抬上去, 子件行就留下一截认不回来的幽灵缺口。
- 一批提交期间不自动发层级预览(`_tableSubmitting`); 每段成功后立即把这些行填的数从 typedOutputs
  摘掉(服务端是「已下达 + 本次填的」, 留着会再加一遍), 批完只在还有未下成的填数时补一次。
- 跑批遮罩与确认框的顺序按
  [组件契约](../02-组件库/UtenBusyOverlay.md)登记: 弹窗前先放开忙标志并等一帧。

## 五、不做的事

- **不把调拨做成批量**(见 §2.8)。
- **不新增权限点。** 四个动作复用既有的四把锁。

## 八、2026-09-22 用户复核修订

主表落地后用户实机复核提了四条, 逐条结论:

### 8.1 物料办理只要调拨, 行内下达退役

原 §2.4 把这一列定成「调拨 + 下达」。回看 §一 记录的用户原话, 括号里只定义了调拨 ——
「下达采购 委外 车间 那里 也要对应的修改」说的是那三个分桶页要跟着改, 不是要这一列长出
下达按钮。所以这次不是改口径, 是回到原话。

行内下达与悬浮区「下单(N)」本来就是同一个 `_submitMaterialTableRows` 的两个入口, 端点、
确认框、数量来源、权限门全同; 可勾判据用的也正是下达那同一个谓词, 凡是行内按钮亮着的行
必定有复选框 —— 撤掉不丢任何能力。调拨必须留在行内的理由不变(§2.8: V311 不许一个物料节点
同时参与多笔未补齐的让料, 多选调拨必然部分失败)。

一处必须一起做的收口: `_tableIssueBlockedReason` 产出的人话原因原来只挂在那个置灰的下达
按钮上, 是全表唯一常驻解释「这一行为什么下不了单」的地方。按钮撤掉后改挂到「下单数量」
格的悬浮说明里, 不能让它跟着按钮一起消失。

### 8.2 自制行的「下单数量」放开

原 §2.6 把自制行定成只读, 理由是「服务端要求逐字等于剩余需求, 给输入框只会让人填完吃 400」。
**这个理由引错了对象。** 那条校验(`createsChildOwnership`)长在 `notifySupply` 里, 而自制行
在同一个方法更靠前的地方就被另一道闸拦掉了(「自制路线请直接『创建生产计划』下达车间,
不再单独创建子件任务」), **根本走不到那条数量校验**。自制行实际走的是 `issue-plans`, 那条路
`demandQty = line.qty().min(remainingQty)` + 超出部分记 `public_surplus_qty`(V577),
明确接受任意数量, 连超量权限都不要。

兄弟页面早就是这个口径:「下达车间」分桶页写着「任何行都可填超量」,「父件 + 下层一起下单」
页把用户填的数原样送进 issue-plans。用户最初的原话也写着「下单数量(可填写, 可超量)」。
所以锁死自制行是引错对象的历史惯性, 不是技术约束。

连带修好一处: 自制行没有输入框时永远进不了 `typedOutputs`, §2.7 那条「父行改量带动子层」
对自制行完全失效 —— 而自制行恰恰是唯一有子层、这条联动本来就是为它做的那一类。

委外那一支不动: 它确实可能落回 `notifySupply` 的整量接管。

### 8.3 顶层产品行不再是一排横杠

`_tableEditableGroup` 原来对产品行一律早退, 导致顶层的物料办理 / 下单数量 / 追加下单 /
生产车间 / 负责人五列全是横杠; 而「还缺数量」走的是另一套判据, 对已确认采购或直接外发委外
的顶层行**会显示真实数字** —— 同一行左边看得见缺口、右边办不了事。

这条排除没有 ADR 依据也没有用例覆盖(ADR-102 的夹具里产品根本没有 `rootMaterialLineId`),
是本 ADR 之前的实现惯性, 与「把顶层父件 + 下层一起下单搬进这张表」的立意相反。V478 之后
产品行直接承载真实的 ROOT_SUPPLY 节点, 它恰恰是「这个产品到底自己做、还是买、还是外发」
的那一行。

放开时有一处不能想当然: **顶层自制与其它自制行走两条不同的提交通道**。服务端
`candidateRoutesByMaterialLine` 的过滤是
`!"ROOT_SUPPLY".equals(nodeRole) || "SUBCONTRACT".equals(sourceConfirmed)` ——
顶层自制既不是候选、也不该走 notify, 它本身就是排产对象, 要按产品的 `analysisLineId` 送进
issue-plans 的 `planDrafts`; 顶层委外**是**候选(ADR-099 放开), 照常走 `materialLineId`。
当成候选按 materialLineId 提交的话服务端解析不出候选、整批失败。

仍然排除的两类没变: 分页补的只读上下文行、汇总视图的聚合行(它五列全横杠, 可勾会让人提交
界面上从没显示过的默认值); 没有根供给组的产品行自然落空。

### 8.4 「还缺数量」与办理/下单两列收口到同一条判据

顶层放开后, 这三列不能再各用各的判据。现在统一成「有根供给组的产品行照常显示, 没有的才是
横杠」。原来只对已确认非自制路线的顶层行显示缺口, 顶层自制明明也能下达车间却看不到数。

## 九、2026-09-22 数量联动收口：主表与级联页共用一份算法

用户口径：「物料分析页面的数量计算应该和顶层的父件 + 下层一起下单里面一样——父类变化子类
自动变化，还有各种判断。」两处入口(改来源产品数量后刷新、在树里任意一层改数)都要跟。

### 9.1 主表上被修掉的四处

对抗审计逐条读码确认，全部有用例钉住(`material_analysis_one_table_test.dart` 新增三例)：

1. **追加格没接 `onTyped`**：`_materialTableAppendQtyCell` 调 `_materialTableQtyField` 时漏了
   回调，而「还需安排为 0 的已下达中间层」只能在追加格填数——填了既不进 `_tableUserTypedQty`、
   也不触发重算，子层纹丝不动，提交时还因为提交量读不到被静默剔掉(口径第六条整个不成立)。
   修法不是简单接上 `_onTableQtyTyped`：下单格与追加格是**同一个提交单元的两半**，各写各的会
   互相覆盖同一个 map 键。现在两格都走 `_recordTableTypedQty`，按「下单格 + 追加格」的合计写
   那一个键；任一格填了就算「用户亲手决定过」，两格都空才交还系统算。
2. **下达成功后不清 `_tableUserTypedQty`**：服务端那一侧是**加进**计划产出量，留着已落库的量，
   下一次重算就把它再加一遍；而且 `_hasUnsubmittedMaterialTableInput` 永远为真，45 秒轮询再也
   不跑。现在按 `groupsByKey[key].representative.materialLineId` 摘键(两套键空间：`done` 装的是
   操作组键)，并把 `_tableCascadePreview` 连同代际一起作废——刚落库的量已进权威快照，上一份
   模拟快照派生的预填必须同时失效。
3. **历史上将「需要数量」与动态备料量合并**：此前为让两列联动，`_materialTableRequiredQty` 改读重算快照。2026-09-23 用户明确要求后，这一展示决策由来源量分离取代：主表需要列只读 `sourceRequiredQty`，还缺数量继续读实际备料/计划预览。来源需要 1000、超量后的备料缺口 1500 是两个口径，不能再强行让来源需要量跟着变。
4. **「填过没有」两个事实源**：收口到 `_tableUserTypedQty` 一个，`_tableSeededQtyTexts` 只当
   系统预填值缓存。

### 9.2 换算与判断抽成共用件

`lib/features/production/models/material_cascade_math.dart`：不依赖 Flutter、不认识任何页面的
行对象，只认「服务端给的三个数 + 用户亲手填的那个数」。级联页已经改为调用它
(`followUpQty` / `applyScaled` / `_scaleSubtreeAt` / `_cascadeTypedOutputs` 全部委托)，主表要
做即时估算时接同一份即可，不必再写第二遍。

两条不能想当然的约定写在文件注释里：

- **子层跟的是父行的「净产出」不是「毛需求」**：服务端 `parentPlannedOutput` 从 `shortageQty`
  (需求扣已分配现货)起算再扣在途，这一行有现货覆盖时两者差着一个覆盖量。
- **传进去的必须是未经投影的全量前序**：屏幕上相邻不等于树上父子，主表按 `_bomPresentation`
  的父子链(表上画出来的那棵树)自己走一遍前序，折叠、表头筛选、分页都不影响它，不能拿渲染行集当层级。

单测 `test/features/production/material_cascade_math_test.dart`(15 例)把六条口径钉在算法层，
不依赖任何假后端——上一轮正是假后端「孙层按 批量 × 单耗 展开、忽略中间层覆盖」的错口径，
差点把「跟净产出还是跟毛需求」判反。

### 9.3 主表「敲一下就当场变」(2026-09-22 下午接线)

用户实机复核：「主表上敲一下就当场变……对应的数值没有变化, 我合并了也没有反应。」两个原因：

1. **只靠服务端那趟太慢**：`issue-plans/preview` 在服务端是真跑一遍下达再回滚, audit_log 里这一天
   的样本 1.4 到 7.7 秒, 去抖 300ms 之后还要等它, 人已经把它当成「没反应」。
2. **顶层产品行根本判成「没有下层」**：`_tableGroupHasChildren` 按 `childrenByParentNodeKey`
   (原始 `parentNodeKey` 桶)查, 而第 1 层子件的 `parentNodeKey` 是空的(它们挂在根供给行下是
   `_bomPresentation` 补的链)。于是在顶层产品行改数既不换算也不发请求。现在按表上画出来的那棵树
   (`_bomPresentation.parentIdsByMaterial`)判, 前置自制接管的分支同理。

接法(`material_analysis_material_table.dart`)：

- 实际备料相关数从 `_tableShownQty` 读取：页面估算值 → 服务端模拟快照 → 权威快照。
  「还缺数量」「下单数量预填」继续跟父行改量；2026-09-23 起主表「需要数量」独立读取来源 `sourceRequiredQty`，不再进入估算放大链。
- `_recomputeTableEstimates` **从头算不增量**：只重算「此刻填数与快照当时不同」的那些树, 一棵树里
  所有填过的行一次算齐——父行与它下面被人改过的中间层要按同一份口径走(共用件口径三)。
- **分母按「快照当时的填数」算**：模拟快照记着它是按哪份填数(`_tableCascadePreviewTyped`)算出来的,
  权威快照对应空表。服务端那趟在路上时用户又改了数, 回来后分母摆到请求时那份填数上, 把这期间多改
  的那部分就地补算, 屏幕不会先跳回旧数字再跳到新数字。
- **已下达量进分子分母**：已下过单的父件再追加, 它下面那一层是按「已下达 + 本次填的」展开的
  (服务端「已下达计划量 + 本次填的量, 再与需求取大」)。共用件为此加了 `committedOutput`,
  否则追加行的分母是 0, 只能干等服务端。顶层供给行按服务端 `plannedSourceOutput` 的口径:
  「来源需求量 与 已下达 + 本次填的 取大」, 需求量那一项不扣现货。
- **净数 = 毛数 − 可自动认领的公共在途**：那个池子与父行数量无关, 换算后按快照里的差值原样扣。

## 十二、2026-09-22 晚：追加联动子件、有数自动勾选与「还缺数量」口径

用户口径：「追加对应的子组件也要对应的追加显示——父组件已经下单了 1000、子组件也下单了 1000, 父组件
追加 200, 子组件追加那里也自动追加 200; 有数值的都自动选中; 但子组件之前已经下单了 2000 的就不用追加了。
各种情况都考虑下, 还缺数量应该怎么显示、怎么计算。」

### 12.1 追加格的预填 = 这一行此刻的缺口

追加格(已下达的行)预填 = 「还需安排」：缺口 0 就是 0(勾着不动 = 本次不下它)。父行改量(下单格或追加格)
把子行的缺口抬起来时, 没被人动过的追加格跟着回填新缺口——与下单格同一套「系统预填 / 用户改过」判定
(`_tableSeededQtyTexts`, 一格被改过就永久归用户, 任何刷新都不覆盖), 两格共用 `_reseedTableQtyCell`。
下达成功的行追加格回 0, 新快照到了再按新缺口预填。

### 12.2 「还缺数量」 = 需求 × 比例 − 不封顶的覆盖量

服务端的「还需安排」封顶在 0：子件只需 1000 却下了 2000 时, 快照里看不出多下的那 1000; 父件追加 200 把
需求抬到 1200, 按封顶值(覆盖 1000)算会错报还缺 200。共用件 `cascadeScaleOne` 加了 `coveredFloor`：
覆盖量 = max(服务端封顶的 `required − residual`, 现货分配 + 已下达 / 在途 **不封顶**), 主表按
`allocatedAvailableQty + exactPeggedQty + _tableGroupIssuedQty` 传(现货那一份读服务端明写的分配量,
不用「需求 − 缺口」倒推)。这是估算：漏算的覆盖来源由封顶值兜底, 剩余误差 300ms 后服务端预览整体覆盖。
级联页暂未传不封顶覆盖量(它的行对象没带现货分配字段), 见待办。

| 子件状态 | 父件追加后 | 追加 / 下单格 | 勾选 |
|---|---|---|---|
| 刚好下够(需求 1000 / 已下 1000) | 需求 1200, 覆盖 1000 → 还缺 200 | 追加格 200 | 替他勾上 |
| 多下了(已下 2000) | 需求 1200, 覆盖 2000 → 还缺 0 | 追加格 0 | 不勾 |
| 多下了一点(已下 1100) | 还缺 100 | 追加格 100 | 勾 |
| 没下过、现货盖住(现货 1000) | 还缺 200 | 下单格 200(不是追加格) | 勾 |
| 单耗 2 | 需求 2400, 按同样算法 | 缺多少填多少 | 勾 |
| 有可认领公共在途 300 | 「还缺数量」是净数(缺口 − 300), 格里仍填毛量(服务端从填的数里切认领量) | 毛量 | 勾 |
| 孙层 | 子件回填的追加抬高它的产出, 孙层按「已下达 + 追加」再换算一层 | 同上 | 勾 |
| 父件清空追加 | 子件回落到快照值 | 回落 | 替他勾的撤掉 |
| 子件亲手填过 | 不覆盖他填的数; 「还缺数量」照实显示缺口 | 保留 | 不动他的勾 |

### 12.3 自动勾选

- 亲手填了数(下单格或追加格 > 0)的行替用户勾上; 清成空 / 0 撤掉替他勾的那个勾(亲手勾的不动)。
- 父行改量带出来的行：回填值与**权威快照**的还需安排不同(= 这个数是改量带出来的)且 > 0 → 勾上;
  回落到快照值或 0 → 撤掉替他勾的勾。按快照本来就预填着数、没被改量碰到的行不动——勾选集只反映
  用户自己的动作, 「有数值的都自动选中」不是「一进页面全勾上」。
- 亲手撤过勾的行(`_tableUserDeselectedKeys`)父行再改也不替他勾回来, 直到他再勾 / 再填数; 权威快照的
  例行刷新(轮询 / 他人下达后)不自动勾。
- 不可勾的行(缺权限 / 本次下不了单)不动：已下满的行再下属超量, 没有超量权限时子件的追加格会填上缺口但
  勾不上、提交也会被既有权限门拦下——这是权限口径, 本节不改。
- 勾选框与底部「下单(N)」在停手 200ms 后那次整页刷新才变(§9.3 的性能口径), 数字与红框仍是当场变。

### 12.5 服务端：顶层纯公共备货追加带「立即审核」被销售分摊拒绝(2026-09-22 实机)

用户实机：顶层产品「已下 2000 / 需求 1000」在主表追加 1000 点下单, 第一段「下达车间(第 0 层, 1 行)」
409。audit_log 里三次 POST issue-plans 全 409、无异常日志; 用回滚式预览复现：带 `publicSurplusOnly`
不带立即审核 → 200, 带立即审核 → 409「计划明细缺少可排产的销售需求量」。

根因在 `ProductionPlanService.collectAllocations`：销售订单来源的计划明细在审核时按分析 link 的
`submitted_qty`(归本需求量)做销售分摊, 纯公共备货追加的 link 是 submitted 0 + public_surplus 全量,
分摊量 0 被当成「没有可排产的销售需求量」抛 409。而 2026-09-15(V588)的口径本来就是「公共备货产出不进
订单侧 planned_qty、不建 plan_order_item_links 容量」——归本需求量为 0 时应当**跳过分摊**, 不是拒绝。
修法：`analysisSubmitted == 0` 的分析计划明细直接 `continue`(无分析关联的手工计划仍要求整行数量为正)。
E2E `PreplanPlannedQuantitySingleEntryEndToEndTest.fullyPlannedSalesRootCanAppendAPureSurplusBatchWithApproveNow`
钉住：追加 4 后 link 0 + 4、计划与第一张同为已审核、订单行 planned_qty 不动、这张计划没有销售分摊。

### 12.6 要先自制目标件的委外行：下单数量只在没有「下达车间」权限时才锁死(2026-09-22 实机)

用户实机：「HV5ZJ012 把路线改成委外后下单数量就定死了不能修改, 我都没有下单过。」这类行(有生产性下层、
不是 V581 单一子件件)在主表上原本不看权限一律锁成「整批接管 N」+ 追加横杠——那是 notify 通道的整量接管
口径; 而 2026-09-16 起有「下达车间」权限时它走 issue-plans 的 ARRANGE 段(与委外桶 / 级联页
`_subcontractChannelOf` 同一口径), 数量可改可超。现在 `_tableGroupWholeTakeover` = 要先自制 且 没有
`_canGenerate`; `_tableIssueTarget` 对有权限的走车间、没权限的走 notify 整批接管(原来没权限也标成
「下达车间」, 结果只会被「没有下达车间权限」拦住)。只读格的悬浮说明改为点明「你没有下达车间权限」。
用例：`material_analysis_one_table_test` 「要先自制目标件的委外行…」两种权限各验一遍。

### 12.7 生产车间 / 负责人跟路线走(2026-09-22 用户口径)

「路线改变后对应的生产车间、负责人就要清空, 除非变回原来的路线——变成采购、委外就不需要生产车间了。」
主表两列改按**路线**判(`_tableAssignable` = 自制)：采购 / 委外一律横杠且不要求指派, 改回自制那一刻
草稿里原来选的车间 / 负责人回来(草稿按提交单元记着不删)。此前按「下达去向」判, 要先自制目标件的委外
走车间通道时照样露出并要求指派——就是用户看到的「改成委外了还要生产车间」。这类委外走 ARRANGE 段时,
车间按学习默认带给服务端, 没有就由服务端排产方案兜底(`segment.workshopDepartmentId` 为空时取
proposal 的), 不再在主表上拦「先指定车间」。级联页(父件 + 下层一起下单)的委外种子仍按学习默认预填
车间, 暂未同步这条口径。

### 12.9 已建前置自制任务的委外子件按锚点算「已下达」(2026-09-22 实机, 根治)

用户实机第二轮：顶层追加 1000 点下单仍 409, 口径「有些子层级之前一次多下了, 那么这次就是不需要下」。
用自签 token 复现：根行纯公共备货 + 立即审核已放行(§12.5), 这次的 409 来自子层——`HV5ZJ012` 是
要先自制目标件的委外件, 前置自制锚点(SUBCONTRACT_MAKE)需求 3000 已排 4000, 发外申请 3000。主表对
委外路线一律按**发外申请明细**算累计已下单(3000), 锚点上多下的 1000 看不见; 父件追加把它的需求抬到
4000 后, 当场估算 = 4000 − max(3000, 3000) = 1000 → 追加格自动填 1000、自动勾上、随批送 ARRANGE 一段,
服务端按锚点(剩余 0、未声明纯公共备货)409「当前分析需求已全部转入生产计划」。服务端预览对这一行给的
`additionalSupplyRecommendedQty` 是 0——只有主表自己的口径错了。

根治：走车间通道的行统一按锚点判——`_tableUsesMakeAnchor` = 自制 或 要先自制目标件的委外;
`_tableGroupIssuedQty` / `_tableIssuedMakeAnchorOf`(→ 还需安排、publicSurplusOnly、排满拦截、覆盖量下限)
全部经它, 与级联页 `preparationAnchor` 同一口径; 没建过锚点的委外照旧按申请明细。已建锚点的委外行只能
经 ARRANGE 追加, 没有「下达车间」权限时勾选框直接说明原因(不再退回 notify 整批接管再建一次子件任务)。
用例：`material_analysis_one_table_test`「已建前置自制任务且多下过的委外子件…」(锚点 1000/1400、父件
追加 600 不缺、追加 1000 才缺 400)。

待办：级联页的 `_ChildCascadeRow` 补现货分配字段并传 `coveredOutput`, 让它对多下过的子件也算得准。

### 12.10 追加自制并入未开工的原计划(2026-09-22 用户口径, 见 ADR-104)

用户: 「追加的自制件, 生产车间没有去领料开工的前提下应该自动合并, 不要每追加一次就单独列一张;
采购那边已经会自动加到一个单子; 如果已经开始执行了就创建新的单据。」

主表这一侧一行代码都不用改——追加格照旧送 `issue-plans`(候选行按 materialLineId、顶层按 analysisLineId,
数量 / publicSurplusOnly 分账同 §12.4 / §12.9)。落点由服务端决定: 同一分析行最近一张还没开工的计划
(库侧 `fn_material_analysis_plan_growable`, V645/V647)就并进去——同一计划单号、明细加量、关联行同一行加量；已审核的直接加到原 ZX 工单，原段和需求身份不变，按冻结耗用规则累计计量并只补备料差额。
提交领料申请即停止合并，仓库尚未发料也一样；已有发料、开工、报工或拆批同样另立新单。`GeneratedPlan.mergedIntoExisting / appendedQty` 回来后,
分段回报写成「下达车间(第 N 层, M 行, 其中 K 张并入原计划)」, 分桶 / 级联页的结果弹层标题改成
「追加已并入原生产计划」。「累计已下单」「还需安排」读的是关联行汇总(`issuedPlanQty`), 并入与新建读数相同。
决策、库侧判据与验证见 [ADR-104](ADR-104-追加自制并入未开工的生产计划.md)。

## 十三、需要数量固定表示来源需求(2026-09-23)

用户明确要求「需要数量」固定显示销售/计划汇总的来源需求，不能因下单、追加或预览变大。主表需要列只读取 `MaterialView.sourceRequiredQty`，产品行读取原始来源 `requestedQty`；不从 `_tableShownQty`、执行锚点追加后的 `requested_qty` 或计划总量回填。汇总视图按真实物料路径的 `sourceRequiredQty` 求和，同一物料不同路径分别计量。

服务端从真实根来源 `requestedQty × unitRate` 出发，按该节点保存的 BOM 规则逐层精确展开，不扣库存、在途、已下达或完工，也不纳入追加输入/公共备货。下单预览和真实下单返回相同的来源量；合法修改来源或 BOM 并刷新时才重算来源量。完整规则见 [ADR-099 §0](ADR-099-计划量单一入口与子层按计划产出展开.md#0需要数量固定读取来源需求2026-09-23)。

原 `requiredQty` 仍是实际备料需求，缺口、建议下单、子层追加和执行材料全部继续按计划实际产出变化；级联页的动态需求列改名「本批备料需求」。来源需 1000、计划多做至 1500 时，主表需要仍为 1000，子层实际备料需求应为 1500。两列语义分开后，不允许为了显示相等而少下单或改小冻结执行需求。本次仅新增只读响应字段并调整显示，不新增迁移，也不改 V647。
