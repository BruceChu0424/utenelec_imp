# ADR-037：数据库数据保护与分级加密

> 日期：2026-08-14
> 状态：已决策；TLS 门禁、V282/V286/V287 员工扩展 PII 迁移链与 V284 个人信息变更敏感快照保护均为源码候选，目标库/目标主机尚未迁移验收
> 详细执行合同：[数据保护与加密分级](../05-架构/数据保护与加密分级.md)

## 背景

业务希望即使数据库、磁盘或备份被他人取得，也尽量无法直接读出财务、销售、人事等数据。同时 ERP 的金额、
数量、余额、汇率和总账事实又必须在 PostgreSQL 内完成聚合、范围过滤、约束、索引、对账和并发事务。

“全列加密”无法同时满足这两个目标：随机密文不可计算，确定性/保序密文会暴露低熵金额关系；把解密密钥与
数据库放在同一处，也无法抵抗数据库凭据或管理员读取。必须按威胁和字段用途分层。

## 决策

1. **保留内部 UUID 作为关联真相**。本 ADR 不改变主外键、业务引用或历史审计关系；展示编码不是密钥也不是关联键。
2. **金额与计算事实保持精确原生类型**。财务金额、销售/采购金额、余额、汇率、税额、成本、数量、工资计算结果
   保持 `NUMERIC`，不做逐列随机、确定性或保序加密。它们由加密卷、加密备份、TLS、最小权限、对象范围、
   制审分离、不可变过账/红冲、审计和恢复对账共同保护。
3. **高危非计算 PII 才做字段加密**。现有员工、薪酬和访客局部字段继续使用版本化 `pgcrypto`
   对称密文作为过渡控制；V282 又把员工户籍地址、居住地址、邮箱、出生日期、婚姻状况、政治面貌和办公电话
   纳入该路径；V284 将审批中的手机、户籍地址和紧急联系人 old/new 快照收口到同一版本化密文，并清理历史
   `audit_log` 中重复的快照键。它们不是 AES-256-GCM envelope encryption，也没有外部 KMS 生成/包裹 DEK，不能据此宣称 DBA、
   已入侵应用主机或运行中数据库无法取得明文。身份证、银行账号、税号、私人联系方式、地址、官网询盘等的
   目标方案仍是在 KMS/HSM/Vault 选型后使用 AES-256-GCM；KEK 不进入数据库，AAD 绑定环境/表/列/记录
   UUID/版本，精确检索使用独立用途 HMAC。
4. **PostgreSQL 16 不宣称 TDE**。静态磁盘/快照保护由 LUKS2 或加密云盘承担，备份由 pgBackRest 仓库加密和
   异故障域/WORM/恢复演练承担；物理副本不是备份。
5. **生产远程数据库必须认证 TLS**。`prod/cloud` 的非回环 `spring.datasource.url` 必须显式使用
   `sslmode=verify-full` 和绝对 `sslrootcert` 路径；cloud 主/副库无条件执行同一要求，并拒绝自定义 SSL 工厂或
   hostname verifier 绕过。显式回环地址继续允许本机开发、测试和固定 migration-only 流程。
6. **后续历史 PII 采用 expand → dual read/write → backfill → verify → cutover → drop later**。不得原地覆盖，
   不得修改已应用 Flyway；旧解密 key 保留到所有受保留备份过期并完成恢复演练。金额/总账历史不做密文迁移。
   V282 是已有 `pgcrypto` 体系内的窄范围前向候选：数据库拒绝普通事务改变 7 个旧明文列；受审 HR 导入与
   JVM backfill 使用独立事务级 capability，并由同一 PostgreSQL advisory lock 串行化。runner 小批取 id、逐员工锁住
   主行和 sensitive 行，只在目标密文为空时条件写；已存在密文必须先解密对账。V286 只移除证件号/主手机号密文列的
   数据库 `NOT NULL`，让 runner 能在锁内为尚未登记主身份的 bootstrap/legacy 员工创建仅含实际扩展密文的行，不合成
   身份值，也不放宽正常入职/补开账号校验。缺失行创建或重载失败、冲突、条件竞争或残留非零仍使应用保持 not-ready
   并启动失败。它不等同于外部 KMS/envelope 全流程，也尚无目标库回填对账证据。
   V284 对 `profile_change_requests` 采用 `value_encoding` 持久进度、分批行锁回填和全表写守卫；每次敏感写还必须
   带精确事务级 codec capability，旧实例/旧 JAR 因而不能审批新密文行。带版本密文按当前/历史 keyring 选择 key；
   无版本旧 pgcrypto 只尝试当前 key，不猜测历史 key。疑似密文无法解密时启动失败关闭，不把坏密文当明文再包裹。
   V287 再增加可选主身份派生约束：`id_card_enc` 为空时 `id_card_last4/id_card_hash` 必须同时为空，`phone_enc` 为空时 `phone_hash` 必须为空，防止 V286 扩展-only 行残留无法解释的派生身份；它不新增密文或扩大字段范围。
   V282/V284/V286/V287 只允许停写并排空旧实例后的单版本切换；禁止新旧实例滚动并存，也禁止旧 JAR 回滚。失败只做前向修复，
   或恢复与旧应用完全一致且已经隔离验证的数据库备份。
7. **KMS/LUKS 属于需确认的生产变更**。供应商、地域、授权、解锁方式、双人保管、RPO/RTO、维护窗口和回滚期
   确认前，不实施目标主机、生产密钥或生产数据库写入，也不伪造本地 KMS 实现。

## 取舍

- 好处：不破坏 ERP 查询、会计对账和数据库约束；针对磁盘、备份、链路、数据库角色、DBA 和应用主机等不同
  威胁各有可验收控制；历史迁移可分批核对和回退。
- 代价：S2/S3 数据对拥有合法数据库读取权限的人仍可见，因此必须真正落实数据库角色、主机/卷、备份和审计；
  envelope encryption 会增加 KMS 可用性、密钥轮换、字段迁移和故障演练成本。
- 排除：不使用自研密码算法、ECB/固定 IV、全库统一密钥、确定性金额加密、把 KEK 存在同库、仅靠 base64/混淆，
  也不把“脚本里写了 AES”描述成目标环境已经加密可恢复。

## 当前证据与 NO-GO

- 源码新增生产 PostgreSQL TLS 门禁及 cloud 复用策略，定向单元测试覆盖回环、远端、双 host、缺 CA、错误
  `sslmode`、占位/相对路径和验证器绕过；这证明源码门禁，不证明目标链路已启用 TLS。
- V282 新增 7 个 `employee_sensitive.*_enc` 列和明文 `employees.birth_month_day` 派生列；应用写路径使用
  `TxSessionVars.encrypt`，启动 runner 由全局 advisory lock、100-id 小批、逐行双表锁、目标密文对账/条件写和最终残留
  计数保护；V286 允许 runner 在不伪造证件号/主手机号的前提下创建缺失的扩展-only 行，创建/重载失败或任何冲突仍失败
  关闭。数据库 plaintext guard 只放行 runner 或受审 legacy-import 的事务级 capability。原有
  `employee_sensitive` 已覆盖证件号、主手机号、员工银行账号/支行，另有薪酬、紧急联系人手机号、备用手机号和
  部分访客字段的既有 `pgcrypto` 路径。现有单元测试证明字段写入会调用加密接口，不等于 V282 已在目标库完成
  回填、明文清零、密钥轮换或恢复验收。
- V284 修复了 V18 列名声称密文、但提交服务实际把手机/户籍地址/紧急联系人明文写入
  `profile_change_requests.old_value_enc/new_value_enc` 的漏洞。新写由统一 codec 加密；历史行先标记
  `LEGACY_UNKNOWN`，只有 JVM 验证/加密成功才转 `PGCRYPTO_V1`；读取、审批和数据库触发器都对未完成状态失败关闭。
  敏感 INSERT/UPDATE 还必须由当前 codec 显式绑定事务 capability，旧应用状态更新也会在数据库失败。V284 同时删除历史
  `audit_log.before/after` 中的 old/new 快照键和审批自由文本；仍需目标库残留计数、解密抽样和审批回归证据。
- V280 仅下线员工删除权限并补授对象级附件权限，V281 仅新增附件分类、头像标记和头像 `storage_key` 引用；
  二者都没有加密附件文件内容。员工合同、身份证件、证书或头像文件仍依赖附件授权和底层卷/对象存储/备份
  加密，当前没有目标环境静态加密验收证据。
- 截至 2026-08-14 本次文档冻结，共享工作树迁移目录最高为 V289，共 270 个迁移文件、270 个唯一版本且无重复。
  V283 只修正生产关联订单审批快照锁守卫；V284 才是个人信息变更敏感快照和历史审计副本保护；V285 收紧客户默认结算方式 UUID；V286 只放宽扩展-only `employee_sensitive` 行的主身份非空约束，V287 只阻止无主密文却残留身份派生值；V288/V289 处理现货借用表、终态守卫和全 `public` 审计覆盖，在线链已接通但不新增加密字段。它们都只是源码候选，不是目标数据库迁移或生产验收证据。
- 客户/供应商联系方式、地址、银行账号和税号，账户 `bank_account_no`，官网询盘电话、邮箱和正文，短期
  `visitor_sms_codes.phone`，以及 `profile_change_requests.review_comment` 等自由文本、姓名等按策略保留为 `PLAIN` 的审批快照仍有明文列；
  销售单据的联系人电话/地址快照等也未整体迁移。故当前实现不是“全库加密”。
- 本轮没有选择或接通 KMS/HSM/Vault，没有写目标数据库/服务器，也没有执行 LUKS、目标对象存储加密或目标
  备份恢复。V282/V286/V287 使用环境注入的版本化 PGP 主密钥路径及其数据库一致性约束，仍属于现有体系的局部源码候选，不是外部 KEK/DEK 方案。
- 只有在目标环境完成证书失败测试、卷离线不可读、异地备份恢复/PITR、字段迁移对账、密钥轮换/断链和权限/导出
  UAT 后，才能把相应层标记为已验收；当前生产数据保护升级仍为 **NO-GO**。
