# 05 - 模具资料 · 新库设计与老库迁移

> 本档记录新系统模具资料（`mould_categories` 分类树 + `moulds` 主档）的表设计、迁移代码用法、校验结果。

> 与货品资料完全同构（同标准、同流程），见 [03-货品分类-新库与迁移.md](03-货品分类-新库与迁移.md)。

## 一、为什么与货品资料「同构但分表」

货品资料用 `material_categories` + `goods`；模具资料用 **`mould_categories` + `moulds`**，物理隔离、互不影响。

- 早期文档（V31 注释、02-溯源初稿）曾设想「material_categories 加 `kind` 字段共享货品/模具/颜色分类」。实际落地选了**独立表**，理由：
  1. **零风险**：不动已上线的货品模块（实体/查询/迁移脚本一律不改）；
  2. **真·同构**：模具拿到与货品完全对等的「分类树 + 主档」全栈；
  3. 表本身即模具，无需 wrapper 分组（货品 shell 路径里的 `GOODS` 顶级分组在模具侧省略）；
  4. 与代码库既有约定一致（Department 树 vs MaterialCategory 树本就是平行复制，非泛型共享）。
- 「货品资料 / 模具资料 同级」体现在**前端「基础资料」hub**（`/basicinfo`），不在 DB 层。

## 二、新库表设计

### 2.1 `mould_categories`（分类树，Flyway `V33__material_category` 的同构副本）

与 `material_categories`(V31) 字段逐一相同：`id(UUID PK) · legacy_id(INT UNIQUE) · code · name · parent_id(自引用 FK) · level(INT 真实深度) · sort_order · path(触发器维护) · 审计4列 · is_deleted · deleted_at`。

- `path` 由触发器 `trg_mouldcat_path`（函数 `fn_mouldcat_path`，逻辑同 `fn_matcat_path`）维护：`path = 父path || code || '/'`。
- `code` 无 UNIQUE（118/Q120 重复），定位用 `id`/`legacy_id`。**2026-08-01 起 `code` 改自动生成**：留空 → `MF` 前缀原子取号（如 `MF000001`），非空 → 查重 409；历史重复码不拦截（应用层校验、无 DB 唯一索引），由 `MasterCodeService.nextCode(MasterCodePrefix.MOULD_CATEGORY)` 生成。
- 数据形状：**65 个扁平根（level 0）**，无嵌套。

### 2.2 `moulds`（主档，Flyway `V34__mould`）

逐字段照搬老库 `B_Mould`（12 字段），起清晰列名（老库字段名有误导，见 [04](04-模具资料-老库溯源.md) §2.2）：

```
id(UUID PK) · legacy_id(INT UNIQUE=B_Mould.ID) · category_id(→mould_categories)
name(MouldName) · code(Number 模具编号) · mnumber(Mnumber 备用编号)
qty(QTY varchar 如 1+1) · tqty(TQTY 总数量)
mstatus(MStatus 制造年月) · status([Status] 使用/禁用) · place(Place 车间) · keeper(summary 保管人) · remark(Remark)
审计4列 · is_deleted · deleted_at
department_id(→departments 车间, V180) · keeper_id(→employees 保管人, V180)   ← 对齐生产计划单「id+文本名双列」，跨模块不建 FK，place/keeper 文本保留作 fallback
```

- `category_id` 由 `B_Mould.ParentID → SystemItem.ItemID`(ItemclassID=18) 反查得到；**19 条 ParentID 悬空 → NULL**。
- 索引：`category_id` / `legacy_id` / `code` / `status`。

## 五、老库迁移代码（两条路径，与货品一致）

| 路径 | 用途 | 文件 |
|---|---|---|
| **Shell（主，离线灌数）** | 分类 + 主档，不依赖 server | `server/legacy_migration/migrate_mould.sql`、`migrate_mould_data.sql`；分类和主档分别单独执行 `migrate.sh --mould`、`migrate.sh --mould-data` |
| **Java（增量/运行时）** | 分类，超管端点触发 | `com.uten.imp.legacy.migration.MouldCategoryMigrator`（ItemclassID=18） |
| **数据导出** | 老库 → UTF-8 CSV | `server/legacy_migration/export_legacy.ps1 MouldCategory/MouldData` |

### 5.1 设计要点

- **扁平根入库**：65 个 ItemclassID=18 全是 `ParentID=0`，直接 level 0（无 wrapper 分组）。保留递归 depth + 孤儿兜底以兼容将来老库加嵌套。
- **幂等 + 增量**：按 `legacy_id` upsert，可反复重跑；Java/shell 两条路径产出形状一致（扁平根，`legacy_id=-1` 孤儿根），互不破坏。
- **清表注意 FK**：`moulds.category_id` 引用 `mould_categories`，故分类迁移 `TRUNCATE moulds, mould_categories`（两表同清；重载分类会让分类 UUID 变化，需重跑主档）。**不依赖 `session_replication_role`**——实测它绕不过 TRUNCATE 的 FK 检查（这个坑也修了货品的 `migrate_goods.sql`）。
- **19 条悬空**：`B_Mould.ParentID` 指向已删分类 → `category_id` NULL（前端「全部模具」可见，多为 Q5 等「封存」系列）。
- **GBK**：老库 `Chinese_PRC_CI_AS`，导出走 PowerShell + .NET SqlClient 原生解码（sqlcmd `-f 65001` 会乱码）。

### 5.2 配置（`application*.yml`，同货品）

```yaml
app:
  legacy:
    enabled: ${UTEN_LEGACY_ENABLED:false}
    datasource-url: ${UTEN_LEGACY_DB_URL:jdbc:sqlserver://(localdb)\MSSQLLocalDB;databaseName=YTDQ_2023;encrypt=false}
    datasource-username: ${UTEN_LEGACY_DB_USER:}
    datasource-password: ${UTEN_LEGACY_DB_PASSWORD:}
```

## 六、如何触发迁移

### 方式 A：Shell 一键（推荐，离线灌数）

```bash
# 前提：server 至少启动过一次（Flyway 已建 V33/V34 表）；老库 CSV 已由 export_legacy.ps1 导出
bash server/legacy_migration/migrate.sh --bootstrap-all --confirm-destructive  # 完整破坏性引导
bash server/legacy_migration/migrate.sh --mould --confirm-destructive          # 仅模具分类
bash server/legacy_migration/migrate.sh --mould-data --confirm-destructive     # 仅模具主档
```

### 方式 B：Java 端点（增量，超管）

```bash
# dev 读 classpath 离线 CSV（resources/legacy-migration/mould_categories.csv）；
# prod 连真实老库（需 UTEN_LEGACY_ENABLED=true）
curl -X POST http://localhost:8080/api/admin/legacy-migration/mould-category \
  -H "Authorization: Bearer <超管token>"
# → {"total":65,"inserted":65,"updated":0,"orphans":0}
```

### 增量同步（老库新增了系列/模具）

Shell 路径：**再跑一次**同一命令（幂等）。Java 路径：再调一次端点。

## 七、迁移校验（实测，2026-07-24）

```sql
-- 分类总数（=65）+ 根数（=65）+ 最大深度（=0）
SELECT count(*), count(*) FILTER (WHERE parent_id IS NULL), COALESCE(MAX(level),0)
FROM mould_categories;

-- 主档对账
SELECT count(*) AS total,
       count(category_id) AS linked,                          -- 1586
       count(*) FILTER (WHERE category_id IS NULL) AS dangling, -- 19
       count(*) FILTER (WHERE status = '使用') AS in_use,       -- 1246
       count(*) FILTER (WHERE status = '禁用') AS disabled      -- 359
FROM moulds;

-- 轨道模具分类（与货品轨道分类对应）
SELECT legacy_id, code, name, path FROM mould_categories WHERE code IN ('GD','GD1');
-- 3065 | GD  | 轨道   | /GD/
-- 2605 | GD1 | 轨道3.0 | /GD1/

-- 抽验模具→分类挂载
SELECT m.code, m.name, m.status, c.code AS series FROM moulds m
JOIN mould_categories c ON c.id=m.category_id WHERE c.code='C20' ORDER BY m.code LIMIT 3;
```

**历史演练结果**：分类 65/根 65/深 0；模具 1605（已挂 1586 / 悬空 19 / 在用 1246 / 禁用 359）。`--bootstrap-all` 可在可清空演练库重跑，不代表切流后可增量同步。

## 八、前端（与货品资料同级）

- `/basicinfo` → **基础资料 hub**（`BasicDataHubPage`）：货品资料 / 模具资料 卡片入口。
- `/basicinfo/goods` → 货品资料页（`ProductCategoryPage`，原 `/basicinfo` 改为 hub 后迁此）。
- `/basicinfo/mould` → **模具资料页**（`MouldCategoryPage`）：左分类树 + 右分类详情 + 该系列下模具分页 + 模具详情弹框（编号/名称/状态/车间/保管人/制造年月/数量/备注）。复用 `UtenCategoryTreeView` / `CategoryEditDialog` / `ProductCategoryNode` 模型（分类节点形状一致）。
- **新增/编辑分类对话框**：复用 `CategoryEditDialog`，使用共享 **`UtenLocationField`**（「上级分类」卡片 + 响应式抽屉 + 暂存勾选 + 取消/确定，与货品/部门一致，见 [../02-组件库/UtenLocationField.md](../02-组件库/UtenLocationField.md)）。level 由父级推导（根=L0，子=父+1）；编辑支持重命名+移动，后端 `MouldCategoryService` 仅在父级真实变化时加锁并递归同步子树 level/path。
- 状态徽标：使用=绿、禁用=灰。
- 工作台「基础资料」卡片仍指向 `/basicinfo`（hub）。
- **主档维护（mould:edit）**：详情弹框带「编辑/删除」按钮；分类详情面板「新增子分类」旁有「添加模具」按钮，弹出通用 `MasterEditDialog` 表单（字段对齐 `MouldSaveRequest`），提交后调 POST/PUT/DELETE 并刷新分页。
- **子页返回**：返回键显式回基础资料 hub（非工作台），同客户/供应商页（见 [07](07-客户资料-新库与迁移.md) §八）。
