# 全平台整改 编排方法、铁律与验收

> 这份文档讲"怎么干": 工作区隔离、给实现者(人或 AI 代理)的铁律、合并与迁移头同步、验收命令、踩过的坑。
> 第一阶段就是按这里的方法做的, 后续每一波照做即可。

## 一、总体方法: 审计 → 分波 → 每个工作流"实现→对抗评审→修复" → 主线程合并验收

1. 审计先行: 13 个只读维度找根因(证据到 文件:行号 / SQL 实测), 完整性评审补缺口, 结果在 `02-审计发现全集.md`。
2. 按"文件边界"把发现归成工作流(同一根因的重复发现合成一项, 见 02 文档末尾 critic 的去重清单), 同一波的工作流文件尽量不重叠, 可并行。
3. 每个工作流在自己的 git worktree 里做, 三步: 实现 → 对抗式评审(多镜头挑错, 默认怀疑, 亲自跑测试) → 修复 blocker/major。第一阶段评审在每个工作流里都抓到了真问题(例如偏好互相覆盖的 blocker、匿名 401 换路径绕过节流、运行账号可提前删审计), 这一步不能省。
4. 主线程(负责人)逐个提交、合并到集成分支、解决冲突、统一改迁移头同步点、跑全量验收, 全绿后才开下一波。
5. 性能改动必须用"语句预算"真库测试证明(ProductionJdbcMeasurement, 见第六节), 不接受推断。

## 二、工作区与数据库隔离

- 集成分支: `wf/platform-overhaul-20260922`, worktree `D:/Projects/uten_imp/.claude/worktrees/overhaul`。第一阶段完成后已合并进 main(见 01 文档), 下一波从 main 新开集成分支即可(建议 `wf/platform-overhaul-wave2`)。
- 每个工作流: `git worktree add -b ov/<key> .claude/worktrees/ov-<key> <集成分支>`, 再 `cp server/.env .claude/worktrees/ov-<key>/server/.env`。
- 克隆库: `uten_imp_overhaul`(dev 库副本, 已跑到第一阶段迁移头)。需要真实数据复现时用它, 不要写主 dev 库 `uten_imp`。新克隆: `docker exec uten-imp-postgres psql -U uten -d postgres -c "CREATE DATABASE x"` 再 `docker exec uten-imp-postgres sh -c "pg_dump -U uten -d uten_imp | psql -q -U uten -d x"`(TEMPLATE 方式会因活动连接失败)。
- 自己的后端实例用 8081: `cd server && mvn -o -q spring-boot:run -Dspring-boot.run.arguments="--server.port=8081 --spring.datasource.url=jdbc:postgresql://localhost:5433/uten_imp_overhaul --uten.audit.retention.enabled=false"`; 8080 留给用户自己的实例。免登录调 API: 用 server/.env 的 UTEN_JWT_SECRET 自签 staff token(issuer 默认 uten-imp-dev; claims: sub=userId, typ=staff, av=users.auth_version, ae=authorization_state.epoch; 本机时钟偏移大, exp 取 now+16h 以上)。
- 所有日志/临时文件写到仓库外或 `.local-tmp/overhaul/<key>/`(已在 .gitignore), 不要写进仓库根目录(第一阶段从仓库里清出了 27GB 这类垃圾, 已移到 `D:/uten_cleanup_quarantine_20260923`)。

## 三、给实现者的铁律(原样放进任务说明)

- git: 只允许 status/diff/log/show; 禁止 add/commit/stash/checkout/restore/reset/branch/merge/rebase/clean(提交由负责人做; stash 栈是所有 worktree 共享的, 乱用会弄丢别人的改动)。
- 构建测试只在自己 worktree: `cd <wt>/server && mvn -o -q compile test-compile`; 真库测试 `UTEN_RUN_DB_TESTS=true mvn -o test -Dtest=...`(Testcontainers, 每次全新库跑全部迁移约 30-50 秒); 前端先 `flutter pub get` 再 `flutter analyze` / `flutter test <文件>`。不要连接或写 uten_imp。
- 迁移: 只用分配的版本号; 迁移自包含; 已存在的旧迁移文件一个字都不能改(checksum); 迁移头同步点不改(负责人合并时统一改), 所以那几个测试在分支上红是预期的; 新建/删除表要同步 `server/ops/reset_business_data.sql` 表分类清单与数据库孪生函数 business_data_reset 的表清单、审计三清单(AuditTriggerCoverageMigrationContractTest)、主档引用目录(MasterReferenceCatalog, 若表引用主档)。
- 口径: 平台未上线, 不做存量兼容, 被取代的旧路径直接删; 根治不打补丁; 业务数只在服务端算一次; 性能优化只能去掉重复/无效工作, 绝不能去掉必要校验或改变业务口径; 安全第一(SQL 参数化+白名单, 敏感操作独立权限点, 输入当数据)。
- 新增内容括号一律 ASCII 半角 `()`; 面向人的文案用中文大白话, 不出现代号/表名/类名; 注释风格与周边一致。
- 每项改动都要有测试(优先真库+语句预算); 改旧契约测试断言要逐条写理由; 同步文档与 ADR。
- 结束前: server `mvn -o -q compile test-compile` 通过; 相关测试全绿; 前端 `flutter analyze` 0 问题、`dart format --output=none --set-exit-if-changed lib test` 通过。
- `flutter pub get` 会改 linux/ macos/ windows/ 下 7 个生成的插件注册文件(只有换行), 提交前 `git checkout -- linux macos windows` 丢弃。

## 四、合并与迁移头同步(负责人)

1. 在工作流 worktree: `git checkout -- linux macos windows`; `git status` 检查有无杂散文件(第一阶段出现过代理误建的奇怪文件名); `git add -A && git commit`(提交说明写清根因与实测)。
2. 在集成 worktree: `git merge --no-ff ov/<key>`; 冲突按"两边意图都保留"解决(第一阶段例: 审计删除 AuditNoisePolicy, 前端性能往里加了路径 → 删除; UserPreferenceController 保留前端删 GET 与审计加注解)。
3. 合并后 `cd server && mvn -o -q compile test-compile` 再提交合并。
4. 一波全部合并后统一改"迁移头同步点"(共 6 处, 漏一处就红):
   - `docs/数据迁移/README.md` 头行"当前正式目录: V头/张数" + 表格补本波各迁移说明行;
   - `server/ops/reset_business_data.sql` 的 `(版本, 张数)` 白名单对 + 异常文案里的"V511至V头完整目录";
   - `server/src/test/java/com/uten/imp/ops/BusinessDataResetSqlContractTest.java` 的头断言, 以及其中 `appTwinFunctionClassifiesExactlyTheOpsScriptTables` 里硬编码的 `(head, count)` 与 "V507/469、V508/470及V511至V<head>完整目录";
   - `server/src/test/java/com/uten/imp/ops/ResetBusinessDataScriptContractTest.java` 的 `currentPolicyClassifiesEveryKnownParentTableAndPreservesEvidence` 里 `.contains("V507/469、V508/470及V511至V<头>完整目录")`;
   - `PreplanFutureTransferForwardMigrationPostgresTest.migrationsExecuted`;
   - `LegacyMigrationSafetyContractTest`(若断言头版本)。
   张数 = 迁移目录里 `V*__*.sql` 的实际文件数(改前先确认 server/target/classes/db/migration 没有孤儿文件, 必要时 mvn clean)。最终以真库为准: 跑 `BusinessDataResetServicePostgresTest` 看它打印的"当前 V%/%"。一起跑: `mvn -o -Dtest='BusinessDataResetSqlContractTest,ResetBusinessDataScriptContractTest,LegacyMigrationSafetyContractTest,PreplanFutureTransferForwardMigrationPostgresTest,BusinessDataResetServicePostgresTest' test`(后两个要 UTEN_RUN_DB_TESTS=true)。
5. 迁移在真实数据上也要跑通: 用 8081 实例指向克隆库启动(Flyway 会把克隆库迁到新头), 看启动日志 "Successfully applied"、再对关键页面接口做冒烟。

## 五、验收命令(与 CI 同款)

- 前端: `dart format --output=none --set-exit-if-changed lib test`; `flutter analyze`; `flutter test`; `node --test web/update_check.test.cjs`。
- **与 CI 同口径的前提**: CI 上没有 `server/.env`, 未设 UTEN_PROFILE 时应用按 prod 启动(fail-closed), prod 口径的配置校验(如内网网段必须显式配置)只在那里暴露。本机跑后端门禁前先把 `server/.env` 挪开, 或在不拷 .env 的隔离 worktree 里跑; 否则 dev profile 会掩盖问题(2026-09-24 v2.0.0 快道 14 个用例就是这样漏到 CI)。
- 后端快道: `cd server && mvn -o verify`(DB 门控测试按设计跳过)。
- 后端全量(权威): `cd server && UTEN_RUN_DB_TESTS=true mvn -o verify`(本机约 1.5-3 小时; 多个套件同时跑会互相拖慢, 并共享 ~/.m2)。
- 全链路: `UTEN_RUN_DB_TESTS=true mvn -o -Dtest=FullChainEndToEndTest test`(约 1-2 分钟起; 单测加 `#方法名`)。
- CI 里 `ServerJarPackagingIT` 需要 `mvn verify` 打包后注入属性, 用 `mvn test` 必失败, 不算回归。
- 基线就存在的失败(第一阶段开始时已存在, 非回归): 前端 `test/core/ui/app_notification_test.dart` 的 "hidden app pauses the countdown but only up to the hold cap"; 后端 `CrossAnalysisReallocationWorkflowContractTest`(源码已改 effectiveReason, 用例仍断言 reason)——第一阶段收尾时会一并修掉并在 01 文档注明。

## 六、性能证明的工具与方法

- `server/src/test/java/com/uten/imp/businesschain/ProductionJdbcMeasurement.java`: 测试里 `@Import(ProductionJdbcMeasurement.Configuration.class)`, `begin()/end()` 包住被测命令, 得到 JDBC 次数、逻辑语句数、按 SQL 指纹的次数与耗时、commit 耗时等。用它写"语句预算"断言(例: WorkshopDirectTransferBatchEndToEndTest 的 APPROVE_STATEMENTS_BUDGET、PrelockStatementBudgetEndToEndTest)。
- 只信语句条数与 SQL 指纹计数; JDBC 耗时受同机并行测试影响大(同一用例两次可差一倍), 不作结论。
- 真实请求耗时看 dev 库 audit_log: `SELECT http_path, percentile_disc(0.5/0.95) WITHIN GROUP (ORDER BY duration_ms) ... WHERE duration_ms IS NOT NULL`(注意第一阶段后成功的 GET 不再写审计, 读路径耗时需看服务器状态页或 Micrometer)。
- 大数据量: `server/legacy_migration/data`(本机主工作区, 约 406MB 老库导出 CSV, 未入库) + `migrate.sh --bootstrap-all` 对演练库; 老库原始输入在 `D:/uten_legacy_inputs`(老库备份、职工信息表、product lists), 脚本通过环境变量 `UTEN_LEGACY_INPUT_DIR` 读取。另有旧演练库 `uten_imp_relation_verify_20260801`(3.5 万货品/1 万订单/56 万流水, 但结构停在 V180, 不能直接用)。

## 七、AI 代理编排要点(若用 Claude Code 的 Workflow 继续)

- 子代理模型: 每个会话开头先"探针": 派 4 个一句话代理(model 分别 'opus'/'fable'/'sonnet'/省略), 谁回 alive 就用谁, 之后所有 agent 显式带 model。第一阶段只有 'opus' 可用。
- 并发: 每波 4 个工作流并行(limited(WS, 4)), 机器 22 核, 再多会被测试拖慢且易撞额度。实现 agent 常跑 2-6 小时(反复跑真库测试), 属正常。
- 额度: 撞"session limit"等重置; 撞模型额度换 model。续跑前先盘点 worktree 里的半成品(`git status`、编译、grep 关键符号), 再在任务说明顶部写"续跑说明: 磁盘已有部分改动, 先核对, 已做跳过"。
- Windows/Git Bash: 超长 heredoc 可能失败, 脚本先 Write 到文件再运行; Python 打印中文要设 `PYTHONIOENCODING=utf-8`, 否则控制台乱码; Workflow 脚本文件不能含 `\r`(控制字符会被拒)。
- 结果读取: Workflow 的 journal.jsonl 里每个 agent 一行 result(JSON), 用小脚本导出为 UTF-8 markdown 再读。

async function limited(items, n, fn) {
  const results = new Array(items.length)
  let next = 0
  async function worker() {
    while (next < items.length) {
      const k = next++
      try { results[k] = await fn(items[k], k) } catch (e) { results[k] = { error: String(e) } }
    }
  }
  await Promise.all(Array.from({ length: Math.min(n, items.length) }, worker))
  return results
}

const out = await limited(WS, 4, async (w) => {
  const impl = await agent(COMMON(w), { label: `impl:${w.key}`, phase: 'Implement', schema: IMPL_SCHEMA, model: 'opus' })
  if (!impl) return { key: w.key, impl: null }
  log(`${w.key}: 实现完成, 进入评审`)
  const review = await agent(reviewPrompt(w, impl), { label: `review:${w.key}`, phase: 'Review', schema: REVIEW_SCHEMA, model: 'opus' })
  const serious = review ? review.issues.filter(i => i.severity !== 'minor') : []
  let final = impl
  if (review && (review.verdict === 'fix_needed' || serious.length)) {
    log(`${w.key}: 评审发现 ${serious.length} 个 blocker/major, 进入修复`)
    const fixed = await agent(fixPrompt(w, impl, review), { label: `fix:${w.key}`, phase: 'Fix', schema: IMPL_SCHEMA, model: 'opus' })
    if (fixed) final = fixed
  }
  return { key: w.key, impl, review, final }
})
return out
