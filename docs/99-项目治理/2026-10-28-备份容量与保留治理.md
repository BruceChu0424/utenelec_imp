# 备份容量与保留治理

## 结论和已完成的生产处置

本次用户要求核对“新一份替换旧一份”、通用材料复用、升级前备份到期，以及其他空闲盘存放。不能把所有副本都归为重复，也不能只靠扩大容量解决清理任务未执行的问题。

已获用户明确批准的唯一生产变更：备份卷 `/dev/ubuntu-vg/uten-backup` 从60GiB在线扩到100GiB，ext4扩展成功。验收时文件系统98.12GiB、可用53.43GiB、使用43%、inode1%；ERP与PostgreSQL仍运行，两仓库备份状态正常。没有删除生产备份、数据库或WAL，没有移动目录、安装清理脚本、修改保留期限或启用云灾备。

## 每类用途、保留和占用

| 类别 | 当前事实 | 占用与控制结论 |
|---|---|---|
| pgBackRest物理备份 | 两仓各15个daily full，约14天恢复窗口；备份覆盖整个PostgreSQL集群 | 每仓压缩备份约7.1GiB、WAL约15.47GiB。WAL是恢复链的一部分，应由pgBackRest配合保留策略过期，不能按文件日期手工删。缩成仅一份会改变历史恢复窗口，本轮未改 |
| 配套恢复集 | `/data/uten-imp-backups/paired`，51套约15.29GiB；14天且至少3套 | 清理实际执行，回执APPLIED/removed0，当前多数仍在窗口。附件副本复用能力已安装；最新4个媒体对象中复用2个，不能称附件每次都完整复制 |
| 通用静态材料 | 配套集中的市场/正式客户端等材料仍有每套复制，最新这部分约293MB | 是后续内容寻址复用候选；应在备份专用、不可变的对象库中按哈希复用，保留catalog、配置和密钥版本。不能直接与在线可变原件硬链接。本轮未实施该去重 |
| 旧源灾备导出 | `/srv/uten-backup/dr-continuous-exports`，42套合计约7.06GiB | 20套有目标回执且超2天，cipher共3,906,396,832 bytes（3.64GiB）；22套未确认/材料不完整，共3,672,617,874 bytes（3.42GiB）。当前最新模式恢复验收未完成，不能据此自动删掉全部旧副本 |
| 升级前备份 | `/srv/uten-backup/pre-activation`，约3.05GiB | 仅按年龄发现5个候选，共185,218,567 bytes（176.64MiB）。现有实际恢复证明属于PAIRED，并没有覆盖这些PREACTIVATION dump；年龄不是删除许可。升级健康不等于旧备份立即全部无用 |
| 演练与旧恢复目录 | rehearsal约6.21GiB，旧恢复材料约1.05GiB | 需要核对恢复索引、绝对路径、历史验收和调查依赖后，才适合归档/迁移或到期清理；未直接删除 |
| 在线演练数据库 | 同一PostgreSQL集群中仍有约5.11GiB演练库，以及隔离历史库 | 物理备份会一起收录。后续可评估迁出经营集群，需先形成独立归档及恢复验证；不能只因当前无连接就DROP |

占用采样时点不同，表中近似量不应与所有目录逐项相加作为单一磁盘精确总量。尤其repo1、paired在机械数据盘，repo2、旧源导出和部分演练在NVMe备份卷。

## 其他磁盘是否更合适

| 存放位置 | 物理关系与余量 | 适用结论 |
|---|---|---|
| `/data` | 两块约2TB机械盘组成RAID1（md0正常[UU]），空闲约1.54TiB | 适合核验后的临时导出、演练归档、备份对象池；repo1本来就在这里 |
| 附件卷 | 空闲约185.5GiB，但与系统、repo2同属约512GB NVMe | 挪到这里主要是配额再分配，不增加独立磁盘副本；不能仅凭盘符判断物理隔离 |
| 当前备份卷 | 已扩至100GiB，仍有约53.43GiB可用 | 保留repo2与机械盘repo1的不同故障域，不建议为了腾空间把两仓合并到同一RAID |

迁移要同步备份配置、systemd `ReadWritePaths`/挂载依赖、恢复索引/路径和回执，复制后核对哈希及权限并验证恢复，再切换并清理旧副本。本轮没有执行迁移，也没有把RAID或双仓等同于异机灾备。

## 已修复的两个本地清理断点

### 源导出保留公共入口

旧导出的清理只在旧archive模式成功后调用；当前改为latest_snapshot后，旧任务停用，新成功路径没有接入源缓存清理，造成历史源导出滞留。

`deploy/dr-backup/continuous_backup.py` 的 `finish_source_export_retention` 现在由archive和snapshot成功路径共用；保留规则仍要求完整匹配的source/target回执、对象/manifest/cipher哈希、实际字节数、两天窗口及目录身份。latest模式只有目标 `cleanupState=COMPLETE`（实际commissioning通过）才允许清理；pending、失败、无回执都保留。此机制只控制源缓存，不改接收端恢复点保留。

独立审查发现两种上传路径的专用锁不能排除同时清理同一目录，已补源namespace内的共同GC锁，覆盖规划和删除；锁忙记录DEFERRED并在下次成功上传重试，不把已成功的新备份误记为异常。snapshot unit只增加既有精确源namespace的写许可，需与代码成套安装。

这些是本地候选，尚未部署；当前42套并未删除。未commissioning时，新代码也会继续保留，不能把7GiB写成已回收空间。

### 升级成功后的过期备份清理

现有updater遇到operations.json后把清理交给存储页，而host worker在stable_health后没有调用自动清理。`deploy/simple/host_operations.py` 现在先耐久保存升级SUCCEEDED/DONE/UP，再在operations锁内取得updater锁，复核当前任务和运行版本，调用 `operations_storage.prune_preactivation_backups`。

公共入口复用已有inventory `canDelete`、preview/delete和耐久回执。最新至少3套、14天、精确实际恢复证明、显式rollback、占用inode、符号链接/跨卷/隔离后身份保护保持原样；每轮最多50项，其余明确deferred。先落cleanup intent，旧intent不自动重放；清理失败单独记录，不把健康升级改为失败。不涉及pgBackRest、paired、业务附件或正式客户端包清理。

本地Linux文件系统测试104项通过，其中新增12项；独立只读复审无新增阻断。尚须在真实update-job unit的受限能力内验收`/proc/*/fd`核对能力，不能为清理放宽sandbox；无法证明安全时应保留并记录失败。

## WAL增长核查边界

归档文件mtime分布显示10月25日至28日约2.3、5.0、6.2、2.0GiB，早前多为每日80–196MiB。现场元数据和已有切换收据确认这段时间有整库导入、复制/迁移及演练库保留；这说明容量不能只按经营库日常增量估计。

但mtime不是精确WAL生成时间，数据库累计统计也不是逐日统计，不能把上述每GiB直接分摊给某项演练、导入或后台任务；本轮不做无证据归因。也没有为了压低占用删除审计、历史、成本数据或更改归档配置。
