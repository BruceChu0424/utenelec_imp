# 业务通知窄动作参与资格修复

基于 `afe6ae810` 的独立修复，不改角色、授权数据、迁移、版本、发布门禁或下一版/WPF 源码。原三个 DB3 失败由组合任务用真实订阅演员复核；不能为让通知通过额外授予 edit/approve 或相信超管目录镜像。

另有两个真实窄动作缺口：`ProcurementFinanceApprovalService.submit` 的委外分支要求 `subcontract_order:submit_finance` 和原单可写范围，canonical 依赖也不要求 `subcontract_order:edit` 或 `subcontract_order:draw`；`MrpController` 的计划包生成入口使用完整码 `production_planning_package:generate` 与可写计划。原通知路由没有这两种组合，因此合法演员被 BOM 阻断后，也收不到原单的 BOM 完善回执。权限码不得省略前缀；`planning_package:generate` 不是目录中的码。

仅在公共 `BusinessNoticeParticipation` 补两项：

- 委外订单：`notice:read + subcontract_order:view + subcontract_order:submit_finance`，与已有采购订单提交资格对称。
- 生产计划：`notice:read + production_plan:view + production_planning_package:generate`，不省略可打开原记录的 VIEW。

原普通路由、registered review/action 事件优先级、对象定向和状态条件不改。不泛化为任意 WRITE；仅 VIEW、缺 notice:read/对应 VIEW/精确动作、无关业务写与公司资料库全写均不能订阅这两个业务回执。新的普通路由资格不能放过财务退回、补料审批等精确事件所需的原动作。

回归入口为 `BusinessNoticeParticipationTest` 与 `BusinessNoticeParticipationPostgresTest`。后者执行现有 V979 原函数，用同一 Java readRules 序列检查授出→撤回→恢复和缺项负例，确保写入资格与数据库列表/计数过滤一致，没有新 DDL 或宽松 baseline。组合还须运行 inventory 的窄演员版本 `SubcontractComponentReturnLegEndToEndTest`、`SubcontractNoBomGateEndToEndTest`，保留完整数量、BOM、等待名单和正负订阅断言。

执行命令：`UTEN_RUN_DB_TESTS=true mvn -o -Dtest=BusinessNoticeParticipationTest,BusinessNoticeParticipationPostgresTest test`。此文记录根因与范围；实际本地及组合结果由对应工作树原始 Maven 日志/回执确认，不把提交源码等同验证通过。
