# ADR-052：关键业务事件强提醒与驳回修订闭环

- **状态**：已接受（源码候选；V406、目标库迁移与真实岗位 UAT 未完成）
- **日期**：2026-08-27
- **影响**：通知、工作台、销售、采购/委外、生产、仓库、财务、人事及其它带明确责任人的审批流程
- **依赖**：[ADR-016 通知模块](ADR-016-通知模块接真后端与瀑布流分栏重写.md)、[ADR-017 可靠异步旁路](ADR-017-模块化单体与异步旁路.md)、[ADR-040 销售财务审核中心](ADR-040-销售开单体验与财务审核中心.md)、[ADR-041 订单进度追踪](ADR-041-快递式全链路进度追踪.md)

## 一、背景

关键业务事件目前虽然会进入通知中心并从顶部滑入，但仍有三类断链：

1. 系统定向通知把展示优先级固定成 `normal`，业务上已经阻断的驳回仍会自动消失；
2. 已读、顶部条播放完成和“员工已手动关闭强提醒”没有分层，无法保证员工离线后登录补显，也无法在换设备后保持一致；
3. 工作台角标部分来自通知未读数，而不是未解决业务状态。销售订单被财务驳回后，通知存在，但销售管理、订单进度查询和订单行都没有形成可处理闭环。

销售订单还存在更直接的矛盾：财务驳回后订单仍为已审核态，普通更新只允许草稿，详情页因此只能改量或取消；文档所说的“驳回→修正→确认”没有真实实现。直接放开已审核订单普通更新又会物理删除订单行，破坏已建立的库存预留和下游引用，不能采用。

## 二、决策

### 2.1 三层事实不得混用

每个接收人分别维护以下事实：

- `read_at`：已经打开通知或办理入口；
- `popup_acknowledged_at`：已经通过“关闭”或主操作显式结束居中强提醒；
- `task_completed_at`：通知型待办已经完成。

关闭强提醒只写 `popup_acknowledged_at`，**不等于已读，更不等于业务完成**。打开通知、全部已读或完成待办是更强动作，可同时结束对应强提醒。三者接口均须按当前用户校验可见性并保持幂等。

`popup_acknowledged_at` 由 V406 前向新增；V1–V405 已应用字节保持不可变，禁止 `flyway repair`。

### 2.2 到达通道为“通知中心 + 顶部条 + 条件式居中强提醒”

所有可见通知仍进入通知中心，并保留顶部滑入提示。只有 `priority=important/urgent` 的**定向、可恢复业务事件**再进入居中强提醒：

- 无自动关闭；
- 点遮罩、系统返回键或 Escape 不能静默消失；
- 一次只展示一条；
- 显示事件标题、单号/正文、责任人或发布人、业务发生时间、原因与恢复动作；
- 次操作“关闭”只确认已看到，主操作关闭后跳真实 `actionRoute`；只有真实业务状态迁移才能清业务角标。

视觉复用 `UtenNotify` / `UtenCenterAlert` 的语义颜色、响应式尺寸、性能档和减弱动效，不在各业务页面散落 `showDialog`。`important` 用琥珀语义，`urgent` 用错误红语义；颜色之外必须同时有图标、级别文字和动作说明。

### 2.3 强提醒只给明确责任人，不给整个广播池

强提醒用于“这个人必须恢复流程”，不是把普通通知放大。允许升级的典型事件：

| 等级 | 事件 | 直接接收人 | 主操作 |
|---|---|---|---|
| L3 | `SALES_ORDER_FINANCE_REJECTED` | 订单归属销售 | 查看并修改订单 |
| L3 | `SALES_SHIPMENT_REJECTED` | 出货/订单明确负责人 | 查看出货驳回 |
| L3 | `PROCUREMENT_FINANCE_REJECTED` | 本次提交人 | 打开采购或委外原单修改重提 |
| L3 | `PRODUCTION_FINISHED_INBOUND_REJECTED/REVERSED` | 报工制单人或已认领负责人 | 查看并纠正生产事实 |
| L2 | `PROCUREMENT_SUPPLIER_RETURN_REQUIRED` | 原下单人/退回任务负责人 | 完成供应商退回 |
| L2 | `SALES_RESERVATION_HOLD_OVERDUE/YIELDED` | 订单归属销售 | 处理发货、让单或交期影响 |
| L2 | 个人资料、报销、工资、资产等“被驳回” | 申请人/制单人/明确负责人 | 返回原业务修正 |

未认领的共享审批池、部门广播、新任务、常规进度和成功回执继续使用顶部条与真实任务角标，不做持久居中弹窗。例如排产、开工、报工、正常完工、正常发货、提交审核、审核通过、待检和生日祝福都不得升级。未来新增强提醒必须同时写清：事件来源、聚合 UUID/幂等键、直接责任人、业务发生时间、解决条件、主操作路由和角标真源。

访客审批是明确例外：申请人属于外部访客账号，HR 批准/驳回和接待人拒绝的结果不能由当前员工在
Flutter 端发布默认全员 Notice。旧 `visitor_notice_bridge.dart` 因存在隐私广播与无权限静默丢失而移除；
员工侧保留本地操作反馈和 HR/接待人真实待办角标，外部结果由访客端/SMS 承载。未来只有“转指定接待人”
这类具备明确内部接收人的事件，才可由服务端 Outbox 生成 normal 定向任务通知。

### 2.4 `source_event` 是事件分类依据，`type` 与 `priority` 各司其职

- `type` 表示通知内容类型（任务、审批、流程、紧急等）；
- `priority` 表示展示强度；
- `source_event` 表示可审计的业务事件类别，用于强提醒策略、未读进度消息和定位测试。

Outbox 处理当前事件时须把事件类型传播到本次生成的定向通知；不能再要求每个分支手工记得补 `source_event`。显式传入的来源优先于当前 Outbox 事件，以支持一个事件生成语义更精确的子通知。

通知里的“几点、由谁、为何”必须读取业务事务已保存的操作者、业务时间和原因快照。`notices.published_at` 只是异步投递时间，不能伪装成审批发生时间。

### 2.5 销售财务驳回采用受控修订，不放开已审核普通编辑

销售订单财务驳回后，订单仍保留本次驳回事实；销售点击“修改订单”进入原编辑页，保存时走受控修订：

1. 悲观锁定订单与有效订单行，确认仍为 `APPROVED + finance_rejected + !finance_confirmed`；
2. 若已有发货/退货/核销、排产/完工、活动计划分摊或仓库作业，失败关闭并给出先撤销下游的明确路径；
3. 对称释放仍生效的订单预留；
4. 请求必须携带既有行 UUID。普通字段原位更新；货品/颜色/单位身份发生变化或行被移除时，旧行软删除并保留其历史引用，新事实新建 UUID；禁止复用草稿更新中的全量物理删除；
5. 保存后回到草稿，保留驳回原因供销售修正期间查看，不自动绕过销售审核；
6. 销售重新审核时重新校验商业事实并建立预留，清除“当前待修正”标志，重新进入财务待确认池并发送新一轮可靠事件。

财务确认与驳回必须使用同一订单行锁，防止并发“确认/驳回”互相覆盖。当前驳回标志可清除，但驳回人、原因和时间不得被当作不存在；订单时间线至少保留最近一次驳回事实，后续多轮审批事件账按正式审计要求继续扩展。

### 2.6 角标使用可处理业务状态，通知未读只补充进度消息

工作台模块角标必须与点击后的可处理页面一致：

- 销售管理和 Sales Hub“订单进度查询”共用同一计数：当前用户范围内 `finance_rejected=true` 的未解决订单数 + 未读的完工进度消息数；
- 订单进度看板增加 `REJECTED` 筛选与行内红色“财务已驳回”状态，显示原因，不再把它误写成“等待财务审核”；
- 打开订单进度页只清完工进度未读，不清未解决驳回；驳回角标仅在受控修订并重新提交后消失；
- 财务角标只数仍在财务可办池的待确认订单。财务驳回后任务转移到销售，销售重提后再转回财务。

采购、委外、仓库、品质和生产继续优先读取各自任务表/工作台投影，不用通知条数冒充业务待办。找不到真实任务真源时，先保持无角标并记录缺口，不允许用相邻模块的中间状态凑数字。

## 三、安全、并发与恢复边界

- 通知可见性、弹窗回执和角标查询都必须按当前账号、权限与对象归属过滤；前端隐藏不是授权边界。
- Outbox 重放不能为同一事件和同一接收人生成重复提醒；同一订单修正后再次被驳回属于新一轮事件，必须再次提醒。
- 业务在员工上线前已经解决时，不能继续用旧强提醒要求其处理；事件策略须有可验证的解决条件。当前销售角标直接读订单状态，天然满足该条件。
- V406 只增加可空回执列，不回填“已确认关闭”的历史事实；历史未读重要通知首次升级后可能补显一次，用户显式关闭后稳定收敛。
- 本 ADR 是源码候选，不代表目标数据库已迁移、服务器已安装、真实岗位已验收或生产可放行。

## 四、验证要求

最低回归必须覆盖：

1. 未登录时发生强提醒，登录后可补显；手动关闭后重启/换设备不重复；关闭不改变通知未读与业务角标；
2. 遮罩、系统返回键和自动计时不能关闭居中强提醒；主操作先安全关闭再走深链，失权时回退通知详情；
3. Outbox 驳回通知带 `source_event`、业务操作者/时间/原因，普通进度仍为顶部条；
4. 销售财务驳回→两处角标+看板行状态→受控修改回草稿→重新审核→财务待办恢复→确认；
5. 受控修订遇到发货、排产、完工、活动计划分摊或并发确认/驳回时失败关闭；
6. 375dp、小/大字号、深浅色、键盘焦点和减弱动效下弹窗仍可读可操作；
7. `git diff --check`、聚焦 Flutter/Java 测试、空库迁移和非空升级演练分别记录，任何一项不能替代真实岗位 UAT。
