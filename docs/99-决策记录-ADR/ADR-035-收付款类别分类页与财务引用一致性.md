# ADR-035：收付款类别分类页与财务引用一致性

- 状态：已接受；V265/V267/V273/V277/V278 仍为共享工作树源码候选，目标库迁移和财务岗位 UAT 待验收
- 日期：2026-08-14
- 范围：基础资料“收付款类别”、费用/收入/收款/报销、账户、总账、固定资产与长期待摊

## 背景

`payment_styles` 是按 `category` 分组的纯分类树，没有“分类下主档表”。原页面仍套用
“分类头 + 下方主档表”的通用详情卡，导致大屏右侧只剩一张居中的孤立卡；窄屏又没有完整的
目录切换入口。另一方面，财务单据和资产子账会直接引用树的叶子节点，总账报表还会按当前
物化路径聚合。若类别移动、停用或从叶子变为目录与业务写入并发，单靠先查后写会产生历史
归类漂移或不可过账引用。

## 决策

### 1. 页面采用专用分类工作区

- 960dp 及以上使用可拖动“类别目录 + 页面级属性检查器”，右侧分基本信息、业务属性、
  层级关系、直接子类别、迁移溯源和保留策略；不修改全局 `MasterDetailCard` 来迁就本页。
- 960dp 以下把完整目录放入 `endDrawer`，选中节点后回到全宽详情。目录始终支持六大类切换、
  名称/编号搜索、局部加载与失败重试。
- 编号服务端生成；排序遵守 `sort_order`。位置选择排除自身、后代、跨大类和禁用节点。
  更新请求只发送真正变化的字段；移动到顶级使用显式 `moveToRoot`，状态快捷操作只发送
  `status`，避免旧详情快照覆盖其他用户的并发修改。

### 2. 财务类别只停用、不删除

- DELETE 端点仅为兼容保留，任何已存在类别都固定拒绝删除并提示改为停用。
- 历史引用、审计链和旧单据名称解析永久保留；新业务选择器只返回“未软删、使用中、对应
  大类、无任何未软删子类别”的叶子节点。
- `auto_created` 只表示迁移或运行时补录，不自动等同系统科目。真正的系统身份由运行时固定
  路径及保留名称确定；这些节点禁止危险移动、改关键名称或停用。

### 3. 层级与引用共用一把事务锁

- 统一锁为 PostgreSQL transaction advisory lock：
  `pg_advisory_xact_lock(hashtextextended('PAYMENT_STYLE_HIERARCHY',0))`。
- 锁顺序固定为“收付款类别层级锁 → 期间/单据/资产对象行锁”。类别维护、费用收入、收款其它
  费用、报销付款、账户类别映射、总账生成、资产政策/快照/账簿/摊销版本/过账行均遵守该顺序。
- 类别移动在锁内按 `parent_id` 用递归 CTE 一次性重建整棵子树的 `level/path`；父子必须同大类，
  成环、禁用祖先、活动后代、历史引用子树和被引用叶转目录均失败关闭。

### 4. V265/V267/V277/V278 是数据库最终防线

- `V265__payment_style_reference_guards.sql` 为当时已有的全部真实 UUID 引用及
  `accounts.style_legacy_id` 安装立即执行的 BEFORE 触发器；V267 新增 `accounts.style_id` UUID
  真源后，保留 V265 的 legacy 兼容影子守卫，并为 UUID 列安装独立守卫。新引用先取得同一层级锁，再校验存在性、
  大类、启用状态和叶子语义，因此原生 SQL、批处理或未来遗漏的服务入口也不能绕过。
- “叶子”统一定义为不存在任何 `is_deleted=false` 的直接子类别，不因子类别已禁用而重新变成
  可过账叶子。
- 总账分录和资产反向过账允许复用后来被停用的历史类别，因此这类冻结事实只校验引用存在并
  参与互斥，不强制当前启用；新费用、收入、账户和政策配置仍必须引用使用中的正确大类叶子。
- 资产政策从 DRAFT 变为 ACTIVE 时，即使四个类别 ID 没有变化，也强制在同一锁内重新校验。
- V267 保留 V265 对 `accounts.style_legacy_id` 兼容影子的守卫，同时为 UUID 真源
  `accounts.style_id` 安装独立守卫；旧库重跑会先清空 `payment_styles.linked_account_id` 反向关联，
  再以受外键约束的 `DELETE` 重建账户，遗漏依赖时整次迁移失败关闭。
- V267 对全部历史/停用账户也回填 UUID 映射并校验身份一致；对“使用中且未删除”账户额外要求
  所指类别同样使用中且为叶子。账户重新启用、账户映射变化、类别停用/软删都会在层级锁内重验，阻断与活动账户绑定并发穿透。
- V277 以前向迁移移除账户 legacy 运行时守卫并安装 UUID 真源一致性触发器：活动账户必须持久化
  `style_id`，`style_legacy_id` 只能由该 UUID 的 `legacy_id` 派生；`payment_styles.linked_account_id`
  同理是唯一关系真源。UUID 与影子冲突、legacy-only 写入以及活动账户空 UUID 均失败关闭。
- 历史活动账户仍为空 UUID 时，V277 只在升级事务按既有明确规则执行一次：CASH 对应唯一启用
  ACCOUNT 叶 `/101/`，其余对应 `/102/`。零命中、多命中、停用、非 ACCOUNT 或非叶都中止迁移；
  `account_style_id()` 升级后只返回已持久化 `accounts.style_id`，不保留路径、类型或 legacy 兜底。
- V278 建立 `system_posting_style_roles` 的 7 个固定过账角色。迁移期仅在审核过的路径/名称对正确
  大类恰好唯一命中时写入 `style_id`；零命中或多命中保持空映射，实际过账失败关闭。运行时
  `GlPostingService` 只调用 `system_posting_style_id(roleKey)`，不再用科目路径、名称或查询第一条
  选择过账科目。
- 角色键和要求大类不可更改，角色不可删除；映射 UUID 必须指向使用中、未删除且大类匹配的
  `payment_styles`，且同一个科目 UUID 不能同时承担两个系统角色。被系统角色引用的科目不可停用、软删、改大类或物理删除，所有变更继续取得
  `PAYMENT_STYLE_HIERARCHY` 锁并进入审计。报表按树路径汇总属于分类口径，不等于过账关系回退。

### 5. 旧库迁移没有永久旁路

`migrate_finance.sql` 因历史顺序先导入 accounts、后导入 payment_styles，只在该单次事务设置
`uten.payment_style_reference_import=legacy-finance-v1`。触发器仍取得层级锁，只暂时放宽运行时
启用/叶子检查；提交前脚本必须逐表核对映射存在且大类正确，任何差异回滚整次迁移。应用运行时
不设置该模式。

### 6. `payment_styles` 不承接结账条件或收付款方式

- `payment_styles` 只表达 M_Style 财务分类树及其费用、收入、账户、总账和资产引用。
- V273 源码候选把老库 `B_PStyle` 独立迁到 `settlement_methods`，供销售、采购、委外和 AR/AP
  的结账条件以 UUID 引用；把独立 `RecStyle` 迁到 `finance_payment_methods`，供收款、付款、费用和
  其它收入的方式字段以 UUID 引用。两套字典互不合并，也都不接到 `payment_styles(category='METHOD')`。
- 普通在线写入只接受对应主档 UUID。旧整数只在受控导入与历史快照中保留；未从真实 RecStyle
  字典确认名称的占位行不得进入正常选择器或在线新写，禁止按名称、数字相等或 UUID 类型相同猜接。

## 不采用的方案

- 不把通用 `MasterDetailCard` 全局改成适合纯分类页，以免破坏货品、客户、供应商和模具页的
  “上下文头 + 主档表”结构。
- 不只使用 Java `COUNT` 预检查；它无法阻止检查后、提交前的并发引用写入，也覆盖不了原生 SQL。
- 不把 `METHOD` 强接到当前收/付款方式字段。V273 已为已核清的 RecStyle 语义建立独立
  `finance_payment_methods` UUID 主档；`METHOD` 仍只是 payment_styles 的预留分类，禁止按名称、
  旧整数或 UUID 类型相似度猜接。

## 发布与验收边界

- 源码、Flutter/Java 定向测试和 disposable PostgreSQL 测试只证明候选实现；不代表
  V265/V267/V277/V278 已应用到仍为 V238 既有口径的公司目标库。
- V272/253 冻结快照的后端 13 类组合定向证据为 68/68：非 Docker 测试 11 类 59/59，
  PostgreSQL 重点测试 9/9（`PaymentStyleHierarchyConcurrencyPostgresTest` 7/7、
  `AccountPaymentStyleUuidPostgresTest` 2/2）。这些是较早冻结字节的历史证据；V273–V278 当前候选的
  最终验证结果以同一冻结字节的本轮交付记录为准，本 ADR 不预写尚未完成的数字。上述都不是全量
  仓库测试、公司目标库迁移或 UAT。
- 目标环境必须从可恢复副本执行 Flyway validate/migrate，核对触发器矩阵、历史引用大类、路径、
  总账余额和资产政策，并完成财务多账号并发 UAT、备份恢复演练与发布签字。已应用迁移不可修改，
  后续修正只能追加更高版本。
