# 产品目录 V2：系列、产品与款式的统一规则

本文档是官网前台、Next 管理后台、旧站导入工具以及未来公司平台 CMS API 的共同业务约定。任何一端都不得单独改变这些含义。

## 1. 为什么重构

旧站把“设计系列”和“功能分类”都存成了分类节点。导入后，这些节点又被统一映射为 `Series`，于是公开页面把 60 个诸如开关、插座、功能件的叶子节点平铺成了“系列”，同时把 1122 个旧页面各合成一个款式。这不符合客户查找产品的方式，也会把占位数据误解为真实 SKU、颜色或型号。

当前来源数据能够可靠证明的事实是：

- 旧站中英文记录按旧站产品 ID 合并后共有 1122 个正式产品条目；
- 每条导入产品只有一个系统合成的基础款式，不能当作真实颜色或 SKU；
- 型号、尺寸、颜色、材质、认证和结构化规格普遍缺失；
- 一个旧站产品页可能包含多个真实型号，同一型号也可能出现在不同外形或宽度的页面中；
- 名称相同、型号相同或图片相似都不是安全的自动合并依据。

因此，页面可以改善导航与视觉，但不得为了“完整”而生成产品事实。

## 2. 对外目录层级

公开目录统一使用以下层级：

1. `FAMILY`：设计系列，例如 S300、Z9、Q7、V1.2；是产品中心的一级入口。
2. `COLLECTION`：系列内的历史功能集合，例如大跷板开关、电子开关插座、功能件；用于辅助分组，不单独冒充设计系列。
3. `Product`：一个可展示的功能产品或旧站 offering，例如单联开关、USB 插座、插卡取电。
4. `ProductVariant`：经过确认的具体 SKU、颜色、材质或表面款式。

`CONTAINER` 只用于保存来源层级，例如旧站“Export products”容器；`ARCHIVE` 保存不对外的人工样例或重复种子数据；两者不得进入公开系列导航。

产品功能采用受控词表：开关、强电插座、USB 充电、弱电/影音数据、智能控制、酒店功能、配件及其他。联数、控制方式和配置是产品属性，不是系列。

## 3. 页面与 URL

- `/[locale]/products`：只展示真实设计系列卡片。卡片优先使用后台维护的系列效果图；缺图时由本系列真实产品图组成准确的拼图，不生成虚构产品。
- `/[locale]/products/[familySlug]`：系列展厅。展示系列视觉、系列内功能分组、联数筛选和产品矩阵。
- `/[locale]/products/[familySlug]/[productSlug]`：产品详情。显示系列、功能、型号（存在时）、真实款式、图库、已确认规格和询盘入口。

公开 URL 使用 `Series.publicSlug`，不再暴露 `legacy-v2-*`。旧链接必须永久重定向到新系列 URL；`sourceIdentity`、`legacyId` 和旧 code 保留用于追溯，不能因改 URL 而重写。

筛选状态应写入 URL 查询参数，便于刷新、分享和返回。颜色或款式选择使用 `variant` 查询参数，canonical URL 忽略该参数。

## 4. 数据可信度

`classificationStatus` 与款式 `dataStatus` 使用三种状态：

- `VERIFIED`：人工根据公司主数据或原始资料确认；可作为正式筛选和规格展示。
- `INFERRED`：系统从旧名称生成的候选；可用于改善导航，但页面必须避免把它写成工程承诺。
- `NEEDS_REVIEW`：缺失、冲突或无法安全判断。

旧站导入器生成的单一基础款式必须标记 `legacySynthetic=true`。它可以承载原始产品图用于展示，但不得填写或展示成真实 SKU，不得标为 `VERIFIED`，也不得自动生成颜色笛卡尔组合。

中英文只按旧站 ID 合并。跨系列同名功能可以共享功能词表，但 S300 的“一开”和 Z9 的“一开”仍是不同系列产品。媒体文件可以按 SHA-256 物理去重，同时必须保留所有来源 URL、语言、角色和归属关系。

## 5. 后台编辑与发布

系列后台需要维护：公开 slug、目录角色、父级、名称/说明、封面、系列效果图/组合图及发布状态。

产品后台需要维护：所属系列/集合、功能类型、联数、控制方式、配置、型号、规格、图库、款式以及分类审核状态。款式需要维护真实 SKU、颜色/材质、色卡、正视图、尺寸、默认款式和数据状态。

发布守卫：

- 对外产品必须属于已发布系列，并至少有一个已发布且有图片的默认款式；
- 场景试装必须指向已发布、有正视图的具体款式；
- 已发布产品或系列不能直接硬删除，应先下架并处理引用；
- 系列和产品保存使用 `rowVersion` 乐观锁，避免两个编辑人员静默覆盖；
- 修改中英文时必须合并原 JSON，保留其他语言；缺英文保持缺失，不能复制中文伪装翻译。

当前 Next 管理后台是过渡实现。正式接入公司平台后，界面可以做到无需二次登录，但必须复用平台 SSO 会话和服务端权限校验，不能变成匿名后台。建议权限至少拆分为查看、产品编辑、内容编辑、媒体上传、发布、询盘查看/处理和站点设置。

## 6. 迁移与审计

目录规范化工具默认只生成 dry-run 计划。Apply 必须满足：

1. 显式指定 SQLite 文件和确认环境变量；
2. 先生成可恢复备份；
3. 在单一事务内执行并用 `rowVersion` 检测并发修改；
4. 重跑后无重复变更；
5. 执行前后 Series、Product、ProductVariant 数量不变；
6. 所有 `sourceIdentity`、产品 `seriesId` 和媒体来源关系不变；
7. 不合并、不删除、不创建 SKU，不自动写入颜色、尺寸、认证或电气规格。

只读目录审计用于检查字段完整度、公开发布边界和“同名/同型号/同图”复核候选。候选始终输出 `needs review`，不能由审计脚本写数据库。

## 7. 云服务器与公司平台边界

单台云服务器预览可继续使用固定持久盘上的 SQLite 和上传目录，但数据库、上传目录、备份都不能放进每次替换的版本目录。多实例、Serverless 或公司平台统一管理上线前，应把内容迁移到 PostgreSQL、媒体迁移到对象存储，并使用共享限流与缓存失效机制。

浏览器只能调用经过 HTTPS 鉴权的 CMS API，不能直连数据库、SSH 或服务器目录。公司平台应成为身份和权限权威；公开 Next 站只读取已发布内容。编辑、发布、媒体上传、询盘隐私查看都要记录真实操作人、目标、前后差异、请求 ID、时间和结果，并支持版本回滚。

本地迁移、自动化测试和构建成功只证明代码与副本数据可运行，不等于生产批准。正式部署仍需目标数据库备份/恢复演练、权限验收、内容复核、移动端验收和回滚验证。
