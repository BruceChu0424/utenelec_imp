# 人事端代码总结

> 当前基线：2026-08-27（同步本人对象级资料、未开户权限交互与细分员工动作权限）
> 本文描述当前工作树，不保留早期“仅 HR 是真实后端、其余全是 Mock”的历史口径。

## 一、模块边界

人事端已使用 Flutter + Riverpod + Dio 调用 Spring Boot/PostgreSQL 真实后端，覆盖：

- 员工列表、详情、入职、编辑、调岗、转正、离职、复职和删除保护；
- 部门树、岗位目录、入职可搜索/自定义岗位和管理中心用人；
- 员工证书、学历、合同、紧急联系人和任职历史；
- 个人信息修改申请、HR 审批和申请人定向通知；
- `GET /api/profile/me` 本人对象级档案、完整字段分组与直接修改/需审核/人事维护提示；
- 账号状态展示，以及账号锁定、启用、停用和临时密码重置入口；
- 按权限点控制的 PII、银行卡和薪酬脱敏；
- 公司/部门人员概况、近 12 个月流动、合同/试用期提醒及历史覆盖质量；
- 部门负责人选择/清空与调岗、离职联动，领导标识和数据库分页前优先排序；
- 部门与个人权限深链，以及高密度权限目录的搜索、折叠、筛选和局部重试。

员工前端使用 `DioEmployeeRepository`。旧 `MockEmployeeRepository`、旧 employee model 和旧
Provider 已删除，禁止恢复 Mock/真实双轨。工资条与员工报销是独立领域，状态见
[新库上线与首装操作指引](../99-项目治理/2026-09-01-新库上线与首装操作指引.md)，不能用人事模块完成来替代其验收。

## 二、入职与账号安全

`POST /api/org/employees` 由 `employee:create` 保护，在同一服务端事务中创建员工资料、任职资料和
登录账号，返回：

```json
{
  "employee": {},
  "temporaryPassword": "仅本次响应可见（=证件号后6位）",
  "loginAccount": "登录账号（默认=手机号）"
}
```

- 登录账号默认使用手机号（手机号须唯一）；系统不开放自助注册。工号（`employees.code`）只由服务端生成（`UT` + 顺序号），旧客户端传入的工号被忽略；V206 校准序列但不改历史工号。
- 一次性临时密码 = 身份证（证件号）后 6 位；首登强制改密，新密码走 `PasswordPolicy` 复杂度。
  账号重置等其他流程仍由 `TemporaryPasswordGenerator` 生成 20 位高熵密码（大写/小写/数字/符号）。
- 服务端只持久化 Argon2id 哈希，并设置首登强制改密；临时密码不得进入数据库、日志或审计正文。
- Flutter 用不可点遮罩关闭、不可返回键误关的一次性弹窗显示和复制凭据；关闭后不缓存。
- 若交付丢失，只能重新执行受 `account:support` 保护且有审计的密码重置，不能再次读取原密码。
- 存量员工补开户同样要求 `account:support`。工作台账号支持候选和业务页权限工作台均明确显示
  未开户；凭据确认保存并关闭后才刷新账号状态/加载权限。负责人身份和
  `authorization:manage` 不自动产生开户权；开户端点当前也不按负责人子树收窄。

具体交互见[入职流程页](../03-页面/入职流程页.md)。

## 三、认证与权限

- access JWT 源码默认 15 分钟，refresh token 默认 7 天并轮换、哈希入库和检测重用。
- staff access JWT 只含 `sub/typ/av/ae` 与标准时效/签发字段；账号状态、员工绑定、角色和权限由
  服务端逐请求复查/解析。解析数据库或权限依赖失败返回结构化 `503 SERVICE_UNAVAILABLE`，不能
  伪装成 403“无权限”，客户端也不能据此销毁会话。
- access/refresh 与 `generation/intentGeneration/sessionLineage` 作为一个权威 JSON 原子记录存于
  标签页级存储（Web：sessionStorage，各标签页独立会话；原生：`flutter_secure_storage`）；
  认证使用 `Authorization: Bearer`，不是 Cookie 会话。记录损坏时
  fail-closed 写 tombstone，旧双键令牌不能复活；刷新锁只交换互斥元数据，不广播 token（ADR-061）。
- `JwtAuthFilter` 每次 staff 请求用一次轻量数据库投影复查账号状态、强制改密状态、超管状态，
  以及 V135 `auth_version`/全局授权 `epoch`。账号停用、锁定或授权版本不匹配立即 401。
- 有效权限以服务端为准：基础权限、员工所在部门及祖先部门配置、中央个人 grant 与仍有效的负责人
  委派，再减中央个人 revoke；revoke 始终优先。
  前端路由和按钮守卫只改善体验，不构成安全边界。
- 他人档案 PII 和薪酬访问分别由 `employee:pii:view`、`employee:compensation:view` 控制，不按
  前端角色名猜测。`GET /api/profile/me` 是对象限定的本人例外：无目标 ID、未绑定返回 NOT_FOUND，
  本人个人 PII 明文；银行/薪酬仍按独立权限，“我的”页固定不渲染。
- 全局 `/admin/permissions` 是共享壳：`account:support` 可进入账号支持区；中央部门/个人授权和
  数据范围只允许超级管理员且具备 `authorization:manage`。业务页面内“权限设置”还可由
  `departments.manager_id` 对应负责人进入，但只管理负责人根/未删除子树内人员的本页权限，
  后端再次校验负责人关系、本人 ceiling、页面目录与 CAS。
- 员工权限深链通过 `GET /api/admin/users/by-employee/{employeeId}` 精确解析账号，不使用模糊搜索兜底。
- 公司/部门人员概况要求同时具备 `department:view` 与 `employee:view`。
- `users.remote_access` 是员工云端入口授权，默认 `false`，不属于普通权限目录。local 站点在 JWT
  之前按 `UTEN_LOCAL_ALLOWED_CIDRS` 限制全部 `/api/**`（含 login/refresh/visitor）；cloud 站点则在
  员工密码与账号状态校验后的 login、refresh 轮换前及每个已认证 staff 请求三处复核远程授权。
- visitor 是独立公网 OTP 主体，没有 `users.remote_access`；cloud 只豁免这个员工字段，访客账号状态、
  `visitor:*` 权限、对象范围、限流和审计仍然生效，local 源网段门禁也不跳过 visitor。
- 远程授权和撤权两个方向只要值改变，都会由 V241 bump 目标 `auth_version`、撤销全部 refresh token
  并记方向审计，要求重新登录。撤权后旧 access 先返回 `401 UNAUTHORIZED`；cloud 旧 refresh 返回
  `403 REMOTE_ACCESS_DENIED` 且不签发替代 token。本地允许网段仍可用账号密码重新登录。

公司目标库只读版本证据已到 V190，迁移序列包含 V135；这不等于现行最小 JWT、权限解析缓存和
客户端稳定性修复已经部署。上线前仍须完成个人覆盖、角色、部门树移动/软删、员工换部门、共享权限、
超管变化的旧 token 失效矩阵，以及权限解析 503、请求头预算和性能测试。

2026-08-09 已在隔离克隆库完成远程授权真实 HTTP 矩阵：未授权 local 登录 200、cloud 登录 403；
授权后 cloud 登录/refresh 200；撤权后旧 access 401、旧 refresh 403 且无新 token；无效授权 body
不改变状态。该证据不包含公司实际 CIDR/可信代理、Release 双端点、Web 同源入口、真实访客公网或
复制链路，不能替代目标环境验收。

## 四、敏感数据与一致性

- 身份证、手机、银行卡和薪酬等字段用 pgcrypto 加密；身份证另存 HMAC 以支持唯一性检查。
- 主密钥来自部署环境/Vault，不写源码、SQL 或 Git；缺少关键密钥时应启动失败。
- 工号、证件和账号唯一性必须由数据库约束兜底，不能只靠前端预查。
- 员工写路径使用版本字段防丢更新；调岗、离职、复职和审批必须由服务端状态机执行。
- 离职会停用关联账号、吊销会话并处理在途申请；V135 再保证授权快照变化可拒绝旧 access。
- 普通员工更新禁止改变部门；跨部门必须走调岗并写 `employment_history`。
- 调岗/离职日期不得晚于今天、早于入职日或早于最新任职事件；未来入职由后端拒绝。
- 当前不提供员工删除/归档入口；离职档案保留，负责人调岗或离职时原部门负责人引用自动解除。
- 部门负责人只能是本部门直属在册员工并支持显式清空。
- 管理中心可挂直属人员、岗位和负责人，结构位置锁定；所有普通负责人根覆盖本节点及未删除后代。
  稳定编码 `GM` 且直属公司根的总经办负责人覆盖全公司；名称、岗位、`supervisorId` 或总经办普通
  成员身份不授权。范围由页面权限 API 递归校验，部门筛选默认空。
- 请求审计覆盖进入应用的 `GET/POST/PUT/PATCH/DELETE/HEAD /api/**`，包括匿名认证、401、CORS 非法
  来源 403、404/405 与 MVC 前异常，并且不记录 query 值或 body；有效 JWT 的请求级快照保留操作人，
  无效令牌不绑定身份。安全事件另由显式审计补语义，V169 为公开业务表（含关键人事表）补齐脱敏
  before/after 触发器；数据库变化与业务事务共享 TxSessionVars 和 Request ID。仍需持续维护覆盖矩阵与故障演练。

## 五、组织统计与负责人闭环

- `GET /api/org/departments/{id}/workforce-overview` 使用递归组织范围，当前人数只统计未软删的
  `active/probation/onLeave`；直属人数只计算所选节点直属员工。
- 近 12 个月统计入职、复职、离职和跨范围调入/调出；父组织范围内部调岗相互抵消。
- 离职率 = `离职事件数 ÷ ((期初在册 + 期末在册) / 2)`。任职事件缺失或反推期初人数为负时不输出
  比率，页面显示 `—` 与数据质量说明，不用零值掩盖异常。
- 合同与试用期分别统计逾期和今天至未来 30 天到期。历史部门范围按当前组织树重述，不是历史快照。
- V170 为在册统计、任职事件和合同提醒增加查询索引；查询公式仍需在真实 PostgreSQL 数据量下验收。

## 六、前端实现约束

- 页面只依赖 Repository 抽象；真实实现通过 `apiClientProvider` 注入。
- 员工、部门、岗位和状态展示复用公共组件；领导标识使用明确文字，不只依赖颜色或图标。
- 部门页 compact/medium 使用组织树抽屉，expanded 才固定左树；详情、概况和员工列表统一滚动。
- 搜索、切部门、状态筛选和加载更多使用请求代次；旧响应不得覆盖新筛选或留下永久 loading。
- “我的”资料只调用无目标 ID 的 `GET /api/profile/me`，以 EmployeeProfile 覆盖可能过期的 session
  姓名/部门/岗位，并区分 loading、error、404 未绑定和真实未填写。当前既有员工缺少紧急联系人时，
  自助页不伪造可提交字段，但 HR 侧也尚无补录 UI，该链路仍是明确缺口。
- API 401 先由跨请求协调的单飞 refresh 处理（会话按标签页隔离，ADR-061）。只有 HTTP 状态与结构化业务码同时匹配
  `401 UNAUTHORIZED`、`401 ACCOUNT_LOCKED`、`401 ACCOUNT_DISABLED`、
  `422 VALIDATION_FAILED`、员工 `403 REMOTE_ACCESS_DENIED`（访客另含
  `403 VISITOR_BLOCKED`），且当前 lineage/代次未变化时，
  才清会话并回登录。HTML/空体/未知 401、结构化 503、断网、超时和其它 5xx 保留令牌。
- 员工主动退出立即清可见 session 并激活 logout fence；令牌记录锁先把旧 refresh 持久交接到
  加密待撤销队列，成功后才写权威 tombstone。交接失败时 token 留在 fence 后供重试；网络撤销异步
  执行，应用启动、连接恢复和封顶退避会继续排空。该队列只允许重试公开幂等 logout，不重放任何
  人事业务写请求。
- 临时密码、身份证、银行卡和完整薪酬不得写前端日志、Provider 持久化或
  `shared_preferences`。

## 八、档案附件与合同附件（2026-08-16 补记）

人事是通用附件系统（V240，`/api/attachments`，前端 `lib/shared/attachments/`）的首个接入域，
复用共享 `AttachmentSection` 组件，不自建上传通道：

- **员工档案文件**：员工详情 Tab 6（ownerType=`EMPLOYEE`），分类 合同/身份证件/学历证书/照片/其他；
  两阶段上传（presign → 字节直传 → confirm，HMAC 一次性 grant）、内容嗅探、病毒扫描、软删 + outbox
  异步清对象存储；图片可设为员工头像（`POST /api/org/employees/{id}/avatar`，仅 image/*）。
- **合同附件**：组织与合同 Tab 的合同时间线每份合同卡提供「合同附件」入口（ownerType=
  `EMPLOYEE_CONTRACT`，`EmployeeContractAttachmentAccessPolicy` 反查员工同口径鉴权），弹窗内独立
  上传/查看/删除该份合同的扫描件。
- **我的文件自服务**：`/profile/me/documents`（我的页入口），员工只读查看本人档案文件，
  上传/删除由 HR 统一维护。
- **权限双层模型**（权限管理页「人事行政 → 附件」可配置）：
  - 通用层：`attachment:view`（查看/下载）、`attachment:manage`（上传/删除）——V280 默认 view 授
    全部在职部门、manage 授 DEPT_HR；
  - 对象层：`EmployeeAttachmentAccessPolicy`——view=本人或 `employee:pii:view`（档案文件=身份证件/
    合同扫描件级 PII；**不能用 employee:view**——该权限因员工选择器需求已授予几乎所有部门，
    2026-08-16 保密审计后收紧），manage=`employee:edit`，拒绝统一 NOT_FOUND 防枚举；合同附件
    （EMPLOYEE_CONTRACT）同口径；
  - 前端门控与后端对齐：员工详情附件区按 `employee:pii:view && attachment:view` 可见、
    `employee:edit && attachment:manage` 可管理（`Perm.attachmentView/attachmentManage`）；
    无权限显示说明性空态，后端 `EmployeeQueryService.detail` 对附件列表降级为空（FORBIDDEN
    不再导致整页失败）。
- **上传保留原件**（2026-09-08）：共享组件与文件选择器均不进行有损缩图或格式转换。
  内部存储按收益选择无损压缩，下载还原原字节；原始大小与实际落盘大小分开记录。
  旧有损压缩器已删除，设计与部署边界见 [ADR-074](../99-决策记录-ADR/ADR-074-公司内部附件存储与原件保留.md)。
- **AttachmentSection UI**（2026-08-16 重构）：文件类型彩色图标（图片/PDF/Word/Excel/zip/文本）、
  分类筛选芯片带计数、计数徽章、多文件批量上传带进度、虚线上传空态、图片 InteractiveViewer 预览
  附「保存到本机」（cacheWidth 限制解码内存）、删除红色确认按钮；只读场景空态克制安静。报销详情页
  （EXPENSE_CLAIM）同组件复用。

## 九、人事域待办通知 HrNoticeService（2026-09-09 接入，2026-09-10 补齐）

- **位置与职责**：`server/.../features/notice/HrNoticeService.java`。人事模块「该谁干活」的节点统一由它
  发居中行动卡 + 通知（ADR-063），业务 Service（`ProfileChangeSubmitService`/`ProfileChangeReviewService`/
  `ProfileChangeQueryService.cancelBatch`、`VisitorApplicationService`/`VisitorHrApprovalService`/
  `VisitorHostConfirmService`、`ExpenseClaimService`、`PayrollService`、`SuggestionService`）在状态落库后
  调用；页面徽章仍以数据库真态为权威，通知只是提醒层。
- **事件目录**（`ReviewNoticeCatalog` 登记，聚合 → 办结按 (kind,id) 批量 resolve）：
  `PROFILE_CHANGE_SUBMITTED`(PROFILE_CHANGE)、`VISITOR_APPLY_SUBMITTED`(VISITOR_APPLICATION)、
  `VISITOR_HOST_CONFIRM_REQUIRED`(**VISITOR_HOST_CONFIRM**，独立聚合——接待人确认后申请回 HR 批准，
  HR 卡不能被误撤)、`EXPENSE_CLAIM_SUBMITTED`(EXPENSE_CLAIM，claim=EXPENSE_APPROVE)、
  `EXPENSE_CLAIM_PENDING_PAYMENT`(EXPENSE_CLAIM)、`PAYROLL_BATCH_SUBMITTED`/`PAYROLL_BATCH_PENDING_PUBLISH`
  (PAYROLL_BATCH)、`SUGGESTION_SUBMITTED`(SUGGESTION)。同聚合两张卡接棒（报销审批→打款、工资审核→发布）
  必须**先 resolve 旧卡再发新卡**。完整表见 ADR-063 附录「人事域事件目录」。
- **接收池**：活跃内部账号（绑定员工档案）× `notice:read` × 职能权限，**不限部门子树**——这是
  ADR-063「部门 ∧ 权限」总口径的明示例外（`ReviewNoticeAudience` 对这些事件只看权限）。候选集用
  `NoticePermissionCandidateQuery` 缩窄，超管走权限快照展开。提交人/审核人本人一律排除（按员工 id
  `belongsToEmployee`；建议箱按账号 id）。
- **隐私**：匿名建议的行动卡与回执正文不带提交人姓名；工资发布只逐人通知持条员工，不广播；
  报销/工资回执只发给申请人/制单人本人。
- **事务语义**：与业务同事务，失败随业务回滚。类内无 `@Transactional`，`NoticeService` 写方法为
  REQUIRED 传播；`sameTransaction()` 只记 warn 日志后原样抛出（旧 `safe()` 吞异常会让业务在提交时报
  UnexpectedRollbackException 且无迹可循，已移除）。单元测试若用真实 `HrNoticeService` 需给全部依赖，
  否则用 `mock(HrNoticeService.class)`（`VisitorAdmissionConcurrencyPostgresTest` 已改）。
- **测试**：`HrNoticeServiceTest`（接收池筛选/本人排除/聚合与目录一致/匿名脱敏/异常传播）、
  `ReviewNoticeAudienceTest`（全目录事件仅 view/仅部门均不弹）、前端
  `review_pending_dialog_test.dart`（8 个人事事件的 `workbenchRouteFor` 落点）。
- **前端落点**：`workbenchRouteFor` / `_eventGroupLabel` / `_eventIcon` 三处登记；新事件接线时三处 +

## 十、人事域列表统一表格与批量约定（2026-09-09 表格化，2026-09-10 筛选与批量）

人事域 12 张列表页全部收口到 `MasterDataTableView`（唯一表格组件），三条硬约定：

1. **表格唯一**：不再有卡片瀑布（`UtenResponsiveGrid`+`UtenCard`）列表；分段仍用
   `UtenSegmentedFilter`/`UtenFilterToolbar`，与表头筛选两层并存（分段管口径、列头管维度）。
2. **表头筛选下推后端**：凡是服务端分页的列表，筛选桶必须来自后端聚合、筛选值必须下推查询参数，
   **不得只裁剪当前页**（当前页聚合会漏掉其他页的命中行）。当前落地：
   - 报销审批：`GET /api/expense-claims/facets?queue=` → 部门 + 年月，下推 `departmentId/year/month`；
   - HR 信息变更：`GET /api/hr/profile-changes/facets?status=` → 部门（`COUNT(DISTINCT batch_id)`），
     下推 `departmentId`；
   - 访客审批：`GET /api/visitor-approval/facets?status=` → 状态 + 接待人部门，下推 `status/hostDepartmentId`；
   - 建议箱：新增 `GET /api/suggestions?status=`（与 `scope`/`category` 正交，派生查询 4 组合）；
   - 个人视角列表（我的报销/工资条/我的信息变更/我的访客）：状态桶 = 当前分段状态集，
     选中即切分段 + 下推后端 status 并回第 1 页。
   - 例外：**HR 任务中心**的 summary 是一次性全量下发、页面无分页，其部门/区间/认领/已祝福
     四个桶在客户端聚合与裁剪（不存在跨页漏行问题）。
3. **多选批量 = 前端循环单审 API**：后端没有批量端点，也不打算加（与生产计划批量同范式）；
   服务端逐单独立事务 + 悲观锁 + 状态机 + 认领守卫仍是唯一权威。统一口径：
   - `selectable` + `idOf` + `selectedIds` + `batchActionsBuilder`；「已选 N 项」只由
     `UtenSelectionSummaryPill` 呈现，任何页面不得自绘；
   - 单次上限 **50** 条（各页 `k*BatchLimit` 常量），超限提示分批；
   - 单条失败不中断整批，成功数与失败数分别提示，首条失败原因回显；
   - 明确不可执行的行（他人认领中、状态不符）**前端跳过并计入提示**，不靠后端报错刷屏；
   - 批量驳回/拒绝统一走公共 [`UtenBatchRejectDialog`](../02-组件库/UtenBatchRejectDialog.md)；
     批量通过/批准/转接待人的确认弹窗统一带
     [`UtenReviewerResponsibilityNotice`](../02-组件库/UtenReviewerResponsibilityNotice.md)。
