# 品质任务中心

> 路由：`/quality/task-center`（`RouteName.qualityTaskCenter`）
> 实现源：`lib/features/quality/pages/quality_task_center_page.dart`
> 下级页面：IQC `/warehouse/inspections` · FQC `/quality/production-inspections` · 检测记录 `/quality/inspection-records`
> 数据源：IQC 待检 sidecar（V222）+ 生产 FQC inspection/decision（V410–V415）+ 两域追加式决定/撤销事件
> 最近更新：2026-08-31（工作台品质管理部顶层只保留本入口；真实只读检测记录并入中心）

## 一、定位

品质管理部在工作台只保留一张「品质任务中心」卡，所有品质入口在本页按职责收口：

- **任务中心**：采购/委外收货 IQC「待检处置」与生产成品 FQC「生产成品质检」；
- **查询与记录**：真实只读「检测记录」，统一查看 IQC/FQC 已发生的质量决定与撤销事实；
- **不属于本页的能力**：旧实验室 `/lab/test*` 与 `lab:test:*` 仍未实现，不能把新的品质记录页写成实验室检测、上传或设备模块。

这样既避免品质人员到仓库菜单寻找 IQC，也避免在工作台品质分区同时出现「任务中心」和另一个孤立入口。仓库先负责登记到货或送检；品质 PASS 只形成合格放行事实和仓库待入库任务，仓库确认实际库位与数量后，库存/齐套链才处理后续业务事实。

## 二、入口、分组与权限

| 分组 | 卡片 | 路由 | 查看条件 | 写动作 |
|---|---|---|---|---|
| 任务中心 | 待检处置（IQC） | `/warehouse/inspections` | `procurement_inspection:view` | 处置另需 `procurement_inspection:handle` |
| 任务中心 | 生产成品质检（FQC） | `/quality/production-inspections` | `production_quality_inspection:view` | 决定另需 `production_quality_inspection:approve` 且服务端确认有效品质组织池 |
| 查询与记录 | 检测记录 | `/quality/inspection-records` | 上述任一 view 权限 | 无；页面只读，不提供修改、删除或导出 |

- `RouteName.qualityTaskCenter` 与 `RouteName.qualityInspectionRecords` 均按 IQC/FQC 两个 view 权限作「任一满足」入口门禁；前端显隐不是服务端安全边界。
- 记录页只请求当前账号有权的域：只有 IQC view 时不请求 FQC；只有 FQC view 时不请求 IQC。两域服务端仍分别鉴权、裁剪对象范围，已知 UUID 不得绕过。
- FQC 记录沿用现有对象范围：有效 `DEPT_QA` 品质组织池可看共享品质队列；非品质池账号只能按生产报工 maker/既有生产数据范围读取相关记录。详情越权与不存在统一按 404 失败关闭。
- 超级管理员沿用现有恢复路径，但不因此获得新的修改、删除或导出动作。

## 三、待办角标与刷新

| 卡片 | 角标语义 | 权威接口 |
|---|---|---|
| 待检处置 | 仍有 `PENDING/PARTIAL` 明细的收货单张数 | `GET /api/procurement/inspection/pending-count` |
| 生产成品质检 | FQC `PENDING/PARTIAL` inspection 数量 | `GET /api/production/quality-inspections/count` |

- 工作台「品质任务中心」角标是当前账号有权 IQC/FQC pending count 的合计；通知条数与未读数不参与业务数量。
- 任一有权计数仍在加载或失败时，不得把该域当作真实 0 后展示一个看似完整的合计；失败应显示可识别的同步异常状态。
- 从下级待办页返回本中心时立即使对应计数失效重拉；回到工作台或客户端检测到新通知后，外壳的全局角标刷新同样重拉两个 provider，不等待下一轮轮询。
- 无对应查看权限时不请求该域计数；任务卡与记录域筛选也不渲染。

## 四、检测记录事实口径

`/quality/inspection-records` 不是把任务当前状态复制成一张可编辑单据，而是读取既有追加式事实：

- IQC：`GET /api/procurement/inspection/records` 与 `/records/{recordId}`，事实来自 `procurement_inspection_events` 的 `PASS`、`FAIL`、`RECEIPT_REVERSED`；收货红冲映射为 `CANCELLED`，父收货已 `REVERSED` 时旧 PASS/FAIL 仍保留但标记 `effective=false`。
- FQC：`GET /api/production/quality-inspections/records` 与 `/records/{recordId}`，事实来自 `production_fqc_decision_events` 与 `production_fqc_cancellation_events`；来源红冲/取消作为 `CANCELLED` 历史保留，原决定不得物理覆盖。
- 两域列表使用同形筛选：`decision`、`keyword`、`from`、`to`、`page`、`size`；汇总指标 `ALL/PASS/PARTIAL/FAIL/CANCELLED` 基于当前域、关键词和日期范围的完整结果计算，不是当前页行数。
- 页面只允许筛选、分页、查看详情与刷新；无修改、删除、重新决定、撤销或导出按钮。办理动作必须回到对应 IQC/FQC 待办页并继续受动作权限、组织池、状态机和幂等校验约束。
- 详情读取记录查看审计；列表/详情中的业务编号、货品快照、数量、原因、操作者、发生时间和 `effective` 只反映权威事件，不由 Flutter 本地推算。

详见 [品质检测记录页.md](品质检测记录页.md)。

## 五、UI 与状态

- 页面复用项目统一的 `UtenAppBar`、内容容器、Hub 卡、语义色与 4/8dp 间距，不另造一套品质视觉语言。
- 待办与查询记录分组有明确标题；每张可办卡只表达一个主要去向，角标固定在统一位置。
- 首次加载、刷新旧数据、加载失败重试、筛选空态和无权限空态必须可区分；错误不能显示成「0 条」或空白页面。
- 窄屏按约束重排，保留与桌面相同的筛选、状态、详情和返回能力；触控目标、键盘/读屏语义与大字体不得因布局压缩而丢失。
- 检测记录的只读状态必须在页面和详情中可见，不能用灰掉的写按钮暗示用户可以申请修改。

## 六、与仓库和生产的分工

- 仓库审核采购收货/委外进仓时，在创建 IQC `PENDING` 隔离行的同一事务内产生业务事实；
  IQC PASS 只增加品质合格量并形成“合格待仓库入库”任务，FAIL 与红冲保留追加事件。
  仓库可分批确认实际入库；只有确认成功后才增加可用库存并推进物料分析、reservation、DRAW 与 READY。
- 新生产 FQC 任务来自仓库已登记送检；PASS/PARTIAL 只形成 FINISHED_IN 待点收上限，不直接增加库存或 `iqty`，仓库实收才是生产完成事实。
- FQC FAIL 进入 REWORK 或 SCRAP/REJECT 补产链；来源红冲必须按顺序取消派生事实，历史决定与撤销记录仍可在检测记录页追溯。
