## 来历

2026-10-04 一次整体发版(v2.4.0，分支 `v797-rollback-backup` 提交 `8a13b4ea2`)里尝试过「仓库任务按子仓负责人范围贯通」，带了本迁移。随后用户把那次发版整体回退(main 回退、服务器切回 v2.3.0)，但服务器库已经执行了 V795/V796/V797。代码目录里没有这个文件时，下次发布的迁移器会以「库里已执行、代码里没有」中止，所以本分支把文件原样恢复。那次回退掉的 Java 代码(按读侧逐条重判通知、`resolve` 只收窄不放宽等)没有恢复，按 [ADR-149](../99-决策记录-ADR/ADR-149-仓库数据范围服务端强制.md) 重新设计。

## 迁移做了什么

1. `fn_warehouse_keeper_user_ids(ids)`(重写 V693)：本仓与各级上级仓登记的有效负责人(员工在职、账号启用)；起点仓必须未删除，上溯时跳过已删除的上级。
2. `fn_warehouse_supervisor_user_ids()`(新增)：超管 + 登记在「有下级的仓」上的负责人。
3. `fn_stock_document_matches_warehouse_scope(document, ids, unassigned)`(新增)：调拨单按发出仓或调入仓；其它单据要求所有行仓都在范围内。
4. `fn_notice_warehouse_visible(user, event, kind, id, route, permissions)`(新增)：通知读侧按现任负责关系逐条判定某张卡对某人是否可见。

回退之后的代码只调用了第 1 个函数(通知分发)，其余三个在服务器上存在但没有调用方。

## 后续处置(V804)

[V804](V804-仓库数据范围服务端强制.md)(ADR-149) 按新口径处理这 4 个函数：

| 函数 | V804 处置 |
|---|---|
| `fn_warehouse_keeper_user_ids` | 重写：只算子仓负责人(登记在本仓或主仓以下各级上级仓)，登记在主仓上的人是主管、不在此列 |
| `fn_warehouse_supervisor_user_ids` | 重写：主管 = 超管 + 仓储部(SUB_WH 子树)部门负责人 + 登记在主仓 001 上的负责人(不再按「有没有下级」推断主仓) |
| `fn_stock_document_matches_warehouse_scope` | 重写(签名不变)：库存单据的所在仓 = 发出仓或调入仓，两个都没有 = 未定仓；库存单据列表、仓库草稿数、生产退料待实收数同用 |
| `fn_notice_warehouse_visible` | 删除：通知改为发送时按唯一规则分发(`fn_warehouse_notice_recipients`)，已发出的卡片不再按读侧逐条重判；这个函数从未接入 |
