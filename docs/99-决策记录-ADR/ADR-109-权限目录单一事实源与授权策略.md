## 一、问题

2026-09-23 权限审计把问题归成一句话：**「一个码能怎么授」写了五份，还互相矛盾**。

| 份数 | 在哪 | 说了什么 |
| --- | --- | --- |
| 1 | `permissions.assignable / bulk_assignable / active` | 能不能分配、能不能批量、是不是停用 |
| 2 | 后端 `INDIVIDUAL_ONLY` 常量 | 审计查看/导出、余额调整只能逐人授予 |
| 3 | `PermissionDelegationPolicy` 硬编码名单 | 负责人不能转授哪些码 |
| 4 | 前端 `authorize_all_excluded.dart` | 「全部授权」不带哪些码 |
| 5 | 前端超管兜底清单 + 两条只认个别码的数据库守卫 | 超管看到哪些码、哪些码不许进部门 |

直接后果：

- `supplier_return_task:view/complete` 既「仅允许点名授权」又「不可分配」，谁都授不出去，超量到货退回供应商的任务卡死；IQC 不合格闭环、官网询盘两条链同理没人持码(permissions-01)。
- 财务部 / 总经办 / 人事部的部门矩阵里本来就有「不可分配」码，原样保存必失败(permissions-02)。保存是「整表删掉再插回」，最大的矩阵保存一次写 140 条语句、278 行审计，却看不出改了什么(audit-retention-settings-03)。
- hub 入口的 any-of 清单是手写的：`/warehouse` 漏了库存查询、`/finance` 漏了应付结算，只持这些码的人在工作台看得到卡片却进不了 hub(permissions-04)。
- 16 个停用码仍在目录、仍能被 `@PreAuthorize` 引用；`production_plan:batchApprove/batchDelete`、`finance_reconciliation:view`、`employee:export`、`finance_asset:export`、`visitor:apply/view` 只在前端生效，服务端不认(permissions-06)。
- 角色体系名义下线(V29)，实际仍给全员基础包、通知受众和入职接口供数(permissions-07)。
- 出货财审一个码管查看 + 放行 + 退回 + 反审；仓库销售出库一个码管查看 + 执行，另有一条绕过仓库入口的重复写端点(permissions-09)。
- 没有负责人的单据对所有持查看码的人公开可读，系统生成的单据还被故意写成空负责人来「属于系统」(permissions-10)；计划子资源 `/plans/{id}/mrp/**` 与订单物料分析只看功能权限不看对象范围(security-07)；访客可以翻出整棵部门树和部门下的全部员工(security-08 / permissions-13)。
- 应收应付台账只要台账查看码就能看全公司余额(security-18)；空闲的超管会话点一下就能清空业务数据(permissions-14)；日报「审核」按钮不看车间直送审核权，点了才被拒(permissions-15)。

## 二、同行做法(设计依据)

- **SAP**：权限对象 + 角色(PFCG)，「能否被派发」由角色模板和授权字段决定，派发本身留变更凭证(SUIM 变更报告按增删列出)。
- **Odoo**：`res.groups` 是唯一授权单位，`ir.model.access` + record rules 管对象范围；「全部」是一个显式组，不是缺省可见。
- **金蝶 / 用友**：功能权限 + 数据权限两层；数据权限默认「本人」，「全部」必须显式授予；敏感权限(如反审核、调账)只能对人授予，不随角色模板批量下发。

共识：**授权规则只写一处**、**变更按差量记凭证**、**没有归属的数据不是公共数据**、**高风险动作要二次身份确认**。本 ADR 按这四条收口。

## 三、决策

### 3.1 授权策略只写在目录里(`permissions.grant_policy`)

`grant_policy text[]`，取值与含义：

| 值 | 含义 | 当前码数 |
| --- | --- | --- |
| `NORMAL` | 部门、个人、负责人转授、全员基础包、「全部授权」都可以带上；只能单独出现 | 399 |
| `BULK_EXCLUDED` | 不随「全部授权 / 本模块 / 本组」批量发放，必须逐项勾选(对象全量范围、商业敏感信息) | 16 只 BULK_EXCLUDED + 16 与 NON_DELEGABLE 组合 |
| `INDIVIDUAL_ONLY` | 只能由超级管理员逐人授予：不进部门矩阵、不可转授、不随批量 | 10 |
| `NON_DELEGABLE` | 组织负责人不能在页面上转授(超管仍可按部门或个人授予) | 4 只 NON_DELEGABLE |
| `SUPERADMIN_ONLY` | 只随超级管理员身份生效：任何入口都授不出去、不挂任何页面权限面 | 4 |

派生规则(服务端 `GrantPolicy`、前端 `PermissionGrantPolicy`、数据库守卫 `fn_guard_permission_grant_policy` 同一口径)：

- 能配给部门 = 不含 INDIVIDUAL_ONLY / SUPERADMIN_ONLY
- 能逐人加授 = 不含 SUPERADMIN_ONLY
- 负责人能转授 = 不含 NON_DELEGABLE / INDIVIDUAL_ONLY / SUPERADMIN_ONLY
- 能随批量 = 能进全员基础包 = 不含 BULK_EXCLUDED / INDIVIDUAL_ONLY / SUPERADMIN_ONLY

`assignable / bulk_assignable / active` 三列删除；前端 `authorize_all_excluded.dart`、后端 `INDIVIDUAL_ONLY` 常量与委派硬编码名单删除。`sensitivity` 只保留为「商业敏感数据」展示标签，不参与任何授权判断。`PermissionGrantPolicyContractTest` 锁住代码里不得再出现按码写死的授权名单。

### 3.2 停用即删除

目录里不再有「软停用」码。V677 删除 16 个停用码与 7 个只在前端生效或没有入口的码，连同授权行、页面权限面映射；对应的服务端端点一并删除(计划执行段取消/红冲、MRP 一键生成采购申请与整树展开、研发任务新建/指派、委外发料单手工新建、采购/委外订货单固定报错的审批入口、待审收件台跳转)；没有调用方的订单物料分析 `order-preview` 同样删除(§3.8)。批量审核/删除生产计划改为服务端单事务批量端点，用单张同一个码(`production_plan:approve / delete`)。打印花名册就是查看员工名册；资产删除只影响草稿，并入 `finance_asset:edit`(不另设删除码)。`PreAuthorizeCodesAreActiveContractTest` 与 `PermissionCatalogBidirectionalContractTest` 锁住：`@PreAuthorize` 只引用目录码；目录码都在服务端被引用；前端 `Perm` 常量都是目录码。

### 3.3 命名统一与动作拆分

- 码形一律 `资源:动作[:限定]`、小写下划线，数据库 CHECK 兜底；`visitor:check-in` → `visitor:check_in`、`visitor:host-confirm` → `visitor:host_confirm`、`dashboard:finance-sensitive:view` → `dashboard:finance_sensitive:view`、`procurement_iqc_rejection:view_all` → `procurement_iqc_rejection:view:all`。
- `finance_shipment_audit` → `sales_shipment_finance:view / approve / reject / reverse`；`sales_shipment:warehouse-work` → `warehouse_sales_outbound:view / execute`；授权按原持有者平移。仓库出库只剩 `/api/warehouse/sales-outbound/{id}/warehouse-work` 一个写入口，销售出货控制器上的重复写端点删除。
- 访客会话的码移到独立命名空间 `visitor_portal:apply`，不进员工权限目录。

### 3.4 链路可达

给三条卡死链路定默认岗位：退回供应商任务(采购部、综合营销事业部)、IQC 不合格闭环(仓储部登记实物退回，财务部确认贷项 / 无贷项关闭 / 红冲 / 看金额)、官网询盘(综合营销事业部)；补结算方式查看/维护(财务部)、模具分类维护(工程研发部)、批准后改量与提交财务同口径。`PermissionChainReachabilityContractTest` 在迁移到最新版本的库上断言：每个执行/审批类码至少有一种人能拿到。

### 3.5 角色体系删除，全员基础包可编辑

`roles / user_roles / role_permissions / department_roles` 四张表删除。原 `employee` 角色的 6 个码平移为 `permissions.baseline`(报销申请、读通知、看本人工资条、改本人资料、提建议、访客接待确认)，管理页第三个分段「全员基础包」可编辑，只收能随批量的码。V679 起「接待访客」移出基础包、改为对外接待白名单(§3.9)，基础包剩 5 个码。

有效权限 = 全员基础包 ∪ 部门配置(本部门 + 上级递归 + 兼职部门递归) ∪ 个人加授 ∪ 负责人委派 − 个人收回；超级管理员 = 全部目录码。前端 `currentPermissionsProvider` 只用服务端下发的集合，超管也不再由前端补一份本地码表。通知受众从「角色」改为「部门子树 + 权限码」。

### 3.6 差量保存 + 一条业务事件

部门矩阵、个人覆盖、负责人页面委派、全员基础包、数据范围五个入口都改为：前端交出期望的完整集合 → 服务端算出新增 / 移除 → 只校验新增的码能否这样授(移除永远允许，已有的「不随批量」码原样保留可保存) → 只写差量行 → 真的有改动时在同一事务里写一条语义化业务事件(`department_permission_change` / `user_permission_override_change` / `manager_permission_delegation_change` / `permission_baseline_change` / `user_data_scope_change`，after JSON 带 `added / removed` 完整列表)；没有改动就 0 写入、0 审计。

「全部授权 / 本模块 / 本组」只把范围交给服务端(`PUT .../grant-all`)，服务端按授权策略挑码、一次写入。

实测(迁移到最新版本的库，39 个带部门矩阵的部门，最大 139 个码)：

| 场景 | 旧写法 | 新写法 |
| --- | --- | --- |
| 最大矩阵原样保存 | 140 条语句、278 行审计 | 3 次 JDBC 调用(只读)、0 行审计 |
| 加一个码 | 同上(整表删插) | 1 行授权 + 1 条业务事件(+1 行授权表触发器审计) |

### 3.7 hub 守卫 = 子卡守卫并集

`lib/core/router/hub_catalog.dart` 登记每个 hub 上全部卡片可能的落点(同一张卡按权限切换「新建页 / 列表页」时两个都登记)。hub 路由守卫 = 子卡守卫的并集(任一子卡能进，hub 就能进)；hub 页与工作台只按 `hubCardAllowed / locationAllowedFor` 过滤卡片，页面里不再写 `perms.contains`。卡片落点带查询参数时先去掉参数再匹配守卫(过去带参数的落点被当成「登录即可」)。`hub_guard_union_test` 经 GoRouter 真实跳转锁住。

### 3.8 对象范围

- **没有负责人的单据不再公共可读**(permissions-10)：只有持「看全部」的人和超管能读，任何人都不能直接写(必须先显式补负责人)。这条口径不只写在 `DocumentAccessPolicy`，手写 SQL 与私有可见性判断同一口径——日报可报工计划行、物料分析在途供给单号、生产物料子资源读守卫里「负责人为空就可见」的旁路一并删除；`NullOwnerIsNotPublicContractTest` 扫描主代码，SQL 里的 `maker_id / owner_employee_id IS NULL` 与 Java 里 `seeAll() || owner == null` 这类短路一出现就红(按旧工号补姓名的联表、主档公共客户/供应商/货品除外)。
- **系统生成的单据必须有明确归属**：由仓库办理的委外发料草稿用显式 `owner_pool = 'WAREHOUSE_SUBCONTRACT_OUTBOUND'`(V678，CHECK 约束 + 仓库出仓码授权读写)；系统自动核对备料生成的生产领料单记业务负责人(执行段负责人，其次生产计划负责人)，不再因为系统身份没有员工号而留空。
- **计划子资源**：`/api/production/plans/{id}/mrp/**` 每个处理方法入口先过 `ProductionPlanResourceGuard`：越权读 404(不泄露存在性)，越权写 403。`ProductionPlanSubresourceScopeContractTest` 锁定。旧的订单物料分析 `GET /api/production/mrp/order-preview` 没有任何调用方(现行入口是持久物料分析)，连同服务端展开逻辑和前端仓库方法一起删除，不再为它补对象范围。
- **应收应付台账**(security-18)：没有按人隔离的归属列，列表与详情都要求 `ar_ap_ledger:view` 且 `finance:view:all`。

### 3.9 访客搜接待人：白名单就是权限目录

访客账号靠短信验证码自助注册，搜接待人是外部主体能碰到公司名册的唯一入口(security-08 / permissions-13)：

- 只对访客会话开放，只能按姓名前缀先搜再选：关键字 2~20 个字、最多 5 人；不接受部门或工号参数，不下发部门树，结果只有 id 和姓名(不带部门)。
- **只列可对外接待的员工**。「能被访客选为接待人」与「能确认本人来访」是同一件事，用同一个码 `visitor:host_confirm`(名称改为「接待访客」)表达：V679 把它移出全员基础包、授权策略设为 NON_DELEGABLE(只由超管按部门或逐人授予，负责人不能自行扩大名单)，默认发给对外接待的部门(总经办、综合营销事业部、轨道事业部、新媒体事业部、行政与人力资源部、PMC运营采购部、品质管理部、工程研发部，部门授权对下级部门同样生效)。不另设名单表或员工标记列，管理员在权限管理页调整即可。
- 判定两步走(与审核组资格同一模式)：一条 SQL 取「可能持有该码」的超集，再逐人交给 `PermissionResolver` 终判(个人收回、离职、委派失效在这里生效)。提交来访申请时同样终判，拿猜到的员工编号挂不上白名单外的人。
- 按访客账号限流(每分钟 10 次、每天 60 次)、按来源地址限流(每分钟 30 次)；每次查询写一条审计(`visitor_host_search`，含关键字与命中人数)，被拦下的写 `visitor_host_search_limited`。
- 同名的两个人都会列出且没有部门可区分：接待人收到申请后要确认，选错的人会退回，这是有意的取舍(不为消歧把部门再露出来)。

### 3.10 高风险动作与按钮

- 清空业务数据与提前分批删除测试业务附件：新增超管专属码 `system:business_data_reset`(管理页可见、任何入口授不出去)，两个端点都要求超管本人 + 该码 + 本次重新输入登录密码。与 ADR-110 合并后，密码复核统一为再认证：端点标 `@RequiresStepUp`，前端由统一再认证弹窗换一次性凭证(与改系统设置、改权限同一道门)，输错计入再认证失败次数并写 `step_up_failed` 审计；请求体不再带密码，也不再单独调用 `PasswordService.verifyPassword`。
- 生产计划批量审核 / 删除一次最多 50 张(服务端 `PlanBatchRequest.MAX_PLANS` 与前端 `ProductionPlanRepository.batchLimit` 同值)：单事务逐张执行，控制在前端接收超时之内；超过先请用户分批。网络中断或超时时服务端可能已经提交，页面先按最新状态刷新列表、请用户核对，不说「没有任何计划被处理」。
- 部门矩阵保存先锁部门行(`FOR NO KEY UPDATE`)再读现有授权，全员基础包保存加事务级互斥：两个超管同时保存时后到者读到先到者的结果；实际写入行数必须等于算出的差量，否则拒绝保存，业务事件与真实授权行始终一致。个人覆盖本来就锁账号行。
- 按钮只按服务端 `allowedActions` 显隐(permissions-15 规定)：日报「审核」(日报审核码 + 对象范围 + 草稿 + 车间直送审核码 + 出料车间成员资格，与审核写路径同一把尺子)；出货财审的放行 / 退回 / 撤回(动作码 + 对象范围 + 单据状态，随核对信息下发；页面据此决定是否认领)。`page_permission_literal_baseline_test` 统计 pages / widgets 目录里全部 `Perm.x` 引用(基线 591)，换个辅助函数包一层也照样计数，只许下降。

## 四、不做什么 / 遗留

- **单据 `maker_id` NOT NULL 未落地(permissions-10 部分完成)**：老库迁移脚本仍会为采购/生产/委外历史单据写入空 maker，约 90 个测试夹具不带 maker 插单，分属多个并行整改的区域。本轮做到：「空 maker 公共可读」在策略类和手写 SQL 里全部删除并由契约测试锁住；运行期两条系统建单路径都有明确归属(委外发料草稿走 `owner_pool`，系统核对备料的领料单记业务负责人)。NOT NULL 约束留给老库迁移脚本补齐负责人之后的下一波。
- 页面权限面表仍保留 `enabled` 列：停用面(委外准备中心、待审收件台，以及只挂了超管专属码、摘完后没有可授码的系统设置面)不装载、不出现页面内授权入口，但行本身未删除。
- permissions-15 只做了规定与两例(日报审核、出货财审)；其余页面按钮改成服务端 `allowedActions` 属于后续逐页迁移，由基线测试保证只减不增。
- 访客搜接待人的限流是单实例内存态(与登录限流一致，ADR-031 单主库部署)；多实例部署时需改共享限流存储或网关兜底。
