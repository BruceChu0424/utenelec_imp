## 背景：一做数量就乱

用户口径(2026-09-21)：「现在计划里面的委外、采购和生产三个环节会相互缠绕, 一做数量就乱」。排查物料分析准备页, 根因不是某一处算错, 而是**同一个数被算了很多遍, 而且各算各的**：

1. **没有「每个节点的计划量」这个概念。** 节点上只有需求量(BOM 展开)和已下达量(链接/行动/台账), 「这个件到底打算做多少」在服务端不存在, 于是客户端(`material_cascade_quantity.dart` 等约 4000 行)自己按 `perProductQty × 本批数量 − 已覆盖` 重算下层, 与服务端的口径只能靠猜。
2. **超量是一条「公共尾巴」, 不往下传。** V577 把车间超量记成 `public_surplus_qty`, 但 BOM 展开只看需求量, 顶层多做 500 时下层的需求纹丝不动——用户看到「顶层 1500、下层 1000」, 只能手动补数。
3. **有子层的委外是一个节点两条路线, 八本账。** 委外申请、前置自制台账、锚点产品行、计划链接、行动、分摊、公共份、认领份各记一份数量, 下达时哪本账是主口径取决于走哪个入口。
4. **同一个「还可下达」在不同桶里有七种算法**(缺口 − 在途、锚点剩余、台账 required − notified、客户端回退……), 一周内 V577/V588/V589/V621/V634/V638 六张迁移都在对账同一个数。

## 决策

**数量只做一次, 在服务端做, 客户端只显示和转发。**

### 0.「需要数量」固定读取来源需求(2026-09-23)

用户要求准备页「需要数量」始终表示销售/计划汇总来源本来需要多少，下单、超量、追加和下单预览均不能改大这一列。为此 `MaterialView` 增加只读 `sourceRequiredQty`，不新增数据库列或迁移：从真实根分析来源的 `requestedQty × unitRate` 基本量出发，沿本节点保存的精确 BOM 规则逐边计算。整包/固定批次逐层取整；同物料多路径分别计算后再汇总，不能先合并根数量再按平均用量乘算。产品行读取原始来源 `requestedQty`，沿产品行原单位展示；物料行按其基本单位展示。

`sourceRequiredQty` 不读取已下达量、追加输入、公共备货量或随执行增长的自制锚点配额，也不扣库存、在途和完成量。只有来源本身或有效 BOM 依据发生合法变化并刷新后，它才随来源重新计算；“固定”不是把旧来源永久冻结。

原 `requiredQty` 继续表示按实际计划产出展开的备料需求，供采购/委外下达、预留、物理缺口、还需安排和追加计算使用。本节只拆开只读展示口径，不将来源量写回执行需求。比如来源需 1000、实际下达 1500、再追加 500：一比一子件的「需要数量」保持 1000，实际备料需求依次为 1500、2000。主表「需要数量」只读 `sourceRequiredQty`，级联下单页动态需求列改称「本批备料需求」。

### 1. 每个节点有且只有一个「计划产出量」

`plannedOutputQty = max(需求量, 已下达计划量)`, 其中已下达计划量 = 计划链接的 `submitted_qty + public_surplus_qty`(未撤销的 SUBMITTED/APPROVED 链接)。

- 来源行(顶层)的计划产出量驱动第一层实际备料需求：顶层按 1500 下达车间(来源需 1000 + 公共备货 500)后，一比一子件的 `requiredQty` 为 1500；主表来源「需要数量」仍是 1000，不能为了保持显示不变少备这 500。
- 中间层沿用 ADR-080 的「父件计划产出」骨架, 只是把第三个输入换成事实：`parentPlannedOutput = max(净缺口, min(内部承诺, 缺口), 父件已下达计划量)`。父件锚点已经排了 1000, 子件就按 1000 展开; 锚点再排 500, 子件跟到 1500。
- 顶层超量后, 既有自制锚点的配额(`requested_qty`)自动按新增需求增长(`refreshWithAnchorGrowth`), 车间桶的「剩余可排」随之变大, 不用重新建锚。委外前置自制锚点不自动增长——它随 ARRANGE 通道按本批量跟到台账(V589)。
- 视图新增两列事实给客户端：`plannedOutputQty`(本节点计划产出量)与 `sharedFutureClaimableQty`(同主仓可认领的公共在途, 含晚到)。

### 2. 下达采购 / 委外：填多少下多少

`SupplyQuantityInput` 只剩 `qty`(本次总量)与 `safetyReplenishmentQty`。服务端按权威余量分账：不超过「还需安排」的归本需求, 超出的记公共备货(仍要 `over_supply` 权限; 我方供料的带 BOM 委外件仍禁公共备货)。客户端原来自己拆「需求量 + 公共量」两个数的 `publicExtraQty` 退役——它正是「客户端算的余量与服务端不一致 → 422 整批回滚」的来源。

### 3. 追加下达时先认领公共在途, 再就地改大未订货的申请

- **自动认领**：外部路线(采购、直接外发委外)下达时, 服务端先按「按期优先、晚到其次」认领同主仓的公共在途, 只为余下部分新下单; 认领动作与新单记在同一条命令里(`claimActionIds` / `acceptedLateSources`), 幂等重放不重复认领。会创建下层责任的组(自制、先自制目标件的委外)与我方供料的带 BOM 委外件不自动认领(它们要的是自己做出来的件)。
- **就地追加**(用户口径「只要委外采购那里还没有下单, 比如财务还没有审批, 多下的直接在之前还没操作的单里面变化数值; 已经审核或者已经在采购的, 就再下达采购委外单」)：对本操作组最近一条仍可改量的申请明细(`fn_preplan_supply_action_growable`: 申请开着、明细未订货、无任何订货单来源引用——含待财务审核的草稿订货单, 那已经是「在采购」), 把明细数量改大(`increaseProductionDraftLine`), 供给行动的需求量/公共量与各物料行的分摊同步只增不减; 没有可改的明细才另立新行动 + 新申请。带安全补库切片的批次仍走新单。追加后按单据再提醒一次「采购/委外需求追加：单号(追加 N)」。
- 数据库侧 V640 只对「明细仍未订货」的供给行动放开只增不减的改量(三个身份守卫 + 申请明细生产联动守卫共四处锚点补丁, 新增 `fn_preplan_external_item_unordered` / `fn_preplan_supply_action_growable` / `fn_is_preplan_supply_line_growth` 三个谓词), 其余谱系约束一个字节不动。

### 4. 父件 + 下层一起下单：数字全部由服务端算

- 车间通道的种子(顶层 / 自制候选 / 先自制目标件的委外)改本批数量时, 整页向 `POST /{id}/issue-plans/preview` 要一份「真实下达后的快照」——服务端真的跑一遍 `issueWorkshopPlans`, 然后 `setRollbackOnly` 整体回滚, 库里一行不留(计划、链接、命令记录、版本号全部还原; 幂等键被真实下达用过则拒绝预览)。**前向批注(2026-09-24, [ADR-116](ADR-116-物料分析下达预览只读投影.md))**：预览改为只读投影——不取锁、不建计划、不回滚, 用同一刷新引擎算内存投影、同一视图构建器出视图, 结果与真实下达后详情逐字段相等; 幂等键不再使用。整页按这份快照重建下层行：本批备料需求、还需安排、可认领公共在途、建议下单量都是服务端事实；来源「需要数量」不随这次预览放大。
- 下层行「还需安排」= 服务端 `additionalSupplyRecommendedQty`(自制/委外前置自制行 = 锚点剩余可排量); 采购行的建议量在此之上按起订量/整包装抬。
- **已下过单的行仍可追加**(用户口径 2026-09-21 第二轮「即使采购、委外已下达甚至已处理, 父层级那里还是可以追加下单; 已处理时还缺数量是 0, 再填的数量就是额外追加, 属公共的」)：采购 / 直接外发委外行不再因「还需安排 = 0」不可填——默认不勾、不预填, 用户填的数就是追加量, 服务端按超量分账为公共备货(要 `over_supply`); 原申请还没被采购 / 委外处理的(下游引用 `growableLineQty` 非空)直接改到那张申请上, 已处理的另立新申请。已建自制任务的行在锚点余量为 0 时也可再下一批**纯公共备货产出**(`ProductView.canIssueSurplus`, V577 本就允许 submitted 0 + surplus N 的链接; issue-plans 只在行上**明确声明** `publicSurplusOnly` 时放行——不声明照旧 409, 重复点击 / 过期候选不能悄悄多建一张计划), 没建过任务的自制候选不放开(服务端对已覆盖候选拒绝建锚)。下层一行都没有缺口时不再问「只下达父件?」, 直接只提交父件。
- **追加量默认就写 0, 且 0 是合法值**(用户口径 2026-09-21 第四轮)：已下达行的输入框预填 0 而不是留空——勾着不动 = 这一行本次不下, 不再报「必须大于 0」; 提交时把填 0 的行从集合里剔掉, **必须连同 notify 的目标集合一起剔**(带着 actionGroupKey 却不给数量时服务端会按「未指定 = 全量剩余」下达, 等于把用户明确填的 0 翻成全量); 被跳过的行如实提示, 不静默丢。
- **分桶页「已下达」段直接追加**：采购 / 委外桶的已下达行(路线已确认、直接外发)仍可勾选, 「下达数量」格改为「追加量」输入框(默认空、旁注已下的总量), 按钮改叫「追加采购 / 追加委外」, 提交走 notify(`allowExtra`); 下达车间桶里需求已全部转入计划的顶层 / 自制锚点行在「下达数量」格填追加量, 按钮「追加生产计划…」带 `publicSurplusOnly` 进整页(树顶填车间 / 负责人、上限 0 照常过超量确认、下层按放大后的需求一起办)。委外前置自制锚点与自制候选不放开。
- 客户端删除：`material_cascade_quantity.dart` 及其测试(约 1000 行纯计算)、`MaterialAnalysisSupplyLink` 与 `GET /{id}/supply-links`(申请进度联动改由服务端就地追加自动处理)、`additionalSupplyRecommendationKnown` 与「旧载荷回退」(服务端恒定下发该字段, 回退分支只在测试夹具里活着)、`publicExtraQty` 全部拆账逻辑、`_CascadeParentChannel.subcontractMakeFirst` notify 整量接管通道(有子层的委外只走「下达车间」通道; 没有生成生产计划权限的账号在分桶页当面被拦下, 不再有第二条数量语义不同的路)。

### 5. 不变量

1. 一个节点一个计划产出量；子件实际备料毛需求只跟随父件计划产出量(含公共备货产出)，父件计划产出为 0 则子树未下达备料需求为 0。只读 `sourceRequiredQty` 独立从原始来源展开，不被此归零或放大。
   **已完工入库的那部分不计入计划产出量**(2026-09-21 用户口径): 它的下层原料早已领走用掉, 再算一遍会让补做场景凭空多备一整批料——
   某件计划做 10、做完 10、其中 4 件报废使锚点涨到 14 时, 下层原料的「还需安排」是 4 而不是 14。逐条计划链接按
   「本批计划量 − 本计划已完工入库量」计、单条不为负再求和; 已完工入库量沿用 `productPlanStates` 的同一口径(计划明细 `iqty` 封顶到 `qty`)。
2. 「还需安排」只有服务端一个算法; 客户端没有任何 `缺口 − 在途` 的回退。本字段**保持毛口径**
   (需求缺口 − 本分析自己的在途), 它同时是专属在途调入与库存再分配两处的数量上限, 就地改语义
   会静默改掉那两道闸门。
   「再扣掉别人计划里可认领的公共在途、给计划员看净数」这件事**落成独立派生字段**, 随物料分析
   主表改造一起给出, 不动本字段。落它必须按行判断「这一行下达时到底会不会自动认领」:
   自动认领对自制组与需要前置自制的委外组是排除的, 在这些行上扣可认领量会把数做小, 计划员
   照着填就会少下。净数成立的另一个前提是「界面显示的可认领量 = 服务端真会认领的量」,
   所以两侧的候选口径必须一致(2026-09-21 起认领候选已按
   [ADR-101](ADR-101-委外单一子层级按到货解锁与容差自动结案.md) §2.7 收成同路线), 一侧放开就得两侧一起放开。
3. 申请明细数量只增不减, 且只在「未订货」时可改; 一张明细仍只对应一条行动。
4. 自动认领只发生在下达那一刻, 认领量 ≤ 来源可认领量且 ≤ 本次需求量; 认领与新单同命令、同幂等键。
5. 预览与真实下达同一段代码, 预览零副作用。(ADR-116 起: 同一套校验、刷新引擎与视图构建器, 预览只读、不再执行下达写路径。)

## 修订一(2026-09-21 第五轮)：任意层级改量都带动它的子层，我方供料委外件放开超量

用户口径：「我修改下面某个层级的父类, 他的子层级也要对应的修改。以前都实现了, 现在只有最顶层
修改数量下面的子层级会修改」——第一版把客户端那 4000 行相乘逻辑退役之后, 只有树顶那一行的
改量会经预览回到服务端, 中间层改了没人管。本轮补齐, 仍然是「数量只做一次, 在服务端做」。

### 1. 预览请求带上层级表**每一行**填的数量

`POST /{id}/issue-plans/preview` 的请求体新增 `typedOutputs`(物料行 id + 本次填的数量),
`lines` 允许为空(只重算、不模拟任何真实下达)。服务端把每个 `typedOutputs` 并进**该节点的
计划产出量**——子件毛需求本来就按父件计划产出展开(§1), 于是第二层改量带动第三层、第三层
带动第四层, 一路到底。

- 并法是 **已下达计划量 + 本次填写量**, 不是与需求取大：这两项是同一种东西(都是「打算产出
  多少」), 而 `parentPlannedOutput` 随后再与物理缺口取大, 所以「填得比缺口少」(缺口里有一
  部分已由在途顶上)不会把子层抬高, 「填得比缺口多」(超量 / 追加)如实带大子层。
- 节点**自己**的需求量与还需安排量不受自己填的数影响(那是祖先决定的), 没有自反循环。
- 输入框挂在**提交单元**上(同一操作组在树里可能出现多条路径, 只有第一处能填), 所以填的是
  整组总量：服务端按各路径当前需求量的占比拆回节点, 全组需求都是 0 时平均分。不拆的话整组
  的量会全压在第一条路径上, 那条路径的子层被撑大、别的路径纹丝不动, 合计对不上。
- 「顶层供给行」(ROOT_SUPPLY)那一行不走 parentSupply——第 1 层是按**来源行**展开的, 它填的
  数量并到来源的计划产出量上(`typedSourceOutputs`)。
- 树顶走车间通道时照旧**真跑一遍** issue-plans 再整体回滚(锚点、台账、转交状态这些不是数量
  的事实只有真跑才有); 走直接外发委外通道时不模拟下达(它不建计划), 它填的量按 `typedOutputs`
  补进去。父件已提交过的重试模式不再补——那时它的量已经是库里的事实。

### 2. 跟不跟父件, 只看「这一行用户有没有亲手填过」

用户口径第九轮原话：「父类变 2000 子类就变 2000; 假如没有下单立马把父类改回 1000, 子类也立马变回
1000——先操作变数然后立马又变, 这样就跟着父类一起变。但是如果先操作子类、子类变到 3000, 那么就不跟
父类变。如果跟着父类变、但是子类没有更改过, 父类再变也跟着变。」

- **没亲手填过的行**: 它的数字只是父件传下来的回声, 父件改大改小都**双向**跟。为此它的数量
  **不进 `typedOutputs`**——服务端那一侧是「与物理缺口取大」, 把回声送回去只会把子树钉在旧值上,
  父件改小时孙层降不下来(这正是第九轮报的那个 bug)。不送它, 服务端就从父件的新数量一路算到底。
- **亲手填过的行**: 本次按他填的数走, 并且**它下面那一支跟着它不动**(孙层按 3000 算, 不按父件的
  2000)。只有父件的需求涨过那个数时才抬上去并点名; 父件之后再改小, 它退回用户自己填的那个数,
  不会停在替他抬上去的值上。
- 实现上分开记「用户亲手填的数」(`userTypedQty`, 只在非程序性输入、且文本能解析成数时写；
  清空 = 置 null = 交还给系统算, 手滑敲一下再删掉不会让这一行永久脱离跟随)与「当前显示值」
  (`followUpQty = max(userTypedQty, 还需安排)`), 页面按比例换算时也按这条规则逐层走：
  每一层按**它自己那个父行**的变化比例算, 手填过的行天然把链条断在自己这一层。
- `typedOutputs` 送的是 `userTypedQty` 而**不是框里显示的数**：显示值可能是按比例换算出来的、
  或按下限替他抬上去的。服务端那一侧 `add + max` 是单调向上的, 送一个放大过的值上去它就成了
  整棵子树的地板, 回来又被子层原样采纳, 再也降不回来(这是第九轮那个 bug 的第二个入口)。
- 页面先行换算的分母是**服务端那份快照当时按的数**, 不是上一拍键入的数：真人是一位一位退格
  改数的, 逐拍相乘时空框那一拍没有比例可算, 丢掉的一档补不回来。从快照出发是幂等的, 退格
  改回来与全选重打逐字一致。树顶还空着时不发重算(那会拿到一份「什么都不下达」的快照把基准
  换掉), 去抖这 300ms 内禁止提交(屏幕上是估算值)。预览失败时数字与输入框文本一起退回上一份
  服务端值。
- 叶子行(下面没有层级)改量不回服务端要重算。

### 2.1 屏幕上的数字不等服务端(2026-09-21 第六轮)

用户口径「输入框输入的时候对应的子层级就要变化, 不是等到确认后; 变化太慢了」。服务端那份
重算再快也要一个来回, 所以页面**每敲一下就先按比例换算**下面每一层：本行从 1000 改到 2000,
它下面每一行的本批需求翻一倍, 已被覆盖的部分(现货 / 在途 / 已下达)是不变量, 「还需安排」=
新需求 − 原覆盖量。这与服务端那份在常见情形下逐字一致, 个别情形(起订量抬量、锚点配额、
包装取整)以服务端为准——300ms 去抖后要回来即整体覆盖。

这不是把 ADR-099 的「客户端不再算量」翻回去：估算值只用来**显示**, 提交的数量与「还需安排」
的权威口径仍然只有服务端一个; 等服务端那份期间「一键下单」禁用(估算值不可能被提交),
重算失败时估算值立刻退回上一份服务端数字并如实报错。原数量为 0 的行没有比例可言, 照旧等。

### 2.2 来源数量改回来时, 自制锚点的配额也要回落

`growMakeAnchorQuotasAfterSourcePreview` 原先只有加法, 而写 `MAKE_COMPONENT.requested_qty` 的
四处全是加法, 唯一的减法只走供给行动的撤回链路——于是把来源数量调高再调回来(**已提交的刷新
端点**, 不是预览), 锚点永久停在高位, 子件那一行的「还需安排」再也降不下来, 只能删掉整条分析
重建。本轮补一条对称的回落：只退**从来没下达过**的那部分(地板 = `submitted + approved`, 与
`cancelMakeDemandRow` 同一道地板), 行动背书的锚点仍归撤回链路, 退到 0 不在这里做(那是「这条
子件任务整个不要了」)。同一条 UPDATE 里要把齐套列(`ready_*`)压回新配额的余量内, 否则撞
`production_material_analysis_item_qty_chk` / `..._stage_ready_qty_chk`; 紧跟着的那次刷新会重算它们。

### 3. 提交顺序按层级自上而下

一键下单改成：**车间段按层级从浅到深逐层下达** → 采购 → 直接外发委外。父行的计划先落地,
下一层的锚点配额与需求才是真的; 顺序反了会把深层按新数量填的量当成超出当时需求的部分, 记成
公共备货产出而不是本需求。直接外发的委外放最后, 是因为它一下达, 我方供料的那颗子件就转由
委外申请负责、需求归零, 必须先把子件下掉。

### 4. 我方供料的带 BOM 委外件放开公共超量备货(V641)

用户实测「V4开关面板(喷油)」(ADR-085 单一叶子子件件)在分桶页不能超量, 提示「最多下达 1000…
需要超量下达权限」, 而给了权限也下不了——客户端裁决、服务端 `ownSupplyBom`、数据库
`preplan_public_surplus_subcontract_leaf_guard` 三层都在拒, 理由都是「多下的量会凭空多出一份
无人负责的子件需求」。本轮既然任意层级的量都能带大子件需求, 这条理由不成立, 三层一起放开;
数据库侧 V641 同时放开运行时超订容量 `fn_preplan_direct_overorder_capacity`(否则放行的公共量
会在委外订货审核撞 23514)。`over_supply` 权限照旧要。认领侧(吃别人的公共在途)不在本轮范围。
