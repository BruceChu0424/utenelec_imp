# 公共运行时设置实际生效

状态：源码候选及定向验证完成；尚未提交、发布或安装。承接 W09 / R2.03 / R6.03 的局部子项，不代表全部设置消费者验收完成。

## 问题与改动

服务端已登记并下发 `badge_poll_seconds`，客户端也解析了字段，但徽章实际轮询仍写死为60秒。管理员保存该设置也没有触发公共设置重读，造成保存值与实际行为不一致。

复用 `IdleTimeoutGuard` 原有的登录读取、每5分钟读取和本机保存刷新信号。公共设置仓库把成功结果发布给同一身份及服务器内的消费者，徽章按新周期重新安排下一次读取，保留已有数量，不因设置变化再打一轮计数请求。不新增后台轮询器。公共设置并发读取合并为同一个在途请求，完成或失败后下一轮仍可重新读取。

管理员本机保存徽章周期后立即触发既有公共读取入口；别的客户端在下一次既有公共设置刷新后生效，最多约5分钟加请求耗时。设置尚未取到时保持原60秒默认，非法周期不启动密集请求；页面隐藏、批量办理暂停、单飞、退出及身份更换合同继续保留。

仓库回写同时核对存活状态、身份和服务器，旧请求不能覆盖新快照或附件上限。空闲守卫应用阈值时也核对原身份及仓库实例，避免换账号后旧请求迟到而覆盖新阈值。独立构造仓库的原附件限制更新合同保留。

新增回归覆盖90/15秒实际计时、默认周期、保存后的刷新信号、并发读取、读取失败后重试、在途改周期不重复请求、切身份/换服务器/退出后的迟到设置响应，以及空闲守卫旧阈值保护。既有隐藏、退出、批量暂停、徽章失败保留计数与空闲超时测试一并通过。

独立复核发现：保存发生于旧GET途中时不能继续复用旧请求；开始刷新时应取消既有轮询计时器，避免慢请求被过期计时器标记为还需补读。保存信号的现有监听入口先使旧仓库失效再读取；旧快照保持到新响应，旧在途响应不得发布或应用。采用显式失效是因为仅由仓库watch同一信号，会受监听通知顺序影响，实测仍拿到旧实例，失败记录保留。

本机证据：主工作区 `.local-tmp/runtime-settings/verification-reviewed.log`、`analyze-reviewed.log`；文件哈希另存 `verified-files.json`。两反例红灯为`review-counterexamples-red.log`；中间通知顺序失败为`verification-final.log`；初轮33项日志为`verification-first.log`，不能当作最终35项证据。本改动不改变页面布局，无新增视觉控件；UI视觉证据仍按对应页面的独立记录维护。
