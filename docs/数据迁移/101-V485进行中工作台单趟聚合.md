# V485 进行中工作台根视图 · 单趟聚合重构（性能）

- 版本：V485（`V485__execution_workbench_roots_single_pass.sql`）
- 日期：2026-09-05
- 性质：纯视图重构（`CREATE OR REPLACE VIEW`）；**零表/零列/零数据改写**，输出列与业务语义与 V470 完全一致。

## 背景

「生产调度与进度 → 进行中」列表（`GET /production/execution-workbench`）在真实数据量下
加载数十秒。根因是 V470 版 `v_production_execution_workbench_roots` 的聚合结构：

1. `roots` 先取**全部历史**分析/根计划（不做未结案预过滤）；
2. 每个根对重型段视图 `v_production_execution_workbench_segments` 做 **6 次独立
   LATERAL 扫描**（段计数/关联订单/工单号/车间/产品/数量摘要各一遍），最后才在
   WHERE 里过滤已结案根——O(根数 × 6 × 段视图)；
3. 服务端每次请求跑 COUNT + 分页两遍，前端大类行计数（size=1）再打一遍，
   单次点击最多 4 次全量视图求值。

## 改法

保持段视图不动，把 roots 视图重写为**单趟分组聚合**：每类事实对段视图**全局
GROUP BY 一次**（segment_rollup / sales_order_rollup / workshop / product /
color / quantity 六个 CTE，窗口函数取前三预览），再按 (root_type, root_id)
join 回根清单；数量摘要的无段分析根回退反连已算好的 segment_rollup（不再逐行
探测段视图）。demand/action/plan 三个逐根 LATERAL 保留（只碰有索引的基表）。

## 实证（容器 scratch 库，同库同数据先后应用新旧视图）

- 种子：300 分析 / 300 计划 / 300 执行段 / 600 销售分摊（含已结案根）；
- 旧视图：COUNT **5969ms**、按完工日期排序取 50 行 **5314ms**；
- 新视图：COUNT **88ms**、同页查询 **66ms**（约 **70 倍**）；
- 等价性：`SELECT * EXCEPT` 双向均为 0 行、300=300 行完全一致。
