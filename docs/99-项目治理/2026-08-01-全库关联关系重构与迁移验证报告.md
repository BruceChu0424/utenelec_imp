# 全库关联关系重构与迁移验证报告

> 日期：2026-08-01
> 范围：货品/BOM、基础主档、销售、采购、委外、库存、生产、财务、组织人员、名称缓存和 legacy 重导
> 最终判定：**NO-GO**

## 一、结论

第一批边界清楚的实时关系已经修复并验证：

- 当前 BOM 通过 component_goods_id UUID 指向组件货品；组件改名后重新读取会显示新名称。
- 销售订单通过 client_id UUID 指向客户；客户改名后当前运营视图会显示新名称。
- 货品及 BOM 已形成“UUID 真源 + legacy 溯源”的双写闭环。
- 销售报价/订单保存和审核会复验客户、货品、单位、软删、停用、迁移占位及 owner scope。
- 库存 worker 属于 B_Worker，maker/approver 属于 Sys_Operator，不再按相同整数误连员工。
- 报表双键 JOIN 已改为 UUID 优先，只有 UUID 为空才允许 legacy fallback。
- Flutter 嵌套 BOM 使用实际所属父件 ID，名称缓存按登录会话隔离。

但“改一个名称，所有地方都变化”不是正确的全局规则：

| 数据语义 | 改主档后 | 例子 |
|---|---|---|
| 当前实时关系 | 应显示新值 | 当前 BOM、选择器、主档详情、运营列表、草稿 |
| 历史快照 | 不应回溯修改 | 审核单重打印、成本、价格、汇率、税额、审核/发布人 |
| legacy 溯源 | 不作为运行时真源 | 各类 legacy ID、旧操作员整数、来源单号 |

当前仍有历史成本漂移、软删除逻辑孤儿、分类树移动路径错误、多态来源不可证明、跨模块校验不统一和审核身份快照缺失，不能宣称全库关联已经完成。

## 六、已落地规则

### 6.1 货品/BOM

- goods：unit、color、mould、client、defaultSupplier、secondarySupplier 六条 UUID 关系。
- goods_bom_items：color、defaultSupplier 两条 UUID 关系。
- UUID 非空时只按 UUID 解析，并回写 canonical legacy ID。
- UUID 为空时才按唯一 legacy ID fallback，并同步写 UUID。
- UUID 与 legacy 显式为空/0 才清空；字段未出现时保留旧关系。
- V181 的 auto_created 历史锚和 operationalRows 门禁保留。
- 新增/替换组件必须 active + visible；旧组件停用后仍可删除或替换。
- 越权组件保留可清理的关系 ID/数量，但名称、编号、规格、颜色、单位、供应商和来源类型全部脱敏。

### 6.2 销售和权限

- 报价/订单在保存和审核两次校验客户、货品和单位。
- 客户字典按 owner scope 过滤。
- 报表 UUID 优先，UUID 为空才用 legacy fallback。

### 6.3 库存人员

- worker_legacy_id 只表示 B_Worker.ID，可映射员工 UUID。
- maker_legacy_id/approver_legacy_id 只表示 Sys_Operator.ID，不映射员工 UUID。
- V182 增加 maker_name_snapshot/approver_name_snapshot。
- 当前 maker/approver UUID 可以指向员工；历史 UUID 为空时回退操作员姓名快照。
- 恢复副本有 55,482 张仓库单据；maker legacy 48,853、approver legacy 55,414、worker legacy 42。
- 因没有绕过 manifest 重跑 CSV 导入，恢复副本的 maker/approver 快照仍为 0，仍需 post-import reconciliation。

## 八、生产 NO-GO

### P0：历史成本漂移

- 总账成本结转、财务成本报表和 DRAW 材料费仍使用“历史数量 × 当前 goods.c_total”。
- 12,113 张已审核发货、90,881 条明细中，88,534 条命中当前非零成本。
- cost_amount 有 76,571 条为 0，仅 14,310 条非零；88,413 条与“数量 × 当前成本”不同。
- 新单 costAmount 仍可由客户端提交，审核没有服务端权威估价和冻结。

要求：审核时服务端生成不可变 COGS 快照，记录估价方法、as-of 和来源版本；GL 重放只读快照。

### P0：软删除逻辑孤儿

- MaterialCategoryService 会级联软删分类子树及货品，违反关系规范。
- 客户、供应商、颜色、单位、仓库、岗位等删除缺全引用图守卫。
- FK 无法阻止软删除。

要求：统一 ACTIVE/INACTIVE/RETIRED/HISTORICAL_ANCHOR；被引用主档只能停用，删除必须先做 impact preview 和显式确认。

### P1：分类/部门换父级

> 2026-08-02 收敛：部门及物料/模具/客户/供应商四类分类已在真实换父前获取各自事务级 advisory lock，防环后以单条递归 CTE 按 parent 链重算整棵 `level/path`（含软删后代），不再依赖旧 path 排序；同父级请求不重算。代码合同测试已覆盖，真实 PostgreSQL 并发集成验收仍待补。

- 已修复：path 触发器只重算当前节点、不级联后代。
- 已修复：relevelSubtree 对子树外的新父级深度计算错误，并按旧 path 排序。
- 仍待办：现有更新契约以 `parentId=null` 表示“不改父级”，尚不能可靠移动到根。

剩余要求：在真实 PostgreSQL 上验证 A↔B 并发移动互斥、含软删后代移动后的路径不变量，并另行设计显式“移到根”语义。

### P1：多态来源不可证明

stock_movements、库存预留、GL、AR/AP 等 source_doc_type/source_doc_id 不是 FK，可能产生孤儿或类型错配。

要求：建立 document_identity 注册表和复合 FK，或使用分类型 deferred trigger 加周期性完整性审计。

### P1：跨模块校验不统一

- 销售报价/订单已覆盖客户、货品、单位。
- 采购仍有 legacy 基本单位路径。
- 委外申请和手工行缺主档状态复验。
- 库存审核未统一复验 supplier/client/warehouse/goods/unit/人员。
- currency、payment style、seller、color 尚未统一进入验证 port。

要求：所有模块在 save + approve 两次调用统一主档验证边界。

### P1：审核身份快照缺失

销售、采购、委外、库存历史报表大量 JOIN 当前主档，旧审核单重打会显示今天的名称。

要求：审核时冻结 party/goods/spec/unit/color/address/tax 等身份快照；运营显示当前值，重打印显示当时值，详情并列展示。

### P1：未统一 ID

- 销售多类单据 payment_style_id 仍是无 FK 整数。
- 一些人员 UUID 没有 FK。
- 财务 settlement_type_id 没有明确目标约束。

## 九、全量重导门禁

- export_manifest.sha256

3. 按主档、业务单据、流水/余额、生产成本快照顺序导入。
4. 运行 post-import reconciliation；来源关系必须等于精确映射加 reject。
5. 核对 maker/approver 姓名快照 48,853/55,414 覆盖。
6. 修复 320 条 reject 或经人工确认保持隔离。
7. constraint validate、权限、性能和 UAT 全部通过后再切流。
