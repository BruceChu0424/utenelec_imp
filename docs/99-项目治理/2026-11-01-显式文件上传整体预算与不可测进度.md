# 显式文件上传整体预算与不可测进度

本项在`d66e3a1bdf99f1540cf05c57514c60a28140374c`隔离分支追加，基础主链仍为238d。保留前项焦点修复，不改main、产品版本、公共SDK、锁文件、权限或next UI 877。使用frontend-design保持现有Uten页面和进度组件，仅修正传输合同及无法测量的状态表达，不混入默认归属、布局、选文件或草稿交互重做。

## 真实证据和根因

正式39双包上传中，Installer为37,232,545B，ZIP为49,672,427B。09:58:09 UTC只读采样中，09:54:06创建的Installer原DRAFT已有30,949,182B临时文件，说明服务端确在持续接收，不能因界面0进度判定未传输。后续Installer已发布，ZIP结果未知后按原ID GET核对仍为无文件DRAFT；不能新建ZIP身份或按状态猜提交成功。

原公共ApiClient为客户端包配置send=30分钟、receive=5分钟。Web WriteDeadlineInterceptor将connect提高至receive；Fetch无法独立观察建连/发送完成，又取connect/send/receive最短值等待headers，实际把整个慢上传提前压到5分钟。IO有分阶段信号，原30/5配置语义不同。

同类源审：AI原文件提交经`postBytes`设置send=3分钟、receive=60秒，也会遇到相同短接收截止；货品导入/BOM导入共用postBytes，报销与成本OCR共用postMultipartFile。只改客户端包端点会留下公共文件入口不一致。

进度的另一个事实是Fetch没有wire-upload进度事件，原adapter只通知起始0和响应headers后的完成。原发布队列把起始0当作可测比例，确定进度条因此停在0；不能据临时文件、经过时间或本地预读字节编造网络百分比。

## 公共合同与完整生命周期

三个显式文件API统一登记`fileUploadOverallTimeoutKey`，通过同一`fileUploadOverallTimeout`入口取有效send+receive，缺省/关闭阶段值按现有有限默认值参与计算。客户端包为35分钟，AI当前为4分钟。IO继续接收原connect/send/receive配置，不改其阶段预算。

| 入口 | 适用调用方 | 保留的差异 |
|---|---|---|
| `ApiClient.postBytes` | AI原文件、货品/BOM导入原文件 | 原文件名/内容类型头、原字节、来源及各自receive值 |
| `ApiClient.postMultipartFile` | 报销发票、成本OCR | 原multipart边界和文件内容；原独立receive覆盖 |
| `ApiClient.uploadClientPackage` | Web/现有Flutter桌面发布队列 | 原releaseId、expected SHA、大小、禁止安全重试；原30/5 IO阶段 |

Fetch只对该显式文件合同使用一个有限总预算，从requestStream预读开始，经过上传、等待headers，持续到最终response body结束。普通JSON、读请求及非此文件合同仍取原最短phase deadline；WriteDeadlineInterceptor未改行为。

- 整体到期会真实AbortController.abort，并以明确整体上传超时结束；不是只调长header timeout。预读流会取消，headers后的body继续受同一预算约束，不重新起算。
- 完成、空body、token取消、body读取错误/关闭、整体到期和强制close均释放对应timer/controller登记。强制close在尚未进入Fetch的预读阶段也立即中断流，不能只取消timer后让预读继续等待。
- 继续使用Fetch的`redirect:error`、原credentials/no-store、原认证/审计/读范围拦截器及无自动重试。显式文件即使调用方误留followRedirects=true，也不能落回会跟随凭据重定向的XHR。没有改服务器catalog或复制目录发布。
- 发布进度初值、每次原ID重传开始、零字节或未知total均为null，现有LinearProgressIndicator自然显示不定进度；实际正字节回调才计算比例。成功/未知提交、冻结元数据、原ID GET恢复、已成功不重传和身份撤销边界保持原样。

WPF候选读取核对：原`ClientReleasePublishCoordinator`是独立30分钟整体CancellationToken及真实流式进度，不使用Fetch最短headers截止，故不存在此同源Web缺陷。本项不继续Win7开发/测试/打包，不改变其候选和未验收事实。877仅只读比较，仍含原progress=0；没有从中合并代码，也没有修改该分支。
