## 一、用户口径(2026-09-22)

> 物料分析准备页面，追加的自制件，生产车间没有去领料开工的前提下应该自动合并啊。现在都是追加的都单独列，没有自动加到对应的单里面。采购好像是对的，就会自动加到一个单子，因为之前的单子没有去执行；没有执行那么可以自动加数量进去，但是如果已经开始执行了就创建新的单据。生产件一样的就放到一起去，或者一个计划单的。

## 二、问题

采购/委外自 V640 起就地追加：申请明细还没被采购/委外部门动过时，追加量直接改到原申请明细上。自制这边没有对应物——`MaterialAnalysisCommandService.issueWorkshopPlansInternal` 对每一行**无条件** `createDraftPlan` 新建一张生产计划，同一锚点(顶层产品行、自制子件锚点、要先自制目标件的委外锚点)每追加一次就多一张单。库侧五道守卫把已建计划的数量钉死：

| 守卫 | 钉住的量 | 出处 |
| --- | --- | --- |
| `fn_guard_material_analysis_plan_item_identity` | 计划明细 qty | V234，V614 只放行日报定稿封顶 |
| `fn_sync_material_analysis_plan_link_qty` | 关联行 submitted_qty / public_surplus_qty | V490 / V577 |
| `UNIQUE(plan_id)` | 一张计划一条关联行 | V234 |
| `fn_guard_production_planning_draft_append_only` + `ProductionPlanningDraftService.save` | 预排草案载荷；分析计划不允许改写草案 | V191 |
| `fn_validate_production_execution_segment` | 执行段 planned_qty | V155 / V524 |

## 三、决策

### 3.1 什么叫「还没开工」(库侧唯一判据 `fn_material_analysis_plan_growable`)

计划未删除、未取消、未中止、未结案；草稿或已审核；恰一条计划明细且完工 / 入库 / 封顶累计全 0；没有报工；没有拆批；每一段仍是 WAITING / READY；每张备料单(DRAW)仍是未审核、未发料、未删除的草稿；已审核时有且只有一个 CONFIRMED(执行模型 1)计划包。

判据与撤销计划包(`ProductionPlanningPackageService.closeExecutionSegments` 只放 READY/WAITING、`closeDraw` 只放 status=0 且 issued_qty=0)同源：能整包撤销的计划就是还没开工的计划。派工(DISPATCHED)、开工(IN_PROGRESS)、备料单审核/发料、报工、拆批任一发生即算开工。

### 3.2 并入的形状

- **同一单号**：计划头不动。计划明细 qty 加追加量；关联行同一行 submitted_qty 加归需求份、public_surplus_qty 加公共备货份(V645 放行，只增不减；关联行触发器顺手把分析行 submitted / approved 与分析版本推进)。
- **草稿计划**：预排草案作废重排(`supersedeActive` + `savePlanningDraft`)；请求带「立即审核」时整张(含此前草稿量)一起审核。
- **已审核计划**：不改任何既有执行段、冻结需求、预留、备料单——它们是已冻结的执行事实，与 V640 不碰「待财务审核的草稿订货单」同一条纪律。追加量在同一个 CONFIRMED 计划包里**另起一段**(`ProductionExecutionPackageCommandService.appendSegment`，与拆批同形态)：段号顺延、有料 WAITING / 无料(DIRECT_MAKE)READY、自带冻结的物料需求与耗用规则、路线等车间确认后按齐套提升。销售来源的计划先 `ProductionPlanService.growAnalysisPlanSalesAllocation` 把排产关联容量与订单行 planned_qty 各加归需求份(公共备货份不进订单侧，与审核时同口径；纯公共备货计划此时补建关联)，新段只分摊归需求份。
- **两条应用侧口径**：请求指定了生产车间时车间必须一致——换车间就是另一张单；没带「立即审核」的请求只并入草稿计划，不能把追加量悄悄并进一张已审核的计划绕过审核(客户端 approveNow = 持有生产计划审核权限)。
- 同一分析行有多张可并入的计划(历史数据)时取最近一张(关联行 created_at 最新，与主表「查看计划」同口径)。

### 3.3 不做什么

- 不改原执行段的 planned_qty(需要重写冻结需求 / 预留 / 备料单，等于改写已冻结的执行事实)。
- 不用「撤销原计划包 + 红冲 + 新建合并量计划」替代(单号会变，用户口径是「加到对应的单里面」)。
- 不放宽 V577 的「排满后不声明 publicSurplusOnly 照旧 409」；并入只是落点变了，数量分账(归需求 = min(填的, 剩余)、其余公共)不变。

## 四、契约

- `POST /production/material-analyses/{id}/issue-plans` 请求不变。`GeneratedPlan` 新增 `mergedIntoExisting`(并入了已有计划) 与 `appendedQty`(并入的追加量；幂等重放为 null)；命令回放记录 `mergedPlanIds`。
- `issue-plans/preview` 走同一段代码后整体回滚，预览自然反映并入后的下层数量。
- 客户端：单张结果弹层标题「追加已并入原生产计划」、计划单旁「本次追加 N 已并入原计划」；多张列表同款副标题；成功提示「追加数量已并入原生产计划单，车间按同一张计划继续」；主表分段回报「下达车间(第 N 层，M 行，其中 K 张并入原计划)」。

## 五、验证

- 真库 E2E `PreplanPlannedQuantitySingleEntryEndToEndTest`：`appendingOnAnApprovedNotStartedPlanGrowsThatPlanInsteadOfCreatingAnother`(明细 600→1000，关联行同一行，包里两段，幂等重放仍标记并入，排满后纯公共备货 200 仍并入并把子件需求带到 1200)、`appendingAfterTheWorkshopStartedProductionCreatesANewPlan`、`appendingOnADraftPlanGrowsTheDraftAndALaterApprovedAppendApprovesItAsOne`、`salesRootAppendGrowsThePlanItsOrderAllocationAndPlannedQtyUnlessTheWorkshopDiffers`；既有「第二批另立一张」的用例改为并入。
- `MaterialWorkshopAnchorEndToEndTest`(计划头与计划包不改写、原执行段与原物料需求一字不动、只多一段)、`FullChainEndToEndTest.materialAnalysis_splitFixedBatches…`(第一批 READY 备料单草稿未发料 → 第二批并入同一张、新段 WAITING 没有备料单)。
- `MaterialAnalysisPlanGrowthMigrationContractTest`：V645 只新增四个函数与一条对账触发器、三处锚点补丁、「未开工」判据逐条在场。
