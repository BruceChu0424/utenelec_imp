# 2.5.6 候选验证与发布依据

本页对应 2026-10-06 提出的九项复核任务，以及 2026-10-07 追加的数量完整性、AI 使用授权、实际超限报工、人员选择、人事账户支持、工作台和计划提醒要求。实现版本 2.5.6，源码迁移 V825/751。本文随候选提交，最终提交、CI、签名制品与服务器激活分别以 GitHub 的 v2.5.6 标签、对应 Actions 运行和更新器现场回执核验，不能用本地测试代替发布完成。

2.5.3 候选的代码 CI 曾全部通过，但签名构建被过时的 Flutter 包元数据常量拦截，未进入签名和 OSS 上传，也未安装到公司服务器。其标签保留为失败候选依据。追加核查又复现了数量精度与高危授权缺口，因此按最新要求将后续修复统一纳入 2.5.6，不把旧候选绿灯视为新提交通过。候选开发期间曾以 2.5.4 规划（工作分支名沿用该号），2.5.4 与 2.5.5 从未发布，最终发布定版 2.5.6。

AI 操作记忆是本人有界操作记录，不能替代权限，也不代表模型在线训练。打开表单、识别填入与正式保存/审核是不同阶段；仍须沿对应业务确认与服务端授权执行。

文件能力还取决于实际模型：表格与文字 PDF 可以先在本地提取内容，销售图片和扫描 PDF 则需要真正支持视觉的模型。单张报销图片另有本地 PaddleOCR 路径。模型配置存在、OCR 健康端点可达、代码回归通过，均不能单独证明实际文件识别成功；运行配置与真实调用验收分别核对。

部署前在旧版 2.5.2 上另做了有界组件核验：默认文本模型沿实际协议、密钥解密和传输链完成一次无业务内容的请求，HTTP 200；本地 OCR 对合成图片完成一次真实推理，五个预设文本片段均识别成功、进程未重启。OCR 初始化仍有可选 ccache、模型参数覆盖和线程库兼容提示，未为消除日志而安装依赖或调整运行参数。这些结果不能代替新版本真实账号的完整业务文件验收。

## 数据库升级演练

发布前只读核对公司服务器运行 v2.5.2，Flyway V811/737、readiness UP。将其 28,831,520 字节 custom dump 恢复到本机独立 PostgreSQL 16 容器，保留角色名、对象所有者及授权关系，使用迁移身份进行前向升级；没有把本机数据库覆盖公司库，也没有执行公司业务清空。

V812 至 V820 共九个迁移已在该副本通过，746 个历史/新增迁移校验通过。带历史 NULL 归属日志的 V814→V820、已应用 V815→V820 及迁移失败回滚另有真实 PostgreSQL 回归，原日志逐行保持不变。逐表行数及排序行摘要对比仅出现权限目录、授权纪元、迁移历史、相应追加审计及四张新增空表；业务数量、金额、人员及来源表摘要未变。原始备份和包含现场标识的摘要只存本机，不提交仓库。

同一副本追加执行 V821 后，747 个迁移校验通过、失败数为零。逐一比较 492 张表，其中 486 张行数和排序摘要完全相同；仅权限目录、页面关联、授权纪元、迁移历史及追加审计六张表变化。业务数量与来源表、部门授权、个人覆盖、管理者委派均未变化，已有三项 AI 部门授权保留；AI 使用权限不再自动授予全员。

合入超限报工和计划提醒后，重新从同一原始备份创建独立副本，以非超级用户、无 BYPASSRLS 的数据库所有者 `uten_migrator` 完整执行 V812–V825 十四个前向迁移；751 项校验通过、零失败，Flyway 日志无 WARN/ERROR。按原 488 张表、8318 个原列核对，482 张表的行数与排序摘要完全相同；六张变化表仅为权限目录、授权纪元、迁移历史和追加审计。原 737 行迁移历史及原 1162 行当月审计另做摘要复核，内容不变；六张新表为空，历史通知的新阶段字段为 NULL。角色属性、成员关系及所有权保留，没有删除原表/原列或改变原列类型。演练未启动 ERP、AI 或业务调度，未更改公司库或本机开发库。

副本中只剩一份已完成的测试产品分析，未见截图对应的旧分析及 600/400 重复单据。因此原截图的历史处置不能据此确认；新增隔离回归覆盖两来源各 100、先下 400 的 BUY 与 MAKE 供给路径。历史正式单据若已存在重复，必须核对审核、领用、入库后沿原撤回链处理，不能直接删行。

2026-10-07 用户追加截图已确认来自本机开发页面。只读核对发现：三个测试产品各需 1000，封箱胶各需 0.5，物料档案无最小订货量或倍数限制；界面校验却把合计 1.5 取整为 2。另发现汇总比例没有沿用已下单只读条件、4000 总单量与 3000 来源份额/1000 公共份展示不清，以及共享父件继续办理后零需求来源进入待办。后续五项底部物料实际已有共享制造、采购或委外记录，但分配挂在共享来源，页面仍从原产品路径取关联而显示“勾选后下单”和保障 0/0。这些问题作为封版阻断，须用同顺序场景补回归后更新本段，当前不能标记已经修好；没有重复下单或直接改写原记录。

2026-10-07 晚收口：上述封版阻断已全部修复并按同顺序场景补齐回归（material_analysis_policy_cases / material_analysis_quantity_presentation_cases / material_analysis_shared_source_cases 三组新增用例与本文件全量 168 项同跑通过）。要点：产品行与汇总格的下单红框下限统一为 10^-4 tick 精确比较（0.4999 < 0.5 差一个 tick 也红、万亿级大数不进 double、来源事实不可解析 fail closed 冒红）；自制行差一个 tick 的悬浮提示按精确差值给出「少 0.0001」；锚点/委派子行下过 0.0001 即锁定车间负责人指派（非自制行不继承父件共享批次的已下达状态）；剩余 0.0001 按私有需求提交、不再被 0.0001 容差判成纯公共备货；公共可用量恢复预算优先口径（未选中态也走 draft budget 投影，池余量随选中/取消/清空实时增减，来源行显示「—」、共享池只在汇总行计一次，已下单合计按「已下单 4000 = 需求份 3000 + 公共备货 1000」拆分明示）；83.3334×3 这类服务端定点分摊尾巴按「来源数个 tick 噪声预算」最粗守恒整分（84/83/833、合计与下限 1000），而 0.5×3=1.5 的真实分数需求不在预算内、保持精确——两条用户口径由 coarsestAggregateScale 统一，整分只向下取整不再上浮。

客户不可见的本机诊断是同名的两个员工身份：旧身份持有客户/货品，登录账号绑定的另一身份没有这些归属。本轮改进人员选择中的身份辨识与权限边界，没有按姓名合并人员、自动转移客户或扩大账号权限；业务归属迁移仍须走正式交接流程，不能把选择器修复写成历史归属已转移。

## 验证与发布口径

- 前端源码和测试静态分析无问题；本地全量 Flutter 6,471 项通过、55 项按平台条件跳过。人事/权限、通知、清空及 AI 专项真实数据库结果分别记录于本机日志；后续修改追加定向回归，最终统一质量门与完整数据库分片以冻结提交汇总。
- Windows 无法执行的 Linux 部署/进程锁场景在 Linux 容器和 GitHub Linux 作业验证。浏览器 IndexedDB 测试单列 Chrome 门，不能用原生存储测试代替。
- 官网静态来源及本机 SQLite 中共 75 个 raw 图片引用均存在；这证明清理未破坏这些已检查的引用，不替代独立网站运行环境的内容验收。
- 正常业务拒绝、对抗测试主动触发约束错误、首次测试库创建管理员提示与真实服务启动告警分开核验；不关闭警告、不删失败用例来制造通过。
- 新一轮依赖数据库把 Spring MVC 6.2.19 标记为 CVE-2026-47890 / GHSA-j9f9-w8pj-32f8。[上游公告](https://spring.io/security/cve-2026-47890/)明确要求应用通过 SSE 向客户端发送视图片段；当前服务器没有 SSE、视图片段或 WebFlux 路径，AI 对话采用任务轮询。仅对该编号记录到 2026-11-06 的不适用例外，由 `NoSseViewFragmentsUsageSourceScanTest` 守住源码及资源前提，到期恢复拦截。组件仍为 6.2.19；官方 6.2.20 修复仅供企业支持，公开修复为 7.0.9，不能在现有 Boot 3.5 中单独替换 Spring 大版本。已有 XSLT 不适用例外另按其原范围与期限管理，其余漏洞继续阻断发布。
- 合并后的完整 CI 暴露了人事核对测试数据的随机碰撞：共享数据库的多个场景使用同一证件前缀与有限随机尾码，导致过期清理用例在准备员工时触发唯一约束。改为确定性的独立场景身份范围，并以固定输入复现原来的 `23505`，同时验证旧证号与升位候选均隔离；生产唯一约束和业务代码保持原样。
- 2.5.6 初始候选的数据库分片还暴露徽章对账用例与其他 Spring 上下文调度共用数据库的问题：两次读取之间新增了通知。该用例改为独立、完整迁移的 PostgreSQL，保留五项原断言，先关闭 Spring 调度/连接池再回收容器；五项通过，关闭阶段没有连接已关闭告警。历史失败不能用于证明后续合并提交已通过，最终 SHA 必须重新运行全部质量门。
- 2.5.6 数量核查把界面原始十进制输入、分单请求、默认量的权威事实和预览贡献证明分别验证，不能将已解析成 double 的投影倒推成精确值。合法最小量 0.0001 不得当零跳过，单位比例保留六位；单行菜单与批量入口共用有效来源筛选。汇总下单的历史回执读取改用精确十进制，避免首次正确、重复读取却丢小数；销售报价、采购审核与普通物料回放的同类 JSON 入口另行核查，分别已有精确文本或仅处理身份字段。库存估算与实际写入的数量合同分开，当前业务库未因这些回归测试生成或改写单据。
- 日报真实输入框复现 `9999999999999.9999` 在预览前被转为 `10000000000000.0`，现保留输入原文及只读精确事实，预览/创建均使用同一值。去向分配改为 BigInt 万分位，验证直送 `9999999999999.9998` 加入库 `0.0001` 守恒，接收上限跨行共用。旧大数草稿保留输入并要求人工核对，程序赋值不视为已确认。相关六文件 171 项 Flutter、四项 Jackson、十项实际 JavaScript 精度检查通过；六位单位比例另按其精度边界验证。
