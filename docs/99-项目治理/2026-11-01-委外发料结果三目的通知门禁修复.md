# 委外发料结果三目的通知门禁修复

同一个 `SUBCONTRACT_OUTBOUND_COMPLETED` outbox 事件由现有 producer 生成三种通知：委外制单/领料人的普通结果回执、原物料分析负责人的普通供料回执、仓库的预计回厂行动卡。原精确事件门禁仅识别 `warehouse_inbound:view + warehouse_inbound:stock_in`，因此已有真实 `subcontract_order:view + subcontract_order:draw` 的经办人也被误过滤；不能给他们追加无关入库权限来让测试通过。

新增一个共用 purpose helper，以现有 producer 的结构分类，Java 投递与 Repository 分页前 HQL 使用同一合同：

- 普通订单回执：`workflow` / `NORMAL` / 单人定向 / 无聚合与来源修订 / 精确订单 UUID 路由。
- 普通分析回执：同上，精确分析 UUID `/summary` 路由。
- 仓库行动：`task` / `NORMAL` / 单人定向 / `SUBCONTRACT_ORDER` 聚合 UUID / 原固定预计到货路由。

普通两类使用各自既有路由的实际操作资格，仓库继续使用原 ActionCatalog、对象状态函数和物理仓范围。未知路由、类型、聚合、修订或受众形状 fail closed；仅 VIEW、公司资料库全写与超管隐式镜像均不因此获得其他业务资格。

普通和聚合发布重载统一先建立完整 metadata，再执行最后门禁，之后才写 notice/user-state；其他事件、人工公告和个人安全消息保留原门禁。共享事件规范化后按完整 metadata 分支判定。SQL 对已证明的普通形状选择对应路由参与规则快照，仍将原 source_event 和 metadata 传入既有 V979 函数；仓库仍走原精确事件快照与原状态检查。没有修改事件身份、历史或用户回执，没有新增 SQL 迁移、权限码、角色、授权或前端/WPF 改动。

原 `SubcontractStepDrawEndToEndTest` 16 例及两条少发/下次补齐强断言保留；新增真实三角色互斥投递、只读/公司库/隐式 SA 零投递、notice/state 零预写、实际 Repository 列表/未读/详情/分页前过滤、符合原 DB 约束但 purpose 无效的存储形状、真实回厂后仓库卡不再可见且迟到不复活、普通结果仍保留历史。数据库本身禁止的聚合半形状只在单测验证，不放宽原约束。

相关回归包括 purpose、Participation、Participation PostgreSQL、NoticeService 与完整 StepDraw；实际次数/结果/日志 SHA 以该独立工作树的原始 Maven 日志和提交回执为准。准备错误、DTO UUID/String 断言错误及非法 fixture 聚合形状的原日志均保留，不能冒称生产失败或删除证据。
