# V780 / V781 命令证明与采购数量版本

本说明是源码合同。私有目录V781/706未含V779，不能当作完整安装结果；完整连续目录应V781/707。业务库升级由主任务另行授权，本包不执行。

V780仅给production_daily_report_commands增加可空的create_payload_version/hash。新CREATE在请求对象变异之前冻结原生CREATE-V3＋实际扩展字段的规范证明，并与原报告、原请求hash同事务落库。旧proofNULL保持LEGACY_UNCONFIRMED，不回填、不按当前值猜原body。纯读POST /api/production/daily-reports/create-receipt以原body/key核对，只允许原actor与当前view/对象scope，返回只读且沿当前遮价的native详情；UNKNOWN/LEGACY不能自动重建。原CREATE-V3及已接受POST回放保留，UPDATE/DELETE/TRUNCATE守卫继续拒绝。

V781仅给purchase_request_items增加数据库生成row_version。原全池view/decompose与准确item/request归属、已下达/未闭案停用、实时ordered/pending guard保持；规范锁之后执行qty＋expectedVersion的SQL条件更新并返回真实新版本。旧qty-only请求422，旧版本409且保原输入。每次item自身native/JPA修改推进版本，不加外表版本触发器。永久前像与INSERT旧行等待确保同UUID恢复不回到旧epoch，陈旧RR40001。前端必须同批解析/提交rowVersion；未知PUT只GET核对并等待明确采用新基准，不能把同qty新版本猜成原提交成功。

两迁移均无新表；V779新版本表的永久保留目录与测试注册仍需随其完整源带入。不得修改旧SQL字节、修复checksum、未经授权实际清空或写入现场数据库来伪造验收。用户已另行要求保留受控测试清空，并允许连同测试历史彻底清除；该例外由后续V782前向恢复，不改变日常永久保留。
