## 1. 代码/迁移现状（已逐行核实，作为一切讨论的事实基线）

> 以下均为本工作区当前文件的真实状态，不是推测。

### 1.1 净需求怎么展开（`MaterialAnalysisService`）

- 第 1 层：需求 = 来源净需求 `materialRequirementQty = requested − rootFulfilled` × 单耗（已扣顶层成品合格交接）。
- 第 ≥2 层：子件需求 = **父件 `shortageQty`（现货物理缺口）** × 单耗（`allocateNestedDiagnostics`，约 3544–3595 行）；父路线为 MAKE 或未接管 SUBCONTRACT 才展开。
- `shortageQty = 毛需求 − 现货分配`，**不扣在途**；系统另有 `additionalSupplyRecommendedQty = demandGap − activeFutureCoverage`（约 7535 行），它**扣了在途，但只用于"建议再下达量"，没有用于子树展开**。
- `activeFutureCoverageByMaterial`（约 5793 行）已能按物料行算出有效在途（含 FUTURE_TRANSFER、SHARED_FUTURE_CLAIM、委外前置未通知量），**数据已现成，只是子树展开没用它**。

### 1.2 三种调入的真实现状

| 机制 | 入口/落库 | 现状能力与限制（已核实） |
|---|---|---|
| 现货让料 | `MaterialStockReallocationService` + 权益事件 | **被 `depth=1` 锁死**：候选/来源 SQL 两处 `material.depth=1`（110、209 行），Java 校验 `source.depth()!=1` 拒绝（687 行）。即深层子件行现在**不能**现货让料 |
| 专属在途转拨 | `PreplanFutureSupplyTransferService` + `preplan_future_supply_transfers` | **Java 已半放开、DB 还锁着（WIP 不一致，落库必报错，见 §1.3）** |
| 公共在途认领 | `claimSharedFuture` / SHARED_FUTURE_CLAIM | 采购公共超量可认领；"带 BOM 委外件不吃公共超量"约束保留 |

### 1.3 ★方案乙挖到、方案甲漏掉的 WIP 硬缺口（已逐行核实）

1. **跨路线在途调入：Java 放开了，DB 触发器仍拒绝 → 现在点了必报错。**
   - Java（`PreplanFutureSupplyTransferService`）：目标白名单已含 MAKE（41、86 行 `Set.of("BUY","SUBCONTRACT","MAKE")`），来源仍限 BUY/SUBCONTRACT（47、85、227 行）；转入新动作**沿用来源路线**取号（109–113 行，如采购在途转给自制目标，新 action.route=BUY）。
   - DB 触发器 `fn_guard_preplan_future_transfer`（**V571 第 135 行**）：`OR target.confirmed_route IS DISTINCT FROM source_action.route` —— 目标 MAKE ≠ 来源 BUY 时直接抛异常；第 132 行来源限 `route IN('BUY','SUBCONTRACT')`。
   - **结论：WIP 的"采购在途→自制目标"在服务层能走到，INSERT 时被触发器打回。必须补迁移放宽，否则该功能不可用。**

2. **有子层委外当"在途来源"被容量函数清零。**
   - `fn_preplan_future_source_private_capacity_qty`（V571 第 93–94 行）：只对 BUY 或**无 BOM 子层**的 SUBCONTRACT 给容量；`(action.route='BUY' OR NOT EXISTS(SELECT 1 FROM goods_bom_items ...))` 使**有子层委外容量恒为 0**。
   - 容量基数是外部订单已批准精确量（`fn_preplan_external_exact_approved_qty`），并扣 `fn_preplan_allocation_received_qty`（第 89 行）。**待核实风险点**：received 是否把"前置自制完工 FULFILL"也算进去——若算入，会把还没发外的自制产出误当"已回厂"而错减可转容量。放开前必须用真库测三阶段（见 §4-P0.4）。

### 1.4 这些"子层级怎么办"其实早已设计好（避免重复造轮子）

方案乙的这一判断成立，方案甲此前低估了现状：

- **缺料不卡上层下达**：缺料批次先进 WAITING，车间侧齐套后自动提升 READY（计划侧不做齐套拦截，ADR-071）。
- **子件各走各路、各回各桶**：BUY 子件→采购桶、MAKE 子件→车间桶、SUBCONTRACT 子件→委外桶，逐行下达。
- **已下达量永不回流成"待下达"**；已领用材料覆盖到委外回厂，不重复采购。
- **调入目标永远是"有缺口的行"，只减缺口、不改路线/车间归属**。
- **"买 100 备 10000"闭环已存在**：下达手填富余→超量归公共池（需 `over_supply`）→他计划从公共在途认领。

> 所以本次**不需要新建"子层级处置流程"**，要补的是两类东西：①把 WIP 放开的能力修通并补齐护栏；②修正一个净需求计算口径（§2）。

## 2. ★最关键的仲裁结论：一个硬币的两面，必须同批上线

### 2.1 两份方案各自的盲点

- **方案甲的盲点**：只从净需求模型推出"在途应净减子树"，但没发现——在当前 WIP 里，在途**根本调不进**自制/有子层委外目标（触发器拦截），且深层现货让料也被 `depth=1` 挡住。只做甲的净算改造，输入端是堵的，能力不完整。
- **方案乙的盲点**：把"在途调入放开到 MAKE/有子层委外"修通后，**默认净需求引擎够用**；但 §1.1 证明：子件 ≥2 层按父件**现货缺口**展开、不扣在途。一旦采购/委外在途转入抵了自制父件的一部分缺口，父件只需少做，**下层子件却仍按父件整件全量展开 → 多采/多产积压**。乙放开的入口，恰好踩甲减掉的那个坑。

### 2.2 强耦合关系（拆开必错）

```
放开"在途调入到自制/有子层委外目标"（乙：修触发器+白名单）
        │  一旦放开，父件缺口被【未入库在途】部分覆盖
        ▼
子件必须按"父件净产出（扣已确认在途）"展开（甲：净需求口径修正）
        │  否则下层按整件备料 → 积压
        ▼
在途撤销/失败时，被净掉的【未下达】子件需求必须回补（甲闭环）
        │  否则在途黄了 → 父件要补做却发现下层没备 → 断料
        ▼
现货让料放开全深度（乙：删 depth=1）才能对深层父件用现货做同样的净抵
```

- **只上乙不上甲**：功能能用但下层需求数字错（多备）。
- **只上甲不上乙**：数字逻辑对了，但在途调不进来、深层现货让不了，等于空转。
- **正确做法：P0.1～P0.4 作为一个变更集同批上线、同批测试。**

### 2.3 统一的双口径模型（定稿口径，吸收甲、约束乙）

每个节点五个量（基本单位、4 位小数）：

```
G 毛需求        = 父"计划净产出" × BOM 单耗（顶层=销售净需求）
S 现货覆盖      = 合格库存 + 精确预留 + 现货让料调入（已入库）
F 已确认在途    = 已批准采购/委外在途 + 专属转入 + 公共认领（按置信分档，§3.3）
N 计划净需求    = max(0, G − S − F)   ← 决定"还安排多少"和【下层按多少展开】
P 物理缺口      = max(0, G − S) = 现 shortageQty，原样保留 ← 决定 READY/领料/开工
```

**三条铁律（把两份方案的边界钉死）：**

1. **子件毛需求 = 父件 N × 单耗**（现状 ≥2 层用 P，改为 N；第 1 层父为根，根净需求已等价此口径）。父 N=0 → 整棵子树未下达需求归零。
2. **净需求缩减只作用于"未下达的待安排量"；已下达单冻结、永不回流**（吸收乙），需要减量时只产生"取消/改量建议"，人确认（行动消息后置到 P3，本期只保证不自动改已下达单）。
3. **实物口径不认在途**：F 未合格入库前，不生成正式预留/DRAW、不把 WAITING 提 READY、不允许开工（与现有齐套门一致，保持不动）。

## 3. 目标业务规则（融合定稿）

### 3.1 调入对象与目标的硬边界（两份方案一致，精确定位到行类型）

- 调入/转入的**标的永远是"同 货品+颜色+单位+同主仓 的最终件缺口"**，只减缺口，不改目标行路线与车间归属。
- **不得作为调入目标**：锚点行/前置自制行（MAKE_COMPONENT、SUBCONTRACT_MAKE）、控制段 SHIP/REFERENCE、已停用行。
- **不得作为调入标的（来源供给）**：自制在制品、委外前置自制半成品（SUBCONTRACT_PREPARE 专属预留）、正在委外商处的料——它们不是最终件。
- 跨主仓不做账面调入，走真实仓库调拨单（沿用 V565）。

### 3.2 三种调入 × 路线 × 对子树影响（定稿矩阵）

| 调入 | 目标路线 | 减 N（计划） | 减 P（实物） | 对下层未下达需求 | 备注 |
|---|---|---|---|---|---|
| 现货让料（放开全深度后） | BUY/MAKE/SUBCONTRACT | 是 | 是 | 立即按父 N 缩减 | 原计划挂优先待补；一节点一条未补齐关系 |
| 专属在途转入 | BUY/MAKE/SUBCONTRACT | 是（firm） | 否 | 按父 N 缩减（**本期新增净算**） | 合格入库才减 P；撤销/失败回补 |
| 公共在途认领 | BUY/MAKE/SUBCONTRACT | 是（firm） | 否 | 按父 N 缩减（**本期新增净算**） | 带 BOM 委外不吃公共超量的原约束保留 |

- **委外双形态**：无子层委外=纯外部，行为同采购；有子层委外=先前置自制目标件再发外，其发外组件按"净发外 N × BOM"展开；N=0 不前置、不通知、不发外。
- **跨路线转入（如采购在途→自制目标）**：目标行路线仍为 MAKE，只是 MAKE 净自产 = N 减少；转入动作沿用**来源路线**（BUY）取号落库（沿用 Java 109–113 行设计）。注意与 ADR-072"MAKE 配额只认新增来源需求、旧物理缺口不扩大"对齐：转入抵缺口后 MAKE 配额**只减不增**。

### 3.3 在途置信分档与回补（吸收甲，配乙的撤销模型）

| 档 | 定义 | 计入 F | 变化处理 |
|---|---|---|---|
| firm 确定 | 已财审批准、ETA≤需期（含已转入/认领） | 计入，净减 N 与下层 | 合格入库 F→S、P 归零 |
| risky 风险 | 晚于需期 / 交期不明 / 待检 / 合格待入库 | **默认不计入**，显式"接受晚到"才计入（沿用 allowLateSupply，黄标、不改计划日期） | 确认不可用即移出、N 重开 |
| failed 失败 | 判废无补 / 供应商取消 / 超期不交 | 不计入 | **回补**此前被净减的下层未下达需求 + 提示重新下达 |

- 撤销拆分沿用 V571：恢复原计划 / 释放公共，二者之和=撤销量；撤销同时按谱系恢复下层 N。
- 待检/合格待入库可作风险档采用（沿用现状），实物仍以仓库实际入库为准。

### 3.4 采购批量 / MOQ（吸收乙的务实版，收敛甲的过度设计）

- **本期只做两个主档字段**（V575）：`min_order_qty` 最小起订量、`order_multiple_qty` 订货倍数（整包装），numeric(18,4) 可空、CHECK≥0。甲方案的 POQ/EOQ/周期合并**后置 P3，不本期做**。
- 采购桶行内"下达数量"默认值：`向上取整到倍数( max( 净需求N, 起订量 ) )`；**软约束**，服务端不硬拦，计划员可改（对齐业界手工单可覆盖）。**仅采购桶**，委外桶后续。
- 超过 N 的部分即富余，走既有公共超量通道（公共池→他计划认领），不新增账套。
- **★乙漏掉、需拍板的小点**：若操作人**没有 `over_supply` 权限**，MOQ 自动抬出来的富余怎么落？两个选项：(a) 抬量仍需有 over_supply 权限者确认，无权限则默认只填 N、并提示"低于起订量"；(b) MOQ 属供应商强制、系统自动公共化，作为 over_supply 的受控特例（记录操作人）。**建议 (a)**，权限模型更干净，待你定。
- 同物料合并下单**本期只在单次分析内**合并（通用件不重复买）；跨分析合并后置 P3。

### 3.5 委外在途来源放开（最难项，严格护栏 + 可灰度）

- 去掉容量函数对"有子层 SUBCONTRACT"的清零（V571 第 94 行），但容量口径必须改为**仅外部委外订单的未回厂量**，分三阶段锁定：
  1. **通知委外前**：无外部订单/无 external_item → 容量 0（不可转）。
  2. **委外订单财审批准后、回厂前**：容量 = 订单批准量 − 已回厂实收 − 已转出。
  3. **回厂合格后**：转为现货/权益，走现货让料，不再走在途转拨，容量递减到 0。
- **前置自制完工的半成品绝不能计入"外部可转容量"**（核实并必要时新增"仅外部实收"函数，把前置自制 FULFILL 从 received 口径里剔除）。
- **灰度兜底**：若上述容量口径在真库测不稳，本期先只开放"委外订单已批准后"阶段，通知前/自制中一律不可转（方案乙亦持此兜底，本定稿升为硬约束）。

## 5. 复杂情形处置矩阵（融合两份，按定稿口径校正）

| # | 情形 | 处置 |
