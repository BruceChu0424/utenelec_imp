# V500 实际平均库存价值核心

日期：2026-09-07。此迁移与独立核心是[存货价值与成本闭环方案](../01-规划/2026-09-07-存货价值与成本闭环重构方案.md)的第一实现包；没有接线采购、销售、生产、委外、StockService 或 GL，不等于成本闭环上线。

## 变更与历史边界

新增8张业务表：`stock_value_pools`、`stock_value_events`、`stock_value_nodes`、`stock_value_edges`、`stock_value_jobs`、`stock_value_tasks`、`stock_value_node_revisions`、`stock_value_postings`。均属于清业务时的 CLEAR 分类；原数量台账、采购/销售商业金额和GL不重写。版本目录与清空白名单须同时包含新增业务表。

`stock_balances` 仍是物理数量唯一投影。pool表只保存价值头和状态；节点 `quantity_basis` 是创建时冻结的分配基数，普通编辑不可改，不提供第二个库存数量写入口。管理中的池在提交时检查当前头与真实余额的数量/金额一致，解除价值头、删除或移动该余额、直接篡改节点价值均不能提交。

迁移对非零数量、非零已记录金额或空金额的旧池只插入 `LEGACY_UNVERIFIED` 证据，不把旧金额认作实际成本，不改变旧余额/流水/GL。普通核心读返回未证状态和空的实际成本，写入拒绝。受控期初批准及非空旧业务运行兼容尚未实现；不能以已加这个保护宣称已完成历史切换。原业务经备份和既定清空流程处理后，新业务可从空池建立明确成本来源。

## 调用合同

实现：[InventoryValuationPort](../../server/src/main/java/com/uten/imp/application/port/InventoryValuationPort.java)、[InventoryValuationService](../../server/src/main/java/com/uten/imp/features/stock/valuation/InventoryValuationService.java)。

1. 调用方先按原业务对象锁序取得业务来源锁，再通过共享 `InventoryMutationLock` 取得全部相关goods/color键锁。所有核心写方法在活动事务内调用 `requireHeld`，不另算advisory锁hash、不扫描pg_locks。REQUIRES_NEW不继承外层的锁证明。
2. 数量动作先预留真实movement UUID；核心在物理数量写入前检查 `expectedQtyBefore`、池头与真实余额，然后返回已知本币成本、价值节点、canonical movementId和状态。调用方在同事务用返回值写movement及余额一次。
3. `replayed=true` 时必须使用原返回结果并跳过物理写。候选新movement UUID和重试时最新expectedQtyBefore不计入逻辑请求hash；同源事件/明细/动作即使换transport key也只执行一次，同键异体拒绝。
4. `EventContext` 的来源事件/单据/明细UUID、版本、责任账号/员工与发生时间必须从稳定的真实业务事件取得，不能在每次重试生成。拆分成多个不同去向时使用明确的子事件身份。四位金额与数量禁止静默截精度。
5. `Receive.knownCostLocal=null` 仅可配 `costFinal=false`。已知组成部分允许0，但来源未证不能标FINAL；有明确核定零成本时，以0和最终确认事件表达。`Issue` 不接收调用方金额。
6. 来源审批、可资本化金额及未分配容量、成本期间和对象权限由服务端应用适配层独立检查。这个port不对外提供任意库存改价API。

物理事件的延迟守卫精确核对相同movement UUID、来源doc/item、仓库/货品/颜色、方向、基本数量和已知本币金额。缺movement、金额为空或误用销售价会回滚整个事务。物理movement金额保留创建时快照；后补价值只改本期追加posting及库存金额投影，不改该movement和任何qty。

## 分配、退回与后补

普通入库创建来源节点和新池头；普通出库按 `round4(V*x/Q)` 分本次出库，剩余严格取 `V-本次`。每个父节点最多两个后继，按节点序号向后，普通动作的SQL数量不随历史增长。

原路退回引用原出库价值节点，按原始总额/总数量的累计区间计算分次退回，而不是重新平均已舍入余值。比如0.0002/3按1件分三次退回得到0.0001、0、0.0001。退回与跨仓同货品同颜色携转会合入当时目标池，之后再次销售仍保留晚费用路径。

来源追加成本冻结新revision并发布job；每个任务只应用一个edge的目标累计金额减已应用金额，至多发布两个子任务。金额和最终状态变更均传播。任务与子任务、edge/node revision、两端posting和job剩余金额同事务提交；乱序先返回等待前序，成功重放零入账，失败回滚可恢复。

`pendingWork` 最多100项，仅只读取得任务及实际子节点poolKey；worker须在新的业务事务内先锁该key再 `propagate`。核心没有自带调度线程、无限递归或长事务持锁遍历整图。job完成须剩余任务及待分配金额都为0。当前任意未完job会保守地让查询显示PENDING，避免尚未被上游标记的叶误报已核定；不会阻止正常物理数量动作。

成本调整只允许原SOURCE，不允许直接改池或COGS节点。反向只支持已传播完成的原正向调整，按同源后进先出追加准确相反金额及状态恢复；旧event/posting/revision/边比例不能改删。来源后来增加时，在库去库存，已售去COGS，已全部出库的空池保持0价值。

## 精确边界与下一包

V500只把材料价值放入WIP位置，尚未把真实消费/损耗posting连到已有FG待成本来源。下一包必须实现跨货品、双端平衡、冻结生产分配版本的价值桥和反向；不能只给FG增加材料600，却让材料WIP还持600。正常损耗进入合格产出、异常损失独立、人工确认实耗/WIP等既有规则保持。已有FG节点与后来WIP确认之间的路由代际需单独设计，不能绕过当前向后边守卫。

GL和页面须消费同源价值事实；不能同时把movement旧金额与所有posting当作两套成本相加。采购AP/加工费原凭证的记账所有者、成本期间与调整凭证、原出库部分冲销的业务门禁、生产多去向分配、历史受控期初、后台调度及报表仍由后续接入包完成。

真实PostgreSQL16定向测试 `InventoryValuationCorePostgresTest` 使用V500原DDL和共享JPA/advisory锁，物理写用最小StockService职责替身。覆盖18个行为场景：平均与全出无残值、待成本后补、原成本分次退回/再售、四位微额、真实零成本、幂等/异体、物理写缺失或错误金额回滚、非空历史保护、跨仓携转、仓色隔离、投影篡改、任务乱序/重放/回滚恢复、调整LIFO反向、两个方向真实PG锁等待、普通语句数与历史无关、所有写入口未持锁拒绝、REQUIRES_NEW隔离与外层恢复。
