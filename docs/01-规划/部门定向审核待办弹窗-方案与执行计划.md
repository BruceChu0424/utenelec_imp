# 部门定向审核待办弹窗 —— 方案与执行计划

> **2026-09-02 第二轮修订（用户口径）**：审核待办弹窗为**屏幕居中弹窗**
> （`ReviewPendingDialog`，非仅顶部卡）——一个事件三形态并存（通知中心条目+顶部条+
> 居中弹窗），**每次登录检查**未办结待审（`ReviewPendingLoginGate`，登录后 3s 拉
> `GET /notices/pending-reviews`）有则弹；见 ADR-063 第二轮节与
> docs/02-组件库/ReviewPendingDialog.md。

> **本文是新会话的直接开工依据**（2026-09-02 调研成文）。需求来源：用户口述「销售下单→财务部负责的人收到弹窗，稍后再看/去审核；他人正在审核、已审核不弹；点按钮通知自动已读；覆盖财务/生产/采购/委外/仓库/品质；配套权限/工作台/新页面/公共组件/DB 迁移/性能/文档/清理」。
> 调研基线：工作树含 V457（货品后模镶件）+ V458（委外先自制）两个未提交 WIP；Flyway 迁移头 = **V458**（420 个迁移），新功能从 **V459** 起；ADR 头 = ADR-062（未跟踪），新 ADR = **ADR-063**；迁移说明文档编号从 **79** 起；permission_surfaces 现有 110 个。

## 二、现状盘点（调研结论，带坐标）

### 已具备（直接复用，不要重建）

1. **通知存储与定向**：`notices`（kind/action_route/source_event/priority/audience 定向，V92→V454 演进）+ `notice_user_states`（已读/自删/popup-ack/task_completed_at）。系统定向唯一落库入口 `NoticeService.publishForUser`（`server/.../notice/NoticeService.java:1021`）。
2. **可靠事件源**：`business_outbox`（V151）+ `BusinessOutboxScheduler` 2s 投递；`ChainNoticeService.java`（3789 行）约 60 种业务事件，含销售/采购/委外/仓库/品质全线。
3. **部门+权限定向寻址范式**：`ChainNoticeService.departmentUserIdsWithAuthority`（:3579 递归 CTE 子树×权限交集）、`WorkflowReviewerEligibility`（ADR-027：DEPT_FIN 子树 OR 个人点名加授）、`SalesOrderFinanceConfirmerEligibility`。**「部门树 OR 个人加授」语义保留**（管理员显式点名=兼职兜底，不与 R1 冲突）。
4. **「他人正在审核」机制**：`task_claims`（V215/ADR-023）统一软认领：show-as-locked + 30s 心跳 + 惰性过期 + 409 兜底；前端 `lib/shared/concurrency/task_claim_session.dart`、`task_claim_badge.dart`、`task_claim_handle.dart`；已登记类型见 `TaskClaimPolicy.java:17-27`。
5. **已读闭环**：`POST /api/notices/{id}/read`、`read-by-route` 批量、全局路由桥 `notice_route_read_bridge.dart`（导航到 actionRoute 自动已读）。
6. **到达链**：`notice_arrival.dart` 10s 增量轮询 + 1min 对账（文件头注明为 SSE/WS 预留同一入口）；`/api/notices/arrivals` keyset 高水位。
7. **销售→财务链路已存在**：`SalesOrderService.approve()` → `notifyOrderPendingFinanceConfirmation`（SalesOrderService.java:1062 → ChainNoticeService.java:2640，逐人 TYPE_APPROVAL 定向通知，现为 normal 顶部条）。
8. **待办列表范式**：财务订货审批任务中心 `/api/finance/procurement-approvals/tasks`（共享队列+batch-approve+count）、销售订单财务确认收件箱（V300/ADR-040）。

### 缺口（本方案要补的）

1. **兼职部门模型不存在**（employees 单部门，无中间表/副部门列）。
2. **弹卡无操作按钮**：`AppNotification` 只有整卡 onTap（`lib/core/ui/app_notification.dart:24-60`）；双按钮只在 alert 居中通道（ADR-059 已规定到达链不弹居中）。
3. **无 snooze 语义**（现只有"关闭=本机 delivered / popup-ack=永不重弹"两档）。
4. **通知不随业务办结撤回**：notices 无聚合定位列（只有 source_event，无 aggregate_id）、无 resolved 状态；审完他人的通知残留。
5. **通知链与认领状态不联动**：弹卡不显示 claim 状态。
6. **实时性**：无 SSE/WS，10s 轮询（可接受起步，SSE 列为后续增强）。
7. **通知中心全量加载**（`notice_list_page.dart` 685 行瀑布流无分页）——数据量痛点直击。
8. **ADR-052 §2.3 限制**：「未认领的共享审批池…不做持久居中弹窗」——需 ADR-063 显式修订边界。

## 三、核心设计决策

### D1 兼职部门 = 新表 `employee_secondary_departments`（不动主部门）
```sql
CREATE TABLE employee_secondary_departments (
  employee_id UUID NOT NULL REFERENCES employees(id),
  department_id UUID NOT NULL REFERENCES departments(id),
  started_on DATE, note VARCHAR(200),
  created_at/created_by 审计列,
  PRIMARY KEY (employee_id, department_id)
);
```
- **权限合成扩展**：`PermissionResolver.baseParts()`（PermissionResolver.java:242）把兼职部门的配置（含其祖先递归）并入现有并集——兼职财务部=拿到财务部权限面。加表默认空=**零行为变化**，完全兼容存量。
- **失效链**：兼职表变更必须触发对应用户 auth_version bump（V135 机制；核实其触发方式是 trigger 还是 service 层，兼职表同样接法）。
- **管理入口**：员工编辑页（基础资料）加「兼职部门」多选，复用统一部门树选择器（ADR-010）；后端 employee 编辑 API 扩展。权限复用现有员工编辑权限码（执行时核实码名，不新增）。
- **寻址统一**：新 `OrgMembershipQueries`（主+兼职 UNION 的"部门子树成员"查询），替换/包装 `departmentUserIds*` 系列与两个 Eligibility 的成员查询，避免 N 处复制。

### D2 弹卡形态 = 顶部非阻塞**可操作卡**（不破 ADR-059 非阻塞原则）
- 扩展 `AppNotification` 模型：新增 `actions: [UtenNotificationAction{label, style(filled/text), onPressed}]`（可空=完全向后兼容，现有 banner 行为零变化）+ 可选 `onExpired`（办结收卡回调）。
- 审核卡布局：左侧 6px 细边条（沿用 AppNotification 语言）+ 待办图标（**遵守 Badge 固定高标准**）+ 标题「销售新下单待财务确认 · SO20260902-001」+ 操作区【去审核（filled 主按钮）/ 稍后再看（text）/ 右上 X】。
- 认领态行：「⏳ 张三 正在审核（2 分钟前）」→ 主按钮文案变「查看进度」仍可进页（页内 show-as-locked 是既有行为）。
- 办结：心跳发现已审 → 卡自动收起 + 轻提示「已由 张三 审核」。
- **UI 约束**：沿用 UtenTokens 深绿品牌一致性打磨（ADR-004），**不引入新设计系统**。

### D3 定向寻址 = 组织归属 AND 职责权限码（双条件缺一不可——用户两轮明确强调）
- **弹卡/收件台推送资格** = **(主部门 ∈ 部门子树 OR 兼职部门 ∈ 部门子树) AND 持有该业务块职责权限码**。
  例：财务部（或兼职财务部）且持有 `sales_order_finance:confirm` → 收「销售新下单待财务确认」弹卡；品质部且持有 `procurement_inspection:handle` → 收「到货待检」弹卡。
  **部门内无该权限码的人不推**（不是部门全员广播）；**有权限码但不在该部门（主/兼职都不在）的人也不推弹卡**。
- **审批操作资格**（能不能审）维持 ADR-027 现语义：部门子树 OR 管理员点名加授——即**推送比审批严格**。部门外被点名加授的专人若也要收弹卡，正确做法是给他**兼职该部门**（D1 新模型正好承接这个口子），而不是只加权限码——这样「谁是这个部门负责这块的人」始终有唯一的组织表达。
- 实现 = 现有 `departmentUserIdsWithAuthority`（ChainNoticeService:3579，递归子树×权限交集）+ Eligibility 范式，叠加 D1 兼职并入。每个审核事件声明六要素：`部门码 + 必需职责权限码(any) + claim 类型 + 专属审核页路由 + 职责权限码盘点（缺则按 D8 五步补码）+ 审核落点`。

### D3b 归属人定向范式（R12：负责该单据的人收提醒）
- 第二类定向：**单据归属人**——不走部门×权限交集，天然"他负责的单据"。现有机制直接复用：`orderRef`（ChainNoticeService:3400，owner_employee_id→seller_id 兜底）+ `userIdOfEmployee`（:3415 员工→账号，无账号静默跳过）→ `publishForUser` 定向。
- 典型事件：**订单关联生产计划全部完工 → 通知负责销售「全部完成生产，可以发货」**。触发判定=完工入库落点 count 该订单未完工计划数，=0 才触发一次（**逐计划完工不触发**；幂等键防重发；若已有逐计划完工通知保留为普通通知，不弹卡）。
- 归属人唯一 → **不需要 claim**（无"他人正在审核"问题）；按钮=【去开出货单 / 稍后再看】；出货单开立落点接 resolveReviewNotices 撤回。

### D4 撤回 = notices 聚合定位列 + 办结落点批量 resolve
- 迁移加列：`notices.aggregate_kind VARCHAR(40)`、`aggregate_id UUID`、`resolved_at TIMESTAMPTZ`、`resolved_reason VARCHAR(40)`；部分索引 `(aggregate_kind, aggregate_id) WHERE resolved_at IS NULL`。
- `publishForUser` 重载补 aggregate 参数（新通知起携带；**老通知 NULL=永不撤回，走既有已读流程**——旧数据适配即"不变"）。
- `ChainNoticeService.resolveReviewNotices(aggregateKind, aggregateId, reason)`：一条 UPDATE 撤回该单全部待审通知（outbox 同事务，与发布对称）；各审核落点（approve/reject/confirm/cancel）调用。
- 通知中心：resolved 通知**保留展示**但灰显+「已办结」徽章（审计价值），弹卡流排除。

### D5 稍后再看 = 服务端 snooze（跨设备一致）
- `notice_user_states.snoozed_until TIMESTAMPTZ`；`POST /api/notices/{id}/snooze {minutes:15}`（默认 15，常量可配）→ 同时 markRead（R6 要求）。
- arrivals 弹窗流排除 `snoozed_until > now()`；到点未办结则下次到达重弹（可再 snooze）。通知中心显示「已稍后 · HH:MM 再提醒」。

### D6 真态校验 = 新批量轻接口（弹前+弹中两个用途）
- `GET /api/notices/pending-review-status?ids=`（输入待审通知 id 集，≤50）：返回每条的 `{aggregateKind, aggregateId, businessStatus, claim:{by,at}|null, resolved}`。
- 弹卡分派前先查一次（已办结不弹）；停留期间 30s 心跳复查 → 办结收卡 / 认领态刷新。
- 服务端实现按 aggregate_kind 分发到各域已有 status/claim 查询，**不做跨域 join 大查询**（数据量友好）。

### D7 新页面 = 「我的待审收件台」`/reviews/inbox`（每域 section，独立新页）
- 后端聚合：`GET /api/reviews/inbox/summary` 并行调各域已有 pending/count 服务（服务端聚合，前端一次请求；数据量=pending 行数天然小）。
- 页面：分域 section 卡（域色标 + 认领状态列 + 「去审核」直达行级审核页 + 空态设计）。
- **去审核跳转原则**：弹卡/收件台直达**单据级域专属审核页**；路由不存在的新建（如缺仓库出入库审核页则建 `/warehouse/doc-review/{id}` 这类新页），不复用他人共享编辑页（R9）。
- 工作台 dashboard 加「待审事项」卡片（badge=各域 pending 和，**只计真实待办**——草稿不计，遵守徽章红线）。

### D8 权限接线（照权限总设计 §五五步清单走）
1. V459 迁移 INSERT 权限码 `review_inbox:view`（action_type=VIEW，零默认 grant）+ permission_surfaces 新面（110→N，同步契约测试）；**同步 `server/ops/reset_business_data.sql` 白名单 + `docs/数据迁移/README.md` 头部计数**；55-权限模块分类只读不动。
2. 前端 `lib/shared/auth/permissions.dart` Perm 常量 + `permission_by_path.dart` 注册（路由守卫+工作台显隐一次到位）。
3. 后端 `@PreAuthorize`（收件台 summary、snooze/resolve 本人校验不需要新码）。
4. 契约测试三件套同步（router_access_policy / page_route_permission_dependency / document_route_segment）。
5. 权限管理页.md 登记新码与 surface；页面总览行同步。

### D9 实时性 = 先轮询加密、SSE 后置
- Phase 内把到达轮询间隔做成常量（10s→弹卡类事件可感知的 5s 档，1min 对账保留）；SSE（`GET /api/notices/stream`，复用 arrivals 高水位+Last-Event-ID）作为**独立后续批次**，不在本计划混做（notice_arrival.dart:37 已预留替换入口）。

### D10 通知中心分页 = keyset 惰性加载
- 现状全量瀑布流；改造为 (published_at,id) keyset 分页 + 滚动加载（复用 arrivals 已有分页范式），筛选/全部已读/多选删除行为不变。索引核对（audience 可见性查询路径）。

## 五、业务接线目录（「所有地方」的完整清单，分三级）

> 每条线六件套：①事件升级为可操作卡（ChainNoticeService 发布点补 aggregate+资格池复核，资格池按 D3 双条件）②TaskClaimPolicy 登记 claim 类型（缺的）③去审核直达路由（缺的建新页）④审核落点接 resolveReviewNotices ⑤**职责权限码盘点——若该业务块缺清晰的审核/处理权限码，按 D8 权限五步补码（Flyway INSERT + Perm 常量 + permission_by_path + permission_surfaces + 权限管理页目录登记 + 契约测试）** ⑥域测试。

## 九、红线与坑（执行会话必读，浓缩自项目记忆）

1. **用户会在 IDE 同步改代码**：编辑前重读文件；commit 前必查 `git diff --cached`（防裹走用户暂存）；Mimosa 拦 commit **不许 --no-verify**。
2. **Mimosa 拦 Bash 写源码**：禁 sed -i 批量替换，逐文件 Edit/Write；SQL 全部参数绑定（禁拼接/f-string）。
3. **零回归红线**：业务逻辑改动全测试绿才能 commit；契约测试 34 项（router/page_route/document_segment）因权限改动必须同步更新而非绕过。
4. **迁移铁律**：前向新迁移，不改已应用迁移；55-权限模块分类与已应用 SQL 只读；加迁移同步 reset 白名单+README 计数。
5. **FullChainE2E 脏树陷阱**：只跑单方法并核对 surefire `Tests run: 1`；直插夹具自清理。
6. **单人维护软提示原则**：认领/职责分离只做 show-as-locked 软提示，**不做硬阻断**（task_claims 现语义即如此，勿加硬拒）。
7. **徽章红线**：待审计数徽章固定高度、只计真实待办（草稿/已办结不计）；父分类=子类真实待办之和。
8. **l10n 三语**：新增文案过 gen 三文件（zh/en/ko）+ dart format。
9. **ADR-059 非阻塞原则不破**：新卡仍顶部非阻塞；urgent 居中模态继续仅 ADR-052 白名单。
10. **V149 受众快照语义**：已选受众是不可变快照，resolve 撤回不改变历史可见性。
