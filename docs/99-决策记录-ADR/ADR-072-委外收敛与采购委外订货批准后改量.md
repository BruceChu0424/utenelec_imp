# ADR-072 委外收敛与采购/委外订货批准后改量

- **状态**：已决策（2026-09-05，V486）；本地源码候选，未部署
- **关联**：[ADR-062 委外先自制后通知](ADR-062-委外先自制后通知与分批通知.md) · [ADR-064 直下单销售式供货流](ADR-064-直下单销售式供货流现货直发缺口才生产.md) · [ADR-068 订货行级条款](ADR-068-采购委外订货单行级商业条款与学习模式.md) · 销售 V482 改量（`docs/数据迁移/98-V482销售订单改量事实账.md`）
- **迁移**：[102-V486采购委外订货改量与委外准备退役](../数据迁移/102-V486采购委外订货改量与委外准备退役.md)

## 一、背景与用户口径

2026-09-05 用户对委外模块整体收敛的口径：

1. 委外入口只保留两个——**计划下达委外**（物料分析 SUBCONTRACT 路线）与
   **委外自己下单**（直接新建订货单）；委外模块不再「自己分析产品」。
2. **有子层的委外件都先发单给计划**，计划安排车间；**等生产完才告诉委外**，
   委外再提交财务审核（与销售同构）；
3. 委外完整闭环 = **财务同意 → 仓库出仓目标件 → 去委外加工 → 回厂品质检查 →
   入库（完全入库）→ 按需通知生产车间领料**；财务批准通过即可出仓，
   不允许「批准后还要等前置生产」的倒挂。
4. 财务批准前可自由修改（草稿）；**批准后修改走另一种方式**——对齐销售 V482
   「改量立即生效 + 重回财务复核 + 修改清单（以前→现在）」，采购同步对齐。
5. 采购/委外 IQC 不合格的通知三件套（通知页 + 顶部横幅 + 居中行动卡）、
   退回供应商/委外商处理入口与历史可查必须补齐。

## 二、决策

### 2.1 委外准备中心退役（删入口，不删机器）

- `/subcontract/preparations` 页面、`GET/POST /api/production/material-analyses/
  subcontract-preparations*` HTTP 入口、`SubcontractPreparationTaskAdapter` 的
  任务读模型（约 500 行 native SQL）全部删除；`subcontract_preparation:view/start`
  权限按 V441 口径停用（不可分配，保留授权行作审计）；路由保留兼容重定向。
- **前置生产机器保留**：`SubcontractPreparationCoordinator.start`（含 V447 权益桥）
  不再由人触发，改由系统自动调用。存量在批单的 MAKE_THEN 行由
  `SubcontractPreparationAutoStartReconciler`（每 10 分钟，`!cloud` profile）
  兜底自动启动——同时自愈「行创建与自动启动之间进程崩溃」的缺口。

### 2.2 直接下单有子层行 = 草稿期自动「发单给计划」

- 草稿保存（create/update）后，系统按与批准同款的「全局可用量池」口径计算
  每个有子层行的缺口，为缺口自动创建 `SUBCONTRACT_PREPARATION` 前置生产分析
  （source_ref=`SC-ORDER:{orderItemId}`，无权益桥——需求为本单新增），并通知
  计划部（居中行动卡，直达分析）；计划在**自己的物料分析工作台**安排车间。
- 草稿编辑导致行 ID 重建时按「货品+颜色+数量」匹配迁移分析；已排产行的
  改动/删除 fail-closed；草稿删除随单取消未排产的分析。
- **提交财务闸门**：`lockAndValidateFinanceSubmission` 重算批准口径，仍出现
  MAKE_THEN 缺口行即拒绝（「等计划部车间生产入库后再提交」）。财务批准通过
  即全部行 READY_OUTBOUND，仓库可立即目标件出仓——兑现「财务同意→仓库出仓」。
- 前置生产产出完工入库（FINISHED_IN 审核钩子）自动通知委外制单人
  「目标件已生产入库，全部备齐后可提交财务审核」。

### 2.3 采购/委外订货单批准后改量（对齐销售 V482）

- 新端点：`POST /api/{purchase|subcontract}/orders/{id}/change-qty`（权限码
  `purchase_order:change_qty` / `subcontract_order:change_qty`，默认不授）。
- 语义：仅财务批准（status=1）且无 PENDING case 的单可改；**立即生效**并同事务
  完成下游对账（预计到货 ordered_qty、申请/来源 ordered_qty 份额增减、委外出仓
  计划行收减/扩行——有子层增量自动再发单给计划）；逐行 old→new 写入
  `procurement_order_qty_change_logs`（append-only + fn_audit，case_id 关联
  本次自动创建的复核 case）。
- 复核：`ProcurementApprovalReconfirmationService` 以改后快照开 PENDING case
  （attempt+1，事件 `PROCUREMENT_FINANCE_CHANGE_SUBMITTED`）；审批任务列表标注
  「改后待复核 · 改量 N 处」，审核详情展示修改清单（以前→现在）。复核通过 =
  确认（订单已批准，跳过草稿校验与重复生效副作用、不再建预计到货）；驳回 =
  保留新数量、制单人收原因后可再次改量（不自动还原——下游事实不可静默回滚）。
- 下游锁定量 fail-closed：新数量不得低于 已收货净量/已登记到货量（采购）与
  已回厂净量/已出仓目标件（委外）；委外减量另受「未出仓未草稿剩余」约束。

2026-09-07 来源对账实现补充：批准后改量须经“冻结本次合法变更→更新订单→逐来源/生产挂接对账→复核case和变化log”的同一事务，见[V503说明](../数据迁移/119-V503批准后改量的来源份额与生产挂接对账.md)。原需求/BOM不随订单减少；减少份额按ADR-069原FIFO的逆序从未履约部分返还，原迁移留存并追加部分反向，不能按比例平均回减后放任sources仍是旧量。增量限原来源剩余可订容量；商业身份、原单位和历史快照继续冻结。V283/V438/V472保护只增加可证明的受控通道，不删除守卫。

### 2.4 IQC 不合格通知与历史

- `PROCUREMENT_IQC_REJECTION_OPENED/RETURNED` 升级为居中行动卡（aggregate
  `IQC_REJECTION_CASE`，贷项确认/无贷项结案/反向时批量撤卡）；通知页记录与
  顶部横幅沿用既有 outbox 投递。处理入口与历史即 V440 列表/详情
  （`/procurement/iqc-rejections`），采购与委外共用，不另造页面。
- 车间领料通知维持既有链路：委外件入库推进原需求齐套 → 生成领料单 →
  `PRODUCTION_DRAW_PENDING`（仓库出库）与 `PRODUCTION_WORKSHOP_TASK_ACTION_REQUIRED`
  （车间领料行动卡）。

## 三、影响

### 2026-09-07 复核通过与驳回统一校验

已批准订单的改量复核，确认和驳回均通过订单 port 加锁并读取当前商业快照，不再进入“仅草稿可提交”校验。两种决定都与送审哈希比对；通过不重复生成预计到货或生效库存，驳回保留当前有效数量并反馈制单人。首审与复审抽取同一 `ProcurementApprovalSnapshot`，共同使用应用配置的 ObjectMapper，修复复审自建未登记 JavaTime 模块的序列化器遇到 LocalDate 无法送审，以及两份规范化实现可能发生漂移的问题。

- 委外 Hub 删除「前置自制」入口卡；申请登记簿合成行、订货详情全链路进度继续
  作为车间进度的权威视图。
- 存量数据全部兼容：已批单的 MAKE_THEN 行照旧走 readiness 推进（由补偿器自动
  补建分析）；V447 权益桥表与历史分析只读保留；V304 LEGACY 行不动。
- 系统测试清空白名单/ops 脚本已同步登记 `procurement_order_qty_change_logs=CLEAR`。

## 四、NO-GO（沿用既有边界）

本地源码与空库迁移不等于上线：目标非空库迁移回放、多真实岗位 UAT（计划/
委外/财务/仓库/品质）、改量复核实物演练、通知三件套真机验证、恢复演练与
部署回读完成前，本 ADR 相关能力保持「已决策未上线」。
