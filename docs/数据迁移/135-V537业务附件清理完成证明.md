## 解决的问题

原清理脚本把所有非人事附件记录都当成未清理文件。正常删除只会把记录改成 `DELETED` 并保留审计，因此即使文件已实际删除，仍永远不能清空业务数据。销售订货草稿先删除后，原订单附件权限也会拒绝再删除合同文件。

现在 `fn_business_attachment_reset_blockers()` 统一判断物理删除证明，正式 psql 脚本和运行时清理函数共用。原历史迁移不改写，V537 前向替换运行时函数中的旧门槛。

- 原件必须 `DELETED`，且同存储提供方、存储键、版本的 `DELETE_FINAL` 队列有 `SUCCEEDED` 和完成时间。
- 已确认上传还须证明临时文件在原上传凭证到期后删除；未到期显示等待时间，不能提前跳过。
- 未确认或拒绝的上传会话，临时文件和最终目录都需完成删除/缺失核对。`NO_STAGING_OBJECT` 只说明临时目录，不足以证明最终目录没有孤儿原件。
- 缺少删除意图、缺少完成时间、提供方/版本不符、未知来源或队列失败继续阻止清理。
- 员工档案和劳动合同范围保持原样；完成删除的业务附件元数据及队列也继续保留审计。

## 操作入口

工作台「系统测试 → 清空数据」先读取附件状态。有未完成文件时，先进入「清理测试业务附件」，查看具体数据库、文件和等待状态，逐字输入独立确认词后提交。

准备操作沿用超级管理员、测试环境开关和排水保护，并绑定当前数据库、操作者和预览内容指纹。内容变化必须重新预览；每次最多准备 100 项，处理后刷新继续。准备只写原有删除队列，文件仍由原 `AttachmentObjectOutboxProcessor` 删除，完成前原业务清理仍被阻止。

内部存储遇到未知最终版本，不能用空版本删掉现存原件；现有存储校验会拒绝，需通过附件对账核实确切对象。若最终目录实际不存在，正常删除 worker 成功记录可作为真实缺失证明。对账模块原有观察次数、等待期限和删除授权规则不放宽。

排水准入改为原子 `tryEnter()`；已运行的 HTTP 和定时任务都计入在途数，并在结束或异常时退出。清理等待旧任务结束，同时拒绝新任务，避免检查与进入分开造成竞态。仅两个真实维护提交路径豁免自身计数，避免互相等待。
