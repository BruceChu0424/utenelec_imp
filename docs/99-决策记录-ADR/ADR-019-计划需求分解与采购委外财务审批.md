# ADR-019：计划需求分解、订货财务审批、未来入库与超量到货控制

- **状态**：已接受（源码候选）；生产启用仍为 **NO-GO**
- **日期**：2026-08-02
- **影响**：计划、采购、委外、钱流、仓库、权限、通知、审计、Flutter 工作台
- **依赖**：ADR-017（模块化单体 + Outbox 可靠旁路）、Flyway V196–V202

## 一、背景

旧页面把“申请”和“订货”都当成采购/委外部门可以直接新建、修改和审核的普通单据，容易让使用者误以为申请单也由采购制作，并让计划人员接触供应商、价格等商业字段。本次业务口径明确为：

```text
计划缺料并下达需求
  → 采购/委外查看只读申请明细
    → 在任务中心分解为一张或多张订货单
      → 指定财务负责人审核
        → 财务通过后订货才生效，并形成仓库未来入库任务
          → 仓库按预计到货登记并审核收货
            → 超出财务批准余量时先隔离并送精确财务负责人
              → 财务批准量由仓库再审入库；未批准量由原下单人退回供应商
```

申请单表达“需要什么、多少、何时需要、送到哪个仓库”；订货单才表达“向谁采购/委外、价格多少、怎样结算”。两类事实不得合并。

## 二、决策

### 2.1 申请归计划，商业信息归采购/委外

- 采购申请和委外申请由计划链生成并以 `status=1` 下达；申请端保存货品、颜色、单位、数量、需求日期、仓库及计划来源。
- 采购/委外的“申请单”页面只提供列表和详情查看，不提供新建、编辑、审核、红冲或删除入口。分解预览是只读计算，不修改申请。
- 计划使用需求投影，不访问含供应商、价格、币种和结算字段的完整采购/委外单据。V198、V200 移除 `DEPT_PMC` 祖先授权造成的商业信息继承泄漏；客户端隐藏字段不能代替该服务端权限边界。

### 2.2 任务中心只显示尚未分解的申请明细

采购和委外任务读取 V199 `v_procurement_decomposition_tasks`。权威剩余量为：

```text
open_qty = 申请数量 - 已生效订货数量 - 待财务审批订货占用数量
```

只有 `open_qty > 0` 的已下达、未关闭明细进入任务中心。待财务审批的订货虽然尚未生效，也必须先占住来源容量，避免两个采购员并发提交后共同超出申请数量；驳回后该占用自然释放。

### 2.3 分解可以跨申请，但一供应商一张订货单

- 使用者可以勾选多张申请中的多个明细，且可以只分解其中一部分数量；余量继续留在任务中心。
- 同一张订货单只有一个供应商/委外商。需要多个供应商时分别生成多张订货单，系统不按猜测规则自动拆单。
- 当前分解预览要求所选明细属于同一仓库；不同仓库必须分别成单。
- 每一条原生采购订货必须保存 `request_item_id`，每一条原生委外订货必须保存 `application_item_id`。没有计划来源、来源已变化、单位不可靠、货品不一致或连同其它待审单已超量时，财务提交和审批均 fail-closed。

### 2.4 保存后立即提交财务，`status=1` 才生效

订货编辑页对老人用户保留一个主要动作“保存并提交财务”。技术上先保存草稿，再调用提交接口；若提交失败，已保存草稿保留并明确提示，不伪装成已送审。

```text
DRAFT
  └─ 提交 → PENDING
       ├─ 驳回 → REJECTED → 制单人修改 → 新 attempt 再提交
       └─ 通过 → APPROVED，同时订单 status 0 → 1
```

`PENDING` 期间订单禁止修改或删除。驳回保留原因和历史审批 attempt；修改后重提创建新 attempt，不覆盖旧事件。历史迁入的 `status=1` 单据继续作为既有生效事实，不补造审批历史，也不重放副作用。

### 2.5 审批任务精确分配，不设超级管理员对象绕过

- 钱流管理右上角“审批负责人设置”只配置两个固定行为：采购订货财务审批、委外订货财务审批。
- 这两个行为也负责对应类型的超量到货审批。异常创建时读取当时有效配置并写入负责人快照；之后修改默认负责人只影响未来异常，不改在途任务。
- 订单审批和超量审批都必须同时满足权限与实例 `assignee_user_id`；负责人设置权、超级管理员标记或已知 UUID 都不能代替对象校验。
- 每个行为同一时刻一个主负责人；负责人必须是财务部门树内在职员工、账号启用且拥有 `finance_order_approval:review`。未配置负责人时提交失败。
- 修改配置需要 `workflow_assignment:manage`、当前密码二次确认和乐观锁版本。该权限不默认授予部门，由明确授权人员或超级管理员完成首次配置。
- 提交时把负责人写入审批实例快照；之后修改默认负责人不偷换在途任务。只有该 `assignee_user_id` 且仍有审核权限的账号收到任务并可通过/驳回。
- 超级管理员拥有权限目录能力，但不能绕过审批实例的精确负责人对象校验；前端动作完全使用服务端 `allowedActions`，不得因本地角色显示审批按钮。

### 2.6 财务通过形成未来入库事实

财务通过在同一事务内调用既有采购/委外生效副作用、把订单置为 `status=1`、写审批事件，并创建唯一的 `inbound_expectations` 及其行快照。可靠 Outbox 通知：

- 提交：只通知精确财务负责人；
- 驳回：通知提交人修改重提；
- 通过：通知提交人，并通知仓储部预计到货。

通知只是提醒，不是权威任务源。仓库未来入库数量以 `inbound_expectations` / `inbound_expectation_items` 为准。

## 三、仓库超量到货的财务授权闭环

V201 把“仓库报告实到、财务决定可追加入库量、原下单人处理未批量”拆成三个互不越权的任务。采购/委外下单人不再决定超量是否可入库。

### 3.1 检出时先隔离，不写库存或应付

仓库从 `inbound_expectations` 登记采购收货或委外回厂。审核事务重新锁订单来源并计算：

```text
财务已批准可收容量 = 原订单批准量 + 已退数量 + 已成功过账的超量批准额度
本次超量 = max(本次申报量 - 当前可收余量, 0)
```

超过余量时返回 `ARRIVAL_EXCEPTION_PENDING`（HTTP 409）。该专用异常允许同一事务提交 `PENDING_FINANCE` 异常及追加事件，但收货单仍为草稿，库存、应付、订单收货累计均不写。异常存在期间，数据库触发器禁止仓库通过改量、换来源、软删或删除收货单绕过财务任务。

### 3.2 只有精确财务负责人决定追加量

异常创建时按采购/委外类型读取当前 `workflow_responsibility_assignments`，复核负责人属于财务部门树、员工在职、账号 active 且仍有 `finance_order_approval:review`，然后冻结 `finance_assignee_user_id/employee_id/name`。V201 只向财务部门补 `purchase_order:view` / `subcontract_order:view` 以查看任务关联订单，绝不授订单编辑权。只有精确负责人能看到任务并执行一种决定：

- `APPROVE_ALL`：批准本次全部超量，并填写财务说明；
- `APPROVE_CUSTOM`：批准追加量必须严格满足 `0 < 追加量 < 本次请求超量`，并填写财务说明；0 使用 `REJECT_EXCESS`，全部使用 `APPROVE_ALL`；
- `REJECT_EXCESS`：追加量为 0，只接收原订单财务批准的当前余量。

服务端据此计算 `accepted_qty = approved_remaining_qty + approved_excess_qty`（不超过本次申报量）和 `unaccepted_qty`，受控收窄草稿收货行及金额。批准额度绑定本异常、本收货单和订单行，不能被另一张并发收货单复用；仓库再次审核成功后才把批准的超量累加到订单行 `arrival_overage_posted_qty` 并按调整后的权威数量/金额写库存和应付。

标准 `10→100` 示例（没有历史收退）：全批对应入库/退回=`100/0`；自定义额外批准 5 对应 `15/85`；不批超量对应 `10/90`。财务决定本身不写库存或应付，接受量仍须仓库再次审核。

### 3.3 未批准量只交原下单人退回

`unaccepted_qty > 0` 时创建唯一 `supplier_return_tasks(PENDING_RETURN)`，负责人是原采购/委外订货的下单人。`supplier_return_task:handle` 只给该人员“确认已退供应商”动作，不能修改财务决定或扩大入库量；完成动作使用 `expectedVersion` 并追加 `RETURN_COMPLETED` 事件。通知只是提醒，财务任务、仓库异常和退货任务均以服务端投影为权威。

通知接收人固定为：检出超量只提醒异常快照中的精确财务负责人；财务决定只提醒仓储部，接受量大于 0 时要求按调整后草稿再审，接受量为 0 时明确该收货行已移除；退回待办和完成回执只提醒原下单人。通知仍不是审批、入库或退货完成的权威事实。

V201 完成的是数量授权、库存/AP 防越权和退货责任闭环，不是完整 IQC。`inbound_expectations` 仍不是实物、质检或库存事实；现有收货过账也不得冒充待检、合格、不良、特采和质量反向。完整质量隔离与岗位实物验收完成前，不能据此宣称物料已具备生产可用质量，生产仍为 **NO-GO**。

## 五、迁移与发布结论

公司目标库当前只读证据最高为 V190。V196–V202 只是源码候选，尚无公司目标库应用、迁移前后快照、真实账号岗位 UAT、仓库收货/财务审批/供应商退回实物演练、完整 IQC 和发布签字，因此不能宣称已上线。

Flyway 已执行迁移不可修改、重命名或重排；生产事实以目标库 `flyway_schema_history` 为准。若 V196–V202 在任何共享环境已经执行，修正只能新增 V203+，不得回写旧 SQL 或用本地顺序回放冒充 Flyway 校验。

## 六、后果

- 好处：计划需求与商业订货职责清楚；老人用户只需在任务中心选需求、在订货页保存提交；普通订货和超量到货都只到具体财务负责人；仓库只能按财务批准量过账；未批准量明确回到原下单人。
- 代价：同一时刻每类订货只有一个主负责人；跨仓库和多供应商必须分单；负责人配置缺失会有意阻断提交；异常收货必须等待财务决定并由仓库再次审核。
- 待续：完整 IQC/隔离/不良/特采与质量反向、负责人离职或停用时的受控改派、真实多账号黑盒验证、仓库及供应商退回实物 UAT、目标库迁移与发布签字。
