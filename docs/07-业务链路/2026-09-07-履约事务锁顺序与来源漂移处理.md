# 履约事务锁顺序与来源漂移处理

状态：2026-09-07 本轮源码实施及专项验证中；本文件不代表全平台回归、压力或上线验收通过。

## 1. 本轮已证实的问题

- 销售订单改量先锁订单头、行及计划分摊，再取库存锁；成品入库先取库存和执行对象锁，随后回写同一销售订单。两条真实路径可以形成订单与库存相互等待。
- 采购、委外改量与收货也存在商业订单头和库存先后不一致；审批下游还会访问原采购申请、委外申请，不能只将最终订单头提前。
- 物料分析原有“分析头 → 主仓协调锁 → 销售来源”在同仓多分析批处理时还可形成“分析 A1 → 主仓 → 分析 A2”与“分析 A2 → 主仓”的环。
- 退货质检原来先锁质检行再锁库存，整单反向又先锁退货单。质检与反向必须共享相同的来源、库存和退货头前缀。

商业来源与执行单据必须区分：销售订单、采购申请、委外申请、采购订单、委外订单属于商业来源；出货单、收退货单、质检行、仓库单属于后续执行对象。不能把所有名称中含“订单/单据”的表头一律放到最前。

## 2. 共同偏序

一次命令在自己的事务内，先只读发现实际访问范围，然后顺序锁定：

1. 全部商业来源头，固定类型顺序：销售订单 → 采购申请 → 委外申请 → 采购订单 → 委外订单；每类按 UUID 文本顺序，与 PostgreSQL UUID 排序一致。
2. 这些来源的全部现存明细，按来源头和明细 UUID 排序。全部来源头先于任何来源明细。
3. 完整货品、颜色库存集合，复用现有 `InventoryMutationLock`。仓库不属于该锁键，NULL 颜色沿用原口径。
4. 全部相关主仓 `MATERIAL-ANALYSIS-WAREHOUSE` 协调锁，排序取得。
5. 全部相关物料分析头，排序取得。
6. 再进入各模块现有计划、计划包、执行段、执行单据和明细的约定顺序。

纯认领、续租没有库存及上游申请回调，可以保留商业订单头 → 审批 case → claim 的已有顺序。实际财审决策、提交和改量若访问来源申请，必须在第一个商业头之前发现并取得整批来源，不能到下游回调才补锁。

这里的集合是实际有向调用范围。实际物理库存变动才扩展它会唤醒的分析；只为保护该分析而增加的其它库存维度不能再次扩展唤醒集合。反向操作另外纳入其原始分析和计划来源，避免漏掉反向前已经完成的分析；不得扫描、锁定全部历史已完成分析。

## 3. 等待期间来源变化

`FulfillmentMutationLocks.acquire(discovery)` 返回本次计划与 `Guard`。取得执行对象行锁后，首次业务写入前调用 `verifyUnchanged()`，重新只读发现并比较来源指纹。旧单据来源与本次请求的新来源必须一起预读，不能只保护其中一边。

**2026-09-23 起(ADR-107)以事务为单位「一轮发现 + 一次版本复核」**：

- 事务里第一次 `acquire` 跑一轮只读发现并按 §2 偏序拿锁；之后的嵌套 `acquire(declared, discovery)` 不再执行发现，只对调用方声明的已知 id(订货单、库存维度、分析)在内存里查是否已在预锁集合内。生产配置下嵌套命令没声明的商业来源与主仓不再有运行期检查；测试类路径默认打开诊断开关 `uten.concurrency.verify-nested-footprint`，嵌套 `acquire` 重跑自己的发现并要求落在预锁集合内，让全部真库用例持续证明嵌套足迹被覆盖(量语句数的用例关掉它，量的是生产配置)。
- 锁后复核整个事务只做一次：取锁命令的守卫第一次 `verifyUnchanged()` 重读一轮与预读比较，之后再调用不读库；嵌套守卫的 `verifyUnchanged()` 只确认仍属于当前事务。取锁命令从没复核就进入嵌套命令时(只为给嵌套出库预锁的入口)，第一个嵌套 `acquire` 替它做一次锁后覆盖复核(重读的足迹必须仍落在已持有集合内)。
- 来源指纹从每行 `md5(to_jsonb(row))` 改为每行 `(id, xmin)` 行版本：任何 UPDATE 都换版本、只加行锁不换版本，新增/消失的行体现在行集合里。一轮发现内订货单、唤醒目标、BOM 等按「方法 + 参数」只读一次，物料分析在本轮末尾对并集只展开一次(`FulfillmentDiscoveryRound`)。
- 主仓 `MATERIAL-ANALYSIS-WAREHOUSE` 协调锁仍是阻塞式咨询锁(在数据库锁管理器里排队、死锁由数据库检测)，等待上限就是连接上的 `lock_timeout`(应用连接默认 10 秒；后台任务可在自己的事务里调短)，到点拿不到返回可重跑 409「有人正在处理同一仓库的单据，请稍后再试」；预锁阶段其它锁(订货单头与明细、库存维度、分析头)等待超过 `lock_timeout` 同样转成可重跑 409「有人正在处理相关单据，本次操作未生效，请稍后再试」。整笔回滚的只读预览(下达车间预览)取共享锁，预览之间互不排队。

已经提交的相同幂等请求可以在锁后验证不可变请求键及内容，然后只读返回原结果；此时不要求旧来源快照继续相等。未命中原结果的请求仍须在任何写入之前验证。不能把不同请求的来源漂移当作成功重放，也不能因另一请求刚完成而拒绝真正相同的重放。

若发现来源、数量快照或库存维度变化，整笔请求返回冲突并回滚，要求使用新数据重新提交；不能在持有库存/执行锁时再取得新商业来源或新库存锁。批量命令必须一次发现全部来源后再处理各行，保持同事务成功或全部失败。

自己的写入会改变状态、数量和分析指纹，因此写后回调只调用 `requireCovered()` 验证所需集合属于当前已锁集合，不再次要求旧业务快照相等。库存锁入口也检查本次已声明集合，遗漏维度会在发出新锁 SQL 之前拒绝。2026-09-23 起写后回调尽量声明已知 id(分析唤醒 `requireAnalysesCovered`、收货送检 `requireReceiptCovered` 只读收货明细的订货单与维度)，拿不出已知 id 的才用 `requireDiscoveredCovered` 跑一轮去重发现。

### 3.1 瞬时冲突由服务端自动重跑(2026-09-21)

用户实测：品质「批量审批」按 4 条并行通道逐单提交，同一张订货单先入库后质检登记的两张收货单同时判定，第二张在 `verifyUnchanged()` 被「来源集合在预读后变化」拒绝(第一张已改了同一订货明细与待检行)，页面只能人工「重试原报告」；所有走本守卫的单据链(收货登记、IQC、仓库入库、出仓发料、财务批准、出货等)在多用户同时操作同一来源时都有同样的现象。

守卫的语义不变：等锁期间别的事务先提交，本事务预读的来源集合已过期，本命令一笔都没写，整笔回滚。变化的是「用新数据重新提交」这一步不再交给客户端：

- 守卫按原因分成两类。`verifyUnchanged()` 的集合漂移、库存锁入口的维度漂移、预锁阶段任一把锁等待超过 `lock_timeout`、以及靠**重新发现**做的覆盖检查(`requireDiscoveredCovered()`、嵌套锁后覆盖复核、诊断开关下的嵌套发现——它们会读到预锁没锁住的依赖，例如计划 BOM 递归，别的事务改了也会超出集合；记 WARN)标记为**可重跑**(`FulfillmentSourceConflictException.retryable()`)；预锁顺序/归属错误(已进入库存锁阶段再补商业来源、登记非本事务新建来源、来源已不存在等)以及 `requireCovered()` 对调用方**声明的已知 id** 的覆盖缺口(2026-09-23 起，ADR-107：这是足迹声明缺口，重跑结果一样，改为不可重跑并记 ERROR)是结构性冲突，原样 409。
- `FulfillmentSourceConflictRetryInterceptor` 以基础设施 Advisor(顺序 1000，位于方法安全拦截之内、事务拦截之外，不引入 AspectJ)挂在本应用全部 `@Transactional` 方法上：进入时线程无事务(即这次调用就是一条完整命令，传播为 REQUIRED/REQUIRES_NEW/NESTED)才会重跑，最多 5 次，间隔 20/40/60/80 ms 递增并带 0..40 ms 抖动，让同批并行命令按到达顺序错开，另有两道时长预算(2026-09-23，ADR-107)：重跑预算 10 秒从**第一次冲突**开始计(第一次执行含排队等锁的时间不算——等锁后才发现来源变了正是要重跑的情形)，命令开始后已过 30 秒不再发起新的一次(客户端 45 秒放弃等待)；嵌套调用(已有事务)一律不重跑，交给外层。超过上限或预算返回原 409 文案(带 `Retry-After`)；客户端不会自动重发业务写请求，由用户稍后重新提交。
- 重跑就是同一请求的完整再执行：重新预读来源、重新按 §2 的偏序拿锁、重新校验业务量。它不会让本来就冲突的两条命令都成功——落后的一条重跑后按新事实校验，该拒仍拒(例如可用量已被先提交的一条用完)。

验证：`FulfillmentSourceConflictRetryInterceptorTest`(重跑/不重跑/上限/嵌套不重跑)、`FulfillmentSourceConflictRetryConfigTest`(切点与顺序)、`FullChainEndToEndTest#concurrentInspectionDecisionsOnTheSameOrderSucceedWithoutManualRetry`(同一订货单三张先入库后质检收货单并行判定全部一次成功、库存 20)。

## 4. 事务新建来源的例外

本事务新建且未向其它事务可见的分析或申请可以登记到已持有范围，不能用这一例外登记旧行。流程为：生成新 UUID → `expectCreated*` 确認该 UUID 不存在 → 普通 INSERT → `registerCreated*`。

登记校验目标行的行版本属于当前事务(xmin = 当前事务号)。2026-09-23 起(ADR-107 / db-schema-02)不再读 `audit_log` 的 INSERT 证据——审计有保留期、可能只记变化列，不能当业务事实源。「既有行」由 `expectCreated*` 事先确认 UUID 不存在来排除；「别的事务抢先提交同一 UUID」由约定的普通 INSERT 撞主键唯一约束整笔回滚来排除；upsert(`ON CONFLICT UPDATE`)不是受支持的新建方式，实体层 `save()` 新实体一律 INSERT(BaseEntity 实现 Persistable)。不引入全局互斥锁。

锁覆盖证明绑定真实 Spring 事务，支持挂起、恢复以及 `REQUIRES_NEW` 独立作用域；提交后清除证明，完成回调不可复用已释放的锁。它不替代 PostgreSQL 锁，也不将内存状态当跨进程的所有权证明。

### 4.1 货品默认写入与保存点

入库会更新货品归属仓，因此在完整 S/I/W/A 前缀之后、首笔入库实物写之前，还须按 PostgreSQL UUID 顺序锁定本事务已声明库存范围中的全部货品。使用共同 `PostgresUuidOrder` 比较高低 64 位无符号值，不混用 Java UUID 的有符号自然顺序。该步骤在 `StockService` 的过账边界执行，不插入 `FulfillmentInventoryMutationAdapter` 的库存阶段。

首次过账后冻结精确的货品/颜色 `InventoryKey` 集合。同一货品的新颜色同样属于新库存锁，不能因 goods UUID 已存在而放行；任何范围外的补锁在发送 advisory SQL 前拒绝，调用方应先声明完整批次。

Spring 管理的保存点创建时，商业来源、库存、主仓、分析及新建来源登记保存证明快照；回滚恢复保存点前实际持有的范围，资源在该保存点之后才建立时没有任何可保留证明。货品过账锁在回滚后失效，重新写入前先按原顺序真实重取当前有效的完整库存范围，再锁货品行。`requireHeld` 与 `requireCovered` 不得继续接受已随回滚释放的证明。

该机制支持 `TransactionStatus.createSavepoint/rollbackToSavepoint` 的 Spring 同步回调；生产代码未发现 raw JDBC 保存点调用。任意手写 SQL `ROLLBACK TO` 不会通知 Java 同步器，不能把其后调用 `requireHeld` 当成数据库仍持锁的证明。真实 PostgreSQL 双连接测试分别检查保存点前锁保留、保存点后锁释放、重取、未声明颜色拒绝与 `REQUIRES_NEW` 隔离。

## 5. 销售入口迁移范围

- 订单修改、审核、反审核、取消、改量、停止、部分发货确认，以及订单行优先级和让单：自己的订单来源和旧/请求库存集合先行。订单行入口先解析并锁来源头，再锁明细，保留原对象范围、动作权限和财审占用门禁。
- 出货创建、修改、删除、财务放行及撤回、仓库作业、发运、驳回和反向：全部来源销售订单与库存先行，再锁出货头。批量创建先取得全部来源，再创建各组。
- 退货创建、修改、审核、反向、客户处置以及质检处置/纠错：同时发现直接订单行与原出货行的真实订单来源，再取得库存、退货头及质检对象。
- 其它出货的新增、修改、审核和反向同样保护已有来源及库存，但仍保留其原业务语义：不自动回写销售订单、不生成正式应收。

现有财务金额权威、原发运/退货数量守恒、预留边界、对象权限、财审认领及幂等检查继续执行。本轮改锁顺序不能放宽这些检查。

## 6. 验证边界

新增 `FulfillmentMutationLocksPostgresTest` 用独立 PostgreSQL 与真实 Spring/JPA 事务验证共同锁机制，包括两个等待方向、无关来源不被全局串行、等待期间来源切换拒绝、完整来源明细保护、库存集合遗漏拒绝、事务挂起/恢复和提交后失效，以及新建来源登记反例。其简化表只用于锁机制，不能替代 Flyway 和真实业务数量/金额验收。

`SalesReturnQualityIdempotencyPostgresTest` 使用实际销售锁前缀、实际库存锁与实际质检服务，继续验证幂等重放、并发、处置纠错的库存与事件事实。完整销售与生产服务跨域正反向竞争、共同前缀尚未接入的入口、全量测试与规模测试，由本轮验收计划逐项登记结果，不能仅以此机制测试声称业务全链已通过。

本轮阶段结果：`sales-lock-plan-r2.log` 的 31 项定向检查通过（含共同锁 PostgreSQL 7 项、销售质检 PostgreSQL 9 项）。`sales-finished-lock-race-r2.log` 中真实 FullChain 的双向竞争通过：原销售订量 10 改为 12、成品实收 10；两种竞争次序最终均保有完工 10、预留 10、实物 10、库存流水净量 10、计划/分摊入库 10，只有一次入库确认。入库先提交时，持旧快照的改量请求返回冲突且无部分写，刷新后可完成。该场景使用明确的兼容手工生产计划，不证明分析来源的变更待财审边界已闭环。

## 7. 普通计划与计划包接入补充

普通计划和执行计划包也须使用前缀，不能仅保护由物料分析创建的计划。`ProductionPlanMutationFootprintService` 发现本计划及实际生成子计划、销售分摊、当前有效包的采购/委外申请、显式供给挂接、完整生产 BOM 库存集合，并合并它们原本所属的分析范围。子计划范围沿真实有向生成关系展开；不扫描无关联的公司历史计划或订单。

删除了 `ProductionPurchaseRequestFacade.lockOpenSupply` 及其独用返回类型：唯一调用丢弃其计算结果，后续 `lockedSnapshot` 读取的是库存、真实预留/权益、计划与 BOM，`v_stock_available` 也没有采购在途来源；该方法仅额外锁定所有同货品开放采购单，未产生真实分配。保留当前库存锁、快照校验和显式 peg；新回归需同时证明无分配的开放 PO 不提供齐套量、其单头占用也不阻塞本计划。

独立未闭环边界：订单改量后重新待财务复核时，原已确认分析任务的实物回调与新增/增量下达如何区分，须按 ADR-072 和本次确认的业务规则处理；不能仅凭“过去财审时间非空”放行全部新需求，也不能跳过初次财审来通过测试。

## 8. V508：撤回计划包后重新安排的销量分摊容量

真实业务回归发现，原 V157 的跨段容量累计包含了已经 `CANCELLED` 的旧段，因此“计划 10 → 下达 10 → 未开工撤回 → 原计划重新下达 10”被累计为 20，错误拒绝正常重建。V508 只替换相关校验函数，不删除、修改或重建任何旧分摊行，也不修改 V157 字节。

有效容量只排除明确 `CANCELLED`、`REVERSED` 的执行段。`READY`、`WAITING`、`IN_PROGRESS`、`COMPLETED` 仍计入；不能仅凭执行段或计划包被软删就忽略其已完成实物。原明细身份、每段分摊合计等于该段计划量、分摊行不可 UPDATE/DELETE 等约束全部保留。

校验先按当前段关联的计划销售分摊 UUID 取得 `FOR NO KEY UPDATE`，再读取身份和累计，使用现有按 plan link 的索引统计当前链接，避免每次聚合全平台历史。锁使用 `NO KEY UPDATE` 是为了兼容新增明细外键的 `KEY SHARE`，避免两个事务在提交期一起升级成 `FOR UPDATE` 而相互等待。

数据库写隔离合同明确限定如下：新增销量分摊，以及修改计划销售联动的容量或身份（`allocated_qty`、`is_deleted`、`plan_item_id`、`order_item_id`），使用应用现行的 `READ COMMITTED`。分摊 INSERT 的隔离错误在 BEFORE 触发器拒绝；联动容量/身份更新由原延迟约束触发器在检查时拒绝，默认发生于提交，整笔事务回滚。该限制不涉及普通报表读取，也不拒绝责任人/审计元数据交接使用的 `REPEATABLE READ`。不声称其它隔离级别允许分摊写入。

## 9. 报工、FQC 与补产恢复入口

`ProductionQualityMutationFootprintService` 按实际日报明细、质检、恢复授权及恢复分析链接收集计划集合，使用一次批量计划发现合并商业来源和库存前缀。日报审核/反向在日报头之前进入前缀；FQC 单条与批量决定在 inspection/执行段之前进入前缀；补产物料确认、创建恢复分析在 task/authorization/plan 之前进入前缀。失败贡献回退及授权撤回的下游方法只验证当前集合覆盖，不在回调里补取新的上游锁。

品质批量命令先只读检查相同用户/幂等键的不可变批次结果。未命中时，锁全批 inspection/执行对象并核对全部待检状态，再复核来源、建立批次及逐项决定；任一失败全事务回滚。已存在同键结果只读返回，且同键异体仍拒绝。

真实服务测试同时修复两项被旧单元夹具掩盖的问题：补产材料确认的单列 `request_hash` 用 `String` 读取，避免重复请求在 PostgreSQL 返回标量时崩溃；恢复撤回的领料单查询改为先锁单头、再锁真实明细并逐项确认实发为零，移除 PostgreSQL 不支持的 `GROUP BY ... FOR UPDATE` 组合，保留有实发必须先退/撤出库的门禁。

## 公共在途采用的来源预锁

`claimSharedFuture`会把另一分析的采购申请或委外申请引用到本分析的新采用行动。仅预锁本分析原有来源不够：写入后正常刷新会发现这个已有商业来源，按锁顺序应拒绝回调补锁。

采用命令现在调用`ProductionMutationFootprintPort.forSharedFutureClaim`，在持锁前发现本仓、本分析有效物料可采用的公共来源，并将来源UUID和可采用量纳入指纹；锁定后再核验。后续仍按路线、到期日、实际可采用量和需求上限选择，不把公共剩余变成原分析需求，也不遍历锁定全库同货品关联图。来源改变时整体回滚并要求刷新。
