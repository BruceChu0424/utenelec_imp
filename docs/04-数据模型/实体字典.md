## 2026-10-04 车间内料仓开通单一真源 (V802 / ADR-147)

决策见 [ADR-147](../99-决策记录-ADR/ADR-147-车间内料仓开通单一真源与发料来源仓.md)，迁移与回填规则见 [V802 说明](../数据迁移/V802-车间内料仓开通单一真源.md)。

| 实体/字段 | 权威用途 | 不变量与边界 |
|---|---|---|
| `workshop_bins` (新, 主键 `workshop_department_id`) | 一行 = 这个车间的内料仓已开通(可收车间直送)；页面三态 未开通 / 已开通 / 整批领料中 由服务端据它与 `workshop_material_settings.periodic_enabled` 给出 | 只能由开通命令(`WorkshopBinService`)写；审计 FULL，业务清空 PRESERVE |
| `workshop_bins.bin_warehouse_id` | 本车间的内料仓(`warehouses.is_line_side` 的那一行，挂在唯一主仓下) | 唯一；必须是本车间未删除的内料仓；未删除的内料仓与开通行同生共死(延迟约束触发器，提交时校验)；一个车间最多一个未删除的内料仓(`ux_warehouses_line_side_workshop`) |
| `workshop_bins.source_warehouse_id` | 默认发料来源仓；空 = 按货品所属仓库 | 只能是启用中的良品子仓(`fn_warehouse_is_good_stock_leaf`)，不能是内料仓自己；仍被引用的仓不能停用/删除 |
| `workshop_bins.opened_by/opened_at/updated_by/updated_at` | 开通人与最后修改 | 存量回填行的开通人取整批领料开启人或建仓人，可能为空 |
| `workshop_bins.row_version` | 开通状态版本：改来源仓、开启/撤销整批领料都加一，批量命令按它判断是否被别人改过 | 每次改动恰好加一，否则 `workshop_bins_version_guard`(回 409) |
| `workshop_material_settings` (V740) | 只存整批领料这个子能力 | 复合外键 `(workshop_department_id, periodic_bin_warehouse_id) -> workshop_bins`；只能开在已开通的内料仓上 |
| `fn_workshop_bin_default_source(内料仓, 货品, 颜色)` | 发料默认出库仓的唯一算法：来源仓有可发量 -> 货品所属仓库 -> 可发量最大的良品子仓 | 都排除不良品仓与内料仓；可发量按 `v_stock_usable`；都不满足返回空 |
| `fn_workshop_bin_revoke_blockers(内料仓)` | 撤销开通前的阻塞原因(大白话数组) | 整批领料还开着、有进出、有余额、有直送、有单据引用、有预留、有领料申请时不能撤销 |
| `production_daily_report_items.output_route_reason` | 增加 `WORKSHOP_BIN_NOT_OPEN`(收料车间没开通内料仓，这部分送入仓库) | 车间直送不再自动建仓 |

### ApprovalRecord（审批记录 / Approval Record）

**用途**：某条业务单据（报销单/工资条）审批轨迹的一格，记录谁、在哪个节点、做了什么决定。
**所属模块**：approval（跨模块通用）
**双写标记**：审批结果属敏感管理数据，按需双写

**关键字段**：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID | 主键 |
| entityType | enum(`expense`/`payroll`) | 关联的业务类型 |
| entityId | String | 关联的业务单据 ID（报销单/工资条批次）|
| nodeOrder | int | 第几节点（对应 ApprovalNode.order）|
| approverId | String? | 实际审批人（指向 Employee）|
| decision | enum(`pending`/`approved`/`rejected`) | 决定 |
| comment | String? | 审批意见 |
| actedAt | DateTime? | 审批时间（UTC）|

**关联**：
- 多条 ApprovalRecord 属于一条 ExpenseClaim / PayrollBatch（按 entityType + entityId）
- ApprovalRecord → Employee（审批人，多对一）

**业务规则**：
- 目标通用审批模型可按 `nodeOrder` 形成时间线，但当前没有 `UtenTimeline`，也没有落地通用

- 当前节点 decision=pending 表示「待审批」，高亮
- 驳回是终态还是允许修订重提必须由流程模板显式定义
- 末节点 approved 只推进为业务“已批准”；报销付款和工资发布仍是独立权限与独立动作
- 状态变更必须使用数据库行锁/版本条件之一，并由集成测试证明并发安全

### ProfileChangeRequest（个人信息修改申请 / Profile Change Request）

**用途**：员工自助修改个人信息时提交的待审申请。一次提交可包含多个字段，共用 `batch_id`；HR 整批批准 / 驳回。
**所属模块**：profile（跨 employee / auth 边界）
**双写标记**：否（首次引入；未来接老系统影子双写时再加）

**关键字段**：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID | 主键 |
| employee_id | UUID (FK→employees) | 目标员工 |
| batch_id | UUID | 同批次多字段共用 |
| field_code | VARCHAR(64) | 机器码（phone / fullName / emergencyContact.0.phone…） |
| field_label | VARCHAR(128) | i18n 标签快照（HR 端直接展示，不依赖客户端语言） |
| field_group | VARCHAR(32) | identity / contact / address / emergency / compensation / org |
| old_value_enc | TEXT | 旧值快照；存储形态由 `value_encoding` 权威标记，不按列名或冒号猜测 |
| new_value_enc | TEXT | 新值快照（必填）；敏感字段必须为带领域标记的版本化 pgcrypto 密文 |
| value_encoding | VARCHAR(24) | `PLAIN` / `PGCRYPTO_V1`；`LEGACY_UNKNOWN` 仅允许存在于 V284 启动回填完成前，未完成时读取、审批和状态更新失败关闭 |
| status | VARCHAR(16) | pending / approved / rejected / cancelled / applied |
| submitted_by | UUID (FK→employees) | 提交人 = 员工本人 |
| submitted_at | TIMESTAMPTZ | 提交时间（UTC） |
| reviewed_by | UUID (FK→employees) | 审批人 |
| reviewed_at | TIMESTAMPTZ | 审批时间 |
| review_comment | TEXT | 审批意见（驳回必填） |
| employee_version | INT | 提交时 employees.version 快照；审批时校验 |
| idem_key | VARCHAR(64) UNIQUE | 客户端幂等键，防重复提交 |

**关联**：
- N → 1 Employee
- 1 个 batch 由 N 条记录共用 batch_id

**业务规则**：
- 字段策略分三档（`ProfileFieldPolicy`）：
  - **directEdit**：民族 / 政治面貌 / 婚姻 / 现住址 / 办公电话 / 邮箱 / 工位 —— 提交即生效
  - **requiresReview**：姓名 / 户籍地址 / 手机 / 紧急联系人 —— HR 通过后合并
  - **hrOnly**：性别 / 出生日期 / 工作地 / 薪资 / 银行 / 身份证 —— 员工不可自助申请
- 乐观锁：审批时校验 `employee.version == row.employee_version`，不一致 → 409
- 24h 内同字段 `pending / approved / applied` 记录数 > 0 → 拒绝重复提交
- 审批人为本人 → 403
- 审批快照保护策略与审核策略分离：手机、户籍地址和全部 `emergencyContact.*` old/new 快照走带领域标记的版本化 pgcrypto 密文；姓名虽需审核但仍为 `PLAIN`。
- V284 新写由统一 codec 编码/解码，敏感 INSERT/UPDATE 还必须绑定 `app.profile_change_snapshot_codec=v1` 事务级能力，数据库因此拒绝旧实例/旧 JAR 的状态变更；历史敏感行先标记 `LEGACY_UNKNOWN`，逐行验证/加密成功后才转 `PGCRYPTO_V1`。带版本密文按当前/历史 keyring 选 key；无版本旧 pgcrypto 只尝试当前 key且不猜测旧 key，无法判定或解密时失败关闭并保留原值。发布必须停写、排空旧实例后单版本切换；禁止新旧滚动并存及旧 JAR 回滚，失败只做前向修复或恢复与旧版本完整一致的隔离验证数据库备份。
- 通用审计不复制 old/new 密文或明文；V284 定向清除历史 `profile_change_requests` / `profileChangeRequest` 审计行中的 old/new 快照键和 `review_comment`，保留对象、状态、操作者和编码状态等业务元数据。

**状态机**：
```
pending  ──approve──>  applied    (字段已合并到 employees / employee_sensitive / emergency_contacts)
pending  ──reject ──>  rejected
pending  ──cancel ──>  cancelled   (员工主动撤销)
applied  ──（终态）──>  applied
```

- [ ] HR 驳回后是否允许员工一键"复用旧值 + 仅修改一项"快速重提

**用途**：轻量的部门岗位目录，挂在可用人组织下，员工可选择担任。它不是独立定编席位，当前不支持多任职、缺编或代岗。

**关联**：属于一个 Department；多个 Employee 担任。

## 五、命名约定（数据层）

- 实体名：UpperCamelCase 单数（如 `Employee`，不是 `Employees`）

- 枚举：lowerCamelCase（如 `status.active`）

- 布尔字段：`is`/`has` 前缀（如 `isActive`、`hasPermission`）

## 七、Phase 2 后端落地实体（Spring Boot + PostgreSQL，已建表）

> 以下实体随"人事模块端到端"在 `server/` 用 Flyway 建表落地（UUID 主键、TIMESTAMPTZ UTC、软删除、审计列）。机密字段 pgcrypto 字段级加密，DTO 按 `employee:pii:view` / `employee:compensation:view` 等权限点脱敏，不按角色名判断。

### User（登录账号 / Employee → User 0..1，User → Employee 1）
`id, employee_id(unique FK), login_account(unique, 默认=手机号), password_hash(Argon2id), must_change_password(首登强制改), status(active/locked/disabled), is_super_admin, auth_version, failed_attempts, locked_until, last_login_at, last_password_changed_at, remote_access, temp_password_expires_at(V297)`
> 登录不开放注册；账号随受 `employee:create` 与敏感写权限保护的入职流程创建，或由 `account:support`
> 持有人在员工详情页/权限管理页补开（账号=手机号、初始密码=系统随机临时密码且限时有效、首登强制改；ADR-110）。
> 在册 Employee 合法地可以没有 `users` 行，这才是“未开户”；`locked/disabled` 是已有账号状态，
> 不得当成未开户创建第二行。User 一旦存在，`employee_id` 必填且唯一。
> 账号状态以 `users.status` 为准。`temp_password_expires_at` 是临时密码有效期：入职、补开账号、
> 管理员重置都写 now + `temp_password_ttl_hours`(默认 72 小时，到期拒登)，本人改密成功清空；
> 离职与复职把它置为当前时刻(旧密码立即作废，复职后由账号支持重新发放)。V682 触发器
> `trg_users_temp_password_expiry`：必须改密的非超管账号写空即按已过期落库(只有引导超管的初始密码可以不设)，
> 库里永远不存在永久有效的临时凭据。

### Role / Permission / RolePermission（历史兼容 + 权限目录）
`Role(id, code[employee/hr/finance/lab/production/manager/admin], name, is_system)` · `Permission(id, code[如 employee:view], name, category, ..., high_risk)` · `RolePermission(role_id, permission_id)` M:N。
> `permissions.high_risk`(V682，ADR-110)：持有者的登录凭据(重置临时密码、给存量员工补开账号)只能由
> 超级管理员发放。清单在迁移里集中维护(V212 高危清单、账号支持、余额调整、财税模块全部审批/执行类、
> 报销审批与付款、工资生成/审核/发布/查看全员)，代码只读标记(`CredentialIssuancePolicy`)。
> V29 起角色不再参与有效权限合成。现行权限 = 全员基础 ∪ 部门配置（含上级）± 个人覆盖；
> 只有 `superAdmin` 享有全量。角色表仅作历史兼容。

### UserRole（用户↔角色 M:N，历史兼容）
`user_id, role_id`。V29 起不决定有效权限，仅保留历史数据/兼容 claim。

### DepartmentPermission / UserPermissionOverride / UserDataScope（现行授权配置）

- `department_permissions(department_id, permission_id, created_at, created_by)`：部门直接权限；员工读取所属
  部门及祖先部门配置的并集。`audit_log:view/export` 禁止部门配置。15 个业务部门的默认权限由
  `V212__department_permission_matrix.sql` 作为单一权威来源种子化（受控重置：先 DELETE 再 INSERT，
  `ON CONFLICT DO NOTHING`），明细见 [部门默认权限矩阵](../数据迁移/54-部门默认权限矩阵.md)；
  3 个管理中心与公司节点保持空白，避免向下越权继承。
- `user_permission_overrides(user_id, permission_id, effect)`：`grant` 个人加授，`revoke` 从合成结果回收。
- `user_data_scopes(user_id, scope, owner_employee_id, created_at, created_by)`：`scope` 为
  `goods/client/sales`（owner 列 `owner_employee_id`）或 `purchase/subcontract/production_plan/stock_doc`
  （V233；owner 列为各单据表的 `maker_id`），表达除本人和公共数据外可额外查看+可编辑的归属人。
  采购/委外/生产/库存单据的对象级归属列 = `maker_id`（create 即填当前员工）；老数据 maker_id 为空 =
  公共可读、普通不可写。`*:view:all`（`purchase/subcontract/production_plan/stock_doc`）持有人或超管看全部。
- `authorization_state(singleton_id=1, epoch, updated_at)`：共享授权版本；与 `users.auth_version` 一起写入
  staff access JWT，并在每次请求复查。个人授权变化提升用户版本，部门树/部门权限等共享变化提升全局 epoch。
- `users.remote_access`（V241）：员工是否允许经云端入口访问，默认 `false`；它是账号部署边界，**不属于**
  `permissions` 目录，也不参与上面的部门/个人权限集合运算。cloud 在员工登录签发前、refresh 轮换前和
  每个已认证业务请求三处复核，未授权返回 `403 REMOTE_ACCESS_DENIED`；visitor 是独立公网 OTP 例外。
  仅超管且持 `authorization:manage` 可调用 `PUT /api/admin/users/{id}/remote-access`。授权和撤权两个方向
  只要值发生变化，都会 bump `auth_version`、撤销该用户全部 refresh token并记审计，要求重新登录；
  撤权后旧 access 先因版本不匹配返回 401，旧 refresh 在 cloud 返回 403。本地入口另由公司 CIDR 门禁
  保护，不能把“local 实例”本身当作可信来源。

最终有效权限 = 全员基础 ∪ 所属部门及祖先部门配置 ∪ 个人 grant − 个人 revoke；超级管理员直接拥有
完整权限目录。以上写接口同时要求 `authorization:manage` 和 `principal.superAdmin`。

### RefreshToken（不透明刷新令牌）
`id, user_id, token_hash(sha256, unique), device_info, issued_at, expires_at, revoked_at, replaced_by, session_id`。轮换 + 重用检测；`expires_at` 随所属会话的绝对期限(从登录起算)，轮换不延长(ADR-110)。

### AuthSession(服务端登录会话，V680)
`sid(PK), user_id | visitor_id(二选一), created_at, last_seen_at, absolute_expires_at, revoked_at, revoked_reason, step_up_token_hash, step_up_expires_at`。
吊销/空闲超时/绝对期限的唯一权威：access token 带 `sid`，`JwtAuthFilter` 在查账号状态的同一条 SQL 里连带判定。
`last_seen_at` 只由人为请求更新且最多 60 秒一次(客户端在用户 30 秒内没有输入时发出的请求带 `X-Uten-Automatic: 1`，
不续期)；`revoked_reason` 取 `logout/idle_timeout/password_changed/account_status_changed/password_reset/
remote_access_changed/refresh_reuse/step_up_locked/login_account_changed`；`step_up_*` 是本会话当前有效的
一次性再认证凭证(只存 sha256，5 分钟)。
机制表，不挂行级审计；清空业务数据时 CLEAR。

### AuthStepUpState(再认证失败计数，V680)
`user_id(PK), failed_attempts, locked_until, updated_at`。敏感操作再认证、改密旧密码、进入切换人共用；
达到锁定阈值暂停验证并吊销当前会话。机制表，不挂行级审计；清空业务数据时 CLEAR。

### PasswordHistory（改密防重用）
`id, user_id, password_hash, changed_at`。改密时校验最近 5 条。

### AuditLog（审计日志，bigserial）
`id, actor_id, actor_account, action, target_type, target_id, before(jsonb), after(jsonb), ip, user_agent,
result, request_id, event_source, http_method, http_path, status_code, duration_ms, risk_level(生成列),
event_category(生成列), client_event_id, device_installation_id, device_name, device_manufacturer,
device_model, device_platform, device_os_version, app_version, app_build, device_form_factor,
device_browser, device_locale, device_time_zone, device_time_zone_offset_minutes, device_is_physical,
client_event_at, device_capture_status, device_profile_hash, created_at`。
> 进入应用的 GET/POST/PUT/PATCH/DELETE/HEAD `/api/**` 由请求过滤器与 MVC 拦截器覆盖；匿名认证、
> CORS 非法来源 403、401、404/405 和 MVC 前异常也由外层兜底。JWT 完整校验成功后将 actor 快照绑定
> 到本次 request，使安全上下文清理后的 404/405 仍能归属账号；无效或过期令牌不会绑定身份。
> 登录、刷新、访问拒绝等由 `AuditService` 显式写；数据变更由 DB 触发器写。
> `request_id` 串联请求和触发器明细。V185 后由通用/高敏函数新写的 before/after 会移除迁移列明的凭证、
> PII、薪资、迁移列明的原因备注类敏感文本和大型嵌套快照字段；业务名称、编号等调查必需字段仍保留。
> V185 不重写旧行，历史记录仍须受限访问并专项扫描。
> V172 的设备字段是服务端收到并清洗后的**客户端声明快照**：`device_installation_id` 是应用安装实例
> 首次运行生成的随机 UUID，不是 IMEI、MAC、硬件序列号；`device_profile_hash` 只用于核对同一份
> 清洗后快照，不构成物理设备认证。`device_capture_status` 取
> `present/partial/invalid/missing/legacy`，Web 或旧版本拿不到的字段必须留空并标明状态，不得猜测。
>
> `audit_log` 与冷归档 `audit_log_archive` 都只允许系统写入。产品不提供人工修改或删除 API；
> 在线记录只由留存任务先归档后删除，归档记录只在总期限到达后由同一任务永久删除。

### LocalAuditReceipt / DeviceAuditProfile（客户端本机证据，非数据库实体）

`DeviceAuditProfile` 保存当前安装实例的随机安装标识、设备名称/厂商/型号（平台可提供时）、平台、
系统版本、应用版本/构建号、设备形态、浏览器、语言、时区和是否物理设备。`LocalAuditReceipt`
按 `client_event_id` 保存请求方法、去除查询值后的路径、开始/完成时间、结果、状态码、
`server_request_id`、重试轨迹和当时的设备快照；不保存请求正文、查询参数值、令牌或业务数据。

- 本机最多保留最近 300 条，并按服务器公开的“在线期 + 追加归档期”总月数自动清理；
- 产品界面和业务 API 不提供手动清除、修改或批量枚举能力，只能凭完整 `client_event_id` 精确核查；
- 精确核查目标回执前必须在线调用服务端授权接口；授权成功并写入 `verify_local_audit_receipt` 后才读取
  本机回执，无权限、离线或授权失败时不读取；
- 本地完整性标记可发现常见的内容损坏或改写，但密钥仍位于本机，不是远程证明或不可抵赖签名；
- 卸载应用、清除站点/应用数据、系统存储清理、设备重置或安全存储异常都可能使本机证据消失；
- 因此本机回执只能与服务器时间、Request ID、安装标识和设备快照交叉佐证，不能单独证明实际操作者
  或宣称“绝对真实”。

审计日志详情和本机回执入口仅向持 `audit_log:view` 的指定核查人员开放；普通员工与访客没有入口，
深链和后端接口均须拒绝。任何审计数据导出还必须同时持有 `audit_log:export`。

### BusinessIdentifier 注册表（V279 当前候选；V76 为历史取号基线）
> 销售、采购、仓库、委外、财务/资产、生产和研发共 37 个文档命名空间由后端 `DocNumberService.nextNumber(...)` 权威生成，**不接受客户端传入**。另有 `VISITOR_ACCOUNT=V` 与 `PRODUCTION_EXECUTION_SEGMENT=ZX` 两个 8 位流水系统号；完整映射见 [ADR-036](../99-决策记录-ADR/ADR-036-全局业务标识与单据号命名空间.md)。

**关键字段**：
| 表 / 字段 | 类型 | 说明 |
|---|---|---|
| `business_identifier_namespaces.namespace_key` | TEXT PK | 不可变的业务命名空间；服务按枚举名查找，不把前缀硬编码到 Flutter |
| `fixed_prefix` | TEXT | 全局终身保留的固定前缀；归一后不重复 |
| `business_document_sequences.sequence_date` | DATE | PostgreSQL `Asia/Shanghai` 业务日 |
| `last_seq` | BIGINT | 本 `(namespace_key, sequence_date)` 已发最大顺序，1–999999 |
| `production_product_no_sequences.plan_id` | UUID PK/FK | 计划行自动编号的稳定所有者与并发锁键；后缀 1–999999，不承载计划行关系 |
| `business_identifier_reservations.normalized_identifier` | TEXT PK | 文档号、系统号和主档编号的全局终身占用 |

**现行业务规则**：
- 格式 `PREFIXYYYYMMDDNNNNNN`，例如 `CD20260814000001`；制单人工号/姓名不入号码，人员以 UUID 关系和审计单独保存。
- 取号用原子 UPSERT，事务回滚或旧号冲突可跳号；不保证无缝连号。
- `create()` 由服务端生成；`update()` 不重取号。Flutter 只读显示“保存后自动生成”，不 peek 下一号。
- 访客号和生产执行分段号由 `MasterCodeService` 按固定前缀原子分配；8 位是硬上限，耗尽时失败关闭。
- 计划行 `product_no` 可承载用户业务语义，但以 `plan_id` 为终身所有者：显式值继续使用；留空时服务端调用数据库函数生成 `<计划单号>-NNN`，销售订单导入、物料分析、报工补产和 MRP 自制子计划均不自行拼号；同计划草稿重建可恢复，不同计划禁止复用。
- 旧 `PREFIXYYMMNNNN` 与其它历史格式原样保留，归一后登记为占用/冲突证据，新格式只用于切换后新建。
- `CJ` 继续属于采购收货，仓库产成品进仓为 `CR`；销售订单为 `XD`，`XS` 终身属于财务收款。

见文首「2026-10-04」节)，它就是订单版本的 BOM 快照；绑定计划行的发料明细只能由委外人员提交领料生成(带
`requested_qty`)，仓库只能改少(整行不发 = 软删并记 `warehouse_dropped_at`)后审核。本节原「没有冻结 BOM 快照、新增发料审核 409」的口径已退役；不得重算旧
BOM 或批量回填伪造快照的约束不变。

### 关联单据累计数量约束（V132）

采购、销售以及委外仍保留的历史来源字段包含 `received_qty`、`shipped_qty`、`issued_qty`、
`returned_qty`、`material_returned_qty` 和 `wasted_qty`。应用层检查之外，V132 在数据库
增加 12 个 `BEFORE INSERT/UPDATE` 触发器，关闭两个并发事务同时通过“剩余量检查”后导致
超收、超发、超退的竞态。触发器存在不代表所有历史累计列仍是当前业务权威字段：

- 任何新的累计负数都拒绝；
- 累计值增加时不得超过来源数量（需要时加上已退数量额度）；
- 退回/损耗不得超过已处理数量，退回撤销后也不能让已处理量重新变成超量；
- 委外发料的退料量与损耗量合计不得超过发料量；
- 委外订货的 `issued_qty/material_returned_qty` 仅作历史兼容，新服务不再写入；
- 历史库已接受的超量异常不在 V132 中自动改写，只允许朝合法方向减少，必须另做异常盘点和业务纠偏。

> V132 的“退料 + 损耗不超发料”只是局部上限，不是完整委外守恒。完整目标还必须满足
> `累计发出 = 合格产出对应耗用 + 良/不良退回 + 审批损耗 + 供应商期末结存`，并经过回厂质量结论；
> 当前供应商持有库存/在制实体尚未落地。

这些触发器保护的是数据库不变量，不替代服务端状态机、权限和幂等校验；应用还必须把约束异常
转换为可理解的冲突响应，并在并发集成测试中验证。

### 销售退货质量冻结（V189）

- `sales_return_quality_items`：一条销售退货明细对应一条质量冻结当前投影，保存仓库、货品、颜色、单位换算率、收货基本单位量以及良品释放/报废/返工累计量。该表不属于 `stock_balances`，冻结数量不能参与 ATP、预留或拣货。

### 底层材料发现与累计学习

`production_material_discovery_requests` 关联精确执行段，状态为 `PENDING / CONFIGURED / CANCELLED`，保留车间提交版本 `expected_version`、申请版本 `row_version`、操作人及提交/配置/撤回的幂等证据。提交时仍按工单范围及岗位校验；同人同键同意图返回原申请身份，同键不同意图拒绝。已有有效申请时，即使客户端使用新键，也返回 `409 CONFLICT`，不取新号、不递增工单版本、不生成需求或改变材料数量；只有合法撤回后才能重新申请，新申请有独立 UUID 和 LQ。

V726 增加 `requested_materials JSONB NOT NULL DEFAULT '[]'`，数据库约束其为最多 100 行数组，历史守卫禁止后续改写。未选材料为 `[]`；已选材料至少有 `goodsId/unitId`，`colorId/qty` 可空，已填数量须为正且最多四位小数，同货品同颜色的车间建议不得重复。输入只接受身份和数量，服务端补齐编码、名称、颜色名、单位名、规格、参考库位的快照；参考库位和货品归属仓不等于实际发料仓。详情 `suggestedItems` 读取快照，正式 `items` 读取配置结果。预填不产生物料需求、库存预留、DRAW、耗用或学习事实。

`production_material_discovery_lines` 是仓库配置的不可变证据，保留 `request_id/demand_id/goods_id/color_id/unit_id/warehouse_id/qty`。每份申请按货品和颜色生成精确正式需求并校验基础单位，同材料可以按实际叶仓拆行；同材料同实际仓须合并。正式配置要求正数量和真实叶仓，最多 100 行。未知材料沿实际领料入口选择；已知材料进入混合批量页时必须保留申请中全部货品、颜色与基础单位，只补改数量及实际仓，不能在批量中替换为未确认材料。
