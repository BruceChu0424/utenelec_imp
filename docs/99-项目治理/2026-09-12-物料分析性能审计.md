# 2026-09-12 物料分析性能审计

本记录覆盖物料分析读取、采购/委外通知、车间批量下达及真实入库后的分析联动。页面交互以[生产物料分析页](../03-页面/生产物料分析页.md)为持续设计入口；本记录保存根因与验证证据。服务器上传、CI、打包与目标库验收由本次总验收分别记录，不能从源码或隔离库测试推断已部署。

## 根因与实现

| 原链路 | 改动 | 权威入口 |
|---|---|---|
| 打开历史分析在 GET 后自动调用 preview，重复整树持久化与分配 | 已有分析只读加载，字典并行，主动刷新才重算 | `lib/features/production/pages/production_material_analysis_page.dart` 及页面分部 |
| 每个生产来源独立执行 BOM 图校验和递归展开 | 一批来源两次查询，来源 UUID、换算率和需求计量保持独立 | `server/src/main/java/com/uten/imp/features/production/analysis/MaterialAnalysisBomSnapshotReader.java` |
| 正式下达逐产品读取当前 BOM 与持久快照 | 按本次选中来源批量比对直接层，旧计量模式及结构漂移继续拒绝 | `MaterialAnalysisService.requireCurrentBomSnapshot` |
| 采购/委外通知逐组选取历史行动组、有效在途和不合格补货 | 当前组及历史分摊别名一次读取，各路线统一聚合，500 个采购组该段为 3 次查询 | `MaterialAnalysisSupplyCoverageReader.read` |
| 车间下达无变化仍重复构造完整详情，委外通知返回的详情被丢弃后再次读取 | 未变化时使用原快照，委外通知后使用其返回快照，只在新建 MAKE 锚点后重读 | `MaterialAnalysisCommandService.issueWorkshopPlans` |
| 同货品重复出现在数百来源路径时，每行重新合并仓库范围及累计分仓量 | 仓库范围一次合并，分仓汇总按物料维度在本次响应内复用 | `MaterialAnalysisService.detailInternal` |
| 跨多张采购/委外收货单批量确认入库，每张都刷新相同分析 | 全批实际入账与正式履约后，一次定位影响维度、每份分析一次刷新 | `MaterialAnalysisSupplyWakeupService.afterInspectionStockInConfirmed(List)` |
| 刷新把所有节点 active 置 false 再置 true、把已有分配清零后重写 | 仅失活真正消失的 BOM 节点；结构有变化才更新；库存参考及最终计算量同语句按差异落库 | `refreshLocked` / `NODE_UPSERT_ON_CONFLICT` / `updateNodeAllocations` |
| 历史列表在分页前汇总所有分析来源 | 先按相同权限/搜索条件冻结本页分析头，再按头 UUID 聚合对应来源 | `MaterialAnalysisService.list` |

这里的读取快照只在当前命令或响应内存在，不是跨请求缓存。BOM 组件失效、基本单位/颜色异常、环、超过十层仍失败关闭。现货数量、精确权益、公共安全库存、在途及下达余量继续分账。MAKE_COMPONENT/SUBCONTRACT_MAKE 仍仅为计划锚点，不复制原树物料需求。

增量落库始终运行现行数量算法，不凭旧 fingerprint 跳过计算。结构阶段保留旧 required/allocated 等计算值，随后 5 个库存参考字段与 7 个最终计算字段一起更新，避免需求减少时出现 allocated 暂时大于 required 的立即约束错误。真正结构变化仍触发原身份/让料/权益校验，有数量变化的行仍正常审计；ROOT_SUPPLY 继续由根供料服务独立维护。

供给批查只把实际合格入库计为到货覆盖；已退回不合格由原订单形成的待补量继续抵扣可重新下达量。审计进一步发现合并来源的剩余量重复从 FIFO 起点分配，已前向修正为来源累计区间差，详见[V554](../数据迁移/152-V554合并订货来源剩余供给区间.md)。旧 action_group_key 通过真实 allocation 的物料 UUID 找回，不凭货品名或编码猜配。批量读在新 action 写入前完成，幂等、版本、指纹、对象权限和全事务预锁没有删除。

入库后置联动仍在来源事务内执行。精确归属容量来自 action allocation、exact peg、legacy reservation 和实际订单来源预算，下一张收货单读取同事务已经写下的权益事实，不依赖上一张的 shortage 展示投影。任何归属、正式履约或分析刷新失败仍回滚整批。

取消分析没有移除服务端已下达计划、根交接、跨分析权益和版本守卫。前端补齐原因 2–1000 字校验及框内错误反馈，业务冲突必须显示给用户，不能静默声称取消成功。

## 数据兼容与迁移

本组改动不增加持久业务列，也不修改已应用的 Flyway 文件，不需要重写库存或历史来源。V554 只前向纠正派生函数和视图。旧活动分析由授权的显式刷新升级投影；缺少根 UUID 时保持既有只读兼容，正式下达遇到旧 EDGE_RULE 之前的快照仍要求刷新。结构和读侧实现优化不能成为清空业务库或 `flyway repair` 的理由。

- `MaterialAnalysisSupplyCoverageReaderTest` 校验 500 采购组读取预算、历史组去重、路线隔离、委外申请与前置自制覆盖相加。

- `.codex-perf-material-r3.log` 47 项通过、0 失败、0 跳过，覆盖取消服务整体持久化/幂等/异载荷/计划阻断，活跃让料和未恢复正式权益拒绝，以及混合采购/委外和成品批量入库候选。该轮仍为 V553，后续 V554 数量修复和提交时库存重算须另行验收。

### 压力过程中实际暴露的瓶颈

100 来源展开 9,800 行、20,000 条历史 BOM 和 20,000 条历史分析来源的前三轮均未通过全部性能门禁，不能称为最终压力通过：

| 观察 | 证据与处理 |
|---|---|
| 首次 preview 42.247s / 1,233 JDBC / 28.639MB 原始 JSON | 单样本定位；后续确认只有一份 flatMaterials，没有 products 内重复整树 |
| 结构批量化后仍扫描全历史 BOM | 改为按当前根/递归前沿/组件做参数化边读取；保留真实 EXPLAIN 门禁 |
| 97 块最终分配 UPDATE 耗 6.226s | 跳过真正无差异的数值更新后降至 0.852s；后续进一步移除 active 与分配清零往返 |
| 无变化 refresh 36.966s | 10 次预锁 BOM 共 12.556s、节点 upsert 6.927s、全量失活 4.745s，作为通用增量 reconcile 的直接依据 |
| 预锁/tree/walk 的 JIT 占执行时间 83%–87% | 真实 EXPLAIN 分别为 1,148/1,378ms、1,321/1,537ms、752/868ms；运行连接池默认关闭 JIT，保留显式覆盖，不改公司全库或独立 migrator |
| 原始 JSON 28.639MB，NON_NULL 对照 25.600MB | 仅减少约 10.6%；关键 0/false 与空列表回退语义保持，没有用删字段冒充性能修复 |
| 活跃列表源聚合扫描 20,100 行 | 先分页分析头、再按页内 UUID 聚合来源，原权限与筛选保留 |

这些单轮定位值受缓存及并行任务影响，不作固定提速倍数。最终 5 样本及 on/off 同查询结果等价对照另行补录，所有运行时/数据规模和中央回归并行负载均保存在测量事件中。

## 继续验收的边界

公司业务库当前数据规模及网络环境与隔离夹具不同；不得只凭空库响应、缓存命中或 SQL 次数减少宣称所有页面已达响应目标。批量计划创建仍逐份履行单据、分摊、审核和执行段事务规则。整树刷新仍须写审计和数量快照，优化目标是消除重复工作，不跳过事实落账。最终以完整回归、规模结果和公司目标版本验收共同确认。
