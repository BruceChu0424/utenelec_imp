## 一、先回答最关心的逻辑问题：单产品分析的对不对？

### 1.1 当前系统实际逻辑（代码 + ADR-033 确认）

1. 点一个产品进去 → 服务端展开**完整 BOM 树**，每条「路径」是独立任务（同一件物料出现在两条路径 = 两个任务，不合并）。
2. 父件**只按自己没被现货盖住的实际短缺**向下展开需求：父件有 80 现货、要 100，下层只按缺口 20 展开，不会重复要 100 的下层料。✔ 这是 MRP 净需求的正确做法。
3. 路线决定后代：
   - **采购（BUY）**：到这里为止，下层不再展开（买回来就是整件）；
   - **自制（MAKE）**：按实际短缺继续向下展开备料；
   - **委外（SUBCONTRACT）**：形成委外任务；如果我方要供料（有供料 BOM），只展开我方供料那一部分。
4. 缺料行显示现货/缺口/建议路线，计划员**显式**点「采用采购 / 采用委外 / 采用自制」才算确认，确认后勾选缺口 →「提交采购需求 / 提交委外需求 / 安排自制生产」分别走三条真实单据链。
5. **自制件的硬门禁**：某个自制组件，必须它的**直接下层物料实际齐套**之后，才允许点「安排生产」，点的那一刻才创建系统子任务（MAKE_COMPONENT）并交给子分析去排子件计划。
6. 计划上限 = 「可完工入库」数量（不是"可开工"、不是"预计可发货"）；**支持分批**——要 10000 件、料只够 1000 件，就先排 1000，剩下 9000 留在原分析里，料到继续排，不会伪造一张"待料计划"。

### 1.2 核对结论：方向是对的，和行业标杆一致

| 用户的疑问 | 核对结论 |
|---|---|
| 是不是"从底层开始生产、生产完底层再生产顶层"？ | **不是严格排队，也不该严格排队**。正确模型 = **依赖门禁 + 自由调度**：父件必须在直接下层齐套后才能安排（物理事实：没料没法装）；但**同层级的不同分支、不同组件之间互不依赖，可以任意先后、任意并行**。这与 APS 的"分级工单"做法一致：子件工单与母件工单建立前后匹配关系，子件完成才排母件；但不相关的工单并行生产。管理员说的"不一定、可能并行"**与此完全兼容**。 |
| 会不会出现"系统强迫按某个顺序生产"？ | 不会。系统只卡"下层没齐不能安排上层"这一道门，门内先后顺序由车间自己定。 |
| 分批生产 / 一次全生产？ | 都支持。本批数量由计划员填，上限是可完工入库量；余量留在分析里继续分批。行业上对应"按需求量齐套率"（料够 800 件就是 80%）和部分齐套分批下达。 |
| 缺货显示「该采购采购、该委外委外、该自制自制」？ | 已实现，且是**建议路线 + 人工显式确认**两步，避免系统猜错路线直接下单。 |

### 1.3 目前真实存在的三个缺口（需要补）

1. **节点级进度可视化不足**：BOM 树上每个组件/子组件现在只有文字状态（待齐套/已齐套/已入库…）和产品卡上的「齐套 X%」，**没有每个组件一条进度条**（用户明确要这个）。当前唯一进度条是"批量提交进度"，不是业务进度。
2. **跨产品调货/借用已有源码候选在线动作**：V288/V289 提供结构、终态守卫与审计覆盖，后端 create/revoke、持久化与双趟生效计算、Flutter「调给其它产品」及撤销入口已接通并留痕。它仍只是未签名、未部署候选；目标库迁移、真实角色权限负测、岗位/实物 UAT、恢复与发布签字未完成，不能写成生产已上线。
3. **分批委派的数量闭环未落地**：自制子件一旦创建子任务，目前是**整节点所有权转移**（父树下层变只读），没有 `delegated_qty` 字段记录"这一批委派了多少、还剩多少"。要实现"子件够多少就先装多少"的部分流转（APS 叫"快速流转"），需要按 ADR-033 §7 追加 V254+ 显式字段。

## 二、调货（借用）逻辑：怎么实现才是对的

### 2.1 场景还原

产品 A 和产品 B 都要用物料 M。M 现在生产的/到货的一批，原本是算给 A 的，但 B 更急（或 B 就差这一个件就能开工），现场想**先把 M 调给 B 用**，A 等下一批。

### 2.2 行业做法（调研结论）

- **SAP MD04 的 pegging（需求溯源）本质上就是"动态建议、不固定绑定"**：SAP 官方明确说明 pegged requirement 不是需求和供给之间的硬绑定，只是系统按数量提出的建议，任何供给都可以满足任何需求，随供需变化动态调整。——这给了"借用"正当性：**在分析/计划阶段，分配本来就应该能调；只有到正式锁料（预留/发料）那一刻才固定**。
- **金蝶云星空「生产齐套分析单」**：多张生产订单一起选进来做齐套分析，**按设置的优先顺序排序、扣除已预留**后逐单分配库存——"谁先分"就是可调的。
- **用友 U9**：缺料风险模拟直接给出"紧急调货、替代料"作为标准处置手段。

### 2.3 建议的三层模型（关键：分得清"软"和"硬"）

| 层 | 事实强度 | 借用怎么做 | 风险控制 |
|---|---|---|---|
| ① 分析分配层（软） | 只是模拟分配，不动库存、不写预留 | **一期就做这个**：在某条缺料/在制路径上增加「调给其它产品」动作 = 把这条路径的分配量改拨给同一分析内另一产品的同物料路径 | 留痕五要素：谁操作的、多少数量、从哪条路径到哪条路径、原因、时间；**双向可见**（借出方显示"已被 X 产品借用 N 件"，借入方显示"借用自 Y N 件"）；正式下达前可撤销 |
| ② 在制委派层（中） | 子件已创建 MAKE 子任务/子计划，但还没锁料 | 二期做：子件产出入库后，把"供给归属（peg）"从 A 改挂到 B（re-peg），或把子计划数量拆分 | 必须数量守恒：A 的缺口重新出现并提示补齐；需要权限 + 原因 + 二次确认 |
| ③ 正式预留层（硬） | 计划已批准、库存已物理预留 | **不允许直接抢**。只能走原计划释放/反向向导，校验未发料未开工后释放，再重新分配 | 现有设计已守住这条线，保持不变 |

**一期落地建议（最省事且够用）**：先做第①层。现场话术就是"这批料先给 X 用"。因为分析分配本来不写 `stock_reservations`，改拨只是改模拟结果，天然安全；再配合已有的"按最新库存刷新分析"，借出方 A 的缺口会自动重新算出来提示补料。

## 三、多产品联合分析（4~20+ 个产品）怎么展示

### 3.1 先澄清一个事实

**代码里"多选产品联合分析"已经存在**：调度台待排列表和物料分析准备页都支持勾选多个产品（上限 500），按钮文案是「联合分析所选 N 项」。如果现场看到的是"只能选一个产品"，多半是部署版本旧或入口没被注意到，**上线前需要先核实现场版本**。

真正的痛点（用户说得对）是：**选 20 个产品进去之后怎么办**——不能把每个配件全部平铺，那会是几千行，没法看。

### 3.2 行业通行的解法：分层视图，而不是一张大表

调研到的成熟做法（金蝶齐套分析单、SAP MD04、古哥计划 MRP 多维表格、树形表组件）可以归纳为一个规律：**默认给结论，逐层给细节，汇总给决策**：

- 金蝶：多张订单 → 一张齐套分析单，先看每张订单齐不齐，再下钻子项明细；
- SAP：每个物料一张供需清单，缺料可以从物料反查"哪些订单要它"（pegging）；
- 古哥计划：按任务 / 按子件 / 按父件 / 按日期多个维度的统计视图自由切换；
- 树形表：表格内原生展开折叠，层级缩进，默认收起。

### 3.3 建议的三层结构（在本系统现有页面上演化，不用推倒重来）

```
第 1 层 · 产品总览（进入默认视图，只显示产品卡）
  ┌───────────────────────────────────────────────┐
  │ ▶ 产品：暖风机 H-220        要 500 个            │
  │   ✅ 最多可生产 320 个      齐套 64% ▓▓▓▓▓▓░░░░ │
  │   还缺 3 种料 · 下一步：2 条采购路线待确认        │
  ├───────────────────────────────────────────────┤
  │ ▶ 产品：电暖器 D-80         要 200 个            │
  │   ❌ 暂不可生产  齐套 12% ▓░░░░░░░░░            │
  │   被什么挡住：发热管（自制）下层缺 2 种料          │
  └───────────────────────────────────────────────┘
  · 默认全部折叠成卡片；可生产置顶（已有）
  · 勾选卡片 → 填本批数量（默认=最多可生产数）→ 安排生产/或先备料
  · 分批天然支持：数量随便改，余量留分析里（已有）

第 2 层 · 单产品 BOM 树（点卡片左侧 ▶ 才展开这棵树）
  · 树形表格：层级缩进加大（建议 ≥24px/层）+ 层级色带 + 物料名大字号
  · 每个组件/子组件行：名称（大）、路线角标（采购/委外/自制）、
    需求/现货/缺口三个数、状态徽标、**一条进度条**
  · 每个分支可单独展开/折叠 + 产品级「全部展开 / 全部收起」
  · 默认"只看缺料"（已有），可切"全部 BOM"（已有）

第 3 层 · 缺料汇总（顶部一个页签「按物料看缺料」，给采购/委外决策用）
  ┌───────────────────────────────────────────────┐
  │ 物料：发热管 Φ8×200       建议路线：采购          │
  │ 总需求 2,400 · 现货 300 · 总缺口 2,100          │
  │ 涉及 5 个产品 ▶（展开：H-220 缺 800、D-80 缺 500…）│
  ├───────────────────────────────────────────────┤
  │ 物料：温控器 KSD301       建议路线：委外          │
  │ 总需求 1,900 · 现货 0 · 总缺口 1,900            │
  │ 涉及 3 个产品 ▶                                │
  └───────────────────────────────────────────────┘
  · 一行一个物料，跨 20 个产品聚合；展开行看"每个产品各要多少"（pegging 明细）
  · 在这里勾选 → 底部「提交采购需求（N）/ 提交委外需求（N）」一次下达
  · **合单不合账**：汇总只是展示投影，后台仍按"每条 BOM 路径"分别记数量与去向
    （ADR-033 的既有原则），保证事后能精确追溯、精确撤回
```

### 3.4 为什么这样是对的

1. **人一屏只想一件事**（适老化"一页一事"原则）：20 个产品时，计划员首先要知道"哪几个现在能做、能做多少"，这是第 1 层的事；要备料时一次只看一棵树的缺料，这是第 2 层；要给采购交底时按物料汇总，这是第 3 层。
2. **数量不会错**：汇总视图只是投影，底层仍是逐路径任务 + 共享池不超分，不会出现"同一件料被两个产品各领一次"。
3. **性能可控**：产品卡分批构建（60 个/批）、BOM 树按产品懒加载（30 个产品/批）在现有代码里已有约定，三层结构不破坏它。

## 四、进度条与适老化细则（直接可执行的规格）

### 4.1 每个组件/子组件的进度条

- **位置**：BOM 树每一行的右侧（窄屏放第二行），一条细进度条 + 百分比文字。
- **口径必须分三种，不能混**（现有文档已立此规矩，进度条要遵守）：
  - 采购/委外件：`合格入库数 ÷ 需求数`（只有 IQC PASS 才算，在途不算）；
  - 自制件（备料阶段）：`下层已齐套数量 ÷ 本批需求`；
  - 自制件（已排产）：`已入库 iqty ÷ 排产量`，另配一行小字"已报工 fqty"——**报工和入库永远分开显示**。
- 不只靠颜色：进度条旁必须有数字文字（色盲/老花友好）。
- 父组件的进度条 = 它直接下层的齐套进度（不是整棵树的加权平均，避免误读）。

### 4.2 适老化（套用项目已有《适老化 UX 规范》基线）

- 数字（需求/现货/缺口/可生产数）≥ 24px、加粗；物料名 ≥ 18px；行高 ≥ 56dp；点按区 ≥ 48dp。
- 层级表达：**缩进加大 + 每层级一条左侧色带 + 层级文字标签**（如"L2 子组件"），三层冗余表达，不靠单一颜色或单一缩进。
- 大白话：按钮和提示用"这批料先给哪个产品用""先做多少"，不用"分配/委派/re-peg"。
- 默认值先行：勾选产品自动预填"最多可生产数"（已有）；借用默认数量=对方缺口。
- 危险动作二次确认并写清影响：借用确认弹"确定把 300 件发热管从 H-220 调给 D-80 吗？H-220 会重新缺 300 件，需要等下一批料。"
- 错误给"下一步"不给错误码（已有 `下一步` 引导机制，保留并延伸到新动作）。
