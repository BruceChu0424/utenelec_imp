## 2. 用户口径 (2026-10-06)

1. 服务器上**所有备份只保留 3 天** (pgBackRest repo1/repo2、配对备份、升级前 dump)。
2. **确认无用就直接删除**, 不走 14 天隔离区。
3. **服务器上不留任何临时脚本或导出文件**, 运维命令经 SSH 标准输入执行。
4. **sudo 免密本次不改** (自动化依赖), 列入长期项。

## 4. 服务器执行计划 (按用户口径修订后的要点)

A 批在线执行、ERP 零停机; B 批与下一次含迁移版本的激活合并在一个维护窗口 (ERP 不可用合计约 15-25 分钟,
分 3 段, 顺序见 RUNBOOK 9.7)。与原计划相比的修订:

- 所有保留期改 3 天: `repo1-retention-full=3`、repo2 `=3`、配对备份 `retention_days: 3`、`UTEN_BACKUP_KEEP_DAYS=3`。
- 不建隔离区: 第 1 节列出的遗留目录、旧密钥目录、env 副本、日期号版本、退役单元, 核对后按 RUNBOOK 9.4
  直接删除; 含秘密的用 `shred -u` 并轮换对应密钥。
- 不在服务器上留临时文件: 扫描脚本、要装的单元与配置都从管理机经 SSH 标准输入传入; 离线托管件经 SSH
  管道直接落到管理机; 证据记在本文, 不在服务器上建 `/root/hardening-*` 目录。
- 新的 `uten-pgbackup.service` 只硬依赖 repo1 所在的 `/data`; 备份卷只 `Wants`/`After`, repo2 路径可写项带 `-`,
  备份卷坏了或没挂上时 repo1 照常备份, repo2 那条命令报错并告警。仍要在备份卷建好、repo2 `stanza-create`
  成功之后再换装, 否则每天的 repo2 那一半都会失败。备份卷掉了时 WAL 归档会卡住, 按 RUNBOOK「备份布局与保留」
  临时停用 repo2 配置。
- 改 `repo1-retention-full=3` 之前, 先只读确认服务器上 `local_backup_health.py` 要求的恢复点下限 (C13);
  下限大于 3 就先改它, 否则 expire 到 3 份之后状态页「最近备份」变红。
- nginx 退出 `uten-imp` 组: 退组前用 `setpriv` 模拟退组后的身份预检, 退组并重启 nginx 后经 nginx 复查站点与
  根证书下载都是 200, 不是就立即把 www-data 加回 `uten-imp` 组 (RUNBOOK「发行目录权限」)。
- 更新器换装时锁路径变为 `/run/lock/uten-imp-updater.lock`, 换装前停定时器并确认没有进行中的激活。
- 80 端口改为跳固定内网域名: 重新渲染前确认员工电脑都能解析该域名 (否则用 IP 打开 http 的人会被跳到解析不了的地址)。
- 各单元的 `OnFailure=uten-alert@%n.service` 在告警通道接入前指向不存在的单元, systemd 只记一行日志, 不影响运行。
