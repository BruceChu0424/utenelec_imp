# FIN06其他应收款对账单来源合同与接续

本项仍在实施，不能以本合同或旧委外流水视图称为完成。目标是财务日后能自行维护真实辅助、来源、重量和加工款，开发不等待金本样例UUID或金额。

## 已落公共合同

- `application/port/FinanceMaterialStatementSourcePort.java`：最小只读真实物理来源，支持`PURCHASE_RECEIPT_LINE`、`STOCK_OTHER_OUT_LINE`、`SALES_OTHER_SHIPMENT_LINE`。采购入库、仓库其它出库、销售其它出库分别保留，不按“金本”“57#”等文字猜模块或对象。
- `features/finance/statement/FinanceMaterialStatementContracts.java`：辅助UUID+币别+商品UUID/颜色的上下文、显式原客户/供应商UUID关系、经审核KG/PCS单位证据、期初重量证据、缺实际称重时的来源行称重核验、同一真实GL allocation的加工款/非加工款完整分配。

## 可独立接手的物理reader子块

实现文件建议独占`features/finance/statement/FinanceMaterialPhysicalSourceReader.java`，实现上述port；不要修改`FinanceStatementService`、本域输入服务或GL金额。

1. `candidates(Query)`按真实角色UUID、商品/颜色、期间和原单号分页，`read(List<Key>)`至多200个指定来源，回传原顺序。公司完整财务+财务报表是本最小来源读取目的；不额外开放仓库编辑、主档详情、价格或HR名册。
2. 采购读取`purchase_receipts/purchase_receipt_items`，保留已审核事实及其后实际反向日期；供应商、商品、颜色、单位只认原UUID。名称优先原单据快照，当前名称不能冒充历史快照。
3. 仓库其它出库读取`stock_documents/stock_document_items`且`doc_type='OTHER_OUT'`；销售其它出库读取`sales_other_shipments/sales_other_shipment_items`。两者原用途与客户/供应商关系一并保留；没有原对象UUID的行需财务明确关联，不能用备注同名自动归户。
4. `stock_movements`是实际数量/重量事件，流水`weight`单位为KG，`weight_source`区分`MEASURED/EXACT/SLICE`和`AVERAGE/ESTIMATE`。估计值可作为核对提示，不当作已确认实际进/出重量。不要把待检、合格仓位搬运重复计作两次来料；原采购收货物理进仓与后续仓位流转须区分。
5. 原数量单位与`unit_rate`保留；`unit_rate`只代表原库存基本量，不能自行推导KG或PCS。缺重量/PCS时由本域经确认的单位/称重证据补足，不把KG、件、箱混加。
6. `identityFingerprint`仅包含不可变原身份、数量/单位/实际重量及原商品快照，合法后续反审另返`reversedDate`，不因新增反向事件抹掉原历史。缺源、未审、已物理删除且无历史证据须显式报错或待核，不静默跳过。

## 本域继续实施块

1. 上下文与来源关系可创建、修改草稿、提交核验、不同财务确认；保存原输入、来源及未知提交请求ID，不回写原库存。
2. 期初重量需真实正/负/0证据。滚动结余为已核期初+已核进仓-已核发出-原0.5%损耗，同一精度/逐行舍入策略固定；任一必要重量未知则该行及后续结余未知，不能用缺失当0。
3. 加工货款绑定已确认其他应收债权GL allocation（明确辅助、币别、科目）原金额，普通回款贷方不当作负加工费。一个源金额按各出库/商品加工份额及明确非加工余项分别守恒，不另造收入或分录；原币无证据保持未知，本币不能装成美元原币。
4. 单价来自实际确认报价/成交证据；加工货款保留原成交/分配额，不拿数量乘最近价重算。跨月补记加工款用真实财务日期的调整效应，不能重复带一遍出库数量或改变KG结余。
5. 原10列与右侧金额/税价区域按原附件；已有字段名取共同模板合同。通过新增auxiliaryId+currencyId+明确上下文的正式重载替代旧委外供应商拼接；旧重载仅兼容原视图，不宣称其已覆盖FIN06。
6. 同源预览/导出及顶层`documentMetadata`承载真实抬头、期间、尾部确认资料。原样模板可导入；外部资料先比对，不直接立账。实际财务对账与仓库物权、会计GL保持各自权威与引用。

迁移号由根协调，不能占用V1000（首次AP）、V1001/V1002（申请/出货）、V1003（分类/结算守恒）或其他并行编号。上述reader/输入/费用分配/原表及导入导出尚未完成最终真实调用验证。

## 2026-11-03 根任务接手边界

根任务已接 FIN06 reader/维护/UI；往来子任务此后不再修改 `FinanceMaterialPhysicalSourceReader`、`FinanceMaterialStatementSourcePort`、`FinanceMaterialStatementContracts` 或新增 FIN06 文件，避免并写。V1005保留给本功能。子任务继续V1000首次AP和FIN08物料/收款分配。

现有物理reader只是初稿，以下问题已发现，不能按源码存在称完成：

- 它用头表 `status=-1 AND deleted_at IS NOT NULL`判断实际反审。但原采购收货、库存其它出库、销售其它出库的反审主要只设status=-1，很多并不设deleted_at；不能用updated_at补时间。可复用同包新 `FinanceNativeStatementSql.reversalDate` 的精确来源思路：显式冻结reversed_at、真实关联AR/AP反向、对应sourceDocUUID/type/movement_type/反自然方向的不可变stock_movements时间。按实际单据变体核清，不按相同金额或日期猜。
- 它直接取采购收货行完整qty，并把“单已审核”当作物理入库完成；现有业务必须实际IQC PASS后由仓库确认，可能多批、部分合格、拒收或先入后检，不能把待检整行提前算进可用进仓。请对照 `ProcurementIqcStockInService` 的真实 stock-in item/movement关联，逐原receipt item累计有权威实物归属的切片；仓位内部流转不能重复计入原来料。
- 仓库确认采购入库的stock_movements.source_item_id是实际stock-in item UUID，不一定是原receipt item UUID；不可直接拿二者相等连接。需要明确stock-in→inspection→receipt item关联。
- 采购 `CHARGED_PLUS_GIFT_V1` 等数量语义可能将额外赠品独立记gift_qty。进仓重量/实物量应取真实物理切片，不以账单计款qty替代，也不把免费替换当新应付。
- 初稿以原单weight且非legacy认作实称；应优先真实movement的MEASURED/EXACT/SLICE证据。AVERAGE/ESTIMATE不可当实称。单位名/当前goods.unit不能证明KG/PCS换算；缺实物计量通过受审输入维护，原始参考值继续保留。
- 原颜色为NULL应表示明确“无颜色”还是“所有颜色”需在Query/Context清晰区分；原料/商品UUID和颜色不得因同名合并。
- 它的fingerprint目前包含不可变原单身份/qty/unit/weight，反审日期另返；若转为实际多批物理来源，应包含有序真实切片ID/qty/weight/source，不能更新后把旧实物流抹掉。新来源关系须由财务显式关联实际辅助对象，不用“金本/57#”名称判断供应商或客户。

原附件4的D42=D41/0.87，原式保留为需求证据，不默认所有期/对象统一13%或乘1.13。应维护真实加工单价/含税与否及实际AR/收入/税源；加工份额与明确非加工余项分别守恒到同一GL金额。普通回款或贷方余额不能直接当负加工费。原人民币附属0行不证明原币0，原币单位必须使用 `original_currency_id`。

## 可复用的账载/表尾接口（2026-11-03固定）

`FinanceAuxiliaryLedgerReadPort.read(Scope(accountCode,auxiliaryId,accountingCurrencyId,originalCurrencyId,dateFrom,dateTo))`：返回同一已记账总账分配的本币/原币开期、借、贷、结期、来源行数、fingerprint及依据。借方正/贷方负；会计属性币别与原币单位分开。用根 `fn_finance_gl_voucher_is_booked` 同时保留已红冲正原及真实负反向，不读草稿；`FinancialLedgerReadScope`按各日期范围给未知，不强求外账证书。无GL/受审零证据仍未知，原币缺证据不能当0。最新实现逐JDBC行流式聚合/摘要，避免保留整户历史；流式及逐分量原币未知增强仍待新轮回归。

该reader只是GL分配视图，不把另一套ERP余额加上去。未分配的原生GL辅助完整性需与根公共writer/读取边界协调，不能将一部分有alloc的金额冒充完整该户余额。新供应商预付/应用/退款已有真实两币别和aux分配；旧普通原生付款/收款/AP_POST的自动辅助对应由根掌握的GL公共边界处理。

V1004 `FinanceStatementDocumentContracts`固定：`Context(templateKey,partyRole,partyId,currencyId,dateFrom,dateTo)`；`Organization`保存实际组织/地址/电话/传真/完整收款资料/收货方；`Settings`为1至20个不重复、同金额口径、同真实币别的明确GL余额来源+受审质保组成+打印备注。首余额`balance`兼容旧3参，追加`additionalBalances`；不混本币账面和原币，即便显示名称相同。质保只是已在余额中的组成，不再次加总，NULL未确认与显式空清单区分。

- `POST /finance/statement-documents/profiles`按requestId/expectedRevision保存加密不可变版本；`GET /profiles`按OWN/COUNTERPART/CONTEXT、模板/真实party/currency分页；`GET /profiles/{id}`读原版；`POST /profiles/{id}/review`不同财务审核。OWN/COUNTERPART的templateKey为ALL，CONTEXT为共同原表key。
- `metadata(Context, periodAmount)`是内部服务方法，金额必须取完整原表同源合计，不接受HTTP编辑合计。元数据除原字段另有`templateKey`、`partyRole`、`organizationName`、可选`headerLines`（同footerLines形状）；原supplier/subcontract客户名称取本方，client取对方。真实银行账号不从仅尾号的原native字段猜全号。
- `POST /preview`由服务器在一个REPEATABLE_READ快照读完整原表（最多20000行），金额冻结为十进制字符串；`POST /reviews`提交requestId+Context+expectedSourceFingerprint；`POST /reviews/{id}/decision`不同审核人确认。原单、账载或受审资料变化时保留旧原件、重新建另一版本。
- `POST /reviews/{id}/counterpart`multipart input+file：保存绑定该documentSha256的真实对方回传件、实际姓名/日期/依据。旧件不能自动套新原件；精确重试幂等；`GET /reviews/{id}/counterpart-file`校验原版本/SHA下载原件。系统审核姓名/账号快照与真实手写签章区分，不生成签名图片。
- `originalTable(reviewId,page,size)`和HTTP`/reviews/{id}/original-table`返回原冻结ReportTableResponse列/行/精确总计，附独立实际确认元数据；`documentMetadata.templateKey`只取reviewed.template_key，根通用report/export会用statementReviewId校验模板，不读live来源。原列、布局writer、导出引擎继续共用。

目前 `FinanceStatementDocumentService.originalPage`对FIN06仍明确拒绝旧委外拼接；根完成正式FIN06 reader后需接到这里或给一个稳定read port，不把此拒绝作为最终功能。打印资料/原件工作台UI根接手，往来子任务不再改该service/controller/contracts；回归发现具体错误先协调。已过的V1004首轮仅原supplier真实来源+冻结/确认链；之后正常metadata挂接、多GL来源、姓名及originalTable增强待重跑。
