# 物料汇总按生产规则自动分单

## 问题与处理

截图中的“相同物料的冻结组件规则不同，请按生产规则分别办理”来自汇总下单预览校验。同一货品、颜色、单位可以出现在不同产品及 BOM 路径中；原客户端只按车间、负责人、超产比例拆单，未把后端冻结组件规则纳入分组，因而把不能共用生产规则的来源送进同一组，整轮被拦截。

现在由服务端返回逐来源生产规则标识，客户端在原有自动拆单入口同时按规则标识分组。规则相同的来源继续合单，规则不同的来源分别下单，仍属于同一次确认和依赖编排。服务端在预览和写入时重新校验，客户端分组标识不构成写入授权。

## 公共入口与覆盖

| 原有入口及调用方 | 比较与处理 | 本次公共入口 / 保留差异 |
|---|---|---|
| `AggregateMaterialOrderPreviewService.resolveGroup` 的递归组件比较 | 业务规则正确，原本只会阻断混组；抽出规则计算并继续用于校验 | `AggregateMaterialProductionRules` 同时供分析投影与预览使用，清理原有私有重复算法 |
| `AnalysisView` 及普通、共享仓库、稀疏投影，含预览/提交嵌套分析 | 所有表示保留同一来源事实，无需改变现有构造参数和请求协议 | 只读派生属性 `aggregateRecipeKeysByMaterialLineId`；历史回执反序列化忽略派生输入 |
| `_MaterialAggregateTableController.partsOf`，由按物料汇总及按产品逐行提交共同调用 | 已有数量分配、请求组数、草稿与幂等键能力；扩充现有分组机制 | 自制按生产规则、车间、负责人、数值超产比例拆分；采购/委外按生产规则拆分 |
| `draftParts`、`requestGroupCount`、`requestFor`、`splitNote`、`partLabels` | 草稿预览、请求窗口、提交、展示共用同一分组结果 | 保留来源顺序；拆分键不依赖数量或行序；一物料不跨请求截断 |
| `ProductionMaterialAnalysisView` 同步/响应式解析 | 新字段在两条解析路径一致，响应式路径分片让帧 | 严格校验规则标识；明确区分旧服务端缺字段与新服务端缺少某来源的证明 |
| `withOwnershipFrom` 归属刷新 | 仅替换货品归属，不能冲掉当前分析生产规则 | 保留规则映射及其存在标记，并保留现有销售要求 |

## 规则与边界

- 沿用既有递归签名：相对 BOM 路径、货品、颜色、单位、管控阶段、用量基础、设计用量、基准产量、整包规则、硬门槛、已确认供应方式。真实学习用量继续用于实际需求；设计规则不随学习用量变化而另开历史批次。
- 来源别名按当前有效目标判定，已退役且无责任的目标遵守原有准入规则。单一原来源指向多个冲突规则、目标缺失或组件成环时，不提供可合并证明；客户端隔离该来源，服务端继续阻止不明确的业务写入。
- 拆分沿用四位定点数分配和逐来源原文，不改变需求份、公共备货、原始产品和销售来源。采购安全补库只确认一次，选择本次最浅 BOM 层级的分组承载。
- 一物料超过 500 个兼容组时显示明确范围提示并保留草稿，避免请求窗口为空后无反馈；总来源上限和整物料请求边界保持原合同。
- 继续沿用原预览指纹、版本比较、权限、锁定事务和未知提交处理。失去身份或分析代次的结果不会回写，不自动重放业务提交。
- 旧服务端缺少整个规则映射时保留原分组协议；此修复需前后端配套更新才能完成自动按规则分组。

## 交互设计

按 `frontend-design` 执行局部交互修复，保留 Uten 组件与主题。颜色沿用品牌 teal `#0F766E`、表面 `#FFFFFF`、背景 `#F5F7FA`、正文 `#0F172A`、边框 `#E2E8F0`；字体、字号、行高沿用现有表格 token。

布局维持“汇总行 → 办理提示 → 一次下单”。不改变输入格布局，原有拆单提示补入“生产规则”，悬浮展示每组数量和生产安排；涉及真实规则差异时提示系统保留来源规则自动分单。原“改成相同车间/负责人即可合单”的说明仅用于生产安排差异。
