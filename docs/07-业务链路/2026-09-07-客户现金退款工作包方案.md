# 客户现金退款工作包方案

日期：2026-09-07。状态：只读调查后的实施方案，尚未实现或批准为新 ADR。本次只新增本文档，不新增迁移、不改已冻结的收款/AR源码；库存成本映射由另一个工作包负责。本文与[销售资金场景矩阵](2026-09-07-销售资金库存场景矩阵与压力验收.md)共同使用。

## 1. 当前边界与确定事实

[ADR-048 第六节](../99-决策记录-ADR/ADR-048-客户预收与销售订单资金事实分层.md)明确客户现金退款未交付：不能通过删除原收款、改余额、取消订单或普通收入/费用单模拟退款。V499允许结案订单上历史预收的合法记账红冲，并不等于客户退款。原现金已收到而后来真实退还客户时，应保留原收款并追加付款事实。

[ADR-053](../99-决策记录-ADR/ADR-053-多币种收款毛额净额与追加式账户流水.md)区分客户结算、账户原币、账户实际出入账本币、费用和汇差。原收款600、公司承担代扣费用40、银行入560时，不能据此自动把客户最多可退额压成560，也不能重复减费。旧的费用冲销不自动当作真实客户现金。

当前代码事实：

| 来源/实现 | 已有能力 | 退款工作包须补的边界 |
|---|---|---|
| `FinanceReceiptService` | 客户预收、AR收款、双币金额权威、另一员工审核、账户流水、即时不可变GL及追加反向 | 不能用原收款红冲表示后来真实支付给客户；增加有效退款/保留额度存在时的来源反向保护 |
| `CustomerPrepaymentOffsetService` | `CUSTOMER_PREPAYMENT`来源转销至同客户同币种正式AR，逐来源份额/尾差/版本/幂等/反向 | 目前只接受预收，未提供通用销售退货贷项抵扣命令；必须扣除已批准待付款的退款保留额度 |
| `SalesReturnAmountAuthority` / `SalesReturnService` | 根据实发/原AR冻结退货金额；形成负AR；客户处置改变补发需求 | `REFUND_CLOSED`只关闭补发需求，没有现金付款。服务中的“红字应收即最终退款结算”“已退款”旧注释须在实施时纠正 |
| `ar_ap_ledger` | 预收为`direction=AR, source_doc_type=DIRECT_RECEIPT, open_item_kind=CUSTOMER_PREPAYMENT`；销售退货为`direction=AR, source_doc_type=SALES_RETURN, open_item_kind=RECEIVABLE`且金额为负 | 销售退货不是AP的`CREDIT`类型；不借用供应商开放项类型。现有余额没有独立“已退款”消费维度 |

| `AccountFlowLedgerService.reverse` | `Propagation.MANDATORY`下按来源追加反向流水、来源锁、原币/本币快照、禁止重复反向 | 只负责流水反向，不负责账户累计或客户AR；不是通用正向付款端口 |
| `GlPostingService.postReceiptDoc/reverseReceiptDoc` | 原凭证/反向凭证双向引用、完整分录后封存、事实金额校验 | 可复用模式与公共期间锁，不能将退款类型放入可删除重建的`REGENERATED_SOURCE_TYPES` |

## 2. 两类来源与金额权威

一张退款申请固定一个客户、一个结算原币、一种来源类型；允许同类多个来源行及分次实际付款。表单只选择来源和本次拟退原币，服务端计算可退额/账面本币。不得输入任意负AR、客户名称或单号作为来源。

### 2.1 订单预收退款

来源必须是已审核且有可核验实际现金来源的客户预收开放项，并保留原`finance_receipts.id`、可选`receipt.sales_order_id`、原账户/原币/本币/费项/GL来源。

可退原币 = 当前未应用预收原币余额绝对值 − 已批准未付款的有效退款保留额度。当前余额须包含已实际退款的消费，不能仅按“原到账减转销”再算一遍。

- 已转销份额不能同时从预收端退款。若退的是已履约后退货，转到销售退货退款来源；若是纠正错误转销，先按原业务的后进先出规则反转转销。
- 原收款仍为已审核、原金额/汇率不变。实际退款单另记现金流出，来源预收负余额逐笔归零。
- 退款完全完成后，订单取消守卫必须检查剩余资金责任及有效应用，而不能继续仅凭“历史存在已审预收收款”永久阻塞。需同时修改`SalesOrderService.assertNoApprovedCustomerPrepayment`与V386对应`fn_guard_sales_order_customer_prepayment_cancel`的前向定义，保留发货/生产等其他取消守卫。

### 2.2 已收清后销售退货退款

来源必须同时有：有效已审核退货、明确来源实发/订单行、唯一有效原AR及退货负AR、冻结退货金额、已收资金的精确订单来源分配、客户“不再补发并申请退款”的商业结论。`amount_balance=0`本身不证明已收到现金；若原AR被坏账/折让等非现金冲销结清，不可直接支付客户现金。

退款上限同时受两条来源约束：

1. 退货负AR尚未处理余额减有效退款保留额度；已抵扣部分不能再次退。
2. 与该原发运/订单来源精确关联、尚未退还客户的现金支持份额。普通收款沿`finance_receipt_source_allocations`；预收已转销沿`customer_open_item_offsets`回到原预收收款。不得以客户总余额、当前订单总额或比例猜分配。

给每条退款消费保存实际现金支持的来源行。预收400中100从未转销、300已转销时，预收端退100与退货端退200合计只能消费同一现金来源的300；其余100仍可追溯，不能让两条路径各自独立放大上限。历史缺分配、部分非现金结算或多订单来源不完整进入待核对队列，不自动猜金额。若今后新增“销售退货抵另一订单AR”，该命令也必须维护现金支持链并使用同一额度权威。

现金支持上限按同一结算原币核验，同时保留实际现金本币快照供追溯；不能要求原到账本币等于AR/退货的账面本币，两者可以使用不同汇率，差额须沿已有汇兑事实解释。

退货审核已经冲回销售收入；实际退款只清理客户负AR并记银行付款，不能再次冲收入、减订单已收快照或改销售出库库存。品质不良与退款合法性不是同一件事；不应把“良品放行”作为所有客户退款的统一条件。

## 3. 数据与并发模型

建议新增专用`features.finance.customerrefund`，不扩展采购付款单的供应商语义。建议的最小数据组如下，具体迁移版本由实施阶段统一分配：

- `customer_refund_requests`：客户/币种/来源类型、申请原因、制单/审核人、审核版本、状态、审批快照哈希。销售可提交商业申请，实际账户与付款由财务负责。
- `customer_refund_source_holds`：批准时保留的来源额度，记录source ledger UUID、订单/退货引用、原币/账面本币、资金支持来源；保留/部分消耗/释放均有追加事件。草稿/待审不占钱，审批时重新原子核验。
- `customer_refund_payments`及其不可变来源行：每次真实出账的原币、本币、真实账户原币、付款汇率/来源/时间、银行凭证、收款人快照、费项和GL科目UUID。每次付款独立UUID、幂等键、哈希；不能覆写已付行来做分批。
- 原始来源AR可增加`amount_refunded_original`和`amount_refunded_book_local`的累计缓存，默认零；权威为上述不可变消费/反向明细。所有写入口和数据库余额约束统一纳入，不能只给新退款页面减一次。

建议的余额恒等式(退款累计为正数，仅允许两类AR来源具有此消费)：

`原币余额 = 原额 − 已收 − 非现金冲销 − 已转销 + 已退款原币`

`本币余额 = 原账面本币 − 账面核销 − 已转销账面本币 + 已退款账面本币`

比如预收原额0、已收400、转销字段-300、退款100，最终余额为0；退货原额-500、退款500，最终余额为0。原收款/退货原额都不改。已批准待付仅保留额度，不先写“已退款”或银行流出。

退款批准、分次付款、释放保留额度、预收转销和未来退货抵扣共用`CustomerCreditCapacityAuthority`；不能各写一条独立SUM。每笔命令稳定排序锁定全部相关AR行及精确来源份额，在同一事务重新计算可用额度，并以唯一键+版本/CAS保证只有一方消费成功。保留额度也是硬约束，不能只在列表扣掉而让旧转销API绕过。

锁序设计应沿用并核对现有资金顺序：业务单头/审核case → 期间锁(涉及GL时) → 真实账户UUID → 全部来源/目标AR UUID → 来源分配/保留额度行。退款必须把原现金支持的AR/预收行纳入预锁范围，使原收款红冲和退款消费争同一把锁。锁住AR后不得再锁原收款头：当前原收款反向先锁收款头再取期间/AR，反过来会产生死锁。原收款头的金额/身份已不可变，可读取核验；原收款反向须在共同AR锁内检查有效退款保留/付款消费。

数据库还需约束：请求/付款幂等唯一、原来源单不重复退款、所有累计不超来源、同客户同币种、终态不可改/不可删除、来源与付款行和账户流水/GL金额一致、反向一对一或可追溯的分次收回。新表逐一登记业务审计触发器，不能放进技术表豁免。

## 4. 员工流程、正向与反向

建议主流程为：草稿 → 待审批 → 待付款 → 部分已付/已付。审批通过只保留额度；财务点击“登记实际付款”并提供银行出账证据时，才追加资金消费、扣真实账户、写`CUSTOMER_REFUND`流水与不可变GL。系统当前没有真实银行转账接口，不能把按钮称为已向银行付款。

- 待审可修改/撤回，但实际审核认领期间禁改；修改后重建本轮审核版本和前后差异。使用本轮严格认领及同代`claimId`协议、原版本CAS和制单/审核分离。
- 待付款取消要释放保留额度并留取消事件；没有付款事实，不生成银行或GL反向。
- 已付不得删除、取消或改金额。网络超时用原幂等键查询/重放同一命令，不能创建另一笔付款碰运气。银行参考号单独不能当唯一键，因为同一银行批次可能含多笔付款。
- “错误登记、银行实际上未出账”的受控记账冲正，按原快照追加反向现金流和GL，明确证据/原因/审核，不能伪称收到客户返还款。
- “退款真实已付，客户后来实际退回款项”是新的现金收回事件，应有专用`CUSTOMER_REFUND_RECOVERY`来源，按真实收回时间、金额、账户和汇率记录，再恢复相应客户额度；不能直接镜像原汇率和手续费。分次收回总量不能超过原已付本金，银行未退回的费用不自动冲回。
- 原收款/原退货红冲在存在有效退款保留或付款净消费时失败关闭。必须先完成相应受控处置，再执行来源反向；原收款、原退款和原GL保留。

品质退货的冻结/良品/报废/返工与现金退款保持独立台账。财务审核页显示真实收货与品质结论，现金操作不改质检数量、`flag_qty`或库存成本。`REFUND_CLOSED`前端文案应改成“不再补发/申请退款”这类事实表述，真实已退金额只读新付款事实。

## 5. 双币与GL

每次付款冻结三个量：客户权利消耗的原币、来源负债/负AR消耗的账面本币、银行实际支付的账户原币及本币。来源尾差按累计来源金额切片，末批精确耗尽；不能按当前主档汇率重算原来源。付款费用另列责任与账户，不从原AR再减一次。

例：退预收100，原账面680，实际付720，则`Dr CUSTOMER_ADVANCE 680 + Dr FX_GAIN_LOSS 40 = Cr 银行720`。退货退款同理以`AR_CONTROL`清理负AR；销售收入已在原退货中冲回，退款不再冲收入。原币账户余额只按该账户的真实币种增减。

复用`accounts.style_id`和`system_posting_style_roles` UUID，不按科目名称/编码猜关系。新增退款GL应在同一付款事务内写完、核对来源分录集合后封存，反向/收回追加独立关联凭证，并从旧期间重生成删除集合中排除。`AccountFlowLedgerService.reverse`可复用记账冲正的流水追加，但外围仍必须同时维护账户累计、客户额度和GL。

现有`lockAutoProjectionPeriod`只是期间并发锁，不能宣传成正式关账制度。首期是否延续收款的当期录入限制需明确；无论采用何规则，实际银行时间必须单列保留，不能改写历史日期来掩盖跨期。

## 6. 权限、界面与接口边界

建议新权限独立于`finance_payment:*`：`customer_refund:view/create/edit/submit/approve/reject/pay/cancel/reverse`，其中是否拆出`recover`由下节选择决定。资金读取保留公司级财务范围要求；销售只能读取/申请自己订单的商业退款信息，不获得银行付款或GL字段权限。

任务入口建议财务工作台一个“客户退款”列表，按来源切换“预收退款/退货退款”，按状态区分待审批与待付款。必要字段只显示来源、可退额、本次申请、原因；付款时才显示账户/实际金额/汇率/银行凭证/收款人。系统计算金额只读，费用/历史核对信息折叠，提示放框内icon。额度不足明确指出正在被哪笔转销/退款占用，可双向查看来源与付款进度。

审批资格复用现有财务资格端口模式，保留明确个人授权例外；弹窗接收继续“财务部门任职 × 当前动作权限”。提醒只通知需要审批/登记付款的人，销售收到实际已退款的结果通知，不把待审批说成已退款。

## 7. 历史兼容与验收

历史`deposit`仍是商业快照，不转成可退款现金。历史退货负AR、`REFUND_CLOSED`、手工费用、负收入或未知PAYMENT都不得自动推断已退款。只有银行证据、客户与精确来源/原GL能够匹配的历史退款，才可通过专用导入/人工核验入口登记其原事实及来源；缺本币快照保留未知，不用现汇率填补。

新退款累计列默认零仅表示新功能尚无记录，不证明历史从未在线下退款。存量来源应保留“历史退款已核验/未核验”的独立资格与证据；未核验来源不直接进入自动可退池。新版本正式启用后生成的来源，由完整资金来源与新退款台账提供持续的可证明余额。

至少覆盖：预收400→转销300→退100与竞争转销；已收清后多批退货/分批付；原币/本币尾差及逆序纠错；同源两人并发只有合法份额成功；两个不同退款来源共用一个现金支持来源不超退；批准保留后旧转销API不能占走；部分付款后取消剩余；真实支付后收回的不同汇率/未返费用；原收款/退货反向受有效退款阻塞；原状态0/1/-1与非空历史升级；无授权/跨客户/跨币种/换收款人/篡改金额拒绝；全事务回滚、超时幂等与账户原币/客户AR/GL逐来源对账。

性能需要来源ledger/ref/receipt UUID上的部分索引，列表服务端分页，单次批量上限明确；退款额度不得每个格子扫描客户几十年全流水。与本轮10万/50万规模测试同样记录完整规模、p95/p99及失败率，不能用空资金库的快速响应证明退款链性能。

## 8. 实施前需定下的业务选择

1. **订单取消与待退款的先后。** 建议允许先记录“申请取消/暂停新履约”的商业意图，最终财务完成仍须等责任清完；但这需要明确哪些已有采购/生产/发运可继续，不能简单放开现`is_stopped/cancel`资金守卫。若暂不做取消意图，首期从仍有效订单发起退款，清完后再最终取消。
2. **审批与真实出账是否拆开。** 建议采用待审批→待付款，批准只保留额度，银行证据到齐才记实付；审批人不得等于制单人。付款登记人能否同时为审批人应按实际人员配置决定，不自行强加第三个岗位。
3. **退款费与币种范围。** 建议首期只支持客户原币及同币/本位币真实账户，手续费默认公司承担；第三币种及客户承担费用须有明确商业协议和独立金额拆分，再开放。未用预收与已收清退货均不能凭现汇率推原账面价值。
4. **已付反向、品质条件及历史现金证据。** 必须区分未真实出账的登记纠错与真实退款后收回；建议同时设计两个typed事件，不能用一个“红冲”按钮自动假设钱已回来。品质不合格也可能按合同或商业约定应退款，本系统先要求明确商业退款结论与仓库数量证据，不强制“全部良品”。历史非现金冲销/缺来源资金须由财务核验后才可退。

以上选择未定、专用实际退款/收回事实与完整余额约束未实现前，订单资金卡继续只显示“客户待处理余额”，不能显示已批准退款或已退款。
