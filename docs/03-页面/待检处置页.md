## 一、页面与权限

- 列表/处置：`/warehouse/inspections`（路由名 `warehouse-inspections`）
- 入口：**品质任务中心**（`/quality/task-center`）「待检处置」卡，卡面数字即角标
  （`GET /api/procurement/inspection/pending-count`，仍待检收货单张数）；
  持有查看权限者可见。处置返回、返回工作台，或客户端检测到新通知使未读数上升后，
  `procurementInspectionPendingCountProvider` 立即失效并重新读取该接口，不再额外等待角标的
  60s 轮询。通知条数/未读数只触发刷新，不是角标计数来源。
- 仓库侧「预计到货任务中心」不再承担待检入口：原「待检处置」卡改为只读状态卡
  「待品质部批准」（不筛列表，点击切换下方提示条的品质部口径说明；角标同口径，
  无 `procurement_inspection:view` 时不拉取计数显示 '—'）。同日该页类型筛选卡
  （采购到货/委外到货）下线，仅保留「全部待到货」与「待品质部批准」两张指标卡。
- 查看：`procurement_inspection:view`（V222 已种子入库，可在权限管理页授予角色）；
  处置（PASS/FAIL）：另需 `procurement_inspection:handle`。无 handle 权限者只读。

## 二、页面结构

1. **待检收货单队列表格**（`GET /api/procurement/inspection/pending-receipts`）：
   展开屏在左侧、紧凑屏在上方，列出类型、收货单号、供应商/委外商、待检行数和待检量。
   初次进入自动选第一单；单击切换当前单，刷新后业务 UUID 未变则保持当前单。
2. **当前单明细表格**（`GET /api/procurement/inspection?receiptType=&receiptId=`）：
   固定显示货品、颜色、来源订货单、到检/已合格/不合格/剩余待检量和状态。
   单击勾选、双击打开单行检验；完成一行只刷新当前表格，不销毁工作台。
3. **连续与批量动作**：
   - 右下角「批量合格放行(N)」仅处理当前收货单已选明细，最多 100 行；
   - 请求 `POST /api/procurement/inspection/{receiptType}/{receiptId}/pass-batch`，每行提交
     `inspectionItemId + expectedRemainingBaseQty + idempotencyKey`，服务端先校验全集再写品质结论
     和仓库待入库任务；不得在品质事务写库存；
   - 任一行状态或剩余量变化，整批事务回滚；客户端不得循环单行接口伪装批量成功；
   - 不提供“批量不合格”：不合格原因属于逐行质量证据；选中单行后登记原因；
   - 本单仍有待检行时保持当前单；全部结案时自动选择原索引处下一单，并以 live region 提示。
4. **单行处置对话框**：
   - 合格放行（PASS）：数量可留空=全部剩余（部分 PASS 支持逐次放行）；放行说明选填，
     留空时仍记录结论、数量、审核员和时间。
   - 不合格（FAIL）：只记质量事实，不进可用库存；原因必填。
   - 业务影响说明上方以红色责任提示明确显示“审核员：姓名(工号)”。姓名和工号来自当前登录
     `sessionProvider.user`，只用于让操作人确认当前身份；客户端请求不提交审核员字段。
   - 幂等键由客户端生成（UUID v4），同一表单同一请求重试复用；服务端事件账幂等
     （同键同命令静默重放、同键异命令冲突）。提交错误留在对话框内，不清空数量和原因。

## 三、业务口径（与 V222/V335 后端一致）

- 收货审核在同一事务内创建 PENDING 冻结行并追加 `PROCUREMENT_IQC_PENDING` 业务 Outbox，
  **不写 stock_balances**；三个可用量口径
  （warehouseAvailableBase/globalAvailableBase/v_stock_available）自然不含待检品。
- 待检 Outbox 按收货单 UUID `publishOnce`：同一收货单有多条明细只投递一次；收货审核事务
  回滚时待检行与 Outbox 一并回滚，不产生孤立通知。
- 待检通知只发给 `DEPT_QA` 子树内当前在职、账号启用，且最终有效权限仍包含
  `procurement_inspection:view` 的账号；PMC/生产默认查看权、跨部门个人加授和超管全集均不扩张
  品质通知池。接收通知不要求 `procurement_inspection:handle`，点击进入 `/quality/task-center`。
- Outbox 真正送达前重查本单是否仍有 `PENDING/PARTIAL` 明细；若已经极速处置结案，则跳过
  过期待检通知。待检角标仍以 `pending-count` 的实时聚合为唯一真相。
- 每次部分 PASS 只追加品质合格数量、事件和“合格待仓库入库”任务；`passed_base_qty`
  不是可用库存，不能直接生成库存流水、分析归属、reservation、DRAW 或 READY。
- PASS 无放行说明时，事件 `reason` 保存为 `NULL`；有说明时才追加说明文字。V335 只放宽
  PASS，FAIL 的非空原因数据库约束保持不变。
- 仓库可按合格待入库量分批填写实际库位并确认入库。只有仓库确认事务才写 `DIR_IN`、
  增加 `warehouse_stocked_base_qty`，并按该次实际入库切片刷新分析与推进正式供给。
- 整张 receipt 品质结案只表示 PASS/FAIL 数量已确定；全部 PASS 量都经仓库确认后，才是
  “仓库已入库”。通知、角标、生产齐套和报表不得把两个状态合并。
- FAIL 不入可用；处置（退/换/补/特采）走对应业务单据，本页只登记质量事实。
- 红冲收货前必须全部明细 RESOLVED；只按实际 `warehouse_stocked_base_qty` 反向库存，
  已 PASS 但未确认入库的数量只取消待入库任务。

## 四、安全边界

- 处置按钮由前端按权限隐藏，服务端 `@PreAuthorize` 独立兜底（view+handle）。
- 审核员显示不是安全边界：服务端忽略客户端身份声明，并以
  `SecurityContextCurrentUser.requireEmployeeId()` 写入追加式 `procurement_inspection_events.actor_employee_id`；
  全局 `fn_audit()` 继续记录事务审计事实。
- 数量校验双保险：前端对话框校验（正数且 ≤ 剩余），服务端按剩余待检量硬校验。
- 处置成功后先从本地明细表移除已提交行，再刷新服务端投影；刷新失败也不恢复旧可操作行。
  整单结案从队列表格移除并自动进入下一单。
