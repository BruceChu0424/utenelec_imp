## 1. 当前事实：线程与预算不能只看配置或任务名字

`application.yml` 7–10 行配置 `spring.task.scheduling.pool.size` 默认 4，但非 cloud 档唯一 `DrainAwareTaskScheduler` 在 51–56 行自行建立 `ThreadPoolTaskScheduler` 并固定 `setPoolSize(1)`，没有读该属性。因此当前共享定时任务实际串行；直接改环境变量不能证明变成四线程。`ServerStatusProbe` 426–442 行也按单线程解释排队。本文不建议未经测量就扩大池。

独立工作线程另外计算：业务 Outbox 1 个 worker，AI 默认 2 个 worker/等待队列 8/1 个续租线程，服务器状态 1 个采样线程。它们可以与共享调度线程和 HTTP 同时运行。Outbox/AI 的调度入口只负责唤醒，`ScheduledTaskRunRegistry` 中的短运行时间不是实际后台消费时间；registry 只保留内存中的最近一次运行，重启清零，不是持续吞吐和队列延迟的证据。

应用 Hikari 默认最大 20、最小 2、借连接超时 10 秒；初始化每条连接的 lock timeout 为 10 秒、statement timeout 为 60 秒；Spring 默认事务 40 秒。测试类路径 `server/src/test/resources/config/application.yml` 改为最大 8/最小 1。全链共用容器还把 PG `max_connections` 提到 400，以容纳多个 Spring 测试上下文；这些值不能误写成公司生产容量。

共享命令 deadline 的起点仍是最外层受支持的事务代理，不包含 HTTP 排队/鉴权，也不能把 PostgreSQL COMMIT 的全部耗时硬截断。`TransactionTemplate` 构造的后台循环不等于一个统一的 HTTP 根命令预算；需要分别记录其实际事务上限和每轮总时间。

## 4. 受控实验：只影响一次性测试资源

先冻结输入 manifest：代码及编译产物 SHA、迁移目录/条数、PG/JDK 版本、CPU/内存/cgroup 配额、存储介质与容量、Hikari/PG 连接配置、数据与种子、计划/BOM 深度、同物料热点比例、后台开关及积压、前台并发/到达率、诊断开关。任何一项改变都建立新档，不混合统计。

实验资源建议作为 R0.07 的待冻结候选：应用测试 JVM、PG、负载发生器都在专属容器/受限测试资源中；总 CPU 硬额度不超过可用逻辑核的 25% 且至多 2 核，内存及存储先校验宿主余量，只使用本次新建 volume。`-XX:ActiveProcessorCount` 只是线程规划提示，不是硬 CPU 限额；不能用它冒充隔离。用户整机不运行无限循环、宿主磁盘填充、drop_caches 或不限速压力工具。不连接公司/开发业务库，不从生产业务表复制私密数据。

分两条实验线：

1. **短诊断线**：测试上下文停止自动计时入口，用真实业务/后台实现按受控一次调用制造明确重叠，分别定位 CPU、SQL、锁和连接等待。该测试控制器不是新增生产调度器，结果不能当默认调度长跑成绩。
2. **真实调度线**：保留现有单线程调度器、独立 worker、默认周期和真实非空积压，不手工重复触发。运行至少 30–60 分钟并记录真正执行了几轮、各轮耗时/积压年龄。只说“已打开后台”但队列始终为空不算混合负载。

## 5. 业务输入和采样方案

固定三个主族：日报一行产出分给 1/3/11 个同车间收料工单；FQC 20 行普通/先入后检/两者混合；普通批领料 1/3/10 单，50 单另列规模预算。另保留全 skip、原键重放、取消后重放作为独立轻路径，不与首次写混算。

每次新写使用新命令键和未处理的真实任务。日报必须有真实原料领用、权益、成本、产出去向和后续自动实发；FQC 必须实际触发分析刷新，不用空来源或 mock 快路径；批领料保留草稿/已审/部分已发混合。大批除单数/行数，还冻结总明细、BOM 深度、来源和仓库维度。

忙碌测试的种子库存必须经正规 OTHER_IN 审核或有证据的期初路径建立，余额/流水/价值源一致。现有部分 SQL 预算夹具直接插 `stock_balances`，适合前后命令差分，但不能打开全量对账后把这些人工余额造成的漂移当生产错误；改为完整来源的负载夹具后要单独做同输入 before/after，不生搬原 SQL 阈值。

先用每档约 30 个独立新命令筛查数量不守恒、SQL 放大、锁序和资源失控，不据此宣称 p95 达标。正式采样预热至少 5 分钟，固定前台并发 1 与 4，再按实测容量冻结到达率；负载发生器记录计划到达与实际开始时间，避免只在前一请求结束后再发下一条而漏掉排队。提供有限 in-flight，客户端限额拒绝也必须计数，不能装成服务器成功。

每个主要业务/负载单元持续至少 30–60 分钟；p95 建议至少 500 个已接收新命令，p99 建议至少 1000 个并附样本数/尾部数量/区间；达不到数量就继续或标样本不足。报告 p50/p95/p99/max、系统错误/超时、业务校验拒绝、未知结果、重试次数与 offered/accepted/rejected。异常/超时不能从延迟分母静默删除。候选与对照交替运行(例如 ABBA)，使用相同配额、数据形状、并发、积压与预热。

沿用已批准 07 的目标，不事后降低：简单审核/单笔出库/普通 FQC 常规 p95≤2 秒、繁忙≤5 秒；11 块直送/20 行品质批处理常规≤8 秒、繁忙≤15 秒并记录提交尾部；50 单按具体家族/明细另冻预算。1/3 块、1/3/10 单各自目标须在 R0.07 明确映射，不能只把少量快样本混入大组稀释慢路径。

测量至少分：HTTP接收/鉴权/准入等待、根服务命令、连接获取、SQL执行、Java/ORM、提交准备与flush、JDBC COMMIT、afterCommit、响应传输、Flutter刷新/首个可操作帧。SQL语句计数与扫描行、临时文件、WAL、锁、连接池、GC、容器CPU/IO、后台积压时间序列一起保留。使用受限测试连接查询 `pg_stat_activity`/`pg_locks`/`pg_stat_statements` 的前后差值；诊断采样开销单独量，避免把后台总量归到一笔前台命令。

HTTP 长跑需要真实端口/安全链，不是 MOCK 服务调用；UI另用隔离 profile 构建和合成账号。响应丢失、401/403权限变化、400/422后续拒绝、同键异内容、取消后重放须联合客户端/服务端演练：真实提交、明确回滚、结果未知三者不得混为失败，已确认行不因本机保存/刷新失败重发。
