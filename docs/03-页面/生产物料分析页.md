## 一、员工看到的主流程

```text
已审核销售订单行 / 合法手工需求
  → 选择产品与本次需求数量
  → 选择主仓库范围，核对实际领料子仓
  → 联合分析，查看产品层级或按物料汇总
  → 勾选根产品或物料，核对上次路线/本次草稿，点击“确认路线”
  → 分别进入“下达采购 / 下达委外 / 下达车间”
     ├─ 采购：确认需求与独立公共补库/备货，形成采购申请
     ├─ 无子层委外：形成委外申请
     └─ 自制（顶层产品/候选/有子层委外/已建子件一视同仁）：
        填「本批数量 + 生产车间 + 负责人」→「创建生产计划」单次原子提交
        （服务端一个事务：候选先建子件任务 → 逐行生成计划 → 有审核权同事务审核下达；
         任一行失败整体回滚，失败不再残留已建子件行）
        → 下层还有没下单的时**先弹**「跟父件一起办」（§3.8 弹窗前置）：数量按本批数量
          算好可改，一键下单按序提交父件 + 下层（采购 / 无子层委外 / 回车间分流），
          下层全已下单则不弹、父件直接提交；委外桶有子层行同款
  → 计划不再做齐套判断：缺料批次以 WAITING 下达（零预留、无 DRAW）
     → 本执行批完整齐套后原子提升 READY，生成内部预留与分仓 DRAW
     → 尚未整批齐套时，可在车间按当前完整套料量核对并显式拆出子批
  → 车间在领料汇总中勾选物料、填写本次申请量并提交，仓库才收到可办理任务
  → 仓库实际发齐本执行批的正式需求，车间明确开工
  → 报工 → FQC → 仓库逐行点收，实际入库量才成为下一层合格供给
```

确认路线只保存所选各自的实际路线与选填原因，不自动下达采购、委外、自制任务或生产计划。进入页面、切换视图、刷新与轮询均不得隐式创建子件任务。

自制/有子层委外采用计划锚点：子件行只承载计划链接与执行进度，不接管子树、不迁移 exact 权益、不再展开第二份 BOM。物料需求和已确认路线始终保持在原树，计划员按原节点下达采购、委外或自制。合格入库后，正式齐套按同分析、同原树直属节点及物料维度核对，足量才把 WAITING 提升为 READY 并生成实际分仓 DRAW。根委外同样保留原树直属子件，见[V495](../数据迁移/111-V495根委外前置自制物料归属.md)。历史遗留委托通过授权刷新归还，`lowerLevelPending` 只解释下层缺料。

## 二、来源、仓库范围与历史兼容

### 2.1 来源选择

销售来源只接受服务端可分析的已审核销售订单行，以销售订单行 UUID 为真源。合法手工需求保留来源类型、稳定来源编号、货品/颜色/单位 UUID、数量和原因。单次联合分析最多 500 个来源，较大任务分批分析。

`MAKE_COMPONENT / SUBCONTRACT_MAKE` 只由服务端响应显式命令生成，员工不能伪造；刷新历史分析时从持久化的用户来源重建，排除这些系统子件，避免重复追加来源。计划产品编号留空时由服务端按真实计划单号分配，不用货号、名称或 `MA-UUID` 反查关系。

### 2.2 计划只选主仓库

计划人员只选择主仓库、查看主仓汇总。不再展示参与子仓多选、领料仓设置、子仓存放明细或“先调入再齐套”的提示；子仓由仓库在真实领料环节处理。

- 新分析的 `warehouseId` 传所选真实主仓 UUID，`warehouseIds` 仅包含同一主仓 UUID。所属库存范围由服务端解析，客户端不枚举子仓、不挑选默认叶仓。
- 旧分析可能保存叶仓 UUID。打开页面时通过主档真实 `parentId` 映射显示主仓；不为显示名称修改旧 `warehouseId`、`warehouseIds`、原单或预留。刷新、追加来源继续保留该旧身份，由服务端作同主仓兼容。
- 缺失父关系或循环关系不能在客户端被伪装为新主仓；仓库资料未能解析时明确显示待更新。
- 同主仓物料按服务端合计齐套，并按实际库存仓分别预留和生成领料单。有原单及品质、实收入库证明的本批专属来源，继续跟随其实际仓；公共库存不能因货品相同就挪用。

同主仓与来源履约规则见 [ADR-073](../99-决策记录-ADR/ADR-073-本批物料履约与同主仓分仓领料.md) 和 [ADR-075](../99-决策记录-ADR/ADR-075-合格来源跟随实际入库仓与车间通知.md)。计划页、物料分析历史列表和计划汇总单均通过 `MasterDictionaryService.mainWarehouseOf` 读取真实主仓名，原业务 UUID 保留。

### 2.3 主仓公共库存与领料分工

物料主表、节点详情和提交确认统一读取 `MaterialView` 的 `mainWarehousePublicAvailableQty`、`mainWarehouseOpenSafetySupplyQty`、`mainWarehouseSafetyReplenishmentGapQty`。这三个数是服务端按主仓汇总的公共库存、公共补库在途和剩余补库量；同货品在多条 BOM 路径重复出现时不能重复相加。安全阈值仍以货品规则为准，按主仓核算一次，不按每个子仓重复扣除。

`MaterialAnalysisCommandService.groupSafetySnapshot` 校验主仓字段完整、非负、同组一致，并核对剩余补库量。旧响应或旧构造缺失主仓预算时，不能拿任意叶仓补出授权预算；命令要求刷新后重试。叶仓 `warehouseBreakdown` 保留原数据含义，但不再作为计划页面安全补库的判断依据。自动刷新比较包含三个主仓字段，预算变化会更新页面。

计划页不再单独显示“物料存放位置”，也不据其它仓数量在客户端推演调拨后缺口。实际领料沿已有领料单办理：`lib/features/warehouse/pages/stock_doc_detail_page.dart` 顶部显示真实领料仓及对应物料数量。仓库侧明细和追溯保持可用。

## 三、分析详情的交互

### 3.1 三个生产准备入口

主页面固定为“下达采购 / 下达委外 / 下达车间”，每个详情内分“未下达 / 已下达 / 需处理”。入口计数和详情使用同一分析快照，不把展示筛选当作新业务状态。

| 入口 | 未下达 | 已下达与进度 |
|---|---|---|
| 下达采购 | 已确认 BUY 且有可提交余量的根产品/组件 | 申请、订货、财务审批、收货、IQC、实际入库的真实来源和进度 |
| 下达委外 | 已确认SUBCONTRACT的根产品/组件，按有无生产子层办理申请或前置准备 | 前置自制、已产/已通知/可通知量、委外申请与回厂入库 |
| 下达车间 | 已确认MAKE根产品、真实自制子件和普通MAKE组件候选；不含根BUY/委外 | 已生成计划、待审核/待料、领料、生产、FQC 与实收入库 |

“需处理”从服务端排产资格、结构、路线和数量约束解释当前阻断。单纯物料不足不应变成禁止先下达车间的理由；已下达行的下一步仍须读取实时下游事实。产品有未排余量且已有计划时，可同时属于未下达和已下达，不能把两个计数相加当作产品总数。

**首列复选框语义（2026-09-10）**：勾选门与「确认路线(N)」的计数/提交门是同一谓词（`_routeGroupSelectable` = 未确认 或 已改下拉的脏组）——已确认且未改动的行**没有勾选框**（此前勾了也不计数，出现「勾着但 N=0」）；下拉对已确认行仍可改（§3.4 手动草稿优先），改成另一路线即出现勾选框并自动勾上，改回已确认值则脱选；表头全选自然只勾未确认/已改动的行。撤回下达（CANCELLED）或根产出红冲后服务端**不清** `confirmed_route`，这类行重新可编辑但同样要先改下拉才可勾选（见 §4.3）。轮询期间被同事确认的行在刷新后自动脱选。

**表头筛选（进度 / 供应方式列头下拉；2026-09-09 接入，2026-09-10 改稳定键 + 投影级过滤）**：桶按当前视图（chip + 关键词）全量行聚合，不按当页、也不含表头筛选本身（选了一个值其余值仍在下拉里）；桶值是**稳定键 + 中文标签**而不是格内文案——进度 = `routePending 路线待确认 / pendingIssue 未下达 / inTransit 处理中 / covered 已齐套 / blocked 不可执行 / inactive 本批无需求` 或流程词表阶段键（标签取阶段名，不带百分比），汇总视图 = `aggregateCovered 已覆盖 / aggregatePartial 部分覆盖 / aggregateUncovered 未覆盖`；供应方式 = `MAKE / BUY / SUBCONTRACT / MIXED`（按当前显示路线：草稿 > 已确认 > 已下达目标 > 学习/主档默认）。过滤在**节点投影层**生效：命中行的祖先（含产品行）保留为只读上下文（灰底、无勾选/下拉/行菜单、状态显示「上级路径上下文（只读）」、数量列「—」）；`hasChildren`/箭头/「N」子件徽章/视图 chip 计数都按筛选后的投影（chip 计数 = 视图条件 × 关键词 × 表头筛选；汇总视图的 chip 仍按节点计数）。改了下拉的行（脏组）对供应方式筛选豁免，确认前不会从表里消失。刷新、轮询、409 恢复、切视图/切汇总后只移除桶里已不存在的筛选值（`_pruneMaterialTableFilters`），仍有效的保留；0 行空态由组件层保留「全屏/退出全屏」并给「清除筛选」按钮 + 「当前有 N 个表头筛选生效」提示（见 [MasterDataTableView](../02-组件库/MasterDataTableView.md)）。

批量动作后整批换行、切段或切列集时，组件自动撤掉已不存在的筛选值
（`UtenEditableGrid._pruneColumnFilters`），不会出现「表头看不见筛选、表体却空」。

**树形箭头与子件徽章**：有子层的行用 28px 层级色实心圆底箭头（选中行反相为白底），未展开时右下角叠「N」= 当前投影可见的直接子件数（产品行 = 直挂子件数；「只看缺料」或表头筛选下是可见数而非 BOM 全量）；汇总行副标题已有「N 来源」不再叠徽章。

### 3.3 按产品与按物料汇总

按产品保留父子层级，搜索具体名称或货号时保留命中路径的祖先。按物料按货品、颜色、单位 UUID 汇总，各任务 UUID 与数量分摊不合并；缺货品 UUID 的历史行按物料行隔离，不凭相同名称猜成同一物料。

已创建的自制/委外前置 child 是**计划锚点行**：不展开自己的物料树（其物料需求保持在原父树原位，单一份数据不重复计量），只承载计划链接与执行进度；详情面板显示「已下达自制 / 计划量 / 已完工入库」。主表进度列在锚点存在时内联子件真实执行状态。

汇总只累加服务端逐节点分配事实，不累加每行重复展示的整仓余额。深层诊断不得再消耗已分配给直接层完整套料的同一公共库存；exact 权益继续只属于精确受益节点。

### 3.4 上次路线与显式确认

1. 已确认路线与已下达事实优先，不被学习默认覆盖；手动修改的本地草稿优先于记忆。未确认节点按货品、颜色、单位 UUID 读取上次确认路线，再回退主档规则；均无可用值时默认委外。每份分析冻结已读取默认，确认一组不能把未选组改成统一委外。
   **服务端建议路线口径（2026-09-10，C05 F8）**：主档来源「采购/自制/委外」→ `BUY/MAKE/SUBCONTRACT`；来源为空/未知且**有 BOM 子层** → 建议 `MAKE`（有维护 BOM 的件默认可自制，子层需求随之展开、可勾选，与主档为自制的父件同一行为）；空来源叶子 → `REVIEW`（前端 `MaterialSupplyRoute.fromWire` 得 null，只影响本条预填默认委外，不展开任何子层）。「上级路线不展开本节点」只在父件有效路线（确认值，否则建议值）不是 `MAKE/SUBCONTRACT` 时出现。空来源行的路线格旁有黄标「主档来源为空，请核对」（`UtenFieldHintIcon`），提醒默认委外只是缺省值，不是已决定。刷新（POST /preview）时若主档/BOM 事实真的变了（含来源真改），服务端清空该行人工确认并在刷新响应带 `routeResetCount`，页面横幅提示「N 条路线因主档变更需重新确认」；旧快照的 `REVIEW` 建议升级为具体建议**不算**事实变更，不清确认（ADR-029 §6.1 前向批注）。不做猜测性回填迁移：有 BOM 但来源为空的货品由计划部在货品主档补齐。
2. `GET .../last-routes` 按 100 个货品分块、限并发读取。会话主体/模拟身份、权限、分析 ID/版本/指纹与加载代际共同防止迟到 GET 覆盖手动草稿或另一份分析。读取期间禁止抢先确认默认值；失败明确提示核对当前路线，不声称已恢复上次选择。
3. 下拉只改草稿并选择对应真实任务。“确认路线(N)”只提交所选未确认或已修改组的各自实际值；根产品与子 BOM 使用同一 `materialLineId/actionGroupKey` 确认通道，不各建一套默认值。
4. **「路线说明(选填)」与「全选筛选结果」已于 2026-09-05 下线**（用户口径：准备页只保留逐行选择 + 确认路线）：路线确认不再采集原因（服务端 API 仍接受可选 reason，V477 的原因可空约束继续生效，历史 `route_reason` 原样保留）；批量选择走表头复选框（作用于当页，跨页靠翻页累积勾选，选择集全局保留）。表头工具条只留视图切换（缺料/全部 BOM/按产品/按物料）；查找框常驻顶部卡片「更新时间」右侧，表格全屏时经 `onFullscreenChanged` 回到工具条（两处共享同一控制器）。
5. 已有计划、有效供料行动或产出交接时根路线冻结；普通节点仍受既有下游状态守卫。409/刷新只保留仍属于原任务、且未被他人改变确认路线的草稿，不能静默覆盖服务端事实。
6. 打开页面、读取上次路线、切视图和轮询均不自动保存或下达。`last-routes` 的返回值只是预填依据，不是新授权；默认车间继续由 V192 学习。

批量确认先按 BOM 深度降序，ROOT_SUPPLY 统一最后，同深度按稳定身份排序，再每 500 项分块；后块使用前块新版本。这样顶层采购刷新停用原 BOM 时，已选组件的路线已先确认，不会让下一批失去目标；根委外则保留原树供前置自制。中途失败显示已完成量，未完成草稿保留，同键重试不重复计量。确认路线不等于下达任务。

### 3.5 顶层供料节点与产出交接

V478 为销售与合法手工来源提供真实 `ROOT_SUPPLY` 节点：`nodeRole=ROOT_SUPPLY`、`level=0`，没有父节点或 BOM 行。产品头以 `rootMaterialLineId` 引用它。普通节点为 `BOM_COMPONENT`；新旧节点、来源分析行和后续单据均以系统 UUID 关联。

- 根 `MAKE` 使用原产品分析行直接下达车间，不通过 notify 再造一个自制 child。**根路线必须显式确认为 MAKE 才能进车间桶与选入车间计划（2026-09-05 起与服务端 canSchedule 同口径双向闸）**：未确认的根与未确认的子层候选一样只留在主表（红色「路线待确认」、无勾选框），车间桶入口计数不含它；确认采购/委外的根只进各自路线桶。服务端对未确认根返回「根产品供料路线未确认，请先确认为自制再下达车间」并拒绝 issue-plans；无根节点的旧分析沿用旧合同（剩余量>0 即可排产）。`readyNowQty=0` 不等于禁止先下达待料计划。
- 根 `BUY/SUBCONTRACT` 进入对应供料任务，不留在未下达车间计划。供料仍使用既有 notify 权限、来源数量、仓库及采购/委外后续审批链；有子层委外继续遵守前置备料合同。
- 根库存/供给使用货品基本单位，计划输入保留原需求单位。例如需求 10 箱、1 箱 20 件，根表和供给为 200 件，计划输入仍为 10 箱；不能把 10 与 200 当同一种数量相加。
- 外部根供给的合格实收入库通过追加式 `preplan_root_output_events` 交接。销售来源将精确入库权益释放并转为销售预留；依法使用已分配存量的销售根也需显式命令。手工来源不能仅凭公共现货写出一笔无来处的完成事实。
- `root_fulfilled_qty` 从 FULFILL/REVERSE 事件按冻结换算率投影，不能直接改数。收货反向必须匹配原切片；已进入拣货/发货的销售预留不允许直接红冲入库。

V478 不在迁移时批量改写旧分析路线。旧记录的根指针初始为空；新建或授权刷新才补真实根节点。旧响应的根区域只读兼容，既有子 BOM、历史单据及旧排产入口仍按原合同处理。详细约束和待验收边界见[V478说明](../数据迁移/94-V478顶层供料路线与产出交接.md)。

### 3.7 统一流程词表（2026-09-06，全站唯一口径）

「进度 / 待办」的状态文案只允许来自**一份词表**：`lib/features/production/models/production_flow_stage.dart`
（展示组件 `production_flow_stage_cell.dart`）。物料分析主表、三个分桶详情、我的车间任务、

- **物料行（BUY/委外/自制子件锚点）**：服务端 `MaterialAnalysisFlowStageService` 按真实单据链
  批量推导 `MaterialView.flowStage` 键（下单/审批/收货/IQC/入库沿 `preplan_supply_actions →
  订货 → 审批 case → 收货 → 检验`)。**入库齐套权威口径**：V490 后本批需求不随下达归零，
  缺口只扣合格库存、精确权益及本批正式领用覆盖。整批下达只改变计划容量与在途责任，
  不能宣称已入库；历史归零行仍沿单据链逐步判定(未下单=
  等待采购下单 → … → IQC 全部合格且仓库实际入库才算已入库；全部不合格=原订单补货通道
  等待补货到货），修复了「采购未下单却显示已入库 / 进度弹窗跳步直达已完成」；弹窗内的逐步
  时间线（supply-progress）与阶段服务读同一批单据事实、同一口径。
- **2026-09-07 部分到货/验收/入库收口**：同一申请明细分批下多个订单时保留全部订单，不以最后
  一张覆盖此前财审或待检事实；收货明细使用真实receipt_item.id关联IQC，并保留order_item_id
  谱系。任一已收货明细缺少检验事实或仍待检，继续等待IQC；合格量大于实际入库量时显示等待入库。
  合格部分虽已全入库但本批仍有shortage，采购等待到货、委外等待回厂，不能标整批已入库。
  历史required=0行须逐订单明细证明收货检验完成、合格部分全部入库且覆盖订单基本量；某订单超收
  不能覆盖另一订单未到货。需求仍在本批且shortage归零的真实库存/权益覆盖口径保持不变。
  全部事实仍按分析批量查询，没有新增逐行HTTP/SQL，没有新增前端状态键，也不把未来到货当现货。
- **执行段 / 顶层产品**：`ProductionFlowStage.forSegment/forProduct` 就地推导（执行段状态 +
  零料标志 + 报工/计划数量，报工量缺失时回退入库完成比，绝不发明 0%）。

### 3.8 父件 + 下层一起下单（2026-09-14 修订二：**整页**·前置，[ADR-081](../99-决策记录-ADR/ADR-081-下层一键办齐与物料表身份列统一.md)）

在分桶页点「创建生产计划（车间桶）/ 下达委外（委外桶，有子层行）」时，若被下达件沿 BOM 还有**没下单的下层**，直接**进入整页**「下层还没下单，跟父件一起办」——父件还没提交，树顶是本次要下达的件（只读，本批数量就是驱动量），往下用与准备页**同款的树组件**（`UtenTreeTableCell`：缩进 + 层级连线 + 展开/收缩箭头 + 未展开子数徽章）逐层列出子层 / 孙层，下单数量已按本批数量算好可改；点右下悬浮组「一键下单」才按序提交：**先父件（车间 `issue-plans` / 委外 `notify`），成功后按最新快照重建下层行并继承已填数量与勾选，再按路线分流办下层**。全部下层都已下单 / 已被现货覆盖时**不进页**，父件按原路直接提交。（第一版为 AlertDialog 弹窗，用户口径「弹窗看的东西太少，直接去新的页面」；再前是「先落库父件、成功后再补弹」，即用户口径「还没确认就把父件下了」，两轮均已改。）

- **数量口径**：`毛需求 = 本批数量 × 本节点单位耗用 ÷ 驱动件单位耗用`；`建议下单 = 还可下达（服务端口径：本批缺口 − 已在途）+ max(0, 毛需求 − 快照需求)`。第二项就是**超量下达多出来的那部分**——V577 / ADR-070 §2.7 下超产不会自动抬高下层需求（锚点行不展开自己的 BOM、父件计划产出按物理缺口封顶），快照里根本没有这段需求，只能在这里按 BOM 算出来补。没有超量时第二项为 0，建议值与各桶的默认下达量逐字相等。
- **展开边界**：只穿过自制与「有自制子层的委外」节点；采购节点与无子层委外节点下单即止。最多 10 层 / 300 行，超出明确提示截断，不静默丢行。本批一起下达的行互为「已安排」——同时下达 P 和它的自制子件 C 时，C 以下的料由 C 自己那条驱动，不被 P 重复展开。同一 `actionGroupKey` 在树里出现多次时只有第一处可填数量（毛需求合并累加），其余行只作层级上下文。
- **数量可改，改上层带动下层**：改动某个「下达车间」去向的行时，它下面**没被手工改过**的行按新数量重算；手工改过的不被覆盖。父件提交后重建的行同样继承用户已填数量 / 车间 / 负责人与勾选；被父件顺带办妥的行（如委外前置自制任务接手的子件）自然变成「已下达」退出提交，并在结果里点名「已随父件下达办妥 N 行」。名称列的展开/收缩只切换可见子集（行对象与已填内容不动，折叠行的勾选随之撤掉——看到的勾选=提交的内容），页面正常上下滚动。
- **一键下单按路线分流**：采购 → 下达采购；无自制子层的委外 → 下达委外；自制与**有自制子层的委外** → 回到下达车间（`issue-plans` 一次原子调用：服务端同事务建前置自制台账 / 锚点、逐行出计划、按权限同事务审核）。表内显示路线与已确认路线不一致的行在第一步一并确认路线（提交前二次确认点名「其中 N 行会先确认路线」）。
- **基础需求已下过单的下层行（已下单子件）**：超产多出来的量按申请进度分流——先查 `GET /{id}/supply-links`（只查「还可下达=0 且本批有超产量」的行，每行取最近一条未撤销下游动作）：申请**未分解出订货单**（已审核、明细无已订货量且无待财务审核占用，与 V477 `adjustItemQty` 守卫同口径）→ 状态显示「已下采购申请 PR-x（未分解）· 并入 20 → 40」，提交时把**同一张申请的明细数量改大**（`PUT /purchase/requests/{id}/items/{itemId}/qty`，权限与守卫由该端点自裁）；**已分解出订货单 / 委外申请** → 状态显示「已下单 PO-x · 追加 X」，提交前二次确认明确问过「按『追加』另立申请」，通过 notify 超量通道生成追加申请（需 `over_supply`）。联动加载失败不阻断，按无联动的普通超量口径展示。
- **不是一个事务**：各下达路径各有自己的校验、幂等命名空间与回滚边界（ADR-080「明确不做」表拒绝合并成一个事务的理由仍然成立）。这里做的是**有序编排 + 逐段如实回报**：任一段失败立即停下并写明停在哪一步、哪几段成功了几行，已成功的段保留在服务端（幂等键可回放，重试不重复建单），表内数量按最新快照重算后留在原地供重试。**失败重试不重发父件段**——首次提交后快照已换版本，重发等于新幂等键真实重复下单，重试只办剩余段。
- **权限与边界**：采购 / 无子层委外超过「还可下达」的部分走公共超量通道（`qty` 归本需求 + `publicExtraQty` 公共备货），**需要** `over_supply`；没有该权限时按余量封顶并写明「超产多需 X，无超量下达权限未计入」，不静默改小（可并入申请调量的行除外——走采购侧 sanctioned 入口，权限由该端点自裁）。下达车间去向的行按 V577 可超量，**不需要**额外权限。主档来源为空、路线只能兜底委外的行不允许在这里替人确认，提示「请先在主表确认路线」。

## 四、计划、齐套与执行门禁

### 4.1 三类数量与先下达车间

`canSchedule / maxSchedulableQty / scheduleBlockedReason` 是排产资格；`readyNowQty` 是当前可完工入库的完整齐套量。两者必须分开。

| 指标 | 含义 |
|---|---|
| ready_start | START 阶段的分析参考，不证明已领料或可以实际开工 |
| ready_finish / readyNowQty | START + ASSEMBLY + FINISH 硬门槛完整齐套量 |
| ready_ship | 增加 SHIP 参考物料后的预计可发提示，不作为实际发货授权 |

`SHIP/REFERENCE` 不写正式生产需求、reservation 或 DRAW。确实在生产消耗的包装材料应放到 FINISH，并按 `PER_UNIT / PER_PACKAGE / FIXED_BATCH` 逐边计算、向上取基本单位四位小数，不能平均单耗近似。

例：需求10、现货只齐6套，计划侧仍可下达剩余需求10；审核按真实齐套形成READY/WAITING执行份额。对于已下达且符合拆批资格的WAITING段，车间可以通过“分批领料”再明确安排完整子批：原需1000件、现货能配齐10件时先办10件，余990件继续保留。拆批保留原数量与来源谱系，不是把原单直接改成10。已有领料、报工、正式供给绑定或人工暂缓等限制由服务端解释；不能任意重写所有历史段。见[ADR-078](../99-决策记录-ADR/ADR-078-完整子批生产与实际用料余料退仓.md)。

### 4.2 审核、领料与通知

`generate` 只允许创建草稿、ACTIVE planning draft 与 SUBMITTED 来源关联；`approveNow` 还需独立 `production_plan:approve`。审核事务按真实齐套拆分 READY/WAITING，保留精确销售已排量和独立来源。

WAITING可在车间任务中持续跟踪。完整齐套后，服务端同事务执行精确权益转正式预留、完整库存分配、生成内部DRAW并提升READY；此时通知车间去领料。车间在汇总页明确提交后，仓库才收到对应“已申请未发”数量的任务。进入详情、预览、刷新或收到通知不等于提交领料。逐行申请与仓库额度见[ADR-077](../99-决策记录-ADR/ADR-077-车间明确提交领料后进入仓库任务.md)。

READY只证明本执行批齐套和预留。DRAW审核不代表实物交接；本执行批正式需求全部FULFILLED后才能明确START，不能把原1000件任务只领10件的材料就直接开工。先拆出有完整套料证明的10件子批，再领齐该子批即可生产。重复通知不代替业务事实；重复命令使用幂等键，旧版本/旧指纹失败关闭。

### 4.3 完工、委外与反向

报工只引用 IN_PROGRESS 执行段。日报审核记录完工申报，FQC PASS 后仍须仓库逐行点收，只有实收量增加库存和 `iqty`；完成率按有效 `iqty / qty`，不是报工量、齐套比例或工资。

有子层委外先内部完成目标件，合格实收进入前置任务专属预留；满批或显式分批后再通知委外。该入库不能提前满足原生产需求；委外回厂经 IQC 和仓库实际入库后才成为原需求合格供给。参见[ADR-062](../99-决策记录-ADR/ADR-062-委外先自制后通知与分批通知.md)与[ADR-046](../99-决策记录-ADR/ADR-046-生产领料仓库点收报工归属与未来计件边界.md)。

取消/红冲走专用命令，不能通用改写已外部化 action、申请、订单、领料、报工或来源分摊。未执行的取消按权益切片恢复；已有真实执行则要求先完成精确反向。历史单据、origin 与物理库存流水不被本轮 UI 或刷新改写。

撤回下达（action CANCELLED）或根产出红冲后，行重新可编辑，但服务端**不清** `confirmed_route`（撤回只作用于 action，不作用于路线确认事实）。主表按 §3.2 的勾选谓词，这类行不可直接勾选：需改下拉（或改成另一路线再改回）形成脏组才恢复勾选与「确认路线(N)」计数——避免回到「勾了不计数」（2026-09-10 口径；若日后要求「撤回后可直接重新确认同路线」，须同时放宽 `_routeGroupSelectable` 与提交门）。

### 4.4 默认车间、打印与合单边界

默认车间唯一来源为 V192 `production_goods_workshop_preferences`；正式确认/合法改派才学习，打开页面、改草稿或取消不学习。默认负责人来自该车间组织树负责人，预填需核对，不能替代服务端组织资格校验。无 BOM 自制件沿已有 ZERO_MATERIAL/DIRECT_MAKE 证据，不造空需求或空 DRAW。

当前仍是一分析行对应独立计划单；同车间批量输入不等于物理合单。共享计划头需另行迁移精确 plan_item 来源桥及取消、报工、入库守恒，本轮未实施。只读备料计划汇总单 (`/production/material-analyses/{analysisId}/summary`)不调用 generate/notify；正式打印使用真实 planId/packageId/segmentId，不把 WAITING 的无 DRAW 描述为无物料自制。

## 五、数量、权限与接口

## 六、大批量与验证边界

- 界面按分析快照缓存、复合节点索引、分页和增量装载，避免一帧构建全部产品/物料 Widget。
- 新版客户端在详情及13个返回整份分析的命令入口显式协商 `projection=shared-warehouses-v1`；`MaterialAnalysisResponseProjection` 将每个稳定 `materialKey`（货品UUID/颜色UUID/单位UUID）的全仓快照集中到 `warehouseBreakdownsByMaterialKey`，节点的分配/缺口/权益字段各自保留。客户端每维度解码一次不可变列表，零库存仓、9个仓库数量和可空日期都保留。无协商参数的旧客户端继续接收节点内联 `warehouseBreakdown`；新版收到缺版本、缺维度、失效金额或重复仓库的共享格式时拒绝展示，不能默认为零库存。此优化不改命令请求体、版本/指纹、幂等结果和权限，也不跨请求缓存动态库存。
- 深层分配使用稳定优先队列；同一 nodeKey 在不同 analysisItemId 下隔离。已有完整套料优先保护，深层诊断只消费剩余公共量，exact 不重复扣减。
- 5000 产品/10000 节点、2000 份共享库存的两次纯计算样本约 0.390 / 0.503 秒；该样本超过前端单分析 500 来源上限，用于算法压力验证，不能当成数据库、HTTP、网络和渲染的端到端耗时。
- 同批委外 BOM 分流改为一次批量查询，验证 500 产品重复物料不产生逐行重复往返。
- 旧活动分析通过正常授权刷新重算新投影；历史来源、单据和已应用迁移不改写。旧接口保留兼容不意味着恢复退役 UI 或绕过新门禁。
- 打开已有分析只读 GET，并行加载公共字典，不自动调用 preview 重算整树。库存/BOM 需要重新计算时使用显式刷新；真实入库继续在同事务内唤醒相关分析。下达仍按服务端版本、指纹和 BOM 漂移校验执行，旧快照缺少根 UUID 时仍按只读兼容展示。
- `MaterialAnalysisBomSnapshotReader` 将每个来源的图校验和展开合并为整批两次查询，按分析行 UUID 保留独立路径、单位换算和精确计量；仍拒绝循环、超过十层、失效组件和单位/颜色异常。正式下达的直接层 BOM 快照也按选中来源批查。
- `MaterialAnalysisSupplyCoverageReader` 在命令写入前一次收集当前及历史行动组，按路线批量读取有效供给和已退回不合格的原单补货覆盖。500 个采购组的这部分读取为 3 次，不再逐组往返；申请、实收、权益、领料和退回保持来源 UUID；V554 将合并来源的待检/待补覆盖统一为累计区间差，避免把已在途数量再次下达。
- `MaterialAnalysisWarehouseBreakdownReader` 将各仓库主仓／可用标记及安全补货进度在本次读取内分别汇总一次，再按货品／颜色关联各单位维度。仍使用 V554 的真实来源进度与原专属权益计算；没有安全来源 UUID 才排除，不能以声明量为零丢弃历史来源，不跨请求缓存。
- 下达车间先按原请求版本、指纹与 BOM 快照校验，再在提交事务内重算一次实时库存分配，防止通用入库/出库未唤醒分析时沿用旧候选数量；随后复用同事务未改变的详情或委外通知已返回的详情；同物料维度的分仓汇总在一次响应内只算一次。该复用不跨请求缓存，不冻结下一请求的库存和权限事实。
- 计划循环内的材料/BOM 静态片段由 `MaterialAnalysisStructureScope` 在开闭边界完整比对，退出后才刷新最终投影。商业来源、来源行、计划、需求、预留和持锁范围仍逐次校验；任何漂移回滚整批。作用域绑定真实事务及单份分析，跨分析、新事务与独立计划入口不复用其数据。
- 大树节点和货品集合以一个数组参数传入数据库，避免 49,000 个展开节点经 IN 参数 padding 超过驱动 65,535 参数上限；仍按分析来源 UUID 与 BOM UUID 路径精确过滤，不以货品编号合并身份。
- 单个物料的已有现货覆盖与产品整体齐套分开。先保护所有完整套料，再以同一剩余公共池补各节点现货覆盖；C 需求 10,000、已有 4,000 而 D 仍缺料时，C 只需再安排 6,000，产品仍等待齐套。专属量不自动转借；跨计划调拨须经独立授权和精确来源命令。诊断覆盖不创建预留或领料，也不把 WAITING 变成 READY，见 [ADR-073](../99-决策记录-ADR/ADR-073-本批物料履约与同主仓分仓领料.md)。
- 采购与委外混合批量确认入库先完成全部实物、精确归属及正式履约写入，再由 `MaterialAnalysisSupplyWakeupService` 一次查询本批影响范围，每份分析仅刷新一次。任何错误仍回滚整批，不能以异步回执代替入账结果。
- 取消分析的原因在前端按 2–1000 字校验，并在输入框内反馈；服务端有关已下达计划、根交接、让料权益及版本的取消守卫继续有效。候选搜索采用最新请求代际控制，输入在旧请求执行期间变化时仍会发起新搜索，迟到响应不能覆盖最新结果。

- 专属在途调入通过 exact sourceAllocationId 选择原计划私有份额，并提交双方版本/指纹。成功后采用同一套原计划补供弹窗。主表及精确详情分别显示调入/让出、已实收、待实收与撤销量；只读账号用 VIEW_FUTURE_TRANSFERS 动作查询进度，写入口仍须 CROSS_REALLOCATE 和本地独立权限。查询失败表示进度未知并提供重试，不当作零。
- 专属在途记录可撤销尚未实收份额，已实收历史保持。弹窗显示本次恢复原计划与释放公共供给的拆分；有公共释放时必须显式确认，保留原计划已有补单，避免因补供完成永久锁住接受计划的未实收份额。最终数量与归属仍由后端事务核准。调拨、补供和撤销出现未知回执时冻结原数量/来源并同键重试，不能生成另一份补单。
- 已到待检或合格待入库仍可能是合法未来供给，界面不一律称为未到货。公共认领来源失败后，在供给行动列表以“撤回认领”调用原 actions/{actionId}/cancel，仅撤本分析认领，不撤原采购/委外单；该按钮须 claim_shared_future 权限，普通任务撤回须 notify，专属在途走自己的精确撤销记录。私有来源失败的 sourceSupplyShortfallQty/supplyWarning 在详情显示异常，保留原约定未实收量及合法撤销入口，不静默消失。

## 2026-09-13 跨路线在途调入、子层按计划产出展开与采购起订量

**一、三个调入入口对三条路线一致开放（ADR-080 / V574）**

- 「物料 / 调拨」里的三个按钮——从其他计划已入库中调入（现货让料）、从其他计划未入库中调入（专属在途）、从公共在途中调入（认领）——对采购、委外、车间（自制）三种确认路线的缺料行一致可用。匹配口径是同主仓、同货品 / 颜色 / 单位，不要求与目标路线一致，也不看子层级。
- 来源永远只能是别的计划**已下单未实收的外部份额**（采购或委外）。自制在制品、委外前置自制的半成品、正在委外商手上的料都不是最终件，永远不出现在候选里。
- 目标行必须仍生效、控制段不是发货段或参考段、路线已确认。候选列表与写入用同一套判定，不会出现「列得出来、存不进去」。
- 调入动作沿用**来源路线**落库（它确实是一张采购单或委外单的份额），单据号与进度链路照常显示真实来源单；但**分桶归属跟着目标行走**：自制物料上的一笔采购在途调入不会让它出现在采购桶，桶内「已下达量」也把这笔调入算进本路线，调入后可下达余量随之减少，不会重复下达。
- 公共在途认领此前按**目标**路线过滤候选，自制目标永远查不到来源；现在按来源路线（采购/委外）取候选，认领动作沿用来源路线落库。仓库口径与专属调入、与让料一致（同主仓）。「我方供料 BOM 的委外件不吃公共超量」这条原限制保留。
- 现货让料放开到第 1 层及以下的所有 BOM 组件层：深层子件（自制件、委外件的下层组件）之间也能互让。第 0 层根供给行不参与让料，它走自己的根产出交付通道。

**二、子件按父件「计划产出」展开（ADR-080）**

```
父件计划产出 = max(已承诺内部制造量, 物理缺口 − 外部最终件在途)
子件毛需求   = 父件计划产出 × 单耗
```

- 调入的在途到货就能顶上，不必为它备下层料；父件计划产出为 0 时，它整棵子树的未下达需求自动归零，不需要人一层层去删。
- 已经下达车间、已经建了前置自制任务的那部分是**冻结承诺**，它的原料一件都不会被在途挤掉。要少做，得由人去减量或撤回那张计划。
- 有效在途覆盖因此分成「外部在途」与「内部制造承诺」两类。两类之和等于原口径，所以主表的「尚需下达」数字口径不变；变的只是下层子件的需求量。
- **第 1 层与执行侧完全不动**：齐套、正式预留、领料、开工仍然只认真正合格入库的货。在途没到就不会提前变成可开工。

**三、采购起订量与订货倍数（V575）**

- 货品主档新增最小起订量与订货倍数（整箱 / 整包），都可以不填。
- 采购桶「下达数量」的默认值 = `向上取整到倍数( max(还需安排量, 起订量) )`，输入框下方一行说明「已按起订量与整包装抬至 X，富余 Y 归公共备货」。
- 这是软约束：计划员可以改小，服务端不硬拦。富余部分走既有公共备货通道，需要超量下达权限。
- **没有超量下达权限时不抬量**，默认只填净需求，并提示「本次 X 低于起订量 Y，需由有超量下达权限的人抬量」，不静默降级。
- 委外桶与车间桶不抬量——它们会产生下层责任，数量必须与需求一致。

**四、性能**

- 两条跨分析热路径（让料软占用、入库唤醒候选）按货品维度扫全库物料行，本轮补了 `(goods_id, color_id, unit_id, analysis_id) WHERE active` 索引；专属在途调拨表补了 `external_item_id` 索引，供采购 / 委外改单的 8 个守卫反查。
- 外部在途与内部制造承诺都按分析一次批量取回，子层展开仍是单趟遍历，不引入逐行查询。
