# V758 受控候选清理与稀疏清空

V758/686 是源码迁移目录头，不代表公司或本地导入库已经安装。此前 V757 演练记录继续作为该版本的历史证据；最终发布必须重新验证 V758 制品和快照。

V757 为报价模板候选增加 BEFORE TRUNCATE 清理，把未被模板版本采用的私有对象登记到保留的 `attachment_object_outbox`。V558 的保守算法遇到任何用户 TRUNCATE 触发器都会完整清空全部业务表，因此原本为空的表也重建文件，破坏了稀疏清空的性能合同。

V758 不改 V558、V747、V757 已应用字节，不执行清库，不改 CLEAR/PRESERVE 集合。前向迁移把同一候选清理函数的对象名和 search_path 固定，再精确识别它的表、触发器、函数体、调用参数、时机、配置及依赖边界。只有该函数仍仅向保留队列写清理命令，且队列没有额外触发器、规则、自定义类型/默认表达式/约束或索引函数等副作用时，才允许稀疏路径。判定中的未知值按不可信处理。

CHECK 和索引谓词按已知纯表达式逐项匹配。PostgreSQL 新建目录与 pg_dump/restore 目录对同一 varchar 数组转 text 的反解析有“整个数组转换”和“逐元素转换”两种写法；仅列出这两种等价形态，不做会吞掉额外函数的通用表达式归一化。

清库先锁完整 CLEAR 集合并精确计数；额外锁定清理队列及模板版本，防止检查和执行之间改变目标结构。非空候选仍进入 TRUNCATE 范围并执行真实清理；引用同一对象的已采用模板版本保留。空候选的受控 INSERT 无行、无额外语句触发器，因此可以跳过。任何其它 TRUNCATE 触发器、已知函数或配置漂移、队列附加副作用，仍执行原完整清空。传统继承、分区外键闭包、高隔离快照、权限检查、行安全、所有最终校验及事务回滚均保留。

运行时函数以失败关闭的唯一锚点替换，核对替换前后 owner、SECURITY DEFINER、search_path 与 ACL 完全一致。`server/ops/reset_business_data.sql` 使用同一算法，白名单追加 `(758, 686)`；旧目录不具备完整受控边界时继续走保守路径。

锁顺序以既有维护入口为前提：应用入口通过 `BusinessDataResetDrainGate` 排干 API 和 `DrainAwareTaskScheduler` 管理的定时任务，再执行完整 CLEAR 锁及候选清理依赖锁；手工 ops 脚本必须按原要求停止应用、定时任务和 outbox worker，并拒绝其它客户端连接。未知连接造成锁竞争时仍由既有 lock_timeout/事务失败回滚处理，不能跳锁继续，也不能把该优化用于在线绕过维护排干。

回归入口：`BusinessDataResetSparsePostgresTest` 保留空表 relfilenode、序列起点、分区、继承、未知触发器、RLS、高隔离和回滚断言，并增加已知函数被替换、配置漂移及队列副作用探针；`QuoteTemplateCandidateTruncateMigrationPostgresTest` 覆盖空库、V748/V757 升级、真实对象清理、保留引用、回滚、权限元数据与零迁移重放。`FlywayMigrationImmutabilityTest` 锁定 V558/V747/V757 历史校验和。
