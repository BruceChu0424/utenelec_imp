# 草稿恢复保存与分类合并修正

本次按用户实际反馈修复“恢复半填草稿后继续保存失败”，并将所有新建表单的填写草稿归入对应业务分类。没有修改业务数据库、重新创建用户现有单据或部署服务器。

## 保存失败的根因和修复

1. 自动保存与显式检查点同时等待一个已完成/将完成的写入，随后各自启动新写入器，带相同旧版本提交，产生同页面的 `FormDraftConflict`。新增回归先在旧代码复现，再用公共单写入器合并等待者，所有模块共用修复。
2. `completeFormDraft()` 后页面执行跳转时，`finally` 尚未清除 `_saving`；退出守卫先检查忙碌状态，反而拒绝保存成功的导航。现在确认完成优先放行，未完成的忙碌操作仍禁止退出。
3. “单据已经创建”被误当成“附件上传失败”。提示改为观察实际失败附件；创建后的本机检查点失败不会冒充业务创建失败。已创建记录复用原 ID，表头/明细锁定，继续完成附件或进入原详情，不重复建单。

公共修复位于 `form_draft_mixin.dart`，确认创建检查点使用 `checkpointFormDraftAfterCreation()`。保存前仍严格等待可持久化检查点；等待期间身份变化则不以新账号提交旧表单。

## 草稿分类

- 销售订货进入“销售任务中心 → 订货进度 → 草稿”；出货、客户发货、退货、报价分别进入自己的草稿状态。
- 采购、委外补齐任务中心草稿分类，再按具体单据类型查看；原有业务草稿与未提交填写共用列表。
- 财务五类单据、报销、日报、手工库存单据归入既有草稿状态；资产和待摊使用各自 DRAFT 状态。
- 车间申请、仓库入库/出库/领料填写、资料/资产政策等原无状态入口的业务增加草稿分类，混合创建类型在草稿分类内再分子类。
- 人事、研发、品质、通知、建议和基础资料均提供对应草稿类别；删除工作台及分类上方的独立草稿面板。`lib/features` 已无 `FormDraftsPanel` 使用。

`FormDraftCategoryTable<T>` 保留真实业务 DTO 和原业务操作，填写草稿使用独立行类型。选择、删除、恢复不把本机 ID 传给业务接口；已创建 ID 对应的恢复记录覆盖原行入口，不多列一行或多计一个业务草稿。分类徽章、筛选与行范围共用同一投影；客户/供应商/币种使用当前选择的 UUID 和已加载名称缓存，价格学习上下文不当成当前选择。

## 验证

- 本次合并回归集合 **124 项通过**，含实际“任务中心 → 草稿 → 恢复 → 补填 → 保存 → 详情”路径、12 种商业单据分类、正式/本机同表、删除、去重、错误提示、空分类、离线列表、筛选及权限架构检查。
- 另有生产/库存/车间相关 **84 项**、资料名称投影 **4 项**等定向回归通过；这些集合与其他测试可能重叠，不合并宣称一个总数。
- 公共保存生命周期最终 **14 项通过**，包括重叠保存冲突复现、完成导航、提交前身份切换等。
- 相关源文件和测试静态分析 `No issues found`，格式及差异检查通过。
- Web release 构建通过，输出 `build/form-draft-category-check`；仅本地验证，未部署。

本次没有重跑此前已记录有无关失败及临时截图阻塞的全项目测试，也不将工作区宣称为全绿。持久化仍是当前设备/浏览器的草稿；既有本机草稿的存储结构和恢复身份保持兼容。
