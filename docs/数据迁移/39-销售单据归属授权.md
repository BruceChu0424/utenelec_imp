## 一、老库取证

- 归属源 = `seller_legacy_id`（老库 S_Order/S_Out/S_OtherOut/S_Withdraw.Emp_ID，已随单据迁移在库）。
- 分布（订货单）：尹志斌 1971 · 张龙 1753 · 苏君丽 854 · 王浩然 356 · 朱德洪 232 …
- 报价单没有独立 `owner_employee_id`；当前服务端统一把 `maker_id` 作为报价有效 owner。
  老库报价源当前为 0 行；若以后发现历史报价，必须先证明 maker 映射，不能默认全员可写。

## 二、设计（同模型三件套 + 中间档）

| 件 | 设计 |
|---|---|
| `owner_employee_id` × 4 表（V91） | 订货 / 出货 / 其它出货 / 退货；NULL=公共 |
| 报价 owner | 不新增 owner 列，使用 `sales_quotes.maker_id` |
| 权限点 `sales:view:all`（V91） | 「查看全部销售单据」 |
| 数据范围 `user_data_scopes` scope='sales'（V91） | 中间档：权限管理页按人勾选「销售单据可见业务员」 |
| 查询与对象守卫 | 列表范围与详情/更新/删除/审核/红冲/驳回/批量入口均按服务端 owner 语义检查；最终覆盖以测试矩阵为准 |
| 公共历史单 | `owner_employee_id IS NULL` 仍可读；普通用户所有写操作返回 403，只有全局授权主体可处置 |
| 新单 owner | 报价取当前员工 `maker_id`；订单取当前员工或从报价继承；出货/其它出货从订单继承；退货从出货/订单继承；同时校验客户和 owner 一致 |
| 批量出货 | 必须按 `customer + owner` 分组，禁止把不同 owner 的上游行合成一张单 |
| 归属迁移 | `migrate_sales.sql` 先保留 `seller_legacy_id` 并让四表 owner 为空；随后 `migrate_sales_owner.sql` 用 `seller_legacy_id→employees.legacy_id` 回填。`--bootstrap-all` 已按此顺序调用，单跑 `--sales` 不等于归属完成 |
| API 可写契约 | 五类单据列表/详情由服务端返回 `writable`；出货另返回 `canReject`，可发行返回 `writable`。前端只按这些字段显隐动作，不根据当前用户/owner 自行猜权限 |
| 报表 | 明细/汇总/facet/导出/月报/待交货按有效 owner 服务端过滤；V137 月报 MV 含 owner 维度，NULL 公共行以 nil UUID 表示 |
| 退货质量操作 | 普通 `sales_return_quality:view` 仍按退货 owner/委派范围读取；已知退货 ID 的质检 GET/POST 在对象策略调用层使用专用 `sales_return_quality:handle` 旁路。当前没有独立跨 owner 任务列表/最小投影，完整退货详情仍按普通 owner 范围保护；方法鉴权组合和 handle-only 负向也待收口，不得称为 PMC 任务闭环 |

迁移脚本还会让已链接的出货/退货继承上游 owner；若一张下游单关联到多个不同 owner，会直接
`RAISE EXCEPTION`，禁止任意选一个归属。owner 回填事务提交后必须执行
`refresh_sales_monthly_mv()`，避免 `--bootstrap-all` 先刷新 MV、后回填 owner 时把已归属聚合暂时
留在 nil UUID 公共 bucket。上述是当前脚本规则，仍须用完整快照做冲突负向测试和对账。

Flutter 已按该契约收口：列表/详情解析 `writable`/`canReject`（字段缺失时 fail-closed 为
`false`）；编辑、删除、审核、红冲和驳回分别按服务端能力显示。直接打开不可写对象的 edit URL
会回到只读详情，批量发货的全选、勾选、数量编辑和提交都会排除 `writable=false` 的来源行。
模型契约定向测试 2/2 通过、相关 analyze 0 issue；仍须用真实 API 覆盖越权响应和路由竞态。

## 五、边界

- 报价使用 `maker_id` 作 owner；通用销售明细/汇总/facet/导出/月报/待交货已按同一有效 owner
  策略隔离。finance 专用跨 owner 报表及生产/MRP 消费方仍须独立产品决策，不能自动套用。
- 销售出货/退货编辑页的「从上游引入」候选列表受范围过滤；这只能防止 UI 正常流程选到越权单，
  不能替代后端对请求中的上游行 ID 和目标单据 ID 再做对象级授权。
- `sales_return_quality:handle` 属高风险操作权限，默认只给 PMC 处置岗位并须完成真实账号职责分离复核；它不自动授予销售退货编辑、红冲或其它销售单据全量权限。现有 owner 边界测试只证明单退货质检 GET/POST 会调用该操作旁路；独立任务发现、view/handle 组合、handle-only、已知 UUID 返回投影和页面深链仍须服务端与真实账号正反向验收。
- 正式迁移必须执行 `migrate_sales_owner.sql` 并生成回填/落空对账。若
  `seller_legacy_id→employees.legacy_id` 无法映射，单据保持公共只读并进入 reject/业务分配清单，
  不得为了可操作性随意归给当前导入人。
