# FQC 结果未知交互修复建议

状态：只读定位与实施建议，尚未修改或验证该写路径。

`lib/features/quality/pages/production_fqc_handling_page.dart:490-504` 对所有 `ApiException` 使用“登记被拒”提示。但 `lib/core/network/api_exception.dart:35-36` 中网络超时异常也继承 `ApiException`，因此响应丢失并不能证明事务被拒绝，界面当前会把两种事实混淆。该页面已持有逐行原幂等键、冻结的提交参数、成功行状态和草稿保护，应保留这些机制。

建议独立落实：

1. 提交结果明确区分已确认成功、已确认业务拒绝、结果未知。HTTP 超时、断连及不明确的 5xx 都进入待核对；只有可证明事务未生效的业务拒绝才显示“被拒”。不能仅按所有 4xx 或 5xx 机械分类。
2. 每行保留原请求键与冻结参数。结果未知时先只读核对该次命令或对应决定事实；不能因一次 GET 仍是待检就推断原事务不再会提交。
3. 已完成行不再提交；可证明未执行的行才以当前版本继续。必要重放必须使用原键原参数，服务端先证明同键回执不可变。页面统一显示完成、被拒、未执行、待核对，并说明下一步。
4. 保留办理页逐行独立提交、首错停止和先前成功；不能把此页静默改为 `passAll` 的全批原子合同。品质数量、处置原因、附件、责任人与权限在同一次命令中核验。
5. 回归至少覆盖：400/422 业务拒绝、提交前断网、服务端提交后响应丢失、500 不明结果、核对请求也失败、仍在处理的旧命令、退出重进恢复、权限撤回，以及原键重放不会重复决定或生成入库。

这项工作应接入 R1 的持久命令回执与截止时间合同后独立验收。单纯替换提示文字不能作为完成证明。
