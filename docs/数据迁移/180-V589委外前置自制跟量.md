# V589 委外前置自制跟量：台账承接车间超量下达

- 迁移：`V589__subcontract_make_task_follows_overquantity.sql`
- 类型：前向，替换一个触发器函数体 + 放开一列 NOT NULL。**不加表、不改历史行。**
- 相关：[V588 分析超量单计划与销售分摊放宽](179-V588分析超量单计划与销售分摊放宽.md)、
  [ADR-062 委外先自制后通知](../99-决策记录-ADR/ADR-062-委外先自制后通知与分批通知.md)

## 为什么要有它

用户实测口径：「顶层要做 5000、委外是他的子层级，那委外件就需要 5000，不然不够
生产 5000 个。」前置自制的产出必须经委外加工才能用于装配顶层——V588 之前「台账
required 恒等于剩余需求、超产部分入库不送委外」会让超产的顶层永远缺一颗未加工的
委外件（死料）。

同批用户还报了一个 V588 引入的回归：**超量 > 需求**（需求 1000 实下 5000）时
「一键下单」409「销售订单剩余可排数量为负」——单计划把公共备货也带上了销售来源，
审核前的二次校验把整张草稿当成销售容量占用（`剩余可排 = 需求 − 超量`）。修复在
Java 侧：`loadSourceLines` 与销售候选三处 LATERAL 的草稿容量只记分析 link 的
`submitted_qty`（归需求量），公共备货产出不占订单可排量；E2E
`salesTopOverQuantityLargerThanDemandStillIssuesSinglePlan` 锁定。

## 委外链跟量的记账（V589）

- **ARRANGE（下达车间建台账）**：行动记 `requested_qty`=归需求量（锁）+
  `public_surplus_qty`=车间腿超量；台账 `required_qty`=两者之和；台账行
  `requested_qty`（需求侧）仍只记需求量。增量下达时 required = 行需求量 + 未撤销
  前置自制行动的公共量合计。人工「下达委外」通道不变（整量接管、禁公共超量）。
- **通知批**：申请明细是整批数量一条；批行动只锁归需求份（先消费需求份，余下为
  公共）：requested=需求份 + public=公共份，公共明细锚指回同一条申请明细（V588
  的合并明细形态）；纯公共批不建需求 allocation。
- **分析投影**：通知批生成后台账（ARRANGE）行动被批行动取代——`downstreamReferences`
  的 allocated_qty 与 `supplyActions` 的总量/公共量对被取代行动归零，避免双计；
  撤回通知批后自动恢复。
- **回厂入库**：归需求份覆盖本分析缺口，公共份按公共备货入库（公共供给捕获的
  「同件超量」口径）。「我方供料 BOM 委外件不吃公共超量在途」保留：公共份在途回厂
  前不能被他分析认领，入库成公共库存后可以。

## 改了什么（数据库）

1. `fn_guard_preplan_public_surplus_shape` 两处锚点替换（行尾归一 LF）：
   - 「SUBCONTRACT 公共超量必须叶子货品」改为只拒 `fn_subcontract_sole_component_goods`
     （ADR-085 单一叶子子件件）；前置自制件的公共量随车间超量产生，放行。
   - 外部化公共量必须锚申请明细——`SUBCONTRACT_MAKE_TASK` 外部化时还没有申请
     （通知批再落明细），仅这一种形态允许公共明细锚为空。
2. `preplan_subcontract_make_task_batches.allocation_id` 放开 NOT NULL（纯公共批
   没有需求 allocation；守卫与对账只看 notify_qty，无人读该列）。

## 兼容性

- 历史台账/行动一个字节不改；required 仍等于历史需求（无公共量）。
- 超量只从下达车间（含级联页）进入；人工下达委外的行为与校验原样。
