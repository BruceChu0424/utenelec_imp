## 一、背景：用户的核心疑问

销售下了订货单，仓库**有现货**时该走什么流程？V90 已实现“审核即订单有效预留 + 部分预留 + 取消释放 + FIFO 消耗 + advisory lock 防超卖”的主链。这里的有效预留减少 ATP，但不扣在手、不指定库位/批次，也不表示仓库已拣货。V178 当时针对三个尾巴收口：

1. **"一直保留别人又不要了怎么办"**——预留没有生命周期，货会被无限期占着。
2. **"只有一件，是有限给他还是让他让出来"**——稀缺时多订单抢同一份库存，无仲裁。
3. **安全库存**——销售可用量口径没扣安全库存，能把库存预留到 0、吃进缓冲。

并附了一份大而全的"方案"（含 7 天有效期+续期、VIP/促销优先级、自动抢占软预留、优先券、批次召回等）。

## 二、关键判断：制造业 ≠ 电商，方案过拟合一半

研究报告（SAP/Oracle/D365 官方文档交叉验证）核心结论：

| 用户方案条目 | 专业做法 | 采纳？ |
|---|---|---|
| 7 天有效期+2 次续期 | 专业系统通常按需求日期、计划日期和业务策略管理承诺，不宜把所有制造订单统一成“创建后 7 天” | ❌ 7 天倒计时 → ✅ **交期驱动** |
| 草稿/提交=软预留可被自动抢占 | 当前销售订单没有独立提交态，草稿不占 ATP；审核后的订单承诺若要重排，必须按业务优先级、影响清单和权限处理；已拣/已领/已出数量不可直接抢 | ❌ 自动抢占 → ✅ **手动让单** |
| VIP/大额/促销优先 + 公平份额自动 | SAP APO Allocation 的高流量分销场景；制造业客户价值差异靠人工判断 | ⏸️ 仅加 priority 字段+排序，不做自动 fair-share |
| 未来到货做"未来预留" | SAP backward scheduling + planned receipts（PO/生产订单/ASN 作 ATP 来源） | ⏸️ 生产侧已有"预计齐套日"，销售侧透出留后续 |
| FEFO/批次召回 | 需批次管理主数据 | ⏸️ SOP §八已标"需老板拍板"，无批次数据 |
| 安全库存从可承诺量扣 | 可承诺量必须与公司的安全库存/供应保护规则一致，且多仓不能只在全公司合计上扣一份 | ✅ **采纳（对齐生产侧）** |

> **结论**：采纳安全库存扣除（缺口 C）+ 交期驱动的预留生命周期（缺口 A）+ 手动稀缺让单（缺口 B）；**不做** 创建后固定 7 天倒计时、自动抢占、按订单金额自动优先。批次召回与 MTO 专属库存需要主数据和架构支持，不能在 V178 假实现。

## 三、三个缺口的落地设计

### 缺口 C：安全库存进销售 ATP（对齐生产侧，最小且修 bug 性质）

**当时的 bug**：销售 `globalAvailableBase = 账面 − 生效预留`，**不扣安全库存**；生产侧另扣安全库存，两侧口径不一致，销售能把库存预留到 0、吃掉缓冲。后续又发现多仓不能在全公司汇总后只扣一次货品级安全库存，否则仓数越多越容易稀释缓冲。

**当前落地**：`StockReservationRepository.globalAvailableBase` 先对每个存在该货色余额的仓计算 `GREATEST(仓余额−goods.min_qty,0)`，再合计并扣一次全部生效预留；查询和调用点均钳为非负。

```
销售可预留量 =
  GREATEST( Σ每个有货仓 GREATEST(仓账面 − 货品安全库存, 0)
            − Σ生效预留, 0 )
```

**数据安全要点**：
- `globalAvailableBase` 是销售审核与改量增量的跨仓承诺口径；生产和仓库仍按自己的仓级可用/可拣口径读取，不能把全局值当某一仓可拣量。
- 调用点已有 `.max(BigDecimal.ZERO)` 钳位，扣安全库存后不会负数预留。
- 安全库存 `min_qty` 仍是货品级、没有仓/颜色配置。当前按每个存在该货色余额的仓保护一份，是 fail-safe 公司口径；上线前须由业务签字确认是否需要改成“货品×仓”主数据。
- **不动存量**：只改查询，不建列、不改既有预留行。
- 部分交接时，`consumeForOrderItem` 只将本次消耗拆为仓级已消费行，剩余有效量复制为新的全局行；总量守恒，避免首仓绑定吞掉其余仓履约能力。

**dev 库实测**：货品 V51022 账面 92850 < 安全库存 200000 → 可预留量 = 0（正确保护缓冲，且与生产侧一致）。

### 缺口 A：预留生命周期（交期驱动，notify-only）

**设计**：`stock_reservations` 加 `hold_until TIMESTAMPTZ`（可空）。**null = 用默认（订单交货日 + 宽限期）动态算**——不做回填、交期改后自动跟随、不会过期（对齐 SAP 按需求日期 BDTER）。非 null = 大客户长单等自定义覆盖。

**持有截止** = `COALESCE(r.hold_until, 订单交货日 + HOLD_GRACE_DAYS)`，`HOLD_GRACE_DAYS = 7`（`StockReservationService` 常量，详情逾期计算与调度器共用，口径一致）。

**过期扫描** `ReservationHoldScheduler`（每日 08:37，镜像 `DeliveryDueWarningScheduler`）：
- 扫"有生效预留 + 持有截止已过 + 订单未结案/未中止/未发完"的订单，通知归属销售（TYPE_URGENT，同订单同人同日去重）。
- 与交货前 3 天的延期预警**互补不重叠**：那个管"快到期"，本扫描管"已过交货+宽限期仍占着货"。
- **默认只通知、不自动释放**（数据安全铁律）：自动释放须同步回写 `sales_order_items.reserved_qty/chain_status` 才不库存漂移，该编排留后续 opt-in。真释放走既有 取消/改量/手动让单。

> 逾期提醒是本公司的运营补充能力。它不替代 ERP 的需求日期、重排或取消规则，也不据此宣称优于任何专业系统。

### 缺口 B：稀缺仲裁（priority + 手动让单，不自动抢占）

**设计**：`sales_order_items` 加 `priority SMALLINT NOT NULL DEFAULT 3`（1 急单 / 2 普通 / 3 现货）。source of truth 在订单行。设急单需 `sales_order:priority` 权限 + 原因 + 审计。

**手动让单** `yieldReservation`（`sales_order:reallocate` 权限）：主管释放某低优先级订单行的部分/全部现货预留 → 库存回池 → 该行 `chain_status` 回退待计划 → 通知其归属销售。释放出的缺口进入计划需求池，由计划员按 MAKE/BUY/SUBCONTRACT/TRANSFER 和已有未来供给处理，不能一律自动转生产。**不自动给急单预留**——急单仍须经过正常的有效预留入口。

**数据安全**：`releaseForOrderItem`（FIFO + 行锁 + advisory lock，既有原语）+ chain_status 回退 SQL **逐字镜像出货驳回 `SalesShipmentService.reject`**（已生产验证范式）+ `WHERE reserved_qty >= :q` + `updated != 1` 抛错 → 防吞并错账、防负数。yield 只动现货预留，不碰 `plan_order_item_links`（让出现货、保留其生产承诺）。

**稀缺面板** `scarceReservations(goodsId, colorId)`：返回该货品+颜色的全部生效预留 + 订单上下文 + 持有逾期天数，按优先级升序、创建时间升序排列（急单在前、先占的在前），供主管判断让谁、让多少。

`priority` 只是主管判断输入，不是自动取得库存的权利。建议实际仲裁依次考虑法规/售后停线、已承诺且临近交期、合同保护、已付款或定制不可取消、最早承诺日，再在同级内看订单年龄；订单金额不能单独决定优先级。数据库事务只负责防超卖。

> **当前保护**：任一未删除、未驳回的出货草稿已经占用订单行可发额度；订单改量、取消/红冲、让单和客户确认撤销都会被服务端阻断。`PICKING/PICKED/EXCEPTION` 还禁止直接编辑、删除和驳回，必须先登记异常并用原因恢复待拣。该保护按订单行生效，但尚不替代库位/批次/实拣数量台账。

### 尚未落地的完整现货履约 P0

1. **订单级发运策略（V187 最小闭环已落）**：`ALLOW_PARTIAL / REQUIRE_COMPLETE / CUSTOMER_CONFIRM` 由服务端在建任务和开始拣货时复核；客户确认保存人员、时间、原因，改量/取消/红冲会清空。`REQUIRE_COMPLETE` 当前保守要求一张出货单覆盖该订单全部未交行；发运组、最小分批量、运费/装车约束仍待配置。
2. **发运时间栅栏**：审核时做全局订单预留；接近计划发运日才绑定具体仓库/批次/库位并生成拣货任务。定制、指定序列号和不可取消品可按合同提前详细分配。
3. **仓库作业状态（V187 最小闭环已落）**：`PENDING_PICK → PICKING → PICKED → SHIPPED` 与有原因的 `EXCEPTION → PENDING_PICK` 已落；仍须补库位、批次/序列号、实拣差异、复核、装箱、承运交接明细和移动端扫码。
4. **质量可用状态**：V189 已让**销售退货**先冻结、只有 `GOOD_RELEASE` 转可用；采购/委外到货仍缺同等 IQC 门，当前直接收货可用的实现不能作为生产放行依据。
5. **多仓来源决策**：按交期可达、真实库存/供给、拆单成本、客户/批次要求和总成本判断，不默认只取距离最近。

### V187 发运与仓库最小状态的安全规则

1. 新销售出货每行必须带 `order_item_id`；无订单零星出库走“其它出货”，不能借销售出货绕过发运策略、归属和硬预留。
2. 出货草稿是“订单可发额度分配”，不是第二份库存预留；同一订单行的并发草稿总量不能超过 `reserved_qty`。
3. 开始拣货是实物作业边界：锁订单行和货品维度，校验指定仓在手减安全库存、其它订单有效预留和已开始任务；现金客户须先财务审核。
4. 只有 `PICKED` 可交接；交接在同一事务消费预留、扣库存、回写订单数量/结案并立应收。
5. 仓库开始作业后财务不得反审；若缺货、货损、复核不符，登记 `EXCEPTION`，实际退拣/处置后写原因恢复 `PENDING_PICK`。
6. 任何 `SHIPPED` 都不得普通红冲直接增加库存；历史缺 `handed_over_at` 只是交接时间未知，不是未交接证据。纠错走 V189 销售退货冻结，只有 `GOOD_RELEASE` 回可售库存。
7. 历史订单写 `LEGACY_UNSPECIFIED`、历史**既有出货草稿**写 `LEGACY_PENDING`，只保留旧审核兼容，不补造客户确认或拣货时间线。V90 `chain_status=0` 且没有预留的旧未结订单不得新建 V187 出货，必须逐行对账后显式激活；当前没有自动批量激活。
8. 新订单只形成币种与原币额，`amount_original=qty×price×discount`；出货的客户、币种、税率/付款条件、价格/折扣及本次原币金额由服务端从来源订单重建并按数量比例计额，`SHIPPED` 才锁定财务汇率、计算发运本币并形成 AR。客户端汇率、本币金额或成本不是会计事实。财务已审先反审才能编辑/删除/驳回；价格无权响应由服务端脱敏。折扣/税额最终结算和分批舍入尾差仍是 NO-GO。
9. V188 仓库转换事件和 V189 退货质量事件均为 append-only，原因、操作者和时间不能通过普通更新/删除改写。
10. V189 退货审核回写 `returned_qty` 并重开替换需求、清空旧客户确认，但不直接增加预留或可拣库存；替换须重新预留/排产。退款结案/换货/补发/维修后返还尚无权威选择和审批，当前默认重开是生产 NO-GO，不得自动触发补产。
11. `GOOD_RELEASE/SCRAP/REWORK` 一旦登记，整单退货红冲正确阻断；当前没有处置级纠错/补偿命令。误判不能改 append-only 事件，上线前须补双人复核或追加式补偿流程。

## 四、V178 数据模型（全加法，零存量变更）

```sql
-- A 生命周期
ALTER TABLE stock_reservations ADD COLUMN hold_until TIMESTAMPTZ;       -- null=动态默认，无回填
CREATE INDEX idx_sr_hold_until ON stock_reservations(hold_until) WHERE is_deleted=FALSE AND status=0;

-- B 稀缺仲裁
ALTER TABLE sales_order_items ADD COLUMN priority SMALLINT NOT NULL DEFAULT 3;  -- PG11+ 元数据级填充
CREATE INDEX idx_soi_priority ON sales_order_items(priority) WHERE is_deleted=FALSE AND priority<3;

-- 权限（不自动授予，超管恒有，管理员分配给主管）
INSERT permissions: sales_order:priority (214), sales_order:reallocate (215)
```

**dev 库验证**（迁移前后对比，全部一致）：
- `stock_reservations` 17 行 / Σqty=587 / Σconsumed=162 / Σreleased=425 → **不变**
- `stock_balances` 8642 行 / Σqty=−956459386.9506 → **不变**
- `sales_order_items` 82629 行 / Σreserved=0 / Σplanned=1092 / Σproduced=0 / Σqty=77229415 → **不变**
- `hold_until` 17 行全 null；`priority` 82629 行全=3；权限点+索引就位。

## 五、对称维护矩阵（新增行，补 V90 §三矩阵）

| 业务动作 | stock_reservations | sales_order_items | 说明 |
|---|---|---|---|
| 设优先级 `setLinePriority` | — | priority 改 + 审计 | 急单须原因；纯元数据，不影响分配 |
| 稀缺让单 `yieldReservation` | `releaseForOrderItem` FIFO 释放（行锁+advisory lock） | reserved_qty −=yieldRow、chain_status 回退（镜像驳回 SQL） | `updated!=1` 抛错防错账；通知归属销售；不碰 plan_links |
| 持有逾期扫描（每日） | **只读**（status=0 生效行） | **只读** | notify-only，零变异；通知归属销售 |

> V178 新字段本身不改变 V90 的取消/改量/驳回维护；但出货反向已由 V187 向前覆盖：**所有 `SHIPPED` 禁止普通红冲**，纠错走 V189 退货冻结。以下只说明 hold/priority 与可释放预留不冲突——
> 取消把预留置 `status=DONE` → 调度器 `status=0` 过滤排除；改量减量 `releaseForOrderItem` 同；驳回同；hold_until 在这些路径都不参与判定。priority 仅在让单/排序时读。

## 六、明确不做项（与原因）

| 不做 | 原因 |
|---|---|
| 自动释放过期预留 | 须同步回写 reserved_qty/chain_status 才不漂移；新变异路径=新风险。notify-only + 既有取消/改量/让单已闭环 |
| 自动抢占订单有效预留 | 会改变既有客户承诺和排产；急单必须权限+影响清单+原因+审计，不抢已拣/已领/已出数量 |
| 7 天倒计时+续期 | 电商购物车思维；制造业按交期不按创建倒计时（SAP 亦按需求日期） |
| VIP/促销/优先券/fair-share 自动 | 专业系统可以做 allocation，但公司尚无渠道配额和服务等级主数据；当前只做人工 priority + 让单，不能写死按金额排序 |
| MTO 销售订单专属库存（special stock 'E'） | 架构级：MTO 不预留成品、生产直接产进订单专属段。需 `manufacturing_strategy` 字段 + 物理库存按订单隔离，后续 ADR |
| FEFO/批次召回 | 需批次主数据；SOP §八已标待老板拍板 |
| 把未来供给称为当前实物预留 | BUY/SUBCONTRACT 与 V194 候选 MAKE supply peg 都只是未来供给来源；销售侧可承诺交期仍待补，任何待收/待检或未完成权威挂接的供给都不能进入当前可用库存 |

## 七补、V178 当时的前端 UI + 定向证据（2026-08-01 快照）

**前端 UI（当时定向 analyze 0 issue）**：
- 订单详情页：明细表加"优先级"列；点行（仅订货单·已审·可写）弹底部 sheet `_LineActionSheet`——设优先级（急单须原因）+ 让单（校验 0<数量≤可发、原因必填），复用返回的 `SalesDocDetail` 直接 `setState` 刷新。
- 独立路由页 `/sales/scarcity`（`SalesScarcityPage`）：选货品 → 列出该货品全部生效预留（跨颜色，按优先级升序）→ 行内"让单"按钮（数量+原因对话框）→ 让单后刷新。
- 路由：`route_names.salesScarcity` + `app_router`（静态段在 `:seg` 前）+ `permission_by_path`（在 `/sales/` startsWith 块前单独 if，守卫 `sales_order:reallocate`）。hub 加"稀缺仲裁"分组（按让单权限显隐）。
- 权限常量：`Perm.salesOrderPriority` / `salesOrderReallocate` + 超管兜底集合（`permissions.dart`）。

**历史测试快照（testcontainers PG16 + 当时 159 个迁移）**：
- `SalesReservationSafetyStockPostgresTest` 当时覆盖单仓扣安全库存、钳位和让单回退；当前又增加两仓安全容量和 `StockReservationWarehouseSplitTest`，须在候选版本目标 PostgreSQL 复跑，不能沿用“159 个迁移已通过”作为 V187–V189 证据。
- `StockReservationSalesCompatibilityPostgresTest`：0 回归（V150 owner 列兼容性不受影响）。
- 跑法：`UTEN_RUN_DB_TESTS=true mvn -o test -Dtest=SalesReservationSafetyStockPostgresTest`（注：`@EnabledIfEnvironmentVariable` 查**环境变量**非 `-D` 系统属性）。

**实现要点 / 避坑**：
- `scarceReservations(goodsId, colorId)` 的 colorId=null 语义 = **所有颜色**（`(:cid IS NULL OR r.color_id IS NOT DISTINCT FROM CAST(:cid AS uuid))`），否则只匹无色预留会漏有色；稀缺面板默认按货品查全部颜色。
- 架构边：`ReservationHoldScheduler` 在 notice 包，**故意不 import stock 特性**（避免 `notice→stock` 跨特性边违反 ADR-017）；宽限期本地常量 `HOLD_GRACE_DAYS=7`，须与 `StockReservationService.HOLD_GRACE_DAYS` 同值（销售侧逾期计算用后者）。
- 后端 `SalesOrderService` 构造器加了 `AuditService` 形参（@RequiredArgsConstructor），既有测试 `ExecutionSegmentSalesAllocationPostgresTest` 的直接 `new` 已补一个 `null` 形参。
- 当时完整套件出现的 3 个其他分支失败不归因于 V178。该记录只解释当次实施快照；当前工作区有并行改动，必须重新执行候选版本全量回归后才能形成新结论。
