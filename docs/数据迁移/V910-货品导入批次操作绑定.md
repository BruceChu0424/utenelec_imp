# V910 - 货品导入批次与撤回操作精确绑定

同一货品 UUID 可以先后出现在多次导入中。旧实现通过批次货品 UUID 与所有导入历史行的交集寻找撤回操作，更新已有货品后会让多批匹配同一组历史，也可能串改其它批次的撤回状态。

V910 只新增 `goods_import_batches.operation_id`，外键引用 `goods_operation_history.id`，并用非空部分唯一索引确保一个历史操作最多绑定一个导入批次。没有新权限码，也不修改现有授权、主档字段、业务数量或旧 Flyway 文件。该未发布候选从 V908 顺延，避免与并行的旧库数量来源迁移冲突；SQL 内容保持原样。

提交服务在同一数据库事务内完成新建、恢复、补齐和选定替换，刷新 Hibernate 写入后，以当前操作者、请求 UUID 和数据库事务 ID 查出真实 `GOODS_IMPORT` 操作并写入批次。批次撤回直接使用这个绑定；通过操作记录撤回或重做时，也只更新该操作绑定的批次状态。新增、已有货品更新及相关主档继续使用现有前后快照、对象范围、字段权限、引用保护和并发校验。

旧批次的该列保留空值，迁移不按货品交集或时间猜测并批量回填。用户请求撤回旧批次时，只允许唯一且尚未被其它批次绑定的完整导入历史，校验成功后在同一事务内补上绑定；存在多项候选或缺少完整快照时拒绝撤回并要求核对，业务资料保持原状。

核对页采用 30 分钟、操作者和文件 SHA 绑定的一次性计划；服务端最多保留 32 个计划、16,000 行和估计 32 MiB 的计划内容。缓存到期或释放、重复提交、检测后主档变化时均要求重新检测。缓存不保存原始工作簿。大量替换选择通过有大小上限的 JSON 请求体提交，原始文件上限保持 10 MiB。

验证入口为 `GoodsImportHistoryPostgresTest`、`GoodsImportMergeTest`、`GoodsImportControllerTest` 及既有 `GoodsOperationHistory*PostgresTest`。独立 Testcontainers PostgreSQL 使用完整前向迁移，实际导入、货品保存与操作历史服务经 Spring 事务代理执行；重点覆盖混合批次撤回与重做、后续变动整批阻止、检测后变动拒绝、连续两批更新相同 UUID 的独立撤回和批次状态。

本说明记录源码候选与本地隔离验证；最终测试结果以本轮测试报告为准，不表示公司服务器已经应用 V910、发布或完成真实用户验收。
