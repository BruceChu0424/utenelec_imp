## 一、问题

用户口径(2026-09-21，节选)：

> 委外件 有子层级得 就是只有一个子层级物料得委外件 现在是 怎么都没有货得 ……
> 现在是 不管这个采购件是不是有货 都可以去通知仓库去出库啥得 应该是 这个采购件入库了
> 不管数量多少 就可以解锁 可以分批发货那样 就是可发数量那里可以提示 ……
> 下单的时候 应该有写 损耗比 ……委外件需要1000个 损耗比是10% 那么我仓库收货 只要大于900
> 就能正常入库 然后这个单子结束 就是不需要再等100个了 但是这100个算损耗件了 ……
> 如果小于900 就需要通知委外 ……超过就是得通知财务
>
> (追加)需要的也要减去公共的 包括公共在途的 直接自动占用公共在途 或者仓库中公共的

ADR-085 已经把「只有一个叶子子件的委外件直接发那颗子件」这条路建好了，但它在**两个方向上
同时是坏的**，而且两者互为因果：

1. **该拦的没拦**。财务一批准，计划行当场落 `READY_OUTBOUND`、建议仓**刻意留空**以躲开
   `reserveDraft` 的库存占用，随后无条件建满量出仓草稿并通知仓库。从下达到通知仓库，
   全链**没有任何一处查过那颗子件的库存**。ADR-085 §2.4 把「保存草稿时 409」称作
   「这正是用户要的那道门禁」——那是一道**保存时的事后闸**，不是下达时的前置门禁。
   仓库看得到、点得进、填得了，只有最后保存那一下被拒。

2. **不该拦的拦死了**。Flutter 的 `SubcontractOutboundFlowMode` 枚举里根本没有
   `COMPONENT_OUTBOUND`，服务端原样回传的流向落到 `unknown`，`readyOutboundQty` 与
   `maxEditableQty` 被 fail-closed 成 0。于是同一行上「已备齐 1000」和「本次最多 0」并排
   显示，填任何数字都报「不能超过本次最多数量」——**与子件有没有货毫无关系，有货也发不出去**。
   现有前端用例还用一个虚构值把这个 fail-closed 断言成了「预期行为」。

这两条叠加，用户体感就是「不管有没有货都能通知仓库出库」与「怎么都没有货」同时成立。

再往下还有四处结构性的坑，都在「这一段从来没有端到端测试」的区间里：

3. **分批发料在服务端也是死的**。出仓审核成功后 `syncAfterIssueApproved` 会为**整笔剩余量**
   自动续生草稿并立刻 `reserveDraft`，占不上就抛 409，把**刚刚审核的那一批一起回滚**。
   子件陆续到 300 想先发 300，连这 300 都发不出去。
4. **接受损耗结案必炸**。料全发完时 `shrinkOrderItemLines` 的 `take = planned − issued = 0`，
   而 `remaining = 短交量 × 冻结单耗 > 0`，抛「新数量仍低于已实发或进行中的前置生产量」
   并把刚开的损耗单、刚落的案件终态一起回滚——用户只拿到一句看不懂的红字。
5. **短交判定与分批发料结构性冲突**。下限按整张订货行算，分批发料时首批回厂必然低于下限，
   每一批都被判成严重短交并把**整张订货单**锁住不让入库。
6. **通知一条都发不出去**。`ChainNoticeService` 四处 `flow_mode` 白名单漏了
   `COMPONENT_OUTBOUND`，快照查空即静默 return。仓库能看见这张单纯粹是因为任务列表的
   聚合 SQL 不按流向过滤。

## 二、决策

### 2.1 解锁点：从「批准即派活」改成「有货才派活」

`preparation_status` 状态机一个取值都不加(避免动 V436 以来的既有形状)。变的是**建不建草稿**：

| 时点 | 此前 | 现在 |
| --- | --- | --- |
| 财务批准 | 落 `READY_OUTBOUND`，建议仓留空，建**满量**草稿，无条件通知仓库 | 落 `READY_OUTBOUND` 不变；`createDraftForPlan` 先按子件此刻的合格可动用量决定——**一件都没有就不建草稿、不通知仓库** |
| 子件采购入库 | 没有任何订阅者 | `SubcontractOutboundWakePort.wakeOutboundAfterStockIn` 按「货品 + 颜色 + 实收仓」叫醒等料的出仓行，补草稿并通知「现在可发 X」 |
| 下单前(2026-09-22 ADR-103 追加) | 任务中心申请行「待处理」可点、建单/送审/批准无守卫 | 四层同锁：子件在作业叶仓合格可动用量合计 > 0 才解锁，否则申请行落 `WAITING_COMPONENT_STOCK` 不可勾选、建单/送审/批准 409；本表上两行降级为批准后的兜底 |

「有没有活可干」因此与「仓里有没有货」严格同步。任务仍然在列表里看得见(计划量、已出、
待出都照常)，但没货时它不带草稿、不发通知、不进红徽章——按 [ADR-100](ADR-100-进行中黄色数量徽章与三形态计数口径.md)
的三形态，这就是「在办但还不用我动手」的黄色档；可发量 > 0 才是「轮到仓库动手」的红色档。

hub 红角标(`countTasks`)因此也跟着收：发现货的两种流向，要么已经有未审草稿(说明开草稿那
一刻确实有货并占住了)，要么此刻仓里还有可动用量，才算「轮到仓库动手」。两条是**或**的关系——
只认草稿会让「仓库把草稿删了、货还在」的单子从角标上消失，反而找不回去补齐。

**通知的粒度**：批准时按**计划级**判断——这张计划一张草稿都没排出来就不叫人，排出来了就叫。
理由是这条通知本身就是一张计划级任务卡(深链指向 `/warehouse/subcontract-outbound/{planId}`)，
每行能发多少由任务详情给。子件到货唤醒时则按**行**判断：只给这一次真补上草稿的行发通知，
否则同一张计划里别的行每来一批货就被刷一遍提醒，通知会变成噪音。

唤醒挂在 `ProcurementIqcStockInService.confirmOne`——单张确认、跨单批量、先入库后质检
自动转正三条路的唯一漏斗。幂等靠「该计划行已有未审草稿就跳过」兜底，入库重放、一次入库
命中多行、以及后续每一批到货都可以安全地再调一次。

**2026-09-22 ADR-103 §2.3**：唤醒收口到 `StockService.recordMovementInternal` 的入库方向(经 `ObjectProvider` 注入)，
`ProcurementIqcStockInService` 不再显式调用；完工入库、调拨入、退料、盘盈、手工单与红冲回仓(发料红冲、出货红冲)
一律唤醒，线边仓 / 不良品仓 / 非作业叶仓的入库在唤醒开头按仓短路。任务中心的锁按查询时库存实时算，不依赖唤醒。

### 2.2 分批发料：草稿量按可动用量截断，占不上就不开单

`draftLineCappedByStock` 在建草稿前对 `DIRECT_OUTBOUND` / `COMPONENT_OUTBOUND` 两种「发现货」
的流向做两件事：

1. 还没定发料仓时，替仓库选一个**有货的作业叶仓**(排除不良品仓、线边仓、非作业叶仓；
   按可动用量降序、同量按仓库编号)。一个仓都没货就返回 null，这一行本轮不建草稿。
2. 本批数量取 `min(计划余量, 该仓合格可动用量)`。

前置自制两种流向吃的是专属预留而不是公共可动用量，原样放行，仍由 `reserveDraft` 按预留
口径把关。

这一条同时解掉了第 1.3 个坑：续批草稿不再按整笔余量去占库存，所以「审核第一批」不会再被
自己开出来的第二张草稿顶回去。

### 2.3 可发数量：服务端算，界面直接显示

`OutboundPlanLine` 新增四个只读字段：

| 字段 | 含义 |
| --- | --- |
| `issuableQty` | 此刻还能再填多少 = `min(计划余量, 该仓合格可动用量)`，两边都已扣掉未审草稿占用 |
| `stockAvailableQty` | `stockWarehouseId` 里该货品/颜色当前的合格可动用量 |
| `stockWarehouseId` / `stockWarehouseName` | 上面两个数算在哪个仓：已定发料仓就是它，未定则是当前可动用量最多的作业叶仓 |

只有「发的是现货」的三种流向(DIRECT / COMPONENT / LEGACY)算得出来，其余一律 null，
客户端回落纯计划口径——旧服务端与新服务端的「不适用」都是 null，行为一致。

客户端上限以 `issuableQty` 为准(已有草稿时再加回本草稿自己占住的量，所以子件陆续到货后
可以把同一张草稿直接改大，不必删了重建)。明细表新增「仓内可动用」一列，排在「本次最多」
**前面**——上限被库存压住时，仓库不用猜是计划没量还是仓里没货。

**2026-09-22 ADR-103 §2.4**：`stockWarehouseId` / `stockWarehouseName` 此前算了却从未显示——界面补「建议发料仓」列，
无草稿时「发出仓」下拉预填它；「本次出库」预填改为可发量，可发 0 的行显示「等子件到货(仓内可动用 0)」。

### 2.4 身份：发出去的是子件，交回来的是委外件

- Flutter 流向枚举补 `componentOutbound('COMPONENT_OUTBOUND', '发子件给委外商')`。这是
  ADR-085 漏做的一环：§2.7「界面」只规定了物料分析侧，对仓库出仓页一字未提。
- 父件列不再只给历史 `LEGACY_BOM_COMPONENT` 行看，`COMPONENT_OUTBOUND` 行同样出列，
  列名从「历史父件名称」改成「回厂交回的委外件」。
- 通知文案分流向：「委外订货单 X 要发出去加工的是子件 A，加工完交回的是 B。当前可发 N」。
  可发量取**已经给仓库开好的草稿量**，不是计划余量。

### 2.5 短交判定：料没发完不判，锁按行不按单

两处口径修正，都是让 ADR-098 与「分批发货」共存：

1. **料还没全部发给委外商时一律不判短交**(`severityOf`)。委外是先发料后回厂，供应商手上
   只有已经发过去的那部分，回厂少是分批发料的常态，不是短交。料发完之后(含仓库「不再出仓」
   关掉余量)再判，口径与用户给的 1000 / 10% / 900 完全一致。
   料是在最后一批货到齐之后才发完的，由 `settleAfterStockIn` 在仓库确认入库那一刻补开案件。
2. **入库放行闸从「同一张订货单」收到「同一行订货明细」**。一张委外单多个货品时，一行短交
   不该把同单其它已经足额到齐的货一起冻在待入库。

### 2.6 容差内自动结案(推翻 ADR-098 §四)

仓库把货确认入库的那一刻，**该行的料已经全部发出去**且**累计回厂落在本单约定的允许损耗
范围内**(`WITHIN_TOLERANCE`)，直接按接受损耗结案：损耗单 → 案件落 `ACCEPTED_LOSS` 记损耗率
→ 受控改量到累计回厂量。三步顺序与 ADR-098 §2.3 完全一致，只是不再等人点。

ADR-098 §四当初拒绝自动结案的理由是「没有『供应商说交完了』的信号，自动结案会把还在路上的
货变成超量」。**允许损耗本身就是那个信号**——它是双方事先约定的「交到这个数就算交完」，
再要人去判定页点一次，只是把一件已经谈好的事又挂起来等人；而且中性档案件**零通知**
(`openCase` 只对低于下限的两档 `publishDetected`)，没人被告知，单子就永远挂着。

只自动结 `WITHIN_TOLERANCE` 一档：

| 程度 | 自动结案 | 理由 |
| --- | --- | --- |
| `WITHIN_TOLERANCE` | **是** | 有约定可依 |
| `UNSET_TOLERANCE` | 否 | 没填允许损耗，没有约定 |
| `BELOW_FLOOR` / `SEVERE` | 否 | 本来就要委外自己判「分批到货」还是「接受损耗」 |

结案后真的又来货，那是超收，走 2.8 的财务链——与用户「不需要再等那 100 个了」的口径一致。

**自动结案绝不能把仓库的入库搞失败**。这段跑在仓库确认入库的同一个事务里，受控改量一旦
抛异常，整个事务就被标成只能回滚，货也入不了库了。所以结案前先体检一次：供应商手上还没
交代的料(`minimumOrderQtyFromIssued`)不超过原订货量才自动结——结案第一步的损耗单会把短交
那一份核销掉，这个条件成立时改量必然过得去。体检没过的行原样留着走人工，多半是供应商手上
还有多发的料，要先退料或记损耗(ADR-098 §三第 14 行)。自动结案是锦上添花，不是必须成功的一步。

两处为此必须一起改，否则自动结案跑不完：

- `shrinkOrderItemLines` 的计划量目标加上**已核销损耗**：计划量该留多少 = 新订货量折算 +
  已精确退回的材料 + 损耗补量额度 + 已核销损耗。结案第一步刚把供应商处那份料用损耗单核销掉，
  不认这份损耗，`planned` 就一点都收不回来(`take = planned − issued = 0`)。
  这条对 `COMPONENT_OUTBOUND` 是必需的——它被 V581 的 CHECK 焊死了 `loss_replacement_qty_base = 0`，
  拿不到 V525 的补量额度，没有别的头寸可吸收短交。
- `changeQtyForShortDelivery` 不再受「无在办财务复核」那道闸约束。受控改量自己就会开一条
  PENDING 复核，于是同一张订货单的第二行结案必被第一行开出来的复核挡死，连它刚开的损耗单
  一起回滚——多货品委外单只要短交两行就永远结不掉。那道闸防的是人为叠加两次自由改量；
  短交结案不是自由改量，它记的是「回厂多少、损耗多少」这个既成事实，且每行只有一个开放
  案件把关。

### 2.7 公共可用与公共在途：需求先扣，下达自动认领

用户追加口径「需要的也要减去公共的，包括公共在途的，直接自动占用」。

**禁令锁的是父件不是子件**。四道守卫(V472 公共超量形态守卫、V571 私有在途来源容量、
V474 运行时超订授予、Java `ownSupplyBom`)全部读 `NEW.goods_id` / `action.goods_id` /
`source_action.goods_id`，也就是委外目标件本身。ADR-085 的子件按判据必然是 BOM 叶子，
`EXISTS(goods_bom_items WHERE goods_id = 子件)` 恒假，一道都命中不了——它就是一颗普通采购件，
本来就照常吃公共可用与公共在途。

真正要改的是两件：

1. **认领侧对父件放开**。`ownSupplyBom` 此前同时挡住「公共超量备货」和「吃公共超量在途」，
   这两件事方向相反：认领吃的是**别人已经下好、料也由别人备的**那一批成品，本计划这一层
   不会因此多出任何子件需求——认领行落 `SHARED_FUTURE_CLAIM`，按 `EXTERNAL` 归类，正好把
   下层展开基准同步净掉。**「超量备货」仍然禁止**(多下的量确实会凭空多出一份无人负责的
   子件需求)，那一侧四处守卫一个字节不动。
2. **认领候选收成同路线**(`sharedFutureSources` 的 `route = :route`)。此前候选是跨路线的，
   而界面提示侧 `SharedFutureIndex.forMaterial` 一直按路线过滤；两侧不一致时会出现
   「界面显示 0、用户填 100 点下达、服务端把需求全认领成 0、一张申请明细都不生成」。
   跨路线认领要放开得连提示那一侧一起放开，那是另一次产品决策。

**「还需安排」显示净数由物料分析主表那一路落，不在本决策里**。用户口径确实要求界面把
可认领的公共在途预先扣掉，但正确做法必须**按行判断「这一行下达时到底会不会自动认领」**：
自动认领对 `createsChildOwnership` 两类组是排除的(自制组、以及需要前置自制的委外组)，
在这些行上扣可认领量会把数做小，计划员照着填就会少下。而视图侧的 `MaterialRow` 没有
「有没有活动 BOM」这个标记(只有含义不同的 `lowerLevelPending`)，判据要随主表改造一起
喂进视图。另外 `additionalSupplyRecommendedQty` 同时是 `PreplanFutureSupplyTransferService`
与 `MaterialStockReallocationService` 的数量上限，就地改它的语义等于静默改掉那两处闸门，
所以净数要落成**独立派生字段**、不动本字段。

本决策只负责把「认领能不能发生」这一半做对：放开父件的认领资格、把候选口径与提示口径
对齐。净数怎么显示由主表那一路决定。

**待用户拍板：自动认领要不要吃「晚到来源」。** 下达时的自动认领传的是
`allowLateSupply = true`，也就是说它**会**把交期晚于需求日的公共在途认过来，事后把
`acceptedLateSources` 记进命令记录。这与 [ADR-070](ADR-070-跨计划让料与在途调入的明确接受.md)
「晚到供给要人明确勾选接受」是先斩后奏的关系——这个张力在 ADR-099 落地自动认领时就已经存在，
不是本决策引入的。两条路可选：① 维持现状，但界面要把「其中 X 来自晚到来源」单独讲出来，
让计划员看得见自己接受了什么；② 收紧成「自动认领只吃按期来源，晚到仍须人工勾选」。
本轮按 ① 处理(主表那一路在悬浮说明里单列)，是否改成 ② 需要用户决定。

### 2.8 超收：不改守恒，改成走财务隔离

用户口径「超过就是得通知财务」。委外回厂此前先撞的是守恒那道闸，抛
「委外目标件尚未足额出仓且无足够IQC失败返修额度，禁止超量回仓」并整笔回滚——仓库看不懂，
单子建不出来，财务完全不知情，多出来的实物落在账外。

多交回的那部分物理上只有一个解释：**委外商贴了自己的材料**。那是价格与归属问题，该由财务
定案。所以：

- **登记**不再因「超过物理上限」拒收(实物已经到厂了，拦下来只会让它落在账外)。仍然拦的
  只有「物理上够、但额度被同明细另一张未审草稿占住」这种并发冲突。
- **审核**顺序反过来：到货异常闸先跑，守恒闸留在后面兜底。委外行的到货上限再压一档
  「我方实际供料折算量」，被它压住时文案改成
  > 回厂数量超过我方发给委外商的材料能做出来的数量，多出来的部分用的是委外商自己的材料；
  > 本次未入库、未立应付，已转交财务审核组确认价格和归属

  走 ADR-019 的 `PENDING_FINANCE` 到货异常：货不入库、不立应付、转到货异常任务中心。
- **守恒本身不放开**，只是把「财务已批准的那份自带料」从守恒台账里摘出去(V642)。它不是
  我方发的料，本来就不该参与「发出去 = 耗用 + 退料 + 损耗 + 供应商剩余」这个等式。
  没有财务批准就一个字节都过不去，所以不会出现来源不明的库存。

## 三、不变量

1. 判据仍然只有一个来源 `fn_subcontract_sole_component_goods`。ADR-085 §三.1 此前已被
   `lockOrderInventoryDimensions` 的内联副本(还漏了 `edge.qty > 0`)推翻，本轮改回调函数本体。
2. 仓库**看得到活** ⟺ 那一行此刻拣得出货。没货时不建草稿、不发通知、不进红徽章。
3. 出仓草稿的数量永远 ≤ 该仓此刻的合格可动用量。系统不再生成一张注定存不下去的草稿。
4. 短交只在「本行的料已经全部发出去」之后判。判定的锁按**行**，不按单。
5. 自动结案只发生在 `WITHIN_TOLERANCE` 一档，且必须料已发完；其余全部保持人工。
6. 超出我方供料的回厂量，没有财务批准就一个字节都进不了库——守恒不因本决策放松。
7. 认领与超量备货是两件事：委外件可以**吃**别人的公共在途，不可以**造**自己的公共超量。
8. 前置自制(`MAKE_THEN_OUTBOUND` / `PREPARED_OUTBOUND`)与历史 `LEGACY_BOM_COMPONENT`
   三条既有链的行为一个都不变。

## 四、明确不做

- **不做跨路线认领**：服务端落库、代次、校验三侧其实都已为它准备好，卡住的只有候选过滤和
  提示过滤两处；但放开要连界面提示一起放开，属于产品决策，单独排期。
- **不放开委外件的公共超量备货**：需要先给「带 BOM 委外件的富余量」设计一份下层责任账。
  并行会话另有一轮改造覆盖「超量下达 + 超量部分按计划产出量带大子件需求」，与本决策不重叠。
- **不做 BOM 深度 ≥ 2 的多层直接外发**(ADR-085 §四不变)。
- **不给 `COMPONENT_OUTBOUND` 放开损耗补量**：V581 的 CHECK 继续焊死
  `loss_replacement_qty_base = 0`；结案所需的头寸改由「已核销损耗」提供(§2.6)，
  不新开一条补发额度。
- **不做容差内自动结案的批量撤销**：结案是既成事实的记账，要退只能走既有的损耗单红冲与
  受控改量反向。
