## 公共在途认领

计划A实际需要100，采购经财审批准订1000时，原需求100仍归A，原有V474运行时公共供给事实记录额外900。计划B需要1000，可以明确认领900，并继续为尚未安排的100下采购或合法委外。认领只建立B对已批准外单的供给责任，不改原订单数量、价格或原A分摊，不生成实物库存，也不让车间自动开工。

`POST /api/production/material-analyses/{analysisId}/claim-shared-future` 保留原版本、指纹、幂等键及操作组，新增可选 `quantities`：每项为精确 `actionGroupKey`、本次数量 `qty`、可选来源 `sourceActionId` UUID。显式数量必须覆盖全部选择组，服务端在统一供给锁内复核真实缺口及同主仓可认领来源。数量超过未安排需求或公共余量时整笔拒绝；不会将901静默裁成900，也不能动用原A的私有100。旧调用未提供数量时保留自动按需采用的兼容行为。同键同内容重试不重复认领，同键改量冲突。

来源仓按既有主仓范围匹配：旧分析使用叶仓、新分析使用其主仓时也可读取和认领同一公共在途。数据库守卫与锁足迹使用相同范围；实际合格收货仍记录真实叶仓，预测供给不会改写库存仓库UUID。

默认只采用交期已明确且不晚于计划需求日期的来源。晚到或交期未明确的来源保持可见，单独投影 `lateSharedFutureAvailableQty`，必须通过 `allowLateSupply=true` 明确接受。原命令审计记录确认标志、实际采用的来源UUID、预计日期与原需求日期。接受晚到不修改原计划日期，不改变品质、仓库入库或车间开工门禁。

前后端数量含义保持分离：

| 字段 | 含义 |
| --- | --- |
| `sharedFutureClaimedQty` | 已采用、未取消的公共在途累计责任，包含后来已经实收的部分 |
| `sharedFuturePendingQty` | 上述责任尚未实际合格入库或完成对应根产出归属的部分 |
| `additionalSupplyRecommendedQty` | 实际需求缺口扣有效在途责任后的可新增供给量 |
| `shortageQty` | 物理尚未履约缺口，不能因通知或认领而归零 |
| `lateSharedFutureAvailableQty` | 尚可采用但晚到或交期未明确、需显式接受的来源量 |

“已认领未实收”保留未取消的承诺历史，不能直接等同仍可兑现的未来供给。共享行动及其物料分摊的有效覆盖，按同来源行动UUID、同外部需求行UUID的公共可兑现量计算，并依真实入库的行动/分摊创建顺序分配。重复认领共享一个公共上限，不同来源互不扣量；品质已失败且没有有效待到量时，原计划和采用计划都会重新出现应补数量。BUY和叶子SUBCONTRACT的共享分支读取同一预算，不改普通委外流程。

例如B认领900并另下100后，未到货时仍物理缺1000，公共待到900，可新增供给0，生产计划仍WAITING。原1000订单先实际合格入库900时，A取得100、B取得800，B物理缺200，其中公共待到100、自己另下100；不能以整张外单已到900将B认领900提前标成DONE。行动状态和在途覆盖按本action的实际归属量计算，服务端也拒绝此时重复通知100。余下两笔100分别实际入库后，才消除相应物理缺口。

已到货待检及已合格待仓库确认的供给仍可被计划明确采用。公共未到量由原V554外单来源未到区间，加上同一来源FIFO分摊的待检/合格待入库区间，再扣有效私有待到责任计算；不会只因收货单已记数量而隐藏900或迫使重复采购。品质判定失败且尚未实际退回的数量不作为有效待检供给，退回后需补货的责任沿V554原规则重新打开。在这些阶段认领仍只有未来责任，实物可用量和READY必须等待真实合格入库。

既有认领仅发生状态或更新时间变化时，继续校验来源身份、精确分摊及累计批准上限，不把本次状态推进当作一次新认领重做瞬时未到余量检查。新建或改变责任的请求仍完整校验瞬时公共容量，因此品质处置不会被旧承诺卡住，也不能利用状态更新扩量。

若原供给仍承载未取消公共认领，自动失效不能破坏原V472保护而直接取消来源。只对这些来源阻止旧自动取消，保留品质失败事实并按真实可兑现量投影缺口；原供给的其他完成与安全补库规则保留。采用计划可经既有 `POST /{id}/actions/{actionId}/cancel` 撤回认领，使用版本、指纹、原因及幂等键，只需对应认领权限，不撤原采购/委外单。

最后一笔认领撤回后，来源仍按有过认领历史的真实预计量显示缺口，不会因为状态尚未写回而退回旧累计数量遮住缺口。只读详情不会改变状态；下一次正常通知补供等写操作会在原事务刷新中完成旧来源失效，再建立新供给责任。历史原请求数量、认领数量及品质结果均保留。

## 撤回未到货私有调配后的公共释放

私有在途调配撤回的审计事实将本次数量分成 `restore_to_source_qty` 与 `public_release_qty`，两者之和严格等于撤回量。原计划仍需要的部分恢复原责任；原计划已经补齐时，不再占有该部分未来供给，而是形成公共释放。该事实不修改原requested数量，不回写已完成到货，不挤占原有公共900。

公共来源上限保留原V474声明及运行时超量合并规则，再加独立的公共释放量；例如原公共900加释放40后为940。批准来源量、按具体外单的入库公共分配量，以及可认领未到量共同读取该事实。计算公共未到量时，扣除原行动及其全部有效私有受让行动尚未实收的责任，防止已给受让计划的到货仍被重复当成私有待到。共享认领的完成归属包含既有根产出履约事实，不会因其精确预留已结转而重新占用公共池。

## 专属在途归属调整

原A需求100、真实批准外单供给100中的40，可经双方版本与指纹确认转给B。原A的行动、分摊、采购或委外单数量不改；新增不可改写的 `preplan_future_supply_transfers` 固定原分摊UUID、外部需求行UUID、目标精确物料、数量、双方快照、日期、确认和幂等身份，另建B的 `FUTURE_TRANSFER` 行动及分摊承接同一真实外单。有效份额统一由 `fn_preplan_allocation_admitted_qty` 计算，A减40、B加40；原A按自己的净待补量继续安排新供给。这不是实物让料，不创建优先归还义务。

本次专属转拨范围为真实批准采购和无前置自制BOM的委外成品供给。MAKE在制及委外前置自制产物不能被当成最终委外物料的在途。来源必须同货品UUID、颜色、单位、路线和主仓范围，当前未实收量足够，双方均有操作权限。已到A的50保留，原100此时最多再转50。受让份额只在实际合格入库时兑现库存归属，不通过预测量产生预留、READY或自动开工。

分批合格入库按专属受让约定先到先分（创建时间、UUID稳定排序），再兑现原计划剩余份额，最后按既有公共认领顺序分配。A100、公共D900、转B40、原单1000时，首批20给B20，后续980给B20/A60/D900。私有双方共享原100预算，原公共900不被新转拨行动重复扣减。已经实收或结转正式计划、根产出履约的数量仍计入已实收，不能重新变成可转拨或可撤销份额。

来源外单的缩量、改来源、反向、删除以及来源行动/分析取消受到数据库守卫保护，不能无声撤掉已存在的受让责任。普通供给取消不能绕过专属转拨撤销流程。双方写操作使用统一供给锁、双端CAS及actor范围幂等键；只读进度不要求跨计划写权限。

### 接口与撤销确认

基础路径 `/api/production/material-analyses`：

| 接口 | 用途 |
| --- | --- |
| `GET /{id}/materials/{materialId}/future-transfer-sources` | 真实来源列表，含sourceAllocationId、来源可转量、目标净待补量、双方快照及交期 |
| `POST /{id}/future-transfers` | 双端确认转拨，返回刷新后的目标分析 |
| `GET /{id}/future-transfers?materialId=` | 本分析调入/调出进度，省略materialId读取本分析全部记录 |
| `POST /{id}/future-transfers/{transferId}/cancel` | 仅撤尚未实际入库量，保留历史事实 |
| `GET /{id}/future-transfer-replenishment-preview?idempotencyKey=` | 当前actor本次成功操作对应的原计划补供预览 |
| `GET /{id}/future-transfers/{transferId}/replenishment-preview` | 按明确转拨UUID读取原计划补供预览 |

补供预览使用与现货调配一致的 `CrossReallocationReplenishmentView`，包含原分析、精确物料、净待补、默认量、允许路线、超供权限及不可执行原因。只读仅需本单查看和对象范围；可执行入口仍按原计划实际补供权限开放。

取消请求的 `qty` 不得超过 `remainingQty`。预览用 `cancelRestoreToSourceQty` 和 `cancelPublicReleaseQty` 显示撤销全部余量时的拆分，部分撤销先恢复不超过原计划净待补的数量。涉及公共释放时必须传 `acceptPublicRelease=true` 明确确认，不能仅因原计划已下补单而把原计划和受让计划锁死。数据库取消事实包含 `restore_to_source_qty`、`public_release_qty`，二者之和等于本次撤销量；只将恢复量加回原分摊，其余进入公共在途来源。原A已补20再撤40时恢复20/公共20，已补40再撤40时恢复0/公共40，原外单及新补单都保留。
