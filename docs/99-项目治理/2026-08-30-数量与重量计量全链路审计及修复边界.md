# 2026-08-30 数量与重量计量全链路审计及修复边界

> **2026-09-04 边界更新**：数据模型不变（`weight` 字段/流水/迁移全部保留），但商业单据
> （采购/销售/委外的申请/订货/收退货）**编辑页不再提供实际重量录入列**——单位已表达重量，
> 重复录入无收益；行模型与保存链路保留透传，既有单据数据不受影响。仓库过磅、生产日报、
> 到货登记等实物称重场景照旧。UI 口径详见
> [订货单公共表头规范 §7](../03-页面/订货单公共表头规范.md)。

## 结论

仓库、采购、销售、委外和生产不能把所有数量解释成“件数”，也不能把原有 `qty` 整体替换为
重量。当前正确模型是两条并行且可审计的事实：

1. `qty + unit_id + unit_rate` 是业务计量量；库存基本量为
   `base_qty = round(qty × unit_rate, 4)`。
2. `weight` 是本次单据行或库存流水切片的可选实际总重量；它不乘 `unit_rate`，也不从
   `goods.m_weight`、数量、计划量或单位名称推导。

本轮共享工作树已经形成 [V435 重量流水候选](../../server/src/main/resources/db/migration/V435__measurement_weight_ledger.sql)。
只读复扫迁移目录为 397 个文件、397 个唯一版本，最高 `V435__measurement_weight_ledger.sql`；
这只是未冻结工作树事实，不是受保护提交、目标库 history
或部署证据。历史重量补证、重量单位、净重/毛重/皮重、盘点实际重量、目标非空库迁移和现场称重
UAT 仍全部 **NO-GO**。

## 一、四类容易混淆的量

| 事实 | 权威字段 | 业务含义 | 不得替代 |
|---|---|---|---|
| 数量 | `qty + unit_id + unit_rate` | 个、套、kg、吨、米等交易量；换算后形成库存基本量 | 不能因单位名像重量就改写为 `weight` |
| 实际总重量 | 单据行 `weight`、V435 `stock_movements.weight` | 本次实物行/流水切片记录的总重量，可空 | 不乘 `unit_rate`，不从单重或数量估算 |
| 货品单重参考 | `goods.m_weight + m_weight_unit_id` | 货品主档的每单位重量参考 | 不能静默生成实际总重量或历史重量 |
| 物流件数 | 销售 `parcel_count` | 一张出货单的独立包装件数 | 不能由不同单位明细 `qty` 求和、四舍五入生成 |

`units` 当前只是 UUID 单位字典，只有编号、名称和状态；没有 COUNT/WEIGHT 维度、换算族或重量
单位治理。kg、g、吨等名称只用于显示，不能作为服务端分支、关系键或历史回填依据。

## 二、页面与汇总规则

- 每个数量输入、列表、详情、打印和导出必须同时显示业务单位；不能只写“数量”后默认理解为件。
- 实物交易页提供“实际总重量”可选输入。未称重时保持 `NULL`；`NULL` 是未知/未提供，不是 0。
- 汇总只按 `unitId` 分组。同一 UUID 单位可以小计；显示名相同但 UUID 不同仍不得合并。
- 缺 `unitId` 的历史行进入独立「单位未维护」桶，不能按单位名称猜测，也不能并入其它小计。
- 混合单位页面显示“明细 N 行”和分组小计，不显示跨单位统一总计。
- 销售 `parcelCount` 是可独立录入的非负整数物流事实，不再由明细数量自动生成。
- CHECK 盘点及授权库存余额调整本轮保持仅数量；不能用本轮 UI 改造冒充盘点重量已实现。

## 三、V435 源码候选

### 3.1 结构与不可变历史边界

V435 新增：

- `stock_movements.weight NUMERIC(18,4)`，非空时必须非负；
- `procurement_inspection_items.received_weight NUMERIC(18,4)`，冻结收货行实际总重量；
- 只读 `v_stock_weight_reconciliation`，按仓库、货品、颜色核对余额重量与逐笔流水重量。

V435 明确不回填既有 `stock_movements.weight`。核对视图只在余额重量已知且每一笔流水都有重量时
返回可核差额；否则分别显示 `BALANCE_WEIGHT_UNKNOWN`、`NO_MOVEMENT_HISTORY` 或
`INCOMPLETE_MOVEMENT_WEIGHT`，`weight_difference` 保持 `NULL`。禁止把未知历史当作 0 或
“已对平”。

### 3.2 应用链目标

当前源码候选将现有单据行重量传入以下物理库存链及其反向：

- 采购收货/IQC、采购退货及历史收货红冲；
- 销售出货、其它出货、销售退货质量良品释放及撤回；
- 委外进仓、成品退货、材料发出、材料退回和损耗；
- 仓库统一单据及审核/红冲；
- 生产日报经 FQC PASS 或受控 legacy 路径生成 FINISHED_IN。

统一到货登记与销售批量发货请求增加可选 `weight`。来源没有重量时保持空；任何路径都不能读取
`m_weight` 自动补值。

### 3.3 质量分批与反向

- IQC 在 inspection 创建时冻结整条收货行的 `received_weight`。
- 部分 PASS 按累计 `passed_base_qty / received_base_qty` 分配该行已登记总重量，最后一个切片
  吸收四位小数尾差；这是对同一已称总重量的切片分摊，不是重新估算整行重量。
- IQC 红冲按累计已放行基本量精确反向相同重量切片。
- 销售退货 `GOOD_RELEASE`/撤回按来源退货行重量与累计处置基本量作同源比例分配。
- FQC PASS 与 legacy 报工生成 FINISHED_IN 时，只能按来源日报行已登记重量及其数量切片传递。
- 重试、红冲和补偿必须沿原来源 UUID 与方向写对称流水；不能从当前货品单重重新计算历史切片。

## 四、财务与成本为什么必须保留双事实

- 铜材其他应收按进仓/发出实际重量计算 0.5% 损耗，同时保留发出业务数量。
- 酸洗入库验收同时核对重量和数量，例如 136.4 KG / 46010 个；两列不能互推。
- 塑料耗用和产品入库明细读取已登记成品入库重量；空重量不得用 `m_weight × qty` 补造。
- 供应商、客户和加工对账中的数量必须连同业务单位解释；跨单位总数量没有财务意义。

V435 只补未来流水证据，不证明历史报表中的 generic `weight` 统一为 kg、净重或实际称重。财务
验收必须逐行保留来源单 UUID、数量及单位、实际重量、红冲方向和报表结果。

## 五、明确 NO-GO

| 项目 | 当前结论 |
|---|---|
| 按单位名判断“按数量/按重量” | **NO-GO**；单位表无计量维度且历史存在噪音名称 |
| 用 `m_weight × qty` 回填交易或历史重量 | **NO-GO**；单重参考不是实称事实 |
| 净重/毛重/皮重 | **NO-GO**；现有 generic `weight` 无对应字段与现场规则 |
| 交易重量单位 | **NO-GO**；当前没有逐交易重量单位 UUID 快照 |
| CHECK 实盘重量及差额 | **NO-GO**；现有结构只有 `count_qty/surplus_qty` |
| 授权余额重量调整 | **NO-GO**；现有命令只调整数量 |
| 历史 movement 重量回填 | **NO-GO**；V435 明确保留 NULL |
| 生产 `fqty/iqty` 改按重量 | **NO-GO**；生产数量、质量和入库量守恒继续独立 |
| 目标库迁移/发布 | **NO-GO**；尚无 live history、非空副本、恢复、岗位 UAT 和部署回读 |

## 六、验收矩阵

| 层面 | 最低证据 |
|---|---|
| 主档 | 单位 UUID 仅作业务单位；同名不同 UUID 不合并；缺单位显式隔离 |
| Flutter | 普通交易行可选实际重量；数量带单位；混合单位分组；parcelCount 独立 |
| API/服务 | weight 非负、最多四位小数；不乘 unitRate；不从 mWeight 推断 |
| 库存 | 正向/红冲逐笔 weight 对称；余额增量与 movement 方向一致 |
| IQC/FQC | 部分放行、尾差、重放、红冲和 FINISHED_IN 来源重量守恒 |
| 报表 | 铜材、酸洗、塑料和产品入库逐行核对数量单位与实际重量 |
| 历史 | 三种未知状态不伪装为 RECONCILABLE；NULL 不转 0 |
| 数据库 | 空库、非空可恢复副本、约束、视图、审计、并发和回滚 |
| 岗位 UAT | 采购/仓库/品质/销售/委外/生产/财务真实账号及实物称重 |

自动化或静态检查通过只能证明当前源码候选；目标库重量分布、真实称重设备/操作时点、历史净毛皮
语义、备份恢复和多岗位签字必须另行留证。
