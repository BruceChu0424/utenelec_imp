# 履约命令共享截止时间

状态：R1 局部实现，机制定向与后续真实 Boot/JPA 验证通过，待整合验收。不是 R0/R1 阶段完成证明。

## 问题和边界

来源漂移重试在事务代理之外运行。旧实现只在一次冲突返回后检查“第一次冲突之后 10 秒”和“命令开始 30 秒”，每次重试却重新取得默认 40 秒事务时限。例如第一轮用时 29 秒后发现来源变化，第二轮正常返回，即使又用了几十秒也可能提交。

本次为同一根服务命令及其重试建立一个单调时钟截止时间。它从根 `@Transactional` 代理开始计时，覆盖连接获取、业务 SQL 和物理 COMMIT 之前的期限检查。它不包括 HTTP 接入和认证前的排队，也不能强制取消 PostgreSQL 16 COMMIT 内部的延迟约束或持久化确认；提交后的同步回调也不属于原事务可回滚时间。网络故障仍可能产生结果待确认，必须按原命令查询结果。

## 实现

1. 根命令沿用显式事务上限；未显式指定时读取现行 `spring.transaction.default-timeout`，不另立更大的时限。每个重试只得到剩余时间。首次可重跑冲突之后，再把剩余时间收紧到既有 10 秒重试预算；退避/线程重新调度后也检查期限。
2. 保留 Spring 原事务属性与回滚规则，只对本次动态 `getTimeout()` 取剩余值。共享的注解属性不被修改或缓存请求期限。
   实际接线由静态 BeanFactoryPostProcessor 在实例化前设置框架 `transactionInterceptor` 的属性：内部包装 BeanDefinition 引用唯一原 `transactionAttributeSource`。不新增同类型可注入 bean，不改变原 pointcut、回滚规则、限定符或只读属性；不依赖可能错过早期基础设施的晚 BeanPostProcessor。
3. 事务获取连接后按绝对期限再次收紧 Spring 资源 holder，避免连接池等待后重新获得完整时限。没有命令上下文的后台 `TransactionTemplate` 保持原行为；显式长事务不被无差别裁为 40 秒。
4. 在全部 `beforeCommit/beforeCompletion` 同步回调之后、物理 COMMIT 之前检查期限。到期异常用普通 RuntimeException 包装 `TransactionTimedOutException`，让 Spring 明确回滚；直接在提交钩子抛 TransactionException 会走另一条“提交失败”分支，不能据此假定显式回滚已发生。
5. 期限检查不增加 SQL，不改变既有 `statement_timeout`，不切换约束的延迟时序。见下文真库反证：仅在 COMMIT 前收紧 `statement_timeout` 并不能限制该阶段，已撤回这项无效开销。
6. 根物理事务成功提交后，最高优先级 `afterCommit` 标记停止期限传播。提交后的独立事务不继承旧期限；嵌套 REQUIRES_NEW 提交不清掉尚未完成的外层期限。已经提交后抛出的来源冲突不得重跑原命令，也不能当作“原事务已回滚”。

## 验证计划

- 原来源冲突回归：允许等锁 4 秒后重跑，结构错误不重跑，次数上限不变；新增退避被高负载调度拖过期限、中断恢复和线程上下文清理。
- 真 Spring 事务代理 + 可控时钟：29 秒首轮失败、11 秒“成功”重试在提交前回滚；CPU 尾段、连接获取、晚提交回调受约束；显式 120 秒和无上下文的 1800 秒后台模板保留；提交后慢回调不把成功改报超时。
- 隔离 PostgreSQL：实际长业务 SQL 取消后前置 INSERT 为零；纯 CPU 超期在 COMMIT 前回滚真实 INSERT；更短事务期限和既有 200 毫秒语句期限不被放宽；同物理连接设置不变；提交后独立事务可继续，嵌套独立提交不会释放外层期限。
- 单列限制回归：延迟 COMMIT 触发器仍可能超出根期限，若 COMMIT 已完成则必须返回成功，并明确断言行已存在，禁止把它伪装为回滚。
- 集成时重跑当前预锁、直送和出库 SQL 预算；本修复零新增 SQL，计量器及总预算保持原样。

测试调度由主会话统一控制；使用独立 `target-deadline`，日志写本 worktree 的 `.local-tmp/deadline`，测试堆通过 `uten.test.jvm.heap.args` 限制为 3 GiB，不覆盖 Mockito agent 或隔离临时目录配置。没有连接公司业务库，没有运行全量测试或部署。

- 最后一次 SQL 后的应用处理尾段超期，在 COMMIT 前拒绝，真实 INSERT 回滚。这不是 CPU 争用压测。
