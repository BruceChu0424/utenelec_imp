# V624 历史委外结算未知来源证明

迁移文件：`V624__legacy_subcontract_settlement_provenance.sql`。

旧库 `E_Order` 没有结算方式列。V378 保留了已经存在的历史 NULL，但拒绝后来插入的已审 NULL 单，因此首次导入旧已审订单会失败。V624 不修改 V378，不猜客户/供应商默认结算，也不把已审状态改成草稿。

## 首导例外

新增 `subcontract_orders.legacy_import_run_id` 和不可变证明表 `legacy_subcontract_order_import_sources`。证明只保存 run、源旧 ID、唯一目标 UUID、完整源行 SHA256、受验 CSV SHA256、目标商业字段 SHA256 及签发事务 ID；不保存源行原文或密钥。

协调器完成来源和候选校验后，在持有同库 bootstrap advisory 锁的同一业务事务中，使用 `fn_register_legacy_subcontract_order_source(run_id,to_jsonb(order_stage))` 登记原始 17 列 `E_Order` 源行。函数只接受受信的迁移登录身份，核对完整 `--bootstrap-all` / RUNNING / BOOTSTRAP、数据库和集群、映射版本、候选提交、源 manifest、离线备份与批准引用，以及本 run 已验 `subcontract_order_m.csv`。

导入已审单必须消费同 run、同旧 ID、同一唯一目标 UUID、同事务签发的证明，目标 14 个原始商业字段必须匹配。其他在线单仍需满足原有已审非空结算约束。任意会话临时表、伪造 GUC 或普通运行时账号填写迁移 run 都不能授予例外；角色与锁证据读取明确限定 `pg_catalog`，不受同名临时关系遮蔽。数据库超级用户本身属于运维信任边界，数据库约束不声称能阻止超级用户撤销约束。

原单不可补挂、换绑或清除 provenance，不能借历史证明变成新草稿/重新审批；原单头商业字段及原明细的数量、价格、单位、来源不可更改。初装明细只允许同一受验 bootstrap 事务。后续真实收货/退货数量、财务授权超到货已过账量、结案等履约进度仍交给现役账务守卫处理；这份证据不能伪造库存或覆盖财务审批。

## 未知条款仍需专项核验

导入后的历史 NULL 可以查看，不意味着旧在途委外单能够自动续走。`SubcontractReceiptAmountAuthority` 继续返回既有 409：“历史空结算方式必须先专项核验”。只有完成有证据的专项核验并合法补齐条款后，才能执行新的收货；本迁移不提供默认条款或自动核验流程。

导入回执应按订单 UUID/旧源 ID 列出待核验对象，不带人员原文。来源证明保留原始未知事实；核验后正常履约所需的收退数量与结案投影可继续更新，已经核实的结算不能重新清空。

## 数据与运维边界

本迁移不更新任何既存业务行。新证明表与 `legacy_migration_runs` 同属 PRESERVE 追溯证据，清空测试业务时保留；运行时角色仅需只读权限，不能改写证明。新增表使用标准审计触发器。`business_data_reset()` 按受检前向扩展添加明确 PRESERVE 目录，原锚点异常时拒绝迁移。

专项 PostgreSQL 测试覆盖历史行零改写、真实证明导入、伪造/跨 run/跨事务/候选身份错误、普通运行时账号、重绑定/清除与商业事实篡改、后段失败回滚、只读保留权限和补齐条款后的履约进度。完整协调器测试负责来源 CSV 到证明注册及所有模块统一事务的端到端验证。
