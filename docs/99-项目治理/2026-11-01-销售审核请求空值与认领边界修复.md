# 销售审核请求空值与认领边界修复

独立分支 `uimp/sales-manager-null-request-fix-20261101`，基线 `9477b9c7a50677f524048736d844ccbeafccacae`。本轮只修改后端请求边界、对应回归及这份证据，不改迁移、Win7 台账、版本、前端或发布配置。下一版发布工作台 UI 仍在另一独立工作树，未混入本修复。

## 已证根因与修正

9477 的 CodeQL SARIF 有三项：`SalesManagerReviewService.rejectOrder` 从可空 request 间接取原因后直接访问请求；同服务反审核的非空保护后仍再次判断 request；`SalesQuoteFinanceService.confirm` 已访问 req 后又判断 req 是否为空。原驳回的 `note(null,true)` 实际会抛校验异常，但依赖这一间接控制流掩盖入口约束，容易再引入空值访问。

现在在每个对应入口显式拒绝空请求，并继续保留原因必填/长度校验。核对同类确认、编辑、退回和撤销入口后，空请求、缺修订号、契约要求的认领代次缺失均明确返回 `VALIDATION_FAILED`；真实存在但已过期的版本、错误/旧代次和阶段冲突仍按 `CONFLICT` 拒绝。报价行的空修改对象/空原行编号明确校验失败，不再落入空值访问；不存在的原行继续冲突失败。

负责人订货批量请求必须为整个选择集携带原修订号和认领编号，缺任一项在做出决定前整批拒绝。报价的“确认备注未提供时保留已保存备注”逻辑未改变；负责人订货撤销的决定身份、原因和下游守卫未改变，报价撤销的原可选原因语义也未收紧。

`TaskClaimService` 的通用旧调用兼容没有修改。本轮非空认领要求只落在已经明确声明必须携带认领代次的负责人决策与报价核价决策。当前 Web/Flutter 共用报价 repository 的编辑、退回、确认 API 均为 `required String expectedClaimId` 并始终发送字段，已发布 `v2.5.38` 标签相同；页面先续租核对，再发送该代次。负责人订货详情与批量入口也发送每个原代次。缺字段的旧或不完整请求会明确校验失败，应按既有协议刷新/更新客户端并重新进入审核，不会借用同一用户后来取得的新租约。原订货财审兼容入口没有扩大修改范围。

WPF C# 当前没有负责人订单/报价核价的可写调用，相关 W7-BIZ-070/074/217 仍未迁移；本修复不开放占位入口，也不把服务器兼容当作 WPF 功能完成。
