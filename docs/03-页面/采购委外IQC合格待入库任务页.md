## 一、为什么必须分成两步

“品质合格”和“仓库已经完成实际入库”是两个不同事实：

1. 品质部只判断本次检验切片是 `PASS` 还是 `FAIL`，并记录数量、原因、操作者和时间；
2. 仓库负责核对实际待入库量、目标仓和实际库位，可分批确认入库；
3. 只有仓库确认成功后，才允许写库存流水、增加 `stock_balances`、刷新可用库存、建立分析归属，
   以及推进 reservation、DRAW 和 `WAITING → READY`；
4. 品质 `PASS` 本身不得再被页面、接口、通知或报表表述为“已入库”。

采购/委外收货审核仍会建立收货单、更新订货实到、按现行财务规则形成 AP，并创建 IQC
`PENDING` 隔离行；待检品、品质合格待入库品都不是可用库存。

## 二、权威数量与状态

每条 IQC 明细必须同时保留以下互不替代的数量：

| 数量 | 含义 | 是否可用库存 |
|---|---|---|
| `received_base_qty` | 收货审核后进入 IQC 隔离的基本量 | 否 |
| `passed_base_qty` | 品质已判定合格的累计基本量 | 否，仍须仓库确认 |
| `failed_base_qty` | 品质已判定不合格的累计基本量 | 否 |
| `warehouse_stocked_base_qty` | 仓库已确认并正式入库的累计基本量 | 是 |
| `passed_base_qty - warehouse_stocked_base_qty` | 合格待入库量 | 否 |

品质明细继续使用 `PENDING / PARTIAL / RESOLVED / REVERSED`；仓库详情按整单聚合显示
`IN_PROGRESS`（仍在检验）/ `RESOLVED` / `REVERSED`。仓库入库状态独立表达：

- `WAITING_QUALITY`：尚无可确认的 PASS；
- `PENDING_STOCK_IN`：存在合格待入库量，尚未确认；
- `PARTIAL_STOCK_IN`：只确认了部分合格量，仍有待入库余量；
- `STOCKED`：品质已结案，全部合格量均已实际入库；
- `REVERSED`：来源收货已受控红冲。

禁止把品质状态直接复用成仓库状态，也禁止用当前 `stock_balances` 反推某个 PASS 切片是否已入库。

## 三、页面结构

### 3.1 任务列表

- 2026-09-01 起列表由合并页「品质部检查结果」提供（`/warehouse/quality-results`）：
  旧 `/warehouse/iqc-stock-ins` 列表与 `/count` API 已删除，筛选为采购/委外、作业状态
  和关键字（覆盖收货单、供应商、目标仓和货品）；
- 列表按收货单聚合显示作业状态、来源类型、收货单号、收货日期、供应商 / 委外商、
  目标仓、品质结论行数、待入库切片数和待退回笔数，不跨货品拼出无单位数量合计；
- 完成任务不留在待办列表（已完结分段可查），通知深链仍可打开同一详情，读取只读入库历史；
- 首次加载、刷新旧数据、失败重试、空态和无权限必须区分；通知和角标只触发刷新，不作为任务真相。

### 3.2 入库详情

- 只显示实物、品质、来源和仓库字段；不得显示采购/委外商业金额，也不得提供财务动作；
- 仓库填写本次实际入库基本量，默认等于当前合格待入库量，可改小但不得超量；
- 实际库位必须作为本次入库事实保存。货品主档 `stock_place` 只可作为“当前建议库位”，
  不能冒充历史库位快照；
- **库位学习（V451）**：确认成功后，本次库位按「仓库×货品×颜色」写入
  `warehouse_goods_place_preferences`（来源 `IQC_STOCK_IN`），并在与主档不同时回写
  `goods.stock_place`。下一次同维度待入库的库位输入框自动带出上次实际确认的库位；
  同一维度本次出现多个不同库位时不学习；幂等重放不重复计数；
  详见[迁移说明 66](../数据迁移/71-IQC入库库位学习.md)；
- 支持同一 PASS 分批入库。每次提交都有独立幂等键、并发字段
  `expectedRemainingBaseQty`、本次 `baseQty`、操作者和时间；服务端必须在锁内重读余量并做精确 CAS；
- “预计去向”按本次 `baseQty` 截取，只用于确认前解释；“实际去向”从提交事务返回并在历史重建，
  前端不得自行把预计去向保存成库存归属，也不得把“形成工单”写成“已经齐套/可领料”；
- 批量确认必须先校验完整集合，任一行版本、状态、仓库或数量变化时整批回滚，不能由客户端循环单行接口伪装成功。

### 3.3 操作反馈

- “确认入库”必须明确说明将增加正式库存并可能推进生产齐套，同时展示本次预计去向；
- 提交中按钮禁用并显示进度；成功后刷新当前任务、库存角标与相关分析；
- 成功反馈必须弹出本次真实分配结果；旧响应缺 allocations 时明确提示以刷新后的入库历史为准，
  不得伪造预定或公共数量；
- 幂等重放只返回原结果，不重复写库存、reservation 或 DRAW；
- 冲突错误保留用户输入，提示刷新后重新核对。

### 3.4 响应式与可访问性

- 列表和详情使用独立深链。桌面列表采用高密度表格，紧凑屏的关键数量、品质说明、库位输入和
  完成历史都在独立详情页按卡片纵向展示，不依赖列表横向滚动完成入库；
- “确认入库”是详情页唯一主动作。本期不在该页面提供独立红冲/撤销按钮；来源收货红冲继续走原单受控反向；
- 搜索、筛选、分页、刷新、库位输入和提交控件的有效触控区不小于 `48dp`，键盘焦点顺序与视觉顺序一致；
- 状态不能只靠颜色表达，图标或状态色必须同时带文本；图标按钮、数量输入和错误信息提供可读语义；
- 首次加载显示骨架或进度，错误态说明原因并提供重试，空态区分“当前没有待入库任务”和“筛选无结果”；
  异步提交期间禁止重复点击，成功与失败都给出明确反馈。

## 四、后端事务边界

仓库确认入库必须在同一事务中：

1. 按稳定顺序锁定收货单全部库存维度、IQC 行、PASS 切片和仓库入库投影；
2. 校验权限、状态、`expectedRemainingBaseQty`、目标仓、实际库位和剩余可确认量；
3. 追加不可改写的仓库入库事件；
4. 写 `stock_movements(DIR_IN)` 并更新 `stock_balances`；
5. 更新 `warehouse_stocked_base_qty`；
6. 按本次实际入库切片建立分析精确归属；
7. 刷新物料分析，并仅按已入库量推进正式供给、reservation、DRAW 和 READY；
8. 刷新仓库任务、即时库存和生产投影；通知只作提醒，不替代这些权威事实。

品质 PASS 事务只更新品质数量和事件，并投递“合格待仓库入库”任务；不得执行上述第 4–7 步。

## 五、部分入库、金额与重量守恒

- 品质 PASS 切片应冻结自身的基本量、分摊本币金额和实际重量；仓库确认消费这些切片，
  不得在确认时用当前累计量重新计算；
- 多次 PASS、PASS/FAIL 交错和多次部分入库后，各切片金额与重量之和必须等于来源可证明总额；
  最后一片吸收四位小数尾差；未知重量保持未知，不能按货品单重或数量猜测；
- AP 仍按收货审核的财务时点处理，仓库确认不得重复立 AP。跨期间出现“AP 已确认、库存待确认”时，
  必须有明确的期间截止、成本和对账规则。

## 六、红冲与撤销

- 来源收货红冲只反向 `warehouse_stocked_base_qty` 对应的实际库存、金额和重量；
- 已 PASS 但尚未仓库确认的数量只取消待入库任务，不生成 `DIR_OUT`；
- 已形成但尚未领料的 READY、reservation、DRAW 和分析归属按实际入库来源对称回退；
- 已领料、已开工、已跨分析让料、已核销 AP 或存在其它不可逆下游时继续 fail-closed；
- 品质 PASS/FAIL 历史不得物理删除或改写为“未检”。红冲另记撤销事实和仓库反向事件。

## 七、权限边界与审计

- 品质查看 / 处置：`procurement_inspection:view`、`procurement_inspection:handle`；
- 仓库待入库查看 / 确认：使用独立仓库权限
  `warehouse_iqc_stock_in:view`、`warehouse_iqc_stock_in:confirm`；
- 页面右上角“权限设置”只显示本页相关权限，仓库确认权不得由品质 PASS 权自动推导；
- 同一员工对同一 PASS 切片先后执行品质放行与仓库确认：自 2026-09-01 起不再硬性拒绝
  （单人维护场景需要同人闭环）；详情接口保留 `containsOwnRelease` 标记，前端在确认前给出
  醒目复核提示，审计上仍可追溯放行人与确认人是否同一员工。

跨期间财务验收与恢复演练；上述证据完成前继续 **NO-GO**。

### 9.1 V446 部署与回退边界

V446 改变了 `PASS` 的库存副作用，数据库与应用版本不能混跑。唯一允许的上线顺序是：

1. **停止全部旧实例**，关闭定时任务和写流量，确认旧 JAR 已不再处理 IQC；
2. 在可恢复备份、迁移前只读校验和历史 PASS / 库存流水对账通过后，执行 **V446 迁移**；
3. 只启动包含两阶段 IQC 合同的**新应用**，禁止旧实例重新加入；
4. 执行迁移后验收：历史已入库 PASS 不得进入待办，新增 PASS 不增加库存，
   `/warehouse/iqc-stock-ins` 可发现任务，仓库确认后库存 / exact 归属 / 生产供给才按本次切片推进；
5. 完成真实品质与仓库双身份 UAT、红冲、恢复和部署回读后，才允许形成发布决定。

禁止滚动混跑、蓝绿期间新旧 JAR 同时写库，也禁止在 V446 已应用后用旧 JAR 作为回滚手段。
失败时保持写入停止，按备份恢复或新前向迁移修复；不得执行 `flyway repair`、改写 V446 字节或让旧程序继续写 PASS 库存。
