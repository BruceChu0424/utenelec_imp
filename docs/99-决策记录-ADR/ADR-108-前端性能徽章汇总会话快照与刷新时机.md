## 一、背景(审计实测)

## 二、决策

### 2.1 徽章一次汇总(服务端单一口径)

- 新增 `GET /api/workbench/badges`(`features/workbench/badge`): `WorkbenchBadgeCatalog` 为**唯一口径登记处**,
  每个入口一行: 归属容器 + 红/黄各由哪些「事实数」相加。事实数 = 各业务模块 `*WorkbenchBadgeSources`
  (经 `application/port/WorkbenchBadgeSources` 端口注册, ADR-017)调用**原计数端点的 controller 方法**取得——
  走方法级安全代理, 原端点的 `@PreAuthorize` 与对象级范围原样复用; 无权限的来源抛 AccessDenied,
  该入口在汇总里缺席(不是 0)。
- 一个只读事务内逐来源 savepoint 隔离: 某个来源 SQL 出错只回滚它自己, 其入口列入 `staleEntries`、
  来源键列入 `staleSources`, 不拖垮整份汇总; 启动时校验目录引用的来源都已注册。
- 前端对 `staleEntries` **按差额修正**: 该入口换回上一份的数, 所在容器与导航总数只减去它本次的残缺数、
  加回上一份的数——不整体沿用上一份的容器/总数(否则某来源持续出错时总数冻结在第一次的值上,
  其它入口怎么变都不动); `staleSources` 的事实数(页内分段)同样沿用上一份。
- 响应: `{generatedAt, entries{key:{todo,inProgress}}, modules{...}, total, facts{source.field}, staleEntries[], staleSources[]}`。
  页内分段细数(各类草稿、品质结果分来源、车间任务分段、访客四档等)读 `facts`, 不再单独请求。
- 通知未读数、未读摘要(digest)与最新发布时间也作为来源 `notices` 随汇总带回。
- 前端 `badgeSummaryProvider` 为全站唯一数据源: watch `authenticatedScopeProvider`(只有已登录才存在),
  登录后立即拉一次、之后每 60s; 页面隐藏暂停, 回前台立即补一次; 单飞 + 在途合并(同帧多处 refresh 只
  1 个请求, 在途再要只在返回后补 1 次); 换身份时代际号作废迟到响应。`BadgeEntry`/`BadgeModule` 与服务端
  枚举逐字一致(`badge_registry_contract_test` 直接读服务端源码核对)。
- 删除: 两张注册表、约 40 个计数 provider 与其轮询、各计数 provider 里的权限判断、对应 repository
  计数方法与 ApiEndpoints 常量。
- 同一服务实现只读端口 `application/port/WorkbenchBadgeReadPort.entries(入口集合)`: 只读所请求入口引用的
  来源(4 个入口 5 条 SQL, 整份汇总 40 条), 口径与汇总逐个相等(真库契约测试核对)。见 2.10。

### 2.2 会话快照(/auth/me 一次带回)

- `/auth/me` 增加 `session`: `delegableSurfaceKeys`(可打开「本页权限设置」的页面)、`documentScopes`
  (六个单据范围普通写能力)、`preferences`(偏好整表)。`sessionSnapshotProvider` 在登录/恢复会话/切代操作
  身份时重建, 令牌刷新带回的权限点变化或页面权限设置保存后重取; 登录流程里刚取过的 `/auth/me` 经
  `RecentMeSnapshot` 接力, 不重复请求。
- 删除 `/department-staff-permissions/capability`、`/auth/me/document-scopes/{scope}`、`GET /user/preferences`
  及前端对应 provider; 详情页不再「每次加载作废写能力」, 失败态的「重试」= 重取快照。
- 快照只决定按钮显隐与默认值, **服务端写接口的对象级校验不变**。已知代价: 正式交接生效后, 接收人最迟
  在下一次登录或点「重试」时看到可写, 期间按只读显示(不越权)。
- 快照是 `/me` 的附带信息: 服务端算快照的任何一部分出错只让 `session` 为空, 不让恢复会话失败;
  前端把「没带快照」按失败处理, 按 5s/15s/45s 退避自动重取三次, 断网恢复(`recoveryEpoch`)时若仍在失败态
  立即重取——一次网络抖动不会让整段会话的详情页只读、权限按钮消失。
- 偏好 notifier 只采用**新加载的快照**(`SessionSnapshot.generation`): 本端写偏好成功后就地派生的快照
  (同一批次)不回灌任何 notifier; 同一身份重取快照时, 本地有未确认的改动(防抖中/推送中/推送失败)
  也不覆盖; 换身份作废上一身份没推完的改动。否则 A 键推送成功会把 B 键还在防抖中的改动冲回登录时的旧值,
  随后再把旧值推上服务端(修复轮回归测试 `uten_page_prefs_snapshot_race_test`)。

### 2.3 返回即刷新: 按数据变没变, 且在转场之后

- 网络层 `DataWriteRevisionInterceptor`: 任何成功的业务写(非 GET/HEAD/OPTIONS, 排除心跳、自动已读、偏好保存、
  令牌、只算不存的预览)推进 `dataWriteRevisionProvider` 并记下路径——调用方漏了 `bumpListRefresh` 也不会显示旧数据。
- `onPageResume`: 返回到我时只有「期间写修订号前进」或「距上次刷新 ≥30 秒」才重拉; 重拉推迟到
  `RouteTransitionTracker` 报告全部路由转场静止之后; 页面登记的 `refreshKeys`(原 listRefresh 精准刷新)
  只在本页位于栈顶时立即执行, 被详情盖住时只记下、返回时合并成一次。嵌入式分段用 `onListRefresh`。
  断网恢复只让当前可见页重拉一次(`pageRefreshRequestProvider`), 不再重建网络层。
  等转场最多 1 秒(`routeTransitionSettleTimeout`): 某个转场卡住(如 ticker 被静音)时照样执行,
  不让全站的返回刷新无限推迟。
- 工作台返回: 徽章汇总 refresh(单飞) + 概览重取; 不再逐个失效 16 个 notifier。未读数本身随汇总带回,
  外壳不再「看到未读上涨就再拉一次汇总」(每条新通知白打一次); 到达 feed 拉到新通知时由到达协调器刷新一次。

### 2.4 轻量转场

- Web 与桌面: 统一约 150ms 纯淡入(`UtenFadePageTransitionsBuilder`, 只动新页, 不缩放);
  移动端保留平台默认。全部经 `TrackedPageTransitionsBuilder` 登记转场进行中, 供 2.3 推迟刷新。

### 2.5 网络层

- `WriteDeadlineInterceptor` 在 Web 上对所有方法生效(连接上限跟随接收超时 45s), 慢 GET 不再 15s 被掐。
- `SafeRequestRetryInterceptor` 只重试「连不上」与 502/503/504; 收发超时不重试、不判断网(慢 ≠ 断)。
  建连超时分平台: 原生端(Windows 桌面包)它是真实的 TCP 建连超时, 服务器宕机/网线断开时就是它,
  按连不上处理(读请求重试, 耗尽后进入断网恢复); Web 端它只是浏览器请求计时器, 不算。
- `apiClientProvider` 不再 watch `recoveryEpoch`: Dio 与各名称服务在会话内稳定, 恢复后由 2.3 与徽章汇总补拉。
- `AuthInterceptor`: 访问令牌剩余寿命 ≤60s(按 `exp - iat` 减去本机首见后的流逝时间, 不受客户端时钟偏差影响)
  时, 请求发出前走与 401 同一把刷新锁提前刷新, 不再每 15 分钟先吃一轮 401。

### 2.6 通知

- 新增 `GET /api/notices/unread-index`(判定用轻量列: id、发布时间、actionRoute、sourceEvent、是否仍该弹)
  + 摘要; 摘要随徽章汇总每分钟带回, 对不上才重拉索引。删除 `/notices/unread-count`、`/unread-count-by-source`。
- 「打开即已读」(read-by-route / read-by-source)只在索引里确有指向该页的未读时才发; 索引未知时照旧发。
- 到达监听: 游标轮询 20s 一轮(原 2s), 汇总带回的最新发布时间超过本地游标时立即拉; 原「每分钟从纪元
  全量对账」改为按未读索引对账(补拉游标后方遗漏、剔除已读/已办结的排队项), 游标就绪时若索引已在手即
  对账一次(重启补弹); 送达前校验暂时失败 2s 后单次重试。
- **取舍(明确记录)**: 本波按工作令第 2 条采用「游标轮询、间隔拉长到 15-30s」, 没有建推送通道(SSE)。
  代价是新通知横幅与居中审核弹窗的到达延迟从最多约 2s 变为最多约 20s(平均约 10s); 换来每个可见标签页
  每分钟约 30 次 arrivals + 1 次从纪元全量对账 + 1 次未读数 → 3 次 arrivals(未读数与摘要并入 60s 汇总)。
  审计 perf-frontend-02 原文建议的 `GET /api/events/stream`(SseEmitter, 推 notice-arrived / badge-dirty,
  断线退回 30s 轮询, nginx 需 `proxy_buffering off`)列为后续工作; 接入后到达轮询退为兜底, 延迟回到秒级。

### 2.7 主档字典与详情页首屏

- `MasterDictionaryRepository`(会话级, 按字典端点单份缓存 + 单飞): Master/Sales/Finance 名称服务与
  颜色/单位下拉共用; 本端对某类主档的写成功后按写路径作废对应字典并推进修订号, 已加载的服务与下拉自动重取;
  钱流「打开另一张单据刷新账户币种」绕过缓存重取一次。
- 详情页(销售/采购/委外/库存/生产计划)首屏只等详情一个请求; 字典与详情并行, 货品批量查询与人员姓名
  在首屏之后并行补齐再重绘一次; 服务端随单已给的姓名(生产计划负责人/跟单员、计划列表跟单员)直接用,
  只对缺名的补查员工。货品名/编号优先用明细快照, 「先查名称再查详情」两次合并为一次批量查询。

### 2.8 表格

- `MasterDataTableView`: 按列 key 缓存量宽结果(值按字符串去重), 取样 30 行; 数据刷新(含静默重拉、同一份数据
  换新 List 实例)不再整表重量, 帧后只补量新出现的值、列宽只增不减; 换列集合或字号档才全量重算; 保留 shrinkWrap。
- `UtenEditableGrid`: 选中集单独通知(`selectionListenable`), 每行单独订阅、只重建选中态真变了的行;
  表体只随行集变化(`rowsListenable`)重建; 表头筛选结果按「行集修订号 + 列集合 + 筛选值」缓存。
  controller 自身 `notifyListeners` 两类都发(宿主照旧可听), 「看到的勾选 = 提交的内容」不变。

### 2.9 部署

- `deploy/nginx/uten-imp-http-lan.conf`: 443 启用 HTTP/2(首屏并行请求复用一条连接); 文件名带内容指纹的
  静态资源一年缓存 + immutable(经 server 级 map 加头, 不丢安全头, `/api/`、`/actuator/` 排除); 入口与未带
  指纹的资源(index.html / flutter_bootstrap.js / main.dart.js)每次回源校验。

### 2.10 工作台概览的本部门待办: 与红徽章同一口径(permissions-08)

- 此前 `/dashboard/overview` 的「待办任务」按「部门 + 权限码」另写一套计数(报销两条 SQL 与报销模块逐字重复、
  履约三部门各跑一次分页查询、访客/资料变更/工资复核各一条), 与模块卡红徽章是两套规则、两个数。
- 现在计数卡全部取自 `WorkbenchBadgeReadPort`: 生产待排产(含「待排产产品」指标与逾期细分, 来自同一来源的
  事实数)、仓库领料与退料、采购任务、委外任务、访客审批、资料变更审核、报销待审批/待付款(财务报销入口按
  事实数拆两张卡, 两张之和 = 该入口红数)。资格判定是各来源原端点的 `@PreAuthorize`(与红徽章是否出现同一判定),
  部门(含兼职部门与祖先, 用户 2026-09-12 口径)只决定请求哪些入口、卡片是否出现在本人工作台上。
- 来源出错: 该入口本次不出卡(徽章侧保留上一次的数); 原「正在自动恢复」占位卡、
  `dashboard_fulfillment_partition_degraded` 审计与前端 15 秒降级重试删除。无权: 入口缺席, 不出卡。
- 工资批次待复核不再单列计数卡: 提交时已给复核人推「待复核」行动通知(`PAYROLL_BATCH_SUBMITTED`),
  出现在通知待办里, 原计数卡与之重复。
- 删除随之失去调用方的 `ExpenseApproverQueuePort`(上一轮为合并报销 SQL 临时加的端口)。

## 四、后果与遗留

- 原各计数端点仍对外暴露(汇总以 controller 方法调用它们, 复用权限判定); 其中订单进度阶段数与订货财务确认
  两个分段数仍有页面在用。其余前端已无调用, 后续可去掉 `@GetMapping` 只留方法——本波未做: 权限目录工作流
  正在改同一批控制器的 `@PreAuthorize`, 相邻行同时改动会在合并时冲突。
- `AuditNoisePolicy` 里已删接口(`/api/notices/unread-count` 等)的路径**保留**: 审计日志查询
  (`AuditQueryService` 按这张表过滤存量行)与解释器仍要把历史行识别为自动请求噪声。
