# V536：生产成本多实际仓与原单撤回

同一真实执行段分批将同一货品、颜色的成品入库到不同实际仓库时，原成本对象只记录首个仓库池，旧校验会拒绝第二个仓库。另一个关联缺口是成品原单红冲曾走通用出库，未撤销对应成本产出，后续费用仍可能分配到已红冲批次。

本迁移配合 `InventoryProductionCostService`、`InventoryValuationService`、`StockValuationCoordinator` 和 `InventoryProductionCostPort` 修复上述链路。SQL 为 `V536__production_cost_actual_output_pools_and_withdrawals.sql`，既有 V535 及更早迁移字节不变。

## 实际仓库与来源身份

一个执行段仍只有一个成本对象，原 `product_pool_id` 保留为历史产品身份。新增产出允许不同仓库，但货品、颜色、成本业务类型、真实来源 UUID 和公司自有库存身份必须保持一致。每一笔产出仍绑定它自己的实际价值池、原入库流水、原单明细和基本数量；不能用另一仓库参数冒充该笔实物来源。

费用分配仍遍历同成本对象下每一个实际产出节点。没有新增成本对象、执行段或平行库存账，也没有按仓库复制原耗用和费用。

## 原成品入库撤回

正式 `FINISHED_IN` 原单红冲必须先验证原入库明细、原正向流水、执行段、实际仓库和整笔数量。存在未退回的出库或使用、未撤回的后续混合入库时拒绝原单撤回。允许精确证明的整池原出库全量退回同一实际池。真实委外使用的 `POSITION_STORE` 与 `RETURN_ISSUE` 都沿原 ISSUE UUID 和实际池父链核验，可一次全退，也可分批退齐；只有部分退回时不能撤回原入库。中间混入另一笔入库、原料被耗用或改从另一来源归还，不能仅凭数量相等放行。

合法撤回在同一事务内完成以下动作：

1. 原产出事实保留原数量和正向流水，仅追加真实撤回流水引用。
2. 新成本版本将该产出的分配区间置为零，通过原分配任务和分摊明细追加负向分配，把已分成本归还各自原 `COST_WIP` 来源。
3. 本实际池成本传播完成后，精确移除原入库数量，恢复原入库之前的价值池。物理撤回事件引用原 `RECEIVE`，不使用通用平均出库充当来源还原。

此时物理撤回事件金额为零，因为成本已经由上述负向分配回到在制，不能再次扣除。成本历史、原来源金额、原分配明细均保留。重复同一撤回命令复用原结果；另一撤回流水不能再次撤回该产出。后续费用不再流入已撤回产出，换实际仓重新入库则产生新的真实产出事实并参与后续分配。

撤回后的成本版本保留未完成状态，不因任务执行完毕冒称整个工单最终结清。待处理的既有成本任务或前序传播会明确提示稍后重试；不关闭守卫、不用损耗或汇差填平。

## 历史兼容与运维范围

V536 新增产出身份和撤回一致性检查，并延续现有采购/委外原入库撤回分支。已有产出、分摊、价值节点和流水不重写；新产出检查不回填历史虚构事实。原成本对象首池和原来源 UUID 保留。

成本版本的 `output_snapshot.withdrawnMovement` 冻结该版本建立时的真实撤回流水 UUID，并在版本插入时对照原产出核验。委外回厂反向会先按原产出区间归还材料成本，再在同一事务撤回实物；延迟约束不能用提交时的新状态推翻此前已冻结的区间。任务继续核验原耗用 revision、原产出 movement、数量与分母；新版本不能隐去已发生的撤回 UUID 来继续分配费用。既有历史 JSON 没有此字段时保留原未撤回快照含义，不改写旧版本；已撤回产出的新版本必须带有正确 UUID。

迁移不新增或删除任何表，不增加业务列，无需调整停机清库的 CLEAR/PRESERVE 表分类。增加的是函数和触发器；迁移失败应由 Flyway 事务回滚，禁止修复校验和、删除已应用历史或关闭触发器继续业务。
