# 2026-09-25 物料汇总只读诊断与共同验收场景

> 公开仓库脱敏版：物料编码、产品名、单号、记录 ID 与精确业务时间使用一致的匿名标记；保留数量形状和规则用于复现，不能用本文定位业务库记录。原始核对信息仅保存在本地未跟踪目录。

## 1. 取证范围与结论

本次只读取当前配置的本地业务库 `localhost:5433/uten_imp`，对应持久容器
`uten-imp-postgres`，不是临时测试容器。数据库已安装迁移头为 **V708**。
没有执行迁移、修复、更新或删除业务数据，也没有读取其他实例。

查询使用只读事务，设置 `statement_timeout=8s/10s`、`lock_timeout=2s`；最终来源与
数量核对使用 `REPEATABLE READ READ ONLY`。连接凭据、账号、客户资料未写入本报告。

已经找到与“三个顶层名称不同、组件相同”的反馈吻合的分析：

- 分析 ID：`LOCAL-001`。
- 状态：`PARTIALLY_PLANNED`，版本 **13**；本次前后核对版本没有变化。
- 创建：`示例创建时刻`；最后更新：`示例更新时间`。
- 三个销售来源产品各需 1000；另有三个已经下达的自制子项。
- 原分析包含 42 个有效物料节点：3 个 `ROOT_SUPPLY` 和 39 个 `BOM_COMPONENT`，
  即每个顶层各有相同的 13 类组件。

**目前没有发现这次案例在数据库中丢失来源份额或下达总量。**
保护门的三个来源分别关联三个 1000 的已批准计划；弹簧的三个来源分别分配 2000，
共同进入一张 6000 的采购申请。尚不能据此认定页面实现正确：

1. `shortage_qty` 仍是物理库存缺口，**不是“还要下达多少”**。
2. 自制的“已安排”来自子分析项及 `production_material_analysis_plan_links`；
   采购的“已申请”来自 `preplan_supply_actions/allocations`。只查其中一条链会漏数。
3. 汇总显示应合计三份来源，写入也必须保留三份来源。只取首个节点、
   `action_group_key`、子项或 BOM 边 ID 都可能在页面上丢掉另外两份。
4. 当前“三张同料自制工单”是已落库事实。此次展示修正不能静默把它们改成一张，
   更不能通过新增一张 3000 的计划去“补”汇总显示。

页面及接口的具体根因仍需结合前后端读写链和重现测试确认；本报告中的候选原因
不等于已确认代码根因。

现有商业订货本身已经支持一行承接多条采购申请来源：

- `POST /api/purchase/orders` 的 `OrderItemLine` 同时支持主锚点 `requestItemId` 和

## 7. 验收矩阵与不变量

| 场景 | 输入或动作 | 必须成立的结果 |
|---|---|---|
| 三根共有组件 | A/B/C 各 1000 | 保护门 3000、弹簧 6000、胶带 1.5；分别保留 3 个来源节点 |
| 已下达回显 | 基线 B 刷新、重进、切换汇总/展开 | 保护门已安排 3000、追加 0；弹簧已申请 6000、追加 0；不能退回首来源的 1000/2000 |
| 重复确认 | 对同一目标 3000/6000 再提交，或网络重放 | 不再创建任何计划、申请、allocation；已安排量和原单号不变 |
| 单根真实需求增加 | 只将 A 的生产责任从 1000 增到 1200 | 保护门新总需 3200，新增 200 全归 A；弹簧新总需 6400，新增 400 全归 A；B/C 不变 |
| 三根不等量 | A/B/C 分别 1200/900/1500 | 系数 1 组件合计 3600，系数 2 合计 7200；不能按平均数重写各来源份额 |
| 汇总总目标编辑 | 已安排 3000，拟总目标改 3300 | 命令必须明确“总目标”与“本次追加 300”，不能再下 3300；原根责任仍为 1000 的额外部分须沿现有公共超量归属，不伪造销售需求 |
| 已安排后减少 | 原已安排 3000，拟总目标改 2800 | 不能用 `max(差额,0)` 掩盖减少；提示受影响来源并走现有变更/取消规则，已发料与已执行事实不得静默改小 |
| 子层联动 | 中层 H 的一个来源实际计划产量加 200 | 仅该路径的系数 1 子件加 200、系数 2 加 400；先扣该路径已安排量，不能把整个 3200 再乘到每一根 |
| 父级已安排、实物未到 | H 已安排生产或在途供给，但实际收货 0 | “已安排”增加、重复下达余量减少；“可领/可开工/已实收”仍为 0，不能伪造齐套 |
| 同物料多父路径 | 同一顶层从两条不同父路径使用同一原料 | 先分别算每条路径的责任再汇总；BOM 边或货品相同不能去掉合法的第二份需求，也不能把委派后的同份需求算两次 |
| 共享公共库存 | 同一可用公共池 300，三个来源各需 1000 | 所有来源合计只能分到 300，待补合计 2700；不能每个来源各扣 300 得到 2100；具体优先策略必须稳定且可追溯 |
| 并发占用公共库存 | 两个操作同时确认同一库存池 300 | 一个取得相应份额后，另一个重算或返回冲突；不能各成功预留 300 |
| 颜色或路线不同 | 同货品不同颜色，或一个 BUY 一个 MAKE | 可分组展示共同名称，但执行组必须区分精确维度；不得把任意来源当代表覆盖另外来源 |
| 单位/换算不同 | 同材料使用 kg/g 等单位 | 使用可信换算率精确归一后才能合计；原单位快照保留，不能将 2 kg 与 500 g 加成 502；不能无依据跨基础单位合并 |
| 不同仓库 | 相同材料由不同实际叶仓供应 | 保留叶仓库存、预留、出库身份；允许的同主仓协调不能把库存重复计入每个来源或改写实际仓 |
| 既有独立批次的包装/固定批耗 | 已有三个独立工单各需 100、每包 60；或每批固定用 2 | 已冻结三个批次仍为整包 2+2+2=6、固定批耗 2+2+2=6；纯展示汇总不能改掉既有三个批次的投入事实 |
| 新建真实共享批次 | 新建一个真实共享工单生产 300，按每包 60 或每批固定用 2 | 只按真实共享批次的 `f(300)` 展开一次，即 5 包或固定批耗 2；不能复制为三套 BOM 再求和 |
| 先子后父再共享 | 旧三份子料工单已下，随后共同父件创建一个共享工单 | 通过原父节点及相对 BOM 边链建立 alias，旧子料未来实收转入 canonical 子节点；不得再创建一套相同子料工单 |
| 共享后只需旧供给的一部分 | 旧三份独立 M 工单共 3，新共享批次的 `f(总量)` 只需 M=1 | 实际累计下单仍为 3，canonical 只承接 1，其余 2 留原源待受控处置；alias 不是第 4 笔下单 |
| 父部分转交 | 原父需 1500、旧子 C 仅已安排 500，本次共享父 1000 | 原剩余父 500 优先保留旧 C500，canonical 不得同时继承这 500；全部父责任转交后才可按冻结 alias 份额承接 |
| 草稿与审批阶段 | 计划草稿、已提交、已批准、拒绝、取消混合 | 明确各数量所处阶段；取消份额释放后才可再下达，已批准/已执行不能与草稿简单相加或相减 |
| 部分到货/领料 | 已安排 3000、到货 600、实发 250 | 仍是已安排 3000，实物各阶段分别 600/250；不能把剩余未到 2400 误当还需重新下达 2400 |
| 手工数量保持 | 用户改汇总目标后刷新、异步读子层、切换展开 | 已输入目标与源分配保持；只重算对应差额，不能用首行或旧快照覆盖，也不能因数量刷新丢掉选择状态 |
| 来源权限与版本 | 少传一个来源、夹带别分析节点、提交前另人下达 | 服务端校验完整源集合、范围和版本；不能只凭 aggregateKey 或货品 UUID 写入；冲突时输入保留 |
| 筛选与分页 | 三份来源跨分页或被筛选隐藏 | 同一汇总页中的总量口径明确且一致；服务器按完整执行组聚合后分页，不能把当页/可见首行假作全量 |

建议共同的不变量：

1. 每个汇总执行组必须能展开为精确来源集合，`汇总需求 = Σ来源需求`。
2. `汇总已安排 = Σ各来源有效已安排份额`，不得拿整张单据数量重复归给每条来源。
3. `本次追加 = Σ各来源本次合法新增份额 + 明确归属的公共额外份额`。
4. 对这次案例，保护门的来源已安排合计是 3000；弹簧 action、allocation、申请行
   三个层级的合计均为 6000。任何 UI 表示或保存请求都应能解释这两个数。
5. 原责任、生产计划、已申请、商业已订货、到货、实发、报工、合格实收分别计量；
   不能用一个“已下达/完成”数字混合代替。
6. 物料按来源路径计算之后再汇总；汇总行是操作与展示入口，不是替换原来源的虚构节点。

## 8. 建议的测试分层与当前边界

- 前端模型/组件测试：使用 A/B 完整夹具，验证 13 行总量、3 份来源展开、累计与追加列、
  数量编辑保持、选择映射、零追加时不发重复写请求、窄屏和异常重试。
- 后端服务测试：真实三根 BOM 和不同节点 UUID，验证完整源集合的聚合预览与写入一致；
  重点测单根加量、不等量、包装取整、公共额外份额和跨仓范围。
- 真实 PostgreSQL 测试：通过实际规划、申请、审批、预留与出库服务生成 B，
  覆盖幂等/并发、部分执行、取消/反向和来源数量守恒。不要将只有汇总行的手写表当全链证明。
- 联调验收：同一个隔离夹具执行“首次准备 → 下达 → 刷新汇总 → 再次同目标确认 →
  单根加量 → 子层追加 → 部分到货/领料”，逐步对比 UI、接口与源账。
