# 附件与工资保密安全加固报告

> 日期：2026-08-16 · 范围：通用附件系统（人事档案/合同/报销附件）+ 工资（payroll/compensation）保密链路
> 方法：两路并行全量代码审计（附件后端逐行、工资数据流全链路交叉）+ 修复 + 单测验证
> 结论：**未发现附件链路可越权下载他人文件的漏洞**（对象级策略/HMAC 防伪/路径穿越/防覆盖均已验证过关）；
> 工资链路发现 **1 个高危审计日志泄露路径（已修复，V295）** 与若干中低风险项（技术项已修，业务项待决策）。

## 一、已验证安全的关键面（不需修复）

| 攻击面 | 结论 | 关键证据 |
|---|---|---|
| 拿到/猜到别人 storageKey 直接下载 | 安全。storageKey 为 122-bit 随机不可枚举；`openRaw` 三重校验（staff + attachment:view + **owner requireCanView**） | `AttachmentService.java:320-344`、`V240` CHECK 约束 |
| 伪造/重放上传 grant | 安全。HMAC-SHA256 覆盖全部字段（key/owner/user/名字/类型/大小/过期）、域分隔、常数时间比较、一次性 session 状态机（FOR UPDATE）+ 三重防覆盖 | `AttachmentUploadGrantService.java`、`AttachmentUploadSessionStore.java` |
| presign 后权限被收回 | 安全。confirm 二次校验 + 落库事务内第三次 `requireCanManageForUpdate` | `AttachmentService.java:101`、`AttachmentConfirmTransaction.java:40` |
| 路径穿越（`../`） | 安全。四层防护：容器路径段拒绝 → `resolveUnder` normalize+startsWith → OSS `validateStorageKey` 正则 + 拒 `..` → DB CHECK | `LocalDiskStorageService.java:252-258` 等 |
| SVG/HTML 存储型 XSS | 安全。白名单 + 魔数映射均无 svg/html；下载强制 `Content-Disposition: attachment` + `nosniff` | `StorageProperties.java:40-48`、`AttachmentController` |

| 薪酬/PII 字段脱敏 | 安全。无 `employee:compensation:view` 时 baseSalary 等不填充（保持 null）；列表 SELECT 无敏感列；全后端唯一含 baseSalary 的响应 DTO 是 EmployeeDetail 且按权限置 null | `EmployeeQueryService.fillSensitive` |

## 三、三项业务决策的落地（2026-08-16 同日复核 V212 矩阵后实施）

1. **`payroll:view:all` 无组织范围限制** → **复核结论：无需改动**。V212 部门矩阵（单一权威来源）
   中该权限仅授予 `DEPT_HR`（连同 generate/review/publish/export）；V06 种子的 manager 角色
   自 V29/ADR-011 起不再参与权限合成。实际可见面 = HR 部 + 超管 + 权限管理页逐人加授，
   与"HR/授权者可见全员"的业务预期一致。若日后财务需共管，在权限管理页按部门/个人加授即可，
   不属于代码缺陷。
2. **报销单与发票图片对审批人全公司可见** → **复核结论：无需改动**。`expense:approve`/`expense:pay`
   仅授予 `DEPT_FIN`（V212）。财务集中审批全公司报销是设计业务流（中小企业通行做法），
   "审批人可见待审单"恰是职责所需。若组织扩张后需按部门分流审批，届时再引入部门过滤。
3. **档案附件对 `employee:view` 持有者可见** → **发现真实漏洞并已修复**。复核 V212 发现
   `employee:view` 因**员工选择器**需求授予了几乎所有部门（GM/HR/FIN/PROD/ENG/PMC/SALES/
   RAIL/NEWMEDIA/QA），而原 `EmployeeAttachmentAccessPolicy.view = 本人或 employee:view`——
   等价于**全公司任何人可翻看任何人的身份证件/合同扫描件**（员工列表/选择器暴露 ownerId，
   附件接口只差一层同样全员持有的 attachment:view）。
   **修复**：EMPLOYEE 与 EMPLOYEE_CONTRACT 两个策略的查看权收紧为 `employee:pii:view`
   （档案文件=身份证/银行卡级 PII，语义完全吻合；V212 中该权限仅 DEPT_HR + 超管可持）。
   前端员工详情「档案文件」Tab 与合同附件入口同步按 `attachment:view + employee:pii:view` 门控，
   无权限显示说明性空态；员工「我的文件」自服务不受影响（本人恒可见）。
   新增 `EmployeeAttachmentAccessPolicyTest` 六个用例，其中含关键回归：
   **仅持 employee:view + attachment:view 的用户必须被拒（NOT_FOUND）**。

## 三·甲、上传图片客户端压缩（2026-08-16 同日上线）

对齐主流 IM/审批应用（微信/钉钉/飞书）的客户端压缩策略，新增
`lib/shared/attachments/attachment_image_compressor.dart`：

- **触发条件**：图片（jpg/png/webp/bmp）且 >300KB；GIF（保动画）、小图、压缩无收益时保留原文件。
- **参数**：长边 ≤1920px 等比缩放（覆盖 A4@200dpi 扫描与主流手机照片），JPEG q85（业界"肉眼无损
  与体积"平衡点）。典型收益：手机原图 3-8MB → 300-800KB，存储与下载流量降一个数量级。
- **实现要点**：解码走 dart:ui 原生解码器（自动应用 EXIF 方向、目标尺寸解码——从不按原尺寸
  解压超大图，与后端 40MP 校验双保险）；白底合成去透明通道；JPEG 编码在后台 isolate 执行不卡 UI；
  扩展名/Content-Type 同步改为 .jpg（与后端魔数校验保持一致）。压缩是标准 JPEG：下载后任何
  看图工具可打开，应用内预览不受影响。任何异常退回原图上传（fail-open，服务端校验兜底）。
- 上传成功提示会注明压缩收益（如"已上传 a.jpg（图片已压缩 3.2MB → 480KB）"）。
- 单测：`test/attachments/attachment_image_compressor_test.dart`（大图压缩/小图与 GIF 保留/损坏数据降级）。

## 四、遗留观察（记录在案，暂不动作）

- `UTEN_HMAC_KEY` 一钥两用（附件 grant 有域分隔；身份证确定性哈希 `TxSessionVars.hmac` 无域分隔）。两侧消息格式互斥、交叉伪造当前不可行；若重构需注意**身份证哈希不可变域前缀**（改了会找不到存量密文），建议新场景用独立密钥。
- 本地后端 `download-grant` 响应的 `expiresAt` 无强制力（每次请求重鉴权，安全性等价更优，但语义与 OSS 不同）。
- 附件端点（presign/raw）无用户级限速；上传有配额（10 个/100MB 每用户）兜底，下载仅靠审计可追溯。可在反代或应用层补限速。
- payroll 表无数据库行级权限（RLS）兜底，保密完全依赖应用层校验；DB 账号与运维账号分离、`pg_hba` 来源限制是运维侧应确认项。
- 工资条 PDF 下载后明文落盘到本机下载目录（文件名含工号）——本人设备属功能预期，共用电脑场景可考虑 PDF 打开密码。
