## 一、问题

大量产品和深层 BOM 同时分析时，页面把任务入口、建议路线、操作列、冗余数量和完整路径混在一起。主表缺少标准多选，搜索与全屏分成两行，空白占据主要区域；路线学习又可能让员工看不到本次实际选择。

还有两个会影响业务判断的缺陷：原父树转交需求后，真实 child 物料被展示过滤一并隐藏；直接层完整套料分配和深层诊断独立使用同一公共库存池，合并显示时可能重复计算。

## 二、现行决策

### 2.1 三入口，状态在详情内部

主页面保留“下达采购 / 下达委外 / 下达车间”。每个详情分“未下达 / 已下达 / 需处理”，显示精确任务、来源、进度和当前下一步。已有部分计划但仍有剩余量的产品可同时出现在未下达和已下达，两个计数不可加成总需求。

采购/委外任务的数量确认、分块、CAS、幂等和409恢复仍共用宿主页命令；详情页保持在前台，完成后更新当前行集。车间计划在表内填写数量、车间和负责人，提交时返回宿主页做预览与生成反馈，不再进入旧计划向导。任务详情沿宿主页权限，不注册另一套页面授权或递归挂载权限按钮。

### 2.2 主表只展示重点

共享 `MasterDataTableView` 默认八列：身份/层级、供料路线、本批需求、现货分配、齐套缺口、待补数量、预计供给、进度/待办。完整路径、计量、仓库、权益与来源放进双击详情，删除处理列和独立建议列。2026-09-14 修订（[ADR-081](ADR-081-下层一键办齐与物料表身份列统一.md) §4）：身份格副行的编号 / 颜色 / 单位提升为三个独立列（八列 → 十一列），身份列改名「物料名称」且不再挂级联号 P1 / P1.1、最底层不再画圆点；「待补数量」改名「下单数量」；「现货分配（已备数量）」已于同日撤除、改「可用数量」。三个分桶详情用同一组身份列，第一列仍是「物料办理」。

表头设置、全屏、搜索、产品/物料视图切换共用工具条。浅色下名称、层级和路线文字为黑色；2026-09-13 起选中行统一淡绿底（primaryContainer 35%）+常态字色（原「选中后白色+深绿底」口径退役）。表格实例在全屏切视图时保持稳定。

多选以实际任务为单位，跨页和筛选保留并显示准确全局数量，提供全局清除与显式全选筛选任务。带真实 ROOT_SUPPLY 的产品标题只选择根自身，不递归选中子 BOM；缺少根 UUID 的旧标题和跨页补充祖先只读。聚合物料选择明确展开到其各条精确路径，不能把上下文重复计量。主表100行/页，采购/委外详情200行/页，车间编辑表首屏100行后增量装载。

### 2.3 记住上次路线，由人明确确认

- 历史确认/已下达事实与手动草稿优先；未确认节点使用货品、颜色、单位 UUID 的上次确认路线，随后回退主档，无可用值才默认委外**(2026-09-16 起默认值只来自货品主档，见本节末修订)**。本分析已加载默认冻结，不能因确认一组而改掉未选路线。
- 进页恢复只读 last-routes 预填，按100货品分块并限制并发。会话、权限、分析版本和加载代际隔离迟到响应，失败可见；加载本身不保存、不下达。**(2026-09-16 起本条整条作废，见本节末「2026-09-16 修订」。)**
- “确认路线(N)”从与显示完全相同的草稿解析器取值，只提交所选真实任务。根节点和组件共用确认协议，禁止另一套“显示主档、提交统一委外”的回退逻辑。
- 原因可空，主确认不强制弹窗。旁边“原因(选填)”只编辑选中草稿，可填、清空或取消，直到明确确认才写入；不伪造原因。V477将旧2字下限前向放宽为NULL或trim后1..1000字符，合法路线和确认人/时间仍必需。
- 已下达/被计划或产出交接占用的根路线冻结。旧右键即时保存与“采纳建议路线”入口继续退役；恢复记忆不恢复自动业务写入。

**2026-09-16 修订：路线记忆改为货品主档单一事实源，`/last-routes` 退役。**
本节原设计里的「记忆」是一条**只在前端预填层存在**的通道：按货品 + 颜色 + 单位去历史分析里捞最近一次
`confirmed_route`。它盖住了真正的缺口——确认路线只写分析行，货品主档 `goods.source_type` 从来没被更新过，
而新分析的建议路线又是从主档算出来的，于是用户实测「在物料分析准备页改了供应方式，下次进来还是老的」。
改法：确认路线在**同一事务**里回写 `goods.source_type`(BUY→采购、MAKE→自制、SUBCONTRACT→委外，含
ROOT_SUPPLY 根行；值没变不落盘，真改了抬 `goods.version`)，同一条 UPDATE 把本行 `source_suggestion`
对齐成确认值(否则下一次刷新会把刚确认的路线当成「主档事实变更」清掉)；建议路线只读主档；
`lastRoutesPerGoods` / `GET .../last-routes` 端点与前端分块读取、并发限制、迟到响应隔离整套删除。
存量确认由 [V598](../数据迁移/189-V598货品来源按路线确认历史回填.md) 一次性回填(每货品取最近一次确认，
最新胜出——旧前端本就是记忆优先于主档，这样用户看到的默认值不变)。
本节其余约定(历史确认/已下达事实与手动草稿优先、确认取值来自与显示同一个草稿解析器、根与组件共用确认协议、
原因可空、已占用根路线冻结)全部不变；变的只是「默认值从哪来」这一条。

### 2.3-A 根产品是可确认的真实供料对象

V478以 `production_material_analysis_items.root_material_id` 引用唯一的 `ROOT_SUPPLY` 物料行，前端 `rootMaterialLineId` 使P1标题直接承载根的路线/复选框，无第二条重复根行。ROOT深度0，普通BOM深度1..10；根维度与换算率不可事后改写。

根MAKE直接按原分析行生成生产计划，不调用notify再创建MAKE child；根BUY/委外走现有供料链。已确认MAKE且服务端可排产时允许待料下达；generate与approve仍独立。没有ROOT字段的旧响应保留根区域只读兼容，不生成伪UUID。

根库存按基本单位，计划按来源单位。外部供给通过追加式FULFILL/REVERSE账本交接，root_fulfilled_qty由事件净额换算投影，和submitted/approved共同受原需求上限保护。销售预留、精确入库权益和收货反向都需匹配同一来源切片；已进入拣货或发货时禁止直接撤回。详见[V478迁移说明](../数据迁移/94-V478顶层供料路线与产出交接.md)。

### 2.4 真实 child 需求必须可见

`MAKE_COMPONENT / SUBCONTRACT_MAKE` 仍是服务端真实所有权和生产任务，不因界面隐藏第二个产品根而消失。按产品把 child 物料挂到精确来源节点；按物料包含其有效需求，原父树已交出的零需求后代不重复计量。无法解析来源的 child 保留为明确异常，禁止按同货名称猜父级。

勾选与下达始终使用 child 自身的 `analysisItemId/materialLineId/actionGroupKey`。相同货品、相同 BOM nodeKey 在不同产品下仍是不同需求；汇总只做展示，不物理合并来源。

### 2.5 先下达车间，齐套后再实际执行

`lowerLevelPending` 是下层缺料诊断，不能阻止有权人员显式创建完整剩余需求的子件任务。无任意部分 `delegated_qty` 时，仍禁止只交接一部分所有权。

计划资格读取 `canSchedule/maxSchedulableQty`。部分齐套的计划保留 READY+WAITING 拆分，WAITING零预留、无DRAW，可先进入车间任务。齐套器必须证明整个待料执行段可满足，才同事务生成完整预留、DRAW、READY和Outbox；仓库与精确车间分别收到待发/待领提醒。全部正式需求真实发料为FULFILLED后才允许开工。

无BOM任务仍依赖单独的ZERO_MATERIAL/DIRECT_MAKE证据；WAITING无DRAW不能被解释成无物料自制。报工、FQC与实际入库分别记账，只有仓库实收才增加库存和iqty。

### 2.6 主仓只作范围，实际领料仓不变成父仓

顶部只列主仓，展开所属可用叶仓范围，最多100个且不静默截断。实际领料子仓由设置入口指定；`warehouseId`仍为物理落点，`warehouseIds`只作参考集合。旧分析保持原仓，未调入实际领料仓的其它仓库存不能算齐套。

这只是V476层级之上的界面范围选择，不修改V471的精确仓库合同，不给父仓开放收发存或预留。规则见[V476](../数据迁移/92-V476仓库主子层级.md)。

### 2.7 公共超量必须独立分账

初始版本“直接扩大需求量、无需新账本”已退役。V472/V474下，真实未绑定需求扣除在途后仍是需求上限；BUY或无子层委外的额外公共量单独确认并保存，不扩大本分析allocation/exact。后续分析只能显式采用已批准公共在途，容量锁和延迟约束防止重复占用。

例：A需求500、批准2000，A只归属500，公共1500；B采用1000后公共剩500。公共安全补库按ADR-056另分切片。MAKE和有子层委外不开放公共超量**子件任务**，子件任务仍按全部实时剩余需求创建。2026-09-14 修订（用户口径「生产是可以超出数量下达的，超出部分就是公共的，其他计划可以占用」）：**本批生产量本身可以超出该任务行的剩余需求**——超出部分记在计划关联行的 `public_surplus_qty`（[V577](../数据迁移/169-V577下达车间超量与公共备货产出.md)），归本需求的量照旧占 `submitted_qty`，`requested_qty` 与 `submitted+approved<=requested` 守恒一个字节不动；多做的产出入库后不被本需求消耗，自然留在公共库存供其他计划使用。它**不会**自动扩大下层物料需求（锚点行本就不展开自己的 BOM、父件计划产出按物理缺口封顶），下达前界面二次确认点明这一点；2026-09-14 起「多做那批的料由计划员另行安排」不再靠人拿计算器——下达成功后由[ADR-081](ADR-081-下层一键办齐与物料表身份列统一.md)的「下层一键办齐」按 BOM 把这段需求算出来并分流下达。销售订单来源的顶层行仍按订单未满足量封顶：超产会同时踩销售分摊守恒与订单未满足需求校验，须另立备货任务。车间桶超量**不要求** `over_supply` 权限（与采购不同），有下达车间权限即可。

## 三、继续有效的相关决策

### 3.1 计划仍按独立分析行生成

同车间批量输入只减少重复操作，不物理合并计划头。当前 `production_plans.material_analysis_item_id` 和来源关联仍按一分析行对应独立计划。共享计划头、独立来源明细须另行迁移plan_item桥和执行/反向守恒，本轮未实现；同货更不能直接合成一条物理执行明细。

### 3.2 销售条款与默认车间

必填空值红框，系统预填黄框并提示核对，用户修改后移除预填提示；错误优先于预填。销售客户最近订单的结账方式、发运策略、币种仍可通过last-terms补空，采购/委外行级条款沿ADR-068既定机制。

销售订货单价只读，由权威主档/报价带入；折扣可调，金额服务端重算。该销售规则不受物料路线预填策略调整影响。

默认车间唯一来源是V192 `production_goods_workshop_preferences`，只在正式确认/合法改派学习。默认负责人来自所选车间的组织树负责人，未维护则留空，预填仍可人工修改并通过服务端资格校验。

### 3.3 权限与历史

页面、工作台入口和权限管理目录统一到 `production.material-analysis`。route、notify、generate、approve、over_supply、claim_shared_future等权限分别控制对应动作，并与服务端allowedActions及对象范围求交；采购/委外来源链接还需对应对象权限。V472已登记的公共超量/采用权限继续有效，本轮不新增权限码或默认授权。

历史确认路线、业务单据、来源UUID及已应用迁移不改写；旧活动分析经授权刷新补充根节点并应用新计算。路线默认值只是未确认草稿，不是新授权或自动下达(2026-09-16 起默认值读货品主档，原按历史分析推导的 GET 记忆已退役)。ROOT_SUPPLY沿production.material-analysis的route/notify；MAKE生成与审核分别要求generate和production_plan:approve，零新增权限码或默认grant。

## 四、数量准确性与性能

直接层完整套料分配是已保护量，深层诊断只能使用剩余公共库存；exact继续归其受益节点。父件已有库存时只按父件真实短缺展开子料，不能因为另一种直层材料不足就重复采购已有父件的子料。

节点索引使用 `analysisItemId + nodeKey`，深层分配用稳定优先队列避免反复全表扫描。纯计算测试为5000产品/10000节点共享2000份库存，两次样本为0.390/0.503秒；它不是数据库、HTTP、浏览器或真实并发压测。前端单分析500来源限制仍有效。

同批委外BOM分流共用一次批量查询，500产品重复物料的查询预算回归确认不再逐行往返。未引入BOM结果跨请求缓存、增量数据库计算或物理合单，不能宣称全接口已达到该纯计算耗时。
