## 第二波

### maengine 物料分析引擎根治(ADR-115, V689-V692)

**为什么**: 用户最痛的"点下一步要等半天"。实测: 公司服务器 4GB 堆 100 来源下达 20 计划 19.4 秒、500 来源 55 秒; dev audit 里 issue-plans/preview p95 18.7s、issue-plans 最慢 20s, 预览之间排队到 22 秒。第一阶段并发核心已去掉 md5 与重复发现, 但引擎本身的"反复重算"仍在。

**负责发现**: perf-material-analysis-01/02/03/04/06/07/08/09/10/12/13/15/16, perf-warehouse-quality-02, perf-warehouse-quality-11, perf-warehouse-quality-03(去掉库存写命令上的主仓锁, 依赖本节第 6 点完成), correctness-stability-04, correctness-stability-08, overhaul-gap-05, perf-frontend-10/11/12, dup-frontend-split-13, dup-backend-split-25。

**文件边界**: `server/.../features/production/analysis/**`、`production/mrp` 下被物料分析调用的计划草案/计划包/执行包服务的"沿用本事务已校验快照"入口、可用量单一函数迁移; 前端 `lib/features/production/pages/material_analysis_*`、`production_material_analysis_page.dart`、`models/material_cascade_math.dart`、`models/production_material_analysis.dart`、相关 repository 方法。

**目标(用规模测试证明)**: 14 行分析各命令 <300ms; 2460 行分析预览 <800ms; 30 计划下达 <2s; 100 来源下达 <3s。用 `ProductionMaterialAnalysisScalePostgresTest` 与 ProductionJdbcMeasurement 语句预算钉住。

**怎么做**(同一 worktree 先服务端后前端):
1. 刷新拆三段: `load`(只读) → `project`(纯函数, 含锚点增长) → `persistDiff`(只写变化行); 表头版本只在指纹变化时 +1; 删掉计划关联触发器 `fn_sync_material_analysis_plan_link_qty` 里对表头版本/指纹的改写(新迁移 CREATE OR REPLACE)。
2. 下达预览新服务: `@Transactional(readOnly=true)`, 不取任何分析锁/主仓锁, 不建计划不回滚, 由内存投影直接出视图; 一致性测试: 同输入"预览结果"与"真实下达后 GET detail"逐字段相等。
3. 一条命令只在末尾刷新一次, 命令内全程共用一份内存 Inputs/Projection(删 detailInternal 的中间重读)。
4. 下达车间按批: 先建全部计划, 执行快照/可用量对全部 planId 一次取; 草案/审核/确认沿用本事务已加锁快照(新增 saveValidated 等入口); 物料分析路径不再调 MRP 预览; planService.create 在该路径只回 id/单号/行。
5. 供给动作状态对账改为下游事件驱动(采购/委外订货审核、收货、IQC 判定、取消/关闭时同事务更新动作状态), 刷新不再跑 13 条 UPDATE; 过渡期至少合成一条集合语句+水位跳过。
6. 仓库/品质/成品点收命令不再在自己事务里同步 refreshLocked: 改为对受影响分析写 stale 标记(一条集合 UPDATE), 提交后由 outbox 消费者按分析去重异步刷新; 分析读取与命令入口发现 stale 先刷新一次; 车间齐套提升不得依赖分析快照。完成后从库存写命令的锁计划里去掉主仓 advisory 锁(只留维度锁+单据行锁), 并发一致性用例全绿后才算完成。
7. 服务端一次办完: `POST /production/material-analyses/{id}/orders`, 请求带全部层的车间/委外/采购行, 一个事务里父先子后(同层先车间再委外, 采购最后), 末尾刷新一次、只回一个视图, 任一步失败整体回滚; ADR-102/104 并入规则与超量权限在服务端按层重放。
8. notify 逐组查重型视图改为循环前一次预取; 热路径视图改维护列或集合查询(见 perf-material-analysis-13)。
9. 可用量单一实现: 数据库函数 `fn_analysis_material_availability`(与 MainWarehouseStockBudget 同一主仓预算分摊), MaterialAnalysisService / PreplanAnalysisStockPegService / ProductionExecutionReadinessService.batchAvailability / ChainNoticeService 全部改用它; 先写过渡属性测试比较三套旧实现, 逐条裁决后删除旧实现。
10. 来源同步批量化+无变化不写; 删除已退役的 MAKE 权益委托归还(restoreAllMakeDelegations 等)及其表/事件类型。
11. 命令响应不再回整份分析视图(返回 {analysisId, version, changedLineIds, 表头汇总}), 客户端按 sinceVersion 增量拉取; GET 详情支持版本号/304。
12. 前端: 所有预览单飞+尾随(同时最多 1 个在途, 离开页面取消); 服务端预览达标后删除 `material_cascade_math.dart` 与 `_optimistic*`/估算层/"三级来源"逻辑; 下单改调一次 `/orders`; 45s 全量轮询改版本比对(不变不拉, 隐藏暂停), 自动读不记"查看"审计; 12 个 part 文件 10 层继承的巨型 State 拆成 Riverpod 控制器+独立 Widget(纯计算下沉 analysis/ 目录可单测), 每文件 ≤1200 行, 输入时只重建当前行与合计条。现有 `material_analysis_*` 与 `production_material_analysis_page_test` 保持绿(按新交互改写需逐条说明)。

**文件边界**: `features/warehouse/**`、`features/stock/**`(StockDocService/StockService/valuation/**/StockReservationService)、`features/purchase/receipt/**`、`features/subcontract/receipt/**`、`common/finance/ProcurementOrderClosurePolicy` 与 `ProcurementReceiptConsiderationService`、PreplanAnalysisStockPegService 的入库归属集合化入口(只加集合 API)、GoodsOwningWarehouseSyncService; 前端仓库批量出库/委外出仓批量页。

**目标**: 7 行 IQC 入库 ≤80 条语句且 <500ms; decide-batch 7 行 <1s; issue-batch 单张 <300ms 且 N 张线性斜率 ≤ 单张×1.2; 到货登记 5 行 purchase_receipt_items 更新 0 次。全部语句预算测试钉住。

**怎么做**: 下游全部提供集合 API(settleStockIns / recordMovements / attributeInspectionStockIns / storeAll-issueAll), `INSERT ... SELECT unnest ... RETURNING` 批量写, 删 V298 legacyAttributed 兼容分支; 订单结案每命令对订单集合算一次且 `IS DISTINCT FROM`(生产计划 is_closed 三份副本合成 ProductionPlanClosure.recompute(集合) 供日报/库存单/计划共用); 批量出库只在开头预锁一次、内核不返回 detail; 到货登记单段内核一次写成最终明细; 归属仓与建议库位不再写货品主档行(读时派生或独立事实表), 去掉库存写路径的货品行锁; 价值账写入一次成形; 生产侧直接 new StockDocument/UPDATE stock_documents 作废的 6+5 处收敛到 StockDocService 唯一入口; 客户端循环逐单(拆单提交财务、批量出库)改服务端批量命令。

### prodwrite 生产写路径(ADR-117, V696-V698)

**为什么**: 日报审核 p50 2.2s, 4 行直送 15.1s(按行 ×4 放大, 5 行以上必超前端 15s); 委外发料草稿 PUT 只写 4 行却 1.2-5.6s(第一阶段已降到 46 条语句); 多执行段订单行完结封顶直接被拒("暂不支持跨多执行段")。

**负责发现**: perf-production-exec-01/06/07/10/12, correctness-stability-09, dup-backend-split-24。

**文件边界**: `features/production/**`(除 analysis/ 与读路径 ProductionExecutionWorkbenchService), `features/subcontract/material_issue/**` 与 SubcontractMaterialPlanService.reserveDraft, warehouses 表冗余列; 调 StockDocService 批量点收只调用不改内核。

**怎么做**: 直送按线边仓分组每仓一张多行放行+一张多行 FINISHED_IN(批量点收上下文), 按收料工单每单一次提升与一张 DRAW, 通知合并走 outbox 提交后发, recomputeClosed 按计划去重; 幂等键改"报工+仓"; 行与单据映射表保留以支持按行红冲; 改写 V584 行守卫(新迁移)。多执行段完结封顶/红冲恢复: 确定性分摊规则(最晚开工段倒序扣减), 一个 PG 函数完成全部段扣减, 红冲按事件反向; `sales_order_items.planned_qty` 与段 planned_qty 改派生(视图或触发器维护), 删 Java 手工镜像。齐套可用量: warehouses 冗余 main_warehouse_id/is_operational_leaf(触发器维护+回填+一致性测试), availabilityRows 改等值连接+一次聚合, tryPromote 只读一次。补偿任务改消费 `production_readiness_dirty`, 保留夜间全量安全扫描, 候选条件改"可用量之和 ≥ 剩余需求"。段进度计数(毛报工/有效报工/FQC/成品点收/可恢复)持久化到段上, 所有增减经 SegmentProgressLedger.apply 一处维护, 夜间对账兜底。委外发料草稿差量保存。

### capacity 公司服务器容量(ADR-119, V702-V703)

**为什么**: 用户要求"考虑公司内部服务器性能, 系统操作不吃性能"。公司服务器: 单机同时跑应用+Nginx+PostgreSQL, 内存约 31GiB, JVM -Xms512m -Xmx4g(C2), PG shared_buffers 4GB/work_mem 16MB/max_connections 100, Hikari 池 20, 约 140 名员工。

**负责发现**: db-schema-10, audit-retention-settings-08, overhaul-gap-07, perf-frontend-02 的 SSE 部分(第一阶段只把通知轮询 2s 降到 20s), 以及以下新增要点。

**怎么做**:
1. 每请求开销: JwtAuthFilter 每次请求都从库里重算整份权限分解。改为按 (userId, auth_version, authorization epoch) 缓存权限快照(Caffeine 有界+过期); 先逐一核实部门调动、在离职、矩阵保存、覆盖、委派、负责人指派都会推进 epoch 或 av(缺的补上); 账号状态与会话仍每请求校验(与 auth_sessions 查询合一条 SQL)。前后对比每请求 SQL 条数。
2. 所有列表 size 统一上限(如 200)。
3. 盘点全部 @Scheduled(ScheduledTaskCatalog): 高耗任务改事件驱动或夜间错峰, 有界批量、互斥防重叠, 运行结果持久化(重启不丢)并在服务器状态页可见。
4. DataHousekeepingScheduler(保留登记表: 表/时间列/条件/保留天数/批大小, 分批删除并写一条 system 汇总事件): refresh_tokens 与访客 token、访客短信码、business_outbox 已处理行(先把去重约束改为只约束未处理/死信的部分唯一索引)、各 *_commands 幂等表(按幂等窗口)、task_claims 已释放行(排除被引用的)、通知已读等; outbox 死信计入服务器状态告警并提供重试。真库测试证明只删过期行。
5. SSE 推送: `GET /api/events/stream`(SseEmitter, 事件源用现成 business_outbox 投递), 推 notice-arrived / badge-dirty / doc-changed; 前端 EventStreamClient(Web 需流式读取方案), 在线只靠推送, 断线退 30s 轮询; 三份 nginx 模板对该路径关缓冲、read_timeout > 心跳; 多标签页用 BroadcastChannel 只留一个连接。
6. 可观测性: 500 响应带 requestId, 异常类/错误码/消息摘要落库; 服务器状态页展示按路径 5xx 率与 p95, 超阈值站内告警。
7. 资源预算模板: 给单机 31GiB 出资源划分(JVM 堆/元空间/线程栈、PG shared_buffers/effective_cache_size/work_mem×连接上限、OS 缓存), JVM 参数(G1、堆上限、OOM 行为), Hikari 池与 PG max_connections 匹配核数; PG 模板加 random_page_cost(SSD)、effective_io_concurrency、checkpoint/wal、高频更新表 autovacuum、pg_stat_statements、log_min_duration_statement=500ms; 更新 `deploy/setup/phase2-postgres.sh` 与 `deploy/simple` 模板和 RUNBOOK(不直接改服务器)。
8. 压测: 可重复的并发压测脚本(k6 或 Python asyncio, 放 `server/perf/`), 模拟约 140 名员工混合操作(工作台/列表/详情/检索/下单/审核/入库), 用公司同款 JVM 参数起本机实例对克隆库跑, 记录 p50/p95/错误率/CPU/内存, 写进 docs 作容量基线(大数据版本在 final 用老库全量引导库再跑)。

### squash 迁移压成基线且保留服务器数据(ADR-126)

**用户要求**: 压成基线, 但公司内网测试服务器原有数据要保留(不要重建库)。
**做法**:
1. 前提: 所有代码波完成、全部迁移已落地、服务器已先部署"压缩前最后一版"(让服务器库跑到压缩前的最终版本号, 例如 V69x)。给这一版打 tag `pre-squash-final`。
2. 生成基线: 空库跑完全部旧迁移 → `pg_dump --schema-only` + 必要种子数据(权限目录、系统设置、编号命名空间、分类根等; 以 BusinessDataResetService/reset 脚本 PRESERVE 清单为准)→ `V1__baseline.sql`; 删除 V2 起全部旧迁移(git 历史保留)。
3. 结构一致性证明: 新基线建的库与旧迁移建的库做规范化 `pg_dump --schema-only` diff 为空(函数体、触发器、索引、约束、视图、种子数据逐项)。写成 Postgres 测试。
4. 重基线脚本 `server/ops/rebaseline_flyway_history.sql`(只改 flyway_schema_history, 不动业务数据): 校验 当前最高版本 = pre-squash-final 的版本 且 结构指纹 = 基线指纹, 通过后在同一事务里清空 flyway_schema_history 并写入一行 V1 baseline(checksum 取新基线文件)。失败即回滚、原样退出。写进 RUNBOOK: 先完整备份并实际恢复验证, 再停应用 → 跑脚本 → 部署压缩后版本。
5. 同步五/六处迁移头(见 04 文档)、`verify_candidate.py`/`migrate.sh` 对版本集合的计算、302 个解析迁移文本的测试改为对 Testcontainers 库做 catalog 断言、60 个手写 DDL 的测试改共用 Flyway 基线并删 column-debt-baseline.txt/dynamic-ddl-files.txt 守卫。
