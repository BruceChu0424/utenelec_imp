# 品质、报工性能与安全维护

本次在 `uimp/quality-report-performance` 独立工作树实施。后端量测基线为 `4c9f8dc89`;
随后吸收主链 `4b9c403a2` 的员工选择器修复, 与本次修改无重叠; 合并准备时同步到 `0cd8866ea`,
两次主链树身份均为 `4e5f96ab8af92af938f30f2bc9e858061848520d`。计划部下单不在本次范围。
本文记录源码、受控本地验证和复测方法, 不表示服务器已升级或真实密钥已轮换。

## 根因与处理

| 路径 | 确认的问题 | 最终处理 |
|---|---|---|
| IQC 先入后检 | 自动实收后再次通过整单结案推进同一生产来源; 物理确认和外层重复关单 | 根命令统一关单一次, 新的完整品质结案编排保留原入库批次身份并推进一次; 删除旧布尔开关协议 |
| FQC 批量放行 | 按份反复读同一批已锁检验、重放记录与 FIFO 放行余额 | 单笔/批量共用批内核, 批读后按原顺序消费余额; 每条决定、来源份额、真实入库单仍独立保存 |
| 分析同步刷新 | 每次执行全部来源类型的状态更新, 即使该分析没有对应采购、委外或自制来源 | 锁内一次读取实际来源类型, 仅执行有候选类型的原规则; 不异步延后权益, 不重建计划下单逻辑 |
| 报工保存/审核 | 每行重复读取执行段、销售分摊与累计产量 | 集合加锁、集合查询; 等锁后用新语句重新读取计划/包/车间身份, 不用等待前快照 |
| 实际用料 | 报工命令丢弃返回值, 却逐段构建完整清账页面 | 共用原写入与权限内核, 报工/反向命令省去无人消费的响应投影; 页面查询保持原响应 |
| 车间直送 | 成功提升后已经检查线边仓出库, 上层又重复检查 | 显式返回本轮是否已完成检查, 早退仍补查, 后续调用仍重新读取动态事实 |
| 直送库存单 | 刚锁图并审核成功的草稿又做第三次完整物理预锁 | 使用既有“已锁定单据”入口产生新守卫; 保留源复核、真实库存读取和原已审单据的完整锁图 |

保留库存价值模型、节点/边/事件、动态余额锁与数据库守恒校验。剖面中的大量价值写入是实际来源事实,
不能用删守卫、合并来源单据或延后库存权益换取较低语句数。前端正常报工审核本来就消费返回详情,
不重复加载详情; 创建后的完整请求回执仍保留, 不删除结果不确定时的恢复协议。

## 量测口径

原 `.local-tmp/2026-10-06-后续待办方案.md` 与原探针已不存在, 因而不能把新夹具与历史 6.7/14.3 秒
直接混算改善比例。新夹具使用合成业务, 经过正式服务与全部 Flyway 迁移, 包含实际事务提交:

- IQC: 四张采购/委外收货单, 两种来源、两个实际仓, 先上架后品质实收入库及原键重放。
- FQC: 四次独立报工与四份先入后检登记, 一次批量决定产生四张真实入库单, 核对观察分析刷新与重放。
- 报工: 十个不同执行段的十行报工, 真实用料; 创建与审核分别计量。
- 压力分支: 十一个直送接收方, 核对实际库存、用料、成本来源、同键重放。

性能采样显式关闭 `verify-nested-footprint`, 正确性测试保留诊断开关。早期继承诊断开关的样本
已标记为诊断证据, 不参与性能验收。三项 PostgreSQL 持久化设置均实际查询并要求为 `on`。
异步通知投递等已声明的旁路不计入窗口, HTTP、客户端渲染、夹具准备和成本预收敛分别排除。

本地可复跑入口为 `server/ops/run_quality_report_performance.py` 的 `prepare` 和 `run`。
它冻结原版/候选主类、同一套测试类、源码与镜像身份; 只复制已有缓存, 离线执行。专属 Linux
Docker daemon 不向宿主发布 API、不挂宿主业务目录, 量测网络不经过 Windows 发布端口。
该入口的 JVM 限 4 CPU/6 GiB、堆 4 GiB, PostgreSQL 使用两侧相同的容器默认资源。
每侧三次重复, 普通 JSON 与 FQC profile 的清单、源码/字节码身份、诊断开关和持久化设置符合
才接受证据; 同时保留宿主 CPU、IO、内存观察, 不把环境差异当作代码收益。

本地 r5 两侧各四个业务方法通过、每侧 30 个样本完整、前后全树校验一致。可确认的结构变化如下:

| 场景 | 原版 JDBC 次数 | 改造后 JDBC 次数 | 原子提交数 |
|---|---:|---:|---:|
| IQC 四张一行收货单 | 1154 | 1104 | 各单独立, 共 4 次 |
| FQC 四份实际入库 | 687 | 654 | 1 次 |
| 十个执行段报工创建 | 153 | 72 | 1 次 |
| 十个执行段报工审核 | 650 | 586 | 1 次 |
| 十一个直送接收方审核 | 3314 | 3193 | 1 次 |

r5 候选期间出现本机其它 Java 与 PostgreSQL 测试, 因而不拿这轮时延作达标证明。r6 只复测了基线:
相同字节码、相同 3314 次调用的复杂直送中位数从 r5 的 5096 ms 变为 6762 ms, 足以说明单机
时间/负载差异不可忽略; 这不证明某一个进程是全部差异的原因, 也不排除代码自身的性能风险。

正式时延验收使用独立 GitHub Ubuntu 工作流 `quality-report-performance.yml` 和
`server/ops/run_native_quality_report_performance.py`。同一运行机顺序执行原版/候选, 共用冻结的
候选测试与运行依赖, 保留各自生产类和资源。工作流保存原始 XML、样本、身份清单与汇总;
最终运行链接、实际中位数/范围和验收结论永久记录在 [PR #39](https://github.com/BruceChu0424/utenelec_imp/pull/39)。
只读取对应源码提交的证据, 不使用其它提交的绿灯。三次合成服务场景既不是生产 P95, 也不包含
HTTP 和页面渲染; 调用次数减少本身不能证明历史 6.7/14.3 秒已变为 1.5/2.2 秒。

## 九项安全代码

| 原编号 | 交付内容 | 操作边界 |
|---|---|---|
| C1 | 固定无前缀历史密钥版本; 默认关闭、本地超管本人再认证的小批轮换; 检查日志安全、核对明文等价、断点与重放 | 不自动轮换或删除真实密钥; 查询结果始终不授权删旧备份密钥 |
| C3 | 附件与 AI/成本/报价原件统一扫描, 包括历史原件读取; 独立追加证据 | 每次真实扫描, 不缓存“干净”判定; 私有两连接池继承主连接安全策略并有严格期限, 不耗尽外层业务连接 |
| C4 | 历史 local/OSS 访问默认关闭; 现役 internal/ClamAV 预检与只读引用盘点; 删除竞争的旧现役模板 | 未认定的旧业务记录与文件不自动删除; 退役内测链明确保持 closed-local |
| C5 | V829 保留四类安全审计; 正式环境默认关闭测试清空, 生产 Nginx 拒绝测试入口; UI 说明同步 | 开发/受控测试的原超管、再认证、排水与回执不放宽 |
| C8 | 更新器在停应用前检查 migrator 可读性, 以 `uten-imp` 身份运行迁移 JAR | 数据库专用迁移角色及备份/失败停机处置保留 |
| C10 | 保留既有 IP/账号限流与锁定期不验真实密码; 从持久审计汇总同来源十分钟十次失败告警 | 通过审计只读端口返回哈希来源与计数, 不向通知暴露原始审计或 IP |
| C12 | 完整备份之间验证后硬链接复用, 损坏/跨盘回退复制, 修正共享文件释放空间计数 | 禁止链接在线原件; 每套备份保持可独立校验, 不把文件验证冒称实际数据库恢复 |
| C13 | 运行版本绑定物理 JAR, 本地双仓健康采样收回仓库并复用三恢复点规则 | 只读健康入口, 不自动执行真实备份、过期清理或恢复 |
| C15 | ClamAV Unix socket、应用组最小访问与协议/超时校验; OCR 预置模型只读 | 真实模型准备及现场服务安装按受控步骤执行 |

群机器人配置已删除。主机事件有界落盘, 通过持久 UUID 去重后进入平台中央确认;
未知事件独立节流、单项失败不阻断其它收件人、损坏队列会提醒通道故障。客户端在展示前重新取授权详情,
切换身份/隐藏页面中断旧弹窗, 明确的已删除通知不永久重试。后台完全停机期间只能保留本机事件,
恢复后补送, 不宣称平台弹窗能提供外部宕机通知。
