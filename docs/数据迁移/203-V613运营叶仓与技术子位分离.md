# V613 运营叶仓与技术子位分离

日期：2026-09-19。源码候选；不代表服务器已经安装。

## 根因与决策

一个原先独立收发的正常仓库，首次同车间直送时会在其主仓下自动配置线边位置。旧代码把任何子节点都当作实际子仓，因此只增加了技术子位，就把原来的正常存放仓判成了不可收发的父仓；旧库存仍在原 UUID，但选择器、入库守卫、供给计算会将它排除。

运营叶仓统一定义为：普通仓库没有有效的普通子仓。技术线边子位不改变其实际收发身份。线边位置自身仍不得有任何有效子节点，且不作为普通单据的新选仓。

新增 `fn_warehouse_is_operational_leaf(uuid)`，统一生产需求分配、物料分析、计划供给、就绪补偿、采购到货记忆、产成品登记、销售实仓分配等查询。Java 仓库范围服务、共享选择器和侧滑面板按同一规则判断；原来的独立仓可直接选定，不会进入只有技术子位的空层级。

`fn_warehouse_is_active_accounting_leaf` 在运营叶仓基础上继续要求启用、记账、祖先链完整且全部启用，并排除线边位置。采购 IQC 入库、预上架、产成品预上架与销售确认出库的数据库守卫都使用这把尺子，保留原有审核、财务与来源约束。

## 公共库存与直送隔离

普通仓原有库存继续参与公共可用量和同主仓安全库存预算。技术位置库存从公共预算中排除；需求在技术位置预留时，数据库必须确认确有指名该需求的有效直送（含合法拆批谱系），并退出公共安全库存预算。普通仓与技术位置继续各用原 UUID 记账，不混合成本、不转移历史余额。

本迁移只新增/替换函数，无历史数据搬迁，无虚构仓库，无历史单据改写。V610 的默认仓边界仍有效：正常入库学习普通仓，直送技术入库不污染主档。

## 验证与兼容

回归场景：原独立仓已有普通库存 → 自动技术子位挂接后仍为运营叶仓 → 真实 IQC 与销售出库守卫接受原仓 → 物料分析仍识别原仓公共库存并排除线边公共供给；技术位置不可通过普通仓选择接口，普通子仓仍让父仓只作聚合。

数据库变更以当前函数定义的精确锚点断言为前提，源形态不同即停下，避免覆盖其他修改。历史已执行 SQL 不改，前向新增 V613。部署须与引用该函数的应用同时升级；回退应用不能撤销数据库历史，修复继续前滚。
