# V557：IQC 批量报告的完整请求身份

本迁移给现有 `procurement_inspection_events` 增加可空 `batch_request_hash TEXT`。新 IQC 同单批量合格/检验报告，将完整规范化请求的 SHA-256 冻结到该批原 PASS/FAIL 事件。原事件 UUID、来源、合格/不合格数量、金额、重量、操作人与发生时间的规则不变。

## 解决的问题

旧 `decide-batch` 在查询事件重放前，先按当前状态和原剩余量检查。成功提交但响应丢失后，同一请求会因为已 RESOLVED 或剩余量已扣减而被拒绝；跨收货单的前端操作在中途失败后，也会被已经成功的前一张单阻断。

仅比较 PASS/FAIL 的数量和原因，不能证明原批成员、操作人提交的剩余量或另一条零量分支。发生时间和审计日志都不是原请求身份，不能拿来猜测旧 body。

## 新请求和历史兼容

- 新 `pass-batch`、`decide-batch` 摘要包括操作类型、采购/委外类型、收货单 UUID、规范化原因以及按稳定 UUID 排序的全部成员、expectedRemaining、PASS/FAIL 数量和每行幂等键。数量不同的小数表示和请求成员顺序不影响相同请求判定。
- `decide-batch` 继续使用原 `-P`、`-F` 派生事件 UUID；`pass-batch` 继续使用原行键的 UUID。服务器查询每行两个潜在分支，即使本次将其中一个数量写成 0，也不能绕过原分支的历史证据。
- 只有完整事件集合、完整摘要以及逐事件来源/动作/数量/原因全部一致，才允许在当前状态 CAS 前完成重放。修改剩余量、原因、数量、成员，遗漏原 FAIL 或仅有部分事件均拒绝，不追加品质或金额事实。
- 旧事件保持 NULL，不回填、不更新。旧单行 `dispose` 的原事件重放语义保持不变；旧 `pass-batch` 保留已能证明的逐行全量 PASS 数量/原因重放。这不宣称能恢复旧批的完整成员集合。
- 旧 `decide-batch` 无完整摘要时保守拒绝重放。工作人员应核对检测记录和当前待检余量，再明确办理尚未完成的行；不能更换幂等键重复已经完成的决定。
- 外部行键仍限定 8–128 个合法字符。内部派生 `-P/-F` 在原行键验证后计算，不因后缀错误缩短已声明的 128 字符输入上限。

## 数据库和事务保证

新增 CHECK 仅允许 NULL 或 64 位小写十六进制。V222 的 `trg_00_reject_procurement_inspection_event_mutation` 为 `ALWAYS`，其函数无条件拒绝 UPDATE/DELETE，因此自动保护新增字段；不改旧函数和任何已应用迁移。新增可空无默认值列不改旧行内容，不新建业务表，清空对象集合不变；本地清空脚本仅维护支持头至V557/515，不代表执行清空。

同一收货单内先规范化全部请求，取得原完整商业/库存/仓库/分析锁，再一次锁定整单 IQC 行和核验来源。逐 UUID 依次写 PASS、FAIL、资金冻结、价值位置及原通知；同一行的后一个事件使用前一笔已写累计量，保留原金额/重量区间计算。任一步失败整单事务回滚。

订单关闭只依赖仓库实际入账量与实退量，不读取本批中间 PASS/FAIL 数量。服务现在在全部事件写完后，对收货单涉及的不同订单各更新一次，随后核对一次整单终态并执行原生产跟进；PASS 仍不会增加库存或立即使生产齐料。跨收货单仍分别提交，前端需准确显示已经成功和仍待处理的分组。
