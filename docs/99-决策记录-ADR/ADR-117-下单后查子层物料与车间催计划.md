# ADR-117 下单后查子层物料与车间催计划

- 日期：2026-09-24
- 状态：已接受(V703，一张新表；零新增权限码)
- 来源：2026-09-24 用户口径「物料分析准备页可以分批下单或者追加，有时只下了父类的物料、子物料忘记下」
  ——计划侧下单后要提示并能一键补下单；车间侧要看得出「计划还没安排」并能催计划。
- 关联：[ADR-102](ADR-102-物料分析一张表直接下单.md)(主表一张表直接下单、`netShortageQty`「还缺数量」)、
  [ADR-099](ADR-099-计划量单一入口与子层按计划产出展开.md)(子层按计划产出展开)、
  [ADR-095](ADR-095-车间路线开工前随时可换与逐种物料事实.md)(车间任务逐种物料事实)、
  [ADR-108](ADR-108-前端性能徽章汇总会话快照与刷新时机.md)(徽章一次汇总)

## 背景

物料分析准备页允许分批下单与追加(ADR-102)，父件下单后下层子件的需求跟着放大(ADR-099)，但下层要不要
补、补多少，界面上只有主表里一列「还缺数量」，计划员一忙就漏。漏掉的后果在车间才暴露：车间任务一直
「缺料 · 等待到货」，而实际上那份料根本没人去订。车间看不出差别，只能打电话找计划。

## 决定

### 1. 「缺」只有一个口径

计划侧、车间侧所说的「还缺 / 计划还没下单」一律是物料分析那一行的 `netShortageQty`(主表「还缺数量」)：
需求扣掉现货已分到、已下单在途(含可自动认领的公共在途)、子件已排的计划。预览估算值不算——库里没有那张单。
发货 / 参考阶段的行(`controlStage` 为 SHIP / REFERENCE)不参与。

### 2. 计划侧：下单后查下层，弹窗去补

- 触发点：主表「下单(N)」、下达采购 / 委外 / 车间三个分桶页(含「父件 + 下层一起下单」页)、行菜单下单，
  **成功之后**。靠下单前后「累计已下单量」快照对比找出这次真正下单 / 追加的件(失败、只预览、被拒的不算)。
- 沿 BOM 往下(最多 10 层、300 行)：刚下单的件下面还有「还缺数量 > 0」的料，弹窗
  「下层物料还不够 · 做不够 N 个」，按钮「稍后再说」/「去补下单」。
- 「补下层物料」页：按树顶分组列出所有缺的料，数量按缺口预填；没下过的写「下单」，下过的写「追加」，
  二者不混(追加只增不减，与主表同口径)。本页不另存一份数据——输入框、车间 / 负责人、供应方式与提交编排
  (`_submitMaterialTableRows`：车间逐层父先子后 → 委外 → 采购，失败即停)全是主表那一份，下完主表的
  「下单数量 / 追加下单 / 还缺数量」当场就是新的。一轮下完更深一层又缺的，自动列出下一层；全部补齐显示「都下够了」。
- 页面顶部常驻提示条：已下单的件下面还有缺的料时琥珀色提醒；有车间在催时变红「车间在催」，补料页给那几行挂红标。

### 3. 车间侧：「等计划下单」与一键催计划

- 服务端端口 `WorkshopPlanningGapReadPort`(实现在物料分析模块)：车间任务缺口桶里的每种料，映射回物料分析节点
  (`fn_analysis_plan_material_matches` + 货品 / 颜色 / 单位)，该节点「还缺数量 > 0」即「计划还没下单」，
  数量封顶到本任务自己的缺口。每个分析整页只算一次完整视图。
- 我的车间任务：状态列新增品红档「等计划下单 · 缺 N 种」/「已催计划 · 等下单 N 种」(与琥珀「已下单等到货」
  一眼分开)；车间自己能先办的(可开工、可领料、已交仓库待发)与「待选生产路线」仍排在前面。物料列多一段
  「计划未下单 N 种」，逐种物料表把这些料标成「等计划下单」(计划还没定供应方式的写「等计划定供应方式」)。
- 任务详情里一个品红提示块：缺哪几种、催过几次、最近谁什么时候催的，右侧「催计划」。
  `POST /api/production/workshop-tasks/{id}/planning-urge`，权限与开工 / 领料同一把
  (`production_execution:view` + `start`)，范围与车间任务列表同一范围。30 分钟内再点不再打扰计划员，
  如实告诉车间几点以后能再催；计划刚好已下够单时 409「不用再催」并刷新。
- 新表 `production_planning_urges`(V703)：一个车间任务同一时刻最多一条在催记录(部分唯一索引兜并发)，
  再催只加次数。

### 4. 计划员收到什么、什么时候消失

- 每次有效的催(不在冷却里)发一张居中待办卡「车间催你下单」给：这份物料分析的制单计划员 + 计划 / 生产部门里
  能在物料分析页下单的人(`production_material_analysis:view` 且有 `notify` 或 `generate`)；再催时先撤上一张，
  一个车间任务只留最新一张。卡片直落被催的那份物料分析(`?analysisId=`)，进物料分析页即置已读。
- 生产 hub「生产计划」卡红色徽章 `productionPlanningUrges` = 计划员可见的分析上仍在催的车间任务数；本人草稿退到
  标题旁(UtenHubCard 口径)。
- 办结：计划员在物料分析页下单后立即请求核对(`POST .../workshop-urges/reconcile`)，后台
  `ProductionPlanningUrgeReconciler` 每 5 分钟兜底；缺口归零记 `ARRANGED`，任务完工 / 取消记 `TASK_CLOSED`，
  同时撤卡。GET 读侧不写库。

## 不做

- 不自动替计划员下单，也不在下单时强制连带下层(只提示 + 一键补)。
- 不改「还缺数量」的算法，不新增权限码；催计划只是协调提醒，不改任何需求、库存或单据数量。
- 不做催采购 / 催委外(料已下单在途的，由既有到货链路负责)。

## 后果

- 车间第一次能分清「料在路上」和「料没人订」；计划员漏下的子件在下单当下就被拦住，漏网的还有车间催。
- 物料分析页在下单后多一次分析详情读取(已有)与一次核对请求；车间任务列表对有缺料的任务按分析各算一次完整视图。
