# 分析关联订单货品清单页 (只读)

- 路由：`/production/material-analyses/:id/sales-orders/:orderId`
- 页面：`lib/features/production/pages/production_analysis_sales_order_page.dart`
- 权限：`production_material_analysis:view`(**不要求 `sales_order:view`**) + 物料分析对象级范围
- 权限面：复用 `production.material-analysis`(与入口页同一面，右上角「权限设置」入口正常出现)
- 端点：`GET /api/production/material-analyses/{id}/sales-orders/{orderId}`
  → `AnalysisLinkedSalesOrderService.linkedOrder`
- 决策：[ADR-088](../99-决策记录-ADR/ADR-088-待排产扣除分析承接量与关联订单只读清单页.md)
- 入口：[生产物料分析页](生产物料分析页.md) 顶部卡片「关联销售订单」里点某个订单编号

---

## 一、为什么另立一页，而不是跳销售订单详情

销售订单详情是**业务单据页**，带编辑 / 审核 / 财务确认 / 价格一整套动作与字段。
计划员从物料分析点过去只是要核对「这张单到底订了些什么货、还差多少要生产」。
把他放进销售单据页，等于把一堆与他无关、也不该给他看的东西一并暴露出来
(用户原话：「不然很多比如加个啥的都能看到」)。

所以本页是一张**专用只读页**：

- 全页零写入动作：没有编辑、没有审核、没有右下悬浮按钮；
- **纯数量口径，不返回也不显示任何单价 / 金额 / 折扣**——生产口径看不到销售价格；
- 权限只要分析查看权，作为交换，服务端过**两道闸**：
  ① `MaterialAnalysisService.requireReadableAnalysis` —— 按 `maker_id` 隔离判定
  调用方能不能读这张分析(跨制单人需 `production_plan:view:all`)；
  ② `orderId` 必须确实被这张分析引用。
  **只做 ② 是越权**：那只挡住「换订单」，没挡住「换分析」。
  两条都由 `AnalysisLinkedSalesOrderServiceTest` 钉死：闸一不过时**一条 SQL 都不发**，
  闸二不过时**第一条 SQL 之后不允许再发出任何取数查询**，且统一吐 404 不吐 403。

## 二、页面结构

**顶部单头事实卡**(key `analysis-sales-order-header`)：销售单号 / 客户 / 跟单员 /
开单日期 / 交货日期 / 状态徽章。**不出单头备注**——销售备注是自由文本，
现实中常写折扣与付款条件，正是这个刻意绕开 `sales_order:view` 的页面最不该泄露的东西。
跟单员按老库回落(`seller_id` 为空时按 `seller_legacy_id` 匹配)，迁移单据也显示得出名字。

状态徽章 = 单头状态(待审核 / 已审核) 叠加已财务确认、已结案、已中止三个独立位；
已中止标红、已结案中性、已审核成功色、其余警示色。

**表格**(key `analysis-sales-order-lines`)：全站统一 `MasterDataTableView`，
14 列，货品身份三列口径(名称 / 编号 / 颜色各占一列，规格留在名称格副行，ADR-081)：

| 列 | 说明 |
|---|---|
| 行号 | `line_no` |
| 货品名称 | 副行显示规格 |
| 编号 / 颜色 | 各占一列 |
| 单位 | 未维护显示「未维护」 |
| 订货量 | `qty` |
| 已发 | `shipped_qty` |
| 未发 | 未交付量 = 订货 − 已发 + 已退 − 核销 |
| 已预留 / 已排产 / 已完工 | `reserved_qty` / `planned_qty` / `produced_qty` |
| 剩余未排 | 剩余未排量 = 未交付 − 已预留 − max(已排产 − 已完工, 0)。**链路口径，不扣物料分析承接量**，所以可能大于调度台「待排产」段看到的缺口。列名刻意不叫「待排产」——同名不同口径会让人拿两屏数字对账 |
| 交货日期 | 行级优先，缺省取单头 |
| 本次分析 | 该行是否是当前这张分析的来源行 |

来源行整行浅色高亮(`primaryContainer` 28% 透明)：一眼看出「这张单里我这次分析的是哪几行」。

**合计条**：表体下方 `UtenTotalsSummaryBar`(`summaryBar` 槽位，表体内滚时合计条始终可见)。
六项：行数 / 合计订货 / 合计已发 / 合计未发 / 合计已排产 / 合计剩余未排。
数量一律走 `utenQuantityTotalEntry` 按 `unitId` 分组，**不同单位绝不相加**
(同一张单里「个」和「箱」分别显示)。

本页**一次取完整张单的明细，不做服务端分页**，所以这里的合计就是全单合计，
不存在「看着像总计其实只覆盖一页」的问题。

## 三、口径与边界

- 返回的是订单的**全部**货品行，含已交付完、已核销的行。本页是「这张单订了什么」，
  不是待办队列，所以不做 `chain_status` 过滤。
- 返回键 `popOrBackTo`：会话内从物料分析页 push 进来，正常一路 pop 回去；
  栈空(Web 深链 / 刷新)时回 `/production/progress`。
  **不能**回 `/production/material-analysis`——那是一条不带 analysisId 的静态路径，
  退回去是一张空白的新建分析页，等于把人丢在半路。
- 空态 / 错误态 / 加载态全部交给 `MasterDataTableView` 渲染，错误可重试。

## 四、验收缺口

- `UTEN_RUN_DB_TESTS` 门控的真实 PostgreSQL 用例尚未覆盖本端点，
  当前证据是替身 EntityManager 的行为测试 + 源码文本断言；
  真库上「未关联订单 404 / 关联订单全量行 / 数量列口径」三态待补。
- 切账号越权走查(计划员 / 纯调度 / 跨制单人)未做。
- 读取会记一条 `view_sales_order_detail` / `sales_orders` 审计(与销售侧详情查看同一
  action/targetType 对)：这是一次跨模块读，必须可追溯。
