# 财务往来原表操作与恢复说明

本文供主任务合并成最终Word指南。当前是独立分支的实施记录，功能尚未发布；示例图片为本地真实Flutter组件渲染、匿名演示数据，不能当作公司实账或已部署截图。首次AP全链与原对账末尾资料仍在实施，未完成部分不计入已验收。

## 辅助核算项目

1. 进入“辅助核算项目”，按财务原账套、原项目编号、原项目名称建立目录。编号为文本，保留前导0；不同原账套或不同原编号保留为不同项目。
2. 按实际类别选择客户、供应商、员工或其他往来对象。客户/供应商可选择原历史对象；员工使用最小业务引用，不需打开HR名册。其他往来按原账套/原编号明确建立对象。
3. 未确定系统对象时可“保存草稿”。已经保存目录不代表已经入账；未对应真实对象不能提交会计分录或期初。
4. 已有分录或受审辅助期初引用后不能直接更换业务对象。原姓名可以更名，已入账的原名称快照不会被当前名称覆盖。

维护需要公司完整财务、财务报表及科目维护权限。无维护权限可查看已授权范围；员工候选和名称回显使用相同权限，不借HR查看权放宽。

## 应收/应付账款明细表导入比对

1. 选择所核对期间和币别属性，再填与会计凭证一致的原账套，选择原XLS/XLSX文件。
2. 预览核对原14列表头、原编号、借贷方向和金额。应付原文“期初贷款余额”“方向4”，两表原文“方向20”按财务提供文件保留。
3. 错误行保留原行号和字段。缺金额、编号被转成数值/公式、隐藏数据、精度超限、余额勾稽不一致时不会猜零或自动改数；修正原文件后重新预览。
4. 点击“导入辅助目录草稿”只建立辅助身份及科目关联。原对方金额不写入总账，也不替代本方应付/应收。
5. 点击“与总账本币比对”。系统按原账套、类别、原编号查到辅助UUID，再逐科目、辅助项目和币别核对。“辅助编号未维护”“缺少总账依据”“待核对”“有差异”“一致”分别显示，不把缺少来源当作零。
6. 导入后可从最近批次恢复。本人普通导入查看仍按本人批次；会计期初审核人通过专用会计授权读取被选中的原资料，提交人关系由会计接续流程再次校验。

这些明细金额是总账本币，即使科目属性写“美元”，也不会直接把本币当作美元原币。真实0户由受审0证据保留，正负不同户不先净成0。月份来源未完成核对或核对后又变化时，期末及有关合计保持待核验。

## 货款/模具款分类及付款分配

1. 在应付账款汇总表外进入“货款/模具款分类”，选择真实应付项目。按单据及实际约定选择“货款”“模具款”；同一应付可明确拆成两类。
2. 原币金额与本币金额分别完整分配，不使用前端浮点计算，不自动补尾差。整笔属于一类时可明确点击“全部分配为货款”或“全部分配为模具款”。填写实际来源依据后确认。
3. 从同一项目下进入“付款行分配”，选择原付款行。分开填写该行的原币份额、实际付款本币、账面核销本币；各轴总额必须分别等于原行。不能将同一笔付款全额放入两类。
4. 从“抵销两端分配”进入真实抵销记录。贷项类别和应付类别分别明确；例如已有货款贷项实际抵模具应付时，使用“贷项货款抵应付模具款”，不把两端改为同一类凑数。
5. 已确认来源分类被付款或抵销分配引用后不能独立改成另一套归属。原记录、分配依据、请求编号和旧版本保留；后续受控整链更正仍须验收，不能删除历史批次覆盖。
6. 原应付账款汇总表保持15列名称及顺序，两个“付款金额”和两个“货款余额”仍在原位。分类和关联分配完整时才显示分类值；未完成时显示待核验，已证明的总应付金额保留。
7. “付款金额”为供应商实际现金，余额按账面核销。货款和模具款的现金减账面差额在原表外核对，不揉进货款冲销；退货保留原负数，反审按原事实在实际反审日反向。

![货款模具款分类实际组件，匿名演示](../../output/finance-party/screenshots/货款模具款分类-实际组件.png)

来源分类需要对应的财务确认权限；付款分配需要付款审核权限；抵销分配需要供应商结算确认权限。全部写操作仍需公司完整财务及相关往来/报表查看权限，未因此放宽实际付款、核销、账户或反审权限。

## 供应商预付款、应用与实际退款

1. 先在现有会计用途设置里，把“供应商实际预付资产”对应到财务明确的资产科目；再维护该科目财务代码、会计币别和供应商辅助对象。系统不会按“预付”字样或同名公司自动配对。未配置时保留原付款草稿，并明确提示缺项。
2. 通过原采购付款入口登记无应付明细的预付，必须填写真实银行账户、原币、实际扣款、手续费、流水号和时间。原制单与审核职责分离保持；审核后只有一次资金支出和一次借预付资产/贷真实银行的GL，不生成负应付。申请执行产生的付款沿用原申请批准约束。
3. 从应付原入口的表格操作区进入“供应商预付款”。与现有表格相同，单击选中、双击打开；表头设置、全屏、分页及窄屏操作面板沿用原组件。打开实际原付款后，先做“货款/模具款分类”，原币与账面本币分别完整分配并填写原依据。
4. 点击“应用到应付”，使用现有正式应付选择器，只选同供应商、同真实原币的一笔正式应付，明确原预付类别、目标应付类别和本次原币。目标尚未分类时可打开其原分类窗口补齐。服务器读取两个原源各自的账面本币份额并处理汇差；应用不再付现金，不重记采购成本。
5. 实际退回预付时点“登记实际退款”，按回单填写真实到账账户、退回原币总额、账户币别净到账、实际手续费、实际账户折本币汇率、银行流水号和带时区的入账时间。保存为待审核记录，须由另一名有收款审核权限的财务核验后生效。不得用银行净到账冒充退款总额，也不按历史预付汇率改写真实银行到账。
6. 处理记录中双击有效预付应用可反审；退款记录中双击待审核记录可审核，已生效记录可反审。原付款仍有有效应用或退款时禁止先反审原付款；后续实际付款/抵销也会冻结其之前的应用。先撤后发生的事实，再按原GL和原银行金额对称反向，不手动改余额。

## 中断、重复点击和反审

- 明确的校验拒绝保留输入并允许修改，不替用户清空金额或来源依据。
- 上传或保存结果未知时固定原文件、原账套、原批次或原请求编号。操作区冻结，使用“核对并重试原上传/原批次/原请求”，不重新创建另一笔。
- 访问范围或登录身份变化后旧结果不发布到新身份。重新进入本人的原批次，核对服务器已保存结果；不能直接以新请求重复付款或应付。
- 结算按真实依赖顺序撤回。已有“先付款→后抵销→更后付款”时，先反审后付款，再撤后抵销，最后处理此前付款。错误顺序应在任何银行或GL反向前被拒绝，eligibility显示相关原单号和抵销记录。
- 新操作在持有同一应付锁时记录真实先后关系；旧存量不按日期或同名推断并批量改写，原抵销余额快照校验保留。

## 原对账纸面末尾继续实施

以下属于原附件要求，不是额外优化，尚未最终验收：对账期间及抬头、双方实际名称、同币历史未结和期末余额、质保金的实际未结归属、金额大写、原收款账户资料、联系人与电话、双方确认及签章、附件确认件下载。无来源不填样例公司、账号或人名；功能需要让财务后续自行维护并走相应确认。

共享预览/打印/导出元数据约定为`documentMetadata`（有行时兼容首行`__documentMetadata`）：`version=1`、`title`、`partyId/partyName`、`currencyId/currencyName`、`dateFrom/dateTo`、`footerLines[{key,label,value,basis,pending}]`。原明细列不增加技术字段；零发生月份也应承载真实历史未结和纸面末尾资料。


## 首次应付确认（2026-11-03 接续实施中）

本节记录当前可继续的入口与操作，不代表采购、委外、IQC 和全部附件已最终验收。当前优先验证启用状态下的真实整链；未完成的待确认来源 IQC 贷项仍须继续实施，不能靠设置关闭算完成。

1. 在原“委外对账单/供应商对账单”选择真实供应商及实际原币，进入原工具栏“对账确认”。主表、表头设置、全屏、分页、窄屏操作面板均复用现有 Uten 表格；原对账单列名、列顺序和原入口不变。
2. 有相应完整财务/会计过账/供应商确认及科目设置权限的人员，在“首次应付设置”明确生效日期及实际依据。启用前维护存货资产、收货暂估债务、待确认供应商退货资产、正式应付用途；后三项需对应唯一财务代码、会计币别和明确供应商辅助维度。缺项会明确拒绝启用，业务金额不猜配。真实金额和来源由财务后续自行维护，不需要先补齐附件样例金额。
3. 生效后新审核的收退货先进入“待确认来源”。候选与正式应付是不同身份；原供应商付款选择器只显示真实正式应付。实物审核、质检及仓库入库继续沿原业务操作；收货成本引用原已批准计款和真实暂估候选，之后财务确认不会重记库存成本。
4. 在“待确认来源”勾选已核对的行，可以跨页保留已选来源。一次只提交同一供应商、同一实际原币的1至500个来源。金额来自服务器已冻结计款，只读，不在这里编辑金额凑差。
5. “提交对账确认”填写实际会计确认日期、对方确认日期及确认人、来源依据，并选择实际原确认件（原电子表/PDF/签章图片）。本次提交编号、原文件 bytes 和SHA共同固定；同编号异内容拒绝覆盖。
6. 另一名有相应权限的财务，在“确认记录”双击待审核记录，下载并核对原确认件及全部来源后审核。只有审核成功才产生唯一正式应付和暂估转应付GL，不再借记存货。原收货商业日期、暂估日期、合同到期日与实际财务确认日期分别保存。
7. 原付款、抵销继续从原业务入口办理。须撤回时，按真实依赖先撤后发生的付款/抵销，再反审对账确认，最后反审原收退货和库存。直接先反审原实物来源应被拒绝，不能手动改余额或消除历史。

## 原生业务科目对应与冻结债务（2026-11-03，接入中）

维护入口组件为 `showFinanceNativePostingAccountsDialog(context)`，由主任务挂在现有财务科目/取数设置工具区。窗口沿用 Uten 主表、分页、弹窗及窄屏操作面板，不改变财务附件的入口名、分类名、原表列名。

1. 新增对应版本，选择原生会计用途、实际交易币别适用范围、已经明确对应系统 UUID 的财务科目，填写生效日期与依据。会计科目的币别属性与真实交易原币分别维护，不把美元科目的本币值当美元原额。
2. 如只对一个往来对象适用，从辅助目录选择已经明确绑定客户/供应商/员工/其他往来真实 UUID 的项目。未选择对象时按该用途范围，在实际过账时通过真实关系读取辅助编号；不按同名公司关联。
3. 保存为待审核版本，由另一名有完整财务、科目维护和过账权限的人员审核。原记录不改写；变更再次新增版本。选择“恢复原有全局用途”同样形成独立受审版本。
4. 新业务冻结使用的对应版本和原币单位。后续付款/收款逐笔冲回原债务的科目与辅助，修改对应仅影响后来符合生效条件的新业务。资金实际收付、手续费和汇差沿用原权威链；不会再次记库存或重复现金。
5. 超时或响应未知时，输入和请求 UUID 保留并锁定。点“核对并重试原提交”使用原完整请求核对结果；不要重新新建同一版本。审核响应未知时先刷新核对原行，或重试同一行。

## 原往来已记账后补充科目与辅助证据（接入中）

原 AR/AP 行详情可以打开 `showFinanceNativeDebtCorrespondenceDialog(context, ledgerId: 原行UUID)`。这里只补原真实分录的代码及辅助证据，金额没有可编辑输入。

1. 选择原已记账分录，再选择与它同一个系统科目 UUID 的财务代码。窗口不会把当前用途里另一科目混进候选。
2. 选择实际往来辅助对象；辅助编号、公司名称相同也不能代替实际客户/供应商 UUID。来源目录主表沿原操作习惯双击选择；选到其他真实对象会明确拦住并保留输入。
3. 填写原凭证及辅助核对依据，保存待审核核对。另一名具备完整财务、AR/AP查看、科目维护与过账权限的审核人，打开同一原行核对记录，双击待审核记录完成审核。
4. 审核只为同一原 entry 增加守恒分配证据，不再产生 AP/AR、库存或资金。已完整冻结的记录不允许在这里换科目、换币别或换对象；实际更正使用原受控更正链。
5. 响应未知时使用原请求重试；保存已确认成功且输入没变化时不重复新建核对。刷新可以核对原审核结果。原账套凭证或原币来源不明的历史导入不会被这里按当前用途猜配。

## 旧未结与原账套期初接续

旧未结接续窗口复用原Uten主表及明细输入表，原台账行通过真实ledger UUID打开。先读取受验旧数据截止日、初始未结本币及旧记录原币，选择同一截止范围的原账套期初分录/核算明细，再明确本/原币份额与依据。关联以真实对象、entry/allocation及原SHA为键，不凭同名或同额推断。每个旧目标明确一个会计核算范围；多个旧目标可以分同一原期初，不能超原金额。

保存只建待审核关系，另一名财务核对完整来源与份额后审核；不会新增AP、总账、库存或银行金额。原金融原币资料未知时保持待核，旧系统已核原币独立保留，不能拿美元科目名称或旧记录数替补金融原币。

固定原分配700仍属于该旧业务，不会因后来还100而释放给公用重复借用。例如原期初5000、核给旧未结700，一般财务可用4300；旧业务还100后仍4300。若公用来源已有实际清偿或预留，审核会同时核可用量，不抢其他已声明来源。期初关系撤回前须先按依赖顺序撤回后续实际结算，原单和原GL保留。

未启用已记账原账套期初之前，原来合法且已受验的旧目标保留原业务收付款流程，标“原立账科目/期初待接续”；这个默认用途仅表示本次记账，不假称历史科目证明。真实期初启用后，必须有原真实分录或已审接续，缺对应时进入本窗口。普通导入草稿不切换模式。

本域真实数据库v7和随后native/减免联合v2已通过：原5000中的700双审关联、实际银行付款100、公用仍4300、反向恢复、未知金融原币保持待核，以及原预付应用/实际银行退款链。界面已加入账号及服务器隔离的私有草稿；中断后可恢复原份额、原依据和同一未知请求，不能重新生成一次写入。当前窗口组件包含390窄屏/1.5倍文字与私有恢复回归；这不是完整Web/Windows实机验收，Win7写入口仍未迁移。

## 对账原件的手续费/尾数逐单决定

1. 先保存并由另一名财务确认原“委外对账单”或“供应商对账单”原件，再从该原件打开“手续费/尾数”。窗口只列出这份原件完整覆盖、对象与原币一致的正式应付；一张单只有部分行落在本月原件时，不能据此处理整票。
2. 勾选实际应付。逐项明确“手续费”或“尾数”、“仍欠”或“不欠”、货款或模具款、精确原币金额、归属依据与实际来源。没有全局默认，也不自动凑整。同一应付可添加另一项，货款与模具款须各自明确，不能按比例推测。
3. “仍欠”只保留本次财务决定，原应付和实际付款金额不变，不形成减免分录。“不欠”需先有原应付的真实记账科目与辅助证据，并明确选择对方损益科目及其必要真实辅助；银行、资产、库存或成本处理须回到相应真实业务入口。
4. 点“预览逐笔金额”，核对每笔处理前后的未结原币、本币与本次减少的账面本币。原币输入不截断；非有限分摊须明确本次保留位数和取舍，选择随本份预览保留到审核。原件本期金额与已付款后的待汇余额是两个数，例如本期80、不欠5，本期净额75；此前已付20时待汇55，不把整户余额当本期净额。
5. 填写本次处理依据，保存待审核。另一名具有供应商确认、付款审核、总账过账及完整财务查看权限的人员，打开原件的“手续费/尾数”记录，双击待审核行核对原单号、原债务科目、对方科目、归属及精确金额后审核。只在审核成功后形成专用负应付及对原应付的确切抵销，不重复现金或库存。
6. 必须反审时，先撤后发生的实际付款/预付应用/抵销，再从原处理记录反审。系统先撤原抵销，再对称反向减免凭证；原单、原件SHA、原输入与历史保留。不从通用抵销入口拆开受审减免链，也不能在有效减免仍存在时取消原件。
7. 超时或响应未知时保留完整原请求，不重建请求编号。窗口可保留私有草稿并在重开后恢复同一原件、原目标指纹、精确文本、精度选择和未知操作；点“核对并重试原操作”只核对原请求。身份、服务器或数据范围变化后旧窗口隐藏业务内容，草稿仍归原账号。

## 已付款往来分类整图更正

1. 在原应收/应付分类目录选择同一往来对象、同一真实币别的来源。需要共同更正抵销对端时，把真实贷项来源一并选择；也可从单个来源编辑窗进入“整图更正”。
2. 逐行查看全部来源、实际收付款、抵销两端和预付应用；已经付款完或已经反向的记录仍保留。发生日期、反向日期和原金额不可改。原币、实际现金、本币冲销及账面核销分别核对，不拿现金替代book。
3. 为每个节点明确选择归属并填写完整各轴。例如真实来源100、实际付款原币100/现金本币720/账面700，可将来源与该真实付款一起归为模具款；金额仍是原100、720与700，不需要反审重付。混合份额由财务明确填写，不自动按比例补。
4. 填更正依据后点“核对整图并更正”。服务端先完整预览，确认后同一事务追加版本；任一关联漏掉、超分类、版本或实际款项变化都会全部拒绝，原输入保留。最多64来源、512节点，超限不截断。
5. 确定未提交的新草稿遇实际业务变化时，点“重新读取关联图”，保留原始文本后逐行核对新版本和新增关联行。不要把旧图当前可见行当成全部图。
6. 原提交结果未知时，输入及原编号冻结，重开也保同一原请求。可“核对并重试原更正”。若需要结束尚未写入的旧请求，使用“核对并终止旧未写请求”：已成功只返回原结果；确实未执行时会永久封口旧编号，晚到原请求也不能执行。收到并安全保存本人完整命令的终局回执后，才允许显式重新读取新图。普通404、409或网络超时不能证明未写；本地保存失败只继续核同一终局命令，不另发新业务。

预付记录同时保留“原目标归属”和“当前目标归属”，资产原来源不变。手续费/尾数保留“原审批归属”，当前有效份额另列；原对账原件SHA与不欠金额不被更正覆盖。原件本期金额、当前待汇仍分别核对。
