## 一、问题

生产部物料分析准备页一次勾选下达多条采购（或委外）缺料时，服务端按
「操作组 × 货品」逐条生成外部单据：10 件采购品就开出 10 张采购申请、
10 条委外就开出 10 张委外申请。业务口径：

1. **需求层**：一次下达 = 一张需求单，多货品作为明细行。采购员/委外部
   在各自的申请列表里看到的是「一批备料」而不是十张碎片单；
2. **订货层**：真正对外的订货单本来就按供应商分组（一张订货单一个供应商），
   与需求单怎么合并不相关，现状保持。

## 二、决策

### 2.1 需求层：同批合并成单（`MaterialAnalysisCommandService.notifySupply`）

一次通知（同一 `POST /{id}/notify`、同一路线）内：

| 路线 | 下达产物 |
|---|---|
| BUY | **一张**采购申请；每操作组一条「生产需求精确备料」明细，公共安全库存补库按既有分账规则单独成行（ADR-056 不变） |
| SUBCONTRACT（无子层级） | **一张**委外申请；每操作组一条明细 |
| SUBCONTRACT（有子层级） | 不变——V458 前置自制任务，逐条 |
| MAKE | 不变——自制备料任务，逐条 |

实现要点：

- 聚合发生在 `prepareExternalDocuments`：先按 action 收集 DraftLine，再各自调用
  `ProductionPurchaseRequestFacade / ProductionSubcontractRequestPort` 的
  `createProductionDraft`（两 Facade 本就支持多行草稿，之前只是被逐 action 调用）。
- 表头需求日期取本批各行最早 need_date；明细交期逐行保留各自操作组的 need_date。
- **明细行仍逐 action 锚定**：`preplan_supply_action_allocations.external_item_id`
  照旧指向本 action 的申请明细行，收货绑定（V298/V422 exact peg）、在途量复核、
  供应进度链路全部不变；同一货品维度出现在多个操作组时保持多行，不做行合并
  （合并行会让两个 action 共享一个明细锚点，撤回/释放语义被破坏）。
- 前端一次提交 ≤500 组（`RequestLimits.DOCUMENT_LINES`），超大批次分批提交时
  **每批一张**申请（合并粒度 = 一次 notify 命令）。

### 2.2 订货层：不变

采购/委外订货照旧从申请明细分解，`PurchaseOrderService.createBatch` 按
「一张订货单一个供应商」分组；合并申请的多条明细按各自供应商进入不同订货单，
同供应商多行走同一张订货单。E2E 已验证同一张合并申请的两行在一张订货单下单。

### 2.3 撤回：共享单据整批撤回

合并后一张申请被同批多个 action 引用（`external_document_id` 相同）。
`cancelAction`（撤回一个备料任务）遇到共享单据时：

- 同分析内引用该单据的全部生效任务**在同一事务内一并撤回**，单据只红冲一次；
- 任何一条存在不可撤回依赖（已转订货、收货已绑定等）时整批失败（fail-closed）；
- `ProductionPurchaseRequestFacade.cancelGeneratedDraft` /
  `ProductionSubcontractRequestPort.closeGeneratedDraft` 的 REVERSE 分支改为
  **幂等**（已红冲直接返回），使整批撤回与 `cancelAnalysis` 循环撤回天然安全；
- 不共享单据的任务（MAKE、前置自制、单独下达的申请）撤回行为不变。

> 撤回目前无前端入口（服务端能力），本决策先固化服务端语义。

## 三、验证

- E2E 新增 `materialAnalysis_bulkNotifyMergesOneRequestPerRouteAndBatchCancel`
  （`FullChainEndToEndTest`）：两 BUY 一次下达 → 一张申请两条明细 + 两 action 各自锚定；
  两无子层 SUBCONTRACT 一次下达 → 一张委外申请；同供应商一张订货单承载两明细；
  撤回一个共享任务 → 整批撤回、申请红冲一次、采购侧不受影响。
- 既有 E2E 逐方法回归：`notifyBuyAndSubcontract…`、`previewBuildsTree…`、
  `qualifiedReceiptWakes…`、`fullyRejectedReceipt…` 全绿；
  `preplanPegging_subcontractWarehouseStockIn…` 与
  `subcontractPreparationStartAtomically…` 在改动前的干净 HEAD 上同样失败
  （V458 遗留：有子层委外件不再直接生成申请），与本次无关。

## 四、影响面

- 单据量：一次 10 品下达从 10 张申请降为 1 张；下游（分解、订货、收货、peg）
  按明细行工作，不受表头合并影响。
- 幂等/重放：notify 命令级幂等不变；合并发生在命令内部。
- 通知（2026-09-03 修订后）：按单据聚合——每张申请一条提醒
  （`PREPLAN_SUPPLY_DOCUMENT_CREATED`，单号 + N 种物料），不再逐 action
  发出；分批提交的超大批次每批一张申请、各发一条。
