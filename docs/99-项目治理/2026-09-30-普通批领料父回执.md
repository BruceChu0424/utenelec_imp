# 普通批领料父回执(R1.04 子项)

状态：子项候选已完成实现、独立评审和 48 个独立定向用例验证，等待父 worktree 定向集成；不是 R1.04 整体完成，也不是公司服务器安装或验收证明。

## 原因与边界

`StockDocService.issueFullBatch` 原来只给每张领料单生成 `SHA-256(actor, batchKey, documentId)` 子键。子事件不能冻结原单据全集、统一备注、称重意图或原先跳过的单据；取消出库或新增领料申请后重新计算当前剩余量，也不能代表原批次结果。

V763 新增 stock 域 `stock_draw_issue_batches` 不可变父回执，不改 V727 的 Discovery 表或权限。`actor_user_id` 必填；`actor_employee_id` 是可空的执行时快照，不把 `AuthUser` 中的可空员工字段变为已审单出库的新前置条件，不虚构员工或历史父回执。当前数据库 `users.employee_id` 实际为 NOT NULL，因此 nullable principal 的兼容测试不能声称当前可以创建无绑定员工的真实账号；本改动不放宽账号表。

## 当前候选合同

1. 规范化单据集合(去重、按 UUID 文本排序，最多 50 张)、trim 后的备注、`WeightInput.kg` 后的重量及 `qtyFromWeight`；同语义顺序/小数尾零/空重量等价，改变单据、备注或有效重量必须冲突。
2. 以 actor + key 的 PostgreSQL 事务级 advisory lock 串行。普通入口在履约图锁之前取得命令锁；Discovery 已有外层图锁，其内层键为本次服务器新生成的 UUID，两层分别留回执，不套用 Discovery 的额外审批/在岗门槛。
3. 已有父回执先比对完整请求指纹，再保留当前 `stock_doc:issue` 入口权限和逐单可读校验，返回已冻结结果；不重新审核、读取剩余量、取得履约图锁或写库存。原来全跳过的批次也返回 `replayed=true`，`skippedCount` 保留原值。
4. 新命令保留原整批锁序、草稿才需要 approve、当前已申请数量、重量归属、备注追加、逐单错误定位及全部原子回滚。取得整批锁后，在任何审核或实发前核查旧子事件。
5. 每笔库存、权益、来源和子事件仍同步完成；末尾核查本批没有已申请但未实际出库的剩余量，再同一事务写父回执，包含全部 skipped 的成功结果。失败不留父回执，原键可在错误修正后重试。
6. 父回执 UPDATE/DELETE 由触发器拒绝，FULL 审计追踪，注册完整业务测试数据重置策略；不引入运行时清理或保留期限。指向 users/employees 的 FK 不属于 `MasterReferenceCatalog` 的七类主档，因此没有新增该目录豁免。

## 旧历史的不可逆限制

没有父回执时，只要本次所选单据命中同 actor/key 派生的旧 ISSUE 子事件(即使后来取消)，就整批报冲突、要求核查历史，不新增审核/扣库，也不把今天的请求补写为原批次成功。

旧子键是不可逆哈希，原正向 ISSUE 也没有完整统一备注证据。因此无法由旧记录还原当时单据全集、漏选成员、原先全 skip 的批次或原备注。当前候选只能识别本次所选单据内的旧子事实，不能声称所有旧批次已有完整回执，或能够识别完全不相交的旧成员。旧历史应人工核查后发起新的明确命令；不做猜测式自动补档。

本子项尚未改变 HTTP 客户端所见版本合同，不能据此宣称已经防止用户使用过期页面提交新的键。HTTP 排队、资源竞争及提交成本的性能验收仍属于后续 R1 工作。
