# 采购/委外到货与物料分析全链路审计整改（2026-08-20）

> 本文是源码候选与验收边界记录，不是目标数据库已迁移、服务器已安装或多岗位 UAT 已通过的证明。已应用的 Flyway 迁移必须保持字节不变，所有整改仅能通过新的前向迁移落地。

## 一、业务结论

仓库“收货审核”与品质“合格放行”是两个不同事实：

1. 仓库收货审核只建立待检事实，不得提前增加合格库存。
2. IQC `PASS` 才写入 `DIR_IN` 库存变动，并在同一事务内追溯到来源物料分析。
3. “本物料合格到货量”、“本分析可覆盖量”与“整套物料最多可生产量”必须分开：一项物料已合格到货，其他物料未齐时，`readyNowQty = 0` 是正确结果，但该物料的合格到货量不得仍显示为 0。
4. 只有实到仓库、货品、颜色、基本单位与分析维度一致，且扣除安全库存后，合格到货才能转化为当前批次的可生产覆盖。到其他仓的物料必须先走受控调拨。

## 二、权威主链

### 2.1 采购

`material analysis row UUID`
→ `preplan_supply_action_allocation UUID`
→ `purchase_request_item UUID`
→ `purchase_order_item.request_item_id`
→ 财务审批
→ `purchase_receipt_item.order_item_id`
→ `procurement_inspection_item.receipt_item_id`
→ IQC `PASS`
→ `stock_movement(DIR_IN)`
→ `PREPLAN_ANALYSIS` 库存归属
→ 刷新来源物料分析。

### 2.2 委外

委外与采购共用前半段的计划和财务门禁，但在委外商回货前增加公司自有材料出仓：

`material analysis row UUID`
→ `preplan_supply_action_allocation UUID`
→ `subcontract_application_item UUID`
→ `subcontract_order_item.application_item_id`
→ 财务审批
→ 冻结 BOM 发料计划/仓库出仓
→ 委外商回货
→ `subcontract_receipt_item.order_item_id`
→ IQC `PASS`
→ 库存与来源分析归属。

委外订单的手工行可以没有 `application_item_id`，但这种行没有物料分析来源，IQC 合格后只能进入公共合格库存，不得按货号猜测并绑定到某份分析。

## 三、本次确认的缺陷与整改

| 问题 | 影响 | 整改 |
| --- | --- | --- |
| 物料供给进度按整张订单/收货单汇总 | 同一合单内兄弟物料的收货或 PASS 会把当前物料误标为完成 | 改为 `allocation -> exact order_item_id -> exact receipt_item_id -> IQC` 逐行投影；委外发料也按精确订单行计算 |
| IQC 自动刷新后，页面仍带旧版本 POST | 服务端返回冲突，Flutter 保留旧的 0 | 版本冲突后自动 GET 最新详情，并按稳定操作组键保留仍有效的未保存路线草稿 |
| Flutter 丢弃服务端归属量，且把整套齐套量与单项到货混用 | 用户看不到“已合格且归属本节点”，容易把整套未齐误认为未到货 | 模型解析节点级 `exactPeggedQty` 与分析仓级 `ownPeggedQty`；物料卡显示“本节点合格入库绑定”，整套区独立显示“整套物料未齐”；“已入库”改为“已齐套（库存已覆盖）” |
| V298 只保留 `analysis_id`，丢失 `analysis_material_id` | 同一联合分析中，针对 A 产品到货的物料可被优先级更高的 B 产品重新分配 | 使用新的前向迁移建立 exact-peg 子账；收货按 action allocation 容量精确绑定原物料行，重算时先保障该行再分配公共池 |
| 重算先暂时失活旧物料行，exact 查询又要求 `active=true` | 真实 PASS 和精确子账均已存在，当前刷新事务仍可能算出 0 | 可用量重算按本轮 BOM 的稳定 `analysis_item_id + node_key` 识别目标，不依赖刷新中间态的 `active` 标志 |
| 分仓展示和主重算的安全库存公式不一致 | 展示层可把本分析归属量加在安全库存之外，高估可用 | 统一为 `max(publicAvailable + ownPegged - safetyStock, 0)` |
| 实际 IQC 仓与分析目标仓不同却无解释 | 目标仓备料显示 0 在业务上正确，但计划员会误认为到货未回写 | 收货登记改离建议仓时明示不会计入原目标仓；分析页按物料维度去重列出“非目标仓的合格绑定量、实际仓、目标仓”，并明确普通调拨不会迁移该分析归属，必须走受控更正/红冲后在目标仓重登验收 |
| 生成/取消/计划直接审核与 IQC 的库存、分析锁顺序相反 | 并发时存在死锁或取消后又写入孤儿归属的窗口 | 生成、行动取消、分析取消、直接审核均先稳定预锁 active 物料和现存有效归属的库存维度，再进入计划/分析/行动锁 |
| 分析权益转正式需求后缺少可逆谱系 | 未领料取消会丢失来源权益；直接红冲又可能抽走 READY/领料链的库存 | V309–V313 以 `FORMALIZE` 精确绑定 package/demand/formal reservation，且只转 READY demand；未领料取消或 segment 回退写 `RESTORE` 并恢复 PREPLAN reservation，已领料、已派工或已开工继续 `409 CONFLICT` |
| 跨分析继续使用“借料/代还”表述 | 容易误导为 B 必须返还同一批货，且无法解释 A/B 下一批供给 | 改为“显式让料 + 来源计划后续合格供给优先补齐”：A 让给 B 后 A 形成优先待补；A 自己或 B 的下一批 BUY/SUBCONTRACT/MAKE 合格 origin 先补 A，余量仍归原供给方，不建立欠款/代还账 |
| MAKE 成品入库仍停留在 analysis+SKU 池 | 同 SKU 兄弟节点可能串用，自制入库也无法参加让料/优先补齐 | V309/V312 以 `plan.material_analysis_item_id -> PREPLAN_MAKE_TASK allocation -> parent analysis material` 写 `ORIGIN_MAKE` exact；先满足既有 formal MAKE 承诺，只有余量进入 PREPLAN exact，超 allocation 仍为公共库存 |

## 四、显式让料与来源计划优先补齐

V288/V289 继续表示**同一份物料分析内**两个产品节点之间的软分配调整；它不改物理库存，也不承担跨分析业务。跨分析能力统一称为“让料”，不再使用欠款、代还、还款或“下一批自动归还”。

业务例：来源分析 A 把已合格且 exact 的 `4` 让给紧急分析 B。B 当下取得 `4`；A 保留“优先待补 `4`”。此后：

1. A 自己的下一批同仓同货品/颜色/单位合格供给，先原地满足 A；
2. 若 B 的下一批 BUY/SUBCONTRACT/MAKE 合格供给先到，最多 `4` 重新挂给 A；
3. 超过待补量的余量继续属于该新供给的原分析；
4. 无关分析 C、正式 reservation、已领料和已开工事实不得参与自动重挂；B 不承担返还义务。

V309–V314 的职责边界：

- V309：`preplan_material_reallocations` 让料头、append-only `preplan_stock_entitlement_events`、lot/beneficiary 余额视图，并扩展 MAKE 来源列；
- V310：给 V309 两张业务账显式附加审计触发器；
- V311：权限、双方端点、CAS/幂等和生命周期守卫；
- V312：以已审核 `FINISHED_IN`、计划行、MAKE_COMPONENT 与 parent allocation 校验 `ORIGIN_MAKE`；
- V313：正/负 entitlement 事件、`FORMALIZE/RESTORE/RELEASE`、正式 demand/reservation 桥和物理数量延迟守恒；历史 V298 无 exact 行不猜测回填；
- V314：重新执行 fail-closed 全 `public` 审计覆盖扫描。

`stock_reservations` 始终是唯一物理预留真相。权益事件只说明当前受益分析物料行，不能凭名称、货号或同 SKU 猜测。人工让料只允许消费谱系终点为 `ORIGIN_IQC/ORIGIN_MAKE` 的 lot；原始权益经正式计划取消或让料撤销形成的 `RESTORE` 仍可再次让料，从 `REALLOCATE_IN/PRIORITY_IN` 恢复的 lot 不得转手，禁止 A→B→C 连环让料。

正式计划只对 READY demand 执行 `transfer -> formal allocation -> FORMALIZE`；WAITING 不持部分正式预留，并同时兼容 V309 beneficiary 与 V298 eventless owner 回加。未领料取消或受控 segment 回退写 `RESTORE`；恢复后仍可按“原始 OUT 根 + 当前 REALLOCATE_IN/RESTORE lot”撤销。分析取消时 OPEN/PARTIAL 409，FULFILLED 按 beneficiary slice 增量 RELEASE 并受控关闭；任何未 RESTORE 的 FORMALIZE、已领料/派工/开工、来源红冲影响他分析 beneficiary 时均 409，禁止整行释放静默夺权。

详细状态机、权限和界面文案见 [ADR-044 跨物料分析让料与后续供给优先补齐](../99-决策记录-ADR/ADR-044-跨物料分析让料与后续供给优先补齐.md)。
## 五、必须保持的不变量

- 仓库收货审核不增加合格库存；每次部分 PASS 立即增加对应数量并刷新分析。
- 任何分配或借用前后，“公共可用+全部有效归属/预留”的总量守恒，不能变出库存。
- 超过上游 action allocation 的财务特批超收部分进入公共池，不伪造分析路径归属。
- 手工采购/委外行、历史无 UUID 谱系行与已取消 action 必须 fail closed，不按货号猜测归属。
- 已转为正式生产 demand 预留、已领料或已开工的库存，不得被收货红冲或软借用静默抽走。

## 六、验收与发布边界

源码候选至少需要以下动态证据：

- 采购和委外合单：兄弟行的收货/PASS 不会污染当前行进度；
- 采购和委外真链：计划任务、订货、财务、仓库、IQC、库存、来源分析全部使用真实服务和 PostgreSQL；
- 同一分析 A/B 同料：A 的精确 action 到货只覆盖 A，不受 B 的优先级影响；
- 部分/多次 PASS、幂等重放、超收、安全库存、错仓与调拨；
- 收货红冲、action 取消、分析取消和计划确认后的对称反向；
- Flutter 旧 CAS 冲突回读、草稿保留、合格到货和整套齐套的独立展示。

目标 PostgreSQL 迁移历史/校验和、最终 JAR/前端产物回读、五岗位真实 UAT、红冲/恢复演练中任何一项未完成时，发布结论仍是 **NO-GO**。
