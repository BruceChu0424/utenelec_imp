# 员工报销全链路 SOP

适用：中国大陆普通企业人民币员工费用报销。流程保持申请、一次审核、财务确认付款三个岗位动作；不配置多级审批引擎。依据、例外凭证和开源识别边界见[合规依据与凭证清单](员工报销合规依据与凭证清单.md)，技术决策见[ADR-094](../99-决策记录-ADR/ADR-094-报销链路完整化.md)，验证入口见[本轮验收](../99-项目治理/2026-09-19-员工报销全链路验收.md)。

## 一、开始前由财务准备

1. 核实公司报销抬头、纳税人识别号、可用付款账户和 EXPENSE 费别。费用科目由财务选择，员工只选交通、差旅、餐饮等日常类别。
2. 按公司制度确认凭证材料要求、无票或特殊凭证的说明要求、报销范围和差旅标准。公司制度可以比系统更细，但不能把行政机关差旅标准写成全国企业强制标准。
3. 分配申请、审核、付款及政策维护权限，附件查看、上传权限一并检查。审核人员还需附件下载权限才能打开原件、登记核验及批准。申请人不得审批或确认支付自己的报销单；审核与支付的岗位分离按系统规则执行。
   付款岗位还须具备账户字典 `account:view`、费用类别 `payment_style:view` 及付款证明上传权限；需要在付款前更正附件时再授附件删除权限。
4. 完成付款账户、费别会计映射和相应核算期间准备。确认付款会生成关联财务费用单及账务记录，不能用测试付款来检查正式账户是否可用。
5. 确定电子原件保管、人工查验、归档移交负责人。本地 OCR 为可选部署，未安装时员工仍可手工完成。

财务报销设置用于公司资料与业务制度，OCR 地址、存储根路径、数据库和密钥属于运维配置，不放入普通业务表单。当前打印公司抬头读取实时设置，尚未冻结到单据快照；公司资料变更后再次打印可能使用新抬头，财务须保留当时正式归档版本并核对实际票面，不能据新抬头改写原始凭证。

## 二、员工办理

| 步骤 | 操作 | 结果及失败处理 |
|---|---|---|
| 新建草稿 | 从“我的报销”新建，填写事由、每项费用日期/类别/金额和必要说明 | 申请人与部门来自登录员工档案；金额由服务端按明细计算。保存后生成 BX 单号。未完成草稿可以稍后继续 |
| 准备凭证 | 按页面提示上传电子原件或纸票影像，登记票面要素并关联附件 | 提交前需有扫描通过的附件；每张登记票据须关联本单可用原件并填写日期。查重报错时核对是否已在其他单据登记，不改号码规避 |
| 图片预填 | 选择图片识别，逐项核对号码、日期、购销方、金额与税额 | 识别结果只是建议；没有识别出字段就手填。拍照或截图不能替代已取得的电子原件 |
| 提交审批 | 核对事由、金额和凭证材料后提交 | 进入待审核；缺少材料或版本冲突时保留已保存草稿，按提示补齐或刷新后重新核对 |
| 补正 | 收到驳回通知后打开原单，查看原因，编辑或补凭证，再重新提交 | 沿用原单号，不另建一张来逃避原审核；历史驳回意见仍在流转记录中 |
| 查看进度 | 在详情查看当前阶段、下一岗位和历史操作 | 审批通过表示等待财务付款；财务登记付款后显示完成及关联财务记录 |

已提交但尚未通过时，申请人可撤回修改。已批准或已付款的单据不可直接编辑、撤回或删除；金额错误、退款或票据红冲交财务按原单引用处理，不能以重新提交制造第二次付款。

财务设置“提交时必须登记票据”启用时，提交至少需登记一张票据，合法 `OTHER` 凭证也计入。
该设置默认关闭；关闭时没有登记票据的申请仍须上传业务凭证，并在备注说明凭证类型和报销依据。
设置不免除财务对凭证适用性的审核，不把暂缺票说明自动变成税前扣除凭证。

## 三、审核人员办理

1. 从“报销审批”待审核队列或通知弹窗进入详情，确认认领状态，核对申请人、业务用途、日期、费用明细和原始材料。
2. 分别检查金额勾稽与凭证真实性。系统“金额一致”仅说明算术关系；人工核验需核对原件，并按凭证种类使用税务或相应官方渠道。逐票记录核验结果和依据，服务端保存操作人及时间；所有已登记票据人工核验通过后才能批准。
3. 异常要有可执行的驳回原因，例如“请补交通电子客票原文件，并说明两段行程与客户拜访的关系”。不得只填“有误”，也不替员工改原件。
4. 对材料和制度均符合的单据通过审核；需要修改的驳回原申请人。批准后交财务付款，尚未发生实际付款。
5. 批量审核只适合逐单已完成材料核对的记录。最多50张，一张状态过期、越权、被他人认领或不满足审核条件时整批回滚；刷新后处理，不把按钮点击次数当作成功单数。

合法非发票凭证、待补票或报销额与票面不一致的情况须依据[凭证清单](员工报销合规依据与凭证清单.md)逐笔判断。支持说明和人工复核是为了如实反映业务，不是自动批准税前扣除或抵扣。

## 四、财务确认付款与核算

“确认付款”记录公司已经通过银行或现金完成的实际付款。本系统没有银企直连，不向银行发起转账，也不能把 HTTP 成功当作银行到账证明。

财务在待付款队列逐单核对申请人、金额、支付安排及凭证。完成实际付款后，在“付款证明”区上传银行回单或现金签收凭据，等待扫描通过，再选择真实付款账户、EXPENSE费别和实际付款日期并确认。服务端至少要求一份扫描通过的付款证明，并在同一事务中关联报销单、YF财务费用单、账户流水和总账处理；有失败则整个业务事务回滚。

付款证明独立使用 `EXPENSE_PAYMENT_PROOF`，不解冻员工原申请附件。仅APPROVED且有付款权、非申请人、非本单审核人的财务人员可上传/删除；PAID后冻结只读，申请人和有权财务可在详情查阅。银行回单内容与实际收款仍由财务核对，上传文件本身不证明到账。

同一张已付款单以相同参数重试应返回既有结果，不再生成第二笔费用或重复扣账；不同参数再提交应拒绝。支付完成后检查关联YF单据、付款证明与实际银行或现金记录一致，并按档案制度保管。系统状态为PAID只证明本系统记录已完成，还要核实真实付款。

本链不把票面税额直接当作可抵扣进项税额，不自动完成税务数字账户用途确认。财务依据纳税人资格、费用性质及适用规则处理记账、扣除、抵扣和必要的纳税调整。

## 五、进度、红色徽章与通知

| 对象 | 表示什么 | 什么动作改变它 |
|---|---|---|
| 员工草稿/待补正红徽章 | 需要本人继续完成的业务单据 | 提交、删除草稿或修订重提后，按实际状态减少 |
| 审核待办红徽章 | 当前有权处理且轮到审核人员的单据 | 审核通过、驳回或申请人撤回后减少 |
| 财务待付款红徽章 | 当前有权支付且需要财务确认付款的单据 | 确认付款后减少 |
| 处理中/历史记录中性计数 | 等待其他岗位或用于查阅的记录集合 | 随业务状态与筛选刷新，不按消息已读减少 |
| 通知未读数 | 尚未阅读的消息 | 阅读通知会清消息未读，不办结业务待办 |

同一张单在同一个入口只计一次；模块与工作台累加统一走待办注册表，不手写重复相加。通知弹窗只是跳转和提示入口，仍由服务端重新校验权限、版本、状态与认领；旧通知打开已处理单据时显示当前结果，不恢复原动作。

正常接力为提交通知审核人员，通过通知付款人员并回执申请人，驳回通知申请人补正，付款通知申请人。重提进入新一轮待办，旧轮审核卡应办结；业务待办不依赖员工是否读了消息。

## 六、打印、汇总与归档

详情可预览并打印 A4 公司费用报销单，包括公司信息、BX 单号、申请人/部门、事由、费用明细、大小写合计、凭证信息、当前状态、真实流转记录及付款信息。签字栏是纸质办理时的人工签认位置，系统操作人姓名不是电子签名认证。

打印单用于公司展示、核对和配套审批，不能独立替代发票、银行付款凭证或会计记账凭证。草稿和驳回单打印时仍显示其状态；文件份数不等于原始凭证张数，多页资料按实际归档办法清点。

审批工作台汇总按服务端口径展示待审核、待付款及本月业务。年月边界使用上海业务时区；单数是报销单数，金额是报销额，不能读成发票张数、票面总额或银行已到账金额。无对应权限的队列不显示；历史查询与行动队列分开。

“已处理”可查当前状态为批准、驳回或已付款的记录：审核人员看到当前由自己批准/驳回的单据，
付款人员可查已付款记录，再进入详情查看凭证、事件和打印。员工仍从“我的报销”查看本人完整列表。
本月付款统计按系统登记完成时间，不按人工补录的实际付款日；正式银行对账仍依据实际支付记录。

归档时以 BX 单号、业务 UUID、关联 YF 单号和会计档号建立检索关系，按[合规依据中的归档清单](员工报销合规依据与凭证清单.md#三人工核验和归档)汇集原件、业务证明、付款证明和审核轨迹。电子原件、元数据、备份与恢复验证必须配套，不能只留打印 PDF。

## 七、岗位验收

至少使用三个不同员工账号覆盖申请、审核和付款；另用无权限账号验证直接链接与接口。实际安装验收使用受控测试数据和测试账户，不向真实收款人转账。逐项检查“员工提交 → 材料核验 → 驳回补正 → 通过 → 财务确认付款 → 关联账务 → 通知徽章刷新 → 打印归档”，结果和限制记录到[本轮验收](../99-项目治理/2026-09-19-员工报销全链路验收.md)。
