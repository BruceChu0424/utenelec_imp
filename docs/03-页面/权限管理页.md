# 权限管理页

> 路由：`/admin/permissions`
> 前端：`lib/features/admin/pages/admin_permissions_page.dart`、`lib/features/admin/widgets/`、
> `lib/features/admin/repositories/admin_repository.dart`
> 后端：`server/src/main/java/com/uten/imp/features/admin/`
> 当前授权边界：`/admin/permissions` 是共享壳；账号日常支持使用 `account:support`，授权配置仅
> 超级管理员 `authorization:manage`

## 一、定位

权限管理页是当前“部门配置 + 个人覆盖 + 数据范围”的管理入口。角色体系已在 V29 下线，
页面和文档不得继续把 `user_roles`、`department_roles` 或“给员工分配角色”写成现行能力。

有效权限由后端计算：

```text
最终有效权限 = 全员基础 ∪ 本部门及上级部门配置 ∪ 中央个人 grant ∪ 当前有效负责人委派 − 中央个人 revoke
```

超管拥有全部权限。前端只展示和编辑结果，不能自行决定授权。

`users.remote_access` 是独立的云端入口开关，不属于 `permissions` 目录，也不参与上述权限并集。
V241 默认 `FALSE`，表示员工默认只能从公司局域网的 local 入口使用；只有超级管理员且持
`authorization:manage` 才能按账号显式授予或撤销。拥有普通业务权限、`account:support` 或超管固有
全权限都不能替代该字段在 cloud 站点的服务端检查。

`audit_log:view` 与 `audit_log:export` 是调查证据权限的例外：超级管理员因固有全权限天然具备；非超管
只能在“按员工授权”的个人覆盖中点名加授，
不能进入部门授权或随部门树继承。只有 `audit_log:view` 才能查询；导出还必须同时具备
`audit_log:export`。普通员工、访客以及仅持导出权限的账号都不能查看审计。

V171/V173 会删除升级前已有的非超管审计导出/查看 grant。发布后由超级管理员依据批准名单重新点名授予，
避免旧部门权限或历史误配继续放大调查证据访问范围。

`stock:balance:adjust` 是另一类高风险业务权限：V167 只注册权限目录，**不默认授予任何部门**。

`account:balance:adjust` 是账户上线开账/差异核对的高风险个人权限：V400 只注册权限目录并连接
“账户资料”页面，**不默认授予任何部门**。它不能由 `account:edit`、`account:balance:view`、
`account:flow:view` 或 `account:warning:manage` 推导，也不能进入部门授权、页面内委派或“全部授权”。
超级管理员只能在全局“按员工授权”中对经批准的具体员工点名加授；服务端仍逐请求校验并记录不可变批次、
逐账户前后值与操作者。余额查看和流水查看可按财税岗位配置，但都不自动带来调整权。

V210 新增 `employee:export`（员工资料打印与导出，ADR-021）：员工花名册打印、部门架构图打印
等文档下载入口按该点显隐，独立于 `employee:view`；默认预配 `DEPT_HR`，其他部门/个人由超管
在本页按需配置。人事若持 `account:support` 可进入同一路由的**账号支持区**，但无权查看或调用
权限目录、个人/部门授权和数据范围；只有超级管理员且持 `authorization:manage` 才能进入这些
全局授权区并配置 `employee:export`，所有接口同源校验。
推荐在“按员工授权”中点名授予领导或仓库负责人；但它不是数据库强制的 personal-only 权限，超管如在
“按部门授权”中明确配置，仍会按现有部门树继承。`stock:view` 和 `stock_doc:edit` 均不会自动带来
余额调整权（历史目录码 `stock:edit` 从无端点强制，已随 V455 删除），
具体业务矩阵见[库存余额页](库存列表页.md)。

## 二、入口与授权

- 位置：工作台 → 系统管理 → 权限管理。
- 前端入口与路由接受 `account:support` 或 `authorization:manage` 任一权限。
- support-only 用户只渲染账号列表、开通账号、锁定/解锁、启用/停用和设置临时密码；不得渲染，
  也不得请求权限目录、员工有效权限、个人覆盖、数据范围和部门授权。
- 后端权限目录、部门权限、个人覆盖和数据范围接口同时要求
  `hasAuthority('authorization:manage') and principal.superAdmin`。
- 账号列表、开通账号候选、锁定/解锁、启用/停用和设置临时密码属于日常账号支持，后端使用
  `account:support`；进入同一共享页面不会下放授权管理能力。
- 云端远程开关位于选中员工详情最顶部，只有 `authorization:manage` + 超管可见、可调用；
  support-only 用户不得渲染或请求该能力。
- V135 后，staff access JWT 携带用户 `auth_version` 和全局授权 `epoch`；`JwtAuthFilter`
  每请求复查，个人覆盖、用户角色、员工换部门、部门树或共享权限定义等变化会使旧 token 立即 401。
  该行为必须在目标库应用 V135 并通过负向矩阵后才能认定完成。

## 三、页面结构

顶部说明条 + 按权限装配功能区：

- **账号支持区**（`account:support`）：账号分页列表、状态筛选、锁定/启停、设置临时密码，
  以及列表上方的「开通账号」入口（为尚无登录账号的在册员工补开，与人事-员工详情页同端点）。
- **远程访问授权卡**（`authorization:manage` + 超管）：位于选中员工详情最顶部、三个页内分区之前，
  展示“未授权/已授权云端访问”，通过明确二次确认执行“授权云端/取消授权”。
- **按员工授权区**（`authorization:manage` + 超管）：最终有效权限、个人加授/收回、数据范围。
- **按部门授权区**（`authorization:manage` + 超管）：选择部门，从权限目录配置直接权限；员工继承上级部门配置。
- expanded 且可用宽度至少 1100dp 时使用左右主从布局；其余宽度使用列表→详情切换，避免中屏详情被固定侧栏挤窄。

账号搜索和状态筛选都参与服务端分页，查询参数为 `page/size/search/status`。切换搜索或状态后回到
第 1 页，加载更多沿用同一组筛选；页面使用请求代次丢弃旧响应，避免快速切换时旧列表覆盖新结果。
状态筛选不得只过滤当前已加载页，也不得因此隐藏后续分页入口。

员工详情分为“操作权限 / 可查看数据 / 账号安全”三个页内分区，一次只显示当前分区。

### 3.1 顶部远程访问授权

- 默认关闭时，员工仍可在公司局域网允许网段通过 local 站点登录和使用，但 cloud 的登录、刷新与
  每个已认证请求都会拒绝；“仅云端”客户端模式不能绕过这一规则。
- 授权或撤权只有在值发生变化时落库；V241 触发器递增目标 `auth_version`，服务层同时撤销该用户
  全部 refresh token，并记录 `remote_access_grant` / `remote_access_revoke` 审计事件。**两个方向都
  要求目标用户重新登录**，不是只在撤权时清会话。
- 撤权后旧 access 下一请求在 JWT 版本校验处先得到 `401 UNAUTHORIZED`；旧 refresh 在 cloud 得到
  `403 REMOTE_ACCESS_DENIED` 且无新 token。本地账号密码登录仍按 local 源网段规则可用。
- 请求体必须为 `{"remoteAccess": true|false}`。`{}` 因 `@NotNull` 返回 422，缺失 body 返回 400；
  无效请求不得默认为 `false`、不得改变远程开关或授权版本。
- 访客主体不使用 `users.remote_access`；cloud 的员工远程策略跳过 visitor，但访客仍受独立账号状态、
  权限与对象范围控制，local 站点也仍对访客 `/api/**` 应用局域网源地址门禁。

### 3.2 账号安全：设置临时密码与开通账号（V297，2026-08-17）

「账号安全」分区（support-only 用户唯一可见分区）自上而下为：账号信息（姓名/工号/部门/登录账号/
上次登录）→「密码与登录」→「账号状态」（锁定/解锁/停用/启用，二次确认）→ 审计提示行。

**设置临时密码**（员工忘记密码场景，`POST /api/admin/users/{id}/reset-password`）：

- 对话框提供两种模式：**系统生成**（默认推荐，20 位高熵随机，含大小写字母/数字/符号）与
  **自定义临时密码**（便于口述转告；前端预校验 + 服务端终审：8–64 位、不含空白、必须同时含
  字母和数字、不得等于登录账号，失败返回 `422 PASSWORD_TOO_WEAK` 及具体原因）。
- 两种模式同一效果：置 `must_change_password=true`、清暴力锁定、写
  `users.temp_password_expires_at = now + 72h`、递增 `auth_version` 并撤销全部 refresh token——
  **该账号所有已登录会话立即失效**。停用账号不会被重置顺带启用。
- 明文只在结果弹窗显示一次（可复制），不持久化、不写日志、不写审计详情；弹窗明示
  「72 小时内有效、员工登录后须设置新密码」。
- 分区状态提示：`must_change_password=true` 时显示「已设置临时密码，等待员工登录后设置新密码」及
  有效期截止时间（`tempPasswordExpiresAt`，逾期红色提示「已过期，请重新设置」）。
- 员工用临时密码登录后只进入强制改密：`PasswordChangeRequiredFilter` 把该会话收口到
  改密/登出/恢复资料三个端点，其余 API 一律 `403 PASSWORD_CHANGE_REQUIRED`；改密成功清除
  `must_change_password` 与 `temp_password_expires_at` 并踢其他设备。
- **临时密码 72 小时过期**（V297）：登录时若 `must_change_password=true` 且已过期，返回
  `401`「临时密码已过期，请联系管理员重新设置临时密码」，审计记 `login_failed/temporary_password_expired`
  （密码校验通过后才提示，不助长账号枚举）。入职/补开账号的初始密码（证件号后 6 位）不写有效期，
  保持原有行为。
- 每次成功重置写显式审计 `password_temporary_reset`（操作人、目标账号、`mode=generated|custom`，
  绝不记录明文）。

**开通账号**（列表上方入口卡，`account:support`）：

- 候选人来自 `GET /api/admin/users/provision-candidates?search=`：在册（未删除、非离职）且尚无
  未删除登录账号的员工，按姓名/工号模糊搜索、工号排序、**最多 20 条**；最小信息集
  （姓名/工号/部门 + `hasPhone/hasIdCard` 布尔位），不解密、不回传手机号/证件号明文。
- 缺手机号或证件号的候选人置灰并提示「缺手机号/缺证件号」，引导先在员工档案补全；开通动作
  仍由 `POST /org/employees/{id}/account` 终审（账号=手机号、初始密码=证件号后 6 位、首登强制改密），
  成功后复用一次性凭据弹窗；弹窗不可通过返回键或遮罩误关，关闭后明文不可再次读取。
- 该入口与人事-员工详情页 Hero 卡「开通账号」能力等价，两处共用同一端点与权限级。
- 各业务页面右上角进入的“本页权限设置”也会列出管理范围内的未开户员工。用户主动点选时先显示
  “该员工还未开通账号，暂不能设置权限”；当前操作者同时持 `account:support` 才追加“是否现在
  开通账号”的确认动作；必须由操作者确认保存并关闭一次性凭据弹窗后，才刷新账号状态、重新定位
  该员工并加载权限详情。仅是部门负责人、仅持
  `authorization:manage` 或仅能委派本页权限都不能开户。
- 未开户、账号锁定和账号停用是三个不同状态：未开户显示文字状态和开户引导；锁定/停用仍是已有账号，
  只能走对应账号生命周期动作，禁止误走开户创建第二个账号。

员工功能权限保留后端下发的完整动态权限目录；部门权限目录过滤“仅限个人授权”的
`audit_log:view` / `audit_log:export` / `account:balance:adjust`。V423 已从权限主表和各授权来源删除
`production_material_analysis:bom_override`，因此部门目录与员工目录都不得再靠前端过滤来隐藏它，
更不得接受旧客户端提交该码。后端服务和 V173 数据库触发器继续硬拒绝审计权限的部门级写入。
两种目录都采用以下渐进浏览方式：

- 目录按「功能模块 → 子类」两级折叠（V228 引入，`permissions.module` 一级 + `category` 二级）：
  一级为 11 个功能模块（基础资料 / 销售管理 / 采购管理 / 委外管理 / 生产管理 / 仓库管理 /
  财税管理 / 工程研发 / 人事行政 / 品质检测 / 系统管理，顺序由后端固定），二级为子类
  （如「货品资料」「销售订货」）。默认只显示模块摘要与“已授权数 / 总数”，逐级展开，不再一次铺开。
- 支持按权限名称、模块或子类搜索；命中的模块与子类自动展开。
- 支持“全部 / 已授权 / 未授权”，员工权限另支持“个人调整”状态筛选。
- 批量操作分三档：目录顶部「全部授权 / 全部收回」（部门 tab 文案为「全部配置 / 全部取消配置」）、
  模块级「本模块全部授权/收回」、子类级「本组全部授权/收回」；均始终作用于完整集合，不受当前
  搜索/状态筛选影响；仅改动本地待保存集，须再点底部「保存更改」才落库。按员工的「全部授权」
  **排除高危个人-only 权限**（见 §六），避免一键放行审计/授权管理/余额调整/资产生命周期/工作流指派/
  稀缺让单、跨计划让料等敏感点；superAdmin 不渲染该按钮。CROSS 仍可按部门或个人逐项显式授权/收回。
- 权限行只展示中文名称、来源标签（部门 / 基础 / 个人加授 / 已收回）与最终状态；**原始权限代码（如
  `payroll:export`）不再显示**，避免暴露后端/库结构标识——代码仅作内部键（Switch 状态、行 key、
  搜索匹配）使用，不作为可见文本渲染。
- 有待保存修改时，底部固定显示修改数量、撤销和保存操作；保存失败须保留本地修改。
- 搜索无结果时提供清除搜索和恢复全部目录的动作。

### 部门默认权限矩阵（V212，2026-08-05）

15 个业务部门的默认权限由 `V212__department_permission_matrix.sql` 作为**单一权威来源**维护：
GM、HR、FIN、PROD、ENG、PMC（及其计划/采购/物控/仓储 4 个子部门）、SALES、RAIL、NEWMEDIA、
QA、SECURITY。该迁移对每个配置部门做**受控重置**（先 `DELETE` 该部门全部权限，再 `INSERT`
矩阵授予集，`ON CONFLICT DO NOTHING`），从而覆盖此前散落在 V29–V211 的零散授予——dev 库
2026-08-03 TRUNCATE 业务表后这些种子不再重跑，V212 即为重新灌入的来源。

设计要点：

- **向上递归继承**：挂在父部门（如 DEPT_SALES）的权限自动对其子部门员工生效，故写权限尽量
  **下沉到叶子部门**（如采购/仓储/计划/物控各自归属），避免在父节点堆权限导致越权下传
  （V198/V200 当年正是在收窄这种泄漏）。
- **3 个管理中心与公司节点保持空白**，不在父级配权限，避免大面积下传。
- **矩阵内任何部门都不授予高危个人-only 权限**（见 §六）。
- 在运行中的库上经页面手工调整部门权限仍然合法且即时生效；但 V212 只在全新 bootstrap 时重跑。
  V212 已应用后不可修改，默认矩阵变化一律使用追加迁移，不得只靠页面手工配置。V233 追加
  `*:view:all`，V234 追加生产物料分析/批准权限及默认部门，详见
  [部门默认权限矩阵](../数据迁移/54-部门默认权限矩阵.md)。

员工详情的权限开关不是本地角色计算。页面先读取
`GET /api/admin/users/{id}/effective-permissions`，再把变化转换为 grants/revokes，
通过 `PUT /api/admin/users/{id}/permission-overrides` 整体保存。

员工详情页可用 `/admin/permissions?employeeId=...` 深链本页。前端先调用
`GET /api/admin/users/by-employee/{employeeId}` 精确解析账号；未开通可用账号时明确提示，不回退
到模糊搜索。部门详情使用 `/admin/permissions?departmentId=...` 精确选中部门。两类深链都只对
超级管理员且具备 `authorization:manage` 的账号开放。

## 四、可查看数据与人员交接（V393–V399）

服务端目录动态返回八个 scope，Flutter 不再硬编码“业务员/制单人”清单：

| scope | 页面名称 | 全量权限 |
|---|---|---|
| `goods` | 货品资料（当前开关关闭时显示“功能未启用”） | `goods:view:all` |
| `client` | 客户资料（内销、外贸、OEM 统一） | `client:view:all` |
| `sales` | 销售单据 | `sales:view:all` |
| `purchase` | 采购单据 | `purchase:view:all` |
| `subcontract` | 委外单据 | `subcontract:view:all` |
| `production_plan` | 生产计划与日报 | `production_plan:view:all` |
| `stock_doc` | 仓库单据 | `stock_doc:view:all` |
| `finance` | 财务单据 | `finance:view:all` |

员工详情分为“操作权限 / 可查看数据 / 账号安全”。可查看数据按客户与销售、采购与委外、生产与仓库、
财务分组，每张卡明确显示“仅本人 / 额外查看 N 人 / 查看全部覆盖 / 功能未启用”。全量权限覆盖或功能
未启用时不发送无意义的 owner 配置请求，并说明原因。

现行公式：

- 手工 `user_data_scopes` 精确增加 raw `visibleOwners`，永远只读；数据库保存 owner 任职代际，A 复职后旧行保留但自动失效，管理员显式 replace 才写新代际；
- 本人和双端任职代际仍匹配的正式 handover 来源进入 `writableOwners`；最新 target 失效时不得回退更旧边；
- `*:view:all` 是显式全量数据范围；只有再具备相应 edit/delete/status 动作时才能写全量对象；
- 单客户只读共享不扩大到同 owner 其它客户；客户交接把 client scope A 精确展开为本批客户 grant，不改成 B；
- `client:assign` 无部门/角色默认，只能超管或中央个人 grant；客户候选走 `/api/master/clients/access-candidates`，不要求 `employee:view`；
- 客户对象的编辑、删除、状态、地址与访问设置分别服从后端 `writable` / `accessManageable`；
- 候选数量排除软删除与客户财务占位，生产范围包含计划、日报和物料分析；离职 raw owner 显示“历史只读”。

因此“额外查看”不再等于“可以修改”。财务审核/红冲等 maker-checker 池化动作必须同时具备普通读范围
和专用 action authority，不能借功能权限发现原本不可达的单据。

业务页面通过 `GET /api/auth/me/document-scopes/{scope}` 获取当前登录主体的普通写能力，响应仅含
`scope/writeAll/writableOwnerIds`，没有目标用户参数。详情页在能力加载或失败期间先隐藏普通写动作；
从地址栏直达编辑页时，必须在填充任何可编辑状态前完成同一检查，失败则提示“当前仅可查看”并返回详情，
不能先渲染表单、保存时才收到 403。能力缓存按 scope 自动释放，详情刷新会显式失效缓存，以便正式交接后
重新计算。

详情页在表头前统一显示操作范围说明：加载时说明正在确认；失败时说明当前仅查看并提供“重试”；额外查看
只读时说明需正式交接或联系管理员。历史 `maker/owner` 为空不是“额外查看”，必须显示“历史单据未维护
负责人，当前只读”，`writeAll` 也不隐藏该提示。提示同时使用图标、文字和主题语义色，支持换行与读屏，
不靠颜色区分。

生产计划 `allowedActions` 空或缺失时不再兼容性放行；采购/委外详情缺少
`canEdit/canDelete/canReverse` 时默认 false。非订单标准详情由服务端明确返回这三个字段，订单详情继续
返回包含财务待审等更细流程限制的字段；前端不得用本地 status 猜测缺失能力。

财务审核/红冲/总账确认、生产审核等池化动作不使用普通 `writableOwnerIds` 代替其专用服务端判断；
生产链仓库任务也继续使用“动作权限 + 仓库组织范围”。采购/委外“提交财务”属于原负责人普通状态动作，
服务端在同一事务内先锁单并校验 submitter owner，再生成审批快照；财务 approve/reject 不走该 submitter
门禁。

整体替换数据范围时，Flutter 同时提交 desired 与 expected owner 集；服务端先取得 user+scope advisory lock，
比较当前集合，不一致返回 409 并刷新，避免两个管理员静默覆盖。候选覆盖八个范围中拥有 raw 数据的
在职及离职负责人，最多 1000 人并稳定排序。desired 非空属于授予，只允许当前员工且账号 active；
desired 为空属于纯撤权，仍按 employee → user 锁定并复验绑定，但允许 resigned/disabled 目标清空旧范围。

“人员数据交接”是另一条真实流程：选择来源、接手人和 scope，preview 数量/阻塞项后原子执行；它改变
当前责任或历史可处理范围，但不复制功能权限，也不改 maker/approver/created_by。详见 ADR-050。

### 4.1 页面状态、历史只读与 CAS 恢复

`GET /api/admin/data-scope-owners?scope=...` 返回拥有真实 raw 数据的负责人，不只返回当前在职人。
候选项包含 `status`、`historicalOnly` 和数量：离职原负责人可选且显示“历史只读”，只增加该员工原有
历史数据，不随其当前接手人的范围或新增数据扩大。接收授权的目标账号本身仍必须是当前员工且账号
启用；锁定、停用账号不显示“人员数据交接”入口，超级管理员也不作为该入口的数据接收人。
账号摘要直接使用服务端 `employeeStatus/currentEmployee`；Flutter 不复制 active/probation/onLeave 列表。
非当前员工禁止启用、锁定、解锁、开放外网、提升超管或新增个人/数据范围授权，但仍允许停用、关闭
外网、取消超管、清空授权及对 disabled 账号重置密码。

从 `*:view:all` 切回普通范围时，Flutter 会重新加载并显示此前保存的 owner 集，不把“尚未加载”误画成
“仅本人”。整体替换同时提交 desired 与 expected owner 集；409 时页面恢复原选择、刷新最新权威设置并
要求重新确认，不静默覆盖另一管理员或窗口的更新。功能关闭或全量权限覆盖时不发送无意义的 owner
更新请求，并在卡片中说明原因。

### 4.2 客户对象能力与“负责人和可见人”

客户列表与详情 DTO 下发两个服务端权威对象能力；Flutter 缺字段时 fail closed：

| 字段 | 服务端语义 | Flutter 用法 |
|---|---|---|
| `writable` | 本人负责人、正式 handover、显式 `client:view:all` 或超级管理员进入可写对象范围；手工 owner scope、单客户 share 为 `false` | 再与 `client:edit/delete/status`、地址新增/删除等功能权限相交，控制详情、行菜单、批量动作和地址簿写入口 |
| `accessManageable` | 服务端已合并 `client:assign` 与对象关系；本人、正式 handover、待分配客户或 see-all 可管理，单纯共享/手工 scope 不可管理 | 控制客户详情中的“负责人和可见人”入口 |

只读客户详情明确显示“只读（额外查看或单客户共享）”。用户仍可查看，并在有权开单时选择已有收货
地址，但不能编辑、删除、启停客户，也不能新增/删除地址；写接口仍逐项执行同一对象策略，前端显隐
不是安全边界。

负责人/查看人选择不复用 `/api/org/employees`，而调用
`GET /api/master/clients/access-candidates?search=&page=&size=`。该端点只需 `client:assign`，按姓名、工号、
部门服务端搜索并分页，只返回当前员工、启用账号和最小非 PII 字段。保存使用客户 `accessVersion` 的
CAS、必填原因和不超过 1000 个字符的审计说明；409 时刷新最新负责人和查看人后要求重新确认。

负责人由 A 改为 B 时，如果 A 仍是当前员工且账号启用，服务端会把 A 暂时保留为该客户的单客户只读
查看人，避免 A 名下引用该客户的在途销售草稿立即失效。保存后以响应中的最终 viewer 列表为准；后续
手工移除 A 前必须确认其没有在途草稿，移除不会改写历史 maker/approver/created_by。

### 4.3 人员数据交接 UI 与影响项次

人工交接是四步流程：选择交出人与 scope → 核对影响项次 → 填原因并确认执行 → 查看完成回执。页面
提供全选/清空；选择全部业务 scope 时还会处理直属下级关系并释放临时任务认领，这两类系统责任不能
单独选择。目标账号必须启用且不是超级管理员。

来源/接收候选调用
`GET /api/admin/data-handovers/candidates?role=source|target&query=&page=&size=`，不依赖 `employee:view`。
服务端按操作者的人事/组织范围裁剪：source 可含未删除离职员工用于补交接；target 只含当前员工、启用
账号且排除超级管理员。人工 preview/execute 本身只允许 `employee:handover`；`employee:offboard` 不能
借候选接口执行独立人工交接。

preview 的 `transferCount / historyAccessCount / releaseCount / blockingCount` 是服务端权威的四类影响
项次，`total` 等于四类相加，**不是去重业务记录数**；合成提示 `target.required` 不进入 blockingCount
或 total。`scopeTargetEmployeeIds / scopeTargetEmployeeNames` 直接给出每个 scope 的实际接手人：已完成
分模块交接的 scope 显示“沿用既有交接”，本次选择者显示“默认接手剩余范围”，不得用本地候选反查姓名。

执行使用 UUID `requestId` 幂等；409 表示预览后对象、接手资格或交接图已变化，页面返回预览步骤并重新
盘点。handover 与 offboard requestId 都比较相关员工任职代际，任一端复职后旧请求不得误报成功。
成功后页面保留完成回执，显示批次、实际分类项次和逐项结果，再由用户主动关闭。交接改变当前责任或
历史可处理范围，但不复制功能权限，也不改 maker/approver/created_by。

本轮 Flutter 发布前证据：定向 `40/40`、完整测试 `1007/1007`、完整 `flutter analyze --no-pub` 为 0 issues、Web release exit 0。后端、
PostgreSQL、迁移与恢复证据统一放在全链路实施报告中，本页面文档不复制可能漂移的数字。

## 六、安全与审计要求

- 临时密码只在重置响应显示一次，不持久化、不写日志；复制后由管理员安全交付。
- 临时密码 72 小时过期（V297 `users.temp_password_expires_at`）：过期后密码正确也拒绝登录
  （401「临时密码已过期」），改密成功清除该标记；入职/补开初始密码不设有效期。
- 重置临时密码写显式审计 `password_temporary_reset`（操作人/目标/生成模式，不含明文）；
  账号支持端点禁止操作超级管理员与本人（`AdminUserSupport.requireAccountSupportTarget`），
  即使持 `account:support` 的账号被盗也无法借此重置超管密码。
- 开通账号候选接口只回传姓名/工号/部门与资料齐备布尔位，单次限 20 条，不构成花名册导出通道。
- 授权管理不能只靠前端路由或按钮隐藏，Controller 与 Service 均需校验超管身份。
- `remote_access` 必须由 cloud 登录、refresh 轮换前和每个已认证员工请求三处共同检查；local 站点
  则由位于 JWT 之前的源 CIDR 门禁覆盖登录在内的全部 `/api/**`。客户端选服务器不构成授权。
- 远程开关变更必须原子更新账号、使 access 版本失效、撤销全部 refresh 并记录审计；任一步失败应
  回滚。重复写入相同值为无状态变化，不应无故驱逐当前会话。
- 进入应用的 `GET/POST/PUT/PATCH/DELETE/HEAD /api/**` 由 Filter + MVC 拦截器记录请求元数据，
  包括匿名认证、401、CORS 非法来源 403、404/405 与 MVC 前异常；
  部门权限、个人覆盖等公开业务表由 V169 触发器补脱敏 before/after，授权变更另有显式语义事件。
- 除超级管理员固有全权限外，`audit_log:view` / `audit_log:export` 只能作为个人 grant；部门权限保存包含任一代码必须整体拒绝，
  直接写 `department_permissions` 也由 V173 触发器拒绝，不能静默丢弃后继续保存其它权限。
- **高危个人-only 权限清单**（任何部门默认都不授予，需逐条个人点名；V212 矩阵与「全部授权」按钮均排除）：
  `audit_log:view`、`audit_log:export`、`authorization:manage`、`stock:balance:adjust`、
  `finance_asset:approve`、`finance_asset:post`、`finance_asset:dispose`、`finance_asset:export`、
  `finance_asset_period:manage`。其中仅 `audit_log:*` 由 V173 触发器
  硬拒绝部门级写入，其余靠迁移不默认授予 + 页面「全部授权」排除来保证；超管仍可对个人点名授予。
  `production_material_analysis:bom_override` 已于 V423 删除，不属于当前 personal-only 清单，超管也不得重新授予。
  「全部授权」在此基础上额外排除敏感业务动作 `sales_order:priority`、`sales_order:reallocate`、
  `supplier_return_task:view`、`supplier_return_task:complete`、`production_material_analysis:cross_reallocate`（急单/稀缺让单/原下单人专属/跨计划权益调整），避免一键放行。
  V328 曾停用历史 `user:manage`（已随 V455 从权限目录删除）与 `supplier_return_task:handle`（保持 inactive 历史证据），两者均不再进入活动目录。
  页面负责人委派还额外禁止 `production_material_analysis:view`，因为 `/production/chain-health` 当前复用
  该权限且查询尚未完成对象范围收口；仍须由超管在全局入口逐人点名授权。
- 回收核查人员的 `audit_log:view` 后，旧 staff access token 由授权版本机制立即失效；重新认证后页面、
  深链和后端列表/统计/详情/本机回执核查都必须返回无权。
- 必须测试非超管即使被错误授予 `authorization:manage` 仍不可进行授权管理。
- 必须测试账号支持人员只有 `account:support` 时不能读写权限目录、个人覆盖或数据范围。
- 必须测试 support-only 打开共享页时不渲染且不发出任何授权/数据范围/部门配置请求；只有
  `authorization:manage` 的非超管即使能看到入口，后端也必须拒绝授权操作。
- 必须测试页面权限负责人未持 `account:support` 时只能看到未开户说明，不能通过页面或手工请求开户；
  同时持有 `account:support` 时，开户仍由员工状态、手机号/证件齐备、登录名唯一和既有账号检查终审。
- 必须测试取消、开户失败或并发下已由他人开户时，不提交任何权限 PUT；开户成功后权限详情只能在
  一次性凭据确认保存并关闭后加载，不能让刷新/导航覆盖凭据交付。
- 必须测试个人覆盖、用户角色、员工换部门、部门树移动/软删、共享角色/权限、超管和员工绑定变化
  都会使旧 access token 立即 401，并验证重新登录后的权限快照。

## 七、涉及实体

- `*:view:all` 只建立显式全量对象范围，不替代 `*:edit/delete/approve/...` 功能权限；反过来，只有功能权限
  但对象不可达时也不得显示或执行写动作。
- 客户 `writable/accessManageable`、数据范围 `historicalOnly` 和交接四类计数均以服务端响应为权威；
  Flutter 缺字段时 fail closed，写接口仍重新鉴权，不能把 DTO 布尔值当成客户端授权票据。
- 人工交接 target 必须是当前员工、启用账号且非超级管理员；source/target 候选接口只返回最小字段，
  不得退回到需要 `employee:view` 的完整员工列表。
- 数据范围与客户访问 CAS 发生 409 时必须丢弃本地乐观结果、刷新权威状态并要求用户重新确认，不得
  静默覆盖另一管理员或另一窗口的更新。
