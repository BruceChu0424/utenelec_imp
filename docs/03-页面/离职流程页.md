# 离职与数据交接页

> 路由：`/employee/:id/offboarding`
> 实现：`lib/features/employee/pages/employee_offboarding_workflow_page.dart`
> 后端：`GET /api/org/employees/{id}/handover-preview`、`POST /api/org/employees/{id}/offboard`

## 一、定位

具备 `employee:offboard` 的账号通过四步向导办理离职。系统先盘点各 scope 的真实接手关系，再原子交接
当前责任、清理个人授权、写离职任职记录、停用账号并撤销会话；不再把一段“交接说明”冒充数据交接，
也不把页面勾选冒充外部门禁/资产系统的自动核验结果。

## 二、四步流程

### 1. 离职信息

- 明确显示员工姓名、工号和部门，避免只凭 URL 办错人；
- 离职类型使用稳定码：`VOLUNTARY / DISMISSED / CONTRACT_END / RETIRE`；
- 生效日期不得晚于今天、早于入职日或最新任职事件；
- 离职原因必填，1–2000 个字符；
- 修改类型、日期、原因、默认接手人或确认清单后离开页面，必须提示放弃未保存内容。

### 2. 默认接手人

- 页面所选人员是“默认接手剩余范围”，不是覆盖所有既有交接关系；
- 如果某个 scope 以前已正式交给 B/C，preview 保留该关系；默认接手人 D 只接尚未交接的 scope；
- `scopeTargetEmployeeIds / scopeTargetEmployeeNames` 由服务端直接返回每个 scope 的实际接手人，页面分别
  显示“沿用既有交接”或“默认接手剩余范围”，不得用本地候选反查姓名；
- 候选走 `GET /api/admin/data-handovers/candidates?role=target&query=&page=&size=`，不要求
  `employee:view`；只含当前员工、启用账号，排除本人和超级管理员，并按操作者人事/组织范围裁剪；
- 系统先请求真实 preview。无未交接责任时允许不选默认接手人；仍有未交接责任时必须选择。

### 3. 数据盘点

盘点卡按模块显示服务端权威的四类“影响项次”：

| DTO 字段 | 动作 | 口径 |
|---|---|---|
| `transferCount` | `TRANSFER` | 客户、货品、供应商、模具、询盘、研发任务、待退回任务、草稿生产责任等当前责任 |
| `historyAccessCount` | `HISTORY_ACCESS` | 历史单据不改 maker/approver/created_by，接手人只获得对应历史范围 |
| `releaseCount` | `RELEASE` | 临时任务认领、待处理个人资料申请和离职账号个人范围等清理项 |
| `blockingCount` | `BLOCKING` | 必须先回专业页面处理，离职不能继续 |

`total = transferCount + historyAccessCount + releaseCount + blockingCount`，是**按分类相加的项次**，不是
去重业务记录数；同一记录可能因“当前责任”和“历史查阅”分别计入。合成提示 `target.required` 不进入
blockingCount 或 total。

阻塞项包括仍担任部门负责人、已派工/生产中执行段、生产组织不匹配、未终态资产/待摊、未来已批准
访客、直属上级环路和交接图环路。红色不是唯一信号：卡片同时显示图标、文字、数量和“必须先处理”。

### 4. 回收与确认

四项确认不是只存在 Flutter 的布尔值，而是随离职命令提交的稳定代码：

| 稳定码 | 页面文案 |
|---|---|
| `ACCESS_CARD_RETURNED` | 已线下确认门禁卡回收 |
| `COMPANY_ASSETS_ACCOUNTED` | 已线下确认公司资产已清点并完成回收安排 |
| `ACCOUNT_DISABLE_ACKNOWLEDGED` | 已知悉：交接与离职事务成功后系统自动停用账号 |
| `SOCIAL_BENEFITS_ARRANGED` | 已线下确认社保公积金停缴安排 |

后端拒绝缺项和未知代码，并把 requestId 与四项中文确认写入离职事件及 `EmploymentHistory`。这些字段
只证明办理人作出人工确认，不代表系统已自动查询门禁、资产或社保外部系统。最终确认展示默认接手人、
影响项次以及“历史操作事实不改写”；只有全部事务成功后账号才自动停用。

## 三、主要接口与请求体

| 能力 | 接口 | 权限 |
|---|---|---|
| 离职 preview | `GET /api/org/employees/{id}/handover-preview?successorEmployeeId=` | `employee:offboard` 或 `employee:handover` |
| 交接候选 | `GET /api/admin/data-handovers/candidates?role=target&query=&page=&size=` | `employee:offboard` 或 `employee:handover`；再按人事范围裁剪 |
| 提交离职 | `POST /api/org/employees/{id}/offboard` | `employee:offboard` |

请求体示例：

```json
{
  "requestId": "UUID，始终必填",
  "resignType": "VOLUNTARY",
  "effectiveDate": "2026-08-25",
  "reason": "离职原因",
  "successorEmployeeId": "有未交接责任时必填，否则可省略",
  "handoverReason": "可选，最多 2000 字符",
  "confirmedChecklistCodes": [
    "ACCESS_CARD_RETURNED",
    "COMPANY_ASSETS_ACCOUNTED",
    "ACCOUNT_DISABLE_ACKNOWLEDGED",
    "SOCIAL_BENEFITS_ARRANGED"
  ]
}
```

`requestId` 即整笔 offboard 的幂等键，即使无需接手人也必须发送。相同 requestId 与相同 payload 在完成后
重试返回成功且不重复交接；相同 requestId 携带不同 payload 返回 409。旧 `handoverRequestId` 已移除。

## 四、服务端事务顺序

1. 校验 `employee:offboard`、自操作/超管保护、离职原因、日期和四项确认清单；
2. 以 requestId 获取 coordinator/advisory lock，创建或重放 `employee_offboarding_events`，并锁定离职人、
   默认接手人与既有 scope 接手人；
3. 同事务把员工置为 `resigned` 并 flush，配合数据库 guard 阻止并发新增责任；
4. 重做 offboarding preview；存在 blocker、缺少默认接手人或 scope 接手资格失效时返回 409 并整体回滚；
5. 按 `scopeTargetEmployeeIds` 分组幂等执行交接，写交接批次、scope、客户访问事件和通用审计；
6. 停用离职人的个人权限覆盖与负责人委派，清除 `user_data_scopes` 和单客户只读 grant，驳回在途资料
   申请并释放 claims；
7. 写 `EmploymentHistory(resign)`，remark 包含 requestId 与四项人工确认；
8. 最后停用账号、关闭 remote access、强制下次改密并撤销 refresh token，再把 offboarding event 标为完成。

任一失败整个事务回滚，因此不会发生“交接失败但账号已停”或“只转了一半”。

## 五、权限与安全

- 离职入口：`employee:offboard`；
- 独立人工交接：`employee:handover`；
- 候选接口可由 `employee:offboard` 使用，不代表它可以调用独立人工交接 preview/execute；
- 默认接手人和既有 scope 接手人必须是当前员工、启用账号且非超级管理员；
- 不复制离职人的功能权限、个人 grant/revoke 或页面负责人委派；只转移服务端定义的当前责任和历史
  可见关系；
- 离职清理会停用个人权限覆盖、负责人委派，删除手工数据范围和单客户共享，释放任务认领；
- 复职只恢复员工/账号为 active，同时保持 remote access 关闭、强制改密；**不会自动恢复**离职前个人
  权限、负责人委派、`user_data_scopes`、单客户共享或原责任数据，必须按新任职重新授权；
- 不可达客户/单据仍按服务端对象策略返回 404，写操作按动作契约返回 403/409。

## 六、响应式与状态

- compact 为单列步骤和底部操作栏；medium/expanded 使用受控内容宽度；
- 四步 Stepper、页面底部主动作和“上一步”形成稳定路径；日期、原因、默认接手人和交接原因在字段附近
  显示必填错误；
- loading、空数据、preview 失败、blocker、409、重复请求回放均有明确反馈和重试入口；
- 快速更换默认接手人时使用请求代次，旧 preview 不覆盖新选择；提交期间按钮 loading 且不可重复操作；
- 执行 409 后自动回到“数据盘点”并刷新权威状态，不留在过期确认页；
- 离开未提交向导前逐步返回并最终提示放弃；
- 颜色不是唯一状态信号，所有阻塞同时显示图标和文字。
