## 一、问题

用户口径(2026-09-15)：

> 车间生产完成的不一定走仓库。物料 A 的子件物料 B 做完(可能只做了一部分)，
> 班组内部检查合格后，不入库，直接运到物料 A 那里投入生产。流程尽量简化。
>
> 关键思路：**通知对应的那个生产任务领料，但是领料位置是另一个。**
>
> 复核后的边界：**两个不同的车间必须走仓库；同一个车间才可以不走仓库。**
>
> 既然是车间内流转，步骤能简化就简化，比如不需要领料、自动解锁。

现状要走满：仓库送检登记 → 品质部 FQC → 仓库点收入库 → 车间提交领料 → 仓库发料 → 开工。
同一个车间、同一批人、料根本没离开过车间，却要惊动仓库和品质部各两次。

## 二、决策

### 2.1 不绕开「仓库」这个数据概念，只绕开「仓库」这个部门角色

给车间一个**线边仓**：车间自己的料架，仓库部门不管、不点收、不进成品仓报表，
但它是一个真实的叶子仓，料确实在那里，流水记的就是它自己的 UUID。

为什么不做成「纯记账、料不在任何位置」——四道既有硬闸会同时挡死：

1. 执行段进 READY 要求每条需求 `stock_backed >= required`(V249)；
2. 需求 FULFILLED 的唯一来源是预留的 `consumed_qty`；
3. `can_close` 要求 `issued_qty > 0`，否则父段永远完工不了(V152)；
4. **成本产出行的 `movement_id` 是 NOT NULL**(V517)——没有库存移动就没有成本产出，
   子件的成本会永远停在在制、结不出来。

绕开第 4 条要新开一条不经 `stock_balances` 的价值路径，与 V500「池头节点必须等于唯一一行
`stock_balances`」正面冲突。而线边仓方案让价值、成本、清账、退料、结算、完工判定
**六条链一行都不用改**，新增的只有「谁登记、谁放行、入哪个仓、谁点收」四个角色换人。

### 2.2 适用边界：同一个车间

子件工单、上层工单、线边仓必须同属一个车间部门，且线边仓与收料需求同主仓。
跨车间一律走原路线——料一旦离开本车间就脱离同一批人的视线，交接与账实相符必须由仓库承担。
这条边界写在数据库守卫里(V584 `fn_guard_workshop_direct_transfer_item`)，不是界面约定。

### 2.3 只有一个人工动作：主管审核

报工时这一行选「转下一道工序」并指名投给哪个上层工单；主管点一次审核，
同一笔事务里自动完成：

1. 写直送事实(谁、把哪一行报工的产出、投给哪条上层需求)；
2. 记一条班组自检放行(FQC 三张表，`inspection_kind='WORKSHOP_SELF'`)，
   由它按既有放行链路生成入线边仓的成品入库草稿；
3. 确认那张入库单：料进线边仓，子件的完工量 `iqty` 与成本才算数；
4. 重算上层工单齐套，齐了就地形成线边仓领料单；
5. 把料投给上层需求，上层立刻可开工。

第 4、5 步是**尽力而为**：上层还缺别的料时不算失败，料留在线边仓等后续到料，
既有的就绪补偿会在齐套时自动提升。绝不因为上层没齐套就把整张报工审核回滚掉。

### 2.4 一行一个去向，要拆量就拆行

送检登记行与 FQC 检验都按报工行唯一(V548/V410 的部分唯一索引)，行内拆量要同时改
这两处唯一性。所以「一部分送仓库、一部分转车间」的表达方式是**报两行**。
超出上层需求的部分不能直送(没有指向对象)，只能另起一行送仓库变成公共备货(V577 口径)。

### 2.5 班组自检复用 FQC 三张表，不另起炉灶

入库放行校验、成本对象覆盖判定、不合格的返工/报废/补产闭环、报工红冲时的检验取消——
四套既有机制全部以「这条报工行有没有 inspection」为判据。另起一套自检表要在四处各开一个
口子，每个口子都是一次 fail-open 风险。所以自检落成一条 `WORKSHOP_SELF` 的 inspection，
只把「谁判的」标出来。

用户明确选择**班组可以判合格/返工/报废**。因此数据库层不限制 `WORKSHOP_SELF` 的决定取值；
责任靠 `decided_by_employee_id` 留痕，品质部保留在放行未被消费前追加决定的翻案通道。

### 2.6 单独一个审核权限码，而不是靠日报审核权顺带

上面那条链在正常流程里分别需要 `production_quality_inspection:approve`(品质部 + QA 范围)、
`stock_doc:approve`(仓库 + SUB_WH 子树)、`stock_doc:issue` 三个码。把它们隐式塞进
「日报审核」等于一次看不见的提权——谁有报工审核权，谁就能写品质放行和库存事实。

所以新增 `production_direct_transfer:approve`。持有本码**不等于**获得那三个码：
它只允许在「同车间直送」这条被数据库守卫钉死的窄路径上写那几笔事实。
服务端对应地把仓库单据的授权判定从「仓储范围」改为「这张单据是不是一次有效直送的某一条腿」，
两条腿各有自己的证据(入库单认来源报工行上的直送行，领料单认计划包映射到的收料工单)，
并且都要求目标仓正是那条直送记录的线边仓。

## 三、明确不做

| 不做 | 理由 |
|---|---|
| 新增过账类型 / 预留归属类型 / 移动类型 | 既有守卫比 CHECK 硬得多，且 V514 的方向断言没有 ELSE 分支，多一种类型会让它返回 NULL、整条断言静默放行。「守卫看起来还在、其实已经瞎了」比报错更坏 |
| 跨车间直送 | 见 §2.2，用户口径 |
| 行内拆量 | 见 §2.4 |
| 接收方单独签收 | 同车间同一批人，没有部门间交接。数量有异议就红冲整张报工重报 |
| 暂存待接(上层工单还没建时先直送) | 需要改动既有分配逻辑的仓库筛选，风险是全局的(所有工单的齐套判定)。上层没下达时界面不给「转下一道工序」 |
| 复用 V194 的 MAKE peg | `packageOwnsSupply` 对新业务是死分支 |

## 四、验证

真实 PostgreSQL 全链 E2E
`FullChainEndToEndTest#workshopDirectTransfer_childFeedsParentInOneWorkshopWithoutTouchingTheWarehouse`
在开发库按真实路径造场景(A 的物料分析 → B 作为自制子件下达 → 领料发料开工 → 报工转下一道工序 →
审核)，断言：

- 子件 `iqty` 按直送量增加(完工量算数)；
- 线边仓余额归零(进一笔出一笔，料只是路过料架)；
- **公共仓库零库存**(整条链没碰过仓库的账)；
- 上层需求按直送量记为已领，执行段从等待物料变为 READY(自动解锁)；
- 仓库待送检登记队列里没有这一行(不产生假待办)；
- 留下一条直送行与一条 `WORKSHOP_SELF` 自检放行，责任人可追。

> **勘误(2026-09-15 复核)**：上述 E2E 未随 b242d1e0 提交入库(当时测试收口阶段被丢弃)，
> 本仓库当前没有直送链的自动化测试；同批回归数字「后端 234 项、前端生产模块 493 项」
> 不含直送链。补回该 E2E 是遗留事项，在本表补齐前 §四 的全链断言以人工验收为准。

同批回归：后端 234 项、前端生产模块 493 项通过。

**未做**：真实车间账号 UAT、跨车间拒绝路径的多账号越权走查、部署回读。
这三项完成前生产 **NO-GO**。

## 五、2026-09-15 补齐：方向勘误与线边仓主档入口

真实链路复检(库内 V6000130 → HV5G001 → 后座/插套组件/压板/保护门，全车间同车间)证实
候选方向**本来就是上层**：子件段报工时，候选=同车间还缺该料的上层工单(需求挂在消费方
段上)，逐段模拟均指向父件工单。用户看到的「无下游」其实是**全线没有一个线边仓**——
V584 建了 `is_line_side` 列与守卫，却漏了主档维护入口，候选查询里的线边仓 EXISTS 把
所有候选筛空，灰显文案「转下一道工序(无下游)」又被读成「方向查的是下层」。修复：

1. **仓库主档支持线边仓标记**(表单/详情/服务端 DTO+前置中文校验)：
   置「是」须有所属车间、参与核算、叶子仓；建法=挂收料主仓下保证同主仓。
2. **候选接口区分空原因**：`/production/direct-transfers/candidates` 返回
   `{candidates, lineSideWarehouseMissing}`；报工页灰显文案相应分为
   「(缺线边仓)」与「(无同车间上层工单)」，表头说明补线边仓前提。
3. 全站措辞把「下游」统一为「上层工单/父件」口径。
4. **审核不卡齐套(2026-09-15 修复)**：真实 BOM 多料场景下，父件还缺其他子件时
   审核曾抛「按本任务已合格入库来源及可用公共库存核算后仍缺料:…」整单回滚——
   直送误用了会抛错的人工重核路径。改为专用尽力而为入口
   `promoteAfterWorkshopDirectTransfer`(缺料与供给未齐都静默返回，料留线边仓等
   既有就绪补偿)，用户口径「父件缺其他物料没关系，各自完成送过去就行，不用卡着」。
5. 候选下拉显示**父件工单的产品**名称+编号(首行)与工单号·还差多少(第二行)——
   车间认「投给谁」认的是产品，不是工单号；`Candidate` 相应增列
   `receivingGoodsCode/receivingGoodsName`。
