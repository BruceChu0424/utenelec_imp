## 一、为什么要这两条迁移

**V574** 修的是一个「服务层通了、数据库还锁着」的断层。专属在途调入的目标已经放开到采购 / 委外 / 自制三条路线，但 V571 的守卫仍要求目标行的确认路线等于来源动作的路线，跨路线写入必被拒；被通用兜底翻译成「数据已被其他操作更新」之后，看起来还像并发问题。公共在途认领则是另一头：服务层按**目标**路线过滤来源，自制目标永远查不到候选，点了只会看到「当前没有可采用的公共在途」——不报错，看起来像没数据。

**V575** 是为「只需 100 却要买 10000」这个常态准备的：货品主档记下最小起订量与订货倍数，采购桶的下达数量默认值按它向上抬一次，富余走既有公共备货通道。

## 二、V574 做了什么

1. **重写 `fn_guard_preplan_future_transfer`**
   - 删掉 `target.confirmed_route IS DISTINCT FROM source_action.route` 这条等值约束。
   - 补上目标行形态不变量：确认路线属于 `BUY / SUBCONTRACT / MAKE`，控制段不是 `SHIP / REFERENCE`。
   - 补上库侧宽松兜底：单笔转入量不超过目标行毛需求。精确的「扣现货与既有在途后的待补量」上限仍由服务层按权威快照把关。
   - 来源侧不变：仍限 `BUY / SUBCONTRACT` 的供给动作、同主仓、同货品 / 颜色 / 单位、不超过未实收容量、交期晚到需显式接受。

2. **公共在途认领零迁移打通**
   守卫 `fn_validate_preplan_shared_future_claim` **不改**：仓库口径 V569 已经统一成同主仓（`fn_warehouse_same_main`），「来源与认领动作同路线」这条也保留不动——服务层改为按来源路线取候选、认领动作沿用来源路线落库之后，这条天然成立。

3. **两条热路径索引**
   - `idx_production_material_analysis_material_goods_lookup (goods_id, color_id, unit_id, analysis_id) WHERE active`：让料软占用与入库唤醒候选都按货品维度跨全库扫活动物料行，既有维度索引以 `analysis_id` 打头用不上。
   - `idx_future_transfer_external_item (external_item_id, created_at, id)`：采购 / 委外改单、关闭、请购中止的 8 个守卫按外部明细反查在途调拨，此前无索引。

4. **刷新两条权限目录文案**（不新增权限码、不改授权关系）：采用公共在途不再写「同路线」、仓库口径写成同主仓；跨计划让料改名为「跨物料分析让料与在途调入」。

**不做的事**：不新增表、不改表结构、不改历史行。因此清库白名单（`business_data_reset()` 与 `ops/reset_business_data.sql` 的表级分类）与审计触发器覆盖都无需变动，只需同步迁移头版本对。

## 三、V575 做了什么

`goods` 表新增两列，均可空：

| 列 | 类型 | 约束 | 含义 |
|---|---|---|---|
| `min_order_qty` | `NUMERIC(18,4)` | `IS NULL OR >= 0` | 最小起订量。允许 0：表示问过供应商、确实没有起订门槛，与「没填」语义不同。 |
| `order_multiple_qty` | `NUMERIC(18,4)` | `IS NULL OR > 0` | 订货倍数（整箱 / 整包）。它是「向上取整到倍数」里的除数，0 既无意义又会除零，因此不允许；服务端把提交的 0 归一成 NULL，数据库检查只是兜底。 |

两列共用一个具名约束 `goods_order_policy_qty_chk`，并各带一条 `COMMENT ON COLUMN`（单字符串字面量，不用拼接表达式）。

`goods` 已在审计触发器的必查业务表里，加列不需要改覆盖白名单；清库脚本按表分类，也不需要改。

## 四、对老数据与目标服务器的影响

- 两条迁移都是前向新增，不改写任何历史单据字节。
- 子层展开的新口径是**重算投影**：分析刷新即进入新口径，不做批量回写。已完结且没有在跑生产计划的分析不会被重算，保持原样；已取消的分析永不刷新。
- 起订量与订货倍数默认为空，等同于现状（不抬量）。维护之后只影响采购桶的默认值，不影响任何已下达单据。
- 目标服务器升级只需跑到 V575；本目录版本不代表公司数据库已经安装。

## 五、怎么验证

- 真库（`UTEN_RUN_DB_TESTS=true`）：采购在途调入自制目标后，目标行「还需安排量」下降而物理缺口不变，合格入库后才形成实物供给；自制目标跨路线认领公共在途成功且动作按来源路线落库；两者的分桶归属都跟随目标行。
- 覆盖量读取：跨路线调入被补算进目标桶的已覆盖量，且语句条数与操作组数量无关（500 组仍是 4 条固定语句）。
- 起订量：默认值抬量与富余提示、无超量权限时不抬量只提示、未维护时保持净需求，三个界面用例。
