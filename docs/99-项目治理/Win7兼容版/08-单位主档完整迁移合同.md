## 2. 单位的事实模型

- 单位是**扁平主档**，日常界面只有 `code`、`name`、`status`。当前列表和详情也只呈现这三项业务字段。不能复制货品分类树，或擅自增加计量规则编辑面板。
- 在线关系身份为 `id: UUID`。`legacyId` 仅为旧库迁移溯源；新建保持null，不能取编号、名称或旧数字ID作为 `goods.unit_id` 等新关系键。
- 读取DTO仍带 `measurementDimension`、`massUnitCode`，供其他业务使用。这两项虽在单位日常UI隐藏，却不能在保存时被默认null清掉。
- 当前单位实体/列表/详情没有对客户端暴露的统一记录version；`unit_measurement_profiles.version` 是计量设置的局部版本，个人操作历史的version又是另一对象，均不能冒充完整单位表单版本。
- `dict()` 返回所有未软删单位，包括禁用项，按名称排序。某个下游选择器是否允许新选禁用单位由其owning合同处理；不能为了让新选择器简单而删掉历史引用需要显示的单位。

## 3. 三个真实写接口

### 3.1 新增

`POST /api/master/units`：HTTP权限为 **`unit:create`**。内部服务也允许 `goods:import`，供其他owning导入流程调用，这不扩大该HTTP接口权限。

```json
{"name":"个","code":null,"status":"使用"}
```

- `name` 必填，服务端trim；新增执行未软删名称的大小写不敏感预查。编号留空由服务器生成；显式编号由服务端查重和全局终身预约保护决定。不能把预检通过或查到同名记录当作提交成功。
- `status` 省略/null时服务器默认“使用”；显式非“使用”目标还要求 `unit:status`。日常UI只提供“使用/禁用”，不能从save DTO没有枚举注解推导可以添加新业务状态。
- 两个计量键都未出现时，服务器可从重量名称学习规则，例如 `kg` 推导 `MASS/KG`。WPF普通新增必须保持省略，不能由通用序列化器发出两个null阻止既有学习，也不能另写一个C#重量名称推导器。
- 成功返回权威 `UnitDetail`。没有客户端命令ID、create receipt或统一记录version。名称/编号冲突不能充当幂等应答。

### 3.2 完整编辑

`PUT /api/master/units/{UUID}`：controller写的是 `hasAny(unit:edit,unit:status)`，**服务层仍无条件要求 `unit:edit`**；显式status与现值不同还要求 `unit:status`。仅status权限的用户不能使用PUT编辑任意字段。

```json
{"name":"箱","code":"原有或新编号","status":"使用"}
```

- 这是name/status的完整目标，不是任意字段PATCH。服务层 `apply()` 直接写name和status：status缺失/null会尝试写null，**不具有“省略保留”的语义**。普通编辑要带原始权威status；没有状态权限时锁定其编辑，不要把原status省略或填默认“使用”。
- code空/null/省略保留当前编号。界面可以编辑code；行内编辑白名单却不包括code，不能将完整编辑全部改走行内PATCH而丢掉这一动作。
- 更新路径没有客户端expectedVersion，也没有创建/编辑receipt。不能将一次提交前GET视为原子并发保护。
- 当前创建做名称重复预查；更新路径没有相同的名称预查。不得在WPF自称拥有源码未实现的更新名称唯一性保证；若业务要求强化，应走共享后端增量并同步两端。

### 3.3 窄状态接口

`PATCH /api/master/units/{UUID}/status`：**`unit:status`**。

```json
{"status":"禁用","version":123}
```

`status` 必须为“使用/禁用”。DTO可带version，但UnitService**没有比较它**，而是悲观刷新当前单位行再只改status。其正确能力是避免窄状态操作覆盖name/code/隐藏计量字段，不是expectedVersion已经生效。

**现有UnitPage单项和多项启停都走 `POST /units/batch-status`**。公共Core先支持这个PATCH是合理的底层接入，不能据此把源页面确认、逐项结果和批量动作标完成。

## 4. 字段 presence：不能把“没有发”和“发了null”合并

`UnitSaveRequest` 只有两个计量键使用@JsonSetter记录presence。普通字段没有相同的标志。

| 场景 | 原值/输入 | 权威结果 |
|---|---|---|
| 编辑日常名称 | 原MASS/KG；两计量键都省略 | 保留MASS/KG |
| 新建重量名称 | name=kg；两键省略 | 可由服务器学习MASS/KG |
| 新建重量名称 | 两键都显式null | 明确未设置，不做名称学习 |
| 编辑仅清重量代码 | 原MASS/KG；`massUnitCode:null`，维度省略 | 保留MASS维度，清代码；在用限制仍可能拒绝 |
| 改离重量 | `measurementDimension:COUNT`，代码省略 | 原重量代码自动清空；在用限制仍可能拒绝 |
| 非法组合 | COUNT与显式KG | 验证拒绝 |
| 明确清全部规则 | 两键显式null/空串 | 目标为删除profile；在用重量限制仍可能拒绝 |
| 普通编辑省略status | name完整，status缺失/null | 不是保留；服务层会尝试写null |
| 普通编辑省略code | code缺失/空 | 保留现编号 |

计量维度合法值：COUNT、MASS、LENGTH、AREA、VOLUME、OTHER。重量代码：G、KG、T、JIN、LB、OZ；服务端trim/转大写，空串视作null。MASS可以不指定重量代码；非MASS不能携带非空重量代码。

当改动涉及改入/改离MASS或更换重量代码，且关联货品有**非零库存或任意出入库流水**时，服务器409拒绝；检查包括已删除货品的历史流水。不能仅查当前可见库存、把未知重量当0，或在客户端换算后绕过。未改变规则是no-op；非重量维度之间改变不应被擅自扩大成相同禁止规则。

### 5.1 实际行内合同

```json
{
  "expected":{"name":"原名称","status":"使用"},
  "changes":{"name":"新名称","status":"禁用"}
}
```

路径为 `PATCH /api/master/inline-edit/units/{UUID}`。API白名单包括name/status/measurementDimension/massUnitCode，本页实际只提供name/status。服务器要求每个变化字段都有原值，NOWAIT单位行锁后比较，再合并当下字段。当前profile/隐藏字段合并不能被WPF变成“拿屏幕三列构造完整对象”。

此入口还要求员工绑定、非访客、账号未锁、未强改密、非模拟身份，及unit:view/edit；状态变化继续要求unit:status。原值比较是正确的局部并发能力，但不具备单调全记录version和命令receipt，也不能防所有ABA/旧全量PUT旁路。

### 5.2 批量与单项生命周期

```json
{"status":"禁用","items":[{"id":"单位UUID"}]}
```

启停为 `POST /api/master/units/batch-status`，删除为 `POST /api/master/units/batch-delete`（没有status）。最多500条，去重后返回 `succeeded/failed/results[{id,label,ok,reason}]`。单位在 `MasterEntityKind` 中 `versioned=false`，即使DTO允许item.version也不能称其已用于单位乐观锁。

成功和失败不能合成一个toast后丢掉：失败保留选中和原因，刷新列表/facets；删空非首页时回退一页。服务端引用目录和可见性规则决定能否删除、拒绝原因能显示什么；不通过本地过滤、原生SQL或新PUT绕过。

### 5.3 两套历史不要混成一个“历史按钮”

| 能力 | 真实API与绑定 |
|---|---|
| 本人窗口 | GET `/api/master/operation-history?entityType=units`；列表含本人操作及事件 |
| 撤回/重做 | POST `/{operationUUID}/undo|redo?entityType=units`，body `expectedVersion`；这是操作记录版本 |
| 对象版本 | GET `/api/master/record-history`，entityType/recordId/过滤/cursor；GET `/{revisionId}` 获取差异和能力 |
| 恢复版本 | POST `/api/master/record-history/{revisionId}/restore?entityType=units`，body `{expectedHead,before}` |

个人操作入口的UI便利条件是有单位写权限；读取仍需unit:view，真正重放还看原动作及字段权限。canUndo/canRedo不是客户端按状态推算的按钮。后续修改、不可见对象、引用、模拟身份和支持范围都可使动作被阻止。

对象历史可以按unit:view读取，恢复要求当前编辑及相应字段/动作权限；DEDICATED授权、责任、计量等证据明确要求走原维护调整。`expectedHead` 只保护这次恢复，不能拿来填UnitSaveRequest不存在的version。

### 5.4 导出、打印与排序的实际边界

- 导出不是屏幕行转Excel。当前 `UtenExportButton` 将 `/master/units/export` 映射到异步 `domain=master/report=unit`，支持时先用原job；不可用才调用原直POST。
- job创建参数去掉密码，保存稳定job ID/查询/列投影和身份；下载时重新授权并用本次密码保护。任务SUCCEEDED、获得下载授权、完整落盘是不同阶段。
- 直接导出POST保持列表筛选、空值语义、columnProjection和服务器导出上限；UnitService用REPEATABLE_READ导出code/name/status。不能把客户端当前页排序或隐藏列数据扩成新的权威导出。
- 当前三业务列未开启 `sortable:true`，UnitController/Repository没有sort/order，服务器按code升序；不能把“公共表格有排序能力”记成单位已支持任意服务端排序。
- **权限差异需保留事实**：预览/实际打印由unit:view可读列表装载；`UtenPrintPreviewButton` 本身不检查unit:export，传入的exportPermission仅供预览内导出按钮使用。源码注释写“导出/打印 unit:export”不能当作当前已执行的权限保护。若决定让打印也受导出权限约束，应在公共owning合同明确并同步Dart/WPF及测试，而不是悄悄只改WPF。
- 打印读取当前筛选完整分页快照，保留中文完整字体、预览分页和列投影；选择打印机或取消不能被记为已交付。单位没有采购原单式服务端打印授权/receipt，不能造一个URL假装接入。

### 5.5 有来源的不适用项

单位页没有独立文件导入、附件上传/预览、审批/驳回或分类树；日常计量编辑也已从此页隐藏。这些是本页的来源事实，不应画空按钮充数。货品导入中内部创建单位、平台自设文件列、其他业务计量治理分别属于各自owning合同，不能据此宣称整个项目的导入/附件已迁移或不适用。

## 6. 当前公共Mutation接入与限制

与Core实施者已对齐以下接口；接手时以实际源码和当前检查再次核对：

```text
CaptureMutationOwner() -> auth generation / issuer / user / dataset / read revision
PrepareMutation(UnitCreate|UnitUpdate|UnitStatus, stable local UUID, raw body JSON,
                owner, resourceId?, observedStatus?) -> frozen request
MutateAsync(request, cancellation) -> NotSent | Confirmed | Rejected | Unknown
```

- 本机requestId冻结同一意图、owner和body，不被发送为虚构的服务器幂等键；原UTF8 JSON与字段presence不重序列化。
- PUT要求name/status完整，unit:edit必需；如果observedStatus无法证明未变化，准备阶段保守要求unit:status。页面必须提供同owner下的权威baseline，不能绕过权限判断。
- PATCH status.version只保留原文并标 **AcceptedButIgnored / EnforcesExpectedVersion=false**。
- 401/REAUTH_REQUIRED或StepUp不自动刷新重放；单位没有专属RequiresStepUp标注，独立StepUp能力不能被强加成虚构单位命令合同。网关明确拒绝与原命令Unknown分别处理。
- 初期接口只有内存冻结、同ID不能换body/owner、Unknown不能重发。**DurableMutationJournalAvailable=false**；尚不能声称重启恢复、草稿或完整单位动作已经做完。
- 冻结的descriptor只允许一次尝试；第二次调用被拒。即使收到明确Rejected，用户修正后也应产生新决定和新的本机ID。无法确认业务数据集时不能准备写入；请求头/请求体中没有伪造的服务器幂等ID。
- 只有合同有效、属于当前owner的成功响应才可更新当前表单。响应无效/断网/取消发生在发送后，不能简单回退NotSent；写入确认后本地刷新失败则保持Confirmed，不重新POST。

## 7. 未知提交的核对规则

| 动作 | 当前可用证据与限制 |
|---|---|
| 新增 | 没有create receipt；同名/同code/相似时间/本人历史只能人工核对，不自动认领或重发 |
| PUT/PATCH | 已知UUID GET能证明当前状态，不能证明原命令因果；匹配目标值不等于本次提交成功 |
| inline | 原值比较能拒绝部分旧变更；不是单调命令身份，不能当通用receipt或无条件重试依据 |
| batch | 保留原集合及已收到的逐项结果；整体丢响应时不能猜哪些成功，不能把已成功/Unknown一起再发 |
| 本人undo/redo | `(operationId, expectedOperationVersion, direction)` 可能有确定单步转移证明；须证明精确下一version/目标state及并发/窗口驱逐边界，再实现专用核对；未经证明仍Unknown |
| 对象restore | expectedHead是CAS，不自动提供原请求receipt；需审查原restore lineage后做专用核对 |
| 导出job | 稳定job UUID已有GET/cancel/download状态；恢复原job，不因丢响应新建同样导出；任务完成不等于本机保存 |

不得用“HTTP方法是PUT”“目标本来就是禁用”“名称有唯一约束”或自增客户端命令号代替强幂等。重启、换账号/服务器/数据集或权限降低后，原意图仍归原owner；可只读核对不等于重新得到写权。
