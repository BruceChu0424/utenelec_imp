# ADR-100 进行中黄色数量徽章与三形态计数口径

- 日期: 2026-09-21
- 状态: 已接受
- 取代/修订: 修订 [准则 14-徽章与计数口径](../00-项目准则/14-徽章与计数口径.md) 的「界面上的数字只有两种」,
  改为三种; 其 §四之二、§四之七 中「球在别人手上一律中性括号」的措辞同步作废。
- 相关: [ADR-098 委外允许损耗与回厂短交判定](ADR-098-委外允许损耗与回厂短交判定.md)(本次采购侧照抄它的
  「三段合并成进行中 + 状态列可筛」范式)

## 一、背景与用户口径

用户 2026-09-21 原话(两段, 后一段是对前一段落位的修正与追加):

> 现在每个卡片右上角都有红色通知徽章, 这是重要或者待处理任务的数量汇总。我想在每个卡片
> 名字后面加个黄色数量徽章, 标识正在进行中的数量。比如生产部「车间生产任务」黄色徽章 =
> 生产中的, 右上角红色 = 等待物料的。「生产管理」后面的黄色徽章 = 任务中进行中的。
> 其他对应的都照猫画虎地去改。然后里面具体页面的分类栏中, 以前「进行中」是 (数量) 这样表示,
> 也统一改成黄色数量徽章。算了算了, 修改下, 工作台卡片的黄色数量徽章也放在右上角,
> 在红色徽章的左边。你仔细理解, 全部页面都好好检查, 然后工作台就是汇总。

> 采购任务工作台顶部的分类, 把「等待财务审核 / 财务已通过 / 财务驳回」这三个统一改成「进行中」,
> 然后进行中的表格加个状态列, 状态就是上面那三个状态, 表头可以筛选。
> 你也检查下其他页面有这样类似的, 都这样改。

## 二、决策

### 2.1 计数形态从两种扩成三种

| 形态 | 组件 | 回答的问题 | 典型档 |
| --- | --- | --- | --- |
| 红色通知徽章 | `UtenNotificationBadge` | **我还欠多少活?** 轮到我动手, 不动会出事 | 待审 / 待确认 / 待收货 / 待出库 / 待检 / 被驳回 / 超期 / 异常 / 等待物料 / 本人草稿 |
| 黄色进行中徽章 | `UtenInProgressBadge`(新) | **我手上还有多少在跑?** 已经在办、还没完、现在不用我动手 | 生产中 / 加工中 / 执行中 / 在途 / 等待财务审核 / 财务已通过待执行 / 等待检查结果 |
| 中性括号 `(N)` | `UtenCountSuffix` | **这里堆了多少东西?** 已经结束的、历史的、全部的 | 已完成 / 已审 / 已出库 / 红冲 / 历史记录 / 全部 / 报表行数 / 主档行数 |

黄徽章的实底色取 amber-600 + 白字加粗, 是用户两轮定色的结果: 先要「数字加粗变白、黄色再深点」,
压到 amber-700 后又说「这个黄色不是黄色了, 稍微淡点」(那一档已经偏棕)。最终落在既读得出是黄色、
白字又压得住的那一档。**不要再往深调**(变棕), 也不要往浅调(白字读不清)。

判定顺序, 逐档问两句:

1. 这个数字变大时, 有人在等我干活吗? 是 -> **红**。
2. 不是 -> 这一档的东西还在流程里没结束吗? 是 -> **黄**; 已结束/纯浏览 -> **括号**。

这条线不是新发明: 准则 §四之二(2026-09-11 收口)早就把「球在别人手上」的档单独列出来说明
「页内照常以中性计数呈现, 但不进红徽章、不参与上卷」。本次只是给那一类数字一个**自己的颜色**,
并让它也能上卷 —— 上卷走的是**另一条链**。

### 2.2 落位: 黄左红右

- hub 卡 / 工作台模块卡: 右上角并排两枚, **黄在左、红在右**(`UtenHubCard.progressBadge` / `.badge`)。
- hub 页顶栏: 「进行中 N」黄药丸(`UtenModuleProgressChip`)排在「待办 N」红药丸左边。
- 分段栏: `UtenSegmentCountForm.inProgress`。**双维度页(大类在上、小类在下)的大类行
  同样可以并排两枚**: 主枚 `UtenFilterSegment.count` + `countForm: actionable` 画红,
  第二枚走 `UtenFilterSegment.inProgressCount` 画黄、照样排在红的左边(组件已代劳, 不要
  自己拼 Row)。每枚都是本大类下同色小类之和。目前两处: 销售订单进度查询、
  仓库品质部检查结果(后者是补挂出来的, 见 §2.5.2)。
- 两枚都遵守 **0 或未知不渲染**(不留黄色的 0, 也不把「未知」伪装成 0)。
  分段栏里因此会出现「黄段有数时占位、归零时缩回」的轻微跳位 —— 红色分段从 2026-09-11 起
  就是这个行为, 不为黄色单开一套。

### 2.3 两条链, 两张注册表, 互不相干

```
TodoEntry        -> BadgeModule -> todoTotalCountProvider          (红: 我还欠多少活)
InProgressEntry  -> BadgeModule -> inProgressTotalCountProvider    (黄: 手上还有多少在跑)
```

**导航 Tab 的角标只有红色, 不挂黄色**。用户口径里的「工作台就是汇总」指的是工作台**页面**:
每张模块卡右上角黄左红右, 分区收起时的组徽标也是两枚。外壳导航那一枚是「提醒你欠了活」的
告警位(宽屏侧栏是数字、窄屏胶囊条只是一个点), 而黄色的定义就是「现在不用你动手」——
把它放进告警位是自相矛盾。`inProgressTotalCountProvider` 仍然存在(它是链条顶端, 也是
回归用例的锚点), 只是外壳不订阅它。

- 容器划分 `BadgeModule` 两张表共用, 单独住 `lib/shared/badges/badge_module.dart`
  (原 `TodoModule`, 本次改名 —— 加了黄链之后名字里带 Todo 会让人以为黄色不能用它)。
- 求和只有一处实现, 页面里不手写加法, 规矩与红色完全一致。
- **同一张单据可以同时出现在红数和黄数里**, 这不是双计: 它既在跑、又等你动手, 是两个问题的两个答案。
  双计只在**同一条链内**才成立 —— 同一条链里同一件活只能被数一次。

### 2.4 黄色的「同一件活只数一次」怎么落

分段计数**永不进注册表**(沿用既有硬规矩, 累加只认入口), 所以页面里的黄分段可以放开挑形态。
需要小心的只有**卡面/注册表入口**这一层。本次定下三条去重结论:

| 模块 | 登记为黄色入口 | 刻意不登记 | 理由 |
| --- | --- | --- | --- |
| 销售 | 「订单进度查询」卡: 待排产 + 生产中 + 出货待财审 + 等仓库出货(按**订单**数) | 出货 / 订货 / 报价 / 退货四张单据卡的在途数 | 订单进度的后两段本就是从出货单派生的(`progressStageExpr` 看 `shipment_*_qty`), 再按单据数一遍就是同一批出货翻倍 |
| 委外 | 「委外任务中心」卡: `statusCounts.IN_PROGRESS` | 「回厂短交判定」卡的 容差内待结案 + 分批等待中 | 短交案件只挂在已回厂/在途的 `FINANCE_APPROVED` 订货单上, 那些单已全在 IN_PROGRESS 里 |
| 生产 | 两个都登记: 「生产管理」卡 = 进行中的分析/根计划**批次**数; 「车间生产任务」卡 = 本人**生产中的执行段**数 | — | 两者**不是同一批活的两次计数**: 前者是计划员视角的批次, 后者是车间工视角的工单段, 读取范围也不同(全部可见 vs 仅指派给本人)。两张卡本来在红链里也是各登记各的 |
| 钱流 | 不登记黄色 | 全部 | 财务的活清一色是审批队列: 要么等财务动手(红), 要么球已经离开财务、落在采购/仓库/销售那几张卡上。在钱流再数一遍就是跨卡双计 |

### 2.5 唯一一处**既有红色数字**的口径修正

「车间生产任务」卡的红徽章此前取 `/production/workshop-tasks/count` 的 `count`,
而后端该字段 = `preparing + inProgress`(等待物料 + 生产中的总和)。按用户口径:

- 红 = `preparing`(等待物料);
- 黄 = `inProgress`(生产中)。

**红色数字会因此变小, 这是预期结果**, 不是回归。同一页的「生产中」分段也从红改黄。

除此之外, 本次**不重新裁剪任何既有红色**。具体地, 仓库「预计到货」维持红色不变 ——
字面虽像「已下单待到货」, 但它的判据是 `status='OPEN'` 且**仍有可收量, 或已经挂着草稿收货单**;
后半截是仓库自己登记到一半的活, 整段改黄会把真待办一起喊没。要拆的话得先在服务端把
「纯在途」与「已登记待审核」分成两个数, 另开决策。

### 2.5.1 「我的访客」: 先做分段栏, 再登记黄色

工作台「我的访客」卡一开始**没挂**黄徽章: 它语义上确实有在办态, 但 `my_visitors_page`
整页只有表头下拉筛状态、不带任何计数, 卡上挂个黄数字点进去无处落地, 「卡面数 = 页内同色
分段之和」这条自检当场破。本次按正确顺序补齐: 先给那一页做统一分段栏
(待我确认 红 / HR 审批中 黄 / 已通过待来访 黄 / 已拒绝 不挂), 再登记
`InProgressEntry.visitorHostOngoing`。

两个黄分段各有自己的数, 靠服务端 `host-pending-count` 在同一次扫描里多给两个 FILTER
(`hrReviewing` / `awaitingVisit`)保证恒等式 `ongoing = hrReviewing + awaitingVisit`;
**不是前端相减凑出来的**, 所以不会漂。之所以要拆成两段而不是一段「进行中」, 是因为
被访人列表的服务端过滤是 `status` 等值、没有分组过滤, 一段「进行中」点进去筛不出东西。

### 2.5.2 仓库「品质部检查结果」: 本 ADR 落地后暴露的第一个回归

这是 §2.5.1 那条自检的**反向破法**: 「我的访客」是卡上想挂黄、页内无处落地; 这一页是
**卡上已经挂了黄、点进去被页内大类行吃掉**。

实测(2026-09-21, dev 库与运行中的后端): 库里 2 张委外收货单处于 `WAITING_INSPECTION`、
采购侧 0 张, 仓库 hub 卡的黄徽章显示 2; 但进页面后「采购收货 / 委外回厂」这一行两个大类
都不带黄数 —— 大类行只接了 `GET /quality-results/type-counts`, 而那支口径自 2026-09-11 起
就刻意剔除了 `WAITING_INSPECTION`(它正是 §四之二 那批「球在别人手上」的档)。用户手上那枚
黄色的 2 一进页面就蒸发, 点「采购收货」还只看到一张空表, 只能理解成徽章在骗人。

**修法不是在前端把两支数拼起来, 而是让红黄两数同出一次服务端聚合**: `/type-counts` 改成
一次响应带回 `TypeCounts(actionable, inProgress)` 两组按来源类型分的数, 复用原来那条按
(来源类型, `STATUS_CASE`) 分组的 SQL 只扫一次, 在 Java 侧分流进两个 map; 红那一支的口径
**逐字不变**(仍不数 `WAITING_INSPECTION` 与已完结, 不许图省事改成「未完结」再相减)。前端
只剩一支 `warehouseQualityResultTypeCountsProvider` 发请求, 红黄两支计数 provider 从它派生,
卡面、大类行、小类行吃的是同一份数据 —— 「卡面 = 页内同色分段之和」从此是结构性保证,
不再是靠人对账的纪律。准则 §四之二 自检那节与 §四之七 第 1 条(原文只管到小类行)已同步补记。

顺带下线: 旧 `GET /quality-results/count` 端点与 `pendingTypeCounts` / `countPending` 两个
服务端方法删除(系统未上架, 不做存量兼容)。折成一支 provider 还堵上一个刷新洞 —— 到货登记
当场造出的「等待检查结果」此前不在 `invalidateWarehouseTaskCounts` 的失效清单里, 黄角标要
等 60 秒轮询才动。本条仍守 §3.3: 不新增任何数据库迁移。

### 2.6 采购任务工作台: 三段合并成「进行中」+ 状态列可筛

照抄 ADR-098 已在委外侧落地的范式:

- 阶段分段行从四段收成两段: 「申请待分解」(红) + 「进行中」(黄)。
- 合并掉的三个阶段(等待财务审核 / 财务已通过 / 财务驳回)降级为**进行中表格里的「状态」列**,
  表头可筛, 颜色刻意拉开。
- 「财务驳回」仍要有红色出口: 它继续以**异常小类行**的红徽章呈现(与委外同构), 并继续计入
  采购任务中心的红徽章 `countPending`, 不因为分段被合并而消失。
- 「进行中」黄数 = `summary.statusCounts.IN_PROGRESS` = 三档之和, **与列表行数相等**。
- 已知量纲差异(**沿袭既有实现, 本次不改**): 卡面红数 `countPending` 数的是**单据**
  (`DISTINCT action_doc_id`), 而分段数是**任务行**。这在红色链里本来就存在, 黄色沿用同一套,
  不新引入问题, 但文档里写明, 免得有人拿两个数去对账。

同款「把流程中间态铺成并列分段」的页面一并合并; 但**本人要动手的档不得被吞进「进行中」** ——
草稿、财务已退回(单据列表页那种要本人改单重报的)保持独立分段并保持红色。

## 三、后果

### 3.1 好的

- 三个问题三种颜色, 工作台一眼分得清「欠的活」和「在跑的活」。
- 准则 §四之二 那批「看得见但不上卷」的数字第一次有了自己的上卷链, 工作台真正成为汇总。
- 采购任务工作台与委外任务中心的分段结构对齐, 不再一个四段一个两段。

### 3.2 要付的代价

- 页面分段行在黄数归零时会缩回, 与红色分段同款行为。
- 「车间生产任务」红数字变小, 需要向使用者说明一次。
- 两支既有用例把旧形态写成了契约, 必须同批改:
  - `test/features/purchase/purchase_doc_list_finance_segment_test.dart` —— 把「等待财务审核 = 中性括号 (N)」
    逐字钉死;
  - `test/features/sales/pages/sales_order_progress_rejected_test.dart` —— 断言待排产/生产中是 `browsing`
    且渲染出 `(0)`。

### 3.3 不做的

- 不给黄色新增任何数据库迁移: 所有黄数字都从既有表/既有 count 端点派生。
- 不往 `GET /documents/drafts/count` 与 `GET /documents/status-counts` 里塞新桶
  (两支 SQL 契约测试逐字钉死了桶集合与往返次数), 黄色一律走各模块自己的 `/counts`。
- 不给基础资料 / 报表 / 主档 / 历史只读页挂任何数字 —— 准则 §二 的结论对黄色同样成立。
