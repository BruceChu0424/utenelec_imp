# ADR-128：往来余额按单据币种显示与信用口径统一

- 日期：2026-09-27
- 状态：已接受(2026-09-27，服务端与前端均已实现并有测试)；本地实现，未部署；零数据库迁移、零新增权限码
- 范围：业务审核中心的销售订单财务确认(列表 + 审核详情)、出货财审(列表出货金额 + 审核详情)、采购/委外订货审批(列表订货金额 + 审核详情)；订单资金汇总卡的币种名；应付页两处手拼的「币种 金额」；IQC 不合格退回/贷项的原币 / 本币金额标注
- 关联：ADR-027(财务审核组)、ADR-040(销售开单与财务审核中心)、ADR-053(多币种收款毛额净额)、ADR-097(出货放行记账汇率)、ADR-112(金额十进制原文)

## 背景

用户 2026-09-27 原话：「客户应收的币种 应该和 订单的币种一样 不然不好看 就是 两个币种一样的 我们才知道 还差多少 你这里改改 对应的计算 还有其他的财务地方」。

改之前三处审核页各算各的，而且都只有本币：

| 页面 | 旧算法 | 问题 |
|---|---|---|
| 销售订单财务确认(列表 + 详情) | 该客户全部 AR 行 `amount_balance` 相加 | 本币；把负数的客户预收冲进去，是净额；不分币种；每翻一页都把全表 AR 按客户汇总一遍 |
| 出货财审 | 只加 `RECEIVABLE` 行本币(毛额)，另查本单币种预收 | 口径和订单确认不同 |
| 订货审批(供应商) | 该供应商全部 AP 行 `amount_balance` 相加 | 本币净额；不分币种 |

实例(克隆库)：美金订单旁边显示「客户应收 人民币 -1400」，订单金额和应收用两种币种没法比；另一张没收过预收的订单也被绑在别的订单上的预收「抵掉」。

`ar_ap_ledger` 每行都有 `currency_id` 和原币余额 `amount_balance_original`(有 CHECK 保证与原币分解一致)，所以按单据币种看余额是**精确求和，不需要汇率**。币种主档的参考汇率没维护(美金、港币都是 0)，也不能拿它换算。

## 同行做法(出处)

- **Odoo**：每条应收应付分录有两个未结金额，`amount_residual_currency`(分录自身币种)与 `amount_residual`(公司本位币)。按币种看未结余额是按 `partner_id, currency_id` 分组对 `amount_residual_currency` 求和，不同币种不直接相加。来源：[odoo/addons/account/models/account_move_line.py (16.0)](https://github.com/odoo/odoo/blob/16.0/addons/account/models/account_move_line.py)、[Odoo 18 multi-currency](https://www.odoo.com/documentation/18.0/applications/finance/accounting/get_started/multi_currency.html)。
- **SAP FSCM 信用管理**：信用额度与信用占用按「信用段币种」保存，记账当时按冻结汇率折算，之后不重估；明细项保留单据币种。来源：[SAP Help: Calculating and Transferring Credit Exposure](https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/7113856e409647838af7891e1429b807/4d7ca1db198e0d6ee10000000a42189e.html)。
- **金蝶**：多币别核算的应收汇总/明细可选单一币别或「综合本位币」；外币原币已为 0 而本位币不为 0 的差额是汇兑差异。来源：[金蝶多币别核算手册](https://help.open.kingdee.com/dokuwiki_std/doku.php?id=%E5%A4%9A%E5%B8%81%E5%88%AB%E6%A0%B8%E7%AE%97)(只取到搜索摘要)。

共识：**余额按原币分币种累计，不同币种不相加；只有信用检查和公司级报表才折成一个币种，而且用记账时冻结的汇率，不用今天的汇率。**

## 决定

### 1. 一个查询、一个视图，服务端只算一次

- 端口 `application.port.PartyOpenBalancePort`：`clients(ids)` / `suppliers(ids)`，一次传入一页用到的全部往来单位，一条 SQL 取完(不 N+1)。跨模块只经端口(ADR-017)。
- 实现 `features.finance.arap.PartyOpenBalanceQuery`：AR、AP 各一份常量 SQL，方向与往来列写成字面量，`idx_arap_client_date` / `idx_arap_supplier_date` 两个部分索引能用上。
- 结果 `common.finance.PartyOpenBalances`(账面事实：往来单位 × 币种的原币合计、全币种账面本币毛额、原币未核实部分)，由 `forDocument(往来单位, 单据币种, 本币额度)` 派生 `common.finance.PartyOpenBalanceView`，和额度比较也只在这里做一次。金额按十进制原文输出(ADR-112)。

### 2. 单据币种一档(「还差多少」)

对单据币种 X：

- `openOriginal` = 正式应收(应付)行 `amount_balance_original` 之和，含退货红字；
- `creditOriginal` = 可用预收 / 预付 / 贷项 / 索赔贷项行的原币余额取正数(AR：`CUSTOMER_PREPAYMENT`；AP：`PREPAYMENT`、`CREDIT`、`CLAIM_CREDIT`)；
- `netOriginal` = open − credit。正数 = 客户还欠 X(我方还欠供应商 X)，负数 = 预收(预付)有余；
- 本位币行缺原币时，原币按账面本币(本位币汇率恒为 1)。

### 3. 其它币种各列各的

同一往来单位其它币种的余额放在 `otherCurrencies`，每档用自己的币种原币，**不换算、不相加**。

### 4. 原币未核实的部分单列

旧系统迁入的 `LEGACY_UNVERIFIED` 行，以及非本位币行满足 `LegacyOpeningBalanceSql.unverifiedOriginalCondition()`(缺币种 / 缺原币)的，只有本币账面可信，汇总成 `unverifiedLocal`(另给行数)，页面提示「另有历史应收 人民币 X 原币未核实」，不并入任何币种，也不悄悄漏掉。

与报表共用的这个条件相比有两点有意的差别：本位币行缺原币不算未核实(原币就是本币)；旧系统迁入行即使原币已证明也仍单列，因为迁入时只按旧系统单据类型推断，没有核实它是应收还是预收，不能直接算进「还欠」或「预收有余」。

### 5. 信用 / 铺底全平台一个口径(行为变更)

信用额度、铺底额都没有自己的币种，按本币理解。比较一律用 `openBookLocal` = **全部币种正式应收(应付)行的账面本币毛额，不扣预收**，也就是出货财审原来的口径(账面本币即记账时冻结的汇率，与 SAP 做法一致)。

- 销售订单财务确认的「超信用」由原来的「全部 AR 行净额 > 信用额度」改为「正式应收毛额 > 信用额度」。理由：预收是绑定在具体订单上的，用净额会让一张单借用别的单的预收来「降低风险」。告警会比以前多，这是有意的。
- 额度为空 = 未设置，不判超额。销售订单沿用 V300 口径：迁入客户的旧额度、不大于 0 的额度都按未设置；出货财审沿用原口径：铺底额未填按 0，`overLimitLocal`(超出铺底额)可为负。

### 6. 接口字段(不保留旧字段)

| 接口 | 删除 | 新增 |
|---|---|---|
| 销售订单财务确认列表 `SalesOrderFinancePendingDto` | `clientOutstanding` | `clientBalance`(视图，额度 = 信用额度)；`totalOriginal` 改为十进制原文 |
| 销售订单财务审核详情 `SalesOrderFinanceReviewDto` | `clientOutstanding`、`clientOverCredit`、`clientCredit` | `clientBalance`(视图，`creditLimitLocal` 即参与比较的信用额度，`overCredit` 即超信用)；保留 `clientCreditFloor` |
| 出货财审 `finance-audit-info` | `outstanding*`、`creditFloor*`、`overFloor*`、`availablePrepayment*` | `clientBalance`(视图，额度 = 铺底额：`openBookLocal` = 正式应收未收，`creditLimitLocal` = 铺底额，`overLimitLocal` = 超出铺底额，`creditOriginal` / `creditBookLocal` = 本单币种可用预收) |

出货放行事件 `sales_shipment_finance_release_events` 仍只冻结本币与本单币种可用预收，数值直接取页面看到的同一份视图(不再另查一遍)；不新增原币应收列，因此本 ADR 零迁移。

### 7. 财务收款时填的当天汇率怎么进账(已按代码核对)

用户转述财务的做法：收到钱时开「销售收款」，填当时的汇率。按 ADR-053 §二.4 与 `FinanceReceiptService.settleAppliedLines` 的实际写法：

- 收款行引用一笔应收，行的币种**必须等于应收的币种**(不一致直接拒绝：「核销原币必须与应收币种一致」)；本次到账金额按应收币种填原币。当天汇率只决定这笔钱折多少本币进账户(`amount_local` = 到账原币 × 当天汇率)。
- 应收的原币余额 `amount_balance_original` 按原币扣减(到账 + 冲销)。所以「按订单币种还差多少」就是原币余额精确相加，和哪天、按什么汇率收的钱无关。
- 应收的账面本币余额按**这笔应收立账时冻结的汇率**(出货放行时财务确认的记账汇率，ADR-097)按原币比例冲减，原币收完时本币同时归零；当天汇率与立账汇率的差额记在收款行的汇兑差额 `exchange_diff`，不回写应收。因此 `openBookLocal` = 未收原币 × 立账汇率，和 SAP 信用占用「按记账时汇率、之后不重估」一致。设计稿里「账面本币已含每笔收款当天汇率」的说法不准确，以代码为准：当天汇率体现在账户进账和汇兑差额里，不在应收余额里。
- 没有引用应收的直接预收立一行客户预收：原币 = 收到的原币，本币 = 按当天汇率折算；以后转销到应收时按原币冲减。收款红冲时这行预收同步作废(`status=-1`、`is_deleted`)，共用查询自然不再计入。
- 旧系统迁入的余额、缺币种或缺原币的行，系统不猜汇率，一律单列「原币未核实」(决定 4)。

算例(`FullChainEndToEndTest.salesCashCycle_foreignAdvanceThenReceiptAndReversalKeepSeparateBookAndBankAmounts` 真库验证)：美金预收 400(当天汇率 6.8，本币 2720)；发货立应收 1000(放行汇率 7，本币 7000)；预收转销 300；再按当天汇率 7.2 收款 200(账户进账本币 1440，冲应收本币 1400，汇兑差额 40)。此时客户在美金下：应收未收 500、可用预收 100、还差 400；信用口径 `openBookLocal` = 3500(500 × 7)，可用预收本币 680(100 × 6.8)。信用额度 3000 时按毛额 3500 告警；旧的净额口径 3500 − 680 = 2820 不会告警。


### 8. 前端：一个模型、一组显示函数、一张共用卡

服务端只算一次，前端只显示，三张审核页不再各写一份：

- **金额显示函数** `lib/shared/formatters/money_display.dart`：`financeMoneyText`(十进制原文，至少 2 位小数、不四舍五入，ADR-112 口径)、`financeCurrencyText`(主档名称优先，不显示 `001` 这类旧编号)、`financeMoneyWithCurrency`(「美金 12000.00」，没有金额只显示「—」)。凡是金额旁边要写币种的地方都用它，不再手拼。
- **共用模型** `lib/shared/models/party_open_balance.dart`：`PartyOpenBalance.fromJson` 镜像服务端视图(缺失时为 null，不猜 0)；`headline` 写「美金 400.00」或「预收有余 美金 200.00」(供应商写「可抵有余」，因为里面可能是预付，也可能是退货或索赔贷项)，`footnote` 写「另有 人民币 30000.00；另有历史应收 人民币 1200.00 原币未核实」，`baseMoneyText` 按本位币名写本币金额。
- **共用卡片** `lib/features/finance/widgets/finance_party_snapshot_card.dart`(`FinancePartySnapshotCard`，见[组件文档](../02-组件库/FinancePartySnapshotCard.md))：余额三格(应收未收 / 可用预收 / 还差多少，供应商为应付未付 / 可抵预付/贷项 / 还差多少)都写成「币种 金额」；页面给了额度名时再列「全部币种应收(折本币)」、额度、超出额度，超额标红，销售订单审核另出横幅；页面自己的格子(本单金额、结账方式、参考汇率等)与专属区块(出货记账汇率区)经参数插入。
- **页面**：
  - 销售订单财务确认列表：订单金额写「美金 144000.00」；「客户应收」写本单币种的还差多少，格子保持单行，其它币种、原币未核实和超信用说明放进格内提示(格尾 ⓘ)，超信用时该格标红；紧凑端卡片把补充说明另起一行。
  - 销售订单财务审核详情：客户快照卡 = 本单金额 + 余额三格 + 全部币种应收(折本币) / 信用额度(未设置写「未设置」) / 超出信用额度 + 铺底额。「还差多少」是客户层；这张单还要收多少看订单资金汇总卡的「预计还需新收」(订单层，服务端 `plannedRemainingOriginal`)。
  - 出货财审详情：快照卡 = 本次发货 / 发货用途 / 结账方式 / 参考汇率 + 余额三格 + 全部币种应收(折本币) / 铺底额 / 超出铺底额，记账汇率区在卡片底部。
  - 订货审批详情：供应商快照卡 = 本单金额 + 余额三格 + 折合本币(带本位币名) + 税率，不比额度。
  - 订单资金汇总卡(4 处使用)各格写「币种 金额」，取代原「资金汇总格只显示数值」的页面规则。
  - 列表金额：出货审核列表「出货金额」、订货审批列表新增「订货金额」(原「本币金额」改名「折合本币」)都带币种；委外损耗索赔抵销弹窗的「未付」和供应商贷项应用面板的「可用余额」改用共用函数。
  - IQC 不合格退回/贷项(业务审核中心「IQC 退回贷项」分段)：原来列表「不合格金额(本币)」把单据币种代码(如 `002`、`USD`)挂在本币金额前，外币单据会把人民币金额写成外币。现在原币金额写「币种 金额」(服务端 `CaseItem` 增 `currencyName`)，本币金额只写金额、由列名或「本币」前缀说明，旧的 `amountLabel` 拆成 `originalAmountLabel` / `localAmountLabel`。
- **删掉的重复代码**：三张页面各自的私有快照卡与其 `_metric`；两张审核页的私有 `_money` / `_currencyLabel`(币种名改由模型的 `currencyLabel` 给出)；确认页过渡期的 `_clientOutstanding`、`_baseCurrencyLabel` 与为它加的名称字典加载，以及 `FinanceNameService.baseCurrencyName`(再无使用方)；出货财审模型的 `outstanding / creditFloor / overFloor / availablePrepayment*` 五个字段；订单确认模型的 `clientOutstanding / clientCredit / clientOverCredit`(额度改读视图里的 `creditLimitLocal`，即实际参与比较的那个数)。
- **显示约定**：金额不加千分位，与全平台财务金额显示(ADR-112 `financeExactMoneyDisplay`)一致；以后要加千分位只改 `financeMoneyText` 一处。

## 备选方案

- **按主档参考汇率折成订单币种**：否。参考汇率没维护(0)，今天的汇率也不是账面事实，会得出假数。
- **只在旧的本币数字前加「人民币」**：否。口径没变，本币和原币放在一起仍然没法比，净额也仍会借用别的订单的预收。
- **列表逐行精确算「本单还要收多少」**：否。需要整套订单资金持仓查询，一页开销太大；订单层数字在审核详情的订单资金汇总卡里(`plannedRemainingOriginal`)，列表只显示客户层。
- **信用继续用净额**：否，理由见决定 5。

## 代价与边界

- 公司级合计(应收应付总览、应收款汇总、应付工作台 KPI)跨往来单位、跨币种，只有本币能加总，保持本币，不在本 ADR 范围。
- 信用口径不含旧系统迁入的历史应收(沿用出货财审原口径)；历史应收转成正式行之前，额度检查看不到它，页面靠 `unverifiedLocal` 提示。
- 出货财审原来的可用预收额外要求对应收款单仍有效；收款红冲时预收立账行已同步作废，改由立账行本身判定，结果相同。
- 信用额度只下发一次：`SalesOrderFinanceReviewDto` 不再单独带 `clientCredit`，前端读视图的 `creditLimitLocal`(迁入客户的旧额度、为空或不大于 0 都按未设置 = null，也就是实际参与比较的那个数)。
- 验证：服务端 `PartyOpenBalanceQueryPostgresTest`、`PartyOpenBalancesTest`、`FullChainEndToEndTest` 外币收款算例、`ProcurementApprovalDisplaySnapshotPostgresTest`(含待审列表的订货金额与币种名)；前端 `party_open_balance_test.dart`、`finance_party_snapshot_card_test.dart` 与六个页面测试(见组件文档 §六)。多币种真实数据的岗位 UAT 仍待做：需要在克隆库造一个同时有美金、人民币、历史导入余额的客户，切财务账号走一遍确认、出货财审、订货审批。
