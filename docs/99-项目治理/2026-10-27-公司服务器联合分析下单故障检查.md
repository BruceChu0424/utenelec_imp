# 公司服务器联合分析下单故障检查

检查日期：2026-10-27。范围：公司现役服务器、截图中的汇总下单、同类库存查询/行锁和已提交结果核对。生产只读取证；修复保存在本地隔离工作区，尚未发布。

## 结论

已实证根因为：两处业务 SQL 把只读库存视图 `v_stock_operable_balances` 当作 `FOR UPDATE` 的行锁目标。生产运行角色 `uten` 有该视图的 SELECT，没有 UPDATE；普通读取正常，但行锁触发 UPDATE 权限检查，报 `42501: permission denied for view v_stock_operable_balances`，后续同事务查询继发 `25P02`。

这不是员工权限配置错误，也不是服务器内存或磁盘不足。不能给只读视图开放 UPDATE 作为修复。应锁已有写权限的底层 `stock_balances`，并通过原视图筛选可操作余额，继续阻止计量单位未明确、原账待核的库存被使用。

- 服务器现役 `/opt/uten-imp/releases/v2.5.32`，Web 版本提交 `3227315ce8bdca85767f90593ef50cac7b7bd3cc`；已应用迁移最高 V947。
- 检查时业务服务、Nginx、PostgreSQL active，readiness 返回 `{"status":"UP"}`；主服务 `NRestarts=0`。根卷使用 31%，媒体卷使用 1%，可用内存约 23 GiB。健康状态不代表下单业务通过。
- 已保留应用日志内有 21 次相同库存视图权限异常；Nginx 对应 18 次 `POST .../issue-plans` 的 500，以及 3 次 `POST .../aggregate-orders/submit` 的 500，涉及三份分析单。
- 首次/末次业务错误发生于用户时区 America/Denver 的 2026-10-27 00:29 至 02:27。原始服务器日志为同日 14:29 至 16:27（Asia/Shanghai）。截至取证，末次错误后未再见 WARN/ERROR，不能据此宣称故障已恢复。
- V928 已明确 `GRANT SELECT ON v_stock_operable_balances TO uten`，现场 ACL 也正确。`SET LOCAL ROLE uten` 的只读事务中，普通 `SELECT ... LIMIT 0` 成功；`EXPLAIN SELECT ... WHERE false FOR UPDATE` 原地复现 42501；同条件改为锁底表后执行计划生成成功。此验证没有创建单据或修改库存。
