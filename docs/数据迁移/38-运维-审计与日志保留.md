## 一、保留策略（对标大厂）

| 数据 | 热保留 | 冷处理 | 理由 |
|---|---|---|---|
| `audit_log`(请求/安全/业务事件与脱敏前后镜像) | 默认 **6 个月**，系统设置可调 1–120 月 | 冷归档默认再保留 **30 个月**，可调 0–240 月；总期限到达后永久删除 | 默认 6 个月在线 + 30 个月冷归档，共 36 个月；高风险/失败记录也遵守同一合同，调查冻结须先做受控独立备份 |
| 本机操作回执（客户端本地） | 与服务器“在线期 + 追加归档期”的总月数一致，同时最多 300 条 | 无冷归档；在下一次本地读取/写入时自动删除过期或超量记录 | 只用于原设备交叉佐证，不能代替服务器审计 |
| 应用日志（server_run.log 等） | 目标为按大小滚动 | 生产部署目标建议 logback RollingFileAppender（如 100MB×30 天）；仓库当前没有对应 logback 文件，须由部署配置并验证 | 防磁盘打满，当前仍是发布门禁 |
| 业务历史数据 | 不删 | 按年分区（已在 V50-V69 落实）+ 后续冷数据归档机制（预留） | 业务数据是资产，只归档不删除 |
| 迁移 staging CSV | 随正式重迁覆盖 | 正式切换后清理 data/*.csv（含 PII） | 最小留存 |

V169 起，在审计存储正常时，进入应用的 GET/POST/PUT/PATCH/DELETE/HEAD `/api/**` 原则上均有请求级记录
（包括匿名认证、CORS 非法来源 403、安全链拒绝、404/405 和 MVC 前异常）；有效 JWT 的 request 级
actor 快照保证安全上下文清理后仍能归属账号，无效令牌不绑定身份。所有公开业务表的变更另有脱敏
before/after，因此审计量会明显高于旧版。
V424 后的应用层降噪只对服务端逐项登记的成功自动端点生效：通知到达/未读数、各模块待办数量、
公共运行设置、员工/访客成功会话续期、任务认领 heartbeat 等不再写通用请求行；任何 4xx/5xx、
失败/重用/会话泄露证据和普通业务写请求仍记录。人工显式业务事件与同请求的泛化 HTTP 行去重，
成功会话轮换不再单独写业务事件，登出仍是人工事件。不能使用任意请求头跳过审计。
`audit_log` 已增加风险、分类、request ID 索引；上线后应按周
观察每日新增量、表与索引大小、归档耗时，再决定保留期，
不能通过停记操作降低容量。

V169 的动态 sweep 只覆盖其应用时已经存在的表。2026-08-01 静态审查曾在 V183 的并行早期草稿中发现
新表尚未带触发器，证明“业务迁移作者记得补审计”不是可靠门禁；最终 V183 已为 9 张资产/待摊新表显式
挂接 `trg_audit_*`，并在迁移尾部自带一次只补缺 sweep。V184 不改 V169，而是在 V183 之后独立复核：
每张业务表必须恰有一个 `trg_audit%`，且已启用、为 AFTER ROW、覆盖 INSERT/UPDATE/DELETE，并调用 public 下的
`fn_audit`/`fn_audit_redacted`；错误配置直接 fail closed，完全无前缀触发器时才补挂 `fn_audit()`。V184 将
`master_code_sequences` 与凭证、令牌、序号、迁移控制等技术表显式排除，避免高频计数器复制行镜像；
系统记录仍可通过请求/显式事件留痕。

V185 让之后发生的 `is_deleted`/`deleted_at` 软删除直接写作 `delete`，扩充凭证、PII、迁移列明的原因备注类
敏感文本及大型嵌套 JSON 快照最小化，同时完整保留 V172 设备关联证据；业务名称、编号等调查必需字段仍保留。V185 不重写历史；读模型将旧的
软删除 update 解释为删除/高风险，旧行若存在后来新增的敏感字段仍按受限访问、留存和批准后的分批治理处理。

V188/V189 随后新增销售仓库事件、退货质量冻结投影和处置事件。仓库事件与质量事件另有业务级 append-only 守卫；V190 在这些表出现后再次执行完整 fail-closed sweep，要求每张非白名单公开业务表恰有一个启用的 AFTER ROW I/U/D 审计触发器并调用批准函数。

V184/V185/V190 只能约束各自生效后的新变化，不能补造 V169 之前或任何触发器生效前的操作历史。当前迁移链为：V183 新表显式挂审计 → V184 全表强校验 → V185 软删除/脱敏加固 → V188/V189 新业务表及追加式事件 → V190 再次全表强校验；最终仍须以公司目标库 `pg_trigger` 为准。对历史缺口只能保留
“无可信事件明细”的事实，结合业务单据、备份、部署日志等独立证据调查，不能从当前行猜测操作人、时间和原值。
仓库内静态测试会扫描 Flyway `CREATE TABLE`，最新 sweep 之后新增的表若不在有理由的技术白名单中即失败；
但它不能执行 PostgreSQL DDL，生产发布仍须查询 `pg_trigger` 做运行态复核。
V252 将 V251 的两张导入来源表明确归入业务审计集合，并把静态契约的最新可信 sweep 同步提升到 V252；后续任何新公开业务表仍必须位于新的后置 sweep 之前。
V169 会原位补齐已经存在的 `audit_log_archive` 新列，并把旧归档的风险与分类回填为快照，兼容原脚本的
`INSERT ... SELECT *`；升级仍应安排低峰窗口，因为热表生成列回填和批量创建触发器需要短时 DDL 锁。

## 二、系统设置语义

系统设置 → 审计与留存提供两个互不依赖的整数：

- `audit_hot_retention_months`：在线可查、可导出的月数，默认 6；
- `audit_archive_retention_months`：相对原始记录时间，在在线期之后追加的归档月数，默认 30。

总保留期为两者之和，两个截止点都按原始 `created_at` 计算，不从实际归档时间重新计时。默认行为是
0–6 个月在审计中心查询；第 6–36 个月仅存在冷归档；超过 36 个月后，在下一次每日任务永久删除。
服务长时间停机时，特别旧的记录可能在同次任务先安全归档、随后立即命中总期限删除。审计中心
list/detail/export 只查询在线 `audit_log`；冷归档不能在页面直接查询或导出，调查时必须走受控恢复/隔离查询
流程。“总保留 36 个月”不等于页面可查 36 个月。归档阶段不代表销毁，永久删除不可恢复。设置更新需要超级管理员、二次密码确认并产生
`update_system_setting` 审计记录。缩短任一期限前必须确认法规、合同、调查冻结和备份要求。

当前没有按单条记录实施“调查冻结/法律保留”的功能。存在调查、诉讼或监管保留要求时，应先走审批并制作
受控独立备份，或先建设专门冻结能力；不能只依赖设置页提示后缩短期限。

本机回执从公开运行时设置同步上述总月数；离线时沿用最近一次成功同步值，首次离线回退 36 个月。
本机还受最近 300 条上限约束，因此不能保证保留到月数上限。产品不提供手动删除/清空本机回执的按钮、
路由或业务 API，只能由超期/超量规则自动清理。卸载应用、清除浏览器站点数据、操作系统清理应用数据、
设备重置或安全存储损坏仍可能让本机数据消失；这属于本地介质边界，不得据此删除或回写服务器审计。

## 三、访问、导出与不可变边界

- 在线审计列表、统计、详情及本机回执核查只向持 `audit_log:view` 的指定核查人员开放；普通员工、
  访客无入口，直接输入深链也必须被前端路由守卫和后端接口双重拒绝。
- 超级管理员因固有全权限天然具备审计能力；非超管的 `audit_log:view` 与 `audit_log:export` 只能通过个人覆盖点名授予；部门权限服务和 V173 数据库守门
  都拒绝把它们授予部门或部门树，避免调查证据权限随组织关系扩散。
- V171/V173 会删除升级前已有的非超管审计导出/查看 grant；发布后必须依据批准的核查人员名单重新授予，
  不得通过回填部门权限恢复。
- 导出还必须同时持有 `audit_log:export`，继续执行密码加密、限流、并发闸门、行数上限和导出行为再审计；
  `audit_log:view` 单独不能导出。审计中心同步导出即使系统 `export_max_rows` 更大，也固定最多 10,000 条；
  超限必须缩小人员 UUID、北京时间区间或其它筛选。
- 服务器在线表与归档表均为系统只写。产品不提供查库人员可调用的编辑、单条删除或批量删除接口；
  在线记录只能由留存任务先归档后删除，冷归档只能在总期限到达后由同一任务永久删除。
- 本机回执不允许人工修改、删除或列出共享设备的完整历史，只能凭审计详情给出的完整
  `client_event_id` 在原设备精确核查。读取目标回执前必须在线通过服务端授权并产生
  `verify_local_audit_receipt`；授权失败或离线时不读取。它与数据库一致时属于交叉佐证，不构成物理
  设备认证或不可抵赖证明。

审计中心先分页选择人员目录中的 UUID(员工与访客，含停用/阻止的历史人员)，再选择北京时间单日或
闭区间；普通列表、统计和导出必须同时提供 `actorId + dateFrom + dateTo`，单次最多连续 31 天。
人员联想只查姓名、登录账号/访客编号、部门和岗位，不读取访客手机号密文/哈希，也不因敲字写审计。
默认 `activityOnly=true`，主列表排除数据库行镜像，展示可读业务/安全主活动及保留的通用并发协调证据；需要核查同一操作的脱敏
数据库变化时，使用规范 Request ID 精确查询并显式设置 `activityOnly=false`。规范 Request ID 可作为
人员/日期的替代精确条件。匿名登录失败/安全拒绝只能用 `actorScope=anonymous` 加完整日期区间查询；
系统任务不开放为空条件的全量默认入口。对象、来源、关键字和操作类型继续由服务端过滤。

第一次列表请求由服务端返回 `snapshotId=max(audit_log.id)`（空表为 0），同一轮列表、统计和导出都固定
`id <= snapshotId`，按 `created_at DESC, id DESC` 排序。通常后续分配的高 ID 日志（包括审计查询自身）
不会推移当前 offset；用户刷新或改变任何筛选才取得新边界。它不是跨请求 MVCC 快照：旧 ID 晚提交和
留存任务并发删除仍可能移动页集，必须避开 03:17 留存窗口并做并发实库验收。

## 四、自动任务

应用默认每天北京时间 **03:17** 执行，可通过 `UTEN_AUDIT_RETENTION_ENABLED` 总开关和
`UTEN_AUDIT_RETENTION_CRON` 部署变量调整任务开关/时间；月份只能从系统设置读取：

1. PostgreSQL session advisory lock：多实例只允许一个任务运行；
2. 每批最多 5000 行，单次最多 200 批，剩余数据下个周期继续；
3. `FOR UPDATE SKIP LOCKED` 选取最老在线行；
4. 同一事务内显式列归档、确认归档 ID、再删除在线行——未归档行绝不删除；
5. 按“在线期 + 追加归档期”分批永久删除冷归档；
6. 成功任务只写服务端运维日志，不再制造一条用户活动噪声；失败会尽力写
   `audit_retention_failed` 系统事件并写 error 日志，不逐行递归制造日志。审计汇总自身写入失败时只记
   服务端 error，不能承诺数据库内一定存在该失败事件。

通用 `TaskClaimHandle/TaskClaimSession` 会在页面挂载/选项变化时自动 claim，并在销毁时 release；这些并发协调
成功事件当前继续进入审计主活动。重复持有不再冒充首次认领，而记为 `task_renew`，中文显示「续租任务认领
(自动协调)」。HR 任务中心的 claim/release/takeover 是用户点击按钮，仍按人工动作解释。移除通用自动
claim/release 成功主活动尚未获得用户对具体动作的明确授权，是当前剩余缺口。

任务认领客户端虽然每 30 秒 heartbeat，但服务端仅在剩余租期进入半租期阈值后实际更新
`lease_until/last_heartbeat`；阈值前只读返回当前租约，避免 JPA dirty-check 触发 UPDATE 和数据库行镜像。
显式状态事件使用与业务事务相同的提交边界；外层回滚时成功事件一并回滚。成功 heartbeat 请求降噪，
失败/冲突仍记录。`task_claims/hr_task_claims` 底层触发器保留，未作不可逆审计覆盖削弱。

设置被直接篡改为范围外值时任务 fail closed，在进入归档/删除 SQL 前失败并尽力留痕。日常任务不执行
`VACUUM FULL` 或 `REINDEX`，由 autovacuum 处理；首次大批清理后的物理重整仍需 DBA 在低峰评估。
Spring 调度线程池默认 4，避免长归档阻塞 Outbox、报表刷新和业务预警。

审计导出继续要求独立权限和密码保护，并强制取“系统配置上限与 10000 条中的较小值”；超出时必须缩小
人员/日期/风险范围，避免实体列表、工作簿与加密副本同时驻留造成内存峰值。日志正文持久化在 PostgreSQL，
不是常驻 JVM 内存；列表卡顿主要由查询范围、索引和序列化决定。当前 V05 只有 `actor_id` 单列索引，
31 天边界是现阶段的安全折中；目标数据量增长后仍需单独评估
`(actor_id, created_at DESC, id DESC)` 部分复合索引，不能未经容量/锁演练直接加入已冻结迁移链。

## 五、人工应急脚本

`server/ops/audit_retention.sql` 保留为人工应急/历史兼容入口，不是常规调度来源。它只按传入天数把热表
记录复制到归档并删除已确认归档的热行，不读取两个系统设置，也不会永久删除冷归档。执行前必须暂停应用
自动任务或设置 `UTEN_AUDIT_RETENTION_ENABLED=false`，并由 DBA 把按天参数与系统设置换算核对，避免两套
策略并行；完成后应恢复自动任务。冷数据永久删除必须另走审批并由应用任务处理，不能把应急 SQL 当成完整
两阶段留存。常规生产环境只使用应用内任务。

归档必须保留 `request_id`、`risk_level`、`event_category` 与 HTTP 元数据，避免恢复调查时无法串联。

```sql
SELECT c.relname AS table_without_valid_audit_trigger
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname = 'public'
  AND c.relkind IN ('r', 'p')
  AND NOT c.relispartition
  AND c.relname NOT IN (
      'audit_log', 'audit_log_archive', 'flyway_schema_history', 'spatial_ref_sys',
      'authorization_state', 'doc_number_sequences', 'master_code_sequences',
      'report_materialized_view_refresh_state', 'password_history',
      'refresh_tokens', 'visitor_refresh_tokens', 'visitor_sms_codes',
      'notices', 'notice_user_states', 'notice_acknowledgments',
      'notice_blessings', 'business_outbox', 'attachment_object_outbox',
      'account_flow_monthly_summaries',
      'production_daily_report_commands', 'production_fqc_release_commands',
      'warehouse_arrival_registration_commands',
      'production_material_analysis_commands')
  AND c.relname NOT LIKE 'legacy_migration_%'
  AND (
      (SELECT count(*)
       FROM pg_trigger t
       WHERE t.tgrelid = c.oid
         AND NOT t.tgisinternal
         AND t.tgname LIKE 'trg_audit%') <> 1
      OR
      (SELECT count(*)
       FROM pg_trigger t
       JOIN pg_proc p ON p.oid = t.tgfoid
       JOIN pg_namespace fn ON fn.oid = p.pronamespace
       WHERE t.tgrelid = c.oid
         AND NOT t.tgisinternal
         AND t.tgname LIKE 'trg_audit%'
         AND t.tgenabled IN ('O', 'A')
         AND (t.tgtype::integer & 1) = 1
         AND (t.tgtype::integer & 2) = 0
         AND (t.tgtype::integer & 4) = 4
         AND (t.tgtype::integer & 8) = 8
         AND (t.tgtype::integer & 16) = 16
         AND fn.nspname = 'public'
         AND p.proname IN ('fn_audit', 'fn_audit_redacted')) <> 1)
ORDER BY c.relname;
```
