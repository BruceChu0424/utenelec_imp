# 仓库查询资格与整合回归修复

状态：隔离工作树修复及定向回归，不代表公司部署、最终 CI 或正式客户端交付完成。

## 根因与统一入口

- 仓库入库将 `Rights.productionPool()` 改为只检查单据查看权限，用于跨部门读取；办理标记仍复用了该方法，丢失仓库参与资格。现将 SQL 可见范围与办理资格分别表达：原仓库及单据归属边界不变，办理继续要求仓库参与资格和动作权限。
- 出库同样把 `Access.production` 同时用作读取与办理条件。保留读取条件，单独传递 `productionParticipant`，生产领料和补料办理须同时满足原动作权限。没有新增写入口或扩大权限。
- 负责人驳回计数新增独立只读 `/api/documents/manager-rejected/count`，工作台来源复用该控制器及已有权威查询，不再另注入一份来源。独立端点与工作台逐字段对照纳入徽章回归。

## 调用方与保留差异

- Web、现有 Flutter 桌面共用 `WarehouseTaskCenterRecord.canHandle` 及公共仓库记录、实物详情组件；批量选择、办理、反登记继续检查服务端标记。后台读取与办理字段契约未更名，不把有动作权限但不属于仓库办理范围的账号标为可办理。
- Win7 原生完整仓库业务仍未迁移，`W7-FLOW-005` 及相关仓库业务项保持 todo。本次不新开原生写入口、不把后端修复当作 Win7 已验收。
- 档案批次的旧 mock 未返回新增 `requireReader()` 的身份，真实守卫原本会返回身份或拒绝。补齐明确具有 `profile:review` 的夹具，不放宽生产守卫。
- 公司文件、委外领料和 AI 权限名断言对齐已经合入的只读目录与直白文案；旧权限码退役、入口绑定和授权策略断言保留。
- 采购结束普通回执遵循同一业务参与资格。回归同时验证只有超管标记时不自动收到回执、明确业务资格时恰好一份；原财务/仓库消息撤回及 Outbox 无残留断言保留。
- 可达性合同沿用已有“必须显式配置”路径，六个负责人决定权限逐项验证零默认授权、NORMAL 可配置和唯一启用权限面。不为通过测试给部门自动加权。首位负责人授权仍须按原任务通过真实管理员及再次认证的既有流程完成。
