# 2026-08-16 来源单号可读化与订货仓库后移收口报告

> **性质**：业务口径纠错的两项收口——①全系统「来源单据/备注」不得向业务人员展示 UUID；
> ②采购/委外订货单不再携带仓库，入库仓库后移到收货/进仓（到货登记）时填写。
> **基线**：分支 `feat/doc-link-picker-sheet`（含同日全链路审计修复与 NO-GO 收口改动之上）。
> **决策记录**：[ADR-038](../99-决策记录-ADR/ADR-038-来源单号可读化与订货仓库后移.md)；
> ADR-019 §2.3/§2.6 已加部分反转批注。
> **结论**：两项均已代码收口并清洗开发原库（V292）；公司目标库迁移、真实岗位/实物 UAT
> 与发布签字未完成，生产整体仍为 **NO-GO**，本报告不改变该结论。

## 一、来源单号可读化（①）

### 1. 根因

计划前物料分析生成的采购/委外申请把 `物料分析-<36位UUID>` 写进 `source_doc_no`（表头+明细）、
`production_plan_no` 与 `remark`，并沿申请→订货谱系继承（`requestItemLineage`）；
生产计划路径本身传的是 `plan.billNo()`，无此问题。

### 2. 修复面（后端）

| 位置 | 修复 |
|---|---|
| `MaterialAnalysisCommandService` | 来源标签改为 `计划前物料分析 <分析日期>`（实时查 `analyzed_at`，`refreshLocked` 会推进）；备注改为「…备料任务自动生成」 |
| `ProductionPurchaseRequestFacade` / `ProductionSubcontractRequestFacade` | 新增 `materialAnalysisId` 参数：按 id 精确回溯销售谱系（`resolveSalesOrderNos` 拆计划/分析两路），不再字符串匹配 UUID；备注按来源分支 |
| `ProductionExecutionPackageCommandService` | 明细备注「执行分段 <UUID>」「执行分段需求 <UUID>」改用分段编号 ZX…（新增 `segmentCodeById`/`segmentDemandRemark`） |
| `MaterialAnalysisSupplyWakeupService` + `ChainNoticeService` | 「剩余物料已可下达」事件新增 `sourceDocumentNo`（按类型解析 CJ/EJ/CR 单号），通知文案只展示单号 |
| `MaterialAnalysisCommandService`（自制备料） | `MAKE_COMPONENT.source_ref` 改为 `自制备料 <日期> <4位尾码>`；满足 `(source_type, source_ref)` 全局唯一索引，插入前查重、撞码换码；`markCreated` 同口径 |

### 3. 前端

无结构性改动：申请详情「来源单据」、任务中心分解预览、「计划/销售来源」行读同一批字段，
数据清洗后自动可读。

### 4. V292 数据清洗（开发原库已应用）

- `purchase_requests` 8 行 / `purchase_request_items` 8 行 / `subcontract_applications` 1 行 /
  `subcontract_application_items` 1 行：`物料分析-UUID` → `计划前物料分析 <日期>`（含备注、
  `production_plan_no`）；
- 订货/收货明细继承行按同前缀防御性改写（当前 0 行）；
- `MAKE_COMPONENT.source_ref` 3 行 → `自制备料 <创建日> <id前4位>`；
- `preplan_supply_actions.external_document_no` 受 append-only 触发器保护**不可改写**；
  其 MAKE 短码经核实不出现在任何界面（界面只展示采购/委外路线单号），保留原值。

### 5. 全盘核查口径（用户要求「所有地方」）

- 后端 81 处 `setSourceDocNo/setPlanNo/setSalesOrderNo/setProductionPlanNo` 赋值点逐点核对：
  销售出货/退货/报价、ArAp 立账（9 处）、排产转研发、报工快照、MRP/领料、财务资产均为单号或用户手填；
- 前端全部「来源」渲染点核对（对账页=类型文案、审批任务=张数、仪表盘=政策来源名等）；
- **全库文本列完整 UUID 正则扫描**（排除审计/outbox/日志内部表）：唯一命中为
  `production_material_analysis_items.source_ref`（已清洗）；其余命中均为身份/技术键
  （`audit_log.target_id`、BOM `node_key`、并发锁、幂等键），属设计如此。

## 二、订货仓库后移（②）

### 1. 口径

订货只表达「向谁采购/委外、价格、结算」；「入到哪个仓库、多少数量」是到货事实——由仓库在
收货/进仓登记时必填。申请单保留仓库（计划侧库存分配、齐套投影与领料使用）。

### 2. 修复面（前端为主，后端本就允许订货仓库为空）

| 位置 | 修复 |
|---|---|
| `purchase_doc_config` / `subcontract_doc_config` | 新增 `hasWarehouse`（订货 `false`）；委外**进仓单**改 `warehouseRequired: true`（采购收货原本必填） |
| 采购/委外编辑页 | 订货不渲染仓库下拉、不预填（近单预填与申请行仓库预填均跳过）、保存不提交；编辑历史订货会把旧仓库清空（订货语义不再是其事实） |
| 采购/委外列表+详情 | 订货隐藏仓库列/行 |
| 委外订货预填 | 删除「所选申请不属于同一仓库」阻断（订货无仓库，约束失去意义） |
| 到货登记 | 收货/进仓模式下仓库不再锁定（预计到货可能不带仓库）；提示条补「请选择本次入库仓库」 |
| `procurement_inbound.dart` | `canCreateReceipt` 去掉仓库门槛；`ProcurementReceiptPrefill.warehouseId` 可空 |
| 预计到货任务卡 | 仓库行无仓时显示「登记到货时选择」 |
| 后端兜底 | `PurchaseReceiptService`/`SubcontractReceiptService` 既有「需指定仓库」校验；`inbound_expectations.warehouse_id` 可空列无需迁移 |

### 3. 兼容性

- 历史订货单若带仓库：详情不再展示（订货无仓库语义）；再次编辑保存后清空该值；
- 已生成且带仓库的预计到货：照旧展示并可预填仓库，登记时仍可改；
- 发料/材料退/损耗/退货等以仓库为物理事实的委外单据不受影响。
