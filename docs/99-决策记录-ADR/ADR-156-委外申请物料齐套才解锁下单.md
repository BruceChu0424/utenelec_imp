## 一、背景(用户原话，2026-10-05)

> 委外这里还是有点需要改的，就是他物料不齐的时候是不解锁的，因为如果说是要等他生产完，那他委外的价格，因为每天是不一样的，所以说等他可以支持部分委外或者全部委外的时候，他才解锁可以去生成委外，然后去仓库领料啊之类的 就是锁住的状态，不给操作就跟之前一样

拆开来是四条：

1. **为什么锁**：委外加工价每天不一样，财务批准订货单那天价格就定了。物料还没齐就先下单，等物料齐了委外商才能加工，价格已经对不上。所以直属物料不齐时，委外申请锁住，不让生成委外订货单。
2. **什么时候解锁**：现有物料够做一部分就解锁这一部分(「部分委外」)，够做全部就全部解锁(「全部委外」)。只能按现有物料够做的套数下单；没齐的那部分继续锁着，物料再到才再解锁。
3. **锁住是什么样**：「跟之前一样」——锁住的申请照样留在委外任务中心「待处理」、照样计红数，只是行上显示锁住、不能勾选、不能生成订货单(ADR-103 时期的锁也是这样呈现)。
4. **解锁之后**：照 ADR-143 走——生成委外订货单 → 财务批准 → 「领料」提交 → 仓库发料 → 分批回厂 → 来料质检 → 入库。

ADR-143 当时定的是「下单不受物料库存约束，物料够不够只影响之后能领多少」，与这条要求冲突，由本 ADR 修订。

## 二、决策

1. **物料池**：每张委外申请明细能用的直属物料 = 它自己的**专属批次**(物料分析分给这张申请的委外节点的直属子节点的库存权益批次，ADR-113 交接，只算可用仓) + **公共可用库存**(`v_stock_available`，可用仓，已扣他人预留)。逐种物料计算，A 的库存永远不能替 B 放行。
2. **已占用**：所有还在办的委外订货单(草稿、在审、财务退回、已批准未结案)都按每种直属物料「还要领的量」占物料：已批准的按领料计划行，没批准的按 BOM 整单算。订货明细有来源申请的部分，先占那张申请的专属批次，不够的部分和没有来源的部分(手工行、超出申请的部分)占公共库存。占用是**虚拟的**：只参与计算，不在仓库里做预留。
3. **可下单**：申请明细这次能下单的数量 = MIN(剩余未下单数量, 现有物料够做的套数)。为 0 就锁住。
4. **锁的呈现**：委外任务中心「待处理」里，一条都不能下的申请显示「等物料齐套」，不能勾选、不能生成订货单，但照样留在「待处理」、照样计红数；能下一部分的显示「可部分下单·可下单 N」。缺 BOM(ADR-143 §二.3)优先。行上「齐套情况」逐种物料列出差多少。
5. **守卫**：生成委外订货单、保存草稿、提交财务、财务批准(批准即锁价，物料必须仍然齐)、批准后加量，都按同一口径核对，不够就 409 并点名缺哪种物料、要多少、能用多少。减量、删除、红冲、结束领料从不被拦。同时下单的两张单按物料加事务级咨询锁串行判定。
6. **预填**：从任务中心勾选申请生成订货单时，所选申请按需求日期先后共用公共库存，每条预填各自这次能下的数量；按预填数量下单一定通过守卫。超委外(超过申请剩余量)的部分同样要有物料。
7. **通知**：申请可下单量比上次提醒时多，就给采购委外部门能生成订货单的人发「委外可下单」行动卡；变少只悄悄降水位，降到 0 撤卡。和 ADR-143 的「领料重算」在同一次 outbox 投递里重算。
8. **只在服务端算一次**：所有数量只在 V809 的 SQL 函数里算，任务中心、齐套情况、预填、守卫、通知都读它；Java 只读不复算，Flutter 不算。
9. **下单之后不变**：领料、发料、分批回厂、回厂核销仍按 ADR-143；同一张订货单内仍按批领料，先提交先得(ADR-143 §二.16)。

## 三、计算口径(只在服务端算一次)

记号：申请明细 a，委外件 P，申请单位换算率 r_a；第 i 种可发外直属物料 = `fn_subcontract_draw_edges(P)` 的一条边。套数正反函数沿用 ADR-143 §三.2：`f(S, b) = CEIL(S × b, 4)`(套数 → 物料量)，`sets(x, b) = TRUNC(x / b, 4)`(物料量 → 套数)。

### 3.1 物料池

```text
每套用量     b_{a,i} = ROUND(r_a × BOM 边用量_i, 6)                       与财务批准时冻结单耗同一口径
专属批次     X_{a,i} = fn_subcontract_application_exact_qty(a, i)
                     = 物料分析分给 a 的委外节点的直属子节点(同货品同颜色)的库存权益批次余量,
                       只算可用仓(未删、非不良品仓、非线边/内料仓、fn_warehouse_counts_as_usable)
公共库存     G_i     = fn_subcontract_component_public_qty(i)
                     = Σ 可用仓 MAX(v_stock_available.available_qty, 0)
```

顶层委外件(分析根节点 ROOT_SUPPLY)的直属物料取分析第 1 层节点，其余取 `parent_node_key` = 委外节点的子节点。

### 3.2 在办订货单的占用

一条在办订货明细 o(订货量 q_o)对物料 i「还要领的量」`n_{o,i}` = `fn_subcontract_order_item_component_need(o, i)`：

| 订货单状态 | n_{o,i} |
|---|---|
| 已批准、未结案(status 1) | Σ 开着的领料计划行 `MAX(needed_i − 已发净量 − 已提交未发, 0)`；needed_i 即 ADR-143 §三.4a 的我方需发量。已提交未发的领料草稿已在仓库占住库存，所以这里扣掉，不重复算 |
| 草稿、在审、财务退回(status 0) | `f(q_o, ROUND(订货换算率 × BOM 边用量_i, 6))` |
| 红冲、删除、已结案 | 0 |

按订货明细的来源份额拆进物料池(`fn_subcontract_component_pool_demands`)，来源按(行号, id)排序累计 c_k，逐份按 4 位小数累计取整求差，合计恰好等于 n：

```text
来源 k(申请明细 a_k)的份额 = ROUND(n × MIN(c_k, q)/q, 4) − ROUND(n × MIN(c_k − alloc_k, q)/q, 4)   → 记入池 a_k
没有来源的部分         = n − ROUND(n × MIN(Σ alloc, q)/q, 4)                                     → 记入公共池 ∅
```

记 `D_{a,i}` = 所有在办订货明细记入池 a 的份额之和，`D_{∅,i}` = 记入公共池的之和。

### 3.3 申请能下多少

```text
专属剩余   E_{a,i} = MAX(X_{a,i} − D_{a,i}, 0)
公共被占   C_i     = D_{∅,i} + Σ_a MAX(D_{a,i} − X_{a,i}, 0)          各申请专属批次不够的部分 + 手工行
公共剩余   F_i     = MAX(G_i − C_i, 0)
现在能用   U_{a,i} = E_{a,i} + F_i
够做套数   K_a     = MIN_i sets(U_{a,i}, b_{a,i})                      没有可发外直属边(缺 BOM)时 K_a = 0
剩余未下单 R_a     = MAX(申请量 − 已下单 − 在审订货单的来源份额, 0)       申请不是「已审核、未结案、未删除」时 R_a = 0
可下单     N_a     = MIN(R_a, K_a)，R_a = 0 时 N_a = 0                  N_a = 0 即锁住
```

- 函数：`fn_subcontract_application_kit_facts(a, 排除订货单)`(逐种物料的事实)、`fn_subcontract_application_kit_qty`(K_a)、`fn_subcontract_application_open_qty`(R_a，与任务中心 `v_procurement_decomposition_tasks` 的 open_qty 同口径：「已下单」是财务批准回写的 `ordered_qty`，「在审」是带待处理财务审批的草稿)、`fn_subcontract_application_orderable_qty`(N_a)。
- K_a 不封顶申请剩余量：超委外的部分同样要物料。
- 还没送审的草稿不减 R_a(与任务中心剩余量同口径)，但它的物料已经算在占用里，所以草稿下了多少，别的申请和它自己的剩余部分就少多少套。

### 3.4 订货单齐套检查(守卫)

`fn_subcontract_order_kit_shortages(O)` 返回本单不够的直属物料，空 = 齐套：

```text
把本单 O 每种物料的还要领量按 3.2 拆成 d_{O,a,i}(各来源申请) 与 d_{O,∅,i}(没有来源)
池 a 还能给本单   = MAX(X_{a,i} − D^{−O}_{a,i}, 0)                     D^{−O} = 不含本单的占用
本单要用公共      = d_{O,∅,i} + Σ_a MAX(d_{O,a,i} − 池 a 还能给本单, 0)
齐套 ⟺ 每种 i：本单要用公共 ≤ F^{−O}_i                                  F^{−O} = 不含本单的公共剩余
```

拒绝文案里的「本单需要」= Σ d_{O,·,i}，「现在能用」= Σ MIN(d_{O,a,i}, 池 a 还能给本单) + F^{−O}_i。

### 3.5 带单下单的联合预填

`SubcontractKitService.orderableForSelection`：所选申请明细按(需求日期, id)排序，公共剩余 L_i 初值 = F_i：

```text
对每条 a：K'_a = MIN_i sets(E_{a,i} + L_i, b_{a,i})
         预填 N'_a = TRUNC(MIN(R_a, K'_a), 4)
         L_i ← MAX(L_i − MAX(f(N'_a, b_{a,i}) − E_{a,i}, 0), 0)          先用自己的专属批次，不够的部分扣公共
```

所有份额都按 4 位小数分摊，与 3.4 同一口径，所以按「可下单 N」或联合预填值下单一定通过守卫(期间库存没被别处用掉的前提下)。

## 四、页面、接口与通知

### 4.1 委外任务中心「待处理」

一行 = 一张仍有未下单量的委外申请(多明细申请聚合成一行)。状态列 `displayStage` 按以下顺序取第一个命中：

| 状态 | 判定 | 行为 |
|---|---|---|
| 缺 BOM·已通知研发 `BOM_MISSING` | 任一明细的委外件没有可发外直属物料(ADR-143 §二.3) | 不可勾选；不计红数(球在研发) |
| 等物料齐套 `WAITING_KIT` | 还有未下单量，但每条明细可下单都是 0 | 不可勾选、不能生成订货单；**照样留在「待处理」并计红数**(`taskStatus` 仍是 `WAITING_ORDER`) |
| 可部分下单 `KIT_PARTIAL` | 至少一条明细可下单 > 0，但可下单合计 < 未下单合计 | 可勾选；显示「可下单 N {单位}」，N = 各明细可下单之和 |
| 原状态(待下单 `WAITING_ORDER`) | 可下单 = 未下单 | 照旧 |

- 行字段增加 `orderableQty`(可下单合计；看不到这张申请的人为空)；`canCreateOrder` 在缺 BOM 或一条都不能下时为假。
- 计数：`statusCounts.WAITING_ORDER` 与 `countPending` 都照算锁住的行，只有缺 BOM 的另计 `BOM_MISSING`、不计红(见[徽章与计数口径](../00-项目准则/14-徽章与计数口径.md))。
- 锁住只显示在行上，不新增分段、不新增黄数。

### 4.2 「齐套情况」弹窗

行上「齐套情况」按申请明细打开，接口 `GET /api/subcontract/applications/items/{applicationItemId}/kit`(权限 `subcontract_application:view`，只读)，返回剩余未下单 `openQty`、够做套数 `kitQty`、可下单 `orderableQty`、`bomMissing`，以及逐种直属物料：

| 列 | 含义 | 接口字段 |
|---|---|---|
| 每套用量 | b_{a,i} | `bomUnitQty` |
| 需要 | 剩余未下单数量要用的量 `f(R_a, b)` | `neededQty` |
| 专属库存 | 物料分析分给这张申请的批次余量 X | `exactQty`(公共库存 G 为 `publicQty`) |
| 已被占用 | 别的还在办委外单要领走的量 | 专属侧 `exactClaimedQty`、公共侧 `publicClaimedQty` |
| 现在能用 | U = 专属剩余 + 公共剩余 | `freeQty`(两部分为 `exactFreeQty`、`publicFreeQty`) |
| 还缺 | `MAX(需要 − 现在能用, 0)` | `shortQty` |
| 够做套数 | `sets(U, b)` | `kitQty` |

够做套数最小的那种物料就是短板。缺 BOM 时没有物料行，可下单为 0。

### 4.3 生成委外订货单(预填)

- 从任务中心勾选申请生成订货单：`POST /api/subcontract/applications/decomposition-preview` 每条明细增加 `kitQty`(联合分配后够做的套数)与 `orderableQty`(= MIN(剩余, kitQty))；订货编辑页按 `orderableQty` 预填数量，为 0 的明细不预填。
- 联合分配按 3.5：需求日期早的申请先分，后面的只能用前面分剩的公共库存；各自的专属批次只给自己。
- 预填值可以改。改大(包括超过申请剩余量的超委外)要物料够，保存时由守卫核对。

### 4.4 委外订货单编辑与财务审批

- 手工直接新建的委外订货单(没有来源申请)只能用公共库存，建单、保存草稿就按守卫核对。
- 已建好的草稿如果物料后来被别的单或车间生产用掉，再保存、提交财务都会 409；把数量改到「可下单」以内即可保存、提交。
- 财务批准时再核一次：批准即锁定当天委外价，物料必须仍然齐套。批准被拒时财务可以驳回，由委外人员改数量后重新提交。
- 批准后改量：任一明细加量时核对齐套；只减量不核对(ADR-143 的缩量下限照旧)。

### 4.5 通知

| 事件 | 收件人 | 内容与生命周期 |
|---|---|---|
| `SUBCONTRACT_ORDER_KIT_READY` 委外申请可下单量增加 | 采购委外部门(`SUB_PURCHASE` 及下级)里同时持有 `notice:read`、`subcontract_application:view`、`subcontract_order:decompose` 的在职账号；显示时复核后两个权限 | 重要级行动卡「委外可下单：{申请单号} {委外件} 可下单 N {单位}」。正文写「直属物料已全部齐套」或「已够做 N(还差 M 等物料)」，请到委外任务中心「待处理」生成委外订货单，可下单数量以任务中心实时计算为准、被别的委外单先占走时会变少。链接 `/operations/workbench/subcontract?segment=pending&keyword={申请单号}`。每个申请明细一张卡(聚合 `SUBCONTRACT_APPLICATION_ITEM`，登记在待办通知目录)，可下单比上次提醒时多才撤旧卡发新卡；变少只降水位、不打扰；降到 0(被别的单占走、已全部下单、申请关闭)撤卡 |

- **高水位**：表 `subcontract_application_kit_notice_marks`(每个申请明细一行，`notified_orderable` + `epoch`)。现在可下单 > 水位：发卡并把水位抬到现值；< 水位：水位降到现值、`epoch + 1`，降到 0 时撤卡；相等不动。与 ADR-143 的 `subcontract_draw_notice_marks` 同一做法。
- **何时重算**：沿用 ADR-143 的「领料重算」outbox 事件 `SUBCONTRACT_DRAW_RECHECK`(按物料)。投递时先重算用到这种物料的委外订货明细可领量(ADR-143)，再重算用到它的委外申请可下单量(`SubcontractApplicationKitRecheckService`：还有未下单量且 BOM 用到这种物料的申请明细，加上水位 > 0 的)。事件来源：ADR-143 原有的(物料入库、预留释放、财务批准、改量)，加上本 ADR 的委外订货单建单、保存、删除、红冲、批准后改量——按本单委外件的直属物料各排一条(`SubcontractKitService.enqueueRecheckForOrder`)。
- **锁**：重算只锁水位行，不锁业务单据；缺的水位行按申请明细 id 一条语句插齐，与下单命令锁申请明细的顺序一致。
- **新委外需求提醒**：计划下达委外申请时原有的「新委外需求」提醒(`PREPLAN_SUPPLY_DOCUMENT_CREATED`)末尾按 `fn_subcontract_application_orderable_qty` 加一句：一条明细都不能下 → 「直属物料还没齐套，委外任务中心先锁住这张申请(委外价格每天不一样，物料齐了才解锁下单)，物料到了系统会再提醒可下单」；部分明细能下 → 「其中 N 条明细的直属物料已够下单，可先按「可下单」数量下单」；全部能下 → 「直属物料已够下单，请按「可下单」数量下单」。

## 五、守卫

全部在调用方事务内、明细落库之后执行(`SubcontractKitService.requireOrderKit`)。先按物料与颜色排序，逐种加事务级咨询锁 `pg_advisory_xact_lock(hashtextextended('subcontract-kit:{物料}:{颜色}', 0))`，让同时下单的两张单串行判定，不会都按同一批公共库存放行；同一事务里按委外商拆出的几张单彼此可见，不会重复占同一批库存。委外件没有可发外直属物料时不在这里拦(缺 BOM 由 ADR-143 §二.3 的守卫转研发并拒绝)。

| 动作 | 时机 | 文案里的动作 | 文案末尾的下一步 |
|---|---|---|---|
| 生成委外订货单(任务中心带单，或手工新建) | 建单 | 生成委外订货单 | 请按委外任务中心显示的「可下单」数量下单，其余等物料到了再下 |
| 保存委外订货单 | 草稿编辑保存 | 保存委外订货单 | 同上 |
| 提交财务 | 送审(在 ADR-143 缺 BOM 检查之后) | 提交财务 | 物料可能已被别的委外单或生产先用掉；请委外人员把数量改成委外任务中心显示的「可下单」数量，或等物料到了再提交 |
| 财务批准 | 批准(在缺 BOM 兜底检查之后) | 批准 | 同上 |
| 批准后改量 | 任一明细加量时 | 加量 | 同生成 |
| 删除草稿、批准后减量、红冲、结束领料 | 不检查 | — | 只排「领料重算」事件，释放出来的物料让别的申请解锁 |

拒绝是 409，文案结构：「直属物料还没齐套，不能{动作}：「{物料编号 名称(颜色)}」本单需要 {x}{单位}，现在能用的只有 {y}{单位}；……」，接着说明已经扣掉其它还在办的委外单要领的量，然后「委外价格每天不一样，物料齐了才解锁下单；{下一步}。」。多种物料不够时逐种列出(按物料编号排序)。被拒的命令整笔回滚，不留下半张单或来源份额。

## 六、用例清单

下面的例子用同一组数据：委外件 P 的直属物料 A(每套 1)、B(每套 2)，委外申请 SA-1 要 P 100；没有专属批次时只看公共库存。

1. **一点物料都没有**：A、B 都是 0 → 够做 0 套 → SA-1「等物料齐套」，留在「待处理」计红数，不能勾选。「齐套情况」：A 需要 100、还缺 100；B 需要 200、还缺 200，两种都够做 0 套。手工建一张 P 1 的单也 409「不能生成委外订货单」。
2. **两种物料只有一种够**：A 到 150、B 0 → A 够做 150 套、B 够做 0 套 → 短板 B，仍锁住。
3. **部分齐套(N < 剩余)**：A 到 100、B 到 80 → A 够做 100、B 够做 40 → 可下单 MIN(100, 40) = 40，状态「可部分下单·可下单 40」，采购委外部门收到「委外可下单：SA-1 P 可下单 40」。下 41 被拒：「B 本单需要 82，现在能用的只有 80」；下 40 放行。草稿占住 A 40、B 80 后，SA-1 剩下的 60 又变成「等物料齐套」。
4. **全部齐套**：A 150、B 220 → 够做 110 套 → 可下单 MIN(100, 110) = 100，状态为普通「待下单」，预填 100。
5. **两张申请抢同一批公共库存**：例 3 的单已批准(SA-1 剩 60)，再来 SA-2 要 P 10、需求日期比 SA-1 晚；B 再到 20 → 两张各自看都是「可下单 10」(各行各算，不互相扣)。一起勾选生成时按需求日期联合分配：SA-1 预填 10，SA-2 预填 0。如果 SA-2 先单独下了 10 的草稿，SA-1 的可下单变 0，它的「可下单」卡被撤回。两人同时下单时按物料咨询锁串行，后到的那张 409。
6. **物料分析给的专属批次**：分析时仓库已有物料 M 30，分析把它分给 SA-3(P' 30，每套 M 1)的委外节点做专属批次，这 30 不在公共可用里。SA-3 可下单 30，按申请带单下 30 放行；手工建一张 P' 1 的单(没有来源申请)只能用公共库存，409。别的申请也用不到这 30。
7. **草稿放弃后删除才释放**：例 5 中 SA-2 的 10 草稿一直不提交，它就一直占着 B 20(草稿、在审、财务退回的单都占物料)；删掉草稿后排「领料重算」，物料放出来，SA-1 重新解锁并收到新的可下单卡。
8. **建单后物料被用掉，送审 / 批准被拦**：SA-2 的草稿建好后 B 被车间领料用掉 20 → 提交财务 409「直属物料还没齐套，不能提交财务：「B…」本单需要 20…，现在能用的只有 0…」。同理，已送审的单在财务批准前物料被用掉，批准 409，财务驳回后由委外人员改数量再提交。
9. **批准后加量**：SA-1 的订货单批准了 40，B 已经没有余量 → 改量到 45 409「不能加量」。
10. **批准后减量不拦**：同一张单改量到 35，不看物料，照常生效(ADR-143 §二.14 的缩量下限照旧)；减出来的物料排「领料重算」后让别的申请解锁。
11. **超委外(超过申请剩余量)**：SA-1 剩余 100，A 150、B 240(够做 120)，从 SA-1 带单把数量改成 110 → 来源份额只有 100，多出的 10 没有来源，用公共库存；物料够，放行。若 B 只有 210(够做 105)，下 110 → 409。任务中心「可下单」仍封顶在剩余 100。
12. **手工直接单**：`/subcontract/orders/new` 新建、没有来源申请 → 只能用公共库存，建单、保存、送审、批准都核对；委外件缺 BOM 时建单不在这里拦，提交财务时由 ADR-143 §二.3 拒绝并转研发。
13. **多明细申请部分明细齐套**：申请 SA-4 有两条明细 P 100、Q 50；P 的物料够做 100，Q 的物料一点没有 → 这一行「可部分下单·可下单 100」，可勾选；生成订货单时 P 预填 100，Q 不预填；Q 继续锁着，物料到了再提醒。
14. **缺 BOM 优先**：SA-5 的委外件没有可发外直属物料 → 显示「缺 BOM·已通知研发」，不计红，不显示「等物料齐套」；研发保存 BOM 后按物料重新判定为等物料齐套 / 可部分下单 / 待下单。
15. **通知升、降、归零**：SA-1 锁着(水位 0)。B 入库后可下单 30 → 发卡「可下单 30」，水位 30；再到货可下单 40 → 撤旧卡发「可下单 40」，水位 40；别的委外单占走一部分，可下单 25 → 水位降到 25、`epoch + 1`，不发卡，旧卡文字仍是 40(正文已写明以任务中心实时为准)；再到货可下单 35 → 35 > 25，发「可下单 35」；SA-1 全部下完或被占到 0 → 撤卡。
16. **下单之后照 ADR-143 继续**：例 3 的 40 套单财务批准 → 冻结领料计划(A 40、B 80) → 「领料」分段可领 40 → 提交领料、仓库发料 → 分批回厂 → 来料质检 → 入库。批准后的单按领料计划占物料：发出多少、占用就少多少(库存同步减少)，已提交未发的领料由仓库预留占住、不重复算，所以齐套计算在领料过程中不会多扣或少扣。

## 七、不变量

1. 可下单、够做套数、占用、齐套检查只在 V809 的 SQL 函数里算一次；任务中心、齐套情况、预填、守卫、通知都读同一套函数，Java 只读，Flutter 不算。
2. 按任务中心「可下单 N」或联合预填值下单一定通过守卫(其间库存没被别处用掉时)。
3. 一张订货单通过守卫 ⟺ 每种直属物料：本单需要 ≤ 本单来源申请的专属剩余 + 公共剩余(都已扣掉其它在办委外单的占用)。
4. 每张在办订货明细的占用按来源份额拆进物料池，每份只算一次，合计恰好等于本行还要领的量；同一批公共库存不会被两张在办单同时认领(并发建单按物料咨询锁串行)。例外见 §八.3。
5. 减量、删除、红冲、结束领料永远不被齐套守卫拦。
6. 锁只决定能不能生成、保存、送审、批准、加量；不改订货单、不占库存、不改 ADR-143 的领料、可领与回厂计算。
7. 锁住的申请仍在「待处理」并计红数；缺 BOM 优先于齐套锁且不计红。
8. 逐种物料取短板，A 的库存永远不能替 B 放行。

## 八、已知限制

1. **占用是虚拟的**：订货单占的物料没有在仓库里预留，车间生产、销售出货、其它出库照样能把公共库存用掉。守卫在送审、批准时再核一次；批准之后领料仍是先提交先得(ADR-143 §二.16)，仓库发料按实际库存。
2. **通知可能滞后**：可下单只在「领料重算」事件投递时重算(委外直属物料入库、预留释放、委外订货单变动、财务批准、改量)。车间生产、出货等别的业务用掉库存不触发重算，卡上的数字可能偏大，水位降了也不改已发出卡片的文字；委外申请刚下达时不单独发「可下单」卡，而是在原有的「新委外需求」提醒里写明直属物料齐不齐(一条都不能下 = 任务中心先锁住、物料到了再提醒；部分能下 = 先按「可下单」数量下单)，行已在「待处理」计红，之后这些物料再变动时按水位提醒。任务中心、齐套情况、预填和守卫永远按实时算。
3. **专属批次重复认领(少见)**：两张委外申请挂在同一张物料分析的同一个委外节点上时，这个节点下的专属批次会被两张申请各算一次；守卫同口径，可能放行超过专属批次的量，到领料时按实际库存兜底。
4. **各行各算**：任务中心每张申请各自按公共剩余算可下单，不互相扣，几张加起来可能超过公共库存；一起勾选生成时按需求日期联合分配，分开生成时后一张会看到变少的数量或被守卫拦下。
5. **不做的事**：不在下单时预留库存；不按物料到货预测解锁；不做询价、锁价或价格有效期管理(价格仍在财务批准时冻结)。
