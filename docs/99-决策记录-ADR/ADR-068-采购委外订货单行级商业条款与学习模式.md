# ADR-068 采购/委外订货单行级商业条款、学习模式与超量订货

- 状态：已实施（2026-09-03；ADR-067 编号被并行会话的「工作台系统测试区」占用，顺延为 068）
- 关联：ADR-065（备料下达同批合并）、ADR-066（分类分段统一）、[订货单公共表头规范](../03-页面/订货单公共表头规范.md)、[权限体系总设计](../05-架构/权限体系总设计.md)

## 一、背景与决策

用户侧操作痛点：采购/委外订货单的结账(结算)方式、币种、汇率、税率长期放在**单头**，
一张单只能一套条款；实际业务中同一批订货不同货品可能对应不同供应商与不同结算条件，
填单时要先拆单再分别录入，操作繁琐。

四项决策（2026-09-03 用户确认口径）：

1. **商业条款全部下移明细行**：结账(结算)方式/币种/汇率/税率与供应商一样逐行录入
   （委外汇率此前固定 1，本次一并放开为行级录入，支持跨币种委外）。单头不再展示这些字段。
2. **多选批量一次写全套**：勾选 N 行 →「统一设置条款」面板一次写供应商+结账方式+币种+
   汇率+税率（留空的项保持各行原值）；行内点选同样联动多选集。
3. **学习模式（记忆预填）**：按货品记住上一次订货的整套条款（新接口 `/last-terms` 一次带回
   供应商/结算/币种/汇率/税率），下次同一货品自动带出；记忆未覆盖的字段回落默认
   （币种人民币、汇率 1、税率 0）；选商后仍未填的结算方式回落供应商主档默认（V452）。
4. **数量上限放开（超采/超委外）**：订货数量允许超过计划申请剩余量；重量本无上限。
   退货上限（≤已收）保留；收货侧沿用既有「批准剩余+超量财务隔离」机制。
   已订满的申请行仍从任务中心消失（追加靠新一轮物料分析）。

附加决策：**订货编辑页拆为专属页面**（`purchase_order_edit_page.dart` /
`subcontract_order_edit_page.dart`，路由 `/purchase/orders/new|:id/edit` 字面量优先 +
委外工厂分派），共享单据编辑页继续服务其余类型——「每页尽量专属、公共 UI 抽组件」。
**每行末尾新增「备注」列**（数据库/DTO 原本就通，前端补列+保存体+回显，铺到采购/委外全部单据编辑页）。

## 二、方案要点

### 2.1 拆单归集：一单一供应商一套条款

- 表结构**零迁移**：行级条款只在录入层存在；保存时后端 `createBatch` 按
  「供应商+结账方式+币种+汇率+税率」**组合分组**（数值按值等价，2.0 与 2 同组），
  每组生成一张订货单、条款归集到该张单头——下游收货/退货/应付沿用单头快照，完全兼容。
- 单张创建/编辑（update）：行值（若携带）必须与表头一致（`requireRowsMatchHeaderCommercial`）；
  编辑既有单一套条款，行内改动同步全部明细行。
- 兼容旧客户端/旧数据：行字段为空回落表头（`groupByCommercial` 逐字段 fallback），
  头字段驱动的老请求仍按原语义拆单；采购 `OrderSaveRequest.settlementMethodId` 的
  `@NotNull` 移到单张路径运行时校验（`requireHeaderSettlement`），批量路径逐行校验。
- 金额口径：`amountLocal = qty × price × 行汇率`；财务送审一致性校验仍按单头汇率
  （= 组内行汇率）。

### 2.2 学习模式契约

- `GET /api/purchase/orders/last-terms?goodsIds=` 与 `GET /api/subcontract/orders/last-terms`：
  返回 `{goodsId: {supplierId, settlementMethodId, currencyId, exchangeRate, taxRate}}`，
  取每个货品最新一张未删订货单的头条款（`distinct on (goods_id) … order by created_at desc`）。
- 与旧 `/last-suppliers` 的差异：**不过滤供应商停用状态**（条款对停用商仍可参考）；
  供应商是否回填由前端判断（停用商跳过供应商、仍带条款）。旧端点保留一个发布周期兼容。
- 触发时机：选货品后 / 任务中心带单预填后 / 从上游引入后；只填各行**为空**的字段。

### 2.3 超量订货放开的落点

- 前端：专属订货页保存不再校验 `qty ≤ maxQty`（maxQty 仅作分解预填默认量）；
  「从上游引入」面板 `allowOverRemaining=true`（订货模式）允许本次数量超过剩余量，
  收货/退货引入保持上限。退货/其它委外单据类型上限不变。
- 后端：移除采购 `LinkedDocumentIntegrityService` 容量校验（保留已审/未中止/维度一致）、
  `PurchaseOrderService.requireCapacityIncludingPending`、委外
  `lockAndValidateSourcesIncludingPending` 的容量段（保留来源锁定与一致性校验）。
- 下游语义（评审确认）：`ordered_qty` 可超过申请 `qty` → 申请照常结案（剩余量为负）；
  物料分析在途供给随之增大（少生成后续申请）；委外发料计划按订货量放大——均为业务期望。
  死代码 `validateSubcontractOrder`（无生产调用方）随容量逻辑一并删除。

- 后端单测：`PurchaseOrderCommercialSplitTest` / `SubcontractOrderCommercialSplitTest`

- Flutter：`purchase_order_row_supplier_batch_test` 迁移至专属页（批量按钮「统一设置条款 (N)」）；
  `subcontract_order_settlement_method_test` 迁移至专属页（行级必填/阻断）；
  `commercial_terms_batch_sheet_test`（面板留空语义）；`link_quantity_validator_test`
  （allowOverRemaining）；`purchase_grid_row_clone_test`（克隆保留条款/备注）。

## 四、影响面与兼容

- 老数据：既有订货单头条款即单据事实，编辑回显按头条款回填各行；学习查询天然覆盖历史单。
- 老客户端：`/last-suppliers`、头字段驱动的 createBatch 语义保留一个发布周期。
- 页面路由：`/purchase/orders/new|:id/edit` 字面量路由优先于 `:doc` 通配（守卫权限码不变，
  复用 `purchase_order` 六类动作码，**零新增权限码**）。
- 文档：订货单公共表头规范（条款行级化）、页面总览、组件总览、页面权限一览同步更新。
