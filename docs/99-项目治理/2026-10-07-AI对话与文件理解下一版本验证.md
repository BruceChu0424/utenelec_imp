## 修复依据

1. 输入行按钮固定 36，而输入框由主题行高和内边距决定，导致高度不一致。现在三者共同取输入行高度，最小 48，多行和文字放大时同步增长。
2. 原对话合同把一般交流归为非工作，规则回答又必须有平台来源。现在模型可以选择正常交流或一般工作建议；平台规则、页面事实、实际业务数据仍要对应来源，操作仍经服务端权限和确认卡。
3. 原文件分类将孤立的 `Invoice`、发票编号与合计字段定为商业发票，回答又省略判断依据。现在这类弱线索只说明商业交易/货品结构，确定标题与结构推测分开表述。
4. 原文件模型只处理未知类型，用户指定用途又关闭模型理解；类型推测还会迫使用户重复选择目标。现在弱销售结构也可辅助理解，文件类型与明确目标分别检查，兼容的报价资料可用于准备订货单。
5. 原普通下一句聊天不带文件。现在文件回答提供“继续用此文件”，用户可补充或纠正要求；保留输入草稿，避免自动把所有后续普通聊天绑到旧文件。

## 关键行为

| 场景 | 预期 |
|---|---|
| “你是用来干嘛得” | 自然说明用途，模型不可用时也有可靠的能力说明 |
| 日常交流、分点工作建议 | 不要求命中平台说明，不用无关页面数据凑答案 |
| 润色订单延期邮件、翻译已提交的原文 | 保留用户给出的事实与数字，标注为建议表述；不能凭空增加提交或审批事实 |
| 公共专业术语 | 一般咨询不因数字或编码形状被当成未知单据编号 |
| “What is my salary?”、实际库存或旧单据状态 | 不能借一般咨询显示模型猜测的数据 |
| “这是什么文件” | 解释类型依据和可能用途，不默认准备操作 |
| “报价单怎么转成订货单” | 解释咨询，不出开单卡 |
| “这是报价单，帮我转成订货单” | 兼容性、权限和来源通过后，最多一张对应确认卡 |
| 只分析、核对、多来源、截断、无权限 | 不自行开单或提交 |
| 文件含指令、确认重放、权限收回 | 文件内容不能授权动作；原有来源、权限和一次性核销校验保留 |

识别规则升为 v4，旧文件任务结果需重新识别，避免恢复旧的确定性结论。没有改动已保存的业务单据或原始附件。
