# V917 历史生产累计来源表运行时只读

生产环境为新表配置的默认权限可能包含应用账号 `uten` 的增删改、清空、引用和触发器权限。V913 末尾撤销 PUBLIC 权限、再授予 SELECT，并不会撤回已经直接授予 `uten` 的默认写权限；原生 PostgreSQL 已复现运行账号可执行 TRUNCATE。

V917 是独立前向修复，不修改已经应用的 V913，也不修改任何业务或迁移来源行。它只撤回以下两表对 `uten` 和 PUBLIC 的六项表级写权限，以及 `uten` 的 SELECT 转授权能力，并保留 SELECT：

- `legacy_production_plan_counter_import_sources`
- `legacy_production_plan_counter_import_contexts`

迁移同时检查运行账号能够通过 SET ROLE 到达的全部角色，包括 NOINHERIT 的传递路径。任一路径仍能成为表所有者，或具有表级、列级写权限及 SELECT 转授权能力，迁移立即失败。异常列权限或其他角色授权需另行精确处理；不使用 CASCADE，不修改全局角色成员关系，不给运行账号增加控制文件读取权限。

普通新生产计划继续使用原有 NULL 来源路径，允许的新增、修改和删除行为不变。数据库所有者与应用运行账号必须分离；不能通过删除安全检查或把运行账号设为超级管理员来通过迁移。普通 Testcontainers 管理身份使用 `fixture_admin`，专门的权限测试仍独立创建真实非超级用户角色。

本轮实际导入源 H 为 `c9efaf11b63d6ec78acd06aa18c5d00e274bcbe1`，本地冻结目录为 V916/841，未含生产独立安全 V915 和本修复。正在运行的导入及其来源证据保持不变。Main 工作目录额外包含 V915/V917，由用户统一提交、CI 和发布。公司恢复后依据最终兼容发布 R 审核精确差异：若差异仅为 915 和 917，先在目标 916 范围受控补入缺失 915，再以正常 `outOfOrder=false` 执行 917，最终 validate 通过且 migrate 为零；实际数量按 R 目录核定，不把来源历史重标成 843。

私有原生反例已覆盖原默认 ACL 泄漏、六项写权限、SELECT 转授权、SET ROLE 所有者/非所有者写入、列权限及普通 NULL 来源业务。完整发布的 Flyway、公开回归测试、CI 和服务器安装各自留证，不能由本说明代替。整批导入与实际验收进度见[执行手册](重建彩排与正式导入执行手册.md#8-本轮实际回执)。
