# 228 · V644 审核生产日报的幂等键

- 迁移：`V644__production_daily_report_approve_command_idempotency.sql`
- 类型：前向，给既有命令账本加一列并换一把唯一键。**不加表、不改历史行、不动触发器。**
- 口径来源：2026-09-22 用户反馈「生产日报审核提交失败，其实数据已经进去了，页面还停在草稿」。
- 编号：V642、V643 留给并行会话，本迁移 593→594。

## 为什么要有它

审核是整条报工链里最重的一次写。实测 4 行车间直送要 15.094 秒、约 350 行落账，
慢的全在车间直送那一段：逐行建单行 FINISHED_IN + DRAW，4 行就是 8 套单据。
Flutter Web 的 `connectTimeout`
在无 body 的 POST 上是「到响应头」的总截止且只被上传/下载进度取消，15 秒是硬上限——
服务端明明已经提交，浏览器这边已经把连接掐断了。

用户看到的是「点了没反应」，再点一次就撞状态闸门，然后分不清「刚才其实成功了」和
「真的失败了」。V409 的创建命令账本已经解决过同一类问题，这次把它从「创建命令账本」
升级成「日报命令账本」：同一张表、同一把 `(操作者, 幂等键)` 唯一键，只多一列区分命令种类。

## 改了什么

| 对象 | 变化 |
| --- | --- |
| `production_daily_report_commands.command_kind` | 新增 `VARCHAR(16) NOT NULL DEFAULT 'CREATE'`，`CHECK (command_kind IN ('CREATE','APPROVE','REVERSE'))`。存量行默认 CREATE，语义与迁移前一致 |
| `uq_production_daily_report_command_report` | 删除。原来是 `UNIQUE(report_id)`，即「一张日报只能被创建一次」 |
| `uq_production_daily_report_command_report_kind` | 新增 `UNIQUE(report_id, command_kind)`。一张日报最多一条 CREATE、一条 APPROVE、一条 REVERSE；原来那条约束的语义没有放宽，只是把命令种类并进键里 |
| 表注释与列注释 | 同步改写，说明这张表现在绑的是「一个操作者 + 一把键 ↔ 一张日报 + 一种命令」 |

`REVERSE` 这一档是给对称的反审核留的位置，本批不写入。

## 应用侧(同批，非本迁移)

- `POST /api/production/daily-reports/{id}/approve` 自此**要求幂等键**：新增
  `DailyReportApproveRequest`（`@Valid @RequestBody`，带日报 id + 当前 `rowVersion`）。
  同键重发原样回放已审详情，而不是撞状态闸门。
- 状态闸门本身**不放宽**，只把「这张日报已不是草稿」的错误码从 400 改成 409，
  让客户端分得清「你该刷新」和「你该改单」。
- 顺带把审核请求改成带 body，绕开 Flutter Web 无 body POST 的那条 15 秒硬上限。
- 明细的货品名称/编号/颜色/单位与表头的车间/负责人全部改成**服务端随单下发**，
  不再让详情页去调员工档案与字典接口现拼——原来权限或时序一变就整片显示成「—」。

## 兼容与影响

- 存量 `production_daily_report_commands` 行全部落在 `command_kind='CREATE'`，
  原有的「一张日报只能创建一次」行为一字未改。
- 不新增业务表，所以清库策略、审计触发器覆盖与 fixture 漂移守卫都不需要跟着改；
  `reset_business_data.sql` 白名单登记 `(644, 594)`。
- **接口是破坏性变更**：`approve` 不带 body 会直接 400。本批已同步改前端，
  但任何绕过前端直接调这个端点的脚本或集成都要跟着改。
