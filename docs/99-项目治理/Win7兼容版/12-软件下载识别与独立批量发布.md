# 软件下载系统识别与独立批量发布

日期：2026-10-28 开始，2026-10-29 收口，客户端 America/Denver。用户本轮明确调用frontend-design。起点e7d3290f2，继续Win7独立分支，不合main、不替换现役Win10、不部署或实际上传公司catalog。本文件先写设计与合同，随后按下方实施/验证记录更新。这里的本机阶段结果不等于整套 Win7 ERP、目标机或正式分发验收。

## 1. 本轮用户目标

- Web和各客户端在软件下载入口识别真实系统、版本及架构，推荐精确兼容目标；显示如“Windows 7 SP1 · X64 兼容版”。浏览器无法可靠识别时明确不确定并允许手选，不能把NT10的冻结UA断言成Win11。
- 显示将下载的具体平台/系统范围、架构、产品版本及文件类型，选择对应已发布安装包。不跨family/arch拿另一包顶替，没有完整有效包就无下载操作。
- 更新上传改为独立完整页面，替换已有弹窗入口，支持单个文件和批量队列。每行元数据、校验、进度、失败/已成功/未知分开，Windows按对应组合配对。
- 同仓库维护公共目标契约、权限和业务语义，保现用Flutter更新默认逻辑。WPF适用下载显示/检测同步，未迁的发布入口不能假称已支持。

## 3. 设计计划与自检

主题使用现有Uten ColorScheme，不在页面另造色板。浅色校准：主操作青绿#0F766E，底色#F5F7FA，纸面#FFFFFF，主字#0F172A，次字#475569，边线#E2E8F0；深色沿当前主题映射。中文Noto Sans SC与既有fallback，页面标题/正文/说明用既有typography。Card16/Table12/Dialog20/Menu8/Control10保持角色差异。

下载页布局：

    软件下载                                   发布客户端
    当前设备事实 / 检测可信度 / 手动调整
    适用目标：Windows 10 / 11 · X64
    产品名 / 版本 / 构建 / 大小       对应文件与主下载动作
    平台与目标选择 / 发布说明 / 下载状态
    其他平台的紧凑版本列表
    安装和更新说明

发布页布局：

    客户端发布中心                        添加文件 / 批量添加
    产品版本与发布说明 / 当前目标设置
    文件队列（每行可核对精确目标、类型、大小和状态） | 配对摘要
    行错误/未知及恢复动作                          | 校验/发布动作
    已发布记录、过滤与撤回

窄屏将摘要移到队列下方，不压缩关键文字。大屏惰性列表，状态变化保留行位置和焦点；上传只更新相应行，不重建全部页面。真实状态做语义颜色与文字，禁止仅颜色区分。

对brief的自检：特色放在“设备→目标→实际包”和“逐文件→完整配对”的关系上，不做营销hero/装饰大数字，不堆相同卡片或渐变。所有文件名/版本/架构都是可检查业务事实，主动作写具体目标，不仅写“下载Windows”。

## 4. 共同契约和兼容边界

- 检测事实与用户选择分开。迟到异步检测不能覆盖用户已经手选的目标；组件或owner退役不回填。平台/系统/架构未知时不把默认x64包装为检测结果。
- Windows10/11现有运行时flutter，Win7SP1/8.1为wpf_legacy。真实更新依旧按当前进程安装上下文匹配，新软件下载推荐按真实OS架构。
- Android APK、Apple store仅在现有服务端合法模式/可信URL合同内提供；Linux若后端尚不支持发布就准确显示未提供，不能做假下载/上传成功。
- 上传文件名只可提供提示，服务端包内容校验仍权威；不能靠后缀或名称确认系统/架构/版本。
- 每行稳定requestId、文件摘要和冻结元数据；已成功文件不因另一行失败重传。未知先查原draft/receipt或以同一强幂等意图恢复，不新建随机ID盲重试。
- 新Windows交付必须完整同组合Setup+ZIP；历史catalog缺配对字段的兼容过渡要保留旧默认，不突然中断现役Win10原下载/更新链。不得反写旧元数据假装已验。
- 既有client_release:publish及step-up执行不绕过；更换账号、issuer、权限、dataset/epoch后的旧上传结果不注入新页。

## 7. 发布和恢复操作合同

1. 从设置的发布入口，或工作台右上角 Windows 下载进入软件下载，再点“发布与管理”，进入完整发布页面。直接 URL 同样走权限门；超级管理员也依赖服务器权限目录给出的实际发布授权，不能仅凭本地标志越权。
2. 先填版本、构建号、说明及新增项目默认目标；可“添加单个文件”或“批量添加”。Windows `.exe` 仅提供安装用途提示、`.zip` 提供更新用途提示，文件名不决定 OS/架构/权威版本。混合家族/架构须逐行核对、必要时编辑，发送前会冻结原意图。
3. 同 Windows 家族、架构、版本及构建号的 Setup 与 ZIP 必须都发布，才开放**新组**软件下载和更新推荐。一个文件可以先上传并发布，摘要会显示等待配对；不把单文件成功当整组完成。不得借历史 null-contract 文件拼成新配对或借其清理旧包。
4. 单行 prepare / upload / publish 均沿原 ID、原 metadata、原摘要及原 owner。未知首先 GET 原记录；权威 404 只允许以**同 UUID**准备原意图，必要时重选同 SHA 文件。已上传可确认文件不重传；与原意图不符的回执保持原记录待核对。
5. Windows publish 超时/500 后，GET 原 ID 读到 PUBLISHED 仅说明发布事实，不能证明旧二进制保留处理完成。必须明确继续同 ID publish 收口，不能新建、重新上传或重复普通已成功行。成功 HTTP 回执以 `publishAcknowledged` 保留，恢复后不重放。
6. 撤回沿原 ID、再认证及逐项回执。未知撤回先核对原状态；已撤回为独立持久终态，恢复后不会再次发布，摘要不能被旧 PUBLISHED DTO 覆盖。撤回不能复活已清理的旧二进制。
7. 离开时可保存发布草稿；未知必须先保全原记录。普通明确未决之外的“不保存”真实清理原草稿，不被离开/销毁回写。换账号/权限/服务器先隐藏数据，原 lease 只能向原命名空间保全，不能授权新网络操作。
8. 发布页当前迁移原有能力：Windows Setup/ZIP、Android APK、iOS/macOS 官方商店。下载端可读取既有合同合法的 Google Play 链接；Google Play 的发布输入原弹窗也没有，本轮没有扩展该新发布方式。Linux 可识别、可手选，但后端没有合法发布方式时始终显示未提供。
