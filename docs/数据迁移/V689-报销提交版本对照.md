# V689 报销提交版本对照

报销原先在编辑时删除并重建明细，驳回或撤回后重新提交时缺少上次真实内容，审批人无法核对改动。V689 为 `expense_claims` 增加 `submission_snapshot`、`previous_submission_snapshot`（可空 JSONB 对象）和 `resubmission`。

提交校验通过后，在原报销行锁及同一事务内将上次提交镜像移至 previous，再冻结本次表头、费用明细和登记发票。草稿编辑不改提交镜像；连续编辑只在下一次实际提交时产生新对照。重新提交涵盖驳回重提和撤回重提；撤回清空 `submitted_at`，但不清空商业镜像。权限、凭证校验、版本冲突、审批人与付款人分离和过账链路保持原守卫。

镜像为 `schemaVersion=1` 对象：`title`、`remark`、`totalAmount`、`items`、`invoices`。金额使用十进制字符串。费用行保留当时行 UUID、行号、类别、金额、日期和说明；发票保留登记商业字段及附件绑定。人工核验状态、核验人及核验备注属于审批工作状态，不列为申请人的商业修改。费用行现有编辑 API 会重建 UUID，展示层按完整商业字段进行保留重复次数的匹配，不能只按新旧 UUID 把所有行误判为替换；发票行使用稳定 UUID。

迁移不会用当前可编辑内容反推历史镜像，也不读审计日志重建业务事实。旧业务提交事件只用于标明已经重提；旧镜像为空时明确表示历史缺失。仍处于 SUBMITTED/REVIEWING 的旧单在撤回或作审批决定前可以保留当前冻结内容，因为此时申请人不能编辑。已经进入 DRAFT/REJECTED 的旧单不作这种推断。V689 不修改任何已发布迁移。

验证覆盖精确金额、核验状态不产生假修改、驳回重提、撤回后连续编辑重提、旧冻结单可靠保留、旧可编辑单不伪造、非空 V688 升级及 JSON 对象约束。源码与隔离 PostgreSQL 证据不代表目标服务器已升级。

升级时先执行 V689 再启用新应用；新实体依赖新增列，不能让新应用连接仍停在 V688 的库。迁移只增加列和约束，旧金额、状态、事件、单号和引用均不改写。已有明确两次以上 SUBMITTED 业务事件的单据只补 `resubmission=true`，两份历史镜像仍为 NULL。

数据库结构对旧应用是加列兼容，回退应用无需也不应删除快照列；这是列结构兼容判断，未实际运行旧版本包进行回退验收。但旧应用不会维护新镜像，因此这不等于允许跨旧应用报销修改后仍宣称对照完整：回退期间应暂停报销提交、撤回和重提；若确实发生旧应用写入，重新启用新应用前须把受影响单据的旧镜像当作不可用，再按冻结状态安全补存，禁止沿用可能过期的镜像。没有执行生产回退或目标库写入。
