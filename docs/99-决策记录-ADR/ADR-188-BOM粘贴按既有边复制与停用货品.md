# ADR-188 BOM 既有边受控复制与停用组件新增边界

> 2026-10-22 后续决策: [ADR-191](ADR-191-禁用货品自动退出当前组装清单.md) 已取代本文对停用组件的复制及覆盖导入豁免。当前禁用会移除所有当前引用，粘贴和导入统一拒绝停用组件。下文保留当时问题和方案的原始记录。

- 日期：2026-10-21；2026-10-22 补齐服务端源边证明。
- 状态：已接受，按本文实现。
- 修订 ADR-111 §三.5（粘贴校验清单去掉「停用」）、§三.6（货品粘贴失败逐条展示原因的实现由本文补明细）。
- 关联：ADR-111（粘贴原子命令）、ADR-129（粘贴行取设计值）、ADR-185（编辑模式门槛不变）。

## 一、背景

2026-10-21 用户在货品资料里复制「3M双联单控」后粘贴：货品副本已建成，组件信息却报
「粘贴没有生效：有 1 处问题，现有组件没有任何改动」，反复重试只是不断多出没有 BOM 的
空副本。dev 库实证该 BOM 12 行组件里恰好一行 UT3118「6M圆标贴（响臻白）」状态=禁用，
`GoodsBomPasteService.usable()` 把「禁用」状态的父件/组件一律拒绝，于是整批 409。

这不是某次回归，而是 ADR-111 把两件事混在了同一把尺子上：

1. **新选语义**——交互式往 BOM 里挑组件（选择器、单行新增）不应再引入停用货品。
   选择器 `excludeDisabled`、单行新增 `requireVisibleActiveGoods` 一直把守这道门。
2. **复制语义**——源清单里本来就存在的停用组件行是合法历史状态（ADR-111 的共识：
   被引用的货品「需要保留历史的一律停用而不是删除」）。完整复制应能保留这条边，但
   服务端必须验证当前有效且可见的源边；客户端声明“快照”或提交组件 UUID 不构成证明。

粘贴命令按新选口径整批拒绝，等于宣布「BOM 里有停用组件的货品永远无法完整复制」，
同一根因还有三处同病：跨货品「复制组件信息→粘贴」、BOM 导出文件原样导回（检测阶段
不查停用、commit 阶段才炸）、复制停用货品（副本状态=禁用，作粘贴目标被拒）。

## 二、决策

1. `usable()` 仍校验未删除、非迁移占位；停用组件的新边另外校验来源。替换时目标已经有的
   同一停用组件边可以保留。向新目标写入时，必须提交 `copiedFromBomItemId`，服务端核对源边
   未删除、源父件可运营且当前可见、源组件 UUID 一致，并对比请求与源行内容。
2. 源父件与目标父件一次按 UUID 顺序加锁，锁后重读源边；源边已删、不可见、被替换、
   内容已变化或伪造 UUID 都整批拒绝，不写入半套 BOM。复制成本继续遵守原价目可见性。
3. 「停用不能新选」由选择器 `excludeDisabled`、单行新增/换件 `requireVisibleActiveGoods`、
   组装编辑模式及批量 ADD 的服务端 active 校验共同执行。批量移除可以选择既有停用组件。
4. 前端货品粘贴结果弹窗把 `ApiException.fieldErrors` 逐行拼进失败原因
   （概括句 + 每行「哪里：为什么」，全角冒号，最多 10 行），与组装编辑保存失败同一
   格式；此前只显示概括句，用户看不到是哪一行、什么原因。

## 三、边界

- 粘贴行的存在性、可见性（归属隔离）、自引用、清单内重复、追加重复、成环、用量与
  阶段、期间边确认、乐观锁（expectedItemIds）全部照旧，本 ADR 只移除状态维度。
- 导入（`pasteImported`）共用同一校验。文件没有有效源边身份，不能凭组件编号向新目标添加
  停用组件；覆盖导回本目标时可保留该目标已有的同一停用边。材质、库存数量是只读导出列，
  导入不会改写主档材质或库存。

## 四、验证

- `GoodsBomPasteDisabledGoodsTest`：有效源边原样复制、停用目标可接收复制；无证据、伪造、
  源边已删、错组件、不可见源父件、复制时改量均拒绝；已删除/迁移占位组件仍整批拒绝。
- `product_category_page_paste_test.dart`：组件粘贴被拒时结果弹窗逐行列出
  「第 N 行 哪个组件：为什么」。
