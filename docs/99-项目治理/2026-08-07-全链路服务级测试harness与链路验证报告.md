## 一、背景与问题

- 业务四模块（销售/委外/生产/钱流）DDL、迁移、Java/Flutter 主体已成型，但"全链路 E2E"长期只停留在文档与 DB 约束层面。
- 旧链路"测试"（如 `ProductionPurchaseSupplyTransitionPostgresTest`）的做法：起 Postgres + Flyway，然后用**原生 SQL `INSERT`/`UPDATE` 手工伪造**整条供应链状态（`consumed_qty`、reservation、receipt、allocation 全手写），只断言**触发器/CHECK/视图**仍成立——**完全绕过服务层编排**。且全部 `@EnabledIfEnvironmentVariable(UTEN_RUN_DB_TESTS=true)` 门控，普通 `mvn test` 不跑。唯一的 `@SpringBootTest`（`RequestHeaderBudgetIntegrationTest`）排除了 DataSource/JPA/Flyway/Security，只是 Tomcat 头部解析探针。
- **结论**：服务编排（业务链路真正依赖的代码）自动化覆盖为 0。

## 二、新建资产：`FullChainEndToEndTest`

- 路径：`server/src/test/java/com/uten/imp/businesschain/FullChainEndToEndTest.java`
- 配置：`@SpringBootTest(webEnvironment=MOCK)`（NONE 会缺 `HttpSecurity` 致 `SecurityConfig.filterChain` 崩）+ Testcontainers `postgres:16-alpine`（`@DynamicPropertySource` 注数据源）+ 全 229 迁移 Flyway 全新跑通 + Hibernate `validate` 通过 + `BootstrapRunner` 建超管 + profile=dev（关 retention / mv-refresh / policy-intelligence）。
- 必填 env（无默认 fail-fast，测试用 `properties` 注合成值）：`uten.jwt.secret` / `uten.crypto.pgp-master-key` / `uten.crypto.hmac-key` / `uten.bootstrap.admin-password`。
- 运行：`UTEN_RUN_DB_TESTS=true mvn -f server/pom.xml -Dtest=FullChainEndToEndTest test`（全量 ~55s；单方法加 `#方法名`）。门控 `@EnabledIfEnvironmentVariable(UTEN_RUN_DB_TESTS=true)`（需 Docker；与项目既有 DB 测试约定一致）。
- **核心方法（可复用）**：`seedWorld(tag)` 建多级 BOM 世界；`loginAs(userId)` 复刻 `JwtAuthFilter`（`PermissionResolver.authorizationSnapshot`）切账号；`createReviewer(w,permCode)` 经 `user_permission_overrides` 建财务审核人；`approvedPlan(...)` / `procureDirectBuy(...)` 封装多步链路；`count/intFor/strFor/stockBalance` 断言助手。**断言一律走真实 DB 状态（jdbc），不手写 SQL 伪造**。

## 三、已验证的 8 段链路（真实服务 + 真数据，8/8 全绿）

| 段 | 入口服务 | 实测验证 |
|---|---|---|
| 销售→审核 | `SalesOrderService.create/approve` | 缺货成品→`chain_status=2 待排产`、零预留；`billNo` 服务端生成 |
| 计划→审核 | `ProductionScheduleService.createMergePlan` / `ProductionPlanService.approve` | `planned_qty` 回写、`plan_order_item_links` 绑单、chain 推进至 待物料(3)/已排产(4) |

## 四、关键实测发现（重设计 / 修复依据）

1. **计划部分解逐层手动（spec #16）**：confirm A 只处理 A 的**直层**组件；D（采购）是 B 的下层件，A 这层**不开采购申请**，须等 B 子计划再 confirm。这正是用户要求的"自底向上全树展开"要改的限制（见路线图 #13）。
2. **超管绕过功能权限，但不绕过财务审核资格**（V229 / ADR-027 审核组 + 个人加授模型）。财务 `approve` 必须有"财务部树持 review OR `user_permission_overrides` 加授"的合格审核人；且 `submit` 前审核人池必须非空（fail-closed）。
3. **IQC 待检不入可用库存**、入库**累加（非覆盖）**、收货审核即过 AP —— 均已实证正确。
4. **数据要求 gotcha（已固化进 seed）**：① 货品须有**基本单位**才能下单（`SalesMasterReferenceValidator`）；② MRP 经**老库桥梁** `units.legacy_id = goods.unit_legacy_id`（UUID `unit_id` 不足）；③ `procurement_inspection_items` 用 `updated_at`（无 `created_at`）；④ `business_outbox` append-only（无 `is_deleted`）；⑤ `users` 列名 `password_hash`/`is_super_admin`/`auth_version`（无 `account_locked`）。
5. MRP 递归展开的**需求计算 / 路由 / 跨层去重**正确——自底向上重设计可放心在此已验证的数学上进行。

## 五、已锁定的 4 个流程决策（用户拍板）

1. **库存路由**：所有销售单（含库存充足）都进计划部；计划员决定"直接发货"或"生产"。（现状：够货自动 `可发货` 绕过计划部，待改）
2. **出货由销售发起**：产品**生产完毕→系统通知销售"可分批发货"**→销售建发货单→仓库备货→销售凭单发货。（缺"生产完毕→通知销售"）
3. **供应商少送（欠交）也进财务决策**。（现状：只多送进财务，待改）
4. **计划部分解=自底向上**：最深层先做，下层入库完成→**自动释放**上层可开工→…→外壳最后；傻瓜式操作。（最大重设计项）

另：**安全拉满**——危险管理面（模拟身份/权限页/超管设置）普通员工（含懂技术）不可达；不能自我提权；对象级隔离。
