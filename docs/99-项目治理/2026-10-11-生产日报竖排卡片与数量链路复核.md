## 找到并修复的数量边界

| 问题 | 当前行为 |
|---|---|
| 大数量上限和实耗使用 double，最后 `0.0001` 可能在比较中丢失 | 来源、恢复、复制、材料、批次及分组传精确原文；数量用 BigInt 刻度比较；缺原文的旧大数要求重核 |
| 同源普通报工各行未超，累计超额时遗漏原因提示 | 按本次实际提交顺序累计，同源取保守最小额度，跨额行填写原因；服务器预览仍是最终分流权威 |
| 非基本单位名义量为正，换算后为零，直到审核／入库才失败 | 保存输入、正式拆份、旧稿审核及直送共用正基本量守卫；客户端提前标错，保留原数，不丢份、不改 HALF_UP |
| 名义量或换算后的基本量超出原数据库范围 | 复用数量 `NUMERIC(18,4)`、换算率 `NUMERIC(18,6)` 的现有范围；实耗和不良数允许0但拒绝超范围，避免晚到SQL溢出 |
| `.5`、`1.` 输入的解析与保存不一致 | 规范化为同一数值提交；单独 `.` 无效；原输入控制器保留 |
| 已有精确换算率但缺数值影子时，提交体遗漏 rate | 根据权威 `unitRateText` 提交；实际页面证明 qty `.5`、defect `.1`、rate exact `0.4` 分别传 `0.5`、`0.1`、`0.4` |
| 审核详情默认三位显示，`0.0001` 看成0 | 用精确数量原文和单位显示；缺原文的旧大数显示待核对 |

正常超限仍如实保存并分账。计划1000、有效允许10%、实际1200时，原需求1000、额度内公共100、超限待处置100；超需求200与超授权100是不同事实。未批准超限份不计可用库存，不扩原计划或比例。不良数只是记录，不减良品量；保存保持实耗，余料只在审核时逐项决定。
