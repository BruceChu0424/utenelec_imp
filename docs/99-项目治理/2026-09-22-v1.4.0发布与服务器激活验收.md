## 三、跨境上传：从 1h23m 降到 4 分钟

第一次发布（run 35674308293，从分支头）构建+签名 4 分钟，之后 20 多分钟连第一个对象都没落地——
和 v1.3.0 是同一个症状。这次先把三段链路各自量出来，再动手：

| 链路 | 实测 |
| --- | --- |
| 服务器 ← OSS 下载 | **10.6 MB/s** |
| 本机 ← GitHub | 3.5 MB/s |
| 本机 ← 阿里云镜像 | 1.3 MB/s |
| 服务器 ← GitHub | **超时 0 字节**（这条路本来就不通，服务器只能从 OSS 取） |
| 本机 → 服务器（Tailscale） | 约 78 KB/s（经境外中转，做不了中转站） |
| GitHub 跑批机 → OSS | 20 分钟传不完一个 113MB 的 JAR |

结论：产物不大、服务器不慢，慢点只有「境外托管跑批机 → 境内桶」这一跳。用户在控制台开了 OSS **传输加速**，
发布链相应改为（提交 `1309df9a`）：

- 上传侧新增可选变量 `OSS_UPLOAD_ENDPOINT`（设 `oss-accelerate.aliyuncs.com`）；下载与清理仍用 `OSS_ENDPOINT`。
- 上传前先打一个探针对象试水：加速不可用就原样回落标准域名并记 warning，绝不让一个加速开关把发布拦下；
  探针对象不在 `SHA256SUMS` 清单里（更新器只按清单逐文件下载），传完顺手删，删不掉也只记 warning。
- 完整性口径不变：上传带 `Content-MD5` 由 OSS 收件时校验，权威闸门仍是已签名的 `SHA256SUMS` + 更新器逐文件核对。

加速是否已生效，可以在服务器上用更新器的只读账号自签 v1 签名直接 GET 加速域名验证（本次 `LATEST.txt` 返回 200）。

重新发布（run 35676075301，从 `main`）：**构建+签名+上传+清理共 4 分 0 秒**。

## 五、事故：发行版自动升级把 clamd 打掉，表现成「发布失败」

- 06:47 服务器 `unattended-upgrade` 把 clamav 从 1.5.3 升到 1.5.4。新版包里多了
  `clamav-daemon-socket-generator`，它按 `/etc/clamav/clamd.conf` 生成 `/run` 下的 drop-in，
  已经写好 `127.0.0.1:3310` 与 `/run/clamav/clamd.ctl` 两条 `ListenStream`。
- `ListenStream` 是**可叠加列表**，我们在 `/etc` 里的 `uten-loopback.conf` 又追加一条 `127.0.0.1:3310`，
  systemd 于是对同一地址绑两次，socket 单元以 `Address already in use` 失败——
  当时 `ss` 里 3310 上其实什么都没有，端口没被别人占，是自己绑了自己。
- 连锁：clamd 起不来 → 附件安全探针 `probe()` UNAVAILABLE → readiness 分组
  （`readinessState,db,diskSpace,attachmentSafety` 四选一垮就是 DOWN）→ 更新器判活失败 →
  把已经切过去的 v1.4.0 回滚。**新版本本身没有任何问题**：日志里 8.853 秒启动完成并正常接了请求，
  业务接口（登录页 200、`/api/auth/me` 401）也一直在服务。
- 修法（提交 `6985e207`，服务器已按同样内容改好）：drop-in 写成幂等的——先 `ListenStream=` 清空，
  再显式写死回环两条。既不重复绑定，也仍把未鉴权的扫描端口钉死在 127.0.0.1，不跟随 `clamd.conf` 漂移。
  改完 `clamd` PING → PONG，readiness 回到 UP。
- **留给下次的判据**：更新器报「启动或健康检查失败」时，先看应用日志里有没有 `Started …Application`；
  有就不是新版本起不来，去查 readiness 分组里的四个探针谁 DOWN，别急着怀疑本次发布内容。

## 七、冒烟查出的真 bug（已修，随下一版上线）

`/api/master/warehouses` 在「整页只有顶层仓」时 500：上级仓名按本页出现过的 `parentId` 一次性载入，
一个都没有时返回 `Map.of()`，再拿顶层仓的 `null` 作 key 去 `get` 就抛 NPE（不可变 Map 的约定）。
页里只要混进一行带上级的就换成 `HashMap`，`get(null)` 合法——所以平常翻页看不出来，只在筛选
「独立顶层仓」或小页恰好只落到顶层仓时现形（服务器上 14 个仓有 13 个带上级，`size=1` 的第一行正好是顶层仓）。
修复与回归用例见 `fe58edec`（`WarehouseListTopLevelOnlyPageTest`，撤掉修复即复现 NPE）。

## 八、边界与后续

- 本记录只证明部署、迁移、只读接口与自动化测试的事实，**真实岗位 UAT 未做**。
- 发布时 PR #24 的 backend-db 全链仍在跑；`main` 上 `6985e207` 的六作业为本轮权威复验。
- `v1.4.0` tag 未推送：tag 触发的发布会用同一版本号重新打一份产物，与服务器上已装的字节不再是同一次构建，
  不如让 `/version.json` 的 `commitSha` 作为唯一凭据（`v1.1.0`/`v1.2.0` 也是这样）。
- 上一版遗留的启动期 `ROLE_INFRASTRUCTURE` 警告已随本版消失。
- Dependabot 的 16 个依赖升级 PR 仍未评估（含 Spring Boot 4.x 大版本）。
- 服务器的 `unattended-upgrade` 会在早上自动升级发行版软件包并连带重启守护进程；本次是 clamav，
  下次可能是别的。**发版前先看一眼 readiness，别把发行版升级的锅算到发布内容上。**
