## 1. 背景

用户原话(2026-09-27)：

- 「我的车间任务 生产中的四个物料 我批量报工 正常来说 最下面那个 就是编号HV5ZJ012 是可以转到下一道工序的 … 又不可以了 … 明明就是有父层级的 还是在同一个车间」
- 「再帮我修改个ui 就是不能转的 你直接红色的字 无法转到下一道工序」
- 「你要把功能函数啥的 该公用就公用 不要每个都重复写」

只读实查(克隆库 `uten_imp_wt15`)：HV5ZJ012 在 2026-09-23 10:26 被改成委外件(有 3 个子件 ⇒ 委外前置自制：先做好送入仓库，发外加工，回来后上层工单从仓库领料)。它的共享批次路线是委外，上层工单 HV5G001 对它的需求也是委外口径。**拦住是对的**(用户已确认「是走委外 没有错」)，**界面给的原因是错的**：下拉只会写「转下一道工序(无同车间上层工单)」，而同车间的上层工单明明存在。

根因不是合单，而是「能不能直送」这一条规则散在约 10 处，已经走样：

| 位置 | 问题 |
| --- | --- |
| 4 个库函数 + 3 个行触发器 | 同车间、接收状态、计划/计划包状态、自制路线、数量上限各被复写 3-6 次；两个守卫报英文 |
| 候选接口 | 自带一套更松的关系预筛，份额为 0 时静默跳过，一个原因都不给 |
| 保存报工 | 只查父子关系，不查接收方停产/关闭/已开工，拖到审核才失败 |
| 审核 | 7 种以上原因共用一句「直送须有同车间的真实上下层供给责任…」 |
| `fn_demand_direct_supply_eligible` | 只看同车间有没有同货品工单(V605)，不看真实父子关系，与其它处口径不同 |
| 前端 | 空候选一律写「(无同车间上层工单)」；读取失败也当成空候选 |

## 2. 决策

### 2.1 一份结构判定，给出原因码

`fn_workshop_direct_relation_code(生产工单, 接收需求)` 是唯一的结构规则：返回 NULL 表示可以直送，否则按固定次序返回一个原因码：

1. `SOURCE_INVALID`(报工来源工单已失效) → `TARGET_INVALID`(所选上层工单已失效) → `SELF` → `GOODS_MISMATCH`；
2. `SUBCONTRACT_ROUTE`：接收需求按委外供应，或生产侧是委外件(分析行为委外前置自制/委外备料，或其共享批次路线为委外)；
3. `BUY_ROUTE`：接收需求按采购供应；
4. `NO_PARENT_RELATION`：没有真实父子关系(沿用 V615 原口径与 V715 共享批次份额证明)，或者路线不对而接收需求与本工单根本不挂钩(见下)；
5. `DIFFERENT_WORKSHOP`：放在最后，历史责任口径只忽略这一条。

**路线只在这里判**。先判路线、再判父子关系，所以委外件被点名为「委外件」，而不是被父子关系证明里的「只认自制」过滤成「没有关系」。**路线只对挂钩的需求点名**：`fn_workshop_direct_linked_demands(生产工单)` 是「结构挂钩」唯一的一份写法——接收需求与生产工单同一个物料分析，或都不走物料分析时有子计划链接/在途挂钩(peg)。没挂钩的需求(别的物料分析里同车间同货品的工单、没有任何链接的计划)哪怕按委外或采购供应，也只回 `NO_PARENT_RELATION`：它们本来就不是本工单的上层，拿它们的路线当「转不了」的原因是错的(复核发现：生产侧是委外件时，别的分析、别的车间里同货品的工单都会被点名成「委外件」列进置灰列表；反过来，一个自制件会因为别的分析里有同货品的委外需求而被说成委外件)。挂钩不等于父子关系成立，所以同一物料分析里挂在别的父件下、按委外/采购供应的同货品需求仍会点名路线，这是有意保留的近似(要完全排除需要一套不看路线的父子证明，见 §3 第 2 条)。V615/V715 的父子证明都要求上面几种关联之一，所以能直送的需求必然挂钩。两个既有函数改成包装：`fn_workshop_direct_relationship_allows` = 原因码为空；`fn_workshop_direct_responsibility_allows` = 原因码为空或只差车间。

父子关系证明本身(`fn_workshop_direct_responsibility_allows_before_v715`、`fn_preplan_aggregate_direct_scopes`)**原样保留**，不去掉其中的「只认自制」条件：路线已先于它们点名，去掉条件只会改变 `fn_workshop_direct_remaining_for_source`、共享切片记录等调用方的内部路径，却不带来任何可见收益。等价性在克隆库 15 对同货品组合上逐对核对一致，并由 Postgres 测试锁定(见第 5 节)。

### 2.2 一张表函数，一份大白话

`fn_workshop_direct_targets(生产工单[, 接收需求[, 本次基本数量]])` 给候选列表与单条校验共用：

- **列表模式**：范围只取与本工单挂钩的同货品需求(`fn_workshop_direct_linked_demands`，任意车间，计划已取消的不列)，**只列结构上的上层**，逐条给出接收工单、需求量、已覆盖、还差多少、本来源最多可送、`receiver_open`、`eligible`、原因码、原因大白话、接近程度与「先急后缓」次序(接收计划所属分析行的优先级、交期/需求日期、计划单号、工单号，与 `AggregateQuantityAllocator.ORDER` 同一次序)。不是上层的行(`NO_PARENT_RELATION`、`SELF`、`GOODS_MISMATCH`、`SOURCE_INVALID`、`TARGET_INVALID`)不列，既不进置灰列表，也不参与「最接近的原因」。一条结构上的上层都不剩时返回一条哨兵行说明真正的原因：`NOT_A_COMPONENT`(顶层产品没有下一道工序)、`NO_RECEIVER_ISSUED_YET`(上层工单还没下达)、`SUBCONTRACT_ROUTE`(生产侧是委外件)、`SOURCE_INVALID`(来源工单或其计划已删)。
  - 此前列表还会把「同车间同货品的在办需求」不分物料分析全部拉进来：这些行必然没有父子关系，却会挡住哨兵(顶层产品报工显示成「上层工单 X 的 G 不是由本工单供应」，送仓原因也存成 `NO_PARENT_RELATION`)，按委外/采购供应的还会带着路线原因进置灰列表、甚至成为红字原因。复核后删掉这一段范围，并把「是否出哨兵」改为按「还剩没有结构上的上层」判断。
- **单条模式**：恰好一行；给了本次数量再判 `QTY_EXCEEDS_REMAINING`。
- 判定次序：结构 → 状态(`PLAN_NOT_ACTIVE`、`PACKAGE_NOT_CONFIRMED`、`RECEIVER_STATUS`、`DEMAND_CLOSED`) → 数量(`DEMAND_ALREADY_COVERED`、`SOURCE_SHARE_USED_UP`、`QTY_EXCEEDS_REMAINING`)。`receiver_open` = 结构与状态都允许，只可能差数量。
- 原因文案只有 `fn_workshop_direct_reason_text` 一份，不含代号，括号半角；接近程度只有 `fn_workshop_direct_reason_rank` 一份。原因码与文案全表见[迁移说明](../数据迁移/255-V736车间直送资格单一事实源与不可转原因.md)。

### 2.3 一个断言，守卫与应用共用

`fn_assert_workshop_direct_target` 锁住接收计划/计划包/工单与需求后读单条校验，不可送即抛 `无法转到下一道工序：<原因>`(SQLSTATE 23514，HINT=原因码，CONSTRAINT=`workshop_direct_target_guard`)。直送明细的守卫触发器改为调用它(新触发器 `trg_a_workshop_direct_target_guard` 名字排在共享切片触发器之前)；旧 V612 接收状态块、数量上限块、段车间相等、V615 关系/数量守卫、V715 切片前复核全部删除。线边仓身份、整行镜像、需求与接收工单身份、追加式不可改删这些与资格无关的不变量保留在原守卫。

`GlobalExceptionHandler` 只认这个约束名与固定开头，把库里的原因原样作为 409 返回，不回显 SQL/DETAIL/HINT；约束名对但开头不对时给一句通用话。

| 调用方 | V736 之后 |

## 3. 考虑过的其它做法

1. **各处各自补一句更准的报错**：改动最小，但原因仍然会在候选、保存、审核、守卫四处各写一遍，下一次改规则还会走样。不采用。
2. **把父子关系证明改成不看路线，路线另外判**：语义最干净，但会改动 `fn_workshop_direct_remaining_for_source`、共享切片、库存认领等 8 个库内调用方的内部路径；本次通过「先判路线再判关系」已能正确点名，收益不抵风险。不采用，证明原样保留。
3. **候选接口只返回空列表，由前端猜原因**：前端没有路线、父子关系与份额的数据，只能继续写死一句话。不采用。

## 4. 同行 ERP 的做法

- SAP S/4HANA：组件从哪里扣料由**消耗方**所在的生产供应区决定，在交接时判定，与供给单怎么合并无关。([生产订单发料](https://learning.sap.com/courses/manage-production-orders-in-sap-s-4hana-manufacturing/posting-goods-issues-for-production-orders)、[供应区确定](https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/48b24fbadbee4e0b9dae0e2b72762e68/ba6bb6531de6b64ce10000000a174cb4.html))
- 金蝶云星空：BOM 子项的发料方式分直接领料/倒冲与调拨领料/倒冲，调拨类从挂在生产车间上的 WIP 仓取料。(社区资料，[生产订单手册](https://help.open.kingdee.com/dokuwiki/doku.php?id=%E7%94%9F%E4%BA%A7%E8%AE%A2%E5%8D%95))
- Odoo：制造单只有同产品同 BOM 才能合并。([拆分与合并](https://www.odoo.com/documentation/19.0/applications/inventory_and_mrp/manufacturing/workflows/split_merge.html))
- Microsoft D365：合并后的供需对应关系单独保存。([Marking](https://learn.microsoft.com/en-us/dynamics365/supply-chain/master-planning/planning-optimization/marking))

共识：合批看「怎么做」，去向看「谁来用、在哪用」，在交接时实时判定；多个需求的对应关系单独保存。本 ADR 第一步把「交接时判定」收成一处并说出原因；第二步(第 7 节)补上「一次分给多个消耗方」。

## 7. 第二步：一行报工分给多个上层工单 (2026-09-27)

### 7.1 背景

用户原话(2026-09-27)：

- 「该分开分开 就是 那些可以车间内流转 那些需要 回到仓库 … 该合并的合并 该分开的分开 毕竟就是 我们计划下单 把相同物料的合在一起 但是没有考虑父类的情况」
- 用户确认：按先急后缓，逐个分满(不按比例摊)。
- 用户对界面的要求：「车间那里选择转到下个工序 就是可以去选择 转到哪个父类 排序按照轻重缓急 然后 就是 比如 填写报工10000 那么他可以填写 1000 转到一个父类 那么 下面自动出现一行 就是 可以填 剩下的 转到哪里 仓库也可以 直到全部计算完」

只读实查(克隆库 `uten_imp_wt15`)：合并批次(例如 HV5G001 共享批 11000)要分给 11 个成品工单各 1000；此前一行报工只能投一个接收工单，其余 10000 被按「需求份」悄悄送进仓库，入库后再按随机 UUID 分给来源，会把本来能在车间内直送的父件份额也占掉。

### 7.2 决策

1. **合并规则不动**：继续按「怎么做」合并(ADR-120)，父件信息不进合并键；去向在报工交接时由工人分配。
2. **报工页的去向分配子行**：每个成品报工行下面挂「去向分配」子行，每条 = (去向：某个上层工单 或 送入仓库, 数量)。
   - 第一条默认给最急的可送上层工单，数量 = min(本行产量, 它还差的)；没有可送的就是「送入仓库」，成品行显示去向摘要，悬停写原因(2026-10-01 更新)。
   - 分完仍有余量时下面自动出现一条：默认下一个还缺的上层工单(先急后缓)，没有就送入仓库。系统给出的建议是黄框。
   - 合计始终等于本行产量：改大一条会压低下面的条目，改小则余量排到下面；工人自己改成 0 或清空的条目消失；一行只留一条「送入仓库」(合并)。产量改小时工人定过的数只被压低显示，压到 0 的条目先藏起来(不提交、不报问题)，改回来按原数恢复(逐键改产量不丢条目)。
   - 「工人要的数」与「顺带接下的余量」分开记：工人定的送入仓库一条并进余量后显示变大，但记住的只是工人自己填的数，余量每次重排重新先急后缓分配，不会把上层工单的份额长期占住。
   - 粘贴行与新建日报改勾选都触发重排(勾选行先占「还差多少」)；重排自身换行不再触发重排。
   - 候选读取失败的行提交前自动重读一次，仍失败即拦下提交(不按整行送入仓库保存)，重读成功则重排后请人核对再提交；下拉里原来选的上层工单写「候选读取失败，暂时无法核对」，不说成「不能收」。
   - 下拉按先急后缓列出可送上层工单「工单号 · 父件产品 · 还差 N」；本张报工其它行已分满的置灰「已分满」；结构上是上层但现在不能收的置灰红字写原因(跨车间、委外件、已备齐等)。工人从某条改掉的上层工单不再被自动建议(想给可以再选)。
   - 多行之间的扣减(同一上层工单共用「还差多少」，同一计划行拆出的工单共用本来源份额)只在 `daily_output_allocation.dart` 一处算，取代原来的跨行合计校验 `directTransferAggregateIssues`。
   - 默认去向不再按上次报工记忆替人选(先急后缓的次序由服务端给出)，候选接口的记忆字段与查询删除。
3. **服务端契约**：报工输入行 = 总量 + `allocations: [{directTransferDemandId | null(=送入仓库), qty}]`，单个去向/单个接收需求的旧输入字段删除(不做存量兼容)。部署前打开、没刷新的旧页面仍会在行上传 `destination` / `directTransferDemandId`：保存、追加计划预览与申请三个入口认出这两个旧字段就整单拒收(400「页面版本已更新，请刷新页面后重新填写去向」)，新旧两种形状不同时接收，绝不按新口径把旧页面想转下一道工序的量悄悄送入仓库(`DailyReportOutputAllocationService.rejectStaleRouteShape`，`ProductionDailyReportCommandTest` 钉住)。服务端回放自己存下的追加申请快照不经过这个入口。`DailyReportOutputAllocationService`：
   - 合计必须等于本行实际产量；一行最多同时转给 `RequestLimits.DAILY_REPORT_DIRECT_RECEIVERS` 个上层工单，超过明确报错，不悄悄送仓。
   - 每个生产工单只读一次 `fn_workshop_direct_targets` 列表，逐条校验并在本张报工内扣减(本来源份额按计划行、还差多少按接收需求)；不能收或超出还差的量报「无法转到下一道工序：<原因>」。
   - 直送只能出自「需求份」：公共备货与实际超产一律送入仓库(ADR-118 §3)；分给上层工单的合计超过需求份时报「本行最多 N 可以转下一道工序…」。
   - 拆出的明细：每个接收工单一条 WORKSHOP 明细(「一条明细一条接收需求」的守卫全部照旧)、需求份余下一条 WAREHOUSE 明细、公共/超产明细照旧；全部共用 `output_batch_id`、同一换算率、同一完结标记(公共明细按 V694 永不完结)。
   - 送入仓库的明细写 `output_route_reason`：`USER_CHOSEN`(还有能直送的没分满) / `RECEIVERS_FULL`(能直送的都已分满) / `PUBLIC_SHARE` / `ACTUAL_SURPLUS` / 或一个可送的都没有时最接近可送的不可转原因。文案仍只由 `fn_workshop_direct_reason_text` 给出，详情随货品身份同一条语句取回(审核返回详情不多一次往返)。
   - 追加实产批次：直送只能出自原工单那一份，追加部分一律送入仓库。追加计划的预览与批准时的回放只算数量(原计划承接多少、超出多少)，不核直送资格与分量：否则某个上层工单在申请到批准之间已备齐，批准会被一个与追加无关的直送原因拦住；直送在保存报工时按当时的判定逐条核对。
   - 幂等指纹改为 V3 并纳入去向分配(不传、空列表与整行送仓视为同一申报)。
   - 审核不重新分流(ADR-118 §3)：保存后某个上层工单不能收了，审核由同一断言报出是哪个工单。
4. **草稿编辑与审核确认**：编辑已存草稿时按 `output_batch_id` 还原成一行报工和它的固定去向(每个上层工单一条 + 送入仓库合成一条)；详情页「去向说明」列写「转给 <父件 · 工单号>」或送仓原因；审核确认框逐批列出「转给哪个工单多少；送入仓库多少(原因)」。
5. **仓库入库也先急后缓**：共享批次送仓部分入库后分给哪个来源，`PreplanAnalysisStockPegService` 由「按份额建立时间、随机 UUID」改为「所属产品行的优先级、交期、建立时间、id」，与直送同一次序(ADR-120 §3)。已直送的份额已计入实收，送仓入库只会落到还没收到的份额(例如跨车间的那一份)。采购/委外到货同样按这个次序分给各份额，到货预览(`PreplanInboundAllocationProjectionService`，仓库看「这批货归哪个产品、计划、车间、仓库」)与入库时的真实归属共用 `PreplanAnalysisStockPegService.INBOUND_ALLOCATION_ORDER` 一个次序常量(行动内的「先急后缓」部分为 `ALLOCATION_URGENCY_ORDER`，自制入库也用它)，预览不会再按份额建立时间/随机 UUID 显示与实际入库不同的去向。

### 7.3 BOM 学习不受影响 (与 V711/V737 对接)

### 7.4 考虑过的其它做法

1. **服务端「全部上层工单自动分」一个开关**：少一步操作，但工人看不到也改不了分给谁，也无法把某个急单留给下一批；用户明确要逐条可选、余量自动补行。不采用。

3. **一条直送明细对多个需求**：要改一行一需求的唯一约束与整行守卫(ADR-087 已否决行内拆量)。不采用；改为一条明细一个接收工单。

## 8. 第三步：一张报工多块直送的审核提速 (2026-09-27)

### 8.1 背景与实测

共享批次一次报工分给 11 个上层工单(§7 的 HV5G001 场景)，审核就是一笔事务里办 11 块直送。服务端事务上限 40 秒、客户端 45 秒放弃等待([ADR-107](ADR-107-履约预锁一轮发现与服务端截止时间.md))，超时整单回滚。

量法沿用「复制 E2E 夹具做探针」：共享子件 → 1/3/11 个同车间上层工单，每块 1，只对「审核」那一笔计量(`ProductionJdbcMeasurement` 语句数 + 墙钟)，另按服务方法归集语句与耗时、用 `pg_stat_user_functions`(track_functions=all)按库函数归集、用 `auto_explain` 看计划。改前(本机负载较轻时)：

| 块数 | 墙钟 | 语句 | JDBC | 提交 |
| --- | --- | --- | --- | --- |
| 1 | 2.5s | 464 | 1.8s | 0.4s |
| 3 | 6.5s | 1054 | 4.9s | 1.0s |
| 11 | 37.4s | 3414 | 29.4s | 5.7s |

语句数随块数线性(每块约 295 条)，时间却接近平方，而且负载一高就成倍放大(同机重负载时 11 块 54-387 秒)。剖面给出的原因都在库函数里，不在单据张数：

1. **关系判定被下推、平方次求值**。`fn_workshop_direct_source_available` / `fn_workshop_direct_covered_base_qty` 把 `fn_workshop_direct_relationship_allows(lot.producing_segment_id, demand.id)` 与「这批料投给哪条需求」并列写在同一层条件里，规划器把判定下推到「同货品的全部报工明细」上逐条先算、再按需求过滤。分给 N 个上层工单就有 N 条同货品明细，每查一次可用量都要把 N 条关系全判一遍：11 块一次审核 1661 次关系判定，单次可用量查询约 400ms(每块 3 次，每次为线边仓行算三遍)。
2. **SQL 函数反复规划**。合格来源证明 `fn_preplan_reservation_has_qualified_origin`、V715 前的直送责任证明、两个公共产出判定、线边仓料是否指名给需求，都是 LANGUAGE sql 的大查询。PostgreSQL 16 不缓存这种函数的计划：外层每条语句(以及从别的函数里每调一次)都要把函数体重新规划。克隆库实测合格来源证明单次调用 63-150ms、同一语句里调 30 次也只要 76ms——几乎全是规划，执行不到 1ms。审核里调它几百次。
3. 合格来源证明 MAKE 分支的通用计划先按车间段扫它的全部入库行、逐行判是否公共产出，再按主键过滤，入库行越多越慢。

### 8.2 决策

1. **库函数(V736 第 9、10 节；只换求值方式，结果逐条不变)**：
   - `fn_workshop_direct_source_available`、`fn_workshop_direct_covered_base_qty`：先按接收需求(与线边仓、货品)取出直送批并物化，再对出现的每个生产工单只判一次关系。同一视图、同一判定、同一求和。
   - 这两个 + 五个 LANGUAGE sql 函数(`fn_preplan_reservation_has_qualified_origin`、`fn_workshop_direct_responsibility_allows_before_v715`、`fn_finished_in_is_public_output`、`fn_daily_report_is_public_output`、`fn_line_side_stock_targets_demand`)改为 plpgsql 的 `RETURN (原查询)`：五个的查询文本在迁移里从现有定义原样取出并断言形状(不手抄)，名称、参数名、返回值、STABLE/STRICT 不变。
   - 函数上固定 `plan_cache_mode = force_generic_plan`：与原 SQL 函数一样按「参数未知」规划(计划形状与改前相同)，只是同一数据库连接内只规划一次。不固定的话 plpgsql 会因「带参数值的计划估价更低」而一直按调用重新规划，等于没改(实测合格来源证明仍要几十到几百毫秒一次)。
   - 合格来源证明加三处「先按主键取驱动行」的 `OFFSET 0` 围栏：按预留取它自己的权益事件、按事件指向的入库行(或到货检验入库行)取那一行，再比对其余条件。条件本来就要求这些主键相等，所以结果不变。
2. **审核仍逐块办**(`ProductionWorkshopDirectTransferService.executeForApprovedReport`)：每块校验、写直送明细、班组自检入线边仓、投给自己的上层工单，办完一块再办下一块。应用层只收一处：线边仓只由 (车间, 收料主仓) 决定，同一次审核里各块共用，不再每块重走一遍查找/配置。
3. **试过、实测更慢而撤回的「按线边位置合成一张入库单」**：按原计划把同一轮、同一线边位置、同一计划行的各块合成一张多行入库单一次点收，再逐个投料(接收侧仍一个工单一张线边仓领料单；同一接收工单的第二块排到下一轮)。语句确实少了(11 块 3415→2946)，但同一次运行里交替实测：逐块 15.2s/18.1s，合单 31.5s/28.2s。原因：合单让各块在投料前同时进了线边仓，后面每个上层工单投料时的可用量查询、成品入库的权益归属与优先级调整都要把「还没投出去的各块」再过一遍，又回到随块数平方增长(可用量查询 33 次共 1.8s→7.4s)。所以不合单，放行端口、班组自检与成品入库草稿的「并入同一张单」改动全部撤回。`FinishedInboundBatchContext` 对线边仓入库只省一次仓库范围校验(线边仓入库本就跳过分析唤醒与就绪提升，[ADR-089](ADR-089-车间直送v2持续生产与线边仓自动配置.md) §2.5)，也不接。
4. **不动的**：每块一条直送明细、一条班组自检(检验、决定、放行命令一块一份)、一张线边仓入库单、接收工单一张线边仓领料单；全部数据库守卫、成本产出逐块逐移动、领料过账按接收需求；BOM 学习口径(§7.3)不受影响。

### 8.3 实测(改后)

同一次运行里把第 9、10 节的函数换回旧定义交替实测(同一负载；这几次运行时本机同时跑着十几个别的测试容器，绝对值比平时大数倍，看同一行的比值)：

| 运行 | 块数 | 旧函数 | 新函数 | 语句 |
| --- | --- | --- | --- | --- |
| A(重负载) | 1 / 3 / 11 | 5.3s / 8.1s / 54.4s、68.1s | 4.0s / 5.9s / 21.2s、24.2s | 465 / 1053 / 3405 |
| B(极重负载，加固定通用计划后) | 3 / 11 | 24.2s / 197.6s | 15.7s / 77.3s、67.5s | 1053 / 3405 |
| C(中等负载，最终代码) | 3 / 11 | 6.0s、9.0s / 38.5s | 3.7s、4.7s / 13.0s | 1053 / 3405 |

最终代码在 C 运行里 11 块 13.0s(JDBC 9.9s、提交 1.8s，旧函数同一次运行 38.5s)，已在 15 秒以内但余量不大：剩下的时间摊在 3405 条语句上(平均约 3ms 一条)，只有投料时的可用量查询(33 次共 1.5s)还算单条偏慢。11 块时关系判定 1661 次→231 次(每块 21 次，线性)；上层工单领料前「按分析权益找合格来源」一次 347ms→13-34ms。语句数改前改后几乎相同(每块约 295 条，线性)。

常驻用例钉住语句数：一块 450 条(`oneDirectTransferApproveStaysInsideItsStatementBudget`)、三块 1080 条以内(`threeReceiverApproveStaysInsideItsStatementBudget`)。时间受机器负载影响大，不做断言，由探针另量。

再往下压要减语句条数：每块约 295 条里，接收侧投料(就绪提升、权益转交、线边仓领料单审核出库)约 145 条、线边仓入库确认与入账约 120 条，都是库存/成本/权益的通用链路，属于另一轮重设计。物料分析侧用到这些函数的夹具步骤(汇总下单、下达计划)新旧函数交替实测互有快慢(±30%，噪声内)，没有看到稳定的变慢。
