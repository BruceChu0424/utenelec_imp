## 1. 背景

2026-09-09 用户定的口径是「清空业务数据 = 连上传的文件一并清空」。2026-10-01 为了永久保留记录，V782 把这件事改造成「签名意图票据 + 精确物理完成证明」：每个测试文件先由应用签发 HMAC 意图，删完写完成证明，数据库在清空时断言每个文件都有本代证明。之后连续三次清空失败，报的都是 409：

| 时间(+08) | 环境 | 报错与原因 |
|---|---|---|
| 10-02 12:02-12:47 | 本机 | 「无业务来源的旧对象任务需要先对账 ×1」。挡路的是货品成本导入的暂存删除任务。当时用 V783 把这类主档暂存任务列为受保护对象，没有改规则本身 |
| 10-04 02:02 | 本机 | 同一句话。挡路的是 AI 识别留下的暂存删除任务。修复提交 275a42bd9 只改了另一个函数，之后靠「先分批清理附件」再清空才成功，属于绕过 |
| 10-05 13:37 | 测试服务器 v2.3.0 | 同一句话，3 次。10-04 10:00 的一次 AI 识别又留下一张自带的暂存删除任务 |

根因有两层：

1. **直接原因**：清空前的预检规则对「自带清理任务」永远判失败。AI 识别原件、未采用的报价模板候选、货品成本导入都会写一张不挂附件、也不挂上传会话的暂存删除任务。视图把它的属主算成 UNKNOWN、位置算成 STAGING，而它对应的原件登记在正式区，所以规则里「同一位置有业务文件」永远对不上。
2. **结构原因**：「哪些文件挡路」有 5 份独立规则，而且互相矛盾：Java 预检 `blockers()`、Java 校验 `requireSource()`、数据库的证明断言、V549 的 `fn_business_attachment_reset_blockers()` 加 outbox 检查、弹窗预览。弹窗说「检测到 N 项，将随本次清空一并删除」，正是这 N 项随后被预检拒掉。以往每次修复只改了其中一份。全仓也没有任何测试把「真实 AI 识别 → 真实清空」串起来跑，服务层测试把整个附件清理接口 mock 掉了。

用户 2026-10-05 的决定：

1. 根治(方案 B)。服务端只用**一条规则**决定「哪些物理文件属于测试业务数据」，弹窗预览、排水前检查、删除循环、数据库内复核都用它，不可能再互相打架。物理删除可以重复执行：删除后确认不在；本来就不在也算成功；中途失败可以直接重试。不要签名意图票据，也不要按清空代数围住的认领机制(清空代数 `business_reset_generation` 本身保留，AI 调用日志的迟到围栏还在用)。所有拒绝条件合并成一处服务端检查，在排水之前、删除任何文件之前运行，并在 `business_data_reset()` 里再跑一次。
2. 删除停机 psql 脚本 `server/ops/reset_business_data.sql` 及其契约测试和同步点。工作台是唯一的清空入口。
3. 删除「先分批清理附件(可选)」整条路径(接口、服务、Flutter 按钮、弹窗、仓库调用、测试)和端口里的死方法。

## 2. 决策

### 2.1 一条对象规则(D1)

新函数 `public.fn_business_test_reset_objects()` 一行代表一个需要「确认不在」的物理对象，是唯一的对象清单。

- **来源**：非主档业务附件(正式文件)；非主档上传会话(暂存副本和正式文件各算一处)；AI 识别原件；报价模板候选及其历史；以及不受主档保护的删除任务，不论状态。已经成功的删除任务也列出来，只是核对时「不在 = 成功」，行本身随清空清除。
- **受保护对象不列出**：沿用 V783 的 `fn_business_test_object_protected()`，不改。人事档案、人事合同、货品的附件和上传会话，已采用的报价模板版本，货品成本导入原件(含 `legacy_unknown` 存储)都不会出现在清单里，也就永远不会被删。
- **物理身份**：internal 和 local 存储一个编号只放一个文件，身份是 `(存储, 位置, 编号)`，不带版本。登记版本只作为核对属性 `registered_versions`，只收 internal 正式区的版本。保护判定用 NULL 版本调用，这是 V783 的最宽口径：同一编号上只要有任何主档行(不论登记的是什么版本)，就保护。其它存储(oss、legacy_unknown、未登记)保留带版本的身份。
- **一个物理对象只出现一次**：业务附件和它的上传会话共用同一个正式文件时只算一行，预览计数和删除计数都不会重复。
- **只输出元数据**：不返回原件字节、候选工作簿或载荷。
- **显示名在 SQL 里生成一次**：`「文件名」(业务附件|上传会话|AI识别原件|报价模板候选|删除任务, 正式文件|暂存副本)`；没有文件名时显示 `「未登记文件名, 存储编号 …」`。同一个编号的暂存副本沿用正式文件的名称和类别，所以 AI 识别的暂存删除任务显示为「AI识别原件, 暂存副本」，不再是看不懂的「文件删除任务」。
- **`recorded_absent`**：同存储、同位置、同编号(带版本身份时还要同版本)已经有一条 `SUCCEEDED` 且有完成时间的删除记录，表示「登记已删除」。它只在「系统删不了这种存储」或「这台服务器没配置这种存储」时用来跳过核对(D10)。

`fn_business_test_reset_object_fingerprint()` 把清单按规范化身份排序后求 sha256，格式 `条数:摘要`，登记版本也算进去。它只用来做并发和完整性自检，**不是身份认证**(第 3 节)。

### 2.2 文件在不在由存储实地判断，删除可重复执行(D2、D3)

- 给 `StorageService` 加只读文件头的 `inspectObject(位置, 编号)`，internal 和 local 两种存储实现，其它存储不实现。不读正文，不算摘要，也没有旧方案的 15MB 上限。
- 判定结果分五类：不在；在(带实地版本)；存储根目录或分区不可用(`StorageResourceUnavailableException`，**绝不当成「不在」**)；本地旧版平铺布局(`StorageLegacyLayoutException`)；位置上有东西但不是本系统写入的文件或读不了(`StorageObjectProblem`，分为不是普通文件、文件头无法识别、无权读取、读取出错)。核对途中被并发删掉按「不在」处理。
- internal 正式区：登记版本非空且**任何一个**和实地版本不同 → 拒绝，一个都不删(文件被替换过)。其余情况按实地版本删除。暂存区和 local 不比版本。
- 删除用原有的 `delete` / `deleteStaging`，它们对「不在」本来就返回成功。删完再读一次文件头，确认不在才计数。重试时已经删掉的文件只多花一次 stat。

### 2.3 一个拒绝检查，三次调用(D6)

数据库能判断的拒绝条件只有 `fn_business_data_reset_refusals()` 一处，直接返回分好组、可以展示的完整文案，Java 不改写；只有配置和存储才能判断的放在 Java 的同一个 `check()` 里。三次调用时机：

1. 弹窗预览 `GET /api/system-test/business-data/preview` 和排水前检查，共用 `BusinessTestResetFilesPort.check()`；
2. 清空事务里加锁之后、删除任何文件之前(`purge()`)；
3. `business_data_reset()` 的第一步(锚点补丁 E2)。

调用身份检查(`fn_require_runtime_maintenance(true)`，即运行账号或清空属主成员、保留临时表名、在职超管审计身份)也提前到排水前，由 DEFINER 小函数 `fn_business_test_reset_require_caller()` 执行。

实现细节：

- 只要有规则 30-35(程序版本问题)，就不做存储核对：`inspectionSkipped=true`、`inspectionComplete=false`，计数都是 0，弹窗不说「文件较多」。其它拒绝照样做核对，用户一次就能看到所有能自己处理的问题。
- 锁内核对时，只要已经知道原因(数据库规则、服务器配置或已核对部分发现的存储问题)，就报这些原因；只有没有任何原因、核对又没做完时才报 C5「核对用完时间」。
- 检查阶段读数据库出错(调用身份、拒绝函数、对象清单、指纹)：等锁超时报 C6；`57014` 或超时报「读取测试文件清单时数据库超时…请稍后点「重新检查」再清空」(409)；其它报「读取测试文件清单时数据库出错…」(500，原话只写服务端日志)。这时一个文件都没删。
- 存储核对的拒绝每类一条，原因码和数量分开保留；拼成整段文字时共用一个开头句「以下测试文件现在无法确认或无法删除，本次没有删除任何文件，也没有清空数据：」。
- 核对有时间上限：预览 20 秒，排水前最多 60 秒。核不完的部分不拒绝，留到清空事务里在删除之前全量核对。
- 「附件读写繁忙」先按 200 毫秒间隔重试 3 次再算存储不可用。
- 文案里不出现异常类名，类名和存储编号前 8 位只写进服务端日志。

旧的拒绝条件处置：

- 「无业务来源的旧对象任务需要先对账」(根因)、`requireSource`、确认指纹、票据核对、意图函数、证明断言、附件守卫的「未证明」、意图表守卫、可选准备入口：**全部删除**。
- outbox 检查原来在文件删完之后才跑，现在在删文件之前判断，锁内再判一次。
- 目录检查和调用身份检查前移到删文件之前。
- 内容、大小、超限、缺版本的检查改为 B3/B4/B5/B6。
- 40 秒事务、应用和数据库时钟不一致、「无进展」这三类问题随机制一起消失：现在是显式超时的清空事务，时间只用数据库时钟和 JVM 截止点，没有轮次。

### 2.4 删除和清空在同一事务、同一把锁下完成(D4)

清空事务(REQUIRES_NEW、READ COMMITTED、30 分钟)按顺序做：

1. 绑定审计身份；设 `lock_timeout`(默认 15 秒，用绑定参数传入)、`statement_timeout=30min`、`idle_in_transaction_session_timeout=30min`。删除文件期间连接在事务里空闲，会话默认的 120 秒空闲上限会杀掉连接，所以要单独放宽。
2. `fn_business_test_reset_lock_sources()`(DEFINER)对 9 张来源表加 EXCLUSIVE 锁：附件、上传会话、附件删除任务、AI 识别原件、报价模板候选及历史、模板版本、货品成本导入、`business_outbox`。EXCLUSIVE 挡住写入和 `SELECT … FOR UPDATE/SHARE`，普通 SELECT(健康检查)照常。没有用 SHARE ROW EXCLUSIVE，是因为模板采用流程先 `FOR UPDATE` 读候选再插版本行，SHARE ROW EXCLUSIVE 和它不冲突，会留下「先读后插」的窗口。
3. 锁内读拒绝原因、对象清单、指纹和死信计数，按同一套代码全量核对。有任何拒绝或核对问题就抛出，这时**一个文件都还没删**。
4. 逐个删除并确认不在。
5. `set_config('app.business_test_reset_objects', 指纹, true)`，然后调 `business_data_reset()`。函数第一步再跑拒绝函数；`fn_clear_business_test_object_metadata()` 再调一次同一把锁(同一事务内不冲突)，由 `fn_business_test_reset_verify_purged()` 重算指纹：不一致就 `UT901`；一致才设「本事务已复核」标记，删除登记行，继续原有的清空流程。
6. 完成回执和清空一起提交(ADR-067 §8)。

直接调用 `business_data_reset()`(没有传指纹)时，清单必须为空才能通过，否则报 `UT901`「还有 n 个测试文件没有删除……」。附件表的删除守卫 `fn_attachment_retained_identity_guard()` 改为要求「本事务已复核」标记，不再查证明。

### 2.5 删除签名意图票据整套机制(D5)

数据库删除 1 张表(`business_test_object_cleanup_intents`，连同 2 个触发器和索引)、1 个视图(`v_business_test_object_sources`)、9 个函数：意图链 8 个(`fn_business_test_object_sources`、`fn_test_object_require_actor`、`fn_test_object_lock_sources`、`fn_test_object_prepare`、`fn_test_object_claim`、`fn_test_object_complete`、`fn_test_object_intent_guard`、`fn_assert_business_test_objects_cleared`)，以及 V549 的 `fn_business_attachment_reset_blockers`。

Java 删除 `BusinessTestObjectCleanup`、`BusinessTestObjectSignature`(HMAC)、`BusinessAttachmentResetPreparation`、`BusinessAttachmentResetPreparationService`、`BusinessAttachmentResetPreparationPort`、控制器的分批清理接口和旧附件预览接口，以及 `AttachmentObjectOutboxStore.enqueueResetVerification`。`CryptoProperties.hmacKey` 的其它使用者不受影响。

保留不动：`fn_business_test_reset_active()` 及 V782 注入的 5 个不可变守卫和 4 个历史捕获函数(V792 的重新报价围栏也依赖它)；`business_reset_generation` 及其守卫，每次清空照样 +1(AI 调用日志迟到围栏依赖它)；V783 的 `fn_business_test_object_protected()`；`fn_require_runtime_maintenance()`。

### 2.6 分类只有一个家，停机脚本删除(D11、D13)

- 每张表清空时是 CLEAR 还是 PRESERVE，只写在 `business_data_reset()` 函数体的 VALUES 清单里。以后的迁移照旧按锚点追加或删除分类行。
- `fn_business_reset_table_policy()` 是这份清单的只读视图，用与 `BusinessDataResetSqlContractTest.POLICY_ROW` 字面相同的正则解析函数定义。函数体里加了一条断言(锚点补丁 E4)：解析结果必须等于实际执行的清单，否则 `XX000` 整体回滚。
- 「每张表都已分类」由两处把关：运行时由拒绝规则 30-35 在删文件前失败关闭；CI 由库测试 `BusinessDataResetCatalogPostgresTest` 核对「安装后的函数 = 评审神谕 `expectedCurrentPolicy()`」。神谕由冻结的 V464 加登记的增删推导。
- 停机脚本 `server/ops/reset_business_data.sql`(914 行)及 `ResetBusinessDataScriptContractTest`、`ResetBusinessDataV446PostgresTest`、`src/test/resources/test-reset/*.sql` 删除。它的版本白名单只登记到 V794，服务器 V797 上本来就用不了，而且它删不了物理文件。

### 2.7 `business_data_reset()` 用锚点补丁修改(D12)

V798 读取已安装的函数定义，逐条编辑后 `EXECUTE`，不整函数重发。每条编辑的锚点必须恰好出现预期次数，否则报错并点名是哪一条(E1-E9)：

- E1：DECLARE 里只给旧检查用的 6 个变量，换成一个 `refusal_text`。
- E2：入口先跑拒绝函数，有原因就 `UT900`，然后再调 `fn_clear`。
- E3：去掉意图表的分类行。
- E4：分类解析一致性断言。
- E5 / E6 / E7：删除旧的前置拒绝和目录检查、TRUNCATE 权检查、范围外引用检查三段。
- E8：保留回执只认 `business_data_reset`、`business_data_reset_received`、`business_data_reset_failed` 三种动作。另外三种动作不会再产生，旧行随下次清空的历史审计一起清除。
- E9：两处提到 psql 版的注释改写。

同一个 DO 块里还比对补丁前后的分类：只允许少掉意图表那一行，其它有任何不同就报错。收尾自检确认函数仍是 SECURITY DEFINER，`search_path` 和属主不变；被删对象都不存在；`public` 下任何函数体都不再引用它们。

两个整体替换的函数(`fn_clear_business_test_object_metadata`、`fn_attachment_retained_identity_guard`)替换前先比对已安装函数体的 md5(去掉 CR 后：`73195ce907a32825dea7923b838e6b21`、`e8b80397f53496ba32613a22040a7fa1`，取自全新库迁到 V797 的实测值)。不一致说明别的迁移改过它们，迁移失败关闭并同时报出期望值和实际值。

这样做的好处：别的分支对这个函数的任何改动(分类行或逻辑)都会被保留。只有它们改了 E1-E9 的锚点文字或这两个小函数时，V798 才会失败，并且会点名。

### 2.8 只有一个截止点(D15)

- 受理时刻 + 5 分钟是文件阶段唯一的截止点，覆盖排水前检查(实地核对最多 60 秒)、排水(最多 45 秒)、清空事务里的加锁、核对和删除。
- 清空函数本身还有 `statement_timeout` 30 分钟、每把锁最多等 15 秒。
- 网关只对 `location = /api/system-test/business-data/reset` 放宽到 600 秒，Flutter 接收超时 10 分钟。文件阶段最多 300 秒，清库至少还剩 300 秒。如果清库超出这个时间，网关会断开连接，但服务端会继续执行到底，结果由 ADR-067 §8、§9 的回执确定，客户端不会重放。
- 预览的实地核对最多 20 秒，快照事务 `statement_timeout=30s`、`lock_timeout=5s`，在通用 `/api/` 的 45 秒网关上限以内。
- 默认值在 `BusinessDataResetTimings.DEFAULT = (5 分钟, 60 秒, 20 秒, 45 秒, 15 秒)`，测试可以传入更短的值。

### 2.9 删掉文件之后的失败要说实话；回执不留文件名(D16、D17)

- 删除调用一返回就计数(在复读确认之前)。复读确认失败(存储繁忙先重试 3 次)报 C7「已删除…但删除后无法再次核对」，这个文件算已删除；复读发现文件还在报 C3，这个文件不计数。
- 只要已经物理删除至少 1 个文件，之后的**任何**失败(删除报错、删完仍在、时间用完、清空函数拒绝、锁超时、数据库错误)都以这句话开头：「本次已经物理删除了 d 个测试文件(无法恢复)，但业务数据没有清空，所以这些测试单据上的附件现在打不开。」接着是原因，最后是「已删除的文件下次不会重复处理。」
- 失败回执记录 `deleted_attachment_files=d`。`GET /business-data/last-result?attemptId=` 返回 `attemptDeletedAttachmentFiles`，工作台据此显示「上次清空没有完成：…(已物理删除 d 个测试文件，数据没有清空)」。
- 一个文件都没删时，以「原因：」开头的文案前面补「清空没有完成，业务数据没有清空。」。
- 提交确认丢失的不确定结果仍然不写失败回执(ADR-067 §8)。已删过文件时，文案末尾追加已删数。
- 清空事务回调内的任何错误都映射为「已整体回滚」。只有提交那一步抛出的异常才算「结果不确定」。
- 失败回执格式：`failed,code=<错误码>,deleted_attachment_files=<d>,reasons=<原因码:数量;…最多 6 项>,message=<摘要>`，总长不超过 480 字。摘要由原因标签拼成，**不含文件名**，例如「失败原因：后台事件排队中 3 条；文件版本对不上 2 个。没有删除文件，也没有清空数据。完整原因(含文件名)请在清空弹窗点「重新检查」查看。」。含文件名的完整文案只出现在 HTTP 响应和弹窗里。旧格式的回执照样能解析。
- 数据库执行失败(DB_FAILED)、清单不一致(OBJECT_SET_CHANGED)、数据库账号无权(CALLER_NOT_AUTHORIZED)、临时表名被占用(CALLER_NAMESPACE)这四类在「重新检查」里看不到，原文也不含文件名：摘要直接写原文的原因部分，结尾给对应的下一步(数据库执行失败「请稍后重新点「确认清空」；如果再次出现，请联系开发人员。」；清单不一致「请联系开发人员。」；两类配置问题「再次提交也会失败，请…处理后再清空。」)，不再指向「重新检查」。例如「失败原因：业务数据清空执行失败，已整体回滚：{原话}。本次已物理删除 2 个测试文件，数据没有清空。请稍后重新点「确认清空」；如果再次出现，请联系开发人员。」。
- 成功回执增加 `dead_events_cleared=<k>`，`Result` 和上次结果增加 `deadBackgroundEventsCleared`。

### 2.10 死信、上传凭证、受保护删除任务和存储豁免(D7、D8、D9、D10)

用户拍板的是把所有拒绝条件**合并**成一处检查。D7-D9 三条起初按设计默认放宽，评审指出放宽没有经过用户同意，2026-10-05 交付前请用户逐条确认，结果如下(D9 因此改回拒绝，新增规则 15/16)。

**用户 2026-10-05 确认：D7 死信随清空清除并报条数；D8 未到期上传凭证不挡；D9 受保护未完成删除任务继续挡住。**

- **D7 死信不挡清空**(用户确认)。`business_outbox` 里 status 0(排队或退避中)的事件仍然拒绝，等几分钟就能拿到准确的处理结果。status 2(连续 8 次失败后的死信)不再拒绝：应用里没有任何入口能让死信重新处理，挡住清空就等于永远清不了。死信随清空清除，预览和结果按类别报条数。会受影响的派生值只有货品单重估算，每晚 02:13 的单重刷新会按观测记录补算(弹窗会提示)；来料检验不合格转财务写的是测试数据，本来就随清空清除。
- **D8 未到期的上传凭证不挡清空**(用户确认)。前提是附件存储为 internal 或 local：上传字节必须经过 `PUT /api/attachments/raw/{key}`，并且要求该编号有 PENDING 会话。排水期间 `/api` 一律回 503，清空后会话行被删，凭证也就作废。附件存储是 oss 直传时由 J1 直接拒绝，这个前提由代码保证。
- **D9 受保护的未完成删除任务继续挡住**(用户否决了放宽，规则 15/16)。这类任务处理的是要保留的文件：货品成本导入原件和已采用报价模板的暂存副本，以及货品、员工档案附件同一编号上的任务。清空按 V783 规则保留这些任务行，所以要等普通删除队列把它们处理完再清空。规则只数清空会保留的行(没有业务属主，且按任务自己的版本受保护，与 `fn_clear_business_test_object_metadata()` 的保留条件逐字相同)；属于业务附件的任务、只按编号受保护但版本不同的任务都随清空清除，不挡。
  - 删除队列的状态(`AttachmentObjectOutboxProcessor`)：PENDING、FAILED 到 `available_at` 就再处理；失败后等 2 的 attempts 次方秒，最长 1024 秒(约 17 分钟)，**没有终止状态，会一直重试**；PROCESSING 领取 15 分钟后没完成会被重新领取(`stale-processing-minutes`)；失败满 5 次(`alert-after-attempts`)日志报「需要人工关注」；SUCCEEDED、RETAINED_HISTORY 是终态。
  - 规则 15「还在处理」：PENDING、PROCESSING(有领取时间)、失败不到 5 次的 FAILED。文案给出约几分钟：取最晚的 `available_at`，处理中的取领取时间 + 15 分钟，至少 1 分钟；下一步「请 N 分钟后点「重新检查」；如果到时仍没有完成，请联系开发人员」。
  - 规则 16「卡住了」：失败至少 5 次的 FAILED(虽然还会重试，但连续失败说明不会自己恢复)，以及处理记录不完整、后台不会再领取的行(PROCESSING 没有领取时间，或已完成状态没有完成时间)。下一步「请联系开发人员查明这些删除任务为什么没有完成(服务器日志里有失败原因)并处理，处理完后点「重新检查」」。
  - 文案列出任务数和最多 5 个文件名(按货品成本导入、已采用的报价模板、货品档案附件、员工档案附件的顺序找名字)；员工档案文件只显示存储编号，不显示文件名。
- **D10 存储豁免**。不支持的存储(oss、legacy_unknown、未登记)由规则 20 拒绝，**除非**该对象已经「登记已删除」。internal / local 在这台服务器上没配置时也一样：「登记已删除」的跳过，其余报 B2 / B2b。

### 2.11 入口与门禁

- 门禁按顺序：运行开关(云端一律关闭；内网服务器测试期开启) → 超管本人(数据库确认在职、未删除、账号与 id 一致，预览和清空都查) → 模拟他人身份时预览和清空都拒绝 → 目录码 `system:business_data_reset` 和再认证(只针对清空) → 口令「清空业务数据」 → 排水闸。
- 另一位超管的清空正在进行时，预览和清空都立即 409 E1a，**不写受理回执**，客户端可以据此撤销本地待确认记录。它和「在途请求 45 秒没结束」(E1b)分开报。`BusinessDataResetDrainGate.beginDrain` 返回 `STARTED / ANOTHER_RESET / IN_FLIGHT_TIMEOUT` 三种结果。
- 检查时的锁超时(55P03)如果正好碰上另一次清空，也按 E1a 报。
- 排水豁免只剩清空接口本身；预览接口在排水期间回 503。
- 数据库返回的 42501 按原话映射：不是在职超管审计身份 → 403 F2(`FORBIDDEN`)；数据库账号无权 → 500 F3；保留临时表名被占用 → 500 F4。F3、F4 的错误码是 `RESET_SERVER_MISCONFIGURED`(再试也一样，要开发人员或维护人员处理；弹窗按 FORBIDDEN 同样处理：显示原话、禁用确认)。
- 错误码与 HTTP 状态：只有提交那一步抛出的异常是 `RESET_OUTCOME_UNCERTAIN`(500，结果不确定，客户端按「待确认」处理、不重放)；其它 500(`INTERNAL`：数据库执行失败、读取清单出错、核对操作人出错、等待时被中断、受理回执写不进去)都是明确失败，已整体回滚，原文照样显示。响应体 `{code, message}` 的 `code` 是错误码名称。

## 3. 信任边界(取代 doc 41「执行与失败处理」末段)

- 取清单、算指纹、核对、删除、清空都在**同一事务、同一把锁**下完成。这期间任何会话都不能新增或修改这 9 张表的行，也不能用 `FOR UPDATE` 读候选去完成模板采用。所以「删掉的集合」就是「数据库清除登记的集合」，指纹相等只是对这一点的自检；不相等只可能是程序缺陷。
- 指纹只用来做并发和完整性校验，**不是身份认证**。旧方案里数据库也从来没有验证过物理删除：doc 41 自己写明 SQL 端不持签名密钥，不能验证 HMAC。
- 残余风险：持有运行库账号、又能冒用在职超管审计身份的人，可以自己算指纹，然后直接调 `business_data_reset()`。结果是数据清掉、文件没删(留下孤儿测试文件，受保护文件不受影响)；或者先写入伪造的业务登记行，诱导应用去删内部存储里没受保护的对象。编号格式校验能挡住路径穿越(internal 的编号正则、local 的目录前缀检查)。这个操作只用于测试，受运行开关控制，限超管本人并要求再认证；能做到上面这些的人已经拿到运行库写权限，本来就能直接改业务数据。所以这个风险可以接受。
- 权限：先对运行角色 `uten` 撤销 `verify_purged` 和 `fn_clear` 并授予六个运行函数，再对 PUBLIC 撤销 7 个新函数，最后给清空属主授予全部执行权(含 `fn_clear`)。顺序沿用 V782，清空属主就是 `uten` 时也不会因为「先授后撤」失去它要调用的两个函数；这是防御性写法，因为 V625 起 `business_data_reset()` 不能归不是超级用户的 `uten` 所有(迁移会失败)，超级用户又不受权限检查约束。运行角色 `uten` 只获得 objects、fingerprint、policy、refusals、require_caller、lock_sources 六个函数的执行权；应用以 `uten` 身份执行的 INVOKER 读取(拒绝函数、对象清单、指纹)依赖部署加固脚本对全部表的 SELECT 授权，同一个测试按加固脚本授权后以 `uten` 跑完整的检查、加锁删除和清空。`verify_purged` 和 `fn_clear` 显式对 `uten` 撤销，因为生产上的默认授权会自动授出，部署加固脚本里的一揽子授权也会授出。即使 `uten` 拿到执行权，这两个函数也要求「清空上下文」(当前角色是清空属主或数据库超级用户)，直接调用只会报 42501。

## 4. 收敛论证

- 重试时，已删除的对象只花一次 stat(没有文件头可读)。删除阶段每删一个，待删对象就永久少一个。只要核对阶段在截止点前完成，每次重试都有进展，最终一定能清完。
- 时间不够删完(C4)时，已删部分如实报出，用户再点一次就会接着删剩下的。测试 `deleteBudgetLeavesAnHonestPartialResultAndTheRetryConverges` 验证：两次删除数之和等于最初仍在的文件数。
- 核对阶段本身超时(C5)只会在对象数量超过「剩余时间 ÷ 单个核对耗时」时发生。本地盘按每个 1 毫秒以内估算，3 分钟以上的预算对应约 18 万个文件。这时重试不会收敛，所以 C5 文案说明数量超限、请联系开发人员，而不是只叫用户重试。

**回执摘要标签**(不含文件名)：后台事件排队中 n 条；保留文件的删除任务未完成 n 个；保留文件的删除任务卡住 n 个；登录状态记录缺失(程序缺陷)；存储编号格式不对 n 个；删除后无法再次核对；读取文件清单超时；读取文件清单时数据库出错；核对操作人时数据库出错；n 个文件在系统删不了的存储；程序版本问题(数据表登记)；附件存储是阿里云直传；存储目录无法访问(n 个文件)；服务器没配置文件所在的存储(n 个文件)；文件版本对不上 n 个；存储位置上不是系统文件 n 个；本地旧版平铺文件 n 个；读文件失败 n 个；删除文件失败；删除用完时间；核对用完时间；数据被其他程序占用；文件清单不一致(程序缺陷)；数据库拒绝清空；数据库执行失败；其他操作未结束；等待其他操作时被中断；另一位超级管理员正在清空；操作人不是在职超级管理员本人；服务器连接数据库的账号无权清空(服务器配置问题)；数据库里有与清空程序内部临时表同名的数据表；其它原因。DB_FAILED、OBJECT_SET_CHANGED、CALLER_* 在摘要里写原文的原因部分(见 2.9)。

**弹窗**(Flutter，见 [工作台首页 §十](../03-页面/工作台首页.md))：

- 核对中：「正在核对测试文件…」。
- 有拒绝原因：「现在不能清空，原因如下：」加每条服务器原文(可复制)，确认按钮禁用。
- 文件计数：「将一并物理删除测试文件：{类别 份数…}(共 n 个存储位置：p 个文件还在存储里，将被删除；a 个已经不在)。人事档案/合同、货品图片/图纸、成本导入原件和已采用的报价模板不会删除。」`inspectionSkipped=true` 时括号改为「(共 n 个存储位置；这次没有核对它们是否还在存储里，先处理上面的问题，再点「重新检查」核对)」，不报还在/不在的个数。
- 死信：「另有 k 条处理失败、已停止重试的后台事件会一并清除(…)。」
- 核对不完：「文件较多，预先只核对了 c / n 个；…」。`inspectionSkipped=true`(有清空分类问题，根本没核对)时不显示这一行。
- 全部不在：醒目黄色提醒(不禁用)。
- 预览被 `FORBIDDEN` 或 `RESET_SERVER_MISCONFIGURED` 拒绝：显示服务器原话，确认按钮禁用(清空会以同样原因失败)。其它预览失败：「无法预先核对测试文件(…)。清空时服务器会再次核对，仍可提交。」
- 每次核对后都有「重新检查」。
- 提交被明确拒绝后，弹「清空失败」提示，服务器原文留在弹窗里(「本次清空没有完成，服务器的说明：」，可复制)，并自动重新检查。
- 明确失败和结果待确认的分界(`isBusinessDataResetOutcomeUncertain`)：带统一错误码的响应都是明确失败，包括 500 `INTERNAL`(例如带 W 前缀的数据库执行失败)和 `RESET_SERVER_MISCONFIGURED`，原文照登，撤销本地待确认记录，可以再次提交。只有连接中断或超时、没有统一错误码的 5xx(网关错误页、框架默认错误页)、`SESSION_*`、`RESET_PENDING_CONFIRMATION` 和 `RESET_OUTCOME_UNCERTAIN` 按「结果待确认」处理，不允许再次提交，等回执确定。为此 `ApiException` 增加 `hasResponseCode`(错误码来自响应体)，`ApiError` 增加 `hasCode`。

## 6. 开发人员把文件「登记为已删除」(只写在这里，不放进界面)

适用于 A2(oss、legacy_unknown)，以及 B2/B2b 中确认那种存储已经永久不存在的情况。前提是已经在原存储上确认文件确实删除或已迁移。一次处理一个对象；用有写权限的维护账号执行；先在克隆库演练。

```sql
BEGIN;
-- 1. 看清单里的这一行(:key 换成拒绝文案或日志里的存储编号)
SELECT object_provider, object_location, object_key, identity_version, display_label, recorded_absent
FROM public.fn_business_test_reset_objects() WHERE object_key = :key;
-- 2. 登记一条已完成的删除记录：存储、位置、编号、版本照抄清单
INSERT INTO public.attachment_object_outbox
       (operation, storage_provider, storage_key, storage_version, dedupe_key, status, completed_at)
SELECT CASE o.object_location WHEN 'STAGING' THEN 'DELETE_STAGING' ELSE 'DELETE_FINAL' END,
       o.object_provider, o.object_key, o.identity_version,
       o.object_provider || '|RECORDED_DELETED|' || o.object_location || '|' || o.object_key
           || '|' || coalesce(o.identity_version, '*'),
       'SUCCEEDED', now()
FROM public.fn_business_test_reset_objects() o
WHERE o.object_key = :key AND NOT o.recorded_absent;
-- 3. 复核：recorded_absent 应为 true；然后回到弹窗点「重新检查」
SELECT object_key, recorded_absent FROM public.fn_business_test_reset_objects() WHERE object_key = :key;
COMMIT;
```

限制：

- 删除记录要求写明存储，编号只能由字母、数字和 `. _ -` 组成。「存储位置未登记」(存储为空)的对象，或者编号格式不符而插入被拒的对象，不能用这个模板，需要开发人员先核对那一行数据的来源。
- 这条记录会随下一次成功的清空一起清除。
- 不要对 internal/local 存储在已配置的服务器上用这个模板：这种情况系统会实地核对，登记不起作用。

## 7. 残余风险

| # | 风险 | 处理 |
|---|---|---|
| R1 | 物理删除先于数据库提交；删了一部分之后失败，会留下「登记还在、文件已经不在」 | 能事先判断的拒绝全部前移到删文件之前；删除与清空同一事务同一把锁；之后的失败一律带 W 前缀和已删数；重试时「不在 = 成功」，会收敛(第 4 节) |
| R2 | 存储盘没挂载时应用重启会重建空目录，所有文件被判为不在 | 弹窗醒目提醒「登记的 n 个测试文件在存储里一个都没找到」；受保护文件不会因此被删(什么都没删)；孤儿文件在附件对账启用时可以找出。存储身份标记(首次初始化写入 UUID 并登记到库)列为可选后续，由用户决定 |
| R3 | 直接 SQL 调用的边界 | 第 3 节；直接调用时清单不为空就拒绝 |
| R4 | 规则 34/35(范围外引用、TRUNCATE 权)只在 `business_data_reset()` 开头查一次，之后才拿 ACCESS EXCLUSIVE 锁，中间如有并发 DDL 不再复查。另外约 360 张清除表的 ACCESS EXCLUSIVE 锁在文件删完之后才拿，等锁超时(D4，15 秒)会在删过文件之后失败 | 接受：清空期间不应有 DDL；原函数中段的同类检查已删除，只留一份实现。清除表不在删文件前加锁：那样文件阶段里健康检查等普通读也会被挡住；D4 带 W 前缀如实说明，重试时已删的文件按「不在」处理，会收敛。纯前置条件(全员登录状态单行)已前移为规则 36 |
| R5 | 文件阶段 9 张来源表被 EXCLUSIVE 锁住(最多约 4 分钟) | 排水期间 API 本来就是 503；普通 SELECT 不受影响；没有经过排水闸的后台写入者会等到自己的锁超时后失败，下一轮再试 |
| R6 | D7/D8 两处放宽属于行为变化(D9 保持拒绝) | 用户 2026-10-05 确认(2.10)；J1 保证 D8 的前提；验收和拒绝测试覆盖 |
| R7 | 存储为 oss 的环境 | J1 直接拒绝；oss 历史对象一律由规则 20 拒绝，除非登记已删除 |
| R8 | 长清空事务会触发连接池泄漏检测(120 秒)的 WARN | 只是日志；以前清库本身就超过 120 秒 |
| R9 | V758 的稀疏截断因为 V773 之后的不可截断守卫永远走全量 | 只影响速度，不在本次范围，单独跟进 |
