## 一、定位

HR 日常事务的集中办理台：提醒仍由后端按「今天」从员工档案动态计算（不落任务表），
v2 解决 v1「四块平铺一页、内容太多、没有快捷操作、多人重复办理」三个问题：

1. **工作台化**：主页 = 今日概览统计卡 + 我处理中的事项 + 事务入口；每类事务独立子页面；
2. **快捷操作**：转正办理行内一键「登记转正」（日期默认今天可改）；
3. **软认领防重复**：任务显示「XXX 处理中」，他人快捷操作禁用（见 §五）。

宽屏主体是 `MasterDataTableView<HrTaskItem>`（`Key('hr-task-table')`）；窄屏（compact）
保留卡片 + `HrTaskTile`（移动端手感，与其他任务中心一致）。

| 列 key | 列名 | 说明 |
|---|---|---|
| `code` / `name` | 工号 / 姓名 | |
| `deptName` / `positionName` | 部门 / 岗位 | 部门列**带表头筛选** |
| `date` | 转正预计日 \| 生日 \| 周年日 \| 入职日 | 列名按类型切换(证件核对为入职日) |
| `note` | 原因 | 仅证件核对：服务端给出的具体原因原文(如「身份证号应为18位，当前为17位」)，红字，不含号码 |

| `claim` | 认领 | 认领人 + 租约到期（`claimedByName` + `claimLeaseUntil`），**带表头筛选**（未认领/我处理中/他人处理中） |

- **行菜单（右键/长按）**：查看档案 / 登记转正（转正类 + `employee:confirm`，被他人认领时不出）/
  送祝福（今日庆典 + 未祝福 + `notice:publish`）/ 修改证件信息(证件核对类，被他人认领时不出，§八) /
  认领 · 释放 · 接管（软认领，§五）。
- **多选批量**（`idOf=employeeId`，「已选 N 项」只由 `UtenSelectionSummaryPill` 呈现）：

  | 类型 | 批量动作 | 口径与门控 |
  |---|---|---|
  | 转正办理 | 批量登记转正(N) | 一次选日期（默认今天、不可选未来），逐人 `POST /employees/{id}/confirm`(后端同时覆盖试用期转正与在职未登记补登)；409(已登记/已离职)直接透出后端文案，**不再回退 `PUT /{id}`**(那条路会被「修改转正日期请使用转正功能」闸门拦死)；**被他人认领的行前端跳过并计入失败**（后端 confirm 无认领守卫）；门控 `employee:confirm` |

  | 证件核对 | 无 | 逐人对照证件修改，故不开多选 |

## 三、提醒区块与口径（沿用 v1）

| 区块 | 口径 |
|---|---|
| 转正提醒 | 预计转正日 = `hire_date` + 3 个月。已登记 `confirmed_at` 不再提醒；逾期只跟踪近 12 个月入职者，更早聚合为补录提示 |
| 生日提醒 | 今日生日 + 30 天内。按 `employees.birth_month_day`('MM-DD'，不含年份)匹配，2/29 非闰年按 2/28(`common.time.BirthMonthDay`，与庆典自动发布、本人今日庆典同口径)；不显示周岁(见下方 2026-10-05 说明)。**PII**：无 `employee:pii:view`(非超管)时不出生日列表、不计入徽标 |
| 入职周年 | 今日入职满 N 年(满 1 年起)。2/29 入职在非闰年按 2/28 过周年、当天即记满 N 年(`common.time.WorkAnniversary`，与庆典自动发布、本人今日庆典、一键/单人祝福的「入职N周年」同口径；见下方 2026-10-05 周年说明) |
| 新近入职 | 近 30 天入职（7 天内高亮） |

| 证件核对 | 证件号码缺失、身份证号没通过校验、历史导入还没校验的员工；只给能修改证件的人(§八) |

徽标数 = 今日转正 + 逾期转正 + 今日生日 + 今日周年 + 证件待核对(只给能修改证件的人计；生日/周年已祝福的不计)。接口：
`GET /api/org/hr-tasks/summary`、`GET /api/org/hr-tasks/count`，权限 `employee:view`。
状态范围：`active` + `probation`。

> 2026-10-05 修复(生日提醒恒空)：V282 把出生日期迁入密文 `employee_sensitive.birth_date_enc`，
> 明文 `employees.birth_date` 被触发器禁止写入、回填后恒为 NULL，而 `HrTaskService` 仍按 `birth_date`
> 计算，导致「今日生日 / 30 天内生日」与生日徽标永远为空(单测因 mock 了 `birth_date` 仍是绿的)。
> 现改按 V282 专为生日匹配派生的 `birth_month_day`；今日生日行 `days` = 0(与 30 天内的「剩余天数」同口径)，
> **不再派生周岁**——页面本就不展示年龄(表格今日行显示 0、卡片显示「今日生日」，AI 工具也不输出)，
> 为一个不展示的数逐人解密出生日期只会扩大 PII 读取面。真实 PostgreSQL 证据：
> `HrTaskServicePostgresTest`(今日生日进 `birthdayToday` 并计徽标 / 已祝福不计徽标 / 无 PII 权限为空)；
> 2/29 口径同时修正了 `CelebrationScheduler` 与 `NoticeService.myCelebrationToday`(此前按当天
> 'MM-DD' 精确相等，2/29 生日在非闰年整年不触发)，见 `CelebrationSchedulerPostgresTest`。

> 2026-10-05 修复(2/29 入职周年三处不一致)：HR 任务中心早已把 2/29 入职在非闰年按 2/28 列入「今日周年」，
> 但 `CelebrationScheduler` 用 `EXTRACT(MONTH/DAY FROM hire_date)` 精确相等、`NoticeService.myCelebrationToday`
> 比对月日，2/29 入职在非闰年既不自动发卡也不弹本人庆典。现三处统一走 `common.time.WorkAnniversary`：
> 第 N 个周年日 = `hire_date` 加 N 年(2/29 在非闰年落 2/28)，满 1 年起；调度器 SQL 按
> `to_char(hire_date,'MM-DD') IN (...)`(非闰年 2/28 另含 '02-29'，与生日共用闰日规则)+ 入职年份早于当年匹配。
> **年数口径**：`Period.between` 与 PostgreSQL `age()` 对 2/29 入职在非闰年 2/28 只算 N-1 年(差 1 天满月)，
> 会出现「今天过周年，卡上写 入职2周年」；现统一按 `WorkAnniversary.completedYears`(最大 N 使入职日加 N 年不晚于当天)，
> 2024-02-29 入职者 2027-02-28 标签为「入职3周年」、HR 列表「满 3 年」，2028-02-29 为「入职4周年」。
> 一键/单人祝福与发布预览派生的年数同步改用此口径；调度器年数改在服务端按扫描业务日算，不再依赖数据库当前日期。
> 证据：`WorkAnniversaryTest`(SQL 匹配集与内存规则逐日对齐、与 `Period.between` 只在该边界差 1 年)、
> `CelebrationSchedulerPostgresTest`(真实 PostgreSQL 固定日期扫描)、`NoticeServiceTest`、`HrTaskServiceBusinessDateTest`。

## 五、任务软认领（Soft Claim）

**调研结论**（Jira / 钉钉审批 / 飞书工单 / Zendesk 等工单与审批系统）：
业界主流**不隐藏**他人处理中的任务，而是显示处理人并阻止他人重复操作；
隐藏会导致工作不可见、被重复创建、卡住无人发现。本系统按此设计：

| 规则 | 行为 |
|---|---|
| 可见性 | 任务始终对所有人可见；被认领的行显示「XXX 处理中」徽标 |
| 防重复 | 他人认领中的行：「登记转正」禁用（锁图标提示处理人）；证件核对行不出「修改证件信息」 |
| 认领 | 点认领图标即认领（幂等：自己重复认领 = 续租 24h）；他人已认领 = 409；认领需 `employee:view`，证件核对另需超管或 `employee:pii:edit`(否则 403) |
| 租约 | 24 小时（`lease_until`），过期读取时惰性失效，无需定时任务/人工释放 |
| 释放 | 本人可释放；释放他人认领需 `employee:edit` |
| 接管 | 需 `employee:task_takeover`：原认领强制释放并转由我认领（防认领人请假卡死）；证件核对另需超管或 `employee:pii:edit`，在释放原认领之前检查 |

> 2026-10-05 更正：本节早期写的「持 `employee:edit` 者可接管」不准确，接管的服务端门槛一直是 `employee:task_takeover`。

接口：`POST /api/org/hr-tasks/claims`（body: taskType+employeeId）、
`DELETE /api/org/hr-tasks/claims/{taskType}/{employeeId}`、
`POST .../takeover`。taskType = confirm/birthday/anniversary/newhire/identity。
认领状态存 `hr_task_claims`（V210，部分唯一索引 + 审计触发器），任务本体仍动态计算。

## 六、前端数据流

`hrTaskSummaryProvider`（AsyncNotifier）一次加载，主页与各子页共享；
快捷操作/认领操作后 `reloadSilently()` 静默重取。员工模块里成功的 confirm / rehire / offboard /
onboard / change-identity 写请求经网络层写路径通道触发同样的静默重取(employee 模块不反向依赖本模块)。
工作台徽标不再由本模块单独轮询(旧 `hrTaskCountProvider` 已删除)，统一走全站徽章汇总
(`badgeSummaryProvider` 的 `hrTask.count`，轮询周期默认 60 秒、本端写后自动补拉)。
文案硬编码中文（与 rd_task 等运维页同惯例）。

## 八、证件核对(2026-10-05，ADR-154，V807)

给已有员工补开账号时，证件号有问题不再拦开号，只提醒，并在这里生成待办，让人事对照证件核对修改。

**口径**：在职和试用期员工里，档案证件号码有下列问题之一的(超管账号的员工除外，人事改不了超管的证件)：

| 种类 | 什么情况 | 列表「原因」列显示 |
|---|---|---|
| 校验未通过 | 证件类型是身份证，但号码没通过校验 | 具体原因原文，例如「身份证号应为18位，当前为17位」「身份证号第18位校验码与前17位不符，…」(全部 10 种见[员工详情页](员工详情页.md) §十) |
| 缺失 | 档案里没有证件号码 | 档案里没有证件号码 |
| 尚未校验 | 号码来自历史资料导入，服务端还没解密判定(下次启动自动判定) | 证件号码来自历史资料导入，系统还没有完成校验 |
| 尚未校验(读取不出来) | 启动回填解不开档案里的号码(数据损坏，或换密钥后没配旧密钥)，存为 `unreadable`，不再重试 | 档案里的证件号码读取不出来，系统无法校验，请人事对照证件重新登记 |

- 数据来源：`HrTaskSummary.identityReview`，每条 `date` = 入职日期(可为空)、`days` = 0、`note` = 服务端拼好的原因(只含位置和长度，不含号码)；按工号排序。服务端只读已存的校验结果 `employee_sensitive.id_card_check`，不解密。
- **谁看得到、谁计数**：只有超管或持 `employee:pii:edit` 的人收到条目，并计入本页徽标与工作台 `hrTask.count`(红数，被认领的照样计)；其他人(包括只有 `employee:view` 的总经办等)收到空列表、不计数。不新增权限点。
- **路由**：`/hr/tasks/identity` 在 `/hr/tasks` 通用的 `employee:view` 之外另需 `employee:pii:edit`(超管照常放行)；工作台入口卡用同一份判定。
- **主页横幅**：有待核对员工时，今日概览上方显示红色横幅「有 N 名员工的证件号码待核对」，右侧「去处理」进子页(2026-10-06 起只留标题一行，说明小字删除；具体哪里缺/错看子页每行红字原因)。
- **子页表格**：列 工号 / 姓名 / 原因(红字，紧跟姓名，普通宽度不用横向滚动就能看到) / 部门 / 岗位 / 入职日 / 认领；没有天数、区间两列，不开多选。原因在表格和窄屏卡片里都是红字、折行显示全文，不用省略号截断(最长的校验码原因在 375 宽手机上也完整可见)。
- **我处理中的事项(主页)**：证件核对行的状态标签只放短标签「证件待核对」(红)；具体原因不拼进灰色副标题，而是在副标题下单独一行红字、占整行宽、不截断。行宽不足 440(手机竖屏)时，「释放」「修改证件信息」等按钮另起一行靠右，不与姓名和标签并排挤占宽度。
- **行操作**：「修改证件信息」(行菜单与窄屏卡片按钮；被他人认领处理中时不显示)，打开与员工详情页同一个修改弹窗，调 `POST /api/org/employees/{id}/change-identity`。保存成功提示「某某 的证件信息已更新」并静默重取，条目消失、徽标同步减。身份证号不合格时弹窗边输边显示具体原因(如「身份证号第5位不是数字(只有第18位可以是X)」)，不发请求；服务端拒绝时(如「该证件号码已被其他员工使用，请核对是否录错或与其他员工档案重复」)弹窗内显示服务端原话，弹窗不关。
- **认领**：taskType = `identity`；认领与接管另需超管或 `employee:pii:edit`(§五)。
- **AI 助手**：人事任务 AI 工具(ADR-141)不读这份列表，不输出任何证件信息。
