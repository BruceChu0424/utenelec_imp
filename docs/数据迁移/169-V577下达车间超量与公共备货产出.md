## 一、为什么改

用户口径（2026-09-14）：「生产是可以超出数量下达的；超出部分就是公共的，其他计划可以占用——你看看采购，参考下。」

采购与无子层委外早有这套分账：精确需求进 `allocation/exact`，计划员主动追加的富余量单记 `preplan_supply_actions.public_surplus_qty`，财审通过即成为公共在途，他计划按 `SHARED_FUTURE_CLAIM` 认领。生产侧此前**没有任何落点**，计划量被三道守恒钉死在需求以内：

1. `production_material_analysis_item_qty_chk`：`submitted_qty + approved_qty <= requested_qty`（V234）
2. V478：`submitted_qty + approved_qty + root_fulfilled_qty <= requested_qty`
3. `fn_sync_material_analysis_plan_link_qty`：计划行数量必须恰等于关联行 `submitted_qty`

所以只要「本批数量 > 剩余需求」，事务必然回滚；前端也在提交前就拦掉，用户看到的是「本批生产数量不能超过剩余需求 N 个」。

## 二、本次做法

只松开第 3 道，前两道一个字节不动。

`production_material_analysis_plan_links` 新增 `public_surplus_qty`，把一次下达拆成两笔：

| 列 | 含义 | 去向 |
| --- | --- | --- |
| `submitted_qty` | 归本需求的量 | 照旧驱动 `items.submitted_qty` 与齐套投影 |
| `public_surplus_qty` | 超出需求、按公共备货产出记账的量 | 不绑定任何需求，产出入库即公共库存 |

计划行数量 = 两者之和；触发器的对账式同步改为 `pi.qty = NEW.submitted_qty + COALESCE(NEW.public_surplus_qty, 0)`，关联行身份不可变的判定也把新列纳入。原 `CHECK (submitted_qty > 0)` 放宽为「两者非负、合计为正」——剩余需求已经是 0 却仍要多做一批，是合法形态。

触发器沿用 V478 既有做法修补：读当前定义（V490 版本）→ 断言形状 → 定点 `replace` → `EXECUTE`，不整函数复制，避免与后续补丁漂移。

## 三、刻意没做的事（都有明确原因）

- **不抬高任何 `items.requested_qty`。** 抬需求会污染 `growMakeAnchorQuotasAfterSourcePreview` 的锚点配额算法：`openQuota = requested − inbound` 一旦高于物理缺口，`increase = demandSupplyGapQty − openQuota` 恒为 0，**后续新增销售来源带来的合法需求增长会被静默吞掉**（不报错、计划员看到「还需安排 0」却实际缺料）；同时会与 `syncRequestedQuantities` 的来源对账脱钩（锚点行被系统性排除在对账之外）。
- **不给超出部分自动展开下层物料需求。** 锚点行本就不展开自己的 BOM（`MaterialAnalysisService#loadBomTrees` 显式过滤 `MAKE_COMPONENT`/`SUBCONTRACT_MAKE`，ADR-071「锚点不再展开自己的 BOM」），父件计划产出还被 `parentPlannedOutput` 的 `.min(shortage)` 按物理缺口封顶。多做那部分的料由计划员另行安排——这正是 ADR-070 §2.7「额外数量尚未形成下层材料需求，请分开处理」的既有口径。前端在提交前用二次确认把这句话说清楚，不让人到车间领料时才发现缺料。
- **销售订单来源的顶层行仍然不允许超量。** 应用层 `requireOverQuantityAllowed` 直接拒绝并说明原因：超产会同时踩 `production_plan_sales_allocations` 的「分摊合计 = 计划数量」守恒与 `ProductionPlanService` 的「排产量 ≤ 订单未满足需求」，还会连带影响报工分摊、订单进度与成本分摊。多做的量另立备货任务下达。
- **不新增权限码。** 用户明确：「不要，有下达车间权限即可」。采购侧的 `production_material_analysis:over_supply` 不扩展到车间桶。
