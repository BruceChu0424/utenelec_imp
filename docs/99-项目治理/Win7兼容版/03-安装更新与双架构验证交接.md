## 4. Receipt、候选快照与包合同

### 4.1 当前 producer 流程

1. `capture_source_state` 要求整个工作树 committed + clean，读取准确 commit、受审源清单/摘要及 pubspec 版本。
2. `build_windows_wpf.ps1 -Build -Configuration Release -DistributionProfile Company` 才尝试 Company source-state/receipt；默认仍是 dry-run。
3. 编译后检查输出，并复制六文件到独立 `build/windows-wpf/company-payloads/<arch>-<GUID>/`。
4. `write_build_receipt` 再核对源状态、编译 profile、版本、依赖/配置及完整文件摘要。
5. `package_update` 默认 dry-run；只有显式 `--build` 才在 receipt 合同满足后生成 candidate ZIP，并独立重读校验。

receipt 是本地构建来源记录，不是 Authenticode、正式发布许可或 Win7 UAT。
当前工作树不干净，审计时也没有 `build/windows-wpf/receipts/` 或 Company payload 回执目录；不能绕过 clean/profile 检查。
用户要求留独立分支，不妨碍后续在该分支提交受审快照，但不授权 merge main、正式打包、上传或部署。

### 4.2 统一目标合同

目标 `platform=windows`、`runtimeFamily=wpf_legacy`、`architecture=x86|x64`。
新 WPF 更新 ZIP 的根必须只有以下六文件和根清单 `uten-client-manifest.json`：

```text
Uten.Legacy.Desktop.exe
Uten.Legacy.Core.dll
BouncyCastle.Cryptography.dll
Uten.Legacy.Desktop.exe.config
BouncyCastle-LICENSE.md
uten.client.json
uten-client-manifest.json
```

不带 ico、PDB、Tests、显式目录、`client_updater/` 或任意额外脚本。根 ico 保留安装器版本。

清单 schemaVersion=1，必须绑定 platform/runtimeFamily/architecture/version/buildNumber/executable，文件记录为
`files[{path,size,sha256}]`。**最新统一决定：新 WPF `packageKind` 必须显式为字符串 `update`，缺失/null 都应拒绝。**
Flutter 历史清单的旧缺省语义不能挪用到没有历史包的 WPF。

producer 还写 `sourceCommit`、`candidate=true`、`releaseReady=false`；candidate 标志不是后台发布权限或 UAT 许可。
单 ZIP≤512 MiB，累计展开量严格<1 GiB；同时验证每文件 size/SHA-256、主/Core PE/CLR 架构及版本，BC DLL/许可按其独立依赖锁检查。
BC 保留库自己的版本，不要求等于应用版本。

### 4.3 当前仍存在的合同差异

| 差异 | 当前事实 | 接续要求 |
|---|---|---|
| WPF kind 缺省 | Updater现已要求显式update；缺/null均有负向fixture | 仍需与producer/backend同一组共享边界样例核验；不据单组件测试声称三方全闭环 |
| 后台允许 ico | 当前 `WindowsWpfPackageInspector.allowedFile` 仍允许根 `uten-wpf.ico` | 与 producer/Updater 的固定六文件更新面统一；不能只通知后就记作已改 |

这些差异必须以源码与共享 fixture 的实际结果关闭，不能用“正常小包恰好通过”代替边界一致。

## 5. Instruction、私有路径与 ready 握手

Updater 的生产入口仅接受一个 instruction JSON 文件路径，不接受 shell 命令、密码、URL、可替换 appRoot 或任意程序路径。
appRoot 从 Updater 自身程序集所在 `client_updater` 目录的父目录锚定，只启动/替换对应 `Uten.Legacy.Desktop.exe`。

```text
%LOCALAPPDATA%/Uten/UIMP-Win7-WPF/client-updates/<GUID>/
  instruction.json
  package.zip
  execution.lock
  stage/                 # 已核验的新六文件
  backup/                # 已核验的原六文件
  update.log
  ready.json
  result.json
  cancel.flag            # 取消优先，存在即拒绝应用
  apply-authorized.json  # ready之后由父程序最后明确授权，普通退出不生成
```

| instruction字段 | 类型及约束 |
|---|---|
| `schemaVersion` | 整数1 |
| `packagePath` | 同一job根的绝对 `package.zip`，不能越出job |
| `sha256` / `sizeBytes` | 小写64hex及1..512 MiB，ZIP实际字节双重核对 |
| `version` / `buildNumber` | 数字三段版本及1..65535；构建号必须大于现安装，产品版本不得倒退 |
| `architecture` | 当前应用/Updater进程对应x86或x64 |
| `runtimeFamily` | 显式 `wpf_legacy` |
| `parentPid` | 正整数，不能是Updater自己 |
| `parentStartTimeUtcTicks` | 父进程UTC启动时间ticks；不是墙钟“最近几秒”猜测 |

严格 JSON reader 拒绝重复键、额外未知字段、超限和错误类型。Parent exe路径从锚定appRoot计算，不信任指令给权限根。

当前握手源码顺序：

1. UI检查适用WPF更新，用户确认，检查当前页面退出保护及身份代次。
2. Coordinator建立私有job，流式下载并核对hash/size/身份代次，写instruction，只启动固定helper。
3. Helper完整验证并提取ZIP到stage，再核实仍存活父进程的PID、启动ticks和exe路径。
4. 写 `ready.json`：`schemaVersion=1,state=ready,parentPid,parentStartTimeUtcTicks,updaterPid`。
5. Coordinator最多等15秒，核对ready与自己和子进程身份，返回 `PreparedUpdate`；MainWindow重查代次及退出保护后调用 `AuthorizeShutdown()`，最后正常 `Shutdown(0)`。
6. Helper在ready前后、等待父进程期间及父退出后检查cancel；最多等30秒，只接受已核实父进程正常退出且ExitCode=0，不Kill父进程。
7. 父退出后必须独立验证 `apply-authorized.json`；缺失/错配/取消均不得开始修改。授权之后仍执行原有文件指纹、单写锁、完整备份和逐文件复核，不跳过预检。

授权文件严格11字段：`schemaVersion=1,state=apply_authorized,runtimeFamily=wpf_legacy,architecture,packageSha256,packageSizeBytes,version,buildNumber,parentPid,parentStartTimeUtcTicks,updaterPid`。
全部须与计划/本helper进程相同，拒绝重复/未知字段和错误类型；不含密码、URL、任意命令或权限根。
该文件在同GUID job中CreateNew临时文件、flush后原子改名发布，发布前后重查身份/取消；变化时落持久cancel。
`Cancel()`明确撤销，`Dispose()`取消未确认准备；确认授权后解除lifetime取消注册，避免正常AppShutdown误取消；显式Cancel始终优先。
Helper在开始修改、每个文件写入前和最后一个文件写完后复查授权/取消；应用中的取消尝试既有逆序回滚并保留材料。

**握手尚未完成真实跨进程集成验收。** 当前限制：

- 完整ZIP预检可能超过Coordinator的15秒；helper的30秒仅从ready之后开始。需统一时间预算、预检进度与超时退出策略。
- 取消/明确授权双门已有源码及临时fixture；fixture模拟父退出后到达同一Apply gate，未执行真实helper/父进程退出流程。需补受控跨进程证据，不能把该负向fixture称作目标机更新通过。

手动“软件下载”可以下载被授权的不同runtime包；真正自更新必须再次限定为当前WPF runtime、架构、更新模式和更高构建，不能执行Flutter包。

## 6. 执行器已有保护与恢复限制

当前 `UpdateExecutor.Execute` 有appRoot固定 `client_updater/update.lock`、job execution.lock及目录句柄保护。
不链接Core DLL；验证包只读PE/CLR及版本资源，不加载包程序集执行。

应用阶段先为六个现安装文件取得 `FileShare.None` 排他句柄并核对预检旧hash，发现外改则不覆盖。
全部备份核验完成后才按批准文件逐个写入，每个文件flush并重验size/hash；所有文件句柄保持到应用/回滚结束。
进程内异常会尝试逆序恢复已修改文件，并保留stage、backup和日志；失败时不自动重启旧程序或半更新程序。
成功路径在最终只读租约下重验六文件，只通过无shell的固定主exe启动。

限制必须明确：

- 当前采用排他句柄下原位写入，**不承诺断电事务或跨文件原子提交**。
- 早期64断言及本轮194断言覆盖的是临时fixture的预检、取消授权、捕获异常、外改和共享锁场景，未覆盖掉电、进程强退及Win7真实NTFS行为。
- 当前旧文件fingerprint和部分回滚状态主要在内存；日志记录phase/文件名，不是完整的、可断电重放的旧hash/版本恢复清单。
  需补落盘恢复manifest与独立恢复验证流程，不能凭backup目录存在就称断电恢复可用。
- 已有stage/backup/update.log等被视为冲突并保留。**不能删除这些材料后强行重跑同job**；应审查原因，使用新job或经批准的恢复工具。
- result状态包含 `failed_before_apply`、`failed_rolled_back`、`failed_manual_recovery`、`succeeded` 等；源中有结果文件，未见Coordinator/下次启动完整消费结果的集成链。
- helper构造、锁或日志创建失败可能只以退出码2结束；不能假定所有失败都有result.json。

- DPAPI、业务附件、其他runtime、服务器回滚版本及整app目录均不属于清理范围；当前没有递归删除整个安装目录的生产代码。

## 7. 后台、配套备份与旧JAR回滚

当前后台源码已有 `runtimeFamily`、WPF模式及按family筛选/保留的实现入口；普通缺省请求和旧记录只归 `flutter`。
WPF使用 `windows_wpf_setup` / `windows_wpf_archive`，不能靠相同 `windows+x64` 或最高build选包。

旧缺失/null family保持旧审计字节，只在校验时解释为Flutter；withdrawn的 `sha256=null,sizeBytes=0` tombstone不会复活残留二进制。

**旧JAR限制：** 一旦catalog中存在WPF记录，不能将不识别runtimeFamily/WPF模式的旧JAR直接回滚到同一个混合catalog。
旧基线服务会只按platform/architecture筛选更新及清理，可能错推WPF包，或在Flutter新完整组出现后清理另一runtime的旧二进制。
不能只凭“JSON能反序列化”认为回滚兼容。

后续回滚验收须：

1. 优先选已有runtime隔离能力的服务端回滚版本，并核对API、catalog及配套helper同一兼容合同。
2. 没有兼容版本时，先形成并批准维护方案，在隔离副本演练；不把旧JAR指向真实混合目录试运行。
3. 保留完整混合catalog、必要审计元数据及配套备份；不删除WPF记录、改family或移动生产目录以迎合旧程序。
4. 如确需准备Flutter-only旧服务环境，使用经审查的转换/恢复流程到**新的空目录**，保留WPF完整集合与绑定回执；当前没有完成此转换/回滚工具的验收。
5. 服务器代码回滚不授权数据库倒退、旧primary重新接管或附件/备份删除；继续遵守现役发布与恢复门禁。
