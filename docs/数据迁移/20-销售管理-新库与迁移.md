## 〇、对老库调研（doc 19）的两处关键修正

写本文前重新跑了 `sp_helptext` 取完整触发器源，对照 doc 19（dump 截断处推断）有两处必须修正，是本文设计的**前提事实**：

| 项 | doc 19 推断（dump 截断）| 完整源验证结论 |
|---|---|---|
| **S_Out 审核生 M_in** | `Total=0, M_In=@Total, M_Rare=-@Total` | ✅ **错**。实际：`Total=@Total_, M_In=0, M_Rare=@Total_, BStyle=3`（M_In=已收=0、M_Rare=未收=总额、Total=应收总额，**全正数**）|
| **S_OtherOut 是否生 M_in** | "S_OtherOut 触发器同样有这段（被注释掉与否需看完整源）" | ✅ **确认完全注释**。`TRI_OCStockItem` 第 106–145 行整段 `M_in` INSERT 与回写 `S_OrderItem` 都在 `/* */` 里——**其它出货只动库存，不挂订单、不立应收** |
| **S_Withdraw 生 M_in** | "推断结构相同（红冲时反向）" | ✅ **确认在用，但是红字应收**：`Total=-@Total_, M_In=0, M_Rare=-@Total_, BStyle=18, Note=@Remark`（**全负数**，直接冲减客户应收余额）|
| 反审保护 | 未提 | ✅ 三个触发器**完全一致**：反审时若 `M_in.M_In <> 0`（已有收款核销）→ `RAISERROR '此单已经存在收款，请先反审收款单!'` 并 `rollback`；否则 `DELETE FROM M_in WHERE BillNo=@BillNo` |

> 结论：销售与钱流的耦合方式是「**审核 → 立应收（正/负）**」，且 **S_Out 与 S_Withdraw 都立应收**（一正一负），**S_OtherOut 不立**。新库照此设计，把触发器副作用上移到 Service 同事务。

| # | 决策点 | 选型 | 理由 |
|---|---|---|---|
| 1 | 库存关系 | **审核同事务联动**（`stock_movements` type 3/4/20 + `stock_balances`） | 复用 V45 已建骨架（[18] §三），取代老库 StockGoods 按月分列台账；与采购/仓库共入口，全链路打通 |

| 6 | 数量回写 | 明细保留 `shipped_qty` / `returned_qty`，Service 回写 | 老库验证过的 RQTY/WQTY 模式（[14]/[15]），触发器上移到 Service；老库 `S_OrderItem` 那 15+ 累计量列只留这两个，其它（IQTY/PQTY/LQTY/POQTY/PIQTY/PWQTY/FlagQTY）丢弃，按需从下游聚合 |

### 补决策表：S_Out 与 S_OtherOut 为什么**拆表**而非合表

字段集 100% 同构（doc 19 §二已逐字段对比），但**业务约束**三处不同：

| 维度 | S_Out（销售出货） | S_OtherOut（其它出货） | 合表代价 |
|---|---|---|---|
| 订单挂接 | 明细 `OrderID → S_OrderItem` 真挂；审核回写 `RQTY` | 明细 `OrderID` 字段在但**孤儿**（触发器 UPDATE 注释）；不挂订单 | `order_item_id` 须可空 + 类型层校验"OTHER 时必须空" |
| 应收联动 | 审核**立 M_in**（BStyle=3，正应收） | 审核**不立 M_in**（触发器整段注释） | Service 须按 `doc_type` 分支，复杂度回到拆表水平 |
| 业务用途 | 订单驱动的对外销售出货 | 样品/赠品/内部领用/其它非订单出货 | 报表/权限/编号前缀（XC vs OC）本就要区分 |
| 字段集 | 完全相同 | 完全相同 | — |

**结论**：合表省 2 张表壳，但约束/分支/报表/权限都得加 `doc_type` 判别——本质是用一个 `doc_type` 字段换拆表的清晰度。**仓库 9 单据能合是因为它们库存效果同构**（都是 ±出入），**销售这两张表业务约束不同构**，故拆。与采购"申请/订货/收货/退货 4 套独立表"的哲学一致。

## 三、表设计（具体 DDL · 可直接落 Flyway V51）

### 3.0 统一约定（与 V44 一致，不赘述）

- 主键 `id UUID PRIMARY KEY DEFAULT gen_random_uuid()`，迁移溯源 `legacy_id INT UNIQUE`（明细表 legacy_id 不 UNIQUE，跨表 ID 重复可能）。
- 单据号 `bill_no TEXT NOT NULL`，主表 `UNIQUE(bill_no)`（业务主键；新库用独立序列生成器，防并发冲突）。
- 审计四件套 `created_at/updated_at/created_by/updated_by` + 软删 `is_deleted/deleted_at`。
- 金额统一 `NUMERIC(18,4)`，数量 `NUMERIC(18,4)`（**纠正老库 float**），汇率 `NUMERIC(18,6)`，税率 `NUMERIC(18,4)`。
- 金额双口径：`*_original`（原币）+ `*_local`（本币 = 原币×汇率）。
- **明细表冗余 `bill_no` + `bill_date`**：查询裁剪 + 报表免 JOIN 主表取日期。
- 性能：单表 + 强索引（出货明细 9 万行、订货明细 8 万行——百万级内单表 + B-tree 毫秒级，**本期不分区**；未来千万级可按 `bill_date` 在线转分区，与 V44 采购明细同策略）。

## 四、状态机与库存+应收联动（Service 层，取代触发器）

> **整节历史契约警告**：§4.1–§4.4 保留 V51/V57 早期伪代码，仅用于解释迁移来源，不得复制实施。当前新流程是 `PENDING_PICK → PICKING → PICKED → SHIPPED`，正式 AR 仅在 `SHIPPED` 建立；销售退货通过负 AR 表达，不直接调用旧 `reverseReceivable` 伪接口；收款核销由 `FinanceReceiptService` 完成。

### 4.1 历史状态机（V51/V90 设计快照）

> 下列代码块保留早期 Service 设计，便于解释历史单据和迁移来源。V189 新退货不再在审核时直接写可售库存，
> 而是“审核→质量冻结→`GOOD_RELEASE` 才入库”；发生任一处置后禁止整单普通红冲，纠错须以后续受控补偿命令实现。

```
录入 → status=0(草稿) 或 1(已审，贴老库"保存即生效")
审核 status 0→1：同事务内
   · sales_shipments：     写 stock_movements(type=3,dir=-1) + upsert stock_balances
                         + 回写 sales_order_items.shipped_qty += qty
                         + 调 AccountReceivableService.postReceivable(BStyle=3, 正应收)
                         + 重算相关 sales_orders.is_closed
   · sales_other_shipments：写 stock_movements(type=20,dir=-1) + stock_balances
                         （不回写订单，不立应收——尊重老库触发器对应段已注释的语义）
   · sales_returns：       写 stock_movements(type=4,dir=+1) + stock_balances
                         + 回写 sales_shipment_items.returned_qty += qty / returned_amount
                         + 回写 sales_order_items.returned_qty += qty
                         + 调 AccountReceivableService.postReceivable(BStyle=18, 红字负应收)
                         + 重算 sales_orders.is_closed
   · sales_orders：        状态机本身无库存/应收副作用（订货只承诺，不动账）
                         · 回写 sales_order_cost_items.l_status 由主表下发（同老库 TRI_S_Order）
红冲 status 1→-1：同事务反向冲销，单据保留不可删
   · 库存：删/反向 stock_movements；stock_balances 倒回
   · 回写量：shipped_qty/returned_qty 倒回（按 -qty）
   · 应收：调 AccountReceivableService.reverseReceivable
            · 内部先 SELECT ar_ap_ledger WHERE source_doc_id=? AND paid_amount<>0
            · 若已有收款核销 → throw "此单已经存在收款，请先反审收款单!"（与老库 RAISERROR 同文案）
            · 否则 DELETE 该应收行
```

**结案派生（Service 重算，对应老库 CheckFulfill 触发器）：**

```sql
-- sales_orders.is_closed 在出货/退货审核同事务内重算（明细变化时）
UPDATE sales_orders o
SET    is_closed = NOT EXISTS (
    SELECT 1 FROM sales_order_items i
    WHERE i.order_id = o.id
      AND (i.qty - i.shipped_qty + i.returned_qty - i.flag_qty > 0
           OR i.qty = 0)

WHERE o.id IN (?);  -- 受出货/退货影响的订单 id 列表

### 4.2 库存联动（同事务，复用 V45 骨架）

```
StockService.applyMovement(doc) 单一参数化入口（同仓库模块 StockDocService.applyStockEffect 范式）：

  source_doc_type = 'SALES_SHIPMENT' | 'SALES_OTHER_SHIPMENT' | 'SALES_RETURN'
  source_doc_id   = 主表 id
  对每个明细：
    INSERT stock_movements (
      transaction_date = bill_date, movement_type = 按上表,
      source_doc_type, source_doc_id, source_item_id = 明细 id,
      goods_id, color_id, warehouse_id,

    ON CONFLICT (warehouse_id, goods_id, color_id) DO UPDATE

### 4.3 应收联动（销售模块独有 · 关键跨模块）

> **本节是销售与采购最大的不对称**（[19] §4.7）：采购入库 `P_In` 触发器**不**自动生 M_Out（应付），由会计在钱流模块单独开单；**销售出库 `S_Out` 与退货 `S_Withdraw` 审核**会自动立 M_in（应收，一正一负）。新库保留此语义，**显式化**为 Service 同事务调用。

**Service 层事务设计（伪代码）：**

```java
@Service
public class SalesShipmentService {

    private final SalesShipmentRepository shipmentRepo;
    private final SalesOrderItemRepository orderItemRepo;
    private final StockService stockService;
    private final AccountReceivableService arService;   // 钱流模块提供（V57 后）
    private final ApplicationEventPublisher events;

    /** 审核销售出货单：同事务完成 库存 + 订单回写 + 立应收 + 结案 */
    @Transactional
    public void approve(UUID id) {
        var ship = shipmentRepo.findById(id)
            .orElseThrow(() -> notFound(id));
        if (ship.status != 0) throw new BizException("单据非草稿态，不可审核");
        if (ship.warehouseId == null) throw new BizException("出货仓库必填");

        // 1. 单据头状态机
        ship.status = 1;
        ship.approverId = currentUser();
        ship.lastDate = now();
        shipmentRepo.save(ship);

        // 2. 库存：写 stock_movements(type=3,dir=-1) + stock_balances
        stockService.applyMovement(ship, items, movementType=3, direction=-1);

        // 3. 订单回写：shipped_qty += qty（同老库 RQTY += QTY*@Status）
        var affectedOrderIds = new HashSet<UUID>();
        for (var item : items) {
            if (item.orderItemId != null) {
                orderItemRepo.addShippedQty(item.orderItemId, item.qty);
                affectedOrderIds.add(getOrderId(item.orderItemId));
            }
        }

        // 4. 立应收：调钱流 Service 在 ar_ap_ledger 插一行 BStyle=3
        //    （M_in: Total=@Total_, M_In=0, M_Rare=@Total_ 全正数）
        if (!ship.arPosted) {
            arService.postReceivable(ReceivableEntry.builder()
                .sourceDocType("SALES_SHIPMENT")
                .sourceDocId(ship.id)
                .billNo(ship.billNo).billDate(ship.billDate)
                .clientId(ship.clientId)
                .totalOriginal(ship.totalOriginal)
                .totalLocal(ship.totalLocal)
                .currencyId(ship.currencyId)
                .exchangeRate(ship.exchangeRate)
                .bStyle((short) 3)               // 销售出货应收
                .pStyleLegacy(ship.paymentStyleId)
                .dueDate(ship.lastDate != null ? ship.lastDate : ship.billDate)
                .build());
            ship.arPosted = true;
            shipmentRepo.save(ship);
        }

        // 5. 重算相关订单结案
        recalcOrderClosed(affectedOrderIds);
    }

    /** V51 历史反审伪代码：只解释迁移来源，不适用于 V187 后的 SHIPPED 出货 */
    @Transactional
    public void reverse(UUID id) {
        var ship = shipmentRepo.findById(id).orElseThrow(...);
        if (ship.status != 1) throw new BizException("仅已审单可红冲");

        // 钱流 Service 先校验：若该出货的 ar_ap_ledger 行 paid_amount<>0 → 拒绝
        // （与老库 RAISERROR '此单已经存在收款，请先反审收款单!' 同语义）
        if (ship.arPosted) {
            arService.reverseReceivable("SALES_SHIPMENT", ship.id);
            ship.arPosted = false;
        }

        // 反向库存：type=3 dir=+1（倒回）
        stockService.applyMovement(ship, items, movementType=3, direction=+1);

        // 订单回写倒回：shipped_qty -= qty
        for (var item : items) {
            if (item.orderItemId != null) {
                orderItemRepo.addShippedQty(item.orderItemId, item.qty.negate());
            }
        }

        ship.status = -1;
        shipmentRepo.save(ship);
        recalcOrderClosed(affectedOrderIds);
    }
}
```

`SalesReturnService.approve/reverse` 不能再套用上面的通用模板。现行 V189 规则为：
- 新退货审核只回写 `sales_shipment_items.returned_qty/returned_amount`、`sales_order_items.returned_qty`，立 BStyle=18 红字应收，并建立质量冻结；不写 type=4 可售库存流水；
- 只有 `GOOD_RELEASE` 处置按已释放基本量写 type=4 / DIR_IN，`SCRAP`、`REWORK` 不增加 `stock_balances`；
- 全部冻结数量尚未处置时可随原退货单受控撤销；任一质量处置发生后，整单普通红冲必须拒绝；
- V189 前没有质量冻结行的历史已审退货继续按旧库存流水反向兼容，不补造过去的质检结论。

`SalesOtherShipmentService.approve/reverse` 同型，差异：
- `movementType=20, direction=-1`
- **不**回写订单（即使 `order_item_id` 字段在，Service 不调 `addShippedQty`）
- **不**调 `arService`（无立应收）

### 4.4 钱流 Service 契约（`AccountReceivableService` · 由钱流模块 V57 实现）

销售模块审核流程依赖钱流模块提供以下两个方法（**同事务**，`propagation = MANDATORY`）：

```java
public interface AccountReceivableService {

    /** 立应收：在 ar_ap_ledger 插一行（BStyle=3 出货正应收 / 18 退货红字负应收）。
     *  幂等：同 (source_doc_type, source_doc_id) 已存在则 NO-OP。
     *  字段：total/remaining 按 BStyle 正/负；paid_amount 初始 0；client_id 必填。 */
    @Transactional(propagation = MANDATORY)
    void postReceivable(ReceivableEntry entry);

    /** 反审：检查无收款核销后删除该应收行；否则抛 BizException("此单已经存在收款，请先反审收款单!")。
     *  调用方（销售 Service）事务回滚时此删除一并回滚。 */
    @Transactional(propagation = MANDATORY)
    void reverseReceivable(String sourceDocType, UUID sourceDocId);
}
```

> `ar_ap_ledger` 表的最终结构由 [26-钱流-新库与迁移.md] V57 定。本文按以下**契约字段**约束：
> `source_doc_type / source_doc_id`（销售立应收时为 `SALES_SHIPMENT` / `SALES_RETURN` + 单据 id）、`client_id`、`bill_no`、`bill_date`、`due_date`、`total_original/local`、`paid_amount`、`remaining_amount`、`b_style`（3 / 18）、`currency_id`、`exchange_rate`、`is_settled`。
>
> 在 V57 落地前，销售模块测试可 mock 此接口（或建一张最小桩表），不阻断 V51 落地。

### 5.3 待交货订货汇总（取代老库 `View_S_OrderItem` "未发数量"）

```sql
-- 按货品+颜色汇总"订了还没发完"的量（对应老库 View_S_OrderItem 未发数量）
CREATE VIEW sales_order_pending_v AS
SELECT goods_id, color_id, client_id,
       SUM(qty - shipped_qty + returned_qty - flag_qty) AS pending_qty,
       SUM((qty - shipped_qty + returned_qty - flag_qty) * price) AS pending_amt
FROM sales_order_items
WHERE is_deleted = false
GROUP BY goods_id, color_id, client_id
HAVING SUM(qty - shipped_qty + returned_qty - flag_qty) > 0;
```

## 十一、订货单锁价 + 折扣自动带价（2026-08-07，V226 周边改动）

订货单（`SalesDocType.order`）明细改为**价由货品主档决定、销售不可改**：

- **选产品后自动带入**：单价 ← 货品主档 `goods.price`；折扣 ← 货品 `goods.zk`（倍率，1=原价；空/0 → 1）。两者在网格中**锁定只读**（`_lockedCell` 禁用输入框，值仍随保存提交）。
- **金额 = 数量 × 单价 × 折扣**：前端 `SalesGridRow._recalc` 与后端 `SalesOrderService.authoritativeOrderAmount(qty, price, discount)` 同口径；折扣空/0 视为不打折（倍率 1）。
- **底部汇总**：网格 `footer` 槽右对齐显示「总数量 + 总金额」（总数量 `_totalQtyNotifier`、总金额 `_grid.totalListenable`）。

数据安全（不影响历史 / 不影响其它单据类型）：

- `authoritativeOrderAmount` 新增 3 参重载（含折扣），原 2 参重载委托 `null` 折扣 → 倍率 1，**老调用方行为不变**。
- 历史订货明细 `discount` 全为 0/null（订货此前无折扣列）→ 倍率 1 → 金额仍 = 数量 × 单价，**历史数据与审核不变量不受影响**。
- 审核（`requireSafeStoredCommercialOrder`）的 `expectedOriginal` 同步改为 `数量 × 单价 × 折扣`，与新存法一致。
- 折扣乘金额用 `SalesGridRow.amountUsesDiscount` 标志**仅订单生效**，出货/其它出货/退货单的折扣列不影响其金额（与各自后端口径一致，避免前端预览与后端存值错位）。

## 十二、销售汇率分权与待收计划（2026-08-08；2026-08-09 修订，V236–V238）

本节取代本文早期“销售审核即立应收”的表述。现行权威链路为：

1. **订货单只保存币种和原币金额**：订单页面选择币种、填写税率，但不显示或提交汇率；服务端按数量、锁定价格和折扣计算原币金额。新建、换币、保存和销售审核都不读取或校验币种主档汇率，不等待财务逐单处理；当前状态机没有独立“提交待审”状态。订单上的 `exchange_rate`/`*_local` 只作历史兼容，不得再用默认 1 合成新事实或作为流转门禁。
   **2026-08-27 UI 口径**：销售订货新建/编辑页的结账方式为必填，空值立即显示红色 `*` 和错误色边框，不提供清空项，保存前再次阻断；业务员显示 `姓名(工号)`，部门位于选择项副行。销售服务仍保留 nullable/历史兼容，不能把 Flutter 门禁描述成直接 API 硬约束。详见[订货单公共表头规范](../03-页面/订货单公共表头规范.md)。
2. **订单审核形成经营待收计划，不形成正式 AR**：财务报表“销售订单待收计划”展示订单号、客户、结账方式、币别、订单原币金额、已发运立账、未发运预计待收、到期日及发运策略；它不写 `ar_ap_ledger`、不写总账，也不读取汇率或换算人民币。跨币种金额必须按币种分列或分组，不能在订单阶段合成本币总额。
3. **仓库 `SHIPPED` 才形成正式应收**：发运交接前锁定当前启用币种主档，以收入确认时点的财务汇率计算发运本币金额并立 AR，该汇率冻结为 AR 开账汇率。一次订单可分批发运形成多笔 AR；一次合并发运也可引用同一客户的多张订单。
4. **订单来源是一对多快照**：`ar_ap_source_refs` 按发运明细的真实 `order_item_id → order_id` 链保存销售订单 UUID、单号和本次原/本币金额，禁止把多订单压成一个头字段，也禁止按单号、客户或日期猜历史关联。
5. **折扣改单口径修复**：已审核订单改量继续按 `数量 × 主档锁价 × 折扣` 重算原币，不读取订单汇率或生成新的订单本币事实，防止折扣订单改量后金额放大。
6. **报价转订单不猜本位币**：报价本身无币种时，只接受唯一启用 `code=CNY` 的主档；无 CNY 时才兼容唯一启用且名称精确为“人民币”的主档。缺失或重复均失败关闭，由财务修正主档。

界面同时删除订货单发运策略选择框下的解释小字；字段本身及服务端 `REQUIRE_COMPLETE` / `ALLOW_PARTIAL` 规则仍保留。发运策略为空的历史兼容不应被当作新单可不选的依据。
