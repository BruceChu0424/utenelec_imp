# ADR-145 仓库主档单主仓与禁用不可选

- 日期：2026-10-04。
- 状态：已接受(本地源码实现，V798；8085 克隆库真实接口、Testcontainers 迁移测试与 Flutter 页面测试验证)。
- 取代/后置覆盖：V476(2026-09-04)「新增仓不选上级=独立顶层仓、任何顶层仓都能当上级」；V587/V590「货品所属仓库只要求存在且未删除，不限叶子、允许父仓/停用仓」；[UtenFilterPickerField](../02-组件库/UtenFilterPickerField.md) 与仓库侧滑面板「查询口径不做可选性裁剪，禁用/不记账仓也能单独看」(2026-09-11)；[32-即时库存](../数据迁移/32-即时库存.md)「指定幻影仓下拉可选」；V540「停用叶仓的既有库存继续参与分析/齐套」退化为历史兜底(停用前置条件生效后不会再出现停用仓上有库存)；[ADR-131](ADR-131-车间整批领料与盘点计耗.md) 「内料仓名字被占用时追加 ({主仓名})」。
- 相关：[ADR-073](ADR-073-本批物料履约与同主仓分仓领料.md) 同主仓分仓领料、[ADR-115](ADR-115-仓库负责人与仓库通知按仓分发.md) 仓库负责人、[ADR-151](ADR-151-表单草稿回到初始值单重参数结构化契约与入库登记单批合一.md) §4 守卫文案映射；后续 ADR-146(不良品仓业务规则与可用量单一口径)、ADR-147(车间内料仓开通单一真源)、ADR-149(仓库数据范围)在本形态上展开。
- 用户问题(2026-10-04)：「仓库很乱，有同名的、有的禁用有的在用」「以前为了禁用的也能选放开过一次，更乱了」「只有仓库(14年版)是主仓，其余全是它的子仓；仓储部负责人管主仓，每个子仓一个负责人」「老系统只能禁用不能删，以后迁数据禁用/删除的旧仓不要迁，旧数据能对上的就迁，对不上没用的就不要」。

## 1. 事实

- 测试服务器 11 个仓里只有塑胶/包材/五金车间和两个内料仓挂在 001 下；五金仓库 C01、成品仓库 C04、原材料不良仓 002、成品不良品仓 C0401、轨道车间 01 各自是独立顶层仓，以 001 为主仓的物料分析、主仓安全数预算、主仓负责人范围都看不到五金和成品库存。原因是 `migrate_warehouse.sql` 每次重导先 `DELETE FROM warehouses` 再按老库平铺插入(老库 ParentID 全是 0)，并照搬老库状态：C01 在老库 2014 年起就是禁用，于是每次重导都被重新置成禁用，用户 10-04 又手工启用了一次。V476 的层级种子只在 V476 执行时跑过一次。
- 5248 个货品的所属仓库指向禁用的 C01：`import_product_lists.py` 按名称匹配仓库时不看状态；所属仓库的两个写入口只校验「存在、未删除、不是内料仓」，前端两个所属仓库入口用的是查询口径面板(`allowParent: true`)，主仓、禁用仓、不良品仓都能选到；入库自动学习还会把所属仓库翻成不良品仓。所属仓库是禁用仓时，入库默认仓、内料仓候选来源都取不到值。
- 「同名仓」的来源：老库单据迁移给已删除的仓补建「(迁移自动补录)」存根(采购/销售的存根还是「使用+参与核算」，会出现在所有新单下拉里；委外的存根状态写成 `'in-use'`，违反状态约束)；多主仓时内料仓按「车间 × 主仓」建，出现「X内料仓 (成品仓库)」这样的变体。
- 停用仓库有两条入口(仓库资料的编辑/启停，主档批量启停)，都不检查库存、货品归属、未结预留、是否主仓；正是这个缺口让「禁用仓上留着库存」，V540 只能事后补。

## 2. 决定

### 2.1 形态：唯一主仓 + 直属子仓，只有两层

- 主仓 = 编号 001「仓库(14年版)」，只作汇总、负责人范围和导航，不能记账、不能被任何新单选中。其余仓(五金仓库 C01、塑胶仓库 XW01、包材仓库 XW02、五金车间 XW03、成品仓库 C04、轨道车间 01、原材料不良仓 002、成品不良品仓 C0401、各车间内料仓)全部是它的**直属子仓**。
- 唯一主仓只在数据库定义一次：`fn_warehouse_root_id()` = 编号 001 的未删除仓；没有 001 时取唯一的未删除普通顶层仓(全新部署第一次建仓、彩排夹具)；判断不了返回空。
- 服务层(`WarehouseService` + `WarehouseMasterRules`)：新建/编辑时上级仓库由服务端补成主仓，请求里写别的仓直接拒绝(「上级仓库只能是主仓「仓库(14年版)」，仓库只有主仓和子仓两层」)；主仓自己没有上级；主档没收敛(多个顶层仓、没有 001)时只允许编辑、不许新建。名称按比对键 `fn_warehouse_name_key`(去掉全部空白含全角空格、全角括号转半角、不分大小写)在未删除范围内唯一。
- 数据库守卫 `fn_guard_warehouse_master_lifecycle`(BEFORE UPDATE OF status, is_deleted, parent_id, is_defective)：子仓不能改成顶层、只能挂在顶层仓下、自己有子仓时不能再挂到别人下面。「唯一顶层」与「名称唯一」不做成数据库硬约束：大量测试夹具按需建多个顶层仓做跨主仓隔离，服务层 + V798 事后断言足以守住生产数据。

### 2.2 「新单能不能选它」只在服务端算一次

- `fn_warehouse_is_good_stock_leaf(id)` = 启用、参与核算、作业叶仓、祖先链全部启用、不是车间内料仓、不是不良品仓。仓库字典 `/master/warehouses/dict`、列表与详情每行下发 `defective` 与 `selectableForNew`(就是这个函数的结果)。
- 前端 `WarehouseSelection` 只认服务端的 `selectableForNew`，不再自己推算启用/记账/叶仓；缺这个字段一律按不可选。选仓分两种用途：运营口径(`WarehouseUse.good`，所有「新选」入口，含货品所属仓库)只列可选子仓、主仓只作分组/导航；查询口径(`WarehouseUse.query`，即时库存/货架/流水等看盘)任意层级可选(主仓 = 自身 + 全部子仓聚合)，**默认不列已停用的仓**，当前选中值总能回显；历史单据仍按字典显示停用仓名称(字典保留禁用仓)。ADR-146 再把用途细分为良品入/出、不良品入/出、盘点、查询，形状不变。
- 撤销 2026-09-15「所属仓库允许选父仓/禁用仓」与 2026-09-11「查询口径不裁剪」两处放开。

### 2.3 退出新选与停用/删除的前置条件(只有一个定义)

一个仓有四条路会「退出新单可选」：停用、删除、改成「不核算」(`is_accountable` 真改假)、改成不良品仓。四条路走同一组前置条件，否则「货品所属仓库一定是可选良品子仓」的不变量会从没设守卫的那条路绕开(2026-10-05 审查发现：改成不核算返回 200，5248 个货品的所属仓库仍指向它，入库默认仓、内料仓来源随之变空)。

`fn_warehouse_selection_exit_blockers(id)` 返回给人看的原因，空数组 = 可以退出新选：

1. 还有 N 种货品有库存(`stock_balances.qty <> 0`)；
2. 还是 N 个货品的所属仓库；
3. 还有 N 条没结束的库存预留(未结量大于 0)；
4. 是已开通的车间内料仓 / 还是某个内料仓的发料来源仓(V800 起由开通表 `workshop_bins` 判定，取代 V798 的「已开启整批领料的内料仓」)。

`fn_warehouse_retirement_blockers(id)` = 「它是主仓(全公司仓库的汇总), 不能停用或删除」(主仓无条件拒绝，不看它下面有没有子仓；测试夹具里下面挂着子仓的其它顶层仓同样拒绝) + 上面四条。改成不核算 / 改成不良品仓只看上面四条(主仓从来不是可选子仓, 它的核算标记不影响任何新选)。

`WarehouseService.update/changeStatus` 与主档批量启停 `MasterLifecycleService.batchStatus` 先按它做中文预检(「仓库「塑胶仓库」现在不能停用: 还有 3 种货品有库存; 还是 12 个货品的所属仓库」「仓库「五金仓库」现在不能改成不核算: 还是 5248 个货品的所属仓库」)，逐条返回；数据库守卫 `fn_guard_warehouse_master_lifecycle`(监听 status、is_deleted、parent_id、is_defective、is_accountable)用同一函数兜底；数据库守卫用同一函数兜底(`RAISE ... USING ERRCODE='23514'`，ADR-151 §4 原样回显 422)。删除先走既有引用守卫 `MasterReferenceGuard`(逐条列出是哪些货品/单据在用它，更具体)，引用守卫之外的前置条件再按本函数说明。停用必须先把库存转走、把货品所属仓库改到别的子仓——这是有意的：停用仓不再可能留着库存，V540 的「停用叶仓既有库存仍可动用」退化为历史兜底。

### 2.4 仓库用途(良品仓/不良品仓)是一等属性

- 仓库资料可以维护「仓库用途」，列表新增可筛选的「仓库用途」列。约束：不良品仓只能是子仓、不能是车间内料仓；有库存时不能改用途(两个方向)；改成不良品仓与停用同一组退出新选前置条件(§2.3：货品归属、未结预留、内料仓开通与来源仓)。服务层预检 + 同一守卫兜底。
- 不良品仓的业务规则(哪些单据能进出、可用量不算它、专门的「转不良品仓/不良复判转回」通道)归 ADR-146。

### 2.5 货品所属仓库只能是可选良品子仓

- 货品资料与物料分析两个写入口只在**值变化**时按 `fn_warehouse_is_good_stock_leaf` 校验(原样带回的旧值不重新判定)；数据库守卫 `fn_guard_goods_ordinary_owning_warehouse` 改为「新写入或值变化时」同一判定。
- 入库自动学习(`GoodsOwningWarehouseSyncService.syncOnInbound`)只学可选良品子仓：进不良品仓、停用仓不翻转所属仓库，也就不会被所属仓库守卫打断过账。
- 两个前端入口(货品详情、物料分析各表的所属仓库列)改用运营口径面板。

### 2.6 车间内料仓

- 仓库资料不能新建内料仓、也不能把普通仓改成内料仓或摘掉标记(由「车间内料仓」页管理，W3 由开通命令接管建仓)；表单里内料仓标记与所属车间只读。
- 单主仓后一个车间只有一个内料仓，名字固定「{车间名}内料仓」，不再追加「 (主仓名)」；名字被占用时直接拒绝，由人改名，不造同名变体。

### 2.7 存量收敛(V798)

锁表后：其余未删除普通仓一律挂到主仓下(内料仓必须已在主仓下，否则中止交人工)；主仓本身置「使用」；禁用但仍被货品归属或还有库存的仓改回「使用」(克隆库与开发库里的 C01)；禁用且全部外键列与物料分析参与仓都没有引用的仓软删除；货品所属仓库指向主仓/不良品仓/不可选仓的置空(不猜仓，由入库学习或人工重填)；规范化名称重名时中止并列出；最后断言恰好一个顶层仓、其余都直挂主仓、没有「禁用却有库存或被归属」的仓。迁移说明见 [V798](../数据迁移/V798-仓库主档单主仓.md)。

### 2.8 老库迁移：只按审过的仓库对照表

- 新增入库的 `server/legacy_migration/warehouse_crosswalk.csv`(不含个人信息)，每个老库仓 id 写清去向：`SPLIT`(老库主仓 132 → 001：单据头记主仓，库存明细/流水/余额按货品所属子仓拆分)、`KEEP`(在用仓 → 同编号子仓)、`MERGE`(老库已禁用的 123 五金仓库 → 并入在用的 C01，不单独建行)、`DROP`(老库已删除的 119/120/121/124/125/127/128/129/130/131 → 不建仓)、`TARGET`(新 ERP 才有的塑胶/包材/五金车间子仓)。
- `migrate_warehouse.sql` 不再 `DELETE FROM warehouses`，按编号增量写目标子仓，上级固定主仓，状态一律「使用」，不良品仓按对照表(002、C0401)标记，不再按名称 `LIKE '%不良%'` 猜；库里还留着旧存根时中止。各单据脚本删除「(迁移自动补录)」仓库存根段，仓库一律经对照表解析；委外脚本单位/颜色/币种存根的 `'in-use'` 改成合法状态。
- 「对不上的就不要」：落在 DROP 仓上的库存单据、余额和采购收货单不迁；老库主仓上所属仓库为空的货品明细/余额不迁(可选参数 `UTEN_LEGACY_UNASSIGNED_WAREHOUSE_CODE` 指定兜底子仓；仓库单据模块里才补建的历史货品锚同样落到兜底子仓——落仓子仓表在货品补录之后才建)；全部逐条记进 `bootstrap_warehouse_exclusions`，全量导入按它扣减行数对账、写进运行记录并导出 `data/import_report/warehouse_exclusions.csv`。销售、委外、采购申请/退货若落在 DROP 仓上，迁移中止交人工(老库目前没有这种单据)。
- 全量顺序：仓库目标主档 → 主档 → 货品 → 货品所属仓库(`--goods-owning-warehouse`，人工清单由 `import_product_lists.py --emit-owning-csv` 生成) → 交易模块。`import_product_lists.py` 只匹配「主仓 001 下、启用、非内料仓、非不良品」的子仓，找不到报错写报告，不再补建存根；根仓明确取编号 001。身份核验不再把仓库引用当历史锚点。导入映射协议升为 `bootstrap-v13`。

### 2.9 同主仓判定保留

`fn_warehouse_same_main`、`WarehouseScopeService`、物料分析参与仓等「同主仓」引擎保留多主仓能力(测试夹具大量依赖)，在单主仓的生产数据上恒为真。是否删减留待后续决定；不良品仓不能因此混进同主仓可用量，由 ADR-146 用统一可用量口径排除。

## 3. 同行做法(出处)

- SAP：工厂(plant)下挂库存地点(storage location)两层组织；库存地点被物料主数据/库存引用时不能直接删除，先清库存、改主数据。
- Odoo：仓库下挂库位，库位里还有在库数量时不允许归档(archive)，必须先移走库存。
- 金蝶云星空：仓库有即时库存时不允许禁用；新单选仓只列启用的仓，历史单据仍显示原仓名。

共识：仓库层级是组织结构不是单据随手建的；「能不能被新单选」由主档状态统一决定；停用/删除前必须先清库存、改引用。本 ADR 与之一致，并把判定放在数据库函数里只定义一次。

## 5. 已知限制

- 红冲/反向过账仍可能把库存冲回一个已停用的仓(过账内核只认流水类型与仓库类别, 不看停用状态)：停用前置条件生效后, 只有「停用之后又红冲了停用之前的入库/出库」才会出现; 查询口径面板默认不列停用仓, 但仓库字典保留它, 历史单据与即时库存的「显示停用仓」仍看得到。要彻底杜绝需要在红冲入口按目标仓状态拒绝, 留待红冲规则整体评审时决定。

- 没有 001、又有多个顶层仓的库(只出现在测试夹具)：服务层不许新建仓库，提示先整理层级；V798 在这种存量上直接中止。
- IQC/FQC 判不合格是否进不良品仓库存不在本 ADR 范围(ADR-090 不变)。
