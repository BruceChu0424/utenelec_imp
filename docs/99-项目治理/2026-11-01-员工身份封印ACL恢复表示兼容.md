# 员工身份封印：恢复后的默认所有者 ACL 表示

## 已确认根因

最终公司备份克隆从 V970 执行审核源码 `9477b9c7a50677f524048736d844ccbeafccacae` 的迁移时，V971–V976 成功，V977 的严格旧目录封印检查拒绝继续；V977 已事务回滚，克隆保持 V976/902 条成功迁移。没有 repair、生产迁移或重置备份数据。

`pg_dump/pg_restore` 不保留“恰好等于默认所有者权限”的显式 ACL 数组，而恢复为等价的 `NULL`。旧 V964/V965 的封印同时包含原始 ACL 表示，因此表示变化会改变目录 SHA，即使有效权限完全相同：

| 目录 | 原封印 | 恢复后的原始目录 | 精确差异 |
|---|---|---|---|
| V965 工号复用 | `e2c48b5d953eff8dcce329556e596c9e1a6bcd461516a85098bf51adce6e29d1` | `89a06250910e8d175c568186730f89f6b52c2c046412081b7a39bec67ca6cf2a` | 三个私有表 ACL 从显式所有者默认数组变为 NULL |
| V964 员工身份合并 | `94321e9a42a3b85d73d113546db9432e9677584548fcd1560f2c89d31404918a` | `e27e73987f5c300a034d3cca6ac35bb6069033f439a59380185879b325e13bd7` | 五个私有表 ACL 的同类变化 |

独立只读候选仅展开这八处 NULL，其他目录 JSON 字节不变，即精确命中原封印。隔离事务中仅给现有所有者登记其本来具有的默认权限后，两份**原始**目录也都命中原封印；对所有 `pg_roles` 逐表十四种权限及授权选项检查，前后完全相同；两个封印记录未改写。随后按真正的员工表所有者运行原 V964/V965 安装器，二者均完成严格 no-op adoption。整个证明事务已回滚。

新安装测试库的真实 dump/restore 还精确复现五个触发器函数的同类表示变化：原本为 PostgreSQL 默认的“PUBLIC 与所有者可执行”，恢复后 ACL 为 NULL。差异仅为 `fn_employee_code_reuse_evidence_immutable()`、`fn_finish_employee_code_reuse_claim()`、`fn_guard_employee_code_claim_insert()`、`fn_guard_employee_code_release_insert()`、`fn_guard_employee_code_reuse_legacy_import()`；定义与其余字段不变。公司克隆这五个函数为非默认的 owner-only ACL，恢复仍为非 NULL，不需要也不允许借此增加 PUBLIC 执行权。

## 有限实现与唯一维护入口

公共入口为 [restore_employee_sealed_owner_default_acls.sql](../../server/maintenance/restore_employee_sealed_owner_default_acls.sql)。该脚本是直接由现有员工表所有者执行的 DO 块，不安装持久函数，不增加 `SECURITY DEFINER` 接口，不修改角色成员关系、实际业务数据或封印记录。

范围仅为三个 `employee_code_reuse_*` 表、上述五个 merge 私有表，以及上述五个固定零参数、返回 `trigger` 的函数。必须满足：

1. 调用者和八表所有者均是现有员工表所有者；两个安装器 payload SHA 仍与原始审核源码一致。
2. 独立使用原 V964/V965 的完整目录表达式计算目录，不能信任一个可能被替换的数据库摘要函数。
3. 原始目录已经匹配时直接 no-op。否则只允许固定对象的 NULL ACL 分别展开为 `acldefault('r',owner)` 或 `acldefault('f',owner)`，**完整候选必须精确匹配既有原封印**，才允许登记所有者已经具有的相同权限。未知非 NULL ACL、函数属性、列级 ACL 或 RLS 状态不在兼容范围。
4. 物化前后逐项比较全角色表权限十四项，以及五个函数的 EXECUTE/授权选项；两份封印记录保持完全不变，最终原始目录必须匹配原封印。任一异常使整个 DO 事务回滚。

未应用的 V977 嵌入同一个 canonical DO 块，然后继续原有“仅改变一个已审核函数定义、CAS 更新目录封印并恢复不可变守卫”的前向逻辑。通过 `python scripts/sync_employee_seal_restore_migration.py` 校验嵌入字节；仅未发布时可加 `--write` 生成。V964、V965 和两份原安装器 payload 均不修改。

## 后续备份恢复收尾

已经应用 V977/V980 的数据库再次 dump/restore，仍可能出现相同 NULL 表示；不能指望已应用的 V977 再执行一次。

批准的恢复顺序是：恢复原角色与成员关系 → 恢复数据库且保持流量关闭 → 核实恢复目标、源版本和原封印记录 → 用**该审核版本的 canonical SQL**、以真实员工表所有者执行收尾 → 验证原始目录封印及原安装器 no-op adoption → 完成其余恢复验收后才开放流量。此入口只负责上述八表的等价表示，不代替完整恢复、附件、密钥或应用验收。

未知 ACL、函数、所有者、触发器或 payload 变化必须拒绝；不能更新旧封印以接纳未知状态，不能修改 Flyway 历史，也不能重放旧安装器 payload 去覆盖当前目录。发布后该 helper 与 V977 的嵌入字节均冻结；新增兼容规则须另行审核、版本化并使用新的前向迁移。

`deploy/setup/harden-existing-postgres-roles.sh` **不是本问题的恢复收尾入口**：其现有 620–638 行会把对象所有权重分配给 `uten_owner`，并先执行面向业务对象的广泛授权；私有表列表并不覆盖这里的八表。直接运行会改变封印所覆盖的所有者/权限，不能拿它证明等价恢复。本次不扩大该脚本授权或修改其职责。
