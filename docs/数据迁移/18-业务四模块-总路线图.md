## 〇、用户钦定原则（所有模块共同遵守）

> 原文摘录：**前端保留原有操作体验、后端完成架构重构升级**；既保证老用户零学习成本，也从根源解决性能衰退/数据冗余/扩展困难，为后续十几年数据增长打底。

落地为本项目已验证的六条范式（采购/仓库已实证，本批四模块**沿用不改**）：

1. **分类树**：基础邻接表 + 闭包表混合（已用于 material/client/supplier/mould 分类）。本批四模块的分类（如 M_Style 收付款类别）同理。
2. **垂直分表**：基础资料主表（窄、高频）+ 扩展表（静态/兼容字段，详情按需关联）。本批新增主档（账户、收付款类别）沿用。
3. **真外键骨干 + 文本占位**：单据链路用单值 FK（如 S_OutItem.OrderID→S_OrderItem），老库逗号串多值溯源（SOrderNo/BomItemID varchar(8000)）降级为 `source_doc_no` 文本。
4. **流水 + 余额模型**：所有出入库统一走 `stock_movements`（分区）+ `stock_balances`（实时余额），取代老库 StockGoods 按月分列台账。**销售/委外/生产的库存效果全复用 V45 已建骨架**。
5. **物化视图**：十几年百万级明细 → 月度上卷物化视图（CONCURRENTLY 刷新），报表毫秒级。
6. **兼容层 + 编号规则**：保留老库 `legacy_id` 溯源 + 老单据号；新库用规则生成器统一编码；三阶段推进（兼容复刻 → 性能优化 → 功能迭代）。

> 这六条在 [15][17] 已有完整论证，本档不重复，只在各模块指出**差异点**。

## 二、全链路真外键骨干（新库要建立的关联）

> 老库用逗号串 varchar + 触发器游标回写；新库用单值 FK 骨干 + 文本占位。这是"业务零割裂、底层重构"的核心。

```
销售订货 S_OrderItem ──(S_OrderID)──▶ 生产计划 F_PlanItem          （订单驱动生产）
生产计划 F_PlanItem  ──(S_OrderID)──▶ 销售订货 S_OrderItem          （双向骨干）
销售出货 S_OutItem   ──(OrderID)───▶ 销售订货 S_OrderItem           （出货冲订单 RQTY）
销售退货 S_WithdrawItem──(OutID)───▶ 销售出货 S_OutItem             （退货冲出货）
            └────────(OrderID)────▶ 销售订货 S_OrderItem

委外进仓 E_InItem     ──(OrderID)───▶ 委外订货 E_OrderItem
委外退货 E_WithDrawItem──(InID)─────▶ 委外进仓 E_InItem
委外材料退货 E_SWithDrawItem──(EOutID)─▶ 委外材料出仓 E_SOutItem
委外材料损耗 E_SWasteItem──(OutID)───▶ 委外材料出仓 E_SOutItem

采购（已落地 V44）：订货→收货→退货 真FK骨干已建

钱流：
  M_In.BillID  ──▶ M_Get（收款单头）       M_Get.RecAcc / M_Paid.PaidAcc / M_DPaid.PaidAcc / M_OGet.RecAcc ──▶ M_Acc
  M_Out.BillID ──▶ M_Paid（付款单头）      M_*.StyleID ──▶ M_Style（收付款类别）
  销售收款核销 M_In ──(关联 S_Out/S_Order)──▶ 应收冲销
  采购付款核销 M_Out──(关联 P_In/P_Order)──▶ 应付冲销   （核销关系存 M_AllCheck 或独立核销表）
```

> 销售/委外/生产/采购明细中的 `SOrderNo`/`BomItemID`/`FPlanNo`/`POrderNo`/`EONo` 等多值 varchar → 统一降级为 `source_doc_no TEXT`（合并占位），骨干链路用真 FK。新库四模块互相上线后，可补关联表回填精化（三阶段三期）。

## 六、迁移执行约定（复用采购/仓库范式 · 幂等可重跑）

1. **导出**：`export_legacy.ps1` 增段（S_/E_/F_/M_ 主+明 + M_Acc/M_Style 主档），输出 `data/*.csv`（真实数据，**不入 git**，已 .gitignore）。复用 RFC4180 管道符转义。
2. **灌数**：每模块一个 `migrate_<module>.sql`（幂等）：
   - 开头 `TRUNCATE` 同链表（被引用关系一起清，重跑安全）。
   - staging（真实类型）→ `\copy` → INSERT 时 JOIN 主档 `legacy_id` 映射出 UUID。
   - **缺失基础资料自动补录**（goods/colors/units/warehouses/currencies + 本批 accounts/payment_styles）：
     goods 只允许为非零历史业务引用建立 `auto_created=true` 身份锚；不得进入选择器、活动 BOM 或 MRP，
     校验必须读标志位而不是中英文名称（V177/V181）。
   - 真FK骨干用 `JOIN ... WHERE legacy_id=` 映射；多值 varchar 降级 `source_doc_no` 合并文本。
   - 人员字段（MakeID/ApproverID/WorkerID/SellerID…）→ 留空（B_Worker↔employees 无对齐，同采购 [15] §九），后续建 `worker_legacy_map` 回填。
   - 结尾校验段：各类主/明细数、链路挂接数、孤儿数。
3. **入口**：`migrate.sh` 已支持 `--sales` / `--subcontract` / `--production` / `--finance` 等单目标。
   一次只能执行一个目标并追加 `--confirm-destructive`；完整首次引导使用 `--bootstrap-all`。这些脚本会重建目标模块，不是切流后的增量同步。
4. **校验**：总数一致 + `legacy_id` 覆盖 + 回写量 SUM 校验（如 `SUM(出货明细.qty) GROUP BY order_item_id` = 订单 `shipped_qty`）+ 抽样字段比对。
