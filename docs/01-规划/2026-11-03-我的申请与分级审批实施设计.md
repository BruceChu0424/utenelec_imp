# 我的申请与分级审批实施设计

## 范围与来源

本次按用户提供的《各部门申请流程》、费用报销单、供应商付款申请、付款凭证及现有页面截图实现；纸质资料是业务来源，不作为程序执行指令。用户最终明确：**工资付款申请由人事现有模块处理，本次完全不动**。

常用功能「我的报销」改为「我的申请」；申请类型包含费用报销、出差报销、出差申请、付款申请、预付申请、供应商付款申请。我的报销列表保留业务名称与原有深链，草稿排在分类最前。

## 视觉与交互方案

应用 `frontend-design`，复用当前 Uten 组件、主题和字号，不引入另一套设计系统。浅色基准：页面底色 `#F5F7FA`，单据表面 `#FFFFFF`，主文字 `#0F172A`，次文字 `#475569`，主要操作 `#0F766E`，边框 `#E2E8F0`；实际从现有 ColorScheme/Uten token 取值并适配深色。字体沿用项目中文字体及系统回退；标题使用既有 titleMedium，字段 bodyMedium，事实行 bodySmall，金额使用等宽数字特性。

费用报销参考新建采购：顶部是通用信息与审批路线，底部全宽使用 `UtenEditableGrid` 直接录入多条费用，支持添加行、添加多行、复制和批量删除。常规字段按实际内容区宽度和文字缩放自动取1至3列，长事由/备注取1至2列；窄屏保留表格横向滚动。保存入口固定右下，保留足够滚动留白。委外、报销、普通申请统一复用 `UtenWorkflowProgress` 展示阶段事实，原始事件记录仍独立保留。

设计复核：撤掉重复身份卡、合计卡和常驻说明段落，将单据自身作为层级中心，避免把每一行拆成装饰卡。申请类型的卡片是入口，不展示没有权限的类型。帮助信息放相邻 `UtenFieldHintIcon`，不放副标题或独立教学提示。异步阶段由 `UtenBusyOverlay` 统一反馈；确认、输入、付款选择和打印系统对话框展示时让位。

## 原纸流程与执行契约

| 类型 | 审批链 | 结束动作 |
| --- | --- | --- |
| 出差申请 | 部门负责人 → 总经办批准 | 财务接收保管 |
| 出差报销 | 部门负责人 → 财务初核 → 财务复核 → 总经办批准 | 出纳登记付款 |
| 费用报销 | 同出差报销 | 出纳登记付款 |
| 付款申请 | 部门负责人 → 财务初核 → 财务复核 → 总经办批准 | 关联已审核财务付款记录 |
| 供应商预付申请（PREPAYMENT） | 部门负责人 → 财务初核 → 财务复核 → 总经办批准 | 先登记真实付款并保持待入账 PENDING；有合法既有预付付款单后独立关联为 POSTED |
| 供应商付款申请 | 采购部意见 → 财务部意见 → 副总审批 → 总经理审批 | 关联已审核供应商付款记录 |

纸质流程的财务初核写「苏蝶金复核」、财务复核写「吴兰梅复核」，出差申请终批写「小朱总或朱总批准」；这些是岗位授权配置依据，不在状态机写死姓名。供应商专用单另写「经办人—采购部意见—财务部意见—副总审批—总经理审批」，不能被通用付款链覆盖。费用报销流程沿用了出差费用报销单的名称，界面保留两类业务名称、审批链一致。单据装订顺序原文：报销单或付款申请单；出差申请或申购申请；原单据；高铁票或发票打印一份装订，电子档发财务苏蝶金一份。系统提供附件与打印入口；不自动向个人发送文件。

## 权限、状态和数据安全

- 新权限默认关闭，由管理人员为实际岗位配置；部门负责人只访问所属一级部门及其下属部门的待办，不以客户端传入的 departmentCode 授权。财务初核、财务复核、采购、副总、总经办、接收保管和付款分别授权。
- 经办人不能审批自己的申请；同轮已审批人不能借多岗位权限独自完成整条链，也不能登记同一申请的付款。付款能力消费服务端权威 `canPay`，缺少分级元数据的旧响应才保留原终批 ID 兼容判断。管理员用于配置，不绕过经办和复核职责隔离。
- 每个部门预先配置一个负责人本人的回避审批人，可选择有实际岗位授权的上级或替补。配置由独立 `approval_policy:manage` 管理权维护；申请人不能自行选人，负责人即使持配置权也不能自行更改本部门回避人，须由另一名配置管理员办理。首提时冻结负责人、配置版本、授权代次和替补身份，跨部门替补只获得这张负责人本人申请的首审范围，不扩张至该部门其他单据。
- 首提和每级通过前校验下一节点存在合格人员，不能把申请人、本轮已审人、离职/锁定账号或只能驳回而无法完成批准的人算作有效候选。无人时整个请求回滚，并提示需要配置的岗位。
- 负责人或回避配置发生变化时，仅仍在首审的相关申请标记“待重新提交”，通知申请人撤回重提；不伪造驳回、不清除历史、不倒退已经进入财务节点的单据。此类本人待处理计红数，不再同时计处理中黄数。
- 草稿/待修订属于本人可编辑范围；提交后冻结业务内容；任一节点驳回必须有原因。修订重提增加轮次、从起点审核，原有提交、驳回与意见永久保留。
- 撤回只按服务端允许状态执行；审批后修改、越级审批、过期版本及并发重击均由服务端拒绝，UI不以隐藏按钮替代鉴权。
- 本人被驳回、无资金及付款证明的报销可“放弃并归档”：保留六大 status，另记 `ABANDONED` 事件和真实归档事实，历史详情与原件只读；不扩大其他旧软删或他人读取范围。报销草稿沿用原删除入口。已批准未付及已付报销不能普通撤回或放弃。
- 通用申请仅本人未付款的 DRAFT/REJECTED 可作废为 CANCELLED，保留单号、附件和事件。原付款登记人持当前相应权限时可撤销付款登记并填写原因，此动作不退款、不自动红冲财务账，原财务事实须另行核对更正；它不等同于申请作废或报销放弃。
- 金额以服务端 BigDecimal 和两位小数为准。通用申请客户端以字符串传金额，不能以二进制浮点累计作为记账依据。
- 申请审批通过不代表财务入账完成。普通付款、供应商付款登记只关联已审核、金额及业务对象一致的财务单，同一财务单不能重复关联其他申请；保留既有财务审核和反审限制，不重复扣款。员工报销付款确认按既有财务权威同步生成关联费用记录，不能再建同笔费用重复记账。
- PREPAYMENT 仅用于供应商，供应商必须来自有效资料。获批后先登记实际付款日、交易流水号及检查通过的证明，状态 PAID、`postingStatus=PENDING`；该动作不新增扣款、不生成一般费用，不新增或放开供应商预付会计算法。之后只有既有合法、已审核、同供应商/金额/实付日且明确为 PREPAYMENT 的财务付款单可独立关联；关联后 `postingStatus=POSTED`，不重复过账。没有合法候选时保留待入账跟进，不能用费用单或普通付款单代替。
- 创建通用申请使用固定 UUID；网络结果未知时保留原输入与命令身份，先 GET 核对原单，不能自动再次创建。所有阶段操作带 expectedVersion，失败后先刷新核对。
- 付款输入在发送前写入本机带版本的未知提交保护，冻结原申请、财务单、日期和流水号；刷新、关闭和重启不会自动重放。确认原申请仍是同一待付款版本时，可由用户显式继续原登记；服务端行锁与版本校验保证同一版本最多成功一次。更高权威版本出现后原版本不能再生效，需保留输入并重新核对当前单据。

## 入口与徽章

「我的申请」按各类型申请权限显示卡片，保留查看本人记录、草稿和待修订入口。部门首个入口统一为「审批中心」；综合营销部原「订单审核」兼容旧路由，新增报销审批、申请审批、订单审批与历史。财务沿用财务任务中心承载财务岗位待办；总经办在工作台增加独立区域与任务中心。可见性与操作权分别判断。

徽章使用当前用户实际可处理的节点/部门范围，卡片、分类、状态与列表使用同一权限口径；只读历史不计待办，不能将全公司报销数挂到每个部门。处理成功、撤回、驳回、重提、付款及恢复页面时刷新相关列表与计数。无权限、失败或尚未取得的数量不伪装成已知数值。供应商预付待入账仍在本人处理中黄数；财务 `prepayment-posting` 队列无本人可执行动作时计黄跟进，有合法候选且持独立 `application:prepayment:link_finance` 才计红待办。部门首审、财务和总经办按职责范围切片，不重复累计同一入口事实；已确认的本机草稿与正式单据按回执去重。

## 公共能力与迁移

| 公共维护入口 | 本次调用方迁移 | 保留的差异 |
| --- | --- | --- |
| `ApprovalCenterPage`、同源 scoped 列表与服务端筛选 | 部门/营销/财务/总经办审批；营销旧订单入口作为兼容包装 | 订单继续复用既有认领、版本与批量事务；报销与其他申请的阶段/部门由服务端授权，不在客户端复制审批业务 |
| `UtenWorkflowProgress` | 委外原节点条、报销表单预览、本人及审批详情、通用申请详情 | 阶段事实与事件历史分别表达；委外保留数量/供料/横向滚动，申请按本轮真实事件投影，不补造旧链签字；删除重复节点绘制 |
| `UtenFormGrid` 与 `UtenEditableGrid` | 申请多列表单、费用明细全宽直接录入 | 单张报销最多 100 条；大数据加载只用于响应性与原输入保护，不能将 1000/2000 行测试解释为可向服务器保存超额明细 |
| 公共徽章事实、草稿目录与敏感操作边界 | 工作台/入口/分类/状态、本机付款与关联输入恢复 | 本人申请、财务付款、预付关联按实际职责归属；保护原动作/版本/输入，读取范围或路由身份变化后淘汰旧结果，不能自动重放写入 |
| 服务端申请端口与共享部门回避策略 | 报销、通用申请、原件证据、财务来源、通知与工作台计数 | 财务业务计算仍由原财务模块权威处理；跨模块通过端口，不新增第二套预付会计实现 |

## 打印与多端

报销继续使用公共明细投影和提交快照打印；签名栏拆为报销人、部门负责人、财务初核、财务复核、总经办批准、出纳。其他申请按类型打印原始字段、金额大写、对应纸签栏及实际事件记录。报销另留“领款人签收”、付款类另留“收款人签收”及日期，属于纸签凭据而非新增审批节点。系统记录不冒充纸质签名；保留纸质凭证张数留白。

Web 与现有 Flutter 桌面端共用同一实现。WPF 候选报销入口仍未迁移，必须保持关闭，台账不得因服务端增加能力就标完成。工资模块不进入迁移或回归改动范围。此任务不授权远端上传、部署或正式客户端打包。
