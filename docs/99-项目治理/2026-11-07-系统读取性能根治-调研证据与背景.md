## 二、任务中心/货品/徽章慢的四层根因（实测数字）

### 根因 1：导入单据判定在读取路径逐行图遍历（总根因）

- `fn_imported_business_document_row`（V926 定义、V933 BFS 去重版现行）：每次调用动态查 pg_trigger/pg_constraint 取 FK 边，逐祖先 `EXECUTE ... to_jsonb(parent)` 整行取回；非导入行必须走完祖先图才返回 false（实测热 1.8ms/行、冷 10.6ms/行；导入行 0.02ms）。
- Java 侧 443 处引用 / 92 文件经 `ImportedBusinessDocumentScope`（nativeTable/nativeRowsByKey/nativePredicate/predicate）+ `ImportedBusinessDocumentPolicy` 触发；关键调用点：履约 `FulfillmentWorkbenchQueryService.java:87/211/778/826`、车间 `ProductionExecutionWorkbenchService.java:48-49`（注意 :49 的 `'production_material_analyses'` 不是守卫成员表恒 false）、物料分析 `MaterialAnalysisService.java` 8 处、销售 `SalesOrderService.java:749-819`、仪表盘/草稿计数/反审守卫等。
- 公司库实测（同数据同环境对照）：

| 查询形态 | 公司库（V1111，含 typed 预筛） | 本地副本（V946 旧版） |
|---|---|---|
| 履约视图 count（26,428 行） | 610ms | 805ms（冷 5.8s） |
| + 逐行 fn（现网读法） | 560ms | 1.69s（冷 7.6s） |
| 先筛状态再 fn（54ms 形态） | **54ms** | 108ms |
| 徽章 purchaseTask 两条计数 | 8–15s | — |

- **残差实测（2026-11-07，副本库，900s 预算只用 ~4s）**：32 张 NATIVE_TABLES 全部 `inherited_imported=0`——无自身 legacy 键的继承导入行当前为零；260 守卫表中无键列的 207 张里仅 `stock_movements`（56 万行，自带 legacy_id）一张大表，其余空/小表。→ 登记表方案的等价性实测成立。
- 判定真值翻转只可能发生在维护通道（增量导入/FK 图变更/DBA 修复，全部被守卫限制在 `uten_migrator`/超管身份下）：V926 `fn_imported_business_document_maintenance_allowed` = session_user≠'uten' 且（rolsuper 或 datdba 或 uten_migrator）；导入工具 `server/legacy_migration/migrate.sh` 一次性 bootstrap（单事务、重跑返回原回执），增量导入方案未交付。
- 守卫写侧：`fn_guard_imported_business_archive_only` 对 UPDATE 同时遍历 OLD+NEW；触发器 `ENABLE ALWAYS`，挂 260 表（V926:232-250 安装器）。`ImportedDocumentFixture`（test support）正则钉死三条 SQL 形状；`ImportedBusinessNativeSourcePostgresTest` 钉 32 表集合与 EXCEPT 等价；`ImportedDocumentAncestryWalkPostgresTest` 钉"无缓存/UPDATE 翻转即生效/GUC 伪造维护被拒"；`AuditTriggerCoveragePostgresTest` 钉守卫触发器快照；`WorkshopDirectTransferBatchEndToEndTest` 钉单事务守卫调用 ≤59。

### 根因 2：状态/分段 100% 现算 + 全量候选集

- 履约：`task_status`= CASE + `fn_procurement_order_latest_approval_status`(V922 定义，逐行取最新审批) + `fn_procurement_order_reserves_source`(V923 定义) + 终止 CASE；关单 30 天窗口按 `updated_at`——导入重置时间戳导致 10,153/10,315 张已关采购单永驻候选（公司库 F 段实测 cold_closed=0）。`FulfillmentWorkbenchPageRead.sql:70` candidates MATERIALIZED 全量后才筛 status；rowsOnlySql 续页重算全 UNION（实测 6.6-7.2s/页 vs 无 fn 0.5s）。
- 车间（公司服务器唯一跑满 60s 被杀的链路，09:03-09:18 反复"Database deadline reached"+自动重试）：`v_production_execution_workbench_segments`（V696 定义）每行 7 组 LATERAL 聚合 + 2 次齐套函数；投影层每行 `fn_split_batch_empty_issued`×4、`fn_actual_supplement_material_ready`×4、`fn_material_discovery_pending`×6、`fn_execution_start_material_ready`、`fn_segment_bin_material_state`、`fn_execution_segment_material_summary`、`nativeRowsByKey`×3；**排序键 `SEGMENT_ORDER_READINESS`(:742) 对全候选集求值使 LIMIT 失效**；一次加载 4 条同构 SQL；`ProductionWorkshopAssignmentScope` 每行一棵递归部门树；根视图 `v_production_execution_workbench_roots`（V1094）自扫段视图 8 次。2026-11-06 抢修（nativeRowsByKey+刷统计）后开工准备 1.25s，仍 >1s。
- 品质：`WarehouseQualityResultService.typeCounts`(:536) 全部已审收货单聚合；`QualityPendingQueueService` metadata+分页同构 2 次。
- 仓库：出入库任务中心 UNION 分支逐行 `fn_is_production_*`/`fn_procurement_item_inbound_warehouse_id`；metadata/rows 同 CTE 链执行 2 次。
- 历史窗口口径混乱：履约=updated_at（失真）、车间=plan_end_date（计划日期）、销售经理复核 HISTORY/销售阶段/品质结果无窗口。

### 根因 3：徽章 51 来源单事务串行

`WorkbenchBadgeService.compute`(:148-158) for 循环 + `readIsolated`(:213) savepoint；重来源 11 个（workshopTask、productionExecution、qualityResult、subcontractOutbound、salesStage×2 遍、warehouseSalesOutbound、purchaseTask、subcontractTask、productionDraw、productionReturn）。客户端（2026-11-07 核实）：`badge_summary_provider.dart:228` pollInterval=60s 仍存在，但仅"工作台可见"时调度；`badgePollSeconds` 公共设置（SystemSettingKey.BADGE_POLL_SECONDS，默认 60、合法 15-600）可调；实际刷新以登录/进页/写后补拉为主（用户口径：高频自动刷新已删、手动为主）。⚠️ 实施时以此现状为准，不要按"每分钟轮询"旧假设设计。

### 根因 4：客户端"全部到齐才显示" + 每批重入

- `ScopedPagedRead.read`（scoped_paged_read.dart:183-196）fetchComplete 优先；结果在 complete 帧后发布；`loadCompletePagedResult`（complete_paged_snapshot.dart:16-20）有 onBatch/onPage 钩子无人用；maxConcurrentPages 默认 1（上限 4）。
- 服务端 `MasterSummaryReadSupport.streamAuthorized:84` 每批重入 `GoodsService.list`（每批 6 组辅助查询；实体 115 字段水合只输出 51）；facets 28 条聚合×每次点击 + 全表 colors/units + keyword 时整表加载分类树。
- 公司实测：根分类 33,079 行 / 18MB 原始 / 2.35MB 压缩流，空闲 DB 6s 完成；忙时（车间查询churn+徽章计数+并行会话 EXPLAIN 探针）用户等 9s 放弃 → 29.8KB/666KB 半截 200。修复统计后（2026-11-06 抢修）主流稳定但 >1s 未达。
- 任务中心客户端仍逐页串行（59 个 readScopedPage 文件中仅 10 个 fetchComplete）；报表 `ReportPagedRead` 逐页 GET 每页重算；16 个财务弹窗直调 loadCompletePagedResult。

### 2026-11-07 上午公司事故时间线（证据）

09:11:51 用户点根分类 → 09:11:56/57 两条"Database deadline reached"（fn 内 pg_constraint 查询被取消）→ 09:12:00 主流 29.8KB/禁用流 666KB 半截；同时段徽章 COUNT 4.6-5.3s 若干条 + 并行会话 postgres EXPLAIN 探针（09:11:43-09:13:39）。09:45:11 重试（DB 空闲）：6 秒完整 2.35MB。**结论：单查询公司库并不比本地慢（还略快），慢=并发负载被上述根因制造。**
