# 账号权限卡住与全平台异步读取收尾修复

## 问题及复现

公司反馈：网页连续修改多个账号权限后，权限明细或员工列表持续加载；再打开服务器状态也没有读数。

本机验收已完成。最终真实 Chrome 使用 3 个合成账号连续保存 24 次，每次都核对 401、刷新、同一账号成功读回和界面授权值；24 次保存对应 24 次写入。5 次退出重开、18 次快速切换、17 个旧员工请求取消、6 个旧通知筛选取消后，服务器状态与当前筛选均正常，未处理浏览器异常为 0。最终生产 Web 入口与回归入口均完成 Release 编译，94 个涉及的 Dart 文件格式及静态检查通过。

修复基线为 `86dffb9db`。只读核对公司当前版本为 `v2.5.52`、源码 `29616bd0cb523f17a12ccf46b9aaee9a0190b581`，其中请求排队器与修复基线相同。检查当时主机负载低、数据库没有等待锁；这只代表检查时状态，不推断故障时负载。未修改公司账号、权限、业务数据或运行版本。

已用真实 `AuthInterceptor`、`SecureStorage`、Dio 链路重现：每次权限修改推进服务端授权版本，旧 JWT 收到 401；登录刷新成功后，`AuthInterceptor.onError` 调用 `handler.resolve`，跳过后面的响应/错误拦截器。原先位于它后面的 `PageReadPriorityInterceptor` 因此无法归还读取名额。默认 6 个名额泄漏后，第 7 次读取停在客户端队列，尚未进入 HTTP；网络接收超时不会启动。服务器状态也共用此队列，因而一起卡住。

旧版回归明确报出 `Account 7 read never dispatched; refreshes=6 writes=7`。这不是服务端鉴权失效策略的错误，V322/V324 的授权失效和 JWT 校验必须保留。

另一个放大因素：`FutureProvider.autoDispose` 只丢弃旧结果，未退休底层请求；切换员工会留下旧 HTTP。共享目录还可能继承启动消费者的活动/认证操作边界，被一个消费者离开误取消。

## 公共修复与完整调用清单

| 入口 | 处理 | 保留的边界 |
|---|---|---|
| `PageReadPriorityInterceptor.installOn` | 同一调度器的回收观察器放最前，准入放所有请求检查之后；一次性安装 | 总读取 6、辅助读取 2、前台优先、队后身份复核 |
| `apiClientProvider` | 完成认证、权限、精度及诊断拦截器安装后，调用唯一安装入口 | 401 单飞刷新、服务端权限权威、原写入恢复规则 |
| 读取 permit | 独立许可对象随 `RequestOptions.extra` 传递，取消/迟到响应/复制均幂等归还 | 旧请求不能归还新请求的名额，不靠加大并发掩盖泄漏 |
| 五类 admin providers | 统一 `_readPermissions` 调用既有 `AuthenticatedRequestScope.sharedRead`；provider 结束或权限边界变化时退休请求 | 共享读取拥有独立生命周期，保留冻结身份；写入不纳入取消或重放 |
| 个人、部门、基础包、模板、批量授权、权限转移 | 全部通过上述目录/部门树/个人有效权限/部门权限/基础包 providers | 草稿、提交和业务语义不改，未新增视觉元素 |
| 调度测试与 `tool/category_read_web_contract.dart` | 全部迁入 `installOn`，移除旧直接安装方式 | 原排序、过滤及读取范围合同 |

Flutter Web 与现有 Flutter 桌面端共用产品修复。WPF 公共读取在前一次 `SendAsync` 释放 request/response/timeout 后才刷新，刷新锁用 `finally.Release()`；没有该 Dio 拦截器名额泄漏。WPF 权限页 `W7-BIZ-007`、服务器状态 `W7-BIZ-013` 仍是 `todo`、`nativeTargets=[]`，本次不改变迁移完成状态，不开放占位写入口。

### 同类问题扩查与预防

用户追加要求后，扩查了认证恢复、通知、服务器状态、交互队列及服务端/原生端共享并发资源。新增修复均先保留旧版失败证据：

| 同类缺陷 | 统一处理及约束 |
|---|---|
| 401 恢复在独立 Dio 重发，绕过成功写修订和精度收尾 | 员工及访客生产客户端由原完整链处理既有的一次认证重放；登录刷新本身仍用独立客户端，保留身份和第二次拒绝保护 |
| 401/再认证拒绝后精度 owner 仍记为在途，后续精度选择被误认未知提交 | 仅既有明确认证拒绝路径发出一次性本地回执；精度入口消费后恢复该次未执行状态，原 `priorUnknown` 保留，超时不获得重放资格 |
| 诊断位于认证恢复之后，首次 401 没有终态记录 | 诊断观察提前，每次尝试都有开始/成功或失败；不增加请求正文、查询值或凭据日志 |
| 精度弹窗队列在保护范围外检查已退休 owner，异常留下未完成 Future | 复用 `SerialTaskQueue`，owner 检查和提示回调一并纳入收尾保护，移除自维护队尾 |
| 通知手动刷新结束后覆盖新的筛选；共享通知/模板读取退出后仍在途 | 刷新回到 provider 唯一 build，读取采用共享 owner；保留刷新失败只在状态中呈现的既有合同 |
| 未读通知索引退休后只挡发布，没有取消旧传输 | 同一 generation/身份 owner 同时约束传输与发布，保持原同步合并与游标语义 |
| 服务器状态/存储读在离开或后台继续占用 `_loading`，恢复时被旧请求阻挡 | 接入 `ReadViewActivity`；退休状态与存储各自代次，旧 finally 不清理新请求状态 |
| 外网请求预算的计时开始/结束回调抛错，漏还共享信号量 | 获取后立即进入 try；监控收尾外层 finally 保证归还，保留原异常、配额、健康请求隔离和业务执行次数 |
| Chrome 中已退休的 Fetch 响应体仍把 `AbortError` 抛入 Dio 未等待的订阅清理 Future | 适配器在 token 取消或 ResponseBody 关闭时正常收尾，以同一幂等入口释放 reader（包括收到响应头但还未 listen）；活跃读取断流、强制中止及真实超时保留原失败语义 |

未发现需改的同类实现：`DataWorkQueue`、`SerialTaskQueue`、响应 JSON 转换和 owned Dio 释放路径经检查及 13 项已有回归通过；后端 SessionWatch/outbox、密码与文件密码哈希、AI/文档/OCR、附件预览与验证、客户端包处理、导入/导出并发入口，以及 WPF 连接名额、读取门闩、刷新/撤销/草稿锁均核对正常异常/取消/早退收尾。没有以统一代码形状为由改动正常实现。

新增实际 `apiClientProvider` + loopback HTTP 集成保护：20 轮写入与四路并发读取，其中 10 轮写前令牌过期；旧版第二轮已成功保存但写修订仍为 1（期望 2），修复后通过。该用例使用产品装配顺序，可防止后续调整拦截器时再漏掉全局收尾。
