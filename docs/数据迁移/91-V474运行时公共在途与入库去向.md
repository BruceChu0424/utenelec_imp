## 业务目标

- 物料分析精确需求 500，采购实际批准 2000 时，500 始终属于原分析；多出的 1500 在到货前显示为可显式采用的公共在途。
- 公共在途采用、采购/委外到货、IQC PASS、仓库实际入库和正式生产需求保持一条 UUID 来源链。
- 一张订货行由多张订单或多个目标仓共同覆盖时，按订单来源份额和目标主仓精确分配；错仓、无人预定和超量只进入实际仓公共库存。
- 计划 100、当前完整套料 50 时，保留底层齐套器的 `READY 50 + WAITING 50`，READY 才预留并生成 DRAW，WAITING 为零占用并等待后续批次。

## 新事实与权威边界

`preplan_public_supply_events` 是追加式运行时超采事件账。计划员显式填写的 `public_surplus_qty` 继续保留在原 action；财务批准后才可证明的直接超采通过 `GRANT/REVERSE` 事件记录，不回写已经外部化的 action。

事件覆盖三种外部锚点：

- 精确需求行：批准量超过 `requested_qty` 的部分；
- 显式公共行：批准量超过 `public_surplus_qty` 的部分；
- 安全补库行：批准量超过 `safety_replenishment_qty` 的部分。安全补库基数本身不可被其它分析 claim，只有超出基数的批准量进入公共在途。

公共在途容量继续由已批准、未关闭订货来源实时封顶。claim 同时受累计批准容量和仍在途容量约束；已经到货的公共现货不能再伪装成未来 claim。

## 多订单与多仓

同一 external item 的公共份额按订单 `bill_date + UUID` 稳定顺序分配。每张订单的精确预算等于来源份额减该订单公共份额；公共 claim 只能消费该订单公共预算。这样无论 300 的订单先到还是 1700 的超采订单先到，原需求合计仍只得到 500。

`production_material_analyses.warehouse_id`、source action 主仓和实际 reservation 仓必须一致。V474：

- Java claimant 查询只接受 action/analysis 主仓等于实际入库仓；
- 新 exact peg 由数据库再次校验；
- exact 生效后 analysis、action 和 reservation 的仓身份不可改；
- 历史不一致只进入 `v_preplan_exact_peg_warehouse_mismatches`，不自动猜仓或搬库存。

参与仓仍只用于“可调拨”参考。未经正式仓间调拨进入主仓，不得提高齐套、建立 reservation 或生成 DRAW。

## 仓库读模型

`PreplanInboundAllocationReadPort` 是 amount-free CQRS 端口：

- 到货登记前按 order item 批量返回 `EXACT_ANALYSIS / SHARED_CLAIM / FORMAL_DEMAND / PUBLIC` 预计数量、基本单位、目标主仓及计划/工单/车间；
- IQC PASS 待入库详情返回同口径预计去向；
- 确认结果和历史按 batch item 从 reservation、exact peg、entitlement 与正式 receipt allocation 重建当前去向；
- 每个 batch item 的所有 allocation 数量之和必须严格等于实际入库基本量。

正式 receipt allocation 与 batch item 的对应只使用稳定 UUID 和 `receipt_item_id`，按确认时间/UUID与 allocation 创建时间/UUID做确定性 FIFO；禁止解析 idempotency key 充当外键。

## 通知

- `WAITING/KIT_SHORT`：只更新“持续备料中”，不弹“现在领料”的行动卡；
- READY 且存在精确 segment→DRAW 关系：显示工单、本批量、领料单号和发料仓，提示按仓库安排领料；
- DRAW 已全部出库：显示备料完毕，可直接报工。
