# 我的申请与审批中心

路由：`/applications`、`/applications/new`、`/applications/mine`、`/applications/approval`、`/applications/:id`、`/applications/:id/edit`、`/approvals/:departmentCode`、`/approvals/settings`

## 页面定位

员工提交并跟进自己的申请，审批人员按实际岗位和授权处理本部门的待办。

2026-11-03，设计使用 `frontend-design`，复用 Uten 主题、分类工具条、表格、提示 icon 与右下悬浮操作组。设计及纸面来源差异见[实施设计](../01-规划/2026-11-03-我的申请与分级审批实施设计.md)。

## 员工入口

工作台常用功能原“我的报销”改为“我的申请”（`/applications`）。按申请权限显示以下卡片：

| 卡片 | 路由 | 权限 |
|---|---|---|
| 申请报销 | `/expense/new?kind=GENERAL` | `expense:apply` |
| 申请出差报销 | `/expense/new?kind=TRAVEL` | `expense:apply` |
| 申请出差 | `/applications/new?kind=TRAVEL` | `application:apply:travel` 或通用申请权 |
| 申请付款 | `/applications/new?kind=PAYMENT` | `application:apply:payment` 或通用申请权 |
| 申请预付 | `/applications/new?kind=PREPAYMENT` | `application:apply:prepayment` 或通用申请权 |
| 供应商付款申请 | `/applications/new?kind=SUPPLIER_PAYMENT` | `application:apply:supplier_payment` 或通用申请权 |
| 我的报销 | `/expense` | `expense:apply` |
| 申请记录 | `/applications/mine` | 通用或任一类型申请权 |

通用申请权为 `application:apply`；不因报销申请权自动获得其他申请权。按用户本次明确要求，不提供工资付款申请，既有工资模块不变。新建入口不挂待办，待办与在办集中于本人记录卡；我的申请总入口合并报销和通用申请的本人待办，导航只累计各事实入口一次。

## 审批入口

| 位置 | 路由及范围 |
|---|---|
| 各业务部门最前的审批中心 | `/approvals/<一级部门code>`，本部门及其子部门的负责人审核；以服务端授权 scope 控制显隐 |
| 综合营销部审批中心 | `/approvals/DEPT_SALES`；报销审批、申请审批、订单审批及历史记录 |
| 财税部部门审批 | `/approvals/DEPT_FIN`；仅财税部部门负责人首审，与财务业务复核分别授权 |
| 总经办部门审批 | `/approvals/GM_DEPARTMENT`；总经办申请人的部门首审，与最终批准分别授权 |
| 财务钱流管理任务区 | `/approvals/FINANCE`；报销及其他申请的财务初核、复核、保管和付款 |
| 总经办任务中心 | `/approvals/GM`；报销最终批准、其他申请副总/总经理批准 |
| PMC 运营部审批中心 | 本部门负责人审核及已授权的采购意见环节 |

卡片只在相应权限和部门授权范围内可见。旧 `/sales/manager-review` 保留并打开营销审批中心的订单分类；原订单审核细节、认领、版本、批量事务、未知提交及财务接力继续复用。选中分类直接进入待审核表格，分类内不再有状态子分类行——待审核、待付款（报销）、预付待入账（申请）等状态由表格首列「状态」表头筛选承载（2026-11-04 分类栏精简，同仓库任务中心范式）；历史记录统一走父分类行「历史记录」段按单据种类查阅。父分类行经外置头挂进内嵌页折叠头，上滑先把表格钉顶。刷新按钮统一位于审批中心右上角 AppBar，随当前分类重拉列表与徽章计数（与仓库任务中心/业务审核中心同范式），内嵌分类页不再各自带工具条刷新。权限设置对应 `approvals.center`、`applications.approval` 和 `common.applications` 服务端页面面，不手工维护第二份权限目录。

## 单据流程

| 类型 | 当前流程 |
|---|---|
| 费用报销、出差报销 | 部门负责人 → 财务初核 → 财务复核 → 总经办批准 → 财务登记付款 |
| 出差申请 | 部门负责人 → 总经办批准 → 财务接收保管 |
| 付款申请 | 部门负责人 → 财务初核 → 财务复核 → 总经办批准 → 关联已审核财务记录并登记付款 |
| 供应商预付申请 | 部门负责人 → 财务初核 → 财务复核 → 总经办批准 → 登记真实预付款 → 待合法专用账后关联入账 |
| 供应商付款申请 | 采购部意见 → 财务部意见 → 副总审批 → 总经理审批 → 财务登记付款 |

纸面人员以岗位授权配置，不能按姓名自动提升权限。升级时旧报销待审单从部门负责人环节进入新链，历史意见保留；已批准/已付款单保留原事实，旧 `expense:approve` 不自动升级为新链节点，需在升级前安排相应岗位授权。各节点均保留审批人、时间、节点、轮次及意见；驳回填写原因，修订重提沿用原单号并保留历史，撤回后旧轮不得继续审批。申请人回避、同轮不同节点兼审限制和服务端版本校验不可由界面绕过。

付款申请审批与实际财务记账分别记录，已有财务单据由后端验证后关联，不因申请批准重复建立付款。操作结果不明先读取权威状态核对，不能自动重放请求。附件扫描、原件权限及实际付款核验保留独立要求。

## 数量与交互

待办红数、本人在办黄数来自服务端工作台徽章汇总，消息已读不改变业务待办。部门卡使用 `expense.departmentPendingByCode.<code>` 与 `application.departmentPendingByCode.<code>` 的切片；总经办与财务按节点计数。表内分类是入口的切片，不再登记为新的全局待办入口。部门显隐使用授权 scope map，零待办仍可打开本部门。

相同业务使用一份审批页面，节点/部门在服务端筛选后分页；兄弟页面分别隔离筛选、队列与缓存。读取身份、服务器、授权或业务范围变化时淘汰旧响应。等待按钮使用 `UtenBusyOverlay`，确认或付款参数交互时让位；成功、失败、取消、中断及未知提交均须保留准确结果与草稿。

## 打印与验收边界

申请、报销详情提供纸面打印及对应签字栏，带当前状态、明细金额和实际流转记录；系统显示姓名不等于认证电子签名。纸面打印仍需连同原单据和原始凭证按公司要求装订，不用打印件代替原件或支付证明。

Web 与现有 Flutter 桌面共用代码。Win7 WPF 对应业务入口仍未完成迁移，保持候选/未迁移记录，不能因页面源码和本地测试存在而开放写入或宣称全端支持。实现测试与本地截图不代替部署、正式安装包、真实员工授权及目标机验收。

## 部门负责人本人申请与审批设置

持 `approval_policy:manage` 的配置人员可从审批中心顶栏或系统管理进入“审批设置”（`/approvals/settings`），逐部门配置负责人本人申请时的回避审批人。申请人不选择审批人；普通申请仍按实际部门管辖范围和对应节点权限处理。

选择器仅展示服务端核准的在职有效账号、具备部门审核及原件权限的候选，并排除该部门负责人本人。配置不自动授予审批权限，两类申请各自仍须具备相应的部门审批权。部门负责人即使持配置权，也不能自行更改本部门的回避审批人，须由另一名配置管理员办理。同一审批轮不同节点不能由同一人兼审，审批与付款继续分权。缺少合格审批人时保留待处理状态，不能自动跳级或自己批准。

修改负责人或回避配置后，已经提交的负责人本人申请快照失效，须撤回重提以重新确认责任人。保存携带原版本，冲突后重新读取并核对；响应未知时保留当前选择并先读回权威设置，不自动重复 PUT。配置候选读取不要求全员人事查看权限。所有网络段使用 UtenBusyOverlay，原件与配置授权仍由服务端终审。

## 本机输入恢复

通用申请的“草稿”段与本人报销一致，合并未形成正式单据的本机填写草稿；工作台本人入口合并一次本机数量。已被服务端确认的 `createdDocId` 只覆盖同一正式草稿，不再计为第二笔。

登记申请付款的本机输入属于财务任务，不归入本人申请或 HR；固定申请身份、原版本与交易输入用于恢复，服务端已读申请 ID 仅作去重回执。付款响应未知先读取申请和关联财务记录核对，不能自动重放，付款面板失败仍保留输入。

## 供应商预付实付与入账

预付申请仅用于供应商，必须通过资料选择实际收款供应商。获批后，财务可核对并登记真实付款日期、交易流水号与检查通过的付款证明；该动作不创建一般费用、不扣减系统账户余额，不代表已经财务入账。

供应商预付状态为 PAID 但 `postingStatus=PENDING` 时，界面显示“已付款 待财务入账”，本人仍列入处理中黄数并排除历史办结桶。财务“申请审批”内的“预付待入账”使用单独队列 `prepayment-posting`；2026-11-04 状态行退役后该入口改为表格首列「状态」表头筛选的一个桶，仅在申请分类为“全部申请/预付申请”时出现，选中后分类行保持可见并显式选中“预付申请”，其他类别（如出差申请）不提供该桶。无本人可执行的合法关联动作时为黄跟进；只有同供应商、金额、实际付款日期的合法 PREPAYMENT 已审核财务记录存在且本人有独立 `application:prepayment:link_finance` 时才为红、`canLinkFinance=true`。关联后才为 POSTED，不能用普通费用记录替代或重复扣账，既有预付会计审核限制不会由此解除。

普通付款与供应商付款仍按原授权关联已审核的对应财务记录后登记，不能套用预付的“先记真实付款事实”例外。登记与关联是两个独立动作，其本机输入及结果未知保护分别冻结原动作和原版本，不自动互相重放。

## 终止申请与保留历史

其他申请在本人 DRAFT/REJECTED 且未付款时可作废为 CANCELLED，保留原号、历史与附件，只读查阅。报销不增加第七个 status：本人 REJECTED 且无资金及付款证明时可“放弃报销”，产生 ABANDONED 事实并软归档，`abandoned=true`。个人历史默认桶请求 `includeAbandoned=true`，显式历史详情为 `GET /expense-claims/{id}/history`；原件只读例外仅限本人且有真实放弃事实，不扩大其他旧软删或其他员工范围。

已批准待付款的报销本次不能普通撤回或放弃，PAID 不以此方式终止，退款与其他资金后续另按财务流程办理。付款资格消费服务端 canPay；任何本轮审批参与者均回避付款，不根据姓名推断身份。仅无分级元数据的旧响应才保留终批 ID 的兼容判断。
