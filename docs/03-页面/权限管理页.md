# 权限管理页

> 路由：`/admin/permissions`
> 前端：`lib/features/admin/pages/admin_permissions_page.dart`、`lib/features/admin/widgets/`、
> `lib/features/admin/repositories/admin_repository.dart`
> 后端：`server/src/main/java/com/uten/imp/features/admin/`
> 当前授权边界：`/admin/permissions` 是共享壳；账号日常支持使用 `account:support`，授权配置仅
> 超级管理员 `authorization:manage`

## 一、定位

权限管理页是当前“部门配置 + 个人覆盖 + 数据范围”的管理入口。角色体系已在 V29 下线，
页面和文档不得继续把 `user_roles`、`department_roles` 或“给员工分配角色”写成现行能力。

有效权限由后端计算：

```text
最终有效权限 = 全员基础 ∪ 本部门及上级部门配置 ∪ 个人加授 − 个人收回
```

超管拥有全部权限。前端只展示和编辑结果，不能自行决定授权。

`audit_log:view` 与 `audit_log:export` 是调查证据权限的例外：超级管理员因固有全权限天然具备；非超管
只能在“按员工授权”的个人覆盖中点名加授，
不能进入部门授权或随部门树继承。只有 `audit_log:view` 才能查询；导出还必须同时具备
`audit_log:export`。普通员工、访客以及仅持导出权限的账号都不能查看审计。

V171/V173 会删除升级前已有的非超管审计导出/查看 grant。发布后由超级管理员依据批准名单重新点名授予，
避免旧部门权限或历史误配继续放大调查证据访问范围。

`stock:balance:adjust` 是另一类高风险业务权限：V167 只注册权限目录，**不默认授予任何部门**。
推荐在“按员工授权”中点名授予领导或仓库负责人；但它不是数据库强制的 personal-only 权限，超管如在
“按部门授权”中明确配置，仍会按现有部门树继承。`stock:view`、`stock:edit` 和 `stock_doc:edit`
均不会自动带来余额调整权，具体业务矩阵见[库存余额页](库存列表页.md)。

V183 新增 7 个资产权限：

| 权限 | 用途 | V183 对 `DEPT_FIN` 的默认配置 |
|---|---|---|
| `finance_asset:view` | 查看资产/待摊台账、计划、事件和批次 | 部门默认授予 |
| `finance_asset:edit` | 草稿维护、提交、调拨/运行状态 | 部门默认授予 |
| `finance_asset:approve` | 类别政策、对象和月度批次复核 | 不默认授予 |
| `finance_asset:post` | 激活、月度过账/反冲；与 dispose 组合批准终态 | 不默认授予 |
| `finance_asset:dispose` | 处置/终止申请、驳回；批准还需 post | 不默认授予 |
| `finance_asset:export` | 资产敏感数据导出权限预留 | 不默认授予；当前无资产导出 endpoint |
| `finance_asset_period:manage` | 关账和受控重开 | 不默认授予 |

V183 会清掉财税部已有的高风险部门默认 grant，但通用授权模型仍允许超管日后把这些权限重新配置给
部门，数据库没有把它们做成 audit 权限那样的 personal-only。因此上线治理必须按个人职责点名授权，
并在真实权限矩阵中证明制单、复核、过账、处置和期间管理没有同人越权。拥有
`finance_report:view` 不会自动获得任何资产权限。

## 二、入口与授权

- 位置：工作台 → 系统管理 → 权限管理。
- 前端入口与路由接受 `account:support` 或 `authorization:manage` 任一权限。
- support-only 用户只渲染账号列表、锁定/解锁、启用/停用和重置临时密码；不得渲染，也不得请求
  权限目录、员工有效权限、个人覆盖、数据范围和部门授权。
- 后端权限目录、部门权限、个人覆盖和数据范围接口同时要求
  `hasAuthority('authorization:manage') and principal.superAdmin`。
- 账号列表、锁定/解锁、启用/停用和重置临时密码属于日常账号支持，后端使用
  `account:support`；进入同一共享页面不会下放授权管理能力。
- V135 后，staff access JWT 携带用户 `auth_version` 和全局授权 `epoch`；`JwtAuthFilter`
  每请求复查，个人覆盖、用户角色、员工换部门、部门树或共享权限定义等变化会使旧 token 立即 401。
  该行为必须在目标库应用 V135 并通过负向矩阵后才能认定完成。

## 三、页面结构

顶部说明条 + 按权限装配功能区：

- **账号支持区**（`account:support`）：账号分页列表、状态筛选、锁定/启停和重置密码。
- **按员工授权区**（`authorization:manage` + 超管）：最终有效权限、个人加授/收回、数据范围。
- **按部门授权区**（`authorization:manage` + 超管）：选择部门，从权限目录配置直接权限；员工继承上级部门配置。
- expanded 且可用宽度至少 1100dp 时使用左右主从布局；其余宽度使用列表→详情切换，避免中屏详情被固定侧栏挤窄。

账号搜索和状态筛选都参与服务端分页，查询参数为 `page/size/search/status`。切换搜索或状态后回到
第 1 页，加载更多沿用同一组筛选；页面使用请求代次丢弃旧响应，避免快速切换时旧列表覆盖新结果。
状态筛选不得只过滤当前已加载页，也不得因此隐藏后续分页入口。

员工详情分为“功能权限 / 数据范围 / 账号安全”三个页内分区，一次只显示当前分区。

员工功能权限保留后端下发的完整动态权限目录；部门权限目录过滤“仅限个人授权”的
`audit_log:view` / `audit_log:export`，并在说明条解释原因；后端服务和 V173 数据库触发器继续拒绝
绕过前端的部门级写入。两种目录都采用以下渐进浏览方式：

- 默认只显示权限分组摘要和“已授权数 / 总数”，不一次铺开全部权限行。
- 支持按权限名称、权限代码和分组名称搜索；命中的分组自动展开。
- 支持“全部 / 已授权 / 未授权”，员工权限另支持“个人调整”状态筛选。
- 分组菜单支持整组授权和整组取消；整组操作始终作用于完整分组，不受当前搜索结果影响。
- 权限行保留名称、代码、来源标签和最终状态，不因简化布局删除权限信息。
- 有待保存修改时，底部固定显示修改数量、撤销和保存操作；保存失败须保留本地修改。
- 搜索无结果时提供清除搜索和恢复全部目录的动作。

员工详情的权限开关不是本地角色计算。页面先读取
`GET /api/admin/users/{id}/effective-permissions`，再把变化转换为 grants/revokes，
通过 `PUT /api/admin/users/{id}/permission-overrides` 整体保存。

员工详情页可用 `/admin/permissions?employeeId=...` 深链本页。前端先调用
`GET /api/admin/users/by-employee/{employeeId}` 精确解析账号；未开通可用账号时明确提示，不回退
到模糊搜索。部门详情使用 `/admin/permissions?departmentId=...` 精确选中部门。两类深链都只对
超级管理员且具备 `authorization:manage` 的账号开放。

## 四、数据范围

当前提供三种 scope：

| scope | 含义 | 全量权限 |
|---|---|---|
| `goods` | 外贸货品可见归属人 | `goods:view:all` |
| `client` | 客户资料可见归属人 | `client:view:all` |
| `sales` | 销售单据可见归属人 | `sales:view:all` |

数据范围在用户首次切入“数据范围”分区时才懒加载；停留在功能权限或账号安全时不提前请求三个 scope。
首次加载后三类 scope 独立并行、独立展示错误并可单项重试；任一失败不得阻断另外两项。
编辑时使用响应式、可搜索的归属人多选抽屉，保存失败要恢复原选择。超级管理员只显示“默认可见
全部数据”的只读说明，不发起无意义的数据范围请求。

普通账号的目标口径是“公共 ∪ 本人 ∪ 显式加看归属人”，超管或持相应 `*:view:all`
者可见全部。数据范围配置在查询期读取，无需重新登录。销售五类单据的列表、详情、写操作、
来源链接、批量与报表已统一走服务端 owner 策略，Flutter 只采用服务端返回的
`writable/canReject`；正式 owner 回填、真实 API 404/403 矩阵和跨模块消费方策略仍属于
[生产 NO-GO 阻断](../99-项目治理/2026-07-30-生产就绪审计报告.md)。

## 五、主要接口

| 能力 | 接口 | 后端权限 |
|---|---|---|
| 账号分页列表 | `GET /api/admin/users?page=&size=&search=&status=` | `account:support` |
| 账号状态/重置密码 | `/api/admin/users/{id}/**` 对应支持端点 | `account:support` |
| 按员工精确解析账号 | `GET /api/admin/users/by-employee/{employeeId}` | `authorization:manage` + 超管 |
| 权限目录 | `GET /api/admin/permission-catalog`、`GET /api/admin/permissions` | `authorization:manage` + 超管 |
| 部门权限 | `GET/PUT /api/admin/departments/{id}/permissions` | `authorization:manage` + 超管 |
| 有效权限 | `GET /api/admin/users/{id}/effective-permissions` | `authorization:manage` + 超管 |
| 个人覆盖 | `GET/PUT /api/admin/users/{id}/permission-overrides` | `authorization:manage` + 超管 |
| 数据范围 | `GET/PUT /api/admin/users/{id}/data-scopes?scope=...`、`GET /api/admin/data-scope-owners?scope=...` | `authorization:manage` + 超管 |

## 六、安全与审计要求

- 临时密码只在重置响应显示一次，不持久化、不写日志；复制后由管理员安全交付。
- 授权管理不能只靠前端路由或按钮隐藏，Controller 与 Service 均需校验超管身份。
- 进入应用的 `GET/POST/PUT/PATCH/DELETE/HEAD /api/**` 由 Filter + MVC 拦截器记录请求元数据，
  包括匿名认证、401、CORS 非法来源 403、404/405 与 MVC 前异常；
  部门权限、个人覆盖等公开业务表由 V169 触发器补脱敏 before/after，授权变更另有显式语义事件。
- 除超级管理员固有全权限外，`audit_log:view` / `audit_log:export` 只能作为个人 grant；部门权限保存包含任一代码必须整体拒绝，
  直接写 `department_permissions` 也由 V173 触发器拒绝，不能静默丢弃后继续保存其它权限。
- 回收核查人员的 `audit_log:view` 后，旧 staff access token 由授权版本机制立即失效；重新认证后页面、
  深链和后端列表/统计/详情/本机回执核查都必须返回无权。
- 必须测试非超管即使被错误授予 `authorization:manage` 仍不可进行授权管理。
- 必须测试账号支持人员只有 `account:support` 时不能读写权限目录、个人覆盖或数据范围。
- 必须测试 support-only 打开共享页时不渲染且不发出任何授权/数据范围/部门配置请求；只有
  `authorization:manage` 的非超管即使能看到入口，后端也必须拒绝授权操作。
- 必须测试个人覆盖、用户角色、员工换部门、部门树移动/软删、共享角色/权限、超管和员工绑定变化
  都会使旧 access token 立即 401，并验证重新登录后的权限快照。
