# 仓库管理枢纽页

路由 `/warehouse`。实现为 [WarehouseHubPage](../../lib/features/warehouse/pages/warehouse_hub_page.dart)，统一入口注册表为 [todo_badge_registry.dart](../../lib/shared/badges/todo_badge_registry.dart)。页面按当前权限显示卡片，不以页面显隐替代服务端对象范围校验。

## 岗位入口

| 入口 | 办理内容 | 待办来源 |
|---|---|---|
| [出库任务中心](出库任务中心页.md) | 财审放行后的销售拣货/交接、委外出仓及对应历史 | 销售待出库、委外待出仓；草稿沿独立草稿口径 |
| [入库任务中心](入库任务中心页.md) | 采购/委外到货与异常、生产成品点收、其它入库 | 预计到货、到货异常、成品待点收 |
| [生产领料任务中心](生产领料任务中心页.md) | 车间明确申请后的待领任务、领料进度、生产余料退仓 | 已申请未发量对应任务，加正式提交但尚未实收的退料 |
| [品质部检查结果](品质部检查结果页.md) | 待检查、合格待入库、不合格退回，按真实切片办理 | 未完结品质/仓库处理任务 |

出入库单据区保留调拨、盘点及委外成品退货/损耗历史；库存查询、货架目视化清单和报表按权限进入。历史与查询数量不能冒充待办。销售开出货单只选择产品和数量，仓库在[销售出货作业](销售出货仓库作业页.md)中确认实际仓库和库位。

## 徽章、退料与刷新

- 顶栏通过 `todoModuleCount(TodoModule.warehouse, ref.watch)` 汇总，工作台仓库卡沿同一注册表，不在枢纽再手写另一套加法。
- `warehouseProductionDraw` 与 `warehouseProductionReturn` 分别登记一次。领料卡已合计两者，不能再把该卡总数登记到模块形成双计。
- `warehouseProductionReturnPendingCountProvider` 只在已登录且有仓库单据查看权限时请求正式待实收数。申请不直接加库存；仓库真实确认后才入账并减少待办。取消、完成的历史不计入。
- 计数按登录身份、代操作身份及只读代操作状态隔离，切换身份后不展示前一人员的成功缓存。首次读取失败保持未知；同一身份轮询失败保留上次成功值，后续继续恢复。
- 仓库写成功和返回枢纽通过 `invalidateWarehouseTaskCounts` 统一刷新，包含生产退料；仅刷新当前列表而遗漏模块/导航计数不算完整接线。

## 测试宿主合同

应用启动会注入 `sharedPreferencesProvider`。新增生产退料徽章后，枢纽顶栏即使某张卡不可见，也可能经注册表读取计数。实际红测链为 `productionReturn → stockDocRepositoryProvider(wdraw) → apiClientProvider → connectionRecoveryProvider → apiBaseUrlProvider → sharedPreferencesProvider`，会话身份也是同图依赖。只覆盖权限或旧的待办provider，不能完整模拟应用宿主。

枢纽Widget测试使用独立mock SharedPreferences并在ProviderScope注入，保持真实会话/权限读取链能够构建。依赖就绪后的初始异步读取须等待稳定，不能仅pump一次就在仍有计时器时销毁宿主。本次修复只补5个测试宿主的prefs及其中两个的`pumpAndSettle`，没有移除生产退料、放宽权限、替换业务provider或把异常伪装成0。退料身份隔离、失败恢复和仓库任务计数另由对应provider及任务中心测试覆盖。
