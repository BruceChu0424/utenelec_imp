# 2026-10-21 物料分析读侧性能与快照一致性核验

本轮在当前源码的隔离 PostgreSQL 16 中先测基线，再修复查询放大、重复投影和无变化写放大。性能主代码与后端最终聚焦组通过；业务数量、来源责任、完整浏览器场景及后续迁移由对应记录分别验收。没有推送、部署或公司库迁移结论。

## 样本与测量口径

- 真实创建、审核及财务确认的销售来源，2/30 个产品，每产品展开 99 个根/BOM 节点，共 198/2970 行。先执行预热，详情和缺省交期刷新各测 3 次；初建、显式交期刷新各 1 次。
- `ProductionJdbcMeasurement` 记录实际 JDBC 调用、逻辑语句、受影响行、事务提交及 SQL 形状/调用位置；不输出 SQL 参数和业务身份。`CommandResourceMeasurement` 在业务操作返回时记录当前线程 CPU/累计分配，排除之后用于诊断的 JSON 大小序列化。
- 线程分配不是存活内存、RSS 或并发峰值。隔离数据库使用测试默认参数；本机存在并行验证，墙钟耗时只作本轮观察，不作为生产 SLO 或严格配对加速比。
- 本轮聚焦组加载 820 条迁移到 V894。后续迁移和责任桥调整需要单独验证，不能沿用这里的结论。

## 已证实的根因与改动

### 详情跨提交混读

命令提交后的读回已经使用 `REPEATABLE_READ`，公开 GET 的 `detail()` 原来使用默认 `READ_COMMITTED`。真实 PostgreSQL 并发测试先让详情读到旧 header，再阻塞来源表读取；另事务原子推进 header 版本并将来源优先级从 1 改为 1001，放行后详情带着旧版本返回 1001。原代码红测为 `expected 1 but was 1001`。

公开详情现在也使用 `REPEATABLE_READ`，同一次响应的 header、来源、库存及供给投影来自一个已提交快照。不新增行锁或跨请求缓存，不跳过对象权限。该并发回归已通过。

### 同一详情重复读取与重复计算

SQL 形状证据确认 `SubcontractComponentCustodyProjection.held` 在每次详情中执行两遍：分别用于实际仓库归属和节点精确权益。现在一次读取，在同一只读快照内复用；刷新兼容性守卫仍独立读取，不复用跨写入阶段的数据。

备料池的物理供给、物理切片摘要及对外池摘要属于「主仓/范围仓/货品/颜色/单位」维度，原来随每个重复 BOM 节点重新求和、拼长键及计算 SHA-256。现在仅在本次响应中按池复用。节点私有权益、外部来源是否允许认领和数量分配仍逐节点保留，不把私有量复制给同料兄弟节点。

### 无变化刷新仍产生实际 UPDATE

30 来源的相同输入刷新，原来 JDBC DML 合计影响 94 行：来源逐条更新 30 行、来源齐套投影 30 行、根供给投影 30 行，以及 header/命令等 4 行。BOM 节点原有 upsert 已能跳过相同值，本轮保留该实现。

现在锁定、校验之后仅更新变化的来源数量、交期和原因；来源齐套、根数量、非自制根齐套清零和履约状态使用完整值差量条件。相同仓库配置不再重复更新 header 配置。显式刷新仍更新分析 header 的版本/时间/操作者并写幂等回执。

真实 PG 回归比较刷新前后的 `xmin`，确认相同输入不改来源、根或 BOM 的任何物理版本；再将一个真实来源数量改为 9，确认新数量仍写入并传到根投影。原数量计算、锁、校验、命令和来源链不变。

### 销售来源的主档和复用探测逐行查询

缺省交期分支与显式交期不同：原 `salesSourceMaster` 每条来源单查。30 来源的初建和缺省交期刷新均查主档 30 次。初建复用探测还在预锁发现、复核和正式阶段各查 30 次，旧 SQL 指纹 `682caba2ce2bd3fb` 在 2/30 来源基线中分别出现 6/90 次。

新增 `MaterialAnalysisSalesSourceReader`，每 256 个 UUID 一批读主档和有效分析关联。保留原三个发现/复核阶段，不把它们合并或省略。审核、中止、关闭、删除、财务确认和单位校验仍在原请求顺序中逐项执行；同一次命令只复用已经读取的事实，不缓存到下一次命令。

MANUAL 合法的空销售来源 ID 不进入销售查询；SALES 缺 ID、非法类型及重复 ID 仍先得到结构化 422。helper 在 `Map.copyOf` 查询前显式处理 null，不会因 `get(null)` 产生 NPE。手工需求编号分组、归属权限、完整来源集合匹配、源锁和并发复核原样保留。

## 实测结果

下表为对应样本的逻辑 SQL 数及测量到的业务 DML 受影响行。它们不包含数据库函数/触发器内部语句的逐行统计。

| 场景 | 2 来源前 → 后 | 30 来源前 → 后 |
|---|---:|---:|
| 详情 SQL | 43 → 42 | 43 → 42 |
| 显式交期、不变输入刷新 SQL | 143 → 140 | 199 → 168 |
| 不变输入刷新 DML 受影响行 | 10 → 2 | 94 → 2 |
| 初建 SQL | 166 → 162 | 344 → 228 |
| 缺省交期刷新 SQL | 142 → 141 | 198 → 169 |
| 初建/缺省交期刷新主档读取 | 2 → 1 | 30 → 1 |
| 初建三个发现/复核阶段关联探测 | 6 → 3 | 90 → 3 |

2970 节点详情的预热线程分配中位值约 79.34 MiB → 71.68 MiB，减少约 9.7%。同样规模的不变输入刷新仍约 243 MiB，不能据此声称所有写流程都显著降低内存。

本轮观察：2970 节点详情中位 296ms → 223ms；缺省交期刷新中位 1328ms → 918ms；初建单次 2786ms → 1461ms。中间一轮详情也曾在相同 SQL/分配下降时从 296ms 变为 371ms，说明并行负载影响明显；以上墙钟不能全归因于本次改动，也不能作为生产保障。可稳定确认的是查询/物理写入减少、每次响应的重复分配减少及并发快照一致性。

新销售备注链单独测得：30 来源始终 1 条 SQL、约 0.11 MiB 线程分配，约 6–7ms；没有发现逐来源查询，因此保留其现行批量 SQL，不对正确路径盲目改写。

## 回归与预算

最终一次聚焦组共 110 项通过，0 失败/错误/跳过：

- `ProductionMaterialAnalysisScalePostgresTest` 4 项真实 Spring/PostgreSQL：读预算与不变刷新/真实数量变更；header/来源并发快照；30 计划只读预览与真实下达逐字段一致；销售主档与缺省交期批量预算。
- `SubcontractComponentCustodyProjectionPostgresTest` 8 项真实 PostgreSQL SQL 回归：逐物料覆盖、来源拆分、精确交接、回厂扣除及公共尾量。补齐旧最小 schema 中缺失的公共责任表/列，未改变原数值断言或替换真实生产 SQL。
- `MaterialAnalysisServiceBehaviorTest` 90 项，含 MANUAL 空销售 ID、SALES 缺 ID、非法类型、重复源的 422，以及 owner 6 + custody 4 = 10、兄弟节点仍为 0。
- `MaterialAnalysisSalesSourceReaderTest` 5 项，覆盖空读取、600 UUID 按 256/256/88 分批、状态/财审/单位和跨命令重查。
- `MaterialPreparationBudgetReaderTest` 3 项，含 500 个重复来源不放大物理预算、单位/颜色不串池及逐节点不同认领资格。

无下达行动的基准详情预算为最多 45 条 SQL，2/30 来源均为 42；来源备注最多 1 条 SQL，两者必须零 DML。预热线程分配上限分别为 32/128 MiB，防止相同固定样本出现平方级回归。带实际供给行动的详情有额外业务查询，不能把 42 误当作所有状态的固定 SQL 数。
