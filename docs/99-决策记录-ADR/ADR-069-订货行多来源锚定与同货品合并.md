# ADR-069：订货行多来源锚定——同货品合并生成订货单

- 日期：2026-09-03
- 状态：已决策；后端/Flutter 为源码候选，真实岗位 UAT 未完成（迁移 V463/V464，目标库未升级）
- 相关：ADR-065（备料下达同批合并——本决策把「单据行合并、锚点逐条保留」的思想下移到订货层）、
  ADR-068（订货单行级商业条款与学习模式）、ADR-038（订货不携带仓库）
- 迁移：V463（sources 两表 + 回填 + 两个视图替换 + FIFO 分摊函数）、
  V464（business_data_reset() 双胞胎同步，320 表）

## 一、问题

采购/委外任务工作台多选多条申请（可跨申请单）生成订货单时，所选申请明细**逐行带入、
同货品不合并**：5 张申请里 3 张都要同一种螺丝，订货单里就是 3 行螺丝。业务口径：

1. 对供应商的订货单应该是「同货品一行、数量总数」（2026-09-03 用户确认合并口径 =
   同「货品+颜色+单位」，交货日取最早需求日）；
2. 采购与委外统一修改。

## 二、决策

### 2.1 订货层：真合并一行 + 多来源分配表

ADR-065 在申请层拒绝合并行，是为了保住「一明细一锚点」（撤回/释放语义）。本决策
把同样的结构下移一层：

- 订货明细仍真合并为一行（订单/详情/财务审核/仓库各处只见一行）；
- 新增 `purchase_order_item_sources(order_item_id, request_item_id, alloc_qty, line_no)`
  与 `subcontract_order_item_sources(order_item_id, application_item_id, ...)`：
  一条订货行锚定多条申请明细，`SUM(alloc_qty) = 行数量`，`UNIQUE(order_item_id, 来源明细)`；
- `purchase_order_items.request_item_id` / `subcontract_order_items.application_item_id`
  保留为**首来源（主锚点）**：历史行由 V463 回填为单来源（alloc = 行数量），兼容旧消费方。

### 2.2 数量拆分：保存时按剩余量 FIFO，末位吸收超额

`saveItems` 收到行级 `requestItemIds[]`（与首来源去重、按「需求日期升序、id 升序」
稳定排序）后，按各申请行当前剩余量（qty − ordered_qty − 待财务占用，与分解预览同口径）
先到先得：

- 份额为 0 的来源丢弃（改小总量时后面的来源不落库）；
- **末位来源吸收超额**（超采备货，ADR-068 口径）；
- 单来源行退化为 alloc = 行数量，与 V463 前行为逐位一致；
- 全部来源剩余为 0 的极端退化：首来源承接全量（超采锚点）。

### 2.3 消费方统一改读 sources

数量账与溯源**全部**从单列锚点改为 sources 汇总（采购/委外对称，共 17 个 Java 文件
+ 2 视图 + 1 SQL 函数）：

| 消费方 | 改法 |
|---|---|
| 审批回写/红冲（PurchaseOrderService / SubcontractOrderService） | ordered_qty 按 alloc_qty 逐来源加减、逐来源重算结案；送审完整性按来源行校验（已下达/未中止/维度一致） |
| 任务台视图 `v_procurement_decomposition_tasks`（V463 替换 V301 版） | 待财务占用 pending 按 `SUM(src.alloc_qty)` 汇总，不再串占首来源 |
| 分解预览（PurchaseRequestService / SubcontractApplicationService） | pending 子查询同上 |
| IQC 入库 exact-peg（PreplanAnalysisStockPegService） | 收货行→订货行→**逐来源**跑既有 claimant 循环（入库量在来源间 FIFO；各来源的分析分摊容量仍逐来源封顶防重复归属）；V312 的触发器本就不钉订货行等式，无需改 |
| 供给转移（ProductionPurchase/SubcontractSupplyTransitionService） | 申请行 peg→订货行 peg 按（订货行×来源）逐条转移；transfer 子账本本就逐申请行，回放加来源过滤；幂等键加来源 id 防同需求撞键 |
| BUY 切片进度视图 `v_preplan_buy_action_slice_progress`（V463 替换 V446 版） | 订货行经 sources 关联；到货/待检/未交量按 FIFO（末位吸收）分摊到各申请行切片 |
| 分析覆盖统计（MaterialAnalysisService / CommandService 的 6+2 段 reconcile） | 到货量汇总经 `fn_purchase/subcontract_order_source_share(行, 来源, 总量)` FIFO 分摊（SQL 函数与视图同款语义，单来源=全量） |
| 建议入库仓（ProcurementArrivalControlService） | allocation 关联改 `external_item_id IN (该行的全部来源)`；多来源跨分析仓时照旧返回 null 手选 |
| 供给进度（MaterialAnalysisSupplyProgressService）、销售时间线（SalesOrderTimelineService）、守卫（ProductionSupplySourceGuard）、通知（ChainNoticeService）、委外发料计划/准备（SubcontractMaterialPlanService、SubcontractPreparationTaskAdapter） | 成员关系 join 经 sources 展开（DISTINCT/EXISTS 语义不变） |
| 财务审核行（ProcurementFinanceApprovalService.loadReviewLines） | 来源单号按行 `string_agg(DISTINCT 单号, '、')`；表头「来源申请张数」按顿号拆开计数 |

### 2.4 前端（采购/委外编辑页对称）

- 任务中心多选带入（`/purchase/orders/new?requestItemIds=…`、
  `/subcontract/orders/new?applicationItemIds=…`）：预填时同「货品+颜色+单位」
  自动合并成一行——数量加总、交货日取最早、来源申请逐条保留；
- 「从上游引入」同样并入既有同键行，不再产生同货品重复行；
- 保存时行携带 `requestItemIds`/`applicationItemIds`（>1 才发），服务端拆分；
- 「申请来源」列：多来源单号顿号连接，点击弹清单逐张跳申请详情；
- 详情页（订货单）与财务审核详情页：合并行展示「来源申请」列（多单号顿号连接）；
  编辑回显经 DTO `sourceRequests[]`/`sourceApplications[]`（明细 id + 申请单 id + 单号）。

### 2.5 谱系与主锚点语义

- 订货行 `source_doc_no/production_plan_no/sales_order_no/deliver_date` 继承**首来源**
  （最早需求日）申请行谱系；跨申请合并时表头「来源申请」不再显示（与既有
  「全单同源才有」口径一致，明细行可见全部来源）。
- 委外行 `application_item_id` 仍可为空 = V304 手工行（不落 sources）。

## 三、边界与后续修复（2026-09-03 同批收口）

1. **超采审批触发器 → 已修（V465）**：V144 的 ordered_qty 上限守卫与 ADR-068
   「放开超采」冲突（单行超采在财务批准回写时 23514）。V465 把两个触发器换挂
   `fn_guard_ordered_qty_non_negative`（沿用原名）：**只禁负数**，上限取消；
   重复回写由应用层状态机（仅草稿可审批、仅已审可红冲、approval case CAS）防护。
   行为证据在 E2E（末位来源 35 > 申请 30 审批成功），见 [迁移说明 84]。
2. **前置自制合并 → 已修（保存时早期拦截）**：`SubcontractPreparationTaskAdapter.
   sourceLineage` / `SubcontractMaterialPlanService.preparedLineage` 按「一订货行=一
   谱系」设计，合并行含「先做后审（V458 前置自制已完成、申请行挂 make 任务批次）」
   来源时会在财务批准/准备启动深处 409。`SubcontractOrderService.saveItems` 现在在
   **保存时**即拒绝并给出可操作指引（「去掉该来源后分开生成订货单」）；普通
   （无前置自制）申请的合并不受影响。
3. FIFO 分摊是**确定性近似**：合并行的到货量按 sources 顺序归集，与「登记时拆分」
   的结果在整数 FIFO 语义下一致；红冲/退货走对称路径。

## 四、验证

- `OrderItemSourceMergeMigrationContractTest`（6 项）：两表+审计触发器+UNIQUE、
  回填（alloc=行数量）、FIFO 函数末位吸收分支、任务台视图 pending 经 sources、
  切片进度视图经 sources、V464 双胞胎/ops 脚本登记两表；
- `PurchaseOrderSourceMergeSplitTest`（5 项）：50=30+20、超采 60=30+30（末位吸收）、
  改小 10 只落首来源、单来源 alloc=全量、缺锚点拒绝；
- `SubcontractOrderMergeGuardTest`（2 项）：前置自制来源合并保存即拒（含可操作文案）、
  无谱系合并放行；
- `FullChainEndToEndTest.orderSourceMerge_ordersApprovalAccountingAndPegsBothAnalyses`
  （真 PG 单方法）：两分析同货品缺口 → 一行合并 55（超采 5）→ FIFO 拆分 20+35 →
  送审后任务台/预览按来源份额占用 → 财务批准 ordered_qty 拆回 20/35（V465：末位
  超申请不再 23514）→ 收货 55 → IQC PASS → 仓库确认 → 两个分析各得 exact-peg
  （20/30），超采尾巴 5 为公共现货；
- 既有受影响测试（ProcurementRejectedOrderEditTest、PurchaseOrderPendingCapacityTest、
  ProductionSupplySourceGuardTest、Reset 系列契约、LegacyMigrationSafety 等）同步后全绿。

## 五、影响面

- 单据体验：选中 3/4/5 张申请 → 同货品一行总数 → 保存按供应商+条款拆单（不变）；
- 数据模型：+2 表（reset 白名单 CLEAR 222→224、总数 318→320，V464 重发运行时孪生）；
  V465 替换两个守卫触发器（不加表，目录头 V465/427）；
- 无权限码变化（沿用 purchase_order:create+decompose / subcontract_order:create+decompose）。
