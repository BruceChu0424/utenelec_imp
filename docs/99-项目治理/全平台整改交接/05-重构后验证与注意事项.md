# 全平台整改 重构后怎么验证、要注意什么

> 用途: 每做完一个工作流/一波, 以及最终合并前, 照这份清单验证。任何一项不过都不能报"完成"。
> 原则(用户铁律): 自测用真实数据+切换账号走全栈, 不接受只跑 mock; 性能只信语句条数/SQL 指纹与真实请求耗时, 不信推断; 业务链路"不撒谎"——徽章数=列表行数=库内事实, 状态文案=实际状态, 报表合计=单据合计。

## 一、每个工作流合并前的四道门

1. **编译与静态**: `cd server && mvn -o -q compile test-compile`; `flutter analyze`(0 问题); `dart format --output=none --set-exit-if-changed lib test`(CI 卡这一步, 新写的超 80 列行会整条流水线红)。
2. **本工作流相关测试全绿**: 改到的每个服务都有对应的真库测试(`UTEN_RUN_DB_TESTS=true mvn -o test -Dtest=...`); 前端改到的页面/组件测试全绿。修改旧契约断言必须在提交说明或 ADR 里逐条写理由(第一阶段每个工作流都这样做了, 见各 ADR)。
3. **性能证据**: 声称"变快"的命令必须有 ProductionJdbcMeasurement 语句预算测试(前后语句数、md5/set_config 等指纹计数、commit 次数), 并把预算常量下调到实测值附近, 防止回退。
4. **对抗评审**: 另一个人/代理只读评审, 镜头至少包括: 正确性与业务口径(有没有去掉必要校验)、并发与事务(锁顺序、锁后复核、@Transactional 自调用)、完整性(对照发现 ID 是否真根治、有没有留旧路径)、测试有效性(是否真的断言了关键行为)、安全(越权/泄露/审计缺口)。blocker/major 全部修完再合并。

## 二、每一波合并后的全量门禁(与 CI 同款)

| 项 | 命令 | 通过标准 |
|---|---|---|

| 前端静态 | `flutter analyze` | No issues found |
| 前端测试 | `flutter test` | 全绿(第一阶段收尾时约 3050 个) |

| 后端快道 | `cd server && mvn -o verify` | 全绿(DB 门控测试按设计跳过) |

## 三、业务链路验证矩阵(最终验收必须全部走通, 切换账号)

每条链都要: ① 用对应岗位账号(不是超管)走完, 每一步断言 服务端响应 + 库内事实 + 徽章数(`GET /api/workbench/badges` 对应入口) + 列表行数 三者一致; ② 结束后跑不变量终检 SQL(见第五节); ③ 再用无权限账号尝试每一步写操作, 断言被拒(403/404), 以及列表里看不到别人的单据(对象级范围)。

| # | 链路 | 必测分支与边界 |
|---|---|---|
| 1 | 销售下单 → 财务确认(订货) → 预留/缺货 | 现货足/部分/无; 外币订单汇率; 一口价行; 改量后重审; 财务退回再提交 |
| 2 | 物料分析(准备页开始分析 → 路线确认 → 一张表下单) | BOM 多层(自制/委外/采购混合); BOM 有问题时报错指出具体行; 同分析并发两人预览; 追加自制并入未开工计划(ADR-104); 取消分析/撤回动作(原因可空) |
| 3 | 采购: 请购 → 订货(拆单) → 财务审批 → 到货登记 → IQC(合格/不合格/部分) → 入库 | 超量到货异常→退回供应商任务(采购岗位能完成); 先入库后检; 不合格退回/贷项(仓储登记、财务确认); 全额退货后应付原币本币都为 0 |
| 4 | 委外: 申请 → 订货 → 发料(草稿编辑、审核) → 回厂收货 → IQC → 入库 | 两条路线(ADR-103); 允许损耗与短交(ADR-098); 损耗赔偿; 委外前置自制 |
| 5 | 生产: 计划下达 → 执行段确认路线 → 领料 → 报工/日报(入仓、车间直送) → FQC → 成品点收 | 多执行段订单行完结封顶与红冲(第三波前会被拒, 属已知限制); 直送 1 行与多行; 补产; 退料 |
| 6 | 出货: 出货单 → 财审(view/approve/reject/reverse 分权) → 仓库拣货出库 → 应收 | 分三次出货金额守恒(3 件 100 元=33.3333/33.3334/33.3333); 直发出货与普通出货本币一致; 销售退货 |
| 7 | 财务: 收款/付款/费用/其它收入/银行转账/余额校准 → 审核 → 红冲 | 每类审核后余额与流水成对, 红冲后余额复原; 总账生成借贷平衡; 附表人工/折旧行取数正确(未配置标注) |
| 8 | 权限管理 | 部门矩阵保存(11 个部门都能保存)、个人覆盖、页面内委派、全员基础包、数据范围; 每次保存一条带 added/removed 的事件, 原样保存 0 审计; hub 与工作台入口 = 有子卡权限即可见 |
| 9 | 账号与安全 | 锁定期对/错密码同一提示; 重置密码不能自定、高危账号只超管可重置; 高危操作要再认证(step-up); 登出后原 token 立即失效; 空闲超时服务端生效; 访客只能按姓名前缀搜接待人 |
| 10 | 审计 | 每个写操作有一条可读业务事件; 成功读请求不记(敏感读除外); 留存任务运行后有完成事件, 服务器状态页显示最近成功时间; 审计导出里手机号只有后 4 位 |
| 11 | 主档 | 删除被 BOM/单据引用的货品被拒且说明被谁用; 批量启停/删除一次请求逐条结果; BOM 粘贴原子 |
| 12 | 系统设置 | 每个设置改值后立即生效(用可控时钟/实际操作验证), 取值范围由服务端下发 |

第一阶段已有的全链路测试: `server/src/test/java/com/uten/imp/businesschain/FullChainEndToEndTest.java`(158 个用例, 真库+真服务+切账号)及同目录各 *EndToEndTest。新链路/新分支按同样方式补用例, 不要只写单元测试。

## 四、性能验收(用户最关心"点下一步不要等半天")

1. **语句预算**(必须): 每个重命令一个预算测试, 已有的: `WorkshopDirectTransferBatchEndToEndTest.APPROVE_STATEMENTS_BUDGET`(424)、`PrelockStatementBudgetEndToEndTest`(委外发料草稿 PUT 51、批量出库 598)、`WarehouseIqcBatchScalePostgresTest`、`ProcurementInspectionBatchEndToEndTest`、`MasterDataIntegrityEndToEndTest`(批量启停)、徽章汇总 `WorkbenchBadgeSummaryPostgresTest`(整份汇总 40 条)。第二波目标见 03 文档各节。
2. **真实耗时**: 在克隆库或老库全量引导库上, 用公司同款 JVM 参数(`-Xms512m -Xmx4g`, 不要带 spring-boot:run 默认的 `-XX:TieredStopAtLevel=1`)起实例, 对 Top 30 端点计时(p50/p95)。第一阶段之后成功的 GET 不再写审计, 读路径耗时看服务器状态页或 Micrometer。
3. **大数据量**: 老库全量引导库(货品 3.5 万、订单 1 万+、流水 56 万、明细 61 万、成本明细 136 万)上跑列表/检索/工作台/报表, 看 EXPLAIN 不出现大表 Seq Scan、深分页不线性变慢。
4. **并发压测**: 约 140 名员工混合负载(capacity 工作流交付脚本), 看 p95、错误率、CPU、内存、连接池(Hikari active 不长期顶满)、锁等待(pg_locks 无长时间 advisory 等待)。
5. **前端**: Chrome DevTools 看回工作台请求数(应 ≤2)、打开详情首屏只等 1 个请求、转场无长帧; Flutter DevTools 看输入时重建范围。

## 五、数据正确性核对(不变量终检 SQL, 第三波 truth 会固化成 @AfterEach 与每日巡检; 在此之前手工跑)

- 库存余额 = 流水累计: `stock_balances.qty = Σ(stock_movements.qty × direction)` 按 仓库+货品+颜色。
- 订单行预留 = 有效预留: `sales_order_items.reserved_qty × unit_rate = Σ(stock_reservations 有效余量)`(第三波会删计数器改派生)。
- 计划量 = 关联量: `sales_order_items.planned_qty = Σ(plan_order_item_links.allocated_qty)`; 段 planned_qty = Σ(execution_segment_sales_allocations.allocated_qty)。
- 已发完订单行 Σ出货金额 = 订单行金额(原币与本币)。
- 应收应付余额 = 原值 − 已结 − 抵销; 全额退货的收货应付余额为 0。
- 预留有效量 ≥ 0; READY 段完整齐套。
- 资金账户余额 = 期初 + Σ流水; 每张已审核资金单据的流水正反成对。
- 总账每张凭证借贷平衡。
- 徽章: 每个入口的 todo 数 = 对应列表"待处理"分段行数。
- 审计: 每个成功写请求有一条 business 事件; `event_source='database'` 的 UPDATE 行里没有前后完全相同的记录。

## 六、各区域最容易出错的地方(注意事项)

**锁与并发(ADR-107)**
- 预锁协议是全平台并发正确性的根: "最外层预读→加锁→锁后复核"必须保留; 新命令要么在最外层声明完整足迹, 要么嵌套时声明已知 id。测试环境默认打开 `uten.concurrency.verify-nested-footprint` 会在嵌套命令里重跑发现并检查覆盖, 新写的命令必须在它打开时全绿。
- lock_timeout 10s / 事务 40s: 真正长的后台任务要显式放宽(已放宽: 报表刷新、清空业务数据); 新增长任务同样处理, 否则会被 57014 取消。
- 可重跑冲突(409 + Retry-After)只用于"来源在预读后变了/等锁超时"这类瞬时情况; 编码缺陷(声明 id 未被覆盖)必须是不可重跑并记 ERROR, 否则会被自动重跑放大。
- BaseEntity 已实现 Persistable: 把已有行的 UUID 塞进 new 出来的实体再 save 不再等于更新, 会被主键拒绝——更新必须先读出托管实体。

**审计(ADR-105)**
- 新建表必须在建表迁移里调用 `fn_audit_track_table(表, 'FULL'|'COLUMN_SCOPED'|'NONE', ...)` 并登记到 `AuditTriggerCoverageMigrationContractTest` 的三清单(写理由); 不许手写 `CREATE TRIGGER trg_audit_*`。
- 业务代码不得读 audit_log(架构测试会拦); 需要的时间点落在单据自己的列上。
- 审计表只追加、按月分区; 留存有 6 个月法定下限。不要在应用里对审计表 UPDATE/DELETE。
- 新增"敏感读"(导出、含个人信息的详情)要标 `@AuditedRead`, 否则不留痕。

**权限(ADR-109)**
- 权限码只有一个事实源: permissions 表 + grant_policy。新增码: 迁移写入目录(带 grant_policy 与两级分类), 服务端 @PreAuthorize 用它, 前端 Perm 常量与路由/hub 目录登记; 契约测试(PreAuthorizeCodesAreActive、PermissionCatalogBidirectional、PermissionChainReachability)会拦住不一致与"没人能办"的码。
- 不要再在任何地方手写权限名单(前端/后端/迁移守卫)。
- 单据对象范围: 负责人为空不再公共可读; 系统生成单据用 owner_pool; 新单据类型要走 DocumentAccessPolicy。
- 按钮显隐以服务端 allowedActions 为准(页面本地拼权限的基线只减不增, 有 lint 测试)。

**金额(ADR-112)**
- 金额只在服务端经 MoneyPolicy 算一次; 除 MoneyPolicy 外禁止 HALF_UP(架构测试拦); 保存请求带 amount 字段会 400。
- 分摊用"累计份额−已分摊, 末批取余"; 库存价值列仍是 4 位投影(用户已决定本轮不改价值账模型), 外币本币超过 4 位时库存价值与财务精确值之间存在一次投影取位差, 应付侧精确守恒。
- 前端展示金额用服务端下发的精确十进制字符串, 不要经 double。

**主档(ADR-111)**
- 新表若引用主档(货品/颜色/单位/仓库/客户/供应商/模具), 必须登记到 `MasterReferenceCatalog`(引用或豁免+理由), 否则覆盖测试失败——这是防止再出现"删了仍被使用的货品"的机制。
- 颜色/单位的引用检查在老库量级会扫大表(明细表的 color_id/unit_id 无索引), 删除颜色/单位可能要约 1 秒; readpath/capacity 可补部分索引。

**前端(ADR-108)**
- 计数只有一个来源: 徽章汇总(`badgeSummaryProvider` / `GET /api/workbench/badges`), 新入口在服务端 WorkbenchBadgeCatalog 登记, 不要再写独立轮询 provider。
- 返回即刷新只在"期间有写或数据超 30 秒"时触发; 写操作成功要推进写修订号(ApiClient 已对非 GET 自动处理), 否则会显示旧数据。
- 会话快照(/auth/me)在授权变化后要刷新; 快照失败会退避重取。

**迁移与数据**
- 已应用到任何持久库的迁移文件一个字都不能改; 本阶段新迁移 V670-V687(有跳号)在公司服务器上尚未执行。
- V671 把 audit_log 改成分区表会复制全部历史行; 在服务器上执行前评估行数与时间, 并先备份+实际恢复验证。
- 老库导入(legacy_migration)必须随表结构改动同步; 最终用 `migrate.sh --bootstrap-all` 对最终结构演练库全量跑一次、23 项结构对账全过才算同步完成。

**安全(ADR-110)**
- 高危写端点要 `@RequiresStepUp`(架构测试会拦 /api/admin/** 写端点); 新增高危操作同样处理。
- 会话以服务端 auth_sessions 为准; 自动轮询类 GET 不续期(约定见 ADR-110), 新增轮询端点要遵守, 否则空闲超时永远不触发。

## 七、公司服务器部署前检查(第一阶段已于 2026-09-24 以 v2.0.0 部署, 记录见 01 文档第四节; 以下为每次发版的检查)

1. 在同一候选提交上本地全量门禁全绿, CI 全绿。
2. 迁移演练只在本机做(pg_dump 服务器库 → 本机 docker 恢复 → 本机 jar 起实例指向克隆库, Flyway 随启动执行)。**不要在服务器上直接运行 uten-imp-migrator.jar**: 它写死连正式库 uten_imp, 不认 UTEN_DB_URL(v2.0.0 发版时因此误迁了正式库, 见 01 文档)。
3. 按 `deploy/simple/RUNBOOK.zh-CN.md`: 停写 → 完整备份 → 实际恢复验证 → 迁移(评估 V671 分区复制时间) → 激活 → HTTPS 健康与版本核验 → 冒烟(登录、工作台徽章、物料分析、到货、出货、收款各走一单)。
4. 部署后看服务器状态页: 审计留存任务、outbox、5xx、慢请求; 次日确认审计留存完成事件已产生。
