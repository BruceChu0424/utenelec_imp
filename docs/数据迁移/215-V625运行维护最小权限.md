# V625 运行维护最小权限

迁移文件：`V625__runtime_maintenance_privilege_boundary.sql`。

应用账号不应依赖迁移角色或对象拥有者的成员资格。原报表定时器直接刷新物化视图，原 `business_data_reset()` 以调用者权限执行临时表、TRUNCATE、序列重置和物化视图刷新，因此单纯撤掉继承会让维护功能失败。审计留存任务仅执行受控批量插入、归档和删除，不需要分区或持久 DDL 权限。

## 固定维护入口

只有以下七个既有入口使用 `SECURITY DEFINER`：

- `refresh_finance_ar_ap_mv()`
- `refresh_production_monthly_mv()`
- `refresh_purchase_monthly_mv()`
- `refresh_sales_monthly_mv()`
- `refresh_stock_monthly_mv()`
- `refresh_subcontract_monthly_mv()`
- `business_data_reset()`

六个刷新函数只操作各自明确限定的 `public` 物化视图，不接受目标名称或 SQL 参数。定时器改为调用固定函数，仍保留原并发 advisory 锁、逐视图结果记录和失败处理。普通应用无需拥有视图，也不能直接执行持久 DDL。

函数使用固定 `search_path=pg_catalog,public,pg_temp`，临时 schema 明确置于最后。PUBLIC 执行权限被撤销，普通登录角色只向真实运行账号 `uten` 授予 EXECUTE。对象拥有者及数据库管理员保留其原有维护权。共享校验函数为 INVOKER、无业务写入，不授予应用直接调用权限；仅向七个经核对入口的实际 owner 定点授予 helper EXEC，以兼容旧入口归 `uten_owner`、新 helper 归迁移登录的单向角色继承布局。不会为此改变 ownership 或让应用继承任何 owner。

## 清库安全边界

迁移从现役函数读取完整 `prosrc`，在唯一、受检入口插入维护校验，保留原所有 CLEAR/PRESERVE 目录、附件完成证明、outbox 拒绝条件、金额和数量终局核对、会话清除与授权 epoch 更新。合同测试验证移除新增一行调用后，函数体与迁移前完全一致。没有替换成旧版清库函数或删减守卫。

校验拒绝 public 中与内部临时表同名的持久关系，以及调用者伪造的同名临时关系，避免提权后误删或误解释政策表。角色和身份读取明确使用 `pg_catalog` / `public`。普通 `uten` 必须绑定真实、有效、未删除的超级管理员用户、匹配登录账号和审计请求 ID。

应用原有超级管理员授权、功能开关、逐字确认、附件准备和排水门继续有效。数据库检查不把任意 `GUC=true` 当授权，也不替代应用身份认证；后台数据库凭据和数据库管理员仍属于受信边界。测试清库依旧是明确授权的破坏性业务功能。

## 部署顺序与回退

V625 不修改角色成员关系、对象 ownership 或普通业务表权限；不会给应用授 schema CREATE、迁移成员资格或全库 TRUNCATE。需先在恢复副本中以真实非超级用户登录验证普通 DML/审计、六个刷新入口和完整清库，再由受控运维步骤撤销已有应用→迁移角色继承。

收紧前记录原角色图（含 grantor、inherit/set/admin 选项）、数据库/命名空间 ACL、对象 owner、函数 ACL 及角色启动设置。停应用并排空连接后处理权限，防止旧连接继续保持先前 SET ROLE 状态；随后使用新连接确认 session_user/current_user 均为运行身份。不得通过全表泛授或恢复迁移继承作为长期修复。

权限回退与数据库备份分开保留：数据库 dump 不包含角色成员图。若发布后新连接验收失败，保持维护窗口，按已记录的原图精确回退本次权限变更；不猜测旧 ACL 或无范围重赋 owner。

## 验证

`RuntimeMaintenancePrivilegePostgresTest` 使用 PostgreSQL 16 的真实独立非超级用户连接，应用不属于对象拥有者/迁移角色，验证普通 DML 与审计、定时器实际调用六个并发刷新函数、完整清库及原 outbox 守卫、epoch 与 refresh token 原子失效、非法调用/目标/actor、临时 catalog/用户/视图影子，以及持久同名关系保护。`MaterializedViewRefreshSchedulerTest` 保留并发锁和固定六入口合同。
