# ADR-104 追加自制并入未开工的生产计划

- 状态：已接受(2026-09-23，按同日复核补齐原车间工单加量)
- 迁移：[V645](../数据迁移/230-V645追加自制并入未开工的生产计划.md)保留原字节；[V647](../数据迁移/232-V647未领料车间工单原位追加.md)补齐同一执行段增长、冻结规则重算需求与追加式增长证据。
- 权限：零新增权限码
- 关联：[ADR-099 计划量单一入口](ADR-099-计划量单一入口与子层按计划产出展开.md)(采购/委外的 V640 就地追加)、[ADR-102 物料分析一张表直接下单](ADR-102-物料分析一张表直接下单.md)(§12 追加联动)、[ADR-081](ADR-081-下层一键办齐与物料表身份列统一.md)

## 一、用户口径(2026-09-22)

> 物料分析准备页面，追加的自制件，生产车间没有去领料开工的前提下应该自动合并啊。现在都是追加的都单独列，没有自动加到对应的单里面。采购好像是对的，就会自动加到一个单子，因为之前的单子没有去执行；没有执行那么可以自动加数量进去，但是如果已经开始执行了就创建新的单据。生产件一样的就放到一起去，或者一个计划单的。

## 二、问题

采购/委外自 V640 起就地追加：申请明细还没被采购/委外部门动过时，追加量直接改到原申请明细上。自制最初每次追加都会新建计划；V645 只解决了计划明细与关联行加量，已审核计划仍调用 `appendSegment` 另建执行段。车间任务按执行段展示，因此同一计划下仍出现两张不同 ZX 工单，违背「尚未领料时直接加到原单」的要求。以下原有身份守卫仍须保留，只为有完整增长证据的受控命令放行：

| 守卫 | 钉住的量 | 出处 |
| --- | --- | --- |
| `fn_guard_material_analysis_plan_item_identity` | 计划明细 qty | V234，V614 只放行日报定稿封顶 |
| `fn_sync_material_analysis_plan_link_qty` | 关联行 submitted_qty / public_surplus_qty | V490 / V577 |
| `UNIQUE(plan_id)` | 一张计划一条关联行 | V234 |
| `fn_guard_production_planning_draft_append_only` + `ProductionPlanningDraftService.save` | 预排草案载荷；分析计划不允许改写草案 | V191 |
| `fn_validate_production_execution_segment` | 执行段 planned_qty | V155 / V524 |

## 三、决策

### 3.1 什么叫「还没开工」(库侧唯一判据 `fn_material_analysis_plan_growable`)

计划未删除、未取消、未中止、未结案；草稿或已审核；恰一条计划明细且完工 / 入库 / 封顶累计全 0；没有报工、拆批或领料申请；每一段仍是 WAITING / READY；每张备料单(DRAW)仍是未审核、未发料、未删除的草稿；已审核时有且只有一个 CONFIRMED(执行模型 1)计划包，且原执行段具备可受控增长的完整来源。

**提交领料申请即进入执行边界**：即使仓库尚未审核或发料，只要已存在领料申请事实，就不再合并。派工(DISPATCHED)、开工(IN_PROGRESS)、备料单审核/发料、报工、拆批也都阻断合并。内部自动生成但尚未提交的 DRAW 草稿属于准备事实，可以保留并按差额补足；「可撤销计划包」不能代替本判据。路线确认本身不等于领料或开工。

### 3.2 并入的形状

- **同一单号**：计划头不动。计划明细 qty 加追加量；关联行同一行 submitted_qty 加归需求份、public_surplus_qty 加公共备货份(V645 放行，只增不减；关联行触发器顺手把分析行 submitted / approved 与分析版本推进)。
- **草稿计划**：预排草案作废重排(`supersedeActive` + `savePlanningDraft`)；请求带「立即审核」时整张(含此前草稿量)一起审核。
- **已审核计划**：同一计划、计划包、执行段 UUID 和 ZX 工单号继续使用，`fn_grow_material_analysis_execution_segment(segmentId, addedQty, salesAddedQty)` 受控增加原段计划量与物料基准量。物料需求沿原冻结耗用规则按**累计总量**重新计算，固定批次/包装不能把「旧需求 + 追加量单独计算的需求」当作新需求；需求身份、物料来源、冻结规则和已有预留不改写。销售来源先扩大订单排产容量，再增加原段的归需求分摊；公共备货仍不计入销售订单。
- **备料接续**：原预留与未提交 DRAW 保留，按新需求减去已有有效覆盖只准备差额；同一实际叶仓复用原未提交 DRAW，新增有来源的明细，不改旧行。齐套路线缺料时保留已有准备事实并等待新增缺口补齐，不能重占原数量或继续宣称全量齐套。无物料任务保持零需求/零 DRAW；未确认路线继续等待车间选择，不能因追加偷偷确认路线、提交领料或开工。新增物料按正常齐套/持续规则接续。
- **不可变证据**：每次原位增长写 `production_execution_segment_growth_events`，记录该次计划量、物料基准量与需求变化的依据。数据库守卫只接受与当前事务、原段和增长量一致的受控变化，普通 UPDATE 仍拒绝改量、换来源或改冻结规则。
- **来源需要量不跟着追加**：准备页「需要数量」读取只读 `sourceRequiredQty`(产品行读原始来源 `requestedQty`)，按真实根来源沿保存的精确 BOM 规则展开；追加只扩大计划、工单和实际备料需求。来源需要 3000、原工单追加到 4000 后，需要列仍为 3000，实际备料按 4000 计算。来源量不取会随追加增长的子锚点配额，也不替换执行 `requiredQty`；见 [ADR-099](ADR-099-计划量单一入口与子层按计划产出展开.md)。这是同日新增只读投影/显示合同，无新增迁移，V647 不改。
- **两条应用侧口径**：请求指定了生产车间时车间必须一致——换车间就是另一张单；没带「立即审核」的请求只并入草稿计划，不能把追加量悄悄并进一张已审核的计划绕过审核(客户端 approveNow = 持有生产计划审核权限)。
- 同一分析行有多张可并入的计划(历史数据)时取最近一张(关联行 created_at 最新，与主表「查看计划」同口径)。

### 3.3 不做什么

- 不在已提交领料或有执行事实的工单上改量；这些追加另建新单。
- 不重读当前 BOM 替换原冻结规则，不撤销既有预留，不改已提交 DRAW、实发、报工或拆批事实。
- 不用「撤销原计划包 + 红冲 + 新建合并量计划」替代(单号会变，用户口径是「加到对应的单里面」)。
- 不放宽 V577 的「排满后不声明 publicSurplusOnly 照旧 409」；并入只是落点变了，数量分账(归需求 = min(填的, 剩余)、其余公共)不变。

## 四、契约

- `POST /production/material-analyses/{id}/issue-plans` 请求不变。`GeneratedPlan` 新增 `mergedIntoExisting`(并入了已有计划) 与 `appendedQty`(并入的追加量；幂等重放为 null)；命令回放记录 `mergedPlanIds`。
- `issue-plans/preview` 走同一段代码后整体回滚，预览自然反映并入后的下层数量。
- 客户端：单张结果弹层标题「追加已并入原生产计划」、计划单旁「本次追加 N 已并入原计划」；多张列表同款副标题；已审核合并成功提示「追加数量已加到原生产计划和车间工单」；主表分段回报「下达车间(第 N 层，M 行，其中 K 张并入原计划)」。车间刷新后保留原 ZX 工单并显示合计数量。

## 五、验收合同

- 未执行的 3000 追加 1000：同一计划、同一 ZX 工单，数量 4000；连续追加和幂等重放不多建段、不重复加量。
- 同时核对来源需要量：真实来源仍需 3000 时，主表需要列保持 3000，子层实际备料及车间材料按新总量变化；汇总视图不混入执行锚点增量，级联列名为「本批备料需求」。
- 已提交领料但未发料、已发料、已开工、有报工或拆批：追加另建计划，原单数量和执行事实不变。
- 已有预留与未提交 DRAW：原 UUID/来源/实际仓保留，只补增量；物料不足时显示真实缺口，后续到料可补齐，固定批次跨阈值按累计总量计算。
- 草稿、销售归需求与公共备货、换车间、无料、未确认路线和权限边界保持原合同。V645 历史迁移合同继续保留，V647 另验受控增长与普通 SQL 绕过拒绝。
