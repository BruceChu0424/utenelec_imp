## 背景：一做数量就乱

用户口径(2026-09-21)：「现在计划里面的委外、采购和生产三个环节会相互缠绕, 一做数量就乱」。排查物料分析准备页, 根因不是某一处算错, 而是**同一个数被算了很多遍, 而且各算各的**：

1. **没有「每个节点的计划量」这个概念。** 节点上只有需求量(BOM 展开)和已下达量(链接/行动/台账), 「这个件到底打算做多少」在服务端不存在, 于是客户端(`material_cascade_quantity.dart` 等约 4000 行)自己按 `perProductQty × 本批数量 − 已覆盖` 重算下层, 与服务端的口径只能靠猜。
2. **超量是一条「公共尾巴」, 不往下传。** V577 把车间超量记成 `public_surplus_qty`, 但 BOM 展开只看需求量, 顶层多做 500 时下层的需求纹丝不动——用户看到「顶层 1500、下层 1000」, 只能手动补数。
3. **有子层的委外是一个节点两条路线, 八本账。** 委外申请、前置自制台账、锚点产品行、计划链接、行动、分摊、公共份、认领份各记一份数量, 下达时哪本账是主口径取决于走哪个入口。
4. **同一个「还可下达」在不同桶里有七种算法**(缺口 − 在途、锚点剩余、台账 required − notified、客户端回退……), 一周内 V577/V588/V589/V621/V634/V638 六张迁移都在对账同一个数。

## 决策

**数量只做一次, 在服务端做, 客户端只显示和转发。**

### 1. 每个节点有且只有一个「计划产出量」

`plannedOutputQty = max(需求量, 已下达计划量)`, 其中已下达计划量 = 计划链接的 `submitted_qty + public_surplus_qty`(未撤销的 SUBMITTED/APPROVED 链接)。

- 来源行(顶层)的计划产出量驱动第一层 BOM 展开：顶层按 1500 下达车间(需求 1000 + 公共备货 500)后, 第一层子件的需求量就是 1500, 不再是 1000 + 一条看不见的尾巴。
- 中间层沿用 ADR-080 的「父件计划产出」骨架, 只是把第三个输入换成事实：`parentPlannedOutput = max(净缺口, min(内部承诺, 缺口), 父件已下达计划量)`。父件锚点已经排了 1000, 子件就按 1000 展开; 锚点再排 500, 子件跟到 1500。
- 顶层超量后, 既有自制锚点的配额(`requested_qty`)自动按新增需求增长(`refreshWithAnchorGrowth`), 车间桶的「剩余可排」随之变大, 不用重新建锚。委外前置自制锚点不自动增长——它随 ARRANGE 通道按本批量跟到台账(V589)。
- 视图新增两列事实给客户端：`plannedOutputQty`(本节点计划产出量)与 `sharedFutureClaimableQty`(同主仓可认领的公共在途, 含晚到)。

### 2. 下达采购 / 委外：填多少下多少

`SupplyQuantityInput` 只剩 `qty`(本次总量)与 `safetyReplenishmentQty`。服务端按权威余量分账：不超过「还需安排」的归本需求, 超出的记公共备货(仍要 `over_supply` 权限; 我方供料的带 BOM 委外件仍禁公共备货)。客户端原来自己拆「需求量 + 公共量」两个数的 `publicExtraQty` 退役——它正是「客户端算的余量与服务端不一致 → 422 整批回滚」的来源。

### 3. 追加下达时先认领公共在途, 再就地改大未订货的申请

- **自动认领**：外部路线(采购、直接外发委外)下达时, 服务端先按「按期优先、晚到其次」认领同主仓的公共在途, 只为余下部分新下单; 认领动作与新单记在同一条命令里(`claimActionIds` / `acceptedLateSources`), 幂等重放不重复认领。会创建下层责任的组(自制、先自制目标件的委外)与我方供料的带 BOM 委外件不自动认领(它们要的是自己做出来的件)。
- **就地追加**(用户口径「只要委外采购那里还没有下单, 比如财务还没有审批, 多下的直接在之前还没操作的单里面变化数值; 已经审核或者已经在采购的, 就再下达采购委外单」)：对本操作组最近一条仍可改量的申请明细(`fn_preplan_supply_action_growable`: 申请开着、明细未订货、无任何订货单来源引用——含待财务审核的草稿订货单, 那已经是「在采购」), 把明细数量改大(`increaseProductionDraftLine`), 供给行动的需求量/公共量与各物料行的分摊同步只增不减; 没有可改的明细才另立新行动 + 新申请。带安全补库切片的批次仍走新单。追加后按单据再提醒一次「采购/委外需求追加：单号(追加 N)」。
- 数据库侧 V640 只对「明细仍未订货」的供给行动放开只增不减的改量(三个身份守卫 + 申请明细生产联动守卫共四处锚点补丁, 新增 `fn_preplan_external_item_unordered` / `fn_preplan_supply_action_growable` / `fn_is_preplan_supply_line_growth` 三个谓词), 其余谱系约束一个字节不动。

### 4. 父件 + 下层一起下单：数字全部由服务端算

- 车间通道的种子(顶层 / 自制候选 / 先自制目标件的委外)改本批数量时, 整页向 `POST /{id}/issue-plans/preview` 要一份「真实下达后的快照」——服务端真的跑一遍 `issueWorkshopPlans`, 然后 `setRollbackOnly` 整体回滚, 库里一行不留(计划、链接、命令记录、版本号全部还原; 幂等键被真实下达用过则拒绝预览)。整页按这份快照重建下层行：需求数量、还需安排、可认领公共在途、建议下单量都是服务端事实。
- 下层行「还需安排」= 服务端 `additionalSupplyRecommendedQty`(自制/委外前置自制行 = 锚点剩余可排量); 采购行的建议量在此之上按起订量/整包装抬。
- **已下过单的行仍可追加**(用户口径 2026-09-21 第二轮「即使采购、委外已下达甚至已处理, 父层级那里还是可以追加下单; 已处理时还缺数量是 0, 再填的数量就是额外追加, 属公共的」)：采购 / 直接外发委外行不再因「还需安排 = 0」不可填——默认不勾、不预填, 用户填的数就是追加量, 服务端按超量分账为公共备货(要 `over_supply`); 原申请还没被采购 / 委外处理的(下游引用 `growableLineQty` 非空)直接改到那张申请上, 已处理的另立新申请。已建自制任务的行在锚点余量为 0 时也可再下一批**纯公共备货产出**(`ProductView.canIssueSurplus`, V577 本就允许 submitted 0 + surplus N 的链接; issue-plans 只在行上**明确声明** `publicSurplusOnly` 时放行——不声明照旧 409, 重复点击 / 过期候选不能悄悄多建一张计划), 没建过任务的自制候选不放开(服务端对已覆盖候选拒绝建锚)。下层一行都没有缺口时不再问「只下达父件?」, 直接只提交父件。
- **追加量默认就写 0, 且 0 是合法值**(用户口径 2026-09-21 第四轮)：已下达行的输入框预填 0 而不是留空——勾着不动 = 这一行本次不下, 不再报「必须大于 0」; 提交时把填 0 的行从集合里剔掉, **必须连同 notify 的目标集合一起剔**(带着 actionGroupKey 却不给数量时服务端会按「未指定 = 全量剩余」下达, 等于把用户明确填的 0 翻成全量); 被跳过的行如实提示, 不静默丢。
- **分桶页「已下达」段直接追加**：采购 / 委外桶的已下达行(路线已确认、直接外发)仍可勾选, 「下达数量」格改为「追加量」输入框(默认空、旁注已下的总量), 按钮改叫「追加采购 / 追加委外」, 提交走 notify(`allowExtra`); 下达车间桶里需求已全部转入计划的顶层 / 自制锚点行在「下达数量」格填追加量, 按钮「追加生产计划…」带 `publicSurplusOnly` 进整页(树顶填车间 / 负责人、上限 0 照常过超量确认、下层按放大后的需求一起办)。委外前置自制锚点与自制候选不放开。
- 客户端删除：`material_cascade_quantity.dart` 及其测试(约 1000 行纯计算)、`MaterialAnalysisSupplyLink` 与 `GET /{id}/supply-links`(申请进度联动改由服务端就地追加自动处理)、`additionalSupplyRecommendationKnown` 与「旧载荷回退」(服务端恒定下发该字段, 回退分支只在测试夹具里活着)、`publicExtraQty` 全部拆账逻辑、`_CascadeParentChannel.subcontractMakeFirst` notify 整量接管通道(有子层的委外只走「下达车间」通道; 没有生成生产计划权限的账号在分桶页当面被拦下, 不再有第二条数量语义不同的路)。

### 5. 不变量

1. 一个节点一个计划产出量; 子件毛需求只跟随父件计划产出量(含公共备货产出), 父件计划产出为 0 则子树未下达需求为 0。
   **已完工入库的那部分不计入计划产出量**(2026-09-21 用户口径): 它的下层原料早已领走用掉, 再算一遍会让补做场景凭空多备一整批料——
   某件计划做 10、做完 10、其中 4 件报废使锚点涨到 14 时, 下层原料的「还需安排」是 4 而不是 14。逐条计划链接按
   「本批计划量 − 本计划已完工入库量」计、单条不为负再求和; 已完工入库量沿用 `productPlanStates` 的同一口径(计划明细 `iqty` 封顶到 `qty`)。
2. 「还需安排」只有服务端一个算法; 客户端没有任何 `缺口 − 在途` 的回退。
3. 申请明细数量只增不减, 且只在「未订货」时可改; 一张明细仍只对应一条行动。
4. 自动认领只发生在下达那一刻, 认领量 ≤ 来源可认领量且 ≤ 本次需求量; 认领与新单同命令、同幂等键。
5. 预览与真实下达同一段代码, 预览零副作用。

## 影响

- 服务端：`MaterialAnalysisService`(计划产出量、锚点自动增长、两列新事实)、`MaterialAnalysisCommandService`(分账、自动认领、就地追加、预览)、两张申请 Facade 的 `increaseProductionDraftLine`、`ChainNoticeService` 的追加提醒、V640。
- 客户端：分桶详情与「父件 + 下层一起下单」整页改为消费服务端数字; 数量语义统一为「本次总量」。
- 与 ADR-080「明确不做」表的关系：「第 0 层根供给行按在途净算下层」仍不做(第一层需求仍是实物执行层基准); 「父件行一键办齐子层」由 ADR-081 接办, 本文只换它的数字来源。
- 与 ADR-081 修订二的关系：`GET /{id}/supply-links` 与「并入原申请调量 / 已分解另立」的客户端判断退役, 由服务端就地追加统一处理。

## 验证

- `PreplanPlannedQuantitySingleEntryEndToEndTest`(真库)：顶层 1500 超量下达后下层需求按计划产出量放大、既有自制锚点配额 1000→1500、锚点再排 500 后孙层计划产出跟到 1500; 预览真实跑一遍再整体回滚且同一幂等键可再预览/可真实下达; 采购追加 600 + 400 就地改大同一条明细、订货后再追加另立新申请; 填 1200 时服务端分账 1000 + 200; 主仓公共在途 900 在下达时先自动认领、只为余下 100 新下单, 幂等重放不重复。
- `PreplanSupplyLineGrowthMigrationContractTest`：V640 只新增三个函数、四处锚点补丁、不建表不动触发器。
- `PreplanPublicFutureReplenishmentEndToEndTest`：需求已被认领 + 自购全覆盖时再填 100 → 整个 100 归公共备货, 需求侧一分不多下。
- Flutter：`material_analysis_child_cascade_test.dart`(8 例, 预览接线、树顶改量重算、拦下空数量)、分桶/根供给/备料路线夹具补齐服务端字段。
