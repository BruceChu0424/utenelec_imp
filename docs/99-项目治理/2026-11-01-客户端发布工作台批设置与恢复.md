## 先比较 owning 实现与根因

- Web/Flutter 桌面共用 `ClientReleasePublishPage`、`ClientReleasePublishQueue` 和 metadata-only 草稿。顶部 `_context` 只供新增项读取；用户先选文件再改顶部版本时，旧行完全不变。
- `_recordFailure` 无条件清除文件句柄；版本、重复项等尚未读取文件的验证失败也要求重选。已成功和已上传项的原队列状态机实际会跳过上传，须保留该保护，不能用新 UUID 或重建队列“重试”。
- 恢复草稿后仅加载总列表，没有逐行核对原 release/request ID；发布成功事实恢复为待核对后，用户容易误以为需要重新选包。只有原 ID 的严格服务器回执能恢复成功，不能相信本机状态或文件名。
- WPF 候选已有发布队列，但核实出相同的默认值仅供新增、验证前误清文件来源问题；已同步适用的最小 C# 行为。旧 75 项仅协议测试未覆盖实际页面，新增真实 View 构造/Arrange 又发现原有两个逻辑父级错误和圆角资源类型错误，详见下文。新版完整布局仍单独待迁移，不能以旧证据称当前 UI 可用。

## frontend-design 计划与自检

沿用 Uten 色板和主题映射：主操作 `#0F766E`、底色 `#F5F7FA`、面 `#FFFFFF`、主字 `#0F172A`、次字 `#475569`、边线 `#E2E8F0`；字体与字号沿现有 Noto Sans SC/textTheme，间距、圆角均取 Uten token。

布局以文件结果为主体，信息左对齐。顶部紧凑呈现“本批设置”和真实同步范围；队列占满桌面主区，成功、未完成、待核对明确分开，配对及草稿说明放入可展开区域。窄屏换行并可滚动，保留键盘焦点与完整动作文字。特色在“批设置 → 继承项”和“原提交 → 确认结果”关系，不另造装饰卡片、渐变或视觉语言。

```
本批设置       自动跟随 n 项 / 单独设置 n 项 / 已冻结 n 项
版本与构建 / 适用设备 / 发布说明
发布队列（全宽）                   添加 / 批量添加 / 核对原状态
逐文件：精确目标、阶段、原记录、必要的恢复动作
已确认 / 待核对 / 待处理                         上传或继续未完成
交付配对与草稿说明（按需展开）
```

复核：既有右侧固定 300px 摘要占用主要工作宽度，改为按需展开；批设置仍直接可见。状态区使用文字与主题语义色，成功后禁用无意义的再次发布入口，待核对只执行原 ID 的 GET。

## 安全合同

- 顶部只联动未绑定 requestId/releaseId/SHA、未提交且未被单行手动覆盖的元数据。设备配置和版本/构建分别成组保留；单行明确选择“使用本批设置”才撤销自己的覆盖。Windows EXE/ZIP 的类型提示继续分开，文件名不推断版本或架构，服务端包内容仍权威。
- 覆盖来源只存有限字段名；旧草稿没有来源信息时保守保留原值。元数据一旦冻结便不可重写，未知结果只核对原记录；已上传项仅继续原 publish，已成功项不创建、不上传、不发布第二次。
- 自动恢复和批量核对只有 GET，不补发 POST。服务器返回目标、包类型、原 SHA、大小和阶段必须匹配原意图；Windows 保留检查仍按既有契约明确收口。
- 未读取文件的验证失败保留本次选择；实际读取过的一次性流不伪装成可重复读取。草稿从不包含文件字节、路径、凭据或未获授权的持久文件句柄。刷新后只对服务器尚未收到的文件要求重选相同 SHA；已有服务器文件和已发布项先按原 ID 恢复。
