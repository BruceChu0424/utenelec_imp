# 227 · V641 我方供料的委外件放开公共超量备货

- 迁移：`V641__subcontract_own_supply_public_surplus.sql`
- 类型：前向，锚点补丁两个函数。**不加表、不加列、不改历史行、不动触发器、不改数据。**
- 口径来源：2026-09-21 用户口径「我把采购超量下单后，委外甚至是车间那里下单就不能超量下单，必须是正常数值才能下单」。实测被拦的是「V4开关面板(喷油)」——我方供料、只有一颗叶子子件的委外件。
- 决策：[ADR-085 委外单一子件直接发料出仓](../99-决策记录-ADR/ADR-085-委外单一子件直接发料出仓.md) §2.2 与 §四；数量口径见 [ADR-099](../99-决策记录-ADR/ADR-099-计划量单一入口与子层按计划产出展开.md)。
- 编号：本迁移 592→593。

## 为什么原先禁，为什么现在放开

原先的理由写在 V472(禁所有带 BOM 的委外件)与 V589(收窄为只禁 ADR-085 的单一叶子子件件)里：多下的量会凭空多出一份**无人负责**的子件需求——多喷 500 片面板，就要多发 500 片素面板给委外商，而计划表上没有人算这 500 片。

2026-09-21 ADR-099 修订之后这条理由不再成立：「父件 + 下层一起下单」整页上**每一行填的数量**都成了服务端事实(`issue-plans/preview` 的 `typedOutputs`)，多下的量按计划产出量如实带大它的子件需求，就在同一张页面里一并下单。既然有人负责了，就不该再拦——用户在采购桶能做的事，委外桶也要能做。

## 改了什么

| 对象 | 变化 |
| --- | --- |
| `fn_guard_preplan_public_surplus_shape()` | 删掉「`NEW.route='SUBCONTRACT'` 且 `fn_subcontract_sole_component_goods(goods_id)` 即抛 `preplan_public_surplus_subcontract_leaf_guard`」那一整段。其余形状校验一个字节不动：公共量只能挂在 BUY/SUBCONTRACT 的 SUPPLY 行动上；OPEN 态不得先有公共明细锚；外部化后必须锚到身份与数量都对得上的申请明细(V588 合并明细形态：独立明细 = 公共量，合并明细 = 归需求量 + 公共量)；`SUBCONTRACT_MAKE_TASK` 外部化仍允许公共明细锚为空(V589) |
| `fn_preplan_direct_overorder_capacity(uuid,uuid)` | 删掉「`source_action.route='SUBCONTRACT'` 且该货品有未删除 BOM 行就恒返 0」那一条。它是订货**批准**时登记运行时公共在途(`preplan_public_supply_events`)的容量上限。**这一处是预备性的**：唯一写这张表的 `PreplanPublicSupplyCaptureService.candidates` 在 Java 侧同样按「委外件有活动 BOM 就排除」过滤，候选集为空，所以这类件放开前后都走不到那道触发器、也不会撞 23514。改它只是不让同一口径的三份拷贝(客户端 / 服务端 / 数据库)里留一份相反的；真要让这类件的公共量变成别人可认领的公共在途，还得连那处 Java 过滤一起放开——那是认领侧的产品决策，不在本迁移 |

两处都按 V580/V588/V589 的纪律做：取 `pg_get_functiondef`、行尾归一 LF、锚点不中就抛异常整批失败，绝不整段重写函数体。

## 同批的服务端与客户端改动(不在本迁移内)

- `MaterialAnalysisCommandService#notifySupplyInternal`：撤掉与数据库同口径的那条可读拒绝(「是我方供料的委外件……不能创建公共超量备货」)。`production_material_analysis:over_supply` 权限照旧要。
- `MaterialAnalysisService`：层级表上「顶层供给行」填的数量并进来源行的计划产出量(`typedSourceOutputs`)，顶层直委外件按 1500 下达时那颗我方供料的子件就按 1500 备。
- 客户端 `_supplyQuantityEntry`：这类行不再在本地把超量输入拦下(原提示「需要超量下达权限」会把人引去申请一个并不解决问题的权限)。

## 存量影响

- 已有数据一行不动：本迁移只替换两个函数体。
- 放开之后，我方供料的委外件也会在订货批准时登记公共在途，可被别的分析认领(认领侧的放开由并行会话另行处理，本迁移不碰)。
- 回滚：把两个函数按 V472/V589/V474 的版本重新 `CREATE OR REPLACE` 即可；已产生的公共量数据不会因此损坏，但会被新的形状守卫拒绝后续改量。

## 验证

- `PreplanPlannedQuantitySingleEntryEndToEndTest#soleComponentSubcontractTakesOverQuantityAndItsComponentFollows`(真库)：单一叶子子件的委外件按需求 1000 + 超量 500 下达，行动记 `requested_qty=1000 / public_surplus_qty=500`，委外申请明细合并成 1500；**预览与真实下达之后**那颗我方供料子件的需求都跟到 1500。

## 多下的那部分由谁负责(同批的服务端补充)

这类件不建锚点、不出计划，`parentSupplyCommitments` 里「已下达计划量」那条查询(计划链接)对它恒为空——所以光放开闸门还不够：真实下达 1500 之后子件需求会退回按物理缺口算的 1000，多出来的 500 片就成了无人负责的需求(仓库要发 1500，只有 1000 下过单)。本批同时补上载体：**未结的委外供给行动**(归需求量 + 公共备货量 − 已回厂量，按行动在各物料行上的分摊比例摊回节点)也计入该节点的计划产出量。没有超量时这一项恒等于原来的需求量，口径不变。
