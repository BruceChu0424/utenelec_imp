# ADR-154 证件号问题不阻塞开号与证件核对任务

- 日期：2026-10-05。
- 状态：已接受(2026-10-05)；本地源码实现(分支 `feat/idcard-nonblocking-provision-20261005`)。迁移用开发期临时号 V807，ADR 编号 154 也是开工时取的第一个空闲号(main 最大 141，142-153 在其他会话在途)，合并时两者都可能按当时 main 重新编号。
- 迁移：[V807 员工证件号校验状态](../数据迁移/V807-员工证件号校验状态.md)(`employee_sensitive` 加一列 `id_card_check` 和两个约束，不加表)。
- 权限：零新增权限码。证件核对任务复用 `employee:pii:edit`，就绪检查复用 `account:support`。
- 关联：[ADR-110 服务端会话与敏感操作再认证](ADR-110-服务端会话与敏感操作再认证.md)(初始密码规则，本 ADR 修订其 2026-10-02 一节)、[ADR-021 人事域完善与任务软认领](ADR-021-人事域完善-转正车辆多联系方式与任务软认领.md)(任务软认领，本 ADR 新增 `identity` 类型)、[ADR-108](ADR-108-前端性能徽章汇总会话快照与刷新时机.md)(工作台徽章汇总)、[ADR-141](ADR-141-AI业务查询与可见表单辅助填写.md)(AI 人事任务工具不输出证件信息)。

## 一、用户要求

1. 开通账号之后，身份证之类的信息有错只给一个明显的红色或黄色警告，让人事有个任务去核对修改，**不要阻塞开通账号**。
2. 前端报错要明确：比如身份证错，要说清楚是长度错还是哪一位错，数据对不上要用更明确的方式说出来。

## 二、背景

2026-10-02 起(ADR-110 修订)新账号初始密码取规范证件号后六位，`EmployeeOnboardingService.initialPassword` 在两种情况下直接抛错：证件号缺失或不足六位；身份证号校验不通过(报「身份证号校验未通过，无法开通账号」)。老库人事导入只做去空白就加密入库，所以存量员工里有校验不通过、号码缺失、证件类型错标(护照、港澳证件被标成身份证)的档案，这些人一直开不了号；而编辑页没有证件号输入框，PUT 也改不了证件类型，错标的人永远改不过来。

所有身份证校验失败都只报一句笼统的「身份证号校验未通过」，人事不知道是长度不对、哪一位不是数字，还是校验码对不上。

## 三、决策

### 3.1 开号只拦确实开不了的情况

| 检查 | 行为 |
|---|---|
| 员工不存在或已删除 | 拦，NOT_FOUND |
| 已离职 | 拦，CONFLICT |
| 已有账号 | 拦，CONFLICT |
| 没有手机号 | 拦，VALIDATION_FAILED(登录账号就是手机号) |
| 手机号已被其他账号用作登录名 | 拦，CONFLICT。这项检查挪到派生密码之前：开不了的号不解密证件密文 |
| ADR-110 高危开号闸 | 拦，同一事务回滚，不留半开的号 |
| 身份证号校验不通过 | **放行**，密码取档案号码后六位，返回结果带 `employee.idNumberIssue` |
| 证件号缺失 | **放行**，随机密码，带 `employee.idNumberIssue` |
| 证件号密文解不开(数据损坏、换密钥后没配旧密钥) | **放行**，按派生不出来处理，随机密码，带 `employee.idNumberIssue`(读取不出来) |
| 非身份证类证件不足六位 | **放行**，随机密码，不算问题 |

### 3.2 初始密码只有一条规则

档案证件号规范化后够六位就取后六位(身份证号校验不通过也一样)；没有证件号或不足六位时由 `TemporaryPasswordGenerator` 随机生成 20 位，只显示一次。有效期、首登必须改密、Argon2 哈希、再认证和高危开号闸都不变。入职(`onboard`)和补开账号(`provisionAccount`)共用 `idSuffixPassword` + `initialPassword`。

补开账号解密档案证件号用 `TxSessionVars.tryDecrypt`：在保存点里用原生 JDBC 执行 `pgp_sym_decrypt`，失败就回滚到保存点并返回空，不会让开号事务作废、也不会被 Hibernate 标成只能回滚；密钥版本不在密钥环里时不发 SQL 直接返回空。返回结果里的员工详情(`EmployeeQueryService` 同样用 `tryDecrypt` 读证件号)号码留空，`idNumberIssue` 说明号码读取不出来。其它敏感字段仍用严格的 `decrypt`，解不开照常报错。

校验不通过仍用后六位的理由：规则只有一句话；六位数字当面口头告诉员工很容易；凭据弹窗会明文显示密码，红色提醒还写明「可能和员工本人证件后六位不一样，请把这里显示的密码告诉员工」。

### 3.3 入职和修改证件仍严格校验，但报出具体原因

用户说的是给已有员工开账号不阻塞，不涉及录入环节。入职时员工本人和证件都在场，录入时把关才能从源头不再产生坏数据；修改证件是给任务结案的动作，允许保存仍不合格的号码，任务就永远结不了。错标证件类型的特殊情况，靠「修改证件信息」可以同时改证件类型来解决，不靠放宽校验。入职时非身份证类证件不足六位不再拒绝，改用随机密码。

### 3.4 身份证号具体问题：服务端一条规则

`IdCardUtil.check(String raw)` 是唯一的判定规则：合格返回 null，否则返回 `IdCardProblem(code, message)`，只报第一处问题。`isValid(raw)` 等于 `check(raw) == null`。先规范化(全角转半角、去首尾空白、转大写)，长度和位置按字符计数。说明文字只写位置和长度，**绝不带号码本身**。

| 顺序 | 问题码(库里存的值) | 给人看的说明 |
|---|---|---|
| 1 | `empty` | 身份证号不能为空 |
| 2 | `length:<n>` | 身份证号应为18位，当前为<n>位 |
| 3 | `character:<位置>`(第1-17位) | 身份证号第<位置>位不是数字(只有第18位可以是X) |
| 4 | `character:18` | 身份证号第18位只能是数字或X |
| 5 | `birth_date` | 身份证号第7-14位不是有效的出生日期 |
| 6 | `birth_too_early` | 身份证号第7-14位的出生日期早于1800年 |
| 7 | `birth_future` | 身份证号第7-14位的出生日期晚于今天 |
| 8 | `region_code` | 身份证号前6位地区码不能全为0 |
| 9 | `sequence_code` | 身份证号第15-17位顺序码不能全为0 |
| 10 | `check_digit` | 身份证号第18位校验码与前17位不符，通常是某一位数字录错或相邻两位颠倒，请对照证件逐位核对 |

- 第7-14位按 yyyyMMdd 严格解析(2 月 30 日之类不存在的日期算 `birth_date`)；「今天」取业务时区 `BusinessTime.today()`。校验码按 GB 11643-1999 规定的 ISO 7064 MOD 11-2 计算。
- `IdCardProblem.fromCode(code)` 从存下来的问题码还原同一句说明，不认识的码返回 null。所以库里只存码，界面文字和录入时当场看到的一致。
- 以前报笼统「身份证号校验未通过」的地方全部改成具体说明：入职(`EmployeeOnboardingService.onboard`)、证件写入口(`EmployeePiiWriter.applyIdentity`，修改证件也走这里)、访客预约(`VisitorApplicationService`，任何非空号码都校验，15 位老证号同样报「身份证号应为18位，当前为15位」；请求体去掉笼统的格式校验，只留 32 个字符的长度上限)、`IdCardUtil.birthDate/gender`。
- Flutter `IdCardUtils.problemOf(raw)` 按同一顺序返回逐字相同的说明；入职页、修改证件弹窗、访客预约页和 `InputValidators.idNumber` 都直接显示它。`test/core/utils/id_card_utils_test.dart` 读取服务端 `IdCardProblem.java` 核对文案逐字一致，任何一边改字另一边就红。

### 3.5 校验结果存一列，不在读取时现算

新增 `employee_sensitive.id_card_check`，取值 `valid`、`unchecked`、`unreadable` 或上表的问题码之一；没有证件号密文时为 NULL。它只含位置和长度，是非敏感元数据，照常进审计。

| | 存一列(采用) | 读取时现算 |
|---|---|---|
| 人事任务和徽标 | SQL 多关联一张表，不解密 | 每次 summary/count 都要把全部在职员工的证件密文解密一遍；任何写入都会触发徽标重拉，开销反复发生 |
| 开号候选、就绪检查 | 直接读列 | 再解密一遍 |
| 符合「只算一次、在服务端算」 | 写入时算一次 | 每次读都重算 |
| 代价 | 1 个迁移、1 个启动回填任务、老库脚本改一行 | 不用迁移 |

- 两个约束：取值约束(正则只允许上面这些值，长度码最多 3 位、位置码最多 2 位)；存在约束 `(id_card_enc IS NULL) = (id_card_check IS NULL)`。以后任何新写入口忘了写校验结果，数据库直接拒绝。
- 写入：Java 侧只有 `EmployeePiiWriter.applyIdentity` 写密文，并在同一处调 `EmployeeIdentityCheck.classify` 写结果。身份证按 `IdCardUtil.check`，其他证件号码不为空即 `valid`。存储的长度码封顶 `length:999`(只影响存储，`check` 仍报真实长度)。
- 存量：数据库拿不到解密密钥，迁移只能把已有密文标 `unchecked`。启动回填任务 `EmployeeIdentityCheckRunner`(`@Order(61)`，启动时先 `REFUSING_TRAFFIC`)和 V282 回填任务、老库人事导入脚本共用同一把 advisory lock `(0x5554454E, 282)`；按 `employee_id` 键集分页每批 100 条，每批一个事务，逐行用 `TxSessionVars.tryDecrypt` 解密(在保存点里执行，解不开只回滚到保存点，本批事务照常可用，也不经 Hibernate 报 ERROR)；解不开的行(数据损坏，或密钥版本不在密钥环里)存成 `unreadable`，**不阻止启动，以后启动也不再重试**；条件更新带上 `unchecked` 和原密文，并发的修改证件不会被覆盖。日志只写数量：有解不开的行时一条 WARN 汇总，否则一条 INFO 汇总，没有逐行日志，不写号码、后四位或姓名。
- `unreadable` 只有回填任务会写；写入口按新号码重判，所以人事对照证件重新登记一次号码(「修改证件信息」)就改写成 `valid` 或具体问题码，任务结案。如果是换密钥后没配旧密钥造成的成批 `unreadable`，配好旧密钥后执行 `UPDATE employee_sensitive SET id_card_check = 'unchecked' WHERE id_card_check = 'unreadable'` 再重启一次，回填任务会重新判定。
- 老库脚本 `migrate_hr_roster.sql`、`migrate_hr_workers.sql` 写密文时同写 `unchecked`；`build_hr_roster.py` 的证件相关告警(出生日期或性别与身份证不一致、身份证解析不出出生日期、校验位不符、长度或字符不对)不再打印证件号、由它推出的出生日期或性别、表内出生日期和姓名，只留序号和原因；号码不是 18 位数字(含 X)时只告警「身份证号长度或字符不对」，不再在算校验位时崩溃。
- 架构测试 `ArchitectureBoundaryTest` 锁边：只有 `EmployeePiiWriter` 调 `setIdCardCheck`；`setIdCardEnc` 只在 `EmployeePiiWriter` 和访客服务(另一张表)；SQL 写 `id_card_check` 只在回填任务；`IdNumberIssue` 只由 `EmployeeIdentityCheck` 构造。

### 3.6 对外的证件问题是一个对象，只有一个出处

`idNumberIssue` 为 null 或 `{"kind": "missing" | "invalid" | "unchecked", "reason": "<服务端拼好的中文原因>"}`，只由 `EmployeeIdentityCheck.issueOf(hasCipher, storedCheck, superAdminAccount)` 构造。员工详情(开号结果同源)要显示号码本来就得解密，此刻解不开时不管存的是什么都按 `unreadable` 传给 `issueOf`，所以同一种情况在人事任务、就绪检查、开号结果和详情里是同一句原因：

| 情况 | kind | reason |
|---|---|---|
| 员工绑定超级管理员账号 | (null) | 人事改不了超管的证件，不能列成永远结不了的任务 |
| 没有证件号密文(或没有敏感行) | `missing` | 档案里没有证件号码 |
| 存的是 `valid` | (null) | |
| 存的是 `unchecked`(或密文存在但结果为空，约束下不会出现) | `unchecked` | 证件号码来自历史资料导入，系统还没有完成校验 |
| 存的是 `unreadable`(启动回填解不开)；或员工详情、开号结果读取时解不开(不管存的是什么) | `unchecked` | 档案里的证件号码读取不出来，系统无法校验，请人事对照证件重新登记 |
| 存的是问题码 | `invalid` | `IdCardProblem.fromCode(码).message()`，例如「身份证号应为18位，当前为17位」；不认识的码兜底为「证件号码没有通过校验，请对照证件核对」 |

用在三处：员工详情 `EmployeeDetail.idNumberIssue`(开号和入职的返回结果里 `employee.idNumberIssue` 同源)；开号就绪检查；人事任务条目的 `note`。

### 3.7 开号前、开号后、详情页都提醒；红黄分级

- 新增 `GET /api/org/employees/{id}/account/readiness`(`account:support`，只读事务)，返回 `{hasPhone, idNumberIssue}`，只看有没有密文和已存结果，不解密。开号确认弹窗一打开先读它：没有手机号显示红色提醒并把确认置灰(服务端照样兜底拦)；证件有问题显示红/黄提醒，确认照常可点；读失败不额外提醒、照常可确认，以服务端结果为准。三个开号入口(员工详情页、权限管理页「开通账号」、页面权限工作台)都走 `showProvisionSelectedEmployeeAccountFlow`，调用参数不变。
- 一次性凭据弹窗：返回结果带 `idNumberIssue` 时，在临时密码上方加同色提醒，说明初始密码怎么来的、要把弹窗里显示的密码告诉员工。
- 员工详情页：头部常驻提醒(每个 Tab 都看得到，修好之前一直显示)；概览「证件号码」一行带「待核对」徽标；持 `employee:pii:edit` 时显示「修改证件信息」。
- 颜色：`invalid` 用红(error)；`missing`、`unchecked` 用黄(warning)。提醒正文第一句原样显示服务端 `reason`(「具体问题：…」)，第二句按场景说明接下来怎么办。人事任务的标签和计数一律红，因为「轮到人事办」。

### 3.8 人事任务中心新增「证件核对」(`identity`)

- 内容：在职和试用期员工里 `idNumberIssue` 不为 null 的人；`date` = 入职日期(可为空)，`days` = 0，`note` = `reason`；按工号排序。`HrTaskSummary.identityReview` 位于 `newHires` 之后、`badgeCount` 之前。
- 可见和计数：只有超管或持 `employee:pii:edit` 的人拿到列表，其他人(包括只有 `employee:view` 的总经办等)拿到空列表、不计数。`employee:view` 发得很广，非人事的管理者不该被这类任务打扰。不新增权限点，也不动 `hr.task` 页面权限范围。
- 徽标：`badgeCount += identityReview.size()`，红数，经现有 `hrTask.count` 进工作台徽章汇总；被认领的照样计红。徽章目录本身不改。
- 认领：`identity` 加入认领类型白名单。**认领和接管 `identity` 另需超管或 `employee:pii:edit`**，否则 403「只有能修改员工证件信息的人可以处理证件核对任务」；检查在接管释放他人认领之前执行。释放规则不变。
- 前端：路由 `/hr/tasks/identity` 要求 `employee:pii:edit`(超管照常放行)；工作台有待核对员工时在概览上方显示红色横幅「有 N 名员工的证件号码待核对」+「去处理」，入口卡只给能修改证件的人；列表页显示「原因」列(红字)，不显示天数、区间两列，不开多选；行菜单和窄屏卡片有「修改证件信息」(被别人认领时不显示)，成功后静默重算徽标。
- AI 人事任务工具(ADR-141)不读这份列表，仍承诺不输出证件信息，测试锁定。

### 3.9 修改证件只有一个入口

- 新增 `POST /api/org/employees/{id}/change-identity`，请求体 `{idType, idNumber}`，`employee:pii:edit`，不要求再认证(改证件号不影响登录凭据，与 `change-phone` 一致)。成功返回 200 空正文(同 `change-phone`)。
- 超管账号的员工返回 403「禁止通过员工管理修改超级管理员的证件信息」；证件类型不在 `身份证 / 护照 / 港澳台通行证 / 其他` 里返回 422 VALIDATION_FAILED「证件类型不正确」；身份证号不合格返回 422 VALIDATION_FAILED + 3.4 的具体说明，且什么都不写；号码已被其他员工使用返回 409「该证件号码已被其他员工使用，请核对是否录错或与其他员工档案重复」(各类证件同一句话，不点名占用者)。
- 走 `applyIdentity`(严格校验、HMAC 查重、密文/后四位/哈希/校验结果同写)；身份证顺带重算出生日期(加密)、生日月日和性别；没有敏感行就新建；员工 `version + 1`，在途资料变更申请审批时 409。任务和徽标随之消失。
- 删掉 PUT `/{id}` 的证件号路径(`UpdateEmployeeRequest.idNumber` 字段、写权限判定和 `updateSensitive` 的身份证分支)。客户端编辑页在组装 PUT 时一律剔除 `idType` 和 `idNumber`。
- 修改证件弹窗(详情页和人事任务共用)：身份证边输边校验并显示具体说明，不合格不发请求；只预填服务端给的明文号码，服务端给的是脱敏值(含 `*`)时绝不预填，提示直接输入完整新号码；切换证件类型后提交新类型。

### 3.10 失败时说清楚原因

开号确认弹窗和修改证件弹窗失败时显示服务端原话(`employeeDialogErrorText`：服务端 message 加上正文里没有提到的字段级原因)，只有不是服务端报错或服务端没给任何说明时才用「开通账号失败，请稍后重试」「保存证件信息失败，请稍后重试」这类笼统话。入职页表单因证件号校验失败时，除字段提示外再用页面提示说一遍具体原因。

## 四、备选方案

| 方案 | 不采用的原因 |
|---|---|
| 读取时解密现算问题 | 人事任务、徽标、就绪检查每次都要解密全部在职员工的证件密文，写后徽标重拉让开销反复发生。保留退路：所有读取只经 `issueOf`，必要时只换这一个函数 |
| 继续阻塞开号 | 违背用户要求；错标证件类型的人永远开不了号 |
| 一律随机密码 | 六位数字便于当面交付是 ADR-110 2026-10-02 修订的用户要求；本次只在派生不出时随机 |
| 修改证件时允许保存不合格号码 | 任务永远结不了；真实的特殊情况(护照等错标)靠同时改证件类型解决 |
| 存 `invalid` 一个值，原因读取时再解密算 | 拿不出具体原因就满足不了要求 2；存问题码不含号码，可审计，又能还原逐字相同的说明 |
| 新增一个「证件核对」权限点 | 能修的人就是持 `employee:pii:edit` 的人，复用即可，不用改权限迁移和授权目录 |

## 五、安全与隐私

- 问题码和说明只含位置和长度，不含号码或其中任何一段；就绪检查、人事任务、详情页的问题字段都不解密。
- 回填任务、构建脚本告警、新增测试的断言信息都不打印号码、后四位或姓名；业务链测试断言人事任务、就绪检查的响应正文里没有证件号码片段。
- 证件核对列表和计数只给能改证件的人；认领、接管同口径。

## 六、后果

- 存量员工证件号有问题也能开号，人事任务中心多一类红色待办，直到人事修好。
- 老库脚本在服务端运行期间导入的行，要等下次启动才判定；在此之前显示为黄色「尚未校验」，人事重新保存一次号码即可结案。
- 回填任务解不开的号码存成 `unreadable`，各处都显示黄色「档案里的证件号码读取不出来，系统无法校验，请人事对照证件重新登记」，直到人事重新登记；不会每次启动都重试、刷日志。前端仍只认 `missing` / `invalid` / `unchecked` 三种 kind，`unreadable` 按 `unchecked` 下发，靠 `reason` 区分。
- 存的是 `valid` 或问题码、之后才解不开的号码(例如换密钥后没配旧密钥)，人事任务和就绪检查不解密、仍按存的结果；会解密的员工详情和开号结果说「读取不出来」。
- 老库重复证件号的残档(有密文但哈希为空)号码本身合法，不会被标记；如果人事去改这些号码，会因号码已被其他员工使用而 409，这类数据应合并或注销，不归本次处理。
- `ProvisionCandidateDto.hasIdCard` 删除(客户端早已不用)。
- 合并时：迁移临时号 V807 和本 ADR 编号可能重编，需同步迁移文件名、`reset_business_data.sql` 版本对与报错文案、数据迁移 README 头行、V807 说明文件名、`EmployeeIdentityCheckMigrationContractTest` 的路径常量以及代码注释里的 V807 字样。
