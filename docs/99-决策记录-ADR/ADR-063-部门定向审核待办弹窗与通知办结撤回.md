# ADR-063：部门定向审核待办弹窗与通知办结撤回

## 2026-09-10 生效修订

以下修订取代 §4「稍后再看」与 2026-09-07 §2 的部分口径，其余历史决定保留溯源：

1. **登录弹窗口径 = 「未办结 且（未确认弹窗 或 稍后到期）」**。一条待办在未办结期间每次
   登录都弹，直到用户确认过它——已读（`markRead`）或【去工作台处理】即置
   `notice_user_states.popup_acknowledged_at`，此后静默直至办结；**「稍后再看」到期恒重弹**：
   `snoozed_until` 非空且已到期时不看 popup_acknowledged，即使期间已读。因此 `markRead`
   只置 read_at + popup_acknowledged_at、**不再清 snoozed_until**；`snoozeNotice` 置
   snoozed_until + read_at。右上 X 不 ack 不 snooze（未确认下次登录仍弹）。
   实现：`NoticeRepository.findVisiblePendingReviews`、`NoticeService.markRead/snoozeNotice`；
   前端【全部稍后再看】只调 `POST /notices/{id}/snooze`（不再并发调 read——两次全列 UPDATE
   竞争会把 snoozed_until 冲回 NULL）；`NoticeUserState` 加 `@DynamicUpdate` 按列落库，
   snooze 与 markRead 各写各列互不覆盖，不新增版本列/迁移。
2. **车间任务 normal 优先级卡也弹**：`PRODUCTION_WORKSHOP_TASK_ACTION_REQUIRED` 的
   备料中/等待领料（normal）与可开工（important）同为「收到的车间任务」，登录检查与
   `isActionableReview` 不再按 priority 过滤；弹窗副标题下按事件分组计数（「车间任务 3 ·
   来料待检验 1」）。
3. **车间任务卡办结点修正**：目录注释曾写「首次报工后按聚合办结」但报工从未调用办结。
   现口径：车间**开工（START）**即按段办结（`ProductionExecutionSegmentService.applyTransition`
   reason=STARTED）；**完工入库**（段 COMPLETED，DB 触发器置态）由完工投递兜底办结
   （`ChainNoticeService.deliverFinishedInbound` reason=COMPLETED）；取消/红冲、清空车间、
   换车间重投同样按段办结。报工本身不办结。
4. **人事域接收池是「部门 ∧ 权限」总口径的明示例外**：`HrNoticeService` 六个事件
   （信息变更/访客申请/接待确认/报销审批/报销打款/工资审核）及本次新增两个（工资待发布/
   建议待回复）按**职能权限、不限部门子树**判定（`ReviewNoticeAudience` 只查权限）——
   HR/财务/回复职能天然跨部门，且这些流程没有「部门归属」维度。提交人/审核人本人一律
   排除（不给自己弹卡）。
5. **人事办结缺口补齐**：访客「待你确认接待」改独立聚合 `VISITOR_HOST_CONFIRM`（接待人确认
   后申请回到 HR 批准，HR 卡不能被误撤；接待人确认/拒绝与 HR 批准/驳回均撤两种卡）；
   员工撤销信息变更批次办结 HR 卡（CANCELLED）；报销审批卡登记 `EXPENSE_APPROVE` 认领
   （弹窗显示「XX 正在审核」），审批通过先办结审批卡再发打款卡（同聚合，顺序不能反）；
   工资审核通过 → 发布人「待发布」卡（`PAYROLL_BATCH_PENDING_PUBLISH`，发布办结）；
   建议箱提交 → 回复人卡（`SUGGESTION_SUBMITTED`，聚合 SUGGESTION；回复推进到
   resolved/rejected 办结并回执提交人，匿名建议正文不带姓名）。
6. **人事通知事务语义**：`HrNoticeService` 与业务同事务、失败随业务回滚（NoticeService 写方法
   REQUIRED 传播，异常已把外层标 rollback-only，吞掉只会推迟到提交时爆）；旧 `safe()`
   的「不影响业务事务」注释与吞异常行为一并移除。
7. **前端死代码清理**：`NoticeRepository.acknowledgePopup` / `ApiEndpoints.noticePopupAck`
   无调用方，删除。后端 `POST /notices/{id}/popup-ack` 保留：有契约测试与服务测试覆盖、
   ADR-059 记为历史兼容 API，且 popup_acknowledged_at 现由 markRead 统一写入。
8. **人工通知登录弹窗与打卡**（用户口径：「人事手动发消息/通知，所有对应的人登录都要显示通知
   弹窗；需要打卡的点击打卡」）。人事经 `POST /api/notices`（`notice:publish`，全员或指定范围）
   发布的通知（`source_event IS NULL`，非庆典）进入同一居中登录弹窗，独立分组「人事/公司通知」，
   数据源新增 `GET /api/notices/pending-popups`（`notice:read`，上限 20，
   `NoticeRepository.findVisiblePendingManualNotices`），登录门与 `pending-reviews` 并行拉取。
   **待处理口径按互动模式分两档**：
   - **打卡（acknowledge）类型**——公告/制度/系统/紧急/福利：本人无 `notice_acknowledgments`
     回执 且（未稍后 或 稍后已到期）即弹，**无时间上限、已读与 popup_acknowledged 均不能静默**，
     唯一退出是 `POST /notices/{id}/acknowledge`（幂等，一人一次）。弹窗条目带【打卡确认】；
     在线到达的顶部条也内联【打卡确认】。打卡不代行已读。
   - **只提醒（none）类型**——任务/审批/流程：`popup_acknowledged_at` 为空 且（从未读且未稍后
     或 稍后已到期）且 **发布 14 天内**（`NoticeService.NONE_MODE_POPUP_WINDOW`）。【知道了】/
     打开详情 = markRead 即静默；旧提醒超过 14 天自然退出，不需要办结机制。
   - 「全部稍后再看」对审核待办与人工通知一起 snooze（服务端语义同 §1，到期重弹）；右上 X 仅本次
     关闭。人工条目无办结/认领语义，不参与 `pending-review-status` 心跳。
   - 排序：打卡类型优先 → 紧急/重要 → 置顶 → 发布时间倒序（20 条上限不让只提醒类挤掉打卡类）。
   - 庆典（bless）不在此列（有独立每日登录弹窗）；系统链路的 system/urgent 定向通知
     （`source_event` 非空）也不在此列——它们有各自的业务办结与徽章口径，不强加打卡义务。
   - 无新迁移：复用 `notices` / `notice_user_states` / `notice_acknowledgments`；类型→互动模式派生
     （`NoticeService.interactionModeFor`）不变，发布页只加一行提示告知 HR 哪些类型要求打卡。
   实现：`NoticeService.pendingPopups`、`ReviewPendingDialog`（`manual` 分组）、
   `ReviewPendingLoginGate`、`notice_arrival.manualAckPending/acknowledgeNoticeInline`；
   验证：`ManualNoticePopupPostgresTest`（真实 PG：全员/指定范围/打卡退出/稍后到期/庆典与系统
   排除/14 天窗口/排序）+ 前端 widget 测试。文档：ReviewPendingDialog.md §八、通知列表页、通知发布页。

## 背景与决策

业务待办（销售下单待财务确认、订货待财务审批、到货待检、订单全部完工可发货等）
此前只有普通顶部条通知：无操作按钮、无认领状态、办结后通知残留。用户要求：
**「部门（主职或兼职）且负责该块」的人**收到可操作弹窗——只有部门或只有权限都不推。

四项决策：

1. **兼职部门模型**（V459 `employee_secondary_departments`）：一人多部门归属的
   唯一组织表达。权限合成把各兼职部门链（含祖先递归）并入并集；行级变更由触发器
   即时 bump `users.auth_version`（V135 机制，单人粒度不走全局 epoch）。
   **推送资格 = (主部门 ∈ 部门子树 OR 兼职部门 ∈ 部门子树) AND 持有职责权限码**，
   双条件缺一不可；「推送比审批严格」——部门外被点名加授者（ADR-027）仍可审但
   不收弹卡，要收弹卡给他兼职该部门。
2. **可操作审核卡 + 居中审核弹窗（2026-09-02 第二轮用户口径修订；2026-09-03
   第三轮修订：顶部条改纯显示）**：一个待审事件的三种提醒形态并存——通知中心
   条目（落库即有）、顶部通知条（**纯显示**：不带操作按钮与状态行，20s 自然
   收起——避免与居中弹窗重复的操作入口；`AppNotification` 的
   `actions`/`statusLine` 能力保留备用）、**居中审核弹窗**
   （`ReviewPendingDialog`，主交互）。居中弹窗单条=大卡、多条=紧凑列表，**高度
   随内容自适应、封顶 min(60% 屏高, 560px)**（多条内部滚动，不再接近全屏）；条目实时
   显示认领状态（「XX 正在审核」/「待处理」，30s 心跳），办结条目自动移除、清空
   自关；【去工作台处理】（2026-09-03 第四轮修订：不再直达单据详情）同域→
   该域任务工作台、跨域混合→待审收件台，单条也去工作台，点列表行去该行
   所属域工作台；后到待办并入已开弹窗（「一共有 N 项」），【稍后再看】全部
   snooze 15 分钟，右上 X 仅本次
   关闭。**每次登录检查**（`ReviewPendingLoginGate`，登录后 3s 拉
   `GET /notices/pending-reviews`：未办结+未稍后，重要度序）有则弹——「稍后再看」
   是唯一静默途径，X 关闭下次登录仍提醒（未办结就还该提醒）。
   这**修订 ADR-052 §2.3** 的边界：资格池待审事件允许居中弹窗，但 ADR-052 的
   前提由办结撤回（不再要求已解决的事）与认领状态展示（不再让多人盲目涌向同一
   单据）实质满足；七要素（事件来源/聚合 UUID/责任人池/业务时间/解决条件/主操作
   路由/角标真源）由 `ReviewNoticeCatalog` 注册表+aggregate 列+task_claims 承接。
   弹窗单例守卫防多事件叠窗（后到待办并入已开弹窗，收件台兜底）。
3. **办结撤回**：`notices` 增加 `aggregate_kind/aggregate_id/resolved_at/resolved_reason`
   （历史行全 NULL=永不撤回，零行为变化）。审核落点（确认/驳回/批准/整单检验结案/
   开立出货单）按 (kind,id) 一条 UPDATE 批量 resolve——全部接收人弹卡停止展示、
   收件台计数归零、通知中心灰显「已办结」（保留审计价值）。居中弹窗停留期间 30s
   心跳调 `GET /notices/pending-review-status` 做真态校验（办结条目自动移除/清空
   自关、他人认领显示「XX 正在审核」）；顶部条到达前也校验一次（已办结不弹）。
4. **「稍后再看」**（`notice_user_states.snoozed_until`）：服务端语义跨设备一致；
   未到期不出弹卡流（通知中心仍可见），到点未办结下次到达重弹；**点稍后或去审核
   同时置已读**（「已处理过这条提醒」）。已办结通知拒绝再 snooze。

## 交付边界

- **收件台**：`/reviews/inbox`（`review_inbox:view` 守卫，surface `reviews.inbox`，
  111 个）聚合各职责域待审数（notices 维度，与撤回自动联动）；工作台「常用功能」
  组有入口卡片。
- **已接线四线（P0）**：销售订单→财务确认（弹卡直达单据审核页+认领+确认/驳回撤回）、
  采购/委外订货→财务审批（case 聚合+批准/驳回撤回）、到货 IQC 待检（整单结案撤回）、
  订单累计入库满足订货量→通知负责销售「全部完成生产，可以发货」（归属人定向、
  无认领、开立出货单撤回）。其余业务线按 §五目录滚动接线（每线=注册表一行+发布点
  aggregate+落点 resolve+claim 登记）。
- **事件名不变**：全部复用既有 source_event 常量，`unread-count-by-source` 等
  统计口径不受影响。
- **实时性**：沿用 10s 到达轮询（方案 D9）；SSE 为后续独立批次（notice_arrival
  已预留替换入口）。登录检查为一次性拉取（每次登录会话一次，登出重登重新触发）。

## 已知遗留

- 通知中心列表仍是后端 500 条上限+前端一次性渲染；数据量持续增长时做 keyset
  分页化（独立批次）。
- IQC/采购审批的**审核页内认领**尚未接线（弹卡已显示认领状态；写入端只接了
  财务确认审核页）——按每线半天滚动补齐。
