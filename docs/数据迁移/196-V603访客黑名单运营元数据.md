# 196 - V603 访客黑名单运营元数据

- 日期：2026-09-18
- 关联：[访客预约系统](../03-页面/访客预约系统.md)、`VisitorGateService`（门岗拉黑/解除/黑名单列表）、
  `VisitorBlacklistTest`
- 用户口径：黑名单需要记录拉黑原因/时间/操作人，且解除拉黑后可再次预约（账号复活）。

## 一、决策

访客拉黑从「状态位」升级为「带运营元数据的动作」：`visitor_accounts` 新增三列承载
拉黑上下文，解除时三列一并清空（账号回到可用态）；历史留痕不由这三列承担——
`visitor_accounts` 上的行级审计触发器（fn_audit）已记录每次状态翻转的操作人与时间，
三列只表达**当前**拉黑事实。

## 二、迁移内容（只加列，不加表、不改既有行）

```sql
ALTER TABLE visitor_accounts ADD COLUMN IF NOT EXISTS blocked_reason TEXT;    -- 拉黑原因（拉黑时必填）
ALTER TABLE visitor_accounts ADD COLUMN IF NOT EXISTS blocked_at TIMESTAMPTZ; -- 拉黑时间
ALTER TABLE visitor_accounts ADD COLUMN IF NOT EXISTS blocked_by UUID;        -- 拉黑操作人（users.id）
```

配套 COMMENT ON COLUMN 三条。`status='blocked'` 时 `blocked_reason/blocked_at/blocked_by`
非空、其余状态全空的约束由应用层守卫（服务端校验 + 单测覆盖），不建库级 CHECK，
避免解除流程被约束次序卡死。

## 三、应用面

- `VisitorGateService`：门岗扫码核验红/绿判定接入黑名单；拉黑（必填原因）、解除
  （清空三列）、黑名单分页列表（按拉黑时间倒序）；
- `VisitorAccountController`（新）：拉黑/解除/列表端点，权限收口在门岗/安全角色；
- 安全模块新增黑名单管理页（`security_blacklist_page.dart`），列表 + 拉黑/解除操作；
- 回归：`VisitorBlacklistTest`（拉黑→核验红→解除→可再约、必填原因、解除清空元数据）。

## 四、兼容性

- 只加列、默认 NULL，旧后端读新库透明；新后端读旧库（V602 及以前）会在首次拉黑时
  报缺列——因此**含本迁移的版本先于库升级属于不支持路径**（发布链：migrator 先行）。
- 不加表：业务清库脚本（`server/ops/reset_business_data.sql`）策略清单不变，仅版本对
  推进到 (603,560)。
