## 一、背景与用户要求

用户诉求：中央提醒弹窗(ReviewPendingDialog)此前几十种事件**全部同一个 teal 样式**——
车间任务、财务审批、物料到货、人事公告在弹窗里长得一模一样，无法一眼识别类型与轻重，
积压多条时只能逐条读标题。要求建立**分级视觉体系**：打开弹窗第一眼就能分清
「哪些必须马上处理、哪些是要做的事、哪些只是进展、哪些是广播」。

数据侧早已具备分级原料：notice 带 `priority`(normal/important/urgent) + `interactive`
(source_event 在审核卡目录) + 人工通知组；「物料到货进展」与「可开工行动卡」同
sourceEvent 但 priority 不同(normal vs important)，正是「轻重由数据说话」的现成例子。

## 二、四档视觉级别(颜色+图标+徽章三重编码)

按 `(priority, interactive/manual)` 归档。**每级三重编码**：色彩槽 + 图标形状 + 徽章文字
(「紧急/待办/进度/公告」，l10n `noticeLevel*`)——色弱/色盲下徽章文字与图标形状仍可区分，
不只靠颜色。

| 级别 | 判定 | 色彩槽 | 徽章 | 卡片强化 | 排序 |
|---|---|---|---|---|---|
| 紧急 urgent | priority=urgent(含人工紧急) | error 红 | dangerStrong 红底白字「紧急」+priority_high | 1.5px error 描边+左侧竖红条+标题 error w700+errorContainer 底 | 1 置顶 |
| 行动待办 action | type=approval/workflow(无论 priority)，或 interactive && important | teal 品牌 | teal 底「待办」+task_alt | 现有 teal 风格(secondaryContainer@35%+描边) | 2 |
| 进度跟踪 progress | task/其余 interactive && normal | info 蓝 | 蓝底「进度」+trending_up | surfaceContainerLow 底+更紧凑行高(dense) | 3 |
| 人事广播 broadcast | 人工通知组(非 urgent) | amber 暖色 | 琥珀底「公告」+campaign | 卡片底色=琥珀容器色(broadcastContainer) | 4 垫底 |

要点：

0. **修订(2026-10-06)：审批/工作流类一律行动级**。`type=approval/workflow` 的条目
   无论 priority normal/important 都归行动级——`SALES_ORDER_PENDING_FINANCE_CONFIRM`、
   `PROCUREMENT_FINANCE_SUBMITTED` 等审批事件后端多标 priority=normal，但语义是
   「待我决定」的强待办，按原 important/normal 二分会被落进最低权重的进度级(产品
   语义错位，红队审查 P1)。`type=task` 维持 important→行动 / normal→进度的区分
   (后端以此区分可开工行动 vs 到货进展)；urgent 一票置顶与人工/广播逻辑不变。
   场景示例：财务登录弹窗里「待财务确认：SO-001」(approval+normal) 带「待办」
   teal 徽章，与「物料到货进展」(task+normal) 的「进度」蓝徽章正确分档。
1. **amber 与 error 拉开色相**：广播的 amber 偏黄、紧急的 error 偏红，且徽章文字不同，
   双保险区分。明暗主题各有容器对(UtenColors `broadcastContainer(Dark)` 新增，
   与 `infoContainer(Dark)` 同构：浅底深字/深底浅字)。
2. **大卡 `_LargeItemCard` 与紧凑卡 `_CompactItemCard` 都吃分级**：大卡是行动/紧急主力
   形态；进度类进紧凑形态并压行高，视觉权重低于行动卡。人工卡 `_ManualNoticeCard`
   保留类型色图标，底色/描边按级改造(人工紧急=红系强化并置组首)。
3. **头部摘要行升级为分级计数**：带各级色点的「● 紧急 N · ● 待办 N · ● 进度 N ·
   ● 公告 N」(l10n `noticeLevelSummary`)，取代旧事件域分组 chips；域信息仍在条目卡上。
4. **排序 `urgent > action > progress > broadcast`**：`sortByReviewLevel` 稳定排序(同级保持
   到达序)；分组顺序为待办审核组在前、人事/公司通知组在后(广播垫底)。
5. **行为零改动**：单例守卫/30s 心跳/认领 chip/snooze 口径/工作台落点/打卡确认/两组
   一起稍后——全部保持 ADR-063 既有契约，本决策只动视觉与排序。

## 三、对 ADR-059 的修订：interactive 紧急事件恢复中央弹窗

ADR-059 §六(2026-08-30)口径：「不能把业务通知升级为阻塞当前仓库/生产操作的模态窗口」，
important/urgent 只提升顶部条的语义色与停留时长。V459/ADR-063 为 interactive 审核待办
开了居中弹窗例外；本决策把该例外**明确覆盖到 urgent**：

- **interactive 的 urgent**(source_event 在 ReviewNoticeCatalog 内，如
  `SUBCONTRACT_SHORT_DELIVERY_DETECTED` 委外短交预警)：与其他 interactive 同路走
  `dispatchReviewCard` 进中央弹窗，以**紧急红卡**呈现；**顶部红条(error, 8s)并行保留**；
  弹前真态校验(已办结不弹)对 urgent 同样生效。紧急待办有动作、有认领语义，属于
  「必须被看见并处理」的提醒，红卡置顶正是分级体系的最高档。
- **非 interactive 的 urgent**(驳回类纯告知，如 `SALES_ORDER_FINANCE_REJECTED`)：
  **维持 ADR-059 现状只弹顶部红条**(「紧急 ·」前缀, 8s)——纯告知没有动作入口，
  居中模态只会打断当前操作，顶部红条已足够。
- 判据只有一条：`notice.interactive`(服务端审核卡目录)，前端不再看 priority 决定
  「弹不弹中央窗」，priority 只决定「弹出来长什么样(红/teal/蓝卡)」。

**修订(2026-10-06)：短交检出的接收人分化披露**。`SUBCONTRACT_SHORT_DELIVERY_DETECTED`
仅 owner(订货单制单人)收 urgent 红卡；purchaser(采购员)与其他持判定权限的 follower 由
后端发送时**有意显式 normal 降级**(`ChainNoticeService.notifySubcontractShortDeliveryEvent`
对 purchaser/follower 调用 `NoticeService.publishForUser` 的 explicitPriority="normal"，
防噪设计与该显式优先级入口注释同源：避免整组持判定权限的人被升级为持久强提醒)，
前端呈现为进度级蓝行。同一案件多接收人视觉分化(owner 红 / purchaser·follower 蓝)是
既定防噪口径，非缺陷；判定权限与处理入口(actionRoute)不受影响。

## 四、无障碍与两级口径统一

- 三重编码原则：**颜色 + 图标形状 + 徽章文字**同时给出，任何单一通道缺失(色弱、小字号、
  截图黑白)仍可分级；urgent 另有「左侧竖红条」形状编码，与广播的暖底不只靠色相差。
- 明暗主题各配容器对，保证对比度(浅底深字/深底浅字)，不拿 alpha 叠加硬凑。
- 顶部条与中央弹窗两级口径统一：顶部条 error 红 8s / warning 橙 6s / info 蓝 4s(不动)，
  中央弹窗四级中 urgent 用同一 error 槽、progress 用同一 info 槽；action 用品牌 teal
  (「轮到我动手」的品牌语义，不引入橙色以免与顶部条 warning 混淆)、broadcast 用 amber
  (与顶部条 warning 同色系但只出现在中央弹窗的公告分组，徽章文字「公告」区分)。
