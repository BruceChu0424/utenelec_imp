# 231 · V650 热表约束/守卫触发器按相关列起跳、单号不可变改列级、收付款类别引用改共享锁(ADR-106)

- 迁移：`V650__hot_table_trigger_relevant_column_gates.sql`
- 类型：前向。只改触发器定义(DROP + CREATE 同名/后缀名)与三处函数锚点补丁、新增一个单号不可变守卫函数；**不加表、不加列、不改历史行、不改任何校验函数的判定**。
- 决策：[ADR-106 热表触发器按相关列起跳与索引卫生](../99-决策记录-ADR/ADR-106-热表触发器按相关列起跳与索引卫生.md)。
- 编号：V650-V652 为本轮「数据库触发器与索引卫生」分配段。

## 为什么要有它

预留、库存单据头/明细、计划明细、执行段、物料分析三表、估值节点/事件、权益事件上的约束与守卫触发器几乎都没有列过滤和 WHEN。
PostgreSQL 给每一次 INSERT/UPDATE 都给每个延迟约束触发器排一个事件，只改 `updated_at` / `lock_version` / 派生数量、甚至空写的更新，
提交时也要把守恒、溯源、预算校验整套重跑。一行车间直送审核实测 600 次触发器函数调用、提交 742ms。

## 改了什么

| 对象 | 变化 |
| --- | --- |
| 94 个热表触发器 | UPDATE 路径加 `WHEN (相关列真变了)`；入口本来就按行类型提前返回的(预留 `owner_type`、估值事件 `operation`/`source_doc_type`、精度界 `value_model`、权益事件 `event_type` 等)把同一条件写进 WHEN，统一写成 `(条件) IS NOT TRUE` 与函数的 `IF ... RETURN` 逐字等价。INSERT 与 UPDATE 共用的拆成原名(INSERT / DELETE 路径不变)与 `原名_upd`，INSERT 与 DELETE 条件不同时另起 `原名_del`。已有 `UPDATE OF` 原样保留，不新增列清单 |
| `trg_purchase_reservation_receipt_provenance` / `trg_purchase_draw_receipt_provenance` / `trg_purchase_draw_item_receipt_provenance` | 删除：它们逐条断言的采购收货分配，同表的 `trg_receipt_*` 覆盖校验在容量检查后逐条再断言一遍(分配的 `reservation_id` 非空)，完全被包含 |
| 33 个 `trg_business_document_<表>` | 只剩 BEFORE INSERT 取号；新增 `trg_business_document_<表>_upd`：`BEFORE UPDATE OF 单号列[, 区分列] WHEN (单号/区分列真变了或单号为空)` |
| `fn_guard_business_document_identifier_immutable()` | 新增，UPDATE 守卫，报错文案与原取号函数的 UPDATE 分支逐字相同 |
| `fn_reserve_business_document_identifier()` | 锚点补丁：删掉走不到的 UPDATE 分支与 `v_old_value` |
| `fn_guard_payment_style_reference()` / `fn_enforce_account_style_uuid_authority()` / `fn_enforce_system_posting_style_role()` | 锚点补丁：`pg_advisory_xact_lock` → `pg_advisory_xact_lock_shared`(引用方共享)；`fn_guard_active_account_style_status()`(类别停用/删除)保持排他 |

原来是 `ENABLE ALWAYS`(复制角色下照样起跳)的 27 个守卫，重建出的每一条(含 `_upd` / `_del`)都逐条恢复 ALWAYS；
`HotTableTriggerHygieneContractTest` 把这 38 条写死成清单逐条断言。
每条 WHEN 的列集来自校验函数及其调用闭包里对本表的全部读取(保守超集)；执行段完整性触发器因 `lock_version` 每次更新都被递增，
写成「相关列变了或 NEW.status = 'CANCELLED'」(只有已退役拆批源段的证明读锁版本号)。补丁方式沿用 V580/V645 纪律：
`pg_get_functiondef` 取定义、行尾归一 LF、锚点必须恰好命中一处，否则 23514 失败宁可不迁。

## 应用侧(同批)

- `PaymentStyleHierarchyLock.lock` 改取共享锁(引用方)；新增 `lockForHierarchyChange`(排他)，`PaymentStyleService` 的层级/状态编辑改用它。
- 用 `SET CONSTRAINTS <名> IMMEDIATE` 立即校验更新路径的测试同时点名 `<名>_upd`；过去「只改 updated_at 逼出延迟校验」的测试改成把一个相关列改过去再改回来。

## 兼容与影响

- 校验判定一字不变：改了相关列照样被拒(负向回归见 `WorkshopDirectTransferBatchEndToEndTest`)；只是只改无关列的更新不再「顺带」复查其它表的状态——跨表不变量由每张参与表各自的触发器守护。
- 触发器执行先后(同表同时机同事件按名字排序)保持不变。
- 实测一行直送审核：触发器函数调用 600 → 416 次、延迟校验 282 → 170 次、提交 742ms → 538-693ms；质检提交报告/整单合格/仓库确认入库的剖面见 ADR-106 §三。
- 只去掉了「无关列变化也排队」的事件；相关列变化时仍是逐行、逐事件校验，同一个键的聚合仍重复计算。按键去重(脏键表或语句级集合校验)、同表校验合并、写入一次成形是下一波写路径重构(ADR-106 §2.1「没有做的」)。
- 不涉及新表/删表，`reset_business_data.sql` 表清单不变。
