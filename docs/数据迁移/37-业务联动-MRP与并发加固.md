## 一、业务联动全景（现状 → 目标）

|---|---|---|

## 二、MRP-lite 设计（生产计划 → 采购申请）

### 口径

```
毛需求 = Σ（计划明细排产量 × BOM 用量），goods_bom_items 递归展开（≤10 层、路径防环）
净需求 = 毛需求 − 即时库存（stock_balances 全仓合计）− 在途订货（已审订货单 数量−已收）
聚合粒度 = 货品（颜色取需求最大贡献行参考色；净需求按货品级计算，避免按色重复扣减）
半成品（组件本身有 BOM）= 标记「自制」，只预览不进采购申请
```

### 防重复与可追溯（mrp_generations，V87）

- 生成即写联动行（plan_id ↔ request_id + created_by）；
- 同一计划存在**未删且未红冲**的生成申请 → 拒绝重复生成（提示既有单号）；
- 申请被删/红冲后可再生成，旧联动行软删留痕（审计可查）；
- 申请明细挂 `production_plan_no` + remark 记录「毛 − 存 − 途」计算过程。

### 接口与权限

| 接口 | 权限 | 说明 |
|---|---|---|
| `GET /api/production/plans/{id}/mrp` | production_plan:view | 预览（毛/存/途/净 + 自制标记） |
| `POST /api/production/plans/{id}/mrp/generate` | production_plan:edit | 生成采购申请草稿（CS 序列取号，采购员走正常审核流） |
| `POST /api/production/plans/{id}/mrp/generate-draw` | production_plan:edit | 生成生产领料单草稿（SL 序列取号，body 传 warehouseId，仓管审核出库） |
| `POST /api/production/plans/{id}/mrp/generate-finished-in` | production_plan:edit | 生成成品入库单草稿（CR 序列取号，body 传 warehouseId，仓管审核入库） |

前端：生产计划详情页「物料需求（MRP）」卡（展开/刷新 + 生成采购申请/领料单/成品入库，按 production_plan:edit 门控）。

### 计划 → 成品入库单（FINISHED_IN）

- 取**计划明细自身**（不展开 BOM），数量 = 排产量 − 已入库量（iqty），全入完则提示无可入库数量。
- 与领料单共用 `plan_draw_links` 留痕（按 stock_documents.doc_type 区分防重复，互不干扰）。

### 计划 → 领料单（DRAW，V88）

- **口径差异**：采购申请按**净需求**（扣库存/在途，避免多买）；领料单按**毛需求**（车间按排产全量领料），
  自制件同样列出（半成品也可能从库存领，明细备注标记「自制件」）。
- 表头 `plan_no` + 明细 `source_doc_no` 挂计划号溯源；`plan_draw_links` 防重复（规则同 mrp_generations：
  有效生成单存在即拒绝，删/红冲后可再生成，旧联动软删留痕）。
- 领料单审核出库即走既有 StockService 库存流水 + 余额，无需新逻辑。

## 三、多账号并发设计（YTDQ 问题②的答案）

### 分层防线

| 层 | 机制 | 覆盖 |
|---|---|---|
| 状态机互斥 | **PESSIMISTIC_WRITE 行锁**：approve/reverse 先锁头行再查状态，同事务并发审核序列化，后到者按「状态已变」拒绝 | **25 个单据 Service / 40 个审核入口**（采购 4 + 生产计划/日报 + 销售 5 + 委外 8 + 仓库统一 + 钱流 5 + 本次注入） |
| 主档并发编辑 | 乐观锁 `@Version` 递增（ADR-009 已全量） | employees 等主档 |
| 库存/回写 | 审核同事务内回写 + 余额增量（StockService），行锁保证同一单据不重入 | 全单据 |
| 单号 | doc_number_sequences 数据库序列取号（同事务递增发号，无重号） | 全单据 |
| 审计 | 触发器审计（fn_audit）逐行留痕，谁改的一查即得 | 全表 |

### 为什么选行锁而不是乐观锁（单据状态机）

状态机迁移（0→1、1→-1）附带**库存/应收应付/上游回写等一串副作用**，乐观锁失败重试的代价是
整串副作用重跑；行锁让并发者直接拿到「状态已变」的明确拒绝，用户重试即见最新状态——
与大厂 ERP（SAP 单据锁、用友/金蝶审核锁）同思路。
