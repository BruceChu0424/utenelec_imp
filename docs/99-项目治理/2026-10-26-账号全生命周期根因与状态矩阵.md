## 已确认的原始数据问题

迁移的旧员工花名册不是公司当前员工全集。它缺少新系统手工新增的员工，也不能覆盖员工后来修改的证件、手机号和账号状态。仅保留登录账号或构造软删除的 `AUTHHIST` 引用锚点，虽然能保住用户 UUID 和历史外键，却不能替代有效员工档案和敏感资料。只按导入人数及账号总数验收不能发现这种损失。

- 万梅：当前登录账号引用的员工失去有效档案及完整资料，旧 Excel 又不包含她。已在公司服务器按两份迁移前配对备份恢复原员工 UUID、已核验资料及当前可用状态，工号改为未冲突的新工号 UT0193。原登录名、永久密码哈希和个人授权不变；不覆盖现持有 UT0143 的另一名历史员工。
- 石磊：存在同一人的在职档案 UT0010、用户确认的旧错档 UT0189，以及历史引用锚点。已把原登录账号绑定回 UT0010，保留原用户 UUID、密码、授权和历史；UT0189 继续归档隐藏。历史聚合别名代码尚随统一版本发布，不重复执行旧版归档脚本。
- 另五个原本停用的账号：源备份证明在迁移前已经停用、临时密码已过期。按用户明确决定保持停用，不批量启用或重置。
- 两个仍有成功登录记录的账号存在旧、新 HR 资料差异。系统支持自定义登录名，因此登录名不等于当前手机号本身不是重新绑定、覆盖证件或重置密码的依据。

## 本轮发现并修复的公共机制

| 触发条件 | 根因 | 统一规则 |
| --- | --- | --- |
| 账号保留但员工已删除或离职 | 登录、刷新、JWT 曾只检查账号，身份条件不一致 | 所有员工鉴权入口必须同时验证账号和当前、未删除的员工身份；日常超管也遵守身份存续条件 |
| 已停用账号执行锁定后解锁 | 解锁把任意状态直接改为 active | 停用只能通过明确的启用操作恢复，锁定和解锁拒绝替代启用 |
| 管理员人工锁定后重置密码 | 密码支持流程和启用状态混在一起 | 重置不清除人工锁定，也不自动启用停用账号；临时暴力锁按既有支持流程处理 |
| 离职后返聘 | 复职自动启用旧账号及凭据 | 先恢复员工在职资格，账号仍停用、外网关闭；由具备账号支持权限的人明确处理密码和启用 |
| 入职自动建号 | 建档和敏感凭据签发未分开授权 | 请求显式 `account.openAccount=false` 只建档；请求开户必须具备账号支持及既有凭据签发资格 |
| 旧客户端省略开户字段 | 无法区别旧开户意图与新页面只建档 | 省略/null 保持旧请求的开户意图并校验权限；不能静默降级成只建档 |
| 开户、离职、重开、账号操作交错 | 非统一读写顺序或脱管实体覆盖新状态 | 公共账号命令锁定员工后锁账号，锁内重读绑定与状态；保留 CAS 和数据库唯一约束 |
| 密码校验期间被管理员重置或关闭 | 慢哈希结束后继续写旧请求的失败计数或会话 | 写入事务核对当前身份、账号和原密码代际，旧结果不能污染新凭据 |
| 新建自定义登录名有空白或超长 | 开户与登录的输入合同不同 | 仅对新标识统一 Unicode 首尾清理、1..128 位与非法字符校验，手机号用公共规则；既有自定义登录名不批量改写 |
| 两个超管同时撤销对方 | 各自按旧资格和总数通过检查 | 超管资格变更使用共享 registry 锁并重读 actor/target 及可用保底；普通不同员工操作保持窄锁，离职取得员工锁后重读账号资格 |
| 模拟目标令牌在原超管失格后取得新 stamp | 仅检查 target 不能替代会话 owner 资格 | 同一鉴权 SQL 同时检查模拟会话原操作者的有效员工、active、超管及已完成改密状态，普通员工自己的会话不额外要求超管 |
| 刷新后用旧 refresh token 注销 | 旧令牌撤销未覆盖同一个仍有效的会话 | 按令牌所属 SID 撤销整条同会话链；不能撤销另一次登录的新 SID |
| 临时密码过期或人工锁定后刷新 | 响应前才检查导致先提交令牌轮换 | 在创建/轮换之前复核资格；拒绝请求不产生可用新会话 |
| 开户或重置等待期间切换操作者、员工或 API | 调用者只检查用户 ID 或等待结束时读取当前依赖 | 账号操作凭据回执绑定原始操作者、会话代际、API、数据集及员工目标；过期回执不展示凭据 |

保持既有防枚举、密码验证、一次性凭据、远程 MFA、访问权限和会话失效机制。没有给停用人员放行、自动合并同名人员或扩大权限。

## 状态与操作矩阵

| 状态或操作 | 预期行为 |
| --- | --- |
| 当前员工 active / probation / onLeave | 满足账号、密码及访问条件后可登录；休假不等于离职 |
| 员工软删除、离职或账号软删除 | 不可签发/刷新/使用普通员工访问令牌；保留历史引用 |
| 无账号的当前员工 | 完整度预检显示可处理的问题；具备资格的操作者可补开，服务端分配真实账号结果 |
| 仅建立档案 | 不生成临时密码、不伪造账号名或 active 状态 |
| 入职同时开户 | 两项在同一业务事务中成功，权限或凭据资格不满足则整体拒绝 |
| 锁定 / 解锁 | 不覆盖停用；人工锁与有截止时间的暴力锁按不同语义处理 |
| 停用 / 启用 | 明确改变账号状态并撤销旧会话；启用需有效员工身份 |
| 管理员重置密码 | 显示一次真实凭据，保留停用/人工锁语义，撤销旧会话 |
| 员工首次改密 / 后续改密 | 核对当前账号和密码代际；成功后旧访问/刷新及再认证凭据失效 |
| 注销登录 | 清本地身份并撤销原会话；网络失败按受信任签发来源重试，不把令牌发送给独立测试服务器 |
| 注销开户 / 重新开户 | 保留用户 UUID 和业务历史，重新开户不得继承已撤回的个人授权；不物理删除被引用用户 |
| 离职 / 返聘 | 离职撤销使用资格并保留轨迹；返聘与明确恢复账号分开，不自动恢复外网权限 |
| 改手机号、证件、工号 | 员工 UUID 为绑定身份；仅按既有明确手机号登录同步规则处理登录名，不凭名字匹配或重建账号 |
| 超管授权 / 撤权 | 资格和最后一个可用超管规则在共同写入锁内复核；不能并发互撤到零 |

## 防止下一次重建丢失员工

旧 `verify_rehearsal_result.py` 仍只验收封存旧源的首次空候选导入。回执明确给出 `SEALED_LEGACY_BOOTSTRAP_ONLY`、`current_staff_preservation=NOT_EVALUATED`、`company_data_replacement_authorized=false`。原先禁止在线重导员工的门禁继续保留。

新增 `server/legacy_migration/verify_staff_preservation.py` 用于**同版本数据库重建/恢复**前后完整保全校验：

1. 在当前真实源库读取只读快照；固定数据库集群标识、数据库 OID、业务数据集和代际，封存文件 SHA-256。不能用本地旧测试库当公司源库。
2. 自动登记全部 `employee_*`、`user_*`、`auth_*`、`notice_*` 表，及部门、岗位、权限目录/模板/委派、MFA、会话、密码历史、紧急联系人、员工任职轨迹；登记实际列和主键。实际公司 V935 元数据核验覆盖 43 张表，实体表登记回归约束新增员工/账号实体不得漏列。
3. 使用受保护超管凭据在数据库只读语句内生成行级 HMAC 保全摘要。私有快照不导出原密码哈希、密钥、电话或证件明文/独立可猜摘要。需保持相同源凭据基准，变化后重新采集。
4. 逐 UUID、复合主键和所有原生字段比对，不能靠总数相同通过。保留密码、自定义登录名、全部档案、个人允许/拒绝、消息及已读状态、委派和历史。用户/员工授权委派代际必须一致，避免行还在却因代际变化失效。
5. 允许行版本和账号认证版本前进，禁止倒退；保留旧撤销记录；候选中旧会话、刷新令牌和再认证凭据必须全部失效。审计及一次性修复完成标记按源高水位聚合校验，可增加新事件，不能丢失或改写原事件。
6. 源和候选证据必须新鲜、同 schema、同业务数据集。默认禁止源库自行充当候选；同库恢复须显式声明。失败返回非零，拒绝覆盖既有证据文件。

此程序不会修改业务数据、不会重导旧 HR、不会决定任何同名合并、不会自动发布或切库。正常应用升级**不执行扫描**；没有新增 StartupRunner、定时任务或每次启动重修数据的开销。完整业务数据、附件实体、加密密钥配对和真实 MFA、复制角色、停写窗口及恢复/切换验收仍须走既有发布/恢复流程，不能用员工保全回执替代。
