# V809 委外申请物料齐套才解锁下单

状态：
- 本地分支的源码候选，**V809 是临时号**，合并时按 main 迁移头 +1 改号，本文件名和正文一起改(见文末)。
- 验证结果见 [ADR-156 §十](../99-决策记录-ADR/ADR-156-委外申请物料齐套才解锁下单.md)。
- 没有在本机开发库、测试服务器或任何业务库执行。

决策与理由见 [ADR-156](../99-决策记录-ADR/ADR-156-委外申请物料齐套才解锁下单.md)。一句话：委外加工价每天不一样，直属物料不齐时委外申请锁住、不让生成委外订货单；现有物料够做几套才能下几套。这个「能下几套」只在本迁移的 SQL 函数里算一次，任务中心、齐套情况、下单预填、建单 / 保存 / 送审 / 批准 / 批准后加量的守卫、可下单通知都读它。

文件：`server/src/main/resources/db/migration/V809__subcontract_application_kit_lock.sql`，全部在 Flyway 单事务内。**不加权限码、不改任何业务数据**，只加 1 张通知水位表和 10 个只读函数，并给清空业务数据登记这张表。

## 执行顺序

### 第 0 步：前置检查

依赖 V798(委外领料)与 V801(可用仓口径)的对象，缺任何一个就失败：`fn_subcontract_draw_edges(uuid)`、`fn_subcontract_draw_f(numeric,numeric)`、`fn_subcontract_draw_sets(numeric,numeric)`、`fn_subcontract_draw_needed_qty(uuid,numeric,numeric)`、`fn_warehouse_counts_as_usable(uuid)`、视图 `v_preplan_stock_entitlement_lot_balance`、`v_stock_available`、表 `subcontract_draw_notice_marks`。

### 第 1 步：新表 `subcontract_application_kit_notice_marks`

「委外可下单」通知的高水位，每个委外申请明细一行，与 V798 的 `subcontract_draw_notice_marks` 同一做法。

| 列 | 说明 |
|---|---|
| `application_item_id` | 主键，外键 → `subcontract_application_items(id)`，随申请明细级联删除 |
| `notified_orderable NUMERIC(18,4)` | 上次提醒时的可下单量，默认 0 |
| `epoch INTEGER` | 可下单回落的次数，默认 0 |
| `updated_at` | 最后更新时间 |

CHECK `subcontract_application_kit_notice_mark_values_chk`：两数 ≥ 0。可下单 > 水位才提醒并抬高水位；< 水位只降水位并 `epoch + 1`，降到 0 撤卡。系统协调状态：行级审计 NONE(`AuditTriggerCoverageMigrationContractTest` 的 notice 组)，清空业务数据 CLEAR。

### 第 2 步：10 个只读函数(SQL，STABLE)

| 函数 | 作用 |
|---|---|
| `fn_subcontract_application_exact_qty(申请明细, 物料, 颜色)` | 这张申请在这种直属物料上的专属批次余量：物料分析分给它的委外节点的直属子节点(顶层委外件取第 1 层节点)的库存权益批次，只算可用仓(未删、非不良品仓、非线边/内料仓、`fn_warehouse_counts_as_usable`) |
| `fn_subcontract_order_item_component_need(订货明细, 物料, 颜色)` | 一条还在办的委外订货明细对这种物料「还要领的量」：已批准未结案的按开着的领料计划行 `MAX(需发 − 已发净量 − 已提交未发, 0)`；草稿 / 在审 / 财务退回按 BOM 整单 `fn_subcontract_draw_f(订货量, 订货换算率 × 边用量)`；红冲、删除、已结案为 0 |
| `fn_subcontract_component_pool_demands(物料, 颜色, 排除订货单)` | 这种物料被还在办的委外订货单占用的量，按物料池分开：有来源申请的按来源份额(按行号累计、4 位小数逐份求差)拆到各申请明细，没有来源的部分(手工行、超出申请的部分)记在 NULL 池 |
| `fn_subcontract_component_public_qty(物料, 颜色)` | 公共可用库存：可用仓 `v_stock_available.available_qty` 之和(负数按 0)，与领料页公共部分同口径 |
| `fn_subcontract_component_public_free(物料, 颜色, 排除订货单)` | 公共库存的现有、被占(各申请专属批次不够的部分 + NULL 池)、剩余 |
| `fn_subcontract_application_kit_facts(申请明细, 排除订货单)` | 申请明细逐种直属物料的齐套事实：每套用量(申请换算率 × 边用量，6 位)、专属现有 / 被占 / 剩余、公共现有 / 被占 / 剩余、现在能用、够做套数。任务中心「齐套情况」与预填的唯一来源 |
| `fn_subcontract_application_kit_qty(申请明细, 排除订货单)` | 现有物料够做的套数 = 各物料够做套数的最小值；不封顶申请剩余量；没有可发外直属物料(缺 BOM)时为 0 |
| `fn_subcontract_application_open_qty(申请明细)` | 剩余未下单 = 申请量 − 已下单 − 在审订货单的来源份额(与 `v_procurement_decomposition_tasks` 的 open_qty 同口径)；申请不是已审核未结案、或明细已删除时为 0 |
| `fn_subcontract_application_orderable_qty(申请明细)` | 这次能下单的数量 = MIN(剩余未下单, 够做套数)；0 = 锁住(等物料齐套) |
| `fn_subcontract_order_kit_shortages(订货单)` | 订货单齐套检查，返回不够的直属物料(空 = 齐套)：本单每种物料按来源拆进各申请的物料池，先用扣掉其它订货单之后的专属剩余，剩下的(连同手工行)必须 ≤ 其它订货单之后的公共剩余。建单、保存、送审、批准、批准后加量共用 |

计算公式见 [ADR-156 §三](../99-决策记录-ADR/ADR-156-委外申请物料齐套才解锁下单.md)。所有份额按 4 位小数分摊(逐来源累计取整求差)，所以按「可下单 N」下出的单恰好通过齐套检查。`fn_subcontract_application_kit_facts`、`fn_subcontract_application_orderable_qty`、`fn_subcontract_order_kit_shortages` 带 `COMMENT ON FUNCTION`。

### 第 3 步：清空业务数据登记

按 V798 同款锚点补丁改 `business_data_reset()`：锚点 `('subcontract_draw_notice_marks', 'CLEAR'),` 必须恰好出现 1 次、且函数里还没有新表名，否则报 `V809 cannot extend business-data reset policy safely`；在锚点后追加 `('subcontract_application_kit_notice_marks', 'CLEAR'),`。评审神谕登记在 `BusinessDataResetSqlContractTest.RUNTIME_RESET_EXTENSIONS`(`subcontract_application_kit_notice_marks` → 809)。

### 第 4 步：自检

`business_data_reset()` 已含新表的 CLEAR 行；`fn_subcontract_application_kit_qty(uuid,uuid)` 与 `fn_subcontract_order_kit_shortages(uuid)` 存在。
