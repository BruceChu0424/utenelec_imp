- 没有在本机开发库、测试服务器或任何业务库执行。

决策与理由见 [ADR-155](../99-决策记录-ADR/ADR-155-清空业务数据测试文件单一规则与幂等删除.md)。一句话：「清空业务数据」要物理删除哪些测试文件，只由一个数据库函数决定；数据库能判断的拒绝条件只在一个函数里判断；V782 的签名意图票据整套机制删除。

文件：`server/src/main/resources/db/migration/V798__business_test_reset_single_object_rule.sql`，LF 行尾，全部在 Flyway 单事务内。迁移本身不清空任何数据，也不改任何业务行。

## 执行顺序

### 第 0 步：字节前置校验

先比对两个要整体替换的函数的已安装函数体，算法是去掉 CR 后的 md5：

| 函数 | md5 |
|---|---|
| `fn_clear_business_test_object_metadata()` | `73195ce907a32825dea7923b838e6b21` |
| `fn_attachment_retained_identity_guard()` | `e8b80397f53496ba32613a22040a7fa1` |

- 两个常量取自全新库迁到 V797 后的实测值，与本机开发库(V794)只读查到的值相同；V795-V797 没有改动这两个函数。
- 不一致时迁移失败，报错里同时给出期望值和实际值，提示「another migration changed it: merge that change into V798 section 2 and update the hash」。

### 第 1 步：新建 7 个函数

| 函数 | 类型 | 作用 |
|---|---|---|
| `fn_business_test_reset_objects()` | SQL，INVOKER，STABLE | 唯一的测试文件对象清单。一行一个物理对象；internal/local 的身份不带版本；受保护对象用 V783 的 `fn_business_test_object_protected()` 排除；只返回元数据。最后一列 `deletable_storage`(internal/local 为真)是「清空能不能自己删除」的唯一判断，规则 20 和 Java 删除循环都读它 |
| `fn_business_test_reset_object_fingerprint()` | SQL，INVOKER | 清单指纹 `条数:sha256`，按身份排序，登记版本也算在内 |
| `fn_business_reset_table_policy()` | SQL，INVOKER | 用与 `BusinessDataResetSqlContractTest.POLICY_ROW` 字面相同的正则，从 `business_data_reset()` 定义里解析 CLEAR/PRESERVE 分类 |
| `fn_business_data_reset_refusals()` | plpgsql，INVOKER | 唯一的数据库拒绝检查，输出 `(sort_order, reason_code, item_count, message)`。规则：10 后台事件排队中；15/16 要保留的文件还有删除任务没完成(后台会处理完 / 卡住了，用户 2026-10-05 决定 D9 继续挡住)；20 存储删不了；30-35 分类重复、有表没分类、分类的表不存在、保留表引用清除表、范围外引用、清空属主没有 TRUNCATE 权；36 全员登录状态单行缺失 |
| `fn_business_test_reset_require_caller()` | plpgsql，DEFINER | 调用身份检查 `fn_require_runtime_maintenance(true)`，排水前调用 |
| `fn_business_test_reset_lock_sources()` | plpgsql，DEFINER | 先做调用身份检查，再对 9 张来源表加 EXCLUSIVE 锁：`attachments`、`attachment_upload_sessions`、`attachment_object_outbox`、`ai_input_originals`、`sales_quote_template_candidates`、`sales_quote_template_candidate_history`、`sales_quote_template_versions`、`goods_cost_imports`、`business_outbox` |
| `fn_business_test_reset_verify_purged()` | plpgsql，INVOKER | 要求在清空上下文里调用。没有传入指纹时，清单必须为空，否则 `UT901`；传入了指纹时，必须等于锁后重算的值，否则 `UT901`。通过后设「本事务已复核」标记 |

### 第 2 步：整体替换 2 个函数

- `fn_clear_business_test_object_metadata()`：
  - 去掉证明断言和证明匹配，换成「加同一把锁 + `verify_purged` 复核」；
  - 删除任务的保留口径与 V783 逐字等价：业务属主的行全删；没有属主的自带清理行，只删不受主档保护的；
  - 对账发现按新身份匹配(internal/local 不看版本)；
  - 函数属性和 ACL 不变。
- `fn_attachment_retained_identity_guard()`：清空上下文里删附件行时，受保护主档附件照旧拒绝；其它行要求「本事务已复核」标记，不再查 `fn_business_test_object_sources()`。非清空路径(V777 的保留规则)逐字保留。

### 第 3 步：锚点补丁 `business_data_reset()`

读取已安装定义(去掉 CR)，逐条编辑后 `EXECUTE`，不整函数重发。每条编辑都检查锚点出现次数，不符就报错：`V798 edit <名称> expected <k> occurrence(s) …; another migration changed this part - adjust V798 by hand`。

| 编辑 | 内容 | 次数 |
|---|---|---|
| E1 | DECLARE 里只给旧检查用的 6 个变量换成 `refusal_text` | 1 |
| E2 | 入口先跑 `fn_business_data_reset_refusals()`，有原因就 `UT900`(多条原因按行拼接)，然后才调 `fn_clear` | 1 |
| E3 | 删掉分类行 `business_test_object_cleanup_intents` CLEAR | 1 |
| E4 | 分类清单写入后加断言：解析结果必须等于实际执行的清单，否则 `XX000` | 1 |
| E5 | 删除区间：旧的「前置拒绝」段(outbox、附件阻塞、目录检查)，现在由拒绝函数负责 | 起止各 1 |
| E6 | 删除区间：TRUNCATE 权检查，由规则 35 取代 | 起止各 1 |
| E7 | 删除区间：范围外引用检查，由规则 34 取代 | 起止各 1 |
| E8 | 清除历史审计时保留的回执动作只剩 `business_data_reset`、`business_data_reset_received`、`business_data_reset_failed` | 2 |
| E9 | 两处提到 psql 版的注释改写(纯注释) | 各 1 |

同一个 DO 块里，补丁前后各解析一次分类：要求「补丁前去掉意图表那一行」与「补丁后」逐行相等(重复行也要一样多)，否则报 `V798 changed reset catalog rows other than business_test_object_cleanup_intents: …`。还要比对补丁前后的 `prosecdef`、`proconfig` 和属主，任何一项变了都报错。

别的迁移对这个函数做过的改动，包括分类行和逻辑，都原样保留。

### 第 5 步：授权(沿用 V782 写法)

顺序和 V782 一样：先处理运行角色，再授给清空属主。

1. 运行角色 `uten` 存在时：先对 `uten` 显式撤销 `verify_purged` 和 `fn_clear`(生产的默认授权会自动授出)，再只授予 objects、fingerprint、policy、refusals、require_caller、lock_sources 六个函数的执行权。
2. 7 个新函数对 PUBLIC 撤销。
3. 对清空函数属主授予 7 个新函数和 `fn_clear` 的执行权。放在最后，是为了清空属主就是 `uten` 时不会因为「先授后撤」失去它要调用的这两个函数。这是防御性写法：V625 起，`business_data_reset()` 归不是超级用户的 `uten` 所有时迁移直接失败(运行维护入口不能归普通应用账号所有)，所以这种库实际不存在；属主是超级用户 `uten` 的开发库不受权限检查约束。
4. 给 DEFINER 小函数的属主授予 `fn_require_runtime_maintenance(boolean)` 执行权。角色拆分后属主可能是 `uten_migrator`。
- 应用以 `uten` 身份执行的 INVOKER 读取(拒绝函数、对象清单、指纹)依赖部署加固脚本对全部表的 SELECT 授权；同一个测试按加固脚本的授权以 `uten` 跑 `BusinessTestResetFiles.check()` / `purge()` 和清空。
- 部署配套：`deploy/setup/harden-existing-postgres-roles.sh` 在一揽子 `GRANT EXECUTE ON ALL FUNCTIONS … TO uten` 之后，补撤销这两个函数。`fn_clear` 是 V782 起就存在的同类缺口，这次一并修掉。`deploy/setup/test_postgres_role_hardening.py` 增加 `test_reset_context_functions_stay_private_after_blanket_grants`。

### 合并时别的分支新建的表怎么登记清空分类

改号以后，本迁移排在 main 已有的迁移之后(例如仓库整改分支的 V800-V806 先于本迁移执行)。分类只有一个家，所以新表的登记**不需要也不能**写进本迁移，做法是：

1. **分类行**：只写在 `business_data_reset()` 函数体的 VALUES 清单里，由**新建表的那个迁移**按锚点补丁追加，不改本迁移。写法照 V802/V803/V805：读 `pg_get_functiondef('business_data_reset()'::regprocedure)`，确认锚点 `(''stock_movements'', ''CLEAR'')` 恰好出现 1 次，在它后面追加 `(''<表名>'', ''CLEAR'')` 或 `(''<表名>'', ''PRESERVE'')`，再 `EXECUTE`。仓库整改分支已经这样登记了 `workshop_bins`(V802，PRESERVE)、`production_fqc_lot_decision_commands`(V803，CLEAR)、`ai_chat_action_proposals`(V805，CLEAR)。本迁移的 E1-E9 锚点不包含 `stock_movements` 那一行，E4 的锚点是清单最后一行 `(''unit_measurement_profiles'', ''PRESERVE'');`，追加在别处的行不会让本迁移失败；本迁移补丁前后的分类比对只允许少掉意图表一行，别的迁移先加的行会原样保留。
2. **评审神谕**：在 `server/src/test/java/com/uten/imp/ops/BusinessDataResetSqlContractTest.java` 登记，CLEAR 的写进 `RUNTIME_RESET_EXTENSIONS`，PRESERVE 的写进 `PRESERVE_RESET_EXTENSIONS`，值是新建表那个迁移的版本号(按 main 上的最终编号)，例如 `Map.entry("workshop_bins", 802)`。两边都改了这个文件，合并时两边的登记都要保留，本迁移那一行 `("business_test_object_cleanup_intents", 798)` 按改号后的版本号改。
3. **停机脚本**：别的分支如果还改了 `server/ops/reset_business_data.sql`(仓库整改分支改过)，合并时是「修改/删除」冲突，**保留删除**，它在脚本里加的分类行不用搬，第 1 步的锚点补丁已经是唯一的家。
4. **漏了会怎样**：
   - 只建表没在 `business_data_reset()` 登记：运行时拒绝规则 31 在删任何文件之前拒绝清空(「数据库里有 n 张数据表没有登记清空时要清除还是保留…」)；`BusinessDataResetCatalogPostgresTest.installedClassificationEqualsTheReviewedOracle` 失败(它还断言新库上拒绝函数什么都不返回)，用到真实清空的库测试(`BusinessDataResetRefusalsPostgresTest`、`BusinessDataResetLiveStateReproPostgresTest`、`BusinessDataResetServicePostgresTest` 等)也会因为这条拒绝失败。
   - 登记了分类行但没登记神谕：`BusinessDataResetCatalogPostgresTest.installedClassificationEqualsTheReviewedOracle` 失败，差异里会列出这张表；运行时清空不受影响。
   - 登记了神谕但版本号写错：`BusinessDataResetSqlContractTest` 整个类失败(加载阶段要求每个登记的版本号恰好对应一个迁移文件)；版本号对应的迁移里没有这张 CLEAR 表时，`runtimeResetExtensionsPatchTheTwinFunctionFailClosed` 失败。

先合并的分支如果改了上面两个整体替换的函数，或者改了 E1-E9 的锚点文字，本迁移会失败并点名，按报错手工调整。main 的 V798(ADR-143)只按锚点改分类行，和 E1-E9 互不重叠。
