# 03 - 数据迁移方案

> ⏳ **本档为方案框架**。具体迁移计划在老系统调研完成、后端启动时制定。

---

## 一、迁移目标

把老系统中的存量数据搬到新系统的新库，**不影响老系统运行**，搬完后新老库并行（新库主用 + 老库影子写）。

---

## 二、迁移的两种数据

| 类型 | 描述 | 时机 |
|---|---|---|
| **存量数据** | 老系统历史积累的数据 | 新系统上线前一次性迁移 |
| **增量数据** | 迁移期间老系统继续产生的数据 | 上线后通过双写或增量同步 |

---

## 三、迁移流程（标准三步）

```mermaid
flowchart LR
    A[1. 全量迁移] --> B[2. 增量追平]
    B --> C[3. 切换真相源]
    C --> D[4. 双写持续]
    D --> E[5. 老系统退役]
```

### 步骤 1：全量迁移（一次性）

- 选业务低峰期执行
- 从老库只读导出 → 字段映射转换 → 写入新库
- 全程不影响老系统

### 步骤 2：增量追平

- 全量迁移期间老系统还在产生新数据
- 用 binlog CDC 或时间戳轮询，把"全量开始之后"的增量数据补到新库
- 直到新库数据与老库差距 < 阈值（如 1 秒）

### 步骤 3：切换真相源

- 确认数据一致后，**新库成为真相源**
- 此后所有写入走新系统 → 新库 → 影子写老库（见 [02-双写与同步方案.md](02-双写与同步方案.md)）

### 步骤 4：双写持续

- 新老库并行运行
- 监控数据一致性
- 引导用户迁移到新系统

### 步骤 5：老系统退役

- 老系统访问量极低 → 逐个关闭双写开关 → 移除 adapter 代码 → 老系统下线

---

## 四、字段映射原则

| 原则 | 说明 |
|---|---|
| 老字段 → 新字段 1:1 | 大多数字段直接映射 |
| 老字段 → 新字段 N:1 | 老系统的多个字段合并（如 firstName + lastName → fullName） |
| 老字段 → 新字段 1:N | 老系统一个字段拆成新系统多个（如 address → province/city/detail） |
| 老有新无 | 老系统有但新系统不需要 → 丢弃（记录在映射表） |
| 新有老无 | 新系统新增字段 → 迁移时填默认值或空 |
| 枚举差异 | 老系统的状态枚举映射到新系统的枚举（如 `1/2/3` → `active/inactive/deleted`） |
| 编码差异 | 老系统用 GBK / 新系统 UTF-8 → 转码 |
| 时区差异 | 老系统本地时间 / 新系统 UTC → 统一 |

详细映射规则填入 [04-新老数据映射表.md](04-新老数据映射表.md)。

## 五、数据校验

迁移完成后必须校验，不能盲信：

| 校验维度 | 方法 |
|---|---|
| 数量一致 | 老库 count == 新库 count |
| 主键覆盖 | 老库所有主键在新库都能找到 |
| 抽样比对 | 随机抽 100 条，字段值逐个比对 |
| 业务规则 | 关联关系是否完整（如员工的部门 ID 都能查到） |
| 报表对账 | 关键统计指标（员工总数、库存总值）新老一致 |

校验失败 → 回滚（新库清空重导）或定点修复。

---

## 六、回滚预案

| 场景 | 回滚动作 |
|---|---|
| 全量迁移中发现严重错误 | 清空新库已迁移数据 → 修复映射规则 → 重跑 |
| 切换真相源后发现新库有问题 | 暂停新系统写入 → 老库继续作为真相源 → 排查 |
| 切换后双写老库失败 | 不影响新系统（双写失败本就不阻塞），但需尽快修复 |

**核心原则**：迁移过程中老系统永远是后备，可以随时退回。
