# 待检处置页（IQC）

> 状态：✅ 已实现（2026-08-16）。后端 V222 待检 sidecar 的前端入口，此前只有 API 无界面——
> 收货审核后货冻结在待检隔离，界面上无人能放行，链路在最后一步断掉。
> **Owner**：品质 + 仓库 | **创建日期**：2026-08-16

## 一、页面与权限

- 列表/处置：`/warehouse/inspections`（路由名 `warehouse-inspections`）
- 入口：预计到货任务中心（`/warehouse/inbound/expectations`）顶部筛选卡行的
  「待检处置」卡（全部待到货/采购到货/委外到货之后），卡面数字即角标
  （`GET /api/procurement/inspection/pending-count`，仍待检收货单张数）；
  持有查看权限者可见。处置返回后列表与角标自动刷新。
- 查看：`procurement_inspection:view`（V222 已种子入库，可在权限管理页授予角色）；
  处置（PASS/FAIL）：另需 `procurement_inspection:handle`。无 handle 权限者只读。

## 二、页面结构

1. **待检单聚合列表**（`GET /api/procurement/inspection/pending-receipts`）：
   仍有 PENDING/PARTIAL 明细的采购收货单/委外回厂单聚合卡片——类型徽标（采购收货/委外回厂）、
   收货单号、日期、供应商/委外商、待检行数、待检量（基本单位）、首末到检时间。点击展开明细。
2. **明细行**（`GET /api/procurement/inspection?receiptType=&receiptId=`）：
   货品（名称+编码+颜色）、到检/已合格/不合格/待检量、状态，以及**来源订货单号**
   （采购→采购订货单号；委外→委外订货单号——服务端沿 receipt_item→order_item 链回溯）。
3. **处置对话框**：
   - 合格放行（PASS）：数量可留空=全部剩余（部分 PASS 支持逐次放行）；说明必填。
   - 不合格（FAIL）：只记质量事实，不进可用库存；原因必填。
   - 幂等键由客户端生成（UUID v4），服务端事件账幂等（同键同命令静默重放）。

## 三、业务口径（与 V222 后端一致）

- 收货审核只建 PENDING 冻结行，**不写 stock_balances**；三个可用量口径
  （warehouseAvailableBase/globalAvailableBase/v_stock_available）自然不含待检品。
- 每次部分 PASS **即时**写合格 DIR_IN 进可用库存并刷新命中的活动物料分析；
- 只有**整张 receipt 全部明细终态**才一次性正式推进累计 PASS 供给到订单累计、
  peg/预约/DRAW/执行齐套并唤醒生产（WAITING→READY）。该两阶段口径分离、不重复计入。
- FAIL 不入可用；处置（退/换/补/特采）走对应业务单据，本页只登记质量事实。
- 红冲收货前必须全部明细 RESOLVED；已放行量由服务端按 passed 精确反向。

## 四、安全边界

- 处置按钮由前端按权限隐藏，服务端 `@PreAuthorize` 独立兜底（view+handle）。
- 数量校验双保险：前端对话框校验（正数且 ≤ 剩余），服务端按剩余待检量硬校验。
- 处置成功后自动刷新明细与待检单聚合；整单结案的卡片从列表消失。
