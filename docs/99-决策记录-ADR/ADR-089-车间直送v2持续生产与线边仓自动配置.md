## 一、问题

用户口径(2026-09-16)，逐条对应：

1. 「同一车间转送给父层级应该不用领料。如果父类所有子层级都来自同一车间且物料转送的，
   就不需要领料了；有子件在仓库(其他车间、采购、委外)才需要领料。」
2. 「子件还缺就是等待物料，子件齐了就是可开工，不用领料；可以分批，子件都有了但只有一部分，就只生产一部分。」
3. 「**部分开工·持续生产**：物料只准备了 20% 也可以先开工，后面物料源源不断来了不用再开工，
   来物料了就继续做，数量最后交付的时候再算，**不是再开个生产单**。」
4. 「现在有时候又不能转下一道工序了。」
5. 「给每个车间在仓库资料里创建一个仓库总觉得不对，明明现实中没有，要么就做个虚拟的、不算在现实的。」
6. 「我最怕数据错乱：该加没加、该减没减、该不算的地方算进去。」
7. 「生产日报审核确认后速度很慢。」

复核 ADR-087 落地后的真根因：

- 第 4 条：候选只列 WAITING/READY/DISPATCHED 的父件，父件一旦开工就再也收不到子件；「还差多少」只按直送行累计，
  父件从仓库领过的部分被重复计算。
- 第 3 条在既有模型里只能靠 V561 分批——每一批都是一个新工单段，要各自开工、各自报工，正是用户不要的「再开个生产单」。
- 第 5/6 条：线边仓是普通叶仓，V584 承诺的「不参与公共可用量与即时库存」全库没有一行 SQL 实现——线边仓余料会被
  别的任务当公共库存抢走(ADR-087 §六已知遗留)，安全库存预算还会扣留它。
- 「先直送、后到货」的父件由采购到货审核提升齐套时，线边仓领料单不自动出库，车间又要去申请领料、仓库要替车间发线边仓的料。
- 第 7 条：实测直送审核 2.9s，其中 0.8s 是线边仓入库触发的整张物料分析重算(13 次供应行动更新 + 3 次预锁足迹扫描)，
  料根本不进公共库存却把分析全刷了一遍。
- 「有时候又不能转下一道工序」的另一半根因在预锁足迹：线边仓完工入库的足迹把「同主仓要这个子件的其它分析」当成
  唤醒目标拉进来，而报工审核开头的预锁集合里没有它们——同车间只要有第二张分析也要这个子件，直送审核就撞
  「回调来源超出本次完整预锁集合」，永远转不了。

## 二、决策

### 2.1 持续生产 = 同一张工单、开一次工、直送子件到一批投一批

不拆批、不新建工单。等待物料的工单多一个动作「部分开工 · 持续生产」：

- 开工前提是「已经有一部分料」(2026-09-17 用户口径)：**每一种**可直送的子件都必须已经送到一部分
  (`fn_demand_has_direct_supply_on_hand`：本车间线边仓里有指名给那条需求的料)，否则入口不出现、
  调接口被拒并列出哪些子件一件都还没到。一件没到就开工等于零物料在产，接着还会去领仓库的料；
- 服务端把**可由同车间直送供给**的需求(同车间有在产该货品的工单，或已有直送指向它，**且货品对得上**)
  冻结为 `direct_supply`，段标 `continuous_supply`；
- 仓库供给的需求照旧**整批齐套**、形成仓库领料单、车间申请、仓库发料——用户第 1 条：有仓库料才领料；
  缺什么直接报出来，整单回滚不留半个标记；
- 直送需求不参与齐套：线边仓里已经到了多少就先预留出库多少，一件没到也不拦；
- 没有任何仓库需求时一键即 IN_PROGRESS；否则停在 READY 走既有「去领料 → 开工」；
- 此后每一笔「转下一道工序」报工审核，接收方是持续生产工单的，就地补投(线边仓预留 → 线边仓领料单 → 同事务出库)，
  上层接着做；超出需求剩余量的部分留在线边仓等下一批需求。
- 直送产出一入线边仓就被收料计划的分析备料权益(ORIGIN_MAKE)预留，不转正它就永远「没有可用量」：开工与补投都先把
  **该线边仓里**的权益批次转成正式预留(`transferToPlanDemandsWithinWarehouse`，不看主仓其它叶仓、不跟合格来源跨仓)，
  再取该线边仓里剩余的无主料，绝不外溢到仓库叶仓(外溢会造出一张要仓库发料的领料单)。逐次补投每次另起一行正式
  预留(上一笔已出库消耗的行不能再挂 V313 的 FORMALIZE 桥接)，`uq_stock_reservation_demand_supply` 改为只约束
  「未动过」的行；尚有未动过的行时追加到它。FORMALIZE 谱系按命令键分次记账。

数量最后再算(第 3 条)靠两道口径：报工累计不超过「同车间直送已到料按单耗折算」的上限
(子件只送来 40 套不可能报 50 个成品，第 6 条「该不算的不算」)；最后一次报工审核后释放直送需求未到料的余量，
需求按「已投入 + 已释放 ≥ 需求量」记履约完成，完工判定的材料结清一字不改。

为什么不改成「随时随地部分预留」：V249 的 READY 守卫是六条守恒链的地基，只对**持续生产段的直送需求**放宽一条
(coverage 多算 `direct_partial`)，其余四道闸(超预留/超领料、WAITING 不许持有部分库存、齐套必须提升、完工必须结清)
一字不动；仓库物料仍走原来的整批路径，风险面只在直送这一种来料。

### 2.2 线边仓由系统自动配置，并真正退出「现实库存」

不再要求任何人去仓库资料里建线边仓：第一次直送时按「车间 × 收料主仓」自动配置(`auto_created`)，
手工建过的照旧复用。它仍然必须是一个真实叶仓(ADR-087 的四道硬闸没有变)，但从此：

- `fn_line_side_stock_targets_demand` 是唯一口径：线边仓里的料只算给直送指名的那条需求(含 V561 分批谱系与原段级匹配)；
  齐套可用量、三条分配路径、物料分析、MRP 预览、销售出货可发量全部按它排除；
- 线边仓库存不进主仓公共预算，也不受安全库存扣留(ADR-087 §六遗留 (a)(b) 一并闭合)；
- 即时库存默认剔除线边仓(`含线边仓` 开关显式打开才计入，与「含不良品仓」同款)。

### 2.3 候选与自动出库两处补洞

- 候选包含持续生产中的父件；「还差多少」= 需求量 − max(已直送, 已预留/已领)。
- 任何带用户身份的齐套提升都自动出库线边仓领料单(此前只有人工重核路径)；系统对账留下的线边仓草稿由
  「开工」与「领料申请提交」就地补出，领料汇总不再出现线边仓行。
- 线边仓出库走仓库单据的审核/出库链，要求履约足迹已完整预锁；车间动作(重核物料、开工、持续生产开工、领料申请
  提交)此前不预锁就进库存维度锁，出库会被守卫拒绝(「已进入库存锁阶段」)。现只在本段真有线边仓料或草稿时
  (`mayIssueLineSideDraws`)先按计划预锁(`beginPlan`)，普通开工/重核的锁形状不变。
- 线边仓完工入库的预锁足迹不再把同主仓要这个子件的其它分析当成唤醒目标(与「线边仓入库不唤醒分析」一致)。
- 两个判定函数的**段级匹配补上货品比对**(2026-09-17)：`fn_line_side_stock_targets_demand` 与
  `fn_demand_direct_supply_eligible` 原来允许「这笔直送指向本段」直接成立，不看送的是哪种货品——
  于是本段收过任意一笔直送后，同段的**采购子件**也被算成直送供给(从此等一笔永不到来的直送)，
  线边仓里**别的货品**的料也会被算给本段其它需求(另一个父件指名的料被算进来)。现两处都要求
  直送行来源报工的货品/颜色等于该需求的货品/颜色。
- 「没有仓库料却能领料成功」堵死：只剩线边仓行的工单提交领料会被明确拒绝，不再以零行静默成功
  (车间以为领到了、仓库什么也没收到)。

### 2.4 报工页记忆与自动计算(用户 2026-09-16 追加口径)

- 「产出去向」与「转给工单」按本车间上次报同一货品的选择预填并**标黄 + 警示图标**，改动即清除；
  记忆直接查历史报工行(草稿也算最近意愿)，不另起记忆表；同产品有两个父件工单时不替人猜。
- 「本次实际用料」按「完工申报量 × 单耗」自动算出并标黄；完工申报量改了按比例重算(用户改过的行按其比例)，
  每次自动变化都重新标黄提醒核对。单耗优先取本批口径(需求量 / 对应产品数量)，退回 BOM 单耗，都没有就留给人填。

### 2.5 审核性能

线边仓完工入库跳过物料分析唤醒与委外备料/订货准备三套钩子(料不进公共库存，刷了也是白刷)，
预锁足迹也不再把同主仓的其它分析拉进来扫描。实测(开发库克隆、C1 编译、同一张子件报工反复审核)：
直送审核由 2.86s 降到 1.70s(热身后；冷启动首笔 3.28s)，仓库去向审核由 0.42s 降到 0.31s。
剩下的 1.7s 里数据库执行约 1.07s，其中提交时的延迟约束触发器约 0.7s、两次齐套可用量扫描约 0.18s，
其余是应用侧对象映射与出箱通知。

#### 2026-09-22 复量：剖面钉进用例，并纠正一个想当然的结论

生产实测(dev 库 audit_log)：一次审核 1.4s–15.1s，按直送行数近似 4 倍放大——
4 行全直送 15094ms / 约 350 行落账，1 行直送 6647ms / 123 行，1 行入仓 1395ms / 70 行。
15.094 秒那次正好撞上 Flutter Web 对无 body 写请求的 15 秒硬上限，服务端提交了、响应被浏览器丢掉
(见 `docs/05-架构/网络层与拦截器.md` §5.2)。

语句剖面自此有了常驻用例：
`WorkshopDirectTransferBatchEndToEndTest#oneDirectTransferApproveStaysInsideItsStatementBudget`
用 `ProductionJdbcMeasurement` 只对「审核」那一段计量，钉住「一笔事务」与语句条数上限。
2026-09-22 实测一行直送审核 **490 条语句、约 2.0s JDBC + 0.4s 提交**。

本轮只落了两处安全削减：

1. 线边仓完工入库连**就绪提升**一起跳过(判定移到 `readiness.onFinishedInboundApproved` 之前)。
   直送服务在同一事务里已经按需求投给确定的接收工单，这一遍是重复的。
   **实测只省 1 条语句**(491→490)：该路径的引导查询在本夹具下命中不到任何段，
   `tryPromote` 根本没跑起来——原先「白跑 N 遍可用量扫描」的推断不成立，记在这里免得下次再猜。
2. 同一张报工里重复的车间成员资格校验按执行工单去重(成员资格只由「工单 + 当前操作者」决定)，
   每多一条同工单的直送行省 2 条语句。

剩下的成本在哪，剖面说得很清楚，也说明为什么**没有**继续动：

| 成本块 | 观测 | 为什么这轮不动 |
|---|---|---|
| 提交时延迟约束触发器 | 约 0.4s | 改触发器触发时机是数据完整性决策，须单开 ADR 与前向迁移 |
| 足迹发现重跑 8 遍 | 约 40/490 条 | `FulfillmentMutationLocks.Guard#verifyUnchanged` 注释已写明这是刻意保留的锁后复核，由 `MaterialAnalysisPreviewPrelockPostgresTest` 与 `MaterialAnalysisStructureScopeEndToEndTest` 两条契约钉住，「不在这里偷改」(2026-09-23 已由 ADR-107 改契约：事务内只发现一轮、复核一次、比行版本，直送审核实测 385 条) |
| 单条慢读 | `read.production_material_analysis_materials` 2 次共 263ms；三条 `read.stock_reservations` 各 60–110ms | 是单条查询本身慢，不是重复调用；要提速得改查询或索引，须先有各自的剖面证据 |

结论：审核要再快一个量级，只能走「合并 FINISHED_IN 单据粒度」或「改延迟约束触发器」这两条路，
两条都改可观测契约，属于重设计而不是调优。在那之前，客户端侧已经不再因为慢而假失败
(写请求超时会重读权威状态，审核也有幂等键可安全重发)。

## 三、明确不做

| 不做 | 理由 |
|---|---|
| 仓库供给的物料也允许部分到料先开工 | 用户口径「有物料在仓库的才需要领料」，且那会把 V249 守卫整体放宽，风险面扩到所有工单 |
| 报工量不受已到料折算封顶 | 「该不算的算进去」——没有物料支撑的产出会在入库时进库存 |
| 持续生产中途改回普通模式 | 标记在开工那一刻冻结；需要停就按既有取消/红冲整包入口 |
| 线边仓完全不建(纯记账) | ADR-087 §2.1 四道硬闸未变，其中成本产出 movement_id NOT NULL 是死结 |

## 四、验证

- `WorkshopContinuousSupplyEndToEndTest`(真实 PostgreSQL)：全直送一键开工 + 逐笔补投 + 报工上限 + 完结释放；
  混合链仓库料缺时开不了工、领齐后开工、直送分次到料；线边仓料只归指名父件(同车间另一工单重核仍缺料、一件拿不走)；
  候选记忆。
- `WorkshopDirectTransferBatchEndToEndTest` 三场景回归。
- Flutter：候选/记忆模型契约、实际用料自动折算算法契约。
- 迁移在开发库克隆上单独执行：守卫函数体、视图列、全部既有段完整性断言通过。
