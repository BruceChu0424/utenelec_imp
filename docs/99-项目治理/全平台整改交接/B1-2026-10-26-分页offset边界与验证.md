# B1 分页 offset 边界与验证

日期：2026-10-26。本记录补齐全仓同类分页表达式，不修改业务筛选、权限、历史来源、金额或数量。当前状态为源码已写，根任务最终组合编译、回归与本地整合待回填；不能将本记录当成 B1 全阶段完成证据。

## 根因与公共合同

JPA `setFirstResult` 只接受 int。此前多处先用 int 计算 `(page-1)*size`，或将 `Pageable.getOffset()` 的 long 强转 int，极大页码会变成负数，产生 500，或读到另一页。`ProductionOverLimitDispositionService` 已有正确 long 检查，现将其优势并入公共入口，保留原中文错误和 422。

唯一公共入口为 `Pageables.checkedOffset(long page,long size)`：保留原页码、页大小至少为 1 的归一化，先 `Math.multiplyExact` 作 long 计算，乘法溢出或结果超过 `Integer.MAX_VALUE` 时明确返回 `VALIDATION_FAILED(422)`。合法 offset 恰为 `Integer.MAX_VALUE` 仍接受；不夹成另一页，不强改各调用方 100、200 或 500 等不同页大小合同。

本轮全部 11 个显式生产 `setFirstResult`，分布于 10 文件，均实际迁移至该入口。完整路径、行号、表达式和状态见[分页 offset 迁移清单](B1-2026-10-26-分页offset迁移清单.csv)。`GoodsService` 已有候选搜索最多 100000 页限制，仍保留；分类上下文及原先会回到末页的入口继续保留各自原合同。

原生 SQL `LIMIT/OFFSET` 能接受 long。9 处错误的 int 乘法仅在乘法前提升 long，保留原归一化、size、权限、count 和原有末页处理；没有套 JPA 的 int 上限。`Pageables.of` 也供原生 SQL 获取长 offset，故本轮未将其全部强制变为 JPA int 合同。清单只证明显式调用迁移，不将框架内部 Repository 的 offset 校验等同于本轮已逐入口验收。

## 通知祝福的必要差异

`NoticeService.listBlessings` 是零基页的原生 SQL 分页，并非内存 subList。原 offset 参数为 int，本轮改为 long。仍先验证通知对当前员工可见；取得完整 count 后，若 offset 已超过末尾则返回空 items 和原 count。合法的 long offset 交给原 Repository，不截到 int 最大值或第一页。原 `created_at DESC` 主序保留，只补 `id DESC` 同值尾序以避免同一时间多条记录跨页不稳。

未改变祝福本人标记、冻结姓名、撤回/再祝福历史或受众资格。没有删除业务行、历史、原件或迁移共享数据库。

## 测试与复验出口

- `PageablesOffsetTest`：正常/负值归一化、不同大小、int 最大合法 offset、越 int/long 上限，以及原生 SQL 深页的原有长 offset 合同。
- `JpaReaderOffsetTest`：调用交接候选、审计人员、固定资产、待摊费用、客户预收款、销售进度的真实公共 reader；溢出不得传给 JPA，不得取回另一页；预收款仍保持 200 行。
- `NativeSqlOffsetTest`：排产待办、报价核价、销售订单财务核价和委外领料真实公共 reader 将极大页码传为正 long；保留 100/200 页大小及负数归一化。
- `NativeSqlOffsetPostgresTest`：同四个真实 reader 的原生查询在 `MigratedSchemaBaseline` 私有数据库执行极大页码；使用随机合成关键词取得空结果，不清表、不写共享数据，确认 PostgreSQL 实际接受 long offset 而不会因负 offset 抛 500。该组由根任务统一 PG 窗口执行。
- `NoticeServiceTest`：补极大零基页空结果且 count 不变、合法超过 int 的 long offset、不必要 page 查询省略；原有本人标记与无权读取 404 断言继续保留。
