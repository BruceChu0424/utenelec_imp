## 背景

三个相互独立但同批落地的问题：

1. **通知模块全是 Mock**：`MockNoticeRepository` 内存种子数据 + 列表页「模拟新通知」演示按钮 + 发布页本地模拟接收端弹窗。需求方明确要求"模拟的都删掉，都是真实的"。
2. **通知无法删除**：列表页只能读，累积后无法清理。
3. **瀑布流"假"问题**：`UtenResponsiveGrid` 用 `Wrap` 实现——Wrap 按**行**布局，每行高度 = 该行最高子项的高度，矮卡片下方被迫留白。用户实测"第二行和第一行有些卡片间隔很远"，多列卡片页（通知/报销/工资条等 20+ 页）全部受影响。

## 决策

### 1. 通知后端：广播本体 + 每用户状态（V92 / V94）

- 表 `notices`：通知本体全员共享（title/content/type/publisher 快照/published_at/top_priority/priority/attachments JSONB）。
- 表 `notice_user_states`：复合主键 (notice_id, user_id)，`read_at` 已读、`deleted_at` 删除；无记录 = 未读未删。**已读与删除都是每用户维度**。
- 删除语义 = 「从自己列表移除」（微信式），**不影响其他收件人**；不做物理删除（广播本体删了别人也看不到，不合理）。
- 发布人 = 后端取当前登录员工 `employees.full_name` **快照**（前端不再传 publisher，防止伪造/改名回溯）。
- 权限：`notice:read`（employee 全员基础包）读 + 已读 + 删除自己的；`notice:publish` 发布。角色体系下线（ADR-011）后由部门配置/个人加授授予。
- 接口：`GET /api/notices?onlyUnread=` / `GET /{id}` / `GET /unread-count` / `POST /`（发布）/ `POST /{id}/read`（幂等）/ `POST /read-all` / `POST /batch-delete`。
- V94（并行任务补）：V92 只建 created_at/created_by，但实体继承 `BaseEntity`（四审计列），Hibernate schema-validation 缺 updated_at/updated_by 无法启动，增量迁移补齐。**教训：继承 AuditableEntity 的实体建表必须带全四审计列。**

### 2. 前端：删 Mock，接 DioNoticeRepository

- `mock_notice_repository.dart` 删除；新建 `lib/features/notice/repositories/notice_repository.dart`（`NoticeRepository` 接口 + `DioNoticeRepository`），providers 换实现。
- 列表页「模拟新通知」按钮删除；发布页本地 `dispatchNoticeArrival` 模拟弹窗删除（接收端提醒待推送/WebSocket 通道触发）。
- 访客审批通知桥（`visitor_notice_bridge.dart`）接真后端：动作人无 `notice:publish` 权限时 **try/catch 静默降级**——审批主流程已成功，通知落库失败可容忍，不反向拖垮业务。

### 3. 通知列表页多选删除

- 「管理」按钮或**长按卡片**进入选择模式；卡片右上角圆形勾选框（teal 填充 + 白勾）；底部操作条（已选 N 条 + 全选 + 删除）；二次确认后 `POST /batch-delete`。
- `UtenActionButton` 无 disabled 参数，空选禁用用 `Opacity(0.5) + IgnorePointer` 包层实现。

### 4. UtenResponsiveGrid 重写为分栏瀑布流 v3

- v2（Wrap）→ v3：`LayoutBuilder` 算列数 → 子项**轮流分配**（第 i 项进第 i % cols 列，保持从左到右阅读顺序）→ `Row` + N 个 `Expanded(Column)`，各列顶部对齐、独立堆叠。
- 同列卡片间距恒为 `runSpacing`，彻底消除行对齐留白。
- **API 零变化**，20+ 调用页（经 `UtenResponsiveGrid` / `UtenPagedGrid`）自动受益；`UtenPagedGrid` 当页切片防卡顿的职责不变。
- 历史结论"勿改 UtenResponsiveGrid（Wrap 真瀑布流刻意）"作废（docs/数据迁移/29 P2-5 已加注）。

## 验证

- 后端 `javac` 全量 736 文件通过；前端 `dart analyze` 改动文件 No issues。
- 端到端 11 步全过（临时测试账号，测完即删）：发布×2（发布人快照正确）→ 列表置顶在前 → 未读数=2 → 标记已读 → 仅未读筛选=1 → 全部已读 → 批量删除（deleted=2）→ 列表=0 → 详情 404 → 未读数=0 → 收回 publish 权限后发布 403。

## 影响与后续

- **待接推送通道**：紧急/重要通知的接收端到达提醒（`dispatchNoticeArrival`）目前只能由本端动作触发；全员推送需 WebSocket/FCM，接口落点已就绪。
- **可见范围**：发布页 UI 有全员/按部门选择，但后端 `notices` 表暂未存 scope 字段，当前全部按全员广播；按部门过滤待补列 + 查询条件。
- **服务端分页**：通知会累积，`UtenPagedGrid` 客户端切片先防渲染；量真大时改 `/api/notices` page/size 真分页。
- ~~`Suggestion`（建议箱）仍是 Mock~~ → **已于当日接真后端**（V96 `suggestions`/`suggestion_replies`/`suggestion_likes` 三表 + `/api/suggestions`；匿名脱敏服务端统一处理、连 submitterId 都不下发；点赞复合主键幂等；官方回复接口可顺带推进状态）。
