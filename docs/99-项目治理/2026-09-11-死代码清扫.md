## 三、性能（先测量，不做投机重写）

### 3.1 已修：两处前端重建风暴

Riverpod 的通知口径决定了「值没变也重建」：

- `FutureProvider` 用 `AsyncValue.==`（比 `valueOrNull`）→ **数据类必须有值相等**，否则每次轮询都是新实例；
- `StateNotifierProvider` 委派给 `StateNotifier.updateShouldNotify`，默认是 `!identical` → **光加 `==` 不够，还得在写 state 前自己按值拦一道**。

| 位置 | 现象 | 修法 |
| --- | --- | --- |
| `WorkshopTaskCountBreakdown`（`production_execution_workbench_repository.dart`）+ `ProductionWorkshopTaskCountNotifier` | 60s 轮询每次 new 一个快照，计数一个没变也把「我的车间任务」（756 行整页 Scaffold）重建一次 | 给数据类加 `==`/`hashCode`；notifier 里把两处 `state = x` 收敛到 `_publish(x)`，`next == state` 直接 return |
| `DraftCounts`（`lib/shared/providers/draft_counts_provider.dart`） | 同上：14 个计数全不变，每分钟仍让每个 hub 卡徽章、每个新建页 AppBar 的草稿按钮、以及在 build 里读它的销售单据列表页整体重建 | 加 `==`/`hashCode`（纯追加，未动该 provider 的任何既有逻辑——该文件另有会话在改） |

其余 60s 计数 provider 是 `FutureProvider<int>`，`AsyncData(5) == AsyncData(5)`，本来就不会重建。

### 3.2 报告：未修（需协调方定夺）

1. **`FutureProvider<Map<...>>` 同类风暴（未修）**
   `warehouse_quality_result_count_provider.dart:28`（`Map<WarehouseIqcStockInReceiptType,int>`）、
   `procurement_inbound_count_providers.dart:34`（`Map<String,int>`）。Dart 的 `Map` 是身份相等，
   所以每 60s 必然通知一次。当前消费方都是小徽章，重建代价低，故不动；若哪天被搬到大页面
   build 顶部，需改成不可变值对象或 `select` 取标量。

2. **草稿计数 14 次往返（未修，属另一会话）**
   `DocumentDraftCountQueryService.counts()` 每次调用循环发 14 条独立 `SELECT count(*)`
   （每条一次 round-trip），并且**每条都 new 一个 `DraftScopeAccessPolicy` 重算一次
   `nativeReadScope`**（归属集合解析可能各自打库）。60s × 每个在线用户。
   建议：单条 `UNION ALL` 一次返回 14 行（表名/列名全是编译期常量，注入面不变），
   并把同 scope（sales / purchase / subcontract / stock_doc / production_plan / finance）
   的归属集合解析结果按 scope 缓存一次。**索引侧已 OK**：
   `idx_so_status` / `idx_po_status` / `idx_sd_status` / `idx_pp_status` / `idx_frt_status` /
   `idx_fexp_status` 等单列 `status` 索引都在，`status = 0` 的草稿集合极小，
   谓词本身是索引友好的。

3. **`rememberPlacesForRegistrations` 的 N+1（未修）**
   `ProductionFinishedArrivalRegistrationService`：先一条 `IN (:registrationIds)` 取
   registration→report 映射（好），随后 `for (registrationId : ids) rememberPlaces(...)`
   逐个再进完整偏好流程（每个 registration 数条 SQL）。批量登记的 registration 数一般是
   个位数，量级可接受；要治的话得把 `buildRememberPlan` 改成一次性按批读源行 + 批量 UPSERT。
   ADR-058「按批次精确绑定」的语义必须保住，属非局部改动，不在本轮实施。

4. **FQC 写路径的逐行 INSERT（未修）**
   `ProductionFqcInspectionService` 有多处 `for (row : rows) { INSERT ... }`
   （送检行建 inspection、release 按 lot 建 allocation、decision 回写等）。都是**写路径**
   且逐行语义不同（每行要带自己的 lot / segment / allocation），不是读 N+1；
   行数受一次登记的明细数约束。改成 batch insert 收益有限、回归面大，只记录不动。

5. **批量读路径复核结论（无问题）**
   `ProductionFinishedArrivalRegistrationService` 的多单汇总登记读取（`batchArrivalRegistrations`
   / `batchPlaceSuggestions`）已经是「一条 `IN (:reportIds)` 取头 + 一条取明细 + 内存
   `LinkedHashMap` 分组」，没有 N+1。
