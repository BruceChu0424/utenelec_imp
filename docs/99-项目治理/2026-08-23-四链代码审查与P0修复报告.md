## 二、确认的 P0 缺陷与修复（本轮全部修复）

### P0-1 仓库点收三条路径全部被 V164/V232 数据库身份守卫拦截

`confirmFinishedInbound` 会 UPDATE 生产链单据的 `remark`/`total_original`/`total_local`，
而这些列在 V232 文档级守卫中不可变（V338 只给明细级守卫加了 GUC 放行通道）：

- REJECTED 路径追加"仓库拒收退回生产"备注 → 23514 异常，拒收事务回滚；
- ACCEPTED/PARTIAL 路径 `applyTotals` 把总额从 NULL 改 0 → 23514 异常；
- PARTIAL 余量草稿先 INSERT 建链再 `applyTotals` → 同样被拦。

现有测试全部是 Mockito 单测（mock EntityManager）或 SQL 直插迁移测试，从未穿越
真实数据库守卫，因此结构性测不到该层。

**修复**（服务端为主，语义不变、信息不丢）：

- 拒收原因只存 `production_finished_in_confirmations.variance_reason`（原本就存），
  不再写单据备注；
- 点收前置校验：明细带金额的草稿 fail-closed 拒绝点收（生产成品入库为纯数量单据，
  历史带金额草稿须先受控更正）；
- 移除点收流程中的 `applyTotals` 调用，总额保持 NULL（正确值），不再触碰守卫列；
- `StockDocDetail` 新增 `finishedInboundDecision`/`finishedInboundVarianceReason`，
  详情接口从确认记录提供权威展示；
- Flutter 详情页拒收徽章改为按 `finishedInboundDecision == 'REJECTED'` 判定并展示
  差异原因，不再从备注字符串解析业务状态；
- ADR-046 §2.4 已同步补充该口径。

**仍欠**：走真实 PostgreSQL（Testcontainers）的端到端点收回归，验证 Java 流程 +
数据库守卫两层同时成立。

### P0-2 多笔 AP_OFFSET 决策共享同一 billNo，毒化 GL 期间重生成

一次超耗决定可包含多条应付抵销方案，每条立一笔负 AP，但 billNo 均为
`损耗单号-索赔抵销`；`gl_vouchers` 有 `UNIQUE(voucher_no, source_type)`，
第二笔即违反约束，该会计期间 `generate(period)` 重生成永久失败。
**修复**：billNo 追加 resolution UUID（`-索赔抵销-<uuid>`），与既有 `SPCL-`/`SPCR-`
按 resolution 唯一的模式一致；GL 反转路径全部走 `source_doc_id`，不受单号格式影响。

### P0-3 Flutter 抵销类型集合与服务端契约相反

`SubcontractLossResolutionType.offsetTypes` 含 `servicePriceReduction`，导致
"加工费折让"在 UI 上被强制选择抵销目标（本地校验拦截），选了目标服务端又必拒 409
——该处理方案在前端是死路。**修复**：`offsetTypes` 收窄为 `{AP_OFFSET}`，与服务端
"只有应付抵销可以选择目标应付"同口径。

### P0-4 颜色页编辑/删除权限互换

细粒度权限改造时 `color_page.dart` 行菜单"编辑颜色"误用 `_canDelete`、"删除颜色"
误用 `_canEdit`。**修复**：恢复正确映射；同批顺带补回"批量复制"菜单项被误删的
`_canCreateMaster` 权限门（与相邻粘贴创建项一致）。

## 四、审查确认无问题的重点（摘要）

- 权限链：GM 特判六处实现一致；无 fail-open；范围交集四重校验；快照失效链路由
  V135/V315/V322 触发器覆盖；员工→账号→部门→授权状态→委派行锁序一致。
- 生产链：V337/V338 数据库级不变量（append-only、accepted+residual=reported 守恒、
  逐行 UUID 溯源）扎实；DRAW→开工门禁→报工→点收状态机闭环无绕过路径；锁序
  inventory→plan/package/segment→stock 一致；通知走 outbox 幂等。
- 应付链：月结恒等式逐行成立；红冲对称；四事实分离（收货立应付/材料是库存/付款清
  AP/索赔需财务决定）贯彻；V332/V362/V365/V373 数据库守恒约束三层防线。
- 前端：分页竞态有 LatestRequestGuard 守卫；乐观锁传参正确；Riverpod 使用规范。

## 五、遗留事项（下轮处理，均有明确定位）

1. **授权语义常量多点重复**：在职状态集合与员工承载层级硬编码在 4 个 Java 类 +
   5+ 条原生 SQL，应收敛到单一常量类并参数化。
2. **LEGACY_APPROVED 历史已审单无红冲修复工具**：有意 fail-closed，但无配套命令，
   需产品决策（提供来源修复命令或运维手工流程文档）。
3. **点收 Testcontainers 端到端测试**（P0-1 的验证缺口）。
4. **月结快照红冲事件日取可变的 `payment.updated_at`**：任何无关 UPDATE 都会移动
   红冲负事件的月份，破坏跨期连续性；应为 `finance_payments` 增加不可变
   `reversed_at`（前向迁移）。
5. **四份 periodIdentity 守卫样板重复**（采购/委外收退四服务）：适合抽
   `SupplierPeriodIdentityGuard`。
6. **`StockDocService` 17 个构造依赖**：建议拆分 FINISHED_IN 点收/红冲子服务。
7. **性能项**：齐套检查 `own` LATERAL 子查询可加覆盖索引；四个 AmountAuthority
   可按 order_item_id 批量查询；委外损耗审核两条路径成本翻倍可合并。
8. **幂等回放终态语义**：点收幂等重放对已红冲单返回当前详情，是否改为明确 409
   待产品确认（改动会弱化幂等契约，本轮不改）。
