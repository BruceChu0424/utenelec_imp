# ADR-023：统一任务并发控制与认领（show-as-locked）

> **状态**：已采纳（后端基础设施 V215 落地，集成按面分批）· **日期**：2026-08-05
> **取代/泛化**：ADR-021 §四 的 `hr_task_claims`（HR 域继续用旧表，新共享面接入统一表）
> **相关**：[ADR-021](ADR-021-人事域完善-转正车辆多联系方式与任务软认领.md)、[安全策略 §4](../05-架构/安全策略.md)

## 背景

全链路审计发现：除 HR 任务中心（`HrTaskClaim`，V213）外，**所有共享待办面（审批队列、采购/委外任务中心分解、履约工作台）都没有"我正在处理"的早期信号**——仅靠单据的 `PESSIMISTIC_WRITE + 状态守卫`。两个有权限的人都能打开同一待办，先提交者成功，后者点击时才报错。采购申请→订货分解在 preview→create 之间还有竞态窗（两买手都见 open_qty，都建单）。这会造成重复操作、困惑和浪费工。

用户的原始问题：**一人处理待办时，他人应该不可见，还是标注"XX 处理中"且不可点击？**

## 决策

采用 **show-as-locked（显示"XX 处理中"且他人动作禁用），不隐藏**，并泛化 `HrTaskClaim` 为统一 `task_claims`（V215）。

### 为什么是 show-as-locked 而非隐藏

对照 SAP S/4HANA（Reserve/Put-Back）、Dynamics 365（Accept/Release，工作项队列排除审批）、Odoo（`user_id`）、ERPNext（Assignment Rule）、Camunda（`claim`/`unclaim` + `REV_` 乐观锁）得出三条共识：

1. **无主流系统为工作流认领而悲观锁业务对象**——认领是工作流层软态，乐观并发在动作时挡碰撞；
2. **无主流系统对人工任务出真心跳/租约/TTL**（普遍缺口；本库 HR 24h 惰性过期反而领先）；
3. **认领后可见性是按工作流配置旋钮**（Workflow Resource Pattern 41），SAP/D365/Camunda 默认隐藏，Odoo/客服工具默认可见。

对本 ERP 选 show-as-locked 的五条理由：财务/HR/审批**可审计性不可妥协**（隐藏抹去 custody 链）；审批人休假需同事**接管**；**maker-checker**是常态；**问责不损吞吐**；隐藏的吞吐增益对本系统无关（任务异质、多角色、低量、高错成本）。隐藏仅留给可替代高量队列（本系统暂无）。

> 现有 `HrTaskClaim` 已实现 show-as-locked（ADR-021 §四 调研 Jira/钉钉/飞书/Zendesk 后选定），本 ADR 把它泛化到全链共享面。

## 设计

- **表 `task_claims`（V215）**：`target_type` + `target_key` 多态目标，部分唯一索引 `uq_task_claim_active ON (target_type,target_key) WHERE released_at IS NULL` 仲裁并发认领（同瞬两认领只一笔成功），`fn_audit()` 审计触发器（与 `hr_task_claims` 同范式）。
- **状态机**：AVAILABLE →（claim，靠部分唯一索引原子）→ CLAIMED（租约活；自己再 claim=续租幂等；heartbeat 续 `lease_until`）→ {RELESED 手动 / EXPIRED 读时惰性 / DONE 动作完成后 `release_reason=completed`}；manage 权限者 takeover（原认领释放后我认领）或 force-release。
- **按类型策略 `TaskClaimPolicy`**：`leaseMinutes / claimPermission / managePermission`。已登记：EXPENSE_APPROVE(30分,expense:approve)、PURCHASE_DECOMPOSE(15分,purchase_request:edit)、SALES_ORDER_APPROVE(30分,sales_order:approve)、FULFILLMENT_TASK(120分,stock_doc:edit)。未知类型 fail-closed。
- **可见性**：任务仍在所有人列表；前端在认领行显示「XXX 处理中（自 HH:MM）」徽标，他人动作按钮禁用，自己见"继续/释放"。
- **租约/心跳**：短租约默认 30 分（vs HR 24h）；可选心跳 `POST /api/task-claims/{type}/{key}/heartbeat`（弹窗打开时每 30s 续）；过期惰性（无调度器，同 HR）。
- **完整性底线（不变）**：认领只是 UX/防碰撞层；动作端点**保留**既有 `PESSIMISTIC_WRITE + 状态守卫`，并应在端点顶部调 `TaskClaimService.requireNoActiveClaimByOther(type,key)` 做服务端兜底（防两人同时操作）。两者纵深，缺一不可。

## 后果

- 正面：消除重复操作与竞态浪费；保留审计链与休假接管；与既有 `PESSIMISTIC_WRITE` 纵深互补；复用已验证的 HR 认领范式，降低风险。
- 负面/代价：短租约下读长弹窗需心跳（或重新认领）；多一个表与服务；集成须逐面测试，避免误锁正常流程。
- 不变：认领不替代服务端状态机；隐藏策略保留为未来可替代队列的配置旋钮。

## 2026-09-07 认领变更与续租竞争收口

认领、手动释放、管理者强制释放、接管、心跳都先以悲观锁读取未释放认领，并在获得锁后重查
真实状态；已释放或已接管的记录不能被迟到心跳恢复。销售财务目标统一先锁销售订单、再锁认领行，
接管不得先写旧认领再等待销售单锁。过期替换和接管先flush释放事实再插入新记录，保留原历史并
满足同目标唯一活动认领约束，不删除重建历史行。

心跳复核与新认领相同的职责权限和销售待审状态。失权不能续租，订单已办结不能新认领、接管或
续租；但本人/有管理权限人员仍可释放已完成或已删除目标的旧认领。未到续租阈值的心跳只读取
锁定状态，不UPDATE、不生成续租审计事件。真实PostgreSQL并发测试通过数据库锁等待状态建立
操作顺序，覆盖手动/强制释放与心跳、接管与旧心跳、心跳先胜出的后续释放、过期替换，以及阈值前
行xmin和租约不变。此修复不新增权限、迁移或页面入口。
