# 公共表格完整读取：大型 ERP 实践对照

日期：2026-11-10。范围：`uimp/table-read-performance-20261110`，基线 `69e35d96bf0ddd9c8ba7992bf0a609ee9191ef98` 及本次未提交实现。网页资料已通过 web 核查；仅用 SAP、Microsoft、Odoo 一手资料。未连接公司服务器。本文件是工程取舍依据，不是容量认证或发布回执。

## 一、先分清“四个规模”

大型 ERP 有千万条历史记录，不能据此推断它会将千万条完整业务对象同时放进一个低配浏览器。下面四项必须独立验收：

| 层次 | 规模含义 | 本项目要控制的成本 | 本次边界 |
|---|---|---|---|
| 数据库存量 D | 所有业务历史、明细和索引 | 查询计划、索引、聚合/排序、锁、临时文件和历史增长 | 后续隔离库检验 10万/100万/1000万历史下，指定业务查询是否稳定；本次不改数据库 |
| 单次查询真实结果 N | 当前权限、来源、搜索、筛选下必须返回的全部摘要 | 一次计数、稳定扫描、有界内部分批、字节数、版本一致性 | 保留全量连续读取；不能把数据库有1000万行当成查询也返回1000万行 |
| 浏览器常驻数据 R | 当前结果、身份索引、解析中数据、保留的页面/旧快照 | 每行实际对象大小、重复引用、缓存生命周期、GC、Worker复制 | 本次减少重复前缀复制；仍完整保留 N 行摘要，空间至少随 N 增长 |
| 实际绘制 V | 屏幕附近挂载的行、列、单元格 | 控件数、布局、文字量宽、主线程计算 | 复用既有行虚拟化；减少隐藏列测量和重复索引，不等于常驻数据也只有 V 行 |

符号是本项目的分析模型，不是某厂商的容量参数。当前“完整交互读取一秒以内”目标保持；首50行、网络结束、完整可操作分别计时。超大压力样本未达标时记录差距，不缩小结果或改验收口径。

## 三、本次已经采用和明确保留的机制

1. **同一读取只封存新增行。** `ImmutablePagedRowsBuilder` 把通过校验的批次封为不可变块，用私有权重二叉树共享已封存块，只复制追加路径；`PagedResult.withRows` 只建立独立响应包装，复用固定树根。旧结果不会被后来追加或重叠替换改写，旧快照也不引用未来 builder。
2. **追加证明只证明行引用前缀。** `pagedRowsAppendStart` 不证明行对象深度不可变、当前权限或动态可选资格。表格仅在明确 `immutableRows`、稳定行键、无额外可变过滤拼接且 owner 仍有效时使用；重复键/重叠更新回到原合并语义。编辑界面维持保守路径。
3. **连续获取与虚拟绘制分开。** 共享计划仍首50行、后台不停读取完整结果、至多200ms合并发布；滚动不触发请求。授权/版本失败撤下临时结果；总计、导出、批量操作等仍等待完整结果。
4. **减少热路径的整表工作。** 直接复用已证明的不可变结果，只验证新增段身份；删除无调用的旧页索引；缓存列结构索引；隐藏列不做无必要量宽。缓存资格和失效由公共入口统一维护。

源码入口：`lib/shared/models/immutable_paged_rows.dart`、`lib/shared/models/paged_result.dart`、`lib/shared/paging/complete_paged_snapshot.dart`、`lib/features/basic_data/widgets/master_data_table_view.dart`。共享批次合同：`contracts/complete-read-batch-plan-v1.json`。前端相关设计与实现使用 `frontend-design`，继续复用 Uten 组件、主题及业务约束。

## 四、分块结构的剩余成本，不能隐去

下面是当前源码的复杂度推导，不是实测内存或耗时。设 N 为结果行数、B 为批次数、P 为实际保留的历史快照数：

| 操作 | 当前成本与限制 |
|---|---|
| 输入批次防御冻结、逐行校验、新块封存 | 总行处理量 O(N)，存在有界批次的必要复制；“每行只封存一次”不等于全链零复制 |
| 直接 `for-in` / `map` 遍历块列表 | 专用迭代器用私有栈按块顺序走，O(N+B)，不对每一行重新找块 |
| `rows[i]` 随机读取 | 按子树行权重下降，O(log B)；不是普通数组的 O(1) |
| `getRange(start,end)` | 先跳过范围外子树，再顺序枚举 k 行，O(log B+k)；不回扫旧前缀 |
| 其他继承的 `ListBase` 扫描 API | 部分方法仍使用索引，可能 O(N log B)；须按实际调用画像决定是否迁移，不能把全部 List API 都说成线性 |
| 新批封存及快照 | 封存批内行 O(批大小)，追加只复制 O(log B) 路径；把已封存根包装为独立快照 O(1)。公开 `snapshot()` 在有未封存批时包含前两项成本 |
| 同时存活内存 | 一份数据/身份索引 O(N)，当前树 O(B)；保留 P 个旧根额外元数据上界约 O(P log B)，旧根不持有未来行。持续保留全部历史根仍有成本，不能无限缓存 |

本次最初采用“每批复制小目录”，在35k/100k时比复制整表轻得多，但继续研究发现其目录累计 O(B²) 不适合作为百万/千万目标的最终结构，已改为上述持久追加树。以下保留**已替换方案**的推导，说明修复原因：

| N | B | 累计复制块引用 B(B+1)/2 |
|---:|---:|---:|
| 35,000 | 41 | 861 |
| 100,000 | 106 | 5,671 |
| 1,000,000 | 1,006 | 506,521 |
| 10,000,000 | 10,006 | 50,065,021 |

这是旧方案的引用操作量，不是业务对象深复制数，不是峰值内存，也不能直接乘一个固定指针字节数当作所有浏览器的实际内存。新树的累计元数据新增改为 O(B log B)；10,000 个小载荷块的结构测试检查每批新增引用最多32、累计小于320,000，对照旧目录50,005,000次引用搬运。该测试等价考察约千万行/千行批次的**元数据结构**，并未在浏览器创建千万个真实业务对象。

新结构仅在原集合实现内维护私有节点/迭代器，没有第二套reader、框架或业务缓存。仍需保留旧快照独立、当前批校验、协变子类、唯一空响应owner及取消语义。直接索引的 O(log B) 常数和剩余索引式扫描，须与普通数组作真实浏览器对照；如其成为主成本，应修具体热入口，不把树形结构本身当性能验收。

## 五、百万/千万能力怎样逐步证明

- **数据库增长**：隔离库分别增加历史量至100万/1000万，查询结果固定50/1k/35k；检查执行计划、扫描行、排序临时空间、锁与普通命令时延。这样证明的是“历史增长不拖慢常用查询”。
- **返回结果增长**：固定列/字段/中文与精确小数合同，测试35k/100k，再测100万；1000万先做纯结构与字节预算推导，再在可控隔离环境逐步扩展。量化输入字节、模型与索引、目录分配、GC、Worker、取消与权限退休；不得据纯整数集合测试宣称真实 ERP 页面通过。
- **绘制与操作**：正式等价构建、4GB/8GB低配真机、中文输入、宽表、快速筛选、来回开关、隐藏恢复、同域写入与取消；分别测首批、完整可操作、滚动/输入延迟及稳态内存。内部批次与并发有界，完整结果不截断。
- **复杂业务**：全量列表/导出不代表允许百万行写入。保存、审批、计价、库存归属、幂等与未知提交仍遵守原边界。

本次已有35k/100k快慢批结构测试、协变与可变输入/并发/退休回归；既有100万整数读取回归通过只证明公共读取器的该合成路径。完整业务页低配和多人能力以独立真实交互证据为准，千万行尚未验收。不采用用户分页、滚动补页、隐藏截断或伪造统计来获得性能数字。
