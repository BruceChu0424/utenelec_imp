# 服务器设置、检查和预约更新

每家公司独立安装服务器。首次安装由主机管理员建立 Linux 服务、数据库、备份和可信发布公钥；
之后公司名称、平台参数、发布 OSS 来源和凭据通过已有设置页面维护，不需要修改应用代码。
个人主题、显示比例等仍是用户/设备偏好，不会改变服务器。业务设置继续使用各业务现有权威入口。

系统设置显示保存值、生效值、生效时机及能力限制。审计永久保留策略不会因修改显示月数而解除；
被数据库最低期限修正的值明确提示。历史自动更新间隔只读保留，自动拉取已退役。

## 授权

- 发布来源、OSS Bucket/区域域名/对象前缀、只读 AccessKey 与 Ed25519 发布公钥：仅超级管理员，
  沿用 `authorization:manage`，保存需要再次认证和版本校验。
- `server:update`：超管单独授予运维，可检查、立即更新或预约；不允许负责人自动继承/再次转授。
- `server:cleanup`：单独授予清理能力，删除前再次认证、预览和确认。
- 状态读取沿用 `server_status:view`，有上述操作权限的人也能读取对应状态；不向普通用户推送服务器更新通知。

应用不拥有 sudo、root shell、任意文件路径参数或读取 root 密钥的权限。主机助手只接受固定操作枚举，
Unix socket 使用 `SO_PEERCRED` 限制为应用账号。秘密只写入 root `0600` 配置；返回仅有凭据是否配置及尾号，
空白表示保留，清除需明确选择，更换 ID 必须同时给新 Secret。配置来源和对应签名文件作为同一版本原子提交，
保存后读取真实文件确认。配置变更期间有未完成作业则拒绝，避免更新途中换来源。

## 更新行为

进入页面、刷新、轮询、工作台徽章和通知任务只读本机。点击“检查版本更新”才读取云端版本号，
此时不下载程序、不重启。检查发现新版本时弹窗，提供立即更新和预约更新；通知按公司来源版本和用户持久去重。
检查到的来源版本保存在主机，换来源后旧提示失效，激活对应版本后待更新徽章消失。

预约选择服务器当地日期及凌晨 02:00/03:00，服务端根据真实 `/etc/localtime` 生成 UTC 执行时刻；
夏令时缺失/歧义时段拒绝，最远三十天，至少一分钟后。预约持久保存，原预约人或超管可以取消。
后端每三十秒只读本机预约，到期检查账号和更新权限仍有效才启动独立 worker；撤权则取消。
超过预约时刻十五分钟仍未能执行则取消，不在白天补跑。预约指定已检查版本，后续发布不会擅自替换它；
指定版本被云端清理则报错并保持原服务。尚未开始的预约会保护所需资源，清理可能因此被阻止。

检查与更新请求使用持久 requestId 幂等；HTTP 超时后查询已有作业，不能盲目重新提交。
worker 独立于应用服务，后端重启不影响它。异常中断不会自动重放迁移；本机状态会标记需要恢复。

立即/预约更新依次下载、验证发布签名与全部 SHA256、创建数据库和内部上传文件配套备份、逐件完整性核验、
`pg_restore --list` 检查备份目录，再执行必要的独立 migrator、原子切换和后端健康检查。
迁移目录比较包含文件内容，迁移历史版本集合与发布资源逐项核对，readiness/liveness 再连续观察一分钟。
观察期还要求同一个 MainPID 与激活后 NRestarts 基线保持不变，历史重启次数不会被要求归零。
稳定性观察使用独立的本机 `UTEN_OPERATIONS_HEALTH_URL`，默认后端回环 8080；既有
`UTEN_HEALTH_URL` 可继续用于验证证书的 HTTPS 入口检查，不改变其值，也不拿公网入口替代本机进程观察。
应用实际 JDBC 数据库、上传根与备份根由后端内部采集，HTTP 不能指定；主机还核对 peer 数据库实例的
postmaster 启动身份，防止同名同端口的另一个集群被当作配套备份。预约到期重新采集身份，正常数据库重启可刷新证明。
独立迁移程序保留既有固定 `127.0.0.1:5432/uten_imp`、`uten_migrator` 与 `public` schema 合同，
不是 Spring Boot，不读取网页/环境里伪造的数据库 URL。其专用环境只允许 `UTEN_MIGRATOR_DB_PASSWORD`。
各公司标准独立部署可复用这一布局；运行目标不一致时直接拒绝自动更新，不会猜测或迁移其他数据库。
检查/准备各阶段有超时，激活受四十五分钟独立限时；外层服务预算覆盖全部阶段并保留余量，
不会在正常准备预算耗尽后只留几分钟停服迁移。最终 cutover dump 超时/失败且尚未迁移时恢复原服务。
备份完整性检查和 dump 目录检查不等于实际隔离恢复演练；真实恢复证明只由 root 在完成演练后登记。
新版本含数据库迁移且失败时不得自动恢复旧库或擅自重放，页面提示管理员使用备份处理。

## 安装与验收

与应用同一已核验提交的 `deploy/simple/` 是主机组件来源。首次启用此功能，先完成同一发布的源码/CI/备份恢复门禁，
核对实际主机路径、已安装单元及 drop-in，停止任何正在执行的更新。运行：

```bash
sudo bash /reviewed/deploy/simple/install-server-operations.sh /reviewed/deploy/simple
```

安装器私有备份旧助手和单元，禁用旧 updater timer，建立本机 socket daemon 和独立更新 job 单元。
旧 `/etc/uten-imp-updater.env` 会复制到 `/etc/uten-imp-updater/source.env` 并保留旧件。
空白新部署可以由超管在页面输入来源，安装过程不会访问 OSS、启动更新或修改数据库。
已有备份/上传/日志路径写在 root `/etc/uten-imp/operations.json`，必须与实际部署、挂载与 systemd 可写范围一致；
不允许通过普通运维文件列表任意改变主机布局。自定义路径需要一次主机安装配置，不需要改应用代码。
首次安装还从正式配套备份配置读取兼容旧上传目录，作为独立只读统计类别；已有配置需要主机管理员核对
`legacy_uploads_root` 与 `local_media_root` 一致。两个目录的容量按各自所在卷展示，不能相加为整卷用量。
旧部署若迁移环境文件复制了整份应用配置，先在 root 私有备份中保留原件，再仅保留原有
`UTEN_MIGRATOR_DB_PASSWORD` 赋值；不改变凭据值，不复制应用密钥到迁移进程。

验收 `systemctl is-enabled/is-active uten-imp-updater.timer` 为 disabled/inactive，
`uten-imp-operations.service` 为 active，应用账号可连接 socket 且无权读 source.env。
在页面验证保存后读回、普通用户/仅运维不能修改来源、无更新权限不能启动、重复 requestId 只执行一次、
预约取消/撤权/错过窗口，以及重启期间作业恢复。只改应用 JAR 不会更新已安装的主机助手和 systemd 单元。

## 存储清理

页面分开显示整机内存、后端进程常驻内存与 JVM 堆，整卷容量和目录实占也分别显示。
上传元数据统计与物理对象统计区分，备份逻辑大小、去重后实际占用、可释放大小与恢复验证级别分别标明。
未能采集的环境显示未知，不能填零。

资源按固定类别列出，带用途、删除建议与受保护原因。数据库、仍引用的上传原件、未知租约缓存不可物理直删。
正在运行/回滚所需版本、最新成功集合、最新实际恢复验证点、最低备份集合数与保留窗口都受保护。
备份缺少可信恢复证明时禁止删除；既有正式备份保留任务也读取同一保护，避免旁路删掉已验证恢复点。
删除预览绑定资源实物指纹、操作人和五分钟有效期；确认后在共同更新锁和备份锁内重新核对，
按 fd 相对路径隔离再删除，不接受客户端路径，符号链接、替换、越界、占用和并发更新均拒绝。
上传文件仍由原业务删除/保留规则管理，运维页面不会绕过历史单据原件保全。

完成真实隔离 PostgreSQL 恢复并核对 Flyway 和业务/文件一致性后，root 才能调用
`python3 -I /usr/local/lib/uten-imp/host_operations.py record-restore-proof`，通过 stdin 提交哈希与恢复验收元数据。
此入口不在 HTTP/Unix RPC 中，不可用 `--verify` 输出替代恢复事实。证明文件保持 root `0600`，
必须保留受保护回滚版本与集合的绑定。
