# 任务弹窗接收池真实授权口径（2026-10-09 第三项）

用户规则：「所有的弹出——只有真实持有这个权限、且是这个部门（该对象归属）的人才会收到」。
两起实例（同一超管账号 17665410007，员工档案挂财务部）：
- 收到「盘点待审核：注塑车间内料仓」（`STOCK_COUNT_PENDING_WAREHOUSE_REVIEW`）；
- 委外财务审批通过后收到「委外可领料」任务通知（`SUBCONTRACT_DRAW_AVAILABLE`）。

## 根因（比单条链更深，是池子解析口径的问题）

1. **发卡池一律用 `PermissionResolver.permsOf` 解析候选权限，而超管的有效权限 =
   全量目录码的镜像**。于是：部门∩权限的池（ADR-063 口径）靠部门条件能挡住超管；
   但**纯权限池全部失守**——盘点审核（V767 两个码 INDIVIDUAL_ONLY 逐人授、开发库无人真实持有，
   池里只剩超管镜像，ADR-149「再没有才发整个池」兜底送达）、委外可领料
   （`userHasAllAuthorities(view:all)` 与 `canReadOwnedDocument` 双双直通）。
2. `canReadOwnedDocument` 的 SQL 里还有显式 `account.is_super_admin OR` 直通。
3. 超管的全量目录码是「什么都能做」的<b>操作授权面</b>，被当成了「这些活归他」的<b>任务归属</b>。

## 修复（ADR-063 2026-10-09 追加修订）

- **`PermissionResolver.grantedPermsOf(user)`**：真实授出的有效权限（baseline ∪ 部门矩阵 ∪
  个人加授 ∪ 负责人委派 − 个人收回），**不含超管全量镜像**；非超管与 `permsOf` 完全一致。
- **全部业务任务卡发卡池换用**（`permsOf → grantedPermsOf`）：
  ChainNoticeService 10 处（含核心 `userIdsWithRequiredAndAnyPermission`、`warehousePool`、
  `departmentUserIdsWithAuthorities/WithSecondaryAuthorities`、IQC 候选、车间任务候选、
  `userHasPermissions/userHasAllAuthorities`、采购/委外申请池）+ HrNoticeService +
  WorkshopMaterialNoticeService + StockCountNoticeHandler（审核池与提交人回执）。
- **三个财务资格类拆分双用途**（应用户"检查全部"要求的全链审计补项）：
  `SalesOrderFinanceConfirmerEligibility.eligibleUserIds`（销售→财务确认卡池）、
  `WorkflowReviewerEligibility.allEligible`（采购/委外→财务审批卡池；到货异常的
  `requireReviewerPoolAvailable` 守卫随之按真实授权判空——没人真实持码就不生成无人能审的任务）、
  `SalesQuoteFinanceReviewerEligibility.eligibleUserIds`（报价核价卡池）均换 grantedPermsOf；
  对应的 `isEligible/findEligible/eligibleReviewers*`（操作与指派资格门）**保留 permsOf**
  ——超管的"什么都能做"在操作侧不变。
- **`canReadOwnedDocument` 摘除 `is_super_admin` 直通**：超管要进归属范围收件人与常人一样
  须真实配置数据范围/交接。
- **运维告警不动**：`ServerAlertAudience`、`AccountSecurityNoticeService`（notifySuperAdministrors）
  面向超管本身，继续用 `permsOf`。
- 兼容性核查：超管在 DEPT_FIN 且部门矩阵真实授予 `sales_order_finance:*`、
  `finance_order_approval:*`、`sales_quote_finance:*`——财务三链的卡照常收到、操作照常可做，
  管理端测试流不受影响；计划部接手卡（SUB_PLAN ∩ 三码）不受影响。

## 契约锁定与验证

- `StockCountNoticeHandlerTest.superAdminWithoutRealGrantIsNotAStockCountReviewer`：
  无真实授权的超管不进池（宁可无人接收也不兜底发给超管）；真实加授后照常进池。
- 其余池子行为由既有回归守护（grantedPermsOf 对非超管与 permsOf 等值，仅超管语义变化）。
- **执行记录（2026-10-09，隔离 worktree 验证——主工作树被并行会话在途编辑阻断整体测试编译）**：
  notice 包 + 三个财务资格类 + 采购财务审批系列单测 **303/303 全绿**（39 skipped 为需真库用例，另跑）；
  真库回归 `WorkshopNoticeDeliveryEndToEndTest` **2/2**、`SalesPlanningNoticeCatchUpEndToEndTest` **16/16**
  （含三个资格类拆分后的最终代码）；适配打桩 13 个测试文件（`permsOf → grantedPermsOf`，
  仅投递路径；ServerAlert/读侧范围测试不动）。

## 用户侧验证口径

- 盘点审核：把 `stock:count:warehouse_review`（车间内料仓）真实授给对应仓库/车间的人后，
  由他们收到「盘点待审核」；超管未真实持码时不再收到（审核页队列仍按页面权限可见可办）。
- 委外可领料：发给订货单归属范围（制单计划员同组）里真实持 `subcontract_order:draw` 的人；
  超管不再因全量镜像收到。
- 超管想真正接管某类任务卡：逐人加授对应码即可（真实授出，立刻进池）。

## 仓库分级负责的落地配置（2026-10-09 用户确认口径）

用户口径：**不同仓库各有负责人；任务卡精准发到该仓（尤其子仓）的负责人，可能就他一个人；
仓库总负责人不需要每条都被打扰**。机制核实：这正是 ADR-149 三级路由
（`fn_warehouse_notice_recipients`：该仓链子仓负责人 ∩ 池 → 没有才指定主管 ∩ 池 →
再没有才整池），且 `ChainNoticeWarehouseKeeperRoutingTest.everyWarehouseDepartmentNoticeIsRoutedByWarehouse`
源码级钉死 14 处仓库通知 + 车间内料仓 + 盘点审核全部只经这一个规则；本轮真实授权口径
只改了「池」的解析，三级结构原样。数据模型：`warehouse_keepers` 按仓登记负责人
（登记在主仓上的是主管、不算子仓负责人）；子仓负责人按「本仓及其上级链」命中。

**开发库落地缺口（2026-10-09 实况）**：`warehouse_keepers` 全表 0 行（10 个在用仓——
主仓 001、五金 C01、成品 C04、成品不良品 C0401、塑胶 XW01、包材 XW02、注塑内料仓
LS-WS_ZHUSU 等——都没登记负责人）；SUB_WH（PMC运营仓储部）矩阵已授 77 码、子树 13 名员工
（含部门负责人庞宗荣 UT0025）**全部没有开通账号**。因此修复超管镜像后，仓库类任务卡在
开发库将无人接收，直至完成配置：

1. 给仓管/主管开账号并挂 SUB_WH（或兼职）——部门矩阵的 77 个仓库权限码自动带上；
2. 在仓库主档给各仓登记负责人（`warehouse_keepers`）——任务卡即精准到人（子仓负责人∩池，
   命中时只发他们，主管不再收到）；
3. 负责人在别的部门时（如车间认料人管内料仓）：登记该仓负责人 + 个人加授对应码；
4. 盘点审核两码（V767）是 INDIVIDUAL_ONLY 逐人授权——审核人需超管在权限管理页逐人加授。
