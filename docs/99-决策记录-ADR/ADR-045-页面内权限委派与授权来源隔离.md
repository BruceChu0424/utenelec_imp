# ADR-045：页面内权限设置与组织负责人单级转授

> 日期：2026-08-21
>
> 状态：V329 源码候选的编译、静态合同、Flutter 聚焦和 PostgreSQL 4/4 已通过；目标库、真实账号 UAT、目标规模性能、恢复与发布仍未完成
>
> 关联：ADR-011、ADR-020、V135、V169、V173、V328、V329

## 背景

系统需要同时满足两种权限维护场景：

1. 超级管理员在全局“账号与权限管理”中查看完整目录，维护部门配置、个人
   grant/revoke 和对象数据范围；
2. 业务负责人在当前业务页面内，只给自己组织管理子树内的员工设置当前页面权限。

负责人身份已经由人事/部门管理维护。权限域再增加一套“负责人范围”、公司领导、副职、
代理和有效期，会形成两个互相漂移的组织权威，因此该方案撤销。

旧“我的部门”面板直接写 `user_permission_overrides` 也不能恢复：负责人和超级管理员会写
同一来源，负责人可能覆盖中央收回，失去负责人资格后历史授权也无法可靠失效。

## 决策

### 1. 每个业务页面提供独立“权限设置”入口

- 登记了 `PagePermissionScope` 的员工业务页，在右上角统一显示“权限设置”。
- 点击后进入独立路由 `/page-permissions/:surfaceKey`，不是弹层。
- 宽屏为 `UtenSplitView`：左侧部门筛选、姓名/工号搜索与人员分页，右侧只显示所选员工的
  当前页面权限；分割线可拖动、键盘调整、双击复位并记忆宽度。部门筛选默认为空，点击后
  复用人事 `UtenDepartmentPicker/UtenDepartmentTreeView`，数据只来自页面权限 API 返回的授权裁剪树，
  不直接调用需要 `department:view` 的完整组织树接口。
- 窄屏采用人员列表 → 权限详情主从切换。
- 权限页自身关闭递归入口；登录、访客 Portal、个人自助、审计、系统设置和全局权限页不显示。
- Flutter 的路由映射只负责交互；V328 的数据库表 `permission_surfaces` 与
  `permission_surface_permissions` 是 surface 及其精确 UUID 权限关联的唯一来源。服务端
  `PermissionSurfaceRegistry` 启动时只从数据库加载一次不可变快照，并对
  `surfaceKey + permissionCode` 终审；不从路由、代码前缀或客户端目录回退。

### 2. 负责人权威只来自人事部门树

组织管理权威只有：

- 超级管理员：全部可挂人员组织；
- `departments.manager_id = 当前员工 UUID`：每一个合法负责人根覆盖该根及其全部未删除后代；
- 稳定编码为 `GM`、直接位于未删除公司根下且负责人是总经办直属在册员工的总经办：其负责人
  覆盖全部可挂人员组织。总经办的可改显示名称不参与判定，结构位置和删除由前后端共同锁定。

部门不选时，人员列表在上述全部授权范围内搜索；选择部门时，服务端取“授权范围 ∩ 所选节点及其
后代”。每行返回员工真实 `departmentId/departmentName`，详情与写请求使用该真实直属部门并再次复核
负责人范围；普通负责人左栏排除本人。

岗位名称、`positions.level` 徽标、旧角色、员工姓名、`employees.supervisor_id`、仅属于总经办或
前端布尔值都不产生权限。需要带组权限的项目经理、领导或组长，应在人事的部门管理中成为对应
组织节点负责人。当前
`employees.supervisor_id` 尚无完整维护、同部门、无环和调岗失效约束，本 ADR 不把它作为授权权威。

全局权限页不再出现“负责人范围”分区，也不提供负责人任职 API。

### 3. 展示范围与可转授范围分离

权限详情按当前 `surfaceKey` 过滤：

- 超级管理员：显示本页面完整权限目录，即使没有显式个人授权也显示；
- 普通负责人：只显示本人当前有效且属于本页面的权限；
- 已存在但因负责人失权、组织变化或策略变化而失效的历史委派，可额外显示，仅用于安全关闭。

“显示”不等于“可转授”。普通负责人的可编辑集合为：

    本人非委派来源的有效权限
    − 全员基础权限
    − 中央个人 revoke
    ∩ 服务端可转授策略
    ∩ 当前页面目录

因此负责人从上级委派得到的权限不能继续递归下放。高危权限可以作为已有效能力显示，但普通
负责人看到锁定原因，不能转授。

### 4. 超管中央覆盖与负责人委派物理隔离

超级管理员在本页设置时写 `user_permission_overrides`：

- 开启写 `grant`；
- 关闭写 `revoke`；
- 来源固定为 `SUPER_ADMIN_CONFIRMED`；
- V326 增加 `row_version`，每项使用 `expectedVersion` 做 CAS；V327 增加中性 `active=false`
  tombstone，全局权限页取消覆盖时不再删除行，版本保持单调，避免删除后重建 ABA。

这样超管在本页给负责人加授的额外权限，会进入该负责人的非委派转授上限。

普通负责人写独立的 `manager_permission_delegations`，不写、不删除中央覆盖。有效权限为：

    全员基础
    ∪ 部门配置（直属部门及祖先）
    ∪ 超级管理员中央个人 grant
    ∪ 当前仍有效的负责人委派
    − 超级管理员中央个人 revoke

中央 revoke 始终最高优先级。

### 5. 查询和批量写必须随人员规模稳定

禁止一次返回“整部门员工 × 本页权限”的完整矩阵。接口拆分为：

- `GET /api/department-staff-permissions/capability?surfaceKey=...`
- `GET /api/department-staff-permissions/managed-departments?surfaceKey=...`
- `GET /api/department-staff-permissions/staff?surfaceKey=...&departmentId={可选}&search=...&page=1&size=40`
- `GET /api/department-staff-permissions/employees/{employeeId}/permissions?surfaceKey=...&departmentId=...`
- `PUT /api/department-staff-permissions/employees/{employeeId}/permissions?surfaceKey=...&departmentId=...`

人员接口在数据库中用递归 CTE 重新验证当前负责人根或总经办公司范围，并与可选部门子树取交集；
按在册状态和姓名/工号过滤，`size` 上限 50。每行只返回工号、姓名、真实部门、岗位与账号可用性等
权限工作台所需字段；账号状态按当前页员工 UUID 一次批量读取。只有选中一个人后才计算其权限分解。

保存请求最多 100 项，每项携带 `code/enabled/expectedVersion`；整批在一个事务中按员工、账号、
部门、权限 UUID 稳定顺序加锁，任一冲突整批回滚，成功后只撤销一次目标 refresh token。

V326 增加在册员工部门分页索引、姓名/工号 `pg_trgm` 部分索引和当前部门负责人索引；V327
保留停用中央覆盖的行版本并增加 active 查询索引；V329 增加当前员工按
`full_name, code, id` 跨部门稳定分页的部分覆盖索引，并包含 `department_id/position_id`。

### 6. 并发、失效和审计

- 委派关闭保留行并递增版本，不物理删除，防止开关 ABA。
- 写入前后复核负责人、目标员工、账号、目标直属部门、页面目录、中央 revoke 和负责人 ceiling。
- V322 的账号、员工、部门单调代际与授权 epoch 防止调出再调回、负责人 A→B→A 等历史授权复活。
- 负责人变化、调岗、离职、账号永久停用和中央覆盖变化会让旧委派 fail closed。
- 负责人委派与中央覆盖都保留审计来源；写成功后目标旧会话按现有 `auth_version/epoch` 链失效。

### 7. V323 显式负责人任职以前向方式退休

V315–V325 可能已在某个持久开发库执行，旧迁移字节不得修改、重命名或删除。V326：

1. 关闭全部 `organization_permission_leader_assignments` 并递增版本；
2. 关闭全部 `scope_source='EXPLICIT_ASSIGNMENT'` 委派并递增版本；
3. 增加约束，永久禁止二者重新启用；
4. 保留表、外键和快照列作为只读审计证据；
5. 运行时代码不再解析该来源。

禁止通过 `flyway repair` 隐藏 checksum 或迁移目录差异。

### 8. “本页”语义边界

- 具体业务页可包含查看、编辑、审核、导出等与该页直接相关的权限。
- 各模块 Hub 只包含控制本页卡片显示/进入的权限，不包含子页面全部编辑权限。
- 普通用户未授权的 Hub 卡片隐藏；超级管理员始终全量显示。
- 同一个权限码可能被多个页面共同使用，例如 `stock:view`。设置该码会影响所有真正检查该码的
  业务接口；`surfaceKey` 负责目录隔离，不把全局权限码变成页面私有副本。
- 字段/区块级显示若没有专用权限码和后端 DTO 裁剪，不得只靠 Flutter 隐藏伪装成安全控制。
- 客户、销售、采购、生产、仓库等对象数据范围仍由 owner、任务实例、`user_data_scopes` 等策略控制，
  本页权限设置不扩大对象范围。

### 9. V328 数据库目录与显式动作分类

V328 在数据库登记 85 个稳定 surface UUID，并用 `permission_surface_permissions` 保存页面 UUID 到
权限 UUID 的精确多对多关系。数据库是唯一 surface 目录；服务启动后只使用该不可变快照，运行时不得
从 Flutter 路由、权限码前缀/后缀或编译期常量推导、补齐页面权限。

`permissions.action_type` 只允许十类权威动作：`VIEW`（查看）、`CREATE`（新增）、`EDIT`（编辑）、
`DELETE`（删除）、`APPROVE`（审批）、`IMPORT`（导入）、`EXPORT`（导出）、`EXECUTE`（执行）、
`CONFIGURE`（配置）、`ASSIGN`（分配）；页面分组使用该列，不再根据权限码名称猜测。

本次新增 204 个按钮级/端点级权限码。后补的 16 个生产码中，11 个为 active/assignable 且已有真实
页面动作与服务端门禁：执行分段 `assign/release_defer/dispatch/start`，计划包
`generate/draft_edit/cancel/reverse`，材料结清 `settle/reverse/close`。另 5 个
`production_execution:cancel`、`production_execution:reverse`、`production_mrp:generate_purchase`、
`production_mrp:generate_draw`、`production_mrp:generate_finished_in` 只兼容历史端点，固定
`active=false/assignable=false`，不会进入运行时活动页面目录且没有 UI；
不得因旧授权展开而将其重新启用。

主数据再增加 `department:move`（`EXECUTE`）与 `department:manager_assign`（`ASSIGN`）：两者均为
active/assignable、登记到 `org.department` surface，并在 Flutter 分别门控父级位置和负责人字段；旧
`department:edit` 授权通过两条新增映射保真展开，但编辑名称不再隐含移动或设置负责人。

`rd_task:create` / `rd_task:assign` 因本轮没有合法 UI 固定为 `active=false/assignable=false`，并移出
Flutter 权限候选；服务端端点、旧 `rd_task:edit` 展开映射和审计证据继续保留，不得据此伪造已交付入口。
`attachment:reconcile:view` / `attachment:reconcile:approve_delete` 为 `active=true/assignable=false` 的
中央目录治理码，不挂任何 business surface。迁移保留历史授权，但禁止新增授权和负责人转授；这不是
“严格 superAdmin-only”的有效权限规则，历史非超管授权只能通过显式对账和前向治理处置。

既有 `*:edit` 只保留编辑现有对象的窄语义；例如旧 `production_material_analysis:manage` 已停用并拆成
`create/refresh/cancel`，旧 `finance_order_approval:review` 已停用并拆成 `approve/reject`。旧码保留为
inactive 历史证据，不得重新显示为可配置的现行权限。

迁移以 207 条旧→新展开映射保真复制四类物理授权来源：`role_permissions`、
`department_permissions`、`user_permission_overrides`（grant/revoke，冲突仍以 revoke 为先）以及在
V327 边界仍有效的 `manager_permission_delegations`。该过程不复活过期/失效委派，也不恢复已下线的
角色配置入口；迁移后统一推进授权 epoch、账号 `auth_version` 并撤销存量 refresh token。

生产执行、员工与附件、主数据三组细权限拆分均已确认并完成。最终本地候选验收：Maven 2058 项
0 failure/0 error（283 skip）；PostgreSQL 16-alpine 空库 309 个版本，页面范围/代际 4/4、
surface 目录 4/4；Flutter 848/848；全量 analyze 0 error/0 warning，仅保留 6 条既有 info。
公司目标库/UAT/目标规模性能/恢复/发布继续是独立门禁。

## 发布与验收边界

源码、迁移和自动化只形成候选证据。V328 基线通过后业务方已明确确认页面权限委派
默认开启；通用/生产源码配置使用 `UTEN_MANAGER_PERMISSION_DELEGATION_ENABLED=true` 的默认值。
这只表示新版本候选在未覆盖环境变量时开启能力，不表示已向目标机发布、已迁移公司数据库或已通过
现场 UAT。紧急停用时将 `UTEN_MANAGER_PERMISSION_DELEGATION_ENABLED=false` 注入运行环境并重启
新版本；不删委派行，不回滚旧 JAR，不改已应用迁移。

目标库 `flyway_schema_history`/live history 只读对账、真实超管/管理中心/部门/班组账号矩阵、对象范围
UAT、目标环境并发/搜索性能、恢复和签名发布仍是独立 GO/NO-GO，不能把本 ADR 写成已部署或已上线。
