# V627 历史收货对价来源证明

迁移文件：`V627__legacy_receipt_consideration_provenance.sql`。现有采购、委外收货的业务数据不回写；四个目标表只增加默认 NULL 的来源运行列。

## 为什么首次导入会失败

V518 对当时已有收货保留 `consideration_required=false`，对新 INSERT 或新审批要求现代收货意图、逐行对价数量和应付守恒。首次导入原 P_In / E_In 时，这些旧行在技术上也是 INSERT，于是误入现代流程，在最后事务校验时因缺少旧系统从未提供的 consideration parts 而失败。

本迁移将经严格核实的历史 INSERT 放回原有历史语义。不会猜测 NORMAL、STANDARD 或原价，不生成现代对价分段、库存移动、应付、质检或新审批。`fn_assert_procurement_consideration_receipt` 及普通在线业务的所有数量、金额和身份守卫保持原样。

## 唯一历史入口

`fn_register_legacy_receipt_import_source(uuid,text,jsonb)` 固定支持采购头、采购行、委外头、委外行四类 source；要求完整 typed 原行，并复用 V626 的真实迁移身份、同数据库与集群、完整受审候选、源文件清单、运行排他锁和 RUNNING 单事务校验。函数按固定映射生成目标 UUID 和商业字段摘要，不接收任意目标表或调用方声明的预期哈希。

表 `legacy_procurement_receipt_import_sources` 保存原文件 SHA、原行 SHA、目标 UUID、固定目标字段 SHA 与事务身份，列入 PRESERVE。没有个人原文或金额 JSON。应用只读，注册入口不向 PUBLIC 或运行账号开放；真实审计保留来源与变更事实。业务清库保留这些证明。

只有新 INSERT 同时满足精确来源证明、同运行同事务、相同目标商业字段时，才能保留历史 `consideration_required=false`。普通新单不能靠设置 GUC、传入 legacy ID、复制另一行证明、重新绑定运行或将 true 改成 false 取得例外。

## 金额和单位保持原意

采购 `Total` 是原币金额。本币金额仅在源汇率明确为正时按原额乘原汇率计算，并保留完整精度；缺失或零汇率保持原状，本币金额留 NULL，不引用今天的主档汇率。

委外收货行的 `STotal` 是原系统月度本币库存成本。保存其本币原值；只有明确本位币且源汇率为 1 时，原币成本才与之等值，其余原币金额留 NULL。它不是委外加工应付的证据，原 `M_Out` 期初余额继续由自己的原始来源决定。原 `Total` 等未采用字段仍由签核 CSV、源备份与整行 SHA 完整追溯。

源单位和 `UnitRate` 的 NULL、0 不补成默认单位或换算率 1。新收货需要沿同一订货明细计算容量时，如果已有非零历史收货数量的单位或换算未经证明，则明确拒绝并要求核验；不能把未知数量当成 0，也不能通过默认 1 计算可收数量。

## 后续动作与不可变边界

历史头、行的原数量、价格、金额、币种、单位、关联订货、原状态和证明不可改。父头为历史来源时，其下已有的无 legacy 标记子行同样受保护，不能通过移出、移入、改价、改量或删除绕过。

既有真实退货等流程允许更新明确的累计退货数量与审计字段，仍受原有处理数量、库存、来源和反向守卫约束。只读历史收货不会变成新的可审批、可送检或可再次记账单据。新的合法订单、收货和应付按原生流程建立，不复用旧证明填补缺失事实。

## 验证

`LegacyReceiptConsiderationProvenancePostgresTest` 使用真实 PostgreSQL 和正式迁移，覆盖非空旧库升级不改业务值、两种历史收货的延迟提交校验、不增加库存/AP/对价分段、NULL/0 与外币成本保真、源证明篡改及冒用、原生 true 规则、应用身份拒绝。整笔 Shell 导入还由 `LegacyBootstrapCoordinatorPostgresTest` 验证后段故障回滚、全部源对账、成功回执和恢复重试。

单独投影测试与正式迁移、业务服务和全链导入证据分别记录，不以事务内 INSERT 成功代替实际提交检查。
