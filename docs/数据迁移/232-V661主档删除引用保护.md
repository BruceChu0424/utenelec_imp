# V661 主档删除引用保护(数据库兜底)

- 迁移文件：`server/src/main/resources/db/migration/V661__master_soft_delete_reference_guards.sql`
- 决策：[ADR-111](../99-决策记录-ADR/ADR-111-主档删除引用保护与批量原子命令.md)
- 新增表：无；新增权限码：无；清库分类不变。

## 背景

2026-09-22 货品 V40001-dy 仍是 V4ZJ005 有效 BOM 行的组件却被删除，货品删除只做
`is_deleted = TRUE`，所有 BOM 树里含它的成品在物料分析准备页一律 409。V181 起
`goods_bom_items` 已挡住「有效 BOM 行指向已删货品」的新增/改写，反方向没有任何闸。

## 内容

只新增三个函数与三个 `BEFORE UPDATE OF is_deleted` 触发器，条件
`WHEN (NEW.is_deleted AND NOT OLD.is_deleted)`，违反报 SQLSTATE 23514：

| 触发器 | 拦截 |
| --- | --- |
| `trg_goods_guard_bom_component_soft_delete` | 货品仍是「有效父件的有效 BOM 行」的组件 |
| `trg_colors_guard_in_use_soft_delete` | 颜色仍被有效货品(货品颜色、默认采购价/委外价的颜色)、或有效父件的有效 BOM 行指定 |
| `trg_units_guard_in_use_soft_delete` | 单位仍被有效货品当作基本/厚度/重量单位，或默认采购价/委外价的单位 |

友好原因(被哪些货品、单据、库存、预留、物料分析用着，以及怎么解除)由服务端
`MasterReferenceGuard` 在写之前给出；触发器只防绕过服务的旁路写入。服务端删父件时先在同一
事务里软删它自己的 BOM 行，所以「父件与组件同批删除」不受同一条 UPDATE 里行处理顺序影响。

## 存量

不做回填。已经存在的「有效 BOM 挂着已删组件」脏数据由物料分析准备页的报错点名到行后人工
修正(2026-09-22 的一条已由主线程按审计镜像恢复)；这类行不影响本迁移执行。

拒绝时服务端全局异常处理把这三条闸映射成大白话(「这个货品还是其它货品组装清单(BOM)里的
组件，不能删除……」)，不再落成通用的「数据已被其他操作更新」。

## 验证

`MasterDataIntegrityEndToEndTest.bypassingTheServiceIsRejectedByTheDatabaseGuards`：
直接 `UPDATE goods/colors/units SET is_deleted = TRUE` 命中上述条件时报 23514，闲置颜色照常可删。
