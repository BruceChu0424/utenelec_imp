## 二、真实数据库链路：17 → 0

`FullChainEndToEndTest` 59 项在本机 PostgreSQL 16（Testcontainers）全绿。分轮修复：

### 2.1 收货结算一致性 ×7（测试对齐）
E2E 的采购收货（`receiveIntoQuarantine`/`receiveAndPassPurchase` 及两处内联）与委外进仓
请求未携带订单结算方式，触发 V300+ "收货与财务批准订单结算方式不一致"校验。修复：新增
`purchaseOrderSettlementMethodOf`/`subcontractOrderSettlementMethodOf` 辅助从订单行回填。

### 2.2 V328 按钮级权限种子对齐 ×8（测试对齐）
V328 将复合权限停用并拆分按钮级权限，E2E 种子仍用旧语义：
- `attachment:manage`（已停用）→ `attachment:upload` + `attachment:delete`（下载另有独立 `attachment:download`）；
- 建单/审核拆分：`sales_shipment:create`、`purchase_order:create`+`:decompose`+`:delete`、
  `stock_doc:create`、`finance_receipt:approve`/`:reverse` 按测试意图补齐；
- `approvePurchaseForAnalysis` 内订货拆单/送审改由超管驱动（规划员无采购权限），
  审核仍由独立 createReviewer 批，职责分离语义不变。

### 2.3 红冲重建回写 totals 违反不可变列（生产缺陷）
`StockDocService.createFinishedInboundReversalDraft` 结尾 `applyTotals` 把纯数量单据的
`total_original/total_local` 从 NULL 改写为 0，触发
`fn_guard_production_linked_stock_document`（totals 在不可变列清单）。分批点收路径
（PARTIAL）本有明确注释"不回写 totals、NULL 即正确值"，专用红冲漏同口径。
修复：删除回写与随之失活的 `replacementItems` 列表。

### 2.4 V391：让料守恒触发器 PL/pgSQL 变量/列名歧义（生产缺陷）
`fn_validate_preplan_reallocation_event_totals`（V313）把局部变量命名为
`reallocation_id`，与 `preplan_stock_entitlement_events.reallocation_id` 列冲突；
延迟约束触发器在提交期以 `column reference "reallocation_id" is ambiguous` 失败——
**任何让料写入都会失败**，此前从未被动态执行暴露。V391 以
`CREATE OR REPLACE` 修复：局部变量改名 `active_reallocation_id` 并显式限定列引用，
语义与 V313 原意一致。E2E #23d 让料/优先补齐/正式桥链路由此首次完整跑通。

### 2.5 跨期间红冲与 LIFO 红冲（测试对齐）
- 会走红冲的收货/收款单改用当期日期（`BusinessTime.today()`）：GL 跨会计期间红冲
  守卫按设计拒绝跨期，固定历史日期的单据在被红冲的链路里不可用；
- 收款红冲遵守后进先出：`receivableSettlement` 先反转 receipt2（360）再 receipt1（600+40），
  断言按两步对称改写；
- `preplanReallocation` 的"来源预留恢复"断言改用稳定不变量
  （FORMALIZE 的 `released_qty` 占用全额归还）：两批 FORMALIZE 可落在不同来源预留
  （A 自有批次 + B 单上的优先批次），有效量合计随批次分布变化，原断言的常数不成立。

### 2.6 全量套件连带修复（18 项 → 0）
E2E 全绿后的全量 `UTEN_RUN_DB_TESTS=true mvn test`（2180 项）又暴露 18 项此前本地
从未执行的 DB 门控失败，全部收敛：

**真实生产缺陷（第三个）**：客户预收直收审核（无核销明细的 CUSTOMER_PREPAYMENT）
自 V379 起在真实库上必然失败——`postArAp` 两步写（先 INSERT 零值行、再 UPDATE 到账额）
撞上 V379 立即 CHECK 的预收 shape 约束；受 `findBySourceForUpdate` 触发的 flush 影响，
INSERT 中间态直接被数据库拒绝。既有"通过"的证据全部来自 mock 测试或迁移回填，从未有
服务路径在真库执行。曾尝试把约束改为 DEFERRABLE（PostgreSQL 不允许 CHECK 延迟）后
改为服务端一步写入终态：`ArApLedgerService.postArAp` 增加携带到账金额的重载，预收
INSERT 即写入 received/settled/负余额终态；结清判定以最终余额为准（V129
`is_settled ⇒ balance=0`）。由 `FinanceDocumentMutationConcurrencyPostgresTest` 的
收款种子改走服务创建后首次暴露。

**测试种子/契约对齐**：`FinanceDocumentMutationConcurrency`（种子改走服务、当期日期、
五族财务按钮权限 + GL execute + 预收看权限）、`FinancePaymentSettlement`（AuthUser
roles/permissions 参数序修正——`hasAuthority` 只认 permissions 不认 superAdmin 标志、
历史付款种子补供应商/币种、当期日期）、`LegacyBootstrapSchemaCompatibility`（Flyway
head 钉 309→354）、`CrossAnalysisReallocationMigration`（pg_get_functiondef 空白归一化
匹配 + V337 收紧后的 ORIGIN_IQC 白名单断言）、`SupplierClosedPeriodLockOrderContract`
（锁序契约改钉 SupplierPeriodIdentityGuard 的新 token，bill-date/today 语义断言移入
守卫类专测）、四个 SQL 契约测试（红冲事件日改钉 `COALESCE(reversed_at, updated_at)`）、
`PreplanExternalSupplySourceGuard`/`ProductionExecutionSegment`（订货审批种子补
settlement_method_id，V378 起已审委外订货必须携带结算方式快照）。

## 三、V390：付款/收款红冲事件日不可变（前向迁移）

月结快照与财务报表此前用可变的 `updated_at` 作红冲事件日，任何无关 UPDATE（乐观锁、
备注）都会移动红冲事件月份。V390 为 `finance_payments`/`finance_receipts` 增加
一次写入即由触发器锁定的 `reversed_at`，历史已红冲行以 `updated_at` 近似回填；
实体与两条红冲路径写 `reversedAt`，四处读取点
（`SupplierSettlementService.snapshotLines`、`FinanceReportService` 付款×2/预收×1）
改读 `COALESCE(reversed_at, updated_at)`。

## 四、代码专业化清理

### 4.1 后端死代码（11 方法 + 2 死访问器 + 1 死记录 + 1 恒同三元）
全部经全库引用计数核实为零引用后删除：`hasActiveFormalizationForSource`、
`requireEligible`、`revokeAllByVisitor`、`NotifyResult`、两个
`recomputeReceiptAmount`（采购/委外平行复制）、`dimensionKey`、
`requireApprovedPlanForStock`、`requireNonBlank`、`resolveMaterialViewGroup`、
`legacyWhereUsedSnapshot`（@Deprecated forRemoval）、`employeeHostLevels()`、
`isManagementCenter()`；`FinanceReportService` 恒同三元
`isAR ? "立帐单号" : "立帐单号"` 收敛为单一文案。

### 4.2 在职状态常量收敛（7 类 → 1）
`("active","probation","onLeave")` 此前在 7 个 Java 类各自复制。新增
`EmploymentStatusPolicy`（features/org/employee）作为唯一权威，7 处全部改引；
原生 SQL（6 文件 12 处）保持字面量镜像并在该类 Javadoc 中登记核对清单
（文本块常量折叠，参数化收益不抵 SQL 文本变更风险）。
`DepartmentLevelPolicy` 顺带清理：`IMMUTABLE_PARENT_LEVELS` 复用既有常量、
删除死访问器后 `EMPLOYEE_HOST_LEVEL_LIST` 内联进 `Set.of`；
`EmployeeRepository`/`MyDepartmentService` 中"管理中心不挂人"的过时注释修正为
与 DepartmentLevelPolicy 权威口径一致（管理中心可挂人）。

### 4.3 SupplierPeriodIdentityGuard 抽取
采购收货/退货、委外进仓/退货四服务的三份逐字样板（`periodIdentity(id)` +
`requirePeriodIdentityUnchanged` + `SupplierPeriodIdentity` record）收敛为
features/finance/payables 下单一组件：表名枚举白名单防注入、
`requireOpenAtBillDate`/`requireOpenToday` 区分审核（单据日期）与红冲（当天）语义，
报错文案与锁序完全不变。

### 4.4 前端清理（约 900 行死代码 + 5 处 controller 泄漏）
按引用计数核实后删除：生产报表旧链路（`production_report.dart` 整文件 +
`production_repository` 死簇）、财务/委外死报表仓库与死模型、4 条死 Provider 及
下游、7 个死顶层函数、死常量/死端点/死字段；5 处弹窗
`TextEditingController` 未 dispose 修复；4 处与现行行为不符的注释修正
（委外禁审口径、工作台刷新时机等）。

### 4.5 性能
V392：`production_plan_items(sales_order_item_id) INCLUDE (plan_id, qty)
WHERE is_deleted = FALSE` 部分覆盖索引——物料分析销售候选列表逐行
LATERAL（在制草稿量 SUM）改走 index-only scan，消除列表页规模下的逐行堆读。
（遗留：四个 AmountAuthority 按 order_item_id 批量查询——FOR UPDATE 批量化
会改变锁语义，需单独设计，本轮不动。）
