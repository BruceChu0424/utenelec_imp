# V558：清空业务数据按实际占用截断

公司清空请求曾在 Nginx 45 秒超时后继续执行并成功。只读检查确认 PostgreSQL 数据目录位于两块机械盘组成的 RAID1；公司副本的独立实验在全部 269 张业务表均为空时，原清空仍需约 18–24 秒，其中 94% 以上位于统计与 `TRUNCATE` 阶段，等待为 `IO / DataFileImmediateSync`，没有阻塞会话。此实验发生在本机隔离容器，不能当作公司耗时。服务器的附件清理记录均在一轮、0 秒内完成。

`TRUNCATE` 会为清空范围内的表和索引重建存储文件。原实现每次处理整张清单，空表也产生文件同步工作。V558 只前向调整 `business_data_reset()` 的这一段，迁移本身不执行清空，不改业务数据、既有迁移字节或清空权限。

执行顺序如下：

1. 原目录分类、附件证明、outbox 和保留表引用拒绝门保持。
2. 按稳定顺序锁定完整 CLEAR 清单，使用 `ACCESS EXCLUSIVE`，包括 PostgreSQL 默认递归锁定的后代；按当前执行身份核验全部显式根的 `TRUNCATE` 权限。取得全部锁后才逐表精确计数。完整根与后代集合仍拒绝来自范围外的外键，即使外部表属于另一 schema 或引用的是空表、分区叶。跳过空表的文件重建不等于允许对其并发写入或绕过权限/引用拒绝门。
3. 普通非空表及当前身份启用行级安全的根作为截断起点，避免被 RLS 隐藏的行残留；递归纳入所有外键引用它们的 CLEAR 表。分区根始终保留原来的完整子树截断；指向分区叶的外键按根与后代映射纳入闭包。传统继承、任一 CLEAR 根/后代存在用户 `ON TRUNCATE` 触发器，或事务使用 `REPEATABLE READ`/`SERIALIZABLE` 时，退回原全量截断，保留触发器跨表写入、执行顺序及旧快照不可见行的清空语义。
4. 只对闭包执行 `TRUNCATE ... RESTART IDENTITY`。闭包外的空表保留存储文件，但其 `pg_depend` 所属序列仍执行事务性 `ALTER SEQUENCE ... RESTART`，使用序列原本的起始值；表为空且序列已经推进时同样重置。
5. 主档金额与期初归零、完整审计、保留表计数、全部 CLEAR 为零、六个物化视图刷新、epoch 递增及 refresh token 清理保持原顺序和口径。任何后续失败同时回滚行、存储和序列重启。

V558 核对完整 V557/515 历史与唯一代码锚点后更新函数，并验证 owner、security definer/invoker、配置和 ACL 均未变化。停机脚本使用相同算法，同时新增 V558/516 目录允许项；运行时与脚本的片段由真实 PostgreSQL 测试逐字核对。

验证入口：`BusinessDataResetSparsePostgresTest`、原 `BusinessDataResetServicePostgresTest`、两份 SQL 合同测试及 Flyway 不可变检查。新回归覆盖多级外键闭包、未截断空表的并发锁、空表已推进序列、分区叶外键与所属序列、最终失败回滚、触发器/传统继承回退、保留表分区和外部 schema 引用拒绝、普通角色及 owner 自撤权限拒绝、真实 RLS 隐藏行和高隔离双连接旧快照。性能绝对值和目标安装状态由本轮发布记录单独确认。

2026-09-12 最终专项 34 项全部通过，失败和跳过均为零，其中上述新 PostgreSQL 回归 13 项。全量 Flyway 从空库迁移到 V558 及原服务提交/停机脚本测试通过；另从校验 SHA 的公司 V552 dump 恢复独立容器，逐表核对 398 张表与 510 条完整历史后，真实执行 V552→V557→V558 的 validate→migrate→validate。原 61,791 条审计及全部原业务行摘要保持，只保留 V553 已知增加的两条设置审计；函数 owner、security、配置、ACL 不变。

专项完成后，在同一独立副本、同一连接设置下交替执行旧 V557 与最终 V558，每个场景各三对。`jit=off`，`fsync/full_page_writes/synchronous_commit` 均为 on；没有并发 Maven/数据库测试。结果如下：

| 夹具 | 原函数中位 | V558 中位 | relation 文件重建数 |
| --- | ---: | ---: | ---: |
| 269 张业务表均为空 | 17.644 秒 | 3.685 秒 | 2,359 → 430 |
| 增加 697 条已处理 outbox 行 | 17.392 秒 | 3.498 秒 | 2,359 → 435 |

每次均核对 269 表清空口径、精确 0/697 行、96 主档分类和货品/客户/供应商保持，然后回滚。计入回滚后的中位分别为 17.700→3.706 秒、17.508→3.513 秒，约减少 79%–80%；数据准备和事后核验不计入该耗时，也没有把回滚测量当作应用提交或公司端到端响应。保守保留的分区树是剩余 430 个文件中的主要部分。原始证据位于忽略目录 `.codex-tmp/reset-performance-20260912/paired-benchmark-final.json`、`rehearsal-proof-v558-final.json`、`targeted-tests-r3b-summary.json`。公司数据库没有为了验收实际执行清空。

公司另一个独立问题是尚未安装仓库已有的清空专用 Nginx 路由超时。发布时应同步安装该配置并通过只读 `nginx -T` 验证；增加超时不能替代本迁移减少文件同步。不得关闭 `fsync`、`full_page_writes` 或 `synchronous_commit` 来换速度。

PostgreSQL 官方语义：[TRUNCATE](https://www.postgresql.org/docs/16/sql-truncate.html)、[ALTER SEQUENCE](https://www.postgresql.org/docs/16/sql-altersequence.html)。
