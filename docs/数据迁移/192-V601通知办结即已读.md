# V601 通知办结即已读（存量回填）

> 2026-09-18。用户口径：「有了对应的操作，通知页应该自动已读——现在很多通知办结了还挂在未读里。」

## 变化

- 对 `resolved_at IS NOT NULL AND audience_user_id IS NOT NULL` 的通知，按接收人幂等补
  `notice_user_states.read_at`（`INSERT..SELECT..ON CONFLICT DO UPDATE`，已读不回退，
  已删除的列表项不复活）。
- 无 DDL、不加表、不改任何其它行；重放幂等（重复执行命中 COALESCE 分支，零变化）。
- 配套代码（同批，不属本迁移）：
  - `NoticeService.resolveReviewNotices` 办结撤回时同步调用
    `NoticeUserStateRepository.markReadForAggregateRecipients`，按 `(aggregate_kind, aggregate_id)`
    把各接收人的通知置已读——此后办结即已读，不再产生新的「已办结未读」；
  - 前端 `NoticeRouteReadBridge` 重写为无状态双清理（精确路由 + 页面事件集），
    见 `lib/features/notice/providers/notice_page_clear_events.dart`。

## 为什么

审核待办通知（`ReviewNoticeCatalog` 注册的事件）业务办结时只置 `notices.resolved_at`，
不置各接收人的 `read_at`；未读数查询也不排除已办结行。结果：财务批完采购单、车间开工、
仓库出库之后，对应「待财务审核/待开工/待出库」通知在通知页灰显「已办结」却仍计未读、
仍占角标，用户要逐条点开才能消掉。本迁移把存量欠账一次补齐，应用层同批修复增量路径。

## 影响

- 存量库升级后，所有已办结的定向通知对全部接收人变为已读（已读不回退，仅补空）。
- 通知页/未读角标即时对齐；`task_completed_at` 语义不受影响。

## 清库策略

无 DDL、无新表；`business_data_reset()` 白名单已登记 `(601, 558)`；`notices` /
`notice_user_states` 属 CLEAR，清库后无残留。
