## 一、用户要什么(原话要点, 2026-09-22 晚 ~ 09-23)

1. 优化、提高整个项目的稳定性和效率: 页面切换流畅, 每个按钮反应快, "点下一步要加载半天"的地方都要快; 但必须保证正确性, 特别是数据计算正确。
2. 减少重复代码: 能提取就提取、能公共就公共、能组件就组件。
3. 问题一定定位到根因, 不要打补丁。
4. 权限: 每个页面的权限 + 工作台权限管理的总权限设计要加好、改好。
5. 审计日志: 该记录的都要能追溯; 数据会很大, 要有合理保留期并能自动清理, 且确保真的能清。
6. 系统设置: 该加的加, 改值后要真的生效。
7. 删掉老的没用的代码、备份、日志、无用文件; 代码结构要优秀; 大文件该拆就拆、模块化。
8. 数据大了响应也要快; 数据库可以改、可以重构、可以合并表, 但数据迁移代码与文件(老库导入)要对应修改, 适配以前的数据。
9. 文档: 老旧的删、该合并的合并, 完成后更新文档。
10. 安全。
11. 平台还没上线, "该重构就重构", 不用担心兼容。
12. 完整完成后合并代码(并行会话都已结束), 最后全量检查, 保证每条业务链都正确、能正常走完、考虑到各种情况, 并给总结。
13. 要考虑公司内部服务器的性能, 系统操作不吃性能、撑得住。
14. 迁移压缩时, 内网测试服务器原有数据要保留。
15. (09-23 午)周额度只剩约 10%: 完成这一阶段后收尾, 写详细交接文档, 下周继续(可能由其他人继续)。

**用户四项拍板(09-23)**: ① 整改最后把 Flyway 迁移压成 V1 基线(但服务器数据要保留 → 用"只改 flyway 历史"的重基线脚本, 见 03 文档 squash 节); ② 删除旧发布链, 打 tag 存档, 修订 ADR-060 §5; ③ 老库备份/职工信息表/product lists 迁出仓库到 `D:/uten_legacy_inputs`(脚本改读环境变量 `UTEN_LEGACY_INPUT_DIR`), 开发库 dump 与 1.37GB 备份移到隔离目录由用户自己删; ④ 库存价值账本轮只降开销(批量写/去派生审计/触发器收窄), 另写 ADR 查同行 ERP 提简化方案, 用户确认后再改模型。

## 二、为什么慢/为什么乱: 审计得出的共同根因

审计(13 个只读维度 + 完整性评审, 全文见 02 文档)用 dev 库真实请求耗时(audit_log 的 duration_ms)和代码/SQL 证据定位到:

1. **预锁足迹重复发现+整行 md5 复核**: 每条写命令"预读依赖图→加锁→锁后整图重读比 md5", 且每层嵌套服务各跑一遍(质检链一次 11 遍)。→ 第一阶段已根治(并发核心)。
2. **仓库/质检事务里同步整张重算物料分析**, 并拿全公司唯一的主仓 advisory 锁, 所有库存写被串成一条队。→ 第二波 maengine 根治(第一阶段已把主仓锁改为 3 秒限时尝试+只读预览用共享锁)。
3. **写放大**: 404 张表行级审计(含派生/计算表, 每行整行 JSON)、285 个延迟约束触发器每行每事件提交时重跑、52 张表语句级单位锁触发器、101 个冗余索引。→ 审计部分第一阶段已根治; 触发器/索引部分由 dbhyg 工作流处理(见第三节状态)。
4. **空写**: 采购订单头 767 次更新里 706 次值没变, 分析明细大量只改 updated_at。→ 第二波 whq/maengine。
5. **回滚式预览**: 物料分析"下达预览"真跑一遍下达再回滚, 持独占锁, 预览之间排队到 22 秒; 前端为掩盖慢又复刻一套估算算法(第二套口径)。→ 第二波 maengine。
6. **前端请求编排**: 工作台约 40 个互不协调的 60s 定时器各打计数端点, 每页 AppBar 现拉权限能力, 详情页 5 步串行请求, 返回即刷新不看数据变没变。→ 第一阶段已根治。
7. **同一个数算多遍**: 可用量 3 套公式、剩余未排量 6 份实现、订单行预留计数器跨单位舍入、金额舍入四套口径。→ 金额第一阶段处理; 其余第三波 truth。

实测基线(dev audit_log, 2026-09-18~23): 采购来料检验批量判定 p50 6.0s/最慢 31s; 物料分析下达预览 p50 2.5s/最慢 22s; 下达 p50 2.9s/最慢 20s; 日报审核 p50 2.2s/最慢 15s; 批量领料 p50 1.7s/最慢 9s; 委外发料 1.3-5.6s。公司服务器(4GB 堆)上 100 来源下达 19.4s、500 来源 55s。

## 五、下一步怎么开工(给下周的自己或接手的人)

**续做第一步(必做, 约半小时)**:
1. `git log --oneline -15 main` 确认第一阶段合并提交在 main 上; `git worktree list` 查看遗留 worktree(`.claude/worktrees/ov-*` 第一阶段分支已合并, 可 `git worktree remove` 清理; `overhaul` 是集成 worktree)。
2. 读本目录 04 文档第二、三、四节(工作区、铁律、合并与迁移头同步)。
3. 基线验证: `flutter analyze`、`cd server && mvn -o -q compile test-compile`; 需要时跑第四节列出的全量命令确认仍全绿。
4. dev 库: 用户自己的 8080 实例启动时 Flyway 会把 dev 库迁到第一阶段迁移头; 克隆库 `uten_imp_overhaul` 已迁好, 供复现与压测。

**然后按波次做**(03 文档): 第二波 maengine / whq / prodwrite / readpath / capacity 五个工作流可并行(每个独立 worktree, 文件边界已划好), 每个都要"实现→对抗评审→修复"; 合并后统一改迁移头、跑全量验收; 再开第三波 truth / cleanup / uikit; 第四波 tables / splitbe / splitfe; 第五波 docs / squash / final。

**优先级建议**(若资源有限): maengine > whq > prodwrite(用户最痛的慢按钮) > truth(数据正确) > capacity(服务器撑得住) > readpath > cleanup > tables > uikit > splits > docs > squash > final。final 的"老库全量引导+大数据压测+逐链多账号 E2E"不能省。

**不要重复做的调研**: 所有根因都有证据在 02 文档; 用 ID 定位, 开工时只需 grep 当前代码核对行号(已漂移)。第一阶段各工作流的详细报告(实测、改过的契约断言及理由)在各 ADR-105~112 与对应迁移说明里。
