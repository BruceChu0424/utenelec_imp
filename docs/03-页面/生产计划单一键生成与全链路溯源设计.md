# 联合排产、供给批次与全链路溯源设计

> **状态（2026-08-11）**：单入口、BOM 树交互、批量选择、计划向导汇总和 V192 车间预填已有源码候选，本文用于约束其业务语义。当前只有部分溯源投影，**不是「全链路已上线」的验收证据**。目标库迁移、真实 HTTP/浏览器、采购/委外收货与 IQC、生产报工/入库和多岗位 UAT 未完成，生产写链路仍为 **NO-GO**。
>
> 项目决策以 [ADR-029](../99-决策记录-ADR/ADR-029-生产计划前需求与物料分析重构.md)、[ADR-033](../99-决策记录-ADR/ADR-033-生产物料节点任务化与自底向上备料.md)和服务端事务边界为准。

## 一、先统一三个概念

| 页面概念 | 实际含义 | 不代表 |
|---|---|---|
| 物料分析 | 对所选需求、目标仓、BOM、当前合格库存和已知供给生成可版本化快照，供员工确认路线和批次量 | 已经生成生产计划、采购单或委外单 |
| 联合排产/供给批次 | 将多个销售订单行、产品和路径任务放在同一任务流中分组核对、补全；MAKE/BUY/SUBCONTRACT 仍分别提交 | 一张混合生产、采购、委外审批职责的「超级大单」 |
| 权威业务单据 | MAKE 生产计划、BUY 采购申请/订单、SUBCONTRACT 委外申请/订单及各自后续单据 | 汇总页上的分组或一条通知消息 |

因此，调度台只保留一个入口：

- 未选中时：「新建物料分析」；
- 选中 N 项时：「联合分析所选 N 项」。

原「物料分析」和「进入分析并生成计划」指向同一页，第二个名称还会让员工误以为点击后已经生成单据，不再保留。

## 二、调度台与物料分析交互

### 2.1 多选需求

- 调度台桌面待排表按服务端默认每页 100 行，表头复选框使用三态：空框=当前可选项全未选，勾选=全选，半选=已选部分；不可选行不参与表头状态。选择可跨页保留，底部显示「已选 N 项（最多 500 项，可跨页选择）」和 48dp「清空已选」，每行记住「本次联合分析数量」。
- 「建议联合分析（本页 N 行）」只作用当前页尚无活动 analysis 的候选。已有活动 analysis 的行只能单独恢复；与新来源混选或同时选多条活动 analysis 时必须提示，不得暗中合并两个分析上下文。
- 当前调度台 compact 待排卡只展示首批 100 行，尚无「上一页/下一页」，不得写成手机调度台已跨页。进入物料分析页后，销售候选才在桌面/手机都按每页 100 项服务端分页；手机明确显示 48dp「上一页/下一页」和「第 X / Y 页、共 N 项」，跨页选择保留。
- 单次联合分析最多 500 个来源（销售产品和手工计划合并计数）。窄屏物料页使用一个连续滚动区，把低频手工来源折叠为「其他需求」；已选数量只显示摘要和「核对数量」，编辑进入独立 90% 高度惰性列表，不把最多 500 个输入框嵌套在主滚动区。
- 调度台「新建物料分析/联合分析所选 N 项」只导航并带入 seed。物料页上真正新建并持久化 analysis、来源和 BOM 快照的按钮是「联合分析所选产品」；已有 analysis 使用工具提示「按最新库存刷新分析」。手工「加入分析」只加入本地来源，文档不得虚构「开始/刷新分析」按钮。

### 2.2 BOM 树与选择

- 完整 BOM 节点保留在分析中，初始默认「只看缺料」；顶部可搜索产品/物料，切换「待确认路线/全部 BOM」，计数准确显示「筛选命中 X 条；保留上级后共 Y 条 / 全部 Z 条」。筛选命中保留产品头和祖先路径，不静默隐藏；当前视图内产品根与分支默认展开，可单独折叠。这一现场交互覆盖 ADR-033 旧文的初始全展开默认，但不删除业务节点。
- 产品、分支和节点使用有间距的卡片布局。层级缩进只放在物料身份列，需求、分配、现货和缺口数量列对齐。
- 产品卡初始最多构建 60 项，按钮为「继续显示下一批（还有 N 个）」；BOM 树首次只构建筛选后前 30 个产品的节点，按钮为「继续显示下一批产品（还有 N 个）」。这是 UI 性能分批，不得删除或忽略未显示项的选中、数量和业务资格。搜索使用防抖，分析索引和筛选投影在同一版本内复用，优先级长列表使用惰性构建。
- 只有已确认路线且当前可执行的节点显示复选框；复选框只改变当前页的本地选中集，不自动调用路线 `PUT`，不自动生成 action，不自动通知下游。未确认、未保存、MAKE 下层未齐和只读节点改用“先确认路线/先保存路线/下层未齐/仅查看”的 48dp 状态控件，不能继续显示一个无法勾选的假框。
- 建议路线必须用「采用采购」「采用委外」或「采用自制」显式确认，不能把建议暗中写成人工决定。
- BUY 和 SUBCONTRACT 可不受 BOM 层级深度限制直接选中，但必须有当前激活需求、实际缺口、已确认路线、合法权限和未过期版本。
- 底部动作使用业务结果文案：「提交采购需求（N）」「提交委外需求（N）」「安排自制生产（N）」。
- 路线确认或任务下达超过单请求 500 条时先按稳定任务身份排序，再按 500 条分批；后一批使用上一批返回的最新版本/指纹，页面显示 X/Y 进度。部分失败只保留未完成且仍合法的选择。幂等键由请求前 CAS 和该 chunk 的排序后精确任务集合生成，不含重试时会重新编号的批次序号；“服务端已成功、客户端响应丢失”的重试必须命中原记录。
- 服务端把 `actionGroupKeys` 和 `materialLineIds` 映射、合并、去重后，再对最终任务集合强制 1–500；不能只让两个字段分别最多 500，从而被非 Flutter 客户端绕成一次 1000 项。

## 三、计划提交向导与只读备料汇总必须分开

### 3.1 MAKE/root 计划提交向导

选择可生成计划的 MAKE/root 后，底部动作按场景显示「生成总装计划（N）」「安排子件生产（N）」或「生成生产计划（N）」，进入标题为「填写生产计划单」的 `ProductionPlanWizardPage`。它只处理生产计划，不包含 BUY/SUBCONTRACT：

- 一种自制件的一个执行批次对应一张计划单；副标题明确「第 i / N 张 · 一种自制件一个执行批次 · 保存时由系统生成单号」。前端不预取下一号；子计划使用独立 `PRODUCTION_SUBPLAN=SZ` 命名空间，与主计划 `SJ` 不共用前缀。
- 每张必填本批数量、生产车间、负责人、计划开始和计划结束，班组可选；没有默认车间时显示红色说明并要求本次补齐。
- 行可通过「拖动调整本次提交顺序」排序；拖动只改变本次提交顺序，不写回 BOM、生产优先级或默认车间。
- 底部操作是「上一张」「应用到剩余」「保存并下一张」或最后一张的「汇总确认」。
- 「批量应用到后续 N 张」默认勾选「计划开始/结束日期」，默认不勾选「生产车间、负责人和班组」，并默认勾选「只填写空白字段（推荐）」；因此不会隐式覆盖已有组织安排，预填且非空的日期在默认“只填空白”下也不会被覆盖。
- 汇总弹窗标题为「确认提交 N 张生产计划单 · G 个车间组」，按车间或「未分配车间」分组；按钮是「返回修改」和「确认并提交审批」。每张仍保留自己的产品、数量、车间、班组、负责人、日期和来源路径。
- 确认后每个 MAKE/root 按 generate 契约生成独立计划草稿、`ACTIVE` planning draft 和 `SUBMITTED` plan link；不默认批准，不创建 READY、正式预留或 DRAW。

### 3.2 AppBar「计划单预览」是只读纸面投影

「计划单预览」打开的页面 AppBar 标题为「备料计划汇总单」，纸面标题为「生产备料计划汇总单」。它根据当前 analysis 只读展示：

```text
一、自制件（按组件安排车间生产）
二、采购件（通知采购部）
三、委外件（通知委外商）
```

待确认路线显示在「待确认供料路线（确认前不会通知任何部门）」；缺车间显示在「缺车间清单（生成计划单前必须指定）」。采购/委外只汇总已确认且正缺口的路线，同货品按货品+颜色+单位聚合但保留总量口径；状态显示真实单号或「待通知」。底部唯一动作是「打印 / 导出 PDF」，**没有提交按钮**，不会调用 route、notify 或 generate。

这张预览不是 3.1 的向导汇总，也不是跨职责的权威大单。BUY/SUBCONTRACT 必须在 BOM 页分别点「提交采购需求（N）」「提交委外需求（N）」；MAKE/root 必须走 3.1 的「确认并提交审批」。

### 3.3 当前公司头与权威结果边界

向导和只读汇总当前都硬编码「中山市优腾电器有限公司」。这是单公司源码现状，**尚未接入当前公司/组织配置**；多公司上线前必须改为权威组织配置并补打印、导出和岗位 UAT，文档不能把未来目标写成当前实现。

| 路线 | 实际提交位置 | 服务端权威结果 |
|---|---|---|
| MAKE | 「填写生产计划单」→「确认并提交审批」 | 每个 MAKE/root 独立草稿、`ACTIVE` planning draft 和 `SUBMITTED` plan link；不默认批准 |
| BUY | BOM 底部「提交采购需求（N）」 | `preplan_supply_actions` + 逐路径 allocation + 真实采购申请；不生成 `production_plans` |
| SUBCONTRACT | BOM 底部「提交委外需求（N）」 | `preplan_supply_actions` + 逐路径 allocation + 真实委外申请；不生成 `production_plans` |

三条写链路具有各自事务和幂等边界。页面必须逐动作显示成功/失败/可重试，不能把其中一条成功渲染为三条链整批成功。

## 四、默认车间学习：V192 是唯一真相

### 4.1 数据边界

- 唯一权威来源为 V192 `production_goods_workshop_preferences`，以货品和车间偏好记录已确认的选择次数、最后选择人和最后选择时间。
- **V253 是官网询盘迁移，不是生产默认车间迁移**。当前头 V289 也没有改变该边界；生产不得向 `goods` 增加 `default_workshop_department_id` 或建立第二份真相，否则会与 V192 分叉且无法表达选择次数与改派历史。
- 向导打开时按 goodsId 批量读取 V192 偏好；客户端每 100 个 goodsId 分块发送，避免 UUID 查询串逼近代理 8KB 请求行和数据库 `IN` 参数限制。接口失败降级为未分配车间，向导仍可由员工补齐，不能静默猜车间。

### 4.2 学习时机

1. 新计划向导只读取偏好并预填；没有偏好的行标记为「未分配车间」，由员工补全。
2. 保存草稿、拖动排序、打开/取消向导不学习，避免暂存或误操作污染后续预填。
3. 生产执行段正式确认时，才把该 goods 实际车间记入 V192。
4. 后续将执行段合法改派到其他车间时，再以新车间更新偏好；改派必须继续受组织、状态、权限和审计约束。

这种「确认事实后学习」保证本次可修改，下次有合理预填，同时不把草稿当成生产事实。

## 五、溯源与进度语义

### 5.1 目标链

```text
销售订单/销售订单行
  → 物料分析/分析产品/逐路径节点
    ├─ BUY → 采购申请/采购订单/采购行 → 收货 → IQC
    ├─ SUBCONTRACT → 委外申请/委外订单/委外行 → 回厂 → IQC
    └─ MAKE → 生产计划/计划行/执行段
BUY/SUBCONTRACT IQC PASS → 原料/半成品合格库存 → 物料齐套
物料齐套 + MAKE 计划 → 生产领料/DRAW → 执行段 → 审核报工
  → 成品入库 → 销售分配/出库/发运
```

页面上从任何单据查看「用于谁」或「来自哪里」，服务端必须用结构化 ID 和行级关联回答，不能只按单号字符串或 goodsId 猜测。

### 5.2 三种数量不能混用

| 事实 | 权威来源 | 更新什么 | 不得更新 |
|---|---|---|---|
| 采购/委外收货并 IQC `PASS` | 收货行、质检结果、合格库存台账 | 目标仓合格可用数量、对应路径的物料齐套/可完工量 | 产成品报工量、成品入库量和销售完成量 |
| 审核报工 | 生产报工/执行事实 | 计划行 `fqty`，页面显示「已报工」 | 成品可用库存和 `iqty` |
| 成品审核入库 | 成品入库单、计划入库关联和库存台账 | 计划行 `iqty`、成品合格库存，页面显示「已入库」 | 把未入库报工量当成可发货库存 |

计划进度卡至少分开「计划量 / 已报工 / 已入库」。客户端不负责凭状态名称推测数量；服务端必须从已审业务事实汇总。

正式计划的「物料齐套」也必须单独显示，并只读取已确认 V1 计划包的执行分段权威投影：`planned_qty` 表示该分段对应的成品数量，`material_ready` 表示该分段已经通过精确预留与领料门禁；`ZERO_MATERIAL` 是可审计的无需物料事实。不得用仓库总余额、采购在途、分析页参考可用量或 `supply_pegs` 猜正式计划齐套百分比。页面分别显示：

- `NOT_PLANNED`：尚未生成正式执行计划，百分比为空；
- `LEGACY_UNSUPPORTED`：旧 V0 计划未计算齐套，百分比为空；
- `WAITING / PARTIAL / READY`：按已齐套执行分段的排产数量计算，并同时显示「已齐 X/Y 段」；
- `DATA_ERROR`：V1 包缺少有效执行分段，明确要求检查，不能伪装为 0%；
- `canStartNow`：至少一个 READY 且物料齐套的分段当前可以开工。

已完成分段保留其历史齐套贡献，避免结算释放预留后进度倒退。父计划和自制子计划各自独立计算；子计划齐套不会提前把父计划标成齐套。

### 5.3 分析上下文与精确 peg/allocation

「这批收货大体属于某个物料分析」不等于「其中 120 件精确供给销售订单 A 的第 2 行、计划 P 的第 3 行、BOM path X」。

完整溯源必须保留行级和数量级守恒：

- `sales_order_item_id`；
- `analysis_id + analysis_item_id + path/node_key`；
- `supply_action_id + action_allocation_id`；
- 采购/委外/生产计划的单据 ID 与行 ID；
- 收货行、IQC 批次、库存批次/台账行；
- 领料行、报工行、成品入库行和销售发运分配；
- 每次正向、撤回、红冲、拒收和替代的数量。

在精确 allocation 尚未连通某一环时，UI 只能标记「分析上下文相关」或「计划相关」，不得显示为「已精确占用给该销售行」。分析分配也不是物理预留；只有计划批准事务内的正式预留和仓库台账变动才能改变权威库存。

## 六、当前部分溯源投影

项目已有多个结构化关联点，例如销售订单行与计划的关联、物料分析与计划的关联、`preplan_supply_actions`/逐路径 allocation，以及计划与仓库单据的关联表。计划详情当前投影明确关联的销售来源、领料、成品入库、旧 MRP 采购申请，以及沿「计划分析产品 → BOM 路径物料 → action allocation」关联的新采购申请和委外申请。

这些只能表述为「当前部分溯源投影」，原因包括：

- 库存单据关联中可同时出现领料和成品入库，页面与查询必须按 `doc_type` 分类，不得都标成领料；
- 采购/委外目前只投影到申请；申请到订单、分批收货、IQC 和库存批次的路径尚未在一个详情投影中完整呈现；
- 部分关联只到 analysis 或 plan 上下文，尚不能证明收货批次已精确分摊到某销售订单行与某 BOM path；
- 断链检查页只能作为治理投影，必须证明每种规则的 JOIN、对象范围、误报/漏报和修复路径，才能宣称可用；它本身不会自动补链。

## 七、参考系统的可借鉴思想

外部文档只用来校准交互与业务边界，不证明本项目已经具备同等能力：

- [Odoo Master Production Schedule](https://www.odoo.com/documentation/18.0/applications/inventory_and_mrp/manufacturing/workflows/use_mps.html)：计划建议与真正制造/采购单据需要分开理解。
- [Microsoft planned order firming](https://learn.microsoft.com/en-us/dynamics365/supply-chain/master-planning/planning-optimization/planned-order-firming)：可批量处理计划建议，但转换后仍形成按类型与规则约束的供给单据。
- [SAP planned order conversion](https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/fe39e10a9a864a8f8dc9537704f0fa13/5a4ab0310c694ed18b94fdd7a4da8b58.html)：计划对象转为执行单据是显式业务动作，不是打开分析页的副作用。
- [Oracle supplies and demands view modes](https://docs.oracle.com/en/cloud/saas/supply-chain-and-manufacturing/26b/faupc/supplies-and-demands-view-modes.html)：供需视图应能解释供给、需求和关联，但页面投影不能替代行级分摊事实。
- [SAP Fiori tree table](https://experience.sap.com/fiori-design-web/tree-table/) 与 [tree](https://experience.sap.com/fiori-design-web/tree/)：层级数据量大时应拆成可管理区块，支持过滤、展开/折叠和按需加载，而不是一次铺满所有深层节点。
- [SAP Fiori table features](https://experience.sap.com/fiori-design-web/table-features-sap-fiori-elements/)：批量操作使用行首选择框、全选和明确工具栏动作；选择本身不应偷偷执行写操作。
- [W3C WCAG 2.2 target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced)：本页关键勾选与操作目标按至少 48×48 设计，且状态同时用文字/图标表达，方便年长员工和触屏操作。

## 八、上线门禁与 UAT

以下条件未完成前，不得将本功能标记为「全链路已上线」，不得仅凭页面能跳转就开放公司生产写权限：

- 目标 PostgreSQL 从实际起点版本迁移，Flyway 校验和历史数据对账通过；
- 真实多销售订单、多产品、多层 BOM、同货多路径的联合分析与批量提交验证；
- BUY/SUBCONTRACT 从 action 到申请、订单、分批收货、部分 IQC `PASS/FAIL`、红冲/退货和物料齐套刷新的 HTTP 端到端；
- MAKE 从草稿、批准、预留、领料、执行段、分批报工 `fqty`、分批成品入库 `iqty`到销售分配/发运的端到端；
- 每一环的正向、撤回、红冲、重试和并发冲突不会造成超量、重复或断链；
- 生产计划员、生产主管、车间、采购、委外、仓库、质量和销售的对象范围/职责分离 UAT；
- 移动端、平板、键盘、读屏、大数据量性能、打印/导出、备份恢复和回滚演练。

验收结论必须明确区分「源码候选」「定向自动化」「真实 HTTP/数据库」「浏览器岗位 UAT」和「生产可上线」，不能用前一层证据替代后一层。
