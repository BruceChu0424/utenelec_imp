## 一、设计决策与理由

### 1. 预留为什么是独立台账，而不是在 stock_balances 上加一列

| 方案 | 否决理由 |
|---|---|
| `stock_balances.reserved_qty` 汇总列 | 只存总数，不知道"这批预留是谁的"，无法支撑：按订单行回写可发货量、驳回时精确释放、订单详情页展示预留构成；且违反"流水可重放"原则，对不上账时无法溯源 |
| 挂在 sales_order_items 上一个数 | 只有订单视角，没有仓库/货品视角，算不出"这个仓这个货还剩多少可卖" |

独立台账 `stock_reservations` 一行 = 一笔预留（谁订的、什么货、哪个仓、多少、消耗/释放了多少），两个视角都能从它聚合，且每笔变化可审计。

### 2. 消耗与释放为什么分两列（consumed_qty / released_qty）

预留的离场只有两条路：**发了货**（消耗，使命达成）和**不要了**（释放，改量/取消/驳回）。分开记才能回答"这单是发了还是退了"，审计和报表都要这个区分。生效量恒为 `qty − consumed − released`，CHECK 约束保证不超。

### 3. warehouse_id 为什么允许 NULL（全局预留）

下单审核时销售还没决定从哪个仓出货，但此时就必须占用库存防超卖。NULL = 占全局可用量；出货开单选定仓库后改绑具体仓。代价是可用量视图里全局预留在每个仓都保守扣减（任何仓都不能把被订的货再卖一次），聚合"全部仓"口径时 Service 需单独处理只扣一次。这是 SOP 开放问题 2 的落地，若老板决定"预留必须指定仓"，把列改 NOT NULL 即可，台账结构不变。

### 4. 数量为什么一律基本单位

`stock_balances.qty` / `stock_movements.qty` 都是基本单位量（已乘 unit_rate）。预留要直接和余额相减，必须同口径，换算在创建预留时一次完成。订单行上的 `reserved_qty/planned_qty/produced_qty` 则沿用行单位（和 qty/shipped_qty 同族），两侧换算由 Service 负责，互不混淆。

### 5. 合并生产为什么用新表而不是复用 sales_order_item_id

`production_plan_items.sales_order_item_id` 是老库单值软关联（一个计划行只挂一个订单），表达不了"两个订单的同产品合并到一张计划单"。新表 `plan_order_item_links` 多对多，还顺带承载三量回写（allocated/produced/inbound）和补产标记。老字段保留只做迁移溯源，新业务一律走新表。

### 6. chain_status 为什么是派生列而不是状态机表

行状态完全由四个数量（qty / reserved / planned / produced / shipped）推导，独立状态机会与数量漂移。存派生列只为列表筛选和工作台置顶排序（索引 `idx_soi_chain`），Service 在每次数量回写后重算，权威来源永远是数量本身。

## 二、表结构速览

### stock_reservations（库存软预留台账）

| 列 | 类型 | 说明 |
|---|---|---|
| order_item_id | UUID | → sales_order_items.id（跨模块逻辑 FK，契约 §一不建 REFERENCES） |
| goods_id / color_id / warehouse_id | UUID | 主档真 FK；warehouse NULL = 全局预留 |
| qty | NUMERIC(18,4) | 预留量（基本单位），CHECK > 0 |
| consumed_qty | NUMERIC(18,4) | 已转出库消耗 |
| released_qty | NUMERIC(18,4) | 已释放（改量/取消/驳回） |
| status | SMALLINT | 0 生效 / 1 已完结（Service 派生） |
| source | SMALLINT | 0 下单现货 / 1 生产入库 |
| source_doc_type / source_doc_id | — | 产生预留的单据溯源 |

### plan_order_item_links（计划明细 × 订单明细，多对多）

| 列 | 说明 |
|---|---|
| plan_item_id | → production_plan_items.id（同模块真 FK） |
| order_item_id | → sales_order_items.id（逻辑 FK） |
| allocated_qty | 排产分摊量（行单位） |
| produced_qty / inbound_qty | 报工 / 入库回写 |
| source | 0 正常排产 / 1 补产 |

幂等：`uq_pol_pair` 部分唯一索引（未删除行 计划行×订单行 唯一），同 V87/V88 防重复规则。

### sales_order_items 新增 4 列

`reserved_qty`（可发货量）· `planned_qty`（已排产）· `produced_qty`（已完工入库）· `chain_status`（0 未启动/1 部分预留/2 待排产/3 待物料/4 已排产/5 生产中/6 部分完工/7 可发货/8 部分发货/9 已发货/-1 已取消）

### v_stock_available（可用库存统一视图）

`available_qty = on_hand_qty − Σ生效预留`，仓+货+色 粒度。下单校验、排产、出货校验**只准读这个视图**。

## 四、自检清单（Service 实现后跑）

1. 两并发审核同货同仓各要 80/库存 100 → 一过一绝，可用量不为负。
2. 审核→出货审核→反审出货→反审订单，全链路后 stock_reservations 无残留生效行、stock_balances 回到初始。
3. 合并生产（2 订单 × 同货）→ 拆单出货 × 2，两订单行 reserved/shipped 各自正确。
4. 报 150 合格 120 → 补产 links(source=1) 生成、订单行 produced=120、chain_status=6。
5. 驳回出货单 → 预留释放量 = 驳回量，可用量回升，订单行回 7→4/6。
6. 全局预留（NULL 仓）下，v_stock_available 每个仓都扣减；改绑仓后只扣该仓。
