界面上的数字只有两种，**选错形态就是 bug**。挑形态前先回答一个问题：

> 这个数字变大的时候，是「有人在等我干活」，还是「这里东西多了」？

---

## 一、两种呈现形态

### 1. 通知数量徽章 `UtenNotificationBadge`（醒目 / 告警色）

只给 **「需要我处理、不处理会出事」** 的入口：

待审 · 待确认 · 待收货 · 待出库 · 待检 · 被驳回 · 超期 · 异常。

- 用户看见它就应该点进去干活。
- **0 → 整个不渲染**（不留灰色的 `0`，不占位）。
- `null`（仍在加载 / 读取失败）同样不渲染——不把「未知」伪装成真实 0。
- 挂在 `UtenHubCard.badge` 槽位（右上角浮层），或分段标签的徽章位
  （`UtenSegmentBadgeLabel` + `UtenSegmentCountForm.actionable`，见 §四·分段标签）。
- **会被上层容器逐级累加**（见 §三）。

### 2. 括号数字 `UtenCountSuffix`（中性 / 不抢眼）

给 **「有多少条、供我掂量」** 的入口：

分段标签 · 我的某某 · 历史 / 记录 · 一切浏览型集合。

> **草稿 2026-09-11 起不在此列**，改走红色徽章并参与累加，见 §草稿。

- 直接写进标签：`等待下达车间 (46)`、`采购收货 (2)`。
- 卡片上 **0 → 不渲染**（`标题 (0)` 只是噪声）；
  **分段标签可以显示 `(0)`** 保持队形（传 `hideWhenZero: false`）。
- 挂在 `UtenHubCard.labelSuffix` 槽位（标题文字右侧，随标题一起换行），
  或分段标签的计数位（`UtenSegmentBadgeLabel` 的**默认**形态）。
- **永不进上层累加**。

> 同一语义的入口，全平台必须用同一种形态。草稿在哪个模块都是红色徽章；
> 「待退回供应商」在采购和委外都是红色徽章。

### 反例

| 写法 | 为什么错 |
|---|---|
| 报表卡挂红徽章显示「本月 320 行」 | 报表不需要我处理，红色是在喊狼来了 |
| 基础资料卡显示「货品 5231」 | 主档行数不是待办，也不是需要掂量的工作量 |
| 待审单据写成 `订货审批 (7)` | 该喊的时候不喊，用户会漏掉审批 |
| 徽章显示灰色 `0` | 占视觉预算却不传递信息 |

## 二、什么绝不挂数字

- **报表 / 查询 / 分析类卡片**（销售报表、仓库报表、钱流 10 张报表、物料反查、链路健康）。
- **基础资料主档**（货品 / 模具 / 客户 / 供应商 / 颜色 / 单位 / 币种 / 仓库 / 账户 / 付款方式 / 结算方式）——
  行数不是待办，基础资料 hub 恒 0 徽章是**设计结论**，不是遗漏。
- **历史 / 只读专页**（委外成品退货单历史、委外损耗单历史、历史 BOM 子件发料、品质检测记录）。

## 三、外层累加内层

```
TodoEntry（入口）
  → TodoModule（hub 卡 / 工作台模块卡）= 该容器内全部入口徽章之和
    → 导航 Tab 总数                     = 全部模块之和
```

三条硬规则：

1. **只有通知数量徽章参与累加。** 括号数字（浏览型计数）永远不进。
   草稿是**红色徽章**，参与累加（2026-09-11 起，见 §草稿）。
2. **同一件活只能被计一次。** 父层按「入口」去重；两个入口指向同一批单据时，
   只让其中一个登记进注册表，另一个在语义标签/副标题里说明「已计入 xxx」。
3. **累加只有一处实现。** 全部登记在 `lib/shared/badges/todo_badge_registry.dart`，
   由 `todoModuleCountProvider` / `todoTotalCountProvider` 求和。
   **不要在 hub 页或工作台里手写加法**——新增入口只改注册表。

已登记的切片（故意不重复登记，避免双计）：

| 入口 | 为什么不单独登记 |
|---|---|
| 钱流「销售订单修改」 | 与「销售订单财务确认」是同一批单据的两个队列切片，累加只认总数一次 |
| 仓库三张任务中心卡的内部分段 | 卡面角标已是分段之和，分段本身不再登记 |
| 采购「采购申请」 | 待处理量已由「采购任务中心 · 待分解」计入 |
| 销售「客户零星发货」草稿 | 与「销售出货」同属 `sales_shipments`，且 `/sales/shipments` 列表本就含这批单 |
| 仓库 `stockTransfer` / `stockCheck` 切片 | 模块累加用 `stockDocument` 整表合计；再把两个切片加进去就是同一张单数两遍（`DraftCounts.sumOf` 里有 assert 挡住） |

## 草稿（2026-09-11 口径反转）

**结论：草稿走红色徽章，并逐级累加到 hub 卡与工作台模块卡。**

### 为什么改

本文件 2026-09-11 上午立的规则是「草稿 = 浏览型计数，走中性括号，永不累加」，
理由是「草稿是我自己没写完的东西，没人在等它」。**当日用户推翻了这条**，原话：

> 一些新建的地方右上角不是有草稿按钮嘛，里面的数字我想要的是改成我们自己写的通知徽章，
> 就是红色的背景里面白色的数字……然后在外面也要显示……最外面的工作台销售管理卡片
> 也要显示里面的全部累计。

产品理由成立：草稿不是「可看可不看的集合」，是**本人开了头却没交出去的活**。
它不出现在任何待办队列里，如果连个红点都没有，就只能靠人自己记得——这正是它该被
喊出来的原因。所以草稿在本文件的分类里从「浏览型」移到「待办型」。

### 落地

| 位置 | 形态 |
|---|---|
| 新建页顶栏「草稿」按钮 | 文案右侧红底白字徽章（`UtenAppBarActionButton.badge`） |
| hub 单据卡 | `UtenDraftBadge`。该卡**没有**其它待办徽章 → 放 `UtenHubCard.badge`（右上角）；**已有**待办徽章 → 草稿徽章退到 `labelSuffix`（标题右侧行内，仍是红色），一个槽位不塞两个红圆点 |
| hub 页顶栏 | 本模块累计（`todoModuleCount(TodoModule.x)`，已含草稿） |
| 工作台模块卡 / 导航 Tab | 自动包含——`module_badge_sum` 早已委托注册表，注册表加了 `TodoEntry.*Drafts` 就生效，**页面里不要手写加法** |

组件：`lib/components/feedback/uten_draft_badge.dart`（原 `UtenDraftCountSuffix` 已删除）。
注册：`TodoEntry.salesDrafts` / `purchaseDrafts` / `subcontractDrafts` / `financeDrafts` /
`warehouseDrafts` / `productionDrafts`，数字来自 `draftCountsProvider` 的模块切片求和
（`DraftCounts.sumOf`）。

### 唯一要小心的地方

仓库模块累加**只能用 `DraftDocKind.stockDocument`（整表合计）**，
不能再把 `stockTransfer` / `stockCheck` 切片加进去——它们是同一张表的 doc_type 切片，
一起加就是双计。`DraftCounts.sumOf` 里有 assert 兜底。

## 四之二、红徽章只数「轮到本部门动手」的档（2026-09-11 收口）

用户当天两条反馈同源：

- 「采购任务工作台『财务已通过』的数量，不合计在采购任务中心的通知数量合计里面」；
- 「仓库·品质部检查结果，如果是『等待检查』这个不计入消息累计，只有检查结束后通知」。

**口径**：同一条链上的阶段，凡是「球在别人手上」的，页内照常以中性计数呈现
（让人看得见进度），但**不进红徽章、不参与上卷**。已落地三处：

| 计数 | 计入 | 不计入 | 实现 |
| --- | --- | --- | --- |
| 采购/委外任务中心 | 申请待分解 `WAITING_ORDER`、财务驳回 `FINANCE_REJECTED` | 等待财务审核 `ORDER_PENDING_APPROVAL`、财务已通过 `FINANCE_APPROVED`、已完成 | `FulfillmentWorkbenchQueryService.countPending` |
| 仓库 · 品质部检查结果 | 待入库、需退回 | 等待检查结果 `WAITING_INSPECTION`、已完结 | `WarehouseQualityResultService.pendingTypeCounts` |

自检方法：**hub 卡上的红数字 = 页内各红色分段之和**。对不上就是某个
browsing 档漏进了合计（前端 `_stageCountForm` 与后端 count 必须同时改）。

## 四之三、徽章数在刷新期间不许清零

`todo_badge_registry._async` 取值一律 `valueOrNull ?? 0`，**不写
`loading: () => 0`**。否则 60s 自失效轮询每转一圈就把徽章打回 0 再弹回来
（用户 2026-09-11：「徽章会突然消失下又出现，然后又消失又出现」）。

配套两条硬性要求：

1. 喂给注册表的计数 provider **一律常驻**（不 `autoDispose`）。autoDispose 的
   provider 一离开页面就销毁，回来没有「上一次」可留，表现为「点进去要等一会
   徽章才出现」，而采购那种常驻 StateNotifier 点进去就有。
2. 常驻后**必须自带轮询**（`Timer(60s, ref.invalidateSelf)` + `onDispose` 取消），
   否则值会停在首次加载那一刻。没人看时定时器不再续期，不会空转发请求。

回归用例：`test/shared/badges/todo_badge_async_retention_test.dart`。

## 四之四、草稿计数：一次往返 + 存盘即刷新 + 进工作台（2026-09-11 晚）

用户三条反馈，三个不同的坑：

**① 「新建销售订货单里明明有草稿，要等十几秒红色徽章才出来」**
不是 21 条 count 慢，是**最多 63 次往返**：`DocumentDraftCountQueryService.counts`
逐类型建 `DraftScopeAccessPolicy`，而 `OwnerVisibility.evaluate` 对非超管每次都要查
「交接继承」+「授权归属人」两条 SQL。现在归属范围**按 scope 串去重**只算一次
（21 个类型只有 6 个 scope），21 条 count 合并成一条 `SELECT (子查询), …`。
闸门用例 `DocumentDraftCountSqlContractTest#allDraftCountsAreFetchedInASingleRoundTrip`
——退回逐条会直接炸。

> 写新的 `/counts` 端点时按这条自检：**范围解析次数 ≤ 不同 scope 数，SQL 条数 = 1**。

**② 「我没审核、退出了，草稿就该立马记录并显示」**
失效点挂在 `bumpListRefresh`——全部单据编辑页保存/审核/删除成功后的唯一公共钩子，
一处覆盖 7 个编辑页。不走该钩子的页面（生产计划单 / 生产日报用 `context.replace`
直达详情）各自补一次 `ref.invalidate(draftCountsProvider)`。
漏一个页面，用户就要等下一轮 60 秒轮询。

**③ 「工作台 销售管理 那里没有显示」**
`module_badge_sum` 里 `WorkbenchBadgeKind.sales` 被写死成**单个入口** `salesAttention`，
不是整模块累计，销售草稿因此永远进不了工作台（hub 顶栏看得到、工作台看不到）。

> 规矩：**模块在工作台只有一张卡 → 用 `todoModuleCount(模块)`；有多张卡 → 用
> `sumTodoEntries([...])` 显式列出该卡负责的入口**，保证「各卡之和 = 模块累计」
> 且互不重叠。「生产管理」卡即属后者（车间任务另有一张卡，不能算进来）。
> 回归用例 `test/features/dashboard/workbench_card_badge_drafts_test.dart`。

## 五、后端计数端点的规矩

新增/扩展计数接口时：

- **一个模块一个 `/counts`**，返回一个小 record；不要一张卡一个端点。
  跨模块草稿走唯一的 `GET /api/documents/drafts/count`（21 类一次返回）。
- 必须复用该模块的 `DocumentAccessPolicy.nativeReadScope`，与列表页同口径。
- **无权限时返回 0 且不查库**（权限自卫），前端同样不渲染——两层一致。
- 必须廉价：走索引的 `count(*)`，不做 N+1 行级展开。
- 前端轮询统一 60s，并登记进登录/刷新时的失效清单
  （`invalidateWorkbenchBadgeCaches` / `rehydrateGlobalState`）。
