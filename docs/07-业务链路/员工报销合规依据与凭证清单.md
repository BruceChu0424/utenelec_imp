# 员工报销合规依据与凭证清单

核对日期：2026-09-19。适用范围为中国大陆普通企业员工费用报销；所属行业、纳税人身份、地方政策和具体业务的特殊规定由财务另行核实。岗位操作见[员工报销全链路 SOP](员工报销全链路-SOP.md)，软件决策见[ADR-094](../99-决策记录-ADR/ADR-094-报销链路完整化.md)。

本专题区分四件事：公司批准向员工报销、会计核算、企业所得税税前扣除、增值税进项税额抵扣。报销审批通过、金额勾稽一致或 OCR 识别成功，不自动得出后三项结论。财务应按真实业务及适用制度分别判断，系统不为凭证盖上“国家合规认证”。

## 二、凭证准备清单

资料以证明业务和付款为目的，避免为了“看起来齐全”无差别收集身份证、银行卡等敏感信息。证据含个人信息时，限定经办、财务和经授权档案人员访问；通知、汇总和打印首页不展示完整证件号码。

| 场景 | 员工提交什么 | 财务核对什么 |
|---|---|---|
| 一般办公、通讯、培训等支出 | 业务事由、发生日期、金额、相应发票原件；需要时附订单、合同、交付或付款材料 | 业务关联、抬头及税号适用性、金额、重复报销、原件来源和实际支付 |
| 差旅住宿与交通 | 出差人员、事由、起止日期或行程；住宿发票、电子客票或行程单及必要的订单、支付凭据 | 行程与业务是否一致；个人实名客票按其适用规则审核，不硬改成公司抬头；限额依据公司制度 |
| 餐饮、业务招待 | 发票、事由、日期；业务招待另写业务对象和人数等必要说明 | 区分业务招待、会议、员工福利等真实用途；报销金额不等于可税前扣除金额，税务调整由财务处理 |
| 财政票据等合法非发票凭证 | 原始财政票据或其他外部凭证及支出依据 | 凭证种类、出具主体和适用业务；不能强行生成8位或20位“发票号码” |
| 依法无需税务登记的单位、符合条件的小额零星个人业务 | 符合规定的收款凭证和内部凭证；必要的身份、项目、金额和付款证明 | 严格核实公告2018年第28号第九条适用条件。不能只按“金额不大”认定，也不在应用内固定一个永久有效的免票金额 |
| 暂缺票、票据遗失或开具错误 | 真实原因、待补材料和业务/支付证明；按要求补开、换开或补充证明 | 公司是否允许进入审核、还缺哪些材料、补正期限及税务处理。允许提交说明不代表自动满足税前扣除条件 |
| 特殊原因无法补开、换开 | 由财务按适用条款列明缺口及证明文件 | 公告2018年第28号第十四条有特定原因及资料要求，普通“商家不开票”说明不能代替 |

电子原件应从开票方或官方渠道取得并保持原字节，保留原文件名、格式及来源。数电票按取得的原生文件保存；有结构化 XML 或其他附加数据时一并交财务。扫描件用于阅读和识别，不能替代原电子凭证。系统不支持的格式由财务先按既有受控档案办法保管，并在报销备注中记录可检索的凭证位置，禁止把文件改扩展名绕过安全校验。

报销额可以小于票面金额，例如部分由公司承担；须说明差额和费用归属。不能简单要求“所有票面总额永远等于报销总额”，也不能在没有分摊链路的情况下允许同一张票在多张报销单中反复报销。退款、红字发票和冲销交财务按原单引用处理，不把已付款报销单直接改回草稿。

## 三、人工核验和归档

财务按凭证类型使用官方渠道查验，常规发票可由[全国增值税发票查验平台](https://inv-veri.chinatax.gov.cn/)或税务数字账户核验。人工核验记录至少应能回答“谁在何时核对了哪份原件、依据是什么、异常如何处理”。OCR 置信度、20位格式和金额加总不是上述证据。

系统报销域号码查重只能覆盖实际登记在本域的记录。财务还须核对普通费用单、采购付款、预付款及其他账套是否重复入账；现有号码索引不能替代跨系统去重或官方入账标识。已读通知只影响消息阅读状态，不能当作审批、付款或档案交接证据。

每张报销单的归档包应能相互检索：公司内部报销展示单、原始凭证及元数据、必要业务/付款材料、审核意见与流转记录、关联 YF 财务费用单、会计记账凭证及档号。实际会计凭证张数由会计清点；附件文件数量、登记票据数量、PDF 页数必须分开。

财务按单位档案制度编制保管与移交清册，完成完整性核对、可读性检查和恢复演练。未经单套电子归档条件及部署验收确认，继续执行受控的纸电配套保存流程；不得因点击了“打印”便删除电子原件。

## 四、开源图片识别选型

| 项目 | 官方来源与许可证 | 本项目取舍 |
|---|---|---|
| PaddleOCR | [官方仓库](https://github.com/PaddlePaddle/PaddleOCR)、[安装文档](https://www.paddleocr.ai/main/en/version3.x/installation.html)，Apache-2.0 | 已有 `InvoiceOcrClient` / `PaddleOcrClient` 及 `deploy/ocr/` 侧车基础。优先本地部署，图片交侧车识字，Java 解析建议字段，员工核对后保存。 |
| RapidOCR | [官方仓库](https://github.com/RapidAI/RapidOCR)、[许可证](https://github.com/RapidAI/RapidOCR/blob/main/LICENSE)，Apache-2.0 | 可作为 ONNX 推理部署方案评估；不是本轮已装配的运行时。仓库注明模型与工程代码的权利归属，分发时须同时核查实际权重和依赖许可证。 |

开源许可不代表零运行成本；本地方案仍有计算、存储、模型下载和维护成本。锁定经验证的运行时、依赖和模型版本，保留许可证及必要声明；启动时不得把真实票据用于联网调试。部署地址属于运维配置，不开放给普通报销人自由填写。未启用、超时或识别失败时明确提示并允许手工录入，绝不生成看似成功的票面数据。

图片识别只负责降低录入成本。结构化电子凭证原件优先保存，OCR 不替代官方数据标准解析、电子签名验证、发票查验、税额抵扣判断或档案验收。
