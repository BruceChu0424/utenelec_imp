# V549 附件清空主档保护集

不新增表、权限或金额字段；清理分类仍为 CLEAR 266 张、PRESERVE 96 张；只 `CREATE OR REPLACE` 一个函数（头部「当前正式目录」版本/计数由迁移索引统一维护）。

## 解决的问题

2026-09-10 审计 C14 H1-3：`fn_business_attachment_reset_blockers()` 的保护集自 [V537](135-V537业务附件清理完成证明.md) / [V539](137-V539已执行迁移兼容与附件证明前滚.md) 起只按「人事」硬编码（`EMPLOYEE` / `EMPLOYEE_CONTRACT`），而货品主档附件（`owner_type = GOODS`：产品图片、图纸、规格书）所属的 `goods` 表在 `business_data_reset()` 中是 PRESERVE。清空流程自 2026-09-09 起会在清库前自动把「阻塞项」标删并物理删除（[ADR-067 §7](../99-决策记录-ADR/ADR-067-工作台系统测试区与业务数据一键清空.md)）——若不扩保护集，货品主档的图片/图纸会随测试清空被物理删除且不再有人工确认清单，与主档保留语义冲突。

## 变更

- `fn_business_attachment_reset_blockers()`：函数体与 V539 逐字一致，仅两处 `upper(btrim(owner_type)) NOT IN (...)`（附件 CTE 与上传会话 CTE）改为 `('EMPLOYEE','EMPLOYEE_CONTRACT','GOODS')`。可重复执行。
- Java `BusinessAttachmentResetPreparation.PROTECTED_OWNER_TYPES` 持同一集合：预览/计数/入队附件/入队会话四处 SQL 以 CSV 绑定参数传入（`<> ALL(string_to_array(?, ','))`），不拼接；清空前置分类 `unpurgeableBlockers` 同样按它过滤。两侧必须同步维护，`BusinessAttachmentResetCompletionPostgresTest` 解析迁移文本与 Java 常量逐项比对。
- `business_data_reset()` 不改：它只调用该函数计数，自然沿用新保护集。

## 影响与边界

- 已上传的货品图片/图纸在测试清空后保留（预期，与 goods 主档 PRESERVE 一致）；此前会被自动清理物理删除。
- 保护集判定用 `upper(btrim(owner_type))`：`' goods '` 等历史大小写/空白写法同样受保护；提供方（internal/local/oss/legacy_unknown）不影响保护。
- 其它 owner（销售/采购/委外/生产/仓库/财务单据等）仍按原规则计为阻塞并由清空自动清理；自动清理消化不了的阻塞（oss/legacy_unknown、`LEGACY_UNVERIFIED`、凭证未到期、删除失败达阈值）在排水前 409。
- psql 停机版 `server/ops/reset_business_data.sql` 内嵌的证明函数保护集须与本迁移同步（版本元组门由统一发布记录维护）。

## 验证

- `BusinessAttachmentResetCompletionPostgresTest`：V537 → V539 → V549 依次执行后，`GOODS`（含 `' goods '`、oss 提供方、NULL 版本）附件与 GOODS 上传会话不计阻塞、清空校验后仍为 `CLEAN`；原 SALES_ORDER / EMPLOYEE 断言全部保持；V549 文本中的保护集 == `PROTECTED_OWNER_TYPES`。
- `BusinessDataResetServicePostgresTest`：附件自动清理 2→1→0 循环（prepare 两次、结果回显物理删除文件数）与排水前 409（不预览、不 prepare、闸门保持 IDLE）。
