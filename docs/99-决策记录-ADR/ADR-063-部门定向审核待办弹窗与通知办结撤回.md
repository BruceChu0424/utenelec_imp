# ADR-063：部门定向审核待办弹窗与通知办结撤回

## 2026-09-07 生效修订

以下修订取代本文早期收件台与仅 view 的接收口径，其余历史决定保留溯源：

1. 常用功能待审收件台退役，前后端页面和聚合 API 删除，V493 停用权限码/surface并保留历史授权。
   `/reviews/inbox` 仅兼容跳回 `/dashboard`。跨域弹窗回工作台，单域及单条进入真实领域任务页，
   新增事件不得落到一个没有对应业务的空收件台。
2. `ReviewNoticeAudience` 统一实时资格：主职或兼职部门祖先命中且具备 notice:read、目标页 view
   与该节点实际动作权限；超管不绕过部门，仅 view 不弹。计划新订单需 create，委外前置排产需
   route/generate；IQC需handle，仓库入库/发料用各自confirm/stock_in/issue动作。审批端依然允许
   中央明确个人加授的部门外审批人，其不会自动收到财务弹窗，此处不收回既有业务授权。
3. 登录事件先按资格筛选后做数据库分页；到达查询过滤旧部门卡仍推进游标；心跳状态批量读取，
   办结、收权、调岗、稍后和删除均撤卡。历史无aggregate通知仅作信息，不再变成永不办结的弹卡。
4. 登录检查使用会话代际与可取消定时器，登出/切换身份后迟到请求不得展示旧账号任务；已打开的
   对话框也随身份更换关闭。心跳单飞，超过50条按服务端上限分批读取后再合并处理。

当前路由/目录与验证口径见[权限体系总设计](../05-架构/权限体系总设计.md)。

## 背景与决策

业务待办（销售下单待财务确认、订货待财务审批、到货待检、订单全部完工可发货等）
此前只有普通顶部条通知：无操作按钮、无认领状态、办结后通知残留。用户要求：
**「部门（主职或兼职）且负责该块」的人**收到可操作弹窗——只有部门或只有权限都不推。

四项决策：

1. **兼职部门模型**（V459 `employee_secondary_departments`）：一人多部门归属的
   唯一组织表达。权限合成把各兼职部门链（含祖先递归）并入并集；行级变更由触发器
   即时 bump `users.auth_version`（V135 机制，单人粒度不走全局 epoch）。
   **推送资格 = (主部门 ∈ 部门子树 OR 兼职部门 ∈ 部门子树) AND 持有职责权限码**，
   双条件缺一不可；「推送比审批严格」——部门外被点名加授者（ADR-027）仍可审但
   不收弹卡，要收弹卡给他兼职该部门。
2. **可操作审核卡 + 居中审核弹窗（2026-09-02 第二轮用户口径修订；2026-09-03
   第三轮修订：顶部条改纯显示）**：一个待审事件的三种提醒形态并存——通知中心
   条目（落库即有）、顶部通知条（**纯显示**：不带操作按钮与状态行，20s 自然
   收起——避免与居中弹窗重复的操作入口；`AppNotification` 的
   `actions`/`statusLine` 能力保留备用）、**居中审核弹窗**
   （`ReviewPendingDialog`，主交互）。居中弹窗单条=大卡、多条=紧凑列表，**高度
   随内容自适应、封顶 min(60% 屏高, 560px)**（多条内部滚动，不再接近全屏）；条目实时
   显示认领状态（「XX 正在审核」/「待处理」，30s 心跳），办结条目自动移除、清空
   自关；【去工作台处理】（2026-09-03 第四轮修订：不再直达单据详情）同域→
   该域任务工作台、跨域混合→待审收件台，单条也去工作台，点列表行去该行
   所属域工作台；后到待办并入已开弹窗（「一共有 N 项」），【稍后再看】全部
   snooze 15 分钟，右上 X 仅本次
   关闭。**每次登录检查**（`ReviewPendingLoginGate`，登录后 3s 拉
   `GET /notices/pending-reviews`：未办结+未稍后，重要度序）有则弹——「稍后再看」
   是唯一静默途径，X 关闭下次登录仍提醒（未办结就还该提醒）。
   这**修订 ADR-052 §2.3** 的边界：资格池待审事件允许居中弹窗，但 ADR-052 的
   前提由办结撤回（不再要求已解决的事）与认领状态展示（不再让多人盲目涌向同一
   单据）实质满足；七要素（事件来源/聚合 UUID/责任人池/业务时间/解决条件/主操作
   路由/角标真源）由 `ReviewNoticeCatalog` 注册表+aggregate 列+task_claims 承接。
   弹窗单例守卫防多事件叠窗（后到待办并入已开弹窗，收件台兜底）。
3. **办结撤回**：`notices` 增加 `aggregate_kind/aggregate_id/resolved_at/resolved_reason`
   （历史行全 NULL=永不撤回，零行为变化）。审核落点（确认/驳回/批准/整单检验结案/
   开立出货单）按 (kind,id) 一条 UPDATE 批量 resolve——全部接收人弹卡停止展示、
   收件台计数归零、通知中心灰显「已办结」（保留审计价值）。居中弹窗停留期间 30s
   心跳调 `GET /notices/pending-review-status` 做真态校验（办结条目自动移除/清空
   自关、他人认领显示「XX 正在审核」）；顶部条到达前也校验一次（已办结不弹）。
4. **「稍后再看」**（`notice_user_states.snoozed_until`）：服务端语义跨设备一致；
   未到期不出弹卡流（通知中心仍可见），到点未办结下次到达重弹；**点稍后或去审核
   同时置已读**（「已处理过这条提醒」）。已办结通知拒绝再 snooze。

## 交付边界

- **收件台**：`/reviews/inbox`（`review_inbox:view` 守卫，surface `reviews.inbox`，
  111 个）聚合各职责域待审数（notices 维度，与撤回自动联动）；工作台「常用功能」
  组有入口卡片。
- **已接线四线（P0）**：销售订单→财务确认（弹卡直达单据审核页+认领+确认/驳回撤回）、
  采购/委外订货→财务审批（case 聚合+批准/驳回撤回）、到货 IQC 待检（整单结案撤回）、
  订单累计入库满足订货量→通知负责销售「全部完成生产，可以发货」（归属人定向、
  无认领、开立出货单撤回）。其余业务线按 §五目录滚动接线（每线=注册表一行+发布点
  aggregate+落点 resolve+claim 登记）。
- **事件名不变**：全部复用既有 source_event 常量，`unread-count-by-source` 等
  统计口径不受影响。
- **实时性**：沿用 10s 到达轮询（方案 D9）；SSE 为后续独立批次（notice_arrival
  已预留替换入口）。登录检查为一次性拉取（每次登录会话一次，登出重登重新触发）。

## 已知遗留

- 通知中心列表仍是后端 500 条上限+前端一次性渲染；数据量持续增长时做 keyset
  分页化（独立批次）。
- IQC/采购审批的**审核页内认领**尚未接线（弹卡已显示认领状态；写入端只接了
  财务确认审核页）——按每线半天滚动补齐。
