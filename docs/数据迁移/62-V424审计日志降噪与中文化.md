# 62 · V424 审计日志降噪与中文化 / V425 全新开始（2026-08-29）

## 背景

审计中心两个突出问题：

1. **系统自动行为混进日志**。全表触发器覆盖（V396 一系）把通知机制自身的数据流
   （系统发布通知、用户已读状态、知悉确认、祝福回复）和后台管道表（事件发件箱、
   月度汇总、幂等指令表）全部记入 `audit_log`。这些行不是人在页面上的操作，
   却占了日志的大头，例如"财务审批通过"本来已有一条审批审计行，系统随后自动发布的
   站内通知又会额外产生多条 `notice_user_states` 触发行。
2. **内容英文且过于简短**。动作/表名/结果码多为英文（列表出现 "notice user states"
   这类兜底 humanize 文本），摘要只有"修改 · 销售订单"级别，看不出具体改了什么。

## V424 做了什么

`V424__audit_notice_and_system_noise_exclusion.sql` 删除以下表的审计触发器：

| 类别 | 表 | 理由 |
| --- | --- | --- |
| 通知机制 | `notices`、`notice_user_states`、`notice_acknowledgments`、`notice_blessings` | 系统发布/投递通知与阅读回执，非人工业务操作；管理员手工发布公告仍留 HTTP 请求覆盖行 |
| 系统管道 | `business_outbox`、`attachment_object_outbox` | 后台事件投递队列 |
| 物化汇总 | `account_flow_monthly_summaries` | 报表汇总数据，系统重建 |
| 幂等指令 | `production_daily_report_commands`、`production_fqc_release_commands`、`warehouse_arrival_registration_commands`、`production_material_analysis_commands` | 命令去重记录，与对应请求级审计行重复 |

- **人工操作不受影响**：所有业务表的触发器审计与 `UserOperationAuditInterceptor` 的
  HTTP 请求覆盖行完整保留。
- 历史已写入的上述触发行不回删，由保留策略自然到期清理。
- `AuditTriggerCoverageMigrationContractTest` 新增 `V424_SYSTEM_NOISE_EXCLUSIONS`
  登记；**今后再写 refresh_audit_trigger_coverage 全表扫描迁移时必须把这 11 张表
  加入排除清单**，否则触发器会被重新挂回。

## 配套的应用层中文化（不涉及数据库）

`AuditEventInterpreter`（服务端一次算好、随行下发）：

- **表名映射补全**：`TARGET_LABELS` 覆盖全部业务表 + 报表虚拟对象 + `user` 别名，
  未收录表名的英文兜底基本消失。
- **详细摘要**：数据库变更行摘要内联前两项字段变更，例如
  `修改销售订单 SO-2026-001：状态：草稿 → 已审核；备注：空 → 加急等 3 项变更`；
  失败操作末尾附中文原因。
- **changeSummary**（详情接口新字段）：逐字段中文变更明细，最多 6 项，
  超出提示去"数据变更"标签页看全量。
- **resultLabel**（列表/详情新字段）：结果码翻译（`bad_password`→密码错误、
  `rate_limited`→尝试过于频繁（已限流）、`success;mode=generated`→成功；方式：系统随机生成 等）。
- **导出动作细化**：`export_purchase_report`→导出采购报表。
- 值与字段可读化：布尔→是/否、空→空、UUID 截短、常见状态枚举翻译、列名中文字典。

## 2026-08-29 补充：用户操作显式留痕（修复降噪误伤）

V424 移除 notice 表触发器后，"任务认领/完成待办/移除通知"这类**用户手工操作**
也失去了带对象信息的记录（只剩泛化的请求行）。补充服务层显式审计，只记人工动作、
不记系统自动行为：

| 动作码 | 触发点 | 记录内容 |
| --- | --- | --- |
| `notice_publish` | 人工发布公告 | 通知标题 |
| `notice_acknowledge` | 确认收到（回执） | 通知标题 |
| `notice_todo_complete` | 完成工作台待办 | 通知标题 |
| `notice_bless` | 回复庆典祝福 | 通知标题 |
| `notice_delete` | 从我的列表移除通知 | 标题或"共 N 条" |
| `hr_task_claim/release/takeover` | HR 任务中心认领/释放/接管 | 任务类型 · 员工姓名 |
| `task_claim/release/takeover/force_release` | 通用任务软认领（ADR-023） | targetType/targetKey |

心跳续租（heartbeat）与自动已读不记录（噪音）。解释器同步补充上述动作的中文标签、
`/api/org/hr-tasks` 与 `/api/task-claims` 的路由/页面标签，以及
`/claim`、`/takeover`、`/force-release`、`/acknowledge`、`/batch-delete`
写请求的路径级动词（请求覆盖行不再显示成泛化的"新增/修改"）；
显式业务事件的 `targetId` 若为可读文本（通知标题、员工名、设置键值），
会作为对象名拼进摘要（路径/UUID/分号统计串除外）。

前端 `admin_audit_log_page.dart`：

- 详情概览重构为**叙事卡**：标题"这次操作做了什么" + 结果徽标；操作人（头像/账号/部门/职位）；
  何时/在哪/记录来源 chips；大字完整动作句（动作 + 对象 + 单号 + 关键变化）；
  操作对象行；"具体变更"升级为字段名 + 旧值胶囊 → 新值胶囊；
  排查线索卡（IP/耗时/接口/事件类型/数据库 ID 复制）。
- 列表底部新增保留策略提示（读 `/api/settings/public` 的
  `auditReceiptRetentionMonths`，即在线 + 归档总月数）。

## V425：审计日志全新开始

`V425__audit_log_fresh_start.sql` 按管理者要求清空全部审计记录并重置自增 ID：

```sql
TRUNCATE TABLE audit_log, audit_log_archive RESTART IDENTITY;
```

- 只动审计两张表（热表 + 冷归档），业务数据不受影响；新库/离线 bootstrap
  目标库本来就没有审计历史，TRUNCATE 为空操作。
- 清空后第一条审计记录（通常为每日保留任务的 `delete audit_retention` 行）
  获得 id=1，新格式（中文摘要/变更明细/结果翻译）从零积累。
- 查询侧对空表安全：`findMaxId()` 使用 `coalesce(max(id), 0)`。
- 各端本机操作回执是客户端本地数据，不受影响；清空后"核对本机回执"
  会提示未找到服务器记录，属预期行为。

## 保留策略（既有机制，本次未改动）

`AuditRetentionScheduler` 每天 03:17（Asia/Shanghai）执行两阶段清理：

1. `audit_log` 中超过在线保留期（`audit_hot_retention_months`，默认 6 个月）的行
   原子迁入 `audit_log_archive`；
2. 归档行超过归档保留期（`audit_archive_retention_months`，默认 30 个月）后彻底删除。

两项均可在系统设置中调整，改完即生效（无需重启）。手动脚本见 `server/ops/audit_retention.sql`，
完整口径见 [38-运维-审计与日志保留](38-运维-审计与日志保留.md)。
