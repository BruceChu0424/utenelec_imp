# 仓库选择范围与库存界面整改

## 业务边界与根因

本次按页面核查统一仓库任务中心、生产领料、内料仓领退料、销售出库、委外出仓、其它/产成品出库、到货登记、品质入库、成品登记/点收、即时库存和库存分析。前端与相关设计文档使用 `frontend-design`，保留 Uten 组件、既有数量来源及权限契约。

- 任务表按实物明细选择，旧导航却先按来源单去重并丢失明细 ID；目标页重载整单，部分命令实际执行整单。
- 内料仓 fulfil 接收明细子集后无条件将申请置为 DONE，未选行从待办消失。
- 品质结果的批量入库页原有精确切片能力，统一任务投影却漏登记其批量操作类型。
- 即时库存是货品与颜色的跨仓汇总；库位、所属仓库来自货品主档，不能将主档编辑冒充实物调仓。
- 库存分析指标使用不同长度标签/说明，卡片随内容独立撑高。

## 实施结果

| 页面/路径 | 调整与保留的边界 |
|---|---|
| 仓库任务列表 | 多选保留明细身份；右下已选数量沿用共享表格；双击也传精确范围；详情投影限定完整 rowKey |
| 生产领料 | 请求和父回执指纹包含 itemIds，只发所选行的剩余量；未选行继续待领 |

| 内料仓审核 | 保留周期盘点与仓库复盘审核；旧通知/收藏深链映射至新方向 |

| 品质入库 | 启用多选，复用 receipts 与 inspectionItemIds 的精确批量登记 |
| 成品最终点收 | itemIds 进入批量指纹；选中行点收，未选量沿已有确认/余量单谱系继续待点收 |

| 待识别物料建议 | 以申请、版本和原建议序号保留所选范围；只显示所选建议，未选齐整份配置申请时不能隐式配置未选建议 |

| 库存分析 | 同行等宽等高指标区，窄屏与大字号换行，键盘可操作；保留服务端数字与筛选行为 |
| 徽章与通知 | pendingIssue 归出库，pendingReturn 归入库；按未办理行计数，兼容入口不重复汇总；盘点审核保持独立事实 |
| 工作台待办摘要 | 原生产领料/退料摘要补入相应内料仓事实数；保持摘要原有业务范围，不直接套用仓库模块总数 |
| 表头默认列序 | 单据类表格先状态、再单号，随后按业务展示车间/往来、货品名称/编码/颜色、数量和仓库；统一待办与历史表同步替换旧的状态/货品固定前缀，保留其它列宽、显隐及相对自定义顺序。到货、品质、普通出入库、委外、领退料和成品点收逐表检查；没有单据状态的库存事实表保留货品身份优先 |

仍受整单状态或财务约束的单据，不能把未选行改为零、删除或仅在界面隐藏后提交整单。委外材料出库已有分批业务契约，因此二次复查继续完成其原子切片、预留守恒和历史谱系，不再以拒绝子集替代该能力。

## 二次根因复查

按用户复查要求重新沿“任务选择—路由—草稿—编辑—确认—请求—库存流水—回执—历史/徽章”逐段追踪，确认并修复以下独立缺口：

- 草稿原先只按整张单号匹配，A 明细草稿会使同单未选 B 也被视为草稿。现在按实际 item/inspection/lot 身份匹配；显式空、重复、矛盾范围不能退化整单。
- 成品点收恢复曾先采用草稿 targets 再验证自己，旧整单草稿可把入口 A 换成 B。恢复现在先锁定原入口来源集合，完整校验通过后才采用草稿输入。
- 普通出入库批页及单页缺少贯穿读取、确认框、写请求和回执的同一身份绑定。现在账号、代操作、只读、权限、服务器或来源变化均使旧页面失效；A→B→A 也不复活，迟到响应不能回填。
- 末轮继续逐页核对仓库 13 个草稿提交入口。旧逻辑在保存草稿后检查页面身份，却在设备审计等待完成后才读取网络身份，仍可能借用新会话。各页现在复用同一请求范围捕获，先同步锁住原选择和输入，再把确认、预读、原请求、附件及回填绑定到原会话；权限边界通过共用可选粘性监听绑定，不改变授权。捕获状态暂不可用可保留输入后重试，真正跨身份/权限边界的旧编辑器不能复活。
- 即时库存及主档行内保存原先在进入 PATCH 前检查、返回后检查，中间设备审计/凭证读取等待可采用新身份。共享写保护绑定当前会话意图及请求身份，覆盖即时库存、平面主档和分类主档共用明细区，包含客户、供应商、货品和模具。
- 领退料未知结果原先允许修改内容生成新键，跨单恢复也只认本机进度。现在写前保存冻结命令和原键，未知结果只原样核对；批次从实办事实恢复，已完成命令不会重复办理。领料和退料都直接使用统一表格与一次确认，补录作为可选折叠区保留。
- 首次材料用途恢复原先可能显示默认用途却提交已存用途。现在恢复原选择后重新读取影响和版本，必须再次明确确认；盘点固定版本约束继续保留，未知命令不重新组装用途。
- 内料仓历史原先把实办数量配到建议仓。历史改按不可变 posting 展示实际仓和实办数量，一原行分两仓不会重复申请量；待办/徽章/通知只计算未办原行的建议范围。
- 成品点收及内料仓历史回执原先在重放时绕过当前对象范围检查。现在回放前重验当前读取/车间范围，保留旧版本、已完结对象正常核对回执的能力，不借此重做库存动作。

二次复查还对未知批次恢复补充精确集合校验：冻结命令行与有当前实办事实的 `priorHandledLineIds` 必须互斥并恰好覆盖原选择。旧格式没有该依据时必须自身覆盖完整选择。仅有本机 `confirmed`、当前明细却未办，改为保留原键重新核对，不会提前宣称全部完成。

末轮交叉审查继续发现批量恢复的协调问题：同批 A 已提交且结果未知、B 尚未提交，B 随后取消或当前读取失败，页面原先整体加载失败，导致仍可读取的 A 无法按原键核对。处理要求按原来源分别判断可读取性和可办理性；新命令仍需完整前置校验，历史未知命令独立核对，不能因 B 失败丢失 A，也不能把 B 隐式移出原选择、当作完成或重新派发。当前不可读来源不得使用旧敏感快照回填显示或绕过授权。

真实认证与草稿初始化回归还复现了返回任务中心时的 Riverpod 3.4.3 菱形依赖恢复异常，与[上游问题 4882](https://github.com/rrousselGit/riverpod/issues/4882)一致。按仍开放的[上游 PR 4884](https://github.com/rrousselGit/riverpod/pull/4884)固定提交 `541a9b599fee9c47915a5ae47f78ee679a4b9a93` 的最小方案回补核心恢复顺序，没有引入整个开发分支。`third_party/riverpod` 保留完整 57 个运行源码及 MIT；与官方 3.4.3 归档逐文件比较，仅 `ProviderSubscriptionImpl.resume()` 的 flush/激活顺序一处变化，运行依赖不变。版本标为 `3.4.3+uten.1` 并记录来源及回归后移除门槛；不修改全局 pub 缓存，也不以页面延时或忽略异常掩盖。
