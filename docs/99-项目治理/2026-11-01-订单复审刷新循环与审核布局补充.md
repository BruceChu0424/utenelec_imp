# 订单复审刷新循环与审核布局补充

基线 `8b1eaf0ac`；分支 `uimp/review-layout-and-finance-badges-20261101`。本轮只改客户端公共行为和布局，不新增数据库迁移，不改服务端审核、权限或认领合同。

## 根因及公共修复

销售订单详情在返回时经 `onPageResume` 调用 `_load(background: true)`。草稿读取会释放旧的 `SALES_ORDER_APPROVE` 租约并重新认领。此前 `isBusinessWrite` 只排除了 heartbeat，claim POST 和普通 release DELETE 仍推进业务写修订号；返回刷新因此认为“读取期间又有修改”，结束后立即再刷新、再认领，形成循环。页面的读取保护在每次刷新期间禁用审核，出现“修改后必须退出再进才能审核”。

在公共 `data_write_revision.dart` 中按精确路径和 HTTP 方法排除自动 claim / heartbeat POST、普通租约 release DELETE。所有通过 `DataWriteRevisionInterceptor` 的同类页面一次修复；不在单个销售页关掉返回刷新，也不放开权限或认领校验。真正的订单保存、审核、管理员 takeover / force-release 仍计为业务写；未知路径、错误方法和嵌套后缀不泛化豁免。

新增实际 `SalesDocDetailPage` + GoRouter 返回 + Dio 拦截器的交互回归，HTTP 回包由测试适配器提供，依次验证：负责人退回的草稿、编辑并保存、返回同一详情、读请求停止、直接打开审核确认并提交一次、显示待销售负责人审核。该测试使用旧公共分类器时失败：有界后续帧内详情请求由 20 继续增至 30；改后首次及返回共读 2 次，认领 2 次，只有真正保存推进一次业务写修订号。旧故障复现与改后成功日志分别保留，不把模拟 HTTP 当成生产数据验收。

## 订单审核布局

- 刷新使用 `UtenRefreshButton` 放入 `UtenAppBar.actions`，位于右上角；窄屏沿用全站顶栏操作面板。
- 批量批准通过 `MasterDataTableView.batchActionsBuilder` 接入既有 `UtenFloatingActionGroup`，选择摘要使用表格唯一的 `UtenSelectionSummaryPill`，右下角按“已选 N 项 / 批量批准”排列。
- 不另写悬浮定位或第二套选择数；表格自动处理末行让位、窄屏换行、底部导航避让及全屏视图。空选灰显、清空选择、跨页选中、旧修订、认领及未知提交保护保留。
- 分类与搜索继续使用公共筛选栏及原主题。沿用主色、字号、间距和状态色，不新增主题数值或视觉变体。截图已核对桌面与窄屏。

## 财务小类徽章

| 入口 | 旧行为 | 唯一新来源 |
|---|---|---|
| 销售订单确认大类 / 待确认小类 | 大类读徽章汇总，小类另发首次/修改两次计数；任一切片未到或失败，小类无数字 | 同一 `salesOrderFinancePendingCountProvider`，取 `salesOrderFinance.count` |
| 出货审核 / 待审核 | 小类没有传 count | `shipmentFinance.count`，与父级同源 |
| 超量到货审批 / 待审批 | 小类没有传 count | `financeArrivalException.count`，与父级同源 |
| 订货审批 / 报价核价 | 已取对应汇总事实 | 保留，回归确认 |
| IQC 退回贷项 | 多个不同责任阶段的切片 | 保留原专用切片口径，不把组合浏览类伪装成一项可办数 |

旧 `salesOrderFinanceQueueCountProvider(false/true)` 客户端路径及两个调用方的失效重拉已清理，库内无剩余引用。后台 changesOnly 计数 API 保留既有合同，不删除其他消费者可能使用的能力。待确认全队列数不由当前页、关键字结果或本地行数推算；未知来源保持 null。手动刷新/详情返回仍同时核对列表和徽章。
