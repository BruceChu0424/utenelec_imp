# ADR-074：公司内部附件存储与原件保留

- 状态：已接受（2026-09-08 用户要求）；实现与验收进行中，尚未安装到公司服务器。
- 范围：ERP 图片、文档附件的存储、权限、下载、容量与恢复。
- 取代范围：ADR-031 中内部部署附件必须使用 OSS 的限制，以及旧客户端缩图转 JPEG 的上传方式。单主数据库、网络授权和其他部署规则继续适用。

## 决策

当前只建设公司内网使用场景。公司部署统一使用 `uten.storage.provider=internal`，新增文件只上传到内部服务器，不上传阿里云，也不提供切换成云上传的业务设置。文件保存在服务器专用私有目录；数据库只保存业务归属、上传人、原文件名、原始大小、SHA-256、扫描记录和精确存储位置，不存文件大字段。`local` 继续用于开发；旧 OSS 代码只用于明确历史版本的只读兼容或受控迁入，不承担新文件上传。已核验公司附件表当前为零条。

上传使用统一附件服务。员工选中的原文件原样上传，服务端校验格式、大小、图片尺寸和病毒扫描后，才确认成业务附件。客户端不缩图、不丢透明通道、不改为 JPEG。无损压缩只是服务器物理保存方式；下载接口自动还原原文件，员工不必安装解压工具。JPEG、PNG、PDF、Office 压缩包等已压缩格式通常原样保存，避免耗时重压却没有收益。已被旧版本有损处理过的历史图片保留已有文件，无法恢复已经丢失的像素。

每个对象固定 `storage_provider + storage_key + storage_version`。V533 单独保存原件大小与实际落盘大小、IDENTITY/GZIP 编码。旧代码只有 OSS 返回非空版本号，因此明确有版本的旧对象可归类 OSS；无版本历史保留 `legacy_unknown`，需核验原存储后处理，不能根据当前配置猜测位置，更不能找不到对象就转到另一后端删除。

文件先进入暂存区，确认后原子发布到正式区；文件与目录需要持久化同步。已确认内容、原始摘要和存储身份不可原地覆盖。删除先提交数据库意图，再由带存储来源的队列删除精确版本，失败可重试。孤儿对账同样按存储来源区分证据。旧审计证据保留，不伪装成新格式扫描或重新确认结果。

## 员工入口与权限

附件挂在已保存的业务单据 UUID 上，不按可改的名称或单号建立关联。所有入口复用 `AttachmentSection` 和 `AttachmentService`。查看、下载、上传、删除各自保留通用权限，并叠加业务对象的负责人范围、状态和并发规则；页面按钮和后端一起控制，不能凭“能打开这个模块”读取所有附件。

新建页（2026-09-10）：单据尚无 UUID 时，`BusinessAttachmentSection.draft` 只把员工选中的原文件暂存在客户端内存（`PendingAttachmentController`，单文件 25MB、合计 100MB），保存成功拿到真实 UUID 后按同一 presign → 直传 → confirm 契约逐个确认；拆单生成多张订货单时同一文件挂到每张单据。任一文件失败页面停留并保留失败项重试，不重复建单，也不以文件名或临时单号预关联。采购/委外订货单先传附件再提交财务，避免提交后对象策略把附件锁成只读。通用功能门槛由 V546 授予单据归属部门；财务审核页只读展示原件。

详情页只读（2026-09-11）：业务单据的**详情页就是审核页**——审核人在那里点「审核/确认/驳回」。
用户口径「到审核页面文件应该不能修改了，只能看已经上传的文件」，故销售/采购/委外/钱流/
生产计划/生产日报六个详情页的附件区一律 `canManage: false`，并带统一说明
`BusinessAttachmentSection.kReviewReadOnlyAttachmentNote`（「本页文件只读，仅可查看和下载；
需要增删请回到编辑页」，仅在确有文件时渲染，空单据下这句话只是噪音）。文件的增删改统一
回到编辑页做，审核人看到的永远是提交那一刻的那一份。
**不在此列的三处不是审核面**，保持可管理：仓库出库单详情的「出库凭证/照片」（出库动作
本身就是审核，凭证是这一步的产物，且与服务端 `StockDocumentAttachmentAccessPolicy` 同口径）、
产成品 FQC 登记弹窗的检验证据（登记结果前必须先传证据，登记后自动锁死）、
IQC 退货处理页的处理证据。

分类（2026-09-11）：分类是可选标注，不在上传前询问。上传与保存前暂存都不带分类，页面上不再有决定归类的芯片；文件进入列表后在文件名旁边逐个设置或清除。已保存单据走 `PUT /api/attachments/{id}/category`，功能门槛 `attachment:upload`（整理自己传的文件，不借用删除权限），对象授权与删除同一条 `requireCanManageForUpdate` 路径 —— 单据被审核锁定或红冲后分类同样只读；空值 = 清除，服务端只限 48 字符长度，词表由各页面决定并留痕 `attachment_category_set`。暂存文件的分类存在客户端，保存成功时随该文件一起 confirm。分类不影响文件的访问范围、下载与生命周期。

已有员工档案、合同、本人文件、报销发票统一接入。新增业务入口的逐项覆盖与未完成项集中记录在 [附件实施与服务器验收](../99-项目治理/2026-09-08-内部附件实施与服务器验收.md)，不把仅有设计的入口记成已上线。审批时不能悄悄替换原材料；补充凭证应保留上传人、时间和历史。员工头像走指定 CLEAN 图片的专用读取路径，员工选择器的查看权限不会开放身份证、合同等私密附件。

## 运行边界

- 内部文件目录不能通过 Nginx 静态映射公开；下载逐次校验业务权限，响应私有且不落公共缓存。
- 上传与还原采用有上限的流式处理；单文件、还原大小、并发、等待时间和磁盘保留空间都有边界。繁忙时明确提示重试，不建立无限队列。
- 图片像素和解压后字节受校验；物理压缩不能绕过原文件的病毒扫描、内容类型和大小限制。
- 正式文件、发布临时文件需满足同一文件系统的原子发布约束。运维不能把尚未支持的跨卷移动假称为原子操作。
- 杀毒和备份资源单独受控。备份错峰、限速、有限并发；业务进程不因附件需求被随意降低优先级。
- 备份必须包含数据库元数据与其引用的精确对象版本，并验证可还原。RAID 和同机副本不等同于异机灾备。
- Office 在线预览（2026-09-10）是派生视图，不是业务附件：服务端 LibreOffice 把已授权的 CLEAN 原件转成 PDF，缓存在存储根目录 `preview/<附件id>-<原件sha256>.pdf`，与原件同卷、私有、不经 Nginx 静态映射，响应 `private, no-store`。转换有超时、并发槽位与缓存容量上限；soffice 缺失/超时/失败一律回落为下载原件；原件物理删除完成后由删除 Outbox 清掉缓存。缓存可随时整目录删除重建，不参与备份与对账。
- 支持哪些文件类型由一张能力矩阵决定，不逐处判断（2026-09-11）：**可上传**＝业务确有需要且服务端能按魔数把声明类型和真实内容对上；**可预览**＝客户端能忠实渲染或服务端能忠实转换；**服务端转换**＝LibreOffice 打得开的办公文档。三者是包含关系，客户端真源在 `lib/shared/attachments/attachment_file_rules.dart`，服务端在白名单、内容检查器与转换集合三处对齐。渲染不了也转不了的类型（tiff/heic、7z/rar）只登记上传能力，行内图标直接显示「下载」——宁可少承诺，也不弹一个必然失败的预览。头像只接受客户端能解码的位图，不按 `image/` 前缀放行。

## 验收要求

原图、透明 PNG、PDF、Office、可压缩文本上传后下载的字节与 SHA-256 一致；旧 OSS 和未知历史路由正确；权限撤销、跨对象访问、重复确认、断网重试、病毒、截断文件、压缩损坏、磁盘不足和并发过载均不产生错误业务附件。必须完成 Linux 真实文件系统的原子发布、故障恢复与备份还原验证，再通过文件上传/下载和业务查询同时运行的压力测试确认部署资源预算。
