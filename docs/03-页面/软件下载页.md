# 软件下载

> 路由：`/software-downloads`。入口：工作台页头右上角“软件下载”。

## 可用平台与权限

登录的员工及真实系统超管可进入页面并下载，服务端同时核验身份、账号状态及软件包已发布状态；系统超管不要求另建员工档案。访客、未登录、须改密及未绑定员工的普通账号不可访问完整客户端目录或通过包 ID 绕过下载。

| 平台 | 当前界面 | 实际下载 |
| --- | --- | --- |
| Windows | 完整客户端主区域；版本、文件大小、架构、更新说明、进度和下载结果 | 仅已发布、校验完成的 Setup.exe；双击安装 |
| Android | “暂时无法下载” | 不提供按钮或下载动作 |
| macOS | “暂时无法下载” | 不提供按钮或下载动作 |
| iOS | “暂时无法下载” | 不提供按钮或下载动作 |

“发布 Windows 版本”仅向具有 `client_release:publish` 的真实员工显示，复用设置页的唯一发布对话框，同时展示首次安装和客户端更新两个 Windows 上传区。撤权、换号或更换服务器会使旧发布工作失效。发布、撤回继续密码再认证；完整客户端与应用内更新包的构建号分别递增。

Windows 发布表单将版本、架构和更新说明共用一次输入，下面同时呈现两个用途明确的区域：Setup.exe 首次安装程序，以及已安装客户端自动获取的更新 ZIP。每个区域独立选择文件、上传发布并显示实际结果；一个成功不代表另一份也成功。各自保留请求 UUID，重试不会重复发布已经成功的那份。两份文件都保存在公司服务器的客户端专用目录中，不从管理员电脑直接推送给每台设备；员工的客户端从公司服务器发现并下载更新 ZIP。

页面通过 Flutter 的主机系统识别能力，在原生端及浏览器中识别当前 Windows、Android、macOS、iOS 设备，将对应平台排在最前并标“当前设备”。识别只决定展示顺序，不开放尚未提供的下载；Linux/未知系统不假称 Windows 设备。中文完整显示“优腾综合管理平台(UIMP)”，其他语言完整显示“Uten Integrated Management Platform (UIMP)”。

尚未发布完整包时显示“Windows 版本正在准备”；读取失败有单独错误及刷新操作，不伪造版本、大小或下载地址。最新包撤回或丢失时，目录只提供仍已发布且可用的旧版本。页面只访问当前公司后端，不检查 OSS。

## 界面设计

默认使用 `frontend-design`，复用项目现有 Uten 组件与主题，不另建品牌、图标或字体系统。

- 浅色参考 token：背景 `#F5F7FA`、面板 `#FFFFFF`、主文 `#0F172A`、次文 `#475569`、主色 `#0F766E`、强调底 `#CCFBF1`；深色跟随同名主题角色。
- 字体为现有 NotoSansSC；Windows 主标题用 headlineLarge，版本和分区用 title，安装说明用 body，避免把版本或文件大小处理成装饰性大数字。
- 布局以当前设备平台在前，Windows 安装程序为主要下载区域；当前设备尚无版本时先显示真实不可用状态。Windows 宽屏左侧版本与操作、右侧简洁电脑示意；窄屏或大字号改为单列，图示隐藏。下方是真实安装步骤及其余不可下载平台。
- 评审后收敛为“完整 Windows 客户端”这一明确动作，避免四个外观相同却只有一个可用的下载按钮。占位平台只说明状态，不出现虚假链接或可点击控件。

## 上传与下载合同

Windows 发布窗口在底部固定一个“上传并发布”按钮，一次处理当前已选且尚未确认成功的文件。
两个文件区域只保留选择、进度及结果，不再分别要求点击发布。版本信息和授权范围在批次开始时
固定；安装包和 ZIP 各自保留请求 ID、成功回执及未知状态。重试跳过已确认成功项，权限、账号、
服务器或元数据变化后停止后续操作；这不是跨两个文件的原子事务。兼容只补发一个文件的入口。

下载进度使用统一 `UtenAnim` 的平滑过渡，进度、错误与完成反馈区域使用淡入淡出和高度动画；
通过公共 `UtenMotion` 响应节能档、TickerMode 和系统“减少动画”，对应时长为零。
下载成功弹出包含保存位置或浏览器下载列表指引的居中提示；失败弹窗允许用户主动重试或关闭，
取消下载不弹成功窗。弹窗复用 `UtenNotify.alert`，不会自动执行下载的 EXE。
账号/服务器更换会关闭本页持有的精确结果弹窗，已有安全或业务弹窗优先；原页面仍保留内联结果。

继续复用 `ClientReleaseService`、`ClientReleaseCatalog`、发布权限、原始流上传和包检查器，不建立第二套软件目录或上传服务。

- `GET /api/client-updates/downloads` 返回 `List<Release>`；只选 `platform=windows`、`packageKind=installer`、`installMode=windows_setup` 的已发布 EXE，各架构取最新可用版本。旧 `windows_bundle` 完整 ZIP 保留兼容管理及直链，但不作为新下载页面的安装程序。
- 普通员工下载沿用 `GET /api/client-updates/{id}/download`，认证、不缓存、撤回失效与更新包共用。
- 发布管理继续 `POST /api/admin/client-releases` 创建草稿、`PUT /{id}/package` 上传、`POST /{id}/publish` 发布、`POST /{id}/withdraw` 撤回。创建请求增加 `packageKind=installer`；旧请求和旧元数据缺省为 `update`。
- Windows Setup.exe 使用标准 Inno Setup 安装流程，按用户安装到可写入程序目录，包含 Flutter Release 运行文件、`data/`、`uten-client-manifest.json` 及固定 `client_updater/client_updater.ps1`。构建器复用完整 payload 清单并验证全部文件；服务端对 EXE 校验有界 PE/版本资源、固定产品标识、实际版本与目标架构及整包 SHA-256，不声称解开验证全部 Inno 压缩内容或完成 Authenticode 证书验证。上传发布权限、密码再认证及 HTTPS 继续承担发行信任边界。
- 应用内检查 `/check` 只返回 `packageKind=update`。安装完整包后的下一次更新允许读取首装清单，但更新包不能覆盖或删除固定更新器。
- 首次下载 EXE 后完成一次安装即可。后续在软件中点“立即更新”，仍使用已有 ZIP 更新通道和当前安装目录，自动下载、校验、等待程序退出、备份替换并重新启动；不重复打开 Setup.exe、不重新选择安装路径。设置及已保存草稿保留，更新前仍须保存当前工作。
- 客户端共用认证作用域、受限 API 下载路径、取消令牌和原子文件保存；分块检查总长度与 SHA-256，失败或取消不发布半包。Web 使用现有 Fetch 流传输和磁盘暂存能力，不把完整安装包重新经 XHR 聚合到内存。
- 服务端上传仍采用现有 512 MiB 上限、至多两个上传、私有暂存和磁盘预留；软件包位置不属于网页静态根目录，不允许直接暴露实际磁盘路径。

## 存储与构建边界

部署通过 `UTEN_CLIENT_RELEASES_DIR` 显式指定现有私有 media 根下独立的 `client-releases`，沿用原目录及配套备份，不迁移历史包：Simple/生产为 `/var/lib/uten-imp-media/attachments/client-releases`，internal-test 为 `/data/uten-imp/attachments/client-releases`。实际环境遵循其存储配置和写权限边界；受控预建步骤、剩余空间及备份恢复说明见部署对应文档。

应用版本切换不会覆盖该目录；普通附件清理和发布版本保留作业不把客户端包当作可删除附件。部署模板要求上传后仍须保留 10 GiB 磁盘空间，避免包上传耗尽业务存储。完整包与更新包的元数据和二进制一起备份、校验和冷恢复。

用户已要求暂停生成实际 Windows 包，等待并行任务结束并再次明确下令。当前允许代码和隔离 fixture 测试。今后本地测试包只连接本地测试后端，正式服务器分发包使用公司及可信远程入口；两类包分开命名、分开存放。必须等用户实测确认后才上传正式包，不能把本地 localhost 包作为正式版本分发。

本页和配置在本地实现不等于已部署或已有正式包可下载；未发布时必须保持真实空态。
