# 仓库质检入库性能审计

本页记录 2026-09-12 本轮仓库子任务的原因、实现边界与验证。业务规则以 ADR-075、仓库到货登记、IQC 合格待入库和采购委外到货退换货文档为准。测试通过不等于公司服务器已经安装；最终发布状态由本轮统一验收记录维护。

## 已确认原因与处理

| 路径 | 原因 | 当前实现 |
|---|---|---|
| 跨收货单批量入库 | 外层已取得整批锁图和 PASS 明细，内层每单再次发现并校验锁图、读取同一明细 | 单张和批量共用 `confirmCommands`。一次发现完整锁集合，按顺序锁命令，全部准备后复核一次；每单 PASS 明细读一次 |
| 多单重复核对仓库 | 相同实际叶仓的祖先、启用状态按每张收货单重复解析 | 在本次事务的准备阶段按实际仓 UUID 去重核对；幂等重放不重新要求历史仓启用，不建立跨事务缓存 |
| 多单关联同一分析 | 每单入账后立即重算分析，后面的单再次重算同棵树 | 全部实物/资金切片/专属归属先按原顺序入账，生产端按单推进真实履约，然后对混合采购/委外整批受影响分析去重刷新 |
| 确认结果投影 | 每张单单独读取实际去向，可能触发重复来源查询 | 生产联动完成后批量读取实际去向，按真实入库项所属批次返回；不会把共享 PASS 身份当成本次入库身份 |
| 送检成功返回 | 仓库只需要收货单号/处理结果，审核网关却重新构建完整商业详情后立即丢弃 | 普通审核保留详情响应；仓库网关共用同一 `approveReceipt` 事务内核并返回 void，不查询无用详情 |
| 品质检查结果列表与徽章 | `event_stocked` 先对全部历史入库行做 GROUP BY，当前仅少量待办也重复聚合旧历史 | 先过滤 `passed_base_qty > warehouse_stocked_base_qty` 的有效品质行，只按候选 PASS 事件通过既有索引汇总其入库切片 |
| 页面快速切换 | 晚返回的旧来源/关键字状态计数可能覆盖新计数 | 状态计数独立采用请求版本，只接受最新响应 |
| 批量请求失败 | 关闭失败提示时连同批量表一起关闭，丢失员工修改和原命令上下文 | 提示关闭后保留表单。网络结果不明时可按原数量、库位和幂等键重试；明确余量冲突时仍要求重新核对 |
| 产成品批量确认入库 | 全批已经预锁，内部审核又重新查询/验证同一关联图；逐单构建完整详情只取单号与状态 | 预锁后的审核内核返回已核对实体，外部单张接口才读取详情；批量复用本次完整预锁 |
| 产成品批量生产跟进 | 每张单的同源分析重复刷新 | 每张单仍立即完成真实库存/成本、生产推进与委外专属转交，再对全部已入库单据统一刷新分析；没有异步旁路替代数量事实 |
| 成品送检多仓交叉等待 | 原来按报工顺序交错取得仓库 A/B 的行锁，不同报工集合可能按相反顺序持仓互等 | 批量先锁全部命令、识别重放，再锁全部新报工/明细，最后按稳定顺序锁全部实际仓；锁后才登记 |
| 成品送检重复基础查询 | 同批同仓和同收货人逐报工重复查权威数据 | 只在本次事务持锁范围内复用仓库快照和收货人身份，已完成重放早于新仓资格核对 |

结构上的查询/刷新次数改进不等于端到端秒数承诺。真实响应时间还受数据规模、并发、网络、审计触发器和源单关联复杂度影响。本次没有用空业务库的低延迟证明历史大数据场景。

## 事务与来源保证

1. 仍是一条仓库命令一个事务。先校验全部类型、UUID、规范化幂等键、版本余量、库位、实际叶仓及委外原材料份额，再开始物理入账。任一冲突整批回滚。
2. 商业来源、库存、主仓、分析的统一预锁协议保持有效；后续生产回调仍检查覆盖范围，不能在持锁后静默补拿上游锁。准备阶段完成后才验证快照，禁止把校验移到提交后。
3. 入库行 UUID、实际库存 movement UUID、资金切片和原始品质 PASS 仍一一可追溯。金额/重量继续用原冻结切片按累计增量分摊，未知重量保持未知，末片保留原守恒规则。
4. 普通到货、免费补回、贷后再采购、少到、超量隔离、FAIL、红冲和来源下游消费规则不变。PASS 本身不增加库存，确认入库不重复立 AP。
5. 已完成命令只读取原批次，跳过库存、学习、生产和通知写入。规范化后重复的幂等键在锁前拒绝，避免空格变体进入同一命令身份。
6. 下一张收货单的专属归属容量读取本事务已追加的来源/权益账本，不能依赖尚未刷新的分析展示数量。返回的 `actualAllocations` 在整批生产回调完成后读取。
7. 实际仓库与原建议仓不同的合法合格专属来源，按 ADR-075 跟随真实叶仓；不能仅因主仓不同就把原专属来源误记为公共库存。其它任务专属、未检和不合格库存不开放。

## 合并来源退补的真实缺陷闭环

后续跨任务复核把合并来源的待检、待补数量校正扩展到了实际归属。V554 由物料任务维护区间分摊；本任务新增 V555，修复系统 IQC 终态 `CANCELLED` 行动下，原单合法补回虽成功入库却未继续归属原分析的问题。

原始真实失败证据为 `server/target-perf-warehouse/merged-iqc-exact-r1.log`：A20/B30 合并到货，合格实收入库 12、实退 38、原单免费补回 38；总库存 50、库存金额和 AP 2500、幂等和取消历史均通过，唯独原分析 exact 归属不足。

修复不复活行动。逐个 V518 资金/品质/库存分项证明同原订单、来源与已实退案件，仅本次替补基本量能延续；旧 allocation、当前节点需求、已持有权益/正式覆盖和其它未来供给共同限额。新增权益前由数据库 `ALWAYS` 触发器再验，普通到货、人工撤回证据及其它实际订单的案件不能借道。说明与入口见[153-V555迁移文档](../数据迁移/153-V555-IQC原单补回来源权益延续.md)。

V555 的节点限额还通过真实让料组合纠正：接受节点已借助让料齐料后，自身原单补回仍应优先补齐来源。初始限额阻断第一片补齐，红例为 `iqc-priority-r1-reproduce.log`；最终只采用现役让料账本精确 to 节点的 `OPEN/PARTIAL` 未补齐量，from、已完成、已撤销记录不增加预算。

最终 V555 组合 26 项全部通过：8 项真实 FullChain 和 18 项 peg/去向投影测试，无失败、无跳过。包含 4/34 两次原单实收入库形成部分/全部优先补齐、让料撤销及重复请求，以及上述普通/人工/错订单来源负测和其它活跃供给保护。证据为 `server/target-perf-warehouse/iqc-priority-r2-final.log` 与 surefire 报告；513 项迁移到 V555 成功，SQL 源与测试资源 SHA256 一致：`D129F40990464F536B7BD0A0A16A3CC426541BB063CFA23C33ACE4723EDF10E9`。
