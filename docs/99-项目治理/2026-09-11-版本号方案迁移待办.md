# 版本号从日期改成语义化：调研结论与执行方案（**已于 2026-09-18 执行**）

用户 2026-09-11：「你把版本号改改 不要用日期 改成正常的 以后版本号就按照这个迭代
小更新就小版本 大更新就大版本 也写到文档或者 readme 里面」，随后补充「如果改版本号太麻烦
可以先不改 以后也可以 你自己看」。

**判断：推迟到下一版单独一轮做，不塞进 2026-09-11 这次发布。**

## 一、为什么推迟

一开始我以为只是三处正则（发布流水线 + 更新器的两处校验）。全仓穷尽扫描后发现不是。

> **2026-09-12 订正（重要，先读这条再读 §1.1）**：下面 §1.1 那道单调性闸门在
> **`release_guard.py` / `release_updater.py` 这条老链路**里，被
> `.github/workflows/release.yml` 与 `_unsigned-candidate-build.yml` 引用。
> 而**公司服务器现在实际走的是 Simple Release（ADR-060）**：
> `.github/workflows/simple-release.yml` + `deploy/simple/uten-imp-updater.sh`，
> 这条链路**完全不调 `release_guard.py`，服务器上也没有 `high-water.json`**，
> 只有 simple-release.yml:55 的一处正则
> （`^v[0-9]{4}\.[0-9]{2}\.[0-9]{2}-[0-9]{1,3}$`）和 updater 脚本里的两处。
>
> 也就是说：**只想让现网改用语义化版本号，代价远小于 §1.1 的描述**——三处正则 +
> §2.3 的 `prune_old` 保护（那条已在 2026-09-12 单独落地）。§1.1/§2.1 的 epoch 设计
> 仍然要做，但它是为了**老链路不被将来某次回退用到时炸掉**，不是现网发布的前置条件。
> 推迟的真实理由退化为「这一版带着 11 个数据库迁移，不顺手动发布链」，仍然成立。

### 1.1 真正的阻断点：版本号是**发布闸门的排序键**

`deploy/updater/release_guard.py:302` 的 `version_sequence()` 把版本号折算成整数：

```python
return int(day.strftime("%Y%m%d")) * 1000 + counter
```

而 `deploy/updater/release_updater.py:2106` 有一道**单调性闸门**：

```python
if sequence <= high_water:
    fail(f"release sequence {sequence} is not above staging high-water mark {high_water}")
```

`high_water` 由 `load_high_water()`（`release_updater.py:1983`）从服务器上的
`high-water.json` 读出。**现网那个文件里存的是 `20260909001`（11 位）**。
朴素的语义化编码（`major*1e6 + minor*1e3 + patch` ≈ 1e6 量级）永远小于它——
**首个语义化版本会被这道闸门永久拒绝入库，而且服务器端状态文件不会自己清零。**

`version_sequence` 被 `release_updater.py` 引用 11 处、`retention_manager.py` 引用 11 处，
是整条发布链的单点。

### 1.2 三个必须逐位一致的数值孪生体

`release_guard.py:347` 与 `:484` 分别对 `channel.json` / `manifest.json` 校验
`version_sequence(version) != sequence → fail`。因此下面三个函数**必须算出完全相同的数**：

| 文件 | 函数 | 现在的末行 |
| --- | --- | --- |
| `deploy/updater/release_guard.py` | `version_sequence()` | `int(day.strftime("%Y%m%d")) * 1000 + counter` |
| `deploy/release/release_tools.py` | `validate_version()` | 同上 |
| `deploy/release/offline_release.py` | `validate_version()` | `int(f"{date:%Y%m%d}{counter:03d}")`（同值不同写法） |

任一不同步，发布当场炸。

### 1.3 判断依据

在一次已经带着 **11 个数据库迁移**（V541–V552）的发布里，顺手改掉**发布完整性闸门本身**
＋ 触碰**服务器持久化状态**，是不该冒的险。方案已经算清楚了，单独一轮做成本很低。

## 二、执行方案（已实算验证，照做即可）

### 2.1 编码

取 `SEMVER_SEQUENCE_EPOCH = 100_000_000_000`，严格大于遗留天花板
`99991231*1000+999 = 99_991_231_999`：

```python
SEMVER_SEQUENCE_EPOCH = 100_000_000_000
SEMVER_MAX_MAJOR, SEMVER_MAX_MINOR, SEMVER_MAX_PATCH = 9_999, 999, 999
return SEMVER_SEQUENCE_EPOCH + major * 1_000_000 + minor * 1_000 + patch
```

实算：

| 版本 | sequence |
| --- | --- |
| `v2026.09.09-1`（遗留，现网） | 20_260_909_001 |
| 遗留天花板 | 99_991_231_999 |
| `v1.0.0` | 100_001_000_000 |
| `v1.1.0` | 100_001_001_000 |
| `v2.0.0` | 100_002_000_000 |
| `v9999.999.999` | 109_999_999_999 |

严格递增且**恒高于任何日期序** → 单调闸门跨方案切换自然放行，
**服务器上的 `high-water.json` 不需要人工清零**。`releaseSequence` 侧无上限约束
（`release_guard.py:346/483` 调 `require_positive_int` 未传 `maximum`），1e11 量级安全。

### 2.2 正则

```python
VERSION_RE = re.compile(
    r"^v(?P<major>0|[1-9][0-9]*)\.(?P<minor>0|[1-9][0-9]*)\.(?P<patch>0|[1-9][0-9]*)$"
)
```

**必须用 `0|[1-9][0-9]*` 而不是 `[0-9]+`**：否则 `v1.01.0` 与 `v1.1.0` 会算出同一个
sequence，现有的反别名保护（`deploy/updater/test_release_security.py:309`
`test_release_counter_is_canonical_and_anti_alias`）会失效。

### 2.3 连带改动清单

- 三个孪生函数（§1.2）同步替换，并加 `major/minor/patch` 上限与 `v0.0.0` 拒绝。
- `release_guard.py:8` 的 `import datetime as dt` 改完即成死导入（全文仅 310 行用过），删除。
- `offline_release.py:242` 原来用 `match.groups()` **位置解包**，分组数变了必须改成按名取。
- `deploy/updater/test_release_security.py` 与 `test_retention_manager.py` 里约 20 处硬编码的
  `20260811001` / `20260812001` / `20260814001` 字面量都是日期序，按新编码同步更新；
  反别名用例的样本从 `"v2026.08.11-01"` 换成 `"v1.01.0"`。
- `.github/workflows/simple-release.yml` 的版本正则与 `deploy/simple/uten-imp-updater.sh`
  的两处正则（`LATEST.txt` 校验、`activate` 参数校验）。
- **`uten-imp-updater.sh` 的 `prune_old`**：用 `sort -V` 保留最新 N 个，注释写着
  「active 永远在最新之列」——**混用两套方案时这个假设不成立**（`v1.0.0` 在 `sort -V`
  下排在 `v2026.09.09-1` 之前）。必须加一条硬保护：**永不删除 active 版本目录**。
  这条即使不改版本号方案也该加，属于独立的健壮性缺陷。
- 文档：`deploy/simple/RUNBOOK.zh-CN.md` 的打 tag 示例、README 里补一节
  「版本号规则」（大更新 → MAJOR，小功能 → MINOR，修复 → PATCH）。

### 2.4 建议起点

`v1.0.0`。系统已在生产运行，这个号表示「从这里开始正式按语义化版本走」。
由于 §2.1 的 epoch 设计，它不需要比旧的日期号「更大」。

### 4.4 遗留人工动作（代码改不了的三件事）

1. **GitHub tag 保护规则**：若规则 pattern 仍是 `v[0-9]{4}.[0-9]{2}.[0-9]{2}-*` 之类，
   推 `v1.0.0` 会被挡；发布前到仓库 Settings → Tags 把 pattern 放宽为 `v*` 或语义化模式。
2. **服务器现存旧日期号目录**：更新器升级后不再识别，不会被清理也不会误删
   （prune_old 只动识别目录且永不删 active）；确认稳定后可人工清掉。
3. `high-water.json` 无需清零（§2.1 epoch 设计），但老链路若真被回用，其 `LATEST`
   语义化版本排序依赖本轮同步的四处校验，勿单独回滚其中任何一处正则。
