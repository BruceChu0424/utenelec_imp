## 改了什么

数量(数量 + 单位 + 换算率 -> 基本数量)仍是计划、采购、销售、委外、生产与财务唯一的事实。重量是仓库自己的一条平行账：统一按千克(kg)存，未称就是 NULL(永远不显示成 0)，估算值带标记，永远不阻塞数量过账。

| 对象 | 变化 |
|---|---|
| `fn_weight_unit_kg_factor(text)` | 新建。封闭重量单位目录 G/KG/T/JIN/LB/OZ -> 每单位千克数(0.001 / 1 / 1000 / 0.5 / 0.45359237 / 0.028349523125)，与服务端 `WeightUnit` 同表；其它编码返回 NULL |
| `unit_measurement_profiles` | 删死列 `canonical_unit_id`、`to_canonical_factor`(连同外键与换算 CHECK)；加 `mass_unit_code VARCHAR(4)`，CHECK 取值在六个编码内且只允许 `MASS` 维度(`MASS` 不填编码也允许，不换算)。按去首尾空白后的单位名精确匹配播种(拉丁字母不分大小写，已删除单位不播种)：kg/千克/公斤 -> KG，g/克 -> G，t/吨 -> T，斤 -> JIN，lb/lbs/磅 -> LB，oz/盎司 -> OZ；`ON CONFLICT (unit_id) DO UPDATE`，来源 `GOVERNED_IMPORT` |
| `stock_ledger_seq` | 新序列。库存数量流水与重量调整账共用的记账顺序号(不随清空业务数据重置) |
| `stock_movements` | `weight` 仍是 NUMERIC(18,4)，语义改为千克(不 ALTER TYPE，不碰 `v_stock_available` / `v_fulfillment_workbench` 视图链)。加 `weight_source`(MEASURED/EXACT/SLICE/AVERAGE/ESTIMATE，取值 CHECK 已验证)、`balance_weight_after`(本条后该维度库存重量，>= 0)、`ledger_seq BIGINT NOT NULL DEFAULT nextval('stock_ledger_seq')`(本句整表重写一次，历史行按物理顺序补号，不触发行触发器)。`CHECK ((weight IS NULL) = (weight_source IS NULL)) NOT VALID`：流水只追加且 IQC 关联行禁止 UPDATE，历史带重量行无法回填来源，读侧按 MEASURED 读。删 `actual_weight_unit_id`。索引 `idx_sm_goods_date` 换成 `idx_sm_goods_ledger (goods_id, transaction_date DESC, ledger_seq DESC)`；加 `idx_sm_src_item (source_doc_type, source_doc_id, source_item_id)`，前缀冗余的 `idx_sm_src` 删除 |

## 为什么这样做

- 不改重量列类型：千克 4 位小数(0.1 g)足够仓库称重；改类型要连带重建 `v_stock_available` -> `v_fulfillment_workbench` -> `v_fulfillment_workbench_actions` 三层视图与 V446/V449 的 `ROUND(...,4)` 切片校验，收益不抵风险。
- `ledger_seq` 而不是时间戳排序：仓库单据按单据日期零点记流水，可倒填且同单同刻；同一维度的写入都持有库存锁，序号顺序就是过账顺序，重量账链(起算/尾差/盘点定重)与流水才能严格前后相接。
- IQC 入库校验只在 MEASURED/SLICE 时比重量：重量账会给未称入库推导重量，旧的「流水重量必须等于本批切片」会让所有未称或质量单位货品的 IQC 入库在提交时失败。
- 观测表 PRESERVE、调整账 CLEAR：学习到的单重是货品知识，清空业务数据后保留(V711 先例)；调整账是库存事实，和流水一起清。

## 核对 SQL

```sql
-- 1. 退役对象(期望全为 NULL)
SELECT to_regclass('public.measurement_capture_profiles'), to_regclass('public.legacy_measurement_exceptions'),
       to_regclass('public.v_measurement_capture_profile_resolution'),
       to_regprocedure('fn_reject_measurement_append_only_mutation()');

-- 2. 余额形状(期望 0 行)
SELECT warehouse_id, goods_id, color_id, qty, weight FROM stock_balances
WHERE NOT (weight IS NULL OR (qty = 0 AND weight = 0) OR (qty > 0 AND weight > 0));

-- 3. 质量单位档案
SELECT u.name, p.measurement_dimension, p.mass_unit_code, p.provenance
FROM unit_measurement_profiles p JOIN units u ON u.id = p.unit_id ORDER BY u.name;

-- 4. 重量对账(上线后观察 DRIFT 行)
SELECT reconciliation_status, count(*) FROM v_stock_weight_reconciliation GROUP BY 1;

-- 5. 清空孪生新策略(期望 4 行 true)
SELECT n, position(n IN pg_get_functiondef('business_data_reset()'::regprocedure)) > 0
FROM unnest(ARRAY['(''stock_weight_adjustments'', ''CLEAR'')', '(''goods_weight_profiles'', ''PRESERVE'')',
                  '(''goods_weight_observations'', ''PRESERVE'')', '(''goods_weight_estimates'', ''PRESERVE'')']) n;

-- 6. 权限授予(期望与 stock_doc:edit 的部门数相同)
SELECT p.code, count(dp.*) FROM permissions p LEFT JOIN department_permissions dp ON dp.permission_id = p.id
WHERE p.code IN ('stock:weight:manage', 'stock_doc:edit') GROUP BY p.code;
```

## 回退与部署边界

- 迁移只能前向。所有补丁都读已安装定义并在锚点缺失/重复时失败，DROP 不带 CASCADE / IF EXISTS：库不在预期形状时直接失败，不静默跳过。
- 旧应用不能跑在 V745 库上：`StockMovement` 实体仍映射已删除的 `actual_weight_unit_id`，Hibernate `ddl-auto: validate` 启动即失败；IQC 与单位管理的旧 SQL 也读已删除列。必须与 ADR-135 的服务端一起发布。
- 合并：V745/ADR-135 为临时号，合并时按 main 头重编号；清空孪生锚点、PRESERVE 分段、CLEAR 恒等式与白名单版本对按真实目录重算(并行分支 V737/V742 同样补丁 `business_data_reset()` 与 PRESERVE 计数，锚点保留，互相兼容)。
