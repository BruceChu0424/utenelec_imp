## 一、问题

用户口径（2026-09-14）：

> 物料分析准备页面里的委外件，如果这个委外件只有一层子层级——展开就只有一个物料、
> 不能有两个——那它就不需要去自制流程，直接下达委外。只要子层级满足了就进行委外操作：
> 委外下单 → 采购通过 → 仓库出库 → 入库 → 品质检查。
>
> 就是把子层级发给委外，回来了就变成了父层级。数据上要对，仓库那里数据该变就变了。
>
> 但是这个子件得先完工——比如这个子件是个采购件，就等这个子件采购完成、入库了，
> 委外去执行委外操作。

这是「来料加工」最常见的一种形态：一个毛坯/一块料出去，电镀 / 喷涂 / 注塑 / 车削回来
就成了另一个货号。公司在这条链上**没有任何装配工序**。

V458/ADR-062 把「目标件有活动 BOM」一律解释成「先自己做出目标件，再整件发外」，
于是这种一进一出的加工被迫走完整条自制链：建 SUBCONTRACT_MAKE 任务 → 排产 → 领料 →
开工 → 报工 → FQC → 成品入库 → 再通知委外 → 出仓。车间收到一张什么都不用做的计划单，
FQC 检一个根本没加工过的件，仓库把刚入库的东西原样再发出去。

## 二、决策

### 2.1 判据：只有一个叶子子件（四条全中才算）

服务端判定，前端不参与。判据本体是数据库函数
`fn_subcontract_sole_component_goods(goods_id)`，**只此一处**：

1. 该货品的**活动 BOM 边恰好 1 条**
   （活动 = 边未删 + 子件货品未删 + 子件不是 `auto_created` 自动补位 stub）；
2. 该边 `consumption_basis = 'PER_UNIT'`——`PER_PACKAGE` / `FIXED_BATCH` 带取整，
   压不成一个标量冻结单耗；
3. 该边 `control_stage ∈ (START, ASSEMBLY, FINISH)`——`SHIP` / `REFERENCE` 只是提示料，
   不是发给委外商的东西；
4. **那个子件自身没有活动 BOM 边**——这才是「只有一层」。

任一条不满足即回落既有 `MAKE_THEN_OUTBOUND` 两段式，**不是报错**。判据同时被
订货批准（`SubcontractMaterialPlanService`）、下达分流
（`MaterialAnalysisCommandService`）、物料分析投影三处调用，口径不会漂移。

> **为什么不按「BOM 树深度 = 1」**：深度判定要递归整棵树，而这里真正决定行为的是
> 「能不能用一个标量冻结单耗把回厂量倒扣成发出量」。一条边 + PER_UNIT + 子件是叶子，
> 恰好是这个条件的充要形态。

### 2.2 下达：不建前置自制任务，直接出委外申请

物料分析确认 `SUBCONTRACT` 路线后点「下达委外」：

| 形态 | 下达后 |
|---|---|
| 无子层（纯外协） | 生成只读委外申请，通知委外部（V436 语义，不变） |
| **只有一个叶子子件（本决策）** | **同上**——生成只读委外申请、通知委外部；**不建** `SUBCONTRACT_MAKE` 任务、**不进**车间桶 |
| 有子层（其余全部） | 建 `SUBCONTRACT_MAKE` 前置自制任务，走车间链（ADR-062，不变） |

数量口径随之对齐「直接外发」那一套：**可改小分批下达**（不再强制整量接管剩余需求）。

**2026-09-21 修订(V641)：公共超量备货放开。** 原先禁止的理由是「多下的量会凭空产生
一份无人负责的子件需求」。ADR-099 修订把「层级表上每一行填的数量」做成了服务端事实
(`issue-plans/preview` 的 `typedOutputs` → 该节点的计划产出量)，多下的量按计划产出量
如实带大那颗子件的需求，就在同一张「父件 + 下层一起下单」页里一并下单——责任有人认了，
这条禁令也就没有了存在理由(用户口径「我把采购超量下单后，委外甚至是车间那里下达就不能
超量下单」)。三层一起放开：客户端不再本地拦截、服务端 `notifySupplyInternal` 撤掉同口径
的可读拒绝、数据库 `preplan_public_surplus_subcontract_leaf_guard` 与运行时超订容量
`fn_preplan_direct_overorder_capacity`(后者不放开会让放行的公共量在委外订货审核撞 23514)
由 V641 一并放开。`production_material_analysis:over_supply` 权限照旧要。

### 2.3 批准：计划行落「子件」，不是目标件

财务批准同事务里，这类订货明细落一条新流向
`subcontract_material_plan_items.flow_mode = 'COMPONENT_OUTBOUND'`：

| 列 | 取值 | 单位 |
|---|---|---|
| `parent_goods_id` / `parent_color_id` | 订货**目标件** | — |
| `goods_id` / `color_id` / `unit_id` | 那颗**子件** | — |
| `unit_rate` | 恒 `1` | — |
| `bom_unit_qty` | `round6(订货换算率 × BOM 单耗)` | 子件基本量 / 目标件**订货**单位 |
| `planned_qty` = `prepared_qty` | `round4(订货量 × bom_unit_qty)` | 子件基本量 |
| `preparation_status` | `READY_OUTBOUND` (批准即待出仓)。ADR-101 起这个取值不变，但**批准时子件一件都没有就不建出仓草稿、也不通知仓库**，任务停在「等子件到货」；子件入库后由唤醒补开草稿 | — |
| `bom_has_children_snapshot` | `TRUE` | — |
| `preparation_bom_fingerprint` | **目标件**的 BOM 指纹 | — |

物理形态与 V304 的 `LEGACY_BOM_COMPONENT` 完全一致，但**必须是新的独立取值**：
LEGACY 行是不可改写的历史事实（无专属预留、无 BOM 快照、不受出仓分配断言约束），
新流向要享受 V436 之后的专属预留、出仓分配断言与 V507 守恒。两者混为一谈会让
历史对账再也分不清「哪些是 V304 留下的」。

**一条订货明细只出一条 COMPONENT 行**，不做「先吃目标件现货 DIRECT + 余量另走」的拆分。
理由：回厂消费按「货品+颜色」分组逐组扣满，同一明细上混两种发出物会两组都扣不够，
把单据永久卡死。数据库另有 `subcontract_component_outbound_exclusive_guard` 兜底。

### 2.4 出仓：仓库发的是子件，有货才给仓库派活(本节已由 ADR-101 改写)

出仓草稿、专属预留、出库流水全部落在**子件**维度，这一条不变。变的是「什么时候才把这张单
交到仓库手上」：

- **没货不开单**：批准时先看那颗子件此刻在各个作业叶仓的合格可动用量，据此挑发料仓、定本批
  数量；一个仓都拿不出货，就不建出仓草稿、也不通知仓库，任务停在「等子件到货」，在列表里
  看得见但不催人动手。
- **到一批发一批**：每张草稿的数量取「计划还差多少」与「该仓此刻能动用多少」两者中的小值。
  子件陆续采购入库，系统就陆续叫醒这一行、补开或改大草稿，并告诉仓库「现在可发多少」，
  不必等凑齐整批。
- **可发数量由服务端算好下发**：界面上的「本次最多」和「仓内可动用」都是服务端给的，
  仓库不用自己猜是计划没量还是仓里没货。
- 出仓审核消费本行专属 `SUBCONTRACT_OUTBOUND` 预留，`fn_assert_subcontract_outbound_issue_allocation`
  要求「已审出仓量 = 专属预留精确覆盖」(与目标件三种流向同款)，不变。

原文那句「保存草稿时按子件库存校验、不足即 409——这正是用户要的那道门禁，不需要另立一道
齐套闸」**已被推翻**：它把一道**保存时的事后闸**当成了**下达时的前置门禁**。任务照样派下来、
仓库照样看得到、点得进、填得了，只有最后保存那一下被拒——人已经白跑一趟。保存校验仍然留着
兜底，但门禁本身前移到了「建不建草稿、通不通知仓库」。

- **2026-09-22 ADR-103**：门禁再前移一次——路线 B 的锁与路线 A 同位，落在**下单前**(任务中心申请行、
  建单/改单、送审、批准四层)，判据「子件在作业叶仓的合格可动用量合计 > 0 即解锁」；「批准后有货才派活」
  降级为兜底。任务中心锁行显示「等子件到货」(黄、不可勾选)，解锁后显示「子件已到货 可下单(仓内可动用 X 单位)」；
  仓库出仓列表对无草稿且可发 0 的计划显示状态桶「等子件到货」，不再显示「目标件已备齐，待出仓」。
  唤醒收口到 `StockService` 入库方向，不再只挂采购 IQC 入库。详见 ADR-103 §2.1 / §2.2 / §2.3。

### 2.5 回厂：交回目标件，按冻结单耗倒扣子件

回厂登记、IQC、仓库确认入库全部针对**目标件**，与既有链完全一致。消费侧按
`frozen_unit_qty`（= 计划行 `bom_unit_qty`）把回厂量折成子件量倒扣供应商处保管台账，
`consumption_basis` 落 `FROZEN_BOM_ESTIMATE`（发出物与回厂物不同货号，天然不是
`DIRECT_TARGET`）。

先出后进与消费守恒因此必须**先折算再比**：

```
子件基本量 ÷ frozen_unit_qty      = 目标件订货单位数
目标件订货单位数 × 订货换算率      = 目标件基本量
```

单耗 ≠ 1 时不折算会把「发 1 颗子件、回 1 个目标件」误判成超收。服务端四处镜像
（回厂审核 / 回厂草稿预检 / 出仓红冲 / 到货登记额度）共用
`SubcontractOutboundFlowSql.ISSUED_TARGET_BASE_SUM` 一个片段，数据库侧由
`fn_assert_subcontract_target_outbound_receipt` 用同一因子把关。

### 2.6 物料分析：子件需求必须保住，发出去以后才归零

这是最容易算错的一块，两件事必须同批做：

1. **委外申请在途不再净掉下层**：这类节点的 `SUBCONTRACT_APPLICATION` 供给按
   `INTERNAL`（已承诺我方供料）分类，而不是 `EXTERNAL`（外部最终件在途）。
   否则一点「下达委外」，子件需求当场归零——没人去买那颗子件，仓库永远发不出货。
   分类改变不动数量，「两类相加 = 历史口径」的不变式仍成立，主表「尚需下达」不变。
2. **已发给委外商的部分要扣掉**：`loadSubcontractComponentIssuedByNode` 把已审出仓量
   折成目标件基本量，从父件驱动量里扣除（与 V447 跨分析接管同一个扣减位）。
   否则料一出仓、子件库存归零，界面立刻又报一份同样的缺口，计划员会重复采购。
   这与自制链的 `formalMaterialCoverage`（已领料覆盖本批需求）是同一件事，
   只是这里的「领料」是发给委外商。

### 2.7 界面

- 服务端在 `MaterialView` 上新增只读字段 `subcontractOutboundForm`，取值
  `"COMPONENT_OUTBOUND"` 或 `null`。**null 一律按旧口径回退**（有子层 ⇒ 先自制），
  旧服务端与新服务端的「不是这种形态」都是 null，客户端行为一致。
- 「父件 + 下层一起下单」整页（ADR-081 §3.8）的分流改口径：
  - **父件走哪条通道 / 能不能改量** → 看 `_subcontractNeedsPreparation`
    （= 有生产性子层 **且** 不是 COMPONENT_OUTBOUND）；
  - **要不要把下层拉进来一起办** → 仍看 BOM 形状（`_analysisMaterialHasChildren` /
    `_hasProductionBomChildren`）。这类件**必须**继续下钻——那颗子件正是我方要备的料。
  两个谓词不能互换：换错的症状不是报错，而是「整页少了一行」或「父件下达了却没人备料」。
- **仓库出仓页**(原文漏掉的一环，由 ADR-101 §2.4 补上)：本节此前只规定了物料分析侧，
  对仓库自己那张出仓单一字未提，于是前端的流向清单里根本没有这一种，整行被判成「未知」
  并保守地把可填数量压成 0——同一行上「已备齐 1000」和「本次最多 0」并排显示，
  **子件有没有货都发不出去**。三件事必须一起做：流向清单登记本形态；父件列对这类行
  同样出列、列名从「历史父件名称」改成「回厂交回的委外件」(发出去的是子件，交回来的
  才是委外件)；明细表增加「仓内可动用」一列，排在「本次最多」前面。
- 「采用公共在途」资格**已由 ADR-101 §2.7 改写**：这类委外件现在可以认领别人计划里已经
  下好、料也由别人备的那一批公共在途——下达时服务端先认领、只为余下部分新下单，界面
  「还需安排」是否直接显示扣掉可认领量之后的净数，由物料分析主表那一路决定，不在本形态范围内。
  **自己造公共超量备货仍然禁止**，服务端与数据库按原口径拒绝。
- **2026-09-22 ADR-103 仓库段补充**：出仓任务列表新增状态桶「等子件到货」(`WAITING_COMPONENT`)，
  列表项带「可发合计」(`issuableTotal`)与等料行数(`waitingComponentLineCount`)；拣货页「本次出库」预填可发量，
  可发 0 的行显示「等子件到货(仓内可动用 0)」；明细表新增「建议发料仓」列，无草稿时「发出仓」下拉预填服务端
  算好的 `stockWarehouseId`；批量出库页按行放行(可发 0 的行取消勾选并标「等子件到货」)。详见 ADR-103 §2.4。

## 三、不变量

1. 判据只有一个来源 (`fn_subcontract_sole_component_goods`)；Java 三处都调它，不各抄一遍。
   补注：这条不变量曾被一处内联副本破坏(那份副本还漏了一个条件)，ADR-101 已把它改回调用
   函数本体。
2. 一条订货明细的发出物身份唯一：要么全是目标件，要么全是那颗子件。
3. (按 ADR-101 §三改写)仓库**看得到活** ⟺ 那一行此刻真的拣得出货：没货时不建草稿、
   不发通知、不进红色待办；开出来的草稿数量永远 ≤ 该仓此刻的合格可动用量，系统不再生成
   一张注定存不下去的草稿。没有第二条捷径，也没有负库存。
4. 回厂量与出仓量的比较**永远先按冻结单耗折算**；缺冻结单耗的行按 0 计（fail-closed），
   不虚增可回厂额度。
5. 前置自制、目标件出仓、LEGACY 三条既有链的行为与字节一个都不变。
6. 本形态**不支持**损耗补量（V525 的补量算式只认 `DIRECT_OUTBOUND`），用 CHECK 焊死，
   不留「有额度却无人校验」的 fail-open。

## 四、明确不做

- **不做 BOM 深度 ≥ 2 的「多层直接外发」**：一次发多颗子件意味着回厂时要在多组之间
  分摊消费，V221 守恒与 IQC 返修额度都要重做，不在本轮范围。
- ~~**不放开公共超量备货**~~：2026-09-21 已放开(见 §2.2 修订 / V641)——ADR-099 修订让多下的量按计划产出量带大子件需求，「下层责任账」就是层级表本身。
- **不放开跨计划在途调拨把这类件当来源**(ADR-101 起要分方向看)：
  - **当来源**——把这类件的在途让给别的计划去用，**仍然不放开**：
    `fn_preplan_future_source_private_capacity_qty` 对有 BOM 的委外件容量恒 0 (V571)，不动。
  - **吃别人的公共在途**——认领别人已经下好、料也由别人备的那一批，**已由 ADR-101 §2.7 放开**：
    认领不会给本计划这一层多出任何子件需求，所以不受那条禁令约束。
  - 注意这两条与上一条的「自己造公共超量备货」是三件不同的事，三者现状：
    自己造超量备货**已放开**(V641)、吃别人的公共在途**已放开**(ADR-101)、
    把自己的在途让给别人当来源**仍禁**(V571)。
- **不改 V507 对 `PREPARED_OUTBOUND` 的既有遗漏**：那条白名单今天就不含它，
  补上会让存量单立刻开始受约束，可能炸出历史脏数据，单独排期。
- **不做成本终态**：`consumption_basis` 仍只有 `DIRECT_TARGET` / `FROZEN_BOM_ESTIMATE`
  两个取值，本形态落后者（与 LEGACY 现状一致）。要给它一个独立的成本终态需要
  同时改 V522/V525/V526 三处镜像，单独排期。
