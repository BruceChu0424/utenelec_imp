# V807 员工证件号校验状态

本迁移只给 `employee_sensitive` 加一列 `id_card_check` 和两个约束，不加表、不改其它表，也不修改任何证件号密文。V807 是开发期临时号，合并时按当时 main 的最新号加一重新编号。本文不代表业务数据库已经安装。决策见 [ADR-154](../99-决策记录-ADR/ADR-154-证件号问题不阻塞开号与证件核对任务.md)(ADR 编号同样可能重编)。

- 背景：给已有员工补开登录账号时，证件号缺失或身份证号校验不通过不再拦开号，只提醒，并在人事任务中心生成「证件核对」任务。提醒和任务列表不能每次都把在职员工的证件密文全部解密一遍，所以校验结果在写证件号时判定一次，存成一列。
- 取值：`valid`、`unchecked`(历史导入、还没判定)、`unreadable`(启动回填任务解不开密文：数据损坏，或密钥版本不在密钥环里)，或一个具体问题码：`empty`、`length:<n>`、`character:<位置>`、`birth_date`、`birth_too_early`、`birth_future`、`region_code`、`sequence_code`、`check_digit`(每个码对应的说明见 ADR-154 §3.4 或[员工详情页](../03-页面/员工详情页.md) §十)。问题码只含位置和长度，不含号码本身，属于非敏感元数据，照常进审计，不加入审计脱敏函数。
- 约束：
  - `employee_sensitive_id_card_check_value_ck`：正则只允许上面这些值(长度码最多 3 位，位置码最多 2 位；Java 侧超长按 `length:999` 存)；
  - `employee_sensitive_id_card_check_presence_ck`：`(id_card_enc IS NULL) = (id_card_check IS NULL)`，有证件号密文就必须有校验结果、没有密文就没有结果。以后任何新写入口如果忘了写校验结果，会直接被数据库拒绝。
- 存量数据：数据库拿不到解密密钥，迁移只能把已有密文标成 `unchecked`。服务端启动时由 `EmployeeIdentityCheckRunner`(`@Order(61)`，完成前保持 `REFUSING_TRAFFIC`)解密判定并写回：
  - 和 V282 回填任务、老库人事导入脚本共用同一把 advisory lock `(0x5554454E, 282)`；
  - 按 `employee_id` 键集分页，每批 100 条，每批一个短事务，逐行用 `TxSessionVars.tryDecrypt` 解密：在保存点里执行，某一行解不开只回滚到保存点，本批事务照常可用，也不经 Hibernate 报 ERROR；
  - 条件更新带上 `id_card_check = 'unchecked'` 和原密文，期间人事已修改的行不会被覆盖；
  - 解不开的行存成 `unreadable`，不阻止启动，以后启动也不再重试；人事任务、开号就绪检查、员工详情和补开账号结果都显示「档案里的证件号码读取不出来，系统无法校验，请人事对照证件重新登记」，开号不拦、初始密码随机；人事对照证件重新登记一次号码，写入口按新号码改写校验结果，任务结案；
  - 员工详情(开号结果同源)读取时解不开，不管存的是什么都按 `unreadable` 提醒；人事任务和就绪检查不解密，按存的结果；
  - 换密钥后没配旧密钥造成成批 `unreadable` 时，配好旧密钥后执行 `UPDATE employee_sensitive SET id_card_check = 'unchecked' WHERE id_card_check = 'unreadable'` 再重启一次，即可重新判定；
  - 日志只写数量(合格、有问题、解不开、并发跳过)，有解不开的行时一条 WARN 汇总，否则一条 INFO 汇总，没有逐行日志，不写号码、后四位或姓名。
- 老库人事导入脚本(`migrate_hr_roster.sql`、`migrate_hr_workers.sql`)写入证件号密文时同时写 `unchecked`(源值为空时为 NULL)，`ON CONFLICT DO UPDATE` 同步覆盖；导入后服务端下次启动时自动完成校验。`build_hr_roster.py` 的证件相关告警不再打印证件号、姓名和出生日期(含由证件号推出的)，号码长度或字符不对时只告警不崩溃。
- 写入路径：服务端只有 `EmployeePiiWriter.applyIdentity` 写证件号密文，同一处写校验结果；入职和「修改证件信息」(`POST /api/org/employees/{id}/change-identity`)仍然严格校验，校验不通过时报出具体哪一位、哪一项不对。`ArchitectureBoundaryTest` 锁定：只有 `EmployeePiiWriter` 调 `setIdCardCheck`，SQL 写 `id_card_check` 只在回填任务。

`UPDATE` 会对每条有密文的员工敏感行产生一条只记录 `id_card_check` 变化的审计行。清库策略不变(只加列)。
