# 数据保护与加密分级

> 状态：架构基线已确定；生产数据库 TLS 门禁、V282/V286/V287 员工扩展 PII 迁移链与 V284 个人信息变更敏感快照保护均为源码候选。外部 KMS、LUKS、其余字段迁移及目标环境验收尚未实施，生产仍为 **NO-GO**。
> 最后更新：2026-08-14
> 决策依据：[ADR-037：数据库数据保护与分级加密](../99-决策记录-ADR/ADR-037-数据库数据保护与分级加密.md)
> 迁移目录边界：截至本次文档冻结，共享工作树最高 V289，共 270 个迁移文件、270 个唯一版本且无重复；V283 是生产关联订货审批快照锁守卫修正，V284 才是个人信息变更敏感快照与历史审计副本保护，V285 收紧客户默认结算方式 UUID，V286 只允许 V282 回填创建不含证件号/主手机号的扩展-only 敏感行，V287 仅保证主身份密文为空时相应 HMAC/last4 派生值也为空；V286/V287 都不扩大加密字段范围。V288/V289 涉及现货借用表、终态守卫和全 `public` 审计覆盖；在线链虽已接通为源码候选，但不增加加密字段，也不代表目标库已应用或验收。

## 一、结论

不能、也不应该把数据库里每个字段都改成应用不可读的密文。

- 金额、数量、汇率、余额、税额、成本、借贷发生额等需要在 PostgreSQL 内执行 `SUM`、范围过滤、
  排序、索引、约束和借贷平衡校验，继续使用精确 `NUMERIC`。随机加密会直接破坏这些能力；确定性或
  保序加密又会泄漏低熵金额的相等关系和大小关系，不能当成安全替代品。
- 身份证、银行账号、税号、私人联系方式、地址、官网询盘正文等高危、非计算型数据，才适合在选定
  KMS/HSM/Vault 后逐步迁移为应用侧 AES-256-GCM envelope encryption。
- 当前并非从零开始：员工、薪酬、紧急联系人/备用手机和部分访客字段已有版本化 `pgcrypto` 密文；V282
  又为 7 个员工扩展 PII 字段提供了同体系的迁移候选，V286 使没有主身份密文的 bootstrap/legacy 员工也能仅迁入实际存在的扩展值。但该密钥由应用环境注入、加解密调用在 PostgreSQL
  `pgcrypto` 中执行，不是外部 KMS envelope，也不能代表全库或目标生产已经加密验收。
- V284 把 `profile_change_requests` 中手机、户籍地址和全部紧急联系人 old/new 审批快照纳入同一版本化
  `pgcrypto` 过渡路径；非敏感审批快照仍为 `PLAIN`。它同时清除历史 `audit_log.before/after` 中重复的快照键，
  但同样不是外部 KMS envelope，也不证明目标库已经迁移或历史明文已经清零。
- “别人偷走硬盘、快照或备份后看不懂”主要由数据卷加密、异地备份加密和密钥分离解决；“拿到数据库
  读取权限后仍尽量看不到 PII”由应用侧字段加密、最小权限、DTO 脱敏和审计解决。这是两个不同威胁，
  不能用一层控制互相替代。
- PostgreSQL 16 本身不能在本项目中宣称已提供透明数据加密（TDE）。磁盘静态加密必须由 LUKS2、
  加密云盘或等价存储层承担。

## 二、数据分级与默认控制

| 等级 | 典型数据 | 数据库形态 | 必需控制 |
|---|---|---|---|
| S0 密钥/认证秘密 | 密码、refresh token、OTP、JWT/PGP/HMAC/备份密钥、AK/SK | 密码/OTP/token 只存不可逆摘要或撤销事实；部署密钥不入业务表 | 外部秘密管理、独立用途密钥、轮换、最小可读主体、禁止日志/导出 |
| S1 高危非计算 PII | 身份证、银行卡/银行账号、税号、私人手机/邮箱、地址、官网询盘正文、敏感人事附件 | 现有局部员工/访客字段为版本化 PGP 对称密文；目标为 AES-256-GCM 密文 + key id + nonce/tag；精确查重另用域隔离 HMAC | 现有 `pgcrypto` 过渡控制 + 目标应用侧 envelope、字段级权限、默认脱敏、导出审批与审计 |
| S2 财务/薪酬计算事实 | 金额、余额、汇率、税额、成本、借贷发生额、工资计算结果 | 保持精确 `NUMERIC`，不做逐列随机/确定性加密 | 加密卷、加密备份、TLS、对象范围、财务权限、制审分离、不可变过账/红冲、审计与对账 |
| S3 内部经营数据 | 数量、交期、单号、货品、客户/供应商名称、BOM、库存 | 原生可查询类型 | 最小权限、对象范围、行级业务守卫、审计、备份与恢复 |
| S4 公开数据 | 官网已发布内容、公开产品资料 | 原生类型 | 完整性、发布审批、备份 |

同一张表可以同时包含多个等级。例如账户余额是 S2，账户银行账号是 S1，账户名称可能是 S3；不能按
“整表统一加密”替代逐字段分类。

## 三、纵深防御与威胁边界

| 威胁 | 主控制 | 仍然不能防住什么 |
|---|---|---|
| 物理磁盘、云盘快照被盗 | LUKS2/加密云盘，密钥与数据分离 | 已解锁运行中的主机、应用账号查询 |
| 备份介质或对象存储泄漏 | pgBackRest 仓库加密、异故障域、受控读取身份、恢复演练 | 同时取得备份密钥的攻击者 |
| 数据库链路窃听/中间人 | 非回环生产 JDBC `sslmode=verify-full` + 显式 `sslrootcert` | 已入侵应用或数据库主机 |
| 业务账号越权 | 细粒度权限、对象范围、DTO 脱敏、导出权限、审计 | 数据库超级用户、应用主机 root |
| 只读数据库凭据/逻辑 dump 泄漏 | 最小数据库角色、凭据隔离；现有已覆盖字段的 PGP 密文；目标 S1 应用侧 envelope | 当前未覆盖的 S1 与原生 `NUMERIC` 的 S2/S3 仍可读，因此磁盘加密不能替代访问控制 |
| 数据库管理员读取 | 目标方案在应用侧加解密且 KEK 不进入数据库 | 当前 `pgcrypto` 的密钥参数会进入数据库执行过程，不能抵抗运行中高权限观察；目标方案也不能抵抗同时控制应用运行时和 KMS 授权者 |
| 应用主机被攻陷 | 外部 KMS/HSM/Vault、短时 DEK 缓存、双人轮换/吊销 | 已获得合法解密权限期间的在线读取 |

## 四、当前源码与真实落地边界

### 4.1 已有或本轮补齐的源码候选

- V03 以来的 `employee_sensitive` 已将证件号、主手机号、员工银行账号/支行保存为 `pgcrypto` 密文，

  访客身份证/手机号也走既有密文路径。证件号、主/备用手机另有 HMAC 查重或查询派生值。覆盖并不等于整张

  `EmployeePiiExtraBackfillRunner` 在应用启动期迁入。runner 与两份受审 HR 导入脚本共用 PostgreSQL 全局迁移锁，

  重载失败、既有密文冲突/不可解、条件写失去所有权或最终明文残留非零都会使启动失败，

  为了满足形式上的 1:1 而创建空 sensitive 行。
- V287 为上述可选主身份补数据库一致性约束：`id_card_enc IS NULL` 时 `id_card_last4/id_card_hash` 必须都为空，`phone_enc IS NULL` 时 `phone_hash` 必须为空。它不会要求主身份必须存在，也不会生成、加密或删除任何身份值；目标库迁移前仍须先盘点不满足约束的异常行，不能通过伪造主密文绕过。
- 上述现有密文依赖应用环境提供的版本化 PGP 主密钥和 PostgreSQL `pgcrypto` 函数；历史 key 由应用配置的

- V284 为 `profile_change_requests` 新增权威 `value_encoding` 状态：敏感快照新写必须为带领域标记的

  或轮询历史 key，无法解密就保留原行并中止。数据库写守卫阻止未完成历史行继续流转，并要求每次敏感 INSERT/UPDATE

- 明确的 `localhost`、`localhost.`、`127.0.0.0/8` 和 IPv6 `::1` 可继续用于本机开发、测试及固定的

- 没有选定 KMS/HSM/Vault 供应商，也没有实现假的本地 KEK 代替外部密钥管理。
- 客户/供应商的电话、邮箱、地址/收货地址、银行账号、税号，账户 `bank_account_no`，官网询盘的电话、邮箱、
  正文、短期 `visitor_sms_codes.phone`，以及 `profile_change_requests.review_comment` 等自由文本、姓名等按策略

  尚未把这些 S1 字段迁移到应用侧 envelope encryption，也没有完成附件内容的逐文件 envelope/SSE-KMS 方案。
- 没有在目标数据库验证 V282/V286/V287 已应用、启动回填完成、原明文清零、需要迁移扩展 PII 的缺失 sensitive 行均已
  安全创建、扩展-only 行无法开通账号、新旧密钥均可恢复；源码与单元测试不能替代这份目标数据证据。
- 没有在目标数据库验证 V284 已应用、`LEGACY_UNKNOWN` 已归零、全部敏感快照可用当前/历史 keyring 解密、
  历史 `audit_log` 快照键已归零，或提交、查看、批准/驳回链路已由真实岗位回归。
- 没有对目标服务器执行 LUKS 格式化、卷迁移、解锁策略变更或生产数据库写入。
- 没有目标数据库字段盘点、历史明文数量、旧备份到期日、密钥轮换和灾难恢复验收结论。

## 五、S1 应用侧 envelope encryption 目标合同

选定密钥服务后，统一加密组件至少满足：

1. 每个密文使用 AES-256-GCM 和新的随机 nonce；禁止 nonce 重用、ECB、固定 IV 和自行设计密码算法。
2. 数据密钥（DEK）按安全域隔离，由外部密钥加密密钥（KEK）包裹；数据库只保存密文、包裹后的 DEK
   或其引用、`key_id/key_version`、nonce 和 tag，不保存 KEK 明文。
3. AAD 至少绑定环境、表、列、记录 UUID 和 schema/encryption version，防止跨记录或跨列搬运密文。
4. 精确查询/查重使用单独用途、可轮换的 HMAC 键；PII lookup HMAC、附件授权 HMAC 和其它签名密钥不得复用。
5. 解密仅在已授权的服务方法发生；列表、搜索、日志、审计 before/after、异常和导出默认不出现完整明文。
6. DEK 缓存必须短时、有界、可清理；KMS 不可用时失败关闭，不得回退到源码、数据库或普通配置文件中的
   固定明文主密钥。
7. 密钥轮换保留明确版本和旧密钥只读窗口；在所有受保留备份过期且恢复演练完成前，不删除旧解密能力。

## 六、旧数据和数据库迁移顺序

金额、数量、汇率和账簿余额不改密文，也不因新策略重编号或重算。V282/V286/V287 的员工扩展 PII 迁移链和 V284 的审批敏感
快照使用当前 `pgcrypto` 兼容迁移路径，仍需按本节的盘点、回填、核对和目标验收门禁执行；后续纳入外部
KMS/envelope 的历史列使用前向、可核对的迁移，不直接覆盖原列：

1. **盘点与冻结合同**：导出表/列分类、行数、NULL/格式异常、引用/导出/搜索路径和旧备份保留期；先完成
   可恢复备份与隔离恢复演练。只读盘点不是生产写入授权。
2. **Expand**：新增 ciphertext、nonce/tag、key id/version、按需 HMAC 和 migration status 列；不删除明文列。
3. **Dual read / dual write**：新写同时产生新密文；读取优先密文并受控回退旧明文，记录回退指标，禁止静默丢值。
4. **Backfill**：按主键小批次、幂等、可暂停地回填旧行；记录批次、成功/隔离/失败数量，不在日志输出明文。
5. **Verify**：核对总行数、非空计数、HMAC 唯一/冲突、授权 DTO、搜索、导出、审计和抽样解密；失败行隔离，
   不用空值覆盖。
6. **Cutover**：停止明文回退，强制新路径；观察一个完整业务/备份周期，并完成新旧 key 的备份恢复和轮换演练。
7. **Drop later**：确认所有旧应用已下线、回滚窗口关闭、包含明文的备份已到期或受控销毁后，另一个前向迁移
   删除明文列。不得修改已应用 Flyway，也不得用旧 JAR 连接新 schema 回滚。

V282/V284/V286/V287 发布必须采用停写、排空旧实例、单版本切换：不能让不理解当前密文/可选身份约束的旧实例与新 schema 并存，也禁止把旧 JAR
作为应用回滚手段。V284 以后旧代码会把领域密文当业务值，数据库 capability 会主动拒绝该写入；失败后只允许
前向修复，或在隔离环境验证后恢复数据库与对应旧版本的完整一致备份。受审 HR 导入必须持有 V282 专用 advisory
lock 与 legacy-import capability，并在释放流量前由 runner 完成加密、清零和残留核对。

旧库导入必须额外保存来源系统、来源表、旧主键、导入批次和校验结果。历史异常先形成冲突清单；不能为了
“看起来整齐”而直接改掉财务历史、原单号或审计链。

## 七、需要用户确认后才能实施的生产决策

1. KMS/HSM/Vault 供应商、地域、可用性、费用、RAM/角色模型和灾难时的密钥恢复方式。
2. LUKS2/云盘范围（仅数据卷还是根盘也覆盖）、启动解锁方式（控制台口令、TPM2+PIN、恢复密钥）、
   双人保管和失钥演练；这些选择直接影响无人值守重启和 RTO。
3. pgBackRest 异故障域/WORM 位置、RPO/RTO、保留期，以及旧明文备份何时可以销毁。
4. 第一批纳入 S1 迁移的字段、维护窗口、回滚观察期和业务/财务抽样签字人。

在上述选择确认前，只允许继续做只读盘点、源码接口/测试和迁移 dry-run；不得修改目标服务器卷、生产密钥、
生产数据库或切换线上读取路径。

## 八、验收门禁

- 源码：TLS 门禁正负向测试、加密组件已知向量/篡改/AAD/nonce/轮换/并发测试、DTO/导出脱敏测试通过。
- 数据：expand/backfill/cutover 每阶段的行数、NULL、冲突和抽样解密对账通过；金额/总账/余额不发生变化。
- V282/V286/V287 专项：7 个旧明文列均为零残留；每名具有待迁移扩展 PII 的员工都有唯一、可解密的
  `employee_sensitive` 行，完全没有敏感值的员工允许无行；扩展-only 行的证件号/主手机号及对应 HMAC/last4 均为空，
  且补开账号失败关闭；`birth_month_day` 数量与合法生日一致；员工列表、详情、变更审批、生日通知和导出权限回归通过。
- V284 专项：`value_encoding='LEGACY_UNKNOWN'` 为零；手机、户籍地址和全部紧急联系人快照均为
  `PGCRYPTO_V1` 且可用当前/历史 keyring 解密，非敏感字段均为 `PLAIN`；两种历史 profile-change target type 的
  `audit_log.before/after` 均不再包含 `old_value_enc`、`new_value_enc` 或 `review_comment`；在线提交、员工查看、
  HR 查看/批准/驳回、乐观锁冲突和旧 key 解密回归通过。任何无法判定/解密的历史行须保持失败关闭并形成不含
  明文的人工处置清单，不得跳过后宣称完成。
- 附件专项：敏感人事附件的对象级越权测试通过；若采用 LUKS、对象存储 SSE-KMS 或逐文件 envelope，必须分别
  提供离线不可读、错 key 失败、轮换与隔离恢复证据。V280/V281 的权限和元数据本身不算内容加密证据。
- 目标数据库：实际 app role 使用 `verify-full` 成功，错 CA、错主机名、缺证书必须失败；数据库角色和审计权限复核。
- 存储：断电重启解锁、磁盘/快照离线不可读、旧卷回退方案及恢复密钥双人取用演练通过。
- 备份：从异故障域加密备份恢复到隔离环境，验证 PITR、旧/新 key 版本、附件版本和业务对账；只看到脚本配置不算验收。
- 运维：密钥轮换、紧急吊销、KMS 断链、应用主机丢失、备份密钥丢失和证书续期都有演练证据与告警。
