# V530 业务事实审计覆盖与稳定对象来源

V530修复新增业务表的未来写入审计覆盖，保留现有数据和审计历史。正式资源为 [V530__refresh_audit_trigger_coverage.sql](../../server/src/main/resources/db/migration/V530__refresh_audit_trigger_coverage.sql)。本迁移没有新增、删除业务表，不改变数量、金额、库存锁或成本计算，清库表分类无需新增条目。

## 一、确认的问题

V503的三张来源改量事实表只有 `AFTER ROW INSERT` 审计，`tgtype=5`；“有一个trg_audit”不能证明有效覆盖。正式规则要求唯一启用的 `AFTER ROW INSERT/UPDATE/DELETE` 审计。受影响表是：

- `procurement_order_source_revisions`
- `procurement_order_source_revision_allocations`
- `procurement_order_source_revision_peg_changes`

V500/V506/V517的库存价值、开账、来源分配及执行状态等新表还缺少审计触发器。V514/V518/V522已经提供完整触发器的表保留其合法既有触发器，不再重复创建。

部分新表以 `event_id`、`input_node_id`、`execution_segment_id`或复合键作为主键，既有通用审计只寻找id、单号等字段，导致 `target_id` 为空。单纯挂触发器不足以形成可定位的对象证据。

## 二、前向修复规则

1. 仅对上述三张V503表识别已知历史形状：准确触发器名、public.fn_audit()、AFTER ROW INSERT、O/A启用、无参数、无WHEN、无列限定、无延迟/transition table，且只有一个审计前缀触发器。符合时改为完整I/U/D并启用ALWAYS。
2. 扫描全部public普通表和分区父表。合法既有审计保持OID、名称、函数引用与启用模式；缺失时创建完整I/U/D审计并启用ALWAYS。
3. 同名前置/语句级/不完整事件、禁用/仅replica、未知函数、WHERE或UPDATE列限定、额外参数、重复审计等异形失败关闭。额外的非标准名称触发器若也调用通用审计函数，同样拒绝，防止一次写入重复记账。
4. 最后再次核验全部应覆盖表。未知形状须先独立核实来源，不能用删除触发器或加入白名单掩盖。

迁移以Flyway事务执行，失败整体回滚。旧行不更新，既有审计不补造、不改写。

## 三、保留的例外

沿用既有审计汇点/归档、Flyway与legacy_migration元数据、编号计数器、授权epoch、凭证材料等技术例外；继续保留 [V424](62-V424审计日志降噪与中文化.md) 的11张通知、发件箱、汇总和幂等机制表，以及V454的 `notice_celebration_subjects`。

没有新增库存价值表例外。`stock_value_jobs`、`stock_value_tasks`、生产成本任务/份额/dirty状态带有金额、分配结果或来源修订信息，参与价值是否完成的判定，应保留变更证据，不能仅因由后台处理就归为普通通知队列。

`master_code_sequences`保持V505确认的计数器例外。安全测试的排除集合据此补齐；委派测试改为重放当前V530全量sweep，避免旧V325把V424已退役的噪声审计重新挂回。

## 四、对象身份与原责任人

`fn_audit_primary_key_identity`读取实际主键元数据。旧id/单号等解析结果非空时维持原结果；原结果为空时，单列主键使用该值，复合主键使用稳定的键值JSON。变动金额、数量或状态不会改变对象身份。

审计执行者仍来自当前事务的 `app.actor_id` 等上下文。后台没有登录会话时保留系统执行语义；原业务责任人由不可变的价值事件/成本修订中的 `actor_user_id`、`actor_employee_id` 及来源UUID追溯。V530不伪造登录会话、不改worker责任信息。

未来审计副本延伸现有最小化规则，排除 `request_payload`、`input_snapshot`、`output_snapshot`、`before_balance`、`original_balance`、`original_pool`、`approval_evidence` 等原文/大型快照。原业务证据仍保存在业务台账；审计保留标量金额、数量、版本、责任UUID、来源键及哈希。既有V398等PII最小化规则原样保留。

## 六、V531：主键 INCLUDE 列不参与对象身份

V530之后的独立回滚探针确认：PostgreSQL的 `pg_index.indkey` 同时包含主键列与 `INCLUDE` 附带列。V530遍历全部列，在 `PRIMARY KEY(event_key) INCLUDE(quantity)` 或复合主键附带数量列时，会将数量写入备用身份，数量变化会拆分同一对象的审计历史。

只读检查当时的V529标准库与服务器升级副本，各有396个public主键，均无 `indnatts > indnkeyatts` 形状；现有表没有该问题的直接影响。旧id、单号等优先身份非空时也不会进入备用主键解析。该结论限于已检查的两个副本，不替代其他目标库核验。

[V531__audit_primary_key_identity_excludes_include_columns.sql](../../server/src/main/resources/db/migration/V531__audit_primary_key_identity_excludes_include_columns.sql)只替换备用身份函数，增加 `key.ordinality <= index_row.indnkeyatts`，限定为实际主键列。单列返回值、复合键JSON、无主键时的NULL及既有优先身份规则保持不变；不改V530字节、不新建业务表、不重写业务或审计历史。

`AuditTriggerCoveragePostgresTest`新增单列、复合主键两条真实触发器回归：创建带INCLUDE数量列的临时表，插入数量1、更新为9再删除，检查三条审计使用相同且准确的主键身份，同时保留各次原数量/新数量。每条测试结束回滚临时表和审计数据。只读探针及其回滚结果仍归档在 `.codex-tmp/audit-v530/pk-include-*`。
