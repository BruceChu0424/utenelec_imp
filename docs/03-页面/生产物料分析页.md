## 一、员工看到的主流程

```text
已审核销售订单行 / 合法手工需求
  → 选择产品与本次需求数量
  → 选择主仓库范围，核对实际领料子仓
  → 联合分析，查看产品层级或按物料汇总
  → 核对主档建议；改单行供应方式后确认立即保存，或勾选多行点击“确认路线”(同事务回写货品主档来源)
  → 分别进入“下达采购 / 下达委外 / 下达车间”
     ├─ 采购：确认需求与独立公共补库/备货，形成采购申请
     ├─ 直接外发的委外：形成委外申请（两类——无子层的纯外协；
     │   以及「活动 BOM 恰好只有一个 PER_UNIT 叶子子件」的我方供料件，
     │   仓库发的是那颗子件、委外商交回目标件，见 ADR-085）
     └─ 自制（顶层产品/候选/**需先自制的**有子层委外/已建子件一视同仁）：
        填「本批数量 + 生产车间 + 负责人」→「创建生产计划」单次原子提交
        （服务端一个事务：候选先建子件任务 → 逐行生成计划 → 有审核权同事务审核下达；
         任一行失败整体回滚，失败不再残留已建子件行）
        → 下层还有没下单的时**先弹**「跟父件一起办」（§3.8 弹窗前置）：数量按本批数量
          算好可改，一键下单按序提交父件 + 下层（采购 / 无子层委外 / 回车间分流），
          下层全已下单则不弹、父件直接提交；委外桶有子层行同款
  → 计划不再做齐套判断：缺料批次以 WAITING 下达（零预留、无 DRAW）
     → 本执行批完整齐套后原子提升 READY，生成内部预留与分仓 DRAW
     → 尚未整批齐套时，可在车间按当前完整套料量核对并显式拆出子批
  → 车间在领料汇总中勾选物料、填写本次申请量并提交，仓库才收到可办理任务
  → 仓库实际发齐本执行批的正式需求，车间明确开工
  → 报工 → FQC → 仓库逐行点收，实际入库量才成为下一层合格供给
```

确认路线只保存所选各自的实际路线与选填原因，不自动下达采购、委外、自制任务或生产计划。进入页面、切换视图、刷新与轮询均不得隐式创建子件任务。

自制/有子层委外采用计划锚点：子件行只承载计划链接与执行进度，不接管子树、不迁移 exact 权益、不再展开第二份 BOM。物料需求和已确认路线始终保持在原树，计划员按原节点下达采购、委外或自制。合格入库后，正式齐套按同分析、同原树直属节点及物料维度核对，足量才把 WAITING 提升为 READY 并生成实际分仓 DRAW。根委外同样保留原树直属子件，见[V495](../数据迁移/111-V495根委外前置自制物料归属.md)。历史遗留委托通过授权刷新归还，`lowerLevelPending` 只解释下层缺料。

## 二、来源、仓库范围与历史兼容

### 2.1 来源选择

销售来源只接受服务端可分析的已审核销售订单行，以销售订单行 UUID 为真源。合法手工需求保留来源类型、稳定来源编号、货品/颜色/单位 UUID、数量和原因。单次联合分析最多 500 个来源，较大任务分批分析。

`MAKE_COMPONENT / SUBCONTRACT_MAKE` 只由服务端响应显式命令生成，员工不能伪造；刷新历史分析时从持久化的用户来源重建，排除这些系统子件，避免重复追加来源。计划产品编号留空时由服务端按真实计划单号分配，不用货号、名称或 `MA-UUID` 反查关系。

### 2.2 计划只选主仓库

计划人员只选择主仓库、查看主仓汇总。不再展示参与子仓多选、领料仓设置、子仓存放明细或“先调入再齐套”的提示；子仓由仓库在真实领料环节处理。

- 新分析的 `warehouseId` 传所选真实主仓 UUID，`warehouseIds` 仅包含同一主仓 UUID。所属库存范围由服务端解析，客户端不枚举子仓、不挑选默认叶仓。
- 旧分析可能保存叶仓 UUID。打开页面时通过主档真实 `parentId` 映射显示主仓；不为显示名称修改旧 `warehouseId`、`warehouseIds`、原单或预留。刷新、追加来源继续保留该旧身份，由服务端作同主仓兼容。
- 缺失父关系或循环关系不能在客户端被伪装为新主仓；仓库资料未能解析时明确显示待更新。
- 同主仓物料按服务端合计齐套，并按实际库存仓分别预留和生成领料单。有原单及品质、实收入库证明的本批专属来源，继续跟随其实际仓；公共库存不能因货品相同就挪用。

同主仓与来源履约规则见 [ADR-073](../99-决策记录-ADR/ADR-073-本批物料履约与同主仓分仓领料.md) 和 [ADR-075](../99-决策记录-ADR/ADR-075-合格来源跟随实际入库仓与车间通知.md)。计划页、物料分析历史列表和计划汇总单均通过 `MasterDictionaryService.mainWarehouseOf` 读取真实主仓名，原业务 UUID 保留。

### 2.3 主仓公共库存与领料分工

物料主表、节点详情和提交确认统一读取 `MaterialView` 的 `mainWarehousePublicAvailableQty`、`mainWarehouseOpenSafetySupplyQty`、`mainWarehouseSafetyReplenishmentGapQty`。这三个数是服务端按主仓汇总的公共库存、公共补库在途和剩余补库量；同货品在多条 BOM 路径重复出现时不能重复相加。安全阈值仍以货品规则为准，按主仓核算一次，不按每个子仓重复扣除。

`MaterialAnalysisCommandService.groupSafetySnapshot` 校验主仓字段完整、非负、同组一致，并核对剩余补库量。旧响应或旧构造缺失主仓预算时，不能拿任意叶仓补出授权预算；命令要求刷新后重试。叶仓 `warehouseBreakdown` 保留原数据含义，但不再作为计划页面安全补库的判断依据。自动刷新比较包含三个主仓字段，预算变化会更新页面。

计划页不再单独显示“物料存放位置”，也不据其它仓数量在客户端推演调拨后缺口。实际领料沿已有领料单办理：`lib/features/warehouse/pages/stock_doc_detail_page.dart` 顶部显示真实领料仓及对应物料数量。仓库侧明细和追溯保持可用。

## 三、分析详情的交互

### 3.1 三个生产准备入口

主页面固定为“下达采购 / 下达委外 / 下达车间”，每个详情内分“未下达 / 已下达 / 需处理”。入口计数和详情使用同一分析快照，不把展示筛选当作新业务状态。

| 入口 | 未下达 | 已下达与进度 |
|---|---|---|
| 下达采购 | 已确认 BUY 且有可提交余量的根产品/组件 | 申请、订货、财务审批、收货、IQC、实际入库的真实来源和进度 |
| 下达委外 | 已确认SUBCONTRACT的根产品/组件，按**要不要先自制目标件**分流：无子层、或只有一个叶子子件（ADR-085）→ 直接出委外申请；其余有子层 → 前置自制 | 前置自制、已产/已通知/可通知量、委外申请与回厂入库；单一子件件另看「发子件出仓 → 回厂 → IQC → 入库」 |
| 下达车间 | 已确认MAKE根产品、真实自制子件和普通MAKE组件候选；不含根BUY/委外 | 已生成计划、待审核/待料、领料、生产、FQC 与实收入库 |

“需处理”从服务端排产资格、结构、路线和数量约束解释当前阻断。单纯物料不足不应变成禁止先下达车间的理由；已下达行的下一步仍须读取实时下游事实。产品有未排余量且已有计划时，可同时属于未下达和已下达，不能把两个计数相加当作产品总数。

### 3.2 十五列主表：看与办在同一张表(ADR-102，2026-09-22)

共用 `MasterDataTableView`，**十五个业务列全部无条件出现**(2026-09-14 前为八列、2026-09-15 为十三列且带两个条件列，见 [ADR-102](../99-决策记录-ADR/ADR-102-物料分析一张表直接下单.md))：

| 列 | 展示重点 |
|---|---|
| 物料办理 | 本行现在能办的事：**调拨**(只能从别的计划已锁定的量里调；没有可调拨量、缺 `:cross_reallocate` 权限时置灰并说明)+ **下达**(按供应方式分流到采购/委外/车间；已下达过的显示「追加」)。退役的「在途调拨」列并进这里的悬浮说明 |
| 物料名称 | 名称 + 层级连线；**不再有级联号 P1 / P1.1 徽标，最底层也不再画圆点**（层级由缩进 + 连接线表达）；汇总视图副行保留「N 来源」 |
| 编号 | 货号。产品行取产品自身货号 |
| 颜色 | 颜色名。产品行取产品自身颜色 |
| 单位 | 计量单位。**以物料行为准**（根供给行记的是基本单位，产品行记的是来源单位——拆列前副行一直显示前者，拆列后不换口径） |
| 供应方式 | 已确认路线或主档建议；改选后确认立即保存。**未确认的行画红框**——先在这里选好并确认，这一行才能下单 |
| 需要数量 | 当前节点的服务端有效需求 |
| 还缺数量 | **把公共的量都当成已占用之后，这一行还要另外下多少**(服务端派生 `netShortageQty`)。仓库公共现货本来就已扣在里面，新扣的是「下达时真会自动认领的公共在途」；自制与需先自制的委外不会自动认领，这两类显示未扣的量。退役的「可用数量」「在途未到」「公共认领未实收」三列的数字并进本列的悬浮说明，含晚到来源单列一行 |
| 下单数量 | 未下达：可填，预填的是**毛量**(建议下单量 `additionalSupplyRecommendedQty`)，**不是**左边那列「还缺数量」——下达时的自动认领是从这个数里切走的，不是在它之上另加，填净数每一行都会少下一个认领量(ADR-102 §2.6)。**可超量**(超出部分记公共备货，需超量下达权限)。已下达：**锁死并改成显示累计已下单量**。自制 / 需先自制目标件的委外必须整批接管，只读 |
| 追加下单 | 已下达的行填这里，默认 0 = 本次不动它。**只增不减**(库侧守卫要求新量大于旧量)，要改小只能撤回重下。下达成功后并进左边的「下单数量」，本格回 0 |
| 所属仓库 | 货品主档归属, **单一事实源**(V587 列 + V590 自动回写)：任何入库(采购/委外/完工/调拨/退料/盘盈/手工单)都会自动把它更新为最新入库仓, 出库/红冲不翻转, 值没变不落盘。点格弹仓库面板仍可手工改, 改完全站生效；表头可按仓库筛选, 没登记的行落「未登记」桶。**不是**单据落点仓, 也不是本次分析的范围仓 |
| 归属车间 | 货品主档归属生产车间(V590, `goods.owning_workshop_department_id`), 只读。最近一次排产确认或车间改派自动记住(原 V192/V488 偏好表学习语义, V590 搬进货品表), 下次下达车间默认带出到右边的「生产车间」 |
| 生产车间 | **本次**下达车间要交给哪个车间(不是货品平时的归属车间)。默认按该货品上次排产记住的车间带出，黄框提醒核对，点格可改。只对走自制的行有意义，采购 / 委外行显示横杠 |
| 负责人 | 本次这批活谁负责。优先带出该货品上次记住的负责人，其次是所选车间在组织架构上的负责人，黄框提醒核对 |
| 进度 / 待办 | 真实阶段与下一步；完整细节双击查看。**未确认路线的行显示「待选供应方式」**，不再落进采购链显示成「等待下发采购」 |

**不给任何列开点击排序**：本表是树，按列重排会把层级打散。列的顺序与显隐仍由表头设置(拖拽换位 / 竖拖隐藏)控制。十五列无条件出现还解决了一个旧坑：原来两个条件列一翻转就把用户调好的列宽列序整体重置。

**表头筛选覆盖十四列**(2026-09-22 用户口径「能加的全部都加好」)，唯一没有的是树形的「物料名称」——它已经有关键词搜索框。实现上收成一张取值器表：加一条取值器，建桶、匹配与失效清理三处自动跟上。

移除最后的“处理”列和独立“建议路线”列。表头设置、全屏、搜索和视图切换在同一工具条。宽屏使用联动折叠滚动，窄屏回退有界表格；不再在准备入口与主表间预留悬浮区高度。

**勾选换义(ADR-102)**：复选框从「选行去确认路线」扩成「选行去办事」。可勾判据是并集——有待提交的路线决定 **或** 这一行此刻能下单/追加；权限门是路线 / 下达采购委外 / 下达车间 / 跨计划调拨四把锁的并集(旧写法绑死在路线权限上，只有采购权限的采购员一行都勾不上)。悬浮区两个按钮 `确认路线(N)` 与 `下单(N)` 各自只对够格的子集动手。折叠或被表头筛选藏起来的勾选行**不进提交集合**，但会在确认框里如实数出来告诉人。

**父行改量带动子层**：父行「下单数量」改动后去抖 300ms(页面级单例，不是每行一个定时器)，带着用户亲手填过的数调 `issue-plans/preview`(`lines` 为空 = 只重算不下达)，拿服务端算好的「下达之后」快照显示子层数量。客户端不做任何数量算术；预览结果只用于展示，提交一律按权威快照走。

**三个入口的详情表用同一组身份列**（2026-09-14 用户口径「都统一，不要物料分析页面的表头一种、其他的不一样」）：第一列仍是「物料办理（物料 / 调拨）」，随后接同样的 `物料名称 / 编号 / 颜色 / 单位`，再接各桶自己的列。规格没有独立列，保留在名称格副行。下层办齐弹窗（§3.8）同样用这组列。

名称、层级标志和供料路线在浅色下为黑色；2026-09-13 起选中行统一淡绿底（primaryContainer 35%）+常态字色（原「选中后白色+深绿底」口径退役）。缺口仍保留数字和文字，不能只靠颜色。全屏与普通视图共用选择、草稿和列配置，切换产品/物料视图不销毁正在使用的表格状态。

### 3.3 按产品与按物料汇总

按产品保留父子层级，搜索具体名称或货号时保留命中路径的祖先。按物料按货品、颜色、单位 UUID 汇总，各任务 UUID 与数量分摊不合并；缺货品 UUID 的历史行按物料行隔离，不凭相同名称猜成同一物料。

已创建的自制/委外前置 child 是**计划锚点行**：不展开自己的物料树（其物料需求保持在原父树原位，单一份数据不重复计量），只承载计划链接与执行进度；详情面板显示「已下达自制 / 计划量 / 已完工入库」。主表进度列在锚点存在时内联子件真实执行状态。

汇总只累加服务端逐节点分配事实，不累加每行重复展示的整仓余额。深层诊断不得再消耗已分配给直接层完整套料的同一公共库存；exact 权益继续只属于精确受益节点。

### 3.4 供应方式单一事实源（货品主档）与显式确认

1. 已确认路线与已下达事实优先，不被建议默认覆盖；手动修改的本地草稿优先于建议。未确认节点的默认值**只来自货品主档 `goods.source_type`**(2026-09-16 起，见第 2 条；按历史分析推导的「上次路线」记忆已整套退役)，主档为空时按下面的建议口径落 `MAKE`/`REVIEW`，`REVIEW` 在前端预填为委外。每份分析冻结已读取默认，确认一组不能把未选组改成统一委外。
   **服务端建议路线口径（2026-09-10，C05 F8）**：主档来源「采购/自制/委外」→ `BUY/MAKE/SUBCONTRACT`；来源为空/未知且**有 BOM 子层** → 建议 `MAKE`（有维护 BOM 的件默认可自制，子层需求随之展开、可勾选，与主档为自制的父件同一行为）；空来源叶子 → `REVIEW`（前端 `MaterialSupplyRoute.fromWire` 得 null，只影响本条预填默认委外，不展开任何子层）。「上级路线不展开本节点」只在父件有效路线（确认值，否则建议值）不是 `MAKE/SUBCONTRACT` 时出现。空来源行的路线格旁有黄标「主档来源为空，请核对」（`UtenFieldHintIcon`），提醒默认委外只是缺省值，不是已决定。刷新（POST /preview）时若主档/BOM 事实真的变了（含来源真改），服务端清空该行人工确认并在刷新响应带 `routeResetCount`，页面横幅提示「N 条路线因主档变更需重新确认」；旧快照的 `REVIEW` 建议升级为具体建议**不算**事实变更，不清确认（ADR-029 §6.1 前向批注）。不做猜测性回填迁移：有 BOM 但来源为空的货品由计划部在货品主档补齐。
2. **确认即写回货品主档 (2026-09-16，[V598](../数据迁移/189-V598货品来源按路线确认历史回填.md))**：点「确认路线」在同一个事务里把结果回写 `goods.source_type`(`BUY`→采购、`MAKE`→自制、`SUBCONTRACT`→委外，含 ROOT_SUPPLY 根行——根确认为 MAKE 即这个产品是自制件)；值没变不落盘，真改了抬 `goods.version`(这是人做的决定)，已软删货品跳过。同一条 UPDATE 顺带把本行 `source_suggestion` 对齐成确认值，否则主档改了以后下一次刷新算出的建议与本行旧建议不同，会被「主档事实变更」当成理由把刚确认的路线清掉(反馈环)；主档回写必须早于刷新，刷新按新主档算建议才与本行对齐。按历史分析推导的 `GET .../last-routes` 记忆**整套退役**(端点、按 100 货品分块读取、并发限制、迟到响应隔离一并删除)：供应方式只有主档一个事实源，用户改过的下次进来就是新值，货品资料页 / 导出 / 其它读主档的地方同步可见。存量确认由 V598 一次性回填(每货品取最近一次确认，最新胜出；分析未删除未取消，停用节点上的确认仍然算数)。
3. 主表和分桶详情改单行供应方式共用同一持久化入口：改选后显示确认，确认即提交该节点(汇总行则提交对应真实节点)，取消保持原值。成功后读取服务端结果，并回写货品默认；失败保留待重试决定并明确报错。“确认路线(N)”继续用于批量采用未确认节点的当前建议以及重试失败决定；不再要求改单行后再找第二个保存按钮。根产品与子 BOM 使用同一 `materialLineId/actionGroupKey` 确认通道。

### 3.5 顶层供料节点与产出交接

V478 为销售与合法手工来源提供真实 `ROOT_SUPPLY` 节点：`nodeRole=ROOT_SUPPLY`、`level=0`，没有父节点或 BOM 行。产品头以 `rootMaterialLineId` 引用它。普通节点为 `BOM_COMPONENT`；新旧节点、来源分析行和后续单据均以系统 UUID 关联。

- 根 `MAKE` 使用原产品分析行直接下达车间，不通过 notify 再造一个自制 child。**根路线必须显式确认为 MAKE 才能进车间桶与选入车间计划（2026-09-05 起与服务端 canSchedule 同口径双向闸）**：未确认的根与未确认的子层候选一样只留在主表（红色「路线待确认」、无勾选框），车间桶入口计数不含它；确认采购/委外的根只进各自路线桶。服务端对未确认根返回「根产品供料路线未确认，请先确认为自制再下达车间」并拒绝 issue-plans；无根节点的旧分析沿用旧合同（剩余量>0 即可排产）。`readyNowQty=0` 不等于禁止先下达待料计划。
- 根 `BUY/SUBCONTRACT` 进入对应供料任务，不留在未下达车间计划。供料仍使用既有 notify 权限、来源数量、仓库及采购/委外后续审批链；有子层委外继续遵守前置备料合同。
- 根库存/供给使用货品基本单位，计划输入保留原需求单位。例如需求 10 箱、1 箱 20 件，根表和供给为 200 件，计划输入仍为 10 箱；不能把 10 与 200 当同一种数量相加。
- 外部根供给的合格实收入库通过追加式 `preplan_root_output_events` 交接。销售来源将精确入库权益释放并转为销售预留；依法使用已分配存量的销售根也需显式命令。手工来源不能仅凭公共现货写出一笔无来处的完成事实。
- `root_fulfilled_qty` 从 FULFILL/REVERSE 事件按冻结换算率投影，不能直接改数。收货反向必须匹配原切片；已进入拣货/发货的销售预留不允许直接红冲入库。

V478 不在迁移时批量改写旧分析路线。旧记录的根指针初始为空；新建或授权刷新才补真实根节点。旧响应的根区域只读兼容，既有子 BOM、历史单据及旧排产入口仍按原合同处理。详细约束和待验收边界见[V478说明](../数据迁移/94-V478顶层供料路线与产出交接.md)。

### 3.7 统一流程词表（2026-09-06，全站唯一口径）

「进度 / 待办」的状态文案只允许来自**一份词表**：`lib/features/production/models/production_flow_stage.dart`
（展示组件 `production_flow_stage_cell.dart`）。物料分析主表、三个分桶详情、我的车间任务、
计划详情执行段卡、生产调度与进度全部引用它，任何页面不得自造状态词。阶段事实的来源分两路：

- **物料行（BUY/委外/自制子件锚点）**：服务端 `MaterialAnalysisFlowStageService` 按真实单据链
  批量推导 `MaterialView.flowStage` 键（下单/审批/收货/IQC/入库沿 `preplan_supply_actions →
  订货 → 审批 case → 收货 → 检验`)。**入库齐套权威口径**：V490 后本批需求不随下达归零，
  缺口只扣合格库存、精确权益及本批正式领用覆盖。整批下达只改变计划容量与在途责任，
  不能宣称已入库；历史归零行仍沿单据链逐步判定(未下单=
  等待采购下单 → … → IQC 全部合格且仓库实际入库才算已入库；全部不合格=原订单补货通道
  等待补货到货），修复了「采购未下单却显示已入库 / 进度弹窗跳步直达已完成」；弹窗内的逐步
  时间线（supply-progress）与阶段服务读同一批单据事实、同一口径。
- **2026-09-07 部分到货/验收/入库收口**：同一申请明细分批下多个订单时保留全部订单，不以最后
  一张覆盖此前财审或待检事实；收货明细使用真实receipt_item.id关联IQC，并保留order_item_id
  谱系。任一已收货明细缺少检验事实或仍待检，继续等待IQC；合格量大于实际入库量时显示等待入库。
  合格部分虽已全入库但本批仍有shortage，采购等待到货、委外等待回厂，不能标整批已入库。
  历史required=0行须逐订单明细证明收货检验完成、合格部分全部入库且覆盖订单基本量；某订单超收
  不能覆盖另一订单未到货。需求仍在本批且shortage归零的真实库存/权益覆盖口径保持不变。
  全部事实仍按分析批量查询，没有新增逐行HTTP/SQL，没有新增前端状态键，也不把未来到货当现货。
- **执行段 / 顶层产品**：`ProductionFlowStage.forSegment/forProduct` 就地推导（执行段状态 +
  零料标志 + 报工/计划数量，报工量缺失时回退入库完成比，绝不发明 0%）。
- **等待物料按开工路线区分（2026-09-18，V599 路线确认配套）**：`forSegment` 新增可选
  `startRoute`——确认后 WAITING 段的等待方式按路线显示：FULL_KIT「等待物料到齐 · 齐套生产」、
  BATCH「等待到货 · 分批生产」、CONTINUOUS「等待直送料 · 持续生产」；未确认/null 保持
  「车间已收到 · 等待物料」（与下表「未下达按路线显示第一步」同款思路，色档仍为 waiting 琥珀）。
  目前我的车间任务页传入路线；其它调用方不传则维持通用文案。

| 路线 | 步骤链（词表顺序） |
|---|---|
| 自制 | 等待下达车间 → 计划待审核 → 车间已收到 · 等待物料 → **物料齐套 · 去领料** → 已提交领料 · 待仓库发料 → 已领齐 · 可开工（零料直制为无需领料 · 可开工）→ **生产中 · 可报工** N% → 品质/实收入库与用料结清 → 已完工 |
| 采购 | 等待下发采购 → 等待采购下单 → 已下单 · 待财务审批 → 财务已审批 · 等待仓库收货 → 仓库已收货 · 等待品质验货 → 品质已通过 · 等待入库 → 已入库 |
| 委外 | 等待下发委外 →（需先自制的有子层件先走「前置自制 · +自制链」）→ 等待委外下单 → 已下单 · 待财务审批 → 财务已审批 · 等待目标件出仓 → 已出仓 · 等待回厂 → 已回厂 · 等待品质验货 → 品质已通过 · 等待入库 → 已入库。**单一叶子子件件**（ADR-085）出仓那一步发的是子件，缺料就是缺子件，子件入库前仓库存不下草稿（「待发子件在该仓的合格可动用库存不足」）；回厂交回的仍是目标件 |

### 3.8 父件 + 下层一起下单（2026-09-14 修订二：**整页**·前置，[ADR-081](../99-决策记录-ADR/ADR-081-下层一键办齐与物料表身份列统一.md)）

级联页使用 50 行页窗，输入对象、选择、净需计算和提交校验覆盖本次全部节点。翻页不取消其他页的选择；页头显示页数/总行数，提交前确认摘要显示全部选中量。发现别页输入错误会跳转到该页，表头筛选隐藏了当前选中行时先清筛选再提交或翻页。最多展开 300 行/10 层的截断仍明确提示，未展开的节点不承诺已办理。

在分桶页点「创建生产计划（车间桶）/ 下达委外（委外桶，有子层行）」时，若被下达件沿 BOM 还有**没下单的下层**，直接**进入整页**「父件 + 下层一起下单」——父件还没提交，树顶是本次要下达的件（**数量可改**，它就是下层的驱动量；父件段提交后置灰），往下用与准备页**同款的树组件**（`UtenTreeTableCell`：缩进 + 层级连线 + 展开/收缩箭头 + 未展开子数徽章）逐层列出子层 / 孙层，下单数量已按本批数量算好可改；点右下悬浮组「一键下单」才按序提交：**先父件（车间 `issue-plans` / 委外 `notify`），成功后按最新快照重建下层行并继承已填数量与勾选，再按路线分流办下层**。全部下层都已下单 / 已被现货覆盖时**不进页**，父件按原路直接提交，并把「已检查下层：都已下过单，本次只下达父件」如实告诉用户；下层全被权限 / 路线挡住或结构过大时同样不进页，但会点名说明「父件按原样下达，下层请回主表处理」，**不再静默跳过**（2026-09-14）。（第一版为 AlertDialog 弹窗，用户口径「弹窗看的东西太少，直接去新的页面」；再前是「先落库父件、成功后再补弹」，即用户口径「还没确认就把父件下了」，两轮均已改。）

- **数量口径**（2026-09-21 [ADR-099](../99-决策记录-ADR/ADR-099-计划量单一入口与子层按计划产出展开.md) 起本条里的客户端计算全部退役——车间通道的下层数字改由 `POST /{id}/issue-plans/preview` 服务端算, 见本文末「2026-09-21 计划量单一入口」; 以下为历史口径）：根产品先按 `unitRate` 转为基本量，然后逐条 BOM 边按 `bomQty/consumptionBasis/basisOutputQty/allowPartialPackage` 计算。`PER_UNIT` 直接相乘；不可拆包装和 `FIXED_BATCH` 先对父产出按包装/批次向上取整，再乘单耗；每条边结果向上保留基本量四位后才驱动下一层。累计 `perProductQty` 只用于缺字段旧线性载荷的兼容，不能代替整包/固定批计量。相同提交单元先汇总路径，再按 `max(0, 本批毛需求 - max(0, 快照需求 - 服务端还可下达))` 扣除已覆盖量；无公共超量权限时以剩余可下达量封顶。采购起订量和整包装只抬本批净需，不能重新抬回整份分析的剩余量，也不能凭零净需产生采购。提交由服务端按实时版本、来源和权限复核。
- **展开边界**：只穿过自制与「BOM 上还有下层要办」的委外节点——含 ADR-085 那类
  「只有一个叶子子件」的直接外发件：父件走 notify，但那颗子件仍要我方备出来，必须继续下钻；
  采购节点与真正的叶子委外节点下单即止。最多 10 层 / 300 行，超出在页顶显示黄色截断提示条（「没列出来的下层本次不会被下单，请到主表逐层办理」）——2026-09-14 前只在内部算了个 truncated 标志却从不展示，属实现与本文档不符，已修。同时选择父件 P 和子件 C 时合并为一棵树，C 由 P 驱动且只提交一次。同一 `actionGroupKey` 在树里出现多次时只有第一处可填数量（毛需求合并累加），其余行只作层级上下文。
- **数量可改，改上层带动下层**（2026-09-21 起「带动」= 树顶改量后向服务端要预览快照重建下层行, 客户端不再自算）：默认子行随父件增减，手工量保留并实时检查是否足够。中间件已有现货及外部最终件在途不再重复驱动其子树；内部制造承诺保留物料责任，不能把「已下达」当「已完工」扣掉。使用服务端 `allocatedAvailableQty/externalFutureCoverageQty/internalCommittedOutputQty` 计算待制造产出，避免自行从通知文案猜测。树顶基本量、逐边包装取整、同提交单元汇总共用纯计量函数；父件提交后按最新快照重建，继承手工数量、车间、负责人及勾选。折叠只影响可见和选中集，展开恢复原勾选。
- **一键下单按路线分流**：采购 → 下达采购；**直接外发的委外**（无子层，或只有一个叶子子件）→ 下达委外；自制与**需先自制目标件的委外** → 回到下达车间（`issue-plans` 一次原子调用：服务端同事务建前置自制台账 / 锚点、逐行出计划、按权限同事务审核）。表内显示路线与已确认路线不一致的行在第一步一并确认路线（提交前二次确认点名「其中 N 行会先确认路线」）。
- **基础需求已下过单的下层行（已下单子件）**（2026-09-21 ADR-099 起：`GET /{id}/supply-links` 退役, 追加由服务端在 notify 时自动就地改大未订货的申请明细、已订货另立新申请（V640）, 本页不再自行判断「并入 / 另立」; 以下为历史口径）：超产多出来的量按申请进度分流——先查 `GET /{id}/supply-links`（只查「还可下达=0 且本批有超产量」的行，每行取最近一条未撤销下游动作）：申请**未分解出订货单**（已审核、明细无已订货量且无待财务审核占用，与 V477 `adjustItemQty` 守卫同口径）→ 状态显示「已下采购申请 PR-x（未分解）· 并入 20 → 40」，提交时把**同一张申请的明细数量改大**（`PUT /purchase/requests/{id}/items/{itemId}/qty`，权限与守卫由该端点自裁）；**已分解出订货单 / 委外申请** → 状态显示「已下单 PO-x 且已分解出下游单据 · 多做的 X 请到采购 / 委外模块对该单追加，本页不下单」，该行**不可勾选**，确认弹窗里单独点名本次不含它们。（2026-09-14 修正：这类行的提交单元在分析侧已不可执行——`_isExecutableSupplyGroup` 的 `_hasSupplySubmitQty` 为假——原先放它们走 notify 超量通道，结果要么整段被挡住把一键下单卡死、要么被静默丢掉却按勾选行数报成功。要让「本页直接追加」成立需服务端另开公共备货通道，属未做项。）联动加载失败不阻断，按无联动的普通超量口径展示。
- **不是一个事务**：各下达路径各有自己的校验、幂等命名空间与回滚边界（ADR-080「明确不做」表拒绝合并成一个事务的理由仍然成立）。这里做的是**有序编排 + 逐段如实回报**：任一段失败立即停下并写明停在哪一步、哪几段成功了几行，已成功的段保留在服务端（幂等键可回放，重试不重复建单），表内数量按最新快照重算后留在原地供重试。**失败重试不重发父件段**——首次提交后快照已换版本，重发等于新幂等键真实重复下单，重试只办剩余段。
- **列与数据（2026-09-14 定稿）**：**表头与外面那张表保持一致，不额外堆列**（用户口径「表头应该和外面的一样，不要添加这么多没用的」）。定稿 13 列(2026-09-15 先从 13 收到 12 删掉「本批要用」, 再加回一列「所属仓库」) = 分桶详情那套 `物料名称树 / 编号 / 颜色 / 单位 / 供料路线 / 所属仓库 / 需求数量 / 下单数量 / 生产车间 / 负责人 / 状态`，外加本页结构上必需的两列：`下达去向`(一键下单按它分流)、`还缺数量`(原名「还可下达」，2026-09-15 改名；说明为什么某行不能下或只能下这么多)。**「本批要用」列 2026-09-15 按用户要求删除**：它是「本批数量 × BOM 单位耗用」的中间量，与「需求数量」只差一个超产量，摆在表上反而要用户自己做减法；字段本身照常参与计算(它是下层展开的驱动量)，差额已在状态列写成整句。**行序与准备页主表逐行对齐**(2026-09-15)：兄弟行排序走库级私有的 `_compareBomSiblings`(先层级、再货品编号)，与 `_orderedBomNodes` 同一个函数——两张表看的是同一棵 BOM，行序不一样用户得在两页之间重新找一遍物料(原按 `nodeKey` 排)。库存/在途/缺口/单位耗用这些**不进列**，改在「下单数量」低于下限时的悬停提示里一次说清——曾一度加到 17 列，用户明确要求撤掉。列显隐与顺序按账号持久化（`production.materialAnalysis.cascade.gridColumns`）。表尾给本地合计（已勾选行数 + 按去向分组的下单量合计）。树顶行不再大量显示「—」。
- **「所属仓库」一列贯穿五张表(2026-09-15, V587)**：主表、下达采购 / 下达委外 / 下达车间三个分桶详情、以及「父件+下层一起下单」整页，都在**供料路线之后**挂同一列。五处共用宿主状态链上的同一份读写助手(`owningWarehouseNameOf` / `owningWarehouseIdOf` / `owningWarehouseFilterValue` / `pickOwningWarehouse`)——分头实现会出现「在 A 表改完, 切到 B 表还是旧值」。写回走 `PUT /api/production/material-analyses/goods-owning-warehouses`(权限复用 `production_material_analysis:route`：所属仓库与供料路线是同一类「计划员在分析页维护的货品级计划属性」，同一批人同一把锁，不另铸权限码)。**写成功后刻意不刷分析快照**：所属仓库不进快照指纹，重拉既慢又会把别人在编的 CAS 令牌搅乱，因此本地留一份覆盖表，读取时优先于快照值，下次真正重拉分析时自然归一。

- **V590 单一事实源收敛(2026-09-15)**：用户口径「仓库只用一个地方」——① 归属仓改由 `StockService` 过账内核在**任何入库**时自动回写为最新入库仓(全路径无旁路), Excel 回填照旧只填空；② 「归属车间」新列只读展示货品表学习字段(偏好表已废弃删除, 学习/预填改走 goods 两列)；③ 展示层不再有「实时 warehouseBreakdown 推导」的第二条链路, 一律读主档字段。详见 docs/数据迁移/181-V590货品归属单一事实源.md。
- **顶层产品行挂红色「顶层」小框(2026-09-15)**：分桶详情「下达车间」的物料名称后，顶层成品行(无 `parentAnalysisLineId` 且 `sourceType` 不是 `MAKE_COMPONENT`/`SUBCONTRACT_MAKE`)挂一个红框徽章。理由：2026-09-05 起「顶层与子层自制同构」，类型列一律写「自制候选」，顶层和子件长得一模一样。**徽章不走 `UtenGoodsIdentityCell.trailing`**，走 `Wrap`：`trailing` 会在名称外面包一层 `Row`，而本页族既有用例按「离名称最近的 Row = 整行」定位数量框与复选框。
- **多选行按 BOM 合并成一棵树**：被勾选祖先覆盖的子行只在祖先树内保留一次，父件段移除该子行，后续按级联数量提交。默认预填值不算人工超产，父件改小后仍联动；只有实际编辑且不同于原默认的超量才保留为人工值。车间和负责人继续沿用。采购边界或展开上限之外的后代保留独立树，截断明确提示。
- **有自制子层的委外件数量可改(2026-09-16, ADR-081 §11.2)**：数量锁死的根因在服务端——`notifySupply` 对「会创建下层责任」的组要求提交量逐字等于剩余需求、且拒绝公共超量，放开输入框只会 422 整批回滚。现改为**非顶层**的这类行在有生成生产计划权限时走 `issue-plans` 的 ARRANGE 段(V589 已让委外台账跟量)：数量可改、超量跟到台账与行动，台账 + 锚点 + 计划**同一事务**建好，不再需要第二段「前置自制任务下达车间」。**顶层供给行只能 notify**(服务端候选解析明确排除 `ROOT_SUPPLY`)，数量保持只读、随后由「前置自制任务下达车间」段按锚点排产；没有生成生产计划权限的账号同样退回 notify。数量格的只读提示按这两种原因分别写文案。委外桶同时勾选两类行时父件段变成两条请求(notify 在前、issue-plans 在后)，逐条提交、逐条记住成功，重试只补没成功的那条。
- **已建任务的行按锚点追加(2026-09-16, ADR-081 §11.3)**：已经建过自制子件任务 / 委外前置自制任务的行不再一律「本页不下达」，改为按它的锚点产品行追加——「还可下达」读锚点的剩余可排量，车间段对这类行走 `planDrafts`(锚点 `analysisLineId`)。原位物料以真实总需求扣除已排产覆盖；只有历史整块转交的零需求物料回退到锚点总 requestedQty，不能用 remainingQty 冒充总需求而重复下达。锚点不可排产或剩余为 0 时阻断并写明原因(排产资格闸早于数量校验，硬提交只会 409 把整条编排卡住)。
- **树顶父件的车间/负责人同样标黄(2026-09-15)**：「这两格是系统带出来的默认值」这个来历随种子(`_ChildCascadeSeed.workshopAutofilled` / `workerAutofilled`)从分桶页带进级联页，并在树顶行改动时回写。之前它止步于分桶页，级联页看到「已有值」就不再补默认(`departmentId.value != null` 那道门)，树顶那两格于是永远是「用户已确认」的素底。
- **子层下单数量有下限**：下限是先扣既有覆盖后的本批净需，采购 MOQ/倍数只是建议，不纳入硬下限。低于下限实时描红并说明本批需要、现货与在途覆盖及不足；提交再次校验。并入已有申请的追加量由采购端点核准。
- **树顶那一行不画多选框**（用户口径「父类应该默认没有多选框」）：它不是待办项，`UtenEditableGrid.showRowSelection` 让整格不渲染 `Checkbox`，而不是画一个点不动的灰框（灰框会被读成权限不足 / 数据有问题）。同一物料的合并上下文行同理。
- **层级竖线**：`UtenTreeTableCell` 的连线改为独立浮层，高度跟随整格并按宿主的纵向内边距（`guideBleed`）向上下各溢出，行与行之间不再断成一截一截；祖先竖线的索引修正为「槽 k 对应深度 k+1 的祖先」（原先整体错开一格，depth≥2 的行画在错误的层上）；肘线横段延伸到展开位圆心，叶子行不再像是没挂在树上；多棵树平铺时树与树之间不互认兄弟。
- **执行期不可离开**：一键下单期间 `PopScope` 拦住系统返回 / 手势（编排是多段的，页面一销毁后面几段就没人回报结果），树顶数量框置灰；**整页盖全屏加载遮罩**（2026-09-15：本页是 opaque 整页压在宿主页/分桶页上，它们 Stack 里那份遮罩被盖住根本不会 build，必须本页自挂；标题逐段跟随宿主两条通道——「正在生成生产计划/正在生成并审核下达 / 正在下达采购任务 / 正在下达委外任务 / 正在确认物料路线」，段间隙用「正在按批次下达所选行」兜底，跑完或停下即撤下——此前只有按钮文字变「正在下达…」，多段串行等待时用户以为卡住）；默认车间 / 负责人与申请联动加载期间提交按钮显示「正在载入默认车间…」并禁用，避免抢在默认值填进来之前提交、白白拿一句「尚未选择生产车间」。
- **逐段如实回报**：采购 / 委外段按**实际提交的行数**上报，被最新快照判为不可执行而丢掉的行单独点名；行内数量无法按 `actionGroupKey` 传达（服务端会回落全量剩余）时当面说明；「并入已有采购申请」失败时逐张列出**已经改大**的申请单号，避免重试重复加量；父件提交后掉出集合的行区分「随父件办妥」与「被挡住没办成」，后者立即停下并点名，不再整页报全绿。
- **权限与边界**：采购 / 无子层委外超过「还可下达」的部分走公共超量通道（2026-09-21 起只传 `qty` 本次总量, 服务端按权威余量拆成需求份 + 公共备货份, `publicExtraQty` 退役），**需要** `over_supply`；没有该权限时按余量封顶并写明「超产多需 X，无超量下达权限未计入」，不静默改小（可并入申请调量的行除外——走采购侧 sanctioned 入口，权限由该端点自裁）。下达车间去向的行按 V577 可超量，**不需要**额外权限。主档来源为空、路线只能兜底委外的行不允许在这里替人确认，提示「请先在主表确认路线」。

## 四、计划、齐套与执行门禁

### 4.1 三类数量与先下达车间

`canSchedule / maxSchedulableQty / scheduleBlockedReason` 是排产资格；`readyNowQty` 是当前可完工入库的完整齐套量。两者必须分开。

| 指标 | 含义 |
|---|---|
| ready_start | START 阶段的分析参考，不证明已领料或可以实际开工 |
| ready_finish / readyNowQty | START + ASSEMBLY + FINISH 硬门槛完整齐套量 |
| ready_ship | 增加 SHIP 参考物料后的预计可发提示，不作为实际发货授权 |

`SHIP/REFERENCE` 不写正式生产需求、reservation 或 DRAW。确实在生产消耗的包装材料应放到 FINISH，并按 `PER_UNIT / PER_PACKAGE / FIXED_BATCH` 逐边计算、向上取基本单位四位小数，不能平均单耗近似。

例：需求10、现货只齐6套，计划侧仍可下达剩余需求10；审核按真实齐套形成READY/WAITING执行份额。对于已下达且符合拆批资格的WAITING段，车间可以通过“分批领料”再明确安排完整子批：原需1000件、现货能配齐10件时先办10件，余990件继续保留。拆批保留原数量与来源谱系，不是把原单直接改成10。已有领料、报工、正式供给绑定或人工暂缓等限制由服务端解释；不能任意重写所有历史段。见[ADR-078](../99-决策记录-ADR/ADR-078-完整子批生产与实际用料余料退仓.md)。

### 4.2 审核、领料与通知

`generate` 只允许创建草稿、ACTIVE planning draft 与 SUBMITTED 来源关联；`approveNow` 还需独立 `production_plan:approve`。审核事务按真实齐套拆分 READY/WAITING，保留精确销售已排量和独立来源。

WAITING可在车间任务中持续跟踪。完整齐套后，服务端同事务执行精确权益转正式预留、完整库存分配、生成内部DRAW并提升READY；此时通知车间去领料。车间在汇总页明确提交后，仓库才收到对应“已申请未发”数量的任务。进入详情、预览、刷新或收到通知不等于提交领料。逐行申请与仓库额度见[ADR-077](../99-决策记录-ADR/ADR-077-车间明确提交领料后进入仓库任务.md)。

READY只证明本执行批齐套和预留。DRAW审核不代表实物交接；本执行批正式需求全部FULFILLED后才能明确START，不能把原1000件任务只领10件的材料就直接开工。先拆出有完整套料证明的10件子批，再领齐该子批即可生产。重复通知不代替业务事实；重复命令使用幂等键，旧版本/旧指纹失败关闭。

### 4.3 完工、委外与反向

报工只引用 IN_PROGRESS 执行段。日报审核记录完工申报，FQC PASS 后仍须仓库逐行点收，只有实收量增加库存和 `iqty`；完成率按有效 `iqty / qty`，不是报工量、齐套比例或工资。

有子层委外先内部完成目标件，合格实收进入前置任务专属预留；满批或显式分批后再通知委外。
**例外（ADR-085）**：活动 BOM 恰好只有一个 PER_UNIT 叶子子件的委外件不走这一段——下达即出委外申请，
财务批准后仓库直接把那颗子件发出仓（`COMPONENT_OUTBOUND`），回厂交回目标件并按冻结单耗倒扣该子件。该入库不能提前满足原生产需求；委外回厂经 IQC 和仓库实际入库后才成为原需求合格供给。参见[ADR-062](../99-决策记录-ADR/ADR-062-委外先自制后通知与分批通知.md)与[ADR-046](../99-决策记录-ADR/ADR-046-生产领料仓库点收报工归属与未来计件边界.md)。

取消/红冲走专用命令，不能通用改写已外部化 action、申请、订单、领料、报工或来源分摊。未执行的取消按权益切片恢复；已有真实执行则要求先完成精确反向。历史单据、origin 与物理库存流水不被本轮 UI 或刷新改写。

撤回下达(action CANCELLED)或根产出红冲后，服务端保留 `confirmed_route`。原路线仍用于重新下达，不需要制造一次虚假的路线变更；确需改供应方式时通过单行确认立即保存，已有下游仍由服务端阻断。

### 4.4 默认车间、打印与合单边界

默认车间与负责人来自货品主档 `owning_workshop_department_id/owning_responsible_employee_id`；正式确认/合法改派才学习，打开页面、改草稿或取消不学习。未维护负责人时才回退该车间组织树负责人，预填需核对，不能替代服务端组织资格校验。V192/V488 独立偏好表已在 V590 迁入货品主档并退役。无 BOM 自制件沿已有 ZERO_MATERIAL/DIRECT_MAKE 证据，不造空需求或空 DRAW。

当前仍是一分析行对应独立计划单；同车间批量输入不等于物理合单。共享计划头需另行迁移精确 plan_item 来源桥及取消、报工、入库守恒，本轮未实施。只读备料计划汇总单 (`/production/material-analyses/{analysisId}/summary`)不调用 generate/notify；正式打印使用真实 planId/packageId/segmentId，不把 WAITING 的无 DRAW 描述为无物料自制。

## 六、大批量与验证边界

- 界面按分析快照缓存、复合节点索引、分页和增量装载，避免一帧构建全部产品/物料 Widget。
- 新版客户端在详情及13个返回整份分析的命令入口显式协商 `projection=shared-warehouses-v1`；`MaterialAnalysisResponseProjection` 将每个稳定 `materialKey`（货品UUID/颜色UUID/单位UUID）的全仓快照集中到 `warehouseBreakdownsByMaterialKey`，节点的分配/缺口/权益字段各自保留。客户端每维度解码一次不可变列表，零库存仓、9个仓库数量和可空日期都保留。无协商参数的旧客户端继续接收节点内联 `warehouseBreakdown`；新版收到缺版本、缺维度、失效金额或重复仓库的共享格式时拒绝展示，不能默认为零库存。此优化不改命令请求体、版本/指纹、幂等结果和权限，也不跨请求缓存动态库存。

- 同批委外 BOM 分流改为一次批量查询，验证 500 产品重复物料不产生逐行重复往返。
- 旧活动分析通过正常授权刷新重算新投影；历史来源、单据和已应用迁移不改写。旧接口保留兼容不意味着恢复退役 UI 或绕过新门禁。
- 打开已有分析只读 GET，并行加载公共字典，不自动调用 preview 重算整树。库存/BOM 需要重新计算时使用显式刷新；真实入库继续在同事务内唤醒相关分析。下达仍按服务端版本、指纹和 BOM 漂移校验执行，旧快照缺少根 UUID 时仍按只读兼容展示。
- `MaterialAnalysisBomSnapshotReader` 将每个来源的图校验和展开合并为整批两次查询，按分析行 UUID 保留独立路径、单位换算和精确计量；仍拒绝循环、超过十层、失效组件和单位/颜色异常。正式下达的直接层 BOM 快照也按选中来源批查。
- `MaterialAnalysisSupplyCoverageReader` 在命令写入前一次收集当前及历史行动组，按路线批量读取有效供给和已退回不合格的原单补货覆盖。500 个采购组的这部分读取为 3 次，不再逐组往返；申请、实收、权益、领料和退回保持来源 UUID；V554 将合并来源的待检/待补覆盖统一为累计区间差，避免把已在途数量再次下达。
- `MaterialAnalysisWarehouseBreakdownReader` 将各仓库主仓／可用标记及安全补货进度在本次读取内分别汇总一次，再按货品／颜色关联各单位维度。仍使用 V554 的真实来源进度与原专属权益计算；没有安全来源 UUID 才排除，不能以声明量为零丢弃历史来源，不跨请求缓存。
- 下达车间先按原请求版本、指纹与 BOM 快照校验，再在提交事务内重算一次实时库存分配，防止通用入库/出库未唤醒分析时沿用旧候选数量；随后复用同事务未改变的详情或委外通知已返回的详情；同物料维度的分仓汇总在一次响应内只算一次。该复用不跨请求缓存，不冻结下一请求的库存和权限事实。
- 计划循环内的材料/BOM 静态片段由 `MaterialAnalysisStructureScope` 在开闭边界完整比对，退出后才刷新最终投影。商业来源、来源行、计划、需求、预留和持锁范围仍逐次校验；任何漂移回滚整批。作用域绑定真实事务及单份分析，跨分析、新事务与独立计划入口不复用其数据。
- 大树节点和货品集合以一个数组参数传入数据库，避免 49,000 个展开节点经 IN 参数 padding 超过驱动 65,535 参数上限；仍按分析来源 UUID 与 BOM UUID 路径精确过滤，不以货品编号合并身份。

## 2026-09-13 跨路线在途调入、子层按计划产出展开与采购起订量

**一、三个调入入口对三条路线一致开放（ADR-080 / V574）**

- 「物料 / 调拨」里的三个按钮——从其他计划已入库中调入（现货让料）、从其他计划未入库中调入（专属在途）、从公共在途中调入（认领）——对采购、委外、车间（自制）三种确认路线的缺料行一致可用。匹配口径是同主仓、同货品 / 颜色 / 单位，不要求与目标路线一致，也不看子层级。
- 来源永远只能是别的计划**已下单未实收的外部份额**（采购或委外）。自制在制品、委外前置自制的半成品、正在委外商手上的料都不是最终件，永远不出现在候选里。
- 目标行必须仍生效、控制段不是发货段或参考段、路线已确认。候选列表与写入用同一套判定，不会出现「列得出来、存不进去」。
- 调入动作沿用**来源路线**落库（它确实是一张采购单或委外单的份额），单据号与进度链路照常显示真实来源单；但**分桶归属跟着目标行走**：自制物料上的一笔采购在途调入不会让它出现在采购桶，桶内「已下达量」也把这笔调入算进本路线，调入后可下达余量随之减少，不会重复下达。
- 公共在途认领此前按**目标**路线过滤候选，自制目标永远查不到来源；现在按来源路线（采购/委外）取候选，认领动作沿用来源路线落库。仓库口径与专属调入、与让料一致（同主仓）。「我方供料 BOM 的委外件不吃公共超量」这条原限制保留。
- 现货让料放开到第 1 层及以下的所有 BOM 组件层：深层子件（自制件、委外件的下层组件）之间也能互让。第 0 层根供给行不参与让料，它走自己的根产出交付通道。

**二、子件按父件「计划产出」展开（ADR-080）**

```
父件计划产出 = max(已承诺内部制造量, 物理缺口 − 外部最终件在途)
子件毛需求   = 父件计划产出 × 单耗
```

- 调入的在途到货就能顶上，不必为它备下层料；父件计划产出为 0 时，它整棵子树的未下达需求自动归零，不需要人一层层去删。
- 已经下达车间、已经建了前置自制任务的那部分是**冻结承诺**，它的原料一件都不会被在途挤掉。要少做，得由人去减量或撤回那张计划。
- 有效在途覆盖因此分成「外部在途」与「内部制造承诺」两类。两类之和等于原口径，所以主表的「尚需下达」数字口径不变；变的只是下层子件的需求量。
- **第 1 层与执行侧完全不动**：齐套、正式预留、领料、开工仍然只认真正合格入库的货。在途没到就不会提前变成可开工。

**三、采购起订量与订货倍数（V575）**

- 货品主档新增最小起订量与订货倍数（整箱 / 整包），都可以不填。
- 采购桶「下达数量」的默认值 = `向上取整到倍数( max(还需安排量, 起订量) )`，输入框下方一行说明「已按起订量与整包装抬至 X，富余 Y 归公共备货」。
- 这是软约束：计划员可以改小，服务端不硬拦。富余部分走既有公共备货通道，需要超量下达权限。
- **没有超量下达权限时不抬量**，默认只填净需求，并提示「本次 X 低于起订量 Y，需由有超量下达权限的人抬量」，不静默降级。
- 委外桶与车间桶不抬量——它们会产生下层责任，数量必须与需求一致。

**四、性能**

- 客户端显式协商 v2 稀疏响应，在模型层集中还原默认字典与行差异，仓库维度明细只解析并共享一次；`null/0/false/空数组` 均是明确覆盖。旧客户端与旧响应保持兼容，关键事实缺失拒绝显示为零。完整合同见[物料分析响应协议](../05-架构/物料分析响应协议.md)。
- 两条跨分析热路径（让料软占用、入库唤醒候选）按货品维度扫全库物料行，本轮补了 `(goods_id, color_id, unit_id, analysis_id) WHERE active` 索引；专属在途调拨表补了 `external_item_id` 索引，供采购 / 委外改单的 8 个守卫反查。
- 外部在途与内部制造承诺都按分析一次批量取回，子层展开仍是单趟遍历，不引入逐行查询。

完整业务口径见[物料调入与子层级供给总纲](../07-业务链路/09-物料调入与子层级供给总纲.md)。

## 2026-09-15 父件+下层整页的收口（ADR-081 修订五）

四件事，都是用户实测后逐条点名的。

**一、「下达了却还在未下达」**。三条真根因叠在一起：① 分桶页那个红色「下达委外(N)」点下去只是打开级联页，父件一个字节都没提交，而级联页的返回箭头与「稍后再办」都直接退出、零提示；② `notify` 遇到「一条 action 都没建」（各组余量都已归零）时照常返回快照，客户端见非空即判成功并弹「委外任务已下达」；③ 有自制子层的委外件 notify 之后，服务端建的是「前置自制任务台账 + `SUBCONTRACT_MAKE` 分析产品行」，既不出计划、也不写路线，而级联页的车间段只提交进页前展开的**物料行**树，这条新的**产品行**永远进不去。

现在：会进页的按钮加省略号（「下达委外(N)…」）；父件未提交时退出**必须二次确认**，按钮改「放弃本次下达」；客户端按「服务端只有真的写了东西才换 version/fingerprint」判定本次有没有产生下达，没产生就不报成功、如实说明原因（服务端语义不动——现货交接、V466 在途已覆盖、幂等回放本来就是合法的零 action 成功）；编排新增「前置自制任务下达车间」段——父件段成功后按最新快照解析出锚点产品行，用树顶填好的车间/负责人调一次 `issue-plans`，锚点因此直接落在「下达车间 / 已下达」。没有生成生产计划权限时不硬闯，如实说该找谁办。链路读模型同批修正：`SUBCONTRACT_MAKE_TASK` / `PREPLAN_MAKE_TASK` 台账现在是链路上的真实事实，台账已建但未排产显示「等待下达车间」，不再与「从未下达」同文案。

**二、什么时候会进那个页面**。只有两种：车间桶的「创建生产计划」，以及委外桶里 BOM 上还有生产性子层的行。**采购桶永远不进页**——页面里出现的「采购」是下层子件各自的「下达去向」，两件事。进页判定收敛成一处（与建树共用同一次纯展开），并且**每一条不进页的路径都必须给出原因**：下层全是出货/参考阶段、全已下过单、全被挡住、结构过大，各有各的话；那句摘要也改到提交成功之后才发。

**三、树顶（父件）行有车间与负责人了**，并且有和子层一样的限制：必填校验挂在提交入口（`_validate` 只遍历勾选行，而树顶永不可勾选）；超过本次可下达上限且是在本页改大的，复用分桶页那句超量二次确认。**有自制子层的委外件数量框是只读的**——服务端强制整量接管，之前那个可编辑的框填了也会被静默丢弃，而下层却按被丢弃的数字备料。

**四、层级竖线全站一套**。主表与级联页原来各写了一份树几何推导，索引基准差一级（主表从深度 1 起算、级联页从 0 起算），而画笔只能按一种读——主表所有 `depth ≥ 2` 的行都读错一级、末位子件永远不收口。现在由 `utenTreeProjection` 一处推导（输入是最终渲染序），`guideBleed` 取表格组件公开的内边距常量、树列开 `fillsCellHeight`，肘线锚在展开位圆心而不是格子中线。

级联数量以 §3.8 的当前净需与逐边计量合同为准；ADR-081 第十二节替代历史累计单耗比例及 `min(毛需求, 还可下达)` 公式。

## 2026-09-15 超量下达的显示合并（V588）

## 2026-09-21 修订二：任意层级改量都带动它的子层(ADR-099 续 / [V641](../数据迁移/227-V641我方供料委外件放开公共超量.md))

用户口径「我修改下面某个层级的父类, 他的子层级也要对应的修改」——第一版只有**最顶层**那一行改量会重算下层, 中间层改了不动, 这一轮补齐。

- **每一行填的数量都是服务端事实**：整页向 `POST /{id}/issue-plans/preview` 送的不再只有树顶那一行, 而是**层级表上每一行输入框里的数量**(`typedOutputs`: 物料行 id + 数量)。服务端把它并进该节点的**计划产出量**——子件毛需求本来就按父件计划产出展开, 于是第二层改量带动第三层、第三层改量带动第四层, 一路到底。节点**自己**的需求量与还需安排量不受自己填的数影响(那是祖先决定的), 所以不会出现「填一个数把自己也撑大」的循环。
- **与祖先取大, 不会被旧值压小**：服务端按 `max(祖先算出来的净需求, 本行填的量)` 展开子层。所以改了树顶之后, 下层那些还没来得及跟着变的旧数字不会把孙层按旧值钉住。
- **跟不跟父件, 只看「这一行用户有没有亲手填过」**(用户口径 2026-09-21 第九轮原话「如果跟着父类变、但是子类没有更改过, 父类再变也跟着变」)：
  - **没亲手填过的行**: 格子里那个数只是父件传下来的回声, 父件改大改小都**双向**跟着走。父件 1000 → 2000(子件跟到 2000) → 还没下单又立刻改回 1000, 子件、孙件原路回落到 1000。这类行的数量也**不会**被送回服务端当输入——送回去只会经「与缺口取大」把子树钉在旧值上, 父件改小时孙层就降不下来。
  - **亲手填过的行**: 本次按他填的数走。先把子件改成 3000、再把父件改到 2000, 子件原样留着 3000, **它下面那一支也跟着它不动**(孙层按 3000 算, 不按父件的 2000)。只有父件的需求涨过那个数时才抬上去(3000 → 4000)并当面提示抬了哪几行——不抬的话父件会缺料, 而且要等到提交时才被红字拦下; 父件之后再改小, 它退回用户自己填的 3000, 不会停在替他抬上去的 4000。
  - 页面为此分开记「用户亲手填的数」与「当前显示值」: 替人按比例换算出来的、按下限抬上去的都不算「亲手填过」; **清空输入框 = 把这一行交还给系统算**(手滑敲一下再删掉不会让这一行永久脱离跟随), 填 0 仍是一个明确决定(追加行「本次不下它」)。
  - 送回服务端重算的也只有**用户亲手填的那个数**, 不是框里显示的数: 服务端那一侧是「加进计划产出量再与缺口取大」, 送一个被换算/抬量放大过的值上去, 它就成了整棵子树的地板, 回来又被子层原样采纳, 再也降不下来。
- **页面先行换算是从服务端那份快照算的, 不是在上一拍估算值上再乘**: 真人改数是一位一位退格的(2000 → 200 → 20 → 2 → 空 → 1 → 10 → 100 → 1000), 逐拍相乘时空框那一拍没有比例可算, 丢掉的那一档再也补不回来——父件回到 1000 了子层还停在 2000 档。从快照出发的换算是幂等的: 中间怎么敲都不影响结果, 退格改回来与全选重打逐字一致。树顶数量还空着时不发重算请求(那只会拿到一份「什么都不下达」的快照把基准换掉), 去抖这 300ms 里「一键下单」也是禁用的——屏幕上那时是估算值, 不许提交。
- **来源数量改大又改回来, 已建的自制锚点配额跟着回落**(服务端): 只退**从来没下达过**的那部分, 地板是「已提交 + 已审核」的计划量。以前锚点只增不减, 把来源数量调高再调回来, 子件那一行的「还需安排」永远停在高位, 只能删掉整条分析重建; 行动背书的锚点仍由撤回链路负责, 这里不碰。
- **已经下过单的量照样抵扣**：子件是采购件、已经在「下达采购」下了 1000 时, 父件仍是 1000 → 子件「还需安排 0」; 父件改到 2000 → 子件「还需安排 1000」。这不是页面减出来的, 是服务端按同一套覆盖口径(在途 / 现货 / 已下达)算出来的。追加下达同理：填在中间层的追加量同样带大它的子层。
- **提交顺序按层级**：一键下单先按**自上而下逐层**下达车间段(第 1 层的计划落地后, 第 2 层的锚点配额与需求才是真的), 再统一下达采购、最后下达直接外发的委外。顺序反了会把深层按新数量填的量当成超量, 记成公共备货产出而不是本需求; 直接外发的委外放最后, 是因为它一下达, 我方供料的那颗子件就转由委外申请负责、需求归零。
- **输入框里一改, 子层当场就变**(用户口径 2026-09-21 第六轮「应该就是输入框输入时候变化对应的子层级就要变化, 不是等到确认后, 变化太慢了」)：
  每敲一下页面先**按比例**把下面每一层换算好——本行从 1000 改到 2000, 它下面每一行的本批需求就翻一倍, 已被现货 / 在途 / 已下达覆盖的那部分是不变量, 所以「还需安排」= 新需求 − 原覆盖量; 没手工改过的行的下单量跟着一起变。
  服务端那份权威重算改成 **300ms 去抖后台要**, 回来整体覆盖估算值(起订量抬量、锚点配额、包装取整这些只有服务端算得准)。等服务端期间「一键下单」按钮照旧禁用, 估算值不会被提交; 重算失败时估算值立刻退回上一份服务端数字并如实报错。原数量是 0 的行(追加行从 0 开始填)没有比例可言, 只能等那 300ms 后的重算。
- **叶子行改量不回服务端**：只有「下面还带着层级」的行改量才重算, 采购件这种叶子行改量不发请求。

### 我方供料的委外件也能超量下达(V641)

用户口径「我把采购超量下单后, 委外甚至是车间那里下单就不能超量下单, 必须是正常数值才能下单」。被拦的是**我方供料、只有一颗叶子子件**的委外件(ADR-085 直接外发, 如「V4开关面板(喷油)」), 页面提示「最多下达 1000…需要超量下达权限」——其实给了权限也下不了, 三层(客户端裁决、服务端 `notifySupplyInternal`、数据库形状守卫)都在拒。

原先禁它的理由是「多下的量会凭空多出一份无人负责的子件需求」。这一轮既然任意层级的量都能带大子件需求, 理由不成立, 三层一起放开：填多少下多少, 不超过「还需安排」的归本需求、超出的记公共备货(照旧要 `production_material_analysis:over_supply` 权限), 那颗我方供料的子件在同一张整页里按新数量一并下单。数据库侧 V641 同时放开运行时超订容量, 否则放行的公共量会在委外订货审核那一步撞 23514。

- **验证**：`PreplanPlannedQuantitySingleEntryEndToEndTest` 增三例(中间层改量带动孙层、树顶下达与中间层改量叠加、子件已下单后父件改大只差余量)+ 一例 V641(单一子件委外件按 1000+500 分账、申请明细合成 1500、子件需求跟到 1500); `material_analysis_child_cascade_test.dart` 增六例(中间层改量带动孙层且叶子行不发请求、改完当场就变不等服务端、父件改大又立刻改回时未手填的子层原路回落而手填过的那一支不跟、退格逐位改数中途空框不发请求也不甩偏倍数、手滑敲一下又删掉仍跟随、手填值的保留与抬升); `PreplanPlannedQuantitySingleEntryEndToEndTest` 再增一例(来源 1000→2000→1000 时锚点配额回落到 1000、已排 1500 时只退到 1500)。
