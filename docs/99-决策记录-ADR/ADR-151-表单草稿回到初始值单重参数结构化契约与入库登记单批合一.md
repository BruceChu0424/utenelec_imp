# ADR-151 表单草稿回到初始值、单重参数结构化契约与入库登记单批合一

- 日期：2026-10-04。
- 状态：已接受(本地源码实现，8085 克隆库真实接口与 Flutter 页面回归验证)。§1–§4 由 W1 落地；§5「入库登记单批合一」由 W4 落地(2026-10-05，V803)。
- 修订：[ADR-135](ADR-135-仓库重量账与单重自学习.md) §7.2 单重参数接口契约(见 §3)；细化 [ADR-121](ADR-121-跨模块新建表单草稿恢复.md) 本机草稿协议中「自动保存回到基线即删除」一条(见 §1)，提交前检查点、未知提交防重放与完成终态不变。
- 用户问题(2026-10-04)：「批量登记实际入库多选就报错」「库存盘点保存审核一直 409，刷新也没用」。

## 1. 表单草稿回到初始值 = 丢弃干净草稿，不是删除

**事实**：`FormDraftMixin` 在自动保存发现快照回到页面初始值(基线)时调用 `FormDraftsNotifier.delete`；而 `delete` 自 2026-10-03(60da1a29b，永久保留生命周期记录)起不再真删，改写 `historyAction=deleted` 终态墓碑。页面沿用同一草稿编号，此后任何保存都撞墓碑抛 `FormDraftConflict`，提交前检查点失败，提交请求根本发不出去。多行登记页「进页默认全选、勾选行里改一格=改全部勾选行」，用户为单独改一行会先取消勾选再勾回——这正好让快照回到基线，于是表现为「单选可以、多选报错」。36 个页面共用这套草稿协议，都会这样坏。

**决定**：区分两种「没有草稿了」：

| 情形 | 存储动作 | 历史 | 同一编号还能再保存 |
| --- | --- | --- | --- |
| 用户显式「不保存」/在草稿列表删除 | `delete`：写 `historyAction=deleted` 终态墓碑 | 留删除记录 | 不能(防旧标签页复活) |
| 业务提交确认成功 | `complete`：写 `completed` 终态 | 留完成记录 | 不能(防重放) |
| 自动保存回到初始值 | `discardClean`：活动记录换成不含任何输入的 `lifecycle=DISCARDED_CLEAN` 标记 | 之前保存过的版本照旧留在不可变历史，不新增删除记录 | 能：只有本编辑器(已清空 revision)可以按 `expectedRevision=null` 继续保存；还拿着旧 revision 的其它标签页仍判冲突 |

防重放不削弱：`discardClean` 遇到「上次提交结果未知」的记录照样拒绝(`FormDraftUnknownSubmission`)，遇到完成/删除终态或别的标签页的新 revision 判冲突。若本编辑器刚得到服务端「明确拒绝」(400/422/409 CONFLICT)而界面又正好回到初始值，先把清除了「提交中」标记的快照按原 revision 写一次，再丢弃，不越过未知提交保护。干净标记不出现在草稿列表、分类计数和恢复入口(`isActiveFormDraftRecord` 为假)。

**回归**：`form_draft_store_test`(干净丢弃不是墓碑、旧标签页不能复活、新会话不列出、未知提交与新 revision 拒绝、完成终态不变)；`form_draft_mixin_test`(回到初始值后同一编号再保存、回到初始值后提交检查点成功且请求只发一次、明确拒绝后先清标记再丢弃)；产成品批量登记页与采购/委外批量到货页各一条「开着草稿保护、取消勾选再勾回、再提交」页面回归——把 mixin 换回旧 `delete` 时两条都失败。

## 2. 提交失败如实报因

**事实**：批量/单张登记页的 `catch (_)` 把草稿检查点异常一律吞成「批量登记失败，请保持当前内容后重试」，用户和排查人员都看不到真正原因，§1 的缺陷因此被掩盖。

**决定**：提交路径不许 `catch (_)` + 通用句。统一用 `describeSubmitError(error, fallback:)`：服务端拒绝带服务端文案(含第一条字段原因)；草稿保护/本机存储异常(`FormDraftConflict`、`FormDraftUnknownSubmission`、`StateError` 等)带它自己的「下一步怎么办」；只有真正未知的异常才用兜底句，并记日志。对「请求是否已发出」有意义的页面(车间领料、退料申请、超产比例申请)在检查点之前失败时不再标成「结果待确认」，直接说明原因；但之前那次已发出、结果未知的标记要保留(超产比例申请：本次在发出前失败时恢复原来的「结果未知」，字段仍锁定)。

**「能不能给人看」只有一条判定**(`lib/core/ui/human_error_message.dart` 的 `humanErrorMessage`)：服务端异常用服务端文案；其余异常(StateError、FormatException、TimeoutException、自定义异常的 toString)消息里有中文才原样给人看——草稿保护、本机存储和页面自己抛的异常都是中文大白话；Dart/框架内部的英文异常('No element'、'Invalid date format')是程序问题，不把代号给人看，用兜底句。`describeFormSaveError` 与全局的 `context.appApiError` 都只走这一个判定，所以 `appApiError(error)` 拿到非服务端异常时不再一律显示「操作失败，请稍后重试」(通知发布、付款方式、物料发现、领料批量出库、仓库单据编辑等直接调用 `appApiError` 的提交路径一并受益)；已发出请求后的未知结果仍用各页的「结果未确认, 请重试/核对」指引，不被英文内部异常替换。

已改：产成品单张/批量登记、采购委外单张/批量到货、领料批量出库、销售单据保存与批量开单、客户收货地址、员工入职/离职、报销引导、工资生成、车间领料、退料申请、超产比例申请、品质批量检验报告(批量审批页)、待检处置页提交检验报告、报工新建/编辑保存(新建请求已发出时仍只给「只读核对原提交」指引)，以及全部经 `appApiError` 报错的提交路径。

## 3. 单重参数结构化契约(修订 ADR-135 §7.2)

**事实**：客户端把 `goods|supplier|warehouse|color` 拼成字符串 key，带仓库和颜色时最长 147 字，服务端 `@Size(max=100)` 整批 422；`WeightParamsCache` 吞掉错误、`lastError` 无人读取，采购/委外到货每行都带供应商，选了仓就必定失败，单重核对、称重折算、库存均重参考全部静默消失(测试服务器 2026-10-04 全天 15 次 422)。

**决定**：

- 请求行只带结构化身份 `{goodsId, supplierId?, warehouseId?, colorId?}`，服务端不再要求、也不校验任何 key。
- 响应分开两类事实：`items[]` 与请求行同序，每项带 `(goodsId, supplierId)` 身份，单重只按(货品, 供应商)解析；`stockBalances[]` 按(仓库, 货品, 颜色)去重，只含带仓库且有正数重量余额的组合，颜色精确匹配(空 = 无色，不是任意颜色)。单重是学习事实，库存均重是账面快照，两者不互相替代。
- 客户端按身份对行：`WeightParamsResult` / `WeightParamsCache.of(...)` 把该行仓库与颜色的库存参考接到单重上供预填；`WarehouseInsightService` 与 `/stock/weight/params` 用同一个 `GoodsWeightEstimateService.params`。
- 取参失败不再静默：缓存记下失败行与原因，`WeightParamsLoadNotice` 在页面上显示「单重参数读取失败：<原因>。称重折算与重量预填暂不可用，数量照常登记。」并提供只重取失败行的「重试」；称重计数弹窗、称样校准弹窗同样显示原因并可重试。重量仍然从不阻断数量登记。

**回归**：`GoodsWeightParamsTest`(4 个 UUID 齐全经 HTTP 200、响应只有结构化身份、库存参考按维度去重、缺货品不泄露余额)；Flutter `weight_params_cache_test`、`weight_params_json_contract_test`、`weight_params_load_notice_test`(失败可见、原因带字段错误、重试只取失败行)。

## 4. 数据库完整性错误映射原则

> 2026-10-04 补充([ADR-147](ADR-147-车间内料仓开通单一真源与发料来源仓.md) §2.8)：约束名以 `_version_guard` 结尾的行版本守卫(V409/V740/V802)是别人刚改过、属于并发冲突, 回 409(有中文原因原样回显, 否则「该记录已被他人修改，请刷新后重试」), 页面据此重读; 其余业务守卫仍回 422。内料仓服务层把自家守卫一律翻成 409 的 `WorkshopMaterialGuards` 同时删除, 统一交本节的全局映射。

**事实**：`GlobalExceptionHandler` 只给少数约束写了人话，其余 23514(CHECK 违反、守卫函数 RAISE)和 23505 一律回 409「数据已被其他操作更新，或数量超出可处理范围，请刷新后重试」。CHECK 违反本质是提交内容不满足规则，不是并发冲突，用户被引导反复刷新；守卫函数里写好的中文原因(例如「批准盘点只能记入当前未盘点期间」)也被吞掉。

**决定**(唯一映射点 `GlobalExceptionHandler.integrityOutcome`)：

| 情形 | 判定 | 状态码 | 文案 |
| --- | --- | --- | --- |
| 已登记的约束/守卫 | 白名单(约束名或固定英文片段) | 保持原 409 | 原专门文案 |
| 我们自己的业务守卫 | SQLSTATE 23514，且服务端例程为 `exec_stmt_raise`(PL/pgSQL RAISE)，主消息含中文 | 422 | 原样回显主消息第一行(最多 300 字)，不带 DETAIL/HINT/WHERE/CONTEXT |
| 真正的 CHECK、未登记的英文守卫 | 23514 其余情形 | 422 | 「提交的内容不符合数据规则，请检查后重试」；约束名、表名、例程只进服务端日志 |
| NOT NULL、数值/文字超范围 | 23502、22xxx | 写请求 422(「提交的内容不符合数据规则，请检查后重试」/「提交的数值或文字超出可保存的范围，请检查后重试」)；读请求(GET/HEAD)500 | 读请求没有用户提交的内容，这类错误只可能是服务端缺陷(拼错参数、漏列、除零)，不让用户去改输入；两种都按服务端缺陷记 error 日志并带完整堆栈 |
| 唯一/排他冲突 | 23505、23P01 | 409 | 「这条数据已被其他操作占用或已重复提交，请刷新后查看结果」；我们自己的守卫函数用唯一冲突码 RAISE 的中文原因(如 V738「需求编号已属于另一份物料分析」)原样回显第一行，不再说成「已重复提交」让人以为办成了 |
| 引用变化 | 23503 | 409 | 「相关资料已被删除或仍被其它数据引用，请刷新后重试」 |

用例程名而不是消息语言判断「是不是守卫」：即使数据库以中文 `lc_messages` 输出约束原文，也不会被当成守卫文案回显。JPA 批量 flush 时驱动抛的是 `BatchUpdateException`(只有 SQLSTATE)，带守卫原文、约束名和例程名的 `PSQLException` 挂在它的 `getNextException`/cause 上，映射时取那一个，守卫原因照样回显。客户端草稿协议把 422 与 409 CONFLICT 都视为明确拒绝，输入保留可改。

**回归**：`GlobalExceptionHandlerTest` 覆盖三种适配路径(JDBC、Hibernate、提交时延迟约束)下的守卫回显、截断、中文本地化 CHECK 不回显、英文守卫中性化、批量异常(cause 与 nextException)里的守卫回显、读请求 22xxx/23502 回 500、写请求回 422、23505 中文守卫 409 回显、23P01/23503；8085 真实接口用临时探针(克隆库，事后删除)验证：中文守卫 422 原文、真 CHECK 422 中性文案且日志带约束名。

**同口径要求**：数据库约束、DTO 与界面必填口径必须在同一次提交里一起改(V795 即因 2026-10-02 只改了界面和服务端、没改 V766 约束而出事)。

## 5. 入库登记单批合一

> W4 落地(2026-10-05，V803，与 [ADR-148](ADR-148-产成品实物交接批同去向合单.md) 同批)。

**事实**：采购/委外到货与产成品登记各有「单张页」和「批量页」两套页面、两套提交：单张页逐仓逐张 POST(部分仓成功、部分失败停在原页，重试只补失败仓)，批量页循环调单张命令；两个页面的列、校验、默认值、草稿协议各自维护，§1 的缺陷就是在其中一套上先暴露。产成品单张页还按「报工 x 仓库」逐次提交，同一张报工的两批货想进两个仓只能分两次。来源对象靠页面跳转时塞进路由 `extra`，刷新、草稿恢复就丢。

**决定**：

1. **一个页面**：双击 = 1 个来源、多选 = N 个来源，进同一个页面。
   - 采购/委外：`InboundArrivalRegistrationPage`，路由 `/warehouse/inbound/arrivals/register?expectationIds=<id,...>&preStock=1|0`；
   - 产成品：`ProductionFinishedArrivalRegistrationPage`，路由 `/warehouse/production-finished-in/arrival-registrations?reportIds=<id,...>&preStock=1|0&returnTo=...`。
   - 来源只走地址里的身份，页面按 id 从服务端重读(`GET /warehouse/inbound/expectations/by-ids`、`GET /warehouse/production-finished-in/arrival-registrations/batch?reportIds=`)，刷新与本机草稿恢复都能拿回同一批来源。
   - 多选时任务中心已选定路线(`preStock=1` 先入库后质检 / `preStock=0` 先质检后入库)，页面只显示这一条提交按钮；双击进来没有路线，两条按钮并排，点哪条走哪条。
   - 「勾选多行后改任一勾选行单元格 = 批量生效」不变；进页默认全选，提交只含勾选行。
   - 产成品登记页的来源报工即使只登记了一部分批、或撤回过，页面仍带回该报工已有的登记批次(含撤回历史)，品质未处理的批次可在本页撤回；批次历史对 N 张报工一次查完。
   - 删除：`WarehouseArrivalReceiptPage`、`WarehouseArrivalBatchReceiptPage`、`ProductionFinishedArrivalBatchRegistrationPage` 及其路由(`/warehouse/inbound/receipts/new`、`/warehouse/inbound/receipts/batch`、产成品 `/batch` 与 `/:reportId`)。
   - 合并时保留单张页的安全信息：「预计去向(基本量)」列、跨仓预定警示条(`warehouse-arrival-allocation-warehouse-notice`)、多仓分组说明、确认框逐行预计去向与「确认跨仓登记送检 / 确认跨仓登记并先入库」。
2. **一个命令、一个事务**：
   - 采购/委外 `POST /warehouse/inbound/arrivals/batch`：`lines[]` 每行带订货类型、入库仓库、采购员、订货明细、数量、重量、到货来源、上架库位；服务端只认库里的来源订货单，按「订货单 x 入库仓库」分组建收货单(登记 + 送检审核一步完成)，逐组回执(`outcome` 含 `EXCESS_QUARANTINED` 超量隔离，隔离单不影响其余组)。批量键 + 组子键(`ARB:` + sha256 前 48 位)幂等：整批原样重放返回原结果，同键换内容 409；任何一组失败整批回滚(超量隔离不是失败)。委外短交确认先对全部委外组一起评估、一次列全再写任何一组。原单张端点 `POST /warehouse/inbound/arrivals` 删除(服务层 `register` 只作为单组构件保留)。
   - 产成品 `POST /warehouse/production-finished-in/arrival-registrations/batch`：`lots[]` 按实物交接批提交(ADR-148 §3)，服务端按「报工 x 实际仓」分组成登记批次——**同一张报工的不同批可以进不同仓**；单张 `GET/POST /arrival-registrations/{reportId}` 删除，撤回登记 `POST /arrival-registrations/{registrationId}/reverse` 不变。
3. **数据库**：`warehouse_arrival_registration_commands` 增加 `batch_idempotency_key` / `batch_request_hash`(与命令身份一样不可改)，见 V803。

**回归**：Postgres `ProcurementIqcPreStockInEndToEndTest.batchArrivalGroupsOrderByWarehouseInOneTransactionAndReplaysAsOneCommand`(一行实物分两个仓 = 一个命令两张收货单、整批重放、同键换内容 409、第二组失败第一组也不留)；`WorkshopPublicSurplusEndToEndTest`、`FullChainEndToEndTest`(一张报工两批进两个仓 = 一个命令)；Flutter `inbound_arrival_registration_page_test`(1 个与 N 个来源都能提交、多选路线只一颗按钮、双击两颗、草稿按来源地址恢复)、`production_finished_arrival_registration_page_test` / `_multi_source_test`(一张报工两批两个仓一个命令、整批失败重试同键)、`arrival_receipt_review_navigation_test`、`warehouse_arrival_weight_capture_test`。

**2026-10-06 修正(多张订货单批量登记整批 409)**：服务端按「订货单 x 入库仓库」分组后逐组建收货单，原来每组各自取预锁，事务里第一组的足迹就成了整个事务的完整预锁集合，后面那组的订货单不在里面，送检回调判结构性缺口、整批回滚(一行一行登记都成功；任务中心多选走同一端点同样失败)。改为分组后、委外短交评估与任何一组写入之前，把要新登记的每一组足迹合成一次预锁(全部订货单、库存维度、主仓、分析)，之后逐组登记只核对覆盖；单组与批量共用同一份足迹推导。规则与同类入口见 [ADR-107 第六节](ADR-107-履约预锁一轮发现与服务端截止时间.md)。回归：`ArrivalRegistrationBatchPrelockCoverageEndToEndTest`(3 张订货单 x 2 个仓两条路线、手工申请、两张委外、两组不同主仓、批量与逐行等价、草稿批量继续送检、并发两批)。

## 同行做法

- 表单自动保存：浏览器端草稿普遍按「当前内容 == 初始值则不保留草稿」处理，而显式丢弃与提交成功才作为终态(例如 Gmail/Outlook Web 草稿、Jira/Confluence 编辑器的未保存内容恢复)；终态用于防止旧标签页复活已提交内容。本 ADR 保持终态语义，只把「回到初始值」从终态里分出来。
- 数据库约束映射：Spring `SQLErrorCodeSQLExceptionTranslator` 把 23xxx 统一归为 DataIntegrityViolation，不区分「冲突」与「输入不合规」；PostgreSQL 错误字段 `routine`/`constraint` 是区分 RAISE 守卫与 CHECK 违反的稳定依据(与 `lc_messages` 无关)。HTTP 语义上 409 表示与资源当前状态冲突，422 表示请求内容语义不合规(RFC 9110 §15.5.10、RFC 4918 §11.2)。
