# 品质待检数量文本修复

品质检查单待检摘要的旧双 `rtrim` 会删除整数末尾的有效零。精确数量不再固定小数位后，`20::numeric::text` 为 `20`，旧表达式显示成 `2`；`2000` 同样变成 `2`，`0` 变为空字符串。这是实际查询缺陷，原 FullChain 的 `pendingQtyText.startsWith("20 ")` 断言保持不变。

唯一生产改动位于 `ProductionFqcInspectionService.sheetSql`，复用同服务单行数量读取已经使用的 PostgreSQL `trim_scale(... )::text`。保留原 `SUM(申报−合格−不良)`、单位分组、来源、权限、状态和检查单身份；删除的只是小数部分多余零，整数和极小有效数均完整输出。`pendingQtyText` 路径供检查单及相应待检摘要共同消费，Web、Flutter 和已实现的 WPF 调用方继续使用同一服务端响应合同。

## 证据

- 在本任务自有、完整迁移至 V1095/1034 份 SQL 的 PostgreSQL 中，以 `BEGIN READ ONLY / ROLLBACK` 原生复现：旧 `0→空、20→2、2000→2`；规范表达式得到 `0、20、2000`，极小数完整保留。
- 原始生产类运行新增的实际 `sheetSql` 表达式回归，完整 2 用例为 1 通过、1 失败；失败为 `0` 被显示为空，日志保留。
- 修复后实际生产类及原 pending-source 用例完整 **2/2、0 skip/abort、native exit 0**。覆盖 `0、20、2000、0.000000000000000000000001`，五行 `3+3+4+5+5=20`，精确小数求和与空 SUM 保持 NULL。测试从真实 `sheetSql` 取得表达式，JDBC 输入为独立精确 numeric 标量。
- 原业务同案 `arrivalRegistration_batchGroupsSameWarehouseIntoOneSheetAndSheetHandlingStaysPerInspection` 已通过：保留原 20 断言、3 份报工、2 张检查单、逐 inspection 的 FAIL/PASS、关闭和原登记撤回事实。它与 AR 发货及 final-report 成本案共同执行；该轮 3 案为 2 通过、1 成本阶段失败，不能写成 3/3。

主源 Java 的同型数值双 `rtrim` 仅此一处。当前测试库 public 活跃 view/function 中无 `rtrim`；迁移源码中的其它 `rtrim` 用于移除 DDL 的分号/换行，不做数量显示。本修复不修改已发布迁移，不新增迁移编号。
