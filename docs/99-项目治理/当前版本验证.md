# 2.5.4 候选验证与发布依据

本页对应 2026-10-06 提出的九项复核任务，以及 2026-10-07 追加的数量完整性和 AI 使用授权要求。实现版本 2.5.4，源码迁移 V821/747。本文随候选提交，最终提交、CI、签名制品与服务器激活分别以 GitHub 的 v2.5.4 标签、对应 Actions 运行和更新器现场回执核验，不能用本地测试代替发布完成。

2.5.3 候选的代码 CI 曾全部通过，但签名构建被过时的 Flutter 包元数据常量拦截，未进入签名和 OSS 上传，也未安装到公司服务器。其标签保留为失败候选依据。追加核查又复现了数量精度与高危授权缺口，因此按最新要求将后续修复统一纳入 2.5.4，不把旧候选绿灯视为新提交通过。

AI 操作记忆是本人有界操作记录，不能替代权限，也不代表模型在线训练。打开表单、识别填入与正式保存/审核是不同阶段；仍须沿对应业务确认与服务端授权执行。

文件能力还取决于实际模型：表格与文字 PDF 可以先在本地提取内容，销售图片和扫描 PDF 则需要真正支持视觉的模型。单张报销图片另有本地 PaddleOCR 路径。模型配置存在、OCR 健康端点可达、代码回归通过，均不能单独证明实际文件识别成功；运行配置与真实调用验收分别核对。

部署前在旧版 2.5.2 上另做了有界组件核验：默认文本模型沿实际协议、密钥解密和传输链完成一次无业务内容的请求，HTTP 200；本地 OCR 对合成图片完成一次真实推理，五个预设文本片段均识别成功、进程未重启。OCR 初始化仍有可选 ccache、模型参数覆盖和线程库兼容提示，未为消除日志而安装依赖或调整运行参数。这些结果不能代替新版本真实账号的完整业务文件验收。

## 数据库升级演练

发布前只读核对公司服务器运行 v2.5.2，Flyway V811/737、readiness UP。将其 28,831,520 字节 custom dump 恢复到本机独立 PostgreSQL 16 容器，保留角色名、对象所有者及授权关系，使用迁移身份进行前向升级；没有把本机数据库覆盖公司库，也没有执行公司业务清空。

V812 至 V820 共九个迁移已在该副本通过，746 个历史/新增迁移校验通过。带历史 NULL 归属日志的 V814→V820、已应用 V815→V820 及迁移失败回滚另有真实 PostgreSQL 回归，原日志逐行保持不变。逐表行数及排序行摘要对比仅出现权限目录、授权纪元、迁移历史、相应追加审计及四张新增空表；业务数量、金额、人员及来源表摘要未变。原始备份和包含现场标识的摘要只存本机，不提交仓库。

同一副本追加执行 V821 后，747 个迁移校验通过、失败数为零。逐一比较 492 张表，其中 486 张行数和排序摘要完全相同；仅权限目录、页面关联、授权纪元、迁移历史及追加审计六张表变化。业务数量与来源表、部门授权、个人覆盖、管理者委派均未变化，已有三项 AI 部门授权保留；AI 使用权限不再自动授予全员。

副本中只剩一份已完成的测试产品分析，未见截图对应的旧分析及 600/400 重复单据。因此原截图的历史处置不能据此确认；新增隔离回归覆盖两来源各 100、先下 400 的 BUY 与 MAKE 供给路径。历史正式单据若已存在重复，必须核对审核、领用、入库后沿原撤回链处理，不能直接删行。

## 验证与发布口径

- 前端源码和测试静态分析无问题；本地全量 Flutter 6,471 项通过、55 项按平台条件跳过。人事/权限、通知、清空及 AI 专项真实数据库结果分别记录于本机日志；后续修改追加定向回归，最终统一质量门与完整数据库分片以冻结提交汇总。
- Windows 无法执行的 Linux 部署/进程锁场景在 Linux 容器和 GitHub Linux 作业验证。浏览器 IndexedDB 测试单列 Chrome 门，不能用原生存储测试代替。
- 官网静态来源及本机 SQLite 中共 75 个 raw 图片引用均存在；这证明清理未破坏这些已检查的引用，不替代独立网站运行环境的内容验收。
- 正常业务拒绝、对抗测试主动触发约束错误、首次测试库创建管理员提示与真实服务启动告警分开核验；不关闭警告、不删失败用例来制造通过。
- 合并后的完整 CI 暴露了人事核对测试数据的随机碰撞：共享数据库的多个场景使用同一证件前缀与有限随机尾码，导致过期清理用例在准备员工时触发唯一约束。改为确定性的独立场景身份范围，并以固定输入复现原来的 `23505`，同时验证旧证号与升位候选均隔离；生产唯一约束和业务代码保持原样。
- 2.5.4 数量核查把界面原始十进制输入、分单请求、默认量的权威事实和预览贡献证明分别验证，不能将已解析成 double 的投影倒推成精确值。合法最小量 0.0001 不得当零跳过，单位比例保留六位；单行菜单与批量入口共用有效来源筛选。汇总下单的历史回执读取改用精确十进制，避免首次正确、重复读取却丢小数；销售报价、采购审核与普通物料回放的同类 JSON 入口另行核查，分别已有精确文本或仅处理身份字段。库存估算与实际写入的数量合同分开，当前业务库未因这些回归测试生成或改写单据。
- 打包工具从可信 checkout 的 pubspec 推导 Flutter 3.44.2 的严格元数据字节，并把来源摘要绑定到盖章事务；不接受产物自报或任意 JSON 替换。Quality Gate 在实际 Web 构建后执行同一盖章验证，浏览器门增加精确数量模型验证，避免只在打标签后才发现契约不一致。
- 发布按 [Git 规范](../00-项目准则/11-Git提交与合并规范.md)经 PR 合并，Quality Gate、CodeQL 和依赖扫描必须在最终 SHA 全部通过，再推送 v2.5.4 标签由 [Simple Release](../../.github/workflows/simple-release.yml)签名上传。
- 更新器先验证签名和清单，含迁移时先备份、停服并前向升级，之后切换并验证健康。迁移后若启动失败，保持应用停止，结合备份恢复或前向修复，不能让旧 JAR 直接运行于未核验的新结构。

日常运行步骤见[现役发布手册](../../deploy/simple/RUNBOOK.zh-CN.md)。旧候选的数字和未部署结论留在各自历史专项或 Git 历史，不再作为当前状态。
