2026-09-08 15:12–15:14 UTC，经既有 SSH 目标和固定主机公钥只读核查：

| 资源 | 实际结果 |
|---|---|
| 内存 | 31.06 GiB，采样时约 28.84 GiB 可用；不存在将磁盘余量解释成可用内存的问题 |
| 512 GB NVMe | 根逻辑卷分配 100 GiB；卷组尚有 373.89 GiB 未分配 |
| 两块 2 TB HDD | 已组成健康 RAID1，不可当两块空闲磁盘重新格式化 |
| `/data` | RAID1 上可用约 1.696 TiB |

| 现附件 | `/data/uten-imp/attachments`，元数据 0 条 |
| 现备份 | pgBackRest 与主数据库同在 HDD；升级 dump 在 NVMe 根目录 |

容量足以采用公司服务器存储，无须先采购硬件。部署方案优先给在线附件分配独立 NVMe 文件系统，解除与 HDD 数据库的直接读写竞争；预留卷组空间供后续扩展。独立文件系统限制附件增长，不把所有空间并入根目录。

主机评估提出媒体 200 GiB、暂存 32 GiB、数据库备份 64 GiB 的初始预算。最终挂载布局须与原子发布实现核对：若发布依赖同卷硬链接，发布临时文件必须留在媒体文件系统内，不能机械照搬独立暂存卷。数据库备份仓库的移动需要独立验证归档和还原，本次不因附件需求直接移动运行中的 PostgreSQL。

本次拟实施布局已收敛：从确认未分配的 NVMe 卷组分出 200 GiB，挂载到新目录 `/var/lib/uten-imp-media`；私有根目录为其中的 `attachments`，`staging/final/scratch` 均在该卷，至少保留 10 GiB，不再单分暂存卷。原 `/data/uten-imp/attachments` 保留作回退来源。数据库仍在 `/data/postgresql/16/main`，既有 pgBackRest 不搬迁；附件与数据库的成套备份另存到 HDD 并错峰限速。

新增 systemd 示例：`deploy/systemd/uten-imp-internal-storage.conf.example` 固定媒体及真实数据库挂载依赖；`clamav-uten-imp-resources.conf.example` 限制扫描 CPU、内存和任务数。仅本机回环开放扫描端口，应用按流送检，不通过 Nginx 暴露附件目录。启用上传前需要实际 ClamAV、原件往返及成套恢复成功，不能仅把配置开关写成 true。

实施前再次核对卷组剩余量、目标路径未被使用、实际块设备及文件系统 UUID，再创建新卷和挂载；不格式化现有 NVMe 根卷或 HDD RAID。回退保留旧应用、配置、目录、发布前数据库备份及对应文件集合；数据库已迁移后不得只切回旧 JAR 冒充完整回退。当前仍未执行这些服务器写入。

只读原始证据保存在本地 `.codex-tmp/internal-attachments-20260908/host-readonly/`：`assessment.md`、`summary.json` 及结构化采集结果。设备 UUID 在私有运维证据中核对，实施前重新检查；源码文档不保存 SSH 凭据。

## 待完成的验证与实施

内部磁盘实现已通过 Linux 64/64 测试、零跳过，包括真实目录持久化同步、创建不可覆盖、损坏/过长文件与原件往返；使用无网络测试容器，未连 OSS 或外网。V533 非空前向迁移6项、真实HTTP上传/下载/删除4项、Linux成套冷恢复18项已通过。新入口各自策略与界面结果见上表，最终全量、实际ClamAV及服务器安装仍需验收，不能将底层测试当成已上线。

附件统一要求 `attachment:view/download/upload/delete` 对应功能权，并叠加原单对象范围、金额读取和当前业务状态；附件权不能绕过业务页权限。新建单据先保存获得真实 UUID，再添加文件。下载每次重新授权，切换员工或撤权时不保留上一个人的文件名和缓存结果。删除文件走现有删除意图及 Outbox；删除业务草稿后原件不再对业务用户可见，审计文件按统一保留及对账机制处理，本次没有引入静默级联清空。

共享调用方使用 `lib/shared/attachments/business_attachment_section.dart`，包含读取、失败重试、无权限隐藏、上传/删除后的单据内刷新。每个 owning feature 的 `AttachmentOwnerAccessPolicy` 在确认和删除时锁定真实原单再核对状态；已审核原件不因页面状态过期而被替换。

配套备份已落地：[成套备份说明](../../deploy/postgres/backup/PAIRED_INTERNAL_BACKUP.zh-CN.md)。同一数据库快照与原件引用锁覆盖复制和dump，完整成功后才原子发布；既有成功副本保留。真实PostgreSQL验证9项覆盖并发删除、缺失或损坏原件、取消、失败及恢复；原子任务状态与监控另有19项组合验证。服务器尚未安装定时器。备份进程的CPU、内存与复制限速不等于限制PostgreSQL服务端扫描，实际负载仍须部署后验证。
