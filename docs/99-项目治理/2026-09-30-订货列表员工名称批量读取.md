# 订货列表员工名称批量读取

日期：2026-09-30。承接 W07/R2.02。源码基线为 `d1bbfb7f467c7082f3ca9340a216a2ee4cf7b138`，在已有 UI 候选工作区中独立实现后端增量；已冻结的 UI 文件不改。当前状态：实现、独立只读审阅及定向验证完成，22 项非 DB 与另一批 8 项真实 PG 测试全绿且 0 跳过；尚未集成或部署。

## 当前事实与范围

- `SalesOrderService.list` 在数据库分页后逐行调用 `EmployeeNameResolver.nameOf(sellerId)`。普通员工 UUID 一次查询，旧 users.id 回退通常两次查询；同页重名或重复员工也反复访问。
- 采购和委外订货列表没有逐行解析员工姓名。它们已通过 `ProcurementApprovalProjectionQuery.latestForOrders` 一次读取本页最新审批 case，并原样展示 `assignee_name_snapshot`。不能为了覆盖模块清单而额外查询员工或用现在的姓名替换审核时的快照。
- 本轮不改销售单写流程、金额、价格遮蔽、对象范围、筛选、排序、分页元数据和状态口径；采购/委外生产代码保持原样，由回归证明已有快路径。

## 实现合同

`EmployeeNameResolver` 新增 `namesOf(Collection<UUID>)` 与 `namesWithCodeOf(Collection<UUID>)` 两个只读接口：

1. 过滤 null、去重，每块最多 256 个 UUID。每块一条 SQL，以请求涉及的 employees/users ID 并集关联直接员工和历史账号绑定；最多展开 512 个绑定位置，不随调用方集合无限扩大单条 SQL。
2. 直接 employees.id 对应值优先，未解析到值才走 users.id → employee_id。沿用单笔读的 SQL 值语义，不加入员工/账号软删除过滤；历史人名仍可追溯。
3. 只返回已解析的键值，未知和空 ID 查得 null；返回映射不可修改、null 查询安全。调用方仍显式检查 nullable sellerId 后再 get，避免将来映射实现变化造成空键异常。
4. 结果仅属于这次读取，无全局或跨请求缓存。新请求读取改名和账号绑定的最新事实，不修改已经返回的映射。
5. 单笔 `nameOf`、`nameWithCodeOf` 以及 `resolveForWrite` 和它的写入校验辅助方法均未改动。

销售列表先取得本页，再批读这页的 sellerId，并按原页面顺序映射到 DTO；空页跳过姓名解析，不多读其它页员工，不改变原 sellerId。

### 带工号的历史边界

现有 `nameWithCodeOf` 注释称缺工号时回退纯姓名，但实际 PostgreSQL `full_name || '(' || code || ')'` 在 code 为 NULL 时得 NULL，并可能继续走旧 users.id 回退；空字符串工号会显示空括号。当前 employees.code/full_name 结构要求非空。

本轮保留实际单笔行为，不借性能优化修订历史显示。真实 PG 投影夹具可构造缺字段的历史边界来验证批量与单笔一致；这个夹具故意不保留业务 NOT NULL/CHECK/FK，不能解释为正式库允许这些不完整资料。是否修订显示政策应另行决定。
