# V729 公共供给按分析先筛选再计算

- 日期：2026-09-26。
- 迁移：`V729__scoped_public_surplus_source_reader.sql`。
- 新增后源码目录 V729／658，不代表业务库已安装。

## 根因与实现

全量验证发现公共供给来源查询先物化全库 `SUPPLY` 来源，再评估容量、认领实收和预计到货，最后才按当前分析的仓库与物料筛选。无关来源增长时会重复支付这些计算成本。只将原 CTE 改为 `NOT MATERIALIZED` 的只读查询计划验证未消除这一问题，未采用该表面修法。

新增 `fn_preplan_public_surplus_sources(p_target_analysis UUID DEFAULT NULL)`，把已有视图的唯一权威查询移入 SQL STABLE 函数。给出分析时，在来源 CTE 先按同主仓、有效物料的货品/颜色/单位过滤；认领计算仍以整个认领动作为单位，仅排除与这些来源无关的动作，不提前裁掉明细以绕过单一来源证明。容量、认领量和预计到货继续使用原函数，未改变计算规则或放宽数量及来源守卫。

旧 `v_preplan_public_surplus_source_state` 作为无范围参数的兼容入口，列名、顺序与 PostgreSQL 类型保持一致。函数采用可内联的 SQL 形式，避免给旧视图按单一来源查询新增强制全量计算边界。迁移对旧定义关键锚点及权威函数存在性逐项检查，不符合预期则失败停止。

生产来源预锁、材料分析的公共供给查询及预算读取统一调用带目标分析的入口。没有在 Java 复制一套数量算法，没有增加超时或排除测试。

同轮应用修复将“可展示”与“可认领”分开：本需求自己产生的公共来源仍展示已批准在途和交期，仅将该需求的可认领量置零；身份以 `fn_preplan_public_target_is_source` 的原行及别名关系判定，不能把同分析其它产品的合法来源一起排除。判断发生在单据身份按权限脱敏之前。这是应用投影修复，不是 V729 改写数量公式。

## 验证口径

隔离 PostgreSQL 先安装 V728，保存旧视图定义与列类型，再前向安装 V729。比较采购、委外、认领和实收前后旧、新结果的全部字段；用真实无关分析来源和会抛错的计算探针，证明 scoped 查询不再对无关来源执行昂贵容量/实收/预计到货计算。另验证同主仓叶仓、颜色、单位和有效物料边界，以及旧视图点查仍可内联。

这项迁移只解决采购和委外公共供给候选范围的计算问题。制造公共供给另由 [V732](251-V732制造公共供给按来源筛选后计算.md) 处理；其他递归 BOM 别名查询是否超时，须以对应最新用例单独复验结果为准，不能从候选优化推断整条链路都无性能问题。各项定向回执及全量未完成边界见[收尾记录](../99-项目治理/2026-09-26-领料申请批量出库与编号收尾.md)。

本次没有修改已应用迁移，也没有在业务库执行迁移、清空或反向删除。应用回退时仍保留原视图接口；上线按既有备份、迁移、制品激活和岗位验收流程执行。
