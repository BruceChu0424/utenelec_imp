## 一、一张图：权限从哪来，到哪用

2026-09-12性能整改保持权限来源和显隐规则。系统设置新增原子批量 `PUT /api/admin/system-settings`，与单项入口一样同时要求 `authorization:manage`、服务端当前超级管理员身份和本次密码确认；批量携带每项旧值，防止并发覆盖。V553仅修改设置说明，不扩授权限。审计统计独立加载、会话先分页取证仍使用 `audit_log:view`，导出仍额外要求 `audit_log:export`；辅助货品/员工名称查询只合并相同会话内请求，不跨账号缓存或放宽对象授权。


## 三、工作台的权限（集散层与任务中心）

**设计原则(ADR-007，ADR-109 收口)**：工作台是功能**集散入口**，不是独立权限域——卡片显隐直接复用路由守卫的
`permission_by_path` 映射(单一数据源)，超管授了什么权限，工作台就出现什么模块。**工作台权限管理总设计**：
每个 hub 上会出现的卡片落点登记在 `lib/core/router/hub_catalog.dart`(同一张卡按权限切换「新建页 / 列表页」时
两个都登记)；hub 路由守卫 = 子卡守卫并集；hub 页与工作台只调 `hubCardAllowed / locationAllowedFor`，
页面里不写 `perms.contains`；`hub_guard_union_test` 经 GoRouter 锁住「能开任一子卡就能进 hub」。因此**没有泛化的
`workbench:*` 权限码**；各任务中心要么复用领域查看权限，要么拥有自己的专属码：

### 部门提醒、操作授权与任务徽章的边界(2026-09-07)

- 页面查看、页面内操作、对象范围和弹窗接收是四道不同检查。中央明确个人加授的财务审核人仍可
  在权限及对象范围内审批；部门外个人加授不会自动产生财务部门弹窗，要接收需维护主职或兼职部门。
- `ReviewNoticeAudience` 在登录查询、到达 feed、详情 DTO 和弹窗心跳按当前部门祖先与有效权限复核。
  超管同样须命中部门；仅 view 不弹，须同时持通知读取、目标页 view 与相应确认/处理/开工/创建动作。
  财务初审/改量复审、IQC、计划分析、车间、仓库入库/发料及退回贷项统一走此规则。
- 登录待办先按有资格的事件集合在 SQL 内筛选再分页，避免旧部门任务占满 20 条上限；到达 feed
  过滤失去资格的任务仍推进原始 keyset 游标，避免永远重复扫描。部门查询每批一次，状态表批量读取。
- 历史未绑定 aggregate 的通知只作历史信息，不成为永远无法办结的弹窗。办结、稍后、删除、调岗或
  收权后心跳撤卡；切换账号/模拟身份取消旧检查与旧对话框，迟到响应不得跨身份展示。
- 常用功能不再提供待审收件台。实际任务页面的服务端 count 是徽章真源；已读/稍后不清业务任务，
  不叠加已退役收件台的通知计数。跨域弹窗回工作台，各条目直接进入其领域任务页面。
- 委外前置自制 GET `/production/material-analyses/subcontract-make-tasks` 使用
  `production_material_analysis:view` 或 `subcontract_application:view`。委外侧沿用共享申请任务池只读，
  纯计划侧的 count/list 同时应用生产 owner 范围；`NOTIFY_SUBCONTRACT` 只在 view+notify、对象可写及
  实际可通知量均满足时返回，不因委外查看权出现计划写按钮。

## 四、管理端总入口（`/admin/permissions`）

- **入口权限**：`account:support` 或 `authorization:manage` 任一可进；support-only 只渲染账号支持区
  （列表/补开/状态/重置密码），授权/部门/数据范围区必须 `authorization:manage` 且后端再校验超管。
- **目录浏览器**（`permission_catalog_browser.dart`）：功能模块 → 子类 → 权限项三级展示，数据来自
  `GET /api/admin/permission-catalog`（`DepartmentPermissionAdminService.catalog()`，固定 11 个模块排序：
  基础资料/销售/采购/委外/生产/仓库/财税/工程研发/人事行政/品质检测/系统管理，未登记归「其他」）。

  不随批量授权 / 负责人不能转授 / 全员默认拥有)。「全部授权 / 本模块 / 本组」只把范围交给服务端

## 2026-09-19 车间路线与持续补料权限

生产路线与供料来源分开：齐套、同工单持续补料、独立分批三种执行方式共用原权限体系。
新有物料任务先确认路线再预留/领料；已经发生的历史库存、报工与成本事实不因路线重构改写。

## 2026-09-28: 车间内料仓 (ADR-131, V740)

[ADR-131 车间整批领料与盘点计耗](../99-决策记录-ADR/ADR-131-车间整批领料与盘点计耗.md) §8.2 新增 **7 个权限码** (模块"仓库管理"、分类"车间内料仓"), 登记进权限目录单一事实源 (ADR-109)。路由守卫共 **216 条 / 17 条豁免**。

|---|---|---|---|---|
| `workshop_material:view` | 查看车间内料仓与用量报表 | VIEW | NORMAL | 生产部 (`DEPT_PROD`, 含各车间)、PMC 运营仓储部 (`SUB_WH`)、PMC 运营计划部 (`SUB_PLAN`)、财务部 (`DEPT_FIN`) |
| `workshop_material:issue` | 发料到车间内料仓与接收退回 | EXECUTE | NORMAL | 仓储部 |
| `workshop_material:request` | 车间申请领料、退回与登记其它耗用 | CREATE | NORMAL | 生产部 |
| `workshop_material:count` | 车间内料仓盘点 (开始、录入、提交、更正、撤回; 立即重试结算) | EXECUTE | NORMAL | 生产部、仓储部 |

| `workshop_material:setup` | 车间整批领料设置、机台与上线准备 | CONFIGURE | BULK_EXCLUDED + NON_DELEGABLE | 仓储部 |
| `workshop_material:reopen` | 撤销车间内料仓结算 (高危) | EXECUTE | INDIVIDUAL_ONLY | 不授予任何部门, 由超管逐人授予; 接口另加 `@RequiresStepUp` 再认证 |

- **部门授予对下级部门同样生效** (ADR-109 §3.5): 授给生产部即覆盖各车间, 不写车间名。
- **路由守卫** (`permission_by_path.dart`): `/workshop-material/bin`、`/reports/workshop-material` 任一 `view`; `/workshop-material/issue` 要 `issue`; `/workshop-material/count` 要 `count`; `/warehouse/workshop-material/setup` 要 `setup`。仓库枢纽子卡并集因此多一个 `setup`; 生产与财务两个枢纽的报表区各登记一次用量报表路由。
- **页面按钮只看服务端 `allowedActions`**: 设置、内料仓现存、领料单、盘点单、期间与结算状态的响应都带 `allowedActions` (如 `REQUEST`、`RETURN`、`OTHER_ISSUE`、`FULFIL`、`CANCEL`、`START_COUNT`、`EDIT_COUNT`、`SUBMIT_COUNT`、`CORRECT_COUNT`、`WITHDRAW_COUNT`、`CLOSE_RETRY`、`REOPEN`、`SETUP`); 车间生产任务的段带 `CHANGE_MATERIAL`、`CHOOSE`。前端 `Perm.workshopMaterial*` 常量只供路由守卫与码表对齐测试, 页面里不引用 (页面权限字面量基线只许下降)。
- **对象范围**: 车间成员 (生产部子树的部门成员, 判定同 `ProductionWorkshopAssignmentScope`) 只看、只办本车间内料仓; 其他部门持 `view` 的人看全部。仓库待办按 ADR-115 `WarehouseTaskScopePort` 分发, 领料单按预填叶仓定范围与通知对象。
- **金额**: 用量报表的单价、金额、单件材料成本按 `goods:cost:view` 返回, 没有时为空值。
- **基础资料侧零新增码**: 发料方式切换预览 `goods:view`, 确认切换 `goods:edit` + `goods:bom:edit`; 上线准备清单 `goods:view` + `workshop_material:setup`, 批量保存 `goods:bom:create` + `goods:bom:edit`; BOM 期间边的新增和改单重仍是 `goods:bom:create` / `goods:bom:edit`。仓储部默认没有 BOM 码, 上线准备的保存要由 BOM 维护部门办或单独加授。
- **权限面** (页面内"本页权限"): `warehouse.workshop-material` (view/issue/count)、`warehouse.workshop-material-setup` (view/setup)、`production.workshop-material` (view/request/count/choose)、`report.workshop-material` (view/reopen)。
- **新权限码写在登录令牌里, 上线后用户要重新登录一次才生效** (使用说明已写明)。
- 契约测试: `PreAuthorizeCodesAreActiveContractTest`、`PermissionCatalogBidirectionalContractTest`、`PermissionChainReachabilityContractTest`、`PermissionGrantPolicyContractTest`、前端 `route_permission_full_coverage_test.dart` 与 `permission_code_alignment_test.dart`。

### 主档学习的「受控回写」例外

基础资料的写入原则是「只在基础资料页由主档编辑权限维护」。ADR-134 为保存报价/订货单后的学习开了一个**受控例外**，限定如下：

| 回写内容 | 需要的权限与范围 | 来源限定 | 审计 |
| --- | --- | --- | --- |
| 客户货品对照(`client_goods_aliases`，客户级) | 保存单据本身的权限 + 对该客户有写范围(只读共享不算) | 只学服务端保存的识别结果里的原文(按 `intakeLineKey` 对行)，用户明确选择或识别已自动对应且未改货品的行 | 自动学习不挂行级审计(NONE/preference)；用户在「货品对照」页签删除写显式审计 |
| 全局对照(`client_id` 为空) | 同上 | 只学与识别原文一致的文字；可信度按不同客户数计，至少 2 个客户才用 | 同上 |
| 货品英文名称(`goods.name_en`，来源 LEARNED) | `goods:name_en:edit` 或 `goods:edit` + 对货品有写范围 | 用户在面板勾选「设为货品英文名」且文字与识别结果的英文描述一致；写入的是去掉描述尾部规格行(如 `Current: 10A`)后的品名文字(2026-09-28) | 货品表行级审计(FULL)保留旧值 |
| 客户资料补全(九个字段：外文名称、全称、联系人、邮箱、电话、手机、地址、税号、网址) | `client:edit` + 对客户有写范围 | 用户在面板勾选；保存事务内校验，不合法 422 整单回滚 | 显式事件 `client.learn_from_document`「从客户文件补全: 字段名」，不含值 |

缺权限的部分静默跳过，不影响单据保存；学习的权限按当前登录人重新判定。价格、折扣与其它主档字段从不学习。
