## 一、结论先行

1. **货品和货品分类的成功新增实际有记录。** 本地开发 PostgreSQL 的只读核查找到 2 条成功 goods insert
   和 1 条成功 material_categories insert；每次都同时存在 HTTP request 与 database insert，Request ID、
   actor 和 POST 200 能串联。失败 POST 仍有 request 记录；事务未提交或回滚时没有 database 变化行是正确结果。
2. **用户感知的主因是“有记录但难找到”。** 旧页面缺少对象、来源、Request ID、操作类型和用户/系统范围，
   大量 GET、迁移和审计查询自身记录把人工写操作推到很后面；旧 offset 页集也会被后续高 ID 审计推移。
3. **复核同时发现并关闭了真实查询边角。** 四个主档快捷对象过去只精确匹配数据库表类型，会漏掉只有
   request 记录的失败/回滚尝试；V185 前普通主档软删除通常以 update/低风险存储；直接 summary/export 未必复用页面边界；
   分页响应曾可能回显未归一的 page/size。上述问题均已在读模型、接口与测试中修复。
4. **触发器覆盖不能只看名字。** V184 现在要求每张非白名单公开业务表恰有一个 `trg_audit%`，且必须启用、
   为 AFTER ROW、覆盖 INSERT/UPDATE/DELETE，并调用 public 下的 `fn_audit` 或 `fn_audit_redacted`；缺失时补挂，
   禁用、错误函数、错误事件、错误时机或重复触发器都 fail closed。
5. **V185 加固未来事实，不伪造或无界重写历史。** 通用与高敏触发器之后都把可识别软删除写为 delete，
   扩充迁移列明的凭证、PII、原因备注类敏感文本和大型嵌套 JSON 快照最小化，并保留 V172 设备关联字段。
   旧软删除由读侧解释为删除/高风险；旧审计行不自动改写，须受限访问并按批准流程专项扫描。
6. **`snapshotId` 是高水位，不是跨请求 MVCC 快照。** 它能排除通常后续分配的更高 ID，消除审计查询自身
   造成的主要漂移；旧 ID 晚提交和留存任务并发删除仍可能改变 offset，必须在生产同构库单独验收。

## 三、请求记录与数据库记录如何对应

| 场景 | request 层 | database 层 | 核查口径 |
|---|---|---|---|
| 成功新增/修改/删除 | `http_post/http_put/http_patch/http_delete`，含状态码与耗时 | `insert/update/delete`，含脱敏 before/after | 用同一 Request ID 联查，不只看一层 |
| 业务校验/服务器失败 | 仍记录失败请求及 HTTP 状态 | 未产生 DML 或事务回滚时没有变化行 | “有失败 request、无 database 变化”合理 |
| 普通读取 | 通常为 `http_get` | 无行变化触发器 | 用 `operationKind=read` 查询 |
| 显式安全/敏感事件 | request 外可有 business/security 事件 | 同时改表时才有变化行 | 按来源与 Request ID 联查 |
| 迁移/后台任务/直接 SQL | 可能没有 HTTP request | 可有 actor 为空的 database 记录 | 切换 `actorScope=system` 或“全部”，不得删除噪声 |

## 五、本次修复

### 5.1 可见性、对象与操作语义

- 默认最近七天 `actorScope=user` + `operationKind=write`，优先呈现人工增删改；“全部”/`system` 仍可查看
  原始系统与迁移记录，不改变保留策略。
- 新增 `keyword`、`targetType`、`targetId`、`eventSource`、`requestId`、`operationKind`、`actorScope`。
  关键字只搜索 action、actorAccount、targetType、targetId、httpPath、requestId，不搜索 before/after、UA 或 IP。
- goods、material_categories、clients、suppliers 快捷项同时匹配数据库表名与对应 `/api/master/**` request
  路由组，成功、失败和回滚尝试可在同一对象入口找到。
- Request ID 独立输入只提交规范 UUID，部分值走关键字；“查看同一操作”清除互斥条件后精确联查。
- create = insert/http_post；update = update/http_put/http_patch，但排除可识别历史软删除；delete =
  delete/http_delete + 历史 `is_deleted false→true` / `deleted_at null→非空` UPDATE；write 为增删改并集；
  read = http_get + `view_%`。
- 历史软删除在解释器、筛选、统计、趋势和导出中统一显示“删除/高风险”，不改原审计行。

### 5.2 查询高水位与导出

- 首次列表不传 `snapshotId`，服务端取当时 `max(id)`（空表 0）；响应返回
  `items/page/size/total/totalPages/snapshotId`，page/size 回显服务端实际归一值（size 1–100）。
- 后续列表、summary 和页面 export 固定 `id <= snapshotId`，排序 `createdAt DESC, id DESC`；刷新、搜索、
  日期、筛选、卡片下钻或“同一操作”定位会清除旧边界。
- 直接调用 summary/export 且未传 `snapshotId` 时，服务端也会在请求开始自行捕获高水位。
- 页面在首次列表高水位尚未取得前禁用 `UtenExportButton`，不会弹密码框或发 API；取得边界后导出复用
  全部筛选与高水位。
- 高水位不是 MVCC：旧 ID 晚提交和留存并发删除是已知边界；生产验收必须覆盖这两类场景。

### 5.3 V184 触发器覆盖治理

- V169 文件保持 byte-for-byte 不变，`FlywayMigrationImmutabilityTest` 固定已应用 checksum `1098302988`。
- V184 对 public 普通表/分区父表执行 exactly-one 复核，跳过分区、明确技术白名单与
  `legacy_migration_%`；没有前缀触发器时创建 `AFTER INSERT OR UPDATE OR DELETE ... FOR EACH ROW fn_audit()`。
- 已有触发器只有在数量恰为 1、启用、AFTER ROW、同时覆盖 I/U/D 且调用批准函数时才通过；错误或重复均
  `RAISE EXCEPTION`，块末尾再以相同 1/1 契约复核全部业务表。
- 静态契约测试解析带/不带 `public.` 与双引号的 `CREATE TABLE`，要求最新 sweep 后的表只能进入有理由的
  技术白名单，并直接断言 V184 exactly-one、启用状态、tgtype、函数与 fail-closed 契约。

静态测试不能执行 PostgreSQL DDL，也不能证明目标库 trigger 状态；部署仍须运行运维文档中的 1/1 查询。

### 5.4 V185 软删除与行最小化

- 同时重定义 `fn_audit` 与 `fn_audit_redacted`，保留 V172 的本机操作 ID、安装标识、设备声明、采集状态与
  `device_profile_hash`，避免加固时丢失既有取证列。
- 两条函数路径都把未来可识别软删除存为 delete；V185 前 update 由读模型兼容，不回写历史。
- 新增 `period` 作为资产会计期间的可用 target ID 候选。
- 扩充 `preview_token_hash`、原因/备注字段、payload、exception/calculation snapshot、required document
  codes/snapshot、source ref/line ref 等列明字段的最小化。业务名称、编号等调查必需字段仍保留，不能表述为
  “所有自由文本均删除”。

## 六、接口契约

- list：原 action/actorAccount/riskLevel/eventCategory/outcome/dateFrom/dateTo，加全部新增筛选及分页；
- summary：action/actorAccount/eventCategory 与基础筛选，不接 riskLevel/outcome，避免卡片被自身条件过滤；
- export：list 全部业务筛选 + `snapshotId`，不接 page/size；缺高水位时服务端自行捕获；
- keyword：仅在批准的六个非敏感列上做不区分大小写 contains；
- targetId/eventSource：忽略大小写精确匹配；四个快捷 targetType 有 request 路由别名，其它 targetType 精确匹配；
- requestId：UUID 精确匹配；负 snapshot、非法 operationKind/actorScope、非规范 UUID 返回 400；
- 查看仍需 `audit_log:view`，导出还需 `audit_log:export`，权限范围未扩大。

## 八、历史边界与数据处理原则

- 不修改或 repair 已应用 V169；后续变化只进入 V184/V185。
- 不向 `audit_log` 人工插入推测事件，不把当前 created_at/updated_at 当历史操作时间，不用当前负责人冒充
  历史操作人。
- 对触发器生效前的缺口，只登记时间范围、库版本、表和独立旁证；旁证与原生审计证据分开标注。
- V185 不无界重写旧审计。旧行先做受控扫描、风险分级、调查冻结/备份判断，再按主键分批治理和维护；不能
  用一次大 UPDATE 锁住热表，也不能声称历史敏感字段已自动清除。
- V184/V185 上线后先做受控 CRUD/软删除探针再开放相关业务；探针审计必须保留。
