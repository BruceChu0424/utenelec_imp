# 待检处置页（IQC + FQC 统一队列）

品质任务中心统一办理采购收货、委外回厂和自制产成品检验。品质决定只形成合格待仓库确认的资格；仓库实收入库、退换补及不合格后续处理仍沿各自来源链办理。本文维护当前界面和实现，历史改版叙述已并入现行规则；发布状态见[本轮验收](../99-项目治理/2026-09-12-全站性能与稳定性验收.md)。

## 一、页面、权限与计数

- 入口为 `/quality/task-center` 的“待检处置”；列表沿用 `/warehouse/inspections`，IQC详情为 `/warehouse/inspections/:receiptType/:receiptId`，批量审批为 `/warehouse/inspections/batch-approval`；FQC检查单办理页为 `/warehouse/inspections/fqc/sheets/:sheetId`、单任务办理页为 `/warehouse/inspections/fqc/inspections/:inspectionId`（2026-09-12 弹窗改页，对齐采购IQC处置页范式），旧深链继续有效。
- 进入要求 IQC `procurement_inspection:view` 或 FQC `production_quality_inspection:view`。两域分别门控：未获得相应查看权限就不渲染、不请求该域任务。
- IQC处理另需 `procurement_inspection:handle`；FQC决定另需 `production_quality_inspection:approve` 且服务端确认有效品质组织池。客户端 `canDecide` 失败关闭写按钮，查看和处理权限不混用。
- 工作台与分段计数来自两个服务端pending-count。IQC按待检收货单张数计；FQC按品质检查单数加无检查单历史任务数计。通知只触发刷新，不能作为任务数；返回处置页、工作台或收到新通知后立即失效重拉。
- 仓库预计到货页仅显示“待品质部批准”的只读状态，不承担待检办理入口。

## 二、当前界面和提交规则

工具条提供“全部待检单／采购收货／委外回厂／自制产成品”四段、红色圆数字徽章及胶囊搜索框。搜索跨收货单号、供应商、报工、计划、货品和颜色，300ms防抖。已授权域仍在加载时不显示半程总计，也不把未知数量显示为零。

统一表格使用 `MasterDataTableView`。IQC一行一张收货单；FQC一行一张同仓送检的品质检查单，V547前无检查单的历史任务单列。FQC检查单和历史任务分别最多读取500条，服务端总数超过已装载行时保留截断提示，不能声称页面含全部任务。状态筛选和页码作用于已装载的客户端全集；筛选、刷新或搜索后移除已不存在的过滤值。2026-09-12 起表格下方的「共N单 / 合计待检行数」合计条撤除（用户口径：分段徽章与行数列已给计数，底部再报一遍是重复）。

双击IQC进入本单处置，直接按行填合格／不合格数量；双击FQC检查单进入检查单办理页、双击无检查单历史任务进入单任务办理页（2026-09-12 起都是独立页面，不再叠弹窗）：办理页与IQC处置页同构——单据摘要卡 + 行级合格／不合格数量（默认全合格）+ 不合格处置方式（含不合格的行）+ 右下角「提交报告」，单任务页另挂检验图片和文件（首检后冻结）；提交走总结确认弹窗后逐行 `decide`（行级幂等键，重试不重复），从列表双击进入时决定成功带结果返回、列表先本地落位再刷新。列表多选后进入批量审批页，IQC按收货单分组、FQC按检查单分组（勾选=全部合格）；同一FQC任务同时出现在检查单和历史选择时只保留一份。

提交报告前展示数量、当前检验员及责任提示。IQC默认合格为剩余待检、不合格为零，两者不得为负、非有限数或同时为零，合计不得超过本行剩余。含不合格数量时结论原因必填。数量使用服务端基本单位，原单1箱=24个、到检48个时，填写24合格+24不合格仍直接提交24+24，不再二次换算；`sourceUnitName/unitRate`只用于框内说明。汇总按单位UUID分组，未知单位提示核对。

| 提交范围 | 当前接口 | 原子性 |
|---|---|---|
| 一张IQC收货单的所选明细 | `POST /api/procurement/inspection/{receiptType}/{receiptId}/decide-batch`，每行含ID、expectedRemaining、PASS/FAIL量及幂等键 | 每单最多100行，整单校验后按原事件顺序写入，任一失败全回滚 |
| 所选FQC任务全部合格 | `POST /api/production/quality-inspections/decisions/pass-all` | 每批最多100项；既有服务端全批来源锁和状态校验，固定批幂等键 |
| 跨多张IQC收货单及FQC | 页面按已确认报告依次调用以上接口 | 各单独立提交；失败停止后续，不声称跨单全回滚 |

旧IQC单行处置和pass-batch接口保留兼容；它们不是当前页面的备用按钮。旧“单行不合格／部分合格／批量放行”三套按钮和右键菜单已退出本单报告界面。

### 加载与失败恢复

- IQC和FQC详情共用最多4个并发读取，保持所选单据顺序；单张失败留在其分组并允许重试。只重拉失败单据，保留其他单据的勾选与已编辑数量。
- 确认后由 `QualityBatchSubmission` 冻结每单成员、数量、原因及原幂等键；FQC全批键同样只生成一次。只有收到成功回执才推进已确认序号；超时或响应丢失继续用完全相同的当前命令核对，已确认成功的收货单不再发送。
- 失败后页面显示已确认单数并保留“重试原报告”；冻结区禁用输入和键盘焦点，避免显示的新数量与重发的旧报告不一致。需要修改时返回待检队列重新读取，不能直接把新请求体配到旧键。
- 请求执行期间拦截工具栏与系统返回；停在错误状态后允许返回。离开加载页后停止发起排队请求，并释放迟到响应创建的输入控制器。
- 数量、原因及来源状态的最终判断仍由服务端负责。新批精确重放的数据库证据由V557保存；旧事件不猜测、不回填批成员。

## 三、业务口径（与 V222/V335/V410+ 后端一致）

- 收货审核在同一事务内创建 PENDING 冻结行并追加 `PROCUREMENT_IQC_PENDING` 业务 Outbox，
  **不写 stock_balances**；三个可用量口径
  （warehouseAvailableBase/globalAvailableBase/v_stock_available）自然不含待检品。
- 待检 Outbox 按收货单 UUID `publishOnce`：同一收货单有多条明细只投递一次；收货审核事务
  回滚时待检行与 Outbox 一并回滚，不产生孤立通知。
- 待检通知只发给 `DEPT_QA` 子树内当前在职、账号启用，且最终有效权限仍包含
  `procurement_inspection:view` 的账号；PMC/生产默认查看权、跨部门个人加授和超管全集均不扩张
  品质通知池。接收通知不要求 `procurement_inspection:handle`，点击进入 `/quality/task-center`。
- Outbox 真正送达前重查本单是否仍有 `PENDING/PARTIAL` 明细；若已经极速处置结案，则跳过
  过期待检通知。待检角标仍以 `pending-count` 的实时聚合为唯一真相。
- 每次部分 PASS 只追加品质合格数量、事件和"合格待仓库入库"任务；`passed_base_qty`
  不是可用库存，不能直接生成库存流水、分析归属、reservation、DRAW 或 READY。
- PASS 无放行说明时，事件 `reason` 保存为 `NULL`；有说明时才追加说明文字。V335 只放宽
  PASS，FAIL 的非空原因数据库约束保持不变。
- 仓库可按合格待入库量分批填写实际库位并确认入库。只有仓库确认事务才写 `DIR_IN`、
  增加 `warehouse_stocked_base_qty`，并按该次实际入库切片刷新分析与推进正式供给。
- 整张 receipt 品质结案只表示 PASS/FAIL 数量已确定；全部 PASS 量都经仓库确认后，才是
  "仓库已入库"。通知、角标、生产齐套和报表不得把两个状态合并。
- FAIL 不入可用；处置（退/换/补/特采）走对应业务单据，本页只登记质量事实。
- 红冲收货前必须全部明细 RESOLVED；只按实际 `warehouse_stocked_base_qty` 反向库存，
  已 PASS 但未确认入库的数量只取消待入库任务。
- FQC 侧口径（并入后不变，详见[生产成品质检任务页](生产成品质检任务页.md)）：
  任务来自仓库已登记送检；PASS/PARTIAL 只形成 FINISHED_IN 待点收上限，不直接增加库存或
  `iqty`；FAIL 进入 REWORK 或 SCRAP/REJECT 补产链；来源红冲按顺序取消派生事实。

## 四、安全边界

- 处置按钮由前端按权限隐藏，服务端 `@PreAuthorize` 独立兜底（IQC view+handle；
  FQC approve + 品质组织池）。
- 审核员显示不是安全边界：服务端忽略客户端身份声明，并以
  `SecurityContextCurrentUser.requireEmployeeId()` 写入追加式事件表的 actor；
  全局 `fn_audit()` 继续记录事务审计事实。
- 数量校验双保险：前端对话框校验（正数且 ≤ 剩余），服务端按剩余待检量硬校验。
- 处置成功后先从本地表格移除已提交行，再刷新服务端投影；刷新失败也不恢复旧可操作行。
- 无对应 view 权限的域前端不渲染、不请求；服务端仍按各自权限与对象范围裁剪，
  前端显隐不是安全边界。
