# 网页更新安全锁误阻塞修复

日期：2026-11-01（用户时区）。基线：`bd7e8525b`，独立分支 `uimp/web-update-safety-recovery-20261101`。本次为客户端交互及请求语义修复，保留现有 `frontend-design`、Uten 组件与主题，无后端、数据库、版本号或发布操作。

## 现象与已确认原因

用户反馈服务器更新完成后，工作台上的新版弹窗持续显示“当前操作尚未完成”，主按钮灰置。`web/update_check.js` 的按钮要求工作安全快照同时满足 ready、无 dirty/busy/blocked。

已复现的缺陷链路：通知已读/弹卡回执及扩展字段只读 POST 被 `ApiClient._trackPost` 当成业务写入；服务器重启返回 502 后，`ApiMutationReloadSafety` 把 `_uncertain` 永久置为 true；之后 `/auth/me` 恢复成功也不能解除该锁。新回归在修复前有 7 项失败，修复后通过。未读取截图页面的实际运行时快照，因此不能断言该实例具体是哪一个请求；以上为可验证的同场景故障机制。

真实业务未知提交不能凭联网恢复消除。本次只修正错误分类，不清空或重置已经存在的业务未知提交标记。

## 公共入口、调用方与保留差异

| 平台/入口 | 原行为及问题 | 本次公共实现/状态 |
|---|---|---|
| `ApiClient.post` / `postList` → `_trackPost` | 除原生 facets 外的 POST 都保留未知业务提交锁 | 统一调用 `lib/core/network/request_reload_semantics.dart` |
| `/platform-columns/{scope}/values:batch`（含 `/api` 前缀） | 只读查询失败也永久锁定更新 | 与原生 facets 一样登记在途读取，结束即释放 |
| `/notices/read-all`、`read-by-route`、`read-by-source`、`/{uuid}/read`、`/{uuid}/popup-ack` | 展示状态回执失败也永久锁定更新 | 请求在途仍 busy；失败保持错误返回，但不新增业务未知提交锁 |
| 其他 POST、PUT、PATCH、DELETE | 保护真实业务未知提交 | 保留原保护；通知 complete、acknowledge、batch-delete、定义创建/use 和相似未知路径没有豁免 |
| `SafeRequestRetryInterceptor` | 自有一份平台字段只读路径正则 | 改用同一个 `isPlatformValuesRead`，删除重复正则；回执和其他写入仍不重试 |
| Web：登记表 → `web_update_bridge_web.dart` → `web/update_check.js` | 错误的 blocked 导致手动/自动刷新都禁用 | 同一登记表随请求结束发布正确安全状态；弹窗样式与最终同步复查保持原样 |
| Flutter 桌面：`client_update_controller.dart`、`client_update_host.dart`、`client_update_dialog.dart`、`client_staged_update.dart` | 同一登记表约束安装 | 同步得到公共请求分类修复；保留包校验、业务草稿与安装前安全检查 |
| WPF：`Updates/ClientUpdateCoordinator.cs`、`IUpdateExitGuard`、`MainWindow.xaml.cs` | 原生手动下载/准备/关闭保护；没有 Dart 的应用全局 `_uncertain` 锁 | 该问题的原实现不适用；空闲自动更新同责入口 W7-UPD-011 尚未迁移，接入合同已追加唯一台账，状态保持 todo |

服务端权威核查：`PlatformColumnController.read` 只调用 `PlatformColumnService.read`；`NoticeService.markRead`、`acknowledgePopup`、`markAllRead`、`markReadBySourceEvents`、`markReadByRoutes` 只处理通知展示状态，不完成业务 TODO。豁免以完整路径白名单表达，不从 HTTP POST、幂等性、方法名称或宽泛前缀推定安全。

未知业务提交先于回执失败时，原锁仍保留。请求分类不修改权限、审计、原始输入、草稿、金额数量、来源、身份代次或业务提交/重试语义。
