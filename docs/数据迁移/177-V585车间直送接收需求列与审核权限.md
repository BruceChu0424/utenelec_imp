## 一、报工行记住「投给哪个上层工单」

直送事实表 `production_workshop_direct_transfer_items` 是追加式的，审核才写。
但车间在填报工**草稿**时就要选好接收工单，而草稿会被反复编辑
(`update` 的实现是整批删明细再重建)，所以这个选择只能落在报工行自己身上：

```sql
ALTER TABLE production_daily_report_items
    ADD COLUMN direct_transfer_demand_id UUID REFERENCES production_material_demands(id);
ALTER TABLE production_daily_report_items
    ADD CONSTRAINT production_daily_report_item_direct_transfer_chk
        CHECK ((destination = 'WORKSHOP') = (direct_transfer_demand_id IS NOT NULL));
```

CHECK 让「去向」与「接收需求」同进同出：选了转送车间就必须指明投给谁，
没选就不许挂一个孤悬的需求 UUID。同车间、同货品同颜色、不超需求量这些更强的约束
由 V584 的行级守卫在审核写直送事实时兜底。

## 二、为什么要一个独立的审核权限码

审核一张带直送的报工，会在同一笔事务里连带写三类事实：

| 事实 | 正常流程里需要的码 |
|---|---|
| 班组自检放行(`production_fqc_inspections` + decision + release) | `production_quality_inspection:approve` + 品质部组织范围 |
| 料进本车间线边仓(`FINISHED_IN` 确认) | `stock_doc:approve` + SUB_WH 部门子树 |
| 投给上层工单(`DRAW` 发料) | `stock_doc:issue` |

把这三样隐式塞进 `production_daily_report:approve` 等于一次**看不见的提权**——
谁有报工审核权，谁就能写品质放行和库存事实。所以新增
`production_direct_transfer:approve`，让这份授权显式、可回收、审计时看得见。

持有本码**不等于**获得上述三个码：它只允许在「同车间直送」这条被 V584 守卫钉死的
窄路径上写那几笔事实。跨车间、跨主仓、货品颜色对不上、超过收料需求量，
在数据库层就会被拒。

默认授予集合与 V543 的车间默认包一致：`DEPT_PROD` / `MFG_CENTER` / `WS_*`；
`bulk_assignable=FALSE`，不随「一键全部授权」发放。
