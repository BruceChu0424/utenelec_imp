## 原图合同

来源：原需求内嵌`image1.png`“各部门申请流程”，已逐框重看。

| 原申请类型 | 原顺序 |
|---|---|
| 出差申请 | 出差人填写→部门负责人审核→小朱总或朱总批准→交财务苏蝶金保管 |
| 出差报销申请 | 附相关凭证→部门负责人→财务苏蝶金复核→财务吴兰梅复核→总经办王经理批准支付 |
| 报销申请 | 附相关凭证→部门负责人→财务苏蝶金复核→财务吴兰梅复核→总经办王经理批准支付 |
| 付款申请 | 经办人附凭证→部门负责人→两次财务复核→总经办王经理批准支付 |
| 预付申请 | 同付款申请，关联真实预付及后续抵扣 |
| 工资付款申请 | 人事附凭证→财务吴兰梅复核→总经办王经理批准支付 |

原姓名作为岗位/示意责任人保留，实际配置明确员工/账号UUID，不能按昵称找人。新流程仅对启用后新申请生效，不把历史APPROVED单退回。批准支付与实际付款分开，工资付款不经过普通费用报销重复计费。

## 已核实当前实现

- `ExpenseClaimService`已有申请人/部门快照、金额明细权威重算、票据查重/人工核验、提交快照、驳回重提、任务软认领、事件姓名快照和付款凭据；目前`decide`一次通过即APPROVED，尚不能代表原四级节点。
- `ExpenseClaimService.pay`在APPROVED后，通过`EmployeeClaimPostingPort`交给`FinanceExpenseService.postEmployeeClaim`，复用账户账本、GL期间锁、费用分录和gl_confirm；已有同参数重放返回原结果以及申请人/批准人/付款人分离保护。
- `FinancePaymentService`是采购应付/预付资金付款，GL默认借AP控制科目，不能把工资塞入这条链假称借应付工资。
- 工资已有原生`payroll_batches/slips/items`应发、扣款、实发和审批/发布状态，尚需支付执行与会计桥；金额必须读批准工资事实，不能重新计薪或自行假定扣款科目。
- `SalesShipmentService.financeAudit`已覆盖全部客户人工放行，冻结汇率、商业修订/hash、认领及风险快照；仓库前置保留。不能新增“现金不足一律拒绝”覆盖已有人工权限。
- 当前出货事件保存actor_user_id和时间，但打印所需审核人当时姓名需核对并补稳定快照。真实到账要与草稿收款、原币、本币及客户账面未结分清。

## 实施路线与分工

1. 先补客户发货审核的真实到账上下文、审核姓名快照/打印和反审回归（V1002预留）。
2. 复用现有金额与执行源，补类型/来源关联、原顺序节点配置及冻结快照、当前责任人队列/通知/认领、退回与幂等；配置有效后仅启用后新申请走新链（V1001预留）。
3. 出差前申请独立于出差后报销，出差报销保存原申请关系；付款/预付关联原付款事实；工资来源和扣款沿原批准工资事实，补可审的资金与GL桥，不能只做审批页面。
4. Web和Flutter桌面共用Uten组件及服务端契约，输入/草稿/未知提交与原请求编号保全；Win7 WPF相关入口尚未迁移，必须明记，不能误开放写入口。

审批人员选择器复用A任务新增`financeApplicationReviewer` purpose（设置权限`expense:settings`）；保存/执行仍须后端复核有效员工/账号、实际节点和处理权限。姓名不能替代UUID。
