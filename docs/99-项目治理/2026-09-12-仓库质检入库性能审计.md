# 仓库质检入库性能审计

本页记录 2026-09-12 本轮仓库子任务的原因、实现边界与验证。业务规则以 ADR-075、仓库到货登记、IQC 合格待入库和采购委外到货退换货文档为准。测试通过不等于公司服务器已经安装；最终发布状态由本轮统一验收记录维护。

## 已确认原因与处理

| 路径 | 原因 | 当前实现 |
|---|---|---|
| 跨收货单批量入库 | 外层已取得整批锁图和 PASS 明细，内层每单再次发现并校验锁图、读取同一明细 | 单张和批量共用 `confirmCommands`。一次发现完整锁集合，按顺序锁命令，全部准备后复核一次；每单 PASS 明细读一次 |
| 多单重复核对仓库 | 相同实际叶仓的祖先、启用状态按每张收货单重复解析 | 在本次事务的准备阶段按实际仓 UUID 去重核对；幂等重放不重新要求历史仓启用，不建立跨事务缓存 |
| 多单关联同一分析 | 每单入账后立即重算分析，后面的单再次重算同棵树 | 全部实物/资金切片/专属归属先按原顺序入账，生产端按单推进真实履约，然后对混合采购/委外整批受影响分析去重刷新 |
| 确认结果投影 | 每张单单独读取实际去向，可能触发重复来源查询 | 生产联动完成后批量读取实际去向，按真实入库项所属批次返回；不会把共享 PASS 身份当成本次入库身份 |
| 送检成功返回 | 仓库只需要收货单号/处理结果，审核网关却重新构建完整商业详情后立即丢弃 | 普通审核保留详情响应；仓库网关共用同一 `approveReceipt` 事务内核并返回 void，不查询无用详情 |
| 品质检查结果列表与徽章 | `event_stocked` 先对全部历史入库行做 GROUP BY，当前仅少量待办也重复聚合旧历史 | 先过滤 `passed_base_qty > warehouse_stocked_base_qty` 的有效品质行，只按候选 PASS 事件通过既有索引汇总其入库切片 |
| 页面快速切换 | 晚返回的旧来源/关键字状态计数可能覆盖新计数 | 状态计数独立采用请求版本，只接受最新响应 |
| 批量请求失败 | 关闭失败提示时连同批量表一起关闭，丢失员工修改和原命令上下文 | 提示关闭后保留表单。网络结果不明时可按原数量、库位和幂等键重试；明确余量冲突时仍要求重新核对 |
| 产成品批量确认入库 | 全批已经预锁，内部审核又重新查询/验证同一关联图；逐单构建完整详情只取单号与状态 | 预锁后的审核内核返回已核对实体，外部单张接口才读取详情；批量复用本次完整预锁 |
| 产成品批量生产跟进 | 每张单的同源分析重复刷新 | 每张单仍立即完成真实库存/成本、生产推进与委外专属转交，再对全部已入库单据统一刷新分析；没有异步旁路替代数量事实 |
| 成品送检多仓交叉等待 | 原来按报工顺序交错取得仓库 A/B 的行锁，不同报工集合可能按相反顺序持仓互等 | 批量先锁全部命令、识别重放，再锁全部新报工/明细，最后按稳定顺序锁全部实际仓；锁后才登记 |
| 成品送检重复基础查询 | 同批同仓和同收货人逐报工重复查权威数据 | 只在本次事务持锁范围内复用仓库快照和收货人身份，已完成重放早于新仓资格核对 |
| 委外回厂到另一实际仓 | 正常损耗与自有材料成本调用已收到实际仓，却把订单/原收货默认仓传给产出登记，导致批次在底层实际仓校验处回滚 | 两个调用端将实物产出的 `physicalPool` 传到底层；成本对象仍保留原订单/收货池作为身份锚点 |

结构上的查询/刷新次数改进不等于端到端秒数承诺。真实响应时间还受数据规模、并发、网络、审计触发器和源单关联复杂度影响。本次没有用空业务库的低延迟证明历史大数据场景。

## 事务与来源保证

1. 仍是一条仓库命令一个事务。先校验全部类型、UUID、规范化幂等键、版本余量、库位、实际叶仓及委外原材料份额，再开始物理入账。任一冲突整批回滚。
2. 商业来源、库存、主仓、分析的统一预锁协议保持有效；后续生产回调仍检查覆盖范围，不能在持锁后静默补拿上游锁。准备阶段完成后才验证快照，禁止把校验移到提交后。
3. 入库行 UUID、实际库存 movement UUID、资金切片和原始品质 PASS 仍一一可追溯。金额/重量继续用原冻结切片按累计增量分摊，未知重量保持未知，末片保留原守恒规则。
4. 普通到货、免费补回、贷后再采购、少到、超量隔离、FAIL、红冲和来源下游消费规则不变。PASS 本身不增加库存，确认入库不重复立 AP。
5. 已完成命令只读取原批次，跳过库存、学习、生产和通知写入。规范化后重复的幂等键在锁前拒绝，避免空格变体进入同一命令身份。
6. 下一张收货单的专属归属容量读取本事务已追加的来源/权益账本，不能依赖尚未刷新的分析展示数量。返回的 `actualAllocations` 在整批生产回调完成后读取。
7. 实际仓库与原建议仓不同的合法合格专属来源，按 ADR-075 跟随真实叶仓；不能仅因主仓不同就把原专属来源误记为公共库存。其它任务专属、未检和不合格库存不开放。

## 合并来源退补的真实缺陷闭环

后续跨任务复核把合并来源的待检、待补数量校正扩展到了实际归属。V554 由物料任务维护区间分摊；本任务新增 V555，修复系统 IQC 终态 `CANCELLED` 行动下，原单合法补回虽成功入库却未继续归属原分析的问题。

原始真实失败证据为 `server/target-perf-warehouse/merged-iqc-exact-r1.log`：A20/B30 合并到货，合格实收入库 12、实退 38、原单免费补回 38；总库存 50、库存金额和 AP 2500、幂等和取消历史均通过，唯独原分析 exact 归属不足。

修复不复活行动。逐个 V518 资金/品质/库存分项证明同原订单、来源与已实退案件，仅本次替补基本量能延续；旧 allocation、当前节点需求、已持有权益/正式覆盖和其它未来供给共同限额。新增权益前由数据库 `ALWAYS` 触发器再验，普通到货、人工撤回证据及其它实际订单的案件不能借道。说明与入口见[153-V555迁移文档](../数据迁移/153-V555-IQC原单补回来源权益延续.md)。

V555 的节点限额还通过真实让料组合纠正：接受节点已借助让料齐料后，自身原单补回仍应优先补齐来源。初始限额阻断第一片补齐，红例为 `iqc-priority-r1-reproduce.log`；最终只采用现役让料账本精确 to 节点的 `OPEN/PARTIAL` 未补齐量，from、已完成、已撤销记录不增加预算。

最终 V555 组合 26 项全部通过：8 项真实 FullChain 和 18 项 peg/去向投影测试，无失败、无跳过。包含 4/34 两次原单实收入库形成部分/全部优先补齐、让料撤销及重复请求，以及上述普通/人工/错订单来源负测和其它活跃供给保护。证据为 `server/target-perf-warehouse/iqc-priority-r2-final.log` 与 surefire 报告；513 项迁移到 V555 成功，SQL 源与测试资源 SHA256 一致：`D129F40990464F536B7BD0A0A16A3CC426541BB063CFA23C33ACE4723EDF10E9`。

## 委外多实际仓与原单补回成本

`SubcontractLossValueService.registerOutput` 与 `SubcontractOwnMaterialCostService.stockStored` 现在分别把该次入库的实际池传给 `InventoryProductionCostPort.registerOutput`。`registerScope` 和成本修订仍引用原订单行/原收货行的产品池，防止按每次入库仓改写成本来源。`InventoryProductionCostService` 对产出节点的货品、颜色、实际仓和 movement UUID 的严格核验保持不变。另一个直接调用端 `StockValuationCoordinator` 原本已传实际池，无需修改。

新增真实回归把两批原回厂失败实退后形成的免费补回送到另一实际仓：原仓保留 12 个原件及价值 120，新仓收到 8 个补回件及价值 280（原材料 80 加原加工费 200），总量 20、总值 400 不变。原两笔收货成本对象仍锚定原仓，免费补回不再领公司材料；相同入库请求重放不增加流水或价值。原默认仓用例继续保留。

数量入库提交与后续价值分摊收敛分别验收。确认事务记录真实实物、供应商费用来源与公司材料成本关联；待处理成本仍通过现有有界价值工作器分摊。不能把待计价金额当作最终成本，也不能在压力夹具关闭工作器后把暂态加工费金额改成最终期望。默认仓损耗全链及核心跨池/错误货品颜色/错误业务类型 9 项 PostgreSQL 回归通过；原默认仓与新增跨仓免费补回 2 项通过。证据为 `.codex-tmp/performance-20260912/subcontract-actual-output-warehouse-r1.log` 和 `subcontract-original-replacement-warehouse-r2.log`。新增回归首轮曾因两个场景复用测试员工编号而失败，已使用独立夹具身份修正，未修改业务断言。

## 验证

### IQC 品质批量报告

`decideBatch`、`passBatch` 原先外层预锁后仍逐行调用完整 `dispose`，重复发现同一来源锁图、锁整单 IQC 行；每个事件还遍历收货单全部订货行，各自重算一次完整订单关闭状态。现在两种批命令和单行处置共用一次锁内行快照，逐事件记账后再按不同订单集合更新一次。金额、重量的累计区间、品质价值来源和逐事件通知仍保留，整单终态只跟进一次。

新 V557 摘要修复响应丢失后重试被已 RESOLVED 状态阻断的问题，并拒绝变数量/原因/成员或遗漏原 FAIL 的请求。历史事件不回填，旧单行及旧全合格批的已有重放语义保持；旧混合批不能从时间戳恢复完整原 body。接口、数据库边界和实现见 [155-V557 迁移说明](../数据迁移/155-V557-IQC批量报告完整请求身份.md)。跨收货单仍是一单一事务，前端负责保留准确的部分成功进度。

第一轮 21 项通过，包括 5 项真实采购/委外流程：每单 3 行、每行 PASS 0.75 加 FAIL 0.5，实际整单 `FOR UPDATE` 只执行一次、同订单审计 UPDATE 只增加一次，PASS 放行金额 112.5、品质资金总额 187.5，AP 和实际库存不变；同体重放、变 body 拒绝、部分/旧证据边界及后段真实 SQL 失败后的回滚均验证。证据为 `.codex-tmp/performance-20260912/iqc-complete-batch-r1.log`。最终 `iqc-complete-batch-r2.log` 的 9 项通过，包括新增全合格真实回放、数值 scale/成员顺序等价、128 字符行键，以及 V556→557 旧事件/表文件/索引/旧迁移保真和 replica 不可变守卫。这是结构与正确性证据，不替代整站实际响应时间和公司旧库演练。

### 大批量价值节点与分配边

`InventoryValueLedger.createDerivedNode` 接收完整、有序的 `Contribution` 列表，沿原 `ValueBounds.weighted/add` 顺序计算完整初始界，将派生节点首次 INSERT 的字段写全，随后逐条 INSERT 全部不可变输入边，完成后才返回 `Node`。旧的半初始化 `createNode`、独立追加派生 `edge` 和 `initializeChild` 入口已删除。SOURCE 仍走独立的未裁剪取得原额初始化；修订仍先写完整 revision 事实，再以旧 revision 条件更新当前节点。未知父界保持未知，零宽区间也不会把旧未证金额升级为精确成本。

`InventoryPositionService`、`InventoryValuationService`、`InventoryOpeningService` 的所有派生路径已迁移，包括多来源入库、余量、退回、实耗补回及原入库撤销。位置根的 self `return_head_id` 在首次 INSERT 中落齐；真正的后续 head CAS、库存/池/节点锁与动态余额复核保留。携转时现在先落 target 的全部输入，再逐来源建立余量；跨父边的全局插入交错发生变化，但同父 target 先于余量、每个 child 的金额累加顺序及 `node_sequence` 顺序不变。V500 的立即外键、BEFORE 序列/二分守卫，V517 的 ALWAYS/deferred 金额与生命周期约束，以及审计全部继续执行。

成本登记仅复用同一次调用中已验证的实际 Node 身份；同 pool UUID 时不再重复读取相同货品/颜色身份。不同 pool 仍按原产品/颜色规则验证，真实输出仓必须匹配该笔物理来源。没有缓存动态版本、库存余额、池头或全局待计价状态。

真实回归包含原价值模型 29 项、精确位置 23 个场景、金额界 3 项、两次旧迁移、真实损耗 5 项、同仓/跨仓原单免费补回 2 项、工作器并发 11 项，以及真实 V500/V506 图前向 V517 后 NULL/零宽边界 1 项。100 个携转来源和 100 携转加 1 个本次取得来源两种合法上限均通过；每笔四位显示为 0 的原额仍完整累加，并沿原资金来源接受 1e-8 后补。旧图对账按 JSONB 数值同值逐旧字段检查，因为 V517 原本会移除 `owned_value_local` 的四位 typmod，0.0000 与 0 的文本哈希不能作为业务金额变化。证据在 `.codex-tmp/performance-20260912/derived-complete-candidate/core-r1.log` 与 `matrix-r2.log`；最初摘要格式失败已由该真实回归闭环，未修改旧迁移或降低金额校验。
