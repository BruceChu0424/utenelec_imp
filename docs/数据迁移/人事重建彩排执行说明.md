## 可重复准备

在 PowerShell 中执行，`<本轮全量导出目录>` 必须来自本轮最新一致性备份，不能取历史缓存：

```powershell
$py = 'C:/Users/bruce/.cache/codex-runtimes/codex-primary-runtime/dependencies/python/python.exe'
& $py server/legacy_migration/prepare_hr_rehearsal.py `
  --xls 'D:/uten_legacy_inputs/中山市优腾电器职工信息表.xls' `
  --legacy-workers '<本轮全量导出目录>/hr_workers.csv' `
  --out-dir '.local-tmp/hr-rehearsal-20261022'
```

准备程序只读来源文件、生成私有产物，不连接数据库。运行依赖 `pandas`、`xlrd`。来源表头及列顺序变化、未知薪酬批注、在职名册重复证件/手机、未映射部门、非法公历日期会阻断，不能带错继续。

| 产物 | 用途 |
|---|---|
| `hr_rehearsal.csv` | 人员主档、学历、敏感信息、薪酬及来源类型的合并输入 |
| `hr_managers.csv` | 沿用已审组织规则生成的部门负责人 |
| `hr_rehearsal_crosswalk.csv` | 每个老库人员 ID 对应的新档案/规范档案 |
| `hr_source_archive.private.json` | 表格全部原始单元格、批注及老库全部导出字段；未被当前应用建模的原文也不丢失 |
| `hr_rehearsal_report.json` | 不含证件号/电话号码/密码的数量、匹配方式、字段覆盖及冲突处理报告 |
| `hr_rehearsal_manifest.json` | 产物 SHA-256；报告另绑定表格及老库 CSV 的来源 SHA-256 |

以上 CSV 与来源归档含真实个人资料，只能留在受控且被 Git 忽略的目录。普通执行文档、聊天报告、Git 提交都不附带这些原文。

## 对人规则及历史档案

按身份证精确匹配，其次按唯一姓名加手机号匹配，再按唯一且证件无矛盾的姓名匹配。表格已有字段不被老数据覆盖；学历、表内空白的联系方式等由老库补充。

同证件姓名差异 `程雪莲→程雪连` 为本次实测确认的旧字差异，仅在同证件时适用，不做模糊姓名合并。姓名及手机号一致但证件不同的旧人员以表格证件为准，报告记录这一处理。

同名但证件矛盾、手机号又无法印证时，保留表格人员为在职，另将旧身份保留为独立离职档案。此举保留每个老库 `legacy_id` 的业务引用，不把无法证实同一人的旧单据强挂给当前员工。后续取得可靠证据后，在本节及对应匹配规则修订。相同旧身份证的重复历史档案同样保留独立旧 ID，只有规范首档持有全局唯一证件哈希，其余仍有加密原文。

老库当前“使用”状态不会覆盖本轮在职口径；表格外人员统一离职，朱德洪除外。历史人员留在离职人员范围，不作软删除隐藏。历史日期缺失时，数据库 `hire_date NOT NULL` 所需的兼容值为 `2000-01-01`，并明确记录 `hire_date_verified=false`；这不是核实的入职日期，不制造入职或离职事件，也不用于可靠流动率统计。

## 字段落点

| 来源信息 | 当前系统落点 |
|---|---|
| 姓名、性别、入职日期、部门、岗位、职级、在职/离职 | `employees`、`positions`，老 ID 进 `employees.legacy_id` |
| 身份证、手机、生日、政治面貌、籍贯、居住地址、邮箱、办公电话 | 直接加密写入 `employee_sensitive.*_enc`；主身份派生 HMAC/尾号与原文同空同有，不在 `employees` 暂存明文 |
| 生日月日 | `employees.birth_month_day`，供生日提示，不含年份 |
| 批注中的转正日期 | `employees.confirmed_at`；其余表格人员沿用已审口径为入职日期 |
| 批注中的基本工资、津贴 | `employee_compensation` 对应加密字段，3 条结构化薪酬资料 |
| 老库学历 | `employee_education.degree`，缺少学校、专业和起止日期时留空，不编造 |
| 表内管理中心/主管部门/分管部门、职级、岗位 | 沿用 53 号文档的组织映射；部门名称对齐表格，稳定部门编码保留以兼容其他业务来源 |
| 老工号、原始工龄、来源原备注/批注、当前应用无对应字段的原文 | 私有来源归档，保留来源位置；薪酬原文不放到普通任职轨迹备注中 |

在职名册异常证件原样加密，写 `id_card_check=unchecked`，应用启动后按现有证件核对机制判定。不能通过猜测改证件来消除提醒。负责人沿用已有 53 号规则，同部门多名部门经理仍需按该文档的已记录口径核验，不因为旧库主管称谓自动赋权限。

## 候选库执行及验收

协调器在同一受控事务内完成空候选库检查后，复制 `hr_rehearsal.csv`、`hr_managers.csv` 至 PostgreSQL 可读取的 `/tmp`，通过临时 `legacy_key_file` 注入与应用一致的密钥，再执行 `migrate_hr_rehearsal.sql`。随后才能导入其他模块；**不要再执行旧的 `migrate_hr_workers.sql`**，以免恢复老库“使用”的错误在职状态或生成 `LEGACY-W-*` 编号。

SQL 会检查管理员精确保留、编号从 `UT0001` 连续、来源状态、部门完整性及最终人数，直接加密全部敏感列；只给表格来源写可核实的 onboard 轨迹。执行过程中不修改 `users`。既有 `employment_history` append-only 守卫保持启用，不关闭触发器、不绕过审计。

验收顺序：

1. 管理员账号、密码验证及管理能力与重建前一致，全库仅该账号。
2. 表格全部人员在职、董事长在职，其他旧身份全部离职；在职数不靠老库 Status 推导。
3. `employees.legacy_id` 非空数等于本轮老库 `B_Worker` 行数，每个业务人员旧 ID 都能命中；不存在 `LEGACY-W-*` 显示工号。
4. 工号首个 `UT0001`，无空洞；`master_code_sequences.UT` 为本轮最大工号，下一次正式入职接着生成。
5. 每字段非空数与准备报告一致；证件、手机、生日、地址的解密回环与权威来源逐项比较，只回报差异数，不打印原文。源值为空时密文/哈希/尾号也为空。
6. 学历、3 条薪酬结构化、部门负责人及在职直属人数对账；同名冲突的历史旧 ID 保留，普通业务引用不断链。
7. 应用启动后检查证件核对任务，核对在职、离职两个页面；历史日期覆盖不足的统计维持已有“不完整”提示。

本模块自动测试：`python -m unittest discover -s server/legacy_migration -p test_prepare_hr_rehearsal.py`。测试通过只证明合并规则；数据库事务、加密回环、实际登录和界面仍由整体彩排单独记录，不能以单元测试替代。
