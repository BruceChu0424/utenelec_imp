# ADR-067：工作台「系统测试」区与业务数据一键清空（应用内孪生版重置）

- 日期：2026-09-03
- 状态：已决策（源码候选；本地全绿，未发版）
- 相关：[权限体系总设计](../05-架构/权限体系总设计.md)（工作台无泛化权限码的设计决策）、
  [工作台首页.md §十一](../03-页面/工作台首页.md)、
  `server/ops/reset_business_data.sql`（psql 停机版，口径唯一事实）、V462 迁移

## 1. 背景与决策

本地开发库与内网测试服务器需要反复回到「干净测试起点」。既有手段只有
`server/ops/reset_business_data.sql`（psql 停机版：要求停应用、零其它连接、
带外传 confirm/库名/system_identifier 三重确认），对非运维角色不友好。
用户 2026-09-03 决策：工作台最底部加「系统测试」区 + 「清空数据」卡，
在**运行中的应用内**一键完成同口径清空：

1. **清空口径完全复用 psql 版**：同一份 318 表 CLEAR/PRESERVE 分类
   （CLEAR 222 / PRESERVE 96），`TRUNCATE ... RESTART IDENTITY`（业务表
   自增 ID 从 1 重新开始），账户五金额/客户供应商期初往来/货品期初库存/
   安全库存/20 项成本金额费率/结算类别期初归零，六物化视图刷新并校验为零，
   全套失败关闭校验（未知表拒绝、保留表行数不变、CLEAR 逐表为零）。
2. **完成后全员强制重新登录**：`authorization_state.epoch + 1`（存量 staff
   access token 下一请求即 401）+ `TRUNCATE refresh_tokens`（断掉静默续期）；
   访客 token 因 `visitor_accounts` 属 CLEAR 同步失效。前端成功后主动本地
   登出并跳登录页。
3. **不创建备份、不可恢复**；只面向可丢弃的测试库。

## 2. 架构：清空逻辑下沉 V462 函数，Java 只编排

安全写入门（Mimosa）实测禁止在 Java 内联 `TRUNCATE`/动态 SQL（变量、常量、
文本块、字面量拼接作 SQL 参数一律判注入拦截；只有单字符串字面量+绑定参数
干净）。因此清空口径整体下沉为 **V462 迁移创建的 PL/pgSQL 函数
`business_data_reset()`**（仓库本有业务逻辑在触发器/函数的先例），Java 侧
`BusinessDataResetService` 只做编排：运行开关 → 排水 → 绑定审计 actor →
`SELECT * FROM business_data_reset()` → 同事务完成审计回执 → 提交 → 异常映射。

双侧同步由 `BusinessDataResetSqlContractTest` 锁定：V462 函数与
`ops/reset_business_data.sql` 的表分类逐表相等（各 318 项），
服务层不得内联清空 SQL。

## 3. 与 psql 停机版的三处刻意差异

| 维度 | psql 停机版 | 应用内孪生（本 ADR） |
|---|---|---|
| 静默前提 | 停应用/worker，零其它客户端连接，否则拒绝 | `BusinessDataResetDrainGate` 排水闸：清空前普通 `/api` 请求回 503（`/actuator` 等运维端点不受影响），等在途请求清零（上限 45s，超时放弃整体恢复）；清空端点自身豁免计数 |
| Flyway 目录版本门 | V443/405…V462/424 元组白名单 | 不复刻——应用永远运行最新目录，未登记新表由「未知 public 表拒绝」兜底失败关闭（与白名单数量门等效且免每次维护元组） |
| 会话收尾 | 无（停机时无会话） | 终局校验全部通过后 epoch+1 并清 refresh_tokens；refresh_tokens 在分类里仍是 PRESERVE（基线行数校验通过后才清） |

两版共用错误码约定：用户可自行解除的拒绝（outbox 有待处理/失败事件、附件存在
非人事 owner、目录漂移）以 `SQLSTATE UT900` 抛出，服务层映射 **409 CONFLICT**
给出处置提示；其余校验失败映射 500 并整体回滚。

## 4. 安全门禁（四重，缺一不可）

1. **运行开关** `uten.features.business-data-reset-enabled`
   （base/cloud 默认 **false**，fail closed；`application-dev.yml` 与
   `application-internal-test.yml` 显式开启，对应「本地开发库」「内网测试服务器」
   两类目标。**2026-09-12 修订（用户拍板）：测试阶段公司内网服务器（prod
   profile）同样放行**——`application-prod.yml` 显式配置默认 true，可用
   `UTEN_BUSINESS_DATA_RESET_ENABLED=false` 临时停用；**正式上线时整个
   systemtest 功能随本 ADR 一并删除**）。
2. **数据库确认的超管本人**：`@PreAuthorize("principal.superAdmin")`；
   前端整区仅超管渲染。**不设独立权限码**——测试工具不进权限目录/部门授权
   体系（与权限总设计「工作台无 workbench:* 码」一致）。
3. **确认口令**：请求体 `confirm` 必须逐字等于「清空业务数据」；
   前端弹窗同款输入框门禁，双保险防误触。
4. **排水闸**（见 §3）：清空期间无并发业务写，任一校验失败单事务整体回滚、
   应用立即恢复放行。

单事务内完成：业务表清空+主档金额归零+物化视图刷新+全部校验+踢人；
主档归零 UPDATE 不停审计触发器，actor 绑定为实际点击的超管
（`app.actor_id`/`app.actor_account`/`app.audit_request_id`），与 psql 版的
`ops:reset_business_data` 可区分；`business_data_reset` 显式完成回执与清空同事务提交。

## 5. 边界与残留风险（已论证接受）

- **应用内定时任务与 HTTP 请求共用排水闸**：`DrainAwareTaskScheduler` 包装全部
  `@Scheduled` 任务，以 `tryEnter` / `leave` 记录在途执行。清空必须等待已运行任务
  结束；排水与清空窗口内跳过新一轮调度，下一周期恢复。这覆盖通知、对账、outbox、
  附件及物化视图调度，避免清空与定时任务交叉持锁。该闸属于当前应用实例，不能替代
  多实例或外部数据库客户端的停写要求。
- **排水未成功必须自行恢复**：等待超时或线程中断时，`beginDrain` 在退出前恢复
  `IDLE`；只有成功进入 `RESETTING` 后，才由调用服务的 `finally` 执行 `endReset`。
  中断异常继续交给服务保留线程中断标记并返回失败。回归测试覆盖在途请求阻塞清空、
  中断后普通 API 恢复与后续可再次清空，防止请求中断留下永久 503。
- **psql 版维护义务不变**：新增迁移如增删 public 表，仍需同步
  `ops/reset_business_data.sql`（版本元组门 + 分类清单）**和** V462 函数内的
  清单（两处由 `BusinessDataResetSqlContractTest` 与既有
  `ResetBusinessDataScriptContractTest` 双向锁定）；`MigrationRehearsalSupport`
  的 head 版本/迁移数同步升到 462/424。
- V462 只加函数不加表，CLEAR 222 / PRESERVE 96 计数不变；内网服务器运行时
  Flyway 关闭，函数随受控迁移进程（uten_migrator）落地，与既有发布链一致。

## 7. 2026-09-09 附件自动清理（补充决策；不改 §1–§6 原文）

**背景**：2026-09-09 用户口径「清空业务数据 = 连上传的文件一并清空」。此前（V537）把「业务附件全部完成物理删除并留有完成证明」当作清空前置条件：前端按钮在预览失败（503/超时/403）或任何 blocker 下永远灰、旧「先清理业务附件」弹窗对 LEGACY_UNVERIFIED / oss / 凭证未到期同样无能为力，内网无法清空（2026-09-10 审计 C14 H1-1～H1-4）。

**决策**

1. **服务端自动清理**：`BusinessDataResetService.reset()` 在排水内、清库前循环「预览 → 标删/入队（`prepare`）→ 同步排空附件删除队列（物理删除 + 完成证明）」直到 `fn_business_attachment_reset_blockers()` 归零；总时长预算 5 分钟、≤200 轮、每轮 ≤5000 项，每轮 `log.info`；无进展即 409。前端确认按钮只看口令（且预览未被运行开关 FORBIDDEN 拒绝），`blockingCount` 只作「N 项业务文件将一并删除」提示；「清理测试业务附件」弹窗降级为**可选**的提前分批入口（文案「可选：提前分批清理；未清理的文件将在清空时自动删除」）。
2. **排水前置分类（快速失败）**：自动清理只走「`lifecycle_state='CLEAN'` 且 `storage_provider∈{internal,local}` 的原件入队 → 排水删除队列」这一条乐观路径。以下阻塞在 **`beginDrain` 之前**直接 409（`ErrorCode.CONFLICT`），不让全站为注定失败的清空白白 503：原件/上传会话不在 internal/local（oss、legacy_unknown）；原件状态非 CLEAN（`LEGACY_UNVERIFIED`、DELETED 缺证明、标删却无删除任务）；上传凭证 `expires_at > now()`；删除任务 FAILED 且 attempts ≥ `uten.storage.outbox.alert-after-attempts`；SUCCEEDED 缺 `completed_at`。文案 = 按原因分组计数 + 前 5 个文件名 + 一行处置指引（附件对账 / 等凭证过期 / 重试删除队列）。`BusinessAttachmentResetPreparationPort.unpurgeableBlockers` 承载分类 SQL。
3. **保护集扩到主档（V549）**：`goods` 表在 `business_data_reset()` 中 PRESERVE，其图片/图纸（`owner_type = GOODS`）随主档保留。`fn_business_attachment_reset_blockers()` 与 Java `BusinessAttachmentResetPreparation.PROTECTED_OWNER_TYPES` 共用同一集合 `('EMPLOYEE','EMPLOYEE_CONTRACT','GOODS')`（Java 四处 SQL 以 CSV 绑定参数传入，不拼接），`BusinessAttachmentResetCompletionPostgresTest` 锁定两侧一致。见 [147-V549](../数据迁移/147-V549附件清空主档保护集.md)。
4. **超时对齐**：清空是同步长请求（排水 ≤45s + 附件清理 ≤5min + 清库 `statement_timeout` 30min）。nginx 对 `location = /api/system-test/business-data/reset` 单独 `proxy_read_timeout / proxy_send_timeout 600s`（`deploy/nginx/uten-imp-http-lan.conf` 与两份 `.example` 同步；精确匹配优先于 `/api/` 前缀与正则块）；前端 `ApiClient.postLongRunning` 对该端点接收超时 10 分钟（单独成方法而非给 `post` 加参数，保住既有覆写 `post` 的测试子类）。客户端仍超时时提示「请求已超时，清空可能仍在后台执行；稍后若被强制下线即表示已完成」——服务端不感知断连，会执行完并踢人。中期若改 202 + 任务号轮询，须把状态查询加入 `DrainFilter` 豁免。
5. **结果回显**：成功后调用 `InternalStorageService.cleanupAbandonedScratch()`（仅 provider=internal）清理内部存储遗留临时文件；`Result.deletedAttachmentFiles`（= 清理前后 SUCCEEDED 删除任务差值）写入审计事件与成功提示。新增只读 `GET /api/system-test/business-data/last-result`（audit_log 最近一条 `business_data_reset`；门禁同预览端点：运行开关 + 超管；不进排水豁免——重登本身发生在清空完成之后），系统测试区展开时回显「上次清空」。
6. **重登刷新（H1-2 根治）**：`sessionEpochProvider`（`lib/shared/auth/session_epoch_provider.dart`）由 `SessionRehydrateGate` 在未登录→已登录时 +1；全局角标 StateNotifier 在 provider 构造里 `ref.watch(sessionEpochProvider)`，新会话从零重建并立即重拉，旧实例（含 60s 轮询与迟到响应）作废；`rehydrateGlobalState` 同时失效工作台概览 / 通知列表 / 卡片徽章聚合缓存；`refreshGlobalBadges`（返回即刷新）补齐此前漏掉的 `hrTaskCountProvider`。

**不变**：§1.3 不创建备份、不可恢复；§4 四重门禁；psql 停机版仍要求手工完成附件清理（脚本不调用应用侧删除，`ops/reset_business_data.sql` 内的证明函数保护集须与 V549 同步）。

**实现**：`BusinessDataResetService` / `BusinessAttachmentResetPreparation(Port)` / `SystemTestController` / `V549__attachment_reset_master_owner_guard.sql` / `system_test_area.dart` / `business_attachment_reset_dialog.dart` / `system_test_repository.dart` / `api_client.dart`（`postLongRunning`）/ `workbench_refresh.dart` / `session_rehydrate_gate.dart` / `session_epoch_provider.dart` / `deploy/nginx/*`。测试：`BusinessDataResetServicePostgresTest`（purge 2→1→0 两次 prepare、排水前 409 且闸门保持 IDLE）、`BusinessAttachmentResetCompletionPostgresTest`（GOODS 保护 + SQL/Java 集合一致）、`test/features/dashboard/system_test_area_test.dart`（blocking>0 可清空 / 预览失败仍可提交 / FORBIDDEN 禁用 / 超时提示 / 上次结果回显）、`test/shared/providers/session_rehydrate_gate_test.dart`（登录后每个角标恰好重拉一次）。

## 8. 完成回执与清空原子提交（2026-09-13）

前端以服务地址、操作者 UUID 与 `attemptId` 保存待确认记录；断连后只读取同一操作者和
同一请求的完成回执，不自动重放清空。旧服务先提交清空，随后才独立写入回执且吞掉审计
异常：这一间隙发生进程中止或审计写入失败时，数据已经清空而重登后永远找不到本次结果。

清库阶段改用应用既有 `PlatformTransactionManager` 创建独立 `REQUIRES_NEW` 事务。
`DataSourceUtils` 取得 `JpaTransactionManager` 绑定的同一 JDBC 连接，原 actor、锁超时、
语句超时和数据库函数保持；函数成功后调用既有 `AuditService.logCommitted`，复用完整
请求、会话及设备元数据。清空、主档归零、epoch、refresh token 与完成回执共同提交，
写入或实际提交失败全部回滚；排水闸在事务完成后才放行。没有增加表、迁移或另一套审计
字段映射。业务附件的物理删除仍是此前已决策的清库前置步骤，不随数据库事务回滚恢复。
提交确认丢失时可能实际已经提交，响应必须提示重新登录核对本次结果，不笼统宣称已回滚。
若超时后最终失败且没有成功回执，待确认记录继续禁止自动重提；本轮不以缺少回执推断失败，
也不新增尝试状态表。

真实 PostgreSQL 回归通过延迟约束触发器在提交时拒绝完成回执，同时检查回执使用清空
连接的 actor 和刚更新的 epoch、空 outbox/token 状态；随后核对业务行、账户五金额、
库存、序列、会话和审计均回滚，普通请求恢复。解除故障后同一请求可完成并精确查询，
错误操作者或请求编号不能匹配，后续清空不能覆盖先前回执；另核对持久化的请求、会话、
操作编号及设备字段。当前 V571 清空范围为 276 张业务表、96 张保留表。
