# ADR-149 仓库数据范围服务端强制(主管 / 子仓负责人 / 其他人)

- 日期：2026-10-05。
- 状态：已接受(本地源码实现，V804；8085 克隆库真实接口切三种身份、Testcontainers 端到端测试与 Flutter 页面测试验证)。
- 取代：[ADR-115](ADR-115-仓库负责人与仓库通知按仓分发.md) 的「我的仓库」(MINE = 我负责的仓 + 所有没负责人的仓，覆盖全部在用仓时退回全部仓)、「不按负责人限制可见性」与「红徽章仍是全公司口径」两条「不做」，以及通知「负责人都不在池里就发整个池」的兜底。ADR-115 的负责关系表 `warehouse_keepers`、登记入口与「登记在主仓上 = 负责全部子仓」保留。
- 相关：[ADR-145](ADR-145-仓库主档单主仓与禁用不可选.md)(唯一主仓 001，主管判定依赖它)、[ADR-108](ADR-108-前端性能徽章汇总会话快照与刷新时机.md)(徽章汇总一次带回)、[ADR-038](ADR-038-来源单号可读化与订货仓库后移.md)(订货不带仓，预计到货的仓要另推)、[ADR-147](ADR-147-车间内料仓开通单一真源与发料来源仓.md)(内料仓请领的预填叶仓)、[ADR-017](ADR-017-模块化单体与异步旁路.md)(跨模块只经 application.port)。
- 用户问题(2026-10-04)：「仓储部负责人或仓库(14年版)的负责人是主管，可以看全部，也可以挑任一子仓看；其余每个子仓登记一个负责人，这个人只能看到、只会收到自己子仓的任务，徽章也只数他自己的仓；右上角仓库选择只有主管才出现，改成和全站一样的右侧滑窗」。测试服务器上把超管登记成五金仓库负责人、选了「我的仓库」，仍然看到全部仓的任务，徽章也没变。

## 1. 事实(调查与复现)

- 「仓库范围」只是前端可选的筛选参数：不带参数 = 全部仓；`scopeWarehouseId` 可以填任何仓，不校验是不是本人负责的仓(8085：只负责包材仓库的非超管带别人的仓 200 拿到单据)；选择器对所有人显示，带「全部仓库」。
- 「我的仓库」= 我负责的仓 + 所有没登记有效负责人的仓 + 未定仓的任务；覆盖全部在用仓时直接退回全部。只要还有一个仓没人负责，「我的仓库」几乎就等于全部。
- 徽章与各级计数从来没按仓算：徽章来源调用的 /count、/counts、/tasks/count 都不带范围；前端为了让分段跟着范围变，盘点审核用 `list(size:1)` 凑数、预计到货另请求 type-counts，其余仍是全公司数，同一页数字彼此对不上。
- 几类任务的「所在仓」没定义或用的是恒为空的列：预计到货按 `inbound_expectations.warehouse_id`，ADR-038 后恒为空(服务器 9/9)；品质检查结果完全没有范围；车间内料仓徽章只按车间分。
- 「主管」不存在：仓储部负责人 `departments.manager_id` 没被用到，主仓靠「有没有下级」推断。
- 通知、AI 查库存、生产链对象范围各写一套「谁负责哪个仓」，兜底各不相同(负责人不在池里就发整个池；不限部门发给所有持权限的人；SUB_WH 子树)。

## 2. 决定

### 2.1 角色与可见仓只在一处判定

数据库函数 `fn_user_warehouse_access(user)`(V804) 是唯一判定，服务端 `WarehouseDataScopeService`(实现 `WarehouseTaskScopePort` v2) 只调它，每次实时解析；只有复用窗口(`WarehouseTaskScopePort.withScopeCache`)里同一账号同一所选仓只解析一次(符合准则 14「范围解析次数 ≤ 不同范围数」)，窗口只有三种，见本节末「解析时机」：

| 角色 | 谁 | 默认看什么 | 能不能挑仓 |
|---|---|---|---|
| 主管 SUPERVISOR | 超管；仓储部(SUB_WH 子树)各部门负责人 `manager_id` 对应员工的账号；登记在主仓 001 上的负责人 | 全部仓库(含未定仓的任务) | 能，任一在用仓(含下级) |
| 子仓负责人 KEEPER | 登记在主仓以外的仓上 | 自己负责的仓及其下级，不含未定仓的任务 | 负责多个仓时只能在这几个仓之间切换 |
| 其他人 OTHER | 有任务权限但没登记负责人(仓库部门普通成员、其它部门持查看权限者) | 没有有效子仓负责人的仓 + 未定仓的任务；全公司还没有任何有效子仓负责人时 = 全部 | 不能 |

- 「有效子仓负责人」= 登记在该仓或其主仓以下各级上级仓上、员工在职且账号启用的人(`fn_warehouse_keeper_user_ids`)。登记在主仓上的人是主管，不算覆盖某个子仓——否则只要给主仓登记一位主管，其他同事就一张任务都看不到。
- 没有登录账号的人不是有效负责人(看不到任务也收不到通知)；仓库资料「设置负责人」的候选里按工号标出同名员工与账号状态，防止登记到没账号的那份档案上。
- 生产链仓库任务的对象范围 `ProductionStockTaskAccessPolicy` 委托同一判定：主管、子仓负责人或仓储部门成员(主部门或兼职部门)。
- 解析时机(2026-10-05 修正)：不按 HTTP 请求一律缓存——授权与范围判断若靠「请求边界」才刷新，同一请求(或绑定成一个请求的长流程)里先改组织、后判定就会拿到旧结果——调离仓储部门的人照样能发料、照样读得到单据(CI 上 `StockDrawIssueBatchReceiptEndToEndTest`、`CloseoutDeletedReceiptReadScopePostgresTest` 复现)。统一规则：
  - **只读请求(GET/HEAD)整请求一个范围快照**：读请求不改组织，列表逐行判定、详情加附件、列表加计数都只解析一次。`WarehouseScopeReadSnapshotFilter` 紧跟 Spring Security 过滤链之后(主体已解析)把处理包进窗口，finally 关闭：处理抛错、异步/流式响应(处理线程返回即关，异步分派不再开窗口)都不会把窗口带进线程池里的下一个请求。
  - **写请求默认实时**：窗口外每次一次函数调用；单张办理与维护流程不开窗口，写请求里先改组织、后判定的立即按新组织算。
  - **批量写显式开窗口**：循环体逐单复核范围、且不改组织、部门、兼职部门、负责人与账号的批量办理整批一个窗口——批量出库 `StockDocService.issueFullBatch`(issue-batch 与 issue-discovery-batch 共用)、领料发现批量出库 `ProductionDrawDiscoveryBatchService.issue`(逐个申请登记材料再整批出库，嵌套沿用同一窗口)、成品批量点收 `confirmFinishedInboundBatch`。只读汇总(工作台徽章 / 本部门待办的一次汇总、按所选仓汇总)与走 POST 的批量读(扩展字段 `values:batch`，逐张借单据详情判可见)同样各一个窗口。修正前非超管批量出库 50 张草稿领料单要调上百次 `fn_user_warehouse_access`(每张审核、出库、两次详情可读各一次；超管在判定前提前返回，规模/语句预算用例量不出)，修正后整批 1 次。

  窗口只在当前线程、只在那段执行期间存在，可嵌套(内层沿用外层)，抛错也关闭；负责关系维护后也就不再需要「清缓存」。

### 2.2 范围由服务端强制，所选仓由服务端校验

- 所有仓库任务端点(列表、facets、/count、/counts、/tasks/count、status-breakdown、status-counts、type-counts、库存分析)统一 `@RequestParam(required = false) UUID scopeWarehouseId -> WarehouseTaskScopePort.current(id)`；删除 `warehouseScope=MINE` 参数与「覆盖全部仓时退回全部」。
- 不传 = 本人默认范围；传了 = 校验在本人可选范围内(主管 = 任一在用仓；子仓负责人 = 自己负责的仓及下级；其他人 = 无)，越界一律 403「所选仓库不在你负责的范围内」，然后取该仓子树(`fn_warehouse_scope_ids`)，不含未定仓。
- `GET /master/warehouses/my-scope` 返回 `{role, canSelectAll, selectable[{id,code,name,parentId}], keeperWarehouses, defaultWarehouseId}`，前端选择器只依赖它；可选清单与服务端校验同一份。
- 范围只限制列表、计数、徽章与通知；单据详情与办理端点仍按原权限。顶班由主管处理(主管能看全部)或在仓库资料里重新指定负责人。
- 库存分析(呆滞库龄、盘点建议)与任务中心共用同一判定；AI 查库存：主管(含超管)查全部、子仓负责人查自己负责的仓，其他人的「没人负责的仓」是任务兜底，不是查库存的授权。
- 盘点申请列表：仓库审核(reviewRoute=WAREHOUSE)是仓库任务按范围过滤；财务审核与「我提交的」不按仓库范围裁剪。车间内料仓请领列表：车间成员按本车间看(车间范围)，不叠加仓库范围。

### 2.3 每类任务的「所在仓」只定义一次

一个任务涉及多个仓时任一仓在范围内即算；一个仓都没有 = 未定仓，只有「其他人」的默认范围(与主管的全部)包含。

| 任务 | 所在仓 | 定义位置 |
|---|---|---|
| 预计到货 | 逐行到货仓：订货表头仓 -> 采购/委外申请表头仓 -> 货品所属仓(不再用恒为空的 `inbound_expectations.warehouse_id`) | `fn_inbound_expectation_warehouse_ids` / `fn_procurement_item_inbound_warehouse_id` |
| 到货异常 | 异常仓 | `ProcurementArrivalControlService.warehouseExceptionFilters` |
| 品质检查结果(新接范围) | 收货单表头仓 + 各检验行目标入库仓 | `WarehouseQualityResultService.RESULT_WAREHOUSES` |
| 产成品待点收 | 点收单入库仓；待登记按成品所属仓(一单多个所属仓时任一仓) | `ProductionFinishedInboundTaskService` `scope_warehouse_ids` |
| 销售出库 | 表头仓或任一明细拣货仓 | `SalesShipmentService.warehouseScopePredicate` |
| 委外出库(只接范围，不改委外业务) | 委外人员已提交、仓库未发出的领料草稿的发出仓(ADR-143 起一行 = 一张领料草稿；仓库发料单所在仓) | `SubcontractMaterialPlanService.outboundTaskFrom`(`WarehouseTaskScope.predicate("issue.warehouse_id")`) |
| 生产待领 / 领料单 | 发料仓 | `FulfillmentWorkbenchQueryService`(列 `warehouse_id`) |
| 库存单据(其它出入库、产成品出入库、领料、生产退料)与仓库草稿 | 发出仓或调入仓 | `fn_stock_document_matches_warehouse_scope`(V796 函数按新口径重写) |
| 车间内料仓请领 / 退料 | 各行预填叶仓(ADR-147 默认来源函数给出)；盘点中按该车间内料仓的来源仓 | `WorkshopMaterialScope.requisitionWarehouseFilter` |
| 仓库审核的盘点申请 | 盘点仓 | `StockCountRequestService` |

### 2.4 计数、徽章与列表同一谓词

- 各徽章来源调用的计数方法与列表共用同一过滤基座；不传范围 = 本人默认范围，所以 hub 卡、工作台、导航自然按人拆开。
- `/workbench/badges?scopeWarehouseId=` 供任务中心选了某个仓时取大类与分段数：先校验(只有主管与多仓负责人能选)，再只算仓库模块的入口，汇总期间各来源都按所选仓计(`WarehouseTaskScopePort.withRequestedWarehouse`)。删除前端 `list(size:1)` 凑数与单独的 type-counts 请求；预计到货分来源(PURCHASE/SUBCONTRACT)并入 `/expectations/count` 的事实数，type-counts 端点删除。
- `drafts.stockDocument`(仓库草稿红数)与 `/documents/status-counts?kind=stockDocument|stockTransfer|stockCheck` 同样按仓库范围计数(与库存单据列表同一判定函数)。任务中心的库存单据分段(草稿段的数)把与旁边列表同一个 `scopeWarehouseId` 带给 status-counts(前端 `DocumentStatusScope.scopeWarehouseId`，挑了仓就按那个仓数)。
- 建单不限仓，所以**本人默认范围里自己还没提交的草稿不论仓都算**：子仓负责人顶班在范围外的仓建了草稿，这张草稿不能从他自己的列表、草稿箱和红徽章里消失(否则只有那个仓的负责人和主管能继续、提交或删除它)。`fn_stock_document_matches_warehouse_scope` 第四个参数是制单人员工 id，只在本人默认范围传(列表/分段计数不带 `scopeWarehouseId`、草稿徽章不在按仓汇总里)；挑了某个仓就只看那个仓。列表、草稿红数、分段草稿数三处同一参数，红数 == 列表。

### 2.5 通知只有一条分发规则

- `WarehouseNoticeRouter.recipients(池, 仓)`：该仓链上的有效子仓负责人 ∩ 池；没有则**指定的主管**(仓储部门负责人、登记在主仓上的负责人，`fn_warehouse_designated_supervisor_user_ids`) ∩ 池；再没有(还没配置)才发整个池。规则本身在 `fn_warehouse_notice_recipients`。未定仓的任务直接走主管那一级。
- 超管在列表范围里是主管(看全部、可挑仓)，但**不因超管身份算作通知的「主管」那一级**：权限池几乎总含超管，算进去会让「再没有才发整个池」永远到不了，没有任何负责人登记时请领、盘点审核等通知全落到超管一个人身上，仓库的人一条都收不到(2026-10-05 审查在克隆库复现：`recipients(XW01, {超管, 仓库员工}) = {超管}`)。
- 池 = 原通知池(仓库部门 × 所需权限) + **这张单涉及的仓**(含上级链)的子仓负责人与指定的主管里同样持有所需权限的部门外的人(`fn_warehouse_notice_candidate_user_ids`)。不再把「任一仓登记过的负责人」都拉进每一张单的池：否则一个在财务部、只负责五金仓库的人(例如测试服务器上超管登记在 C01)会成为所有没负责人的仓的通知收件人，仓库的人反而收不到。
- 弹卡资格同口径：部门外登记的负责人与仓储部门负责人(`fn_warehouse_responsible_user_ids`)在 `ReviewNoticeAudience` 里按仓储部门成员对待(销售待拣货、IQC 待入库、生产待领料、领料发现、采购财务通过五类仓库待办)，发给他们的待办照样弹出行动卡，不只躺在通知列表里。
- ChainNoticeService 的 13 处仓库通知、车间内料仓通知(请领、结算被拦)、盘点审核通知都只经这个 router；「采购财务通过」的预计到货通知与委外回厂通知按 2.3 的逐行到货仓分发。
- 通知在发送时按当时的负责关系分发；已经发出的卡片不按读侧逐条重判(V796 的读侧函数没有接入，V804 删除)。

### 2.6 前端

- `WarehouseScopeSelector` 重写：主管显示小标签，点开全站仓库右侧滑窗(先主仓后子仓)，首行「全部仓库」；负责多个仓的人同样的滑窗，首行「我负责的全部仓库」、只列自己的仓；只负责一个仓显示只读标签「我负责：包材仓库」；其他人不显示。任务中心、出库/入库/生产领料任务中心、库存分析共用。
- 偏好 `warehouse.taskScope` 只存 `warehouseId`；记忆的仓不在当前可选范围内(负责关系变了、仓被删)回到默认范围；旧的 `{mode: MINE/ALL}` 偏好一律回到默认。本人可选范围(my-scope)在任务中心返回页面与点「刷新」时重取，负责关系刚改过也能回到默认，而不是一直拿登录时缓存的范围去请求、得到 403。
- 任务中心大类与小类数都来自同一份汇总(没选仓 = 全站汇总；选了仓 = 带 `scopeWarehouseId` 的汇总，`warehouse_task_badges.dart`)；独立任务页不带参数，同样由服务端按本人范围过滤。品质检查结果页接入范围。

## 3. 迁移(V804)

不改表、不改数据，只定义函数(见 [V804 迁移说明](../数据迁移/V804-仓库数据范围服务端强制.md))：重写 V796 的 `fn_warehouse_keeper_user_ids`(去掉主仓上的登记)、`fn_warehouse_supervisor_user_ids`(新主管口径 = 超管 + 指定的主管)、`fn_stock_document_matches_warehouse_scope`(发出仓或调入仓，第四个参数为本人草稿例外；V796 的三参数版删除)；新增 `fn_warehouse_designated_supervisor_user_ids`、`fn_user_warehouse_access`、`fn_warehouse_responsible_user_ids`、`fn_warehouse_notice_candidate_user_ids`、`fn_warehouse_notice_recipients`、预计到货所在仓三个函数；删除 V693 的 `fn_user_warehouse_scope_ids` 与 V796 未接入的读侧 `fn_notice_warehouse_visible`。

## 4. 不做 / 后续

- 单据详情与办理不按负责人拒绝(用户口径：顶班由主管处理或重新指定负责人)。
- 一张单跨多个仓(销售出库拣货仓；ADR-143 后委外领料草稿只有一个发出仓)时，每个相关仓的负责人都看到整张单；行级归属不做。
