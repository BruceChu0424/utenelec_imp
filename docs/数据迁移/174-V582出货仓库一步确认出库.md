# V582 销售出货仓库作业一步确认出库

- 迁移：`V582__sales_shipment_one_step_outbound.sql`
- 类型：前向。**不新增表、不新增列。** 收窄一个 CHECK、重建四个已有函数体、重建一条部分索引与一个只读视图、拨回在途行。
- 相关：[ADR-084 出货仓库作业一步确认出库](../99-决策记录-ADR/ADR-084-出货仓库一步确认出库.md)、
  [162 V566 销售无仓提交与仓库实仓拣货](162-V566销售无仓提交与仓库实仓拣货.md)、
  [销售出货仓库作业页](../03-页面/销售出货仓库作业页.md)

## 背景

用户实测口径（2026-09-14）：产品做完、销售开出货、财务放行之后，仓库要点四次才能把货发出去——
「开始拣货 → 拣货完成 → 交接出库」，外加一条「登记异常 → 恢复待拣货」的退拣回路。

这三个中间态**既不产生会计事实，也不改变库存余额**：

| 阶段 | 实际副作用 |
|---|---|
| `PENDING_PICK` | 占用订单行可发额度（建单时就有），不扣 ATP、不扣在手 |
| `PICKING` | 校验可拣量 + 写表头三列；零星发货额外建一条 `CUSTOMER_SHIPMENT_ITEM` 占用 |
| `PICKED` | 只写 `picked_at/by` 两列 |
| `EXCEPTION` | 只写 `warehouse_exception_reason`；**不释放**已建的占用 |
| `SHIPPED` | 扣库存、消费预留、回写 `shipped_qty`、推进链上状态、立唯一正式 AR |

也就是说前三步只是把同一批校验拆成三次点击，代价却是：状态机、退拣回路、事件账、
三处「其它在拣任务占用」的可用量减项、以及仓库任务中心五个分类页签。
对齐生产领料 DRAW 的「出库即审核」，把它压成一步。

## 状态机变化

```
改造前：PENDING_PICK → PICKING → PICKED → SHIPPED   （+ EXCEPTION ⇄ PENDING_PICK）
改造后：PENDING_PICK → SHIPPED
```

`LEGACY_PENDING`（历史迁移异常，只读）、`CANCELLED`、`REVERSED` 三个状态不变。

确认出库在**同一个事务**里依次完成：锁来源订单行 → 校验来源关联与商业条款 → 校验发运策略 →
确认实际叶仓（无仓提交的单由仓库现场指定）→ 收集逐行实际库位 → 证明本仓可发
（扣安全库存与其它订单硬预留）→ 扣库存、消费预留、回写订单已发量、推进链上行状态、
按本次上海业务日立唯一正式 AR。任一步失败整事务回滚，不留半条占用。

## 在途老单拨回策略

按 `warehouse_work_status IN ('PICKING','PICKED','EXCEPTION')` 捞在途单，顺序如下（不可颠倒）：

1. **fail-closed 断言**：若在途单已经有 `consumed_qty>0` 的 `CUSTOMER_SHIPMENT_ITEM` 占用，
   说明状态与出库事实矛盾，迁移直接 `RAISE`，必须人工核对，禁止盲拨。
2. **释放拣货占用**：`released_qty=qty, status=1, release_reason='CUSTOMER_SHIPMENT_UNPICKED'`，
   与 `CustomerShipmentInventoryService.releaseUnpicked` 逐字段同语义。
   `EXCEPTION` 态同样持有占用（原 EXCEPTION 分支不释放，只有显式恢复待拣才释放），
   所以三态一起捞。不释放会同时造成三个后果：幽灵占用永远不可用、
   `requireNoUnreleased` 让这些单再也不能编辑/删除/驳回/改附件、
   以及新占用撞 `uq_customer_shipment_item_active_reservation` 唯一索引。
3. **追加事件账留证**：往 `sales_shipment_warehouse_events` 补一条
   `<原状态> → PENDING_PICK`，reason 写明本次改造（`from_status='EXCEPTION'` 时
   V188 的 `reason_chk` 本来就要求非空）。事件账是追加式不可改写，历史
   `PICKING/PICKED/EXCEPTION` 行一个字节不动。
4. **拨回状态列**：同时清空 `picking_started_at/by`、`picked_at/by`、`warehouse_exception_reason`，
   否则会留下「待出库却带着拣货时间戳」的自相矛盾行。
   `warehouse_id` **保留**（无仓提交的单在拣货那一跳写入过）：仓库下次确认出库时
   可以沿用也可以改，两种情形都会走到重建后的叶仓校验（见下）。
5. **重开待办通知**：这批单当年「开始拣货」时以 `WAREHOUSE_STARTED` 办结过 `notices` 行；
   红徽章读 `sales_shipments` 表会自动恢复，但待办弹窗/审核收件台读 `notices`，
   不重开就永远看不到。只改值不改行数。

已 `SHIPPED` 的历史单**完全不在本次范围内**：时间戳、事件账、AR、库存流水全部原样保留。

## 数据库对象变化

| 对象 | 变化 |
|---|---|
| `sales_shipments_warehouse_work_status_chk` | DROP + ADD，取值收窄为 `LEGACY_PENDING/PENDING_PICK/SHIPPED/CANCELLED/REVERSED` |
| `fn_guard_sales_shipment_picking_warehouse`（V566） | 选仓时机由「`PENDING_PICK→PICKING` 那一跳」改为「财务已放行的待出库草稿确认出库的同一事务」：允许 `OLD=PENDING_PICK` 且 `NEW ∈ {PENDING_PICK, SHIPPED}`、`OLD.status=0` 且 `NEW.status ∈ {0,1}`。**叶仓校验从「换仓」那一支提出来**，对推迟选仓的单在确认出库这一跳无条件复核（在途单拨回后保留了原仓，选同一个仓时不会触发 `IS DISTINCT FROM`，原写法会静默跳过启用/可核算/叶子三项） |
| `fn_assert_sales_shipment_picking_warehouse`（V566，DEFERRED） | 只对 `SHIPPED` 断言；取证事件接受两种形态——新流程 `to_status='SHIPPED'` + `handed_over_by/at`，历史单 `to_status='PICKING'` + `picking_started_by/at` |
| `fn_guard_sales_shipment_picking_evidence`（V566） | 库位证据改挂 `to_status='SHIPPED'` 的事件；写入时单据必须仍是财务已放行的 `PENDING_PICK`（`status=1/SHIPPED` 由同事务末尾与 `approveLocked` 一起落盘，中途提前 flush 会撞 V511「已出库事实不可变」闸） |
| `fn_guard_sales_shipment_finance_release`（V511） | 财务放行前禁入的实物态由 `IN ('PICKING','PICKED','SHIPPED')` 收窄为 `='SHIPPED'` |
| `idx_sales_shipments_warehouse_pending`（V450） | DROP + 重建，部分索引谓词与 `countPendingWarehouseWork()` 的新枚举逐值一致（`LEGACY_PENDING/PENDING_PICK`），否则 60s 轮询的角标计数用不上索引 |
| `v_sales_shipment_finance_gate_migration_exceptions`（V443） | `CREATE OR REPLACE`，状态白名单去掉三值，避免口径撒谎 |
| `sales_shipment_warehouse_events` 的三个 CHECK（V188） | **不动**。表是追加式（`trg_00_reject_..._mutation` + `ENABLE ALWAYS`），历史行里就存着 `PICKING/PICKED/EXCEPTION`，收窄约束必然校验失败 |
| `sales_shipments.picking_started_*` / `picked_*` / `warehouse_exception_reason` | **列保留**。前四列是历史证据且被重建后的取证函数按历史分支读取；`warehouse_exception_reason` 在仓库驳回时仍在写，不是三态专属 |

本迁移**一个触发器都没有 DROP**，只用 `CREATE OR REPLACE FUNCTION` 换函数体——
`DROP/CREATE TRIGGER` 会把 `ENABLE ALWAYS` 退回 `ORIGIN`，在 `session_replication_role='replica'` 下静默失效，
并打破 V530 审计触发器全量 sweep。

## 配套服务端行为（同批代码）

- `POST /api/sales/shipments/{id}/warehouse-work` 与
  `POST /api/warehouse/sales-outbound/{id}/warehouse-work` 端点、方法名、DTO 均不变；
  `targetStatus` 只接受 `SHIPPED`，其余值（含三个已退役状态）一律 `VALIDATION_FAILED` 明确拒绝，
  不做静默兼容——老前端或重放脚本若被当成合法目标，会跳过整套可发量与来源承诺校验。
- `warehouseId` 与 `stockPlaces` 改为随确认出库一起提交（原来只允许挂在 `PICKING` 上）。
  `reason` 变成选填的出库备注，随事件账留证。
- 「其它在拣任务占用」的可用量减项在四处删除：`SalesShipmentService.assertWarehousePickCapacity`
  三段、`WarehouseSalesOutboundProjectionService.warehouseOptions`(V631 起为 `lineWarehouseChoices`) 三处 LATERAL、
  `CustomerShipmentInventoryService.reservePicking` 两臂。一步式没有「已开拣但未出账」的中间态，
  其它草稿要么仍在待出库（由硬预留覆盖），要么已确认出库（`stock_balances` 已扣）。
  **预览侧与闸门侧必须同批改**，否则会出现「预览可发 / 确认报库存不足」的用户可见不一致。
- `MaterialAnalysisRootSupplyService` 的 `requireNoPicking` 与
  `hasReversibleExistingOutput` 的同族 `NOT EXISTS` 一并删除：撤回根产品现货交接的唯一真闸门
  是那条 `consumed_qty=0 AND released_qty=0` 的 CAS，确认出库后必然失败。
- `GET /api/warehouse/sales-outbound?warehouseWorkStatus=` 增加取值白名单：
  老客户端筛「拣货中/已拣货/异常」时返回明确报错，而不是静默空列表。
- 「待出库」待办的办结时机由「开始拣货」挪到「确认出库」（`resolveReviewNotices` 的
  reason 由 `WAREHOUSE_STARTED` 改为 `WAREHOUSE_SHIPPED`）。

## 覆盖声明

本迁移显式取代以下既有口径，原文保留不改写：

- [162 V566](162-V566销售无仓提交与仓库实仓拣货.md) 的「填仓发生在财务已放行的 `PENDING_PICK → PICKING`」
  与「`targetStatus=PICKING` 时接受 `warehouseId` 和 `stockPlaces`」两条；
  现在填仓与库位都发生在 `PENDING_PICK → SHIPPED` 这一跳。
- [163 V567](163-V567销售批量出货来源与幂等身份.md) 里「仓库还需明确确认实际叶仓和逐行库位」的时机同上顺延。
- ADR-030 关于「仓库开始作业后须先异常退拣才能财务反审」的表述：
  现在财务反审的边界就是「仍是 `PENDING_PICK`」，没有退拣动作。
- ADR-082 里「仅未放行且**仓库未作业**的退回单」判定：等价于「仍是 `PENDING_PICK`」。
- [46 号](46-报销分录与发货财务审核.md)、[69 号 V443](69-V443销售货款客户标签全客户发货财审与铺底口径.md)

## 验收

- `SalesShipmentWarehouseAssignmentEndToEndTest`（6 个方法，`UTEN_RUN_DB_TESTS=true`）：
  无仓提交 → 财务放行 → 仓库现场选仓 + 逐行库位 → 一步确认出库；错仓被拒后既不落仓也不推状态；
  全局预留被别单占住时确认出库 CONFLICT 且不产生任何 `stock_reservations`；
  两张直发单竞争同一有限库存池时在真实库存互斥锁上串行，落败方整事务回滚。
- `FullChainEndToEndTest`：`shipThroughWarehouse` 压成一步后覆盖 23 个调用点；
  失败回滚用例（不可表示本币）断言确认出库失败后连拣货占用都不留下。
- `WarehouseTransitionTargetsContractTest` / `SalesShipmentWarehouseTransitionPolicyTest`：
  拓扑只剩一条边，且三个退役状态字面量被 fail-closed 拒绝。
- `SalesShipmentWarehouseReservationSqlContractTest`：新增「`setHandedOverAt` 必须早于
  `recordWarehouseEvent`」的顺序契约——取证触发器按 `handed_over_by/at` 与事件逐字段比对，
  而比对依赖「原生 INSERT 前 Hibernate 会 flush 脏表头」这一隐式行为，调换顺序 Java 侧看不出区别。
