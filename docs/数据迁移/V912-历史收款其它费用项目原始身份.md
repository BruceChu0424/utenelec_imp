# V912 历史收款其它费用项目原始身份

本规则只处理旧 `M_Get.qtfymc` 的历史身份与现平台费用类型之间的冲突，保留原收款，不补造费用分类、凭证、审批、账户流水或应收事实。

## 先确认来源命名空间

旧视图 SQL `server/legacy_migration/data/biz_m_views_def.txt` 的 `View_M_Get` 明确将 `M_Get.qtfy` 显示为其它费用金额，将 `M_Style.StyleName` 显示为费用项目名称，并使用 `M_Get.qtfymc=M_Style.ID` 连接。旧列定义中 `qtfymc` 为非空整数；旧外键清单未声明该 FK，因此这是旧视图证明的业务关联。

`qtfymc` 属于 **M_Style**，收款方式 `RecStyle` 属于独立的 **RecStyle** 字典。两个字典里相同的数字没有同一身份。例如 M_Style 的 1 是销售收入，RecStyle 的 1 是现金。

## 导入顺序与字段规则

在付款类别、账户和收款方式字典导入后，V626 唯一受验入口仍接受完整 typed `M_Get` 行，按原数量与金额建立 `LEGACY_UNCLASSIFIED`、金额权威版本 0 的只读历史收款。

V912 向 `finance_receipts` 新增 `other_fee_style_legacy_id`，保存正数的原 `qtfymc`。0 或空值保存为 NULL；负值中止待核，不猜测其含义。原整数不是新平台费用分类授权。

`other_fee_style_id` 只解析到同一 `payment_styles.legacy_id` 且类型为 `EXPENSE` 的真实节点。原节点是收入类型或不存在时，当前费用 UUID 保持 NULL，原整数和原 `other_fee` 仍完整保留。历史导入沿用原有类别与存在性规则，不额外用当前在用/末级选择器规则替换历史的合法费用节点；普通新单的选择器和数据库在用/末级守卫继续执行。

新增原 ID 与当前 UUID 都进入同一个完整来源证明的字段集合与目标哈希，源 JSON、原行 SHA 与文件 SHA 的含义不变。首次写入要求同 run、同事务、RECEIPT/m_get 来源种类、文件 SHA、新字段签入及完整投影一致。旧证明没有新字段时只兼容 NULL，不回填旧单；新原 ID 不能在线添加、修改、清空或改绑。V626 的原收款只读与普通新单守卫保持。

`migrate_finance.sql` 对账增加逐行检查：原 ID、原费用金额和相同原 ID 的 EXPENSE UUID 必须与源行一致。原 typed UUID 非空时的类型与存在性阻断继续保留，不能靠删除检查让错误映射通过。现金流水来源留档逻辑不受本变更影响。

## 当前彩排的待核范围

当前源有 7,805 条收款，正数 `qtfymc` 共 8 条。其中 20/23 分别为“其它费用/销售费用”，是原有合法费用节点，保留真实 UUID。其余 6 条原收款 11727、11802、12016、12159、17094、17361 指向收入节点 1/4，其中 2 条费用非零；这 6 条完整迁入，原 ID 保存，费用 UUID 留空待核。

另有 729 条费用非零而源 `qtfymc=0` 的历史收款，本来就缺少费用项目证据，继续遵守既有 V0 未决分类规则；本变更不扩大清理范围，也不为其指定默认费用。

待核清单可从本 run 的 `other_fee_style_legacy_id IS NOT NULL AND other_fee_style_id IS NULL` 派生，连接 `legacy_finance_import_sources` 查原文件/原行 SHA。确认真实分类后，应遵循独立的有证据核验流程，不能覆盖原始收款事实或自动把收入节点改为费用节点。

## 验证边界

私有独立 PostgreSQL 完整迁移至 V912（838 个迁移），23 项聚焦断言通过，覆盖错误类别/缺节点、合法历史费用、旧 proof 的 NULL 兼容、新字段防伪与不可改、SHA/跨事务、普通运行类别守卫及旧收款只读。

6 条真实收款使用原 CSV 记录及实际 typed COPY，在规范身份锚点中复核：原费用、现金金额、汇率和状态逐项相等；原 M_Style ID 保存，费用 UUID 全部为空，RecStyle 身份保持独立，无新增 GL/现金流水/AR，无收款留档或删除。原载荷仅通过内存管道传递，未写入测试日志。以上是隔离验证，不代替完整实际导入、切换、账号登录或验收。
