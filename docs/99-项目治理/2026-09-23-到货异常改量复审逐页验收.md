# 到货异常改量后的复审展示

## 实际链路与范围

人工沿仓库到货异常列表 → 异常详情 → 财务超量审批详情 → 财务决定确认框逐页检查。后端 `ProcurementArrivalControlService.financeDecide` 调用 `adjustDraftReceipt`，将同一收货明细从原申报 `declaredQty` 调整至 `acceptedQty`；接收量为零时删除收货行，接收量大于零时进入 `RECEIPT_ADJUSTED` 等待仓库重新审核。因此本入口采用与销售、采购、委外复审一致的完整行对比。

| 页面/入口 | 展示与边界 |
| --- | --- |
| `warehouse_arrival_exceptions_view.dart` / `_WarehouseExceptionDetailDialog` | 财务已决定时，以完整原申报行红色划线、批准接收行绿色展示。仍待财务决定时保留原申报事实，不把默认 `acceptedQty=0` 当作删除。列表仍为任务列表。 |
| `finance_arrival_exception_pages.dart` / `FinanceArrivalExceptionDetailPage` | 财务决定已形成时，原事实卡下展示同一共享对比表；原金额明确标为“原申报原币金额/原申报本币金额”。未决定时不显示已执行调整。 |
| 同文件 / “再次确认财务决定” | 按明确选择的接收数量显示“调整预览”“拟接收/拟删除”；提交前明确尚未生效，服务端仍按最新容量、版本和权限复核。确认框支持滚动。 |

## 行与金额语义

- `ArrivalQtyRevisionTable` 统一使用 `UtenRevisionTable`，保留货品名称、编号、颜色、单位、数量和有权限可见的原单价。
- 接收数量改变：原行红色并贯穿删除线，完整接收行绿色；全部接收且数量相同保持中性。
- 绿色接收行中，真正改变的数量单元格加粗并以红字强调，其余未变字段保留绿色。
- 已决定接收数量为零：只显示原行删除，不造一条数量为零的新明细。待审的默认零值没有该含义。
- 当前异常 DTO 没有批准后金额，本次不在绿色行复用原申报金额，也不由前端推算新金额。
- 不改变财务决定、批量处理、价格权限、库存/IQC、应付或供应商退回业务流程；不增加任何服务器写入。

本次补审从真实页面操作继续跟到 repository 与服务端状态流，区分“原单商业内容修改后再审”“对剩余数量继续办理”“旧单撤销后另建新单”。没有仅凭“退回/重新”字样把独立业务事实画成同一行的修改。下表记录实际入口及核对结论；本轮未找到需要再增加的同单修改复审入口。

### 既有采购/委外快照的数据边界

`ProcurementApprovalSnapshot` 的历史 `ItemSnapshot` 保存货品/颜色/单位/来源身份、数量、单价、换算率、金额和交期，未保存允许损耗率、重量、行/头备注及完整多来源。这个新提交仍可能遗漏差异的缺口已在本轮用 **V691** 补齐：`procurement_order_approval_cases.display_snapshot` 与新 case 同事务冻结，覆盖初次提交、退回重提和批准后改量两条 Java 建 case 入口；原 `submission_snapshot`、`snapshot_hash` 及审批核验算法不改。

- 新展示快照冻结供应商、仓库、币种、汇率、税率、结算方式、订货人、日期、头备注；各行冻结名称/编号/颜色/单位、核心数量金额、重量、赠品量、允许损耗率、备注、原来源单号及每个申请来源的身份、单号、行号和分配数量。
- 新 case 必须携带 canonical items，逐 ID 匹配同一订单的有效明细，不允许用另一条实时行兜底；展示快照写入后不可修改。历史 case 保持 NULL，不做任何当前值回填。
- 只有两侧都已保存的值才可证明修改并标红加粗。仅因旧扩展字段缺失而无法判断的行单列“待核对”，不计入“修改 N 行”；缺失头备注仅提示未知，不以缺键冒充原来为空。已保存的 JSON null 则是可证明的未填写/清空。
- 来源申请张数按冻结 `sources[].documentNo` 去重，不能拆自由文本 `sourceDocNo` 猜数；历史未保存时明确显示未知。
- 复审顶部明确显示“采购订单修改”或“委外订单修改”，单号和审批状态另列。实际收货改量显示“收货数量修改”；未提交决定的预览标明“收货数量修改预览”，不会冒称已经生效。
