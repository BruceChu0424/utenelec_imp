## 为什么要建表

用户口径(2026-09-15)：报工和实际用料原来是两处操作，要合并到报工页一次填完。

问题在于**两边的生效时点不一样**：生产日报 `create` 只产出草稿(`status=0`)，要主管审核
才增加完工量；而材料消耗(`production_material_settlement_postings` 的 `CONSUMED`)是立即
生效的实账。如果保存草稿就记实耗，草稿被删或日报红冲时实耗不会跟着退回去，材料台账和报工
事实会长期对不上，只能靠人工冲销补救。

所以本迁移让日报**先承载**用料数字(不记账)，审核时才在同一笔事务里转成结算。

## 三处结构变化

| 对象 | 变化 | 说明 |
|---|---|---|
| `production_daily_report_material_usages`(新表) | `report_id / line_no / plan_id / demand_id / material_execution_segment_id / qty_base` | 一张日报对一条物料需求只登记一次(`UNIQUE(report_id, demand_id)`)——同一个执行工单挂在多个成品行下时，它的物料只有一份额度。`qty_base >= 0`：允许填 0，「这批料一点没用」是合法事实，逼车间编个正数就是在造假账 |
| `production_daily_reports.surplus_return_requested` | 新列，默认 FALSE | 收尾余料退仓意愿。最后一次报工时车间确认「剩下的料退回仓库」，审核时才真正开退料单 |
| `production_material_settlement_events.daily_report_id` | 新列，可空 | 实耗溯源。历史结算(计划详情侧滑窗单独登记的)没有日报来源，不回填；日报红冲时按它反查本单 POST 事件下的全部 CONSUMED 过账逐条冲销 |

`material_execution_segment_id` 不等于报工行的执行段：分批生产时本批段可能一条物料需求都
没有，料挂在**前批原领料段**上(V561 `fn_production_material_usage_source_segments`)。

## 顺序是硬约束

审核事务内必须是 **先结实耗、再按剩余可退量开退料单**，不能颠倒：

退仓申请一提交就用 `fn_material_issue_pending_return` 冻结该领料过账的额度，而
`availableToSettleQty = GREATEST(uncleared − pending, 0)`。先冻后结会让实耗登记撞
「本次清账超过准确原领料未耗用数量」(`ProductionMaterialSettlementService`
FIFO 摊分处的 409)。

同理，退料单的数量口径是**原领料单位**(`Source.availableQty` 已经除过 `unit_rate`)，
而台账是基本量；换算率不为 1 时两者不相等。所以差额一律由服务端在审核时按
`return-requests/sources` 现算，前端和编排层都不做换算。

## 不新增什么

- 不新增过账类型：实耗仍走既有 `CONSUMED`，由 `ProductionMaterialSettlementService`
  按 FIFO 摊到该需求的各张 ISSUE 过账上。
- 不新增权限码：登记实耗 `production_material:settle`、冲销 `production_material:reverse`、
  退仓申请复用 `production_material:settle`(ADR-078 既有口径)。
- 不改 V152 的材料守恒视图与触发器，不回填历史行。
