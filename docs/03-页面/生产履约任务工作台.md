## 〇、计划前分析到任务工作台的交接（当前优先）

当前新业务不必等正式生产计划包确认后才产生采购/委外需求：

1. 生产计划员在[生产物料分析页](生产物料分析页.md)的统一 BOM 树中，按逐路径节点确认缺口路线；BUY/SUBCONTRACT 可不受层级深度限制处理，但仍必须满足本批激活需求、正缺口、版本和权限门禁；
2. 建议路线必须显式点「采用采购」或「采用委外」。未确认、未保存、MAKE 下层未齐或只读节点不渲染假复选框，而显示 48dp 的「先确认路线/先保存路线/下层未齐/仅查看」；真正可执行节点才允许多选；
3. 点底部「提交采购需求（N）」或「提交委外需求（N）」后，`POST /api/production/material-analyses/{id}/notify` 才同事务创建 `preplan_supply_actions`、逐节点 allocations 和真实采购申请/委外申请；勾选本身不写路线、不下达任务；
4. 采购/委外工作台按权威申请剩余量显示 `WAITING_ORDER`，通知中心是否及时送达不影响任务可发现性；
5. 业务人员跨申请选行、填写本次数量，按单供应商/委外商和单仓分别生成订货，保存并提交财务；
6. 合格财务审核组成员从自己的任务队列打开受控只读详情并批准；该临时任务详情权限不扩大采购/委外普通列表、编辑或 view-all；批准后任务消失，普通无对象读取权者仍不可借审批链接继续查看；
7. 财务批准形成 `inbound_expectations`，它只是未来到货，不增加可完工量；实际到货/回厂后只有 IQC PASS 并转目标仓合格可用的数量才能唤醒物料分析。收货、质检和入库必须沿申请行、订货行、逐路径 allocation 回查到原 analysis/item/path，不能只按货号或通知文本猜“给哪个产品”。

路线确认和下达单次请求上限都是 500 个最终任务。客户端先按稳定任务身份排序再按 500 分批，后一批使用前一批返回的最新 `version + fingerprint`；同一精确 chunk 重试沿用同一幂等键，不把重新编号的批次序号写入 key。部分失败只恢复最后成功版本后仍未提交且仍合法的任务，不能重复创建已成功的采购/委外申请。

MAKE 路线不会进入采购/委外工作台，而是生成 `PREPLAN_MAKE_TASK + MAKE_COMPONENT` 子分析来源。子件须单独齐套并由生产选择生成正式子件计划，不能把 MAKE 任务或一条通知当作已创建正式计划。

「计划单预览」打开的「生产备料计划汇总单」只读汇总自制/采购/委外并提供「打印 / 导出 PDF」，不负责上述下达。MAKE/root 的「填写生产计划单」向导只提交生产计划草稿；BUY/SUBCONTRACT 已由各自底部动作独立进入本工作台，三条职责链不得被文档写成一次混合提交。

下文“生产确认计划包后形成工作台任务”仍适用于 V191 兼容计划链；若与本节的新计划前入口冲突，以本节为准。

## 一、目标和入口

无论任务来自新计划前 action，还是来自历史 V191 已确认计划包，仓库、采购和委外都不依靠口头消息或各自重算缺口，而是在本部门工作台处理权威履约任务：

- 仓库：提前看到待备料、部分领取和已领取任务，也可查看财务已批的预计到货与只读超量异常，进入真实领料/收货单处理；
- 采购：查看计划下达但尚未全部分解的采购申请明细，跨申请选行并按供应商生成订货单；
- 委外：查看计划下达但尚未全部分解的委外申请明细，跨申请选行并按委外商生成订货单；
- 三个部门都可以按状态、异常和关键词筛选，并从任务追溯到计划、物料和来源单据。

生产进度投影必须分开「已报工」「已入库 / 排产」和「物料齐套」。采购/委外 IQC PASS 只增加目标仓合格可用库存并推动物料齐套；它不能直接增加生产计划的报工量或成品入库量。只有生产审核报工和成品审核入库分别更新对应事实，子件合格入库也必须先通过精确 MAKE peg 推动父需求，不能直接冒充父产品或销售订单完成。

入口位于仓库、采购、委外 Hub 的任务中心卡片，对应接口：

- `GET /api/operations/workbench/warehouse`
- `GET /api/operations/workbench/purchase`
- `GET /api/operations/workbench/subcontract`

到货链使用独立的最小任务投影：

- 仓库预计到货：`GET /api/warehouse/inbound/expectations`；
- 仓库只读到货异常：`GET /api/warehouse/inbound/arrival-exceptions`；
- 财务审核组超量任务：`GET /api/finance/procurement-arrival-exceptions/tasks`；
- 原下单人供应商退回任务：`GET /api/procurement/arrival-exceptions/tasks`。

这些列表与通知分开：通知可以失败或延迟，但任务仍可从服务端权威投影发现。
接口统一支持 `status`、`exception`、`keyword`、`page`、`size`；权限由服务端按部门现有权限点校验，前端隐藏按钮不能代替权限控制。

## 二、权威数据和数量口径

仓库工作台继续读取 `v_fulfillment_workbench_actions`；采购和委外的分解任务读取 V199 `v_procurement_decomposition_tasks`。后者只返回已下达、未关闭且尚有剩余量的申请明细，并把其它 `PENDING` 财务审批订单的数量也计入已分配量。Flutter 不重新计算库存、缺口或单据状态。

采购/委外申请是计划下达的需求事实。采购/委外申请 Controller 只公开列表、详情和分解预览，没有新建、编辑、审核、红冲或删除映射；页面同样只读。计划只看需求投影，不通过完整采购/委外单据接触供应商、价格、币种或结算字段。

每条任务至少包含：

- 计划、计划包、仓库、货品、颜色、单位和供给路线；
- 需求量、已分配量、已履约量、已挂供给量和未结量；
- 需求日期、预计日期、任务状态和异常编码；
- 当前可操作来源单据及其明细 ID、单号和审核状态。

必须遵守以下规则：

1. 卡片计数、筛选选项和表格数据来自同一后端视图；
2. 状态卡统计按当前部门、关键词和异常计算，不因正在选中的状态而把其他状态卡清空；
3. 异常选项按当前部门、状态和关键词计算，不从当前分页数据猜测；
4. 页面刷新、切换筛选或翻页不会直接改变业务状态；
5. 仓库发料、采购下单和委外推进必须进入真实来源单据，由对应审核事务更新库存和履约账；
6. 页面显示数量不是库存账本，任何写操作都要由服务端重新取锁、校验版本、数量上限和幂等键。

### 2.1 时间协议与非空数据约束

`updated_at` 的数据库类型是 PostgreSQL `timestamptz`。Hibernate 在 UTC JDBC 模式下执行原生查询时，非空值可以投影为 `Instant`；不同查询路径还可能得到 `OffsetDateTime` 或 `java.sql.Timestamp`。服务端必须同时接受这三种权威时间类型，并按同一瞬间归一为 UTC `OffsetDateTime` 后再进入 JSON 协议。不得依赖字符串强转，也不得保留输入偏移造成同一接口时区不一致。

空工作台只会证明“零行查询可返回”，不会执行行映射，因而不能覆盖这类故障。发布证据必须至少包含一条真实 PostgreSQL 非空任务：先确认 Hibernate 原生 `timestamptz` 投影类型，再走完整 `FulfillmentWorkbenchQueryService.query` 并断言 `updatedAt` 为 UTC。遇到不支持的对象类型仍返回 409“工作台更新时间类型异常”，不能静默伪造时间。

### 2.2 关联单据权限不是“看见工作台就全能看”

工作台的部门读取权限只允许查看公共履约任务，不自动授予采购、仓库或委外每一种关联单据。服务端按 `department + actionDocType` 映射到目标单据的精确 `*:view` 与目标动作权限（普通单据为 `*:edit`，申请分解为 `*:decompose`）：

- 无目标查看权：响应保留“存在受限关联动作”这一事实，但清空单据类型、ID、单号、明细 ID 和状态，返回 `actionDocRestricted=true`；前端只显示“无权查看关联单据”，没有可点击深链。
- 有查看权无编辑权：可打开目标详情，后续编辑/审核仍由目标模块自身权限和状态机控制。
- 未知部门/单据类型：服务端 fail-closed，不因新增枚举未同步而泄漏元数据。
- 采购分解动作必须同时具备 `purchase_request:view`、`purchase_order:create` 与 `purchase_order:decompose`；委外分解必须同时具备 `subcontract_application:view`、`subcontract_order:create` 与 `subcontract_order:decompose`。前端只消费服务端 `capabilities`，不得回退猜测旧 `*:edit` 权限。
- 保存草稿不等于有权送审；提交财务还分别要求 `purchase_order:submit_finance` 或 `subcontract_order:submit_finance`。

前端不渲染无真实动作的按钮：仓库不显示批量选择条或“批量状态变更（未开放）”，无采购/委外分解 capability 时也不显示复选框与生成入口；无可读来源时以说明文字和锁图标替代伪深链。

## 三、统一页面结构

页面从上到下为：

1. 部门标题、业务说明和刷新按钮；
2. 状态统计卡：待完成（默认视图）+ 各阶段卡 + 逾期/异常，即使某状态数量为 0 也保留入口。
   **「全部」卡自 2026-08-17 起不再显示**（三部门统一）：再点已选卡取消、或用筛选下拉的
   「全部状态 / 全部异常」，同样回到全量视图；
3. 关键词、状态、异常筛选（三个控件同高 56——搜索框与带 label 的状态/异常下拉对齐）；
4. 有采购/委外分解 capability 时显示已选数量、全选本页、清空；生成采购/委外订货单是右下角唯一悬浮主操作（large 高度 52），未选或选择不合资格时常驻灰显，合法选择后变为主色；
5. 宽屏使用统一任务表格，窄屏使用任务卡片列表；
6. 空数据、加载失败和重试使用统一反馈，不用空白页代替错误。

**宽屏滚动布局（2026-08-17 起，与货品资料一致）**：expanded 断点使用

**宽屏表格「供给方式」列（2026-08-17 起）**：后端返回供给路线码（`BUY` / `MAKE` /
`SUBCONTRACT`），页面经统一解析器 `operationsWorkbenchSupplyRouteLabel` 显示中文标签
**采购 / 自制 / 委外**（与生产物料分析侧口径一致）；未知编码保留原值，不丢任务。

### 3.1 首页聚合的分区故障隔离

首页 `/api/dashboard/overview` 会按当前用户权限分别读取仓库、采购和委外履约分区。任一分区发生非认证/授权运行时异常时，聚合接口继续返回其他指标、待办和政策动态，并用明确的不可用卡替代失败分区，同时写显式审计：

- `action=dashboard_fulfillment_partition_degraded`
- `targetType=fulfillment_workbench`
- `targetId=WAREHOUSE | PURCHASE | SUBCONTRACT`
- `result` 为归一化业务错误码或异常类型，不写原始异常消息

不可用卡按部门显示“仓库/采购/委外任务正在自动恢复”，摘要固定为“其它功能可继续使用，无需退出或反复刷新”，保留对应工作台路由，并返回 `sourceType=FULFILLMENT_UNAVAILABLE`、`tone=warning`、`count=0`。其中 `count=0` 只是 DTO 不可用态占位，绝不表示权威任务数为零；前端和报表必须以 `sourceType` 区分，不得把降级卡汇总为零待办。

首页聚合故意不使用一个包住所有查询的共享事务；每个工作台查询保留自己的只读事务，避免已捕获的子查询异常把外层事务标成 `rollback-only` 后再次导致整体失败。审计写入自身失败时记录受保护的服务端错误日志，不反向拖垮首页。

Spring Security 的 `AuthenticationException` / `AccessDeniedException` 和业务 `401/403` 必须原样重抛，不能伪装成普通分区缺失。该边界只隔离履约分区；全库不可用或首页其他聚合源失败仍使用整体可重试错态，不用 Mock、旧数据或零值冒充权威结果。

### 3.2 连接恢复后的当前页重载

仓库、采购和委外工作台页面监听全局 `connectionRecoveryProvider.recoveryEpoch`。只有客户端曾
确认完全断开、随后严格 health 或成功 API 证明连接恢复时，epoch 才递增；页面在下一微任务调用
`_load()`，按当前部门、页码、关键词、状态和异常筛选重新读取。用户不需要退出、切页或连续点刷新，
页面也不重置正在查看的筛选条件。请求代次继续保证恢复前的迟到响应不能覆盖恢复后的新结果。

该机制只重放工作台 GET 查询，不重放选择、分解、审核、收货、退货或其它业务写操作。结构化
`503 SERVICE_UNAVAILABLE` 表示 HTTP 服务可达但账号/权限解析依赖暂不可用，安全读可以有限重试，
但不递增全局断网 epoch、不显示成“无权限”、不清除会话。首页的 15 秒轮询是另一条局部自愈机制，
只在响应含 `FULFILLMENT_UNAVAILABLE` 时运行；正常首页和当前工作台都没有持续后台轮询。

## 四、部门状态和动作

### 4.1 仓库

| 状态 | 页面含义 | 允许动作 |
|---|---|---|
| `READY_TO_PICK` | 待备料 / 待领取 | 打开真实 `DRAW` 领料单 |
| `PARTIAL` | 部分领取 | 继续进入领料单处理剩余数量 |
| `DONE` | 已领取 | 查看来源和处理结果 |

仓库工作台不直接提供“批量改状态”。DRAW 审核只确认领料需求；仓库按行分轮 `issue` 时才产生实物发料、库存扣减和占用消费。页面必须同时展示单据审核态和实际发料累计，不能把“已审 DRAW”写成“已经领走”。

当前 V1 尚无独立的“待备料→备料中→待双方交接→已交接/生产在制”状态机，所以页面不能虚构拣货人、交接时间或双方签收。

`WDRAW`/良品退料必须是生产发起、仓库验收后才入库，并保留原 DRAW/issue 来源、实际退回数量和受控反向。当前由生产结清页选择原 DRAW 创建 WDRAW；仓库审核 WDRAW 后才增加库存并写 `GOOD_RETURN` posting，红冲沿原 posting 对称恢复。当前没有独立“待收料/双方签收”状态机，不能用负数 issue、改 DRAW 累计或直接调余额冒充退料；真实岗位与正反向 UAT 完成前仍按 NO-GO 管理。

### 4.2 采购

| 状态 | 页面含义 | 允许动作 |
|---|---|---|
| `WAITING_ORDER` | 计划已下达，申请行还有未分解数量 | 查看只读申请；选择明细生成订货单 |
| `PENDING`（订货财务态） | 已保存并提交，等待财务审核组审批 | 采购只读等待，不能修改/删除 |
| `REJECTED`（订货财务态） | 财务驳回 | 查看原因，修改后重新提交 |
| `APPROVED` / 订单 `status=1` | 财务通过，订货正式生效 | 进入采购管理继续收货链；仓库得到未来入库任务 |

采购分解规则：

1. 可以同时选择多张采购申请中的明细，也可以只填写部分数量；未分解余量继续留在任务中心。
2. 同一订货单只有一个供应商。需要多个供应商时分别生成多张订货单；系统不按价格、税率、MOQ 或历史偏好自动猜测拆单。
3. 订货不携带仓库（V292/ADR-038）：跨仓库明细可并入同一张订货单，「入到哪个仓库」由收货登记时必填；申请单仍保留仓库供计划侧分配。
4. 每条原生订货明细必须保存 `request_item_id`。无来源、来源已失效、货品/单位不一致或总量连同其它待财务订单已超申请剩余量时，提交和审核都拒绝。
5. 订单编辑页主要动作是“保存并提交财务”。保存成功但提交失败时保留草稿并显示错误，不能把草稿显示成待审。

剩余量口径：

```text
采购申请行剩余量 = 申请量 - 已生效订货量 - 其它待财务订货占用量
```

### 4.3 委外

委外申请与采购申请同样由计划下达、在委外部门只读。任务中心只显示 `WAITING_ORDER` 的未分解申请明细；可以跨申请选行和部分分解，但一张订货单只选一个委外商（订货不携带仓库，V292/ADR-038；跨仓库明细可同单，回收仓库到进仓登记时必填）。每条原生委外订货明细必须保存 `application_item_id`，待财务订货数量先占住申请余量。

委外订货使用与采购相同的 `DRAFT → PENDING → APPROVED/REJECTED` 财务状态。财务批准并把订单置为 `status=1` 后，才允许进入后续发料、回厂等链路并生成未来入库任务。驳回后由原制单人修改、重提；旧 attempt 和原因保留。

委外订货编辑页也只保留主要动作“保存并提交财务”：提交成功直接进入 `PENDING`；提交失败保留已经保存的草稿、明确提示并进入详情供重提。订货明细在保存前先校验有效委外单价，避免等到服务端送审才报商业字段缺失。

新增委外发料当前只允许保存草稿；由于缺冻结 BOM 快照和子件台账，上游引入与审核在前端禁用，服务端返回 409。历史已审核发料保留查看和受控红冲兼容；材料退/损耗只能按具体 `materialIssueItemId` 的权威已发、已退、已损耗累计计算余量，不得再用委外订单 legacy `issuedQty` 代替。

### 4.4 财务审核组与未来入库

钱流管理同时提供“订货审批任务”和“超量到货审批”，两者均为共享队列，对所有持 `finance_order_approval:view` 的财务人员可见，不再按个人 `assignee` 过滤。审批人为「财务审核组」：财务部门（`DEPT_FIN` 及子树）内在职、账号启用、持 `finance_order_approval:review` 的员工，或在权限管理被个人加授（`user_permission_overrides` effect='grant'）该权限的人（不限部门）；由 `WorkflowReviewerEligibility` 实时查库判定。V201 只给财务部门 `purchase_order:view` / `subcontract_order:view` 以查看关联订单，不授 edit。V229/ADR-027 起已删除单点负责人设置（页面、权限 `workflow_assignment:manage` 与表 `workflow_responsibility_assignments`）。

订单提交或仓库检出超量时不写实例负责人快照，由 `WorkflowReviewerEligibility` 实时判定合格审核人；只有合格审核人才得到对应 `allowedActions`。超级管理员不在财务部且未被点名加授不可代审，配置管理员或已知对象 ID 都不能绕过资格判定。2026-08-18 起订货审批操作收敛到财务「订货审批任务中心」（`/finance/procurement-approvals`）页内执行；采购/委外订货详情页对任何账号不再渲染审批按钮，业务侧只读看到「等待财务通过」状态（ADR-027 §五增补）。

财务通过在同一事务内执行订单既有生效副作用、写追加式审批事件，并创建唯一 `inbound_expectations` 及明细快照（订货不携带仓库后快照仓库允许为空，登记时选仓，V292/ADR-038）。Outbox 通知提交人和仓储部，但通知只作提醒；未来入库台账才是仓库预计到货任务源。

### 4.5 供给覆盖与实物可用的边界

工作台必须区分以下事实：

| 事实 | 当前解释 | 能否使生产 READY |
|---|---|---:|
| 申请/订单/未来供给 peg | 已有来源承诺 | 否 |
| 收货/回厂待检 | 实物已到但质量未判 | 否 |
| 合格转可用 | 质量结论生效且进入可用库存 | 才可参加整套物料原子分配 |
| DRAW 已审核 | 领料需求已确认 | 否，尚未扣库存 |
| 分轮 `issue` | 仓库已实物发料 | 是生产物料领用事实 |

V196 的 `inbound_expectations` 只是财务批准后的未来到货承诺，不是实际到货、质检、库存或应付事实。仓库预计到货页只显示财务已批订单，并按服务端 `allowedActions` 打开采购收货或委外回厂登记；预计到货可无仓库（订货不带仓库，V292/ADR-038），入库仓库在登记时必填，不作为登记门槛。

订货 10 吨、当前财务批准余量 10 吨、实到 100 吨时，已迁移的 V201/V202 契约按以下顺序处理；真实仓库/财务/供应商实物 UAT 未完成前仍不得视为生产验收：

1. 仓库首次审核重新锁来源和数量，发现超量后返回 `ARRIVAL_EXCEPTION_PENDING`（409）；异常任务与事件提交，但收货仍为草稿，库存、应付和订单累计保持不变。
2. 异常状态为 `PENDING_FINANCE`，受数据库守卫保护；仓库异常中心只读，不能靠修改数量、换来源、软删或删除绕过。
3. 系统按订单类型由 `WorkflowReviewerEligibility` 实时判定合格审核人。只有合格审核人可三选一：
   - `APPROVE_ALL`：批准全部超量，并填写财务说明；
   - `APPROVE_CUSTOM`：填写严格大于 0 且严格小于本次请求超量的批准追加量，并填写财务说明；0 必须选“不批”，全部必须选“全批”；
   - `REJECT_EXCESS`：不批准超量，只接收原财务批准的当前余量。

   标准 `10→100` 结果是：全批时入库/退回=`100/0`；自定义额外批准 5 时=`15/85`；不批超量时=`10/90`。三种结果都要等仓库按接受量再次审核后才实际入库。
4. 服务端计算接受量与未接受量并受控收窄草稿行及金额。批准追加量只绑定本异常、本收货单和订单行；另一张并发收货单不能借用。
5. 仓库再次审核时，只有接受量写库存/AP；成功后才累加订单行 `arrival_overage_posted_qty`。未接受量形成唯一 `PENDING_RETURN` 任务。
6. 退货任务只显示给原采购/委外下单人，`supplier_return_task:handle` 的唯一动作是“确认已退供应商”。下单人不能改变财务批准量，也不能批准入库。
7. 通知按职责最小投递：超量检出发全体合格审核人；财务决定发仓储部，接受量大于 0 提醒再审、接受量为 0 告知草稿行已移除；退回待办与完成回执只发原下单人。任何通知都不能替代服务端任务投影。

状态主线为：

```text
PENDING_FINANCE
  ├─ 接受量 > 0 → RECEIPT_ADJUSTED → 仓库再审
  │                    ├─ 退货仍待办 → RECEIPT_POSTED → 退货完成 → CLOSED
  │                    └─ 无退货或已先退回 → CLOSED
  └─ 接受量 = 0 → RETURN_REQUIRED → 退货完成 → CLOSED（收货行已删除，无需仓库再审）
```

这条闭环解决的是超量数量授权、库存/AP 防越权与退货责任，不是完整待检/IQC。页面的 `COVERED` 不能宣称“可生产”；目标采购状态仍应扩展为“预计到货→实际到货隔离→到货待检→部分合格可用→已覆盖”，目标委外链仍需“待发料→部分发料→供应商在制→回厂待检→合格入库→待余料/损耗核销→结案”。

委外目标守恒为：

```text
累计发出 = 合格产出对应耗用 + 良/不良退回 + 审批损耗 + 供应商期末结存
```

供应商处我方库存、回厂质量和逐需求核销尚未落地；工作台不得用一个 `COVERED` 状态遮蔽这些未决数量。

## 六、Dropdown 崩溃复盘和永久约束

### 6.1 根因

状态统计卡是固定定义的，因此数量为 0 时仍可点击；旧实现的下拉选项却只来自后端非零 `statusCounts`。用户点击仓库 `READY_TO_PICK`、采购/委外 `UNPEGGED` 等零计数卡片后，当前值已更新，但 `DropdownButtonFormField` 的 `items` 中没有同值选项，触发 Flutter“当前值必须且只能匹配一个选项”的断言。

同类问题还会在刷新后当前状态的最后一条任务消失时发生，不是单一页面或单一状态的偶发现象。

### 6.2 修复后的组件不变量

任一筛选下拉都必须满足：

```text
selectedValue 为空：
  items 中只有一个“全部”空值项

selectedValue 非空：
  items 中与 selectedValue 相同的项恰好一个
```

实现规则：

1. 所有后端选项先 `trim`，忽略空值并按 `value` 去重；
2. 当前已选值若不在选项中，使用统一状态/异常标签解析器补入一个临时选项；
3. 未知编码显示原编码，不能显示为空；
4. 下拉使用包含当前值的 `ValueKey`，确保统计卡外部更新能同步到表单字段；
5. 后端刷新后即使不再返回当前状态，筛选仍保持合法，用户可以主动清除或切换；
6. 状态卡数量为 0 仍可点击，用于验证“当前确实没有任务”，不能以禁用卡片掩盖数据变化。
