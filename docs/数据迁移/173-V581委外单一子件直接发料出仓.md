# V581 委外「单一叶子子件」直接发料出仓（COMPONENT_OUTBOUND）

## 背景

用户口径（2026-09-14）：委外件如果展开后**只有一个物料**（一层、一颗），就不该走自制流程——
把那颗子件发给委外商，回来就变成父件。等子件采购入库了，委外才执行出库。

V458/ADR-062 把「目标件有活动 BOM」一律解释成「先自制目标件再整件发外」，于是这种
一进一出的来料加工（电镀 / 喷涂 / 注塑 / 车削）被迫建一张车间什么都不做的生产计划，
FQC 检一个没加工过的件，仓库把刚入库的东西原样再发出去。

业务口径见 [ADR-085](../99-决策记录-ADR/ADR-085-委外单一子件直接发料出仓.md)。

## 变化

### 1. 新增形态判据函数（唯一口径来源）

`fn_subcontract_sole_component_goods(goods_id) RETURNS BOOLEAN`（STABLE）：

- 活动 BOM 边**恰好 1 条**（边未删 + 子件货品未删 + 子件非 `auto_created` 占位）；
- 该边 `consumption_basis = 'PER_UNIT'`（PER_PACKAGE / FIXED_BATCH 带取整，压不成标量单耗）；
- 该边 `control_stage ∈ (START, ASSEMBLY, FINISH)`（SHIP / REFERENCE 不是投入料）；
- **子件自身没有活动边**（真正的一层）。

数量基准守卫、物料分析子层展开分类、以及 Java 侧
`SubcontractMaterialPlanService.soleOutboundComponent` /
`MaterialAnalysisCommandService.soleComponentSubcontractGoodsIds` /
`MaterialAnalysisService.soleComponentSubcontractGoods` 全部调它，判据不在多处各抄一遍。

### 2. `subcontract_material_plan_items.flow_mode` 第 5 个取值

`COMPONENT_OUTBOUND`：父件 = 订货目标件，`goods_id/color_id/unit_id` = 那颗子件，
`unit_rate = 1`，`bom_unit_qty = round6(订货换算率 × BOM 单耗)`（子件基本量 / 目标件订货单位），
`planned_qty = prepared_qty = round4(订货量 × bom_unit_qty)`（子件基本量）。

物理形态与 V304 的 `LEGACY_BOM_COMPONENT` 一致，但**是独立取值**：LEGACY 是不可改写的
历史事实（无专属预留、无 BOM 快照、不受出仓分配断言约束），新流向要享受 V436 之后的
专属预留、出仓分配断言与 V507 守恒，两者混同会让历史对账再也分不清。

### 3. 五个既有守卫按新流向扩展

| 守卫 | 原口径 | V581 |
|---|---|---|
| `subcontract_material_plan_item_flow_mode_chk` | 四值 | 加 `COMPONENT_OUTBOUND` |
| `subcontract_material_plan_item_preparation_shape_chk` | DIRECT 分支 | 改 `flow_mode IN ('DIRECT_OUTBOUND','COMPONENT_OUTBOUND')`（批准即待出仓、prepared=planned、不挂前置自制分析）。**刻意不约束 `preparation_warehouse_id`**——仓库存草稿时要写它 |
| `subcontract_material_plan_item_bom_snapshot_chk` | 四分支 | 加「有子层 + 冻结**目标件**指纹」分支。重建前先断言库内确是 V529 之后的形态（DIRECT 分支为 `IS NOT NULL`），避免把 V529 的放开静默回退 |
| `fn_guard_subcontract_target_quantity_basis_insert`（V502） | 非 LEGACY 行强制 `goods_id = 订货货品` | 新增 COMPONENT 专属分支：父件=订货货品、goods=那条唯一活动边的子件、`unit_id`=子件基本单位、`unit_rate=1`、`bom_unit_qty=ROUND(订货换算率×边单耗,6)`、且 `fn_subcontract_sole_component_goods(oi.goods_id)` 成立 |
| `fn_assert_subcontract_outbound_issue_allocation`（V458） | 三值白名单 | 加 `COMPONENT_OUTBOUND`——同样要求「已审出仓量 = 专属预留精确覆盖」。其货色一致性判断天然正确（计划行与出仓明细两边都是子件） |
| `fn_assert_subcontract_target_outbound_receipt`（V507） | 直接比出仓量与回厂量 | COMPONENT 行按 `v_per_base = bom_unit_qty / 订货换算率` 折算后再比：`expected = ROUND(回厂目标件基本量 × v_per_base, 4)`，先出后进与消费守恒都用它。缺冻结单耗即 23514（fail-closed） |

### 4. 两条 fail-closed 新守卫

- `subcontract_component_outbound_exclusive_guard`：同一订货明细不得混用
  `COMPONENT_OUTBOUND` 与其它新流向。回厂消费按「货品+颜色」分组逐组扣满，
  混行会两组都扣不够而把单据永久卡死。
- `subcontract_component_outbound_no_loss_replacement_chk`：COMPONENT 行的
  `loss_replacement_qty_base` 必须为 0。V525 的补量算式只认 `DIRECT_OUTBOUND`，
  不焊死就会出现「有额度却无人校验」的 fail-open。本形态的损耗补量单独排期。

### 5. 刻意不动的两处

- **`v_subcontract_quantity_basis_issues` 不加白名单**：它的判据
  `pi.bom_unit_qty <> oi.unit_rate` 对 COMPONENT 恒为真（单耗 ≠ 换算率），
  加进去等于把每张单都判成异常、在出仓/回厂 approve 的一致性预检里卡死。
  本迁移只补 `COMMENT ON VIEW` 写明它只覆盖目标件同一性的三种流向。
- **`fn_assert_subcontract_target_outbound_receipt` 对 `PREPARED_OUTBOUND` 的既有遗漏**：
  该函数白名单今天就不含 `PREPARED_OUTBOUND`，补上会让存量单立刻开始受约束、
  可能炸出历史脏数据，单独排期。

## 兼容与数据影响

- 纯前向：不新增表、不改历史行、不改已应用迁移的字节。
- 存量 `LEGACY_BOM_COMPONENT` / `DIRECT_OUTBOUND` / `MAKE_THEN_OUTBOUND` /
  `PREPARED_OUTBOUND` 行行为与字节一个都不变；新取值只在新批准的订货行上出现。
- 老分析刷新后即进入新口径：命中判据的委外件下达时不再建 `SUBCONTRACT_MAKE` 任务。
  **已经建了前置自制任务的在途单不受影响**，继续走原链（判据只在下达那一刻生效）。
- 两条 CHECK 均为 `NOT VALID`（不回扫历史行）。
