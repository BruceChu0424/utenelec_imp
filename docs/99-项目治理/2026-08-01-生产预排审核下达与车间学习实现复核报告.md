## 一、回答业务问题

“一键生成子计划”应该在审核前先做，但审核前产物只能是**预排草案**，不能是生产执行、库存占用、采购、委外或领料的正式事实。这样既能在审核前看到完整计划，又不会让未审计划提前占料或越权建单。

建议的确定流程是：

1. 草稿计划进入“物料需求评审”，查看当前直接 BOM 层和 READY/WAITING、BUY/MAKE/SUBCONTRACT 结论。
2. 用户可调整实排数量、生产优先级、车间、班组、负责人、开工和完工日期，然后保存 V191 预排草案；保存后可按服务端不可变载荷重新打开精确明细。
3. 点击审核时，服务端重算当前 BOM、库存、数量和指纹，并在同一事务内审核计划与正式下达。
4. 任一下游生成失败，计划审核也回滚，不留“已审但只生成一半”。
5. 已审无计划包可后续补建一次；已审有有效包只回放单据结果，不再“生成剩余”或原地篡改。系统待料齐套后自动转产；人工暂缓只能经有权限、带版本和幂等键的“解除人工暂缓”恢复。

## 二、本轮确认的问题与原因

### 2.1 “确认生成”看起来没反应

前端曾将 MAKE 缺口也放入用户可编辑 `routes`请求，而服务端请求契约只允许 BUY/SUBCONTRACT。包含 MAKE 的请求会在进入正式确认服务前被参数校验拒绝。页面又没有把所有结果单据和可行动错误完整呈现，形成“按了什么都没有”的体感。结果回查现对已确认计划包持悲观读锁，避免与并发取消/反向交错后返回过期的“已确认”快照。

当前契约收紧为：前端只回传 BUY/SUBCONTRACT 用户选择，MAKE 由服务端根据货品主档和当前直接 BOM 层权威推导；请求期间显示忙态、禁止双击，失败显示可行动原因，成功后立即展示真实单据。

### 2.2 审核边界不完整

原 V1 正式确认能生成执行分段、DRAW、采购/委外草稿和自制子计划，但服务端正式确认入口需强制父计划已审，草稿不得直接落执行事实。V191 用不可变预排草案补上审前评审需求，并由计划审核事务调用正式确认内核。

## 三、完整下达与数量不变量

正式下达必须在一个事务中保持：

```text
对每一条 production_plan_items：
Σ READY 分段数量 + Σ AUTO_WAIT 分段数量 + Σ DEFERRED 分段数量 = 该计划明细数量
```

- READY 只在全部必需物料可同时占用时生成，一次写全套 `stock_reservations` 和 DRAW 来源；
- AUTO_WAIT 与 DEFERRED 都写全量需求和未来供给挂接，不锁零散现货；AUTO_WAIT 齐套可自动提升，DEFERRED 必须人工放行；
- BUY 缺口生成采购申请草稿和 supply peg；
- SUBCONTRACT 缺口生成委外申请草稿和 supply peg；
- MAKE 只按本 package 的当前直接 BOM 层缺口，按货品/颜色聚合生成真实子 `production_plans` 和 `subplan_links(source='EXECUTION_V1')`；
- 任一路线或文档生成失败，计划状态、计划包、分段、占用和全部下游一起回滚。

### 3.1 MAKE 的逐级边界

A→B→D 多层自制 BOM 中，A 的评审和正式包只生成 B；调度员进入 B 子计划后，再评审并生成 D。禁止在 A 包里递归 explode 所有层级，否则 A 与 B 都可能生成 D，造成重复需求与子计划。物料评审卡也仅显示当前直接层，与本次真正会生成的采购/委外/子计划保持一致。

### 3.2 系统待料与人工暂缓

两类 `WAITING` 不再混为一种状态：系统缺料保存 `auto_promote_when_ready=true`，权威到货或回供后可齐套自动转 READY；人工暂缓保存 `false`，任何到货回调都不得提升。解除人工暂缓由 `POST /api/production/plans/{planId}/execution-segments/{segmentId}/release-defer` 完成，只允许 `false→true` 一次，校验编辑权限、期望版本、幂等键和活动计划包，并在同一事务重查全套物料。数据库要求提交时存在匹配前后版本的 `RELEASE_DEFER` 事件，阻止绕过服务直接改标志。

## 四、物料需求评审交互

评审弹窗按库存充足、采购缺料、自制缺料、委外缺料、自制无 BOM 分类。每个卡片有“查看详情”，详情展示：

- 生产流水号/分段临时号、货品编号、名称、规格、颜色和来源订单行；
- 计划数量、实排数量、单支基本用量、毛需求、自由库存、已分配、缺口和供给路线；
- READY/WAITING、车间、班组、负责人、计划开工与计划完工。

用户可分拆执行行、改实排数量和安排字段，并跨产品选择哪些分段先标为 READY、哪些先 WAITING；页面不以初始建议限制单个产品的 READY 上限，服务端仍按全计划实时库存做最终整套齐料校验。提交前实时检查 READY/WAITING 全量守恒。紧凑屏用接近全屏的底部面板，中/宽屏用侧面板或全高对话框；保存后可通过“查看已存草案”只读回查当时精确分段、采购申请开关以及采购/委外路线。

## 五、车间建议学习（V192）

V192 是便利性建议，不是业务事实或自动决策：

- 首次计划包正式下达成功后，同一产品的全部分段都使用同一有效车间时才学习；
- 执行段后续 assign 成功且真实改变安排时也学习；幂等 replay 不重复学习/计数；
- 同货品同次被拆到多个车间，或任一分段没选车间，视为歧义样本，本次不学习；
- 用户每次可修改系统建议；学习表只影响未来预览，不回写任何历史执行分段；
- 车间必须是 `DEPT_PROD` 直属有效组织，班组必须直属该车间；负责人须位于所选组织范围且为 `active/probation`。前端只展示有效范围，服务端在草案保存、正式下达、后续改派和真正派工时重复校验，V194 数据库触发器再兜底车间/班组层级。

## 六、V191–V195 数据结构与历史边界

### 6.1 V191 预排草案

`production_planning_drafts` 保存仓库、JSON 请求载荷、请求哈希、预览指纹、规划人/时间和终结证据。每个计划最多一个 `ACTIVE`；载荷不可变，只允许 `ACTIVE→APPLIED` 或 `ACTIVE→SUPERSEDED`，终态不可改写/删除。

### 6.2 V192 车间建议

`production_goods_workshop_preferences` 每产品一条建议，保存 `workshop_department_id`、`selection_count`、`last_selected_by/at`。只接受未删除货品和车间部门，数据变化进入通用审计。

### 6.3 V193 审计覆盖扫尾

`V193__refresh_audit_trigger_coverage.sql` 在 V191/V192 新业务表之后重跑 fail-closed 审计触发器覆盖检查。它只确保以后发生的新增、修改、删除进入审计，不读取业务含义、不更新旧业务行，也不补造历史审计。

### 6.4 V194 MAKE 回供、人工暂缓与组织守卫

V194 将直接层 `PRODUCTION_PLAN_ITEM` 子计划明细绑定为 MAKE peg 的唯一明确来源，增加 `production_material_make_receipt_allocations` 追加式回供/红冲链，校验路线、计划包、子计划链接、入库容量、预约和 DRAW 守恒，并统一行锁顺序阻止并发超配。它同时持久化 `auto_promote_when_ready`，使 AUTO_WAIT 与 DEFERRED 的行为可由数据库和语义事件共同验证；新写入的车间、班组和负责人还须通过组织层级守卫。

### 6.5 V195 审计覆盖再次刷新

`V195__refresh_audit_trigger_coverage.sql` 在 V194 新业务表之后再次执行 fail-closed 审计 sweep，确保 MAKE 回供分摊表等公开业务表具备唯一、启用、AFTER ROW、覆盖 I/U/D 的批准审计触发器。V195 仅保护迁移后的未来操作，不补历史审计、不重算业务数据。

### 6.6 零回填原则

V191/V192 迁移只建表、约束、索引、不可变守卫和审计触发器，不含历史 `INSERT ... SELECT`；V193/V195 只检查/补齐未来写入的审计触发器；V194 只增加新字段、守卫、MAKE 供给/回供结构与索引，不补造历史供给、分摊或执行事实。

- 不为历史已审、草稿或终态计划补造预排草案/计划包；
- 不重算历史 BOM、物料需求、READY/WAITING、占用或下游单据；
- 不从历史 `production_plan_items.department_id`、报工车间或文本字段猜测车间偏好；
- 历史记录原样保留、只读回查；新规则只由迁移后用户主动预排、审核下达和后续派工产生。

## 八、A4 计划单/工卡决策

本轮选择“**结构化业务事实优先，确认后提供只读 A4 工卡**”，不把 PDF 当作数据库真相。

- 计划包、执行分段、真实子计划、采购/委外申请和 DRAW 是可查询、可关联、可反向的业务事实；
- 已确认 V1 计划包可生成横向 A4 生产执行工卡打印预览，包含分段、货品/规格/颜色、数量、物料承诺/缺口、车间/班组/负责人、开完工、销售订单、领料单、包版本、名称口径和签字栏；失效包拒绝打印；
- 工卡不是工艺路线卡或第二套业务实体；补打、丢失或纸张上的手写不得改变系统业务状态。

外部依据：

- Microsoft Dynamics 365 [Production process overview](https://learn.microsoft.com/en-us/dynamics365/supply-chain/production-control/production-process-overview) 将创建、估算、排程与释放分阶段；
- Microsoft Dynamics 365 [Release a production order](https://learn.microsoft.com/en-us/dynamics365/supply-chain/production-control/tasks/release-production-order) 将仓库原料作业和工卡/路线卡放在释放后；
- SAP S/4HANA [Converting Planned Orders](https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/af9ef57f504840d2b81be8667206d485/c498b6535fe6b74ce10000000a174cb4.html) 将计划订单视为内部计划元素，后续转换为生产订单或采购申请；

## 十、剩余风险与放行结论

候选实现解决了“审前看不到完整建议”、“确认无反馈”、“生成结果不可回查”和“历史车间经验不能用于未来建议”的交互/生命周期问题，但不消除以下上线阻断：

1. 目标库仍在 V190，V191–V195 未正式应用和前后差异验收。
2. 21,336 行无 BOM 明细、2,420 张相关计划、1,713 个自制无下层 BOM 货品仍是主数据风险；新数据必须 fail-closed。
3. V1 计划包实际历史数为 0，尚无目标库真实业务样本证明 BUY/MAKE/SUBCONTRACT/DRAW 全链路稳定。
4. MAKE 直接层回供/红冲/重新齐套已补齐候选数据库语义与真实 PostgreSQL 用例；V195 也已覆盖其未来审计写入。采购/委外回厂 IQC 隔离、委外发料/在制/余料、仓库实物交接、有限产能和跨组织授权仍有既定 NO-GO 边界。
5. 尚未完成真实登录账号、真实岗位、实物交接、并发、压测、备份恢复和发布签字。

因此最终放行结论是：**候选代码已通过本轮本地定向与隔离 PostgreSQL 验证，但不得把这些工程证据等同于生产上线；目标库迁移、真实岗位 UAT 和既有全链路门禁未完成前仍为 NO-GO。**
