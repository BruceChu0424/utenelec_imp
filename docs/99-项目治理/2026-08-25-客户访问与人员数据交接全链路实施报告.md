## 一、用户目标

本轮解决四个直接业务问题：

1. 客户不区分内销、外贸，普通销售默认只查看自己负责的客户；
2. 需要协同时，可以让指定人员查看某位负责人的整批数据，也可以只共享单个客户；
3. “能看”“能改”“当前由谁负责”必须分开，不能因为加看同事数据就获得修改权；
4. 员工离职或岗位交接时，当前责任可移交给接手人，但历史制单人、审批人和审计事实不得改写。

## 二、最终权限模型：查看、修改、接手分离

### 2.1 操作权限

- 页面查看、编辑、导出等动作继续使用既有按钮级权限；
- `client:assign` 单独控制客户负责人和单客户可见人的维护，不再混入普通 `client:edit`；
- `employee:handover` 单独控制人员数据交接；
- 超级管理员和显式 `*:view:all` 仍是全量查看例外，但写操作仍需对应业务动作权限。

### 2.2 数据查看范围

- 默认查看本人当前负责的数据；V393 收回 `DEPT_SALES`、`DEPT_RAIL` 对
  `client:view:all` / `sales:view:all` 的部门默认授权；
- `user_data_scopes` 只增加“可查看哪些负责人数据”，不进入可写集合；
- 单客户 `client_visibility_grants` 只增加该客户的只读查看，不改变客户负责人；
- 全局权限页以服务端动态 catalog 展示“仅本人 / 额外查看 N 人 / 查看全部覆盖 / 功能未启用”，
  保存携带 desired + expected owner 集合做 CAS，防止两个管理员静默互相覆盖。
- 数据范围 owner 是 raw 历史口径：A 离职后仍可选 A 并标记 `historicalOnly`，只查看 A 原历史，
  不自动扩大为当前接手人 B 的范围；
- 正式 client scope 交接把“A 的全部客户”精确转换为本批已转出客户的逐客户 grant，不把旧 raw scope
  改写成“B 的全部客户”，避免接手人未来新增客户被无意扩权。

### 2.3 修改范围与当前责任

- 普通写入要求“对应操作权限 + 当前可写负责人范围”；

### 2.4 统一单据 scope 能力与跨模块对象边界

客户权限收口后继续检查了共用单据页面，新增当前登录主体专用的
`GET /api/auth/me/document-scopes/{scope}`。服务端只接受白名单
`sales / finance / purchase / subcontract / production_plan / stock_doc`，返回
`scope / writeAll / writableOwnerIds`；任意调用方自造 scope 会被拒绝。`writableOwnerIds` 只含本人和
正式交接继承的历史归属人，手工 `user_data_scopes` 仍只读。

Flutter 将该能力接入六类详情页和六类直接编辑页，共 **12 个页面**：

- 详情页在 capability loading/error 时一律 fail closed 为只读，显示统一说明、重试按钮并支持 provider
  invalidate；
- 直接编辑路由必须先等待 capability，不能在未知状态先填充可编辑表单；无权或请求失败时返回详情页，
  不提供“加载失败所以暂时可写”的 fallback；
- `ownerEmployeeId` 缺失同样不可写；`writeAll` 只代表服务端认可的全量对象范围，仍需页面动作权限；
- 池化财务审核/红冲、生产日报审核/红冲和 production-linked 仓储动作保留显式例外，不把例外扩成普通
  编辑权。

采购/委外“提交财务”曾只检查 `purchase_order:submit_finance` /
`subcontract_order:submit_finance`，持有功能权限的只读查看人可能绕过 owner 范围创建 PENDING 审批案。
现由 `ProcurementFinanceApprovalService.submit` 在锁单、生成快照和写审批案之前调用
`requireFinanceSubmitterWritable(orderId)`：提交人必须同时拥有对应订单可写范围；失败立即 403，且不会
读取/固化快照或写 case/event。财务审核员的池化 approve 路径仍按审核资格执行，不错误套用提交人 owner
守卫。

生产领料与计划材料子资源另补 P0 IDOR 防护 `ProductionMaterialReadAccessPolicy`：

- 计划类子资源要求 `production_plan:view` 与可见 owner，或具备 `stock_doc:view` 且处于明确的生产仓库
  任务池；
- 领料单必须真实存在、类型为 DRAW；仓库任务池例外只对 production-linked DRAW 生效，人工 DRAW 仍按
  普通 `stock_doc` owner 范围；
- 已知但不可达 UUID 与不存在/错误类型统一返回 `NOT_FOUND`，避免用材料、结清或可退料接口探测对象；
- `returnableSources(planId, drawId)` 会校验每个提供的父对象，clearance/settlementSources 先验计划，拒绝
  时在任何 picker/ledger SQL 之前停止。
- 本人责任和已完成交接后继承的责任进入可写范围，普通加看不进入；
- `*:view:all` 是显式全量对象范围，不替代 edit/delete/status/approve 等动作权限；
- 新建或新指派的负责人必须是 `active / probation / onLeave` 在册员工；
- 客户列表/详情由后端下发 `writable/accessManageable`，Flutter 缺字段 fail closed，写接口仍重新鉴权；
- `maker_id`、`created_by`、审批人和审计 actor 是历史事实，永不因交接改写；系统通过交接边和
  当前负责人解释“现在由谁接手”。

## 三、客户单体授权

客户详情新增“负责人和可见人”入口：

- 一个权威负责人，使用员工 UUID；
- 多个额外只读查看人；
- 修改原因必填；
- `clients.access_version` 独立于普通客户编辑版本，负责人或共享变化均单调递增；
- 更新必须携带 `expectedAccessVersion`，并发冲突返回 409 后刷新；
- `client_access_change_events` 追加保存负责人、查看人 before/after、原因、操作者和结果版本，禁止修改或删除。

客户列表已使用“负责人”权威姓名，普通客户编辑表单不再直接修改 owner；内销与外贸客户使用同一规则。
负责人/查看人候选调用 `/api/master/clients/access-candidates`，只需 `client:assign`，不再借
`employee:view` 读取完整花名册；端点只返回当前员工、启用账号和最小非 PII 字段并服务端分页搜索。

负责人由 A 改为 B 时，如 A 仍是当前员工且账号启用，服务端自动暂时保留 A 为该客户只读 viewer，
避免 A 的在途销售草稿因客户引用不可达变成死单；保存后以响应 viewer 列表为准，后续移除前须确认无
在途草稿。客户详情、行菜单、批量动作和地址新增/删除均以 `writable × 对应动作权限` 门控。

## 四、整人和按模块交接

人员数据交接支持以下八个 scope：

`goods / client / sales / finance / purchase / subcontract / production_plan / stock_doc`

预览逐组返回四种明确动作：

| 动作 | 含义 |
|---|---|
| `TRANSFER` | 转移当前责任 |
| `HISTORY_ACCESS` | 历史事实不改写，给接手人建立后续查阅能力 |
| `RELEASE` | 释放个人占用、认领或临时关系 |
| `BLOCKING` | 必须先回原业务页面处理，禁止跳过 |

preview 同时返回 `transferCount / historyAccessCount / releaseCount / blockingCount`；`total` 是四类相加
的影响项次，不是去重业务记录数，合成的 `target.required` 不进入 total。`scopeTargetEmployeeIds /
scopeTargetEmployeeNames` 给出每个 scope 的实际接手人：既有 scope 接手人继续生效，默认接手人只承接
尚未交接范围，因此整人离职也可形成多目标交接。

`employee_data_handovers.requested_scopes` 保存用户原始请求；实际执行 scope 与接手人写入有效 scope
记录，requested/effective 不混写，重放时校验原请求一致。

人工入口位于“账号与权限管理 → 按员工 → 可查看数据 → 人员数据交接”：

- 当前选中员工是接收人；
- 交出人可选择在册或已离职员工，但不能与接收人相同；
- 八模块默认全选，可明确缩小范围；
- 先预览，再填写原因和生效日期，最后确认执行；
- `requestId` 使用 UUID v4，重复请求返回原回执，不重复执行；
- 结果记录模式、scope、数量摘要、序号和 replay 状态，形成可审计交接回执。
- source/target 候选走 `/api/admin/data-handovers/candidates` 最小端点，服务端按操作者人事范围裁剪；
- UI 为“选择 → 预览 → 确认执行 → 完成回执”四步，409 自动回到权威 preview；

## 五、离职阻断与事务原子性

员工详情“办理离职”进入新的四步流程：

1. 显示姓名、工号、部门，填写稳定离职类型 code、日期和必填原因；
2. 选择一个在册接手人；无责任数据时可不选；
3. 加载真实数据盘点，按模块显示数量、处理方式和阻塞恢复路径；
4. 完成门禁、资产、账号、社保公积金等线下回收确认，再查看最终影响摘要。

服务端在同一事务内重新盘点并执行：

- `hasBlockers=true` 时拒绝离职；
- `requiresTarget=true` 且无接手人时拒绝；
- 交接 requestId 缺失或请求不一致时拒绝；
- 交接、清理离职员工关系、任职历史、员工状态、账号停用和 refresh token 吊销任一失败，事务整体回滚；
- 只有事务成功才显示完成并离开页面，失败不会留下“已停账号但数据未交”的半状态。

V395 的当前员工引用触发器与 V397 的 `employee → user` 锁序继续关闭“离职与并发新指派/新授权”竞态。
V398 新增 `employee_offboarding_events`，以整笔 requestId 幂等保存 payload、四项 checklist、状态和结果；
相同 requestId/相同 payload 完成后重放成功，不同 payload 返回 409。离职支持按 scope 沿用既有接手人，
默认接手人只接剩余范围。

离职事务还会停用个人权限覆盖与负责人委派，删除手工 data scopes、单客户 share，释放 claims 并驳回
在途个人资料申请；`EmploymentHistory(resign)` 写入 requestId 和四项人工确认。复职只恢复员工/账号
active，保持 remote access 关闭并强制改密，不恢复离职前个人覆盖、负责人委派、data scopes、单客户
share 或原责任数据。

V398 为手工 owner scope 与正式交接图分别保存任职代际；正式图同时绑定 source/target 代际，并先选
同 scope 的最新边、再校验 target 代际，接手人复职后不会回退复活更旧接手边。复职后旧整人 scope
仍保留审计事实，但不再授予新任职数据；管理员显式重授时由数据库写入新代际。

离职还会把未完成附件上传会话原子置为 `EXPIRED/EXPIRY_CLEANUP_PENDING`，交给既有暂存清理链；
已签发下载 presigned URL 无法服务端即时撤销，只能等待短 TTL，是本地候选明确保留的残余风险。
V399 为 `users` 增加独立 JPA `@Version` CAS，并统一管理员账号写的 employee→user 锁后复验，旧实体
快照不能覆盖离职后的 disabled、remote access 关闭或临时凭据收紧。
