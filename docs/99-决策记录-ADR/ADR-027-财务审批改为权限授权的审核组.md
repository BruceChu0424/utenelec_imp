# ADR-027：财务审批由「指定单一负责人」改为「权限授权的审核组」

- **状态**：已接受（源码候选）
- **日期**：2026-08-07
- **影响**：钱流、采购、委外、仓库、权限、通知、审计、Flutter 钱流 hub/任务中心
- **依赖**：ADR-019（被本 ADR 部分反转）、Flyway V196/V201（被 V229 收尾）、V229
- **反转**：ADR-019 §2.5、§3.2 中「精确负责人对象校验」的决策

## 一、背景

ADR-019 为采购/委外订货审批与到货超量审批确立了「每类行为恰好一名指定负责人」的模型：`workflow_responsibility_assignments` 每个行为码一行，提交时把该人快照写进审批实例，只有这个精确的 `assignee_user_id` 才能看到任务并通过/驳回。这是为了 fail-closed 与对象级审计。

实际运行暴露了单点瓶颈：该人请假、出差、离职或临时不在时，审批整体卡住；业务方希望在权限管理里给财务部门的多个员工授权，互为备份。与此同时，系统内其它审批（如报销 `expense:approve`）本就是「按权限的审批池」模型——采购这两条流程是异类。本 ADR 让它们对齐系统既有的权限模型。

## 二、决策

### 2.1 审批人是「财务部门审核组 + 跨部门点名加授」

可审批者（由 `WorkflowReviewerEligibility` 统一判定，唯一权威）满足其一即可：

- 财务部门树（`DEPT_FIN` 及子树）内在职、账号启用、且持有 `finance_order_approval:review`（默认全体财务人员，因 `DEPT_FIN` 已在 V196 获该权限）；**或**
- 被**个人加授** `finance_order_approval:review`（`user_permission_overrides` 中 `effect='grant'`），不限部门——用于点名跨部门人员（如主管）做审批。

不再读取 `workflow_responsibility_assignments`，不再快照单一负责人。跨部门审批必须**个人点名**（`user_permission_overrides`）；仅给其它部门授部门级权限不构成审批资格——这是有意的收窄，保证审批人都是被明确指名的个体。增减人选：在「权限管理」给员工个人加授/收回该权限，或调整财务部门人员。

提交与检出超量时**失败闭合**：若当前没有任何合格审核人，提交/异常生成立即报错阻断，绝不产生无人可审的任务。

### 2.2 任务队列改为共享，而非个人收件箱

- 订货审批任务（`procurement_order_approval_cases` 中 `PENDING`）与到货超量任务（`procurement_arrival_exceptions` 中 `PENDING_FINANCE`）对所有持 `finance_order_approval:view` 的财务人员可见。
- 任何一个合格审核人都可处理；前端按钮（`allowedActions` 中的 `APPROVE/REJECT` 与到货的 `APPROVE_ALL/APPROVE_CUSTOM/REJECT_EXCESS`）由服务端按「当前用户是否合格审核人」计算，不因本地角色或超管标记显示。（2026-08-18 增补：订货审批按钮只在财务「订货审批任务中心」页内渲染，订货详情页一律不再显示，见 §五。）
- 并发由既有乐观锁 `expectedVersion` 保护：两人同时处理时，第二人的 `UPDATE … WHERE version=?` 得 `changed!=1`，提示「已被处理」。

### 2.3 通知改为广播给审核组

- 提交（`PROCUREMENT_FINANCE_SUBMITTED`）与检出超量（`PROCUREMENT_ARRIVAL_EXCEPTION_DETECTED`）的通知接收人，由「快照中的单一负责人」改为「当前全部合格审核人」（`FinanceReviewerEligibilityPort.allEligible()`）。
- 驳回/通过仍通知提交人，预计到货仍通知仓储部——不变。

### 2.4 安全边界保留：超管不可绕过

- 审批 gate 走 `WorkflowReviewerEligibility.findEligible`（含财务部门树判定 + 跨部门须 `user_permission_overrides` 个人加授），**而非**纯 `@PreAuthorize` 权限命中。
- 超级管理员虽然拥有全部权限，但其权限来自 `is_super_admin` 标志而非 `user_permission_overrides`；若不在财务部门树内、且未被个人点名加授，仍被服务层资格判定拒绝——保留 ADR-019 「超管不可代审」的安全边界。需要让某位超管审，就显式给他个人加授或在财务部任职。
- 客户端两层防御不变：路由守卫 `permission_by_path` 拦截未授权深链（直达 `accessDenied`/`notFound`），服务端 `@PreAuthorize` + 服务层资格判定是权威。

### 2.5 移除「审批负责人设置」

- 删除 `WorkflowResponsibilityController`/`Service`/`Contracts`、`workflow_assignment:manage` 权限码与 `workflow_responsibility_assignments` 表（V229）。
- 删除前端「审批负责人设置」页面、路由、菜单入口与仓库方法。
- `WorkflowReviewerEligibility` 保留，作为审核组资格的唯一判定。

## 三、数据与审计（V229）

- `procurement_order_approval_cases.assignee_*` 与 `procurement_arrival_exceptions.finance_assignee_*` 改为可空；V229 起新行为 NULL，旧行保留为历史快照。
- `DROP TABLE workflow_responsibility_assignments`；`DELETE` 权限码 `workflow_assignment:manage`（先清 `department_permissions`/`user_permission_overrides` 关联）。
- 审计不变：实际决策人仍由 `decided_by_*` 记录；审批/到货事件表仍追加式、禁止 UPDATE/DELETE。

## 四、后果

- 好处：消除单点瓶颈；财务组互为备份；与系统其它审批模型一致；配置入口收敛到权限管理。
- 代价：审批人不再是单一可指名对象（任务可被组内任一持权者处理）；审计需通过 `decided_by_*` 而非 `assignee_*` 追溯实际决策人。
- 待续：真实多账号黑盒验证（多人同审、超管被拒、即时回收权限生效）、目标库迁移与发布签字。

## 五、增补（2026-08-18）：审批操作入口收敛到财务任务中心

- **问题**：订货详情页按 `allowedActions` 渲染「财务通过/退回修改」按钮，导致任何命中审核资格的账号（典型如挂在财务部或带超管标记的 admin）在提交订货后，同一详情页立刻变成「财务审核」视角，采购/委外人员与财务审批界面职责混在一起。
- **决策**：采购/委外订货详情页对**所有账号**（含合格审核人与超管）不再渲染审批按钮；业务侧提交后只读看到「等待财务通过」状态。审批的唯一前端入口是财务「订货审批任务中心」（`/finance/procurement-approvals`）页内操作（`APPROVE/REJECT`，到货超量仍在超量任务页）。
- **不变量**：服务端 `WorkflowReviewerEligibility` 资格判定与 `@PreAuthorize` 兜底不变；`allowedActions` 仍由服务端计算并随任务接口返回，详情页只是不再据此展示审批动作；共享队列、乐观锁并发保护与通知广播均不变。

## 六、增补（2026-08-29）：表格任务中心与原子批量决定

- 订货审批任务中心取消逐张大卡片和卡内单笔按钮，统一使用 `MasterDataTableView`：单击勾选，350ms 内同行双击打开订货主详情；紧凑端同样为平面表格，不另画一套卡片。类型使用分段筛选，关键词由服务端按单号/供应商/提交人搜索。
- 表头上方只显示「已选 N 项 + 清空」，右下悬浮「批量驳回(N) / 批量通过(N)」。按钮显隐和逐行可选性仍以服务端 `allowedActions` 为权威；APPROVE/REJECT 不能互相替代。
- 客户端禁止循环调用单笔端点冒充批量。批命令一次最多 100 项，仅提交 `{caseId,expectedVersion}`；服务端解析真实订货身份、稳定排序锁、校验 case/version/快照并在一个事务内处理。批量驳回使用一个明确、必填且最多 1000 字的共同原因；任一项冲突或失败，整批无业务事实。
- 主详情路由允许 `order view` 或 `finance_order_approval:view` 进入，但只有实时合格审核人且该订单仍有精确 PENDING case 才能穿透 owner；不放宽订单列表、编辑、完整委外履约进度或商业扩展权限。

## 七、增补（V328 / 2026-08-30）：动作分权、撤权即时生效与旧单笔入口停用

- 本 ADR §2–§4 的 `finance_order_approval:review` 描述是 V229 历史决策。V328 已将该复合码标记为 inactive、不可配置，并把迁移前既有授权保真展开为 `finance_order_approval:approve` 与 `finance_order_approval:reject`；旧码不得作为现行门禁。
- `finance_order_approval:view` 只允许查看共享任务；批准与驳回分别要求对应动作码，二者不可互替。送审前必须至少存在一名实时合格的批准人，只有 reject 人员时失败关闭，不创建无人可批的任务。
- 财务部门树内人员或跨部门个人点名人员仍须在职、账号启用且拥有当前动作。跨部门点名只认 `user_permission_overrides.active=true AND effect='grant'` 且权限本身 active；撤权墓碑、inactive 旧权限和超管聚合权限都不能复活点名资格。
- 采购/委外业务详情的 PENDING 投影不返回 `APPROVE/REJECT`，正式 Flutter 业务仓库也不再暴露单笔决定方法；详情只展示等待状态及提交/重提能力。
- 历史 `POST /api/purchase|subcontract/orders/{id}/approve|reject` 映射过渡保留但无条件返回 `CONFLICT`，提示前往财务任务中心，绝不写业务。它们旧有的 `orderId+version` 协议未绑定 case，不能继续使用。
- 唯一可写协议是财务任务中心的 `batch-approve/batch-reject`；选择一笔同样提交单元素批命令 `{caseId,expectedVersion}`。任一 case、version、订单快照或资格不一致，整批回滚。

## 八、增补（2026-09-03）：双击落点改为财务专用审核详情页

- **问题**：任务中心双击明细直接跳共享的采购/委外订货单详情页——那是业务编辑视角（含 owner 穿透、业务状态机语境），财务要决策还得退回任务中心列表才能批量操作；审阅语境与业务语境仍然混在一起。
- **决策**：新增财务专用审核详情页 `/finance/procurement-approvals/:caseId`（按审批 case 定位）。任务中心双击与行菜单主入口「打开审核详情」进本页；右键菜单保留「查看原订货单详情」作为次要入口。页面结构对齐销售订单财务审核页（V300）范式：状态条（单号+类型+轮次+下一步说明）→ 供应商财务快照卡（应付余额本币 AP 未结合计 / 本单金额原币 / 折合本币 / 税率）→ 订单信息卡（币种加粗红色等商业事实）→ 订货明细表（含逐行申请来源单号）→ 审批历史卡（逐轮提交/驳回/通过与原因）→ 底部常驻 驳回（原因必填）/ 通过（选填备注）/ 返回。
- **接口**：`GET /api/finance/procurement-approvals/tasks/{caseId}/review` 只按 `finance_order_approval:view` 开放（与任务中心同面 `finance.order-approval`），投影审批 case 关联的订单头、明细、供应商应付快照与审批历史；不授予采购/委外业务 view/edit。`allowedActions` 仅对 PENDING case 按当前审核员实时资格返回，历史 case 只读无动作。
- **通过备注**：`batch-approve` 请求新增可选 `remark`（≤500 字，写进 APPROVED 事件快照留痕）；列表批量操作不填、单笔详情页选填，向后兼容。
- **不变量**：写路径不变——详情页的通过/驳回仍走单元素批命令 `{caseId,expectedVersion}`（version CAS + 快照哈希校验 + 实时资格），业务订货详情页依旧对任何账号不渲染审批按钮（§五）。任务中心批量按钮保留（多笔同办），详情页负责看清再判的单笔决策。
