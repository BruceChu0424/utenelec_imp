# V703 车间催计划记录（ADR-117）

## 背景

2026-09-24 用户反馈：物料分析准备页可以分批下单、追加下单，计划员有时只下了父件，下层子件忘了下；
车间那边只看到「缺料 · 等待到货」，分不清是「料已经订了在路上」还是「根本没人去订」，只能口头找计划。
ADR-117 在计划侧下单后查下层还缺的料并引导补下单；车间侧把「计划还没下单」单独标出来，并允许一键催计划。
本迁移只为车间催计划这件事新增一张协调状态表。

## 结构

- 新表 `production_planning_urges`：每行 = 一个车间任务(`execution_segment_id`)对一份物料分析
  (`material_analysis_id`)的催计划记录。`status` 为 `OPEN`(在催)/`RESOLVED`(已办结)；
  `urge_count` 催了几次；`gap_kind_count` / `gap_summary` 是最近一次催时「计划还没下单」的物料种数与点名
  (只是给计划员通知正文用的快照)；`first_urged_*` / `last_urged_*` 记谁、什么时候催的；
  `resolution` 为 `ARRANGED`(计划已下够单)/`TASK_CLOSED`(任务已完工 / 取消)。
- 形状约束：在催行 `resolved_at` / `resolution` 必须为空，办结行必须都有；`last_urged_at >= first_urged_at`；
  次数、种数 ≥ 1；点名与催办人姓名长度受限。
- 部分唯一索引 `uq_production_planning_urge_open_segment`：一个车间任务同一时刻最多一条在催记录，
  并发两次点击落到同一行(服务端 `ON CONFLICT ... WHERE status = 'OPEN' DO NOTHING` 后转为「再催」分支)。
- 另建按任务、按分析、按在催时间三个索引，分别服务车间任务列表、计划侧提示与徽章、核对任务扫描。

## 登记

- 审计三清单：`NONE / data_change`，归 queue 组(`AuditTriggerCoverageMigrationContractTest`)——协调提醒不挂行级审计，
  发起人与时间在行内，人的操作由请求级语义事件记录。
- 清库策略：`CLEAR`(与所指的车间任务、物料分析同属业务流程数据)。ops 脚本 `server/ops/reset_business_data.sql`
  与数据库孪生函数 `business_data_reset()` 同时登记；孪生函数按 V686 起的锚点补丁法改写，锚点缺失即失败。
  清库清空表数 311 → 312(`BusinessDataResetServicePostgresTest`)，脚本白名单 412 / CLEAR 312。
- 迁移头 V703 / 632：本目录 README 头行、ops 白名单与异常文案、清库契约测试同步。
- 后台核对任务 `ProductionPlanningUrgeReconciler.reconcile` 登记到服务器状态页任务目录(「车间催计划核对」)。

## 兼容与数据

- 只建表、索引与清库/审计登记，不回填、不改任何已有数据，不改任何需求、预留、库存或单据数量；已应用迁移不改字节。
- 旧应用连接 V703 库不受影响(新表只被新代码读写)；新代码在没有任何催办记录时行为与 V702 一致，
  车间任务列表只多出「计划还没下单」的只读事实。

## 验证

- 本地 PostgreSQL(项目 Flyway)从空库迁到 V703 成功；`WorkshopPlanningUrgeEndToEndTest` 6 例在真库上覆盖：
  计划没下单 → 车间看到缺口并催 → 计划员收到待办卡 → 30 分钟内再催不再打扰 → 计划补下单后核对办结并撤卡；
  任务取消后办结；不在本车间范围的人不能催；计划部门以外的人收不到卡。
- 清库真库用例、审计覆盖契约、ops 脚本契约同步通过。真库全链以 GitHub CI 为准。
