# V594 日报审核补链放行

> 2026-09-15 · 事故：生产日报登记了实际用料后点「审核」直接 500。用户本地实证（audit + 堆栈）：`ProductionDailyReportMaterialWriteAdapter.stampDailyReport` 的 `UPDATE production_material_settlement_events SET daily_report_id = …` 被 `fn_reject_production_material_ledger_mutation`（V161 只增不改守卫）以 55000 拒绝，整笔审核事务回滚。

## 根因

V583 把「实际用料」并进报工页时，审核链路设计为**同一事务**两步：

1. `ProductionMaterialSettlementService.post()` INSERT 结算事件行（`daily_report_id` 为 NULL）；
2. `stampDailyReport()` UPDATE 回填该列——红冲时按 `daily_report_id` 反查整单冲销、对账也靠它。

V161 的守卫函数对四张 ledger 表（stock_events / stock_postings / settlement_events / settlement_postings）的一切 UPDATE/DELETE 无差别 RAISE，第 2 步必然炸。测试为何没拦住：守卫的 Postgres 行为测试只断言「拒改拒删」，没有任何用例走「审核带实际用料」的放行路径（E2E 未登记实耗行）。

## 修复（只 CREATE OR REPLACE 守卫函数，不加表、不改任何既有行）

**唯一放行形态**：UPDATE 仅当

- `daily_report_id` 从 NULL 首次回填为非空；
- 其余列逐列不变（`to_jsonb(行) - 'daily_report_id'` 整行 `IS NOT DISTINCT FROM` 比较，未来加列自动纳入约束）。

这是给同事务内**刚插入**的事件行补来源，不改写任何已过账事实。以下仍然全拒：

- DELETE；
- 已回填的来源再改挂别的日报、或清空回填；
- 借补链顺带改其它列（如 reason）；
- 另外三张没有该列的 ledger 表的一切 UPDATE/DELETE（`to_jsonb(NEW) ? 'daily_report_id'` 键存在性判断自然落入拒绝分支）。

## 验证

- 本地真库事务内造数实测六用例：首次回填=UPDATE 1；改挂/清空/顺带篡改/DELETE=55000；回填持久（ROLLBACK 零残留）。用户正在跑的后端无需重启即生效（函数已替换）。
- `ProductionMaterialAppendOnlyLedgerPostgresTest` 扩展同款断言进 CI：既有「拒改拒删」断言原样保留作回归锁（`set created_at = created_at` 这类无实际变化的 UPDATE 也仍然拒绝，与 V161 行为一致）。
