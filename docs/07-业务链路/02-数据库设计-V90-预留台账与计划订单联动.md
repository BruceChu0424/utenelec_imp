## 一、设计决策与理由

### 1. 预留为什么是独立台账，而不是在 stock_balances 上加一列

| 方案 | 否决理由 |
|---|---|
| `stock_balances.reserved_qty` 汇总列 | 只存总数，不知道"这批预留是谁的"，无法支撑：按订单行回写可发货量、驳回时精确释放、订单详情页展示预留构成；且违反"流水可重放"原则，对不上账时无法溯源 |
| 挂在 sales_order_items 上一个数 | 只有订单视角，没有仓库/货品视角，算不出"这个仓这个货还剩多少可卖" |

独立台账 `stock_reservations` 一行 = 一笔预留（谁订的、什么货、哪个仓、多少、消耗/释放了多少），两个视角都能从它聚合，且每笔变化可审计。

### 2. 消耗与释放为什么分两列（consumed_qty / released_qty）

预留的离场只有两条路：**发了货**（消耗，使命达成）和**不要了**（释放，改量/取消/驳回）。分开记才能回答"这单是发了还是退了"，审计和报表都要这个区分。生效量恒为 `qty − consumed − released`，CHECK 约束保证不超。

### 3. warehouse_id 为什么允许 NULL（全局预留）

下单审核时销售还没决定从哪个仓出货，但此时就必须占用 ATP 防超卖。NULL = 全局订单有效预留。销售全局 ATP 由 Service 计算“各有货仓分别 `GREATEST(余额−安全库存,0)` 的合计，再扣全局/仓级生效预留”，因此安全库存按仓保护、每笔全局预留只扣一次。创建发货单/进入发运窗口只校验具体仓；实际交接时把**本次消耗量**拆成仓级已消费行，未发余量继续保持 NULL 全局承诺。该列应继续允许 NULL；若审核即定仓或部分发货时整行改绑首仓，会把远期承诺过早锁仓并阻断其他仓履约。

### 4. 数量为什么一律基本单位

`stock_balances.qty` / `stock_movements.qty` 都是基本单位量（已乘 unit_rate）。预留要直接和余额相减，必须同口径，换算在创建预留时一次完成。订单行上的 `reserved_qty/planned_qty/produced_qty` 则沿用行单位（和 qty/shipped_qty 同族），两侧换算由 Service 负责，互不混淆。

### 5. 合并生产为什么用新表而不是复用 sales_order_item_id

`production_plan_items.sales_order_item_id` 是老库单值软关联（一个计划行只挂一个订单），表达不了"两个订单的同产品合并到一张计划单"。新表 `plan_order_item_links` 多对多，还顺带承载三量回写（allocated/produced/inbound）和补产标记。老字段保留只做迁移溯源，新业务一律走新表。

### 6. chain_status 为什么是派生列而不是状态机表

行状态完全由四个数量（qty / reserved / planned / produced / shipped）推导，独立状态机会与数量漂移。存派生列只为列表筛选和工作台置顶排序（索引 `idx_soi_chain`），Service 在每次数量回写后重算，权威来源永远是数量本身。

## 二、表结构速览

### stock_reservations（订单有效预留 / 生产物料占用台账）

| 列 | 类型 | 说明 |
|---|---|---|
| order_item_id | UUID | → sales_order_items.id（跨模块逻辑 FK，契约 §一不建 REFERENCES） |
| goods_id / color_id / warehouse_id | UUID | 主档真 FK；warehouse NULL = 全局预留 |
| qty | NUMERIC(18,4) | 预留量（基本单位），CHECK > 0 |
| consumed_qty | NUMERIC(18,4) | 已转出库消耗 |
| released_qty | NUMERIC(18,4) | 已释放（改量/取消/驳回） |
| status | SMALLINT | 0 生效 / 1 已完结（Service 派生） |
| source | SMALLINT | 0 下单现货 / 1 生产入库 |
| source_doc_type / source_doc_id | — | 产生预留的单据溯源 |

### plan_order_item_links（计划明细 × 订单明细，多对多）

| 列 | 说明 |
|---|---|
| plan_item_id | → production_plan_items.id（同模块真 FK） |
| order_item_id | → sales_order_items.id（逻辑 FK） |
| allocated_qty | 排产分摊量（行单位） |
| produced_qty / inbound_qty | 报工 / 入库回写 |
| source | 0 正常排产 / 1 补产 |

幂等：`uq_pol_pair` 部分唯一索引（未删除行 计划行×订单行 唯一），同 V87/V88 防重复规则。

### sales_order_items 新增 4 列

`reserved_qty`（可发货量）· `planned_qty`（已排产）· `produced_qty`（已完工入库）· `chain_status`（0 未启动/1 部分预留/2 待排产/3 待物料/4 已排产/5 生产中/6 部分完工/7 可发货/8 部分发货/9 已发货/-1 已取消）

### v_stock_available 与销售全局 ATP

`v_stock_available.available_qty = on_hand_qty − Σ生效预留`，仓+货+色粒度，供仓级库存/生产读取。V298 起「生效预留」还包括 `PREPLAN_ANALYSIS` 归属预留（分析来源备料入库绑定，[ADR-039](../99-决策记录-ADR/ADR-039-计划前物料分析备料库存绑定.md)）：公共现货口径无需改视图即自动剔除，归属分析侧由服务层加回本分析绑定量。销售下单是跨仓承诺，权威入口为 `StockReservationRepository.globalAvailableBase`：`Σ GREATEST(各仓余额−goods.min_qty,0)−Σ生效预留`，整体再钳为非负。出货开始拣货则按指定仓校验在手、安全库存、其它仓级预留和已开始任务；不得把三种口径互相替代或重复扣减。

### V187 向前覆盖：订单发运策略与仓库作业事实

V187 不改写 V90 预留事实，只在两张既有表增加控制字段：

| 表 | 新增权威字段 | 规则 |
|---|---|---|
| `sales_orders` | `shipment_policy`、`partial_shipment_confirmed_at/by/reason` | 新单默认 `CUSTOMER_CONFIRM`；历史行为写 `LEGACY_UNSPECIFIED`，不回填伪造客户确认。改量、取消、订单红冲清空确认 |
| `sales_shipments` | `warehouse_work_status`、作业人/时间、异常原因 | 新单 `PENDING_PICK → PICKING → PICKED → SHIPPED`；`EXCEPTION → PENDING_PICK` 必须说明退拣/处理原因；历史草稿写 `LEGACY_PENDING` 且 V443 起只读，不伪造拣货事实也不再直接审核出库 |

新流程数量边界：

1. 出货草稿每行必须关联销售订单行；无订单零星出库走“其它出货”。
2. 草稿只占订单行可发额度，防两张任务重复分配同一预留；此时不新增预留、不扣库存。
3. 开始拣货才校验指定仓的在手、安全库存、其它订单有效预留和已开始任务；V443 起月结、现金、定金客户都必须先完成逐张财务发货审核，未分类客户不得放行。
4. 只有 `PICKED` 可交接。交接事务内消费 V90 预留、扣库存、回写已发/结案，并以该次 `SHIPPED` 上海业务日建立唯一正式 AR、起算到期日；任一步失败整体回滚。未转销客户预收不得净掉正式 AR。
5. 已开始/异常任务不得直接编辑、删除、驳回、让单、改订单量、取消订单或撤销客户确认；先登记异常并完成有原因的退拣恢复。
6. 所有 `SHIPPED` 都禁止普通红冲把货直接加回在库，包括历史缺 `handed_over_at` 的行；缺时间只代表交接证据未知，纠错必须走销售退货/质量冻结。

应用层同时收紧商业事实：销售订单行只形成 `amount_original=qty×price×discount`，不在订单阶段生成 `exchange_rate` 或 `amount_local` 新事实；新建/批量出货从来源订单头/行重取客户、币种、税率、付款方式、销售员、价格、折扣、单位换算及本次原币金额，并按发货数量比例计额，`SHIPPED` 才锁定财务汇率、计算发运本币并形成 AR。不兼容条件不合单；客户端汇率、本币金额或成本字段不是会计事实。财务已审核出货必须先反审才能编辑、删除或驳回；无价格权调用方由服务端清空商业字段。折扣/税额最终结算和多次分批舍入尾差仍需完整 condition/invoice 引擎。

### V188/V189 向前证据账

- `sales_shipment_warehouse_events`：每次创建、仓库状态转换、异常/恢复、驳回、受控反向都追加前态、后态、原因、操作者和时间；数据库拒绝 UPDATE/DELETE。V187 字段是当前投影，V188 是不可变时间线。
- `sales_return_quality_items`：新销售退货审核后进入质量冻结，不属于 `stock_balances`；`sales_return_quality_events` 记录 `RECEIVED/GOOD_RELEASE/SCRAP/REWORK/RECEIPT_REVERSED`，同样不可改删。只有 `GOOD_RELEASE` 增加可售库存。
- V189 不回填历史已审核退货；没有质量行的旧退货保留既有反向路径，不能凭脚本补造过去的检验结论。
- 任一 `GOOD_RELEASE/SCRAP/REWORK` 发生后，原退货整单红冲会 fail-closed；当前尚无处置级受控纠错/补偿事件命令，误判不能 UPDATE/DELETE 事件，只能停下调查。双人复核或追加式补偿命令是上线门禁。
- V190 随后重跑公开业务表审计完整 sweep，确保 V188/V189 新表也处于“恰有一个合法审计触发器”的 fail-closed 规则下；它只记录迁移后的新操作，不补历史。

上述仍是“单据级最小仓库状态 + 销售退货最小冻结”，不是完整 WMS/QMS：未建库位、批次/序列号、实拣数量、复核、装箱、物流件级台账、检验项目和返工工单。

## 四、自检清单（Service 实现后跑）

1. 两并发审核同货各要 80/全局 ATP 100 → 一过一绝，可用量不为负；两仓各 50、安全库存各 10 时全局 ATP 应为 80，不是 90。
2. 审核→仓库交接→尝试普通反审出货必须失败；销售退货审核只进冻结并重开替换需求，不直接加预留，良品释放后库存才增加。
3. 合并生产（2 订单 × 同货）→ 拆单出货 × 2，两订单行 reserved/shipped 各自正确。
4. 报 150 合格 120 → 补产 links(source=1) 生成、订单行 produced=120、chain_status=6。
5. 驳回出货单 → 预留释放量 = 驳回量，可用量回升，订单行回 7→4/6。
6. 全局预留（NULL 仓）只在全局 ATP 扣一次；部分从 A 仓交接后，本次消耗段绑定 A 仓，剩余有效预留仍为 NULL，可由 B 仓继续履约。
7. 两个不同订单头同时预留同 goods+color 时，第二事务必须在资源锁后重读已提交预留；不能因各自
   头锁互不冲突而双双通过。
8. 两个销售员并发为同一订单行建出货草稿，总草稿量不得超过该行 `reserved_qty`。
9. 新出货单混入无 `order_item_id` 行、跳过 `PICKING/PICKED`、客户未分类、或任一客户未财务审核即开始拣货，均须由服务端拒绝。
10. 开始拣货后，订单改量/取消/让单、客户确认撤销、财务反审和出货编辑/删除均须失败；异常退拣恢复后才能继续。
11. 已记录物流交接的新流程出货调用普通红冲必须失败，不能凭红冲制造在库数量。
12. 历史 `SHIPPED` 即使 `handed_over_at=NULL` 也必须拒绝普通红冲；`LEGACY_PENDING` 旧草稿同样只读，旧审核、财审和仓库动作都必须失败并提示重建。
13. V90 历史未激活订单新建 V187 出货必须提前失败；逐行对账并显式激活前不得批量造预留。
14. 财务已审出货的编辑、删除、驳回均失败；无价格权限的列表/详情商业字段为空。
15. V188/V189 事件 UPDATE/DELETE 被数据库拒绝；新退货只有 `GOOD_RELEASE` 产生库存流水。
