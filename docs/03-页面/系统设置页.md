# 系统设置页

> 运行时可配的**安全/业务策略阈值**（超级管理员 `authorization:manage`，且后端校验 `principal.superAdmin`）。改设置**立即生效**（不缓存），保存需**二次密码确认**。
>
> 位置：`lib/features/admin/pages/admin_system_settings_page.dart`
> 后端：`server/.../features/admin/systemsetting/`（`SystemSetting` entity/repo + `SystemSettingsService` + `SystemSettingController`）+ `V72__system_settings.sql`（建表 + 11 项种子）。
> **安全规范**：[../05-架构/安全策略.md §10.2](../05-架构/安全策略.md)（强制，新增高危配置功能照此）

---

## 入口

工作台 → 系统管理 →「系统设置」卡片。路由 `/admin/system-settings`，授权管理入口要求
`authorization:manage`；后端 Controller 与 Service 还必须确认当前主体仍是超级管理员——**普通用户连入口卡片都看不到**。

---

## 可配项（4 类 12 项；默认值同 application.yml / V73·V75）

| 分组 | 设置项 | 默认 | 影响 |
|---|---|---|---|
| 安全策略 | 登录主体限流 / 锁定阈值 / 锁定时长 / 密码历史 / 导出限流 / **会话空闲超时** | 5/分·账号或手机号 · 5次 · 15分 · 5个 · 10/分·用户 · **30分** | `LoginRateLimiter`/`LoginService`/`PasswordService`/`ExportRateLimiter`/前端 `IdleTimeoutGuard` |
| 登录令牌 | 登录令牌有效期(access TTL) / 登录保持时长(refresh TTL) | 源码回退 **15 分钟** · 7 天；运行值必须查目标库 | `JwtService` / `RefreshTokenService`×2（access 最小 5 分，防登录即过期） |
| 短信验证 | 验证码 TTL / 发送间隔 / 每日上限 | 5分 · 60秒 · 10条 | `VisitorSmsService` |
| 业务限制 | 导出行数上限 | 100000 | 6 处 `*ReportService.paginateAll` |

> access TTL 曾在 V74 被删，V75 重新开放并曾以 480 分钟铺底。**该历史铺底不能作为当前安全基线**：
> `application.yml` 与 `JwtService.readLong(..., 15)` 的源码回退值都是 15 分钟，但目标库
> `system_settings.jwt_access_ttl_minutes` 会覆盖它。V133 仅把仍等于旧默认 480 的设置收敛为 15，
> 明确自定义值不会被覆盖。部署/审计必须查询目标库实际值并由安全负责人批准；
> 不得在文档中笼统宣称“默认 8 小时”。refresh TTL（V74 改名「登录保持时长」）与会话空闲超时
> （V73 加，V74 改名「自动退出登录」）仍独立存在。
> V135 的权限版本不匹配会让旧 staff access 在下一请求立即 401，与令牌自然 TTL 也是独立机制。

**不含**（绝不入配置页）：密钥类（jwt.secret / crypto / sms AK——涉密钥/轮换）、部署类（CORS / swagger / DB / legacy——启动时定）。这些走 `.env` / 环境变量 / Vault。

## 安全（五道防线，强制规范）

1. **路由守卫** `/admin/` 仅超管 → 普通用户看不到入口。
2. **`@PreAuthorize("hasAuthority('authorization:manage') and principal.superAdmin")`** Controller/Service 双层校验。
3. **二次密码确认**：`SystemSettingsService.write` 用 `PasswordEncoder` 校验当前账号密码——即使 access token 被盗，改策略还需密码（防令牌泄露篡改安全策略）。
4. **审计**：`update_system_setting`（谁/哪项/旧→新值），审计页可查。
5. **类型 + 非负校验**：后端权威 + 前端提示。

## UI（精心设计）

按 4 类分组卡片（安全策略/登录令牌/短信验证/业务限制）+ 改动跟踪（dirty 项高亮 primaryContainer）+ 底部「保存改动(N)」+ 二次密码弹框（含危险操作警告）+ 顶部警告横幅（影响全员提示）+ 每项显示说明 + 上次修改时间。

## 改设置如何立即生效

`SystemSettingsService.readInt/readLong` **不缓存**，每次 `findById`（表仅 11 行 PK 查询亚毫秒）。各安全组件动态读取（替代硬编码 `*Properties`）：
- `LoginRateLimiter`/`ExportRateLimiter`：令牌桶阈值动态，变更后下次 check 检测到新值重建桶。
- `LoginService`（lockout 阈值/时长）、`PasswordService`（密码历史）、`JwtService`（access TTL）、`RefreshToken`×2、`VisitorSmsService`（短信 3 项）、6 处导出上限。

详见 [ADR-013](../99-决策记录-ADR/ADR-013-系统设置与安全策略可视化.md)。

## 会话空闲超时 vs 登录令牌有效期（两套独立机制，别混淆）

「自动退出登录（会话空闲超时）」和「登录令牌有效期（access TTL）」是**两层独立、叠加**的会话保护，作用层不同：

| | 登录令牌有效期（access TTL） | 自动退出登录（会话空闲超时） |
|---|---|---|
| 层 | 后端 + 网络层（令牌本身） | 前端行为层（人有没有在操作） |
| 计时对象 | 令牌多久过期 | 用户多久没操作 |
| 基线/运行值 | 源码回退 15 分；目标库可调（最小 5），上线前必须核验实际值 | 30 分（可调） |
| 到期行为 | 前端用 refresh 静默换新令牌（**用户无感**）；refresh 也过期（7 天）才需重输密码 | 前端弹窗「您已 N 分钟没有使用…」→ 登出 |
| 防的是 | 令牌被窃后可滥用多久 | 用户离开但系统还开着，别人趁机操作 |

- **一直操作**：access 到期前端自动续期（无感），idle 因有操作不计时——**两层都不打扰**。
- **离开 30 分钟**：idle 弹窗登出（即使令牌还没到期）。
- **离开 7 天**：refresh 过期，需重新输密码。

> 关键修复（2026-07-27）：access 过期时后端必须返 **401**（`SecurityConfig` 配 `AuthenticationEntryPoint`），前端 `AuthInterceptor` 才会自动 refresh；若返 403 会被误判成「无权限」、需重登才恢复。详见 [ADR-014](../99-决策记录-ADR/ADR-014-会话超时与token刷新机制修复.md)。

### 改了阈值何时生效

- **「自动退出登录」**：前端 `IdleTimeoutGuard` 三管齐下保证实时生效——① 进系统拉一次；② 每 5 分钟轮询（别处改了最迟 5 分钟生效）；③ 超管在本页保存后自增 `idleThresholdVersionProvider` 信号 → **立即重拉**（当前会话即时生效，不必重登）。
- **「登录令牌有效期」**：只影响**之后签发**的令牌（已签发令牌按旧 TTL 到期）；用户下次 access 到期、前端自动 refresh 时拿到新 TTL。无需重登。
