# ADR-020：入职工号、岗位与管理中心用人语义

> 日期：2026-08-03 · 状态：已实施，待运行时冒烟与生产发布验收
> 本 ADR 修订 [ADR-010](ADR-010-组织岗位模型与统一部门选择器.md) 中“管理中心不挂人、不设负责人/岗位”的旧决策；结构不可移动与能否承载人员是两个独立维度。

## 背景与问题

1. 入职工号由页面预取或沿用旧值，提交时后端又信任非空 `code`，会把已经使用的 `UT0001` 当作显式工号再写入，最终返回 409。
2. 岗位被默认成“普通职员”，页面又同时展示辅助小字，造成无意义的预填和字段高度不一。旧组合框只保留名称，无法稳定区分“选中已有岗位”和“创建自定义岗位”。
3. 历史模型把管理中心同时当成“不可移动的结构节点”和“不能用人的空骨架”。实际业务中，研发/制造等中心有自己的领导与直属员工，中心负责人还需要管理下属部门。

## 决策

### 1. 工号只能由服务端分配

- `POST /api/org/employees` 不再把请求中的 `code` 当作写入依据；旧客户端即使传入也会被忽略。
- 后端在入职事务内通过 `MasterCodeService` 分配 `UT` 工号，数据库唯一约束是最终竞态防线。
- V206 以当前未删除与历史员工工号的最大数字后缀校准主数据序列，不修改任何已有工号。
- 前端不预生成、不缓存、不显式提交工号；成功后以服务端返回值为准。

### 2. 复用 `positions` 作为部门岗位目录

不新建第二张“所有职位”表。当前 `positions` 已有编码、名称、所属组织、职级、排序和软删除语义，足以承担本阶段的“部门岗位字典”：

- 入职页岗位默认为空，不再显示“默认普通职员”或辅助小字，岗位仍为可选字段。
- 点击字段时展示当前组织的全部有效岗位；输入名称、编码或职级任意字符即时筛选。
- 弹层内点选只更改草稿；只有点击底部“确定”才回填，取消、点遮罩或返回不改表单。
- 若文本与已有岗位匹配，提交已有 `positionId`；若无匹配，提交规范化后的自定义名称。后端按“组织 + 不区分大小写名称”加锁后复用或创建，避免并发重复；新岗位职级为中性的“员工”。
- 岗位名称和 `level` 只用于分类、展示和排序，不产生任何管理或授权。

大型 HCM 通常还会分离全公司的 Job（标准职能）、Position（定编席位）、Assignment（人员任职）和 Business Title（对外职称）。当前系统的 `positions` 仍是轻量的“部门岗位目录”，不假装已经实现定编、缺编、代岗或多任职。该边界与 [Microsoft Dynamics 365 的部门/Job/Position 划分](https://learn.microsoft.com/en-us/dynamics365/human-resources/hr-personnel-departments-jobs-positions) 和 [Oracle HCM 的 Job/Position 结构](https://docs.oracle.com/en/cloud/saas/human-resources/fawhr/job-and-position-structures.html) 一致；未来可以在不破坏员工历史任职的前提下独立演进。

### 3. 管理中心可用人，但仍是结构锁定节点

| 组织类型 | 可直属挂人/岗位 | 可设负责人 | 可在通用编辑中移动 |
|---|---:|---:|---:|
| 公司、历史决策层 | 否 | 否 | 否 |
| 管理中心 | 是 | 是 | 否 |
| 一级部门/二级班组/三级科室 | 是 | 是 | 是（受防环和层级规则约束） |

- 从部门管理的中心或部门点“添加员工”，路由预填完整组织选择对象；从全局入职入口进入时保持为空。
- 管理中心可维护直属岗位、直属员工和负责人。负责人必须是该中心直属且在册员工，不允许指向子部门或离职员工。
- 管理中心的上级位置仍只读，不因“可挂人”而放开组织树基线移动。
- 通用员工/部门选择器可选管理中心；车间、班组等专用业务选择器继续使用更窄的节点策略，不会因全局放开而把管理中心当作生产车间。

### 4. 负责人是唯一管理事实，不从职位名称推导

- `departments.manager_id` 是当前组织负责人的唯一事实来源。“总监”“中心主任”“领导层”等名称都不自动授权。
- 普通部门负责人继续只能管理本部门直属员工；管理中心负责人在“我的部门”可选中心本身或子孙部门，每次仅查看/管理所选节点的直属员工。
- 成员权限转授上限仍是“负责人本人有效权限 − 全员基线”，中心层级不会自动产生 `employee:create`、`employee:edit` 或系统管理权限。
- 后端对每个目标部门递归校验负责范围；前端隐藏按钮不能代替对象级授权。

## 不变量和边界

- 选择一个岗位必须校验它未删除且属于目标组织；入职、编辑和调岗共用该后端规则。
- 同组织历史重名岗位不在 V206 中冒险合并；查找必须确定性取一，后续经人工确认后再单独治理。
- 不回写历史任职事件，不修改已有员工工号，不通过岗位名称补猜负责人。
- V206 是新增迁移；已应用的历史 Flyway 文件不做原地改写。

## 验收

1. 连续入职不传工号，以及模拟旧客户端传入已存在工号，都由服务端生成新工号。
2. 未选部门时不可选岗位；选部门后可搜索已有岗位、选自定义岗位、取消不回填、确定才回填。
3. 从部门或管理中心点“添加员工”时正确预填完整名称/路径，选择弹层可响应，确定后才改表单。
4. 中心可添加直属员工/岗位/负责人，但无法移动中心本身；中心负责人能管理子部门，普通部门负责人不能越界。
5. 各表单字段使用一致的标签、内边距和至少 44dp 点按高度；提交中防重复，失败保留表单并给出可见错误。

## 发布边界

源码、迁移契约和本地回滚演练通过不等于生产已就绪。只有 V206 在目标库成功应用、后端实例重启为新代码、真实权限组合与并发入职 E2E 通过，且日志/审计无敏感数据泄露后，才可发布。
