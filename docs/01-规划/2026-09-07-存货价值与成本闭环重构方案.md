# 存货价值与成本闭环重构方案

- 日期：2026-09-07。
- 状态：计价原则与核心方向已确认；V500独立价值核心及V506受控开账/历史余额隔离已形成源码候选，普通业务完整接线仍在进行。用户最新已选“实际单据/银行原额+精确分摊/保留剩余”；下文早期4位累计金额机制须依[精度分界与升级复核](../99-项目治理/2026-09-07-库存成本账内精度与精确份额复核.md)前向升级，不能把软件量化余数算作损益。详见[核心迁移与接入合同](../数据迁移/116-V500实际平均库存价值核心.md)、[V506开账边界](../数据迁移/122-V506受控库存开账与历史余额待核对.md)。
- 本包保留 StockService 的唯一数量所有权；没有修改采购、销售、生产、委外或 GL 调用方，不能据此宣称全链成本已经闭环。
- 已定：同仓库、同货品、同颜色按实际平均成本出库；成品承接实际材料投入与已确认加工费；后补费用追加调整，不改旧账。

## 1. 已有规则与本次决定

依据：[ADR-055](../99-决策记录-ADR/ADR-055-即时库存台账金额与货品成本完整性.md)、[成本核算43](../数据迁移/43-成本核算.md)、[ADR-047](../99-决策记录-ADR/ADR-047-采购委外应付月结与超耗责任分层.md)、[委外全链路](../07-业务链路/08-委外全链路-订货出仓回仓重设计.md)、[生产需求§8.8](../07-业务链路/04-生产订单排产与执行全链路需求.md)。

| 项目 | 确定规则 |
|---|---|
| 库存价值 | 只认存货价值事实及其台账投影，不能用 `goods.c_total × qty` 填平。保留唯一的物理数量账。 |
| 出库计价 | 用户已选择：`warehouse_id + goods_id + color_id` 库存池实际移动平均。颜色空值作为同一明确维度处理。 |
| 自制成本 | 承接实际材料价值与已确认加工费。没有来源的标准预算、预设零值不成为实际成本。 |
| 正常损耗 | ADR-047 §5、委外链路第148行已定义：正常允许损耗留在合格产出成本。不得再次要求用户选择。 |
| 超耗及追回 | 超耗先记独立异常损失，赔偿追回另行入账，不净掉原损失。缺少正数发料账面成本时，继续保留超耗审核的失败关闭约束。 |
| 实耗 | 生产需求§8.8第939行已定义：责任人确认实耗、正常损耗、报废、在制；不能把领用减退回默认为消耗。领料价值是可归集投入上限，不等于已确认全部消耗。 |
| 分批生产 | 可分批入库及发货。未完成成本归集不阻止正常实物流转；金额未证时显示待成本，不冒充合法零成本。 |
| 后补 | 追加价值调整；在库份额进入库存，已售份额进入销售成本，未产及合法在制份额留在 WIP，不给零数量库存留下残值。 |
| 历史与期间 | 不重写历史数量、换算率、流水、已确认凭证。按既有期间守卫和前向修复治理处理，不把旧期重开或普通跨期红冲作为绕过路径。 |

库存计价方法和归集维度已定。本轮实现评审决定：生产暂计分母采用同一执行段当前已批准的有效目标产量，统一换成该产出货品的基本单位；不跨产品或执行段混用。该规则不改变上表实耗和损耗原则。首版成本源限实际材料与已确认加工费，其它费用只有明确的后续批准成本范围和来源分配，才可进入本机制。

## 2. A/B/E 实际反例

主验收在隔离环境报告的结果：生产20件A，投入B材料价值400、E材料价值200，A销售金额2000。全部出库后：

| 货品 | 当前数量 | 当前库存台账金额 |
|---|---:|---:|
| A | 0 | -2000 |
| B | 0 | 400 |
| E | 0 | 200 |

这与下列代码一致：自动领料行没有金额，领料减数量不转价值；自动成品行没有金额；销售出库却以销售金额扣库存。不是更换页面显示公式能解决的问题。

在无其它费用、退回或损失的前提下，未来必须满足：A/B/E库存数量和价值全部为0，在制为0，销售成本600，销售收入仍是2000。不能直接给现有余额补一个净额来制造此结果；必须分别核对原库存事实和GL，再生成有依据的前向调整。

## 4. 可复用的 UUID 与必须补齐的关系

| 范围 | 可复用关系 | 缺少的价值关系 |
|---|---|---|
| 采购/IQC | 订单行→收货行→inspection item→PASS event→stock-in batch item→stock movement | 扩展取得成本的来源、成本状态及后补调整，而非重建收货链。 |
| 生产材料 | planning package document item→demand/reservation→material stock event/posting→stock document item；反向有source posting | 每次确切movement→数量posting→价值位置的分配。 |
| 生产产出 | execution segment、plan item、daily report item、FQC decision、release command/allocation、FG stock item、warehouse confirmation/residual item | 投入价值→对应产出批次的批准分配及后补关系。 |
| 销售/退货 | shipment item与其movement；return item.out_item_id；quality event→quality item→return item | 原COGS切片、已退份额、后补价值恢复；不能用return amount代替。 |
| 委外 | order item、冻结material plan item、发料/退料行、目标件出仓、回厂行与IQC | 每笔自有投入价值、加工费、返料、损耗、产出的独立转移。 |

来源边一律用 UUID，不按名称、编码、单号或接近的时间猜关联。相同SKU发出加工后回厂也应按不同事件/状态节点表达，不能按货品自身关联递归。

## 5. 核心设计：受限价值图，不建设通用图引擎

### 5.1 为什么不能只保存一个移动平均价

单独保留当前平均价能算眼前出库，却无法知道后来的费用有多少属于已售、在库、在制和退回部分。逐次扫描所有历史入库批次又不符合性能要求。

建议采用每个库存池的不可变状态节点与有界分配边：普通入库只连接前状态和本次取得成本，普通出库只把前状态拆成本次出库和剩余状态。每次数量动作增加常数个节点/边，不展开全部采购批次。只有后补费用、生产重分摊、价值冲销任务沿受影响关系处理。

这部分结构是精确后补的必要信息，不应省成当前单价。可简化之处是只实现库存合并、移动平均拆分、原成本退回、生产分摊四种节点规则；不做任意表达式引擎、通用图查询框架或逐采购批次FIFO明细。

### 5.2 V500 核心 schema 与后续扩展边界

| 结构 | 关键字段 | 权威/约束 |
|---|---|---|
| stock_value_pools | warehouse/goods/color 唯一键、`head_node_id`、ACTIVE/LEGACY_UNVERIFIED、历史余额证据 | 只存价值头及来源状态，不另存可独立修改的物理数量。实际数量仍读 stock_balances。 |
| stock_value_events | 来源事件/单据/明细UUID、版本、责任人、稳定发生时间、`request_hash/payload`、唯一来源/幂等键、`movement_id`、结果、原调整/反向UUID | 完整 INSERT 后不可改删。金额仅为本位币；商业原币和已审批金额容量继续由来源应用服务负责。 |
| stock_value_nodes | SOURCE/POOL/ISSUE_POSITION/RETURN_SOURCE、`pool_id`、`movement_id`、`quantity_basis`、累计区间、创建事件/金额、当前basis/revision/活动标记 | 身份及基数不可改。basis是分配计算依据，只有当前活动位置的 `owned_value_local` 贡献余额；历史basis不能重复相加为资产。 |
| stock_value_edges | parent/child、累计区间/分母、创建revision/金额、已应用revision/累计金额/待证贡献 | 每个父节点最多两条前向边；冻结比例不改。V500只实现合并、二分和原出库退回，不包含生产分配方案版本。 |
| stock_value_jobs | 原调整事件、源节点、剩余任务数、处理数、待分配金额、PENDING/APPLIED | 完成时必须任务数和待分配金额均为0。后台只做价值追加，不生成物理数量。 |
| stock_value_tasks | 原job、edge/revision唯一、目标累计金额/待证状态、顺序、应用差额/child revision | 不保存任意表达式；每次只处理一条边、至多发布两条子任务。已应用重放不重复写。 |
| stock_value_node_revisions | node/revision、event/task、前后金额/待证计数/最终标记 | 追加事实；节点投影修改必须有对应revision，不能直接改当前成本。 |
| stock_value_postings | event/task/node、INVENTORY/WIP/COGS/损失/在途/来源/过渡位置、带符号本币差额 | 事件/任务两端守恒；通过 node.movement_id 及 creation_event 精确联系原库存流水。金额流水原快照与后补posting不能重复汇总。 |

节点、边投影可按实际实现把小型状态列合并存储，但必须用数据库守卫区分不可变身份和可重建缓存，不能对外开放直接改金额。所有结构都属于存货价值子账及投影，不再建立另一套数量账。

实际索引包括：库存池唯一维度、唯一物理movement、两个来源/幂等唯一键、父/子边、活动owner、待处理task顺序、待完成job部分索引、posting事件及owner。普通动作不按历史取得批次计算当前平均。期间/GL、生产方案版本和已批准来源容量属于后续接入合同，不能把未实现的字段当作已受数据库保护。

字段约束必须落实为DDL/API合同：

- UUID为主键/关系；金额与基本数量沿现有 `NUMERIC(18,4)` 存储，revision为BIGINT、时间为TIMESTAMPTZ。分配分子/分母保存精确数量，不先截成6位比例再计价；除法直接按4位目标金额舍入。
- 每笔物理movement只有一个主价值锚点（movement UUID与锚点角色唯一）；池后继状态另用creation movement关联。业务行分给多个需求时，增加本次明确去向的分配边，不丢原movement。
- 普通单笔movement的读写为O(1)；一次业务请求有n个合法去向时为O(n)，n受批量上限约束。不能把“有界”写成遍历所有历史取得批次。
- 已确认posting金额非空；来源缺证时实际总成本保持未证，已确认组成部分可以累加，但不能把空成本转成“已核定0”。真正零成本必须有明确批准来源/理由，状态完成事件照常传播。
- 来源金额分配总额不得超过该批准来源的可分配额；stock/quantity anchor、goods/color及所属业务对象交叉校验。同币种本币价值才能相加，商业原币只按其币种保存和展示。
- 投影不得开放通用修改接口；每次变更必须能由event/posting/revision重放得到。实际金额为待证时API返回状态与已确认组成部分，不给旧UI一个伪装成完整实际均价的0。

### 5.3 StockService/应用接口边界

已实现的内部 [InventoryValuationPort](../../server/src/main/java/com/uten/imp/application/port/InventoryValuationPort.java) 使用少量record；业务适配方仍须提供服务端核定来源，出库接口根本不接收销售金额：

```text
receive(Receive(context, movementId, pool, qtyBase, expectedQtyBefore, knownCostLocal, costFinal))
issue(Issue(context, movementId, pool, qtyBase, expectedQtyBefore, destinationKind, destinationId))
returnIssue(ReturnIssue(context, movementId, pool, qtyBase, expectedQtyBefore, originalIssueNodeId))
  -> MovementValue(eventId, canonicalMovementId, valueNodeId, poolHeadId, knownValueLocal, state, replayed)

adjustSource(SourceAdjustment(context, sourceCostNodeId, deltaLocal, markFinal))
reverseAdjustment(context, originalAdjustmentEventId)
  -> AdjustmentValue(eventId, sourceCostNodeId, pendingTasks, replayed)

pendingWork(limit <= 100) -> taskId, rootEventId, actualTargetPoolKey
propagate(taskId) -> applied, replayed, waitingForPriorRevision, jobComplete
pool(poolKey) -> head, actualQty, knownValueLocal, FINAL/PENDING/LEGACY_UNVERIFIED, propagationPending
```

库存数量接口仍复用当前库存维度锁、可用量和反向约束；价值接口不绕过它们。采购、销售、生产、财务通过中立应用端口连接，不互相直接改对方余额。实际出库时取得本池价值，收入/AR仍使用销售金额权威。

每个写入口要求调用方已经在同一事务内持有共享 `InventoryMutationLock`，并由 `requireHeld` 校验；REQUIRES_NEW不能借用外层事务锁。库存数量方法须在写物理movement和修改余额前调用核心，之后以返回的 canonical movementId/knownValue 同事务写一次。重放返回原结果，调用方不得再写物理数量；候选movement UUID和锁内最新 expectedQtyBefore 不参与业务请求hash。

## 6. 移动平均与4位尾差算法

库存池键K在锁内读取 `Q`（基本数量）、`V`（截至本revision已确认价值）及head。

**入库**：取得数量q、确认成本c，新状态为 `Q+q, V+c`，前状态到新状态的价值携转比例为1，本次成本源到新状态比例为1。若成本尚未证实，仍记录数量与待成本来源；不能把c缺失宣告成已核定0。

**出库**：要求 `0 < x <= Q`。

```text
issueValue = x == Q ? V : round4(V × x / Q)
remainingValue = V - issueValue
remainingQty = Q - x
```

冻结分子x、分母Q和两条去向边。全出库时剩余价值严格为0；不靠额外清零补丁。多次业务出库仍按当时库存池移动平均，物理数量使用既有规则。

后补成本不是对每次差额单独乘一个四舍五入比例。节点累计金额从C变成C′后，对每条边计算目标累计金额，再减已应用累计值：

```text
targetIssue = x == Q ? C′ : round4(C′ × x / Q)
targetRemain = C′ - targetIssue
edgeDelta = targetCumulativeAmount - alreadyAppliedCumulativeAmount
```

这样多笔微小费用与反向不会逐次丢尾差。生产N个分配对象按固定行序使用累计区间：`round4(C×prefix_after/D) - round4(C×prefix_before/D)`，最后一个剩余对象吸收精确尾差。分母是同一明确计量/分摊基数，不能相加不同材料单位。

**关键数例**：原库存10个/100，新到10个的成本待确认；出10个时已确认部分分配50，另50仍在库，两端都标记尚有待成本来源。新到成本100确认后，追加50至原出库去向、50至在库，结果出库成本100、剩余价值100。未证成本从未被声明为合法零成本。

## 7. 后补传播、并发与原路反向

### 7.1 常规动作与后补竞态

新边保存创建时父节点revision与已含的基准金额：

- 后补先应用：随后普通出库读到已更新V，新边的基准revision已经包含该后补，旧任务不能再加一次。
- 出库先创建边：后补随后按冻结的x/Q流向出库和剩余节点。
- 全部出库后，剩余边比例为0，后补只走原出库去向，不增加当前空库存价值。

所有节点更新按本地revision推进；任务记录目标累计金额及来源事件，边按revision顺序应用。不能用无来源的“最新总额覆盖”合并掉不同费用的审计事实。金额差额为0但来源从未证变为已证时，也要完成状态传播。

普通出库与后台传播都锁住当前活动节点：若节点已经因物理动作变为历史节点，后台只向冻结的后继边转发，不再给旧库存头加钱；若后台已经记入活动节点，物理动作读取该revision的新金额。禁止边创建后不保存基准revision，否则作业重放会漏分或重复分配。

### 7.2 不把历史节点金额重复记成资产

历史池节点的累计价值只用于分配计算，只有当前活动位置贡献库存/WIP/COGS/损失余额。来源费用确认先挂明确的待分配价值位置，后台每完成一个终点的分配即从该位置转出。各分块两端守恒；作业中断时剩余差额可核对，不能一边遍历一边在每个历史节点重复增加资产。

任务完成必须满足：来源事件已批准、全部已发布边revision已应用、无未处理子任务、待分配余额为0、投影对追加事实无差异。没有错误消息不等于成本已完成。

### 7.3 锁序与事务

- 普通业务继续先持有既有来源/业务对象锁，再批量取得库存键锁；价值扩展按库存键→成本对象键→节点ID稳定顺序取锁。
- 后台先读不可变owner信息，再取同一owner锁及节点锁；一笔任务只更新当前节点/终点并追加下一跳任务，不在持锁过程中递归锁整个下游图。
- 生产费用分配对象先生成完整候选快照，再用expected output/value revision发布。新产出可继续登记待成本，不能把半份分配方案当作生效方案。
- 来源事实、数量movement、初始价值posting、库存投影、Outbox在业务事务内提交或回滚。后补各块的posting、edge revision与子任务同事务提交。
- 重放同键同体返回原结果，同键异体冲突；冲销与正向分配互斥，余额和来源容量都在锁内核对。

### 7.4 原路退回和冲销

退料/销售退货携原出库价值，而非当前移动平均价。原出库切片按已退与剩余数量拆分；退回部分进入当前目标库存池，未退部分仍在原WIP/COGS去向。之后原成本再增加时，两部分仍各承担冻结份额。

例如原出15个成本150，退回5个携50；后补原切片成本15，应再分5到退回物料当前去向、10到未退部分，不能把15全部压回当前仓。若退回物料再次售出，继续沿其后续池状态流向COGS。

反向库存动作保留现有实物可逆门禁；价值-only纠正不伪造返库数量。反转费用或重分摊使用新事件和原事件UUID，旧账不改。普通跨期红冲不因本方案自动开放。

## 8. 生产/委外分批与成本归集

### 8.1 材料先到在制，确认后分类

实际领料价值先成为车间/WIP价值。责任人既有清料确认提供实际耗用、正常损耗、报废、合法在制的数量依据；良品退料按原领料价值返回。未确认分类不能按领退差填成实耗。

正常允许损耗与实际耗用一起进入合格产出；超耗/异常报废进入独立异常损失位置，赔偿追回沿现有独立索赔账，不净原损失。当前缺少明确正常/异常分类的历史posting应待分类，不把全部 `APPROVED_LOSS` 自动当作某一种。

### 8.2 产出成本方案有版本，池内出库比例不改

生产成本对象首选执行段及其产品UUID，不把多产品物料分析直接作为一个数量分摊池。已确认加工费必须明确来源与分配对象；不能把整张费用单按所有产品数量自动摊开。

普通FG入库创建来源明确的产出价值节点，引用已有已确认分配，或处于 `PENDING_ALLOCATION`；不逐次重算全部历史批次。生产结算/暂计方案按批准事件版本冻结，包含各产出movement UUID、同产品分摊基数及WIP剩余位置。计划量只可能成为明确批准的暂计分摊参数，不会成为可用库存。

当实际产量、确认耗用或损耗使原分配需要改变时，发布新的分配快照并生成“目标累计值−已分配值”的前向调整。原池的移动平均x/Q保持不变；新差额继续沿原产出之后的库存/COGS关系传播。不得编辑旧边来无声改变历史。

重新分摊及后补作业可以遍历本成本对象的受影响批次，采用索引和分页。它不属于普通数量出入库的同步路径。暂计分母不足、实际多产等情况可先入库待成本，再由新版本分配，不能用金额缺口阻挡已允许的物理入库。

生产分配路由版本与库存移动平均边必须分开：生产方案变更时旧方案及已记分配仍保留，新方案逐目标计算累计差额，并为后续费用指定当前有效路由；旧库存池x/Q永不改写。方案发布与正在传播的旧版本任务按版本协调，旧任务不得在新方案完成后再次覆盖目标累计值。真实新投入、返工或产量变化不通过负比例边偷偷改旧方案，而通过明确的新成本代际或新分配事件处理。

### 8.3 委外

自有材料/目标件发出时价值转入委外在制，回厂承接实际投入价值加已确认加工费。已自制完成的目标件已有子件成本，后续委外不得再次按BOM加子件成本。

同SKU发出后回厂按不同事件节点表达。返工使用独立执行/成本代际，禁止把某次产出的价值反向接入它自己的投入节点形成循环。费用确认晚于产出可以引用旧成本对象补差，真实新投入则必须有合法的生产/返工来源关系。

### 8.4 下一工作包：生产价值桥，不能由独立成本调整替代

V500能把材料出库价值定位到 WIP，也能让FG先登记待成本来源，但还不能把前者的价值跨货品转到后者。必须新增以真实消费/损耗posting为依据、两端平衡的纯价值归集/分摊接口：减少原材料WIP拥有价值，增加已有FG来源或异常损失拥有价值；未耗用部分仍留WIP。物理数量完全不变。

生产方案要保存批准事件、分配版本、固定目标movement/source node、数量确认posting与累计区间。后补材料成本沿该方案的原边继续流向当前在库、COGS及WIP；撤回或改方案追加成对差额并保留原版本。不能给A独立 `adjustSource(+600)` 却让B/E的WIP仍各持400/200，也不能以FG入库先后推断已确认耗用。

这一扩展涉及“较早建立的FG待成本源”与“后来确认的WIP归集”之间的路由。V500 的严格向后节点序号仅证明现有合并/二分图无环，不能直接接一条逆序边来绕过。下一包需明确生产路由代际及已有FG来源的平衡转接协议，独立测试返工、分批、方案反向和晚费用；该接口尚未实现。`pendingWork.lockKey` 已取每条任务实际子节点的库存键，跨产品扩展不能一直返回初始原料键。

## 9. 后补分批示例与必须测试的断言

在分摊基数仍为20件、无其它差异的示例中：实际材料600，先入库10件、其中售8件，暂计为COGS240、库存60、WIP300。追加确认费用60后，分别追加COGS24、库存6、WIP30，总计660。全部20件售出后，库存和WIP均为0，COGS660。

该示例验证传播机制，不替代责任人实耗确认或生产暂计分配规则。若有未耗用材料、异常损失或产量变更，必须使用相应已批准分配结果。

验收至少覆盖：

1. A/B/E完整非零价值反例，收入2000与成本600分别守恒。
2. 不同入库成本混池、部分出库、清空池、跨仓调拨、实际零成本与缺成本分开。
3. 分批FG/部分销售后补费；全部销售后补费；部分退料/退货及再次销售后补费。
4. 正常损耗留产出、异常损失独立、追回不净损失；未确认实耗不能自动结清。
5. 4位微额、1/3等循环比例、多次补费和反向；全出严格取剩余价值，无尾差残留。
6. 后补先赢/出库先赢两方向、同费并发重放、任务中断恢复、重复或乱序投递。
7. 实际产量改变后的新分摊版本，原池出库比例及旧posting不被修改。
8. 来源费用已批准但未归集、金额来源缺证、历史无法唯一关联、当前期间限制均明确显示。
9. 每事件价值两端守恒；库存/WIP/COGS/损失/待分配总额对账；数量事务回滚不遗留价值。
10. 日常单笔出入库不随历史批次数增长，10万/百万历史下验证SQL次数与索引；仅后台后补遍历受影响关系。

## 10. 历史切换与交付顺序

历史事实分为可精确关联、仅能核定期初价值、无法证明三类。可证明部分追加修正事实；不完整的数量/金额/source UUID保留未证状态。不能用当前BOM、当前标准成本或清零“修复”。

切换先冻结原始摘要及源数据证据，核对仓库、待检、在制、委外在制与GL。批准的期初价值建立明确基准事件，旧流水保留为legacy历史；新价值投影只能选择一个切换基线和其后的事实，不能把期初与整段旧流水重复相加。金额修复与数量修复分别审批、分别记录。

财务源也只能记一次：加工费/AP已确认事实作为价值来源，不意味着再立一笔AP或再付款。取得成本与现有AP_POST资产入口必须明确唯一的GL记账所有者；价值子账可引用原finance ledger/source event及其凭证投影，不能和旧AP_POST同时重复借记库存。内部库存/WIP/FG转移、真实COGS与成本调整再按同源posting投影到对应科目。现有销售收入、客户贷项、付款汇兑等继续各有来源，不能通过新价值账再算一次。

建议交付顺序：来源与状态契约/失败反例→实际平均池与原路退回→投入与产出价值桥→后补传播及生产分摊版本→GL/报表同源→非空历史切换与完整压力、多角色验收。不能仅完成前两步就宣称成本闭环。

发布采用当前 [ADR-060](../99-决策记录-ADR/ADR-060-单维护者简化发布链与旧发布链退役.md) 和 [deploy/simple操作手册](../../deploy/simple/RUNBOOK.zh-CN.md)；先完成本地实现与全量验收，再按用户授权提交/CI/打包和手动更新。目标环境仍须只读核对真实版本、配置、数据库历史并备份，不以服务器现状默认正确，不repair已应用迁移。

## 11. 只读证据脚本

[`server/ops/inventory_value_reconciliation.sql`](../../server/ops/inventory_value_reconciliation.sql) 用于当前价值重构前结构的限定范围对账：

- 必须传入1–500个明确货品UUID；可限定仓库。每区输出上限1–1000行，并返回截断前发现数。
- REPEATABLE READ / READ ONLY，30秒statement timeout；不创建临时表、函数，不写余额/单据/GL。
- 当前余额与所选维度全部保留流水比较，不拿日期截断流水去对完整余额。
- 区分数量投影差异、已记录金额投影差异、零数量非零价值、负已记录价值和生产/销售成本来源未证。
- 空金额、缺来源或不完整迁移历史不冒充真实0成本；商业原币不求合计，数值等于销售金额本身也不是误用的充分证明。
- 0发现只表示本次范围和当前保留记录未命中条件，不证明历史已完整或计价正确。价值账上线后，应更新来源验证部分以读取真正的价值分配关系。

示例使用一次性验收库现有连接，不在脚本中保存凭据：

```powershell
psql -X "$env:TEST_DATABASE_URL" -v goods_ids='{A的UUID,B的UUID,E的UUID}' -v limit_rows=200 -f server/ops/inventory_value_reconciliation.sql
```

脚本是证据工具，不是修复工具。运行缺少最终 `READ_ONLY_RECONCILIATION_COMPLETE` 标记时，不得把部分输出当作对账完成。

本次已在无网络、无宿主端口的一次性PostgreSQL16容器实际执行脚本，使用合成A/B/E同形反例、真实0金额、投影差异、历史缺UUID、不同商业币种和重复余额键。验证了：A/B/E即使流水与余额数值相符仍显示残值症状；0金额不进入数值错误条件；原币没有混加；限制行数仍给出截断前总数；无范围请求以非零退出码拒绝；执行前后余额和流水内容摘要一致。容器已清理，原业务库未连接。

数理原型另验证了移动平均合并/出库、原成本部分退回、再销售后补费、清空池后差额全部去COGS，以及累计4位尾差。原型和只读脚本通过不等于价值引擎已经实现；证据保存在本地忽略目录 `.codex-tmp/inventory-value-query-check/`。

## 12. V500 独立核心验收范围

`InventoryValuationCorePostgresTest` 使用真实PostgreSQL16、共享JPA事务及实际库存advisory锁，执行V500 DDL与现有StockService物理写职责的最小测试替身。覆盖实际平均合并/清空、原出库分次退回及再售、晚费用到库存/COGS、真实零与未知、累计4位尾差、仓库/颜色隔离、幂等异体、失败回滚/乱序/重放、严格原调整反向、非空历史未证、投影篡改、未持锁拒绝和REQUIRES_NEW隔离。两个竞争方向均观察 `pg_stat_activity.wait_event_type='Lock'`，然后核对最终两端金额。

普通出库在1次与120次既有出库历史下的JDBC语句数量相同且小于30；这是算法不扫描历史的定向证据，不代替10万/百万真实HTTP压力。后台每次取任务最多100，一次事务只传播一条边，失败回滚后可重新执行。

发布状态采用保守门槛：任一未完后补job存在时，当前查询暂返回PENDING，避免远端尚未传播的叶误报FINAL；活动节点仍保留自身待证来源计数。该门槛不禁止实物流转，但可能让无关库存短时显示待成本。后续如要缩小显示范围，必须有同样可靠的待传播来源投影，不能只看叶节点尚未更新的标记。

尚未交付：StockService及业务调用方完整接线、来源审批金额容量、跨货品WIP/FG价值桥、生产分配版本、成本期间/GL、成本报表、后台调度及开账的应用审批入口。历史金额差额也仍需独立财务批准/前向GL工作包。现有只读对账脚本按重构前来源结构解释；接线后必须升级对账规则，不能直接把“原movement金额+所有新posting”混加。以上独立测试不代表A/B/E完整成本链已修复。
