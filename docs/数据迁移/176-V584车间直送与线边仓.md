## 需求与适用边界

用户口径(2026-09-15)：

> 车间生产完成的不一定走仓库。物料 A 的子件物料 B 做完(可能只做了一部分)，
> 班组内部检查合格后，不入库，直接投入物料 A 的生产。流程尽量简化。
>
> 关键思路：**通知对应的那个生产任务领料，但是领料位置是另一个。**
>
> 复核后的边界：**两个不同的车间必须走仓库；同一个车间才可以不走仓库。**

所以本迁移支持的是**车间内部流转**：子件工单与上层工单必须属于同一个车间部门。
跨车间一律走原路线(仓库送检登记 → 品质部 FQC → 仓库点收入库 → 仓库发料)——
料一旦离开本车间就脱离同一批人的视线，交接与账实相符必须由仓库承担。

## 为什么是「线边仓」而不是「纯记账」

把直送做成「只记 B 交给 A 多少个、完全不碰库存」会同时撞死四道既有硬闸：

1. V249：执行段进 READY 要求每条需求 `stock_backed >= required`；
2. 需求 FULFILLED 的唯一来源是预留的 `consumed_qty`；
3. V152 的 `can_close` 要求 `issued_qty > 0`，否则父段永远完工不了；
4. V517 成本产出行的 `movement_id` 是 **NOT NULL** —— 没有库存移动就没有成本产出，
   子件的成本会永远停在在制、结不出来。

绕开第 4 条要新开一条不经 `stock_balances` 的价值路径，与 V500「池头节点必须等于唯一一行
`stock_balances`」正面冲突。

所以取向是：**不绕开「仓库」这个数据概念，只绕开「仓库」这个部门角色。**
线边仓是车间自己的料架——仓库部门不管、不点收、不进成品仓报表，但它是一个真实的叶子仓，
料确实在那里，流水记的就是它自己的 UUID(不违反 ADR-073「实仓记录不得重标为计划仓」)。
于是价值、成本、清账、退料、结算、完工判定六条链一行都不用改。

## 结构变化

| 对象 | 变化 |
|---|---|
| `warehouses` | **只加** `is_line_side BOOLEAN NOT NULL DEFAULT FALSE`。车间归属沿用 V274 就有的 `workshop_department_id`(原注释：`Live workshop UUID -> departments.id; must be a non-deleted direct child of DEPT_PROD`)——重复建一列会是第二份权威。`fn_guard_warehouse_line_side` 只约束线边仓：必须是**参与核算的非不良叶子仓**、必须指明车间、**有余额时禁止摘掉标记**(摘掉后在制品会立刻出现在公共可用量里被别的工单领走)；非线边仓照旧，V274 起普通仓库也可以挂车间归属。不复用 V43 的 `workshop_legacy_id`：V274 头注释写明它是 `B_Storage.WorkID -> Sys_Operator.ID`，历史上被误命名，从来不是车间桥 |
| `production_daily_report_items` | 加 `destination TEXT NOT NULL DEFAULT 'WAREHOUSE' CHECK (IN ('WAREHOUSE','WORKSHOP'))`。放在行上而不是单头：一张报工里一部分送仓库、一部分转车间是常态。**一行只有一个去向**——V548 的 `production_finished_arrival_registration_item_active_uk` 与 V410 的 inspection 都按 `source_report_item_id` 唯一，行内拆量要同时改这两处唯一性，所以要拆量就拆行 |
| `production_workshop_direct_transfers` / `_items` / `_reversals`(新 3 张，追加式) | 直送单按本车间线边仓归集；行是「一条报工行 → 同车间一条上层物料需求」的点对点承诺；撤回不删原行，只打 `reversal_id`。`_items` 有部分唯一索引 `WHERE reversal_id IS NULL`，撤回后可以重来 |
| `production_fqc_inspections` | 加 `inspection_kind TEXT NOT NULL DEFAULT 'ARRIVAL' CHECK (IN ('ARRIVAL','WORKSHOP_SELF'))` |
| `fn_guard_production_fqc_inspection` | 前向替换 V548 版：按 `inspection_kind` 分流「入哪个仓由谁证明」——`ARRIVAL` 认仓库送检登记行，`WORKSHOP_SELF` 认车间直送行；并校验去向与检验种类必须一致(送仓库的行不能靠班组自检放行，反之亦然)。替换前先用 `pg_get_functiondef` 做形状断言，上游被别人改过就停下 |

## 为什么复用 FQC 三张表做班组自检

`requireInboundReleased`、成本对象的覆盖判定、FAIL 的返工/报废/补产闭环、报工红冲时的
FQC 取消——四套既有机制全部以「这条报工行有没有 inspection」为判据。另起一套自检表要在
四处各开一个口子，每个口子都是一次 fail-open 风险。所以自检落成一条
`inspection_kind='WORKSHOP_SELF'` 的 inspection，只把「谁判的」标出来。

用户明确选择**班组可以判合格/返工/报废**(2026-09-15)。因此数据库层不限制
`WORKSHOP_SELF` 的决定取值；责任靠 `decided_by_employee_id` 留痕，品质部保留在放行未被
消费前追加决定的翻案通道。

## 行级守卫(`fn_guard_workshop_direct_transfer_item`)

1. 追加式：行写下后只能打一次 `reversal_id`，其余列不可变，不可删。
2. 数量必须等于该报工行的申报量(V1 不做行内拆量)。
3. 收料需求必须属于收料工单，且**货品与颜色与该报工行一致**——直送是点对点承诺，
   认错料就是把上层的需求用别的货顶掉。
4. 指向同一条需求的有效直送量不得超过该需求的需求量；超出的部分没有指向对象，
   只能走仓库变成公共备货(V577 口径)。
5. **子件工单、上层工单、线边仓必须同属一个车间部门**，且线边仓与收料需求同主仓
   (`fn_warehouse_same_main`，V489 的硬前提)。

## 不新增什么

- 不新增 `production_material_stock_postings.posting_type`：V152 的两个 NOT NULL 外键与
  V514 的延迟约束触发器比 CHECK 硬得多，且 V514 的 `expected_direction` CASE 没有 ELSE，
  多一种类型会让它返回 NULL、整条断言静默放行——「守卫看起来还在、其实已经瞎了」比报错更坏。
- 不新增 `stock_reservations.owner_type`、不新增 `movement_type`。
- 不复用 V194 的 MAKE peg(`packageOwnsSupply` 对新业务是死分支)。
- 不碰 `production_fqc_legacy_exemptions`(V414 触发器对任何写入一律 `RAISE 55000`)。
