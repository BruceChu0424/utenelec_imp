## 一、设计决策总览（含理由）

| # | 决策点 | 选型 | 理由 |
|---|---|---|---|
| 1 | **8 类单据存储** | **8 套独立主从表**（贴采购 [15] 范式，非仓库 [17] 的统一表） | 8 类语义差异显著（询价/申请无物流、订货带 BOM 展开、发料无 Price、损耗带 WRate/Cause、进仓/退货带币种），独立表约束清晰；与采购模块对称便于理解维护；前端"8 单据 8 页"零割裂。**不合并空表**（询价/申请老库 0 行仍独立建结构，保未来启用零成本，贴 P_Ask/O_Waste 先例） |
| 2 | **链路溯源** | **真外键骨干 + 文本占位**（沿用 [15]/[18] §二） | E_InItem.OrderID / E_WithDrawItem.InID/OrderID / E_SOutItem.EOrderID / E_SWithDrawItem.EOutID/EOrderID / E_SWasteItem.OutID 共 7 条单值 FK → 新库真外键；老库 17 个多值 `*No`/`BomItemID` varchar 串 → 统一降级为 `source_doc_no TEXT` 文本占位 |
| 3 | **BOM 自动展开**（委外 vs 采购的根本差异） | **本期：建表保结构 + 迁老库 67 行数据原样；展开触发逻辑上移 Service 并标注"后置/手动触发"，本期不实现自动展开** | 与生产 `F_PlanCostItem`（136 万行原样迁、成本重算后置）一致策略；`+0.46` 魔法数字 → 规则化为 `waste_allowance` 字段；空表/极少表保未来扩展零返工 |
| 4 | **反向库存纠正** | **新库 movement_type 17 按 `direction=+1`（成品进仓增加库存）** | 老库 `TRI_EIStockItem` 写 `StockGoods.QTY = QTY − @Status×@QTY`（**减**库存），是"成品收回冲减发出数"的特有模型，违反直觉。新库不照搬反向逻辑，仅做正向流水事件；余额由 `stock_balances` 独立维护。**这是本模块最重要的"不照搬"决策** |

| 9 | **金额双口径** | `*_original`/`*_local`（进仓/退货/订货带币种；发料/材料退/损耗无币种仅 `amount_local`） | 与采购一致；老库 `E_In/E_WithDraw` 有 `Total`（抽样全 0）、`E_SOut/E_SWithDraw/E_SWaste` 根本无金额字段——印证"材料按成本发出、成品收回不直接计价"，加工费走 BOM 成本子表 |

| 12 | **归属部门** | **`DEPT_SALES`（综合营销部）**（[21] §七建议，待 bruce 终定） | 数据强共享（委外商=供应商主档）、流程耦合（委外/销售订货同构）、避免新部门成本；权限按部门+`feature_key` 已能隔离，无需独立 `DEPT_OUTSOURCE` |

## 三、表设计（DDL · V53 蓝图）

### 3.0 统一约定（同 V44 采购）

- 主键 `id UUID PRIMARY KEY DEFAULT gen_random_uuid()`，迁移溯源 `legacy_id INT UNIQUE`（主表）；明细 `legacy_id INT`（**不 UNIQUE**，因老库各 `E_*Item` IDENTITY 独立、跨表 ID 重复，同仓库 `stock_document_items` 踩坑，见 [17] 踩坑①）。
- 单据号 `bill_no TEXT NOT NULL` + `UNIQUE(bill_no)`（业务主键）；老库 `IX_E_*` 唯一索引保留。
- 审计四件套 `created_at/updated_at/created_by/updated_by` + 软删 `is_deleted/deleted_at`。
- 金额 `NUMERIC(18,4)`、数量 `NUMERIC(18,4)`、汇率 `NUMERIC(18,6)`、税率 `NUMERIC(18,4)`、损耗率 `NUMERIC(8,4)`（百分比，老库 WRate）。
- 金额双口径：`*_original`（原币）+ `*_local`（本币 = 原币×汇率）。
- **明细冗余 `bill_no/bill_date`**：查询裁剪 + 报表免 JOIN 主表取日期。
- 人员字段：`*_id UUID`（无 FK，迁移留空）。
- 多值 varchar 串（17 个 `*No`/`BomItemID`）→ `source_doc_no TEXT` 合并占位文本。
- 权限 seed 底部统一挂 `DEPT_SALES`。

### 3.3 委外订货单 `subcontract_orders` / `*_items` + `*_cost_items`（E_Order,2/5/67·BOM 展开）

委外模块的核心特色：订货明细带 **BOM 自动展开成本子表**（与采购订货单的根本差异）。

> **业务口径（V292/ADR-038，2026-08-16）**：`warehouse_id` 列保留（迁移兼容），但订货不再填写——委外成品回收入哪个仓库由进仓单（到货登记）必填；任务中心不再要求「同仓库申请才能生成一张订货」。
>
> **2026-08-27 结算方式口径**：委外订货新建/编辑页必选启用中的结算方式；字典加载失败、空字典、空值或停用历史项均阻断保存，服务端保存强制有效 UUID，提交财务时再次复核。采购员显示 `姓名(工号)`，部门位于副行。进仓/退货继续沿用来源快照与历史兼容。详见[订货单公共表头规范](../03-页面/订货单公共表头规范.md)。

```sql
    goods_id        UUID NOT NULL REFERENCES goods(id),    -- 子件货品（GoodsID）
    color_id        UUID REFERENCES colors(id),            -- 子件颜色（ColorID）
    unit_id         UUID REFERENCES units(id),
    unit_rate       NUMERIC(18,6) DEFAULT 1,
    unit_qty        NUMERIC(18,6),                         -- DQTY 单支用量（BOM 子件单位用量）
    qty             NUMERIC(18,4) NOT NULL,                -- QTY = 父件量×子件用量+余量（迁老库原值）
    waste_allowance NUMERIC(18,6) DEFAULT 0,               -- ★规则化余量（老库硬编码 +0.46；新库字段化，可配置）
    issued_qty      NUMERIC(18,4) DEFAULT 0,               -- SQTY 已出仓量（E_SOut 审核按 BomItemID 累加）
    returned_qty    NUMERIC(18,4) DEFAULT 0,               -- WQTY 已退量
    line_class      TEXT,                                  -- 老 Class 字段
    source_doc_no   TEXT,                                  -- SendNo/WDrawNo 多值降级
    remark          TEXT,

    updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    is_deleted BOOLEAN NOT NULL DEFAULT FALSE
```

> **BOM 展开决策（关键）**：本期 `subcontract_order_cost_items` 表**完整建结构 + 迁老库 67 行原样数据**，但**新系统不实现自动展开触发器**（老库 `TRI_E_OrderCostItem_Insert` 的 `while @BomStatus=1` 递归逻辑）。展开逻辑标注"后置/手动触发"——未来用 Service 方法 `expandBom(orderItem)` 在订货单审核时显式调用（一次性展开缓存进本表，去触发器、可测、可审计）。此策略与生产 `F_PlanCostItem`（136 万行原样迁、成本重算后置）一致。详见 §五。

## 四、状态机与库存联动（Service 层，去触发器）

```
录入 status=0(草稿) / 1(已审，贴老库"保存即生效")
审核 0→1：同事务内，按单据类型执行：
  · 真FK 骨干回写累计量（received/returned/issued/wasted_qty 等）
  · 写 stock_movements（direction/type 见下表）+ upsert stock_balances
  · 重算相关单据 is_closed / fulfill
红冲 1→-1：同事务反向冲销（库存反写、回写量倒回），单据保留不可删
```

**单据 → movement_type / direction / 回写映射（Service 单一参数化路径 `applySubcontractEffect(doc)`）：**

| 单据（doc_type） | movement_type | direction | 库存效果 | 回写目标（Service 同事务） |
|---|---:|---:|---|---|
| 收回成品 `E_In` (subcontract_receipts) | **17** | **+1** | 入库（成品收回增加库存，**不照搬老库 QTY-= 反向**） | `order_item.received_qty += qty`（IQTY） |
| 成品退 `E_WithDraw` (returns) | **18** | **-1** | 出库 | `receipt_item.returned_qty += qty` + `order_item.returned_qty += qty`（WQTY 双回写） |
| 发料 `E_SOut` (material_issues) | 历史 **15** | 历史 **-1** | 新增审核禁用；历史出库事实保留 | 不写 `order_item.issued_qty`；待冻结 BOM 快照和子件台账落地后再启用 |
| 材料退 `E_SWithDraw` (material_returns) | **16** | **+1** | 入库 | 只写 `material_issue_item.returned_qty += qty`，不写订货 legacy 累计 |
| 损耗 `E_SWaste` (wastes) | 新增无流水；历史 **19** | 新增无方向；历史 **-1** | 发料时已离开公司仓，新增损耗不二次扣库存 | `material_issue_item.wasted_qty += qty`；历史实际出库红冲时才写对称补偿 |

**结案派生（Service 重算主表）：**
- 订货单 `is_closed = (所有明细 `qty − received_qty + returned_qty ≤ 0`)`（贴老库 `CF_E_Order` 规则，源 [21] §4.5）
- 进仓/发料等物流单据：红冲后 `is_closed=true`

**红冲规则：**
- 已审单据（`status=1`）只可红冲（→ `-1`），不可物理删除。
- 红冲同事务：反向 `stock_movements`（插一条等量反向 direction 流水）、倒回累计量、倒回余额。
- 父单存在有效下游累计时必须先红冲下游：申请→订货；订货→进仓/退货/发料/退料；
  进仓→退货；发料→退料/损耗。订货红冲按稳定 UUID 顺序锁申请来源明细后再回减
  `ordered_qty`，避免并发丢失更新或负累计。
- 有应收应付的进仓/退货红冲先由 `ArApLedgerService.reverseArAp` 校验无核销并反立账；已核销时
  直接拒绝，不允许库存和累计量先发生部分冲销。

## 五、BOM 展开（委外核心特色 · 决策段）

### 5.1 老库 BOM 展开机制（参考）

老库 `TRI_E_OrderCostItem_Insert` 在 `E_OrderItem` INSERT 时按成品 `GoodsID` 查 `View_B_BomItem` 一级子件，递归 `while @BomStatus=1` 展开多层（最深 30），每次插入 `E_OrderCostItem`：
- `ParentID` = 上级 ID（自关联）
- `Level` 由 `TRI_E_OrderCostItem_Level` 计算
- `QTY = 父件量 × 子件用量 + 0.46`（**+0.46 是余量补正的魔法数字**）
- `DQTY` = 子件单用量

`CheckChange_E` 触发器维护 `SQTY`（已出仓量）：任一子件 `QTY>SQTY` 则父件 `SQTY=0`，否则 `SQTY=QTY`（父件视为"全部发料"）。`E_SOut` 审核按 `BomItemID` 串游标消耗 `SQTY`（性能重灾区）。

### 5.2 本期决策（与生产 F_PlanCostItem 一致策略）

> **本期：建表保结构 + 迁老库 67 行数据原样；新系统自动展开逻辑不实现，标注"后置/手动触发"。**

具体含义：
1. **DDL 完整建 `subcontract_order_cost_items`**（含 `parent_cost_item_id`/`bom_level`/`waste_allowance`/`unit_qty`/`issued_qty` 等全部字段）。
2. **迁移保数据**：老库 67 行 `E_OrderCostItem` 原样迁入（含 `bom_level`、`parent_cost_item_id` 映射），作为历史订货的 BOM 状态留底。
3. **新系统录入不自动展开**：本期新增委外订货单时，明细保存即可，`subcontract_order_cost_items` 暂不自动展开。
4. **`waste_allowance` 规则化**：老库硬编码 `+0.46` 替换为字段（默认 0，可按子件配置），为新系统未来启用展开提供参数化入口。
5. **未来启用路径（后置）**：写一个 Service 方法 `expandOrderBom(orderItemId)`：
   - 读现有 `goods_bom_items`（V79 当前 BOM 主档）；只取未删除边，且父件/组件必须为未删除、`auto_created=false` 的正常货品，V181 数据库守卫负责阻止再次写入 stub 端点
   - 递归 CTE 展开多层（去触发器递归）
   - 计算 `qty = 父件量 × unit_qty + waste_allowance`
   - 一次性 INSERT 到 `subcontract_order_cost_items`
   - 订货单审核时显式调用（手动触发），保证可测、可审计、可重算。

### 5.3 风险与对策

- **风险**：本期不展开 → 新增订货单无冻结 BOM 子件快照 → 无法证明应发子件、版本和累计守恒。
  **当前对策**：发料单只允许保存草稿，前端禁用从订货引入和审核，服务端审核返回 409；
  禁止以手工挂 `order_item_id/goods_id` 绕过。老库历史单据保留查询、红冲和下游来源兼容，不重算旧 BOM。
- **与生产模块的协同**：生产 `F_PlanCostItem`（136 万行）与委外 `E_OrderCostItem`（67 行）同属 BOM 展开模式。本期两者都按"原样迁保数据、展开后置"策略，未来在统一的"BOM 引擎 Service"上实现，避免两套重复逻辑。
- **当前/历史分离**：`goods_bom_items` 是当前理论结构；`production_plan_costs` 与 `subcontract_order_cost_items`
  是历史展开/单据快照。31 个 `goods.auto_created=true` 只为历史 FK 保留，不得作为新委外展开输入。

### 6.2 物化视图 `subcontract_monthly_mv`（V54 蓝图）

```sql
CREATE MATERIALIZED VIEW subcontract_monthly_mv AS
SELECT 'ORDER'::text  AS doc_type,
       date_trunc('month', bill_date) AS ym,
       goods_id, supplier_id, currency_id,
       SUM(qty)             AS qty_sum,
       SUM(amount_local)    AS amt_local,
       SUM(amount_original) AS amt_original,
       COUNT(*)             AS line_cnt
FROM subcontract_order_items it
JOIN subcontract_orders o ON o.id = it.order_id
WHERE it.is_deleted = false AND o.status = 1
GROUP BY 1,2,3,4,5
UNION ALL
SELECT 'RECEIPT', date_trunc('month', it.bill_date), it.goods_id, o.supplier_id, o.currency_id,
       SUM(it.qty), SUM(it.amount_local), SUM(it.amount_original), COUNT(*)
FROM subcontract_receipt_items it JOIN subcontract_receipts o ON o.id = it.receipt_id
WHERE it.is_deleted=false AND o.status=1 GROUP BY 1,2,3,4,5
UNION ALL
SELECT 'RETURN', date_trunc('month', it.bill_date), it.goods_id, o.supplier_id, o.currency_id,
       SUM(it.qty), SUM(it.amount_local), SUM(it.amount_original), COUNT(*)

UNION ALL

       SUM(it.qty), SUM(it.amount_local), SUM(it.amount_local), COUNT(*)
FROM subcontract_material_issue_items it JOIN subcontract_material_issues o ON o.id = it.issue_id
WHERE it.is_deleted=false AND o.status=1 GROUP BY 1,2,3,4
UNION ALL
SELECT 'MATERIAL_RETURN', date_trunc('month', it.bill_date), it.goods_id, o.supplier_id, NULL::uuid,
       SUM(it.qty), SUM(it.amount_local), SUM(it.amount_local), COUNT(*)
FROM subcontract_material_return_items it JOIN subcontract_material_returns o ON o.id = it.material_return_id
WHERE it.is_deleted=false AND o.status=1 GROUP BY 1,2,3,4
UNION ALL
SELECT 'WASTE', date_trunc('month', it.bill_date), it.goods_id, o.supplier_id, NULL::uuid,
       SUM(it.qty), SUM(it.amount_local), SUM(it.amount_local), COUNT(*)
FROM subcontract_waste_items it JOIN subcontract_wastes o ON o.id = it.waste_id
```

### 6.3 委外出入状况表（综合 O · 参数化查询）

按委外商×货品汇总发料/收回/退/损耗/净额（贴老库 `View_E_InOutStatus` 口径）：

```sql
-- 示意：按 supplier + goods 汇总各类型流水
SELECT supplier_id, goods_id,
       SUM(CASE WHEN movement_type=15 THEN qty ELSE 0 END) AS issue_qty,    -- 发料
       SUM(CASE WHEN movement_type=16 THEN qty ELSE 0 END) AS m_return_qty, -- 材料退
       SUM(CASE WHEN movement_type=17 THEN qty ELSE 0 END) AS receipt_qty,  -- 收回成品

       SUM(CASE WHEN movement_type=19 THEN qty ELSE 0 END) AS waste_qty     -- 损耗

JOIN (SELECT id, supplier_id FROM subcontract_material_issues WHERE status=1
      UNION ALL SELECT id, supplier_id FROM subcontract_receipts WHERE status=1
      -- ... 其余单据
     ) d ON d.id = m.source_doc_id
WHERE m.movement_type BETWEEN 15 AND 19
GROUP BY 1,2;
```

## 十二、计划申请分解、订货财务审批与超量回厂（V196–V202 已迁移，待生产验收）

本节是当前后置专用契约；与前文“委外申请由业务部门 CRUD/审核”的历史设计冲突时，以本节为准。

### 12.1 申请只读、订货承载商业决策

- 委外申请由计划链下达，委外部门只查看 list/detail 并使用 decomposition-preview；Controller 不再公开申请新建、编辑、审核、红冲或删除。
- 计划需求不负责选择委外商，也不应看到供应商主档、价格和结算信息。委外商在订货分解阶段由委外部门选择。
- 任务中心读取 V199 `v_procurement_decomposition_tasks`，剩余量同时扣除已生效订货和待财务订货占用；驳回后待审占用释放。

### 12.2 分解约束

可以跨委外申请选择多行并部分分解；同一订货单只有一个委外商，不同委外商分别成单。当前预览要求同一仓库。每条原生订货必须带 `application_item_id`，并在财务提交/审核时重新锁来源、核对已下达状态、货品/颜色/单位/换算率、可用数量和来源委外商兼容性。

### 12.3 财务审核组审批

```text
DRAFT → PENDING → APPROVED（委外订单 status=1）
              └→ REJECTED → 修改 → 新 attempt 重提
```

保存后立即提交财务；提交失败保留草稿。共享任务、批准、驳回分别要求 `finance_order_approval:view/approve/reject`，动作还须由 `WorkflowReviewerEligibility` 实时验证财务部门资格或 active 个人点名加授；超管不自动代审。2026-08-18 起审批操作入口收敛到财务「订货审批任务中心」（`/finance/procurement-approvals`），委外详情始终只读；2026-08-30 起旧 `orderId+version` 单笔入口 fail-closed，单选也使用 `{caseId,expectedVersion}` 的 batch 协议。财务通过才回写申请 `ordered_qty`、执行供给副作用并生成未来入库任务。

没有 `subcontract:view:all` 的合格审核人仅在精确 PENDING case 时读取任务详情，列表范围不放宽。财务 batch service 在同一事务锁定订单与 case、校验 caseId/version/快照、执行业务副作用并返回决定 receipt；任一项失败整批回滚，case 结束后普通 GET 重新服从 maker/对象范围。

### 12.4 预计回厂与超量财务批准

V196 的未来入库台账是财务已批委外订单的预计回厂任务，不是实际回厂、质检、供应商处我方库存或余料核销。仓库审核委外收货并发现申报量超过财务批准余量时：

1. 返回 `ARRIVAL_EXCEPTION_PENDING`（409）并提交 `PENDING_FINANCE` 异常；委外收货仍为草稿，库存/AP/订单回厂累计均不写。
2. 异常由 `WorkflowReviewerEligibility` 实时判定合格审核人（不再冻结单点负责人快照）；V201 只给财务部门 `subcontract_order:view` 以看任务详情，不授委外订单编辑权。
3. `APPROVE_ALL` / `APPROVE_CUSTOM` 要求 `finance_order_approval:approve`，`REJECT_EXCESS` 要求 `finance_order_approval:reject`；三者都叠加实时审核资格。全部/自定义批准必须填写财务说明，超管不自动代审。
4. 服务端按接受量收窄草稿 `qty`、重量、原币/本币金额和单头合计；委外 `girth_qty` 按接受比例缩放，`check_qty` 取原值与接受量的较小值，订货 `order_qty` 不改。批准追加量绑定本异常、本收货单和订单行；仓库再审成功后才写库存/AP并累加 `subcontract_order_items.arrival_overage_posted_qty`，不能被其它回厂单借用。
5. 未批准量生成唯一 `supplier_return_tasks(PENDING_RETURN)`；负责人优先取订单 maker 对应的有效账号，其次订单 `created_by`，最后回退到委外经办人对应的有效账号。`supplier_return_task:handle` 只允许该退货任务负责人（原下单人）版本化确认已经退给供应商，不能决定入库量。

标准数量场景（无历史收货/退货/超量过账）：财务已批委外订货 10 吨、仓库草稿申报回厂 100 吨，先形成 90 吨 `requestedExcessQty` 并返回 409。`APPROVE_ALL` 接受 100/退回 0；`APPROVE_CUSTOM(customApprovedExcessQty=5)` 接受 15/退回 85；`REJECT_EXCESS` 接受 10/退回 90。财务决定本身不写库存/AP，接受量仍须仓库再审；若决定时并发使批准余量为 0，不批将移除该草稿行并直接形成 100 吨退回任务。

```text
PENDING_FINANCE
  ├─ 接受量 > 0 → RECEIPT_ADJUSTED → 仓库再审
  │                    ├─ 退货仍待办 → RECEIPT_POSTED → 退货完成 → CLOSED
  │                    └─ 无退货或已先退回 → CLOSED
  └─ 接受量 = 0 → RETURN_REQUIRED → 原下单人完成退回 → CLOSED（无需仓库再审）
```

### 12.5 未完成边界
