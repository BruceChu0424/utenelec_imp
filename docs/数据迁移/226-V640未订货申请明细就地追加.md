## 为什么要有它

物料分析准备页改为「计划量驱动子层」后，顶层追加下达会让下层物料的「还需安排」变大。计划员再下达采购/委外时，最自然的结果是把之前那张还没被采购/委外部门动过的申请明细直接改大，而不是每追加一次就多一张小申请。

供给行动(`preplan_supply_actions`)与它的分摊行(`preplan_supply_action_allocations`)是这条申请明细在计划侧的镜像。V250/V460 把外部化之后的 `requested_qty` / `allocated_qty`、V472 把 `public_surplus_qty` 与公共明细锚钉成不可变——那是为了保住「一张申请明细对应一条行动、数量只增不减、历史可追溯」的谱系。就地追加恰好满足这三条，所以只对「明细仍未订货」的行动放开只增不减的改量。

## 改了什么

| 对象 | 变化 |
| --- | --- |
| `fn_preplan_external_item_unordered(route, item)` | 新增。采购申请明细/委外申请明细是否仍未订货：申请开着(草稿或已下达、未结案、未中止、未删除)、明细未删除、已订量为 0、没有任何订货单来源引用它(含待财务审核的草稿订货单——那已经是「在采购」) |
| `fn_preplan_supply_action_growable(action)` | 新增。供给行动是否允许就地追加：SUPPLY、CREATED、路线采购/委外、外部化到采购申请/委外申请、没有被别的计划转走份额或认领、锚定的每条需求明细与公共明细都仍未订货 |
| `fn_is_preplan_supply_line_growth(table, old, new)` | 新增。申请明细/委外申请明细的这次 UPDATE 是否就是就地追加：只动 qty(与审计列)、只增不减、被某个仍可就地追加的供给行动锚定(需求明细或公共明细) |
| `fn_guard_production_supply_source_item()` | 锚点补丁(V503 版)：生产联动的申请明细原本一律不可改；`fn_is_preplan_supply_line_growth` 为真时放行(与 V503 的 `fn_is_proven_procurement_qty_revision` 并列) |
| `fn_guard_preplan_supply_action_history()` | 锚点补丁(V460 版)：外部化之后 `requested_qty` 允许在 growable 时只增不减，其余身份列与生命周期约束不变 |
| `fn_guard_preplan_supply_allocation_history()` | 锚点补丁(V460 版)：外部化之后 `allocated_qty` 允许在 growable 时只增不减 |
| `fn_guard_preplan_public_surplus_history()` | 锚点补丁(V472 版)：`public_surplus_qty` 允许在 growable 时只增不减；原本没有公共份的行动追加公共份时，公共明细锚只能从空指向它自己的需求明细(V588 合并明细形态) |

补丁方式沿用 V580/V588/V589 纪律：`pg_get_functiondef` 取定义、行尾归一 LF、锚点必须恰好命中一处，否则 23514 失败宁可不迁。

## 应用侧(同批，非本迁移)

- `MaterialAnalysisCommandService.notifySupplyInternal`：外部路线先自动认领同主仓公共在途，再对本操作组查 `growableSupplyLine`——命中就把申请明细改大(`increaseProductionDraftLine`)、行动的需求量/公共量与各物料行分摊同步增长，不另立新单；没命中才走原来的新行动 + 新申请。
- `ProductionPurchaseRequestFacade.increaseProductionDraftLine` / `ProductionSubcontractRequestFacade.increaseProductionDraftLine`：申请侧的唯一改量入口，自己再校验一次「申请开着、明细未订货、无订货单引用」。
- 通知：追加后按单据各提醒一次「采购/委外需求追加：单号(追加 N)」，与新申请的提醒分开。

## 兼容与影响

- 存量行动全部保持原样：只有此后发生的就地追加会改写这三类数量，且只增不减。
- `v_preplan_buy_action_slice_progress`、公共在途来源视图等都按行动与明细的当前数量计算，就地追加后自动跟上；一张明细仍只对应一条行动，不引入多行动共用一条明细的形态。
- CLEAR 目录不新增业务表，`reset_business_data.sql` 白名单登记 `(640, 592)`。
