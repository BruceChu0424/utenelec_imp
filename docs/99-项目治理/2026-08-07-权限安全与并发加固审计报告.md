## 一、核心结论：普通用户/懂技术者能否自己给自己授权或越权？

**不能。** 权限模型在后端是堵死的，前端怎么绕都无效。证据（`file:line`）：

| 攻击路径 | 为什么堵死 | 证据 |
|---|---|---|
| 直接调 API 给自己加权限 | 所有权限写入端点要求 `authorization:manage AND principal.superAdmin`（类级+方法级双重） | `AdminPermissionController:26`、`AdminUserController:76,101` |
| 伪造超管标记 `is_super_admin` | 超管标志**每请求从数据库重读**，不信 JWT；改超管本身也要已是超管 | `JwtAuthFilter.resolveStaff()`、`AdminUserController.setSuperAdmin` |
| 部门负责人偷偷越权 | 只能转授**自己持有的**权限（ceiling=本人有效权限−全员基础），禁改本人/部门基线 | `DepartmentStaffPermissionService:192,208-218` |
| 传入不存在的权限码"造"权限 | 权限码必须 `permissions` 表存在，DB 拒绝 | `PermissionOverrideAdminService:77-83` |
| 改 JWT 提权 | staff JWT 最小化（只 `sub/typ/av/ae`），权限每请求服务端重合成；版本戳不匹配即 401 | `JwtAuthFilter:147-154` |
| 批量赋值(mass assignment) | 入参是显式 record DTO（`SuperAdminBody` 等），不直接绑实体 | `AdminUserController:81` |
| 配置文件/源码篡改 | Web 用户碰不到服务器文件（主机安全范畴）；**无文件上传端点**（无路径穿越） | 全仓 grep 无 `MultipartFile` 控制器 |
| SQL/公式注入 | 原生 SQL 值全参数化；动态拼接仅表名/列名且为硬编码常量或经白名单（`TableSort.resolve(...,ALLOWED_SORT)`）；导出强制文本格式防 `=CMD()` | `FinanceAssetWorkflowService`、`ArApLedgerQueryService` |

**数据越权**：销售/敏感数据有完整 owner 隔离（`SalesDocumentAccessPolicy`，不可达返 404）；采购/生产/仓库当前为部门内共享——**业务既定方向是改为按负责人隔离（用户 2026-08-07 确认），属对象级授权统一（范围 B），本次并发加固未动，单列待办。**

## 二、并发模型（审计澄清）

**两层并存，职责不同，机制平台统一：**

| 层 | 机制 | 防什么 | 现状 |
|---|---|---|---|
| 正确性底线 | 悲观行锁 `SELECT...FOR UPDATE` + 状态前置条件 + DB 数量不变量触发器(V132) | 重复审批、并发状态翻转、超收/超发/超退 | ✅ 全部业务单据（销售/采购/委外/仓库/生产/钱流）写与审批路径已覆盖。**「重复审批导致数据错」已防住。** |
| UX/防碰撞层 | 统一任务软认领 `TaskClaimService`+`task_claims`(V215) show-as-locked | 「两人同时操作同一待办」；显示「XXX 处理中」、他人 409 | 🟡 基础设施+单测就绪；**守卫已接入**费用审批/销售订单审核/采购分解；前端徽标与履约任务台待补 |

**关键澄清**：交易单据编辑路径已有行锁（无丢失更新）；**主档（客户/货品/供应商…）编辑路径无锁**，是丢失更新真实薄弱面。

## 三、本次已落地并验证（mvn 绿 + E2E 29/29）

### 3.1 Gap 1——「别人正在操作」并发认领守卫

- `TaskClaimService` 此前在本分支**零调用、零测试**：新增 `TaskClaimServiceTest`（7 例，覆盖守卫空/他人占用/本人/租约过期/匿名、claim 首认领胜出/他人 409）。
- 守卫 `requireNoActiveClaimByOther` 接入：`ExpenseClaimService.approve/reject`、`SalesOrderService.approve`、`PurchaseRequestService.decompositionPreview`（复用查询结果行取 distinct request_id，不发额外 query）、`StockDocService.update`（FULFILLMENT_TASK，履约工作台仓库单据编辑）。四个登记类型（EXPENSE_APPROVE/PURCHASE_DECOMPOSE/SALES_ORDER_APPROVE/FULFILLMENT_TASK）全部接上服务端兜底。
- 新增 claim-view API：`GET /api/task-claims/{type}`（批量）、`GET /api/task-claims/{type}/{key}`（单个），供前端显示处理人。
- **架构边界**：四个协作 feature 依赖 `features.common.taskclaim`，已登记 `ArchitectureBoundaryTest` 白名单 + ADR-017 豁免（2026-08-07），与 admin/finance 等共享枢纽同构；后续可抽 `TaskClaimPort` 入 foundation 逐步归零。
- **修 2 个潜伏 bug**：`TaskClaimPolicy` 中 `SALES_ORDER_APPROVE` 用了**不存在的权限码** `sales_order:approve`（实际 `sales_order:edit`）、`PURCHASE_DECOMPOSE` 错配为 `purchase_request:edit`（实际 `purchase_order:edit`）——导致这两个功能原本根本没人能认领。已对齐动作端点真实权限。

### 3.2 Gap 2——主档乐观锁（防丢失更新）

- 全局 `OptimisticLockingFailureException`/`jakarta.persistence.OptimisticLockException` → 409 处理器（`GlobalExceptionHandler`，此前落 500）。
- 统一 helper `OptimisticLocks.requireUpToDate(current, expected)` + 单测 4 例。
- `V231__master_optimistic_lock_version.sql`：`clients/goods/suppliers` 加 `version BIGINT NOT NULL DEFAULT 0`。
- `Client`/`Goods`/`Supplier` 实体加 JPA `@Version`；编辑 DTO（`*SaveRequest`）回传 `version`、详情 DTO（`*Detail`）返回 `version`；`update` 显式版本校验 + flush 自动兜底。E2E 验证迁移应用 + 实体加载正常。

> **作用域说明**：覆盖业务关键且偶有并发编辑的客户/货品/供应商三大主档。简单查照类（颜色/单位/币种/账户/模具）并发编辑极少，按同一模式（本迁移 + `@Version` + DTO 回传）按需追加，非本次阻塞。
> 交易单据编辑路径已有悲观锁，无需乐观锁；资产/研发任务已用手动 `row_version` 等价机制（V183/V204）。
