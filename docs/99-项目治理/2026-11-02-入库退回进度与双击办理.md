# 入库退回进度与双击办理

日期：2026-11-02（America/Denver）。分支：`uimp/warehouse-inbound-clarity-20261102`，基线 `9a6c728c5`。这是本地实现与验证记录，不表示内部服务器、客户端或完整 CI 已更新。

## 问题与结果

到货异常在接收部分已质检、入库后，仍因超量退回未办结留在进行中。原列表显示最初申报数量和「异常已批准送检」，无法看出已入库；旧异常模型又把送检过账误称为入库。双击可处理异常只弹只读明细，必须返回勾选，办理入口不明显。

示例为申报 2.52 条、批准且已入库 2.42 条、待退回 0.10 条。新表分列申报/单据数量、已入库、合格待入库、剩余待退回和下一步。异常仍由实际退回闭环；不通过隐藏待退任务、重写状态或重复入库清除待办。

设计采用 `frontend-design`，保持 Uten 原主题、字号、单行表格与数量带单位的口径。进度列紧接原数量；状态说明流程，数量说明实物，下一步说明接手人。窄屏沿原横向表格与 Uten 操作面板；不引入系统下拉框。

## 唯一事实与公共入口

`server/.../warehouse/inbound/ProcurementReceiptProgress.java` 统一采购和委外收货明细/异常的查询连接。按原 receipt_type、receipt_id、receipt_item_id 精确关联检验行，排除红冲与赠品批次，使用检验快照 unit_rate 换回收货行单位。金额、应付、库存写入和单据原量均不修改。

- 已入库取真实 warehouse_stocked_base_qty；合格待入库取已通过但未确认入库的差额。
- 当前待退回取 PENDING_RETURN 供应商退回任务，加未记录实物退回的不合格品。任务办结后归零，原 unacceptedQty 保留为历史财务决定。
- 十进制字符串贯穿 JSON；`ProcurementReceiptProgress` Dart 模型共用格式化。没有可核对的入库事实显示「—」，不冒充零。
- 显示阶段在原 SQL 关系中确定，分页、状态筛选、facets、数量表头筛选、打印与导出共用；未引入逐行 HTTP 查询。退回任务经原异常关联的索引定位，不逐行扫描所有退回任务。

共享合同：[v1.json](../../contracts/warehouse-procurement-progress/v1.json)。旧异常/负责人 API 增量返回 receiptProgress；价格脱敏复制该只读字段，原价格权限不变。

## 双击与操作边界

| 当前任务 | 双击结果 |
|---|---|
| 可办理到货异常 | 直接打开按财务批准量继续送检的原确认框；确认后才 POST |
| 已登记待送检 | 原继续送检确认 |
| 合格待入库 / 不合格待退回 | 保持原质检结果办理页与精确检验明细范围 |
| 已入库、超量待退回 | 有原负责人/显式全读资格时打开对应退回任务；原用户+员工 owner、完成权限、expectedVersion 仍由目标页与服务端检查 |
| 无办理/退回查看资格、其他只读记录 | 打开实物详情，显示数量与下一步；菜单明确为查看处理进度 |

双击、行菜单和下一步单元格共用同一入口。等待确认期间重复打开被拦截，取消不发送命令。账号、服务器、仓库范围、权限及未知提交保护沿用原公共流程。
