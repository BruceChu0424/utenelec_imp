## 二、主表字段语义

五张在用/待启用主表（`S_Quote`/`S_Order`/`S_Out`/`S_OtherOut`/`S_Withdraw`）结构同构，共性字段：

| 字段 | 类型 | 含义 | 备注 |
|---|---|---|---|
| `ID` | int IDENTITY | 主键 | 自增，PK 聚簇 |
| `BillNo` | varchar(50) | 单据号 | **唯一索引** `IX_S_*`，业务主键 |
| `BillDate` | datetime | 单据日期 | — |
| `ClientID` | int | 客户 → `B_Client.ID` | 必填，所有销售单都有 |

| `Remark` | varchar(250) | 备注 | — |
| `Total` | decimal(18,2) | 合计金额 | 触发器/应用层维护 |
| `Status` / `Status2` | int | 单据状态 / 上一次状态 | 状态机核心，见 §四 |
| `Cancel` | bit | 取消标志 | — |
| `CurID` / `CRate` / `TRate` | int / decimal | 币种 / 汇率 / 税率 → `B_Currency.ID` | 报价单无；多币种销售 |

各单据特有：

| 单据 | 特有字段 |
|---|---|
| `S_Quote` | `Stop`（中止 bit）。最简单——无币种/税率/结帐方式 |
| `S_Order` | `SendDate`（出货/交货日）、`SellerID`（业务员 → `B_Worker`）、`ContractNo`（合同号）、`LinkPhone`、`SignAddr`（签订地址）、`BillStyle`、`SStyle`（发货地点 varchar(5000)）、`Deposit`（定金）、`Fulfill`/`Stop`（结案/中止 bit）、`CStatus`（成本状态 int） |

## 三、明细表字段语义（重点）

明细表是老库设计的「重灾区」，也是新库优化的主战场。结构比采购明细更复杂——多了一组**包材/重量/价格分层**列（`KQTY`/`Boxs`/`SPrice`/`WPrice`/`JPrice` 等）和一组**成本/BOM 展开**（`S_OrderCostItem`）。

### 3.1 基本行字段（共性）

| 字段 | 含义 |
|---|---|
| `ID` | 明细主键 |
| `BillID` | → 主表 `ID` |
| `GoodsID` | 货品 → `B_Goods.ID`（新库 `goods.legacy_id`） |
| `ColorID` | 颜色 → `B_Color.ID`（可空，无色货品为 0/null） |
| `QTY` | 数量（`S_OrderItem` 是 `float`，其余 `decimal(18,4)` — **金额数量用 float 是精度隐患**） |
| `Price` / `Total` | 单价 / 金额 = QTY×Price |
| `STotal` | 成本金额（出货/退货明细；触发器调 `RefreshTotal_PROC` 重算） |
| `UnitID` / `URate` | 单位 → `B_Unit` / 换算率（`QTY×URate` = 基本数量，用于库存写账） |
| `Weight` / `KQTY` / `Boxs` | 重量 / 件数（把/箱） / 箱数（包装辅助计量） |
| `Summary` | 摘要 |
| `CNumber` | 客户型号（varchar(500)） |
| `Discount` / `TTotal` | 折扣 / 税额 |
| `SPrice` / `WPrice` / `JPrice` | 材料价 / 压铸价 / 机加价（`float` —— 成本分项） |
| `KQTY2` | 围数（`float`，包装尺寸派生） |

## 四、触发器揭示的业务规则（设计金子）

老库 91 个触发器中，销售模块 **7 个**（dump `biz_triggers.txt` 行 1374–1623）。它们把业务逻辑全下沉到触发器，新库必须保留语义、改用 Service 层。

### 4.1 状态机驱动一切（`Status` / `Status2`）

```sql
IF (@Status <> 0 AND @Status2 <> @Status)   -- 状态确实变了才触发
```

- `Status = 0`：草稿，**不产生任何业务影响**
- `Status = 1`：审核生效 → 出货扣库存 / 回写上游订单 / 重算成本 / 生成应收单
- `Status = -1`（反审/红冲）：**反向冲销**（用 `@Status` 当乘数：`QTY * @Status` 自动反向）
- `Status2` 记录「上一次状态」，用于判断状态迁移方向

`TRI_S_Order` 主表触发器（行 1374）：状态变化时，**级联更新所有子明细的 `LStatus`** —— `UPDATE S_OrderItem SET LStatus=@Status WHERE BillID=@BillID`。这是单据头对明细的状态下发。

> 新库语义保留：单据头有 `status` 状态机，审核/反审驱动下游，红冲做反向冲销。

### 4.2 全链路回写（审核生效时）

```
S_Order（订货）          ──LStatus──▶  S_OrderItem：明细状态随主表
S_Out（出货）            ──OrderID──▶  S_OrderItem：RQTY += QTY×Status, OutNo 追加/移除 BillNo
S_OtherOut（其它出货）   ──(空挂)──▶   不回写 S_OrderItem（触发器中 OrderItem UPDATE 已注释，见行 1462-1471）
S_Withdraw（退货）       ──OutID───▶   S_OutItem：    WQTY += QTY×Status, SWTotal += Total×Status, SWDrawNo 追加/移除
                        └─OrderID──▶  S_OrderItem：WQTY += QTY×Status, SWDrawNo 追加/移除
S_OrderCostItem（BOM）   ──BillID──▶   S_OrderItem.CStatus=1 (当 Class<>0)
```

回写是**逐条 `UPDATE WHERE ID=`**，方向随 `Status` 正负（`@Status=1` 追加，`@Status=-1` 反向扣减）。

> ⚠️ `S_OtherOut` 触发器（行 1448–1504）里**回写 `S_OrderItem` 的整段被注释掉**（`/* ... */`）。这意味着**老库实际行为：其它出货不挂订单链、不冲减订单已发量**，只动库存。`S_OtherOutItem.OrderID` 字段虽然在，但是孤儿。新库要尊重这个语义——「其它出货」是新库存事件，不进订单累计。

### 4.3 结案标志（`Fulfill`）—— `CheckFulfill` 触发器

`S_OrderItem` 上的 `CheckFulfill`（行 1434）：明细 `UPDATE` 后，重算主表 `S_Order.Fulfill`：

```sql
IF EXISTS(SELECT ID FROM S_OrderItem
          WHERE (BillID=@BillID AND QTY-RQTY+WQTY-FlagQTY > 0)
             OR (BillID=@BillID AND QTY=0))
   Fulfill = 0   -- 未结案
ELSE
   Fulfill = 1   -- 已结案
```

**结案条件**：所有明细的「订单量 - 已发量 + 已退量 - 标记量 ≤ 0」且无 0 量行。与采购的 `QTY - RQTY + WQTY <= 0` 同型，多了 `FlagQTY` 扣减项（人工标记的「不交付量」）。

### 4.4 库存台账（`StockGoods`）—— 与销售强耦合

`S_Out` / `S_OtherOut` / `S_Withdraw` 审核时直接写 `StockGoods`（游标逐条），套路与采购 `P_In` / `P_Withdraw` 完全一致（doc 14 §4.4）：

- **台账粒度**：`StockID + GoodsID + ColorID + Year`
- **按月分列**：`OUTQTY01..OUTQTY12` / `OUTWeight01..12` / `OUTTotal01..12`（出货），`INQTY*`（退货入库）
- **当前余额**：`QTY` / `Total`（同时影响 `Year > 当前年` 的期初行）
- `S_Out` 审核 → `OUTQTY<月> += 量`，`QTY -= 量`（出库扣减）
- `S_OtherOut` 审核 → 同上（其它出库同样扣减）
- `S_Withdraw` 审核 → `INQTY<月> += 量`，`QTY += 量`（退货入库反向）
- **跨年补期初**：若当年无该货品的台账行且当前年无记录，自动 `INSERT` 一行 `Year=今年` 的余额行（保证后续年份余额连续）

> ⚠️ `QTY` 在写账前先 `set @QTY=@QTY*@URate` 换算到基本单位（行 1473/1533/1604），明细单位的数量与基本单位的数量通过 `URate` 转换。新库 `stock_movements` 流水只存基本单位量 + 原始量双口径。
> ⚠️ **销售/采购触发器都用 `exec('UPDATE StockGoods SET ...')` 动态 SQL** 拼月份列名，是老库按月分列设计的硬伤——**不可静态优化、不可跨年平滑**。新库改用流水行（每月一行）。

### 4.5 应收单（`M_in`）自动联动 —— 销售比采购多一层财务耦合

`S_Out` 触发器在 `Status=1`（审核）时（行 1559–1564，dump 文本被截断，完整源需 `sp_helptext TRI_SOStockItem`）：

```sql
if(@Status=1)
BEGIN
   if(@Last_Date is null) set @Last_Date=@BillDate
   INSERT INTO M_in(BillNo, ClientID, MIn_Date, Last_Date, Total, M_In, M_Rare,
                    Work_ID, Note, Paid, PaidDate, BStyle, PStyle, BillID, CurID, CRate, ...)
   VALUES(@BillNo, @ClientID, @BillDate, null, 0, @Total, -@Total, ...)
END
```

即 **销售出货审核自动在钱流 `M_in`（应收账款）插一行**——`Total=0`、`M_In=@Total`、`M_Rare=-@Total`（实收=0、未收=总额）。`S_OtherOut` 触发器（行 1499–1504）同样有这段（被注释掉与否需看完整源）。`S_Withdraw` 触发器行 1623 后的 dump 也被截断，推断结构相同（红冲时反向）。

> 🔎 这是销售与采购**最大的不对称**：采购入库 `P_In` 触发器**不**自动生成 `M_Out`（应付）——应付由会计在钱流模块单独开单。而销售出库 `S_Out` **会**自动生成 `M_in`（应收）。新库需保留这个语义差异：**销售审核 → 自动产生应收流水**；采购审核 → 不自动产生应付。
> ⚠️ dump 文本在 1504/1564/1623 行多处被 `inspect_sales.ps1` 截断（约 1000 字符）。完整触发器源码需用 `sp_helptext 'TRI_SOStockItem'` 等重新导出。**这是本文档最重要的待确认项**——尤其 `S_OtherOut` 与 `S_Withdraw` 的 `M_in` 插入是否被注释、参数列表（`BStyle`/`PStyle` 取值）需以完整源为准。

### 4.6 `S_OrderCostItem` BOM 联动 —— `CheckChange2` + `Level`

`CheckChange2`（行 1385）：明细成本项更新时：

1. 临时 `disable trigger CheckFulfill` 和 `TRI_S_OrderCostItem_Update`（防递归）
2. 若 `Class<>0`（子件），置 `S_OrderItem.CStatus=1`（标记有成本展开）
3. 若有父 `ParentID<>0`：检查所有兄弟子件是否 `QTY > OrderQTY`/`QTY > PDrawQTY`，决定父行的 `OrderQTY`/`PDrawQTY` 是否清零（语义：子件超量则父不再需要采购/领料）

`TRI_S_OrderCostItem_Level`（行 1418）：`INSERT` 时递归算 `Level`（BOM 深度，防死循环 `@Level<30`）。

> 与 `F_PlanCostItem` 同型，只是销售侧未铺开。新库建表保结构，迁移原样落，**BOM 重算逻辑后置到未来成本模块**（同 [18] §五 F_PlanCostItem 决策）。

### 4.7 与采购触发器的关键差异

| 项 | 采购（doc 14） | 销售（本文） |
|---|---|---|
| 全局开关 `(SELECT ISplan FROM SystemAccinfo)` | **有**（影响生产联动是否触发） | **无**（dump 全文搜索 `ISplan` 0 匹配）—— 销售触发器**不做**生产计划联动判定 |

dump `biz_s_views_def.txt` 含 11 个 `View_S_*` 视图定义。它们 `JOIN` 主从表 + 基础数据带名 + 计算列，是**老库报表与查询口径的来源**：

|---|---|---|

| `View_S_Order` / `*Item` | `B_Client` / `B_PStyle` / `B_Currency` / `B_Worker` / `B_YesOrNo` / `Sys_Operator` / `B_Veil` | 销售订单主从，含「未发数量 = QTY - 发货数量」「需产数量」「订单数量」等关键报表派生列 |
| `View_S_Order2` | 同上 + `View_S_OrderCostItem` | 订单 + 成本展开联表（用于 BOM 视图） |
| `View_S_OrderCostItem` / `*2` | `View_Goods` / `B_Color` / `B_Provider` / `View_StockGoods2` / `View_P_OrderNoRec` / `StockSLabel` | **MRP 核心视图**：实订/实排/计划需购/扣成品需购 公式（依赖库存余额 + 采购在途 + 已领料） |
| `View_S_Out` / `*Item` | `B_Client` / `B_Storage` / `B_PStyle` / `B_Currency` / `B_Step` / `B_Worker` | 销售出货主从；`View_S_OutItem` JOIN `S_OrderItem ON OrderID` 带出「订单数量」 |
| `View_S_OtherOut` / `*Item` | 同 `S_Out` | 其它出货（结构与 `S_Out` 几乎相同视图） |
| `View_S_Withdraw` / `*Item` | 同 `S_Out` + `B_Unit` | 销售退货；明细含「处理方案(`qlfa`)/责任单位(`zrdw`)」退货专属字段 |

## 七、老库设计的核心问题（新库要解决的）

1. **业务逻辑全埋在触发器**（状态机 / 库存 / 应收 / 回写 / BOM）→ 换库即丢失、不可测、不可审计。新库上移到 Service 层事务。
2. **审核即生应收（`S_Out → M_in`）**——销售与钱流强耦合 → 跨模块副作用难追踪。新库保留语义但显式化（销售审核 Service 显式调钱流 Service 创建应收单，事务可见、可回滚）。
3. **按月分列库存台账**（`OUTQTY01..12` 写死 + `exec()` 动态拼列名）→ 跨年复杂、不可静态优化、扩展僵化。新库用 `stock_movements` 流水 + `stock_balances` 余额（V45 已建，销售挂 `movement_type=3/4/20`，见 [18] §三）。
4. **状态字段冗余混乱**（`Status`/`Status2` + `Fulfill`/`Stop`/`Cancel` + `CStatus`/`LStatus`）→ 多套体系并存。新库用单一 `status` 枚举 + `is_closed` 派生 + 业务中止用独立字段。
5. **多值空格分隔溯源**（`OutNo`/`SWDrawNo` varchar(250)，触发器 `replace` 管理）→ 性能与正确性双输。新库用真 FK 骨干（`S_OutItem.OrderID`、`S_WithdrawItem.OutID/OrderID`），多值降级 `source_doc_no TEXT` 合并文本。
6. **`S_OrderItem` 一行塞 15+ 数量列**（原生量 + 销售累计 + 生产累计 + 采购累计）→ 跨模块紧耦合、回写顺序敏感。新库只留原生量，累计量从下游聚合或专门回写表。
7. **`float` 存金额数量**（`S_OrderItem.QTY`/`SPrice`/`WPrice`/`JPrice` 均 `float`）→ 精度风险。新库统一 `numeric`。
8. **`S_Out` 与 `S_OtherOut` 字段集完全同构**却拆两表 + 两套触发器 + 两套视图 → 代码重复、维护双倍。新库可合并为 `sales_shipments` 单表 + `shipment_type` 区分（待 [20] 终定）。
9. **人员字段双轨**（`MakeID/ApproverID → Sys_Operator` vs `SellerID/SenderID → B_Worker`）→ 历史包袱。新库统一指向 `employees`，留空 + 后续回填。
10. **`S_OrderCostItem` BOM 展开未启用却建了完整 MRP 公式视图**（`View_S_OrderCostItem` 一长串「需购」公式）→ 老库想做 MRP 没做起来。新库建空结构保未来，重算逻辑后置。
