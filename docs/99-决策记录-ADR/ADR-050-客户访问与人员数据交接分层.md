# ADR-050：客户访问与人员数据交接分层

> 日期：2026-08-25
> 状态：V393–V399 与前后端源码候选；本地聚焦验证中，目标库/UAT/发布未完成
> 关联：ADR-011、ADR-023、ADR-045、V86、V89、V91、V233、V261、V393–V399

## 背景

客户归属策略原本已经覆盖内销、外贸和 OEM，但存在四个互相放大的缺口：

1. `DEPT_SALES`、`DEPT_RAIL` 默认持 `client:view:all` / `sales:view:all`，使普通销售实际看全量；
2. 新客户可保存空负责人，空值又按公共客户全员可见；
3. `user_data_scopes` 的“加看”同时被用于写权限；
4. 离职页只有交接备注，没有数据盘点、接手人、阻塞项或真实转移。

客户地址簿还存在嵌套对象越权：只要知道他人客户 UUID，旧实现可能读取或修改其地址。

## 决策

### 1. 只保留三种清楚的业务动作

- **额外查看**：只读，不改变负责人；可按某负责人整批设置，也可只共享一个客户。
- **变更负责人**：改变当前业务责任，必须填写原因、使用 CAS，并保留追加式事件。
- **人员交接**：默认一个接手人，可选择业务范围；先预览，全部可自动项原子完成后才成功。

不建设任意工作流设计器，也不把功能权限页伪装成对象数据范围。

### 2. 客户统一规则，不区分内销、外贸或 OEM

- 新客户负责人默认当前登录员工；负责人必须是当前员工且具有启用账号。
- `owner_employee_id IS NULL` 表示“待分配”，普通员工不再把它当公共客户；持 `client:assign` 或显式全量权限者可处理。
- 单客户 `client_visibility_grants` 永远只读；它不能授予编辑、状态、删除或负责人变更。
- 普通客户编辑不得携带负责人变化；负责人和可见人只走 `/master/clients/{id}/access`。
- 列表、搜索、字典、facets、详情、导出、销售引用和地址簿使用同一 `ClientAccessPolicy`；不可达对象返回 404。
- 手工改负责人时，仍在职且账号启用的前负责人默认保留为单客户只读可见人，避免既有草稿变成死单；确认已无在途业务后可显式移除。
- `client:assign` 不从 `client:edit`、部门或角色默认继承，仅允许超管或中央个人显式授权；专用候选 API 不要求开放 HR 档案权限。
- 页面默认排除 `LEGACY-FIN-CL-*` 财务占位；列表 total、facets、dict、picker、导出和负责人候选数量使用同一口径。

### 3. 可见与可写责任物理分离

`OwnerVisibility.OwnerScope` 分为：

- `visibleOwners`：本人、正式交接来源、手工额外查看来源；
- `writableOwners`：本人和正式交接来源；
- `seeAll`：超管或显式 `*:view:all` 例外。

因此 `user_data_scopes` 只增加查看，并精确绑定 raw owner：授权 A 只看 A 原历史，不会因 A 交接给 B 而扩大到 B 的其它数据。每行同时保存 owner 当时的任职代际（rehire 计数）；同一任职期有效，A 复职后旧行保留为审计事实但不再授予查看，管理员显式整体替换后才写入新代际。recipient 必须在职且账号启用，raw owner 只要求员工存在且未删除。

显式 `*:view:all` 是受控全量数据范围；只有再持有对应 edit/delete/status 等功能权限时，才按“功能权限 × 全量数据范围”操作公司级对象。普通销售的部门默认全量权限已经收回。

客户主档 owner 会从 A 转到 B，因此原“整批查看 A 客户”的 client scope 在交接时仅对本批实际转出的客户展开为逐客户只读 grant，再移除该 client scope；不得粗暴改成 B。其它 scope 保留 raw A 历史只读。采购、委外、生产、仓库、财务和销售单据只有正式交接才把来源 owner 加入接手人的可写集合。货品归属开关关闭时仍按既有决策全员可见。

### 4. 历史操作人与当前责任分离

交接绝不修改：

- `maker_id`、`approver_id`、`created_by`、历史 `updated_by`；
- 审批、库存、质量、总账和其它追加式事件的 actor；
- 已过账金额、数量、状态或快照。

客户、货品、供应商、模具等可变主档负责人实际转给接手人。历史单据保留原 owner/maker，通过 `employee_data_handovers` 的最新 `source + scope` 交接边，使接手人获得相应历史范围。交接边保存 source 与 target 双方任职代际：两端任一复职，旧边立即失效；先选当前 source 代际的 sequence 最新边，再校验该唯一最新 target 代际，target 失效时不得回退更旧边。新下游单据只沿仍匹配双端代际的链路解析当前责任人。

### 5. 离职必须先完成真实交接

离职顺序为：

1. 校验权限、稳定离职类型、日期、原因和四项人工确认；以整笔 `requestId` 获取全局 handover coordinator 与请求 advisory lock；
2. 查询 `employee_offboarding_events`：事件保存 source 与默认接手人的任职代际；同 payload、双端代际仍匹配且来源员工仍 resigned 才幂等返回，任一端复职、异 payload 或旧任职 requestId 返回 409；新请求先按 UUID 锁 source/default target，再写 `EXECUTING` 事件；
3. 在同一事务把员工标为 `resigned` 并 flush，数据库 current-responsibility guard 随后阻止并发新增责任；
4. 按 scope 解析既有有效接手链；已有 sales→B、production→C 时继续由 B/C 接手，默认 D 只接尚未交接或既有接手人已失效的范围；
5. 先检查部门负责人、生产、资产、访客和组织环等阻塞；无阻塞时按实际 target 分组执行。批次 `requested_scopes` 保存显式命令，交接 scope 子表只写存在真实责任或历史访问的 effective scopes，release-only/空 scope 不得产生未来路由边；
6. 客户 owner 交接把有效 client raw scope 精确展开为本批转出客户的逐客户 viewer，不得让接收人看到新 owner 原有客户；manual 且 source 仍 current+active 时保留 source viewer，offboarding 不保留；
7. 释放认领、驳回在途资料申请，停用个人 permission override 与经理委派，清来源账号作为 recipient 的数据范围/单客户 viewer，把未完成附件上传会话转为 `EXPIRED` 并进入暂存对象清理链，关闭 remote access 并设置复职后强制改密；
8. 写任职历史（含 requestId 与人工确认），最后停用账号、撤销 refresh token 并把 offboarding event 置为 `COMPLETED`。

任何一步失败全部回滚，账号不会先被停用。

以下项目不允许静默改写，必须先在专业页面处理：

- 已派工或生产中的执行段；
- 接手人不属于原车间/班组的待派工执行段；
- 未终态固定资产或待摊责任；
- 未来已批准访客；
- 会形成员工直属上级环路或交接图环路的选择。

复职是新任职：先按 employee → user 锁序锁定并复验绑定，再恢复员工/账号 active，保持 remote access 关闭并强制改密；个人 override、经理委派、单客户共享不会恢复，raw owner scope 和 formal handover edge 因任职代际不匹配自动失效。管理员在复职后明确新增的授权才属于新任职。

### 6. 并发、审计与锁序

- 客户访问设置使用 `clients.access_version` CAS；原因写入 append-only `client_access_change_events`。
- 人员交接先获取同一常量事务级 coordinator advisory lock，再获取 request UUID advisory lock；HR 低频交接彼此串行，随后按 employee → business row → user → grant/subtable 顺序加锁并写结果摘要。
- 同一用户/范围的额外查看整体替换使用 advisory lock + expected owner 集合比较，冲突返回 409。
- 当前员工引用触发器覆盖客户/货品/供应商/模具及询盘、访客、研发、生产段、采购到货责任、资产/待摊、直属上级和认领等当前责任。业务行 BEFORE trigger 与 offboard 反向竞争时 PostgreSQL 仍可能让一方回滚，锁异常统一映射 409“刷新重试”，不伪称绝无死锁。
- V396 对全部 `public` 业务表重新执行 fail-closed 审计覆盖 sweep。
- V398 将同次数据范围写入的 recipient/owner UUID 排序后统一锁员工，再锁 recipient user；owner 可为离职历史员工，recipient 仍须 current + active。
- V398 在数据库层约束 requested scopes 唯一且为 1–8 个白名单值；effective child scope 插入先锁父批次，只允许父状态 `EXECUTING` 且 child 属于 requested，完成后禁止再加边；任职历史 UPDATE/DELETE 全拒。
- V399 为 `users` 增加独立 JPA `@Version` 写入 CAS；它与 token/权限快照用的 `auth_version` 分离，登录、改密、管理员和手机号同步的旧实体快照不能覆盖离职最终 disabled/remote/凭据状态。
- 已签发的对象存储预签名下载 URL 无法由应用即时撤回，只依赖短 TTL；这是明确残余风险，不能宣称离职时已撤回。
- 客户共享查询使用数据库 `EXISTS`；多 SQL 的 total/facets/export/access GET 使用 `REPEATABLE_READ`，同一请求不混合并发前后快照。

## 权限与 UI

- `client:assign`：设置客户负责人和单客户只读可见人。
- `employee:handover`：预览和执行人员数据交接。
- 全局权限页使用“操作权限 / 可查看数据 / 账号安全”；数据卡明确显示“仅本人 / 额外查看 N 人 / 查看全部覆盖 / 功能未启用”。
- 客户详情直接提供“负责人和可见人”，无需去全局权限页寻找。
- 离职向导显示员工身份、接手人、真实数量、历史不改说明和阻塞恢复路径。
- 客户列表/详情由服务端下发 `writable` 与 `accessManageable`，只读对象不展示必然失败的编辑、状态、删除、地址或归属动作。

## 发布边界

源码、迁移和本地测试只形成候选。目标库仍需：

1. `flyway_schema_history` 与 V393–V399 字节/校验和只读核对；
2. 非空恢复副本升级，盘点空 owner、离职 owner、无账号 owner 和历史授权；
3. 两名销售、销售主管、HR、财务/生产等真实账号的允许/拒绝矩阵；
4. 客户地址已知 UUID 负测、离职交接并发、恢复演练和签名发布决定。

在这些门禁完成前，不得写成已部署或已上线。
