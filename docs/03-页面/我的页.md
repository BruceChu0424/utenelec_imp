# 我的页

> 路由：`/profile` · 实现源：`lib/features/profile/pages/profile_page.dart`
> 关联：`/profile/edit` · `/profile/me/changes` · `/profile/me/department` · `/hr/profile-changes` · `/hr/profile-changes/:id`
> 最后更新：2026-08-28 · 状态：v7 — 档案区 Tab 化（基本信息 / 组织与合同 / 联系与车辆 / 任职记录 /
> 我的文件），与人事端员工详情页同一范式（顶部折叠 + Tab 吸顶 + Tab 内滚）；「我的车辆与号码」
> 「我的文件」独立页吸收为 Tab，路由下线。档案值统一以对象限定的 `GET /api/profile/me`（`EmployeeProfile`）
> 为准，字段维护口径沿用 v6（直接生效 / 需人事审核 / 人事维护），薪酬与银行保持有意不在本页展示。

## 一、定位

给所有员工使用的个人资料中心 + 业务快捷入口。同时承载**个人信息修改闭环**的员工侧入口。

- 解决的问题：
  - 查看自己的姓名 / 工号 / 部门 / 岗位 / 联系 / 组织 / 紧急联系人等完整字段
  - 查看本部门、本人档案文件、车辆/备用号码和资料修改申请
  - **自助修改个人信息**（直改字段即时生效；需审核字段提交后走 HR 审批）
- 产品位置：底部 / 侧边导航"我的"项。

## 二、入口与导航

- 进入路径：
  - 底部 / 侧边导航"我的"项
  - 工作台首页（如有相关入口）
- 离开去向：
  - 「修改我的信息」→ `/profile/edit`
  - 「修改密码」→ `/change-password`（Phase 1 已有路由）
  - 「我的修改申请」→ `/profile/me/changes`（`goFrom` 带 `?returnTo=/profile`，返回键恒回"我的"）
  - 「我的部门」→ `/profile/me/department`（同上带 returnTo）
- 页内切换（不离开 `/profile`）：档案区 5 个 Tab——基本信息 / 组织与合同 / 联系与车辆 /
  任职记录 / 我的文件。原 `/profile/me/vehicles`、`/profile/me/documents` 独立页已吸收为
  Tab（v7），路由下线；分组名与员工详情页对齐，「我的档案就是人事看到的我」。

## 三、字段展示与维护口径（v6）

本人资料不再复用需要宽泛 `employee:view` 的他人详情端点，而调用不接受目标员工 ID 的
`GET /api/profile/me`。服务端只从当前 `AuthUser.employeeId` 解析对象，因此员工可看到自己的个人
PII 明文，但不会因此获得查看同事 PII 的 `employee:pii:view`。姓名、工号、部门、岗位等档案字段也以
该响应为准；会话 `AppUser` 只提供认证状态和角色徽标，避免调岗或改名后两份值漂移。

| 分组（Tab） | 显示字段 | 本人维护口径 |
|---|---|---|
| 基本信息 | 工号、姓名、性别、证件类型/号码、出生日期、民族、政治面貌、婚姻状况、现住址、户籍地址、紧急联系人 | 姓名需人事审核；民族/政治面貌/婚姻状况/现住址直接生效；性别/出生日期由获授权人员编辑；证件类型/号码当前无补录 UI；修改第一紧急联系人需人事审核 |
| 组织与合同 | 部门、岗位、直属主管、入职/转正日期、状态、用工性质、工作地点、工位、账号状态、合同摘要（类型/起止/试用期/续签）、任职轨迹、隐私边界脚注 | 工位直接生效；部门/转正/离复职走专用命令；用工性质/工作地点由获授权人员编辑；合同与轨迹只读由人事维护 |
| 联系与车辆 | 主手机、备用手机号、办公电话、邮箱 + 车辆卡 + 备用号码卡 | 主手机需审核；办公电话/邮箱直接生效；车辆与备用手机号在 Tab 内「管理」弹层直接维护并即时生效 |
| 任职记录 | 入职/调岗/转正/离职/复职轨迹 | 只读，由人事专用业务命令维护 |
| 我的文件 | 合同、证件、学历、照片等本人档案附件 | 本人只读；上传、删除和设头像由人事按附件权限维护 |
| 我的部门 / 修改申请（身份组入口） | 安全花名册入口、本人待审申请数 | 只读入口；修改申请可查看或在允许状态下撤销 |

**有意不对齐项**：员工详情的薪酬与银行区需要独立
`employee:compensation:view` / `employee:pii:view`。仅有 `profile:edit:self` 时不会下发这些字段；
账号若另持独立权限，同一 DTO 可按权限返回，但“我的”页仍有意不渲染。本人月度收入继续从工资条查看。
这样两页共享字段语义和状态字典，但不会为了视觉一致扩大财务敏感数据范围。

页面必须区分四种状态：加载中、加载失败（含重试）、账号未绑定员工档案、字段确实未登记。不得再把
前三种情况和真实空值统一画成“—”。

## 四、Hero 用户卡 + 两个 CTA

```
┌───────────────────────────────┐
│ 👤  张三                       │
│     生产部 · 操作工            │
│     [员工]  [HR]  …           │  ← 角色 chip
├───────────────────────────────┤
│ [修改我的信息]  [修改密码]     │  ← 两个 CTA，全员可见
└───────────────────────────────┘
```

- 「修改我的信息」——**全员可见**（任何登录员工都能进编辑页；能改什么由编辑页字段策略定）
- 「修改密码」——任何登录员工可见，路由 `/change-password`
- Hero 的姓名、工号、部门和岗位以 `GET /api/profile/me` 返回的当前员工档案为准；角色徽标仍来自
  登录会话，只用于说明当前账号身份，不参与字段可见性或编辑授权。
- 编辑页（v7.1）分区与查看页 Tab 卡片一一对齐：**基本信息 → 地址 → 紧急联系人 → 联系方式 →
  组织信息**，只列可编辑字段；原 hrOnly 锁定行已砍（查看页灰徽章已说明），改为顶部一行策略图例
  （绿=提交即生效 / 黄=需 HR 审核 / 其余字段由人事维护）。每个字段仍显示“可直接修改”
  或“需 HR 审核后生效”徽章；页面另在有待审申请时置顶冲突提示。表单必须在提交前执行真实
  `FormState.validate()`，非法手机、邮箱和办公电话不能只显示错误后继续提交。
- **行级铅笔快捷入口**（v7.1）：查看页每个可编辑字段行尾有小铅笔（直改=绿、需审核=黄），
  点击跳 `/profile/edit?field=xxx`，编辑页滚动定位并聚焦该字段；Hero 的「修改我的信息」保留为
  整表编辑入口。数据复用 `myEmployeeProfileProvider`，从「我的」页进入编辑页零额外请求。

- 点击 → `/profile/me/department`（全页面，`context.go`，主 Tab 前缀子路由须 go 不 push）。**布局复用「部门管理」页（`/department`）**：expanded 全高分栏（左组织树 `UtenDepartmentTreeView` | `UtenSplitView` 可拖分割线（初始 300、双击复位、宽度本地记忆）| 右详情），compact/medium 组织树进 `endDrawer`。右侧详情 = `MasterDetailCard`（部门概况，只读：在册 / 子部门 / 负责人 / 编制 + 路径）+ 安全花名册（`UtenPersonCard`，**负责人 / 管理人排最前**，安全字段）+ 负责人说明。权限不在本页配置；合法负责人到对应业务页右上角“权限设置”处理本页权限。

- **点击员工弹「只读联系卡」**（2026-08-06 修复）：`_staffRow` 的 `UtenPersonCard` 原先无 `onTap`（点了无反应）；现点击弹底部联系卡（compact）/ 居中弹窗（expanded），展示头像 + 姓名 + 负责人/本人徽标 + 岗位·部门 + 工号 + 办公电话（可拨号 `tel:`）+ 邮箱（可发件 `mailto:`）。**只走花名册安全字段，不进 `/employee/:id`**——普通员工无 `employee:view`，跳受限路由会被守卫拦下转 `/access-denied`。安全字段在原有基础上补了 `departmentName`（子树聚合后用于区分员工所属下级部门）。

- **统一关联搜索（2026-08-14）**：组织树顶部一个搜索框同时匹配授权分支内的部门名称/编号与安全花名册员工姓名/工号。页面只从分支根调用 `/api/my-department/roster`，用返回的 `departmentId` 展开完整祖先路径并定位，绝不回退到 `/api/org/employees` 全员接口。内容命中分支保留同词过滤；纯部门命中展示该部门全部花名册；输入和手动点树立即使旧请求失效。compact 正文与抽屉输入同步，加载、失败、无结果均显式可见。共享契约见 [UtenHierarchySearch](../02-组件库/UtenHierarchySearch.md)。

## 五、响应式布局（v7 Tab 化）

- compact（手机）：单列。Hero + 我的部门 + 我的修改申请随上滑折叠收起（
  `UtenCollapsingHeaderScrollView`），Tab 栏吸顶，各 Tab 正文（ListView）内滚。
- medium（平板）：同 compact 结构，内容居中 ≤720dp。
- expanded（桌面）：双列。左 380dp 身份组（Hero + 我的部门 + 我的修改申请，超高自滚）固定，
  右栏 TabBar 常驻顶栏 + TabBarView 内滚（无折叠，Tab 天然钉在右栏顶部）。
- Tab 栏与员工详情页同款：`isScrollable` + `tabAlignment: start`，吸顶时补不透明底色
  （`scaffoldBackgroundColor`）避免正文透出；Tab 内 ListView 无显式 controller，
  自动拾取 NestedScrollView 注入的 PrimaryScrollController 参与联动。
- 返回导航修复（v7）：身份组快捷入口改 `goFrom`（带 `?returnTo=/profile`），配合子页
  `UtenBackButton(backTo(defaultPath: /profile))`——从「我的」进「我的部门 / 我的修改申请」
  再点返回恒回「我的」，不再落入工作台兜底。

## 十、权限要求

- **全员可见**——「修改我的信息」与「我的修改申请」入口对所有登录员工开放，不挂权限点路由守卫，也不按权限点控制按钮显隐
- 数据范围：仅本人；他人看不到自己的页面
- 本人资料读取接口仍要求全员基础权限 `profile:edit:self`，且对象 ID 只能从认证主体解析；它不授予
  `employee:view`、`employee:pii:view` 或 `employee:compensation:view`。
- 字段级控制（在编辑页 + 后端 `ProfileFieldPolicy`，单一来源）：
  - 直改字段（民族 / 政治面貌 / 婚姻 / 现住址 / 办公电话 / 邮箱 / 工位）——提交即生效
  - 需审核字段（姓名 / 户籍 / 手机 / 紧急联系人）——提交后进 pending 批次，HR 审批通过才合并
  - HR 专属字段（性别 / 生日 / 工作地点）——员工页只读，提示「请联系人事」
- 后端 `profile:edit:self` 权限点保留（`employee` 角色全员基础包已覆盖），用于接口鉴权与未来「禁止某员工自助改」的兜底；**前端入口不再依赖它**
- **我的文件 Tab**：不挂守卫（登录即可见 Tab），数据随 `GET /api/profile/me` 一并返回且需
  `attachment:view`（V280 默认授予全部在职部门）+ 对象级限本人（`EmployeeAttachmentAccessPolicy`），
  无权限点时后端降级为空列表；前端检测无 `attachment:view` 时 Tab 内显示无权提示（不报错）；
  上传/删除无入口——由 HR 在员工详情「档案文件」Tab 统一维护

## 十一、边界情况

- 「修改我的信息」「我的修改申请」入口全员可见可点；若当前账号未绑定员工档案，服务端返回
  `404 NOT_FOUND`，只读页和编辑页都显示“当前账号未绑定员工档案”独立空态。
- 本人档案加载中显示进度；失败显示错误与重试；当前账号未绑定员工档案显示独立空态；只有响应成功但
  某字段确实为空时才显示「未登记 / —」。
- 普通 `GET /api/org/employees/{id}` 仍按他人查看权限脱敏；本次本人对象例外不得扩散到该端点。
- 仅凭本人对象例外和 `profile:edit:self` 不返回银行/薪酬；若账号另持独立读取权限，服务端仍可按权
  返回，但“我的”页固定不渲染。
- 我的修改申请网络异常：占位「—」+ 顶部 appError 提示
- 我的文件 Tab：无 `attachment:view` 显示无权空态；附件下载失败走附件组件自身错误态；
  未绑定员工档案时不渲染 Tab 档案区（页面级独立空态）
- 性能档 = lite：Hero 卡 boxShadow 关闭、CTA 动画简化
- 网络断开：当前没有本人档案离线缓存；页面显示加载失败与重试，不把旧会话快照冒充完整档案。

（聚合 PROFILE_CHANGE=batchId，落点 `/hr/profile-changes`）。办结点：HR 批准/驳回，以及**员工在

reason=CANCELLED，2026-09-10 补闭环——此前撤销后 HR 弹卡会一直悬挂）。通知与业务同事务。

## 附录 C：两张信息变更列表的统一表格契约（2026-09-09 表格化，2026-09-10 表头筛选 + 批量驳回）

两页都用全站统一的 `MasterDataTableView`，「已选 N 项」只由 `UtenSelectionSummaryPill` 呈现。

### C.1 我的信息变更 `/profile/me/changes`（`Key('my-profile-changes-table')`）

| 列 key | 列名 | 说明 |
|---|---|---|
| `fields` | 变更字段 | `fieldLabels` 顿号连接 |
| `itemCount` | 项数 | number |
| `status` | 状态 | **带表头筛选** |
| `submittedAt` | 提交时间 | date |
| `reviewComment` | 审核信息 | HR 意见（驳回原因等），无则留空 |

- 表头「状态」筛选桶 = 顶部分段状态集（待审 / 已生效 / 已驳回），选中即切分段、
  下推后端 `GET /api/profile/me/changes?status=` 并回第 1 页；选「所有」= 全部段。
- 无多选：本人只能撤销自己的 pending 批次，逐条语义。
- 行双击开本批「旧→新」差异弹窗；行右键/长按菜单：查看差异 / 撤销申请（仅待审）。

### C.2 HR 信息变更队列 `/hr/profile-changes`（`Key('hr-profile-changes-table')`）

| 列 key | 列名 | 说明 |
|---|---|---|
| `employeeName` / `employeeCode` | 员工姓名 / 工号 | |
| `departmentName` | 部门 | 员工**当前**所属部门（非提交时快照）；**带表头筛选** |
| `itemCount` | 变更项数 | number |
| `fieldCodes` | 变更字段 | 机器码顿号连接 |
| `submittedAt` | 提交时间 | date |
| `status` | 状态 | **带表头筛选** |

- **部门筛选接后端（2026-09-10）**：桶来自 `GET /api/hr/profile-changes/facets?status=`
  （`ProfileChangeRepository.countBatchesByDepartment` 按状态聚合 `COUNT(DISTINCT batch_id)`），
  选中后下推 `GET /api/hr/profile-changes?departmentId=` 并回第 1 页。
  此前 bucket 只从当前页 items 聚合、过滤也只裁剪当前页，第 2 页的命中行根本看不到。
- 「状态」筛选桶 = 三个队列状态，选中即切顶部分段并回第 1 页（与分段同一口径）。
- **待审段多选批量**：`idOf=batchId`，右下角「批量通过(N)」「批量驳回(N)」，
  逐批调用 `POST /api/hr/profile-changes/{batchId}/review`（幂等，服务端逐批事务把关）：
  - 批量通过 → `showUtenReviewerConfirmDialog`（含 `UtenReviewerResponsibilityNotice`，
    actionLabel「信息变更审核」）；
  - 批量驳回 → 公共 [`UtenBatchRejectDialog`](../02-组件库/UtenBatchRejectDialog.md) 一次填原因
    （原因必填、内置责任提示），逐批应用同一原因；
  - 单次上限 50 批，单批失败不中断整批，失败聚合提示；结束后刷新队列、筛选桶与导航徽章。
- 行双击用 `goFrom` 进批次详情（写 `?returnTo`），详情返回键按全站契约回本队列。
