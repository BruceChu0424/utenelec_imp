# 生产履约任务工作台（仓库 / 采购 / 委外）

> **文档版本**：v1.1
> **更新日期**：2026-08-01
> **代码基线**：历史 V1 基线 + 2026-08-01 关联单据权限和真实动作加固；最终以候选提交与验证报告为准。
> **当前结论**：V1 页面和同源查询已有源码及历史自动化证据；`COVERED` 只证明数量/peg 覆盖，不证明 IQC、供应商库存或委外清账，生产发布仍为 **NO-GO**。

## 一、目标和入口

生产确认计划包后，仓库、采购和委外不再依靠口头消息或各自重算缺口，而是在本部门工作台处理同一批履约任务：

- 仓库：提前看到待备料、部分领取和已领取任务，进入真实领料单处理；
- 采购：看到待采购、申请/订单/收货中和已覆盖任务，可从同一张已审采购申请批量生成采购单；
- 委外：看到申请、下单、回厂和覆盖状态，进入对应委外单据继续处理；
- 三个部门都可以按状态、异常和关键词筛选，并从任务追溯到计划、物料和来源单据。

入口位于仓库、采购、委外 Hub 的任务中心卡片，对应接口：

- `GET /api/operations/workbench/warehouse`
- `GET /api/operations/workbench/purchase`
- `GET /api/operations/workbench/subcontract`

接口统一支持 `status`、`exception`、`keyword`、`page`、`size`；权限由服务端按部门现有权限点校验，前端隐藏按钮不能代替权限控制。

## 二、权威数据和数量口径

工作台只读 `v_fulfillment_workbench_actions`，不在 Flutter 端重新计算库存、缺口或单据状态。每条任务至少包含：

- 计划、计划包、仓库、货品、颜色、单位和供给路线；
- 需求量、已分配量、已履约量、已挂供给量和未结量；
- 需求日期、预计日期、任务状态和异常编码；
- 当前可操作来源单据及其明细 ID、单号和审核状态。

必须遵守以下规则：

1. 卡片计数、筛选选项和表格数据来自同一后端视图；
2. 状态卡统计按当前部门、关键词和异常计算，不因正在选中的状态而把其他状态卡清空；
3. 异常选项按当前部门、状态和关键词计算，不从当前分页数据猜测；
4. 页面刷新、切换筛选或翻页不会直接改变业务状态；
5. 仓库发料、采购下单和委外推进必须进入真实来源单据，由对应审核事务更新库存和履约账；
6. 页面显示数量不是库存账本，任何写操作都要由服务端重新取锁、校验版本、数量上限和幂等键。

### 2.1 关联单据权限不是“看见工作台就全能看”

工作台的部门读取权限只允许查看公共履约任务，不自动授予采购、仓库或委外每一种关联单据。服务端按 `department + actionDocType` 映射到目标单据的精确 `*:view` / `*:edit`：

- 无目标查看权：响应保留“存在受限关联动作”这一事实，但清空单据类型、ID、单号、明细 ID 和状态，返回 `actionDocRestricted=true`；前端只显示“无权查看关联单据”，没有可点击深链。
- 有查看权无编辑权：可打开目标详情，后续编辑/审核仍由目标模块自身权限和状态机控制。
- 未知部门/单据类型：服务端 fail-closed，不因新增枚举未同步而泄漏元数据。
- 采购“批量生成采购单”还必须同时具备 `purchase_request:view` 与 `purchase_order:edit`；仅能看申请或仅能改订单都不显示动作。

前端不渲染无真实动作的按钮：仓库不再显示“批量状态变更（未开放）”，委外不再显示“批量处理（未开放）”，无可读来源时也不显示可点击的“打开所选单据”。说明文字与锁图标替代伪按钮。

## 三、统一页面结构

页面从上到下为：

1. 部门标题、业务说明和刷新按钮；
2. 固定状态统计卡，即使某状态数量为 0 也保留入口；
3. 关键词、状态、异常筛选；
4. 已选数量、全选本页、清空、打开所选单据和部门批量动作；
5. 宽屏使用统一任务表格，窄屏使用任务卡片列表；
6. 空数据、加载失败和重试使用统一反馈，不用空白页代替错误。

筛选发生变化时回到第一页并清空跨筛选选择，避免把已不可见任务误带入批量操作。

## 四、部门状态和动作

### 4.1 仓库

| 状态 | 页面含义 | 允许动作 |
|---|---|---|
| `READY_TO_PICK` | 待备料 / 待领取 | 打开真实 `DRAW` 领料单 |
| `PARTIAL` | 部分领取 | 继续进入领料单处理剩余数量 |
| `DONE` | 已领取 | 查看来源和处理结果 |

仓库工作台不直接提供“批量改状态”。DRAW 审核只确认领料需求；仓库按行分轮 `issue` 时才产生实物发料、库存扣减和占用消费。页面必须同时展示单据审核态和实际发料累计，不能把“已审 DRAW”写成“已经领走”。

当前 V1 尚无独立的“待备料→备料中→待双方交接→已交接/生产在制”状态机，所以页面不能虚构拣货人、交接时间或双方签收。

### 4.2 采购

| 状态 | 页面含义 | 允许动作 |
|---|---|---|
| `UNPEGGED` | 待采购处理 | 生成或挂接采购申请 |
| `WAITING_SUPPLY` | 申请 / 订单 / 收货中 | 打开当前采购来源单据 |
| `COVERED` | 供给 peg/数量已覆盖 | 查看供给结果；不等于到货已质检可生产 |

“批量生成采购单”只有同时满足以下条件才启用：

1. 所选任务都有采购申请明细 ID；
2. 全部来自同一张采购申请；
3. 该采购申请已经审核；
4. 所选任务尚未进入采购订单或收货阶段。

不满足时页面显示具体原因。跨采购申请按供应商、币种、税率、MOQ 自动合并仍未实现，不能为了“能批量”而错误拼单。

### 4.3 委外

| 状态 | 页面含义 |
|---|---|
| `UNPEGGED` | 待委外处理 |
| `APPLICATION_PENDING_APPROVAL` | 委外申请待审核 |
| `WAITING_ORDER` | 委外申请已审 / 待下单 |
| `ORDER_PENDING_APPROVAL` | 委外订单待审核 |
| `WAITING_RETURN` | 委外中 / 待回厂 |
| `RECEIPT_PENDING_APPROVAL` | 回厂单待审核 |
| `COVERED` | 供给 peg/数量已覆盖；当前不证明回厂质量、供应商库存或余料已清账 |

委外任务可以打开申请、订单、回厂等真实来源单据。由于后端尚无可靠的委外批量履约写接口，V1 明确禁用“批量处理”，避免页面先改状态、业务单据和履约账没有同步。

### 4.4 供给覆盖与实物可用的边界

工作台必须区分以下事实：

| 事实 | 当前解释 | 能否使生产 READY |
|---|---|---:|
| 申请/订单/未来供给 peg | 已有来源承诺 | 否 |
| 收货/回厂待检 | 实物已到但质量未判 | 否 |
| 合格转可用 | 质量结论生效且进入可用库存 | 才可参加整套物料原子分配 |
| DRAW 已审核 | 领料需求已确认 | 否，尚未扣库存 |
| 分轮 `issue` | 仓库已实物发料 | 是生产物料领用事实 |

当前采购/委外回厂尚无完整待检隔离门，因此页面的 `COVERED` 不能宣称“可生产”。目标采购状态应扩展为“到货待检→部分合格可用→已覆盖”；目标委外链为“待发料→部分发料→供应商在制→回厂待检→合格入库→待余料/损耗核销→结案”。

委外目标守恒为：

```text
累计发出 = 合格产出对应耗用 + 良/不良退回 + 审批损耗 + 供应商期末结存
```

供应商处我方库存、回厂质量和逐需求核销尚未落地；工作台不得用一个 `COVERED` 状态遮蔽这些未决数量。

## 五、异常筛选

当前统一异常编码包括：

- `OVERDUE_ANY`：全部逾期；
- `OVERDUE`：已逾期；
- `OVERDUE_SHORTAGE`：逾期缺料；
- `SHORTAGE`：缺料；
- `LATE_SUPPLY`：供给延期；
- `SUPPLY_PEG_REQUIRED`：待生成采购/委外单；
- `UNLINKED`：待挂接。

异常标签由统一解析器显示；未知后端编码保留原值，不能因为客户端字典尚未更新就丢掉任务。

## 六、Dropdown 崩溃复盘和永久约束

### 6.1 根因

状态统计卡是固定定义的，因此数量为 0 时仍可点击；旧实现的下拉选项却只来自后端非零 `statusCounts`。用户点击仓库 `READY_TO_PICK`、采购/委外 `UNPEGGED` 等零计数卡片后，当前值已更新，但 `DropdownButtonFormField` 的 `items` 中没有同值选项，触发 Flutter“当前值必须且只能匹配一个选项”的断言。

同类问题还会在刷新后当前状态的最后一条任务消失时发生，不是单一页面或单一状态的偶发现象。

### 6.2 修复后的组件不变量

任一筛选下拉都必须满足：

```text
selectedValue 为空：
  items 中只有一个“全部”空值项

selectedValue 非空：
  items 中与 selectedValue 相同的项恰好一个
```

实现规则：

1. 所有后端选项先 `trim`，忽略空值并按 `value` 去重；
2. 当前已选值若不在选项中，使用统一状态/异常标签解析器补入一个临时选项；
3. 未知编码显示原编码，不能显示为空；
4. 下拉使用包含当前值的 `ValueKey`，确保统计卡外部更新能同步到表单字段；
5. 后端刷新后即使不再返回当前状态，筛选仍保持合法，用户可以主动清除或切换；
6. 状态卡数量为 0 仍可点击，用于验证“当前确实没有任务”，不能以禁用卡片掩盖数据变化。

## 七、验证与验收

自动化已覆盖：

- 仓库、采购、委外三个工作台点击零计数状态卡均不抛异常；
- 零计数“逾期 / 异常”卡仍可成为合法筛选；
- 刷新后选项不再包含当前后端状态时，当前筛选仍保持且不崩溃；
- 重复/空状态选项被标准化；
- 采购批量动作只接受同一张已审申请的有效明细；
- 无关联单据查看权时，服务端不泄漏 ID/单号/状态且页面没有深链；未知类型 fail-closed；
- 采购批量动作还受服务端能力字段控制，只有申请查看权与订单编辑权同时存在才显示；
- 仓库/委外未实现批量动作和无来源动作不再渲染成可点击或看似可点击的按钮；
- Hub 卡片可以进入三个真实工作台；
- 手机、平板和桌面测试尺寸分别覆盖 `375×667`、`800×1200`、`1200×800`。

2026-07-31 发布基线的历史验证为：Flutter 157/157、`flutter analyze --no-pub` 无问题、Web Release 构建成功；后端 343 tests、0 failure/error、48 skipped。该数字不应被改写成当前脏工作区的新全量结果；自动化通过也不替代真实权限、质量、岗位和实物 UAT。
