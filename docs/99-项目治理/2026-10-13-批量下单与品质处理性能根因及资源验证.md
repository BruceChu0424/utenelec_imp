# 批量下单与品质处理：根因、资源边界与验证

本轮从 `a7e3fc9db`（V858）继续排查物料分析批量下单和品质批量通过。改动在 `uimp/batch-command-root-cause-20261013` 隔离分支，未覆盖原工作区的部署、备份、附件等并行修改。

合并时，本地 `main` 已推进至 `03b0cce0f`，价格分析功能占用了 V859/V860。因此本轮未发布源码迁移顺延为 **V861（精确供给范围）、V862（IQC 财务触发条件）**，仅调整文件编号和诊断中的版本号。本文下面 V859/V860 的实验描述是冻结测量当时的真实版本，保留原样；不改已应用实验库的历史记录，不使用 Flyway repair。合并后的完整链另用新数据库验证。

## 根因

1. **批量接口内部仍有大量逐项数据库工作。** 品质汇总批量通过页已使用 IQC `decide-report`、FQC `pass-all`，物料按真实依赖阶段提交；该结论不适用于另一个检查单报告入口，见第 6 项。继续增加客户端并发不能消除服务内部的重复读取、单行写入及成本流转。原版 20 张采购/委外收货单、每单 5 行的真实预上架混合判定诊断出现 16,788 次 JDBC 调用；不能把只创建待入库草稿的测试当成实物入库性能。
2. **当前位置查询没有从可用的索引入口开始。** 采购、委外自有材料、委外损耗、生产等多个成本适配器复制了由 root 反查 head 的查询，未利用已有的有效 owner 索引。诊断中委外残留的 50 次读取累计约 2.75 秒。收口为按 owner 查当前 head，再通过主键证明原 root 身份，保留原先的 FIFO、来源切片与保守拒绝语义。
3. **计算范围大于实际操作范围。** 一种物料的下单会调用整份分析的公共供给计算，然后在外层筛选；同样问题存在于共享制造供给。V859 将采购/委外的货品、颜色、单位以及自制的目标物料 UUID 传入来源选择的最内层，在容量、认领、收货及交期计算之前缩小范围；当前分析、同主仓、原来源排除和实际认领前的余额复核均保留。旧入口仍委托同一权威算法，没有缓存库存或公共供给余额。
4. **与资金无关的投影更新重复核对全部历史资金。** `procurement_inspection_items` 的入库累计、通知与时间戳更新会重新遍历全部品质/入库资金记录。V860 仅在该财务断言实际依赖的身份、数量分段或红冲状态变化时排队；INSERT/DELETE、ALWAYS、延迟约束以及资金断言正文保留。数量累计仍由原数量守卫验证。
5. **以前的测量窗口没有覆盖用户的完整等待。** 物料的旧外部组基准未计入根产品下达和前置预览；FQC 的草稿路径不能代表真实预上架。聚合预览与提交还漏接了已有的稀疏响应协议，每个阶段都可能传输完整分析。
6. **检查单报告仍走另一条逐行提交链。** `ProductionFqcHandlingPage` 的多行报告此前逐行等待 `decideLot` / `decide`，每行发送前保存草稿、成功后再存检查点，最后重新读取检查单。它与汇总页的 `pass-all` 不是同一入口，因此旧 `passAll` 基准不能证明报告提交已提速。这里需要支持精确合格/不合格数量和返工、报废等处置，不能用按当前全部余量通过的接口替代。

## 实施方式

- 物料单组与证明独立的阶段共用集合写入内核，仍保留每个真实批次、供给动作、来源分配、事件、版本和单据。重复兼容组拒绝、父子依赖、借料、公共权益和失败回滚不改。世代查找按既有复合索引查询本次 group/route，不扫描无关历史组；读取安全量快照时，内存映射只索引本批实际需要的来源行。根产品和依赖分组路径在单个计划完成、结果转为值对象后 flush/clear，避免后续查询反复检查已完成计划的持久化实体；数据库事务和已持有的锁不变。
- IQC 先写本单的品质事实，再按原事件顺序冻结资金并批量转移成本。实际入库仍逐条按“入库明细 → 资金份额 → 实物及价值 → 检验累计 → 原来源归属”推进，后续行不会提前占用前一行的库存。
- `move` 和 `moveBatch` 共用锁内内核，批量读取重放回执、原 root、当前 head，按原顺序推进本次命令的剩余区间。每个来源、成本节点、边、转移和分录仍存在；没有用汇总余额代替原始事实。
- `InventoryValueWriteSet` 使用绑定参数按原 SQL 顺序发送写入，保留即时触发器、逐条影响行数及 CAS 验证；读状态前 flush，异常由原事务整体回滚。JDBC 往返减少不等于删掉数据库业务语句，测量分别记录这两个数量。
- 聚合预览/提交接入现有 `shared-material-defaults-v2` 协议。旧客户端保持原响应；新版客户端显式请求协议后才获得缩减，因此后端更新与客户端更新必须分别确认。
- 检查单的精确 FQC 报告增加 `/api/production/quality-inspections/decisions/report`：每行继续使用原 LOT 或 INSPECTION 身份、原请求 hash 和原防重复提交键。一次收齐有序幂等锁、完整写足迹与业务锁，按原行顺序写决定、统一放行与入库收尾、集合读取最终回执。已有旧决定只重放，本次新增决定一起提交、晚失败一起回滚；前端确认框明确说明该原子边界。全 LOT 旧键重放保留原来的无需重新取得可写足迹的路径。
- 检查单前端一次冻结并保存所有本次行、发送一个报告请求、严格核对全部回执行身份/键/模型后才确认成功，再保存一次检查点。未确认结果仍保留原精确内容；切换账号、服务器、路由及本机保存失败继续受原草稿隔离保护。单任务入口保留原 API。没有为列表刷新引入新的无界并行。

## 资源约束

没有提高线程池、连接池或服务端超时，没有并行提交相互依赖的业务命令，没有跨请求缓存库存或成本余额。

成本计划按最多 100 个 move 分块；每个 move 沿用最多 100 个来源的既有边界，当前 SQL 写缓冲最多约 60,000 个标量绑定后发送。资金集合写按 500 行分块。临时 head、资金分配与读取上下文只属于当前调用，资金 scope 在退出时清理，并拒绝跨线程、乱序、关闭后继续使用及被吞掉的写入异常。后一块失败仍回滚已 flush 的前一块。

新的 FQC 报告入口最多 100 行且展开不超过 100 份检验明细，客户端与服务器共同校验；每一实物批仍整体按需求、计划公共、实际超产的既有规则分配，不拆开同一批绕过来源守卫。

这些边界限制中间工作集，**不表示整个操作占用固定内存**：输入、返回值和真实业务事实仍随批量大小增长。测量记录命令线程的 CPU 时间和累计分配字节、JVM 堆前后快照/GC，以及隔离 PostgreSQL 容器 CPU 与内存快照。累计分配包含可回收对象；快照差值不是存活内存或峰值，容器内存还包含缓存。

正式资源参数使用 `uten.test.jvm.heap.args=-Xmx2g`、`uten.test.jvm.args=-XX:ActiveProcessorCount=3`，并由运行中的 JVM 回报实际值。前期把 `-DargLine` 当成覆盖项的物料样本没有真正限制测试 fork，已从该资源口径剔除。处理器参数是 JVM 并行度依据，不是操作系统硬性 CPU 配额；堆上限也不是整个进程 RSS 上限。

## 已确认的结构及业务证据

- 30 个采购组 JDBC `923 → 661`；30 个委外组 `926 → 664`。10 个自制组 `1650 → 1567`；混合 15 个制造计划 `2408 → 2288`。根产品路径仍有必要的逐计划工作，不能套用外部组的降幅。
- 对 16 个同分析外部供给维度、8 个同分析制造供给维度，真实数据库拒绝探针分别证明无关来源的容量/收货函数、无关来源的认领函数不被评价；旧外层筛选路径作为负对照确实触发拒绝。与旧算法全字段结果相等，同事务内追加认领后余额立即更新。
- 1000 行聚合预览/提交的原始 JSON 约 `3.35 MB → 94 KB`；gzip 约 `49.5 KB → 28.7 KB`。完整字段展开等价，不能把原始 JSON 降幅当作 gzip 传输降幅。
- 来源守恒、原键重放、同键异体、并发、整批回滚、末块失败、微小金额精确分摊、100 来源、历史未知成本、收费/赠品分段、采购反审、生产退料、销售退货、委外损耗/退料和车间结算均有定向回归。
- 首轮物料业务矩阵为 106 个完整 XML 用例；随后固定资源运行的两个 reader 类为 8 个用例；最终 writer 收口再通过 9 个定向用例。中途在类边界主动停止未限制堆的测试进程，不把该进程退出码说成整次 Maven 成功，也不重复累加重跑的测试数。

## 时延与 CPU 比较的限制

第一轮整套物料 A/B 两边均完成真实提交及重放，但后半段出现全局漂移：相同旧迁移、只读重放、JVM CPU 和 PostgreSQL CPU 同时变慢，机器上另有不属于本轮的多进程 Flutter 测试。该轮原始结果完整保留，不能据其宣称提速或把语句数下降替代耗时证明。

第一轮五类提交各有 3 个样本，自制/混合的聚合预览也单独计时；根产品、30 组采购和 30 组委外的前置预览当时仍未计入。第二轮使用测试专用可选开关补齐这三种预览，分别记录 preview、submit、replay，并核对预览后分析版本及实际下单事实不变。采样覆盖服务方法与事务提交，仍不包含 HTTP 传输、JSON 编解码及 Flutter 渲染，不能把各阶段中位数相加后称为用户点击耗时。

其中命令线程分配量的观察为：采购约 `74.2 → 69.6 MiB`、委外 `86.8 → 83.4 MiB`、根产品 `37.8 → 29.6 MiB`；自制/混合基本持平并略增。不能宣称所有路径的内存均下降。这些是累计临时分配，非峰值或常驻内存。

品质正式“批量通过”采用全合格输入；含 PASS/FAIL 的诊断样本单独标识，不能与全合格样本混比。

### FQC 正式真实入库对照
