## 四、触发器揭示的业务规则（设计金子）

> 老库 11 个 F_ 触发器（表清单见 `biz_triggers.txt`）。其中 **F_PlanCostItem 的 BOM 展开 + F_Plan 的状态机 + F_ProductingItem 的排产联动** 构成生产模块最复杂的逻辑链。

### 4.1 状态机驱动（F_Plan / F_Transfer）

`TRI_Plan_Order`（F_Plan, UPDATE）和 `TRI_Transfer_Plan`（F_Transfer, UPDATE）都以状态变化为触发条件：

```sql
IF (@Status <> 0 AND @Status2 <> @Status)  -- 状态确实变了才触发
```

- `Status = 0`：草稿，**不产生任何业务影响**
- `Status = 1`：审核生效 → 排产填充 / 回写销售订单 / 重算 F_PlanCostItem
- `Status = -1`（反审/红冲）：反向冲销（清排产、减上游回写）

> **反审守卫**：若 `F_StepItem` 已有 `IQTY`（已派工完工），则禁止反审并 RAISERROR `'第N行货品已经存在调派,请改正后再反审!'`——保护已完工数据的完整性。

> 🔎 **与采购的差异**：F_ 触发器**未引用 `SystemAccinfo.ISplan` 全局开关**（`grep ISplan` 在 F_ 段无命中），全凭 `Status/Status2` 状态机驱动。采购 [14] §4.6 提到的 ISplan 开关是 P_ 模块独有，生产逻辑显式化程度略高。

### 4.2 生产计划审核 → 销售订单回写 + 排产填充（TRI_Plan_Order）

F_Plan 审核生效时的核心逻辑（`biz_triggers.txt` 第 519-617 行）：

```sql
-- 1) 禁用下游触发器（避免连锁）
alter table S_OrderCostItem disable trigger [CheckChange2]
alter table S_OrderItem     disable trigger [CheckFulfill]
alter table F_PlanItem      disable trigger [CheckFulfill4]
alter table F_PlanItem      disable trigger [TRI_F_PlanCostItem_Update]
alter table F_ProductingItem disable trigger [ProductingItem_BQTY]
alter table F_StepItem      disable trigger [CheckFulfill_StepItem]

-- 2) 对每条 F_PlanItem：
DECLARE inv CURSOR FOR
  SELECT ID,GoodsID,QTY,LQTY,PBeginDate,PEndDate,S_OrderID,ProductNo
  FROM F_PlanItem WHERE BillID=@BillID

-- 2a) 回写销售订单明细 S_OrderItem
IF (@Status = 1)
  UPDATE S_OrderItem SET
    PQTY  = PQTY  + @QTY*@Status,     -- 已排产量累加
    LQTY  = LQTY  + @LQTY*@Status,    -- 本次用量累加
    PlanNo = replace(PlanNo,@BillNo+' ','')+@BillNo+' '   -- 追加计划号
  WHERE ID=@S_OrderID
ELSE  -- 反审：移除 @BillNo
  UPDATE S_OrderItem SET ... PlanNo=replace(PlanNo,@BillNo+' ','')

-- 2b) 设置 F_PlanItem.StepID（取首条非外协工序）
update F_PlanItem set StepID=@StepID where ID=@ItemID

-- 2c) 按日填充排产 F_ProductingItem（机器负荷 PRatio 之和 ≤ 1）
WHILE (@PQTY > 0)
  SET @MonthDay = dateadd(day,@ADay,@BDate)
  SELECT @TRatio = sum(PRatio) FROM F_ProductingItem
    WHERE MachineID=@MachineID AND MonthDay=@MonthDay
  IF (1 - @TRatio >= @PRatio)
    INSERT INTO F_ProductingItem(BillID,PItemID,MonthDay,StepID,MachineID,
                                 BillDate,PQTY,PRatio,Style,ProductNo,...)
    SET @PQTY = 0
  ELSE ... -- 跨日分配
```

**揭示的规则**：
1. **销售→生产双向回写骨干**：F_PlanItem.S_OrderID → S_OrderItem.ID（真 FK），审核时回写 `PQTY/LQTY/PlanNo`
2. **机器日负荷上限**：每台机每日 `SUM(PRatio) ≤ 1`（产能约束）
3. **首工序派定**：F_PlanItem.StepID 由触发器自动写入

### 4.3 结案派生（CheckFulfill4）

`CheckFulfill4`（F_PlanItem, UPDATE）：明细增删改后，根据剩余量派生主表 `F_Plan.Fulfill`：

```sql
IF EXISTS(SELECT ID FROM F_PlanItem
          WHERE (BillID=@BillID AND QTY-IQTY > 0)             -- 还有未完工
             OR (BillID=@BillID AND QTY = 0))                 -- 或零数量行
  UPDATE F_Plan SET Fulfill=0 WHERE ID=@BillID               -- 未结案
ELSE
  UPDATE F_Plan SET Fulfill=1 WHERE ID=@BillID               -- 已结案
```

**结案判定**：所有明细的 `QTY - IQTY ≤ 0`（订货量已全部完工入仓）。同采购 [14] §4.3 的 Fulfill 派生范式。

### 4.4 BOM 自动展开（TRI_F_PlanCostItem_Insert）⭐ 最核心

新增 F_PlanItem 时，触发器**自动展开 BOM**写入 F_PlanCostItem（`biz_triggers.txt` 第 674-748 行）。展开有两条路径：

```sql
IF (@S_OrderID <> 0)
  -- 路径 A：订单驱动生产 → 从 S_OrderCostItem 取成本 BOM
  DECLARE inv_F_PlanCostItem_Insert CURSOR FOR
    SELECT ID,GoodsID,ColorID,DQTY,Price,Total,VendID,Summary,Class
    FROM S_OrderCostItem WHERE BillID=@S_OrderID AND ParentID=0
ELSE
  -- 路径 B：计划型生产 → 从货品档案 BOM 取
  DECLARE inv_F_PlanCostItem_Insert CURSOR FOR
    SELECT GoodsID,ColorID,数量,成品价,金额,VendID,摘要
    FROM View_B_BomItem WHERE BillID=@MGoodsID

-- 顶层展开（ParentID=0）
INSERT INTO F_PlanCostItem(
  BillID, MGoodsID, MColorID, GoodsID, ColorID,
  QTY, PQTY, Price, Total, VendID, Summary, DQTY, SOCItemID, Class, LQTY)
VALUES(@ItemID, @MGoodsID, @MColorID, @GoodsID, @ColorID,
  @MQTY*@QTY, @PQTY*@QTY, @Price, @MQTY*@QTY*@Price, @VendID, @Summary,
  @QTY, @SOCItemID, @Class, @LQTY*@QTY)
```

然后**多层递归展开**（`WHILE @BomStatus=1`，循环对每行 `ParentID<>0` 节点继续展开下级 BOM）。

**揭示的规则**：
1. **BOM 双数据源**：优先用销售订单成本 BOM（`S_OrderCostItem`），无订单时回退到货品档案 BOM（`View_B_BomItem`）
2. **数量传递公式**：`QTY = OQTY(成品量) × DQTY(单支用量)`，子层乘以父层 `DQTY` 逐层放大
3. **SOCItemID 保留溯源**：路径 A 把 `S_OrderCostItem.ID` 写入每行，构成生产→销售成本的双向链路
4. **MGoodsID/MColorID 冗余**：每行都带"顶层成品 ID"，便于按成品汇总报表

### 4.5 数量联动重算（TRI_F_PlanCostItem_Update）

F_PlanItem 的 `OQTY/QTY/LQTY/IQTY` 变化时，按层级倍数重算 F_PlanCostItem：

```sql
-- 顶层（ParentID=0）：以 F_PlanItem.OQTY 为基准
UPDATE F_PlanCostItem SET
  QTY   = @MQTY * DQTY,           -- = OQTY × 单支用量
  PQTY  = @PQTY * DQTY,           -- = QTY(排产) × 单支用量
  LQTY  = @LQTY * DQTY,
  RQTY  = @RQTY * DQTY,           -- = IQTY(完工) × 单支用量
  Total = @MQTY * DQTY * Price
WHERE BillID=@ItemID AND ParentID=0

-- 中间层（每层 ParentID 循环）
DECLARE inv_F_PlanCostItem_Update CURSOR FOR
  SELECT ID,QTY,PQTY,LQTY,RQTY FROM F_PlanCostItem
  WHERE BillID=@ItemID
    AND ID IN (SELECT DISTINCT ParentID FROM F_PlanCostItem WHERE BillID=@ItemID)
-- 每层循环：UPDATE ... WHERE ParentID=@ID2（逐级下钻）
```

**揭示的规则**：F_PlanCostItem 的所有数量都是「**父层 × DQTY 单支用量**」自上而下派生。任何上层排产调整，整棵 BOM 子树数量级联重算——这是 136 万行表的高频写入来源。

### 4.6 BOM 层级计算（TRI_F_PlanCostItem_Level）

新增 F_PlanCostItem 时自动计算 Level：

```sql
SET @Level = 0
WHILE (@ParentID <> 0 AND @Level < 30)   -- 防 BOM 循环引用死循环
  SELECT @ParentID = ParentID FROM F_PlanCostItem WHERE ID=@ParentID
  SET @Level = @Level + 1
UPDATE F_PlanCostItem SET Level=@Level WHERE ID=@ItemID
```

**揭示的规则**：BOM 最深 30 层（硬编码上限），防循环引用保护。

### 4.7 成本变更回写（CheckChange_F）

F_PlanCostItem 更新时，若 `Class<>0`，标记父 F_PlanItem 为成本已变更：

```sql
IF (@Class <> 0)
  ALTER TABLE F_PlanItem DISABLE TRIGGER [TRI_F_PlanCostItem_Update]
  UPDATE F_PlanItem SET CStatus=1 WHERE ID=@BillID
  ALTER TABLE F_PlanItem ENABLE TRIGGER [TRI_F_PlanCostItem_Update]
```

注释段揭示**已废弃的设计**：原本会上溯 ParentID 链汇总 `SUM(OrderQTY/INQTY/PDrawQTY/...)` 到 S_OrderCostItem，即「订单成本回写」——但已被注释，证明老库放弃了生产→销售成本反向同步。

### 4.8 工序/排产/调派联动（5 个触发器）

> 本组对应未启用的排产/在制模块，本期不迁数据，但触发器逻辑揭示了**未来成本/车间模块**的语义骨架：

| 触发器 | 表 | 副作用 |
|---|---|---|
| `ProductingItem_BQTY` | F_ProductingItem UPDATE | 若 `B_Step.IsEnt=1`（入库工序）则回写 `F_PlanItem.IQTY/IWeight`；汇总回写 `F_StepItem.PQTY/BQTY/IQTY/FWeight/TranNo` |
| `ProductItem_BQTY` | F_ProductItem UPDATE,INSERT | 派生 `F_PlanItem.BQTY/FQTY`（在产/完工） |
| `PStep_FQTY` | F_PStepItem UPDATE,INSERT | 派生 `F_ProductItem.FQTY = MIN(F_PStepItem.FQTY)`（瓶颈工序决定总完工） |
| `CheckFulfill_StepItem` | F_StepItem UPDATE | 派生 `F_PlanItem.FQTY/FWeight/TranNo`（取首条工序 BQTY） |
| `TRI_Transfer_Plan` | F_Transfer UPDATE | 工序调派回写 `F_PlanItem.TQTY`（开工）/ `F_ProductingItem.TQTY`；**直接 UPDATE StockGoods OUTQTY<月>**（调拨出库库存联动！） |

> ⚠️ `TRI_Transfer_Plan` **直接动 `StockGoods`**（动态 SQL `UPDATE StockGoods SET OUTWeight<月>=...`），同采购 [14] §4.4 的按月分列台账模式——证明在制工序调拨老库视为库存出库。

> **口径金子（View_F_PlanCostItem 的需购量公式）**：

```sql
-- LStatus=0：用当前库存

-- LStatus=1 且 库存≥安全库存：用本次用量
实订需购 = QTY + 安全库存 - (SLQTY + 安全库存) - OrderQTY + PWDrawQTY + MQTY

## 七、老库设计的核心问题与新库对策

### 7.1 F_PlanCostItem 136 万行的分区难题（**重点**）

| 问题 | 现状 | 对策 |
|---|---|---|
| **无日期列** | 41 字段全无 date/datetime | 迁移时**反冗余 `bill_date`**：从 `BillID → F_PlanItem.BillID → F_Plan.BillDate` JOIN 回填 |
| **单表 1.36M 且仅 PK 索引** | 查询慢、运维难 | 新库 `production_plan_costs` **按年 RANGE 分区**（2018–2030 初始 13 个分区）；部署 `pg_partman` 或 cron 月度建分区 |
| **BOM 多层冗余** | 顶层 + 中间层 + 叶子在同一表，靠 ParentID 自引用 | 原样保留树结构（邻接表模型）；新库加 `parent_id` 自引用 FK + `level` 字段 + 索引 `(bill_item_id, parent_id)` |
| **成本重算逻辑全埋触发器** | 数量级联重算（4.5）+ 需购量公式（§五）| **本期不上移到 Service 层**，原样保数据，只读查询；成本重算/MRP 归未来模块（同 [18] §五决策） |
| **多值溯源 varchar**（POrderNo/EONo/PDrawNo 各 250–1000） | 多值逗号串 + 触发器 f_split 回写 | 降级为 `source_doc_no TEXT` 文本占位；真 FK 骨干走 `S_OrderID`/`SOCItemID` 单值 |
| **decimal(18,4) 精度** | 量/价/金额 4 位小数 | 新库 `numeric(18,4)`（不改精度，避免累加误差） |
| **legacy_id 溯源** | 老库 ID 不连续且无业务主键 | `legacy_id INT UNIQUE NOT NULL` + 原始 BillNo 留底 |

#### F_PlanCostItem 迁移与分区建议（决策）

```
production_plan_costs (
  id              UUID PRIMARY KEY,
  legacy_id       INT UNIQUE NOT NULL,          -- 老库 F_PlanCostItem.ID
  bill_item_id    UUID NOT NULL,                -- → production_plan_items.id (FK)
  bill_date       DATE NOT NULL,                -- ⭐ 反冗余自 F_Plan.BillDate，分区键
  parent_id       UUID,                         -- 自引用（BOM 树）
  level           SMALLINT,                     -- BOM 层级
  goods_id        UUID NOT NULL,                -- → goods
  color_id        UUID,
  master_goods_id UUID,                         -- 顶层成品（MGoodsID）
  master_color_id UUID,
  qty             NUMERIC(18,4),
  dqty            NUMERIC(18,4),                -- 单支用量
  pqty            NUMERIC(18,4),
  ... (全数量族 18 个 + 溯源号 9 个 → source_doc_no)
  sales_order_cost_item_id UUID,                -- → sales_order_cost_items (SOCItemID)
  supplier_id     UUID,                         -- → suppliers (VendID)
  source_doc_no   TEXT,                         -- 多值溯源合并文本
  ...
) PARTITION BY RANGE (bill_date);
-- 初始分区：2018..2030 逐年；DEFAULT 分区兜底；pg_partman 维护
-- 索引：(bill_item_id), (parent_id), (legacy_id), (sales_order_cost_item_id)

### 7.2 BOM 展开冗余（F_PlanCostItem 设计反模式）

| 问题 | 现状 | 对策 |
|---|---|---|
| 销售订单 BOM 与货品档案 BOM 双数据源 | 触发器优先取 `S_OrderCostItem`，否则回退 `View_B_BomItem` | 新库**保留双路径展开语义**，归未来 MRP 模块实现；本期只迁结果数据 |

| Level 计算 ≤30 层 | 防 BOM 循环引用 | 保留 `level` 字段 + 应用层校验循环 |

### 7.3 varchar 多值溯源（生产/采购/委外跨模块）

老库生产明细用 varchar(250–5000) 串多值单号：`InNo varchar(5000)`、`TranNo varchar(5000)`、`POrderNo varchar(250)`、`EONo varchar(1000)`、`PDrawNo varchar(250)`……

|---|---|---|
| `F_PlanItem.InNo` | 仓库进仓单号（O_Production） | `source_doc_no TEXT` 合并占位 + `stock_movements` 流水骨干（type 13 产成品进仓） |

### 7.4 状态字段冗余混乱

F_ 模块沿用全库的状态体系堆叠：

- `Status / Status2`（状态机骨干）
- `Fulfill` bit（结案，触发器派生）
- `Stop` bit（中止，手工）
- `Cancel` bit（取消）
- `ISR` int（是否入仓，触发器派生，已注释）
- `CStatus` / `LStatus`（成本状态 / 排产状态，多套并存）

新库用单一 `status` 枚举（`draft / pending / approved / written_off`）+ `is_closed` 派生 + `is_stopped` 手工标志，其余废弃。

### 7.5 float 存数量、text 存备注、varchar 存 ID

- `F_PlanItem.QTY float` / `F_QTY float` / `FWeight float` —— **金额/数量 float 精度风险**（同采购 [14] §七），新库统一 `numeric(18,4)`
- `F_Plan.Remark text`（text 大字段）—— 新库 `TEXT` 或 `VARCHAR`
- `F_Plan.WorkShop / WorkerID / Seller` **varchar 装 ID/名字** —— 新库改 `department_id UUID` + `worker_name TEXT` 占位
- `F_DateReport.WorkShop`（int）vs `F_Plan.WorkShop`（varchar）**同名字段类型矛盾** —— 老库未启用日报，本期保结构即可

### 7.6 成本核算逻辑全埋触发器

`View_F_PlanCostItem` 中的 `实订需购 / 计划需购 / 实排需购` 计算公式随 `LStatus` 三分支不同（§五口径金子），这套 MRP 需求公式是**生产模块最复杂的业务逻辑**，全部以视图 CASE 表达式实现，无任何文档。

**本期决策**：
- **成本/MRP 不做**（同 [18] §五决策、[01] 总览 §九 判定）
- F_PlanCostItem 原样保数据（包含所有数量族 + Level + ParentID BOM 树）
- 触发器逻辑不上移，新库只读查询
- 视图公式不重算，归未来成本/MRP 模块（M_ 钱流和 F_Cost 都属未来）

### 7.7 业务逻辑依赖 6 个外部表/视图（迁移顺序约束）

`TRI_F_PlanCostItem_Insert` 触发器依赖：
- `S_OrderCostItem`（销售订单成本 BOM，V51 本批建）
- `View_B_BomItem`（货品档案 BOM；新库已由 V79 落为 `goods_bom_items`，V181 隔离 stub 误接边并禁止占位端点进入活动 BOM）
- `F_PlanCostItem` 自身（自引用递归）

**迁移顺序**：必须先迁销售订单（V51）→ 再迁生产（V55），否则 SOCItemID 无法映射；本期新库迁移是**一次性导入历史数据**（不跑触发器），但 FK 完整性依赖前序模块完成。

> **现状校准（2026-08-01）**：上述段落记录老库触发器依赖。当前理论 BOM 已存在于
> `goods_bom_items`，历史 `production_plan_costs` 仍是不可回溯重算的计划快照；两者不得混作同一真源。
