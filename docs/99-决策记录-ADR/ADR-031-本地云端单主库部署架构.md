# ADR-031：本地/云端单主库部署架构（流复制 + 远程访问授权）

- **状态**：已接受（源码候选）
- **日期**：2026-08-09
- **影响**：部署、安全、网络层、权限、Flutter 设置/网络、运维
- **依赖**：V241（`users.remote_access`）、`CloudRoutingDataSource`、`RemoteAccessGuardFilter`、`server_selection.dart`、`deploy/cloud/README-cloud.md`
- **相关**：ADR-005/ADR-017（均为「新系统↔老系统」双写，**不是**本地↔云端，勿混淆）

## 一、背景

公司有一台本地服务器（公司内网），希望再起一台阿里云云端服务器，让少量居家/出差员工也能使用本平台。诉求包含：

1. 默认所有账号只能在公司内网使用；仅被**显式授权**的账号可远程（云端）使用。
2. 在公司内就自动用本地后端，在外面才用云端。
3. 本地与云端要「实时」一致；断网恢复后数据要自动补齐。
4. 断网期间本地多人写入、云端也有人写入时，两边的写入要能合理合并。

第 4 条的直观设想是「两个可写库各自写入、恢复后合并」。但对一套管钱、管库存、管账的 ERP，让两台库各自写、再自动合并，是业界公认的「静默算错账」大坑：库存余量、账户余额、单号、审批状态这类字段被两端并发修改后，任何自动合并策略（最后写入胜、字段级合并、CRDT）都可能丢账或双记账。多方调研结论一致——金融/ERP 类系统应以「单主库」为默认，仅在「分区期间仍必须可写」是硬性业务需求时才考虑多主，且必须按数据类型逐一定义合并语义（参见 Postgres 多主、Oracle 冲突解决、offline-first 综述）。

本平台没有「分区期间居家员工必须可写」的硬性需求（居家人数极少，断网罕见），因此**主动放弃多主合并**。

## 二、决策

### 2.1 单主库 + 只读副本（PostgreSQL 流复制）

```
内网员工 ──LAN──> [本地服务器: App + PG 主库(唯一可写)] ──IPsec VPN / 高速通道──┐
                                                                                ▼ 流复制 + 复制槽 cloud_rep
授权外网员工 ──HTTPS──> [阿里云 ECS: App(cloud) + PG 副本(只读)]  ──RAM 角色──> [阿里云 OSS]
```

- **永远只有本地主库可写**（零双主冲突、零丢账）。
- 云端 App（`UTEN_PROFILE=cloud`）经 `CloudRoutingDataSource` 路由：主库健康→一切走主库（与内网同库，实时一致）；主库不可达→写请求直接 503（**不在云端缓存写**，因此永远不存在「两份写入要合并」）。
- 实时一致 = PostgreSQL 流复制（秒级，**无需任何自写同步代码**）。断网恢复后，副本经复制槽 `cloud_rep` 从 WAL 断点自动续传，本地写的数据自动补到云端。
- 因此背景里的第 4 条「合并」**根本不会发生**：云端从不独立攒写。居家员工在网络正常时**完全能实时写**（云端实时转给本地主库）；仅在「公司到云端那条网断了」的罕见窗口，云端写才被拒（503），等网络恢复即可。

### 2.2 远程访问授权门禁（`remote_access`）

- `users.remote_access`（V241，默认 FALSE）。云端实例（`uten.deployment.site=cloud`）由 `RemoteAccessGuardFilter`（注册在 `JwtAuthFilter` 之后）拦截：已认证主体若 `remote_access=FALSE` → 一律 403。
- 仅超管可改：`PUT /api/admin/users/{id}/remote-access`（`authorization:manage` + 超管）。变更由 V241 触发器即时 `bump auth_version`，目标账号旧 access token 立即失效（`JwtAuthFilter` 逐请求复读 `auth_version`）。
- 本地实例（`site=local`）门禁空操作：公司内网全员可用。
- 权限管理页**最顶部**提供「云端访问授权」开关（`AdminUserDetailPanel`，仅超管可见可改），`UserSummary` 回传 `remoteAccess` 供回显。

### 2.3 客户端局域网自动识别（`server_selection.dart`）

- 编译期 `API_BASE_URL` = 公司内网本地后端；设置页可填「云端地址」并选模式（`auto`/`local`/`cloud`，默认 `auto`）。
- `auto`：启动与每 60s 探测本地 `/actuator/health`（短超时、permitAll）；**本地可达→用本地，不可达→用云端**。探测结果持久化，避免每次启动抖动。满足「在公司自动用本地、在外用云端」。
- 切换后 `invalidate(apiBaseUrlProvider)`，所有 watch 它的 Dio（`apiClient`/`visitorApi`/`connectionRecovery`）自动重建指向新地址。

## 三、断网行为（精确不变量）

公司到云端那条网（VPN/专线）断开期间：

- **公司内员工**：完全不受影响（局域网直连本地主库）。
- **云端（居家）员工**：主库不可达后（`PrimaryHealthIndicator` 约 10s 翻 DOWN），**所有经认证的业务请求返回 503**（`JwtAuthFilter` 加载账号状态需主库；**故意不从陈旧副本鉴权**，保证 `remote_access` 撤销即时生效、无安全窗口）。即云端在此期间对居家员工「不可用」，等网络恢复即可。
- 副本的角色是**灾备热备**（可 `pg_promote()` 提升为新主库），而非对外读流量——`CloudRoutingDataSource` 的只读降级分支对「经认证」流量实际不可达（认证先 503），仅对个别 permitAll 端点可能生效。

> 注：早期 `deploy/cloud/README-cloud.md` 称「断网时 GET 仍可走副本」，对**经认证**的 GET 并不准确（认证先 503）。本 ADR 以「断网即云端不可用（安全闭合）」为准，README 已据此订正。

## 四、为什么不做多主合并

1. 金融数据一致性 > 分区可写性；本平台无「分区必须可写」硬需求。
2. 多主合并需为每个数据类型定义合并语义，工作量数月且难以证明正确；自动合并对货币/库存有「静默丢账」风险。
3. 单主库 + 流复制已是 PG 原生能力，**零自写同步代码**，断网恢复自动续传。

## 五、后果与权衡

- **代价**：罕见的「公司↔云端断网」窗口内，居家员工写不了（503）、云端对其不可用；公司内不受影响。可接受（居家人数极少、专线/VPN 稳定）。
- **无缝自动切换前提**：本地与云端部署须用**相同的 `UTEN_JWT_ISSUER` 与 `UTEN_JWT_SECRET`**（二者共享同一份数据库副本，同一 token 可在两端校验通过），否则切换服务器需重新登录。
- **附件**：本地用 AK/SK、云端用 ECS RAM 角色访问同一 OSS Bucket（`StorageService` 多实现）。
- **灾备**：本地主库彻底毁时，云端副本 `pg_promote()` 提升为新主库（属灾备，非日常；此后须重建复制方向）。
