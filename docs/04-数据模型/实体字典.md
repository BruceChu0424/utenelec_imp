# 实体字典

> ⏳ **随源码和数据库演进的活文档**。本档同时记录概念模型与落地状态；真实表结构以
> `server/src/main/resources/db/migration/` 的 Flyway 迁移为准。
>
> 状态必须严格区分“已落地”和“目标设计”。页面存在不等于后端实体/API 已存在。

## 一、使用说明

### 1.1 何时更新
- 设计一个新页面 → 把它需要的实体加进来
- 修改一个页面 → 同步修改涉及的实体
- 发现新关联 → 更新 [ER草图.md](ER草图.md)

### 1.2 实体描述模板

```markdown
### <实体名>（中文 / English）

**用途**：一句话说明这个实体是什么
**所属模块**：employee / payroll / expense / ...
**双写标记**：是否老系统已存在（→ 见 06-老系统融合）

**关键字段**：
| 字段 | 类型 | 说明 |
|---|---|---|

**关联**：
- 关联到 XX（多对一/一对多/多对多）

**业务规则**：
- 关键约束、状态机、计算规则

**待定问题**：
- 还没想清楚的地方
```

### ApprovalNode（审批节点定义 / Approval Node）

**用途**：定义某个审批流程由哪些节点、按什么顺序组成（可配置）。
**所属模块**：approval（跨模块通用）
**双写标记**：视具体业务（报销/工资条）而定

**关键字段**：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID | 主键 |
| flowType | enum(`expense`/`payroll`) | 所属流程 |
| order | int | 节点顺序，从 1 开始 |
| name | String | 节点名（如「直属主管审批」）|
| approverPermissionCode | String? | 审批权限点（如 `expense:approve`），与固定审批人策略组合使用 |
| approverId | String? | 可选固定审批人（指向 Employee）|

**业务规则**：
- 同一 `flowType` 下 `order` 唯一且连续
- 默认节点必须由业务审批制度确认，不能从旧角色名推导
- 流程可按部门/金额配置不同节点数（如 >1万 加一级）

### ApprovalRecord（审批记录 / Approval Record）

**用途**：某条业务单据（报销单/工资条）审批轨迹的一格，记录谁、在哪个节点、做了什么决定。
**所属模块**：approval（跨模块通用）
**双写标记**：审批结果属敏感管理数据，按需双写

**关键字段**：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID | 主键 |
| entityType | enum(`expense`/`payroll`) | 关联的业务类型 |
| entityId | String | 关联的业务单据 ID（报销单/工资条批次）|
| nodeOrder | int | 第几节点（对应 ApprovalNode.order）|
| approverId | String? | 实际审批人（指向 Employee）|
| decision | enum(`pending`/`approved`/`rejected`) | 决定 |
| comment | String? | 审批意见 |
| actedAt | DateTime? | 审批时间（UTC）|

**关联**：
- 多条 ApprovalRecord 属于一条 ExpenseClaim / PayrollBatch（按 entityType + entityId）
- ApprovalRecord → Employee（审批人，多对一）

**业务规则**：
- 目标通用审批模型可按 `nodeOrder` 形成时间线，但当前没有 `UtenTimeline`，也没有落地通用
  `ApprovalNode/ApprovalRecord` 表；工资和报销仍使用各自固定状态及操作时间字段。
- 当前节点 decision=pending 表示「待审批」，高亮
- 驳回是终态还是允许修订重提必须由流程模板显式定义
- 末节点 approved 只推进为业务“已批准”；报销付款和工资发布仍是独立权限与独立动作
- 状态变更必须使用数据库行锁/版本条件之一，并由集成测试证明并发安全

**待定问题**：
- [ ] 审批人离职/调岗时，pending 节点如何转交（代理审批）
- [ ] 是否支持加签/会签（多人同节点）—— Phase 2 先不支持

### ProfileChangeRequest（个人信息修改申请 / Profile Change Request）

**用途**：员工自助修改个人信息时提交的待审申请。一次提交可包含多个字段，共用 `batch_id`；HR 整批批准 / 驳回。
**所属模块**：profile（跨 employee / auth 边界）
**双写标记**：否（首次引入；未来接老系统影子双写时再加）

**关键字段**：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID | 主键 |
| employee_id | UUID (FK→employees) | 目标员工 |
| batch_id | UUID | 同批次多字段共用 |
| field_code | VARCHAR(64) | 机器码（phone / fullName / emergencyContact.0.phone…） |
| field_label | VARCHAR(128) | i18n 标签快照（HR 端直接展示，不依赖客户端语言） |
| field_group | VARCHAR(32) | identity / contact / address / emergency / compensation / org |
| old_value_enc | TEXT | 旧值（敏感字段 pgcrypto 加密） |
| new_value_enc | TEXT | 新值（必填；同字段加密策略） |
| status | VARCHAR(16) | pending / approved / rejected / cancelled / applied |
| submitted_by | UUID (FK→employees) | 提交人 = 员工本人 |
| submitted_at | TIMESTAMPTZ | 提交时间（UTC） |
| reviewed_by | UUID (FK→employees) | 审批人 |
| reviewed_at | TIMESTAMPTZ | 审批时间 |
| review_comment | TEXT | 审批意见（驳回必填） |
| employee_version | INT | 提交时 employees.version 快照；审批时校验 |
| idem_key | VARCHAR(64) UNIQUE | 客户端幂等键，防重复提交 |

**关联**：
- N → 1 Employee
- 1 个 batch 由 N 条记录共用 batch_id

**业务规则**：
- 字段策略分三档（`ProfileFieldPolicy`）：
  - **directEdit**：民族 / 政治面貌 / 婚姻 / 现住址 / 办公电话 / 邮箱 / 工位 —— 提交即生效
  - **requiresReview**：姓名 / 户籍地址 / 手机 / 紧急联系人 —— HR 通过后合并
  - **hrOnly**：性别 / 出生日期 / 工作地 / 薪资 / 银行 / 身份证 —— 员工不可自助申请
- 乐观锁：审批时校验 `employee.version == row.employee_version`，不一致 → 409
- 24h 内同字段 `pending / approved / applied` 记录数 > 0 → 拒绝重复提交
- 审批人为本人 → 403
- 敏感字段（手机 / 紧急联系人电话）走 pgcrypto 加密存储

**状态机**：
```
pending  ──approve──>  applied    (字段已合并到 employees / employee_sensitive / emergency_contacts)
pending  ──reject ──>  rejected
pending  ──cancel ──>  cancelled   (员工主动撤销)
applied  ──（终态）──>  applied
```

**待定问题**：
- [ ] 是否需要"修改后再改"二次自动确认
- [ ] HR 驳回后是否允许员工一键"复用旧值 + 仅修改一项"快速重提
- [ ] 通用 ApprovalRecord 接入（多级审批）留待 Phase 7+

## 七、Phase 2 后端落地实体（Spring Boot + PostgreSQL，已建表）

> 以下实体随"人事模块端到端"在 `server/` 用 Flyway 建表落地（UUID 主键、TIMESTAMPTZ UTC、软删除、审计列）。机密字段 pgcrypto 字段级加密，DTO 按 `employee:pii:view` / `employee:compensation:view` 等权限点脱敏，不按角色名判断。

### User（登录账号 / 与 Employee 1:1）
`id, employee_id(unique FK), login_account(unique, 默认=工号), password_hash(Argon2id), must_change_password(首登强制改), status(active/locked/disabled), failed_attempts, locked_until, last_login_at, last_password_changed_at`
> 登录不能注册，只能 HR 创建。账号状态=users.status。

### Role / Permission / RolePermission（历史兼容 + 权限目录）
`Role(id, code[employee/hr/finance/lab/production/manager/admin], name, is_system)` · `Permission(id, code[如 employee:view], name, category)` · `RolePermission(role_id, permission_id)` M:N。
> V29 起角色不再参与有效权限合成。现行权限 = 全员基础 ∪ 部门配置（含上级）± 个人覆盖；
> 只有 `superAdmin` 享有全量。角色表仅作历史兼容。

### UserRole（用户↔角色 M:N，历史兼容）
`user_id, role_id`。V29 起不决定有效权限，仅保留历史数据/兼容 claim。

### RefreshToken（不透明刷新令牌）
`id, user_id, token_hash(sha256, unique), device_info, issued_at, expires_at(7d), revoked_at, replaced_by`。轮换 + 重用检测。

### PasswordHistory（改密防重用）
`id, user_id, password_hash, changed_at`。改密时校验最近 5 条。

### AuditLog（审计日志，bigserial）
`id, actor_id, actor_account, action, target_type, target_id, before(jsonb), after(jsonb), ip, user_agent,
result, request_id, event_source, http_method, http_path, status_code, duration_ms, risk_level(生成列),
event_category(生成列), client_event_id, device_installation_id, device_name, device_manufacturer,
device_model, device_platform, device_os_version, app_version, app_build, device_form_factor,
device_browser, device_locale, device_time_zone, device_time_zone_offset_minutes, device_is_physical,
client_event_at, device_capture_status, device_profile_hash, created_at`。
> 进入应用的 GET/POST/PUT/PATCH/DELETE/HEAD `/api/**` 由请求过滤器与 MVC 拦截器覆盖；匿名认证、
> CORS 非法来源 403、401、404/405 和 MVC 前异常也由外层兜底。JWT 完整校验成功后将 actor 快照绑定
> 到本次 request，使安全上下文清理后的 404/405 仍能归属账号；无效或过期令牌不会绑定身份。
> 登录、刷新、访问拒绝等由 `AuditService` 显式写；数据变更由 DB 触发器写。
> `request_id` 串联请求和触发器明细。before/after 是最小化后的脱敏副本，不保存凭证、PII、薪资或自由文本。
> V172 的设备字段是服务端收到并清洗后的**客户端声明快照**：`device_installation_id` 是应用安装实例
> 首次运行生成的随机 UUID，不是 IMEI、MAC、硬件序列号；`device_profile_hash` 只用于核对同一份
> 清洗后快照，不构成物理设备认证。`device_capture_status` 取
> `present/partial/invalid/missing/legacy`，Web 或旧版本拿不到的字段必须留空并标明状态，不得猜测。
>
> `audit_log` 与冷归档 `audit_log_archive` 都只允许系统写入。产品不提供人工修改或删除 API；
> 在线记录只由留存任务先归档后删除，归档记录只在总期限到达后由同一任务永久删除。

### LocalAuditReceipt / DeviceAuditProfile（客户端本机证据，非数据库实体）

`DeviceAuditProfile` 保存当前安装实例的随机安装标识、设备名称/厂商/型号（平台可提供时）、平台、
系统版本、应用版本/构建号、设备形态、浏览器、语言、时区和是否物理设备。`LocalAuditReceipt`
按 `client_event_id` 保存请求方法、去除查询值后的路径、开始/完成时间、结果、状态码、
`server_request_id`、重试轨迹和当时的设备快照；不保存请求正文、查询参数值、令牌或业务数据。

- 本机最多保留最近 300 条，并按服务器公开的“在线期 + 追加归档期”总月数自动清理；
- 产品界面和业务 API 不提供手动清除、修改或批量枚举能力，只能凭完整 `client_event_id` 精确核查；
- 精确核查目标回执前必须在线调用服务端授权接口；授权成功并写入 `verify_local_audit_receipt` 后才读取
  本机回执，无权限、离线或授权失败时不读取；
- 本地完整性标记可发现常见的内容损坏或改写，但密钥仍位于本机，不是远程证明或不可抵赖签名；
- 卸载应用、清除站点/应用数据、系统存储清理、设备重置或安全存储异常都可能使本机证据消失；
- 因此本机回执只能与服务器时间、Request ID、安装标识和设备快照交叉佐证，不能单独证明实际操作者
  或宣称“绝对真实”。

审计日志详情和本机回执入口仅向持 `audit_log:view` 的指定核查人员开放；普通员工与访客没有入口，
深链和后端接口均须拒绝。任何审计数据导出还必须同时持有 `audit_log:export`。

### DocNumberSequence（单据号序列，2026-07-27 V76 落地，跨模块共享）
> 业务四模块（销售/委外/生产/钱流）+ 采购/仓库的所有 21 个 create-单据 Service 的 `bill_no` 现由后端 `DocNumberService.nextNumber(...)` 系统生成，**不再由客户端传入**。详见 [数据迁移/27-DDL一致性契约] §一 V76 段 + [数据迁移/28-Java后端契约] §九。

**关键字段**：
| 字段 | 类型 | 说明 |
|---|---|---|
| prefix | TEXT | 单据类型前缀（如 CD/CJ/CR/SO…，对应 `DocNumberPrefix` 枚举，21 类） |
| period | CHAR(4) | YYMM 周期（年月） |
| last_seq | INT | 本 (prefix, period) 月内已发出的最大顺序号 |
| UNIQUE(prefix, period) | — | 联合唯一约束 |

**目标业务规则（尚未实现）**：
- 生成原子：`INSERT ... ON CONFLICT(prefix, period) DO UPDATE SET last_seq=last_seq+1 RETURNING last_seq`（PG 行锁，并发安全）。
- 格式：`[prefix][YYMM][4位顺序号]`，如 `CD26070001`。
- `Service.create()` 当 billNo 为空时生成，**忽略客户端传入值**；`update()` 不重新生成。
- 迁移 backfill 扫描现有 `bill_no` 按 (prefix, period) 回填 `last_seq` 最大值，新号不撞老号。
- 撞号解决案例：CJ 采购收货 / 仓库产成品进仓让步改用 CR。

### 关联单据累计数量约束（V132）

采购、销售、委外的来源单据会累计回写 `received_qty`、`shipped_qty`、`issued_qty`、
`returned_qty`、`material_returned_qty` 和 `wasted_qty`。应用层检查之外，V132 在数据库
增加 12 个 `BEFORE INSERT/UPDATE` 触发器，关闭两个并发事务同时通过“剩余量检查”后导致
超收、超发、超退的竞态：

- 任何新的累计负数都拒绝；
- 累计值增加时不得超过来源数量（需要时加上已退数量额度）；
- 退回/损耗不得超过已处理数量，退回撤销后也不能让已处理量重新变成超量；
- 委外发料的退料量与损耗量合计不得超过发料量；
- 历史库已接受的超量异常不在 V132 中自动改写，只允许朝合法方向减少，必须另做异常盘点和业务纠偏。

这些触发器保护的是数据库不变量，不替代服务端状态机、权限和幂等校验；应用还必须把约束异常
转换为可理解的冲突响应，并在并发集成测试中验证。
