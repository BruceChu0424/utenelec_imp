## 一、背景

公司有一台本地服务器（公司内网），希望再部署一台阿里云 ECS，让少量居家/出差员工也能使用本平台。诉求包含：

1. 默认所有账号只能在公司内网使用；仅被**显式授权**的账号可远程（云端）使用。
2. 在公司内优先使用本地后端，在外面才使用云端入口。
3. 本地与云端应近实时一致；断链恢复后数据自动追平。
4. 需要明确断链期间两端是否都能写，以及若都能写如何解决冲突。

第 4 条若解释为「两个可写库各自写入、恢复后自动合并」，会给财务、库存、单号和审批状态引入无法通用证明正确的冲突语义。最后写入胜、字段级合并或通用 CRDT 都不能保证这类守恒量不丢账、不重记。因此，除非“网络分区期间远程端仍必须可写”被确认为硬性需求，并逐类设计业务命令、幂等、补偿和冲突审批，否则不采用多主。

当前确认的优先级是财务和库存一致性高于分区可写性，因此**主动放弃双主及恢复后自动合并**。

## 二、决策

### 2.1 本地唯一主库 + 云端异步只读副本

```text
内网员工 ──LAN──> [本地服务器: App + PG 主库（唯一可写）] ──IPsec VPN / 高速通道──┐
                                                                                 ▼ 异步流复制 + 物理复制槽 cloud_rep
授权外网员工 ──HTTPS──> [阿里云 ECS: App(cloud) + PG 副本（只读）] ──RAM 角色──> [阿里云 OSS]
```

- **永远只有本地主库可写**。云端 App 在链路健康时也把所有业务事务路由到本地主库；一次 API 写请求只有在本地主库提交成功后才能向客户端报告成功。
- 云端 PostgreSQL 是**异步**物理副本，不是第二个业务写库。这里的“近实时”是异步 WAL 传输和回放，不能写成强同步、实时零延迟或零 RPO。
- 正常运行必须保持 `pg_stat_replication.state=streaming`；复制延迟、告警阈值和最大可接受 RPO/RTO
  由业务与运维根据真实网络/写入量签字后登记，当前不得预填“5 秒”或“零丢失”。实际故障 RPO 以最后
  已接收并回放的 LSN 与主库提交 LSN 的差为准。
- 当本地主库仍存活、只是 VPN/专线中断时，本地已提交数据继续保留在主库；链路恢复且所需 WAL 仍可取得后，副本从断点追平。此场景相对**仍存活的主库**不需要业务合并，也不应丢已提交数据。
- 当本地主库和其未复制 WAL 同时永久损毁并强制提升云端副本时，异步复制允许非零数据损失；禁止宣称“零丢账”或“RPO=0”。
- 云端 App 主库不可达时拒绝业务写；当前鉴权也依赖主库的最新账号状态，因此经认证业务请求整体返回 503。云端不缓存 POST/PUT/PATCH/DELETE，也没有恢复后的离线写重放。
- 云端请求的正常响应延迟包含公司↔云端链路 RTT 和主库事务耗时。不得仅以云端本机副本延迟推导 API 延迟；P95/P99 必须在真实 VPN/专线、真实报文和并发下验收后登记。

#### 为什么不直接改为同步复制

把云端配置为 PostgreSQL 同步 standby，并要求提交等待远端 WAL 持久化/回放，可以降低或消除计划内切换的复制 RPO；但 VPN、专线、云端 PostgreSQL 或云地域不可用时，本地主库提交也会等待或失败。也就是说，只有两个站点时，下列两项不能同时无条件保证：

1. 云端副本故障切换 RPO=0；
2. 公司外网/VPN 中断时，内网员工仍可持续写本地主库。

本方案选择第 2 项，并接受异步副本的有限、需监控 RPO。若未来两项都成为硬要求，需要新增独立故障域、仲裁/共识、明确降级策略和完整容量验证，不能只改一个 PostgreSQL 参数。

### 2.2 远程访问授权门禁（`remote_access`）

- `users.remote_access`（V241）默认 `FALSE`。云端实例（`uten.deployment.site=cloud`）必须拒绝未获授权员工的远程业务访问；本地实例不以该字段阻断公司内员工。
- 仅超管可通过 `PUT /api/admin/users/{id}/remote-access` 修改（`authorization:manage` + 超管）。授权或
  撤权只要值改变都会递增 `auth_version`、撤销该用户全部 refresh token并审计，要求重新登录。
- 权限管理页用户详情顶部提供“云端访问授权”开关，仅超管可见可改。
- 该应用门禁不替代网络边界：本地 Nginx、后端 8080 和数据库端口仍必须只允许精确的公司/VPN/代理网段，不能把本地站点暴露到公网来绕过云端门禁。
- `remote_access` 只用于员工主体。现有访客预约是独立的公网 OTP/受限权限主体，不取得员工 ERP 权限，
  云端 visitor auth 仍按访客状态与访客权限开放；这是外部访客预约的显式例外，不得借访客 token
  访问员工 API。若公司决定访客预约也只能内网使用，必须另行关闭云端 `/api/visitor/auth/**`，
  不能误以为 `users.remote_access` 会覆盖访客表。
- 生产验收必须覆盖云端 login、refresh、已认证业务请求、撤权旧 token、访客边界和本地负向路径；只验证数据库布尔列变化不等于远程门禁已验收。

### 2.3 局域网优先与 Web 入口

Web 正式环境不通过浏览器跨域探测内网 API 来决定服务器。浏览器的混合内容、CORS、Private Network Access 和 CSP 会让该方案不稳定，也不能让普通用户填写任意 API host 后携带 token 访问。

Web 采用以下二选一入口方案，运行时均固定同源 `/api`、静态资源与 API 同源；Release 不读取绝对
`API_BASE_URL`/`CLOUD_API_BASE_URL`：

1. **推荐：split-horizon DNS**。同一受控域名在公司 DNS 内解析到本地 Nginx，在公网 DNS 解析到阿里云 Nginx；两端都持有该域名有效证书。公司内即使命中 `remote_access=TRUE` 的账号也自然走本地入口。
2. **双域名**。公司书签/桌面入口固定打开只在办公室/VPN 可达的本地域名；居家员工打开云域名。两个域名都各自同源代理 `/api`，不从一个页面跨域探测另一个 API。

本地入口必须以精确 `OFFICE_CIDR`/批准 VPN CIDR 和防火墙限制，不依赖“域名不公开”。云端入口由公网 TLS、远程授权和应用权限共同保护。移动/桌面 Release 同时固化构建期批准的本地/云端 HTTPS
端点，优先探测本地；忽略历史 SharedPreferences host，不允许用户输入任意服务器地址。当前仍须补登录页
“恢复自动选择”入口，避免已保存“仅本地/仅云端”在换网或撤权后把用户锁在登录外。

## 三、断链行为（精确不变量）

公司↔云端的 VPN/专线断开期间：

- **公司内员工**：继续通过 LAN 访问本地 App 和唯一主库；前提是选择异步复制，且本地 DNS、Nginx、应用、数据库和办公网络本身健康。
- **云端居家员工**：经认证业务请求返回 503，不得显示“已提交”，不得保存通用离线业务 payload，也不得在恢复后静默重放。
- **云端副本**：保持只读和最后已回放状态，不承接需要最新账号授权的业务流量。
- **链路恢复**：先确认复制重新进入 `streaming`，监控接收/回放 LSN 和延迟直至追平，再恢复云端可用判定。这里是单向 WAL 追平，不是两份业务写入合并。
- **WAL 不可取得或复制槽失效**：不能声称会自动续传；必须重新做受控 base backup/副本构建，并在此期间保持云端业务不可用。

## 四、为什么不做多主合并

1. 财务和库存一致性高于网络分区可写性；当前没有“分区期间远程端必须写”的已批准硬需求。
2. 多主需要按单号、审批状态、库存移动、余额、付款和附件元数据分别定义命令、幂等、因果顺序、人工冲突处置与补偿，不能用一个数据库级“最后写入胜”规则覆盖。
3. 单主使所有成功业务事务仍服从现有服务端锁、约束、幂等和审计；代价是链路故障时远程端不可用。

## 五、灾备提升、恢复与备份

云端副本提升不是一个单独的 `pg_promote()` 命令。生产 Runbook 和演练必须至少包含：

1. **判定与 fencing**：先区分主库永久损毁与网络分区；通过停机、存储隔离、交换机/防火墙封锁或等效 STONITH 确保旧主库不可能继续写。不能确认 fencing 时禁止提升，避免 split-brain。
2. **记录 RPO**：记录最后接收/回放 LSN、时间戳、复制延迟和无法复制的事务窗口，经业务负责人接受实际 RPO 后再提升。
3. **提升与切换**：执行 `pg_promote()` 后验证可写性、约束和 Flyway 版本；切换云 App 的主库端点/服务发现，并通过 split DNS、受控域名或客户端配置把需要恢复的内外网流量切到新主库。不得只提升数据库而遗漏应用连接和入口。
4. **反向访问与复制槽**：`pg_basebackup` 不保证复制 PGDATA 外部的 `hba_file`。恢复流量前必须按云端 `SHOW hba_file` 的真实路径写入本地 App/待重建 standby 的精确私网 `hostssl` 规则，收口安全组/防火墙，并在云端新主显式创建立即预留 WAL 的反向物理槽；不得开放公网 5432 或 admin HBA。
5. **阻止旧主回归**：旧主不得以原角色自动重启或重新接入。恢复后若时间线和 WAL 条件允许，受控使用 `pg_rewind`；否则从新主重新做 base backup，把旧主重建为 standby，并使用新主上的反向槽。
6. **受控 failback**：完成复制追平、校验、备份和恢复演练后，在维护窗口冻结写入、重新 fencing、切换端点并重建复制方向/新槽。禁止自动 failback。

物理副本**不是备份**：误删、勒索、逻辑损坏和恶意写入会被复制。必须另有加密、受限账号、不同故障域的基础备份 + 连续 WAL/PITR，定义保留期，并定期从备份恢复到隔离环境验证 RPO/RTO。

## 六、后果与发布边界

- **可用性代价**：公司↔云端链路故障时远程端不可用，本地仍可用；这是明确接受的 CAP/同步复制权衡。
- **令牌切换前提**：本地与云端必须使用相同的 `UTEN_JWT_ISSUER` 与 `UTEN_JWT_SECRET`，并制定同时轮换顺序；否则跨入口需要重新登录。
- **发布前提**：当前没有旧版 token/claim 兼容 writer，本地与云端禁止新旧 JAR 滚动混跑；只能维护窗口关闭入口、排空、清退会话并把两端原子切换到同一版本，回滚也适用同一边界。
- **加密数据前提**：两端必须使用兼容的 PGP/HMAC 密钥版本，密钥仅由服务器密钥管理注入。
- **附件前提**：本地与云端访问同一私有 OSS Bucket；云端用 ECS RAM 角色，本地用受限 AK/SK。Web 只允许经 CSP 和 Bucket CORS 明确登记的公网预签名 origin。确认时固定服务端实际校验/哈希的 OSS `versionId`，下载点击时重新做对象级授权并签发短 URL；运行身份必须有精确版本的 `GetObjectVersion`/授权删除所需 `DeleteObjectVersion`，版本清单与恢复使用分离的临时身份。版本控制下 PUT 重放会生成新版本，业务仍固定已确认版本，不能再以“第二次 PUT 冲突”为门禁。任何已确认 `storage_key + versionId` 不得被生命周期或批量脚本无对账永久清理。V244 应用后、切换云端前目标库 `SELECT count(*) FROM attachments WHERE storage_version IS NULL` 必须为 0，否则必须先隔离并在人工核对 OSS 精确版本与服务端哈希后回填，不得回退读取 current 版本。真实 OSS 的 PostPolicy 大小限制、staging/final 隔离、恶意内容扫描、删除 outbox/状态机、pending 配额/孤儿对账清理与恢复演练未完成前仍是生产 NO-GO。
- **运维前提**：复制延迟、复制槽 WAL 占用、磁盘、VPN、两端 health、备份/PITR 和证书必须纳入外部告警。

本 ADR 的实现已有自动化、隔离 PostgreSQL HTTP/迁移与独立 Docker 复制证据，但这些不是阿里云、
公司目标 PostgreSQL、真实 VPN/专线或真实 OSS 的验收证明。未完成目标库迁移核对、真实多账号负向
权限、三网浏览器、未登录端点恢复、复制断链/积压、磁盘保护、fencing、提升/failback、PITR 恢复和
发布签字前，生产结论保持 **NO-GO**。
