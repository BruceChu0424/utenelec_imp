# ADR-102 物料分析一张表直接下单

- 状态：已接受，按 2026-09-26 用户复核收敛主表与三个准备桶。
- 修订 ADR-033/081 的独立路线确认与桶内私有下单编排；数量预览以 [ADR-116](ADR-116-物料分析下达预览只读投影.md) 为准，原回滚式预览已经退役。
- 现行页面合同：[生产物料分析准备](../03-页面/生产物料分析页.md)。本文记录决策，不重复维护列宽、测试次数或部署状态。

## 背景

多次改动把准备页、三个桶、父子级联页及同料汇总页变成几套流程。原行需求转进制造锚点后，产品视图只读、显示 0 或要求跳到汇总视图，无法独立追加；父件改量又依赖子件输入框已经创建，分页和折叠状态影响自动勾选。数量预览曾把首次输入与追加输入同时累计，实际提交却只读一列。

用户要求的是稳定的原产品树、供应方式自动保存、同料自动合单以及每个子件可独立办理，不是新增需要学习的共享批次步骤。

## 决策

### 供应方式自动保存

已有主档供应方式直接带出并保存；主档未定但 BOM 能合法推导 MAKE 的情况继续按服务端建议处理。无法确定的行保持空值红框，不能下单。改选后立即保存，不再出现“确认路线”按钮或确认换桶弹窗。

自动保存走原 route 权限、对象范围、版本及幂等守卫，只确认供应方式，不创建任务或计划。人工修改失败保留草稿，不能清掉人工输入；不进行无限自动重试。

#### 2026-09-27 修订: 自动确认挪到服务端, 与分析重算同一次请求

用户反馈「一进物料分析准备页就弹窗加载, 要卡一会」。实测不是在读 BOM, 而是页面拿到分析后又发一次 PUT /routes 自动确认供应方式: 服务端整份再算一遍、再组装一遍详情, 页面期间盖全屏遮罩, 新建分析从点下去到能操作 p50 约 2.4 s、最长约 5.7 s。改为:

- **谁来确认**: 页面发起的新建/刷新 (POST /preview) 与人工改路线 (PUT /routes) 在服务端那一次重算里、快照写完且换指纹之前、同一事务直接确认, 只算一次; 版本只涨一次, 响应里的 version/fingerprint 已含这次确认。页面不再为自动确认发 PUT /routes, 也不盖任何遮罩; PUT /routes 只剩人工修改这一个用途。
- **判据只有一份** (`MaterialAnalysisRouteAutoConfirm`): 按操作组 (与 PUT /routes 同一分组) 判定, 组内每行都要: 未确认且有独立需求; 产品没被计划闸挡住; 路线定得下来 (顶层行有历史生产计划即自制, 否则取货品主档推出的采购/自制/委外; 主档空且无下层的 REVIEW 不碰, 留红框给人); 没有仍有效的下游任务, 挂在它上面的自制计划也没下达过; 组上没有未撤销的供给行动。写入复用人工确认的 `MaterialAnalysisRouteBatchWriter` (同一套行级校验与主档回写), 只有主档来源真要改的货品行才加锁。确认的值就是本行重算时已经生效的路线, 不需要再重算一遍。
- **同一道闸**: 与 PUT /routes 相同 (查看 + route 权限, 本人负责或按归属范围可写), 再加分析仍在安排中、不是只做成品检验补货的分析; 详情里的 CONFIRM_ROUTES 能力改用同一个方法判定 (`canConfirmRoutes`), 两处不会不一致。没有权限就一条不确认, 不报错。
- **别的单据顺带触发的重算不确认**: 到货、审核、跨分析转移、委外前置自制建分析等流程里的重算, 操作人未必是这张分析的负责人, 也不该在那些事务里改货品主档、多拿货品行锁, 所以不替人确认。详情响应用同一判据数出 `pendingAutoConfirmRouteCount` (还能自动确认但尚未确认的组数; 当前账号没有 CONFIRM_ROUTES 能力时恒为 0), 页面在有刷新与确认能力时据此静默刷新一次即可, 不必自己判断哪些行。
- **响应字段**: `autoConfirmedRouteCount` = 本次请求自动确认的组数, 只在做了确认的新建/刷新/改路线响应上非零 (详情、其他命令与幂等重放恒为 0), 页面据此轻提示「已按货品档案自动确认 N 条供应方式」; `pendingAutoConfirmRouteCount` 见上 (下达预览响应恒为 0)。
- **自动确认只补空白档案, 不改写填过的来源** (同日集成复核): 人工确认会把路线回写货品档案 (记住这次的选择); 自动确认只在档案来源为空时补上, 档案已填 (哪怕与本次按顶层历史计划定的自制不同, 例如档案写着委外) 一律不改、不抬版本, 只确认本分析这一行。否则仅仅打开分析就会悄悄把别人在货品档案里定的委外改成自制。回归: `MaterialRouteAutoConfirmEndToEndTest.automaticConfirmationNeverOverwritesAFilledGoodsMaster`。
- 同一次刷新里若有确认因主档/BOM 事实变更被清掉, 定得下来的会按新事实马上重新确认, 与以前页面紧接着补发 PUT /routes 的结果相同; 响应里的 `routeResetCount` (页面提示「N 条路线因主档变更需重新确认」) 只数没被补回、真要人补选的那些, 以前页面补发确认后套用新快照, 这条提示同样随之消失。

对照: 金蝶/用友/SAP/Odoo 的 MRP 运算都是按物料主档的「物料属性/采购类型 (自制/外购/委外)」直接生成建议, 计划员只对例外改选, 不需要逐行再点一次确认; 这里按同样的共识把「主档已给出的供应方式」当作运算的一部分落库。

页面侧 (同日):

- 删除页面自己的自动确认 (`_maybeAutoConfirmRoutes`、按纪元防重的 `_autoRouteConfirmEpoch`、套用快照后的帧后触发, 以及 `_saveRoutes` 的 automatic 分支与失败回滚)。PUT /routes 只由人工直改发起; 其回包里服务端顺带确认的条数并入成功提示。新建 / 刷新的回包 `autoConfirmedRouteCount` > 0 时轻提示「已按货品档案自动确认 N 条供应方式」。
- 打开已有分析时若详情报 `pendingAutoConfirmRouteCount` > 0, 且有刷新与确认路线能力 (REFRESH、CONFIRM_ROUTES 与本地权限)、没有未提交输入或在办操作, 静默发一次 POST /preview (完整来源 + 版本/指纹, 与手动刷新同一入口), 由服务端在那次重算里确认; 每个 (分析, 版本, 指纹) 只试一次, 刷新回包本身也登记, 服务端若仍报待确认不连环刷新。没有任何全屏遮罩, 只在顶部给一行小提示; 版本冲突时静默重读最新, 其他失败轻提示可手动刷新。
- 第一次分析进行中显示页内进度卡「正在展开 N 个产品的 BOM 并核对库存…」, 不再闪空的候选表; 打开已有分析显示页头骨架 + 一行说明。
- 进页重画收敛: 在途调拨、车间在催、可调拨量、车间/负责人默认值四项附带读取由一个公共装载器 (`_requestCompanionReads` / `_runCompanionReads`) 合批并发、全部回来后只 setState 一次, 各读取只剩一个取数函数 (返回套用动作, 套用时再核对作用域/代际); 下单前必须等默认值的调用方也走同一个装载器。去掉主仓库字段的帧后测高再 setState (改为宽屏同一行 IntrinsicHeight 拉伸)。套用快照时只对仍勾着的行核对能否继续勾选。
- 轮询 / 返回即刷新先比较版本、指纹与动态投影 (投影键按快照对象缓存, 并含 `pendingAutoConfirmRouteCount`), 没变就不套用——编辑中也一样; 原来编辑中不比较就整份套用, 每 45 秒整页重画并补发一次汇总预览。
- `preparationPoolKey` 改为摘要后页面只当不透明分组键用, 解析无需改动。

### 一个办理入口

准备主表直接填写、勾选、确认下单。采购、委外、车间桶保持按岗位查看任务的作用，勾选后进入复用主表组件和状态的“核对并下单”页。旧级联页及其独立输入、预览和提交编排删除。

原行 UUID 和 BOM 路径贯穿展示、输入、选择及请求。服务端负责把原行解析到当前真实承载的需求，不能将名称匹配或首个同货品节点当作写入身份。

### 统一数量

- “需要数量”固定读取来源需求；实际备料按真实计划产出变化。
- “下单数量”显示本行实际下单量，包含超量，不能拿私有需求分配量冒充总下单量。
- “追加下单”只表示本次新增。预览与提交都只读当前有效列，旧控制器不得叠加。
- “可用数量”包含可安排的现货、在途和已下达但未办理供给的剩余量；扣除已占用/认领的量，不把在途当作可领实物。
- 各产品行的输入独立，一行手改不覆盖其它产品默认量或手工量。它们只同步共同可用和缺口，同产品父子仍按实际 BOM 联动；确认显示所有选中行的真实输入合计。可用列不加回本行已经占有的私有份额。
- 同货品编辑预算只预扣已选中且有效的本次下单/追加输入，取消勾选或减量立即释放，历史只读数量不再次扣除。它不写正式库存或认领，提交后按实际供给重建；真实办理资格与展示净缺口分别计算。
- 缺口为正的后代默认选中，与输入框是否渲染无关。手填数量和手动取消的选择分别保存。
- 首次、追加允许分批；缺少车间或负责人在同一页面补齐，不用隐藏复选框掩盖缺项。

### 同料自动合单

组件使用统一核对/提交管道，单来源和多来源遵守同一套规则；顶层产品保留销售来源的计划管道。同料只在颜色、单位、BOM、路线与制造参数相容时合并，数量相加，原来源分账仍完整保存。合单是内部单据组织方式，不再增加用户办理步骤。

预览返回真实执行目标以及完整原行集合证明，前端只沿同份分析的精确对应图验证，防止合单编号变化中断深层提交。

先顶层、再按真实父子依赖办理组件。任一步失败停止后续，不因为某条是采购或单来源就绕过依赖顺序。原工单追加条件遵循 [ADR-104](ADR-104-追加自制并入未开工的生产计划.md)，不以新建执行段冒充原工单增长。

### 同一进度

主表、三个桶和核对页使用相同的数量投影及 `ProductionFlowStage`。有真实单据阶段时显示该阶段；来源转交、库存覆盖和公共认领在详情解释，不以技术前缀替代进度。未下达、等待到货、已入库、可领料、已开工必须分别有事实证明。

三个桶统一使用平台筛选工具条，仅待处理、进行中、需处理；已下达分类退役。待处理为红色徽章，进行中为黄色，需处理是待处理的子集，用中性计数。计数与落地列表同源。完成/取消保留历史，不能回流为进行中。

表格待办状态以同一语义颜色函数映射，主表和三桶使用相同整格背景与文字色，真实业务步骤名称保留。

### 指派和货品归属

已下单顶层的生产车间和负责人取本产品真实计划/执行任务，并锁住显示；单纯采用他人供给不能借用对方指派。所属仓库、归属车间直接读取货品主档，正常入库和生产指派学习沿既有主档写入链更新。页面资料更新不能覆盖历史任务，也不能清空未提交数量和选择；旧 GET 不得回滚新归属。

## 性能与一致性

预览只读、去抖、单飞和尾随最新输入；提交期间不另发预览。页面按快照缓存索引、按页构建，父子默认选择作用于完整源数据。系统建议可变化，人工输入保持独立。

同一分析写入串行受版本、来源与库存锁保护；加速通过合批与删除重复全图读取实现，不用无界并发制造冲突。分段回执必须区分成功和未提交；网络不确定时用原幂等键核对，不能生成新键重复下单。

独立组可在同阶段合批读取来源和 BOM 责任，执行库存快照只在同一计划的锁内窗口复用，正式写入前失效，不跨计划共享。一次用户确认可包含多轮依赖提交，每轮事务原子，不能宣称后轮失败会回滚前轮已经成功的单据。分析头版本未变不代表库存、认领和主档归属未变；动态事实继续刷新，未提交输入保持独立。

2026-09-27 详情接口提速 (每次进页、每个写操作的回包、每次轮询都走它): 合单原行私有份额读取 (`AggregatePrivateIntentReader`) 由逐条分配调用在途量函数 (一个行动 N 条分配回查 N^2 次) 改为每个行动判一次、分配按创建先后用窗口累计切片, 叶子量仍调同一批库函数; 在克隆库 16 来源/207 节点的分析上约 110 ms 降到约 45 ms, 176 行结果逐行相同, 与库函数的逐条一致性由合单/在途转拨端到端测试收尾时对库里全部分配比对守住。委外子件托管读取先按本分析过滤再做逐行来源证明 (以前先对全公司托管记录逐行做证明再过滤), 同一分析约 130 ms 降到约 3 ms, 且不再随全公司托管记录增长。每个节点上的共用备料池标识 (`preparationPoolKey`) 只下发池键的 SHA-256 摘要 (64 位十六进制), 同池同值、不同池不同值, 页面只拿它分组比较, 不解析内容; 原来每个节点重复一串约 600 多字节的范围仓 ID。

本决策被接受不代表所有规模的性能已达标。实测结果及极大混合单的未完成边界见[本轮收尾记录](../99-项目治理/2026-09-26-物料准备统一流程修复.md)；验证批次与部署状态分别记录。

## 验证要求

正常/部分/超量下单、A/B 不等量合单、原位追加、开始执行后新单、多层与多路径 BOM、包装阈值、分页未渲染子件选择、父量回落、手填保留、三个桶与主表数字一致、缺路线/权限、失败保留与重试、实际供给采用和入库反向。测试记录与部署状态分别维护，历史通过结论不自动沿用。
