# 本地报销图片识别

`ocr_server.py` 是同机 PaddleOCR 侧车；Spring Boot `PaddleOcrClient` 请求它获取文字行，
`InvoiceTextParser` 提取票面建议，员工确认后登记。图片识别不做税务查验，不上传或替代凭证原件。
操作依据见[报销 SOP](../../docs/07-业务链路/员工报销全链路-SOP.md)。

## 文件和契约

| 文件/接口 | 职责 |
|---|---|
| `ocr_server.py` | FastAPI服务；固定PP-OCRv5 mobile检测/识别与文本行方向模型，CPU、关闭MKLDNN，使用PIL检查并解码输入 |
| `uten-paddle-ocr.service` | systemd 单进程，独立 `uten-ocr` 无登录用户，回环8501，模型缓存 `/opt/uten-ocr/models`，4G内存上限 |
| `install-paddle-ocr.sh` | 在 `/opt/uten-ocr` 准备运行环境与 unit；使用前核对脚本行为和依赖版本 |
| `requirements.txt` | 部署依赖入口；固定PaddleOCR 3.7.0、PaddlePaddle 3.3.1、PaddleX 3.7.2、FastAPI 0.141.1和opencv-contrib-python 4.10.0.84，其余按文件版本边界安装 |
| `requirements-test.txt` | 无模型的安全边界测试依赖，不代表真实 OCR 推理环境 |
| `prepare_models.py` | 显式准备 `PP-OCRv5_mobile_det`、`PP-OCRv5_mobile_rec`、`PP-LCNet_x1_0_textline_ori`，准备后仍需样本推理 |
| `GET /health` | 返回 `status` 与 `engine_loaded`，仅 HTTP 存活检查 |
| `POST /ocr/invoice` | multipart `file`，成功返回 `{"lines":[{"text":"..."}]}` |

图片最大8MB；JPEG/PNG/WebP 类型和内容必须匹配；总像素不超过4000万、单边不超过30000，
不接受动画。并发推理串行，忙时429；非法图422、超体积413、引擎失败502。
返回最多2000行、每行最多2000字符，错误日志仅记录异常类型，不输出原始票据内容。
HTTP 上传层可能使用受控临时文件，不宣称整个传输过程完全无磁盘写入。

运行 unit 使用私有临时目录、只读系统、空能力集和仅回环网络白名单；在线推理不访问模型下载站。模型在显式准备阶段下载。CPU 上限为两核配额，数值库线程限制为 2，内存上限 4G；这些是隔离上限，实际速度和峰值仍需目标样本验证。

后端配置：`UTEN_EXPENSE_OCR_PROVIDER=disabled|paddle`，默认 disabled；
`UTEN_EXPENSE_OCR_ENDPOINT=http://127.0.0.1:8501`；超时默认60秒，可设1至120秒，
图片上限可设1至8MB。endpoint 仅同机回环 HTTP，不允许用户自定义外部服务。
现役Nginx模板对图片识别精确路径单独设置9MB请求体和130秒代理等待，Dart仅此识别请求使用140秒；
其他接口保留各自限制。9MB用于容纳8MB图片的multipart封装，不提高服务的8MB文件上限。

## 安装和启用

服务器写入遵循[发布手册](../simple/RUNBOOK.zh-CN.md)：先只读核对当前版本、运行状态、容量、
依赖和可恢复配置，形成候选、影响与回滚方案，经授权后执行。以下为操作说明，本轮未执行安装或启用。

1. 保存当前侧车代码、unit、后端配置和虚拟环境依赖清单的受控备份；不把包含秘密的环境文件复制进仓库。
2. 将本目录部署文件送入受控暂存区，核对候选摘要，再按安装脚本要求放到 `/opt/uten-ocr`。
   检查 `uten-ocr` 对模型目录及临时目录的访问权限，代码和虚拟环境由 root 拥有；运行服务不使用 SSH 管理员账号。
3. 按 `requirements.txt` 安装CPU运行时、OpenMP和上游指定的OpenCV contrib，并记录实际 `pip freeze`。
   当前只固定主要运行包并约束其余版本，不是所有传递依赖的完整锁文件；正式候选仍需按实际环境验证并保存冻结清单。
   不要在正式启用过程中无范围地追随最新依赖或默默换模型。
4. 在运维准备阶段显式运行 `prepare_models.py` 下载模型；当前目标已有v6缓存不能代替v5模型。
   使用脱敏样本预热、核对模型文件与离线重启，再处理真实票据。侧车只加载现成v5缓存，
   模型不齐时失败，不在用户提交图片时隐式下载；运行时不向第三方服务发送图片。
5. 先启动侧车并完成下表验证，再以受控方式配置 provider=paddle 和重启后端。
   实际调用路径为员工请求 → 公司后端授权与限流 → 同机侧车，不对公网暴露8501。

安装脚本的 `--verify` 选项会短暂启动后停止服务，健康接口检查不能代替样本推理验收；
在已运行实例升级前必须检查其停机影响，不直接把它当作无中断升级命令。

### OpenCV依赖兼容

本轮真实模型准备发现：PaddleX 3.7.2的OCR依赖检查要求 `opencv-contrib-python` 发行包，
仅安装headless变体即使 `import cv2` 成功，仍会在创建OCR pipeline时报 `DependencyError`。
因此固定上游指定的4.10.0.84，安装脚本先清理其他OpenCV wheel，再安装并强制重装contrib以恢复共享文件。
Linux补齐 `libgomp1`、`libgl1` 和发行版对应的 `libglib2.0-0t64` 或 `libglib2.0-0` 运行库即可，
不要求安装桌面环境，不伪造包元数据或跳过依赖检查。失败与修正验证均保留在本地OCR实测日志中。

### 模型选择证据

本轮在Windows/Python3.12用同一张完全虚构的1800×1260票面比较：server模型冷调用121.019秒、
热HTTP调用124.051秒且票号漏识两位，超出在线预填预算，已淘汰；mobile候选冷33.489秒、热21.530秒，
七项关键文本在这张样例上全部匹配，内存采样峰值约535MiB。最终产品源码直接识别41.836秒，
独立uvicorn进程真实回环HTTP冷请求39.167秒、200，结果与直接识别一致；测试服务随后关闭。
这些是单张样例的文字及传输结果，不是Java字段解析、通用准确率或目标Linux服务器性能承诺。
完整证据见[验收记录](../../docs/99-项目治理/2026-09-19-员工报销全链路验收.md)。

## 验证清单

| 范围 | 需要的证据 |
|---|---|
| 依赖和模型 | 包版本、模型名称及文件摘要；许可声明保留；PP-OCRv5实际成功加载 |
| 正常样本 | 数电票、传统票、旋转/小字/低清晰度脱敏图；号码、日期、购销方及金额识别结果与人工对照 |
| 失败路径 | 非图片伪装、动画、超8MB、超像素、损坏图片、模型缺失、引擎超时均明确失败；无伪造字段 |
| 并发和资源 | 并行请求被拒或按限制处理；记录新候选实际内存峰值与延迟，4G限制本身不是内存足够的证据 |
| 离线 | 断开模型下载网络后重启和识别仍可用；未就绪时仍能手工登记 |
| 全链 | 员工确认建议、原件附件单独留存、审核人工核验；识别不触发自动报销或支付 |

结果写入[报销验收](../../docs/99-项目治理/2026-09-19-员工报销全链路验收.md)，不要用旧服务的耗时或内存数字证明新版本。

## 停用和回滚

先将后端 provider 恢复为 disabled，并按批准的部署流程重启，再停用侧车。
这样员工看到未启用提示并手工登记；仅停侧车但保留 paddle 会产生识别失败提示。
保留原件、业务记录和模型缓存；回滚只恢复经核验的代码、运行环境和配置，不修改已登记凭证或 Flyway 历史。

开源信息：[PaddleOCR 官方仓库](https://github.com/PaddlePaddle/PaddleOCR)使用 Apache-2.0；
分发时保留许可证及必要声明，并分别核查实际模型和第三方依赖。替代方案 RapidOCR 只是研究候选，当前未装配。
