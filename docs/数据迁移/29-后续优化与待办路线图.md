# 29 - 业务四模块 · 后续优化与待办路线图

> 销售/委外/生产/钱流四模块已**全链路打通并验证**（DDL V50-V63 + 数据 100% 迁移 + Java 后端 + Flutter 前端 + e2e）。本文档汇总**本期未做/已知限制/待优化**项，按优先级分级，每条含【现状 / 为何留 / 影响 / 怎么续】，供后续接手直接开工。
> 上下文见 [18-总路线图] · [27-DDL契约] · [28-Java契约] · 各 design doc。

## P0 · 功能缺口（影响当前正确性/可用性，建议优先补）

### P0-1 前端人员名解析（显示 UUID）
- **现状**：销售/委外/钱流单据详情页的 seller/sender/maker/approver/receiver/purchaser/worker 字段显示原始 UUID（如「员工 a1b2c3d4」）。
- **为何留**：后端 `employees` 与老库 `B_Worker` 无 `legacy_id` 对齐（迁移时人员字段全留 NULL）；前端无统一 EmployeeNameService。
- **影响**：用户看不出单据是谁制的/审批的/经手的。
- **怎么续**：① 新建 `B_Worker↔employees` 映射（见 P0-2）；② 前端建 `EmployeeNameService`（仿 `masterNameServiceProvider`，缓存 `/master/employees/dict`）；③ 详情页用 `employeeNameOf(uuid)` 替换 UUID 文本。涉及 `lib/features/{sales,subcontract,finance}/providers/`。

### P0-2 B_Worker↔employees legacy_id 对齐 + 历史单据人员回填
- **现状**：历史单据的 MakeID/ApproverID/WorkerID（指向老库 B_Worker.ID）迁移时全留 NULL（无法落到 employees.id）。
- **为何留**：employees 是 Phase 2 重做的（UUID 主键），与 B_Worker 无 legacy 映射。
- **影响**：历史单据制单/审批人永久缺失；新系统录单填当前登录用户不受影响。
- **怎么续**：① 建映射表 `worker_legacy_map(worker_legacy_id INT, employee_id UUID)`（人工或按姓名/身份证比对 B_Worker 与 employees）；② Flyway 加 `*_legacy_id INT` 列到单据主表（若未加）；③ 迁移脚本回填 `*_legacy_id`；④ 用 map 回填 `*_id` UUID。属一次性数据工程，参考 [15] §九风险表。

### P0-3 ar_ap_ledger 历史 source_doc_id 回填 ✅ 已完成（2026-07-26）
- **现状**：已修。`migrate_finance.sql` 末尾加了跨模块 source_doc_id 回填块（按 source_doc_no JOIN sales_returns/shipments、subcontract_receipts/returns、purchase_receipts/returns、finance_receipts/payments 回填，幂等 `WHERE source_doc_id IS NULL`），并已在运行库执行。
- **效果**：source_doc_id 命中率从 0% 提升到 31–69%（SALES_SHIPMENT 12113/26404、SUBCONTRACT_RECEIPT 10731/15562、PURCHASE_RECEIPT 12341/20017、PURCHASE_RETURN 1152/1772、SALES_RETURN 220/707）。历史单据红冲 `reverseArAp` 现可命中 AR/AP。
- **残留**：未命中的是 source_doc_no 在新表不存在（超迁移范围/它类单号），保留 NULL，属正常。

### P0-4 客户字典端点 `/master/clients/dict` 缺失
- **现状**：ClientController 无 `/dict` 端点（不像 suppliers）。销售/钱流前端用 `?size=9999/10000` 一次拉全量建本地 dict。
- **为何留**：clients 主档早期未加 dict 端点。
- **影响**：客户量大时前端首屏慢；typeahead 搜索缺失。
- **怎么续**：ClientController 加 `GET /master/clients/dict` 返回 `[{id,name}]`（仿 SupplierController.dict）；前端 `SalesMasterNameService`/`finance_name_provider` 改用 dict 端点 + 可选 typeahead picker。

### P0-5 退货/材料退 双挂单 双字段（v1 单字段）
- **现状**：销售退货明细、委外退货/材料退明细用单个 `upstreamItemId`，保存时优先写一端（退货优先 receiptItemId 丢 orderItemId；材料退优先 materialIssueItemId 丢 orderItemId）。与采购退货同款 v1 限制。
- **为何留**：明细行 model `_ItemRow` 单上游字段，UI 单次引入。
- **影响**：双挂回写的另一端链路在编辑后丢失（后端审核仍能按主端回写；查询/报表可能少一条关联）。
- **怎么续**：明细 model 扩成双字段（`outItemId + orderItemId` / `materialIssueItemId + orderItemId`）；编辑页"从上游引入"支持二次引入另一端；保存分别落两列。涉及 `lib/features/{sales,subcontract}/models + pages/*edit_page.dart`。

## P1 · 按设计留待后续（功能完整度，本期明确不做）

### P1-1 FinanceBankTransfer（银行存取款）审核未实现
- **现状**：`FinanceBankTransferService.approve/reverse` 仅翻转 status，**不动 accounts 余额、不写 finance_reconciliations**（代码有 TODO）。
- **为何留**：老库 `M_Bank` 0 行（未启用），跨币种 `TRI_BankItem` 换算逻辑（OCRate/CRate）复杂，本期无真实数据验证。
- **影响**：银行存取款单审核后账户余额不变（UI 显示与业务预期不符）。
- **怎么续**：实现 `approve` 内：按 in_account/out_account + 跨币种换算更新 accounts.balance + 写 finance_reconciliations；`reverse` 反向。参考 design [26] §4.7/§5.3 + 老库 `TRI_BankItem` 触发器。**或**：本期 Controller 直接拒绝审核（返 400）+ 前端禁用按钮，避免误导。

### P1-2 F_PlanCostItem 成本重算 / BOM 自动展开（本期只读保数据）
- **现状**：`production_plan_costs`（136 万行）原样迁入，**只读查询**；老库的 BOM 自动展开（`TRI_F_PlanCostItem_Insert`）、数量级联重算（`TRI_F_PlanCostItem_Update`，子=父×DQTY）、Level 计算、MRP 需购量公式（`View_F_PlanCostItem` 三分支 CASE）全部未上移。
- **为何留**：成本核算是独立大模块（design [24] §四"本期不做"清单），触发器逻辑重、需重构为可测 Service。
- **影响**：新系统不能重算成本 / 自动展开 BOM；历史数据只读可查。
- **怎么续**：① BOM 展开：Service `expandPlanBom(planItem)` 用递归 CTE 展开（去触发器递归）；② 成本重算：`recalcPlanCost(planItem)` 实现 `TRI_F_PlanCostItem_Update` 的级联公式；③ Level 计算；④ MRP 需购量报表。归"成本/MRP 模块"。

### P1-3 生产日报 / 排产 / 工序 / 在制 / 成本核算（老库全 0 行）
- **现状**：`production_daily_reports`(+items)、F_Arrange/F_Cost/F_Step/F_Producting/F_Transfer 老库全 0 行；新库建了日报空结构 + Java CRUD，但**审核/工序/排产/在制/成本逻辑全无**。
- **为何留**：老库这些模块未启用（0 行），无业务数据驱动设计。
- **影响**：生产仅"计划单 + BOM 成本只读"可用；日报/排产/工序录入后无联动。
- **怎么续**：待老库启用这些模块或有新业务需求时，参照 F_ 触发器逐个实现（日报→工序派工→排产→在制→成本归集）。design [23][24] 已留接口位。

### P1-4 委外 BOM 自动展开 + waste_allowance 规则化
- **现状**：`subcontract_order_cost_items` 原样迁 67 行，`waste_allowance` 字段已建（规则化老库硬编码 +0.46），但**展开逻辑未实现**。
- **为何留**：与生产 BOM 展开同策略（本期保数据，后置）。
- **影响**：新委外订货单不会自动展开 BOM 成本子件。
- **怎么续**：Service `expandOrderBom(orderItem)`（递归 CTE），`+0.46` 用 `waste_allowance` 字段配置化。

### P1-5 支票登记簿（finance_check_register）
- **现状**：V57 建了 `finance_check_register` 表（空结构），V63 删了悬空权限码；支票管理 UI = `AccountPage(initialAccountTypeFilter: CHECK)`（账户过滤视图）。
- **为何留**：老库 M_Check 0 行，支票流水实际在 M_in/M_out（账户=支票类）。
- **影响**：无独立支票登记簿（开/领/作废跟踪），但支票收支在收付款单里可见。
- **怎么续**：若需独立登记簿，实现 `finance_check_register` 的 CRUD（开票/领用/作废/核销）+ Controller + 前端页。

## P2 · 性能优化（当前够用，海量后做）

### P2-1 stock_movements 在线转 RANGE 分区
- **现状**：V45 建表非分区；V59 仅更新 movement_type 字典注释，**分区转换脚本存档未执行**（在线转分区锁表，blind 写有风险）。
- **为何留**：当前规模（数十万行 + 索引）单表足够；转换需低峰 + 测试。
- **影响**：十几年后流水数千万行时查询变慢。
- **怎么续**：低峰执行 V59 注释里的转换脚本（CREATE 分区表 + INSERT SELECT 回灌 + rename + 重建索引 PK 含 transaction_date），或上 pg_partman 自动月度建分区。

### P2-2 物化视图定时刷新
- **现状**：sales/subcontract/production/finance 月报物化视图已建（CONCURRENTLY 刷新），但**无定时刷新机制**（仅手动/审核触发）。
- **怎么续**：pg_cron 或 Spring @Scheduled 每日 03:00 `REFRESH MATERIALIZED VIEW CONCURRENTLY ...`（4 个 mv）；审核接口可手动触发增量。

### P2-3 前端客户/供应商 picker typeahead
- **现状**：客户量大时全量拉 dict 建本地缓存（P0-4 修后仍是一次拉）。
- **怎么续**：picker 改 typeahead（输入触发 `/master/clients?keyword=` 分页搜索）。

### P2-4 索引/查询调优
- **现状**：各表索引按 V44 范式建（bill_no/date/status/legacy_id/FK/goods）。
- **怎么续**：上线后看慢查询日志，针对性加复合索引（如报表的 (goods_id, bill_date)）。

## P3 · 已知非阻塞观察（记录备查）

- **委外历史 receipts `ap_posted=false`**：迁移单据 status=1 但 ap_posted 未置位（迁移不重放审核联动；AP 已从 M_out 独立迁入 ar_ap_ledger）。新单据不受影响。报表对账注意口径。
- **reverse 无条件调 reverseArAp**（委外 receipt/return）：靠 reverseArAp 幂等兜底，未加 `if(apPosted)` 守卫。非 bug。
- **postArAp 结清判定 `(==0)` vs refreshSettlement `(<=0)`**：负应收语义跳变（P0 配合负应收核销一并梳理）。
- **recalcOrderClosed 空明细=已结案**：`COALESCE(bool_and,...true)` 边界；approve 已挡空明细，update 删光明细才触发。
- **报表 `/reports/*/detail` 返回裸数组**（非 PageResponse）：前端用"返回行数≥size 判定有下一页"，末页可能空表；后端可补 total。
- **T_ 账套**：老库 T_ 全 0 行未启用，不迁（与 S_/E_ 对称但空）。
- **鉴权细节**：无 token/伪造 token 落 403 而非 401（JwtAuthFilter 设计）；若前端登出依赖 401，确认是否符合预期。
