# V598 货品来源按路线确认历史回填：供应方式收口成货品主档单一事实源

> 2026-09-16 · 用户实测反馈：「在物料分析准备页改了供应方式，下次进来还是老的。」
> 同批 Java 改动把供应方式收口成**货品主档单一事实源**，本迁移负责把库里既有的确认倒灌进主档。

## 为什么要有它

准备页上那个「供应方式」下拉，点确认后走 `PUT /routes`，服务端把值写进
`production_material_analysis_materials.confirmed_route`——**只写分析行**。货品主档
`goods.source_type` 从来没有被这条路径更新过。

而新开一份分析时，每个物料节点的建议路线是从主档算出来的
(`MaterialAnalysisService.suggestion`：采购 → `BUY`、自制 → `MAKE`、委外 → `SUBCONTRACT`，
主档为空则有 BOM 子层建议 `MAKE`、叶子 `REVIEW`)。两头一对，结论就是用户看到的现象：
**改过的供应方式只在那一份分析里活着，下次进来建议路线回到主档的旧值**。

中间那层「看上去还记得」的假象来自旧的 `GET .../last-routes`：前端进页时按货品 + 颜色 + 单位
去历史分析里捞最近一次确认路线，捞到就预填。它把真正的缺口盖住了——记忆只在前端预填这一层
存在，主档、货品资料页、导出、其它读主档的地方全都还是旧值，而且一旦分析被删/取消，或者
按不同颜色单位维度捞不中，默认值就无声地退回主档。

## 新口径 (2026-09-16)

| 环节 | 新行为 |
| --- | --- |
| 确认路线 | `MaterialAnalysisService.saveRoutes` 在**同一个事务**里回写 `goods.source_type`(BUY → 采购、MAKE → 自制、SUBCONTRACT → 委外)；值没变不落盘，真改了抬 `goods.version`(这是人做的决定)，已软删货品跳过 |
| 建议路线 | 只读 `goods.source_type`，不再有第二条记忆通道——用户改过的供应方式下次进来就是新值 |
| 本行 `source_suggestion` | 同一条 UPDATE 里对齐成确认值。否则主档回写后下一次刷新算出的建议 = 刚确认的值，与旧建议不同，会被 `NODE_FACT_CHANGED_CONDITION` 当成「主档事实变更」把确认清掉(反馈环) |
| `/last-routes` | 整套退役：`lastRoutesPerGoods` / `LastRoutePerGoods` / `GET /last-routes` 端点全部删除 |
| 存量 | 本迁移一次性回填 |

## 本迁移做了什么

一条 `UPDATE goods SET source_type = ... FROM (SELECT DISTINCT ON (goods_id) ...)`：

1. **只认有效确认**：`confirmed_route IS NOT NULL`，且所属分析
   `is_deleted = FALSE AND status <> 'CANCELLED'`——作废的分析不是有效决定。
   **停用行 (`active = FALSE`) 仍然算数**：那次确认是人做的，不能因为节点后来被 BOM 刷新
   掉就丢掉用户选过的供应方式(旧记忆查询当年就是这个口径，回填必须同口径)。
2. **每货品取最新一条**：`DISTINCT ON (goods_id)`，按
   `COALESCE(route_confirmed_at, created_at) DESC` 排序，跨颜色 / 单位 / 分析一律取最新；
   并列到同一确认时刻时再按 `created_at DESC, id DESC` 兜底，排序稳定、结果可复算。
3. **映射**：`BUY` → `'采购'`、`MAKE` → `'自制'`、`SUBCONTRACT` → `'委外'`。
   `goods.source_type` 的值域见 V128 (`V128__goods_source_type.sql`)：`VARCHAR(20)`、**没有 CHECK 约束**，
   约定取值就是这三个中文词(与前端编辑下拉 `kGoodsSourceTypeOptions`、
   `MaterialAnalysisService.sourceTypeForRoute` 同一张表)；`confirmed_route` 的取值又被 V234 的
   `production_material_analysis_material_route_chk` 限死在这三个里，`CASE` 不会漏到 NULL。
4. **只在与现值不同时更新**(`IS DISTINCT FROM`)，已软删货品跳过。

### 为什么是「最新确认胜出」而不是像 V591 那样只填空

旧前端本就是**记忆优先于主档**(未确认节点先读 `/last-routes`，读不到才回退主档)，用户一直
看到的默认值就是最近一次确认的路线。只填空会让存量货品的默认值在本次改版后倒退回主档旧值，
等于当着用户的面改掉他们的默认；「最新确认胜出」才让用户看到的默认保持不变。

## 幂等与兼容性

- **幂等**：值相同即被 `IS DISTINCT FROM` 短路，重放零行。
- **无 DDL**：全部是 UPDATE，**不受 goods 审计 / 行触发器的 ALTER 顺序限制**
  (V259/V587/V590/V591 同款规矩，触发器排队事件不与任何 ALTER 冲突)。
- **只写一列**：不抬 `version`、不改 `updated_at`(存量种值是系统行为，不是某个人的一次编辑，
  与 V591 同规矩)，不触碰 `goods` 上任何其它列，不加表、不改清库分类。
- **没有确认历史的货品一行不动**：主档来源为空的照旧为空，建议路线仍按「有 BOM 子层 → MAKE、
  叶子 → REVIEW」落，页面上那个「主档来源为空，请核对」黄标不受影响。
- **旧客户端**：`/last-routes` 已删除，旧前端调用会拿 404 并按既有失败分支提示核对当前路线，
  不会写坏任何事实。

## 验证

  确认 MAKE → 主档 `'自制'` + `version` +1 + 本行 `source_suggestion='MAKE'`；同一分析再刷新
  一次确认不被清掉(反馈环回归)；改确认 SUBCONTRACT → 主档 `'委外'`，相同值再确认不再抬
