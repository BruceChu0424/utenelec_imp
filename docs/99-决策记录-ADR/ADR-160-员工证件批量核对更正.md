## 一、背景(用户原话，2026-10-05)

人事任务列表「证件核对」页(列：工号/姓名/原因/部门/岗位/入职日/认领)：

> 表格最前面有个多选框 能够批量处理 右下角有个按钮 ui应该和其他页面的一致 … 多选后 直接进入到新的页面 然后就是跟销售 编辑后 财务那里再次审批的销售一样 就是 一行是旧消息 划去对应的信息 显示新的内容啥的 就是 表格样式的展示 … ui弄得好看 算法厉害

拆开来是五条：

1. **多选与批量条**：表格最前面多选框、右下角按钮，UI 与其他页面一致(沿用 `MasterDataTableView` 多选 + 右下角悬浮批量条，与转正、生日页同款，「已选 N 项」只由 `UtenSelectionSummaryPill` 呈现)。
2. **新页面**：多选后直接进入新的页面，表格样式展示。
3. **旧新对照**：像「销售编辑后财务再次审批」那样，旧消息划去、显示新内容。
4. **算法厉害**：证件号能推出正确号码就推出来，说清依据和把握，拿不准不乱填。
5. **UI 好看**。

ADR-154 已把证件号问题变成人事任务并给了单人「修改证件信息」入口；本 ADR 补批量链路。花名册上传(对照系统补齐差异、新增名册里有而系统没有的人)与 AI 确认卡同属完整方案，本期不做(§八)。

## 二、决策

### 2.1 本期范围(id-repair 入口全链)

| 环节 | 决策 |
|---|---|
| 证件核对页开多选 | `idOf` 对被他人认领的行返回 null(勾选位换锁，提示「某某处理中」)；右下角「批量处理(N)」danger 大按钮(2026-10-06 由「批量核对」改名，§十一)，未勾选时提示「请先勾选要处理的员工」；按钮可见性与 `/hr/tasks/reconcile` 路由守卫同源(`locationAllowedFor`)，页面不新增 `Perm.` 字面量(权限基线只降不升) |
| 新页面 `/hr/tasks/reconcile` | 一人一行：类型、员工(姓名主行+工号·部门副行)、原因、问题字段(动态列，本期证件号码：旧值红删除线、新值绿底加粗、实际改动字符红色加粗下划线)、把握(徽章 Tooltip 带建议依据)、说明/结果；勾选框管一个人；被他人认领的行不可勾选 |
| 生成核对计划 | 勾选的人(≤200，active/probation 未删员工)交服务端生成「核对计划」：每人一行 + 若干修复建议项，先展示后执行，生成计划不改任何业务数据 |
| 确认更正 | 「确认更正 N 人 M 处」→ `UtenDialog` 确认 → 输登录密码再认证(`@RequiresStepUp`)→ 服务端逐人调既有 `EmployeeCommandService.changeIdentity`，其 `employee:pii:edit` 与全部校验原样生效；执行期间 `UtenBusyOverlay` |
| 操作记录 | 每处改动留操作记录：4 张表(计划、逐人行、建议项、执行回执) + 显式业务审计事件(§五) |

页面与交互细节见[人事花名册核对与员工资料更正页](../03-页面/人事花名册核对与员工资料更正页.md)。

### 2.2 三件拍板的事

1. **清空业务数据时核对记录 PRESERVE 保留**。与 `profile_change_requests`、`employment_history` 同类：员工档案保留时更正记录一并保留。V810 用锚点补丁把 4 张表登记进 `business_data_reset()` 的 PRESERVE 分类(锚点为 V809 插入的 `('subcontract_application_kit_notice_marks', 'CLEAR'),` 行，补丁前校验锚点恰好出现 1 次、四个新表名都不在定义里，末尾自检四行都在)。表里的值列只有密文或统计数字，保留不会泄漏证件号。
2. **新旧值展示一人一行**。核对对象是「人」不是单据明细行，一人一行让勾选/批量语义干净(勾选框 = 这个人这次要执行)，视觉仍是上旧下新：证件号码格内上行旧值红色删除线，下行新值绿色加粗浅绿底、实际改动的字符红色加粗下划线。抽新共用组件 `UtenRevisionCell`(复用 `utenRevisionForeground/Background` 颜色 token，与[重新提交审批差异展示](../03-页面/重新提交审批差异展示.md)同色系；字段级对照仍是 `UtenRevisionFields`、整行快照对照仍是 `UtenRevisionTable`，三个组件各管一层)。用户原话「一行是旧消息 划去对应的信息 显示新的内容」的「每人完整两行」形态(`UtenRevisionTable` 旧行/新行)是备选，未采用。
3. **事务粒度：每人每写入口一个 `REQUIRES_NEW` 事务**。一人失败不连累他人；同一人的不同写入口也互不连累。本期每人只有 `changeIdentity` 一个写入口，所以实际是每人一个新事务；后续花名册包加 `update/transfer/changePhone` 时按写入口再拆(顺序固定：证件先、手机最后)。

## 三、计算口径与算法(只在服务端算一次)

完整推导、蒙特卡洛统计与黄金用例见方案 §4.4；常量一份在服务端 `IdRepairScoring`。号码只在服务端内存，不写日志。

### 3.1 校验码的数学性质(GB 11643 MOD 11-2)

- 17 个权重 `7 9 10 5 8 4 2 1 6 3 7 9 10 5 8 4 2` 都不是 11 的倍数、相邻权重差也都不是 → **前 17 位任一处替换、任一对相邻对调必被校验码发现**；多一位/少一位不受校验码保护。
- **擦除可解**：已知位置的单个未知字符由校验式唯一解出；反过来凡是「用校验式解出来」的字符，校验码对它没有验证作用(构造即通过)。由外部证据决定的改动(15 位升 18、生日锚点、确定性字符映射、删除重复、相邻对调、花名册号码)才被校验码真正验证，偶然通过的概率只有 1/11。
- 每个候选带 `verified` 标志：操作是 NORMALIZE / UPGRADE15 / ANCHOR_BIRTH / ROSTER / DEL / SWAP 为真，SUB / INS / 擦除求解为假。**只有 `verified` 的候选才可能评「高」并默认采用**。

### 3.2 候选来源

| 来源 | 操作 | verified |
|---|---|---|
| 去分隔符(空格/横线/点/引号) | NORMALIZE | 是 |
| 错字符映射：×/Х/Χ→X(仅第 18 位)、O→0、I/L/\|→1 | NORMALIZE | 是 |
| 15 位升 18 位：第 6 位后插「19」再算校验码 | UPGRADE15 | 是 |
| 生日锚点：档案生日与证号生日段解析出的日期**不同**(或解析不出)时，档案生日才算独立证据，把生日段对齐到证据生日 | ANCHOR_BIRTH | 是 |
| 单步邻域：18 位做 17×9 替换 + 16 相邻对调；17 位做 18 位插入；19 位做 19 个删除；非数字位做擦除求解 | SUB / SWAP / INS / DEL | 对调、删重为真；替换、插入、擦除求解为假 |

同一号码保留得分最高的操作后去重。哈希冲突集合(`takenHashes`)一次 `id_card_hash IN (...)` 查出属于别人的候选并剔除。

### 3.3 打分常量要点(log10 似然)

```text
BASE:  SUB=-2.31 (log10(.79/18/9))   SWAP=-2.23 (log10(.10/17))
       INS=-3.26 (log10(.10/180))    DEL=-2.28 (log10(.10/19))
       NORMALIZE=0  UPGRADE15=0  ANCHOR_BIRTH=-1.0
BONUS: DEL 删掉的字符与相邻相同(双击) +0.5;  INS 第 18 位补 'X' +0.7;
       SUB (旧,新) 属易混数字对 +0.3 ({17,38,56,60,08,49,27,69,14,25,36,47,58,12,23,45,78,89,02})
EVIDENCE: 证据生日 != 候选生日 -2.0;  证据性别 != 候选第 17 位奇偶 -1.7;  候选 == 花名册号 +3.0
OTHER = -3.3 (多处错误/模型外);   p_i = 10^s_i / (Σ_j 10^s_j + 10^OTHER)
```

错误先验取 Verhoeff(1969，12112 条邮政实录)：单字替换 79.05%、相邻对调 10.21%、增删一位 10-20%。

### 3.4 分级(四档)

| 档位 | 条件 | 页面表现 |
|---|---|---|
| **高** | `p_top ≥ 0.90` 且 `verified`，且与独立生日、性别不矛盾，且哈希不冲突 | 新值直接填好，**默认采用并勾选** |
| **中** | `p_top ≥ 0.60` 且 ≥3 倍于第二名，但改动是解出来的(SUB/INS/擦除)或缺证据 | 显示「建议」，不预选，点一下「采用」 |
| **需人工** | 2 个以上可比候选 | 候选 ≤3：列成胶囊、带 p 与差异位高亮，点选采用；>3：只列「可能出错的位置：第 2-6、15-18 位」+ 输入框 |
| **无候选** | 3.5 守卫命中、`region_code`、`sequence_code`、多处错误 | 红字原因 + 输入框，请人对照证件 |

### 3.5 守卫与过滤

- **守卫(命中即无候选，只提示)**：号码含 `*` →「号码已脱敏」；存量号形如 `^\d{15}000$` 且校验不过 →「疑似被 Excel 截断，后三位已丢」；护照(E/G/P + 8 位)、港澳通行证(H/M + 8 或 10 位)、台胞证(8 位数字)形态 → 不修数字，建议「证件类型可能是 护照/港澳台通行证」；候选哈希已被其他员工占用 → 剔除；员工绑定超管账号 → 不出建议(人事改不了超管的证件，ADR-154 §3.6)。
- **过滤(候选生成之后)**：省级码 ∈ {11-15, 21-23, 31-37, 41-46, 50-54, 61-65, 71, 81, 82, 83}；出生年 1940..(今年-16)；入职时 16-70 岁。
- **地区段/顺序段单错数学上不唯一**(顺序码 000 有 90 种过校验)：不乱列号码，只给「可能出错的位置」请人对照证件或手输。
- 复杂度：每人 ≤198 个串 × 18 次乘加 + 一次哈希查询，150 人毫秒级。

## 四、守卫与生命周期

| 机制 | 决策 |
|---|---|
| 计划有效期 | 24 小时(`expires_at = created_at + 24h`，CHECK 钉在 (0, 24] 小时)。过期或放弃只清**未执行**项的密文(`ReconcilePlanHousekeeping` 每 10 分钟跑，已登记 `ScheduledTaskCatalog`「员工核对清理」)，**已执行**项的旧值/新值永久保留作操作记录 |
| 执行租约 | 5 分钟(`APPLYING` + `applying_until`)防并发：第二处同时执行 409 `RECONCILE_PLAN_BUSY`；进程中断由清理任务把 `APPLYING` 收回 `OPEN`(版本 +1 让在看的页面重读)，执行回执标 `INTERRUPTED` |
| 幂等 | `requestId` 唯一(`(plan_id, request_id)` 唯一约束)防网络重试重复执行，重放返回上次结果 |
| 旧值守卫 | 计划版本(页面乐观锁，不符 409 `RECONCILE_PLAN_CHANGED`) + 员工版本 + 逐项旧值：生成后系统值被别人改过 → 该处跳过 `STALE` 并说明原因，其余照做 |
| 可见与执行 | 只有创建人能执行；不是本人的计划一律 404(不暴露存在性)；核对记录(只读)对持 `employee:view` + `employee:edit` 的人可见 |
| 认领 | 他人认领中的行在证件核对页不可勾选(勾选位换锁)；执行成功自动释放**操作人自己**在这名员工上的 `identity` 认领，任务消失、徽标同步 |
| 再认证 | 执行接口 `@RequiresStepUp`：一次可改上百人的证件号，风险高于逐人修改，须输登录密码 |

## 五、个人信息保护与操作记录

- 计划里的证件号(旧值/新值/候选)**全密文**(版本化 pgp，`TxSessionVars.encryptAll` 批量一条 SQL 加密)：不进日志、不进 URL(查询参数只放员工 UUID 或计划 UUID，绝不放证件号)、不进 AI 结果。
- 无 `employee:pii:view` 时打码 `****` 尾 4，且不带差异位与候选。
- `outcome_message`、回执 `result` 有数据库 CHECK 拒绝 6 位以上连续数字；4 张表登记审计 NONE(值列只有密文或统计，整行复制只会留下密文噪声)。
- **显式业务审计事件**：`employee_reconcile.plan_created`(生成核对，摘要只有数量)、`employee_reconcile.apply`(每人每轮一条，证件号只记「已修改」+ 依据码)、`employee_reconcile.discarded`(放弃)。数值明细在 4 张表(密文)，人事从核对更正页右上「核对记录」回看。
- 迁移 [V810 员工资料核对计划](../数据迁移/V810-员工资料核对计划.md)(迁移头 V810/736)；`ReconcilePlanStore`(`@Repository` + `JdbcTemplate`，全参数化 SQL)是四张表的唯一存取类，不做业务判定、不知道密钥。

## 六、用例清单

证件号码均为编造，校验码按 GB 11643 核算(与方案 §4.4.8 同一组基准号：F1 = `44200019900307123X`，男；F2 = `450322198511122646`，女)。

| # | 档案里的号 / 场景 | 结论 |
|---|---|---|
| 1 | `442000 19900307 123X`(带分隔符) | 清洗 → F1，高(去分隔符)，默认采用 |
| 2 | `45032219880516012×` | 映射 ×→X，高(字符纠正) |
| 3 | `4420001990O307123X` | 映射 O→0，高(字符纠正) |
| 4 | `442000900307123`(15 位) + 档案生日 1990-03-07 | 升位 → F1，高(15 位升 18 位)，唯一候选 |
| 5 | `450322198521122646`(生日段错) + 独立档案生日 1985-11-12 | 生日对齐 → F2，高；无证据时同一候选属「解出」，只给中 |
| 6 | `442000199900307123X`(19 位，双击多一个 9) | 删重复 → F1，高(删除重复数字) |
| 7 | `45032219880516012`(17 位丢 X) + 生日/性别 | 首选补 X(p≈0.72)，但补 X 是解出来的 → **中**：显示建议不预选，人点「采用」才计入 |
| 8 | `442000199003071231`(校验位错，X 录成 1) | 14 个过校验候选、真值排不进前 3 → **需人工**：可能出错的位置 第 2-6、15-18 位，请对照证件或手输 |
| 9 | `44200019900307213X`(第 15/16 位对调) | 13 个候选并列 → 需人工：第 1-5、15-18 位 |
| 10 | `442000199003071000` | 无候选「疑似被 Excel 截断，后三位已丢」；请把该列设为文本后重新处理 |
| 11 | `44200019900307000X`(顺序码 000) | 无候选「顺序码是 000，请对照证件」——90 种过校验，数学上不唯一 |
| 12 | 候选号码的哈希已属其他员工 | 该候选剔除；全部被剔 → 无候选；手输后执行也会被 `changeIdentity` 409「该证件号码已被其他员工使用」 |
| 13 | 员工绑定超级管理员账号 | 无候选(不出建议)；行仅提示 |
| 14 | 档案密文解不开(`unreadable`) | 无候选，提示「档案里的证件号码读取不出来……请对照证件重新登记」；手输新号仍可走 `changeIdentity` |
| 15 | 计划生成后某人证件被别人改过 | 执行时该处 SKIPPED(STALE)并说明；其余人照常更正 |
| 16 | 同一 `requestId` 网络重试重放 | 返回上次结果，不重复写 |
| 17 | 两处同时执行同一计划 | 第二处 409 `RECONCILE_PLAN_BUSY`「这份核对正在执行」 |
| 18 | 执行中途进程中断 | 5 分钟后租约被清理任务收回，计划回 `OPEN` 可再来；已完成的项有结果 |

1. 建议、打分、分级只在服务端算一次；Flutter 只显示，手输即时校验用 `IdCardUtils.problemOf`(与服务端文案逐字一致，测试锁定)。
