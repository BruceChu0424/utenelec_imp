# 2026-08-08 对象级授权（按负责人 maker_id 隔离）统一实施报告

> 闭合 2026-08-07 权限审计的「范围 B 待办」与 `全局机制 §6.5` / `安全策略 §4.8` 的 NO-GO：
> 销售（V91）之外的 **采购 / 委外 / 生产 / 库存** 四模块此前只有粗粒度 `@PreAuthorize(:view/:edit)`，
> 任何持 `:view` 者可看全模块全部单据。本次按制单人 `maker_id` 做行级归属隔离，新增 `*:view:all`
> 权限点，并把可见性委托（`user_data_scopes`）扩展到 4 个新模块。

---

## 一、业务决策（已与用户确认）

1. **归属列 = maker_id**（4 模块所有单据表都有，create 即填当前员工；无需加列/回填）。
2. **严格按人隔离**：普通员工只看自己制单的；持 `*:view:all` / 超管看全部。
3. **老数据 maker_id 为空**：公共可读、普通用户不可写（同销售范式，不回填）。
4. **跨部门角色授 view:all**：GM 全部 4 个；财务(DEPT_FIN) purchase/subcontract/stock_doc；QA(DEPT_QA) purchase/subcontract。
5. **采购申请 / 委外申请不隔离**：计划系统生成、业务端只读、跨角色消费的「需求」单，持 `:view` 可见全部。
6. **不做「转移归属」**：用 `user_data_scopes` 委托覆盖交接/转交。

**运营必要性偏离（默认授权矩阵已含）**：生产计划 maker=计划员但车间执行、库存流水含生产自动生成且仓库须全见，故
`production_plan:view:all` 额外授 DEPT_PROD/DEPT_ENG/SUB_PLAN；`stock_doc:view:all` 额外授 SUB_WH。

## 二、技术实现

### 2.1 平台级策略泛化（一处机制）
- 新建 `security/DocumentAccessPolicy`（abstract 基类）：把销售 `SalesDocumentAccessPolicy` 的全部判定逻辑
  （`scope` / `readablePredicate` / `nativeReadScope` / `canRead` / `requireReadable`(404) / `canWrite` /
  `requireWritable`(403) / `ownerForNewDocument` / `NativeReadScope`）参数化为 `(scope, viewAllAuthority)`。
- `SalesDocumentAccessPolicy extends DocumentAccessPolicy`（薄壳，sales 8 个 Service 零改动）。
- 4 模块薄壳：`PurchaseDocumentAccessPolicy` / `SubcontractDocumentAccessPolicy` /
  `ProductionDocumentAccessPolicy` / `StockDocAccessPolicy`（各 `@Component`，固定各自 scope/viewAll）。
- **架构边界**：基类在 `security/`（foundation），feature→security 已合法，**未新增任何 feature 边**
  （`ArchitectureBoundaryTest` 绿）。不可达返 404 不泄存在性（仿销售）。

### 2.2 V233 迁移（自包含，无加列）
`V233__object_level_auth_view_all.sql`：① 4 个 `*:view:all` 权限点 INSERT（带 module/category）；
② 部门授权矩阵（见下）；③ `user_data_scopes.scope` CHECK 放开 purchase/subcontract/production_plan/stock_doc；
④ maker_id 部分索引（采购/委外/生产/库存各 list 表，加速过滤）。

**默认授权矩阵**（V212 已应用不可改，本迁移追加；可在授权页调整）：

| 权限点 | 授予部门 |
|---|---|
| `purchase:view:all` | GM, DEPT_FIN, DEPT_QA |
| `subcontract:view:all` | GM, DEPT_FIN, DEPT_QA |
| `production_plan:view:all` | GM, DEPT_PROD, DEPT_ENG, SUB_PLAN |
| `stock_doc:view:all` | GM, DEPT_FIN, SUB_WH |

### 2.3 Service 接 gate（按 maker_id）
统一模式：`list` 加 `readablePredicate("makerId")`；`detail` 加 `requireReadable`（404）；
`update/delete/approve/reverse` 加 `requireWritable`（403）。**gate 放用户面公开方法顶部**，不进共享
`requireXxxForUpdate`（避免误拦内部 port）。

- **采购**：订单/收货/退货（3 Service）。申请不隔离。
- **委外**：订单/询价/发料/退料/进仓/退货/损耗（7 Service）。申请不隔离。
- **生产**：计划（含原生 SQL 进度看板 3 方法 `progress/progressSummary/progressWorkshops` 用 `nativeReadScope`
  注入归属过滤，避免「list 受限但看板全见」的不一致）+ 日报（**补 create 设 maker**——此前日报 maker_id 落 NULL）。
- **库存**：StockDocService（list/detail/update/delete/approve/reverse/issue/reverseIssue）。

**豁免（不加 gate）**：采购/委外订货的财务审核 port（`lockAndValidateFinanceSubmission`/`applyFinanceApproval`，
`@Transactional(MANDATORY)`，财务审核人≠制单人，由财务权限门把关）；`ProductionPlanService.autoApproveForOrchestrator`
（MRP 自底向上自审核）；生产 Facade 直接建/删（已绕过 Service）。

### 2.4 可见性委托扩展（user_data_scopes → 4 新 scope）
复用现有机制（goods/client/sales 全链路）：`DataScopeAdminService.SCOPES` + `ownerCandidates` switch 加 4 模块
（owner 列为 `maker_id AS owner_employee_id` 的 UNION）；前端 `admin_user_detail_panel._scopeDefs` 加 4 条。
`visibleOwners` 同时影响 canRead/canWrite → 授权同事「看+改」。

### 2.5 前端
`permissions.dart`：4 个 `*ViewAll` 常量 + 超管兜底 Set 4 行。授权页目录后端动态下发（`/admin/permission-catalog`），
**前端零改**即显示新权限项。view:all 是 Service 行级过滤，不挂路由守卫。
