# 科目弹窗与真实 I/O 测试时钟 CI 修复

本批保留科目目录宽屏、窄屏、软键盘、搜索结果、导入唯一请求与唯一等待、未决导入时旧关闭回调无效及完成后原修改结果等断言。产品源码、后端业务、SDK、真实数据解码及超时预算均未修改。九类财务完整列表夹具另见本目录的[《2026-11-06-财务九类完整读取CI夹具》](2026-11-06-财务九类完整读取CI夹具.md)，其九项 Chrome 成绩不混入本批。

原测试仍寻找已退休的底部 `UtenDialogActions` / 文字关闭按钮；现在定位实际标题内 `UtenCloseButton`，仍检查关闭入口可点击且位于软键盘以上。导入用例保留实际外层与内层关闭回调，未决时执行原回调并验证弹窗不关闭、没有重复写入，完成后才返回原修改结果。

真实 Chrome 的另一个首因是测试时钟：适配器已收到并返回 JSON 字节，但 Dio 响应流/解码依赖实际浏览器任务；仅推进 widget fake clock 时响应没有发布，原 `pumpAndSettle` 正确超时。只读诊断先证明直接真实异步请求能完成、单次 I/O turn 不足以驱动整个界面、逐原帧交替 I/O turn 和 pump 后真实弹窗能完成。字体资产路由 v3 单独验证仍失败，不能把本问题归因于字体。

共享测试入口 `pumpAndSettleWithIo` 在每个原帧前用 `tester.runAsync` 等一个 `Duration.zero` I/O event turn，然后仍以原 100ms fake-clock 步长及 10 分钟 deadline 判定是否稳定。具体生产者等待通过 `pumpUntil(realIo: true)` 使用同一入口，原 16ms 步长与 2 秒 deadline 不变；原调用方默认行为不变。它没有增加等待预算、跳过错误或预置业务结果。新回归使用真实 Dio JSON 响应证明发布及生产者完成，并证明永久转圈仍在选择的原 deadline 抛出原超时错误。

最后相同源码帧两个完整文件：Native 6/6、真实 Chrome 6/6，0 skip。严格分析三文件 0 issues。证据位于本地 `output/release-ci-20261106/finance-chart-launcher-clock-final-{native,chrome}.log` 及 `finance-chart-launcher-clock-final-analysis.log`。原始及中间失败、诊断探针保留，初次负例错误的异步 matcher guard 调用已改为延迟回调后重新跑完整两文件，不搬用中间 5/6 成绩。

此前完整两财务文件的 Chrome 结果仍为九项通过、科目三项失败；本次是独立后续修复，不能追改旧证据。以上是定向测试，不代表完整 CI、公司部署、真实业务 UAT 或 Win7/WPF 完整支持；未重建或覆盖冻结发布包。
