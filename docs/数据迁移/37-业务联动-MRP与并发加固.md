## 二、MRP-lite 设计（生产计划 → 采购申请）

### 口径

```
毛需求 = Σ（计划明细基本量 × BOM 用量），goods_bom_items 递归展开（≤10 层、路径防环）
BOM 用量 = goods_bom_items.qty；无独立单位字段，表示组件货品基本单位下的每台用量
合法在途基本量 = Σ（max(qty − received_qty, 0) × unit_rate）
净需求 = 毛需求 − 即时库存（stock_balances 全仓合计）− 合法在途基本量
聚合粒度 = 货品 + 颜色（空颜色单独成组；库存、预留和在途使用同一粒度）
半成品（组件本身有 BOM）= 标记「自制」，只预览不进采购申请；其净需求缺口由 V1 排产确认事务内的派生内核（`generateSelfMadeSubplansForPackage`）生成子生产计划供给，写 `subplan_links(source='EXECUTION_V1')`
```

MRP 只读取未删除的当前 BOM。V181 已将 81 条 stub 误接边软删，并由数据库触发器保证活动边两端
都是未删除、`auto_created=false` 的正常货品；历史 `production_plan_costs` 中保留的占位身份不参与本公式。
20,798 条源端 BOM reject 仍须独立治理，不能因活动端点已清零就宣称迁移完整。

合法在途只包含已审核、未停止、未结案、未删除且剩余量大于零的采购订单行。采购单位可以不是货品
基本单位，但单位必须有效且 `unit_rate` 必须是可靠的正数；本文不声称当前另有一张权威、已审核的
单位换算表。与本次货品/颜色需求相关、满足状态及剩余量条件的任一开放行若单位或换算率无效，MRP 必须 **fail-closed**
并提示治理，不能忽略该行或按零在途继续生成采购申请。

校验边界仅限相关开放行：没有相关开放采购行时，本次 MRP 不要求采购单位；已完成、已停止、已结案
或已删除的历史行不参与在途，也不因其旧单位问题阻断计算。业务确认不再到货的历史旧尾数，应由采购
停止或结案，迁移不得按单据年龄自动关闭。

`V168__normalize_legacy_purchase_item_units.sql` 只对“单位缺失、换算率为 1、货品基本单位可确定”的
历史采购明细做确定性回填。它不猜测非 1 换算关系、不改变采购状态；仍无法确定的相关开放行继续作为
数据治理阻塞项。

### 防重复与可追溯（mrp_generations，V87）

- 生成即写联动行（plan_id ↔ request_id + created_by）；
- 同一计划存在**未删且未红冲**的生成申请 → 拒绝重复生成（提示既有单号）；
- 申请被删/红冲后可再生成，旧联动行软删留痕（审计可查）；
- 申请明细挂 `production_plan_no` + remark 记录「毛 − 存 − 途」计算过程。

| 接口 | 权限 | 说明 |

前端：生产计划详情页「物料需求（MRP）」卡（展开/刷新 + 生成采购申请/领料单/成品入库，按 production_plan:edit 门控）。

`/production/plans/{childPlanId}` 详情。V1 确认生成结果中的“执行子计划”是

### 计划 → 成品入库单（FINISHED_IN）

- 取**计划明细自身**（不展开 BOM），数量 = 排产量 − 已入库量（iqty），全入完则提示无可入库数量。
- 与领料单共用 `plan_draw_links` 留痕（按 stock_documents.doc_type 区分防重复，互不干扰）。

### 计划 → 领料单（DRAW，V88）

- **口径差异**：采购申请按**净需求**（扣库存/在途，避免多买）；领料单按**毛需求**（车间按排产全量领料），
  自制件同样列出（半成品也可能从库存领，明细备注标记「自制件」）。
- 表头 `plan_no` + 明细 `source_doc_no` 挂计划号溯源；`plan_draw_links` 防重复（规则同 mrp_generations：
  有效生成单存在即拒绝，删/红冲后可再生成，旧联动软删留痕）。
- 领料单审核只确认领料需求，不扣库存；仓库按行分轮 `issue` 时才写库存流水、扣余额并消费占用。

## 三、多账号并发设计（YTDQ 问题②的答案）

### 分层防线

| 层 | 机制 | 覆盖 |
|---|---|---|
| 状态机互斥 | **PESSIMISTIC_WRITE 行锁**：approve/reverse 先锁头行再查状态，同事务并发审核序列化，后到者按「状态已变」拒绝 | **25 个单据 Service / 40 个审核入口**（采购 4 + 生产计划/日报 + 销售 5 + 委外 8 + 仓库统一 + 钱流 5 + 本次注入） |
| 跨单据共享资源 | 单据头锁只能防同一张单重复审核；不同单据竞争同一资源时还须锁资源本身：库存预留锁 goods+color 事务 advisory key，排产锁销售行，报工锁计划行，AR/AP 核销按稳定顺序锁 ledger | 库存可用量、销售行可排量、计划行可报量、应收应付可核销余额 |
| 主档并发编辑 | 乐观锁 `@Version` 递增（ADR-009 已全量） | employees 等主档 |
| 库存/回写 | 审核同事务内回写 + 余额增量（StockService），行锁保证同一单据不重入 | 全单据 |
| 单号 | doc_number_sequences 数据库序列取号（同事务递增发号，无重号） | 全单据 |
| 审计 | 触发器审计（fn_audit）逐行留痕，谁改的一查即得 | 全表 |

### 为什么选行锁而不是乐观锁（单据状态机）

状态机迁移（0→1、1→-1）附带**库存/应收应付/上游回写等一串副作用**，乐观锁失败重试的代价是
整串副作用重跑；单据头行锁让同单并发者拿到「状态已变」的明确拒绝。但它不能串行化“两张不同
订单同时占同一库存”这类竞争，因此可用量检查、累计校验和写入必须在同一事务内锁定共同资源，
并按稳定顺序取锁以降低死锁风险。

### 2026-07-30 并发复核

本轮复核发现“40 个审核入口有头锁”曾被误写成所有并发不变量都已安全。已补的源码边界：

- 两张订单预留同一 goods+color：事务级 advisory lock 后再读可用量和写预留。
- 两个生产计划分配同一销售行：先锁销售行，再检查/累计 `planned_qty`。
- 两张日报审批同一计划行：先锁计划行，再检查/累计 `fqty`；数据库触发器再兜底拒绝超报。
- 多笔收付款核销同一 AR/AP：按稳定 ID 顺序锁 ledger 后再校验余额与更新。
