# ADR-130 手工需求单多货品与新建物料分析页表格化

- **状态**：已接受(2026-09-27，V738，零新增权限码、零新增业务表)
- **修订**：[ADR-029](ADR-029-生产计划前需求与物料分析重构.md) §三「手工需求」一段隐含的「一个需求编号只对应一个产品」口径；「同一来源类型与需求编号只能归属一份物料分析」保留。
- **相关**：[ADR-102 物料分析一张表直接下单](ADR-102-物料分析一张表直接下单.md)、[ADR-106 热表触发器按相关列起跳](ADR-106-热表触发器按相关列起跳与索引卫生.md)(触发器拆 `_upd` 的写法)、[ADR-121 跨模块新建表单草稿恢复](ADR-121-跨模块新建表单草稿恢复.md)(物料分析工作台不在草稿保护范围)、
  [257 V738 手工需求单多货品](../数据迁移/257-V738手工需求单多货品.md)、[生产物料分析页](../03-页面/生产物料分析页.md)、[UtenGoodsPicker](../02-组件库/UtenGoodsPicker.md)

## 一、背景

用户 2026-09-27 原话：「把自己新建物料分析的那个页面 UI 重构，用我们自己写的表格；现在只能一个货品，我想可以多个货品，上传完多个货品后一起分析；跟 销售那里下单 → 计划多选 → 分析 是一个流程才对。」

改造前的新建物料分析页(候选模式)：

1. 销售候选是一张 `MasterDataTableView`，已选行的「本次分析数量」另放在表格下方一个最高 240px 的已选列表框里编辑。
2. 手工需求是折叠卡「其他需求」：一次选一个货品、填编号/数量/日期/原因，点「加入分析」才加一条；同一张返工单有 10 个货品就要重复 10 次，而且前端直接拦下同编号的第二个货品(「同一来源类型下，一个需求编号只能对应一个产品需求」)。
3. 数据库索引 `uq_production_material_analysis_manual_source_ref`(V234 建、V529 重建)对全部非销售来源行按 `(source_type, lower(btrim(source_ref)))` 全局唯一，于是一个编号在全库只能有一行，也就只能有一个货品。

服务端预览链路其实已经按「一行 = 类型 + 编号 + 货品 + 颜色 + 单位」处理手工来源：去重键、`SourceIdentity`、复用已有分析时比对完整来源集合都带货品；下游计划关联、根供给、ADR-104 追加、车间段、履约工作台全部按 `analysis_item_id` 走，编号只是展示和搜索标签。挡住「一号多货」的只有上面的前端拦截和全局索引。

顺带暴露的潜在缺陷：`normalizePreviewItems` 的去重键用未规整的原始编号，`RW-1` 与 ` rw-1` 加同一货品会通过规整，再在 `Collectors.toMap` 里撞键变成 500，而不是一句能看懂的校验提示。

## 二、同行做法(调研)

按「不熟的业务逻辑先查同行」的约定，查了 SAP、金蝶云星空、用友 U8 与 Odoo 的公开资料(链接见文末参考；用友 NC 没有找到可核实的公开说明，未列入)：

| 系统 | 手工/独立需求怎么录 | 与销售订单怎么一起算 |
|---|---|---|
| SAP ERP / S/4HANA | MD61 录计划独立需求(PIR)。首屏可以不填物料而填一个「需求计划号」(requirements plan number)，在同一个号下录多个物料并在一屏里查看；这个号由人输入，社区答复指出 4.5 以后已不再内部取号。一条 PIR 是一个物料的计划数量，按日期拆成计划行 | MRP(MD01/MD02)把 PIR 与客户需求一起做净需求计算；按策略(如 40)销售订单消耗 PIR，避免同一需求算两遍 |
| 金蝶云星空 | 「预测单」是计划管理下的独立单据，单据体逐行录物料与预测数量，支持拆分行 | 销售订单与预测单都是 MPS/MRP 的需求来源，按需求优先级占用供给并建立预留关系；「预测冲销」让销售订单冲减预测可冲销数量；计划订单携带预测单号作为需求单据号(补丁说明) |
| 用友 U8 | 需求规划 → 需求来源资料维护 → 「产品预测订单输入」，按行录存货与预测数量，可用「预测订单展开式」快速维护多行多期间；公开资料里没有单独的「手工需求」来源，手工录入的独立需求即走产品预测订单 | 客户订单与产品预测订单同为 MRP 毛需求来源，按 BOM 展开并扣现存量与未关闭订单；需求跟踪方式可按销售订单、订单行或需求分类号给供需分组 |
| Odoo(MPS) | 主生产计划页「Add a Product」逐个加产品，在同一张表里按期间手填预测需求 | 打开「Actual Demand」后，同一行同时显示已确认销售订单的需求与手填预测，补货建议一起算 |

共识：

1. **独立/手工需求是一张带号的单据：一个表头(编号、类型、日期)下挂多行物料(物料、数量、可选日期)**，不是一个物料一张单。
2. **需求编号是追溯锚点**：计划订单、建议供给沿需求单号(必要时加行号或需求分类号)回查来源。
3. **它和销售订单在同一次 MRP/分析运算里一起净算**，共用库存和在途，不另开一套计算。

与本系统的差异及取舍：

- 同行的「预测」会被随后到来的销售订单消耗(SAP 策略 40、金蝶预测冲销)。本系统的五类手工需求(返工、试制、样品、备库、其他)是销售之外的真实额外需求，不做冲销，直接与所选销售行叠加计算。
- 同行把需求单持久化成独立单据表。本系统按 ADR-029 的模型保持「页面内输入 → 点分析才成为分析来源行」，不另建需求单表；表头字段(来源类型、编号、原因、日期)随每一行来源保存。
- SAP 同一物料不同日期是同一条需求下的计划行；本期同一编号下同一货品只允许一行，不同日期请合并或换编号。

## 三、决策

### 3.1 业务口径

- **手工需求像一张小订单**：一个需求编号，表头 = 来源类型(返工/试制/样品/备库/其他) + 需求编号 + 来源原因 + 需求日期；明细 = 多行货品 + 数量 + 可选的行需求日(不填沿用表头日期)。
- **同一编号下同一货品身份(货品 + 颜色 + 单位)至多一行**。编号比对忽略大小写和首尾空格。
- **一个(来源类型, 需求编号)仍只属于一份物料分析**(ADR-029 原规则保留)。改变的是：这个编号下现在可以有多行货品。
- **本次分析 = 录入的手工需求行 + 多选的销售订单行**，由一个按钮「联合分析所选 N 项」一起分析，与「销售下单 → 调度台计划多选 → 分析」同一流程。一次分析可以录多张手工需求单(默认一张)，各有各的编号，因此仍可在一次联合分析里混合返工与样品。
- **仍是页面本地输入**：只有点联合分析、服务端预览成功后才落成分析来源行(ADR-029 模型)。不新建需求单表，不进调度台待排列表，不做 Excel 导入。
- **分析建立后不能在原编号下增减货品**：同编号、同货品集合再次提交 = 恢复原分析；货品集合不同，服务端返回 409：调用人看得到原分析时点名原分析号与货品数，说明已建的分析不能增减货品，要增减货品请换一个需求编号(只改数量请打开原分析刷新)；看不到原分析时只提示这个编号已被另一份物料分析使用、请换一个编号，不透露分析号。这与销售来源「刷新不能改来源集合」一致：原分析里既没有增减货品的入口，取消原分析也不会释放编号。
- **500 上限不变**：销售行与手工行合计最多 500 条来源，每个手工货品行计一条。

### 3.2 候选模式页面

桌面：

- 顶部一行引导文字 + 「主仓库」下拉。
- 分段切换 `UtenSegmentedFilter`：「销售订单产品 (已选 a)」「手工需求 (b 行)」，计数为中性数字。
- 销售段：搜索框 + 原候选表，新增行内列「本次分析数量」；已选行显示输入框(预填剩余量)，未选行显示「—」。原表格下方最高 240px 的已选列表框删除。
- 手工需求段：可滚动的需求单卡片列表 + 「再建一张手工需求单」。每张卡：表头一行(来源类型下拉 | 需求编号 | 来源原因 | 需求日期 | 多于一张时可「删除此单」，有明细先确认)，下方是自研可编辑表格 `UtenEditableGrid`，列为 货品名称(必填，点开多选货品选择器) | 编号 | 颜色 | 规格 | 单位(只读，取自货品) | 数量(必填，大于 0) | 需求日(选填)。多选时第一个货品填入所点的行，其余依次填入其后的空行，不够再追加新行；本卡已有的货品跳过并提示。行可删除、表尾可加行，合计按单位分组，不跨单位相加。
- 货品选择器用 `showUtenGoodsPickerMulti`，范围「除未分类外的全部货品」，与销售订单编辑页一致；通过 Riverpod Provider 注入以便测试替换。
- 右下悬浮组：「已选 N 项」胶囊(N = 已选销售行 + 已选货品的手工行) + 「联合分析所选 N 项」。胶囊上的清除同时清空两边，有手工行时先确认。

窄屏：同样两段放在滚动区顶部；销售段沿用卡片 + 翻页 + 底部数量编辑；手工段为全宽的需求单卡片，数据模型与桌面同一套。

提交前页面按大白话拦截并不发请求：未选来源类型；需求编号为空或超过 200 字；来源原因少于 2 个字；填了表头或数量却没选货品；数量为空或不大于 0；同一张单里货品重复；两张单用了同一类型同一编号(提示合并成一张)；什么都没录。没有货品也没有数量的空行忽略。每个有货品的行生成一条来源：类型、去掉首尾空格的编号、货品/颜色/单位、数量、去掉首尾空格的原因；日期先取行需求日，没填取表头需求日期，再没有取页面默认日期。预览幂等键把每条来源的日期算进去。

候选页的已录手工需求不纳入 ADR-121 表单草稿保护(边界不变)。

### 3.3 分析模式

顶部卡片在「关联销售订单」旁增加只读手工需求标签，按(类型, 编号)分组显示如「返工 · RW-001 · 3 个货品」，悬停显示来源原因。

### 3.4 服务端

- 预览规整：手工编号去首尾空白；去重键用规范编号(去空白 + 小写)。同一编号下货品重复返回校验错误「需求编号 X 下货品重复，请合并为一行」，不再 500。同一编号的多行统一使用第一行的写法保存，历史列表里该编号只出现一次。
- 并发：`lockSourceIdentities` 在原有逐货品咨询锁之外，为每个不同的手工(类型, 规范编号)再取一把编号级事务咨询锁，锁键文本与数据库触发器完全一致，全部锁键一次排序后依次获取，避免 {X:A} 与 {X:B} 两个并发请求绕过“一号一分析”。
- 手工来源的货品主档校验(基本单位等)改为整批一次查询，不再每行两条语句。
- 复用：`findReusableAnalysis` 每个不同编号只查一次；编号已在进行中的分析里但货品集合不同时，返回专门的 409，文案按调用人能否看到原分析分两种(与打开、刷新分析同一套可见范围判定，即 V233 按负责人隔离：本人负责或交接给本人的分析可见，有 `production_plan:view:all` 的看全部；没有当前用户的系统路径按可见)：
  - 看得到：「需求编号 X 已在物料分析 WL… 中(N 个货品)；已建的分析不能增减货品，要增减货品请换一个需求编号(只改数量请打开原分析刷新)」。
  - 看不到：「需求编号 X 已被另一份物料分析使用，请换一个需求编号」，不带分析号和货品数，也不提示打开原分析。
  这一步在写权限检查之前执行，所以必须自己判断可见范围，否则会把别人的分析号漏给无权查看的人。两种文案都只指向走得通的路(换编号)：已建分析的来源集合改不了(刷新会拒绝任何来源增减)，取消原分析也不释放编号。销售来源的通用提示不变。
- 下游不变：每个分析行下达一张计划，与多行销售订单一致。

### 3.5 数据库规则(V738)

1. 删除 `uq_production_material_analysis_manual_source_ref`(现行定义在 V529)。
2. 系统来源保持全局唯一：新建 `uq_production_material_analysis_system_source_ref`，`(source_type, lower(btrim(source_ref)))`，条件为未删除、来源类型不是销售行与五类手工类型、且不是 `SUBCONTRACT_PREPARATION` 的 `SC-ORDER:%`。所有系统来源编号仍按(来源类型, 编号)全局唯一；其中只有 `MAKE_COMPONENT`、`SUBCONTRACT_MAKE` 在生成前做「编号可用」探测并换码重试，依赖此索引；`AGGREGATE_MAKE`(「共享制造 日期 批次号前 8 位」)与 SC-PREP(`SC-PREP:` + 订货行 id)靠构造保证唯一，没有探测，由此索引在数据库层兜底。
3. 手工行唯一：新建 `uq_production_material_analysis_manual_source_line`，`(source_type, lower(btrim(source_ref)), goods_id, color_id, unit_id) NULLS NOT DISTINCT`，只覆盖未删除的 `REWORK/TRIAL/SAMPLE/STOCK/OTHER` 行。
4. 一号一分析：函数 `fn_guard_manual_demand_single_analysis()` 挂 INSERT 触发器 `trg_guard_manual_demand_single_analysis`，并按 ADR-106 / V734 的写法另挂 UPDATE 触发器 `trg_guard_manual_demand_single_analysis_upd`(WHEN：`analysis_id`、`source_type`、`source_ref`、`is_deleted` 有变化，且为未删除的手工行才起跳)，两条都 ENABLE ALWAYS。函数先取事务咨询锁 `MATERIAL-ANALYSIS-MANUAL-REF:<类型>|<小写去空白编号>`，再查是否有其它未删除的同类型同编号手工行属于另一份分析；有则以 SQLSTATE 23505 报「需求编号 X 已属于另一份物料分析, 同一需求编号只能在一份物料分析里; 请换一个需求编号」。查询条件写死五类手工类型，确保走第 3 条的部分索引。
5. 不回填：新规则严格宽于旧索引，存量数据不可能违反。

为什么用触发器而不是需求单表或排他约束：库里没有 `btree_gist`，排他约束不可用；需求单表要新增审计登记、清库分类、主档引用登记和一整套读写接口，与「页面本地输入、不新建表」的决定相悖。FQC 品质恢复自动建的返工来源(`FQC-RECOVERY-` 编号，单货品)同样受新索引与触发器约束，行为不变。

## 四、明确不做

- 不新建持久化需求单表，不由系统取需求单号；需求编号仍由人填，作为稳定业务编号。
- 手工需求不进调度台待排列表，不做 Excel 导入。
- 不做预测冲销：手工需求不被销售订单消耗。
- 同一编号同一货品按日期拆多行(计划行)不做，请合并为一行或换编号。
- 分析建立后在原编号下增减货品不做；要增减货品请换一个需求编号新建，只改数量可打开原分析刷新。
- 需求编号不带到生产计划单、车间任务的搜索与展示；现有可搜索处(分析记录页、调度台进行中、借料候选)不变。
- 用户录入编号与系统保留前缀(`FQC-RECOVERY-`、`SC-PREP:`、`SC-ORDER:` 等)的冲突拦截不在本次范围。

## 五、后果

- 一张返工/样品单的多个货品一次录入、一次分析；分析记录里该编号只出现一次，每个货品行各自下达计划。
- 编号大小写/空格变体不再触发 500，改为可读的校验提示。
- 手工行插入与相关列更新多一次触发器检查；按 ADR-106 用列级 WHEN 限定起跳，只在分析、类型、编号、删除标记变化时执行。
- 表头字段在每行重复保存，服务端不强制同号各行原因、日期一致(由页面按表头统一填)；若以后需要需求单实体，再另立表并迁移。
- 迁移头同步点(迁移索引、清库白名单、契约测试)需在合并时按真实目录重算；V735-V737 在其它会话在途。

## 六、测试

- 后端：`MaterialAnalysisServiceBehaviorTest` 覆盖一号多货接受(统一写法)、同号同货品大小写/空格变体报校验错误而非 500、同号同货品集合重开复用、货品集合不同返回新 409(看得到原分析的点名分析号，看不到的只得到中性提示)；`ProductionMaterialAnalysisPersistencePostgresTest` 改写为新规则(一号三货同分析可建；同号同货品重复 23505；同号进第二份分析 23505；系统类型仍全局唯一；SC-ORDER 例外不变)；`FullChainEndToEndTest` 增加一号三货联合预览、逐行下达计划、分析记录只显示一次编号的场景，并换一位只看得到本人分析的计划员确认 409 不透露原分析号；迁移契约测试随头同步。
- 前端：`production_material_analysis_page_test.dart` 覆盖多选三个货品填数后联合分析的请求体(同类型/编号/原因，逐行数量与日期，加上已选销售行)、重复货品跳过、两张单同号拦截、缺编号/原因/数量不发请求、清除胶囊确认、375px 窄屏不溢出且可分析、分析模式手工需求标签、500 上限提示；另覆盖分析请求进行中明细表格锁住、再次校验时清掉过期标红、新建的需求单卡片滚进视野、640 宽窗口与 375px 加 1.5 倍字号下两个分段完整可见、表头日期早于 2020 年时行需求日选择器仍能打开。
- 源码与测试通过不代表业务库已安装；部署以迁移索引与服务器更新记录为准。
