# V532：销售来源UUID查询索引

V532只新增 `ar_ap_source_refs(source_type, source_id, ledger_id)` 普通索引，支持按销售订单UUID查找其应收来源，再沿台账UUID计算余额。正式文件为 [V532__sales_source_uuid_lookup_index.sql](../../server/src/main/resources/db/migration/V532__sales_source_uuid_lookup_index.sql)。不修改查询、金额、数量、历史来源记录或既有迁移，也不改变唯一约束；没有新增业务表。

V531的50万订单压力副本显示，`SalesOrderMoneyPositionQuery.invoices` 从 `source_type='SALES_ORDER'` 与真实UUID `source_id` 定位来源时，会扫描50万条来源记录。既有索引以 `ledger_id` 或 `source_no` 开头，不能直接限制这次UUID查找。V508与V531的四个原索引定义完全相同，问题不是金额迁移丢失了索引。

新索引第三列为随后使用的 `ledger_id`，无需再包含金额、说明或其他宽字段。迁移采用普通 `CREATE INDEX`：名称意外冲突时明确失败，不能用 `IF NOT EXISTS` 将异形索引当成成功。该索引建立期间会限制该表写入，应随既定迁移维护窗口执行。

## 本地验证与范围

使用原专用合成压力数据的独立副本，保留V508基线和V531计时证据，没有重新生成50万数据。`SalesSourceUuidIndexPressurePostgresTest`是显式压力开关启用的真实PostgreSQL回归，要求已有独立副本及私有身份标记；普通测试环境不会自动生成大数据集。

该回归从V531/490仅应用V532，升级至V532/491。索引前后调用同一个实际查询，参数仍为UUID；完整 `InvoicePosition` 结果相等，计划从扫描50万来源行转为使用新索引。订单、订单明细、发货、发货明细、退货、退货明细、应收台账和来源记录共八张表的行数与按UUID排序的业务字段摘要全部不变。

索引建立只对独立迁移连接限制并行线程，以适应测试Docker的64MiB共享内存；没有修改数据库、角色或容器的全局参数。应用压力连接保持原默认值，独立的计时前探针核验八条实际连接的查询/维护并行值均为2。

定向计划证据与数据摘要位于 `.codex-tmp/release-preflight-20260908/pressure-v532/index-proof/`，V531原结果与共享内存故障/事务回滚证据保留在相邻 `pressure-v531/`。执行计划证明了访问范围缩小；端到端查询吞吐仍以相同8线程、4000次逐次校验的独立计时结果为准，不将单次EXPLAIN耗时直接当成应用吞吐倍数。

原压力用例未改，每次调用核对资金摘要完整性及三项金额。两轮均使用同一生产代码、同一合成副本和8线程/4000次调用，应用连接的并行默认值均为2；准备与迁移不计入以下耗时。

以上为本机受控合成数据的一次前后对照，证据支持消除该来源查询的线性扫描；不是HTTP吞吐、写入链吞吐或生产环境固定加速倍数。更早V508的历史记录单独保留，不将其环境差异混入本次索引归因。原用例没有输出逐次延迟或最大值，因此只报告实际采集的分位数。
