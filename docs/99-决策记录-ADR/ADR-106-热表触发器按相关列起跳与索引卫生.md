# ADR-106 热表触发器按相关列起跳与索引卫生

- 状态：已接受(2026-09-23，V674-V676，零新增权限码、零新增业务表)
- 关联审计：db-schema-06 / perf-production-exec-02 / perf-warehouse-quality-06 / perf-material-analysis-14(守卫与延迟约束部分) /
  perf-production-exec-11(单号触发器部分) / db-schema-13 / perf-warehouse-quality-13 / db-schema-14 / db-schema-15 / db-schema-08
- 完成度：db-schema-06 / perf-production-exec-02 / perf-warehouse-quality-06 只完成第一步(按相关列起跳 + 删除被包含的重复
  校验)，「每键只校验一次」等根治步骤见 §2.1「没有做的」；其余各条在本 ADR 范围内完成。

## 一、背景

守恒与身份规则写在数据库触发器里是平台的最后一道防线(全局机制 §6.3)，这一点不变。问题出在「什么时候起跳」：

1. 预留、库存单据头/明细、计划明细、执行段、物料分析三表、估值图、权益事件这些热表上，约束/守卫触发器几乎都没有
   列过滤和 WHEN。PostgreSQL 对每一次 INSERT/UPDATE 都给每个延迟约束触发器排一个事件，提交时逐个执行；只改
   `updated_at` / `lock_version` / 派生数量、甚至什么都没改的更新，也会把守恒、溯源、预算校验整套重跑一遍。
   2026-09-23 实测一行车间直送审核调了 **600 次**触发器函数(其中 282 次延迟校验)，提交 742ms。
2. 单号不可变守卫 `fn_reserve_business_document_identifier` 挂 `UPDATE OF 单号列`，但 JPA 整行更新会把所有列写进
   SET，于是每次保存都整行转两次 jsonb 只为确认单号没变。
3. 「已被数量引用的货品不能改基本单位」靠 52 张表上的 104 个语句级触发器维护 `goods.quantity_unit_locked`，每条
   写入语句都跑一段动态 SQL；UPDATE 版本受过渡表限制不能加列过滤。
4. 收付款类别引用校验取全局排他咨询锁，引用同一类别的财务单据、总账分录互相排队。
5. 迁移逐次追加索引从未去重：96 个普通索引被前缀覆盖或与同列唯一约束重复；而估值图、需求、预留、计划明细、总账
   凭证的反查列没有领头索引。

## 二、决策

### 2.1 约束/守卫触发器只在「相关列真变了」时起跳(V674)

- **不改任何校验函数的判定**，只改触发器定义。对热表上每个对 UPDATE 起跳的约束/守卫触发器，列出它对本表真正读取的
  列，加 `WHEN (OLD.a, OLD.b, ...) IS DISTINCT FROM (NEW.a, NEW.b, ...)`。
- **相关列集怎么来的**：从触发器函数出发，沿函数体里出现的函数名、视图名递归展开调用闭包；只取「函数本身」以及
  「文本里提到本表或依赖本表的视图」的那些函数/视图，把其中出现过的本表列名全收进来(保守超集：列名只要出现过就算
  相关)。整行引用(`to_jsonb(NEW)`、`EXECUTE`、行作参数)逐个人工核对，都只按字面键取列。永远变化的簿记列单独核对：
  执行段的 `lock_version` 每次更新都被 `trg_validate_production_execution_segment` 递增，唯一读它的是已退役
  (CANCELLED)拆批源段的证明，所以执行段完整性触发器写成「相关列变了 **或** NEW.status = 'CANCELLED'」。
- **函数入口本来就按行类型提前返回的，把同一条件写进 WHEN**：如预留按 `owner_type`、估值事件按 `operation`、
  精度界按 `value_model`。为了与函数里 `IF 条件 THEN RETURN` 的 NULL 语义逐字等价，统一写成
  `(条件) IS NOT TRUE`。
- **为什么等价**：延迟校验读的是提交时的终态。某行终态里相关列的取值，一定来自「最后一次改动这些列的那个事件」
  (或插入)，这个事件的 WHEN 为真、照常排队；只改无关列的事件，终态读到的相关列与上一次排队时相同。BEFORE 守卫
  本来就只在身份列/状态真变化时才会拒绝，WHEN 就是函数里拒绝分支的条件。
- **语义边界**：收窄后，一次只改无关列的更新不再「顺带」复查别的表的状态。跨表不变量本来就由每张参与表各自的
  触发器守护(另一张表变化时由那张表的触发器排队)，平台从不依赖这种顺带复查；测试里过去用「只改 updated_at」来
  逼出延迟校验的写法，改为把一个相关列改过去再改回来(终态不变)。
- **只用 WHEN、不新增 UPDATE OF**：PostgreSQL 的列清单只看 UPDATE 语句的 SET 目标，看不到 BEFORE 触发器改写的列
  (例如预留的投影列、执行段的锁版本)；WHEN 在最终行上求值。已有的 `UPDATE OF` 原样保留。
- **INSERT 与 UPDATE 共用的触发器拆成两条**(WHEN 在 INSERT 里不能引用 OLD)：原名只保留 INSERT(/DELETE)路径，
  UPDATE 路径为 `原名_upd`，INSERT 与 DELETE 条件不同时另起 `原名_del`。后缀命名保证同表、同时机、同事件的触发器
  按名字排序的执行先后不变(迁移生成时逐表核对)。需要用 `SET CONSTRAINTS <名> IMMEDIATE` 立即校验更新路径的
  地方，要同时点名 `_upd`。
- **重建时保留启用模式**：DROP + CREATE 会把 `ENABLE ALWAYS`(复制角色 `session_replication_role=replica` 下照样起跳)
  复位成默认。27 个原为 ALWAYS 的守卫(估值图、预留保管、执行段谱系等)重建出的每一条(含 `_upd` / `_del`)逐条恢复，
  绕过普通触发器的维护写入仍被它们拦住；契约测试把这 38 条(27 条原名 + 11 条 `_upd`)写死成清单逐条断言仍是
  ALWAYS(只拿变体和原名互比，两条一起丢了 ALWAYS 时照样相等，抓不到)。
- **合并被完全包含的重复校验**：预留、领料单头、领料明细上的三条采购来源溯源触发器(`trg_purchase_*_provenance`)
  逐条断言的「生效中的采购收货分配」，正是同表覆盖校验 `fn_assert_receipt_reservation_coverage` 在容量检查之后
  再逐条断言的同一批分配(`production_material_receipt_allocations.reservation_id` 非空)，三条删除。
- **只完成了第一步，根因还在**。审计 db-schema-06 / perf-production-exec-02 / perf-warehouse-quality-06 说的根因是
  「逐行延迟校验在提交时对每一行、每一个事件把同一个键的聚合重算一遍」。本轮只去掉了「无关列变化也排队」那一部分
  事件；相关列一变，每行、每个事件仍各算一次聚合，同一个键的 N 行仍算 N 遍。实测(§三)提交里的延迟校验仍是几百毫秒，
  离审计给的「一行直送审核 COMMIT < 50ms」差一个数量级。三条发现都按「部分完成」登记。
- 没有做的(另立任务排期，属于下一波写路径重构)：
  1. **每键只校验一次**：行触发器只往事务级脏键表(如 `pending_integrity_checks(txid, check_kind, key)`)登记，提交时
     每个不同的键校验一次；或改成语句级触发器(`REFERENCING NEW TABLE`)先按键去重再做一次集合校验(exec-02 第 3 步、
     db-schema-06 修法 1)。要改写每个校验函数的入参与读法，不是改起跳条件。
  2. **同表校验合并成一个函数、共享聚合只算一次**(exec-02 第 2 步、pwq-06 第 2 步，如预留的 16 个延迟校验合并到 3 个以内)。
     本轮只删掉了被完全包含的 3 条；其余各自读不同的聚合，合并不减少聚合次数，要和第 1 条一起做才有意义。
  3. **写入一次成形**(pwq-06 第 3 步)：估值 SOURCE 节点插入时带齐精度界、停用与退货游标合并成一条 UPDATE，要改
     `InventoryValueLedger` / `InventoryPositionService` 的写路径。
  4. **预留按归属类型拆表**(db-schema-06 修法 2 的中期部分)与**把派生不变量挪到应用层 + 对账兜底**(pwq-06 第 4 步)：
     后者会削弱数据库最后一道防线，要先有对账与测试替代，本轮不做。

### 2.2 单号不可变改列级守卫(V674)

`fn_reserve_business_document_identifier` 只挂 BEFORE INSERT(取号路径一字不变，删掉走不到的 UPDATE 分支)。
33 张取号表各加 `trg_business_document_<表>_upd`：`BEFORE UPDATE OF 单号列[, 区分列]
WHEN (单号或区分列真变了 OR 单号为空)`，执行新的 `fn_guard_business_document_identifier_immutable`，报错文案与原来
逐字相同。

### 2.3 货品基本单位「已使用」改为按需现查(V675)

- 删除 104 个语句级触发器、`fn_lock_goods_quantity_unit_from_references` 和 `goods.quantity_unit_locked` 列。
- `fn_goods_quantity_unit_in_use(货品)` 沿用 V498 的来源清单 `fn_goods_quantity_reference_sources()`(唯一事实源)，
  拼成一条 UNION ALL 的 EXISTS，命中第一行即止；各来源货品列由 V676 补齐完整领头索引。
- 数据库守卫 `trg_goods_quantity_unit_immutable` 只在单位真的变化时起跳：先对本货品行 `FOR UPDATE`，等正在写
  引用的事务结束(外键检查与 `GoodsQuantityBasisLocks.lockForQuantityUse` 都对货品行持 `FOR KEY SHARE`，二者互斥)，
  再用新快照判定。反方向(先改单位)时，写引用方的 `FOR KEY SHARE` 等改单位事务提交后读到新单位。并发写同一货品
  的业务互不排队(以前未使用货品的基准锁是 `FOR NO KEY UPDATE`，同货品写入会串行)。前提是读已提交隔离级别
  (平台默认)。
- 串行化靠「一行变成数量引用必经外键检查」：60 个来源货品列都有指向货品的不可延迟外键(插入、或把货品列改指别的
  货品，都会对新货品行取 `FOR KEY SHARE`)；唯一带行条件的来源 `legacy_measurement_profile_snapshots`
  (`distinct_document_count > 0`)自 V442 起只追加，UPDATE/DELETE 一律被 ALWAYS 守卫拒绝，已有行不可能被改成
  「已使用」。这两条前提由 `SchemaIndexHygieneContractTest` 在迁移到头的库上钉住，新加来源不满足时先红。
- 货品详情的 `quantityUnitLocked` 改为查询时计算(`GoodsRepository.quantityUnitInUse`)；编辑时现查一次，拦截、
  写入、回显共用。接口字段不变。
- **口径变化(推翻 V498「一旦用过终身锁定」，待业务确认)**：「是否已使用」现在只看此刻还在不在的数量行，
  下面两种情形货品不再算「已使用」、可以改单位——此时确实没有任何数量按旧单位存在：
  1. 引用被**硬删除**：草稿明细被删掉；**清空业务数据**(V498 与基础资料页原写「清空业务数据不自动解锁」，现改为
     清空后可改单位)。
  2. 草稿明细**改指别的货品**(`UPDATE ... SET goods_id = 另一货品`)：原货品若没有别的数量行就放开，新货品随即锁定。
  软删、取消、红冲的历史行仍算使用；组装清单是主档，清空业务数据后仍锁定。旧契约用例
  `deletingOrReassigningReferencesCannotUnlockTheOriginalGoods` 断言的正是旧口径，已改为
  `softDeletedOrCancelledReferencesKeepTheUnitWhileRemovedDraftLinesReleaseIt`(软删仍锁、改指与硬删后放开)。
  若业务坚持「终身锁定」，要另行设计「首次使用」登记，届时再评估写入开销。

### 2.4 收付款类别引用改共享锁(V674)

引用方(`fn_guard_payment_style_reference`、账户类别 UUID 权威、系统过账角色)与 Java 的
`PaymentStyleHierarchyLock.lock` 改取同一把咨询锁的共享模式；层级/状态变更方(`PaymentStyleService` 走
`lockForHierarchyChange`、`fn_guard_active_account_style_status`)保持排他。引用方之间不再排队；改层级仍要等所有
在途引用提交后，看到已提交的引用再决定。账户类别权威与系统过账角色本质是「引用一个类别」，归引用方(审计原文把它们
列在层级侧，按代码事实纠正)。

### 2.5 索引卫生(V676)

- 删 96 个冗余索引。判定：同表、同访问方法、同部分谓词、同表达式，键列(连同算子类、排序规则、排序选项)是另一索引的
  前缀，且 INCLUDE 列已被对方携带；支撑主键/唯一/排他约束的索引永不删除，唯一索引只在对方是同列唯一索引、且对方的
  空值规则不比它宽(`NULLS NOT DISTINCT` 只被 `NULLS NOT DISTINCT` 覆盖)时才算重复；完全相同的两条留旧删新。
  本次删掉的 96 条全是普通(非唯一)索引。带 INCLUDE 的覆盖索引(如 `idx_stock_balances_goods_cover`)保留，被它覆盖的
  窄索引删掉。暂不删两条并写进白名单：审计归档表的索引(审计整改工作流统一处理)，
  `idx_procurement_iqc_stock_in_item_batch`(重置脚本的 V448 读路径自检要求它在)。
- 补 44 个热点关联列领头索引(含 V647 车间工单原位增长事件的 plan_item_id)：估值图(`stock_value_*`)、物料需求、库存预留、计划明细、总账凭证的引用方；补 31 个
  货品数量来源列的完整领头索引(契约只要求等值探针用得上：不带条件，或只带「该列 IS NOT NULL」的部分索引也算，
  其它条件的部分索引不算)。不补 `*_by` 审计列和字典/人员父表；估值节点自引用游标列(每次移动游标都会改写，
  建索引会让这些更新失去 HOT)、没有查询按其回查的列、已退役的 MAKE 委托表不补，逐条写进契约测试白名单。

## 四、测试

- `HotTableTriggerHygieneContractTest`：热表上对 UPDATE 起跳的延迟约束触发器必须带 WHEN；取号函数只挂 INSERT、每张表
  都有列级不可变守卫且函数里不再有 UPDATE 分支；三条被包含的溯源触发器不能装回来；引用方共享锁、层级方排他锁；
  V674 重建的 38 条 ALWAYS 守卫写死清单逐条断言仍是 ALWAYS。
- `SchemaIndexHygieneContractTest`：与 V676 同一条前缀覆盖 SQL 结果为 0(白名单写明原因)；热点外键都有领头索引；
  货品数量来源列都有等值探针用得上的领头索引；V675 的两条并发前提(来源列都有不可延迟外键、带行条件的来源只追加)；
  单位锁触发器与列已不存在；在一笔回滚事务里自检规则本身(NULLS NOT DISTINCT 唯一索引不被误判冗余、部分索引只认
  「该列 IS NOT NULL」)。
- `WorkshopDirectTransferBatchEndToEndTest`：真实直送链上每类收窄各做负向回归(改单号/单据类型/生产关联单据身份/
