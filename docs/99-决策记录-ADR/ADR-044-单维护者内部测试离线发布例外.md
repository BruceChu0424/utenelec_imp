# ADR-044：单维护者 internal-test 离线发布例外

- 状态：Accepted（仅源码框架；未执行发布）
- 日期：2026-08-21
- 适用环境：internal-test

## 背景

Uten IMP 当前是私有仓库，维护者只有一人；GitHub 当前套餐/仓库设置无法把私有 Environment reviewer
当成真实的第二位独立审核人。为了内部测试购买 Enterprise 或把 ERP 私库改 public 都不是合理控制。
但直接让同一在线 CI 同时测试、持有签名 key、写 OSS 和连接服务器，也不能接受。

本 ADR 是单维护者补偿控制，不虚构双人审批，不等同于独立人审或生产发布治理。它不能豁免签名、
H01–H12、项目专用 `known_hosts`、目标数据库、恢复、真实岗位 UAT 或人工 activation。

## 决策

### 1. 保留现有链，新增完全独立的 unsigned-only 链

`.github/workflows/release.yml` 保持字节不变。新增：

- `.github/workflows/unsigned-release-candidate.yml`：仅 `workflow_dispatch`；
- `.github/workflows/_unsigned-candidate-build.yml`：仅 `workflow_call`。

入口只接受 canonical version、40 位 lowercase `expected_main_sha` 和精确确认串。顶层权限仅：

```yaml
permissions:
  actions: read
  checks: read
  contents: read
```

没有 Environment、secret、`id-token:write`、OSS、签名、服务器、staging 或 activation 能力。

入口强制 `github.ref=refs/heads/main`、exact-SHA checkout、`persist-credentials:false`，并在构建前后读回
current main 与远端 tag 不存在。它精确绑定三个 push workflow、当前 run attempt 和七个
`github-actions` job；缺失、重复、额外、旧 attempt、分页不完整或任何非 success 状态都失败。

builder 复用现有 unsigned `publish-candidate.tar` 七成员合同与完整 Java/Flutter/部署/wheelhouse 门禁。
manifest 仍写 `refs/tags/<version>`，不修改 manifest/channel/updater runtime schema。GitHub artifact
保留 1 天；最终 job 绑定 artifact ID、service SHA-256、size、run/head SHA，回读原始 ZIP 并要求唯一
`publish-candidate.tar` 成员。

### 2. 离线设备验真和签名

离线 verifier 是预审并通过带外记录固定 SHA-256 的 stdlib-only 工具。它不 import 或执行 candidate
中的 JAR、Python、Shell、Web 或 `.pth`，只解析和核对字节、exact-set、摘要与已有 `release_guard`。

人员 Git tag key 与 Release artifact key 分离。Git authority 在离线 repository 创建并验证 signed
annotated tag object/bundle；该 tag 当前不 push GitHub，因为推送 `v*` 会触发现有 `release.yml`。

Release key 使用兼容现有 updater 的 namespace 签：

- manifest/channel：`uten-imp-release-v1`；
- wheelhouse attestation：`uten-imp-updater-wheelhouse-v1`；
- release decision：`uten-imp-single-maintainer-decision-v1`。

`release-decision` 必须是 canonical exact-key JSON，固定：

- `environment=internal-test`；
- `singleMaintainerException=true`；
- `maintainerCount=1`；
- `independentReviewerPresent=false`；
- `activationAuthorized=false`；
- `stagingAuthorized=false`；
- `ossPublicationAuthorized=false`；
- `remoteTagPublished=false`。

签名设备不持有 GitHub、OSS 或服务器 SSH 凭据。
`ossPublicationAuthorized=false` 也意味着该 decision 不能作为 OSS 写入授权；任何后续 apply 必须
另行绑定变更授权、canonical plan SHA-256、精确确认串和短期 STS。

### 3. 在线管理机只处理已签 publication

在线管理机使用短期最小权限 STS。先只读下载并验签旧 pointer/channel，要求 sequence 严格递增；
version 对象与 versioned channel create-only，按现有 updater 对象键逐对象上传后立即执行有大小上限的
byte readback。每个旧 pointer 先 create-only 写入永久 transition 记录，绑定获批 plan、signed
publication、目标 version/sequence；同一旧 pointer 的异计划拒绝，`LATEST.txt` 最后。首次 bootstrap
使用独立精确确认串。verify 与 plan 都从 signed manifest/decision lineage 反向校验 artifact sidecar、
standalone SBOM 和 attestation；重算未签 inventory/receipt 不能替换它们。失败不删除、不覆盖 immutable
对象，同一计划只允许完全相同字节的续跑。

Git tag key、Release artifact key、Admin Key A、Admin Key B、服务器 Host Key authority 五者相互分离。

### 4. 服务器仍为人工边界

updater/retention timer 保持 disabled。staging 与 root activation 均人工，且必须由后续独立授权记录
放行；本 decision 永远不能授权 activation。H01–H12 或项目 `known_hosts` 缺一项，包含只读 SSH 在内
都禁止。

## 被拒绝的方案

1. 把私有 ERP 仓库改 public：信息安全边界不可接受。
2. 为内部测试强制购买 Enterprise：成本与真实风险不匹配，也不能替代离线 key custody。
3. 虚构第二审核人或让同一人使用两个账号互审：制造虚假证据。
4. 复用 `release.yml` 的 publish/bootstrap job：会把 Environment、OIDC、签名和 OSS 权限带入本例外。
5. 在 main dispatch 中把 manifest `sourceRef` 写成 `refs/heads/main`：破坏现有 updater tag 合同。
6. 把离线 verifier 放进 candidate 并执行：candidate 是未信任输入，不能决定自身可信度。
7. 让 decision 直接授权 staging/activation：超出单维护者补偿控制范围。

## 后果与残余风险

正向结果：构建/test 进程没有发布 key 或云权限；离线签名 key 不接触网络凭据；OSS 写入可由已签字节、
单调 sequence、create-only 和 readback 守住；真实单维护者事实被如实记录。

残余风险：同一维护者仍能同时决定代码与发布；补偿控制降低但不消除内部人风险，也不等价于独立人审。
GitHub 私库保护能力不可用、staging/activation 仍为人工、没有独立 human reviewer 必须永久写入 decision。

## 验收与本次执行边界

源码必须通过新增 workflow/Python/template 安全测试、全 updater 测试、模板检查、shell/AST 合同，且
`.github/workflows/release.yml` 与业务 Java/Flutter/Flyway/manifest/channel/updater runtime schema 不变。

合并本 ADR/框架不会生成 unsigned candidate。本次不 dispatch workflow、不创建 tag/GitHub Release、
不签名、不写 OSS、不连接服务器或目标数据库、不 staging、不 activation。后续每一层必须绑定同一
version/commit/artifact/tag/manifest/decision lineage，并分层报告。
