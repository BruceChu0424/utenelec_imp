## 一、背景：用户的核心疑问

销售下了订货单，仓库**有现货**时该走什么流程？用户在 V90 已实现"审核即软预留 + 部分预留 + 取消释放 + FIFO 消耗 + advisory lock 防超卖"的主链之上，提出三个未收口的尾巴：

1. **"一直保留别人又不要了怎么办"**——预留没有生命周期，货会被无限期占着。
2. **"只有一件，是有限给他还是让他让出来"**——稀缺时多订单抢同一份库存，无仲裁。
3. **安全库存**——销售可用量口径没扣安全库存，能把库存预留到 0、吃进缓冲。

并附了一份大而全的"方案"（含 7 天有效期+续期、VIP/促销优先级、自动抢占软预留、优先券、批次召回等）。

## 二、关键判断：制造业 ≠ 电商，方案过拟合一半

研究报告（SAP/Oracle/D365 官方文档交叉验证）核心结论：

| 用户方案条目 | 专业做法 | 采纳？ |
|---|---|---|
| 7 天有效期+2 次续期 | SAP **OMBN 保留期(默认 30 天) + 批程序 RM07RVER 按"需求日期 BDTER"清理**，不是创建日期倒计时；三大 ERP **无"过期前提醒"原生功能**（自建领域） | ❌ 7 天倒计时 → ✅ **交期驱动** |
| 提交=软预留可被自动抢占 | SAP 走 **backorder processing（CO06/V_V2）人工/半自动重排**；硬预留不可抢、已领料不可抢 | ❌ 自动抢占 → ✅ **手动让单** |
| VIP/大额/促销优先 + 公平份额自动 | SAP APO Allocation 的高流量分销场景；制造业客户价值差异靠人工判断 | ⏸️ 仅加 priority 字段+排序，不做自动 fair-share |
| 未来到货做"未来预留" | SAP backward scheduling + planned receipts（PO/生产订单/ASN 作 ATP 来源） | ⏸️ 生产侧已有"预计齐套日"，销售侧透出留后续 |
| FEFO/批次召回 | 需批次管理主数据 | ⏸️ SOP §八已标"需老板拍板"，无批次数据 |
| 安全库存从可承诺量扣 | SAP OVZ9「with safety stock」制造业默认扣 | ✅ **采纳（对齐生产侧）** |

> **结论**：采纳安全库存扣除（缺口 C）+ 交期驱动的预留生命周期（缺口 A）+ 手动稀缺让单（缺口 B）；**不做** 7 天倒计时、自动抢占、VIP 优先、批次召回、MTO 专属库存（架构级，后续）。

## 三、三个缺口的落地设计

### 缺口 C：安全库存进销售 ATP（对齐生产侧，最小且修 bug 性质）

**现状 bug**：销售 `globalAvailableBase = 账面 − 生效预留`，**不扣安全库存**；生产侧 `MrpService` 已是 `账面 − 销售预留 − 货品安全库存，最小 0`（doc04 §5.3）。两侧口径不一致——销售能把库存预留到 0、吃掉缓冲。

**落地**：在 `StockReservationRepository.globalAvailableBase` 查询里扣 `goods.min_qty`（`GREATEST(COALESCE(CAST(min_qty AS NUMERIC),0),0)` 防脏数据负值），整体 `GREATEST(...,0)` 防负数预留。

```
销售可预留量 = GREATEST( 全仓账面 − 生效预留 − 货品安全库存 , 0 )
```

**数据安全要点**：
- `globalAvailableBase` **仅** `SalesOrderService` 审核与改量增量两处调用（已确认无其他消费者）；生产侧读 `v_stock_available` 自行另扣 → **不双重扣减**。
- 调用点已有 `.max(BigDecimal.ZERO)` 钳位，扣安全库存后不会负数预留。
- 安全库存 `min_qty` 仅货品级（无颜色维度），对每个颜色分别应用是**保守口径**（与生产侧 `MrpService:46-47` 完全一致）。
- **不动存量**：只改查询，不建列、不改既有预留行。

**dev 库实测**：货品 V51022 账面 92850 < 安全库存 200000 → 可预留量 = 0（正确保护缓冲，且与生产侧一致）。

### 缺口 A：预留生命周期（交期驱动，notify-only）

**设计**：`stock_reservations` 加 `hold_until TIMESTAMPTZ`（可空）。**null = 用默认（订单交货日 + 宽限期）动态算**——不做回填、交期改后自动跟随、不会过期（对齐 SAP 按需求日期 BDTER）。非 null = 大客户长单等自定义覆盖。

**持有截止** = `COALESCE(r.hold_until, 订单交货日 + HOLD_GRACE_DAYS)`，`HOLD_GRACE_DAYS = 7`（`StockReservationService` 常量，详情逾期计算与调度器共用，口径一致）。

**过期扫描** `ReservationHoldScheduler`（每日 08:37，镜像 `DeliveryDueWarningScheduler`）：
- 扫"有生效预留 + 持有截止已过 + 订单未结案/未中止/未发完"的订单，通知归属销售（TYPE_URGENT，同订单同人同日去重）。
- 与交货前 3 天的延期预警**互补不重叠**：那个管"快到期"，本扫描管"已过交货+宽限期仍占着货"。
- **默认只通知、不自动释放**（数据安全铁律）：自动释放须同步回写 `sales_order_items.reserved_qty/chain_status` 才不库存漂移，该编排留后续 opt-in。真释放走既有 取消/改量/手动让单。

> 这是**超越 SAP 的差异化点**：三大 ERP 都没有过期提醒，我们补上了。

### 缺口 B：稀缺仲裁（priority + 手动让单，不自动抢占）

**设计**：`sales_order_items` 加 `priority SMALLINT NOT NULL DEFAULT 3`（1 急单 / 2 普通 / 3 现货）。source of truth 在订单行。设急单需 `sales_order:priority` 权限 + 原因 + 审计。

**手动让单** `yieldReservation`（`sales_order:reallocate` 权限）：主管释放某低优先级订单行的部分/全部现货预留 → 库存回池 → 该行 `chain_status` 回退待排产（缺口自动回调度转生产）→ 通知其归属销售。**不自动给急单预留**——急单销售随后经改量/新建审核走正常预留链占用释放出的库存。

**数据安全**：`releaseForOrderItem`（FIFO + 行锁 + advisory lock，既有原语）+ chain_status 回退 SQL **逐字镜像出货驳回 `SalesShipmentService.reject`**（已生产验证范式）+ `WHERE reserved_qty >= :q` + `updated != 1` 抛错 → 防吞并错账、防负数。yield 只动现货预留，不碰 `plan_order_item_links`（让出现货、保留其生产承诺）。

**稀缺面板** `scarceReservations(goodsId, colorId)`：返回该货品+颜色的全部生效预留 + 订单上下文 + 持有逾期天数，按优先级升序、创建时间升序排列（急单在前、先占的在前），供主管判断让谁、让多少。

## 四、V178 数据模型（全加法，零存量变更）

```sql
-- A 生命周期
ALTER TABLE stock_reservations ADD COLUMN hold_until TIMESTAMPTZ;       -- null=动态默认，无回填
CREATE INDEX idx_sr_hold_until ON stock_reservations(hold_until) WHERE is_deleted=FALSE AND status=0;

-- B 稀缺仲裁
ALTER TABLE sales_order_items ADD COLUMN priority SMALLINT NOT NULL DEFAULT 3;  -- PG11+ 元数据级填充
CREATE INDEX idx_soi_priority ON sales_order_items(priority) WHERE is_deleted=FALSE AND priority<3;

-- 权限（不自动授予，超管恒有，管理员分配给主管）
INSERT permissions: sales_order:priority (214), sales_order:reallocate (215)
```

**dev 库验证**（迁移前后对比，全部一致）：
- `stock_reservations` 17 行 / Σqty=587 / Σconsumed=162 / Σreleased=425 → **不变**
- `stock_balances` 8642 行 / Σqty=−956459386.9506 → **不变**
- `sales_order_items` 82629 行 / Σreserved=0 / Σplanned=1092 / Σproduced=0 / Σqty=77229415 → **不变**
- `hold_until` 17 行全 null；`priority` 82629 行全=3；权限点+索引就位。

## 五、对称维护矩阵（新增行，补 V90 §三矩阵）

| 业务动作 | stock_reservations | sales_order_items | 说明 |
|---|---|---|---|
| 设优先级 `setLinePriority` | — | priority 改 + 审计 | 急单须原因；纯元数据，不影响分配 |
| 稀缺让单 `yieldReservation` | `releaseForOrderItem` FIFO 释放（行锁+advisory lock） | reserved_qty −=yieldRow、chain_status 回退（镜像驳回 SQL） | `updated!=1` 抛错防错账；通知归属销售；不碰 plan_links |
| 持有逾期扫描（每日） | **只读**（status=0 生效行） | **只读** | notify-only，零变异；通知归属销售 |

> 取消/改量/驳回/红冲/出货消耗：**沿用 V90 既有矩阵不变**。新字段与它们零冲突——
> 取消把预留置 `status=DONE` → 调度器 `status=0` 过滤排除；改量减量 `releaseForOrderItem` 同；驳回同；hold_until 在这些路径都不参与判定。priority 仅在让单/排序时读。

## 六、明确不做项（与原因）

| 不做 | 原因 |
|---|---|
| 自动释放过期预留 | 须同步回写 reserved_qty/chain_status 才不漂移；新变异路径=新风险。notify-only + 既有取消/改量/让单已闭环 |
| 自动抢占软预留 | 制造业会造成客户关系+排产混乱；doc04 §11 自己的哲学就是"急单插单需权限+影响清单+不抢已领料"。手动让单一致 |
| 7 天倒计时+续期 | 电商购物车思维；制造业按交期不按创建倒计时（SAP 亦按需求日期） |
| VIP/促销/优先券/fair-share 自动 | B2C 概念；制造业靠人工 priority + 让单 |
| MTO 销售订单专属库存（special stock 'E'） | 架构级：MTO 不预留成品、生产直接产进订单专属段。需 `manufacturing_strategy` 字段 + 物理库存按订单隔离，后续 ADR |
| FEFO/批次召回 | 需批次主数据；SOP §八已标待老板拍板 |
| 未来预留（backward scheduling 透出） | 生产侧已有"预计齐套日"；销售侧透出"可承诺交期"留后续 |

**实现要点 / 避坑**：
- `scarceReservations(goodsId, colorId)` 的 colorId=null 语义 = **所有颜色**（`(:cid IS NULL OR r.color_id IS NOT DISTINCT FROM CAST(:cid AS uuid))`），否则只匹无色预留会漏有色；稀缺面板默认按货品查全部颜色。
- 架构边：`ReservationHoldScheduler` 在 notice 包，**故意不 import stock 特性**（避免 `notice→stock` 跨特性边违反 ADR-017）；宽限期本地常量 `HOLD_GRACE_DAYS=7`，须与 `StockReservationService.HOLD_GRACE_DAYS` 同值（销售侧逾期计算用后者）。
- 后端 `SalesOrderService` 构造器加了 `AuditService` 形参（@RequiredArgsConstructor），既有测试 `ExecutionSegmentSalesAllocationPostgresTest` 的直接 `new` 已补一个 `null` 形参。
