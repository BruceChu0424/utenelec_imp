# ADR-005 - 老系统融合：单向影子双写

- **状态**：已被 [ADR-017](ADR-017-模块化单体与异步旁路.md) 取代（保留为历史背景）
- **日期**：2026-07-21
- **影响**：后端架构、数据架构、部署

---

## 上下文

企业已有老系统，仍在运行，有数据库、有用户、有数据。新系统（Uten IMP）要：
1. 不能影响老系统运行
2. 老系统的数据要能"拿过来"用
3. 新系统是新数据库、新结构、新功能
4. 新系统的写入操作如果对应老系统已有功能，要同时写老库
5. 最后老系统不用了，新系统独立运行

候选方案：

1. **单向影子双写（Shadow Write）**：新库为主，新→老影子写
2. **双向同步**：新老库互相同步
3. **新系统读老库**：新系统直接查老库
4. **一次性迁移后停老系统**：大爆炸式切换

## 历史决策

当时采用方案 1：单向影子双写。

> 2026-07-30 修订：实际工程已经落地幂等老库→新库迁移，但尚未落地 Outbox
> 新→老影子写。现行策略改为“按模块迁移、统一切换写入口、老模块只读”，只有老系统
> 仍需展示新数据时才启用 Outbox 兼容写。详见
> [ADR-017](ADR-017-模块化单体与异步旁路.md)。

> 新库是新数据的唯一真相源；新系统写新库的同时往老库"影子写一份"作为过渡期的双重保险；不读老库、不改老库结构；老系统退役时移除双写代码即可。

详见 原 06-老系统融合/00-融合总策略（已删除，现行口径见 ADR-017 与 数据迁移/）。

## 理由

### 为什么不双向同步？

- **复杂度爆炸**：双向同步要处理冲突、循环、回环
- **数据一致性难保证**：两库同时改同一条数据怎么合并？
- **改老库风险高**：双向意味着新系统会写老库，可能破坏老系统

### 为什么新系统不读老库？

- **耦合**：新系统业务逻辑会被老库结构绑架
- **老库结构烂**：新系统设计新结构就是为了摆脱历史包袱
- **性能**：老库可能慢、连接数有限
- **迁移后麻烦**：将来老库停了，新系统所有读老库的代码都要改

### 为什么不大爆炸切换？

- **风险极高**：制造业 200-1000 人，老系统突然停摆 = 停产
- **回滚困难**：发现问题想退回老系统时数据已经乱了
- **用户适应期**：员工需要时间学习新系统

### 单向影子双写的优势

| 优势 | 说明 |
|---|---|
| 新系统独立 | 新库全新设计，不被老库绑架 |
| 老系统安全 | 不改老库结构，老系统该怎么跑还怎么跑 |
| 双重保险 | 新库出问题，老库还有数据 |
| 可渐进退役 | 老系统访问量低 → 关双写 → 删代码 |
| 失败不阻塞 | 双写失败不影响新系统主流程 |

## 五大铁律

1. **新系统是新数据的唯一真相源**
2. **绝不破坏老系统**（不改表结构、不停机）
3. **双写是"尽力而为"的影子操作**（失败不阻塞主流程）
4. **双写必须可关闭**（每个点有 feature flag）
5. **前端零感知**（前端不知道老系统存在）

## 实现方向

详细方案待后端启动时定（见 原 06-老系统融合/02-双写与同步方案（已删除，现行口径见 ADR-017 与 数据迁移/）），倾向：

- **Outbox 模式 + 异步 Worker**：新库事务内写 outbox 表，独立 Worker 轮询转写老库
- **字段映射集中在 `legacy_adapters/`**：退役时整体下线
- **失败重试 + 告警**：不丢数据但不阻塞

## 后果

### 正面
- 新系统可以按最优结构设计，不被历史绑架
- 老系统持续运行，业务不中断
- 退役路径清晰（关开关 → 删代码）
- 前端零感知，前端方案完全不推翻

### 负面
- 后端复杂度增加（双写 + 字段映射 + 重试机制）
- 过渡期新老库数据有秒级延迟（异步双写）
- 需要监控双写健康（积压、失败率）
- adapter 代码量随双写点增加

## 缓解措施

- 双写代码集中在 `legacy_adapters/`，下线时一把删除
- outbox 模式保证新库写成功 ↔ 双写事件必产生
- 监控 outbox 积压、失败率、死信表
- 每个双写点独立 feature flag，可单点关闭

## 退役时机判断

- 老系统访问量 < 总流量的 5% → 进入收缩期
- 老系统某模块访问量 = 0 → 关闭该模块双写开关
- 老系统整体访问量 = 0 → 全部双写关闭，老系统下线
