# ADR-011 工作台按业务部门分区 + 权限配置动态化

- **状态**：已实施
- **日期**：2026-07-24
- **关联**：ADR-007（三层权限模型，本文档演进其"部门角色"层）、V27 迁移

## 背景

ADR-007 的权限模型把"部门能干什么"通过 `department_roles` 预置角色写死，新增/调整权限需要改代码发版；工作台分区按功能域（人事/财务/生产…）硬编码，与公司实际 9 个业务部门不对应；分区折叠状态只存在组件 State，换设备即丢失。

## 决策

### 1. 工作台按业务部门分区

分区与公司组织架构一级部门一一对应（部门树 V07 已有全部 9 个一级部门节点）：

| 分区 key | 标题 | 内容 |
|---|---|---|
| common | 常用功能 | 工资条 / 我的报销 / 我的访客 / 基础资料 / 意见箱 |
| hr | 行政与人力资源部 | 原人事组 6 项（员工档案/部门管理/入职向导/通知发布/访客审批/信息变更审核） |
| fin | 财税部 | 采购管理 / 客户资料 / 供应商资料 / 账户资料（新占位）+ 报销审批 / 工资条生成 / 工资条审核 / 财务报表 |
| prod | 生产部 | 流水线看板 / 产量录入 / 产量统计 / 空调控制 |
| eng | 工程研发部 | 物料反查产成品（BOM 反查，工程研发部 + 生产部共用） |
| pmc | PMC运营部 | 库存查询 / 出入库记录 |
| qa | 品质管理部 | 检测记录 |
| sales / newmedia / rail | 综合营销部 / 新媒体事业部 / 轨道事业部 | （待接入） |
| security | 安保部 | 访客核验（门岗扫码，对应部门树 DEPT_SECURITY） |
| system | 系统管理 | 权限管理 + 经营 Dashboard / 多维分析 / 异常告警（原决策支持并入） |

可见性仍复用 `requiredAnyPermFor`（路由守卫同一数据源）；普通用户只见有可见卡片的分区，超管见全部分区（空分区显示占位文案，便于预先排布）。

### 2. 分区折叠 + 排序按用户持久化到后端

- 新表 `user_preferences(user_id, pref_key, pref_value JSONB)`（V27），通用 KV，本场景 key = `workbench.layout`，value = `{order:[...], collapsed:[...]}`。
- API：`GET /api/user/preferences`（全量）、`PUT /api/user/preferences/{key}`（upsert，value ≤16KB）。
- 前端 `workbenchLayoutProvider`：冷启动读 shared_preferences 缓存防闪烁 → 会话就绪拉服务端合并（丢弃已删分区、按默认顺序补新增分区）→ 乐观更新 + 防抖 800ms 回写。**换设备登录自动恢复布局**。
- `UtenCollapsibleSection` 增加受控模式（`expanded` / `onExpandedChanged`），默认非受控用法（权限矩阵）不受影响。

### 3. 权限配置动态化（替代"部门角色写死"）

- 新表 `department_permissions(department_id, permission_id)`（V27，**无种子，全部部门初始空白**）。
- `PermissionResolver` 有效权限 = 直接角色 ∪ 直属部门角色（存量兼容）∪ **直属部门直配权限点** → ± 个人覆盖；超管全量。合成逻辑单一事实来源（`breakdownOf`），TokenIssuer 与 admin 接口共用。
- 权限目录动态化：`GET /api/admin/permission-catalog` 按 `category` 分组下发全量权限点（permissions 表新增 `sort_order`），前端不硬编码清单。**以后新增功能只需在迁移里登记新权限点，权限管理页自动出现，超管即可分配给任意部门/个人。**
- 权限管理页重构：
  - 「按部门」：单选部门 → 目录勾选 → `PUT /admin/departments/{id}/permissions` 整体替换（事务）。
  - 「按员工」：权限明细两态显示「已授权 / 未授权」（数据源 `GET /admin/users/{id}/effective-permissions`，前端不再平行合成），来源小字标注（部门/角色/个人加授/已收回），Switch 拨动即生成个人 grant/revoke 覆盖。**UI 不再出现"继承"。**
- 角色体系保留（存量数据兼容 + 账号段角色分配仍可用），但新授权主路径是"部门直配权限点"。

### 4. 数据级范围（data scope）用分级权限点表达

不做独立的 scope 框架，用权限点命名约定 `资源:动作:范围`，例如客户资料三级：

- `customer:view:self`（底层销售，只看自己的客户）
- `customer:view:department`（主管，看本部门）
- `customer:view:all`（管理层，看全部）

路由守卫/工作台显隐支持"任一满足"（`requiredAnyPermFor` 返回 List）；业务查询按持有的最高范围过滤（客户模块实现时落地）。该约定对未来任何资源可复用。

### 5. 权限目录只列已实现功能

V27 初稿曾种子化采购/客户/供应商/账户/基础资料等 10 个权限点，但这些模块尚未实现，已按"权限目录只列已实现功能"的原则从迁移中撤下；库中老系统迁移脚本导入的未实现模块权限点（finance/sales/manufacturing/master/subcontract/inventory 扩展共 27 个）同样清理，备份在 `server/legacy_migration/backup_unimplemented_perms_20260724.sql`（含部门授权，可整体回滚）。工作台的 4 个财税部占位卡片保留，仅超管可见作预览；模块落地时随对应迁移登记权限点（含数据范围三级 `资源:动作:范围`）即可被分配。

## 后续演进（2026-07-24 同日，V29）：角色体系下线

角色（hr/finance/lab…）是旧模型的中间层，与"部门配置 + 个人调整"两层模型重复且难以理解，决策下线：

- **权限只留两层**：部门配置（集体）+ 个人覆盖（例外）。另有隐性**全员基础权限**（employee 角色包：看本人工资条/提报销/读通知/提建议/被访人确认等，人人有份，可用个人收回调整）。
- **PermissionResolver 新合成**：`有效 = 全员基础 ∪ 部门配置（所在部门 + 所有上级部门，递归 CTE 向上取并集） ∪ 个人加授 − 个人收回`；超管全量。user_roles / department_roles 不再参与合成（数据保留：JWT roles claim 与 DataAccessPolicy 脱敏仍读）。
- **部门配置向上生效**：在「综合营销部」配的权限，销售一~四组员工自动获得；子部门可单独追加。取代了 ADR-007 的"仅直属不继承"（那是部门角色时代的保守决策）。
- **V29 迁移保底**：把每个普通用户当时通过非 employee 角色获得的权限按直属部门沉淀为 department_permissions，实测老用户有效权限零丢失（并新增应有的全员基础权限）。
- **管理页**：员工详情不再显示"角色分配"，账号段只读展示所属部门（部门归属由「员工档案」维护）；来源标签为 基础/部门/个人加授/已收回。

## 安全与逻辑加固（2026-07-24 同日，V30）

全链路复查后修复三处：

1. **超管权限页显示 bug**：员工权限页前端本地计算有效状态，未识别"超管=全量"特例，导致超管大部分权限显示"未授权"。修复：`effective-permissions` 接口下发 `superAdmin` 标记，前端对超管全部显示"已授权"、开关禁用、隐藏"保存覆盖"，并提示"超管默认拥有全部权限"。
2. **敏感字段脱敏改按权限点**（安全）：`DataAccessPolicy` 旧实现按角色名（hr/finance/admin）判断身份证/银行卡/薪资明文可见性。角色下线后残留角色会造成"权限已收回但仍能看明文"（fail-open）。改为按权限点：PII（证件/手机/银行）= `employee:pii:view`（V30 新增并预配给行政与人力资源部）；薪资 = `employee:compensation:view`。判定入参从 JWT roles claim 改为 permissions claim。实测：超管看明文 ✓、无 PII 权限者看掩码（****2148 / 136****5900）✓。
3. **前端路由守卫后门**（安全）：`AppUser.can()` 原来对持 admin 角色的用户短路放行全部页面，与后端 @PreAuthorize 语义不一致。角色下线后改为只认 `superAdmin || permissions.contains(perm)`。

生效时效：权限配置写库即时（department_permissions / user_permission_overrides 直写，已实测）。**即时生效（同日加固）**：保存部门配置时吊销该部门子树（含下级部门）所有用户的 refresh token，保存个人覆盖时吊销该用户的 refresh token——access token 到期（≤15 分钟）后强制重新登录，新权限随新令牌下发，杜绝"权限已收回但旧令牌还在用"的窗口。已实测：保存后相关用户 refresh 立即 401。管理端读取均为实时查库。

**角色授权接口清理（同日）**：`/admin/users/{id}/roles`、`/admin/roles`、`/admin/department-roles`、`/admin/departments/{id}/roles` 四个端点及对应服务方法/DTO/前端 repository/provider/model 全部移除（角色已不再影响权限，留着只会误导）。`user_roles` 数据保留：入职仍默认登记 `employee` 角色供 JWT roles claim 兼容；`AdminGrantGuard` 保留（入职流程沿用）。

## 验证记录（2026-07-24）

- V27/V28 在开发库（docker uten-imp-postgres）实测执行成功；`permissions.category` 全量中文化。
- API 全链路实测通过：权限目录（14 个中文分组）/ 部门权限保存+回显（PMC运营部）/ 员工有效权限分解（基础∪部门∪个人加授−收回，收回即时从 effective 移除）/ 个人覆盖写读 / 用户偏好写读。
- V29 角色下线迁移实测：老用户有效权限零丢失（角色权限完整沉淀为部门配置），并自动获得全员基础权限；部门配置向上继承实测生效（财税部员工继承总经办配置）。
- 手工 javac 运行需加 `-parameters`（已补进 compile-check.sh），否则 @PathVariable 解析 500。

## 生效时机

权限变更保存即写库，并吊销相关用户 refresh token 强制重新登录（最晚 15 分钟 access token 到期后生效，见上文"即时生效"）。工作台布局保存即生效（本设备即时，他设备下次拉取）。

## 已知限制

- 角色授权接口（`/admin/users/{id}/roles`、`/admin/roles`、`/admin/department-roles`、`/admin/departments/{id}/roles`）已于 2026-07-24 移除；`user_roles`/`department_roles` 数据保留仅作 JWT roles claim 兼容。
- 空分区（sales/newmedia/rail）仅超管可见，接入功能后对普通用户自然出现。
- V28 将权限目录分组名（`permissions.category`）统一中文化为扁平模块名（员工档案/工资条/报销…）；权限点 `code` 为技术标识保持英文不变，管理页以 code 小字辅助显示。
- 前端 `Perm` 常量中保留了占位模块（采购/客户/供应商/账户/基础资料）的 code 与路由映射，仅超管兜底可见占位卡片；对应权限点待模块落地时再登记。

## 后续计划：客户资料模块（首个三级数据范围实战，待实施）

作为 `资源:动作:范围` 数据范围约定的第一个落地业务模块，实施步骤：

1. **迁移登记权限点**：`customer:view:self` / `customer:view:department` / `customer:view:all`（看自己/看本部门/看全部）+ `customer:edit`，category=客户资料；超管在权限管理页分配给综合营销部（部门级给 `department`，管理层个人加授 `all`，基层销售默认 `self`）。
2. **数据模型**：`customers` 表（名称/联系人/电话/来源/负责人 `owner_employee_id`/所属部门快照/审计列），负责人=底层销售归属依据。
3. **后端查询过滤**：按持有的最高范围过滤——`all` 不过滤；`department` 按负责人所在部门子树（复用递归 CTE）；`self` 只查 `owner_employee_id = 当前员工`。取最高范围的判断顺序：all > department > self。
4. **前端**：客户列表/详情页启用现有占位路由 `/finance/customers`（`requiredAnyPermFor` 已支持三级任一满足），工作台财税部卡片对获权用户自然出现。
5. **验收**：底层销售只见自己的客户；主管见本部门子树；授 `all` 者见全部——同一接口三种结果。
6. 同模式后续可复制到 供应商资料 / 采购管理 / 账户资料。

## 后续演进（2026-07-28）：工程研发部分区接入首个功能（物料反查产成品）

`eng` 工程研发部分区自 ADR-011 落地起一直为空（仅超管可见占位）。本次接入**首个**功能卡片——「物料反查产成品」（BOM where-used）：

- **功能**：输入一个原材料（如 A 螺丝），查出它被用在了哪些产成品上（数据源 `production_plan_costs` 136 万行 BOM 展开快照，按顶层产成品 `master_goods_id` 汇总）。详见 [物料反查产成品页](../03-页面/物料反查产成品页.md)。
- **入口双挂**：工作台「工程研发部」分区卡片 + 生产部 hub「生产报表」卡片（生产部用户亦常需反查），同一页面 `/production/where-used`。
- **权限**：`production_where_used:view`（V78 seed，默认授权全员——该反查能力对各业务部门通用）。卡片显隐复用 `requiredAnyPermFor`，工程研发部分区由此对普通用户自然出现（不再仅超管可见）。
- **语义边界**：仅含历史上被排产展开过的自制产成品（未投产新品 / 委外路径不覆盖），页面顶部有"只读历史数据"告示。
