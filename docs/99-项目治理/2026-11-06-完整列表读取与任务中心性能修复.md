## 根因与实际证据

历史追到 `d08f64c4f`（2026-07-25）：入口先读分类、货品每次20条。9月公共主档和10月窗口读取仍只先读当前页。`5880bfe54` 把公共读取改成每100条读完整个结果后才发布；后来的版本摘要增加四并发，但仍每批调用原列表服务。旧版首屏快不能当成旧版完整读取快。

只读核对公司网页为 `v2.5.50`、源码 `9895766cebd9b0a58cb28c5c968d95db1ec1b634`，其主档读取链与本次起点 `0bac0981cb938f1678eb775f5cc8a971d22e79d1` 相同。公司库未软删货品38,942、客户529、供应商399、模具1,626；货品按100条约需390个内部批。主表、禁用及占位分组仍各自保持原筛选和真实总数，不能把这些数量混算。

另有来源过滤的索引退化。原 native SQL 对整行执行 `to_jsonb` 再判断 `legacy_id`，导致现成索引不可用于预筛选。只读 `EXPLAIN (ANALYZE,BUFFERS)` 对照如下，保留完整来源图权威函数：

| 57,716张库存单的 native 计数 | 374.051ms，顺序扫描 | 53.344ms，`idx_sd_legacy` | 334条；原/新预条件全表差异0 |
| 10,844张销售订单的 native 计数 | 119.435ms，顺序扫描 | 9.982ms，现有 legacy 索引 | 11条 |

前端还复现保留路由在动画中被 `TickerMode(false)` 隐藏、动画登记未退休的问题：返回刷新会等到一秒兜底。修复监听实际可见性，保留原兜底和读归属边界。

## 公共实现与迁移范围

`MasterSummaryReadSupport` 在一个完整请求内维护原只读快照和最终新快照核对。`BoundedMasterReadSource` 从导出游标抽出共用，一次计数、一次稳定排序、数据库100条 fetch，DTO消费后清理实体；导出原权限、行数和截止时间策略继续由导出 owner 负责。未增加业务缓存、修改来源函数或放宽单页/业务写入上限。

客户端 `postSummaryStream` 在同一读归属内消费整个响应，顺序帧交给原 `readVersionedSummarySnapshot` / `loadCompletePagedResult`；完整尾帧、总数、权限/数据版本和 EOF 全部核对后才发布。旧服务端、断流、取消、重复身份或版本漂移明确失败，不静默回到逐页读取。完整响应结束才记录耗时，响应头时间不能冒充完整耗时。

完整流沿用现有压缩链，Tomcat主连接、远程连接和 Nginx 的既有 gzip MIME 增加 `application/x-ndjson`；不因传输格式变化把大列表改成未压缩传输。

| 基础资料 | 当前入口 |
|---|---|
| 货品、模具、客户、供应商 | 公共主档完整流；主表和原独立分组保持原筛选 |
| 颜色、单位、币种、资金账户、结算方式 | 同一完整流 owner；保留原过滤、排序、敏感词 body、金额/单位及掩码 |

| 收付款类别 | 原单 HTTP `/master/payment-styles/tree`，保留层级与分类 |

业务参考货品/客户/供应商仍使用各自更窄的投影和原业务权限。货品/客户/供应商/模具的公共选择器随 gateway 接入，BOM浏览顺序及停用组件移除选择也接入同一完整查询。仓库、收付款类别和原字典服务内部的既有整实体读取未在本轮改写，不能把它们记成已迁移有界数据库游标。

任务中心来源 SQL 统一到 `ImportedBusinessDocumentScope.nativeTable` / `nativePredicate`；已映射实体的 CURRENT 查询也先用真实 legacy 字段预筛选。来源图检查、已选关系的 MATERIALIZED 边界、生命周期、权限、精度、数量及来源均保留。没有增加持久化来源缓存或新业务表。

已实现的 WPF 货品、单位同步一次完整 HTTP，复用原认证/TLS/HTTP 和完整列表验证，保留原始数值文本与内存失败保护。其余9类 WPF 主档仍未迁移，候选/Win7真机状态见唯一台账，不因本次主链合并改变。
