## 一、设计决策总览（含理由）

| # | 决策点 | 选型 | 理由 |
|---|---|---|---|
| 1 | **应收应付模型** | **统一 `ar_ap_ledger` 取代 M_in/M_out 两张分立表**（direction 区分 AR/AP） | 老库两张表字段对称（BillNo/Total/M_In或M_Out/M_Rare/Paid/BStyle/BillID），合并后规则一份、报表一份、核销一份；前端按 direction 分"应收单/应付单"零割裂 |
| 2 | **来源标识** | `source_doc_type` 枚举（SALES_SHIPMENT/SALES_RETURN/PURCHASE_RECEIPT/PURCHASE_RETURN/SUBCONTRACT_RECEIPT/SUBCONTRACT_RETURN/DIRECT_RECEIPT/DIRECT_PAYMENT）取代老库 BStyle int 字典 | BStyle→TableName 映射靠 `SystemSource` 表（未 dump 全）+ 触发器硬编码；新库枚举自描述、跨模块可读，迁移时按 BillNo 前缀 XC/XT/CJ/CT/EJ/XS/CF 精确映射 |
| 3 | **立帐时机** | **跨模块 Service 调用**（销售/采购/委外审核事务内显式调 `FinanceService.postArAp(...)`），**不走触发器** | 老库立帐埋在 S_Out/P_In/E_In 触发器（11 个），换库即丢、不可测、不可审计；新库上移 Service 层显式调用，事务原子保证，跨模块解耦但语义零割裂 |
| 4 | **账户类型** | **重建 `account_type` 枚举**（BANK/CASH/CHECK/FOREIGN_CHECK/THIRD_PARTY/OFFSHORE/GENERAL） | 老库 `M_Acc.AStyle` 27 行全为 1（退化死字段），账户类型实际靠 `AccName` 字符串区分；新库枚举化，按 AccName 关键字映射（农行/工行→BANK、现金→CASH、支票→CHECK、微信/支付宝→THIRD_PARTY、香港→OFFSHORE） |
| 5 | **支票管理** | **不单独建模块**：支票 = `accounts.account_type IN (CHECK, FOREIGN_CHECK)` 的账户 + 其收付款流水子集；可选 `finance_check_register` 扩展表迁 M_Check 空结构 | 老库无独立支票单据，支票是 M_Acc 里的支票账户 + M_Check 登记簿（0 行）+ 触发器维护。详见 [25] §九结论 |
| 6 | **收付款类别字典** | **`payment_styles` 邻接表 + 物化路径**（仿 material_categories V31，**非**闭包表 —— 与现有主档一致），按 `category` 分根（ACCOUNT/EXPENSE/INCOME/METHOD） | 老库 M_Style 124 节点混合树（StyleClassid 1=账户类叶节点/2=应付科目/3=资本/4=费用项目/5=收入项目），现有 V31 范式是邻接表+path+触发器维护，沿用保持一致 |
| 7 | **账户余额** | **保留 `balance_current` 列**（Service 层维护，由 `init_balance + sum(receipts) − sum(payments)` 推导但冗余存储） | 老库 GetTotal/PaidTotal/FactTotal 由触发器维护，账户列表毫秒级显示需要；新库保留冗余字段但 Service 层显式累加，触发器废弃 |
| 8 | **结清标志** | **`is_settled` 冗余存储 + Service 维护**（仅 `amount_balance = 0` 时置位），非纯派生 | 老库 `Paid` bit 由 `TRI_GatheringCheck` 自动维护（M_Rare=0 置位）；V129 `ar_ap_ledger_settled_consistency_chk` 强制 `is_settled ⇔ balance=0`。负余额是仍可使用的预收/预付，不是“已结清” |
| 9 | **状态机** | `0草稿/1已审/-1红冲` + `is_closed` 派生（同采购 V44） | 沿用采购已验证范式，贴老库"保存即生效"语义 |
| 10 | **核销关系显式化** | `finance_receipt_lines.applied_ledger_id` / `finance_payment_lines.applied_ledger_id` 显式 FK 指向 `ar_ap_ledger.id` | 老库核销靠 M_in.M_In 数字累加 + BillID 推断，"哪笔收款核销哪笔应收"无法精确查询；新库显式关联，支撑报表 I/J/K/L 单客户/供应商对账单 |
| 11 | **银行存取款** | `finance_bank_transfers(+lines)` 保留老库 0 行结构，并已实现跨账户/跨币种审核与红冲 | M_Bank/M_BankItem 老库没有历史行，但新单运行时按 `TRI_BankItem` 语义原子更新转出/转入账户和对账流水；不能再把它描述成 Service 骨架 |
| 12 | **历史迁移** | **全量十几年**（M_in 4.2 万 + M_out 4.5 万 + M_AllCheck 3 万 + 6 类单据），单表 + 强索引足够；远期可按 `bill_date` 在线转分区 | 钱流表行数远小于库存/生产（十几年累计 10 万级），单表 + B-tree 毫秒级，无需分区 |
| 13 | **23 报表** | **物化视图 `finance_ar_ap_mv`（月度上卷）+ 参数化查询**，按 4 大类（应收应付/收付款单据/费用收入/账户流水）落地 | 老库 23 报表 SQL 不在 DB 视图（应用层水晶报表），口径只能从底层表+业务重建（[25] §六存疑 10） |
| 14 | **金额/汇率精度** | 全 `NUMERIC(18,4)` / `NUMERIC(18,6)` | 老库 M_in.CRate 等 float 存金额有精度风险（[25] §八问题 9），新库一律 numeric |

> 与采购 [15] 的差异点：① 应收应付是**跨模块枢纽**（销售/采购/委外都要调），不是本模块闭环；② **统一台账合并两张老表**（M_in/M_out）；③ **账户主档需重建类型枚举**（AStyle 退化）；④ **23 报表无现成视图**，需基于底层表重建口径。

## 三、基础资料补迁（accounts + payment_styles · 归「基础资料」模块 · V50）

> **归属**：账户、收付款类别是全公司共用的基础资料，与货品/模具/客户/供应商/颜色/单位/币种/仓库**同级**，挂「基础资料」页面，有独立 CRUD（复用 `MasterDataTableView` 表格模式，见记忆 *basic-data-master-ui-pattern*）、独立迁移脚本、独立权限点。**不是钱流模块私有字典。**
>
> 编辑权限挂财税部 `DEPT_FIN`（账户/收付款类别归财务口维护），`view` 给全员（基础资料全员可查）。

### 3.1 `accounts`（账户主档 · 迁 M_Acc，27 条）

#### 字段映射

| 老库 M_Acc | 新库 accounts | 说明 |
|---|---|---|
| ID | `legacy_id` | 溯源 + 重跑幂等 |
| Number | `code` | 老号 `001`~`009` / 新号 `UT00101`（含币种前缀 UT=美元？） |
| AccName | `name` | 农业银行/现金/微信/支票/基本户… |
| AccNode | `bank_account_no` | 银行账号尾号（仅基本户填） |
| — | `account_type` | **新建枚举**，按 AccName 关键字映射（见下表） |
| InitTotal | `init_balance` | 期初金额（仅基本户 445,897 / 现金 3,433,599 有非零值） |
| GetTotal | `receipts_total` | 收入累计（迁移照搬，运行时 Service 累加） |
| PaidTotal | `payments_total` | 支出累计（迁移照搬，运行时 Service 累加） |
| FactTotal | `balance_current` | 实际余额 = init + receipts − payments（冗余，Service 维护） |

#### `account_type` 枚举（按 AccName 关键字重建）

| 枚举值 | 含义 | 数量 | AccName 关键字映射规则 |
|---|---|---:|---|
| `BANK` | 银行账户 | ~18 | 农行/工商/建设/交通/招商/邮政/信用社/工商牡丹/工行/招行/交行/兴业/中国/广发/建行/工行牡丹卡/基本户/一般帐户 |
| `CASH` | 现金 | 1 | 现金 |
| `CHECK` | 本公司支票 | 1 | 支票（ID 50 禁用） |
| `FOREIGN_CHECK` | 外来支票 | 1 | 支票（ID 56 使用）—— 区分本公司/外来靠 Status + 备注，迁移时人工标 |
| `THIRD_PARTY` | 第三方支付 | 2 | 微信 / 支付宝 |
| `OFFSHORE` | 境外账户 | 1 | 香港公司帐号 |
| `GENERAL` | 一般账户 | 1 | 一般帐户（与 BANK 区分：未指明银行） |

> 💡 关键：老库 AStyle 全为 1（"银行存款"）即使现金/微信也是 1，**类型识别实际靠 AccName 字符串**。新库迁移时写 CASE WHEN 映射函数，运行时录账户由用户在表单选枚举（前端下拉）。
>
> 实际活跃账户仅 4 个（基本户/现金/香港/工行，占 99% 流量），其余 23 行保留为占位（保历史 + 名字），`status='禁用'`。

#### DDL 蓝图（V50）

```sql
CREATE TABLE accounts (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    legacy_id       INT  UNIQUE,                       -- M_Acc.ID
    code            TEXT,                              -- Number
    name            TEXT NOT NULL,                     -- AccName
    bank_account_no TEXT,                              -- AccNode（银行账号）
    account_type    TEXT NOT NULL DEFAULT 'BANK',      -- BANK/CASH/CHECK/FOREIGN_CHECK/THIRD_PARTY/OFFSHORE/GENERAL
    currency_id     UUID REFERENCES currencies(id),    -- 币种（多币种账户：香港=USD，其它=RMB）
    init_balance    NUMERIC(18,4) DEFAULT 0,           -- InitTotal（期初）
    receipts_total  NUMERIC(18,4) DEFAULT 0,           -- GetTotal（收入累计，Service 维护）
    payments_total  NUMERIC(18,4) DEFAULT 0,           -- PaidTotal（支出累计，Service 维护）
    balance_current NUMERIC(18,4) DEFAULT 0,           -- FactTotal = init + receipts − payments（冗余，Service 维护）
    parent_legacy_id INT,                              -- M_Acc.ParentID（→SystemItem，保留 legacy 不 FK）
    style_legacy_id INT,                               -- M_Acc.StyleID（→M_Style.ID，账户类叶节点）
    status          TEXT NOT NULL DEFAULT '使用',      -- Status（使用/禁用）
    auto_created    BOOLEAN NOT NULL DEFAULT FALSE,    -- 单据迁移/运行时自动补录标记
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    created_by   UUID, updated_by UUID,
    is_deleted   BOOLEAN NOT NULL DEFAULT FALSE, deleted_at TIMESTAMPTZ
);
CREATE INDEX idx_accounts_legacy_id ON accounts(legacy_id);
CREATE INDEX idx_accounts_code      ON accounts(code);
CREATE INDEX idx_accounts_type      ON accounts(account_type);
CREATE INDEX idx_accounts_status    ON accounts(status);
```

### 3.2 `payment_styles`（收付款类别字典 · 迁 M_Style，124 节点 · 树形）

> 老库 M_Style 是**多用途混合树**（StyleClassid 分组：1=账户类叶节点/2=应付科目/3=资本/4=费用项目/5=收入项目）。新库按 `category` 字段分根，统一在一张邻接表 + 物化路径树里（与 material_categories V31 同构）。

#### 字段映射

| 老库 M_Style | 新库 payment_styles | 说明 |
|---|---|---|
| ID | `legacy_id` | — |
| StyleClassid | `category` | 映射：1→ACCOUNT / 2→LIABILITY / 3→EQUITY / 4→EXPENSE / 5→INCOME；新增 METHOD 根收 M_Get.RecStyle/M_Paid.PaidStyle（RecStyle 表独立字典，未 dump，存疑 §九） |
| StyleNumber | `code` | 101/102/041/031… |
| StyleName | `name` | 现金/银行存款/办公费用/销售收入… |
| Parentid | `parent_id` | 0=根 → NULL（邻接表） |
| NextNumber | `sort_hint` | 老库用作同级排序 + 编号生成；新库仅辅助 |

## 四、表设计（DDL 蓝图 · V57）

> **历史 DDL 提示**：本节 `DEFAULT 1` 仅是 V57 存储蓝图/老数据兼容，不是现行汇率业务默认。销售订单不保存汇率；`SHIPPED` 必须取得财务正开账汇率；销售收款每个 AR 核销行及直接收款/预收都必须显式提供正到账汇率，本币由服务端派生。

### 4.1 统一约定（沿用采购 V44）

- 主键 `id UUID DEFAULT gen_random_uuid()`，迁移溯源 `legacy_id INT UNIQUE`。
- 单据号 `bill_no TEXT UNIQUE NOT NULL`。
- 审计四件套 `created_at/updated_at/created_by/updated_by` + 软删 `is_deleted/deleted_at`。
- 金额统一 `NUMERIC(18,4)`，汇率 `NUMERIC(18,6)`。
- 金额双口径：`*_original`（原币）+ `*_local`（本币 = 原币×汇率）。
- 状态：`0草稿/1已审/-1红冲` + `is_closed` 派生。
- 人员 `*_id`（maker/approver/operator）：UUID，无 FK（employees 与老库 Sys_Operator/B_Worker 未对齐，迁移留空，新系统录入填当前登录用户）。
- 单据明细冗余 `bill_no` / `bill_date`（查询裁剪 + 报表免 JOIN 主表）。

#### `source_doc_type` 完整枚举（取代 BStyle）

| source_doc_type | direction | 老 BStyle | 来源单据 | 单号前缀 | amount_original 语义 |
|---|---|---:|---|---|---|
| `SALES_SHIPMENT` | AR | 3 | S_Out 销售出货审核 | XC | 出货总额（应向客户收） |
| `SALES_RETURN` | AR | 18 | S_Withdraw 销售退货 | XT | 退货金额（红冲 AR，负数或反向） |
| `DIRECT_RECEIPT` | AR | 20 | M_Get 直接收款（无应收单核销） | XS | 0（直接收款：original=0, settled=收款额, balance=负 = 客户预付） |
| `PURCHASE_RECEIPT` | AP | 1 | P_In 采购收货审核 | CJ | 收货总额（应向供应商付） |
| `PURCHASE_RETURN` | AP | 17 | P_Withdraw 采购退货 | CT | 退货金额（红冲 AP） |
| `SUBCONTRACT_RECEIPT` | AP | 30（规划） | E_In 委外进仓审核 | EJ | 委外进仓总额（老库 BStyle=30 规划但实际未启用，见 §九存疑） |
| `SUBCONTRACT_RETURN` | AP | — | E_WithDraw 委外退货 | ET | 红冲 AP（待委外模块确认） |
| `DIRECT_PAYMENT` | AP | 21 | M_Paid 直接付款（无应付单核销） | CF | 0（直接付款：original=0, settled=付款额, balance=负 = 供应商预付） |

> 💡 **DIRECT_RECEIPT/DIRECT_PAYMENT 的特殊性**（来自触发器 `TRI_M_get_B_M_in` 分支 B 实测）：M_Get 直接收款无 M_GetItem 核销明细时（老库实际全走此分支，M_GetItem 0 行），触发器 INSERT 一行 `M_in(Total=0, M_In=+收款额, M_Rare=−收款额)`。语义是"客户预付款 / 未对应应收的收款"，balance 为负表示客户已付多余应收。新库保留此语义，前端"客户预付款"报表查 `source_doc_type=DIRECT_RECEIPT AND amount_balance<0`。
> 负余额必须保持 `is_settled=false`：它代表仍可用于后续业务的预收/预付余额，不是余额恰好归零的
> 已结清单。V129 数据库约束与 Service 都使用这一口径。

## 五、跨模块应收应付联动（Service 层 · 去触发器）

> **历史 V57 接口警告**：本节 Java 片段是早期设计快照，签名和调用时点均不得复制。现行 `postArAp` 返回 `void`；销售出货只在仓库 `SHIPPED` 调用，销售退货用 `postArAp` 建负 AR，`reverseArAp(sourceId,type)` 仅撤销来源；收款核销由 `FinanceReceiptService` 自身事务完成。现行销售链以 §十四和 ADR-030 为准。

> 老库 11 个触发器（TRI_SOStockItem/PIStockItem/M_get_B_M_in/M_Paid_B_M_Out/GatheringCheck/PaymentCheck/M_in_STotalCheck/M_Out_STotalCheck/GetItem/PaidItem/BankItem）的语义全部上移到 Service 层，用 `@Transactional` 保证原子性。这是 [25] §五"设计金子"的落地。

### 5.1 立帐接口（销售/采购/委外审核时调用）

```java
/**
 * 销售/采购/委外单据审核时跨模块调用，在事务内建立应收/应付台账行。
 * 取代老库 TRI_SOStockItem / TRI_PIStockItem 触发器的立帐分支。
 *
 * @param request.direction       "AR" 或 "AP"
 * @param request.sourceDocType   SALES_SHIPMENT / PURCHASE_RECEIPT / SUBCONTRACT_RECEIPT 等
 * @param request.sourceDocId     来源单据 UUID（如 sales_shipments.id）
 * @param request.billNo          立帐单号（XC/CJ/EJ 前缀，由来源模块生成器产出）
 * @param request.billDate        立帐日期
 * @param request.dueDate         到期日（Last_Date）
 * @param request.partyId         客户/供应商 UUID（自动落 client_id 或 supplier_id）
 * @param request.amountOriginal  应收/应付原额（原币）
```

### 5.2 核销接口（收款/付款单审核时调用）

```java
/**
 * 销售收款审核（finance_receipts 0→1）时调用：
 *   1. 若 receipt.lines 非空（指定核销 AR）：
 *      - 每行 UPDATE ar_ap_ledger SET amount_settled += line.amount_local,
 *              amount_balance = amount_original_local - amount_settled
 *        WHERE id = line.applied_ledger_id
 *      - 自动结清：仅 amount_balance == 0 时 is_settled=true, settled_date=业务日期
 *   2. 若 receipt.lines 为空（直接收款，老库实际全走此分支 M_GetItem=0）：
 *      - 调 postArAp(direction=AR, sourceDocType=DIRECT_RECEIPT, amountOriginal=0,
 *              amountSettled=receipt.amount_local, amountBalance=-receipt.amount_local)
 *   3. accounts.balance_current += receipt.amount_local（账户余额累加）
 *   4. accounts.receipts_total += receipt.amount_local
 *   5. INSERT finance_reconciliations(source_doc_type=RECEIPT, in_amount=...)
 *   6. 若有 invoice_no（支票号）→ INSERT finance_check_register(source='收')
 *
 * 取代老库 TRI_M_get_B_M_in + TRI_GatheringCheck 触发器。
 */
SettlementResult settleReceipt(FinanceReceipt receipt);

/** 采购付款审核：与 settleReceipt 对称（AP/账户余额-/out_amount）。取代 TRI_M_Paid_B_M_Out + TRI_PaymentCheck。*/
SettlementResult settlePayment(FinancePayment payment);

/** 红冲收款/付款（status 1→-1）：全部反向冲销（删核销累加、删台账行、回滚账户、删流水）。*/

void reversePayment(UUID paymentId);
```

### 5.5 联动一致性校验（Service 层断言）

每次审核事务提交前断言（失败回滚）：
- 账户余额守恒：`account.balance_current == account.init_balance + account.receipts_total − account.payments_total`
- 台账余额等式：`ledger.amount_balance == ledger.amount_original_local − ledger.amount_settled`
- 核销额非超核：`ledger.amount_settled <= ledger.amount_original_local`（DIRECT_RECEIPT/PAYMENT 除外，允许负 balance 表示预收/预付）
- 结清等式：`ledger.is_settled == (ledger.amount_balance == 0)`；DIRECT 负余额保持未结清
- 账户余额守恒由 V142 `accounts_balance_consistency_chk` 再做数据库兜底；同源 AR/AP 和同源同账户
  对账流水分别由 V142 部分唯一索引防重复
- 现有开发数据扫描中，账户守恒异常、同源 AR/AP 重复和同源账户流水重复均为 0；这只证明当前
  快照，不替代迁移后全量对账、并发/回滚、权限和财务签字

### 6.1 物化视图 `finance_ar_ap_mv`（应收应付月度上卷）

```sql
CREATE MATERIALIZED VIEW finance_ar_ap_mv AS
```

### 财务口径校准（2026-07-27 复核——钱是财务命脉，算法必须对）

> 用户要求「仔细检查整个业务逻辑、算法都对」。复核后校准了 5 处金额口径：

1. **B 应收汇总 — 时序口径**：期初/发货/回款/退货/期末 改用「立帐(`ar_ap_ledger.amount_original_local`) − 收款(`finance_receipts.amount_local`)」按 `bill_date` 归期，**不用累计 `amount_settled`**（它无法按期切分，会让 期初/期末 与 回款 口径不一致）。恒等式 **期初+发货+退货−回款=期末** 实测成立（如 Azeem A：0+1023117.25+0−228175.08=794942.17=期末 ✓；退货为负自动冲减）。实现：CTE `posting`(GROUP BY client_id, CASE bill_date <from / between from,to) + `coll`(同款 finance_receipts)，方向 AR→`receivableSummary`。
2. **D 应付汇总 — 结构校正**：用户 D 列表仅 7 列（立帐单号/供应商/开单日期/币别/汇率/应付帐款/已付金额）= **按立帐单号一行一单**，非按供应商 16 列（那是 B）。故 `arApSummary` 按 direction 分流：AR→`receivableSummary`(按客户 16 列 CTE)，AP→`payableSummary`(按单 7 列，走通用 execute)。实测 total=44525（=M_out）。
3. **S 帐户流水 — 期初余额**：余额从「账户 `init_balance` + dateFrom 之前流水净额」起算累加（**不随日期筛选清零**），保证跨期余额连续。实测 dateFrom=2020 时首行余额=9,084,880.55（期初结转），非 0。
4. **E/V 本次余额**：`= 未收(client AR Σamount_balance) − 本次收款(amount_local)`（原误填为 amount_local）。实测 XS26070039：未收 8140379.57 − 收款 337047.75 = 本次余额 7803331.82 ✓。未收 = LEFT JOIN `(SELECT client_id, SUM(amount_balance) bal FROM ar_ap_ledger WHERE direction='AR' GROUP BY client_id)`。
5. **H 采购付款汇总 — AP 立帐关联**：LEFT JOIN `ar_ap_ledger(source_doc_type='DIRECT_PAYMENT', source_doc_id=付款单id)` 取 立帐单号/已付(amount_settled)/未付(amount_balance)/本次付款/本次余额/摘要（21 列）。直接付款 1:1 建一条 AP 立帐行（无行放大）；迁移 source_doc_id ~69% 命中，未命中则空。

**通用口径**：只计 `status=1`（草稿 0 / 红冲 −1 排除）；退货/退货立帐 status=1 且 amount 为负 → 自动冲减应收应付；多币种本币(`amount_*_local`)口径汇总正确，原币列按行展示（跨币种原币累加仅参考，同老系统）；`is_deleted=false` 全程过滤。

### 12.1 审批人资格（V229 / ADR-027）

V229 起不再单点指定负责人：已删除『审批负责人设置』页面、`workflow_assignment:manage` 权限码与 `workflow_responsibility_assignments` 表。订货审批与超量到货审批的审批人 = 财务部门（`DEPT_FIN` 及子树）内在职、账号启用且持有 `finance_order_approval:review` 的员工，或在权限管理里被个人加授（`user_permission_overrides effect='grant'`）该权限的人（不限部门）。判定由 `WorkflowReviewerEligibility` 实时查库，每次审批都重读；超管不可绕过（其权限来自 `is_super_admin` 标志而非 overrides）；取消权限即时生效。当前无任何合格审核人则提交/异常生成失败（fail-closed），配置在权限管理完成。

### 12.2 财务任务中心

- 订货待审：`GET /api/finance/procurement-approvals/tasks`、`GET /api/finance/procurement-approvals/count`，要求 `finance_order_approval:view`，V229 起列出全部 `PENDING` 待审（不再按 assignee 过滤）。通过/驳回仍走采购或委外订单 Controller，要求 `finance_order_approval:review`、合格审核人资格（`WorkflowReviewerEligibility` 实时查库）与 `expectedVersion`；驳回还要求原因。
- 超量到货：`GET /api/finance/procurement-arrival-exceptions/tasks`、`GET /api/finance/procurement-arrival-exceptions/count`、`GET /api/finance/procurement-arrival-exceptions/{id}` 要求 view，V229 起列出全部 `PENDING_FINANCE`；`POST /api/finance/procurement-arrival-exceptions/{id}/decision` 同时要求 view+review、合格审核人资格（实时查库）与 `expectedVersion`。
- `allowedActions` 是按钮事实源。超管不可绕过，审批资格按「财务部门资格 + `finance_order_approval:review`（含个人加授）」实时判定，订单 edit 不能替代。通知只是提醒，不是任务或权限事实源。
- 合格审核人即使没有 `purchase:view:all` / `subcontract:view:all`，也只可读取与自己当前 PENDING 财务任务精确匹配的订单详情；采购/委外列表仍按 maker 和对象范围过滤。case 结束后该详情旁路立即消失，普通 GET 对无权用户返回 404。

### 12.3 金额与库存边界

订货财务通过才把订单从 `status=0` 变为 `status=1`、回写计划申请累计并生成 `inbound_expectations/items`；这一步不入库存、不做 IQC、不立 AP。审批资格预检、case 决定、订单状态/来源副作用和决定后详情投影由采购/委外各自的 finance decision command service 包在同一事务；响应投影失败必须连审批事实一起回滚。仓库申报超量时先提交异常并返回 409，仍不写库存/AP/订单累计。财务可 `APPROVE_ALL`、`APPROVE_CUSTOM` 或 `REJECT_EXCESS`；全批/自定义必须填写说明，自定义额外量必须严格大于 0 且小于请求超量。服务端调整草稿，接受量仍须仓库再审才过账。

标准 10→100 场景：财务已批 10 吨，仓库草稿申报 100 吨，`requestedExcessQty=90`。全批为接受/退回=`100/0`；自定义额外批准 5 吨为 `15/85`；不批超量为 `10/90`。未批准量由精确退货任务 owner 处理，财务不能代替仓库确认实物入库，也不能代替采购/委外完成供应商退回。

## 十四、销售待收、正式应收与分批收款重构（2026-08-08；2026-08-09 修订，V236–V238）

### 14.1 订单可见与正式应收分层

- 销售订单只保存币种和服务端计算的原币金额；保存和销售审核（当前无独立提交态）不读取或校验汇率。审核后进入“销售订单待收计划”，供财务按原币提前跟踪订单号、客户、结账方式、币别、订单额、已发运立账和未发运预计额；该视图是经营计划，不写 AR/总账。
- 待收计划只展示币种和原币金额，不读取汇率、不换算人民币；已发运正式立账与未发运预计待收按对应币种分列或分组，不能在订单阶段合成本币总额。
- 仓库完成 `SHIPPED` 后才锁定财务维护的有效汇率，按发运批次形成正式 `ar_ap_ledger`，并把该汇率冻结为 AR 开账汇率。分批发运形成多笔 AR；合并发运可通过 `ar_ap_source_refs` 关联多张销售订单，来源金额使用发运当时快照，不回查并改写历史订单。
- 正式 AR 列表/明细展示：应收单号、客户、一个或多个销售订单号、来源发运单、立账日/到期日、结账方式、币别、开账汇率、原币应收、累计到账、累计费用冲销、原币未收、本币拆分及备注。关键字可查 AR/来源/订单号；客户维度仍由客户选择器过滤。

收入确认与外币初始确认的决策理由见 [ADR-030](../99-决策记录-ADR/ADR-030-销售待收计划与正式应收分层.md)。

### 14.2 销售收款交互与服务端权威金额

- “引用应收”位于顶部“查看历史”左侧；普通销售收款不得手工加空行，必须先选客户再引用同客户未结 AR。客户选择器复用销售模块右侧滑窗，左侧一个搜索框同时搜索分类和客户；取消更换客户不清空既有行。
- 单头：服务端自动单号、客户、收款账户、手续费、其它费用、其它费用项目、备注。手续费和其它费用均按人民币填写，账户来自启用的账户主档。
- 明细：本次收款原币、币别、到账汇率、自动换算人民币、费用冲销原币、冲销人民币、冲减应收账面人民币、收款前后原币余额、备注。币别默认取 AR；当前单币金额结构只接受与 AR 同币种，真正跨币种核销在双币金额/双汇率模型完成前失败关闭。
- 服务端忽略客户端派生的本币金额、账面冲减和汇兑差额，按权威快照重算：
  - `到账人民币 = 本次收款原币 × 到账汇率`
  - `费用冲销人民币 = 费用冲销原币 × 到账汇率`
  - `冲减应收账面人民币 = (本次收款原币 + 费用冲销原币) × 开账汇率`
  - `汇兑差额 = 到账人民币 + 费用冲销人民币 − 冲减应收账面人民币`
  - `本次总收到金额 = 本次收到金额 + 冲销费用`
- 单头 `手续费 + 其它费用` 必须等于所有明细的冲销人民币合计；其它费用非零时必须选择一个启用的 `EXPENSE` 项目。账户只增加客户实际到账，费用只冲减 AR，不冒充现金。

### 14.3 分批、审核、红冲与总账

- 审核强制制单人与审核人分离，并在悲观锁内校验收款单、账户和每笔 AR，拒绝重复引用、跨客户、跨币种、已结清、超收及未核验历史原币余额。
- 每次审核更新：`累计到账原币 += 本次收款原币`、`累计冲销原币 += 本次冲销原币`、`未收原币 = 原币应收 − 累计到账 − 累计冲销`；收到最后一笔时以本次收款单日期记录结清日。红冲按行级审核快照对称恢复 AR、账户和资金流水；`FinanceReceiptService` 不直接修改通用总账。若相关期间已生成 AUTO 凭证，红冲后须由财务重跑该期间，让 `GlPostingService` 从当前已审核事实重建。
- 总账分录：借收款账户（实际到账）、借手续费/其它费用、贷应收账款（按开账账面冲减），差额进入启用的汇兑损益科目；借贷必须平衡。账户币种与流水金额使用同一单位，有历史流水或非零余额的账户禁止改币种或期初余额。
- 普通 UI 不暴露直接预收；后端保留兼容入口，但直接收款/预收同样必须提供正数原币金额和显式正到账汇率，本币由服务端派生且不允许费用冲销。后续预收分配应做独立流程，不能伪装成 AR 引用。

### 14.4 报表、铺底额与兼容边界

- 销售收款明细/汇总拆开实际到账、费用冲销、账面冲减和汇兑差额；客户对账按币种分别滚动原币余额，并把筛选日前发生额带入期初，本币余额统一滚动。
- **历史口径（V236–V238）**：当时只升级 AR/销售收款，采购付款仍沿用本币字段。该限制已被 V246 的当前付款结算模型部分取代：新保存付款由服务端根据付款原币、付款汇率和 AP 开账账面金额派生现金本币、账面核销本币与汇兑差额，并写入 `amount_authority_version=1`；客户端金额不再作为会计权威。V246 不自动证明历史付款正确，`amount_authority_version=0` 的记录继续 fail-closed，必须经过有审计的财务核验后才能重生成总账或红冲。
- `clients.credit_floor`（铺底额）只用于客户应收汇总的 `超铺底 = max(应收余额 − 铺底额, 0)` 提示，不参与单笔收款核销，不改写 AR。
- V236 已部署 checksum 不可修改，其初始回填边界较宽；V238 仅对保守安装时间窗内、可证明由 V236 合成且币种停用/删除或汇率不为 1 的行撤回原币拆分。V236 后新事实和时间边界不清的行不自动改写。最终只有“显式人民币主档、启用未删、汇率精确为 1、原/本币恒等式成立”的历史行可自动使用，其余在引用时提示财务核验；不得按单号、日期或旧外币汇率猜历史事实。
