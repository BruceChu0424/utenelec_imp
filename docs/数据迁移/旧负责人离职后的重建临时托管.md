# 旧负责人离职后的重建临时托管

2026-10-22 本地全量重建中，`migrate_client_data.sql` 曾触发 `clients_owner_employee_id_current_employee` 并整事务回滚。真正原因是把旧业务员精确匹配到已按本次名册规则离职的员工后，又把该历史身份写进“现任负责人”。这不是金额、信用额度或数据校验过严的问题。

V398 的 `fn_require_current_employee_reference_strict` 要求现任负责人是未删且状态为 `active/probation/onLeave` 的员工。离职人员仍保留历史身份，不因导入困难而改回在职；数据库守卫、外键与权限配置保持启用。此次修复放在迁移适配层，不修改已应用 Flyway。

## 历史人与现任责任分别落位

| 来源状态 | 当前归属 | 历史事实 |
|---|---|---|
| 唯一旧 ID 对应真正在职员工 | 该员工 UUID | 原 `emp_id/seller_legacy_id/seller_id` 不改 |
| 旧员工离职、已删、非法状态、旧 ID 缺失或不唯一 | 保留的超级管理员 ADMIN 暂管 | 原 ID/UUID 与原因进入逐对象交接账本 |
| 来源非空但无法作为准确旧 ID 解析 | ADMIN 暂管，禁止按姓名猜人 | 原文字完整保留，不伪造原员工 UUID |
| 原来源为空或数值0，且原本没有负责人 | 保持公共 | 不把本来公共的资料全改为管理员私有 |
| 已人工维护且有效的当前负责人 | 保留 | 不由历史重导清空或重写 |
| 出货/退货具有可验证上游单据关系 | 继续遵守原有上游归属继承和混合归属拒绝规则 | 原销售业务员身份不改；继承 ADMIN 暂管的下游也逐对象记录 |

ADMIN 仅在员工 `code=ADMIN`、员工在职未删，且绑定唯一正确账号 `17665410007`、账号启用未删且 `is_super_admin=true` 时可用；条件不满足即阻断。不能挑其他同名员工，也不能任意选择“第一个管理员”。这保证现任归属满足当前数据库规则，又不会把原私有资料改成 NULL 后暴露给未来开通的账号。

本次涉及客户、供应商、外贸分类私有货品，以及销售订单、出货、其他出货、退货。模具保管人原文、生产计划原制单/业务员/经办人快照及其他历史操作者不通过姓名猜 UUID，也不替换成管理员；当前并无从这些旧文本自动创建现任责任的迁移路径。

## 共享执行与证据

`compose_bootstrap.py` 对以下5个模块自动前置 `migrate_owner_custody.sql`，完成模块后先 flush 交接账本，再清理临时表：

- `migrate_client_data.sql`
- `migrate_supplier_data.sql`
- `migrate_client_owner.sql`
- `migrate_goods_owner.sql`
- `migrate_sales_owner.sql`

完整重建协调器和原 `migrate.sh` 都已通过该组合器执行这些模块，因此没有“新增辅助函数但旧入口没有调用”的缺口。模块需要当前独占导入 claim：完整事务取 `uten.bootstrap_run_id`；原 CLI 单模块模式取当前数据库唯一 RUNNING claim。不新增业务表，不插入额外结构对账项，不改变23项结构对账口径。

持久证据位于：

```text
legacy_migration_runs.reconciliation_summary
  .currentOwnerCustody
  .<迁移SQL文件名>
  .helperSha256
  .pendingHandoverCount
  .entries[]
```

每项包含目标表、目标 UUID、目标旧 ID、来源引用、原员工 UUID、实际暂管员工 UUID及原因。原员工不存在或无法证实的，原 UUID 留空但来源原值完整保留。每模块保存辅助 SQL 的 SHA-256；重复运行按目标表及 UUID 合并去重，不抹掉已记录的其他模块或既有条目。

此处是**本次导入时的交接清单**。后续正式安排责任时，从当前 ADMIN 交接给核实的在职员工，不能把账本中的离职历史人重新设为现任负责人。未来已办完的交接是否仍在导入快照中，不代表当前仍由 ADMIN 负责，须看实际现任归属与交接事件。

读取清单的只读查询：

```sql
SELECT module.key AS mapper,
       item.value->>'target_table' AS target_table,
       item.value->>'target_id' AS target_id,
       item.value->>'target_legacy_id' AS target_legacy_id,
       item.value->>'source_reference' AS source_reference,
       item.value->>'original_employee_id' AS original_employee_id,
       item.value->>'assigned_employee_id' AS assigned_employee_id,
       item.value->>'reason' AS reason
FROM legacy_migration_runs run
CROSS JOIN LATERAL jsonb_each(run.reconciliation_summary->'currentOwnerCustody') module
CROSS JOIN LATERAL jsonb_array_elements(module.value->'entries') item
WHERE run.run_id = '<本轮成功run_id>'::uuid
ORDER BY target_table,target_legacy_id;
```
