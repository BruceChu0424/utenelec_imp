# V736 车间直送资格单一事实源与不可转原因

> **2026-10-04 [V798](275-V798委外按工序领直属物料与分批回厂.md) / [ADR-143](../99-决策记录-ADR/ADR-143-委外按工序领直属物料与分批回厂.md)**：删除 `fn_workshop_direct_source_is_subcontract`，`SUBCONTRACT_ROUTE` 只剩「接收需求按委外供应」(生产侧委外件判据与哨兵分支已删)；`fn_workshop_direct_reason_text` 的 `SUBCONTRACT_ROUTE` 文案改为「上层 X 是委外件：本工单做的物料先送入仓库，由委外人员领料发给委外商」。下文按 V736 当时口径保留。

**日期**：2026-09-27
**决策**：[ADR-127](../99-决策记录-ADR/ADR-127-直送资格单一事实源、不可转原因与报工自动分流.md)
**改动**：建/换函数，换掉一个守卫触发器；`production_daily_report_items` 加一列可空的 `output_route_reason`(送仓原因码，存量行为空)；审核提速换七个函数的求值方式(结果不变，ADR-127 §8)；不加表、不改任何存量数据。

## 背景

用户报：批量报工时 HV5ZJ012「明明有父层级、还在同一个车间」却转不了下一道工序，界面只写「(无同车间上层工单)」。

只读实查(克隆库 `uten_imp_wt15`)：HV5ZJ012 在 2026-09-23 被改成委外件(委外前置自制：先做好入仓，发外加工，回来后上层工单从仓库领料)。它的共享批次路线是委外，上层工单对它的需求也是委外口径。**拦住是对的，界面给的原因是错的。**

同一条「能不能直送」的规则此前散在约 10 处：4 个库函数、3 个行触发器、3 个 Java 服务、3 处前端，已经互相走样(保存只看父子关系不看接收方状态；审核 7 种原因共用一句话；`fn_demand_direct_supply_eligible` 另有一套更松的判定)。

## 新增函数

| 函数 | 作用 |
| --- | --- |
| `fn_workshop_direct_source_is_subcontract(生产工单)` | 生产侧是不是委外件：分析行是委外前置自制/委外备料，或它锚定的共享批次路线是委外 |
| `fn_workshop_direct_linked_demands(生产工单)` | 「结构挂钩」唯一的一份写法：与生产工单同一个物料分析，或都不走物料分析时有子计划链接/在途挂钩(peg)的同货品需求(附带接收计划是否已取消)。可内联的 SQL 表函数；候选列表的范围，也是路线原因只对谁点名的依据。挂钩不等于父子关系成立 |
| `fn_workshop_direct_relation_code(生产工单, 接收需求)` | **唯一的结构判定**：NULL=可直送；否则按固定次序返回 `SOURCE_INVALID` / `TARGET_INVALID` / `SELF` / `GOODS_MISMATCH` / `SUBCONTRACT_ROUTE` / `BUY_ROUTE` / `NO_PARENT_RELATION` / `DIFFERENT_WORKSHOP` 之一。路线只在这里判，且只对挂钩的需求点名；没挂钩的委外/采购需求回 `NO_PARENT_RELATION` |
| `fn_workshop_direct_reason_rank(原因码)` | 原因的接近程度(越小越接近可送)，没有可送工单时界面显示最小的一条 |
| `fn_workshop_direct_reason_text(...)` | **唯一一份原因大白话**(不含代号，括号半角)，界面、审核报错、数据库守卫共用 |
| `fn_workshop_direct_targets(生产工单[, 接收需求[, 本次基本数量]])` | 候选列表与单条校验共用的表函数：逐条给出接收工单、需求量、已覆盖、还差多少、本来源最多可送、`receiver_open`(结构与接收状态都允许，只可能差数量)、`eligible`、原因码/原因/接近程度、「先急后缓」次序与 `receiver_label`(文案里称呼接收方的那几个字，保存报工核数量时复用)。列表模式只在挂钩的需求里找(任意车间，计划已取消的不列)，只列结构上的上层：`NO_PARENT_RELATION` / `SELF` / `GOODS_MISMATCH` / `SOURCE_INVALID` / `TARGET_INVALID` 的行不列、也不当原因；一条结构上的上层都不剩时返回一条哨兵行(`NOT_A_COMPONENT` / `NO_RECEIVER_ISSUED_YET` / `SUBCONTRACT_ROUTE` / `SOURCE_INVALID`)。别的物料分析里同车间同货品的工单不拉进列表，所以不会挡住哨兵，也不会以委外/采购的名义冒充上层 |
| `fn_assert_workshop_direct_target(生产工单, 接收需求, 基本数量)` | 锁住接收计划/计划包/工单与需求后读单条校验，不可送即抛 `无法转到下一道工序：<原因>`(SQLSTATE 23514，HINT=原因码，CONSTRAINT=`workshop_direct_target_guard`) |
| `fn_guard_workshop_direct_target()` + 触发器 `trg_a_workshop_direct_target_guard` | 直送明细写入前调用断言。名字排在 `trg_aggregate_direct_slices` 之前(行级 BEFORE 触发器按名字字母序执行)，共享切片只在资格通过后才记录 |

原因码与文案、接近程度：

| 接近程度 | 原因码 | 大白话(示例) |
| --- | --- | --- |
| 10 | `QTY_EXCEEDS_REMAINING` | 转给上层工单 ZX… 的本次基本数量 60 超过最多可送 50，超出部分请送入仓库或分给其它上层工单 |
| 20 | `SOURCE_SHARE_USED_UP` | 本工单承担的份额已全部交接 (同计划行拆出的工单共用额度) |
| 21 | `DEMAND_ALREADY_COVERED` | 上层工单 ZX… 的 HV… 已经备齐 (仓库备料或其它直送) |
| 30 | `RECEIVER_STATUS` | 上层工单 ZX… 已按齐套开工/已完工/已取消，不再接收直送 |
| 31 | `PLAN_NOT_ACTIVE` | 上层工单 ZX… 的生产计划已暂停/已结案/已取消/未审核 |
| 32 | `PACKAGE_NOT_CONFIRMED` | 上层工单 ZX… 的计划包已取消，不再接收直送 |
| 33 | `DEMAND_CLOSED` | 上层工单 ZX… 已不再需要 HV… |
| 40 | `DIFFERENT_WORKSHOP` | 上层工单 ZX… 在二车间，跨车间必须送入仓库 |
| 50 | `SUBCONTRACT_ROUTE` | HV5ZJ012 是委外件：做好后先送入仓库，发外加工回来后，上层工单再从仓库领料 |
| 51 | `BUY_ROUTE` | 上层工单 ZX… 的 HV… 按采购供应，只能从仓库领料 |
| 60 | `NO_PARENT_RELATION` | 上层工单 ZX… 的 HV… 不是由本工单供应 (属于别的物料分析或已由其它来源承担) |
| 61-64 | `SELF` / `GOODS_MISMATCH` / `SOURCE_INVALID` / `TARGET_INVALID` | 不能转给本工单自己 / 所选上层工单需要的不是这个货品 / 报工来源工单已失效 / 所选上层工单已失效 |
| 70-71 | `NO_RECEIVER_ISSUED_YET` / `NOT_A_COMPONENT` | 上层工单还没下达到车间 / 本工单做的是顶层产品，没有下一道工序，请送入仓库 |

同一个文案函数还给出报工「送入仓库」那部分的原因(不是不可转原因，只写进下一节的新列)：`USER_CHOSEN`「报工时选择送入仓库」、`RECEIVERS_FULL`「能直送的上层工单都已分满，其余送入仓库」、`PUBLIC_SHARE`「计划内的公共备货部分，统一送入仓库」、`ACTUAL_SURPLUS`「超出计划的实际产量，统一送入仓库」。没有接收工单、车间、状态上下文时(报工详情按已存原因码回看)给中性说法，例如「上层工单在其它车间，跨车间必须送入仓库」。

## 新增列：报工送仓原因 (ADR-127 第二步)

一行报工由工人逐条分给上层工单(先急后缓)，其余送入仓库。服务端每个接收工单写一条独立的转送明细(「一条明细一条接收需求」的守卫全部照旧)，送入仓库的明细写原因码：

| 列 | 说明 |
| --- | --- |
| `production_daily_report_items.output_route_reason TEXT NULL` | 送入仓库的报工明细为什么没转下一道工序。取值白名单(CHECK `production_daily_report_items_output_route_reason_chk`)：`USER_CHOSEN` / `RECEIVERS_FULL` / `PUBLIC_SHARE` / `ACTUAL_SURPLUS`，或一个可送的上层工单都没有时最接近可送的那条不可转原因码；只允许出现在 `destination='WAREHOUSE'` 的明细上。转送明细与存量明细为空 |

- 只在保存报工时写，审核不重新分流(ADR-118 §3 不静默改去向)。
- BOM 学习(V711/V737)读明细的 `execution_segment_id/qty/unit_rate/is_final/is_deleted/fqc_recovery_authorization_id`，学习触发器也只看这几列：新列不影响学习口径与触发。

## 等价性证明

- 克隆库 `uten_imp_wt15` 全部同货品的(生产工单, 需求)组合共 15 对：旧 `relationship_allows` / `responsibility_allows` 与新原因码推导结果逐对一致(14 对可直送，1 对 `SUBCONTRACT_ROUTE` 即 HV5ZJ012)。
- 「路线只对挂钩的需求点名」只把原先的 `SUBCONTRACT_ROUTE` / `BUY_ROUTE` 换成 `NO_PARENT_RELATION`，两者对两个包装都是「不可直送」，所以包装结果不变；父子证明都要求同一物料分析或子计划/挂钩，能直送的需求必然挂钩，列表里的结构上层不变。克隆库事务内以临时函数名建新版本、比对后回滚：720 对(16 个工单 × 45 条需求)原因码与包装逐对一致，单条校验与每个工单的列表逐行一致(HV5G001 → 11 个上层工单各 1000；三个子件 → ZX00000653 各 11000；HV5ZJ012 → 委外件)。
- 结构上：新规则 = 旧规则 AND「生产侧不是委外件」。旧关系证明成立时生产侧必然不是委外件(父子证明只认 `MAKE_COMPONENT` 或路线为自制的共享批次锚点，一个锚点只有一个批次)，所以两个包装对所有调用方逐一等价。
- `WorkshopDirectTargetReasonPostgresTest` 在真实迁移后的库上逐条断言全部原因码(含共享委外批次的 `SUBCONTRACT_ROUTE`)、两个包装、断言报错与持续生产识别；另有同车间同货品但没挂钩的自制/委外/采购需求：不进列表、不成为原因，顶层产品仍说 `NOT_A_COMPONENT`、上层未下达仍说 `NO_RECEIVER_ISSUED_YET`、委外前置自制仍说 `SUBCONTRACT_ROUTE`。

## 审核提速：只换求值方式，结果不变 (ADR-127 §8)

一张报工分给 11 个上层工单时审核实测 37 秒(贴着 40 秒事务上限)。原因在库函数，不在单据张数(ADR-127 §8 有剖面与交替实测)：

| 函数 | 改法 |
| --- | --- |
| `fn_workshop_direct_source_available(线边仓, 需求)`、`fn_workshop_direct_covered_base_qty(需求)` | 原写法把关系判定与「投给哪条需求」并列，规划器把判定下推到同货品的全部报工明细上逐条先算(分给 N 个工单就判 N 遍，审核随 N 平方增长)。改为先按需求(+线边仓、货品)取出直送批并物化，再对出现的每个生产工单判一次关系；写成 plpgsql。同一视图、同一判定、同一求和 |
| `fn_preplan_reservation_has_qualified_origin`、`fn_workshop_direct_responsibility_allows_before_v715`、`fn_finished_in_is_public_output`、`fn_daily_report_is_public_output`、`fn_line_side_stock_targets_demand` | 由 LANGUAGE sql 改为 plpgsql 的 `RETURN (原查询)`。PostgreSQL 16 对 SQL 函数不缓存计划，外层每条语句都要重新规划函数体(合格来源证明一次 60-130ms，执行不到 1ms)；plpgsql 在同一连接内只规划一次。查询文本在迁移里从现有定义原样取出并断言形状(不手抄)；名称、参数名、返回值、STABLE/STRICT 不变 |
| 以上七个函数固定 `SET plan_cache_mode = force_generic_plan` | 与原 SQL 函数一样按「参数未知」规划，计划形状不变；不固定的话 plpgsql 会因「带参数值的计划估价更低」一直按调用重新规划 |
| 合格来源证明另加三处 `OFFSET 0` 围栏 | 按预留取它自己的权益事件、按事件指向的入库行(或到货检验入库行)取那一行后再比对其余条件；条件本就要求这些主键相等 |

以后若再用 `pg_get_functiondef` + 锚点替换改这五个函数，函数头已是 `LANGUAGE plpgsql` 并带 `SET plan_cache_mode`，正文包在 `BEGIN RETURN ( … ); END` 里，锚点仍在原查询文本内。
