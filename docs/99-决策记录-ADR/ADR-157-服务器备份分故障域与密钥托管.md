## 1. 背景

2026-10-06 对测试服务器做了 6 份只读审计 (存储、密钥、SSH、监控、附件、Nginx/TLS), 合并后的高危项:

1. 数据库和它的全部备份 (pgBackRest repo1、配对备份、升级前 dump 的一部分) 都在同一组老机械盘 md0 上,
   两块盘同批次, 其中一块已有 70 次 ATA 错误; 没有异地副本, repo1 也没有加密。
2. 明文密钥散落: PostgreSQL 历史日志和 journal 里出现过数据库口令和 PII 主钥 (应用把主钥作为绑定参数传给
   `pgp_sym_encrypt/decrypt`, 慢日志默认完整记录参数); 旧配置目录能被 nginx 读到; 根 CA 私钥未加密放在服务器上;
   `postgres` 超级用户口令仍有效; 更新器把 OSS Secret 放在 `openssl -hmac` 的命令行参数里。
3. SSH 仍允许口令登录, 运维账号是免密 sudo。
4. 没有任何主动告警: 备份失败、RAID 降级、服务宕机都不会通知人。
5. 配对备份还是 2026-09-09 的 v1 脚本, 不备私有原件也不自动清理, 状态页却显示绿色 (另由配对备份 v2 与自动保留修复)。

## 2. 用户决定 (2026-10-06)

1. **所有备份只保留 3 天**: pgBackRest repo1 与新建 repo2 都是 `repo-retention-full=3`; 配对备份 `retention_days`
   默认 3 (配置与示例都是 3, 每天 2 次); 更新器升级前 dump `UTEN_BACKUP_KEEP_DAYS` 默认 3 (至少保留最新一份)。
2. **确认无用就直接删除**, 不设 14 天隔离区。
3. **服务器上不留任何临时脚本或导出文件**, 运维命令经 SSH 标准输入执行。
4. **sudo 免密本次不改** (自动化依赖 `sudo -n`), 列入长期项。

## 3. 决策

### 3.1 备份分故障域

每份备份都和它保护的数据放在不同的物理盘上:

| 编号 | 位置 | 介质 | 加密 | 说明 |
|---|---|---|---|---|
| repo1 | `/data/backups/pgbackrest` | md0 机械盘 (与库同盘) | 否 (现状) | 保留; 库迁 NVMe 后 (C11) 它就成了跨盘副本 |
| repo2 | `/srv/uten-backup/pgbackrest` | NVMe 新卷 `uten-backup` | aes-256-cbc | 新建; 与库不同盘 |
| repo3 | 独立 OSS bucket + WORM | 云 | aes-256-cbc | 待建 (D6); 专用 RAM 子账号无删除权限 |

- 编号以此为准, 已退役的 `deploy/postgres/backup/README.zh-CN.md` 里 "repo2=OSS" 作废。
- 每日 `uten-pgbackup.service` 依次对 repo1、repo2 各做一次全量; 任一仓失败不影响另一个仓, 但单元记为失败并告警。
  backup 结束时 pgBackRest 自动 expire, 不再单独跑 expire。
- WAL 归档保持同步, 不开 archive-async (少一个变量, 等加 repo3 时再评估)。
- 升级前 dump 默认目录改为 `/srv/uten-backup/pre-activation` (NVMe)。
- 配对备份仍在 `/data/uten-imp-backups/paired` (md0), 每天 03:40 与 13:10 两次; 它的异地副本见 C2。
- **附件不迁 /data**: 迁过去后在线附件、PGDATA 和全部备份会挤在同一组准备退役的老盘上, 故障更集中。
  附件缺的是备份覆盖面 (配对备份 v2) 和异地副本 (C2)。
- `/srv/uten-backup` 挂载点 `chattr +i`, 卷没挂上时写不进去; fstab 带 `nofail`, 阵列出问题系统照样启动。

### 3.2 保留 3 天的落地口径

- pgBackRest: `repo1-retention-full=3`、`repo2-retention-full=3` (count), 每天一份全量即 3 个还原点,
  WAL 保留到最旧全量, 按时间点恢复窗口约 3 天。
- 配对备份: 最近 3 个日历日且至少最新 3 份 (数量下限防止连续失败或时钟前跳把历史删光);
  每天 2 次时正常留 6 份。服务器状态页的集合数上限随之改为 `2 × 每天次数 × retentionDays`。
- 升级前 dump: 最近 3 个日历日, 最新一份已完成的 dump 无论多旧都保留。
- 异地仓 (待建) 至少 3 天。
- 健康门禁同口径: 仓库里旧双仓链路 (新专用主机 `phase2-postgres.sh` 之后的 commissioning) 的恢复点下限
  统一为 3 (`pgbackrest_repo2.MINIMUM_RESTORE_POINTS`, `backup_commissioner`/`backup_acceptance`/`release_updater`
  同值, 契约测试锁住), 否则只留 3 份全量的主机永远过不了健康检查。服务器上不在仓库里的
  `local_backup_health.py` 改 repo1 保留期前先只读确认它的下限 (C13)。
- 代价: 本地只能回到 3 天以内; 3 天后才发现的数据问题只能靠异地仓或人工记录, 所以 repo3 与每月恢复演练是配套前提。

### 3.3 密钥纪律与托管

- 秘密不出现在任何进程的命令行参数里。更新器的 OSS 签名改为 Secret 经环境变量交给 python 计算 HMAC
  (`/proc/<pid>/environ` 只有同一账号和 root 能读)。平台内告警不配置外部 webhook 凭据。
- PostgreSQL `log_parameter_max_length = 0` 与 `log_parameter_max_length_on_error = 0`;
  `postgres` 超级用户无口令, 只能本机 peer 登录; 除 `postgres`、`uten`、`uten_migrator`、`uten_repl`
  外不允许可登录角色 (现有集群加固脚本前后检查)。
- 不产生 core dump: 应用单元 `LimitCORE=0`, `fs.suid_dumpable=0`, 停用 apport。
- 离线托管件: 两位管理员各自的 age 公钥加密, 托管件经 SSH 管道直接落到管理机, 服务器上不落盘;
  存两处 (密码管理器附件 + 保险柜加密 U 盘); 轮换任何密钥、改 env、改备份仓口令后当天重做; 每月解开一次验证。
  根 CA 私钥托管后从服务器删除。
- SSH 只认密钥, cloud-init 钉死 `ssh_pwauth: false`。
- 运维命令经 SSH 标准输入执行, 部署文件从 `main` 的 git blob 取并核对 sha256, 服务器上不留临时脚本、
  导出文件或配置副本。

### 3.4 删除流程

确认无用就直接删除, 不设隔离期: 只读核对它不在任何运行路径里 → 只按明确的完整路径删除 →
含秘密的文件用 `shred -u` 且同时轮换对应密钥 (NVMe 上 shred 只是尽力而为) → 记入当次治理记录。
程序自己命名的备份集合只交给程序自己的保留规则清理。

### 3.5 单元沙箱与权限分离

- `uten-imp.service`: 只放开附件卷与日志 (`/data/uten-imp/attachments` 不再可写), 空能力集、
  `ProtectProc=invisible`、`RestrictNamespaces`、`SystemCallArchitectures=native`、`MemoryHigh=5G/MemoryMax=6G`、
  `TasksMax=1024` (高于服务器状态页线程红线 800, 状态页先黄先红、最后才撞顶; 调低时先调低两个阈值)、
  `UMask=0077`、`LimitCORE=0`、依赖附件卷挂载与 ClamAV。不加 `MemoryDenyWriteExecute` (JIT)。
- `uten-imp-updater.service`: `ProtectSystem=strict`, 可写路径逐一对应更新器与调度器实际写的位置
  (契约测试校验); 更新器锁移到 `/run/lock`。人工 activate 不经过该单元。
- `uten-pgbackup.service`、`uten-paired-internal-backup.service`、OCR 侧车同样加固。`uten-pgbackup` 只硬依赖
  repo1 所在的 `/data`; 备份卷 (repo2) 只 `Wants`/`After`、可写路径带 `-`, 备份卷掉了 repo1 照常备份,
  repo2 失败由单元自己的退出码报出 (挂载依赖失败不会让单元进 failed, 也就不会触发 OnFailure)。
- nginx 只加入 `uten-web` 组, 只能读发行目录的 `web/`; 更新器暂存与激活时设置
  `releases/<v>` 0751、`server/` root:uten-imp 0750、`web/` root:uten-web 0750, 缺组时在停应用之前报错。

### 3.6 告警

各关键单元 `OnFailure=uten-alert@%n.service`, 每 10 分钟只读巡检 (磁盘、RAID、服务、WAL 归档、备份新鲜度),
SMART 与 mdadm 钩子; 只记录固定大白话, 同一维度 6 小时一次。2026-10-07 用户确定统一使用平台内
中央弹窗, 删除群机器人配置。主机脚本原子写 root:uten-imp 只读共享的本机有界事件文件, 应用按持久
UUID 去重并送达当前具备告警接收和通知阅读权限的账号。队列上限 128 条/64 KiB、保留 7 天;
损坏和容量超限保留原文件并失败, 不伪称送达。ERP 停机时只记本机事件, 恢复后补送, 无外部宕机通知。
界面逐条中央确认, 身份变化关闭旧弹窗, 回执成功后确认送达; 恢复事件继续普通通知。

### 3.7 Nginx

登录类限流拆成三档: 登录每 IP 每分钟 30 次 burst 10; 访客发验证码每分钟 6 次 burst 3; 续期与退出每秒 10 次
burst 50。只允许 TLS1.2/1.3 且 TLS1.2 只留前向保密 AEAD 套件; 关闭 session tickets; HSTS 先 300 秒观察一周再改一年;
80 端口跳到固定内网域名, 不照抄客户端 Host 头; 现网补齐 `/api/ai/jobs` 专用 location。

## 4. 否决的方案

| 方案 | 否决理由 |
|---|---|
| 附件迁到 `/data` | 在线附件、库和全部备份集中到同一组老盘, 故障域更集中 (3 份审计一致) |
| 删除先进 14 天隔离区 | 用户 2026-10-06 决定直接删除; 隔离区里的旧密钥副本本身就是风险 |
| journal 保留 180 天 | journal 里出现过密钥; 取证靠 auth.log 26 周与 auditd |
| 开 archive-async | 多一个变量; 本地两仓同步推送足够 |
| 本次收紧 sudo | 自动化依赖 `sudo -n`; 先靠只认密钥 + 私钥加口令 + Tailscale ACL, 白名单放 C7 |
| 保留 7 天 / 14 天 | 用户统一口径 3 天; 更长历史由异地仓 (待建) 承担 |
