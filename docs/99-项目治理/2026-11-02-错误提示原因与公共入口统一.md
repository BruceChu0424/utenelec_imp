# 错误提示原因与公共入口统一

按用户要求及 `frontend-design`，错误提示简短说明已确认的原因，而不是只显示“操作失败”或异常对象。继续使用 Uten 顶部通知、居中弹窗和页内错误组件，保留原权限、提交、撤销、数据范围和重试规则。

## 公共规则

- `ApiException.message` 统一规范空消息、框架通用错误与旧泛权限文案。明确错误码优先于 HTTP 分类：首次改密、再认证、只读模拟身份、外网权限和数据范围变化分别说明；未知业务码不按 403 猜成普通权限不足。
- 后端给出的具体业务原因、字段校验、部分成功与结果待确认说明原样保留。`code`、`httpStatus`、`hasResponseCode` 和 `fieldErrors` 不因文案修改而改变。超时或 5xx 不宣称事务已经回滚，也不自动重新提交。
- `humanErrorMessage` 保留本地草稿、文件及输入校验的可读原因。英文内部异常没有可确认原因时使用诚实兜底，不编造网络或权限原因。
- `appApiError` 是通知中的唯一原因提取入口；`UtenNotify.apiError` 和 `guardAction/guardRun` 复用它，避免 catch-all 丢失具体原因。`UtenEmpty.error(error: ...)` 供页内错误直接复用同一原因。已有 `ApiException.message` 调用方自动采用同一文案。
- 三语 `commonError` 只作无法确认原因时的最终兜底。正常成功消息、业务提醒、字段内容和操作确认不统一改成错误。

示例：权限不足提示“此账号没有进行该操作的权限，请联系管理员”；连接失败提示“无法连接服务器，请检查网络或服务器状态”；服务器超时提示“服务器未及时响应，请先核对操作结果”。

## 跨端与验证

`contracts/user-error-message/v1.json` 固定 20 组展示契约，覆盖明确原因、具体业务保留、未知提交和未知业务码；Web 与 Flutter 共用实现。Java 同步权限不足和内部处理异常的两条默认消息，具体业务消息继续原样返回。WPF 候选在唯一异常构造入口同步 `UserMessage` 与基础 `Message`；同一 20 组样例及既有 Core 合同分别在 32/64 位 .NET Framework 下通过，两架构以 `/warnaserror` 编译。状态、响应来源及提交结果未知标记保持不变；没有为此运行用户 UI 或宣称完整 ERP、Win7 真机验收完成。

本地公共回归 45 项通过：包括 20 组契约、字段及响应证据保留、顶部通知、居中弹窗、页内错误和草稿保护的实际展示。三语由 ARB 重新生成。页面独立 catch 的逐项迁移及台账另由调用方审查记录维护；此记录不代替最终发布检查，也不把未等待的新一轮 CI 记为通过。
