# 批量领料成本写入与回归

本轮修复批量领料中的重复成本读取，保持原有 SQL 预算、物理流水、来源数量、精度策略和完整父回执。候选基线为 `52d8d051e`；未覆盖的运行类来自精确 `243920515` 的只读全编译目录，四份生产改动及所选测试均重新按实际源码编译，`javac -Werror` 无警告。

## 根因与公共入口

原完整三单夹具产生六条实物流水，首次执行为 537 条 SQL；扣除原已单独计数的 3 条到货范围读取和 6 条计量检查，原业务工作为 528，超过既有 479 预算。完整 11 用例中仅该预算用例失败，原日志与两份 command/replay trace 保留。

| 唯一维护入口 | 改动与保留的约束 |
| --- | --- |
| `ProductionInventoryValueService.bound` | 按原 movement 顺序、各 item 的原 posting UUID 顺序，有界读取实际 posting、既有回执和原 ISSUE root 的当前池身份；调用现有 `InventoryPositionPort.moveBatch`。原 GOOD_RETURN_REVERSE 的恢复事实检查继续保留。每项仍由公共 writer 复核真实 root、原数量、余额和幂等身份。 |
| `InventoryBusinessValueSupport.context / contexts` | 所有原 context 调用统一进入有界身份读取；显式来源账号与当前事务账号分别解析，保留原 event/doc/item、员工和幂等 key。每次读取当前事务真实设置与 users 关系，无跨调用或跨事务缓存。不存在账号保留原 `EmptyResultDataAccessException`，未绑定账号或员工仍明确拒绝。 |
| `InventoryValueLedger.insertEdge` | 全部 edge 的 precision admission 归入公共 write set；没有 write set 的入口仍逐 edge 检查。没有删去真实 edge、来源守卫或精确区间计算。 |
| `InventoryValueWriteSet` | 每次实际 flush 前检查该次消息全部原 goods/color key。先处理 60,000 bind 内部分块，再登记新 edge 的 admission，避免分块边界漏核；key 读取仍内部有界。窗口只存在于一次 ordered writer，flush 后清除，不保存跨操作的池头或资格。 |

适用调用链为 `StockDocService.issueFullBatch/issueLocked → StockValuationCoordinator.bindProductionMovements → ProductionInventoryValueService.bound → InventoryPositionPort.moveBatch`。公共 `context` 的所有调用方与所有 write-set edge 自动采用同一维护入口；单条 `move` 继续薄委托同一 `moveBatch`。其它带独立业务阶段或结果依赖的调用保持其原阶段，不合并币种、库存归属、源 posting 或审批责任。

HTTP 路径、请求、响应、业务批次上限及未知提交恢复合同均未改变。服务端仍统一决定业务事实；已实现的 Web、Flutter 桌面/移动及 WPF 调用方继续消费同一服务端合同。本记录不改变 Win7/WPF 的完整业务和目标机验收状态。
