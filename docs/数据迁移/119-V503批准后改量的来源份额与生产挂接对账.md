# V503 批准后改量的来源份额与生产挂接对账

日期：2026-09-07。对应[ADR-072 §2.3](../99-决策记录-ADR/ADR-072-委外收敛与采购委外订货批准后改量.md)、[ADR-069](../99-决策记录-ADR/ADR-069-订货行多来源锚定与同货品合并.md)。本地候选未部署，不能修改已应用的 V283/V438/V463/V472 字节。

## 修复的根因

原 `changeQty` 仅按比例增减申请 `ordered_qty`，没有改变订单 `sources.alloc_qty` 或申请→订单的生产挂接。既有V283快照和来源保护、V438商业冻结、V472来源冻结又没有合法改量入口，真实已财审订单的20→18会报错；只删除某一层保护仍会留下原20份额和20挂接。

新行为以当前批准数量为基线：订单20→18即时生效，原BOM需求/生产需求仍是20；原申请恢复2个待订份额，订单供给只保留18。原transfer的20不改，追加−2的部分反向事实。恢复至20时，只能使用该原来源仍可订的2，再追加+2，不能新造需求或公共超量。

## 两阶段、同一事务

[ProcurementOrderSourceRevisionPort](../../server/src/main/java/com/uten/imp/application/port/ProcurementOrderSourceRevisionPort.java) 由生产域实现，采购/委外订单服务通过port调用：

1. 调用方先发现原订单与请求中的完整来源集合，通过共享 `FulfillmentMutationLocks` 按全部商业头→全部明细→库存键取得前缀，再校验对象权限、已批准状态、无在审case及净实物流转下限；为每个改量行预留 `changeLogId`。
2. `prepare(orderType, orderId, lines)` 先只读取得实际订单/原申请头和库存维度，`requireCovered` 确认属于外层已预锁集合，不在回调内补拿上游头或新库存键。再独立复核原数量/单位、所有行含无来源委外的净实收下限、原来源有效性和剩余容量，冻结原商业快照及逐来源前后份额。
3. 订单服务修改数量，按冻结单价计算原币金额，再按冻结汇率将该原币金额换成本币，合计表头并flush。即时守卫只承认当前事务的精确old→new准备事实；价格、单位、币种、供应商、税率、结算方式、来源身份和历史货品快照不放开。
4. `apply(orderType, orderId, changeLogIds)` 更新来源份额、申请已订量和生产peg两端投影，并重算申请结案。调用方继续同步预计到货与委外出仓计划。
5. 新建财务复核case和原 `procurement_order_qty_change_logs`，log.id使用同一changeLogId。延迟守卫在提交时证明case、差异账、来源份额、申请累计量、原transfer净额和两端投影全部一致。缺任一环节整事务回滚。

JPA在UPDATE里携带未变化的快照字段不再被当成改写快照；真正首次锁快照仍须草稿审批且与原来源/主档一致。商业冻结保留原函数与触发器，只增加上述窄通道；没有禁用trigger。

## 来源顺序与容量

原来源 `line_no,id` 的FIFO顺序保持。减量先撤末尾尚未履约份额，逐份额保护原FIFO已收货份额和实际被生产收货转换的数量；不能按比例平均减少所有来源。没有足够未使用份额则拒绝并要求先处理真实下游。

增量按原FIFO，最多使用原申请 `qty−ordered_qty−其他草稿已送审占用`；不新加来源、不借另一份需求、不静默扩BOM。ADR-068初始下单时经明确来源允许的超采记录照旧保留；已批准改量的无来源追加超量不是本通道的权限。原来多订的尾巴在减量时先被减少，再减少真正的生产挂接。

来源减到0后保留原UUID、顺序和0份额，供历史追溯和之后从原来源恢复。两个FIFO分享函数和BUY切片视图排除0份额参与当前分配，防止末位吸收规则把新到货分给已撤份额；委外前置生产读取也只将正份额作为当前来源。0份额不表示原历史关联不存在。

历史缺sources、份额合计与原订单不一致、单位与原来源不一致时，明确拒绝猜测分配。没有任何来源的合法旧手工委外行仍可按冻结商业事实和实际下限改量；不会伪造生产挂接。

## 新账与原账

新增3表，均为业务CLEAR：

| 表 | 责任 |
|---|---|
| procurement_order_source_revisions | 一改量行一command；id关联原数量变化log，冻结旧/新数量、单位、原商业快照、原审批attempt、事务与责任人。 |
| procurement_order_source_revision_allocations | 逐原source的前后份额、前后申请已订量、受保护实物量、前后生产挂接净量。 |
| procurement_order_source_revision_peg_changes | 精确原transfer与两端peg UUID；追加CREATE/ADJUST和带符号基本数量；先核对原两端数量，再变更投影。 |

既有 `production_material_peg_transfers` / `production_material_subcontract_peg_transfers` 的身份和原 transferred_qty 不变。新增正向量增加订单peg累计allocated，减少量增加其released；原申请peg的released按相反归属同步变化。所有原订单余量、收货转换、红冲都按净迁移量解释；整单红冲只退回当前仍生效份额，不能再按最初20多退一次。

新事件、来源明细、peg变化与原qty变化log只可追加。两端peg的当前投影受原transfer基线与追加事实校验；0净量不删除原transfer。普通收货、已领料、公共在途认领和原反向门槛保持，后补数量不能越过这些真实关联。

新事实及复用的来源/商业/peg证明触发器使用 `ENABLE ALWAYS`。真实PG负测切到 `session_replication_role=replica` 后，改量日志、原transfer和历史快照仍拒绝改写；复制模式不能成为业务纠错接口。

本迁移不重算旧BOM、需求、原transfer、库存数量或金额。清空runtime/ops分类由单独 V504 合并 V500 八表与本次三表，V503不重复改清空函数。
