# ADR-017：模块化单体 + CQRS 读侧 + Outbox 异步旁路

- **状态**：已接受
- **日期**：2026-07-30
- **影响**：Flutter 前端结构、Spring Boot 模块边界、跨模块事务、老系统切换、测试与部署
- **取代**：ADR-005 的“默认单向影子双写”实施方向；ADR-005 保留为历史决策背景

## 背景

系统已经从前端 Demo 演进为覆盖销售、采购、委外、仓库、生产、钱流、总账、人事、
访客等领域的完整业务平台。当前仍是一个 Flutter 应用、一个 Spring Boot 应用和一个
PostgreSQL 数据库，但业务链已存在大量跨域协作：

- 销售订货 → 库存预留 → 排产 → 报工 → 成品入库 → 发货；
- 采购/委外/仓库审核 → 库存流水与余额；
- 销售/采购/委外 → 应收应付 → 收付款 → 总账；
- 主事务完成后发送通知、刷新统计或执行兼容操作。

这些链路需要强事务一致性。直接拆微服务会把本地事务变成分布式事务，同时显著增加
部署、消息、排障和数据一致性成本。另一方面，继续允许模块直接依赖对方 Entity 和
Repository，会使单体逐步失去模块边界。

## 决策

### 1. 系统拓扑

现阶段采用**边界强化的模块化单体**：

- Flutter 保持一个可部署应用；
- Spring Boot 保持一个可部署应用；
- PostgreSQL 保持一个中央数据库；
- 按业务域划分模块并声明数据所有权，不按技术层拆服务；
- 不为“看起来先进”而拆微服务。

只有满足以下至少两项时，才为某个模块单独评估服务化：

1. 需要独立扩缩容且负载特征明显不同；
2. 需要独立发布节奏并已有稳定团队所有权；
3. 已不存在跨模块本地事务要求；
4. 已通过公开契约与异步事件运行至少一个稳定周期。

### 2. 后端模块边界

每个业务模块逐步收敛为以下内部结构：

```text
features/<module>/
├─ api/              Controller、外部 DTO
├─ application/      用例编排、事务边界、公开 Facade/Port
├─ domain/           状态机、领域规则、实体
└─ infrastructure/   JPA Repository、SQL、第三方适配
```

迁移采用渐进方式，不要求一次重排全部目录。立即生效的约束：

- Controller 不直接依赖 Repository；
- 跨模块调用公开 Facade/Port，不直接调用对方 Repository；
- 跨模块不暴露可变 Entity，以 ID、命令对象或不可变结果传递；
- `common/` 不承载具体业务规则；
- 新增跨模块依赖必须通过架构测试登记，禁止形成新的模块依赖环。

### 3. 同步主链与异步旁路

以下操作继续在单体内同步执行并使用本地数据库事务：

- 审核状态机；
- 库存预留、库存扣增；
- 排产数量、报工数量与订单数量校验；
- 应收应付立账、红冲和总账过账；
- 任何决定主请求成败的业务不变量。

以下操作通过 **Transactional Outbox** 异步执行：

- 业务通知、提醒和外部消息；
- 老系统兼容写；
- 物化视图/搜索索引刷新；
- 大型导出准备、非实时统计；
- 其它允许重试且不能拖慢主事务的旁路动作。

Outbox 事件与业务写入同事务落库；Worker 负责幂等消费、指数退避、死信和告警。
在 Outbox 基础设施落地前，现有 `afterCommit + REQUIRES_NEW` 只作为过渡实现，不再复制
出新的同类机制。

### 4. 报表采用 CQRS 读侧

报表、看板和跨模块查询属于读侧：

- 允许使用只读 Service、原生 SQL、视图和物化视图；
- 不要求为了“纯 JPA”重写复杂聚合；
- 读侧不得承担审核、扣库存、立账等写模型规则；
- 返回统一的分页/列/行契约；
- 报表 SQL 必须有排序白名单、数据范围过滤和性能验证。
- `dashboard` 当前只允许通过已登记的 CQRS 读侧边依赖 `notice`、`operations`、
  `production`、`profilechange` 和 `visitor`；具体限于 `NoticeService` 的未读/待办查询、
  `FulfillmentWorkbenchQueryService.query`、`ProductionScheduleService.pendingCount`、
  `ProfileChangeReviewService.pendingCount` 和 `VisitorHrApprovalService.pendingCount`。
  这些调用只能返回计数或不可变 DTO，禁止向工作台注入对方 Repository、暴露 Entity 或调用写用例。

### 5. Flutter 前端

继续使用 feature-first + Riverpod，不对全部 CRUD 套用重型 Clean Architecture：

- 简单页面保持 Page → Provider → Repository；
- 销售、生产、库存、财务等复杂状态机可增加 application/use-case 层；
- 跨 feature 复用能力放入 `shared/` 或 `components/`；
- 每个 feature 提供自己的路由清单，由根路由组合；
- 禁止新的 feature 直接 import 对方私有实现；现有依赖通过基线测试逐步归零。

> **基线豁免（2026-08-06）**：`notice→admin`、`org→admin` 列入 `ArchitectureBoundaryTest` 白名单——admin 作为账号管理（`UserAccountAdminService`）与系统设置（`SystemSettingsService`）的共享枢纽，notice 庆典调度读设置、org 员工详情锁账号均属合法跨切面依赖（与既有 `finance/production/stock/visitor→admin` 同构）。后续若抽 `SystemSettingsPort` / `AccountLockPort` 可把这两条边逐步归零。

> **基线豁免（2026-08-07）**：`expenseclaim/purchase/sales/stock→common` 列入白名单——`features.common.taskclaim.TaskClaimService`（ADR-023 统一任务并发认领，show-as-locked）被四个协作 feature 作为**重复操作服务端兜底**调用（UX/防碰撞层；正确性底线仍是各 feature 自己的悲观锁+状态守卫）。`features.common` 是跨 feature 共享能力落点。后续若抽 `TaskClaimPort` 入 foundation `common`，可把这四条边逐步归零。

> **Flutter 依赖基线复核（2026-08-11）**：修复 Windows 对 `/`、`\` 混合路径的漏检后，重新盘点出当前功能分支实际存在 74 条跨 feature 方向。原 45 条白名单中 `admin→basic_data`、`dashboard→hr_profile`、`payroll→employee`、`purchase→production` 已不存在并同步删除；另补录 33 条在远端功能分支 `1e6265c5` 已存在、但此前被路径问题漏检的方向。这 33 条只作为“现状冻结、禁止继续增长”的临时架构债，不代表永久合法边界；其中 `basic_data↔department`、`dashboard↔notice` 等依赖环，以及跨域 Repository、Page、Widget、Provider 直连应优先改为 `shared/components` 或公开 Port/只读契约并逐步归零。当前 edge 级棘轮见 `test/architecture_boundaries_test.dart`；后续应升级到具体 import 点/数量基线，避免在既有 edge 内继续扩张。

### 6. 老系统切换

采用**按模块绞杀式切换**，而不是默认双向可写：

1. 迁移模块数据并完成数量、主键、金额和抽样字段对账；
2. 将该模块的全部写入口切到新系统；
3. 老系统对应模块转只读；
4. 老系统若仍需展示新数据，才启用 Outbox 新→老兼容写；
5. 老模块访问量归零后删除兼容写和适配器。

铁律是“一个业务模块同一时刻只有一个写入真相源”。若无法停止老模块写入，必须单独
设计数据所有权、冲突处理和对账，不得假设单向影子写能够解决老→新的数据漂移。

## 验证与治理

- 架构测试进入 `mvn test` / `flutter test`；
- 第一阶段使用“现有依赖基线 + 禁止新增”的棘轮策略；
- 每次消除一条依赖后同步收紧基线，不允许回退；
- 优先为销售→生产→库存→财务主链补 Testcontainers 集成测试；
- CI 至少执行后端测试、后端编译、Flutter analyze 和 Flutter test；
- 多实例部署前，内存限流迁到共享存储，定时任务增加分布式互斥，Outbox Worker 使用抢占锁。

## 后果

### 正面

- 保留 ERP 主链的本地事务与简单部署；
- 模块边界可被自动化验证；
- 报表与写模型各自选择合适实现；
- 通知和兼容操作不再拖慢或污染主事务；
- 为未来按需拆服务留下真实、可验证的接缝。

### 代价

- 需要持续消除现有跨模块 Repository/Entity 依赖；
- 需要建设 Outbox、Worker、死信和监控；
- 架构测试会对新增依赖提出约束；
- 文档和 ADR 必须随实现同步维护。
