# 关系、主档改名与历史快照规范

> 状态（2026-08-11）：开发原库 `uten_imp` 已确认到 V244/installed_rank 225，故 V181/V182 均已应用；当前源码到 V252/installed_rank 233（V251 货品导入，V252 审计覆盖），一次性生产物料克隆仍是 V250/installed_rank 231 历史证据，公司目标库保留 V238 既有只读证据。迁移存在不等于历史关系已全部对账、真实岗位 UAT 已通过或已获生产放行（各库仍以 `flyway_schema_history` 为准）。
> 适用范围：货品/BOM、基础资料、组织与人员、采购、销售、委外、库存、生产、财务、工资、公告、建议与审计。
> 结构权威：已应用的 Flyway DDL；本文说明运行时语义、迁移门禁和后续收紧顺序。

## 一、为什么必须区分三种数据

系统里看似都叫“名称”，实际有三种完全不同的语义。任何新字段、接口或报表必须先确定属于哪一种。

| 类型 | 定义 | 改主档名称后 | 典型字段 |
|---|---|---|---|
| 当前主档关系（live reference） | 当前业务对象指向一个仍可维护的主档 | 重新读取时显示新名称 | `goods_id`、`client_id`、`supplier_id`、`department_id` |
| 历史快照（snapshot） | 单据审核、发布、核算或审计当时的事实 | 不回溯修改 | 价格、汇率、地址、`publisher`、`*_name_snapshot` |
| 迁移溯源（legacy trace） | 老系统主键或原始文本，用于对账、重放和人工定位 | 不作为新系统运行时真源 | `*_legacy_id`、`source_doc_no`、legacy 人名文本 |

核心原则：**实时关系用 UUID，历史事实用显式快照，legacy/text 只做溯源。三者不能混成一个字段。**

## 二、实时关系规范

### 2.1 标识与显示

1. 关系键使用目标表稳定的 `id UUID`，数据库建立 FK。
2. 名称、编号、手机号、部门路径等可变字段不得充当关联键。
3. 改名只更新主档一行；引用表不复制当前名称，查询时按 UUID JOIN 当前名称。
4. UUID 主键不可修改，因此不使用 `ON UPDATE CASCADE`。
5. 主档被引用时不得硬删除；FK 默认 `ON DELETE RESTRICT`。
6. 有历史引用的主档应改为“停用/离职/禁用”，不能用软删除隐藏关系目标。

### 2.2 新关系上线顺序

新关系必须按以下顺序上线，不允许在一个版本里直接把 legacy 列替换成 `NOT NULL UUID`：

1. 加 nullable UUID 列和索引。
2. 加 `NOT VALID` FK，让新写入立即受保护，但保留历史异常的治理窗口。
3. 只按唯一、可证明的键做回填。
4. 应用层双写 UUID + legacy；读取 UUID 优先、legacy/text 仅 fallback。
5. 完成 preflight、reject 和 reconciliation。
6. fallback 命中率归零后 `VALIDATE CONSTRAINT`。
7. 后续版本再收紧新写入必填；legacy 列通常永久保留作审计，不要求物理删除。

### 2.3 名称不是映射规则

以下做法一律禁止：

- `DISTINCT ON(name)`、`MIN(id)` 或“取第一条”解决重名；
- 用客户名、供应商名、员工姓名反查 UUID；
- 未命中时自动生成一个看似正常、可进入运营选择器的主档；
- 把不同老库命名空间中相同的整数当作同一人，例如 `Sys_Operator.ID` 与 `B_Worker.ID`；
- 为了让迁移通过而删除原始 legacy/text 字段。

只有目标表 `legacy_id` 唯一且来源字段语义已经确认时，才允许：

```sql
UPDATE source_table s
SET target_id = t.id
FROM target_master t
WHERE s.target_id IS NULL
  AND s.target_legacy_id IS NOT NULL
  AND s.target_legacy_id <> 0
  AND t.legacy_id = s.target_legacy_id;
```

未命中或歧义行进入 reject，不能猜。

## 四、V180 模具关系的治理

V180 已应用，必须保持原字节，不能直接编辑或 repair 掩盖 checksum。

V180 曾按部门名/员工名使用 `DISTINCT ON` 回填 UUID。V182 的处理规则是：

1. 当前同名活动部门候选数大于 1：记录 `MOULD_DEPARTMENT_NAME_AMBIGUOUS`，清空 `department_id`。
2. 当前同名活动员工候选数大于 1：记录 `MOULD_KEEPER_NAME_AMBIGUOUS`，清空 `keeper_id`。
3. UUID 已无物理目标：记录 orphan，清空 UUID，保留 `place/keeper` 文本。
4. V182 不新增任何名称匹配。
5. 人工确认后必须直接写 UUID，并记录确认人、确认时间和证据来源；不能只改文本。

模具运行时显示规则：

- UUID 存在时，详情、列表、筛选和导出都使用目标主档当前名称；
- UUID 为空时，才显示 `place/keeper` legacy fallback，并标记“待映射”；
- 文本不得覆盖 UUID 对应名称。

## 五、BOM 的当前关系与历史成本

### 5.1 当前 BOM

`goods_bom_items.goods_id/component_goods_id` 是当前货品主档关系。组件改名后，当前 BOM 应显示货品的新名称。

V182 增加：

- 当前组件颜色 UUID；
- 当前默认供应商 UUID；
- `qty > 0` 的 `NOT VALID` CHECK；
- `goods_id <> component_goods_id` 的 `NOT VALID` CHECK。

直接自引用只是最低门禁。多层防环仍需写入侧使用**无固定深度上限**的递归 CTE，并在同一事务锁定相关 BOM 边。现有“最多 10 层”只能作为展示/展开保护，不能作为完整写入约束。

### 5.2 成本语义

必须区分：

- 货品主档/BOM 当前成本：可随当前组件价格和当前 BOM 变化；
- 已审核生产计划的 `production_plan_costs`：审核时成本/BOM 快照，不能因今天改组件而重写；
- 已审核销售、采购、委外单价和金额：单据事实，不能回溯更新。

当前 BOM 行的 `price/total` 语义需要后续 ADR 明确为“人工覆盖”还是“缓存”。在决策前，V182 不重写它们，也不伪造 `total=qty*price`。

## 六、必须保留的快照

以下信息必须保持事件发生时的值：

### 6.1 已有明确快照

- 工资批次、工资条的员工和部门快照；
- 公告发布人；
- 建议提交人、回复人及回复角色；
- 审计日志的 actor、before、after；
- legacy 制单/审核姓名 fallback，包括仓库单据从 Sys_Operator 精确导入的
  `maker_name_snapshot/approver_name_snapshot`；
- 生产计划的旧 `workshop_name/client_name/worker_name/seller_name`；
- 财务流水 `counterpart_name`；
- 来源单号 `source_doc_no`。

### 6.2 审核单据重打印快照

审核后仍需还原当时纸面内容的单据，应保存：

- 客户/供应商当时名称、地址、联系人、税务信息；
- 货品当时编号、名称、型号、规格、颜色、单位；
- 仓库/部门当时名称（如果是单据业务含义，而非纯当前筛选维度）；
- 数量、价格、折扣、税率、汇率和金额；
- 客户订单号、客户型号、交货地址及其它原始文本。

建议同时提供两套展示：

- 运营页面显示当前主档名称；
- 已审核单据重打印显示 `*_snapshot`；
- 详情页可以并列显示“当时名称 / 当前名称”。

历史数据无法从老库恢复原名称时，只能标记 `snapshot_provenance=BACKFILLED_CURRENT`，不能声称它是原单据快照。
### 6.3 订货财务审批与到货异常快照（V196/V201 已迁移，待生产验收）

以下字段是事件发生时的责任和金额事实，不能随当前配置或主档改名偷换：

- `procurement_order_approval_cases` 的提交载荷、attempt、提交人和 `assignee_user_id/employee_id/name_snapshot`；修改默认负责人只影响未来提交，不能改在途或历史 case；
- `procurement_order_approval_events` 与 `procurement_arrival_exception_events` 是追加式时间线，禁止 UPDATE/DELETE；纠错追加后续事件或补偿事实；
- `inbound_expectations/items` 是财务批准时的供应商、仓库、预计日期、订单行和数量快照，只用于未来到货任务，不是库存、AP 或质检合格事实；
- `procurement_arrival_exceptions` 的申报量、财务批准余量、单价/原币金额/本币金额快照、检测人和冻结财务负责人；金额必须由服务端十进制事实返回，客户端不能用浮点数重算替代；
- `supplier_return_tasks` 的原下单人责任、未批准量和完成事件；人员改名/调岗不应抹掉当时责任，当前授权只决定谁今天可执行动作。

历史迁入且已是 `status=1` 的采购/委外订货保持原事实：不补造审批人、审批 attempt、预计到货或异常事件，也不重放生效副作用。V196–V202 已包含在开发原库 `uten_imp` V244 和公司目标库 V238 以内，但不得把“迁移存在”写成历史已补造、岗位/实物 UAT 已通过或业务已生产上线。

### 6.4 生产备料来源谱系快照（V234/V250）

生产物料分析通知形成的 `preplan_supply_actions`、逐节点 allocation 及其外部来源，必须作为一条可追溯
谱系保存，不能为了让通用编辑继续工作而断开关系：

- BUY 只能外部化为 `PURCHASE_REQUEST`，SUBCONTRACT 只能外部化为 `SUBCONTRACT_APPLICATION`，MAKE 只能外部化为 `PREPLAN_MAKE_TASK`；route/type/id 组合必须一致；
- action 从 `OPEN` 到首次外部化、allocation 从空来源到首次绑定下游行，是专用握手；握手完成后业务身份、数量、来源文档和来源行不可改删，状态只能走受控生命周期；
- 采购申请/委外申请的直接来源行始终保留生产谱系；其后续订货草稿只在 action 仍为 CREATED 且订单未批准时允许正常编辑，订单批准/反向或 action 进入 IN_PROGRESS/DONE/CANCELLED 后受保护；
- 来源单取消必须与 action 取消/释放在专用事务内完成；有任何历史 action 的来源单不得通过通用 CRUD 复活；
- 通知和来源关系不代表系统已经自动形成商业订货。供应商、价格、币种等仍由采购/委外人员在任务分解后建立，财务批准才形成有效订单与预计到货。

V250 通过 deferred trigger 同时检查 UPDATE/DELETE 的 OLD 与 NEW 关联，避免先改外键或先删订单头再逃逸。
该迁移当前只有一次性隔离克隆证据，开发原库仍为 V244，公司目标库仍以 V238 证据为准；目标环境迁移前必须对现有 action 的
route/type/id、allocation 总量、下游行归属和取消状态做零差异核验。


## 七、软删除与停用

FK 只能阻止物理删除，不能阻止 `is_deleted=true`。因此服务端和数据库门禁必须共同遵守：

1. 有任何当前 BOM、未结订单、有效预留、生产需求或历史单据引用时，主档不得软删除。
2. 历史上使用过但当前不再使用的货品、客户、供应商、仓库、颜色、单位、员工应改为停用/离职。
3. 选择器排除停用记录；历史详情仍能按 UUID 解析名称。
4. `goods.auto_created=true` 的历史锚继续保留，但不得进入当前选择器、活动 BOM 或 MRP。
5. 分类删除不得隐式软删整棵货品子树；应先做引用影响预览和显式确认。

## 八、Preflight、reject 与 reconciliation

### 8.1 Preflight 必查

每次全量重导或关系回填前，至少记录：

- 数据库备份标识；
- 代码 commit；
- 导出 manifest、输入文件和迁移脚本 SHA-256；
- 来源总行数和每个 legacy 关系的非空/零哨兵/唯一命中/未命中数；
- 目标主档 `legacy_id` 重复数；
- 当前 UUID orphan 数；
- V180 部门名、员工名的重复候选数；
- 活动 BOM 中占位货品、自引用、非正用量和环路数。

任何唯一键异常必须先停止回填。

### 8.2 Reject 原则

复用 V134：

- `legacy_migration_runs`：一次执行；
- `legacy_migration_rejects`：逐行问题；
- `legacy_migration_reconciliation_items`：计数和不变量；
- `legacy_migration_run_files`：输入文件哈希；
- `legacy_migration_checkpoints`：增量成功游标。

要求：

- 每个非空非零来源引用必须“成功映射”或“有一个 reject”；
- `source_identifier` 使用目标行 UUID、字段名和 legacy 整数，不记录敏感姓名；
- reject 不得因为迁移执行成功而自动 waived；
- 自动 stub 必须标为历史锚/隔离状态，不能混入正常运营主档。

### 8.3 Reconciliation 状态

`legacy_migration_runs.status='SUCCESS'` 只说明 SQL 正常提交，不等于数据验收通过。

V182 仅对**执行 Flyway 当时已经存在的关系数据**计算：

- 有来源关系且全部指标通过、issue=0：`PASSED`；
- 有来源关系但存在 reject/失败指标：`FAILED`；
- 空库在导入前应用 V182：`NOT_RUN`。

无论迁移时是什么状态，V182 都标记 `postImportReconciliationRequired=true` 和 `productionAcceptance=false`。

## 九、2.2GB 历史数据的重导顺序

允许清空测试库不代表可以省略历史治理。推荐顺序：

1. 在隔离环境恢复一份生产等规模副本并生成备份。
2. 空库执行全部 Flyway；V182 此时应为 `NOT_RUN`。
3. 按主档→业务单据→流水/余额→生产成本快照顺序导入。
4. 导入脚本同时写 UUID；若仍先写 legacy，紧接着运行与 V182 相同的确定性 UUID backfill。
5. 20,798 条历史 BOM 孤儿逐行进入 reject/quarantine（旧脚本跳过 20,717 条，另有 81 条曾被 stub 错接后由 V181 隔离）；不得静默跳过，也不得进入活动 BOM。
6. `production_plan_costs` 约 136 万行按年份/批次导入和核对，不放进单个 Flyway 长事务。
7. 完成全量 reconciliation，再推进 checkpoint。
8. 只有 `PASSED` 且人工抽样、业务 UAT、权限和性能门禁通过，才能进入切流候选。

计数守恒至少满足：

```text
非空非零来源引用数 = UUID 精确映射数 + reject 数
来源 B_BomItem 218,820 = 有效源 BOM 198,022 + reject 20,798
活动目标 BOM 198,025 = 有效源 BOM 198,022 + 新系统手工 BOM 3
```

V181 软删的 81 条目标边属于上述 20,798 条 reject 的历史误接痕迹，不能再作为第三项重复相加。

金额、数量、库存余额和历史成本还需要分别做 SUM/状态不变量对账，不能只对行数。

## 十一、验收门禁

V182 及其应用改造至少需要以下自动化验证：

- 迁移只新增 nullable UUID，不删除 legacy/text，不设 `NOT NULL`；
- 所有新 FK/CHECK 都是 `NOT VALID`；
- backfill 只出现 `target.legacy_id = source.*_legacy_id`；
- SQL 不出现新的名称回填或 `DISTINCT ON`；
- V180 重名映射被清空并写 reject；
- 空库执行结果为 `NOT_RUN`，不得伪造 `PASSED`；
- 当前脏数据不会阻塞迁移，但新无效 UUID 写入会被 FK 拒绝；
- 组件改名后当前 BOM 显示新名，已审核生产成本快照不变；
- 软删除主档不会让历史详情名称消失；
- 仓库 worker 可按 B_Worker legacy 回填 UUID，maker/approver legacy 不出现 employees 回填或 unmapped coverage；
- 仓库历史 maker/approver 报表显示 operator 姓名快照，当前 UUID 存在时优先显示员工当前名；
- 20,798 BOM 孤儿在重导报告中逐行可追溯，其中 81 条曾误接目标边必须标明已由 V181 隔离。

最终生产报告必须分开写：已通过的结构门禁、历史数据 reconciliation、运行时双写/双读、人工 UAT、性能/容量以及仍然存在的 NO-GO 项。
