## 二、端到端走查：数据应当怎样变化

### 2.1 销售审核与生产待排

1. 销售订单审核后，生产待排列表按交期和急单规则读取审核有效订单。
2. 未排量必须由订单有效数量、已发/退、销售成品预留和有效计划关联聚合计算；页面缓存不是权威值。
3. 销售只能看获授权订单，成本、物料价格、内部质量责任和绩效字段不得进入销售 API。

**失败语义**：订单来源、单位换算或累计为负时 fail-closed，不允许调度用手工数字覆盖错账。

### 2.2 预览与确认

1. 打开排产详情时，全部产品 BOM 直接显示；系统计算单台用量、总需求、现货、其他单据占用、安全库存、未来供给和缺口。
2. 点击“一键生成子计划”只生成预览，不写计划包、执行段、库存占用、采购申请或领料单。
3. 用户在编辑面板调整后确认；服务端重新锁定订单/计划/库存，校验预览指纹、版本和稳定幂等键。
4. 示例：产品需求 10 件，物料 A 可支持 10、B 可支持 6，结果必须是 READY 6 + WAITING 4。READY 为 A6/B6 建完整物理占用和 DRAW；WAITING 的 A4/B4 只保留需求，不占 A 的零散现货。
5. 若计划明细合并多个销售订单行，确认时还必须把每个执行段按 link 剩余容量做不可变精确分摊；每段分摊合计等于段计划量，不能把一个段 JOIN 到所有订单行形成笛卡尔重复。
6. 确认事务还会对自制组件（有 BOM 且净需求>0）派生子生产计划（`subplan_links.source='EXECUTION_V1'`，V176）；成品未维护 BOM 的计划行通过 `noBomPlanItemIds` 返回，前端引导补 BOM，不再整批失败。

**为什么这样算**：如果 WAITING 把已有的 A4 先锁住，它可能长期饿死更早能凑整套的任务；如果不做临时覆盖，采购端又会把 A4 错算成采购缺口。V160 因而只在采购建议中按需求优先级临时抵减，不生成占用；正式转 READY 时再次原子抢整套。

### 2.3 缺料、采购与到料

1. BUY 路线的核验缺口随计划包生成采购申请和逐需求 peg；如果用户要求不生成采购申请但仍有 BUY 缺口，确认整体失败。
2. 采购工作台可按状态/逾期/异常筛选，并多选同一张已审申请的明细转采购订单。当前不支持跨多张申请自动合并，避免无供应商/币种/税率/MOQ 规则时错误拼单。
3. 采购订单审核把申请 peg 一对一迁移为订单 peg。
4. 分批收货只把实际审核收货量转为目标仓库存及收货供给事实；部分到货不足整套时，WAITING 不提前转 READY。
5. 当所有必需物料可一次覆盖整段时，事务内稳定锁定仓货色、创建全套 `stock_reservations`、生成精确 DRAW，并把段转 READY；只有真实迁移成功才同事务写 READY Outbox 事件，按执行段+触发收货去重。
6. V162/V163 要求申请/订单来源、收货头/行、订单 peg、生产需求、reservation、DRAW 和执行段同源；采购订单、收货或申请反向时，若对应数量已被生产占用/消耗，必须先解开精确下游，不能用 `GREATEST(...,0)` 静默吞差异。

### 2.4 委外供给（不是委外执行闭环）

1. 物料主数据明确选择 SUBCONTRACT 时，确认生成委外申请草稿并为每个生产需求建立 peg；未知来源和 MAKE 继续 fail-closed。
2. 委外订单审核把申请 peg 等量迁移到订单 peg；回厂单审核按 receipt item 分配并可分批累计，重复回调不重复挂接。
3. 只有 WAITING 段的全部必需物料都可覆盖时，才整体转 READY 并建立全套物理占用和 DRAW；单项提前回厂不会假开工。
4. 未开工的订单/回厂反向会整套撤回 READY 分配；已有消费时数据库和服务共同阻断直接反向。
5. 当前不把委外发料单、委外在制消耗、余料退回/损耗自动挂到该生产需求；这些仍须后续统一清账。

### 2.5 仓库备料与领料

1. 仓库工作台只显示后端同源 DRAW 任务；当前把未审核 DRAW 归为“待备料/待领取”，部分审核累计为“部分领取”，全部为“已领取”。
2. 仓库审核发料才产生库存流水，并按 posting 精确消费原 `stock_reservations`；重复审核或相同幂等请求不得二次扣料。
3. 取消/红冲必须沿原 posting 恢复同一需求、同一占用和同一库存方向。
4. 生产关联 DRAW/FINISHED_IN 的通用库存编辑、删行和删单由 V164 阻断；审核、分批出库、完成重开和专用反向必须走对应业务入口。

**当前边界**：尚无独立的“待备料→备料中→待双方交接→已交接/生产在制”状态机；因此现有卡片不能假装已经记录实物交接时间、拣货人和双方签收。

### 2.6 派工、开工与分批报工

1. 调度可在执行段上更新车间、班组、负责人和日期，然后派工；状态版本必须匹配。
2. 开工后进入生产中；报工页面从执行段入口带入精确身份，不再只按货品猜计划。
3. 同一执行段允许多次报工；审核累计合格量不得超过执行段计划量，跨计划/跨段身份直接拒绝。
4. 草稿报工不改变生产进度；审核后才更新段累计和销售/看板旁路事件。

**当前边界**：不良原因、照片、完整参与人员/实做工时、返工/补产幂等、阈值通知尚未全部实现，不得标为“质量报工完整闭环”。

### 2.7 成品入库、物料清账与结案

1. 成品入库行必须指向正确执行段；审核数量不得超过该段已审核合格且尚未入库的数量。
2. 首次或部分入库只更新入库累计；不能因为报工达到计划量就提前把成品视作可发库存。
3. 物料实际消耗、良品退料、审批损耗/报废和合法在制必须与累计领用对平。
4. 良品退料先生成 WDRAW，仓库审核点收后才增加原料仓可用库存；申请草稿不增库存。
5. 只有成品入库数量达标且物料结清，执行段才允许 COMPLETED。

### 2.8 完成后的反向

1. COMPLETED 段不允许直接红冲报工，防止出现“成品仍在库但合格报工已减少”的倒挂。
2. 先对已审核成品入库发起完成重开：锁单据和全部关联段，校验版本、累计和下游，写唯一 `REOPEN_COMPLETION` 事件，段从 COMPLETED 回到 IN_PROGRESS。
3. 然后红冲成品入库，最后才允许红冲原报工。
4. 一个入库单关联多个执行段时必须全有或全无；任一段失败，重开事件、段状态和库存单据都回滚。
5. 完成时已释放的未用物料不会因重开自动恢复占用；若需继续生产，应重新走可用量校验和领料，不得凭历史占用复活。

### 2.9 销售同步、部门任务和审计

1. 排产、缺料、开工、部分完成、完成、延期等事件与主事务一起写 Outbox。
2. 消费者按 `dedupe_key` 幂等投递；READY 使用执行段+触发收货去重，失败回滚本次消费并重试，达到阈值进入人工处理。
3. 销售订单详情按订单行读取 V157 精确分摊，只显示该行的执行段编号、计划量、状态、车间、日期、已报工和已入库；不通过货品 JOIN 猜归属。
4. 仓库/采购/委外工作台读取同一履约读模型；数字变化必须能追到需求、执行段、来源单据和审核状态；READY 待办按 `SUB_PLAN`/`DEPT_PROD` 部门及有效子部门解析接收人，不依赖已下线角色。
5. 系统管理审计详情显示脱敏的 before/after；业务数量变更还应带来源、幂等键、操作者、原因和前后累计。

### 2.10 任务工作台筛选稳定性

1. 仓库、采购、委外的状态统计卡使用固定业务定义，即使数量为 0 也允许点击；这表示“用该条件确认当前无任务”，不是无效状态。
2. 旧实现只用后端非零 `statusCounts` 生成下拉选项，点击零计数卡或刷新后当前状态消失时，选中值在 `DropdownMenuItem` 中匹配 0 项，因而触发 Flutter 断言。
3. 修复后先清理空选项、按值去重；当前选中值缺失时补入一个由统一标签解析器生成的临时选项，并用包含当前值的 `ValueKey` 同步外部筛选状态。
4. 任何时刻都必须保证：空筛选只匹配一个“全部”项，非空筛选在下拉项中恰好匹配一次。未知后端编码保留原值，不能为了避免异常而静默清空筛选。
5. 回归覆盖仓库 `READY_TO_PICK`、采购/委外 `UNPEGGED` 的零计数卡、零逾期卡，以及刷新后当前后端状态从选项中消失的场景。

详细交互和部门动作边界见[生产履约任务工作台](../03-页面/生产履约任务工作台.md)。

## 三、不会让数据乱掉的关键算法

### 3.1 可排完整套数

```text
物料 i 可支持套数
= floor((合格自由库存_i - 安全库存_i) / 单台基本用量_i)

立即可生产量
= min(订单未排量, 所有必需物料可支持套数)
```

未来采购/委外供给只用于预计齐套与净需求，不直接进入立即可生产量。

### 3.2 占用和清料

```text
占用有效量 = qty - consumed_qty - released_qty >= 0

累计审核领用
= 已确认耗用
+ 已验收良品退料
+ 已验收不良/报废
+ 审批损耗
+ 合法在制结转
```

任何红冲必须按原 posting 反向；不能靠重算当前 BOM 猜原来领了什么。

V161 进一步把四张生产物料事件/posting 表设为 append-only：已接受事实不能原地改或删，错误只能新增对应反向事实，避免审计、幂等和清料恒等式被历史重写破坏。

### 3.3 V160 临时覆盖

```text
自由库存池 = 账面可用 - 已生效占用 - 安全库存
按 仓库/货品/颜色 分区
按 需求日、计划、需求稳定排序依次抵减
采购建议 = max(需求未覆盖量 - 本需求取得的临时覆盖, 0)
```

临时覆盖只影响工作台建议，不是库存承诺；正式 READY 仍必须重新取锁并一次占齐。

### 3.4 并发与幂等

- 单据表头先 `PESSIMISTIC_WRITE`，上游和需求按 UUID 稳定排序。
- 库存按仓库/货品/颜色取得事务级 advisory lock。
- 相同幂等键 + 相同请求哈希返回同结果；相同键 + 不同载荷返回冲突。
- 任何中途失败整事务回滚，Outbox、库存、累计和审计不能各自成功一半。

### 3.5 销售分摊守恒

```text
Σ(某执行段的销售分摊量) = 执行段计划量
Σ(某计划销售 link 被各执行段冻结的分摊量) <= link 有效分配量
报工/入库累计 <= 对应执行段销售分摊量
```
