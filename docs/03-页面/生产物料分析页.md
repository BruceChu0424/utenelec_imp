## 一、员工看到的主流程

```text
已审核销售订单行 / 合法手工需求
  → 选择本次要分析的产品与数量
  → 勾选至少一个参与仓、明确主领料仓，再点「联合分析所选产品」
  → 完整 BOM 已加载；无直接 BOM 的当前层显示“无下层物料，可直接自制”
  → 有 BOM 时按父件实际短缺与路线激活下一层：BUY 停止、MAKE 展开、供料委外展开
  → 计划员逐路径节点确认 BUY / SUBCONTRACT / MAKE 并处理真实缺口
      ├─ BUY → 提交采购需求
      ├─ SUBCONTRACT（无子层）→ 提交委外需求
      ├─ SUBCONTRACT（有子层）→ 与 MAKE 同构；无论下层是否齐套，员工都可显式按
      │    全部实时余量创建 SUBCONTRACT_MAKE，缺料只决定后续计划进入 WAITING
      └─ MAKE → 可显式批量创建 MAKE_COMPONENT；下层缺料不再阻止 child 创建
  → child 不会由进入页面或刷新自动创建；创建后按精确 UUID/path 接管父树后代
  → 已存在的 MAKE child 与根产品可按剩余需求填写本批车间、负责人和日期
     ├─ 当前完整齐套：计划批准后形成 READY、完整预留和 DRAW
     └─ 当前未齐套：计划批准后形成 WAITING，零预留、无 DRAW，齐套后自动提升
  → 服务端重新预览并生成计划草稿，提交审批；页面不跳走
  → 计划批准后形成精确销售已排量；剩余未排数量继续保留在原物料分析
```

销售订单有 10,000 件需求而当前生产硬门槛物料只完整支持 1,000 件时，页面默认建议先排 1,000；也可整批排 10,000 并冻结同一车间/负责人，由服务端拆成 1,000 READY 与 9,000 WAITING。只有 READY 批锁完整套料并生成 DRAW，WAITING 不占零散库存。若只排首批，未排余量继续留在原分析；采购、委外或 MAKE 合格供给到仓后继续按新增完整套数形成下一批。

物料分析生成正式计划时不自行写 `MA-UUID` 产品编号。计划服务先持久化带 UUID 的计划头和服务端计划单号，再由数据库为留空的计划行原子分配 `<计划单号>-NNN`；后续分批计划拥有不同计划 UUID/单号，因此不会复用前一批产品编号。来源追溯始终使用分析、需求行、销售订单行和计划行 UUID，不按这些可见编号反查关系。

从“新建生产计划”带入的显式产品编号只作为当前路由内的计划向导初值，不写入物料分析来源表；销售来源按销售订单行 UUID、手工来源按来源类型/来源编号/货品/颜色/单位复合身份匹配回正式分析产品。用户可在计划向导继续修改；非空值同时进入联合预览指纹和生成幂等指纹并原样交给计划服务，留空才由服务端自动分配。

物料分析、MRP 和执行分段使用的 BOM 节点必须已经维护当前 UUID：基本单位来自 `goods.unit_id`，颜色来自 `goods_bom_items.color_id`，未覆盖时才继承 `goods.color_id`。只有 legacy 单位/颜色影子、UUID 悬空或目标已停用时，在线预览、重算和下达均失败关闭，不在运行时按 legacy 整数补造 UUID；应先通过受控迁移完成回填与对账。`SHIP/REFERENCE` 虽不形成正式生产物料需求，也不能借此绕过当前 UUID 完整性门禁。

自制件仍按自底向上完成，但不再按自底向上**创建任务**。每个 MAKE 节点只以自己的直接子件判断齐套；计划员可在直接子件不足时显式创建 `MAKE_COMPONENT` child 并先排车间，审核后诚实进入 WAITING、零预留、无 DRAW。child 仍独立经历主仓齐套、DRAW 实发、报工、FQC 与仓库点收，合格入库后父级可完工量才上调。父树完整路径用于解释下一步，不能扁平为根计划一次领料；当前仍以 child 存在性表达整节点 ownership，没有任意分批 `delegated_qty`。

## 二、历史记录与来源选择

### 2.1 物料分析记录

历史页只读取服务端按负责人、部门和对象范围裁剪的记录，支持：

- 搜索需求编号、销售单号或产品；
- 按 `ACTIVE / PARTIALLY_PLANNED / COMPLETED / CANCELLED` 筛选；
- 按销售、返工、试制、样品、备库、其他或系统自制子需求筛选；
- 查看需求、已提交、已批准、待处理、可立即/按期数量；
- “继续处理”回到原分析 ID，不能用重新创建代替恢复。恢复后点“按最新库存刷新分析”时，前端自动用该分析已持久化的来源重算（从产品行重建销售/手工来源、跳过系统 `MAKE_COMPONENT`，与服务端 `requireSameSources` 排除 MAKE_COMPONENT 一致），无需重新选产品。

历史记录宽屏使用 `MasterDataTableView`，窄屏改为带状态、数量和明确「继续处理/查看」文案的卡片；搜索、筛选、分页和打开记录都是安全读操作，不改变业务状态。新分析候选的移动分页、多选与数量核对属于下一节，不得误写成历史记录列表能力。

### 2.2 新分析来源

- 销售来源只列已审核且仍有可排剩余量的销售订单行；支持勾选多行联合分析，不显示价格。
- 候选接口每页 100 项。桌面候选表使用表头三态复选框：空框=当前可选项全未选，勾选=全选，半选=已选部分；表头动作不改变不可选行或已失效行。手机候选卡固定显示 48dp 的「上一页/下一页」和「第 X / Y 页、共 N 项」，跨页选择保留。
- 单次最多 500 个分析来源，销售订单产品与手工计划合并计数；新增、表头全选和最终提交都执行同一上限，不能选满 500 个销售产品后再绕过前端加入手工来源。
- 手工来源只允许 `REWORK / TRIAL / SAMPLE / STOCK / OTHER`；必须填写稳定需求编号、原因、产品、数量和日期。
- `MAKE_COMPONENT / SUBCONTRACT_MAKE` 只能由服务端响应员工的显式 child 创建命令幂等生成；员工不能手工伪造，页面加载和刷新也不能自动生成。下层未齐允许创建，但后续计划审核必须进入 WAITING。
- 窄屏主页面使用单一滚动区，「其他需求（返工 / 试制 / 样品 / 备库）」默认折叠；已选销售产品只显示数量摘要和「核对数量」，点开独立 90% 高度惰性列表编辑，不在主滚动区嵌套最多 500 个输入框。
- 「加入分析」只把一条手工来源加入当前本地表单；勾选、搜索和本地数量编辑也尚未写业务事实。新建时真正持久化 analysis、来源和 BOM 快照的按钮是「联合分析所选产品」；已有 analysis 的刷新入口是工具提示「按最新库存刷新分析」，文档不得再虚构一个「开始/刷新分析」按钮。
- AppBar 标题是「物料分析准备」，次要入口依次为「备料汇总预览」「物料分析记录」「生产计划历史」。

### 2.3 下游单据的来源单号可读化（V292/ADR-038，2026-08-16）

- 分析下达生成的采购申请/委外申请：表头与明细的「来源单据」显示 `计划前物料分析 <分析日期>`（上海业务日），备注为「…备料任务自动生成」；不再出现 `物料分析-<UUID>`。销售谱系（「为哪些销售订单备料」）由服务端按分析 id 精确回溯写入 `salesOrderNo`，不靠字符串匹配。
- 生产计划路径生成的申请来源单据仍是计划单号（SJ…）；MRP 明细备注使用执行分段编号（ZX…），不写分段 UUID。
- 系统自制子需求（`MAKE_COMPONENT`）的来源编号为 `自制备料 <创建日> <4位尾码>`（尾码仅去重，满足全局唯一索引），历史记录页「来源/需求编号」列据此可读。
- 「剩余物料已可下达」通知文案只带业务单号（收货 CJ…/进仓 EJ…/成品入库 CR…），分析/单据 UUID 只做内部关联键。
- 历史数据由 V292 一次性清洗；`preplan_supply_actions.external_document_no` 的 MAKE 短码受 append-only 守卫保留原值，但不出现在任何界面。

## 三、分析详情的傻瓜式交互

### 3.1 产品与自制备料项

- 结果区顶部保留六个分桶入口：**可安排生产 / 暂不可安排 / 已转生产 / 可采购 / 可委外 / 待自制**。分桶只负责给计划员快速聚焦和显示权威计数；进入分桶后的批量操作与下方统一物料表调用同一组选中集、权限、CAS 和写命令，不形成第二套业务状态。
- 下方自研 `MasterDataTable` 是具体物料明细的主工作台。产品、MAKE child 和所有 BOM 路径在同一数据投影中展示；六分桶不再用大卡片重复铺完整节点信息。
- 产品排产资格只认服务端 `canSchedule / maxSchedulableQty / scheduleBlockedReason`。`readyNowQty=0` 的根产品或已合法创建的 child 仍可先选择车间、负责人、日期和本批数量；页面必须写明“待料可排产”，不得用齐套颜色冒充物料已备齐。
- 计划向导同时显示可排产上限与当前齐套量，并提供“先排当前齐套 / 整批排入车间 / 自定义”三种选择。本批数量超过当前齐套但不超过 `maxSchedulableQty` 时不是输入错误；明确确认后，齐套部分生成 `READY`，余量生成零 reservation、无 DRAW 的 `WAITING`。当前齐套为零时才是整批 WAITING；后续到料继续按完整套数拆批/提升。
- MAKE 与有子层 SUBCONTRACT 的 `lowerLevelPending` 是诊断信息，不再是创建 child 的硬门槛：
  - 路线已确认、操作组仍有真实余量且操作者有权时，可在“待自制”分桶、表格批量动作或行右键中**显式**创建 child；
  - 当前没有分批 `delegated_qty`，首次创建仍须按操作组全部实时剩余需求交接 ownership，部分委派失败关闭；
  - 页面加载、库存刷新、路线学习和定时轮询都不得隐式创建 child；取消计划向导也不撤销已经显式创建的 child。
- 已创建的 `MAKE_COMPONENT / SUBCONTRACT_MAKE` 不再作为第二个顶层 BOM 根或重复分桶卡出现。原父路径通过精确 `delegatedToAnalysisLineId` 显示关联 child；详情分层列出“已转自制需求 / 执行计划量 / 已完工入库”，计划深链仍受 `production_plan:view` 权限保护。
- 无直接 BOM 不是异常：当前层按直接自制处理，可排产但不生成空物料需求、空预留或空 DRAW。BOM 循环、超深、非正用量、停用组件、颜色/单位 UUID、包装计量或指纹异常仍失败关闭并显示具体原因。
- “调整物料优先顺序”只改变共享自由库存的分析模拟顺序，不创建正式库存预留；确认后才写服务端并重算。
- 准备、生产和完成必须分开：物料齐套来自主领料仓的合格库存与 exact entitlement；日报审核形成当前有效 `fqty`，FQC 决定质量资格，仓库实收才累计 `iqty`。生产完成率只按有效计划明细的 `Σ bounded(iqty) / Σ qty`，不能用齐套比例或报工量冒充。
- 同货多路径必须沿 `analysisItemId + nodeKey/path` 和 child UUID 精确关联；前端不得按货号、名称或裸 `requiredQty=0` 猜父子任务。

### 3.2 三个数量不能混用

| 页面名称 | 权威含义 | 是否证明当前完整齐套 |
|---|---|---:|
| 可开工（分析参考） | `START` 阶段物料当前可支持的数量，只用于看准备进度 | 否 |
| 可完工入库 | `START + ASSEMBLY + FINISH` 生产硬门槛完整齐套后的数量 | **是** |
| 预计可发货（参考） | 加上 `SHIP` 参考物料后可支持的提示量 | 否 |

`可开工/可完工入库/预计可发货` 的语义和服务端计算始终保留，并在表格状态、详情或计划向导中按需展示。它们回答当前物料能支持多少，不再充当“是否允许先排车间”的唯一门槛。

`readyNowQty` 是当前可完工入库的完整齐套量；排产资格和本批计划上限分别读取服务端 `canSchedule` 与 `maxSchedulableQty`。本批量可大于 `readyNowQty` 但不得超过 `maxSchedulableQty`；审核后只允许 `readyNowQty` 覆盖的完整批次进入 READY，差额进入 WAITING、零预留、无 DRAW，不能把未齐套差额伪装为 READY，也不能把已有齐套量一起冻结成 WAITING。

`SHIP/REFERENCE` 永远只是参考：不写正式生产物料需求、不占库存、不生成 DRAW，也不阻止生产计划或销售实际发货。生产过程确实消耗的纸箱、胶袋、说明书等必须在 BOM 中配置为 `FINISH`，并按 `PER_UNIT / PER_PACKAGE / FIXED_BATCH` 计算；不能把纸箱放在 `SHIP` 后再假装已经为生产预留。

### 3.3 BOM 层级表格、缺料与只读详情

- 统一物料表默认按**产品 / BOM 层级**展示，也可切换为**物料 / 路径汇总**。汇总只合并视觉阅读和公共池提示；选择、下达、取消和反向仍回到每条 UUID 路径 allocation，绝不合账。
- 表格每页 100 行并启用虚拟化，只构建当前页和必要祖先上下文；几百产品、几千节点时不得恢复整棵树卡片 `Column`、首次 30 产品增量卡或 60 产品卡片分页。
- 顶部支持“全部 BOM / 只看缺料 / 待确认路线”和产品/物料搜索。命中子节点时保留产品头与所有祖先，分别显示直接命中数和保留祖先后的可见数；祖先只作上下文，不计入选择或缺料数量。
- 第一列是紧凑身份行（2026-09-04 收敛）：`P几 + 名字` 同排一行、编号（货品编码）第二行，用 UtenTreeTableCell 的 `sequenceInline` 模式；不再显示 BOM 路径与「组件 N 级」文案，层级仍由缩进、连接线与级联序号表达，完整路径只在只读详情弹窗里展开。后续数量列保持纵向对齐，不用整卡左移、彩色色带或竖向 rail 挤压表格宽度。
- 表头提供列显隐、拖动排序和宽度调整；主表行支持双击详情、右键菜单（无勾选列——批量选择统一在分桶详情页）。右键至少包含详情、采用建议/更换路线、采用公共在途和当前可执行任务；菜单动作完成后清除上下文选择，取消菜单则保留原选择。
- 详情是只读解释入口，展示完整 UUID 路径、阶段、单位、有效预留、主仓库存、其它参与仓可调拨量、安全库存、未来在途、下游来源和关联 child 三项数量。打开/关闭详情不改变选择、路线、分析版本或业务状态。
- `requirementState` 必须区分 `ACTIVE / DELEGATED_TO_MAKE_CHILD / DELEGATED_TO_SUBCONTRACT_PREPARATION / INACTIVE_PARENT_COVERED / INACTIVE_PARENT_ROUTE / INACTIVE_REFERENCE / TRANSFERRED_TO_PLAN / INACTIVE`。委派状态显示精确 child 来源，不用一排零值代替原因。
- 缺口必须同时有数字、文字和状态图标，不只靠颜色。物料保障率仍按 `(requiredQty - demandSupplyGapQty) / requiredQty` 解释，但不再绘制旧卡片竖轨；生产执行百分比单独读取 child/计划的 `iqty` 投影。
- 主领料仓仍是 `readyNow`、reservation、DRAW 和 physical entitlement 的唯一仓库真值。其它勾选参与仓只展示“所选仓合计可用 / 其它仓可调拨 / 调拨后仍建议另补”，未完成受审计调拨入主仓前不提高齐套。
- 公共在途按 V472 显示“批准公共候选 / 尚可采用 / 已采用 / 预计日期”。同 SKU 多路径共用一个容量池，批量确认文案去重；来源单号和 UUID 还须通过 purchase/subcontract 对象范围。
- 分析内借用和跨计划让料只调整软分配或精确 entitlement 受益人，不直接写库存账本。详情保留双向数量、对方任务、原因、撤销资格和审计结果；正式预留后的调整继续走原计划释放/反向链。

> **历史，已被 2026-09-04 统一物料表覆盖**：2026-08-14 至 2026-08-30 的独立 BOM 卡、左侧色带、44px 竖向保障 rail、层级胶囊、完成态折叠卡、首次 30 产品/60 产品卡片以及卡内唯一动作，是旧 UI 演进证据，不再描述当前界面。其数量定义、UUID 路径守恒与 fqty/iqty 边界仍由上文现行规则继承。

### 3.4 统一物料表的路线确认、下达与 child 创建

1. 路线建议不是人工决定。计划员必须通过表格可见动作或右键明确选择“采用建议 / 更换路线”；偏离建议必须填写原因。路线写入使用分析 `version + fingerprint` 和幂等键，失败后保留可重试草稿，不静默采用。
2. 主表不提供勾选列；批量下达的行可入桶条件为：本批需求仍激活、未转交、仍有可执行余量、路线已保存、服务端 action group 有效，并同时具备客户端权限和服务端 `allowedActions`。不满足的行不进入对应分桶，未确认路线、脏路线、只读权限或陈旧快照在桶内行与状态列显示原因。
3. 对 MAKE 与有子层 SUBCONTRACT，`lowerLevelPending` **不得再禁用 child 创建**。它必须醒目说明下层缺料和后续 WAITING 风险，但路线与 ownership 条件满足后仍可在分桶、右键或行内动作中显式创建任务。
4. 批量勾选只发生在分桶详情页（本地选中集）；批量动作仍提交稳定的 `actionGroupKey/materialLineId`、精确数量与 CAS。超过 500 个任务时按稳定身份分块，后一块使用前一块返回的新版本；中途失败只恢复未完成选择，原块重试沿用同一幂等键。
5. BUY 与无子层 SUBCONTRACT 可分批提交真实需求；V472 起超量必须作为独立 `publicExtraQty/public_surplus_qty` 明示并要求 `production_material_analysis:over_supply`，不得写入本分析 exact allocation。MAKE 和有子层 SUBCONTRACT child 不允许公共超量。
6. MAKE / 有子层 SUBCONTRACT child 首次创建继续按全部实时剩余需求交接，保留父节点、child UUID、路径和 action allocation。创建完成后原父树后代只读，不重复通知、重复分配或重复生成 child；系统绝不在进入页面或刷新时自动创建。
7. child 创建后即可按 `maxSchedulableQty` 进入计划向导选择本批数量、生产车间、负责人和日期。审核时未齐套形成 `WAITING`、零预留、无 DRAW；齐套后再进入 `READY → 备料中 → 备料完毕 → 报工`。根产品同样允许先排车间。
8. 公共在途必须显式“采用”。例如 A 需求 500、批准采购 2000，只给 A 锁定 500、公共可采用 1500；B 需求 1000 可采用 1000，采用后公共余 500，也可以另行采购。采用要求 `production_material_analysis:claim_shared_future`、同主仓/物料维度/路线/交期和实时容量锁。
9. V420 公共安全库存补库与 V472 公共超量是两种不同切片。BUY 必须分别展示和回传需求量、安全补库量、公共超量；SUBCONTRACT/MAKE 遇安全库存缺口仍按既有策略失败关闭，不伪装为生产需求。
10. 已下达行可打开供给全链路进度：需求 → 下单 → 财务批准 → 收货 → IQC → 主仓入库/齐套；MAKE 走 child → 生产计划 → 报工 → FQC → 仓库实收。单号、负责人和 UUID 读取继续受对象范围保护。
11. 页面没有“标记已领料 / 生产中 / 完工”捷径。领料只来自仓库实际 issue，当前有效报工只来自审核日报 `fqty`，质量资格来自 FQC，最终完成只来自仓库实收 `iqty`。

### 4.1.1 多产品合单演进（设计结论，尚未实现）

当前代码与数据库合同仍是“一种自制件的一个执行批次一张计划单”：`generatePlan` 逐项创建计划，分析计划关联表又以计划头的单一 `material_analysis_item_id` 和 `UNIQUE(plan_id)` 约束来源。因此本轮不能只把前端卡片合并或把循环挪到外层；那会让报工、入库、MAKE 父路径和反向无法回答“数量属于哪个分析任务”。

为避免以后联合分析几十个产品产生几十个单号，第一阶段采用**共享计划头、独立计划明细**：同一安排组只生成一张 `production_plan`，组内每个产品/自制来源仍保留自己的 `production_plan_item`、分析行 UUID 和执行分段。员工只看到“已选 Y 个生产任务，将生成 X 张计划单”，默认自动归组，异常任务可移出；计划详情仍按清楚的大卡片逐任务展示和多选操作。这样减少单号、审批和打印数量，但不合并来源账。

首版自动归组必须至少同时满足：同一 analysis、目标仓、来源责任类、生产车间、负责人、班组、开始/结束/交期、审核意图，并设置稳定的单内明细上限；任一关键安排不同即自动拆单。一次合单意味着共同审批、取消和红冲边界，确认前必须明确提示本单含 N 个任务。

落地前必须以前向迁移完成精确来源链：给 `production_material_analysis_plan_links` 增加并回填 `plan_item_id`，移除 `UNIQUE(plan_id)`，让每条正数量计划明细恰有一条分析来源关联；V234/V247/V312/V313/V337/V426 等已应用迁移字节不可修改，只能在新版本替换其“计划头只有一个分析行”的守恒函数和服务查询。计划头旧 `material_analysis_item_id` 只保留历史兼容影子，不再作为新单权威来源。分组预览、幂等哈希、审批锁、权益正式化、WAITING 唤醒、MAKE 进度和本页进度都必须改为沿 `segment → plan_item → analysis link` 精确回溯。

“相同货品直接合成一条物理计划明细”属于第二阶段，首版禁止。它还需要不可变的 `execution_segment → analysis allocation` 分摊，才能将报工、FQC、成品入库、MAKE 父路径和反向精确回写；`PER_PACKAGE / FIXED_BATCH` 等非线性 BOM 还必须按合并后的数量重新计算，两个 5 件批次不能假定等于一个 10 件批次。未完成这些门禁前，只允许同货品在一张计划内视觉归组，不得吞掉独立任务 UUID，也不得恢复历史 `/production/schedule/merge-plan` 货号级合并入口。

该演进需分别验收：非空库无歧义回填；同组 3 产品形成 1 头/3 明细/3 来源关联；不同仓/车间/人员/日期自动拆组；多销售来源与 MAKE 多父路径守恒；部分完工不提前关闭整单；取消、反向、并发重放与 20/50/500 项性能。上述迁移、服务、页面和 PostgreSQL/岗位 UAT 未完成前，合单仍是 **NO-GO**，当前运行时继续按独立计划生成。

### 4.2 生成后的计划详情

计划详情不再重复提供旧“物料需求只读估算（MRP）→预排/补建正式计划包”入口。分析生成事务已经保存计划草稿与 ACTIVE planning draft；批准应用该草案并冻结执行段。详情只读展示：

- 当前层直接物料需求、reservation、DRAW 与仓库实际发料进度；
- `ZERO_MATERIAL / DIRECT_MAKE` 的正常无领料状态；
- 真实 MAKE child 计划及其各自的领料、开工、报工、FQC 和仓库点收入库；
- 历史 `PLAN_BOM_OVERRIDE` 冻结证据，只读、不可新建或再次授权。

计划详情物料表为空时，必须先看执行段物料形状：合法 ZERO_MATERIAL 显示正常说明；遗留计划缺分析事实时引导回物料分析准备重新生成。两者都不得显示“该产品要求 BOM，但未维护有效 BOM”。

### 4.4 默认车间只使用 V192 偏好

- 默认车间的唯一权威来源是 V192 `production_goods_workshop_preferences`，不是 `goods.default_workshop_department_id`。V253 只建立官网询盘表，**不是生产迁移**；当前头 V392 也没有建立第二份默认车间真相。
- 向导打开时按 goodsId 批量读取 V192 偏好并预填；没有可用偏好的组件进入「未分配车间」清单，必须由计划员在本次向导补齐后才能提交。
- 客户端按最多 100 个 goodsId 分块读取偏好，避免 UUID 查询串逼近代理 8KB 请求行；服务端上限不是前端必须用满的分页尺寸。
- 学习发生在生产执行段正式确认，以及后续合法改派车间时；仅保存草稿、打开向导、拖动排序或取消不学习，避免误填污染后续预填。
- 本次手工修改车间必须继续用于本计划的组织、班组和人员校验；只有正式执行确认/改派后，V192 才更新 `selection_count` 与最后选择事实，供后续向导预填。

未勾选 approveNow 时走普通 generate：创建计划草稿、`ACTIVE` planning draft 和 `SUBMITTED` plan link，不直接批准。生成成功后回到/留在当前分析页，行状态刷新为“计划草稿待审”，显示计划号和“查看计划”；员工可以继续处理其他节点。

具有 `production_plan:approve` 的人员仍从权威审批入口批准。批准成功后按当前完整套料形成 READY 或 WAITING，并写精确销售已排量；只有 READY 形成完整库存预留和 DRAW。多选生成默认整批原子成功或失败；任一库存、版本、指纹、BOM、组织或数量变化都使整批失败并要求刷新，不能静默部分成功。
