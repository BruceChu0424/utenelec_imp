# V568 让料后的自制补供责任

日期：2026-09-12。本文记录V568源码规则与当时隔离证据；实际环境迁移、部署及岗位验收状态另记，不以文档同步代替执行回执。

原物料已自制完成10件，再显式让出4件后，原需求仍为10，实物覆盖变为6。旧车间候选只复用已存在的子件锚点，其剩余待排量为0，因此采购能继续补4，自制却找不到合法新增责任入口。直接按物理缺口扩大旧任务会造成刷新和重试重复生产。

V568 增加追加式 `preplan_reallocation_make_supplements`：每次增加责任明确关联让料 UUID、原物料 UUID、同一子件 UUID、本次让料补供量，以及子件需求前后数量。原父BOM需求仍为10；原计划、报工、品质及完成入库10的历史不变；既有子件可明确追加4，后续形成新计划。

新增权威字段 `priorityMakeSupplementQty` 只对已有真实自制/委外前置子件、来源方仍有未补让料的节点提供额度。数量同时受未补让料、原让料量减累计追加责任、当前物理需求缺口减有效在途和既有自制未完成责任限制。普通缺料和无让料事实均不会触发旧锚点增量。

MAKE 继续从“下达车间”调用原子 `issue-plans`：按权威额度追加子件责任并记事实，再按本次填写量生成计划。可以先排一部分；剩余留在原子件待排。重放原请求返回原计划，新请求或刷新也不能再把已经追加的4加一遍。取消尚未执行的补做计划后，子件待排余量仍可重排，不能再追加同一份责任。

委外原有通知接口 `POST /api/production/material-analyses/{id}/notify` 仍按真实缺口扣有效供给后建立下一代行动，叶子委外不会因旧DONE被阻断；有子层委外继续复用原前置自制子件和任务，其增量属于让料补供时补记相同证据。新字段不会替代或关闭原先合法的委外数量流程。

若已有补供证据、子件还有新增待排量，而旧计划汇总是COMPLETED，当前子件汇总派生为NOT_STARTED；历史计划链接的已完成状态、数量和时间全部保留。

数据库守卫验证来源关系仍OPEN/PARTIAL、同分析/物料/颜色/单位、精确既有子件、真实请求量增量、单笔不超未补、累计追加不超实际让出量。证据与审计触发器始终启用，禁止修改和删除事实。新表纳入 `business_data_reset()` 的CLEAR分类，主档、员工和审计保护不变。


真实业务链进一步发现并修复两处下游边界：自制实入库原来仍以父物料10减历史已归属10计算为0，补做4落为公共库存。现由同一数据库函数读取父需求加本child/本物料的补供证据上限，Java与数据库exact守卫同源；仍不能超过本次真实成品入库行数量。原A权益最终恢复10、B保留4，父需求不增为14。

有子层委外复用任务时，原查询把单列UUID作为Object[]读取而失败，现按UUID读取保留原任务。旧前置H10已最终委外回厂，再补H4时，旧L10已领用也曾错误遮住新增L4。对有补供证据的委外前置子件，分析按同child和原BOM节点约束共享覆盖：保留已正式预留尚未完工的数量及已前置制造但尚未最终合格回厂的数量；真实已回厂部分退出旧原料覆盖。最终回厂量按原委外申请/订货来源分摊与实入库事实读取并扣实际退回，不以让料后的当前受益量猜测；不修改或释放历史库存预留和实际耗用。


调料成功后的补供弹窗使用只读预览：`GET /api/production/material-analyses/{sourceId}/cross-reallocations/{reallocationId}/replenishment-preview`，或以成功命令的当前操作人及幂等键查询 `/{sourceId}/cross-reallocation-replenishment-preview?idempotencyKey=...`。预览返回原供料分析A最新快照、精确物料、原调用量、该笔仍待补量、扣已有供给后的可新增量、默认量、当前合法路线、具体操作与公共超量权限。接受计划B不能作为补供归属；不按名称、数量相等或最新排序猜关系。

打开预览不创建采购、委外或车间任务；取消补供不撤销已经成功的调料。提交仍走原 `/{id}/notify` 或 `/{id}/issue-plans`，保持版本、指纹、幂等、权限及库存状态复核。BUY/叶子委外可将“原计划需求q”和“公共extra”分别提交，超量权限不足时不得开放extra；MAKE/有子层委外只承接净补责任，额外公共制造必须另走完整BOM备库计划，不能扩大原父需求。员工入口见[生产物料分析页](../03-页面/生产物料分析页.md)；公共/专属在途是另一来源范围，见[V569基础与V571前向补齐](165-V569在途供给归属调整.md)。
