# 物料分析数量与规模验证（2026-09-20）

本记录区分业务正确性、SQL/协议体积和隔离环境时延。源码与数据库迁移的验证不能替代最终提交 CI、公司数据库恢复演练和安装后验收；发布证据另行记录。

## 数量和状态合同

- 委外前置生产二次安排先消耗原任务尚未安排量。仅超出原任务余量与本次真实新增需求的部分进入公共增产；从物料候选入口和已生成生产锚点入口进入时使用同一计算。
- 只有公共增产的操作可能没有需求分配行，任务公共量必须按实际操作的外部任务 ID 汇总。撤回同时减原需求与公共量，不能减穿仍有效的计划承诺、已生产量或已通知量。
- `externalFutureCoverageQty` 与 `internalCommittedOutputQty` 分开提供给逐层计算。外部在途可覆盖本层需求；内部委外/制造承诺仍可能需要其子件。两者均不冒充合格实物或 READY。
- 同货品不同 BOM 路径可以各自确认 BUY/MAKE/SUBCONTRACT；同批路线混合时保留原主档默认，同批一致才学习主档，避免请求排序决定默认值。

`MaterialWorkshopAnchorEndToEndTest` 覆盖部分安排、二次安排、超量、撤回、纯公共操作、两父路径同货分配、路线顺序与并发旧版本；未来供给测试继续覆盖公共/私有来源、真实到货与反向。V621 只基于不可变操作和有效计划事实修复任务投影，事实无法自证时拒绝迁移并报告对象。

## 大响应与批量路线

`shared-material-defaults-v2` 保留全部字段、精度、空值与权限；显式共享默认字典，材料列表由原对象直接流式输出。旧客户端继续使用原表示或 v1，客户端须明确协商 v2。合同详见[响应协议](../05-架构/物料分析响应协议.md)。

在同一个已生成快照上交替进行三次序列化，不保留整个输出体，测得：

| 来源数 | v1 字节 | v2 字节 | v1 中位序列化 | v2 中位序列化 | v1/v2 线程分配字节中位数 |
|---|---:|---:|---:|---:|---:|
| 100 | 28,246,604 | 10,542,714 | 268.65 ms | 290.48 ms | 4,482,288 / 3,720,488 |
| 500 | 141,499,622 | 52,998,506 | 644.29 ms | 323.43 ms | 22,438,088 / 17,093,888 |

未压缩响应减少约 62.5%；100 来源的 CPU 中位数没有改善。5 ms 堆采样受 GC 影响，不能当成精确峰值。这里不包含网络、HTTP 缓冲、gzip 和 Flutter 解码；即使压缩后，500 来源约 53 MB 仍属于大响应。

批量路线写者完整验证范围、路线与已下达限制后，集中读下游事实并按 PostgreSQL UUID 顺序锁主档，用有类型的记录集更新。500 行路线在 100 来源测试中的 JDBC 调用从 1194 减至 170，在 500 来源中从 1349 减至 325。相同路线不改写确认人/时间。共享主机的时延波动较大，这一结果只证明消除了逐行 SQL。

## 提交期完整性与无变化快照

100 来源、20 计划的提交期诊断发现旧执行段守卫 1660 次调用内部重复求值单需求函数 43160 次。V622 将这些事实按执行段集合化，保留每次完整校验与全部约束：同规模事务提交由 24.26 s 降至 7.24 s，总服务调用由 71.20 s 降至 42.57 s。独立差分、主动错误 SQL 变异与正式 Flyway 621→622 合同验证见[迁移说明](../数据迁移/212-V622执行段物料覆盖集合校验.md)。

500 来源仍存在大量无变化刷新输入。真实影响行计数确认结构 upsert 194 次、配给 UPDATE 194 次全部为零 DML。刷新局部基线只比较与原 SQL `IS DISTINCT FROM` 相同的结构及数量字段，在生成 JSON 和发出 SQL 前省略这些无变化行；新节点、重激活节点或结构变化仍执行原 SQL。完整需求/库存计算、实际发生的 DML、审计与提交约束均保留。

`MaterialAnalysisStructureScopeEndToEndTest` 以真实独立连接验证：无变化节点不必锁 tuple，但批内其他事务改变原快照时闭合校验必须整批回滚；库存变化仍进入新配给。`MaterialAnalysisAllocationSnapshotPostgresTest` 对原子字段、范围/active 谓词、等待后重查及执行计划作真库验证。旧确认节点失活后重加且 BOM 改量，仍清除旧确认并准确报告重置数量。

动态来源查询仍在每次发现时重新读取商业/执行事实。单个分析头的主仓解析和全行哈希在 `MATERIALIZED` 头集合中计算一次后再联接来源行，避免每来源重复计算相同头值；原 UUID、行哈希、空行与排序保持一致，不能把这项优化扩展成缓存动态来源。

## 最终 500 来源端点预算采样

最终代码在专门协调的独占验证窗口运行同一 500 来源、49,000 个 BOM 节点、20 计划方法：其余 Maven/Flutter 重任务已停止，保留原开发库和公司恢复副本。保持默认数据库参数、实际事务和全部约束；没有扩大普通接口的 45 秒等待预算。

| 项目 | 结果 |
|---|---:|
| 服务调用，含真实事务提交 | 29,250.82 ms |
| v2 回执流式序列化（先于旧协议诊断） | 415.17 ms |
| 服务调用加 v2 序列化 | 29,665.98 ms |
| 事务提交 | 2,009.18 ms |
| JDBC 调用 / 累计等待 | 4,245 / 21,322.10 ms |
| v2 未压缩回执 | 54,701,876 字节 |

快照 upsert 与数字 UPDATE 原先 388 次零 DML 调用均不再发出。执行段完整性守卫仍调用 1660 次（自身约 797.49 ms），审计函数仍调用 3304 次。主仓函数从原 43,502 次减至 89 次（33.70 ms）；动态来源发现仍执行 87 次，新的头部投影查询总计约 937.75 ms，没有把这些动态发现省略掉。剩余最大的 SQL 成本是两次 BOM 业务展开约 2.82 s、八次完整物料结构指纹读取约 2.78 s，以及 BOM 合法性检查约 1.69 s。

本表 54.70 MB 是完成下达后的 `GenerateResult`，包含变化后的分析与 20 个计划摘要；前表 v1 141.50 MB / v2 53.00 MB 是下达前读取快照的成对对照。两组材料/执行状态不同，不能把 54.70 MB 当成同一快照的体积回退，或混用它们计算压缩比例。

该样本的服务加序列化在 45 秒内，有约 15.33 秒余量；真实 HTTP 写出、gzip、网络和客户端处理没有包含在此值，且数据库 `fsync=off`，因此仍不是目标部署的端到端承诺。独占之前共享主机的同功能采样曾为 58.35 s，保留该结果以说明负载敏感性。正确性断言验证 20 个计划及各物料需求完整守恒、未虚增实物库存或销售完成量，测试 1/1 通过。完整 JSON/日志为本地验证产物，最终发布仍需新提交 CI 与服务器验收。

## 环境和复现边界

规模测试入口为 `ProductionMaterialAnalysisScalePostgresTest`，同时设置 `UTEN_RUN_DB_TESTS=true` 与 `UTEN_RUN_PRODUCTION_STRESS=true`，分别运行 wire 对照或 `profileWorkshopIssueDeferredFunctionsInAnIsolatedTransaction`。测试保持真实事务、正式迁移和触发器；函数统计只在被测事务内 `SET LOCAL track_functions=all`，提交后验证恢复。

本轮默认容器为 PostgreSQL 16，`shared_buffers=128MB`、`work_mem=4MB`、`max_connections=100`、`fsync=off`、`synchronous_commit=on`。存在其他 Maven/Flutter 验证竞争，测试宿主资源也不等于公司服务器。禁止据此承诺部署 SLO，或用延长客户端超时替代端点预算验证。HTTP 测量必须用真实 URI query 参数并断言回包协议；早期只给 MockMvc 参数表赋值的“shared”采样已排除。
