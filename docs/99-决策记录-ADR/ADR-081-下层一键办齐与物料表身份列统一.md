## 一、背景

ADR-080 的「明确不做」表里留了一项：**父件行「一键办齐子层」批量编排**，理由是「把确认路线 + 调入 + 三桶下达压成一个事务要同时穿过三条各有校验的下达路径，任一行失败需整体回滚，与本轮正确性改动同批会放大回归面。单独排期。」

现在把它做了，但**不按当时设想的「一个事务」做**——见第三节。

用户口径（2026-09-14）：

> 下达车间可以填写超过需求的数量，然后它会自动分析子层级有没有被下单了，没有就显示弹窗，里面按 BOM 列出来，跟物料分析准备页面那个样式；最上面是点击下达车间的那个件，下面是子层级、孙层级；根据最上面的层级自动把下面的层级下单数量都填了，也支持修改；然后可以一键下单：采购自动下达采购，没有子层级的委外自动下达委外，有子层级的委外自动添加到下达车间然后自动下达车间。

同一轮还给了一组表格统一口径，见第四节。

## 二、为什么非做不可：超量下达把下层需求算漏了

V577 / ADR-070 §2.7 让下达车间的本批数量可以超过剩余需求，超出部分记 `plan_links.public_surplus_qty`。但那条决策同时钉死了一句话：**超出部分不会自动扩大下层物料需求**——锚点行本就不展开自己的 BOM，父件计划产出也按物理缺口封顶（ADR-080 §3）。

于是出现一个真实缺口：计划员按 20 下达（需求 10），服务端快照里下层还是按 10 算的需求，多做那 10 个的料**没有任何界面告诉他要补**。原文写的是「多做那批的料由计划员另行安排」，实际就是让人自己拿计算器按 BOM 乘一遍。本决策就是把这件事接过来。

## 三、决策

### 3.1 展开口径：按本批数量算毛需求，按服务端口径算余量

下达车间成功后，对本次下达的每一行按 BOM 自顶向下展开（最多 10 层、300 行，超出明确截断不静默）：

```
毛需求(C)   = 本批数量 × C.perProductQty ÷ 驱动件.perProductQty
超产额外量  = max(0, 毛需求(C) − 快照需求(C))
建议下单(C) = 还可下达(C) + 超产额外量
```

- `perProductQty` 是「每 1 个来源单位产品」的累计单耗（`MaterialAnalysisBomSnapshotReader` 的 BOM 递归 CTE），顶层产品行除数取 1、候选/锚点行取该节点自己的 `perProductQty`。缺单耗的历史行不硬凑比例，退回快照需求并在状态列标明「未按本批放大」。
- 「还可下达」= 既有的 `_residualSubmitQty`（服务端口径：本批缺口 − 已在途），**不是**另算一套。没有超量时超产额外量为 0，建议值与各桶的默认下达量逐字相等——这是本设计的自检点。
- 展开只穿过自制与「有自制子层的委外」节点；采购节点与无子层委外节点下单即止，不再往下展开（与服务端「上级路线不是 MAKE/SUBCONTRACT 就不展开本节点」同向）。
- 本批一起下达的行互为「已安排」：同时下达 P 和它的自制子件 C 时，C 以下的料由 C 自己那条种子驱动，不被 P 的数量重复展开。
- 同一提交单元（`actionGroupKey`）在树里出现多次时，只有第一处可填数量（毛需求合并累加），其余行保留为层级上下文——提交单元是 actionGroupKey，一个单元只能有一个数量。

### 3.2 「有没有被下单」由服务端口径判定，不靠界面猜

`还可下达 ≤ 0` 即视为已下单 / 无需再下单：这类行在弹窗里只读显示，不可勾选。全部下层都如此时**不弹窗**。

已下单但因超产还差一截的行（`还可下达 = 0` 且超产额外量 > 0）如实写明「已下达；多做的 X 需回对应桶按富余量下单」——不假装能在这里补。原因：`_isExecutableSupplyGroup` 要求该组仍有可提交余量，已有未撤销下游行动且余量归零的组不在可执行集合里，硬塞进去只会被服务端拒；放宽这道闸会影响三个桶的成员判定，不在本轮范围。

### 3.3 一键下单 = 有序编排，不是一个事务

四段依次执行，每段复用既有链路（各自的数量裁决、分批、幂等键、CAS 与 409 恢复）：

1. **确认路线**（`PUT /routes`）——只针对表内显示路线与已确认路线不一致的行；
2. **下达采购**（`POST /notify` target=BUY）；
3. **下达委外**（`POST /notify` target=SUBCONTRACT，只含无自制子层的行）；
4. **下达车间**（`POST /issue-plans`）——自制行与**有自制子层的委外行**一起，一次原子调用：服务端在同一事务里为委外行走 `notifySupply` 建前置自制台账、为自制行建锚点，再逐行出计划、按权限同事务审核（ADR-071 §2 既有能力，本轮零后端改动）。

**明确不做一个事务**：ADR-080 拒绝的理由没有失效——三条路径的校验、幂等命名空间与回滚边界各不相同。改为**有序编排 + 逐段如实回报**：任一段失败立即停止后续段，弹窗列出「哪段成功几行、停在哪一步」，已成功的段保留在服务端（幂等键可回放，重试不重复建单），表内数量按最新快照重算后留在原地供重试。不会出现「说成功了其实只做了一半」。

### 3.4 数量可改，改上层带动下层

每行下单数量可改。改动某个**下达车间去向**的行时，它下面那些**用户没有手工改过**的行按新数量重算（`新毛需求 = 新数量 × 子件单耗 ÷ 本行单耗`）；手工改过的行不被覆盖。初始填充一律由最顶上那次本批数量驱动。

### 3.5 权限与超量

- 采购 / 无子层委外行超过「还可下达」的部分走既有公共超量通道（`toInput` 把数量拆成 `qty` 归本需求 + `publicExtraQty` 公共备货），**需要** `over_supply` 权限；没有该权限时建议值按余量封顶，并在状态列写明「超产多需 X，无超量下达权限未计入」——不静默改小、也不假装能下。
- 下达车间去向的行按 V577，本批数量本身可超量，**不需要**额外权限。
- 路线未确认且**主档来源为空**（`_draftRoute` 只能兜底委外）的行不允许在这里替人确认，状态写「主档来源为空，请先在主表确认路线」。有主档建议 / 上次记忆 / 已确认值的行才允许随一键下单一并确认——弹窗逐行显示路线、提交前二次确认点名「其中 N 行会先确认路线」，仍然是人明确确认（ADR-070 §2.3 不变）。

## 四、物料表身份列全站统一（同批用户口径）

1. **主表第一列拆成四列**：`物料名称 / 编号 / 颜色 / 单位`，顺序固定，其余列不动。原来编号·颜色·单位挤在身份格副行里，同名不同色/不同单位的行分不开，也没法各自排序筛选导出。列头由「产品 / BOM 层级」改名「物料名称」。取值优先级与原副行逐字一致（编号、颜色以产品行自身为准；单位以物料行为准——根供给行记的是基本单位）。
2. **级联号 P1 / P1.1 下线**：层级已由缩进 + 连接线表达，名称前再挂一串编号只是把货品名挤到后面。`UtenTreeTableCell` 的 `sequence` 传空串即不渲染徽标（其他宿主传非空仍照旧）。
3. **叶子圆点下线**：`showLeafMarker: false`（新参数，默认 true 不影响货品 BOM 宿主）；占位宽度保留，各层级名称仍对齐。
4. **层级连接线明暗对称调**：原来两种明暗都取 `outlineVariant`，白底上几乎与表格网格线同色。改为 `onSurfaceVariant` 按明暗两档——浅色 0.70（看得出层级走向又不抢名称），深色 0.40（深底上线条本就更跳，压下去才不刺眼）。
5. **三个入口的表格与主表同一组身份列**：`下达采购 / 下达委外 / 下达车间` 详情的第一列仍是「物料办理（物料 / 调拨）」，随后接同一组 `物料名称 / 编号 / 颜色 / 单位`。规格没有独立列，保留在名称格副行。
6. **「建议下单」列改名「下单数量」**（`materialToSupply`）。

## 五、供应方式就地改，改完自动换桶

三个入口的详情表都加「供应方式」列（与主表同一个下拉）。改动后弹确认框点名「本行会从 X 桶移到 Y 桶」，确认即写一次路线确认（`PUT /routes`），行随之离开当前入口。

- 桶归属只认服务端的 `confirmed_route`，所以「换桶」必须真的写一次确认——这不是自动保存：仍然是人在弹窗上明确点确认（ADR-070 §2.3 的「由人明确确认」不变），主表那条「改下拉 → 勾选 → 确认路线(N)」的批量通道也原样保留。
- 已有未撤销下游行动、被排产阻断或无路线权限的行只读显示，不给下拉。
- 确认后的路线**同事务回写货品主档 `goods.source_type`**，下次分析的建议路线直接读主档带出(2026-09-16 改版，见 [ADR-070](ADR-070-物料分析分桶详情页与三处学习记忆及超量下单.md) §2.3「2026-09-16 修订」；原按历史分析推导的「货品 + 颜色 + 单位」记忆 `/last-routes` 已整套退役，存量由 [V598](../数据迁移/189-V598货品来源按路线确认历史回填.md) 回填)。

## 七、修订二（2026-09-14 同日）：弹窗前置 + 已下单子件

用户口径：「就是有子类的点击父类下单，然后就会出现个弹窗，点击下单就会连通父类子类一起下单——现在被改错了，先把父类下单了才弹窗」；「子层级已经下单了：采购收到但还没下单的可以直接修改对应的数量；已经下单了的问是不是追加，选是追加就对应的采购那里收到追加」。

### 7.1 整页前置：先进页、一键下单里才提交父件

原实现是「分桶页提交成功 → 再弹下层办齐」——用户在弹窗出现前父件已落库；第一轮修订先改成 AlertDialog 弹窗，用户随后口径「不要弹窗了直接去新的页面，弹窗看的东西太少」，终版为**整页**（Scaffold + UtenAppBar + 右下悬浮动作组，与分桶详情同款页面范式）。要点：

- 车间桶「创建生产计划」与**委外桶有子层行的「下达委外」**在提交前先构建下层行：有可勾选行 → 直接进入「下层还没下单，跟父件一起办」整页（树顶显示「本次将下达 X」）；没有 → 按原路直接提交不打扰。
- 页面名称列换**与准备页同款的树组件**（`UtenTreeTableCell`：缩进 + 层级连线明暗两档 + 展开/收缩粗箭头 + 未展开子数徽章，「BOM 层级」列退役）：树结构由扁平 DFS 行序推导（子树范围 / 各层祖先连线 / 末位标记）；展开/收缩只切换可见子集（`UtenEditableGridController` 新增 `swapRows`——不 dispose 的视图级换行，行对象与已填内容不动），折叠行的勾选随之撤掉，**看到的勾选 = 提交的内容**；整页上下滚动正常（弹窗时代的「不能滚动」随之消失）。
- 「一键下单」的第 0 段是**父件段**：静默执行分桶页收集好的那次提交（车间 `issue-plans` / 委外 `notify`，silent 跳过结果弹层，由弹窗统一汇报），成功后**按最新快照重建下层行**——父件提交会让快照整体换一份，提交前抓的行对象立即过期；重建继承用户已填数量 / 车间 / 负责人 / 勾选，被父件顺带办妥的行（如委外前置自制任务接手的子件）自然退出并在结果里点名「已随父件下达办妥 N 行」。父件失败即停，下层未动。
- **失败重试不重发父件段**：首次提交后快照已换版本，重发等于新幂等键真实重复下单。弹窗记 `_parentSubmitted`，重试只办剩余段。
- 委外桶种子驱动量取全量剩余（有子层委外 notify 不可改量的 2026-09-06 守恒决定不变）；无子层委外是叶子，构建不出下层行，自动走原路。

### 7.2 已下单子件：并入申请调量，或问过追加另立

`还可下达 = 0` 且本批超产又有新量的行不再「只读让人回对应桶」：

## 八、修订三（2026-09-14 晚）：全量审计后的收口

用户口径：「ui 也都不对，特别是表示层级的竖线；icon 按钮有些按了没反应；新页面里父类应该默认没有多选框；里面很多数据都没有显示；各种情况都要考虑到。」

对本页做了一轮 11 维度全量审计（数量口径 / 树形 UI / 列数据 / 勾选 / 失效按钮 / 编排 / 入口种子 / 后端契约 / 边界异常 / 可用性 / 测试文档），确认 108 条。以下是改动与口径变更，**凡与前七节冲突的以本节为准**。

### 8.1 三条会真下错单的缺陷

1. **委外入口的父件段永远报失败**：`_executeBucketAction` 的 buy / subcontractOnly 两支丢掉结果直落末尾 `return false`——那是「要不要关掉分桶页」的旧语义，而 §7.1 的父件段拿同一个返回值判「父件成功没有」。于是从「下达委外」进本页时，父件明明已经提交，编排却一律报「父件未提交成功，下层未动」，下层一行都下不出去。改：返回值收敛为**本次命令是否提交成功**，「关不关页」由 `_run` / `_submitWithCascade` 按 `request.type` 自己决定（采购 / 委外仍留在本页，只有下达车间成功才退出）。
2. **改树顶数量把下层算小 unitRate 倍**：重算时除数取了树顶所挂 ROOT_SUPPLY 行的 `perProductQty`，而那个值是销售换算率（`COALESCE(sales.unit_rate,1)`）。建表时用的根本不是它（顶层产品=1）。销售单位是「箱」而基本单位是「件」时，一改树顶数量，整棵下层需求缩水 unitRate 倍，界面无任何提示。改：一律取建表时存下的 `parentPerProduct`。
3. **委外种子用错基数**：委外桶的「下达数量」框可编辑（`_notifyRoute` 的 `allowOverDemand` 对 BUY / SUBCONTRACT 都成立，超量需 `over_supply`），但种子 `batchQty` 写死取 `_residualSubmitQty`，且 `_patchRequestWithSeedQtys` 只处理「创建生产计划」。结果：用户在委外桶改大数量，下层按剩余需求备料；在本页改树顶数量，父件仍按老数量提交。改：种子取**本次真正会提交的数量**（表里填了就用填的，否则回落 `_defaultSubmitQty`），补丁对两条入口都生效。**§7.1 末句「委外桶种子驱动量取全量剩余」作废。**

### 8.2 「已下过单且已分解」的行不在本页下单（§7.2 ORDERED 分支改口径）

这类行的提交单元在分析侧已不可执行（`_isExecutableSupplyGroup` → `_hasSupplySubmitQty` 为假：residual=0、非根行、已有未撤销同路线行动）。原先放它们走 notify 超量通道，两种结局都错：该段只剩这类行时 `_notifyRoute` 拿到空组，弹一句「请先勾选要提交的采购缺料」并整段停下（**而父件已经落库**）；该段还有正常行时它们被静默丢掉，却按 `batch.length` 报成「下达采购 N 行」。

改：该行**不可勾选**，状态列写明「请到采购 / 委外模块对该单追加，本页不下单」，确认弹窗单独点名本次不含它们。要让「本页直接追加」成立，需服务端给公共备货另开一条不吃 `actionable` / `_hasSupplySubmitQty` 的通道（`MaterialAnalysisCommandService.selectedGroups` 与 `_hasSupplySubmitQty` 同时放行「demandQty=0、只提交 publicExtraQty」的组）——**本轮明确不做**，属未做项。

### 8.3 逐段如实回报（编排层）

- 采购 / 委外段先按 `_executableSupplyGroups` 算出本段真正能提交的行，`count` 用它而不是勾选行数；被丢掉的行点名。
- 行内数量只能按 `actionGroupKey` 传，缺这个键的行服务端会回落「全量剩余」——当面说明「填的数量未生效」，不再无声换掉。
- 「并入已有采购申请」逐行串行且**不回滚**，失败时逐张列出已经改大的申请单号，避免重试重复加量。
- 父件提交后掉出集合的行区分「随父件办妥」与「被挡住没办成」，后者立即停下并点名，不再整页报全绿。
- 一键下单期间 `PopScope` 拦住系统返回 / 手势；树顶数量框置灰；默认车间与申请联动加载期间提交按钮禁用并显示「正在载入默认车间…」。

### 8.4 UI 与数据（用户直接点名的四项）

- **层级竖线**：`UtenTreeTableCell` 的连线改为独立浮层，高度跟随整格并按宿主纵向内边距（新增 `guideBleed`）上下溢出，行间不再断成虚线；祖先竖线索引修正为「槽 k 对应深度 k+1 的祖先」（原先整体错开一格，depth≥2 画在错误的层上，**准备页主表同样受益**）；肘线横段延伸到展开位圆心；多棵树平铺时树与树不互认兄弟（新增 `treeIndex`）。
- **父类没有多选框**：`UtenEditableGrid` 新增 `showRowSelection`，返回 false 的行**整格不渲染 Checkbox**（只留空位保持列宽对齐），而不是画一个禁用的灰框。树顶行与合并上下文行都用它。
- **按了没反应**：车间 / 负责人格的点击条件由 `row.selectable` 改为 `_canAssignWorkshop`（本行确实要下车间、未被阻断、不在提交中）；不可点时不再显示「点击选择」，改灰底 '—' + tooltip 说明原因。截断提示、列设置持久化、全部展开/收起入口一并补上。
- **数据没显示**：列从 12 扩到 15–17 列（见 §3.8 的「列与数据」条），树顶行不再一片 '—'，合并行显示本支贡献量，状态列加 tooltip 且筛选值改用阶段桶。

### 8.5 其余口径修正

- 树顶数量清空 / 填 0 时种子归零并当场拦下提交（原先保留旧值，按界面上根本不存在的数量提交父件）。
- 折叠撤掉的勾选在展开时**原样恢复**；用户手工取消过的行由 `_userDeselected` 记住，重算 / 重试都不替他勾回。
- 展开去重由「全局 visited」改为「祖先链」——原来同一物料在别处出现过，第二处连同整棵子树被整段跳过，那条路径的下层需求凭空消失。
- `perProductQty` 缺失的行标 `scaled=false`，状态列写明「缺 BOM 单位耗用，数量未按本批数量放大」。
- 数量框加 `inputFormatters` + `isFinite` 校验（原来 `1e400` 会以 Infinity 进 JSON）。
- 失败重试改走 `_rebuildAfterParent`，继承数量 / 车间 / 负责人 / 申请联动 / 勾选（原先丢一份全新行集，提示写着「可直接重试」，实际第二次提交必报「尚未选择生产车间」）。
- 下层「全已下单 / 全被挡住 / 结构过大」时不进页，但把原因如实告诉用户，不再静默跳过。

## 十、修订五（2026-09-15）：委外前置自制接上车间、进页判定单一化、层级树组件化

**凡与前九节冲突的以本节为准。**

### 10.1 「下达了却还在未下达」的三条真根因

1. **分桶页那一下根本没提交**。ADR-081 §7.1 把父件提交挪进了级联页的「一键下单」，但分桶页按钮仍叫危险色的「下达委外(N)」，级联页的返回箭头与右下角「稍后再办」都直接 `pop(false)`、零提示——用户点了一个写着「下达」的红按钮，退出后自然以为已经下达了。
   改：会进页时按钮加省略号（「下达委外(N)…」，通用「还要再过一页」约定；文案不能更长，悬浮动作组窄屏会 RenderFlex 溢出）；父件未提交时退出**必须二次确认**（`PopScope.canPop` 同步置 false），「稍后再办」改「放弃本次下达」，文案直说「上一页点的那一下只是打开了本页」。
2. **一条 action 都没建，客户端却判成功**。`notifySupplyInternal` 对 `delta = 0` 的组静默 `continue`；一批全是这种时 `created` 为空，不 `refreshLocked`，照样 `recordCommand` 并返回 detail，客户端见非空快照即弹「委外任务已下达」。
   先试过在服务端一律回 409，**行不通**：`FullChainEndToEndTest` 当场红 11 条——「现货交接」（`rootSupply.fulfillExisting`，本来就不建 action）、V466「原订单是唯一补货通道」的在途已覆盖、以及幂等回放，都是**合法的零 action 成功路径**，把它们变成冲突等于改坏端点语义。
   定稿改在客户端判：服务端**只有真的写了东西才会 `refreshLocked`**，也就是只有那时 `version` / `fingerprint` 才换版。`_notifyRoute` 提交后比对两者，都没动就不报成功，而是如实说「本次没有产生任何下达：所选行在服务端已无可下达余量……也可能是同一份请求被幂等回放」，并返回 null 让「一起下单」的编排在这一段停下。零 API 改动，也不碰上面那三条合法路径。假后端同步补上「写请求之后推进一版快照」——不这么做，每次写都会被判成「什么都没发生」。
3. **前置自制任务建完就没人管**。有自制子层的委外件 notify 之后，服务端在同一事务里建的是「`preplan_subcontract_make_tasks` 台账 + `source_type='SUBCONTRACT_MAKE'` 分析产品行」，**不出生产计划、不写 confirmed_route**；而级联页的车间段只提交进页前展开的那棵**物料行**树，新产生的**产品行**不可能出现在里面。于是 §一 承诺的「有子层级的委外自动添加到下达车间然后自动下达车间」缺了最后一步。
   改：编排新增第 0.5 段「前置自制任务下达车间」——父件段成功后按最新快照经 `_subcontractMakeChildProductOf` 解析出锚点产品行，用树顶那一行填好的车间/负责人调一次 `issue-plans`（后端零改动，`IssuePlanLine` 本就支持 `analysisLineId`）。没有 `generate` 权限时不硬闯，如实回报「已创建 N 个前置自制任务，尚未下达车间，请让有该权限的人到『下达车间』排产」。
4. **读模型也在说假话**：`MaterialAnalysisFlowStageService` 只认 `PURCHASE*` 与 `SUBCONTRACT_APPLICATION` 两种外部单据，`SUBCONTRACT_MAKE_TASK` / `PREPLAN_MAKE_TASK` 被整体丢弃；台账已建但锚点还没出计划时 `childStatus` 为空，整条回落 `SC_PENDING_ISSUE`（界面「等待下发委外」），与「从未下达」一字不差。改：链路事实新增 `hasMakeTask`，这种情形返回 `MAKE_PENDING_ISSUE`（界面「等待下达车间」）。零新增枚举、零前端改动。

### 10.2 进页判定收敛成一处，且每条不进页的路径都必须有话说

进页门槛原来用 `_analysisMaterialHasChildren`（看的是分析快照的全部子行，含 SHIP/REFERENCE、含失效行），建树却走 `_bomPresentation` 的父子图并跳过非生产阶段——门槛宽、建树窄：「只有出货/参考子件的委外件」会被判成有子层、进来一行都展不出来，而判定阶段已经把几百个 `TextEditingController` 建了又逐个 dispose。

改：`_buildChildCascadeRows` 拆成 `_cascadeNodes`（纯展开、零副作用）+ `_materializeCascadeRows`；`_pendingChildCascadeRows` 先跑前者，**展不出非树顶节点就如实说**（「BOM 上没有需要本次一起办的生产性子件（出货/参考阶段的子件不形成备料需求）」）。原来这一支返回 `note == null` 完全静默，与 §8.5 直接相违。不进页时的那句摘要也改到**提交成功之后**才发——原来是先弹再提交，文案却用「父件按原样下达」的已然口吻，取消确认或服务端拒绝时那句话就是假的。

**采购桶确认不进页**（`_submitMaterialBucket` 的 buy 分支直接 `_run`，全仓只有委外桶与车间桶两个 `_submitWithCascade` 调用点）。用户看到的「采购」是页面内子行的「下达去向」列——两件事，界面上要分开表述。

### 10.3 树顶（父件）行获得车间 / 负责人与相应限制

`_ChildCascadeSeed` 从「ID + 本批数量」升级为**父件段完整的提交意图**：新增 `channel`（`workshop` / `subcontractMakeFirst` / `subcontractDirect`，显式声明，不再靠 `actionGroupKey != null` 猜入口）、`maxQty`（本次可下达上限）与可变的 `departmentId/Name`、`workerId/Name`。

- 「要不要车间」与「是不是提交单元代表」彻底拆开：`needsWorkshop` 对树顶行按 `seed.channel` 判定（`ownsInput` 只管合并上下文行），`_canAssignWorkshop` 只留「需要车间 + 未被阻断 + 不在提交中 + 父件段未提交」。车间/负责人改动回写种子（与 `_onSeedQtyChanged` 回写 `batchQty` 同款）——快照一换行对象就作废，种子是这份用户输入唯一不失效的落点。
- `_loadWorkshopDefaults` 只在种子没带值时写学习默认，避免「界面显示 A 车间、提交 B 车间」。
- **父件级校验挂在 `_submit` 开头**（`_validateAndConfirmSeeds`），不是 `_validate`——后者只遍历勾选行，而树顶永不可勾选，塞进去也跑不到。校验三项：数量必须是大于 0 的有限数；`needsWorkshop` 的种子必须有车间与负责人（这就是用户说的「限制都没有」）；超过 `maxQty` 且**是在本页改大的**才复用分桶页那句超量二次确认（进页前那个数上一页已经问过一次）。
- `_patchRequestWithSeedQtys` → `_patchRequestWithSeedInputs`：数量、车间、负责人一起回写父件请求。
- **有自制子层的委外件数量框改为只读**：服务端 `createsChildOwnership` 要求提交量逐字等于剩余需求、且拒绝任何 `publicExtraQty`，而 `_resolveSubcontractQuantities` 提交时本来就会用 `entry.maxQty` 把用户填的数静默换掉——界面可编辑、提交端丢弃、下层却按被丢弃的数展开，是三方不一致。现在如实置灰并写明「要多做的量请在前置自制任务下达车间时填」。

### 10.4 数量口径的六处修正

| 口径 | 原来 | 现在 |
|---|---|---|
| 「还可下达」的来源 | 主口径写着 `缺口 − 已在途`，实则**死代码**（判定条件还捆着 `sharedFuturePendingQty`，真实服务端恒下发 0 → 恒真），全部分桶用例只覆盖这条死分支 | 服务端投影的 `additionalSupplyRecommendedQty` 是**唯一主口径**，回退只服务于缺该字段的旧载荷；夹具同步补齐该字段 |
| 本行下限 | `= 建议量`，含采购起订量抬出来的部分 —— 把软约束变成硬下限（需求 430、起订量 500 → 填 430 被红框拦死，提示还打印「已覆盖 −70」） | 拆成 `minQty`（下限）与 `suggested`（预填，采购再按起订量抬）；`shortfallHint` 的「已覆盖」不再反推负数 |
| 下限的基准 | `还可下达 + 超产额外量`，而 `还可下达` 是**整批分析**口径、`本批要用` 是**本次下达**口径，两者相加 | `min(本批毛需求, 还可下达) + 超产额外量`——父件分批下达（顶层需求 100、这次只下 10）时下层不再被要求一次下齐 100 |
| 改父件数量后的重算 | 两趟循环，第二趟用 `row.enteredQty`（本次重算**还没写入**的旧输入框文本）当驱动量：往大改被 max 掩盖，**往小改孙层继续按旧值算** | 一趟自顶向下；用户手工超产量单独存 `manualDriverQty`（只在真手工改过时写），驱动量取 `max(毛需求, 手工量)` |
| 无 ROOT_SUPPLY 行的顶层产品 | depth-1 行的 `parentMaterialLineId` 为 null，重算查不到驱动量整段跳过——「改父件数量下层一起变」对这类分析静默失效 | 子行一律挂树顶行的 `row.id`（含 `PRODUCT|` 前缀那种） |
| 提交单元成员集合 | 收全量物料行；失效路径的在途照扣、需求却不计入 → 本页算出的余量比服务端小、少下单 | 与服务端 `selectedGroups` 同口径过滤（`actionable / ROOT_SUPPLY / 优先补自制`） |

另外三处：车间段与采购/委外段一样**先按 `_isExecutableSupplyGroup` 求交再提交**并点名被剔除的行（原来勾选行原样送进 `issue-plans`，一行不可排产就 409 整批回滚、结果里还写着「下达车间 N 行」）；`_cascadeBlockedReason` 补上「已建自制子件任务」这道闸；`_loadSupplyLinks` 的裸写数量框改走 `_setQtyText`（原来立刻被记成「用户手工改过」，此后不再跟随任何父层重算）；`_rebuildAfterParent` 继承数量时不再加 `> 0` 的门（用户清空 = 「本次不下」，是明确意图）。

结果汇报也改了：父件提交后掉出行集的行，命中 `DELEGATED_TO_MAKE_CHILD` / `DELEGATED_TO_SUBCONTRACT_PREPARATION` 的单独报「需求已转交前置自制任务……本次没有为它们下单」，不再一律计进「已随父件下达办妥」。

### 10.5 层级树形收敛成一个组件 + 一份推导

用户口径「物料分析页面下面那个 BOM 表是那样显示的，都不一样，对着抄或者直接写成组件」。根因是**同一个画笔被喂了两套互不兼容的索引口径**：2026-09-14 把祖先槽的读法从 `[level]` 改成 `[level+1]`，这只对「按绝对深度索引、长度 == depth」的列表成立；级联页与货品 BOM 是这个口径（画对了），而主表的 `_materialTreePositions` 是从深度 1 起算的相对口径（长度 == depth − 1），改完之后主表每个 `depth ≥ 2` 的行都读错一级、最深那级恒定越界回落成「保守连画」，末位子件的竖线永远不收口。§9 里「准备页主表同样受益」的说法是反的——那次改动正是把主表画歪的原因。

- 新增 `lib/shared/widgets/uten_tree_row_projection.dart`：`utenTreeProjection` / `utenTreeProjectionByRow` 由**最终渲染序**推导 `ancestorContinuations` / `isLastChild` / `childCount` / `subtreeEnd`。口径写成硬契约：长度恒等于 `depth`，`[i]` = 深度 i 的祖先后面还有没有兄弟，`[0]` 占位但永不绘制。主表与级联页都改成调它；主表原来那份自建 DFS 只保留「级联编号」职责（它的排序比较器与真正决定行序的 `_orderedBomNodes` 不同，兄弟顺序一旦不一致，收口的肘线会画在中间某行上）。
- `guideBleed` 不再靠调用点记魔数：两个表格组件各自公开 `cellVerticalPadding`（`MasterDataTableView` = 8、`UtenEditableGrid` = 4），宿主传常量。主表与货品 BOM 原来一个都没传（默认 0），行与行之间恒定空 16px，整列看着像虚线——这正是用户说的「都不一样」。
- 树列新增列级 `fillsCellHeight`（两个表格组件都加，默认 false）：行被别的列撑高时树格不再被竖向居中收缩，连线才接得到上下行。这段差值是运行期量出来的，常量补不准。
- 肘线的纵向位置由 `size.height / 2` 改为 `guideBleed + 24`（展开按钮固定 48 且在 Stack 里顶端对齐）：带副标题的行不再出现「肘线掉在圆心下方」。
- `maxVisualDepth` 默认值 8 → `UtenTreeTableCell.defaultMaxVisualDepth = 10`，与业务展开上限同源，调用点不再各传各的。

## 十一、修订六（2026-09-16）：多选合并成一棵树、委外可改量、已建任务可追加

用户口径（实测后逐条）：

> 我下达车间，选择很多，就包括顶层的，那么它们都是顶层的子层级；我多选后改顶层的数量，其他的就不会变。
>
> 委外那里也检查：委外选中，就是子层有很多物料的时候，下单数量不可以修改。你不能仅仅改成数量可以修改，你还要检查——改了数量其他的会不会影响、怎么做；先下单了委外的，下达车间那里要怎么弄最好。

**凡与前十节冲突的以本节为准。**

### 11.1 多选行之间按 BOM 祖先关系合并成一棵树

原实现里每颗种子各成一棵树（`_cascadeNodes` 撞上「也被勾选」的后代就 `continue` 跳过，注释写的是「本批一起下达的行互为已安排」）。于是同时勾选父件与它的子件时，两棵树平铺在同一张表里**互不驱动**：改父件数量，子件那棵树纹丝不动——正是用户说的「其他的就不会变」。更糟的是父件段会按分桶页那个旧数量把子件也提交一次，与级联页里算出来的量不是一个数。

现在：

- 种子按展开起点的**层级从浅到深**排序处理（同层按勾选顺序），祖先先展开；撞上也被勾选的后代时**吸收**它——该后代作为普通下层行留在祖先树里（`_CascadeNode.absorbedSeed`），并在它自己的种子上记 `absorbedBy`，轮到它时不再单独成树。
- 只有**真被祖先展开到**的才会被吸收：中间隔着采购件（采购节点不下钻）、或展开撞上行数/层数上限时，后代仍各自成树，与原行为一致。
- 被吸收的行沿用分桶页填好的车间 / 负责人；数量默认跟着祖先算（这正是用户要的），只有分桶页填得**比算出来的还多**（明确想多做）才当手工值保留——可以多不能少，且手工值不被祖先重算覆盖。
- 父件段的请求里把被吸收的行**剔除**（`_patchRequestWithSeedInputs` 返回 null 表示这条请求没有父件要单独提交），它们改由级联页的车间段按算好的数量提交。不这么做就是同一行下两次、数量还不一样。
- 顶部提示逐行点名说清「你勾的这几行是上面这些件的下层，已并进对应的树里：数量随上层一起算，车间/负责人沿用你在上一页填的」——勾了的行在树顶名单里看不见，不说清楚会被当成弄丢了。
- `_topSeeds` 成为「本次将下达」的唯一口径：父件段行数、退出确认名单、顶部提示、超量二次确认全部改读它。

### 11.2 有自制子层的委外件：改走 issue-plans，数量可改

数量锁死的根因不在界面，在服务端：`notifySupply` 对 `createsChildOwnership` 的组（自制、以及要先自制目标件的委外）要求 `requested` **逐字等于**剩余需求，且拒绝任何公共超量。所以「把输入框放开」是修不了的——提交必被 422 整批回滚。

正确的入口是 **issue-plans 的 ARRANGE 段**：[V589](../数据迁移/180-V589委外前置自制跟量.md) 已经让委外台账跟量（行动记「归需求量 + 公共超量」、台账 `required` = 两者之和），下达车间那条腿本就支持超量。所以：

- 有生成生产计划权限时，**非顶层**的有自制子层委外件的父件段改走 `issue-plans`（候选行 `materialLineId`）：数量可改、超量按 V589 跟到台账与行动，且台账 + 锚点 + 计划**同一事务**建好。ADR-081 §一承诺的「有子层级的委外自动添加到下达车间然后自动下达车间」至此在一步里完成，§10.1 那段单独的「前置自制任务下达车间」编排对这类行不再执行。
- **顶层供给行只能 notify**：服务端 `candidateRoutesByMaterialLine` 明确排除 `ROOT_SUPPLY`，根件当 issue-plans 候选会被「候选物料节点不存在或路线未确认」拒掉。这类行保持整量接管、数量只读，随后由「前置自制任务下达车间」段按锚点产品行排产（要多做的量在那一步填）。
- 没有生成生产计划权限的账号同样退回 notify 整量接管，数量只读，如实说明该找谁办。
- 数量格的只读提示按上面两种原因**分别**写文案，不再一句话糊过去。
- 委外桶同时勾选「要先自制」与「直接外发」两类行时，父件段变成**两条请求**（notify 在前、issue-plans 在后），逐条提交、逐条记住成功；重试只补没成功的那条——重发已成功的那条会因快照换版拿到新幂等键，等于真实重复下单。
- 改走 issue-plans 的行在分桶页**没有**过超量确认（那道确认挂在车间桶的 `_validatePlanRows` 上），种子记 `overQtyConfirmed=false`，由级联页提交前补问一次。
- 「关不关分桶页」的判据由**请求类型**改成**本页是哪个桶**：委外桶如今也会发 issue-plans 请求，再按类型判断会把委外桶一起关掉。

### 11.3 已经建过任务的行：按锚点追加，不再一律拒绝

§8.2 定的是「已建自制子件任务的行本页不下达，请到『下达车间』对那个任务排产」。可用户多选时恰恰会把父件和这些已建任务的子件一起勾上，改父件数量却没人跟着变，且那些行永远只读。

现在这类行按它的**锚点产品行**（`MAKE_COMPONENT` / `SUBCONTRACT_MAKE`）追加下达：

- 「还可下达」改读锚点的剩余可排量（`canSchedule` 且 `remainingQty`），不再读分析侧提交单元的余量（后者对已建任务的 MAKE 组恒为 0）。
- 车间段对这类行走 `planDrafts`（`analysisLineId` = 锚点），其余行照旧走 `candidateInputs`；提交前按**最新快照**重新解析锚点复核资格，不看分析侧的 `_isExecutableSupplyGroup`。
- 锚点不可排产、或剩余可排量为 0 时才阻断，并如实写明原因——`canSchedule` 资格闸早于数量校验，硬提交只会 409 把整条编排卡在车间段（而那时父件已经落库）。V577 放开的是「本批数量可以高于剩余需求」，不是「需求已清零还能再下一张」。
