# ADR-071 下达车间原子化与计划侧齐套判断下线

- 状态：已决策（2026-09-05，零迁移）。
- 背景事故：车间桶「创建生产计划」显示失败后，回到下达车间发现每次失败都多出一条自制子件行；部分行「当前齐套」还会自动从 0 变满。
- 关联：[ADR-070](ADR-070-物料分析分桶详情页与三处学习记忆及超量下单.md)（分桶详情页与单按钮）、[ADR-029](ADR-029-生产计划前需求与物料分析重构.md)（WAITING/READY 执行段）。

## 一、事故根因（为什么打补丁修不好）

旧链路是**三段独立事务**：客户端先 `notify`（建子件任务+权益委托，独立提交），再 `plan-preview`（排产资格/数量校验），最后 `generate-plan`（凭预览指纹生成计划）。任意后段失败（预览 422/409、库存 CAS 冲突、网络中断）时，前段已提交——子件行残留、权益已委托，重试又可能再建行。这不是某一处 catch 的缺失，而是**把一个业务动作拆成三个可独立落库的事务**的结构性问题；补丁只能在失败后补偿回滚，复杂度只会继续膨胀。

「当前齐套从 0 变满」是同一结构性复杂度的另一个症状：子件任务建立后权益委托重算，父行齐套投影随之变化——在计划侧展示齐套，用户就要理解一套本应属于车间侧的账本口径。

## 二、决策

1. **所有自制行一视同仁**：顶层产品、自制候选、有子层委外候选、已建子件，不分形态，都是「数量 + 车间 + 负责人 → 下发」。
2. **单次原子调用**：新端点 `POST /api/production/material-analyses/{id}/issue-plans` 在**一个事务**内完成：候选行按全部剩余需求建子件任务（复用 notifySupply 的增量/幂等/权益委托口径）→ 逐行生成生产计划 → 有审核权限同事务审核下达。任一行失败**整体回滚**，不可能再出现「已建子件、未出计划」的残留行；重试靠幂等键回放，子件增量口径天然防重复建行。
3. **计划侧不再判断齐套**：`plan-preview` / `generate-plan` 两端点与 PlanPreview 契约族整体退役。客观齐套结论只决定执行段 READY/WAITING（缺料批次 WAITING、零预留、无 DRAW，到料后自动提升 READY），不再拦截计划创建。**车间收到计划单后自己判断物料齐不齐、不齐就等**；依赖其它车间产出的件，等上游完工入库后自动提升。
4. **计划侧仍保留的门槛只有资格类**：路线未确认（根必须显式确认为自制）、需求已全部转计划、BOM/订单来源漂移（`requireCurrentBomSnapshot`）。数量上限=剩余需求（业务上限，非库存上限）。
5. **UI 减法**：可安排桶列收敛为 类型 / 货品 / 剩余需求 / 本批数量 / 生产车间 / 负责人 / 状态——「订单/上级」「当前齐套」「建议首批」「可排产上限」四列下线；数量默认=剩余需求（不再按齐套量预拆批）；状态词统一「未下达」（原「待安排生产」「物料准备中」按齐套分叉的文案废弃），颜色图标与全站 `materialTaskPending` 同款。
6. **命令语义**：issue-plans 复用 `production_material_analysis_commands` 的 `GENERATE_PLAN` 操作码与幂等键命名空间（`material-analysis-issue-plans` 前缀），无 CHECK 约束变更、无迁移；候选编排部分以 `-ARRANGE` 后缀键记录 NOTIFY 命令（同事务回滚/提交）。

## 三、影响面

- 服务端：`MaterialAnalysisCommandService.issueWorkshopPlans`（替代 `generatePlan`）；`MaterialAnalysisService.planPreview` / `buildPlanPreview` 族删除；`preview_fingerprint` 列保留（历史数据），不再写入。
- 权限：无新权限码——`production_material_analysis:generate`（+审核时 `production_plan:approve`）口径不变。
- 兼容：已存在的子件行（历史失败残留）在重试时被增量口径识别（余量归零跳过建行），计划直接落在既有子件行上；无根节点的旧分析沿用旧合同。
- 适配验收：`FullChainEndToEndTest` 全部两段式调用改为单调用；三个陈旧红用例（root-wait / ma5 分批 / sma74 拆批）补「先确认根路线」以对齐 V478 双闸现行契约。

## 四、2026-09-05 二次简化：锚点模型（用户口径「为什么要转交？搞这么复杂」）

- **废除转交**：子件行（MAKE_COMPONENT / SUBCONTRACT_MAKE）降级为**计划锚点**——只承载计划链接与执行进度，不再接管子树需求（投影废除 delegated 清零）、不再迁移 exact 权益（notify 删除委托调用）、不再展开自己的 BOM（refreshLocked 跳过锚点源的树展开）。物料行保持在原树**单一份数据**，计划员照常在采购/委外桶对原行下达——修复「下达车间后采购桶旧行变 0 + 同物料重复出现在未下达」的事故。
- **notify MAKE 退役**：单独「创建自制子件任务」入口下线（行菜单删除、服务端 fail-closed 指引走创建生产计划）；有子层委外仍走 notify 登记台账（已产未通知账本），计划同样由车间桶出。
- **到货→车间通知链保住**：锚点计划无料行使原「计划=同 item 料行」的提升触发失效——`applyPriorityForOriginEvent` 增加「同分析 + 需求物料维度」兜底分支重查 WAITING 段；是否真齐套仍由 `isFullyAvailable` 严格判定（库存 − 他人预留 + 自有权益），不会误提升。无关联的公共到货（直接入仓）维持旧行为。
- **锚点齐套口径**：分析侧锚点行 readyNow 恒 0（齐套由计划执行段判定），`requireCurrentBomSnapshot` 对锚点跳过 BOM 指纹比对（其料行在原树，由父行校验覆盖）。
- **旧数据适配**：历史转交的子树/委托在分析**刷新时整体归还**（`restoreAllMakeDelegations`），投影自动收敛到单份数据；旧「需求已转交自制子任务」状态与详情文案退役（改「已下达自制/计划量/已完工入库」）。

## 五、权衡

> 2026-09-06 修订见 [ADR-073](ADR-073-本批物料履约与同主仓分仓领料.md)：计划侧不再用分析 `readyNow` 拦截正式预览的 WAITING 结果。正式计划包仍严格核对实际库存分配与 READY 提案一致，数量、版本和事务回滚校验保留；下文较早的 `savePlanningDraft` 双齐套结论比较已退役。

- 放弃两段式预览指纹换取原子性：库存变化导致的冲突由 `requireCurrent` 版本闸与 `requireCurrentBomSnapshot` 漂移闸承担（原本也依赖它们）；齐套正确性由 `savePlanningDraft` 内部「预览与齐套结论一致性」不变量守护（不一致即回滚重试）。
- 2026-09-12 交互修订：下达车间在当前桶内显示进度并保留输入，成功结果关闭后才返回宿主页；失败仍留在当前桶复核。旧的「先返回宿主页再执行」导航契约已退役，事务与幂等规则保持。
