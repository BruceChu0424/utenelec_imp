# V600 庆典通知自动发送默认关

> 2026-09-17。用户口径：「生日之类的祝福通知人事都没有主动发、都是自动发——不要自动发，要人事自己去发；或者页面上设个按钮，打开了才自动发。」

## 变化

- `system_settings` 里 `celebration.auto_enabled` 存量为 `true` 的一律翻为 `false`（**有意的策略变更而非遗漏**；幂等——已是 `false` 不动），设置项描述同步新口径。
- 无 DDL、不加表、不改任何其它行；重放零行。
- 配套代码（同批，不属本迁移）：
  - `CelebrationScheduler` / `NoticeService.getCelebrationSettings` 读取处的代码默认值 `true → false`（无存量值的库同样默认关）；
  - 新端点 `PUT /api/notices/celebration/auto`（`notice:publish`，与手动批量祝福同级）供 HR 任务中心「生日关怀/入职周年」页的「自动发送祝福」开关翻转；系统设置管理页原 `PUT /api/notices/celebration/settings`（authorization:manage + 二次密码）保留；
  - 审计事件 `notice_celebration_auto_toggle`（谁开的自动发送可回溯）。

## 为什么

此前 V224 种子 `auto_enabled = true`，每天 08:00（北京时间）`CelebrationScheduler` 自动扫描在职员工生日/入职纪念日并直接发布聚合祝福卡，人事全程无感。新口径把「发不发祝福」的决定权交还人事：默认手动（页面上多选批量送祝福 / 单人定制卡本就齐备），人事想在页面上打开「自动发送」才恢复代发。

权限说明：开关只翻一个 bool，能手动发祝福（`notice:publish`）的人即可委托系统代发同等内容，不构成提权，故不走超管 + 二次密码。

## 影响

- 存量库升级后自动祝福立即停发（当天已发的卡不回收）；HR 在页面重新打开即恢复。
- 新库默认关。

## 清库策略

无 DDL、无新表；`business_data_reset()` 白名单已登记 `(600, 557)`；`system_settings` 为 PRESERVE，开关不会被清库重置。
