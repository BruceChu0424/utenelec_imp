# V684 分类删除与「往分类里加东西」的并发闸

- 迁移文件：`server/src/main/resources/db/migration/V684__master_category_live_guards.sql`
- 决策：[ADR-111](../99-决策记录-ADR/ADR-111-主档删除引用保护与批量原子命令.md) §3
- 新增表：无；新增权限码：无；清库分类不变。

## 背景

物料分类/模具分类删除会级联软删子树里的货品/模具(先做 ADR-111 引用检查)，客户/供应商分类
删除要求分类下已没有有效客户/供应商。这些检查都是「先读后删」，而新建货品、把货品挪进分类、
在分类下建子分类读到的都是提交前的快照：删除事务读完、还没提交时有人把货品挪进来，提交后
货品就挂在一个已删除的分类下，在分类树里再也找不到。

## 内容

| 对象 | 变化 |
| --- | --- |
| `fn_guard_goods_live_category()` + `trg_goods_guard_live_category_insert` / `_update` | 新建货品、或货品的分类真的变化时，对目标物料分类 `FOR KEY SHARE` 读一次「未删除」，已删报 23514 `goods_category_live` |
| `fn_assign_uncategorized_master_category()`(V272/V275 既有函数，`CREATE OR REPLACE`) | 客户/供应商/模具的「分类未删除」那次读改为 `FOR KEY SHARE`，失败改报 23514 `master_category_live`(原来是无错误码的 P0001)；其余逻辑逐字不变 |
| `fn_guard_live_parent_category()` + 四棵分类树各两条触发器 | 新建子分类或挪动父分类时，父分类必须未删除(`FOR KEY SHARE`)，已删报 23514 `category_parent_live` |

服务端删除一方先对子树分类行 `SELECT … FOR UPDATE`(物料/模具分类另外先拿层级锁，并在锁后重读
子树，锁前刚提交的子分类也带上)。两把锁互斥：删除先拿锁，加东西的一方等它提交后按最新版本
重读、看到已删除即拒绝；加东西的一方先拿锁，删除等它提交后才读子树里的货品，新货品自然在检查
范围内。`KEY SHARE` 之间互不冲突，平时建货品、改客户不因此串行。

触发器只在分类真的变化时触发(`WHEN NEW.x IS DISTINCT FROM OLD.x`)，保存一个分类没变的货品不会
被历史脏数据挡住。服务端全局异常处理把三个 23514 映射成「所选分类刚被删除，请刷新后重新选择
分类」「上级分类刚被删除……」。

## 存量

不做回填：老库迁移的分类全部以未删除状态写入，迁移脚本不受影响。

## 验证

`MasterDataIntegrityEndToEndTest.movingGoodsIntoACategoryBeingDeletedWaitsAndIsRejected`：删除事务
锁住分类后，另一个连接把货品挪进该分类会一直等待(500 ms 内不返回)，删除提交后被 23514 拒绝，
货品的分类保持为空；之后在已删分类下建子分类、挪货品都被数据库直接拒绝。
