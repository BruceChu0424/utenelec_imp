# 客户零星发货统一审批与出库方案

状态：2026-09-07 已经本轮统筹审查采用，开始实施；前向迁移 V511。方案通过不代表源码、测试或上线已交付。

## 1. 已确认的问题与复用基础

现行 `/api/sales/other-shipments` 仍允许新建、编辑和审核，统一销售编辑页也明确引导无订单零星出库到此入口。客户可填可空，地址、发货人和出库类型均可录入。`SalesOtherShipmentService.approve` 从草稿直接调用库存出库，没有财务放行或仓库作业阶段；这与“所有客户发货先财务确认、再仓库实际确认”冲突，不能以“不立应收”作为免费样品的例外。

常规 `sales_shipments` 已有真实财务放行事件、财务/仓库共享任务列表、待拣/拣货中/已拣/异常/SHIPPED、库存与应收同事务、来源退货和通知链。优先在这套事实模型中扩展“客户零星发货”，不再给旧其它出货表复制一套审批、仓库、通知和应收。

源码对照还确认两个不能假定已经具备的能力：常规发货财审目前没有 TaskClaim 类型或审核修订号，详情弹窗仅先取信息再直接审核；收款的订单分配器对 SALES_SHIPMENT 应收要求 SALES_ORDER 来源，不支持凭空没有订单来源的新收费发货。二者都必须在此包内按真实身份补齐。

## 2. 统一存储及历史边界

新客户零星发货写入 `sales_shipments` / `sales_shipment_items`，使用同一个 UUID 和既有 `/api/sales/shipments` 流程。销售入口显示“客户零星发货”，列表使用类型筛选；财务和仓库仍在现有发货任务页处理。

原 `sales_other_shipments` 历史记录继续保留原 UUID、数量、价格快照、库存流水和来源关系。旧列表/详情只读；原已审核单仅保留通过原来源、库存及计价事实校验的受控反向。不得将旧行搬成新已发运行，不补造销售确认、财审、SHIPPED 或应收。旧新建/编辑/审核接口拒绝继续绕行，并提示新的客户发货入口；真正内部领用从仓库内部出库业务建立，销售入口不接受“客户留空但填写客户地址”的内部伪装。

客户发货始终要求有效客户 UUID。“收费/不收费”是明确人工选择，不能由客户月结/现金/定金标签、有没有参考价、价格是否为零推断。内部单据的领取部门/人员身份属于仓库业务，不能靠销售其它出货的任意文本自称内部。

## 3. 建议字段及约束

| 位置 | 字段 | 语义 |
| --- | --- | --- |
| sales_shipments | `shipment_kind` | `ORDER`（真实订货来源）、`DIRECT_CUSTOMER`（客户零星发货）；历史不能证明来源的行标为兼容历史类型，不能充作新直发 |
| sales_shipments | `billing_mode` | 新直发必须明确 `CHARGED` / `FREE`；订单发货继续按订货金额，不从历史金额反推免费 |
| sales_shipments | `direct_purpose`、`free_reason` | 样品/赠送/其它用途；免费说明须录入并交财务查看 |
| sales_shipments | `sales_confirmed_at/by`、`sales_confirmed_revision` | 本次发货内容的销售确认事实；原订单发货沿用实际订货确认及提交依据，不增加第二张销售订单 |
| sales_shipments | `review_revision` | 有关客户、收费选择、商品、单位、数量、单价、地址、仓库等内容变化时递增，旧确认不得继续覆盖新内容 |
| finance_release_events | `review_revision`、`commercial_snapshot`、快照哈希 | 新财审保存完整内容，用上次审核快照与本次内容展示前后变化；保留旧事件字节和缺失快照的事实 |
| stock_reservations | 直发单据归属 | 订单直发没有销售订单行可借用；需要明确的客户发货单归属及来源 UUID，不能伪造订单或物料需求 |

复用 `finance_gate_version` 的前向版本区分新协议与历史记录。新协议须有销售确认、财审和仓库 SHIPPED 事实；历史字段为空不能伪装已确认。已存在普通发货的历史兼容继续按既有门禁处理，不回填虚假的历史事件。

免费模式的客户货款明确为零，库存仍按真实账面成本出库；免费不等于零成本。收费金额由真实行数量、实际单价、折扣及税率按既有货币精度重算。客户端金额只作预览，不能作为库存成本或应收最终权威。免费页面可隐藏无须录入的货款字段，成本按权限查看。

## 4. 流程与修改规则

1. 销售填写客户、用途、收费选择和明细，形成草稿；新直发必须显式“确认并提交财务”。常规订货发货保留其已存在的订单确认/发货提交基础，避免再增加一套重复下单步骤。
2. 销售确认后进入现有出货财务队列。财务先成功认领，取得当前修订号和内容快照，再人工通过或退回。所有客户标签都不能自动放行。
3. 财务通过后才进入现有仓库待拣队列。仓库依次开始拣货、确认已拣、登记异常/恢复、最终交接 SHIPPED。
4. 新收费直发只在 SHIPPED 同一事务形成一次正式 AR；免费直发不创建虚构的收款或退款，仍登记真实库存成本。任何中途失败全部回滚。

财务有效认领期间，任何账号（含认领本人、兼岗和超管）都不能修改。未开仓库作业时允许受控修改，撤销旧放行、递增修订并重新销售确认/财审；审批页显示旧审核内容与当前内容。拣货开始后不得直接修改商业内容；必须由仓库先退出或解决作业、释放其直接发货预留，再走受控退回。SHIPPED 后原数量、收费选择、金额和成本快照保持不可变，使用退货或受控反向。

现有普通 `sales_shipment:approve` 不能继续成为绕过仓库最终确认的独立库存写通道。新客户发运事实只由仓库 SHIPPED 命令产生；旧客户端必须得到明确的流程提示，不能以成功响应伪装已经发运。

## 5. 审核认领、版本和锁序

新增共享 TaskClaim 类型 `SALES_SHIPMENT_FINANCE_AUDIT`，复用已有 strict session、claimId、续租/释放/接管和本人有效认领原子守卫。其权限沿用财务发货审核操作及现行主动授权规则；弹窗仍比审批资格严格，按部门与动作权限交集投递。

认领/续租只锁发货头与 claim，检查待审状态和资格；实际决定在共同商业来源/库存前缀后锁发货头，再锁 claim，校验本人、同代 claimId、原修订号及内容哈希。修改同样在发货头锁内拒绝任何有效认领。批量如开放，必须一次声明全部来源和库存，在同一事务内全部通过或全部失败。

普通发货编辑目前删除并重建明细，不能据此可靠对比行级变更。新编辑需用行 UUID 匹配、保留历史身份，新增行才生成 UUID，移除行保留历史；不按可变名称、单号或相同行号猜关联。

## 6. 库存与财务联动

订单来源发货继续消费原销售订单预留和精确发运分摊。直发在仓库开始拣货时，对所选仓库的真实公共可用量建立明确归属于该发货单的预留；不能抢占其它订单、生产或委外已占用量。退出/取消作业对称释放，SHIPPED 精确消费后扣实物，重复命令不重复扣减。全部复用库存货品/颜色互斥锁和现有预留余额守恒规则。

收费直发的正式债权通过 `ledger.source_doc_type=SALES_SHIPMENT`、`source_doc_id` 和新直发身份精确回联。它没有 SALES_ORDER，不能为通过旧收款分配器而伪造订单。建议仅将“分配到销售订单”这一补充分配步骤限定到确有订单来源的应收：新直发须由服务端验证新流程、收费模式、已发运和金额/客户/币种一致，随后沿既有收款行 → AR 的权威链结算；历史缺少订单来源的普通发货仍拒绝猜测。收款、手续费、汇兑和双币 AR 余额算法继续复用，不另写一套。

订单绑定预收不得自动挪到没有该订单身份的直发。收费直发退货继续按原实际发运量、冻结价/汇率和原 AR 精确退回；免费直发退货只允许按明确 FREE 来源恢复实物/成本且客户货款仍为零，不能凭“原 AR 缺失”猜免费。已收后退货形成的待处理余额继续如实展示，本包不冒充现金退款。

库存计价及 GL 与 V509 责任包对齐：两种收费模式都使用已冻结出库成本，收费收入与免费用途对应的成本科目分别按财务映射处理；不能将客户端售价、参考价或零货款作为成本。旧其它出货没有可靠成本来源时沿历史计价差异处理规则，不自动重写旧余额。

## 7. 页面、通知及实施文件边界

- 统一 `SalesDocConfig`、销售入口/列表/编辑/详情与 `SalesRepository`，新客户零星发货进入普通发货数据模型及原财务/仓库工作台；旧其它出货详情保留历史展示与允许的反向。
- 保留 `sales_other_shipment` 这组权限作为客户零星发货的独立页面权限。共享表和路由不能扩大授权：服务端按 `shipment_kind` 判定查看、创建、编辑、销售确认及反向权限；只有零星发货权限不能读写普通订单发货。财务与仓库继续按其池化动作处理两类客户任务。
- 财审预览接 strict claim，显示“收费/不收费”、销售确认、待复核变更；失去租约立即暂停决定。沿用现有原生控件和框内提示，不新增待审收件台。
- 财务通过、退回、仓库待办、实际发运、退货/反向继续使用原发货事件和耐久 outbox。无订单直发完成通知其明确销售负责人，不能因没有订单归属漏通知或发给所有销售。
- 后端主要边界：SalesShipment 实体/DTO/Service/Controller、原其它出货写入口退役、TaskClaim 的中立目标锁适配器、统一预留接口、退货金额权威的明确 FREE 分支、收款来源分配适用性、V511 前向约束与索引、对应页面/ADR/SOP。

## 8. 验收矩阵

必须以真实 PostgreSQL 服务调用验证：收费/免费两条新直发完整正向；客户为空及带客户地址的伪内部拒绝；财务未确认不能拣货或发运；同本人/异人/失效认领与原修订提交；审批后改动重新审核；两张直发抢同一可用量只允许真实容量；订单预留不被直发消费；重复/并发发运只一次库存/AR；部分收费收款与反向、免费退货零货款但恢复原成本；已收清后退货如实呈现待处理余额；历史其它出货只读及有来源的受控反向。额外验证旧正常订单发货的金额、来源、部分发货与仓库异常恢复，不能用放宽既有金额/数量断言来通过。

已采用“新客户其它出货统一到 sales_shipments、保留常规订单确认基础、收费直发使用精确发运债权但不伪造订单分配、仓库拣货建立直接归属预留”的边界。未完成这些相互依赖项前，不单独启用收费或免费直发新入口。

已发运价款不能通过虚做退货、再发货纠正；没有真实实物流转的价款更正须用财务追加调整，当前包保留明确的受控边界，不生成虚假库存或退款事实。库存价值核心不按免费标志猜费用科目；保留用途/免费原因及原发运明细 UUID，由实际财务科目映射处理。

实施检查点：V511 字段与约束、按 kind 的权限、草稿与销售确认、strict 财审与变更快照、直发库存预留及最终 SHIPPED、收费 AR/收款适用性、免费退货真实成本、共享页面/徽章/通知、真实 PostgreSQL 正反向及本地前端回归。上述项目全部完成前，本包持续标记为实施中。
