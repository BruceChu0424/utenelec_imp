# 规划通知审核代次办结与事务回归

本项基于组合主链 `65063dd8a`，修复真实负责人重审后，同一订单、同一接收人的旧、新 `SALES_ORDER_APPROVED` 规划行动卡同时未办结的问题。不改变经理先审、财务确认、计划接手资格、动作权限、业务修订号、数据库迁移或版本。

## 已证实的根因

inventory 任务在真实两级审核夹具上运行原 17 例时，`aNewManagerGenerationPreservesTheOriginalUnreadReceiptAndPublishesOneCurrentCard` 出现唯一失败：原卡来源版本 1，新经理批准后来源版本 2，历史两条身份不同且均未读，但 `resolved_at IS NULL` 的行动卡数预期 1、实际 2。原始证据位于主工作区 `output/release-2539-resume/db-fixture-fix-20261031-223719/focused-qty-notice-first-reports/TEST-com.uten.imp.businesschain.SalesPlanningNoticeCatchUpEndToEndTest.xml` 及同目录上一级的 `focused-qty-notice-first.raw.log`。

发布入口按订单、接收人和 `finance_review_revision` 去重，能够保留每轮独立回执，却没有在新轮发布时办结已证明的旧轮。列表的当前来源资格筛选不能代替通知生命周期办结；不能删除旧记录、把旧版本改成当前版本，或将用户未读状态伪造为已读。

## 唯一处理入口与边界

- 正常投递与 catch-up 仍走 `ChainNoticeService.deliverSalesPlanningHandoff`。取得有效订单表头锁、核对事件期望版本等于当前版本、确认仍需初次计划接手后，在同一投递事务内先办结同订单、同来源事件、非 NULL 且小于当前版本的未办结卡，再按原规则发布当前轮。
- 旧卡只写 `resolved_at` 和明确的 `SUPERSEDED_BY_REVIEW` 原因；身份、内容、来源版本与发布时刻均保留。所有 `notice_user_states` 读、确认、删除、稍后提醒字段保持原值；当前轮与 NULL 来源的历史不改。
- 晚到旧轮的订单批准、财务确认和 catch-up 事件在版本检查处返回，不允许其办结当前轮或复活旧轮。取消、下游已接手、临时失权等既有资格保护仍在办结之前。
- catch-up 除补缺失接收人外，也识别“已有当前轮，但仍有更早已知轮未办结”的旧数据；只入队，仍由上述公共入口原子办结，当前轮去重不重发。不把 inbox 读取变成写入，不按时间猜测 NULL 历史归属。

Web 与现有 Flutter 桌面共用服务端通知入口，无客户端契约变更。Win7 WPF 仍是未完成完整 ERP 迁移与真机验收的候选；此处未新增写入口或更改其支持状态。未修改 UI、WPF 进度、SQL、权限与公共 TaskClaim 兼容规则。

## 事务证据

`BusinessOutboxProcessor.processNext` 使用 `REQUIRES_NEW` 事务，异常重新抛出为运行时 `OutboxDeliveryException`；`deliverAtomically` 直接执行回调，不吞异常；`NoticeService` 的办结与发布加入该事务。

新增真实 PostgreSQL 用例在新通知及用户状态已实际写入后注入发布失败，经真实 outbox 处理器观察异常。独立查询断言旧卡仍未办结、其完整用户状态不变、新轮通知与用户状态都未残留；恢复发布后重试恰有一张当前行动卡。该证据覆盖实际回滚，不以注解或 mock 调用次数代替事务结果。
