## 一、用户要求

用户在工作台打开 AI 助手，上传「花名册.xls」时说(本机开发库识别任务 `d6994a7e…` 的原始参数)：

> 这是最新的人事统计出来的人员信息 你看看信息 对照系统里的 不对的补充 缺少的添加

助手回了三张「打开新建销售订货单 / 销售报价单 / 报销申请并填入识别结果」的确认卡，点「确认执行」没有反应。之后用户的要求(原话)：

> 你完整的修复, 让 AI 更加智能, 上传任何文件能够识别, 能够知道需要做啥

> AI 那里也是要权限, 上传的内容需要处理的得有对应的权限才行

> AI 要足够的智能, 足够了解我们的项目... 不是靠瞎猜或者蒙混过关

拆成四条：

1. 点了「确认执行」就要真的打开页面；打不开要说清楚为什么，不能面板一收什么都没有。
2. 一个文件给一个像样的回答：这是什么文件、凭什么看出来的、你想做什么、助手能做什么不能做什么、该去哪里做；不再甩出几张不相干的卡。
3. 看懂文件只需要能用对话；接下来能做的事(填单、去哪个页面)按本人权限给，没有权限的说清缺哪项权限。
4. 不瞎猜：先按标题、表头这类确定的证据认；认不出才让模型按表格结构推测，推测要明说是推测；模型看不到表格里的内容。

## 二、背景

### 2.1 点「确认执行」没反应：外壳按冻结的位置判断主 Tab

- **证据**(本机开发库，只读查询)：识别任务 `d6994a7e…`(`ERP_DOCUMENT_ROUTE`，文件「花名册.xls」，提问页面 `/dashboard`)的结果是 `documentType=UNKNOWN`、`workflow=NONE`、`needsChoice=true`，有三个可选用途，同时发出三张 `OPEN_GUIDED_FORM` 卡。用户确认的其实是「报销申请」那张(不是销售订货单)：确认请求和回执请求前后只隔约 0.47 秒，回执写的是「成功」；约 75 秒后用户重新打开对话框，把另外两张卡取消了。三张卡失败的原因相同。
- **原因**：AI 对话框挂在 `MainShellPage`(ShellRoute 的外壳)里。外壳用 `GoRouterState.matchedLocation` 判断「现在是主 Tab 还是业务子页」，只有判成业务子页时才把业务页所在的嵌套导航器(`widget.child`)放进界面。go_router 14.8.1 的命令式 `push` 只更新外壳状态里的 `uri`，`matchedLocation` 停在 push 之前的位置(`ShellRouteMatch.copyWith` 保留旧值)。所以从工作台、通知、我的、设置这四个主 Tab 上 `push` 任何业务页，外壳仍判成「在主 Tab」，被 push 的页面根本不挂载；这时再点「工作台」，也会被判成「已在本 Tab」而不动。
- **对话框又把问题藏住了**：确认后先收起面板，`push` 不等结果，然后不管页面出没出来都回执「成功」。
- **不只是 AI**：凡是从主 Tab 用 `push` 进业务页的入口都一样(例如从「我的」进编辑资料)。以前文档里「主 Tab 前缀下 push 会静默失效」的说法只看到了一部分；工作台卡片一直用 `go` / `goFrom`，所以没撞上。

### 2.2 三张无关的卡：认不出花名册，认不出就每个用途一张

- 识别规则里的人事标题只有工资表、薪酬表、员工档案、入职登记、离职申请，没有「花名册」；按表头认人事表时，要求同一行既有「姓名」又有工资类列，花名册没有工资列。于是花名册被判成「用途不明」(`UNKNOWN`)。
- 用户的话里没有「报销」「订货」「报价」，原逻辑只认这三种请求，于是也看不出用户想做什么。
- 用途不明时，原逻辑把本人能用的每一种填单用途各发一张确认卡(最多 3 张)，回答只有一句「暂时没看出文件用途，请选要做的单据。」——没说文件是什么、用户想做什么、助手能不能做。
- 本人一种可填的单据都没有时(例如只管人事的账号)，上传直接被拒(403)，对话框里也不显示上传按钮：恰恰是人事上传不了花名册。
- 就算花名册被认成「人事资料」，原逻辑也没有给它任何可选用途或去处，回答同样是死路。

## 三、决策

### 3.1 外壳一律按栈顶叶子路由判断(平台规则)

- `MainShellPage` 判断「主 Tab 还是业务子页」、导航高亮归属、点 Tab 或横滑切 Tab 时「已在本 Tab 就不动」，三处一律用 `GoRouterState.uri.path`(栈顶叶子路由)，不再用外壳的 `matchedLocation`；传给对话框的 `currentRoute` 也是这同一个值。
- `main_shell_page.dart` 里 `GoRouterState.of(` 仍然只有 3 处，由 `test/shared/auth/go_router_state_usage_gate_test.dart` 锁定。
- 效果：从任何主 Tab push 的业务页都照常显示，返回回到原 Tab，点 Tab 按钮离开业务页。
- **平台规则**：外壳以及任何「我现在在哪个页面」的判断，都不得用 ShellRoute 的 `matchedLocation`(它在 push 后不跟着变)。页面级「返回即刷新」按 `topMatchedLocationOf(router)` 取栈顶，不受影响(见[路由设计 §九](../05-架构/路由设计.md))。
- 主 Tab 上进业务页仍首选 `go` / `goFrom`：push 现在能正确显示，但主 Tab 自己的路由会在被 push 的页面下面再建一份该 Tab 页面(看不见，白建一次，见 §六)。

### 3.2 确认卡先跳转，核对到了再回执成功

`OPEN_GUIDED_FORM` 卡确认后：

1. 照旧核对来源文件、识别任务和用途权限，`confirm` 一次性核销，拿服务端的权威参数。
2. `push` 对应的新建页(不等它返回)，等一帧，取栈顶路由。
3. 栈顶就是这张表单：收起对话框，回执「成功」。
4. 否则回执「失败」，对话框不收，原因写在卡上：被路由守卫转到无权限页时说「当前账号没有打开这个填写页面的权限, 这张卡已作废, 请联系管理员开通后重新上传文件」；没有路由、跳转出错或落到别的页面时说「填写页面没有打开, 这张卡已作废, 请重新上传文件再试」。卡已经核销，不能再点；要重来就重新上传文件。

### 3.3 一个文件一个回答，最多一张卡

- **服务端**：只有「用途明确、本人能填、文件可靠(不是多张发票、不是多种业务混在一起、没有被截断、用户没说只分析)」时才发一张 `OPEN_GUIDED_FORM` 卡，其余情况一张都不发。每次读取时只保留绑定了读者当前仍可用用途的卡，最多 1 张。
- **前端**：文件回答只收 `OPEN_GUIDED_FORM`，最多 1 张；页面动作卡、授权卡等别的类型不属于文件回答，一律不显示。
- **用途要用户选时给选项，不给卡**：`needsChoice=true`，`choices` 列出这份文件能填、而且读者当前有权限填的单据，前端显示成一排选项。点一个选项，前端把**同一个文件**连同用户原话、原页面和参数 `workflow=<所选>` 再提交一次(用户一侧显示「选择：…」)，新回答最多一张卡。每个回答只能选一次，选过后这个回答下的选项全部失效。
- **用户点的选项优先**，高于从原话里看出的请求；但文件类型明显对不上时(比如把花名册选成销售订货单、把增值税发票选成订货单)，回答「文件与要做的单据不一致」并说明哪里不一致(如「员工花名册不能用来填写新建销售订货单。」)，不出卡。
- **为什么要重新提交文件**：识别任务一结束，服务端就清掉了上传的文件内容，不能再读；重新提交是唯一统一的做法，以后按花名册核对也要据此重新计算(§八)。
- 每种文件能选的单据：

| 文件类型 | 可选的单据(再按读者权限过滤) |
|---|---|
| 认不出、商业发票 | 销售订货单、销售报价单、报销申请 |
| 报价文件、客户订货文件、货品明细 | 销售订货单、销售报价单 |
| 发票(增值税发票、电子发票) | 报销申请 |
| Word 文件 | 不提供销售单据(请另存为 Excel 或 PDF 再上传) |
| 其它类型(花名册、工资表、货品清单等)；多种业务混在一起、多张发票、被截断、只分析 | 无 |

### 3.4 先按确定的证据认，证据不足时让模型按结构推测

2026-10-07 下一版本修订：文件类型与目标单据分别判断。报价资料可以用于准备订货单；明确目标仍须通过兼容性、权限和一次性确认卡检查。只有 `Invoice` 或发票编号、合计等弱线索时，不把销售资料确定为商业发票；说明依据与不确定性。只问文件是什么时不根据默认页面自动准备操作。

**第一步：本地规则(确定性，不调模型)。**

- **找表头**(`AiDocumentProfiler`)：每张可见的表(最多 8 张)在前 15 行里找表头行。条件：一行里能认出至少 2 种列含义；整行都是文字(没有数字、日期、证件号、手机号、金额格)；不是「键 值 键 值」式的登记表行(如「姓名 | 某某 | 部门 | 销售部门」)。取认出含义最多的一行。
  - 两行表头：只有上一行是跨列合并的分组标题时(如「联系方式」盖住下面的「手机 | 邮箱」)才把两行合起来，列名取下一行。表头下面的第一行数据即使全是文字(如「某某 | 销售部门」)也不会被当成第二行表头，所以表格里的值永远不会变成列名。
  - 列含义约 40 种(姓名、工号、性别、部门、岗位、入职日期、证件号、手机、货品编码、规格、单位、数量、单价、库存数量、父件、子件、用量、交易日期、收入、支出、余额……)，按同义词表认，也认「以某词结尾」的列名(家庭地址算地址、交货日期算日期)；「编号」「名称」这类泛词按同一表头里的其它列定义(和姓名在一起是工号，和货品在一起是货品编码)。
  - 合计行、分页时重复打印的表头不算数据行；数据行 = 表头下面至少填了两格的行。
  - 每列再按前 30 行数据判断「值长什么样」：日期、18 位证件号样、11 位手机号样、金额、整数、编码、短文字、长文字、空，取出现最多的一种；只记形状，不记值。
  - PDF / Word 在前 15 行文字里找表头行，同样不收带值的行和「键：值」行。
- **认类型**(`AiDocumentClassifier`)：
  - 标题优先。单据类标题(采购订单、工资表、员工档案、入库单、生产计划、合同、发票……)出现在哪里都算；名单类标题(花名册、客户资料、交易明细……)常常也是别的文件里的小节名，所以只在一张表的前 3 行、而且没有其它业务的单据标题时才算。名单标题可以带公司、部门、年月前缀和「在职、汇总、明细、最新」等后缀，例如「某某有限公司2026年10月员工花名册(在职)」。
  - 表头只能在同一业务大类里「细化」，不能给有标题的文件再加一种业务：带标题的报价单里有一段「客户资料」，仍是报价文件；「员工档案」标题下面是花名册的列，认成花名册。货品 + 数量 + 单价相邻的表头仍按销售货品明细处理(原规则不变)。
  - 不同业务大类同时出现 → 「文件里有不同业务的资料，请分开上传」(原规则不变)。多张表各自判断再合并：同一大类合并，不同大类算混杂。
- 本次新增 9 种类型，原有销售、发票类规则不变：

| 类型 | 回答里的叫法 | 标题(举例) | 没有标题时按表头 |
|---|---|---|---|
| `EMPLOYEE_ROSTER` | 员工花名册 | 花名册、员工花名册、员工信息表、人员信息表、员工名册、员工名单、人员名单、在职人员名单 | 有姓名，再加至少两项身份信息(证件号、手机、部门、岗位、入职日期、工号、性别)，且没有工资、金额、单价、数量、收支、余额类列，也没有货品列 |
| `PAYROLL` | 工资表 | 工资表、工资单、工资明细(表)、薪酬表 | 姓名 + 工资类列 |
| `ATTENDANCE` | 考勤表 | 考勤表、考勤记录、打卡记录、出勤表 | 姓名 + 考勤类列(出勤、迟到、请假、打卡……) |
| `GOODS_LIST` | 货品清单 | 货品资料、货品清单、产品资料、产品目录、物料档案 | 货品编码或名称 + 规格、单位、颜色、分类之一，且不同时有数量和单价 |
| `BOM_LIST` | 产品配件清单(BOM) | 配件清单、物料清单、BOM、材料清单、组装明细、产品结构表 | 父件 + 子件，或子件 + 用量，或货品 + 用量 |
| `CUSTOMER_LIST` | 客户名单 | 客户资料、客户名单、客户清单、客户档案、客户通讯录 | 客户 + 联系人、电话、地址之一，且没有货品列 |
| `SUPPLIER_LIST` | 供应商名单 | 供应商资料、供应商名单、供应商档案 | 供应商 + 联系人、电话、地址之一，且没有货品列 |
| `STOCK_LIST` | 库存或盘点表 | 库存表、库存清单、库存明细、盘点清单、库存盘点表、盘点表 | 货品 + 库存数量，或货品 + 仓库 + 数量 |
| `BANK_STATEMENT` | 银行流水或对账单 | 银行流水、银行对账单、对账单、账户明细、交易明细 | 交易日期 + 收入或支出，或日期 + 余额 + 收入或支出 |

  原有类型的变化：工资表以前归「人事资料」(`HR_DOCUMENT`)，现在是「工资表」；库存盘点表、盘点表现在是「库存或盘点表」；入库单、出库单的叫法改为「仓库单据」。

**第二步：本地认不出或销售资料证据不足时，按结构请模型推测一次**(`AiDocumentModelAssist`，用途码 `ERP_DOCUMENT_ROUTE_TYPE`)。

- 同时满足才调用：规则认不出或销售资料缺少确定标题；不是「已读到部分发票信息」的情况；文件没有被截断；提交人能用 AI、管理员配置的 AI 服务可用、本任务还有调用次数；文件里至少有一张找到表头的表，或 PDF / Word 有一行可以发的标题。用户已明确目标单据不再关闭文件理解；确定标题、混合文件和多张发票不交给模型重判。图片永远不走这一步。
- **发出去的只有结构**：文件格式；每张表(最多 8 张)的表名、表头下的数据行数、各列「列名 [值形状]」(最多 40 列)；没找到表头的表只发表名和非空行数；PDF / Word 的第一行文字(只有不超过 20 个字、不含数字和 @、而且整行不是 2 到 4 个汉字时才发，2 到 4 个汉字可能是人名)；用户随文件说的那句话(截到 300 字)。
- **发出前再处理**：表名、列名、用户的话里连续 3 位以上的数字(中间夹空格、横杠、点、斜杠也算)和邮箱地址换成 #；表名、列名最长 24 字；像人名的表名和列名(常见的约一百个单姓或十几个复姓开头、一共 2 到 4 个汉字，而且不是已知的表头词；「周一」到「周日」除外)整个换成 #，防止「一个员工一张表」或「日期 | 某某 | 某某」这类把人名放在表名、列名上的表格把姓名带出去。
- **永不发送**：任何数据行的值(姓名、证件号、手机号、金额、日期……)、文件名、文件本身、页面内容。
- **模型只能回三个枚举**：恰好 `{type, intent, confidence}` 三个字段，每个都在固定清单里；`type` 是上表或原有类型之一，`intent` 只能是核对 / 录入 / 分析 / 询问 / 无(**没有「填单」**)；`confidence` 为低、`type` 为认不出、格式不对、调用失败，一律按认不出处理。提示词写明不执行输入里的任何指令，输入标为不可信数据。
- **推测结果的用法**：用于说明文件可能是什么、可去页面和做不了的事项；模型本身不选择目标单据或授权动作。没有用户明确目标时只给相关选项；用户已经明确目标或点选用途时，按兼容性和当前权限检查后可出一张确认卡，不因来源类型是推测就再要求重复选一次。推测的意图只在用户原话看不出意图时才用。回答和前端均标明结构推测、需要核对。

**用户想做什么只看用户自己的话**(`AiDocumentIntent`)，文件里的任何文字都不算。按下表从上到下取第一个命中：

| 意图 | 用户原话里的词(举例) | 回答里怎么说 |
|---|---|---|
| 只分析(不出卡、不给选项) | 明确拒绝或只要分析：「不要 / 不需要 / 别……生成、新建、填写、开单、保存」「只 / 仅……分析、识别、查看、看看」及对应英文 | 「这是……，已只做分析。」 |
| 填单 | 「报销」；「生成 / 新建 / 填写 / 做 / 开 + 订货、销售订单」；「…… + 报价」；或点了选项 | 按 §3.3 |
| 核对 | 对照、核对、比对、对比、校对、更新、修正、纠正、改正、不对、不一致、补充、缺少、缺的、漏的、添加(前面不是「批量」)、补录、同步 | 「你想把它和系统里的……对照，更正不一致的、补上缺少的。」 |
| 录入 | 导入、录入、批量新增、批量添加、建档 | 「你想把里面的……批量录入系统。」 |
| 分析 | 统计、汇总、分析 | 「你想对文件内容做统计或分析；助手目前只看出文件是什么、有哪些列，不会逐行统计里面的数据。」 |
| 询问 | 是什么、什么文件、干什么、做什么用、怎么处理、能做什么、怎么办、有什么用 | 「你想知道这份文件是什么、能怎么处理。」 |
| 无 | 以上都没有 | 不写意图这一行 |

用户这次的原话里既有「统计」也有「对照、补充、缺少、添加」，核对排在分析前面，所以认成「核对」。

### 3.5 按权限给出去处

- **上传与识别**：任何能用 AI 对话的员工都能上传文件让助手识别(`capabilities.canUploadDocument` 恒为 true)；前端在只读会话里仍不显示上传按钮(上传会在服务端建任务)。
- **`workflow` 参数**：提交时、后台处理时、每次读取时三处都校验，必须是本人当前可用的单据，否则 403「当前账号没有这项业务的填写权限」。
- **可去页面**(`AiDocumentDestinations`)：一份固定目录，一行一页，共 18 页，路由是写死的固定路径，从不来自模型或文件。读者拥有这一页要求的**全部**权限才给，前端点之前再过一次与路由守卫同一份判断(`locationAllowedFor`)，通过后跳转并收起对话框。前端契约测试逐行解析这份目录，保证服务端给的页面前端路由守卫一定放行。
- **做不了的事项**(`blocked`)：只写中文原因，不出现权限码，例如「需要「员工档案编辑」权限，请联系管理员开通。」。分四类：
  1. 系统或助手确实做不到的(按文件类型和意图，例如「按花名册批量更正员工资料」)；
  2. 用户想做的下一步缺权限(只在意图需要时才列，例如想核对却没有编辑权限)；
  3. 这类文件对应的页面读者进不去；
  4. 文件本来能填的单据读者没有权限(只对认出类型的文件列，认不出的文件不列，免得一堆无关的「填不了」)。销售单据有权限但不在销售部门时说「只有销售部门的人员可以用助手填写销售单据，请联系管理员确认你的部门。」
- **每次读取按读者当前权限重算**：结果里存一份内部清单(这个文件能填哪些单据、固定的说明句)，读取时去掉内部字段，按读者**当前**权限重新生成选项、可去页面、做不了的事项和回答正文。本次之前保存的识别结果读取时提示「文件识别方式已更新，请重新上传。」(识别规则版本由 v2 升为 v3)。

花名册(核对或录入)的去处：

| 去处 | 读者需要的全部权限 | 缺了时的说明 |

### 3.6 如实回答

回答正文(`summary`，最多 1200 字)按固定顺序拼，只写服务端确定的事实：

1. **结论**：用途明确且出卡时「已识别为……。请在下面的确认卡里确认后，我再打开……并填入识别结果。」；规则认出的非填单类型「这是一份……，是从标题和列名(或：标题 / 列名)看出来的。」；模型推测见 §3.4；认不出「暂时没看出文件用途。」；文件有问题时说清是哪种(多种业务混在一起、多张发票、内容太多被截断、Word 版销售资料、与所选单据不一致)。
2. **结构**：「工作表「花名册」约 86 人，列有：姓名、部门、岗位、身份证号、手机号、入职日期。」——最多两张表，每张最多列 8 个列名，多了写「等 N 列」；人员类表格写「人」，其它写「行」。只有列名和行数，没有任何数据行的内容。
3. **意图**：见 §3.4 的表。
4. **能做到什么**：这类文件助手或系统做不到的事(§3.5 的表)，有对应权限时再加一句怎么办(如导入货品)。
5. **去处**：「可以去「员工档案」逐个核对、修改员工资料。」——只列读者能进的页面。
6. **其余**：有做不了的事项时「另有 N 项你暂时办不了，原因见下方。」；有选项时「需要填写单据的话，请在下面选要做的单据。」

只有真的发了卡才说「我再打开……」；不说「已保存」「已修改」。

本次花名册对只有「员工档案查看」权限的人事账号的回答(示例)：

> 这是一份员工花名册，是从标题和列名看出来的。
> 工作表「花名册」约 86 人，列有：姓名、部门、岗位、身份证号、手机号、入职日期。
> 你想把它和系统里的员工资料对照，更正不一致的、补充缺少的员工。
> 助手暂时还不能按花名册自动批量更正或补录员工资料，这次没有改动任何数据。
> 可以去「员工档案」逐个核对、修改员工资料。
> 另有 6 项你暂时办不了，原因见下方。

下面是「打开员工档案」按钮，和 6 行灰字(按花名册批量更正员工资料、修改员工资料、修改身份证号和手机号、新增缺少的员工、证件核对、办理入职，各带原因)。没有确认卡，没有选项。

### 3.7 花名册批量更正不在第一阶段

花名册 + 核对或录入的意图，第一阶段如实回答「助手暂时还不能按花名册自动批量更正或补录员工资料，这次没有改动任何数据」，并按权限给出员工档案、证件核对、办理入职三个页面。不读花名册的内容做比对，不发卡，不改任何员工数据。真正的核对与更正见 §八。

### 3.8 结果字段

`ERP_DOCUMENT_ROUTE` 读取结果新增 `typeSource`(本地规则 RULES / 模型推测 AI / 认不出 NONE)、`intent`(RECONCILE / IMPORT / FILL / ANALYZE / QUESTION / NONE)、`pages`(`[{key, title, route}]`)、`blocked`(`[{title, reason}]`)、`profile`(`{sheets: [{name, dataRows, columns}]}`，最多 8 张表 × 40 列，列名不超过 24 字，不含数据行的值)；`actions` 最多 1 张；提交参数新增可选的 `workflow`。完整契约与前端执行顺序见 [AI 平台接入指南 §8.7](../05-架构/AI平台接入指南.md)。

## 四、备选方案

| 方案 | 不采用的原因 |
|---|---|
| 只改对话框：确认卡改用 `context.go` 打开表单 | 只治 AI 这一处；外壳的判断仍然错，其它从主 Tab push 的入口照样坏。外壳改一处，全平台都好 |
| 保留「每个用途一张卡」，只把花名册加进识别 | 确认卡是一次性的确认，不是菜单；三张里两张注定要取消；认不出的文件仍然毫无说明 |
| 新增「对已识别的任务选用途」接口，不重新提交文件 | 识别任务结束时上传内容已清空，服务端拿不到文件；这条路只能出卡、不能重新识别，以后花名册核对也用不上 |
| 把整份表格(或前几行)交给模型判断类型 | 花名册、工资表里是姓名、证件号、手机号，违反 ADR-133 的最少必要与 ADR-153「个人信息不进提示词」。本地规则能认出常见表格，只把认不出的文件的结构交给模型 |
| 认不出就只说认不出，完全不用模型 | 用户要求「上传任何文件能够识别」；列名和值形状足以区分大多数业务表，又不含内容。没有 AI 权限或 AI 服务不可用时仍是这个退路 |
| 让模型直接决定去哪个页面、出哪张卡 | ADR-150：动作与去处只来自固定登记的清单；模型只回枚举 |
| 新增「AI 上传文件」权限码 | 识别本身不改任何数据；之后能做什么都由业务原有权限决定，沿用「零新增权限码」的做法 |
| 可去页面直接用对话里的页面说明目录 | 那份目录按路由规则匹配、每页只记一个权限，不是可以直接跳转的固定路径，也对不上前端路由守卫的组合权限；这里要「读者拿全权限才给」并与路由守卫逐条对上，所以单列一份一行一页的固定目录，由前端契约测试核对 |

## 五、安全与隐私

- **发给模型的**：只有 §3.4 列出的结构，在认不出或销售资料证据不足时发一次。不发任何数据行的值、文件名、文件本身和页面内容；像人名的表名、列名换成 #；用户的话里的长数字和邮箱换成 #。外送字段已登记在[中国大陆部署与兼容性 §2.3.1](../99-项目治理/中国大陆部署与兼容性.md)。
- **存下来的**：识别结果(`ai_jobs.result`，长期保存)只有类型、意图、固定说明句、表名、列名和行数，不存任何数据行的值；列名、表名里连续 3 位以上的数字和邮箱已换成 #，所以证件号、手机号存不进去。存储时不做人名替换：只有用户自己的文件把人名当成表名或列名时，人名才会出现在识别结果里，而结果只有上传人本人能读。
- **日志**：模型调用失败只记失败类别或异常类名，不记文件名、列名、提示词和模型回答。
- **权限在服务端**：提交、后台处理、每次读取三处校验；可去页面只给拿全权限的读者，前端跳转前再过路由守卫；确认卡仍是一次性、只能本人确认(ADR-150)。
- **文件里的文字不当指令**：用途只看用户自己的话和点选；模型的回答只能是枚举，提示词也写明不执行输入里的指令。
- **第一阶段没有任何写入路径**：对花名册不比对、不发卡、不改员工数据。

## 六、后果

正面：

- 从主 Tab push 的页面全平台都能显示(AI 确认卡、「我的」进编辑资料等)。
- 只管人事的账号也能上传文件；花名册得到如实的回答和能去的页面。
- 一个文件最多一张卡；认不出的文件有说明、有选项，不再甩出无关的卡。
- 新增 9 种文件类型的确定性识别，认不出的再按结构请模型推测。

代价与限制：

- 本次之前保存的识别结果要重新上传(规则版本 v2 升到 v3，结果格式变了)。
- 类型调整：工资表、库存盘点表、入库单 / 出库单的叫法变化见 §3.4。
- 点选用途会把文件再提交一次，算一个新的识别任务，计入每人每天的任务数和同时进行的任务数上限。
- 认不出的文件、本人有 AI 权限时多一次模型调用(只发结构，回答最多 200 个 token)。
- 人名替换靠姓氏表，是大幅减少而不是保证(生僻姓、外文名不在表里)；底线仍是「数据行的值一律不发」。
- 从主 Tab push 业务页时，`app_router.dart` 里四个主 Tab 的路由仍会建真实页面(工作台、通知、我的、设置)，所以被 push 的页面下面会多建一份该 Tab 页面：看不见、无害(庆典弹窗有一天一次的守卫)，但白建一次。以后可以让这四个路由返回空占位。
- 文件回答在刷新页面后不恢复(沿用 ADR-152，文件识别不进对话记忆)。

## 七、验证

实施时已跑(以实施记录为准)：

- 服务端定向测试(`-Dtest='AiDocument*Test,AiChat*Test,ArchitectureBoundaryTest,AiPermissionGrant*Test'`，`UTEN_RUN_DB_TESTS=true`)：39 个测试类 429 项，0 失败、0 跳过，含 5 个 Postgres 测试类。其中：
  - `AiDocumentProfilerTest`(11)：结构里从不带数据行的值；表名列名打码与截断；合并单元格的两行表头；表头下全是文字的第一行数据不会变成第二行表头；「键 值 键 值」登记表不当表头；泛词按同表其它列定义；值形状只是标签；每表最多 40 列；PDF / Word 的表头行。
  - `AiDocumentClassifierTest`：花名册、工资表、销售表互不混淆；人事类多表同族合并、花名册挨着报价单算混杂；货品、库存、银行流水按列认出；报价单里的名单小节不算混杂。
  - `AiDocumentIntentTest`：本次用户原话认成「核对」；空话无意图；全角文字规整。
