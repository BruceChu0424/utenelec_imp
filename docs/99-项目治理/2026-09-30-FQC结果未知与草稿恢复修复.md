## 根因与修复

原页面将包含网络超时的所有 `ApiException` 叫作“登记被拒”，且 400/422 会清除冻结体。共享草稿逻辑也会清除 pending 标记。此前已经丢失响应时，后一次拒绝只能说明后一次请求没有通过，不能证明原请求未提交。原检查单还把网络写入、草稿保存、刷新和导航置于同一失败处理，可能用已经递增到末尾的 `selected[done]` 读取错误行。

新流程按每个原命令维护 `notSent / rejected / unknown / confirmed`，继续兼容原 `completed`、幂等键与冻结参数:

| 事实 | 页面处理 | 草稿与下一步 |
| --- | --- | --- |
| 发送前本机持久化失败 | 明确显示本行未发送 | 可保留页面修复后重试；不宣称业务结果未知 |
| 首次收到可识别的应用拒绝 | 显示明确拒绝，允许修改 | 首次 400 BUSINESS/MALFORMED_REQUEST/VALIDATION_FAILED、422 VALIDATION_FAILED，以及已知权限/冲突响应按合同处理 |
| 超时、断连、500、无应用拒绝证据的 400 | 显示待核对 | 原键、原数量、处置和原因继续冻结 |
| 原请求已经未知，随后收到 400/422/403 等 | 继续待核对 | 后一次拒绝不清除原冻结体或 pending 标记 |
| 收到含决定事件 ID 与匹配任务 ID 的成功回执 | 立即标记已确认并取消勾选 | 先锁住成功行，再做本机保存、刷新和导航；本地收尾失败不变成业务失败 |

`FormDraftMixin.runFormDraftSubmission` 仅新增可选 `isDefiniteRejection` 回调。未提供回调的调用方保持原有 400/422/CONFLICT 分类，未顺带改变其他表单。FQC 按本行此前是否已有未知结果提供判断。首次明确拒绝后第二次本机保存出错时，仍保留已取得的拒绝事实，不把保存错误改写成未知业务结果。

两入口复用同一个行级发送方法。发送前由现有单写者草稿机制落盘完整冻结体和 pending 标记；是否进入网络闭包单独记录。成功后才更新 `completed` 与决定事件 ID。检查单失败处理不再按 `selected[done]` 反查错误行。

## 原命令恢复与业务边界

已只读核对主集成版本的 `ProductionFqcInspectionService.decide / recordDecisionLocked / normalizeRequest`: 当前请求先通过品质组织和审批权限，锁定原任务后按 `inspection_id + idempotency_key` 找决定事件并校验 `request_hash`，回放检查早于剩余数量判定。冻结参数继续使用原 `decide` 入口，未新增旁路命令、查询 API 或自动生成新键。

普通详情只展示任务当前状态，不能证明某个未知命令未曾提交。页面在失败后尝试刷新详情和办理能力，但 GET 仍待检、已无待检量、读取失败，都不会解除未知状态。需要继续时，使用者点击“核对并继续原提交”，看到只读的原数量与原因，再明确继续。服务端有原决定时返回既有结果，未登记时按同一原命令继续执行。

检查单有未知行与未发送行混合时，本次恢复只核对已勾选的未知行；确认框明确说明其他未发送行保留，核对完后再继续提交。每次仍逐行首错停止。已确认的原命令不再发送，但“本次命令确认”与“该检验任务全部完成”分开判断。

合法部分检验如报工 10、本次合格 3，在新鲜详情仍有待检 7 时生成新的办理内容与新键，默认不勾选；使用者明确选择/提交后才办理剩余数量。其它未提交行的原始数量、处置与选择状态继续保留，其它未知行保持原键原体。刷新失败时只显示本次提交已确认、待检状态尚未刷新，不显示整单已处理完成，也不开放基于旧数量的新命令。完成本机草稿前先取得新鲜状态，避免刷新失败后剩余数量被 finished 草稿阻挡。

本机每行仅保存当前命令、最近一条已确认命令的键/冻结参数/事件 ID，以及累计确认次数，不建立无限历史数组。滚动到新的剩余办理内容时，仅替换已经确认的上一条简要回执；任何未知或未发送项不做裁剪。长期决定历史以服务器 decision events 为准。

旧草稿只要仍有冻结体且未完成，一律按待核对恢复，不依赖新字段存在。即使最新详情剩余数量为 0 或已经取消，也保留原体供已有决定核对。旧稿原键缺失时不伪造新键执行。当前失去办理权限时保留原提交并只读显示；恢复权限后仍按原键原体继续。

若服务器成功回执已经到达，但本机存储随后不可写，当前页面仍锁住已确认行并显示本机保存问题。若进程在成功状态尚未落盘时终止，磁盘上的发送前草稿仍是保守的未知状态；再次打开只能恢复原键核对，不能承诺物理网络请求绝不重发。服务端原键回放承担“不再新增第二个业务决定”的合同。

## 账号、服务器与路由隔离

FQC 本页捕获原账号/代理身份、服务器和当前路由。检查覆盖:

1. 实际进入网络闭包之前再次检查，封住本机写盘 await 期间切换页面的窗口。
2. 检查单每一轮发下一行前再次检查，封住第一行确认后的 checkpoint 等待窗口。
3. 回执到达后与本地收尾后再次检查，禁止旧请求给新身份发成功通知或把新页面 pop 掉。

旧事务仍可在原服务器成功完成，测试明确允许这一事实；页面隔离控制的是后续发送与通知/导航归属。此逻辑只加在 FQC 本页，未扩大共享 mixin 的默认导航合同。

### 同一路由切换单据的追加复核

原 `app_router.dart` 两个 FQC builder 没有 child Key。本地锁定的 go_router 14.8.1 在 `match.dart:220/230` 用含 `:id` 的路由模板生成 pageKey，不能保证动态 ID 变化创建新 State。普通同身份在途退出会被现有 onExit 的 busy 检查拦住，这一合同仍保留；不能据此声称所有允许换单路径都安全。首次 GET 尚未注册草稿守卫、保存未知草稿后允许离开、身份改变后允许退出，均需要独立的单据 State。

实际 `app_router.dart` 与回归夹具共同使用两页面的静态 `route` factory，child 按 `(业务 id, draftId)` 设 Key，单笔继续传递原 `extra`，`DraftAwareGoRoute` 与 onExit 不变。未在旧 State 的 didUpdateWidget 中重载草稿 owner。页内响应 fence 另加捕获的业务 ID 比较，防御非路由调用意外复用同一 State。

8 个真实 GoRouter 用例覆盖上述四类情形的两个入口。旧无 Key builder 的对照开关仅存在于测试夹具，复现 6 项失败；busy onExit 对照的 2 项保持通过。新 factory 下全部通过，旧草稿 route、业务 ID、原体保持原归属，新单生成独立草稿，旧在途成功不产生新身份成功通知或后续行写入。`app_router.dart` 修改前两树 SHA 一致为 `1E2B9CB6E8A9F0E4966F8F6517EC2E880423EC6067FA8E4B8858377E2FC6E40C`，记录在 `document-identity-input.json`，主目录并行变化需要三方合并。

## 使用者说明

页面常驻显示已确认、明确拒绝、待核对、未提交数量及后续操作。未知行字段继续冻结，恢复弹窗不允许把新原因套到旧请求。检查单说明明确逐行登记与首错停止。

回放成功使用“原提交已确认，请以当前任务状态为准”，不会把原有决定说成本次新建。成功通知不再统一承诺仓库待最终点收。先入后检提示按已上架事实说明自动点收，普通单笔表单才说明合格部分待仓库点收；纯不合格与混合结论仍保留原处置合同。检查单空状态也不再把全部结果解释成新增的仓库待办。
