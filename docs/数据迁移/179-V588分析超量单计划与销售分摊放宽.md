# V588 分析超量下达：一张计划 + 销售分摊只认归需求量

- 迁移：`V588__analysis_surplus_single_plan_sales_allocation.sql`
- 类型：前向，只替换两个触发器函数体。**不加表、不加列、不改历史行。**
- 相关：[V577 下达车间超量与公共备货产出](169-V577下达车间超量与公共备货产出.md)、
  [V580 销售顶行公共备货计划对账](172-V580销售顶行公共备货计划对账.md)、

## 为什么要有它

2026-09-15 用户实测超量下达（需求 1000 实下 5000）后反馈两类「多余的单独列」：

1. **采购/委外申请明细**：同一颗料在申请单上拆成「生产需求精确备料 1000」与
   「主动公共备货 4000」两条，用户要的是一条 5000。
2. **车间计划**：销售订单来源顶层行超量被 V577/V580 拆成两张计划单
   （订单行 1000 + 无销售来源的公共备货行 4000），计划列表/车间任务页各占一行。

第 1 条由 Java 侧解决（`prepareExternalDocuments` 把需求片与公共超量片合成一条明细，
`markCreated` 把 `public_surplus_external_item_id` 指回同一条；锁定面不动——allocation
仍只分摊需求片、coverage 按 `requested_qty`、公共供给捕获走「需求件同件超量」口径）。
但合并明细的明细数量 = `requested_qty + public_surplus_qty`，与
`fn_guard_preplan_public_surplus_shape` 的「明细数量 == public_surplus_qty」校验冲突
（该守卫对「明细同时是 demand allocation 外部件」的共享形态虽然留了口，但 allocation
外部化受握手守卫强制**晚于** action 写入，共享识别在写入时序上永远来不及）。

第 2 条由 Java 侧取消拆单（与非销售来源同一形状：一张计划、link 记
`submitted_qty` + `public_surplus_qty`），但销售守恒链有三处假设「计划数量 == 销售分摊」：

- `ProductionPlanService.collectAllocations`：审核时按整行数量建 `plan_order_item_links`
  并回写订单 `planned_qty`——5000 会冲破「排产量 ≤ 订单未满足」；
- `ProductionExecutionPackageCommandService.persistSalesAllocations`：要求
  「执行分段总量 == 销售分摊总量」并把每段铺满；
- DB 断言触发器 `fn_assert_execution_segment_sales_allocation`：有销售 link 的段
  「分摊合计 = 段计划量」逐段相等。

## 改了什么

两个函数体补丁（V580 式形状断言纪律：取定义、锚点不中宁可失败；行尾统一归一 LF
——历史函数体 CRLF/LF 混杂，锚点匹配必须与行尾无关）：

1. **`fn_guard_preplan_public_surplus_shape`**：独立公共明细的合法数量补一个分支
   ——`明细数量 == public_surplus_qty` **或** `== requested_qty + public_surplus_qty`
   （合并明细）。身份校验（单据/货品/颜色/单位）、路由与叶子委外限制原样。
2. **`fn_assert_execution_segment_sales_allocation`**：计划明细挂着的分析计划关联行带
   `public_surplus_qty > 0` 时，「逐段分摊 == 段计划量」放宽为
   「计划件级 Σ有效段分摊 == min(Σ有效段计划量, link 容量合计)，且单段分摊不超过
   本段计划量」（有效段 = 未删除且非 CANCELLED/REVERSED；分批拆段后取消段连同其
   分摊一起退出合计）。**不带公共备货的计划件（全部历史计划）逐段相等口径一个字节不改。**

配套 Java（同批，非本迁移）：`collectAllocations` 对分析计划行按 link 的
`submitted_qty` 建销售分摊；`persistSalesAllocations` 按
`min(段总量, 分摊总量)` 依序分摊、分摊仍须精确消耗完。

## 兼容性

- V580 之前拆出的历史「两张计划」不动：纯公共备货 link 的明细不带销售来源，V580
  的放宽继续对历史行生效；`ProductionPlanService.validateAnalysisLink` 的
  `pureSurplusLink` 分支为历史行保留。
- 不加表、不改任何既有行；锚点替换失败时迁移以 23514 失败（宁可不迁不可盲改）。
