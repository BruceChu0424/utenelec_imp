## 〇、`E_` = 委外的判定与证据

[01] 老库总览曾把 `E_` 标为「疑似第二套销售/出口账套」（因为 S_/E_/T_ 三套结构对称）。本轮逐字段读触发器后**确认 E_ = 委外（外协加工）**，证据：

1. **典型委外物流闭环**：`E_SOut`（材料发料出仓，5 万明细）→ `E_In`（成品进仓收回，4 万明细）→ `E_WithDraw`（成品退）/ `E_SWithDraw`（材料退）/ `E_SWaste`（材料损耗）。销售 S_ 没有这套"发料—收回—损耗"流。
2. **`E_SOut` 明细无 `Price`/`Total`**（仅 `STotal` 成本额由触发器写）—— 材料按成本发出，**不是销售**。
3. **`E_SWaste` 损耗单**（损耗率 `WRate` + `Cause` 损耗原因）—— 销售无损耗单；委外因加工过程必然有损耗。
4. **`E_OrderCostItem`（委外订货的 BOM 自动展开）**—— 触发器 `TRI_E_OrderCostItem_Insert` 在 `E_OrderItem` 插入时按 `View_B_BomItem` 展开多级子件，正是委外"按成品 BOM 发料"的核心。
5. **命名 `E` = 外（外协）**；单据号前缀 `EC`（材料出仓）/`EJ`（进仓）/`ET`（成品退）独立成系。

> `T_` 仍是与 `S_` 对称的「未启用第二账套」（全 0 行），与 `E_`（委外）**不是同类**。这是 [01] 旧判定的修正。

## 四、触发器揭示的业务规则（设计金子）

老库把全部业务逻辑下沉到触发器（`biz_triggers.txt` 中 E_ 相关 **10 个触发器**）。委外的核心规则：

### 4.1 状态机驱动一切

所有库存/回写/成本联动，都由主表 `Status` 字段变化触发：

```sql
IF (@Status <> 0 AND @Status2 <> @Status)  -- 状态确实变了才触发
```

- `Status = 0`：草稿，**不产生任何业务影响**
- `Status = 1`：审核生效 → 入库增库存 / 回写上游 / 重算成本
- `Status = -1`（反审/红冲）：**反向冲销**（库存减、上游回减）
- `Status2` 记录「上一次状态」，用于判断状态迁移方向
- 触发器末尾 `UPDATE E_* SET Status2=Status WHERE ID=@BillID` 完成状态推进

> 新库语义保留：单据有「草稿 / 待审 / 已审 / 红冲」状态机，只有「已审」才驱动下游（同采购 [14] §4.1）。

### 4.2 全链路真 FK 回写（审核生效时）

10 个触发器中的 5 个（`TRI_EIStockItem`/`TRI_EOStockItem`/`TRI_ESStockItem`/`TRI_ESWStockItem`/`TRI_EWStockItem`）都做"沿真 FK 骨干回写累计量 + 追加单号串"两件事：

```
E_Order（订货审核）       ──SQID──▶ E_ApplicationItem：WQTY += 订货量, EWDrawNo 追加
E_In（进仓审核）          ──OrderID──▶ E_OrderItem：IQTY += 进仓量, EInNo 追加
E_WithDraw（成品退审核）  ──InID──▶ E_InItem：WQTY += 退量, EWTotal += 退额, EWDrawNo 追加
                         └─OrderID──▶ E_OrderItem：WQTY += 退量, SWDrawNo 追加
E_SOut（材料发料审核）    ──EOrderID─▶ E_OrderItem：OQTY += 发料量, ESONo 追加
E_SWithDraw（材料退审核） ──EOutID──▶ E_SOutItem：WQTY += 退量, WDrawNo 追加
                         └─EOrderID─▶ E_OrderItem：WQTY += 退量, ESWNo 追加
```

- 回写量按 `@QTY * @Status` 累加（`Status=1` 正向、`Status=-1` 反向扣减）。
- 单号串用 `replace(@No, @BillNo+' ', '') + @BillNo + ' '`（审核时追加，反审时 replace 移除）—— 老库用 varchar 拼接做"软关联 + 去重"。
- `E_InItem.STotal` / `E_SOutItem.STotal` / `E_WithDrawItem.STotal` / `E_SWithDrawItem.STotal` 在审核时由 `RefreshTotal_PROC` 重算（按当年当月成本）。

> ⚠️ `E_SWaste`（损耗单）**没有回写 `E_SOutItem` 的累计**（损耗触发器不在 dump 范围 / 老库未实现），损耗仅写库存台账。新库需补全这条链路（损耗 → 冲减发料单已发量）或显式说明损耗独立结算。

### 4.3 委外订货的 BOM 自动展开（`E_OrderCostItem`）

委外订货的核心特色（与采购 `P_Order` 的最大差异）：

1. **`TRI_E_OrderCostItem_Insert`（`E_OrderItem` INSERT 触发）**：当订货明细插入时，按成品 `GoodsID` 查 `View_B_BomItem` 一级子件 → 插入 `E_OrderCostItem`（`ParentID=0`, `DQTY=子件单用量`, `QTY=父件量×子件用量+0.46`，`+0.46` 是余量补正）。
2. **递归展开多层 BOM**（`while @BomStatus=1`）：以一级子件为新父件再查 BOM，循环插 `E_OrderCostItem`（`ParentID=上级 ID`, `Level` 由 `TRI_E_OrderCostItem_Level` 计算，**最深 30 层**）。
3. 若货品无 BOM，退化为插一条自身记录（`MGoodsID=GoodsID`）。
4. **`TRI_E_OrderCostItem_Update`（`E_OrderItem` UPDATE 触发）**：订货量改了 → 重展 BOM 或按 `QTY=DQTY×父件新量` 重算所有子件。
5. **`CheckChange_E`（`E_OrderCostItem` 触发）**：维护 `SQTY`（已出仓量）—— `if 任一子件 QTY>SQTY` 则父件 `SQTY=0`，否则 `SQTY=QTY`（即父件视为"全部发料"）。
6. **`E_SOut` 审核按 `BomItemID` 拆分消耗 `E_OrderCostItem.SQTY`**（见 §4.4）。

> 新库语义保留：委外订货单审核时**自动展开 BOM 到成本子表**；发料按 BOM 子件消耗；这是委外与采购的根本区别。新库上移到 Service 层事务实现，去掉触发器递归（性能 + 可测性）。

### 4.4 库存台账（StockGoods）—— 与委外强耦合

`E_In`/`E_SOut`/`E_WithDraw`/`E_SWithDraw` 审核直接写库存表 `StockGoods`（同采购 [14] §4.4）：

- **台账粒度**：`StockID + GoodsID + ColorID + Year`
- **按月分列**：`INQTY01..12` / `INWeight01..12` / `INTotal01..12`（入），`OUT*`（出）——写死 12 个月列
- **当前余额**：`QTY` / `Total`（且影响 `Year > 当前年` 的期初行）
- 单据→台账方向（`movement_type` 见 [18] §三）：

| 单据 | 触发器 | 库存方向 | 列 | movement_type |
|---|---|---|---|---|
| `E_SOut`（发料） | `TRI_ESStockItem` | 出库 `OUT* += 量`，`QTY -= 量` | OUTQTY月份 | **15** |
| `E_SWithDraw`（材料退） | `TRI_ESWStockItem` | 入库 `IN* += 量`，`QTY += 量` | INQTY月份 | **16** |
| `E_In`（成品进仓） | `TRI_EIStockItem` | 入库 `IN* += 量`，`QTY -= 量`（**反向**！） | INQTY月份 | **17** |
| `E_WithDraw`（成品退） | `TRI_EWStockItem` | 出库 `OUT* += 量`，`QTY -= 量` | OUTQTY月份 | **18** |
| `E_SWaste`（损耗） | （触发器未在 dump 内） | 出库 | OUTQTY月份 | **19** |

> ⚠️ **关键发现**：`E_In` 进仓触发器写 `QTY = QTY - @Status*@QTY`（**减**），与销售进仓 `+` 相反！这是老库"成品收回冲减发出数"的逻辑（委外成品收回 = 从发出材料里"销账"）。新库 movement_type 17 仍按 `direction=+1`（成品入库增加库存），老库这个反向逻辑**不照搬**，仅做流水事件记录；新库余额由 stock_balances 独立维护。

> 同采购，**E_SOut/E_SWithDraw 明细的 `BomItemID` varchar 串**触发器开 `inv_E_SOut2` 游标 + `f_split` 拆分，逐个 ID 减 `E_OrderCostItem.SQTY`（已出仓量累加），即"按 BOM 子件消耗订货量"。这是性能重灾区（5 万明细 × N 子件）。

### 4.5 结案标志（Fulfill）

`CF_E_Order` 触发器（`E_OrderItem` UPDATE）：明细增删改后，若主表下所有明细的剩余量 ≤ 0，则 `E_Order.Fulfill=1`（结案）：

- 订货单：`QTY - IQTY + WQTY <= 0`（全部已进仓，扣除已退）
- 或 `QTY = 0`

### 4.6 全局开关

所有触发器开头判断 `(SELECT ISplan FROM SystemAccinfo) = 1`——「是否启用生产计划/成本联动」全局开关。新库无需此开关，逻辑显式化（同采购）。

## 七、归属部门建议

总路线图 [18] §1.2 / §七"待确认"列了 `DEPT_SALES` vs `DEPT_OUTSOURCE` 二选一。本文档**建议 `DEPT_SALES`**，理由：

1. **数据强共享**：委外商 `VendID` 与销售客户、采购供应商共用 `B_Provider` 主档；综合营销部已管理供应商关系，委外归属可天然对齐。
2. **业务流程耦合**：委外订货 `E_Order` 与销售订货 `S_Order` 结构同构（连触发器都对称）；委外出货报表常与销售出货合并查看（综合营销视角）。
3. **避免新部门**：当前 `departments` 表已有 `DEPT_SALES`、`DEPT_PMC`、`DEPT_PROD`、`DEPT_FIN`、`DEPT_HR` 等，新增 `DEPT_OUTSOURCE` 仅当委外数量足够大、需独立权限隔离时才值；当前委外单据量（1 万主表）小于采购，独立部门成本 > 收益。
4. **权限粒度**：新库权限按部门 + `feature_key` 控制（V43 已落地），`subcontract_*` 单据的 `edit` 权限可以只给综合营销部特定角色，不需要新建部门来隔离。

**待 bruce 终定**：若未来委外业务扩展（自有外协车间、独立核算），可后续追加 `DEPT_OUTSOURCE` 并迁移权限组，无返工成本。

## 八、老库设计的核心问题（新库要解决的）

1. **业务逻辑全埋在触发器**（10 个 E_ 触发器 + `RefreshTotal_PROC`）：合计、库存、BOM 展开、回写、损耗全部下沉 → 换库即丢失、不可测、不可审计。新库上移到 Service 层事务。
2. **多值字符串溯源**（`BomItemID`/`EOrderNo`/`EInNo`/`ESONo`/`ESWNo`/`SWDrawNo`/`EWDrawNo`/`WDrawNo` varchar + `f_split` 游标回写）：性能（5 万明细 × N 子件游标）与正确性双输。新库用单值 FK 骨干 + `source_doc_no` 文本占位。
3. **BOM 自动展开用递归触发器**（`TRI_E_OrderCostItem_Insert` 的 `while @BomStatus=1`，最深 30 层）：每次订货明细插入都全展 BOM，**写放大严重**。新库改为审核时一次性展开 + 缓存到 `subcontract_order_bom` 表。
4. **按月分列库存台账**（`INQTY01..12` / `OUTQTY01..12` 写死）：跨年复杂、扩展僵化。新库用 `stock_movements` 流水 + `stock_balances` 余额。
5. **`E_In` 进仓减库存的反向逻辑**（`QTY -= @Status*@QTY`）违反直觉，是老库特有"冲销发出"模型 —— 新库统一按 `direction=+1`（movement_type 17）记流水，余额由独立结算。
6. **状态字段冗余混乱**（`Status`/`Status2` + `Fulfill`/`Stop`/`Cancel` + `CStatus` + `LStatus`）：多套体系并存。新库用枚举 + `is_closed` 派生。
7. **十几个语义模糊的数量列**堆在一行（`QTY`/`IQTY`/`OQTY`/`WQTY`/`CQTY`/`OrderQTY`/`FlagQTY`/`STQTY`/`SWQTY`/`FQTY`/`DQTY`/`SQTY`）：新库只留单据原生量 `qty`，累计量（已进/已发/已退）按需从下游聚合或专门回写表。
8. **`float` 存数量金额**（`QTY float`）：精度风险。新库用 `numeric`。
9. **损耗单 `E_SWaste` 未回写发料累计**（触发器缺失或不完整）：委外损耗与发料脱钩。新库补全"损耗→冲减发料已发量"链路。
10. **`E_OrderCostItem.QTY = 父件量 × 子件用量 + 0.46`**（硬编码 +0.46 余量补正）：业务规则藏在 SQL 里、魔法数字。新库规则化（`waste_allowance` 字段或独立损耗率配置）。
