# ADR-111 主档删除引用保护、BOM 报错定位与批量原子命令

- 状态：已接受(2026-09-23，V683/V684，零新增权限码；同日第二轮评审修复见 §六)
- 关联：审计发现 dup-frontend-split-03 / dup-frontend-split-06 / correctness-stability-14，
  2026-09-22「删了还在 BOM 里的组件」事故
- 涉及：`features/master/lifecycle/*`、`GoodsBomPasteService`、`GoodsBomService.deleteAll`、
  `MaterialAnalysisBomSnapshotReader`、分类级联删除与导入撤回；前端 `MasterEntityDetailPane`、
  `showUtenMasterPicker`、`UtenHierarchyTreeView`

## 一、背景

2026-09-22 超管在货品资料里删掉了组件 V40001-dy「V4开关底衬(电镀铂银)」，它还是 V4ZJ005
「V9开关面框组件(铂银)」有效 BOM 行的组件。货品删除只做 `is_deleted=true`、不查任何引用，
于是所有 BOM 树里含它的成品在物料分析准备页一律报 409「BOM 存在非正用量、失效组件、
颜色或基本单位异常」——既不说哪一行、哪个组件，也不说为什么，用户无从修。

排查同时看到同一根因的几种形态：

1. 颜色、单位、仓库、客户、供应商、模具的删除同样只是一行软删；物料分类删除还会把整棵
   子树的货品一条 UPDATE 批量软删，完全绕开任何检查；货品导入撤回同理。
2. 批量启停/删除在前端逐条循环调单条接口：选 100 条客户就是「GET 详情 + PATCH 状态」
   200 次串行请求，失败 `catch (_)` 吞掉，只报「N 个跳过」。
3. BOM「粘贴组件」由前端逐条删除现有行、再逐条新建，失败静默跳过，BOM 可能半新半旧；
   物料分析与 MRP 直接以 BOM 为输入，错一路传下去。组装信息页签的跨层批量删除也是按
   父件分组、每组一个事务。
4. 四张分类主档页的右侧明细区、客户/供应商选择器、分类树/部门树各复制一份，上面这些
   循环也跟着复制了四份。

## 二、同行做法(共识)

金蝶、用友的基础资料「被业务单据或其它资料引用时不允许删除，只能禁用」；SAP 物料删除
走「删除标记 + 归档前的使用检查(BOM where-used、未清单据、库存)」；Odoo 的 BOM 行对组件是
必填外键，被引用的产品不能直接删除、只能归档。共识是：**删除前由服务端查引用、有引用就
拒绝并告诉用户去哪里解除；需要保留历史的一律停用而不是删除**。本 ADR 按这个共识落地。

## 三、决策

### 1. 服务端权威引用检查(MasterReferenceGuard + MasterReferenceCatalog)

一次查询给出一批记录各自被谁引用(每类最多列 10 个样例 + 总数)，拒绝原因用中文大白话写
「被谁用着、怎么解除」。**查哪些表不靠人记**：`MasterReferenceCatalog` 是一张引用目录，库里每一个
指向七种主档的列，要么登记为引用(带「什么状态算还在用」的口径)，要么登记为豁免(带理由)；
`MasterReferenceCatalogCoverageTest` 在迁移后的真库上把「全部指向主档的外键列 + 按命名约定
(`…goods_id` / `…color_id` / `…warehouse_ids` 等)却没有外键的 uuid 列」与目录逐列对账，
新加一张引用主档的表而没归类，测试直接失败并点名该列。2026-09-23 实测：305 列，224 列登记引用、
81 列登记豁免。

| 类别 | 在办口径(命中即挡住删除) |
| --- | --- |
| 主档互引 | 有效货品的颜色/单位(基本、厚度、重量、默认采购价/委外价的颜色与单位)/所属仓库/专属客户/默认与备选供应商(含默认采购价/委外价供应商)/模具；货品计量采集设置的业务单位与实重单位；有效父件的有效 BOM 行(组件、行颜色、行默认供应商)；下级仓库；单位换算基准 |
| 订单类单据(表头 + 明细) | 销售订单、请购、采购订单、委外申请、委外订单、生产计划(含母件列)：未删除、未结案、未红冲(生产计划另加未取消) |
| 过账类单据(表头 + 明细) | 出货单(另排除作废/冲回)、销售退货、其它出货、报价、采购收货、采购退货、委外询价、委外收货、委外退货、委外损耗、委外发料、委外退料、生产日报(另排除作废)、收款单(含明细客户与代收供应商)、付款单(含明细供应商)：未删除、未结案、草稿；出入库单另加「领料部分出库未出完」 |
| 在办流程 | 到货预期 OPEN；到货异常未过账/关闭/取消；来料检验、成品检验、退货质检未检完；来料不合格退货/索赔未办完；生产任务段未完工、生产用料未领完、排产包/排产草稿仍有效(均要求计划在办)；委外发料计划未发完(订单在办)；委外损耗、委外短交未处理完；研发任务未完成 |
| 物料分析 | 进行中的分析(主仓、参与仓)及其来源行、物料行、借料、备料动作、委外自制任务、改派、委外交接 |
| 往来 | 未结清的应收(客户)/应付(供应商)、未收回的供应商索赔款、未对完的供应商对账 |
| 库存 | 非零库存余额、未释放的库存预留 |

豁免四类(目录里逐列写明)：流水/事件/快照(库存流水、放行与仓库作业事件、已完成的核销、
计量采集证据……)、老库迁移只读记录(老库成本展开、计量迁移异常……)、主档自己的附属设置
(客户收货地址、可见人授权、仓位偏好、父件自己的组装清单……)、已由另一处覆盖(库存成本池跟着
库存余额、退料申请本身就是出入库单、返工授权跟着生产任务)。

SQL 全由目录常量拼成(表名、列名、状态值都是白名单)，唯一的绑定参数是逗号拼接的 UUID 串，
批量 500 条也只绑两个参数、一条语句。**样例按调用人的可见范围过滤**：每段 SQL 同时返回标签的
归属人与可见范围(`public` / `goods` / 单据模块的归属范围名)，看不到的只计数不展示
(「共 N 处(你没有权限查看明细…)」)，删除照样被拒，不借删除报错泄露别人的单号或货品。

### 2. 删除、批量启停、批量删除共用一条写路径(MasterLifecycleService)

- `SELECT … FOR UPDATE` 按 id 顺序锁住本批 → 逐条对象级授权(客户按负责人范围，货品按
  归属人范围开关)与乐观锁版本(货品/客户/供应商，列表行带 `version`)→ 删除再过一遍引用检查
  → 一条 `UPDATE` 写入全部放行的记录。批量逐条返回 `{id, label, ok, reason}`，部分成功照常
  提交；单条删除失败直接 409 + 原因。
- **删父件连带软删它自己的 BOM 行**(同一事务、先于货品本身)。
- **同批一起删的父件与组件按不动点放行**：父件对组件的 BOM 引用先记为内部边；只有父件因别的
  原因删不成时，组件才跟着删不成——否则父件留下、组件被删，正是事故的形状。不动点只在
  「删不成的货品集合」上迭代(只增不减、上限是本批条数，必然收敛)，样例与总数在收敛后一次拼好
  (外部父件的 SQL 总数 + 删不成的同批父件个数)；第一轮实现把截断过的样例列表拿来判「有没有变化」，
  一个组件有 10 个以上父件时会死循环并攥着整批 FOR UPDATE 锁，已在第二轮修掉。
- 物料分类、模具分类的级联删除，以及货品导入撤回，都改走这条路径：子树里任何一个货品/模具
  还被引用，整个分类一条都不删并列出前 5 个原因；导入撤回另查「本批新建的分类下后来加了
  批外货品」。
- 端点：`POST /api/master/{goods|colors|units|warehouses|clients|suppliers|moulds}/batch-status`、
  `…/batch-delete`(上限 500 条)，单条 `DELETE /api/master/{…}/{id}` 也移到这里。每个主档一个
  显式映射，权限点沿用各自的 `X:status` / `X:delete`，零新增。

### 3. 数据库兜底(V683/V684)

只防绕过服务的旁路写入，取最硬的三条：货品仍是有效父件的有效 BOM 行组件时不能软删；颜色
仍被有效货品或有效 BOM 行指定时不能软删；单位仍被有效货品当作基本/厚度/重量单位时不能软删。
触发器 `BEFORE UPDATE OF is_deleted … WHEN (NEW.is_deleted AND NOT OLD.is_deleted)`，
报 23514。服务端删父件先删自己的 BOM 行，所以同一条 UPDATE 里父件与组件的处理顺序无关。

V683 第二轮把颜色/单位两条闸补上货品的默认采购价/委外价的颜色与单位列；三条闸的 23514 由
全局异常处理映射成大白话(不再落成「数据已被其他操作更新」)。

**V684 分类删除与「往分类里加东西」互斥**：删除一方先对子树分类行 `SELECT … FOR UPDATE`(物料/
模具分类另外先拿层级锁，并在锁后重读子树)；新建货品/挪货品(新触发器)、新建客户/供应商/模具
(既有 `fn_assign_uncategorized_master_category` 的「分类未删除」读改为 `FOR KEY SHARE`)、新建或挪动
子分类(新触发器)都对目标分类 `FOR KEY SHARE` 读一次「未删除」。删除先拿锁，加东西的一方等它提交
后看到已删除而拒绝；加东西先拿锁，删除等它提交后才读子树里的货品，新货品自然在检查范围内。

并发窗口：删除命令对被删记录 `FOR UPDATE`；BOM 新增/改行/粘贴在读之前先按 id 顺序对父件与
组件 `FOR KEY SHARE`(`GoodsRepository.lockForReference`)。两者互斥：删除先拿锁，BOM 写入等它
提交后读到「已删除」而拒绝；BOM 写入先拿锁，删除等它提交后做引用检查、看到新行而拒绝。
KEY SHARE 与数量单位锁的 NO KEY UPDATE 不冲突，平时建 BOM 不因此串行。

### 4. 物料分析 BOM 报错点名到行

`MaterialAnalysisBomSnapshotReader` 的图校验保持一次往返、同样的判定口径(循环、超过十层、
用量不大于 0、组件已删、组件无基本单位或单位已删、行/组件颜色已删、老系统颜色未对应)，
但不再只回一个布尔：按「问题 × 父件 × 组件」去重返回违规行，报错列出前 5 条——
「成品往下第 N 层，父件 → 组件：原因。怎么修」，并给出总处数。

### 5. BOM 粘贴与跨层批量删除改为服务端原子命令

- `POST /api/master/goods/bom/paste`：`{mode: REPLACE|APPEND, targets:[{goodsId, expectedItemIds?}], items:[…]}`，
  1~50 个目标、200 行。先把全部目标与行校验完(存在/停用/占位、组件是否目标自身、粘贴清单内
  重复、追加模式与现有重复、用量/阶段/计量方式/硬门槛/颜色/供应商、成环、目标已被他人改过)，
  **任何一处不合格一条都不写**，409 + `fieldErrors` 逐条写「第几行 哪个组件：为什么」；全部合格
  才在一个事务里替换或追加，写入中途数据库拒绝也整体回滚。成环检查把新边加到现有组装图上
  (替换模式先摘掉目标旧边)按层批量下探，不逐节点查。
- `expectedItemIds` 是页面读到的目标现有组件行，作为乐观锁；替换还要 `goods:bom:delete`。
- `POST /api/master/goods/{id}/bom/batch-delete` 允许勾选横跨组装树多层：服务端一条查询取回全部
  仍有效的行与父件、按层批量核对每行父件都在 `{id}` 的组装树里、一条 UPDATE 软删(实际删掉的条数
  对不上就整批回滚)，一次请求、一个事务，每个受影响父件只重算一次材料合计；语句数与勾选条数无关。
- 组装信息页签的「添加组件」同样走 `paste`(APPEND，目标 = 所选父级)：勾多个组件一次请求、整批
  原子，被拒时逐行原因留在弹窗里；前端仓库接口里已删掉逐条新建/删除组装行的方法，想循环也调不起。

### 6. 前端去重

- `MasterEntityDetailPane<TItem, TDetail>`：分类信息卡 + 标题/搜索/添加 + 表格(筛选/排序/
  分页/多选/前导分组)+ 打印导出 + 行启停(单条窄命令，带列表行版本、不再先拉详情)+ 行删除/
  批量启停/批量删除(服务端批量命令，结果经 `showMasterBatchOutcome` 逐条展示原因，失败行
  保留勾选)。客户/供应商/模具/货品四页只剩配置与特有动作(客户负责人/可见人、模具详情弹层与
  车间树、货品复制粘贴与组件信息)。
- `showUtenMasterPicker<TItem>` + `UtenMasterPickerField<TItem>`：客户/供应商选择器与表单字段
  缩成几十行的配置封装，保留原函数名与构造参数。
- `UtenHierarchyTreeView<T>`(shared)：分类树与组织架构树共用一份实现，`UtenCategoryTreeView`
  / `UtenDepartmentTreeView` 成为薄封装(层级徽标、行文字、公司根透传、编码排序以参数给出)。
- 颜色页批量启停/删除同样改为批量命令；货品粘贴(新建副本)仍是逐个保存，但失败逐条展示原因，
  不再吞掉。

## 四、实测(Testcontainers 真库，MasterDataIntegrityEndToEndTest / MasterReferenceCatalogCoverageTest)

| 场景 | 改造前 | 改造后 |
| --- | --- | --- |
| 批量禁用 100 个货品 | 200 次请求(每条 GET 详情 + PATCH)，服务层 1099 条 SQL，3415~6393 ms(五次实测) | 1 次请求，3 条 SQL(绑定会话变量 + 锁行 + 一条 UPDATE)，100~235 ms；审计行 99 条(与逐条一致，1 条因版本过期被拒) |
| 替换粘贴 4 个组件到 1 个货品 | 1 + 3 + 4 = 8 次请求，任一步失败即半新半旧 | 1 次请求 16 条 SQL(含并发锁)，整批原子 |
| 组装信息跨两层勾选删除 | 每个父件一次请求、各自一个事务 | 1 次请求、一个事务 |
| 同批删父件 + 组件，组件另有 11 个外部父件(第二轮) | 死循环，攥着整批 FOR UPDATE 锁不放 | 3 条 SQL、95~318 ms 返回，组件原因「等共 12 处」 |
| 组装信息页签展开一层(第二轮) | 5 个组件 18 条 SQL、30 个组件 76 条(按组件逐个懒加载与查可见性) | 两者都是 4 条 |
| 追加 1 个组件并重算材料合计(第二轮) | 已有 5 个组件 18 条、30 个组件 51 条 | 两者都是 11 条 |
| 组装行批量删除(第二轮) | 逐行 findById + save 2N 条起步，外加重算 N+1(只改删除、未改重算时删 10 条剩 50 条实测 59 条) | 删 10 条 9 条 SQL、删 50 条 8 条，与勾选条数无关 |
| 引用目录对账(第二轮，MasterReferenceCatalogCoverageTest) | 手工挑了 8 类单据，漏应收应付、草稿退货、委外发料等 | 305 列逐列归类(224 引用 + 81 豁免)；每种主档一条检查语句(货品/颜色 48 段、单位 49、仓库 39、供应商 30、客户 10、模具 1)，空库上单次 26~77 ms(含解析规划；首条含连接预热约 345 ms) |

## 五、影响与边界

- 零新增权限码、零新增表；迁移 V683 只新增三个函数与三个触发器；V684 新增两个函数与十条触发器，
  并 `CREATE OR REPLACE` 既有 `fn_assign_uncategorized_master_category`(只多一把 KEY SHARE 锁、错误码改 23514)。
- 列表 DTO：货品/客户/供应商列表行新增 `version`，供应商列表行新增 `status`(行菜单直接显示启用
  或禁用、行底色按状态)。
- 被取代并删除：`GoodsService/ColorService/UnitService/WarehouseService/ClientService/
  SupplierService/MouldService.delete`、`MaterialCategoryRepository.softDeleteGoodsByCategoryIds`、
  `MouldRepository.softDeleteByCategoryIds`、四页各自的 `_DetailPane`、两份选择面板与两份树实现；
  第二轮再删前端 `GoodsBomRepository.create/delete`(逐条新建/删除组装行，已无调用点)。
- 不做存量回填：已经存在的「有效 BOM 挂着已删组件」脏数据由物料分析报错点名后人工修正
  (2026-09-22 的一条已由主线程按审计镜像恢复)。

## 六、第二轮评审修复(2026-09-23)

| 评审点 | 处理 |
| --- | --- |
| blocker：同批删除不动点在组件有 10 个以上被挡父件时死循环 | 改为在「删不成集合」上迭代，收敛后一次拼样例与总数；`MasterReferenceGuardFixedPointTest`(10 外部 + 1 同批、11 个同批、三层链、全放行、样例按可见范围过滤)与真库用例「一个组件被 12 个父件挡住」30 秒超时内返回，实测 3 条 SQL |
| major：引用保护只覆盖部分在办业务 | 引用目录 + 真库逐列对账测试(见 §三.1)；真库用例覆盖草稿销售退货挡货品、未收完应收挡客户、草稿采购退货挡仓库与供应商 |
| major：「添加组件」仍逐条新建、吞错 | 改走 `paste`(APPEND)，组件测试断言只发一次请求、被拒原因逐行显示 |
| minor：组装行批量删除逐行 findById + save | 改为一次取行 + 一条 UPDATE；顺带把组装行列表与重算材料合计的按组件懒加载改为一条语句取齐(EntityGraph + 批量「有无下层」查询 + 可见性一次判定) |
| minor：拒绝原因泄露看不到的单号/货品 | 样例按可见范围过滤，只计数 |
| minor：分类级联删除与新增/挪入的并发窗口 | V684 + 服务端锁子树(见 §三.3) |
| minor：V683 的 23514 落成通用文案 | 全局异常处理映射大白话(含 V684 三条) |
| minor：迁移头未同步 | 按工作流约定由主线程合并时统一改(README 头行与表格、清库白名单、两个契约测试、migrationsExecuted) |
